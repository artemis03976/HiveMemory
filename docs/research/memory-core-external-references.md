# 记忆核心的外部参考

## 0. 研究问题、来源与范围

本文汇集 v0.8 记忆核心重新设计时参考的外部项目与文章，2026-11-16 从[记忆核心总纲](../ideas/memory-flow-short-to-mid-term.md)原第 8 节移出：外部事实与横向比较留在这里，对 HiveMemory 的启发与候选设计留在 Ideas（总纲第 3 节与各子文档）。

- **研究问题**：其他记忆系统由谁决定记什么（被动提取与主动写入）、怎样保存与组织、怎样维护与评估。
- **来源与取证**：第 1 节依据 DeeperResearch 工作区（不在本仓库）中八个项目的调研报告，不是各项目的源码；第 2、3 节依据 VCPToolBox 的调研与对其源码（基线 `73fd165`）的只读核实；第 4 至 6 节依据公开文章、仓库说明、演讲材料与论文摘要，阅读日期见各节。
- **限制**：报告与文章中的数字来自各自的评估，只作方向参考；只读了摘要或没能核实的部分在各节注明。

## 1. 八个项目的两类写入路径与保存形态

依据是 DeeperResearch 工作区（不在本仓库）中八个项目的调研报告：mem0、Hindsight、EverOS、spatial-memory-engine（SME）、BaiShou-Next、VCPToolBox、dsh-agent-soul、gliding_horse。2026-11-14 按"谁决定记什么内容"重新整理。结论来自报告，不是各项目的源码；mem0 的命令行与集成、EverOS 的 MCP 适配器、Hindsight 的集成不在报告范围内，下表中的"没有"只表示报告里没有看到。

**归类**

分类的界线是谁决定内容，不是谁发起调用：Hindsight 的 `retain` 可以由 agent 经 MCP 或 hook 调用，但记什么由服务端的提取决定，仍归为被动。

| 项目 | 被动提取 | 主动写入 |
|:---|:---|:---|
| mem0 | `add()`：LLM 从对话中抽出事实句 | 没有 |
| Hindsight | `retain`：服务端 LLM 分块抽取事实 | 没有单独的通道 |
| EverOS | `/add`：LLM 判断边界切出 memcell，再产出 episode 与 agent case | 没有 |
| SME | 模块 01（默认关闭）：逐条消息抽取原子事实 | 没有 |
| BaiShou-Next | 没有 | 日记技能、`memory_store`、`graph_upsert` |
| VCPToolBox | 只记录原始发言，不产生可检索的记忆 | DailyNote 写日记、整理日记 |
| dsh-agent-soul | 压缩上下文时产出指回原文的摘要 | 账本 |
| gliding_horse | 每轮机械归档，不做取舍 | `create_skill`，没有接通 |

gliding_horse 与 dsh-agent-soul 的被动路径不判断值不值得记，下面的被动类只指前四个项目。

**被动提取类（mem0、Hindsight、EverOS、SME）**

- **共同点**：
  - 产出单位都很小：mem0 是 15～80 词的自包含事实句；Hindsight 是一句"什么 | 何时 | 何地 | 涉及谁 | 为什么"；SME 与 EverOS 是原子事实。
  - 都标出记忆来自哪一方：mem0 的 `attributed_to`，Hindsight 的 world 与 experience，EverOS 的用户轨与 agent 轨，SME 的 `source`。
  - 提取时只追加，基本不处理与已有记忆的关系：mem0 只按 md5 精确去重（它曾在写入时让 LLM 裁决增删改，后来改为只新增）；Hindsight 与 EverOS 写入时不查重；SME 只有余弦相似度 ≥0.92 就丢弃的规则。与已有记忆的协调推迟到后台（Hindsight 的 consolidation、EverOS 的 reflection、SME 的 consolidate），或者不做（mem0 开源版）。
- **差异**：
  - 提取哪一方：SME 只记用户的话，避免把模型自己说的再记回来；mem0 两方都抽，产出同一种事实；Hindsight 两方都收但分成两种事实（用户的偏好、规则与纠正是 world，agent 的动作与决定是 experience）；EverOS 两方分成两种产物（每个用户各一条 episode；agent case 从助手消息与工具调用中产出，先经过筛选）。
  - 怎样切分材料：SME 逐条消息；mem0 每次调用；Hindsight 每次调用再按约 3000 字符分块；EverOS 让模型判断最后一段是否讲完，没讲完就留在缓冲里，并且明确不按 token 数或时间收尾。
  - 提取时看不看已有记忆：mem0 看向量最相似的 10 条；Hindsight 不看，到 consolidation 才看相近的 observation。
  - 取舍标准：Hindsight 问两次，时间尺度不同（提取时"六个月后还值得回忆吗"，沉淀时"一个月后还值得知道吗"）；mem0 拿不准就抽；SME 用规则丢掉情绪、短句与闲聊；EverOS 的 episode 不设门槛。
  - 原文证据：Hindsight 与 EverOS 保留原文并挂指针；mem0 的记忆没有证据链接。

**主动写入类（VCPToolBox、BaiShou-Next、dsh-agent-soul）**

- **共同点**：
  - 取舍规则写在给 agent 的说明或技能里，不在处理流程里：VCPToolBox 的日记说明书要求"一事一记"；BaiShou-Next 的日记技能只追加日记里还没有的事实，并用"半年后还重要吗"决定详略；dsh-agent-soul 的账本规定了八种类型。
  - 写入只追加，写入时基本不检查。例外是 BaiShou-Next 的 `memory_store`：相似度大于 0.92 直接跳过，在 0.70～0.92 之间由对话模型判断跳过、合并还是新建，合并时给旧条目留墓碑、另写一条新的。
  - 避免重复主要靠写的人自己看得到相关的已有记忆：VCPToolBox 每轮把已有日记注入上下文；BaiShou-Next 写日记前先读当天的日记。
  - 作者署名由写的人自己填，没有验证。
  - 之后的整理也交给 agent 或人；系统自动的加工只有 BaiShou-Next 从日记抽取关系图，输入是日记而不是对话。
- **差异**：
  - 谁决定什么时候写：VCPToolBox 由 agent 自己决定，没人看着的定时请求里也会写；BaiShou-Next 由用户要求，应用内的写入需要用户确认，对外的 MCP 则自动放行。
  - 产出单位：VCPToolBox 是一篇日记一个文件；BaiShou-Next 是按发生时间插进日记的段落，或单行记忆、图谱的边；dsh-agent-soul 是一行带类型的账本条目。
  - 类型：dsh-agent-soul 有八种，其中"搁置""承诺""线索"表示工作状态；VCPToolBox 只有 Tag。
  - 状态怎样改变：VCPToolBox 可以替换文中的一段；BaiShou-Next 从不改旧文；dsh-agent-soul 没有"关闭"类型，未完成的条目只增不减，它的文档自己承认这是缺陷。
  - 内容取向：BaiShou-Next 的技能偏生活与关系，原话、态度与情绪写详细，代码改动只写一两句结论；dsh-agent-soul 的账本类型偏工作。

**两类之间**

- "用户说的"与"agent 做的"是在每条路径内部区分的，不是两条路径各管一方：被动类里 Hindsight 与 EverOS 从同一次提取中分出两方的产物；主动类里 BaiShou-Next 的伙伴写日记，记下的主要是用户的原话与态度。
- 只有 dsh-agent-soul 同时有两类路径：压缩摘要进入索引，账本单独存放，两者写入时互不可见，只在读取时合并、标注来源，冲突时以原文为准。没有一个项目在写入时协调两类路径。
- 结构多出现在派生层：Hindsight 的 observation 按"单主体、单侧面"组织，另有 mental model 文档；EverOS 给每个用户合成一份 `user.md`，技能写成 `SKILL.md`。用户偏好单独成层的有 EverOS（`user.md`）、dsh-agent-soul（`USER.md` 与 `SELF.md`）与 BaiShou-Next（手写的身份卡）；mem0 开源版是反例，偏好与其他事实一样平铺。

**保存形态**

- **以文本文件为真相**：EverOS（Markdown 是唯一真相，系统状态存于 SQLite，检索索引可以整份重建，用户手改文件后按内容哈希重建索引）；BaiShou-Next（主记忆是日记 md）；VCPToolBox（一篇日记一个 txt 文件）；dsh-agent-soul（`SELF.md`、`USER.md`、账本与会话日志）。主动写入类都在这一组。
- **以数据库记录保存**：mem0、Hindsight、SME、gliding_horse，但单位只是一句文本加元数据，并不比文本更丰富。
- 八个项目中没有一个定义了比文本更丰富的内容格式。
- Claude Code 的原生记忆（不来自调研报告，来自它自身的记忆机制）：每条记忆一个 md 文件，frontmatter 有名称、一句描述与 user、feedback、project、reference 四种类型之一，正文之间用 `[[名称]]` 链接；`MEMORY.md` 是索引，一行一条指针，每次会话载入它的开头部分（前 200 行或 25 KB 以内，见第 4 节），具体文件用到时才读。写入用普通的写文件工具，写之前由 agent 自己检查有没有已经覆盖它的文件，另有整理技能合并重复、修正过时的内容；系统不记录使用状态。

## 2. VCPToolBox 的 Rust 记忆运行时

VCPToolBox 是 owner 一年前开始做 HiveMemory 的启蒙，它的 Rust 记忆运行时（`rust-vexus-lite`）是该项目最扎实的部分（owner，2026-11-14）。依据是 DeeperResearch 工作区中的 VCPToolBox 第 2 轮调研（基线 `73fd165`，调研者在本机跑通了全部单元测试），不是源码通读。

- **三层真相**：日记文本文件是内容的真相，人可以直接编辑；SQLite 是向量与全部派生资产的记录系统，损坏时隔离旧库、从文件重新灌入；ANN 图、磁盘快照与 Memo 产物都是可以丢弃的缓存，随时从 SQLite 重建。ANN 在恢复后主动释放原始向量，精排一律回 SQLite 读原值，所以索引陈旧只损失一点召回，不会返回错误内容。
- **五个机制**：
  1. 单写者：进程里只有一个 SQLite 写线程，一条命令一个事务，所有事实提交持有全局排他闸门；起因是早先多连接写入导致库损坏。
  2. 文件到 SQLite 只求最终一致：不追求跨介质原子性，用代际号、稳定采样、提交前复核与按文件版本 CAS 挡住常见竞态，再用全量对账兜底；embedding 的网络调用放在事务之外。
  3. 新鲜度水位：把"派生索引落后于事实"与事实写在同一个事务里（标为 invalid，记下已提交水位），事务后应用增量、成功后用 CAS 置为 ready；查询时发现没有 ready，就当场从 SQLite 重建。即物化视图的已提交水位与已应用水位，加查询时修复。
  4. 快照的提交点在数据库事务里：写全新的不可变文件，rename 进非活动槽，再在带版本 CAS 的 SQL 事务里写背书，这一刻才算提交；恢复只认背书过的槽，再按 SQLite 补齐差量；删除文件之类的磁盘副作用记在事务性 outbox 中，重启后幂等重试。
  5. 近似只找候选，精度留给裁决：每维 2 位的量化图只产出约 128 个候选，精确余弦、近重复去重与重排都读原始向量，并在同一个冻结的读事务里完成。
- **两个小设计**：加载原生模块时做能力握手，能力字符串、ABI 版本或向量维度不匹配就拒绝启动；schema 迁移只做加法，遇到比自己新的 schema 就拒绝启动。
- **代价**：只能单进程；入库提交期间所有查询都要等；写线程 panic 之后再也写不进去，只能重启；查询不能取消；文档与实现漂移严重。

## 3. VCPToolBox 的 OneRing 与一份社区讨论稿

依据是 2026-11-14 对 VCPToolBox 源码（基线 `73fd165`，之后主分支对 OneRing 没有改动）的只读核实，关键处已经抽查。

- **是什么**：主服务进程中的一个消息预处理器。每个 Agent 一个本地 SQLite 账本（`data/{Agent}.db`），消息表只有角色、发送者、前端名、正文与时间，没有会话 ID，也没有消息 ID；每次插入后只保留最近 100 条，其余直接删除。
- **默认只记录、不补齐**：`ONERING_RECORD_ONLY` 默认为 true，要在配置中关掉才会补齐。
- **写入**：每次请求只把最后一条真实的用户消息入库；AI 回复要等整轮成功、HTTP 发送完毕才写入，只写可见正文，推理与工具结果不写；写入失败不重试，也没有锁。
- **补齐**：只在客户端带来的对话块少于 10 块时触发；从这个 Agent 最近 30 条中，按 hash 挑出本次请求里没有的，补到 10 块；只插进时间戳可信的缝隙，晚于最后一块的丢弃；每条加 `[OneRing通知:X于T发送于F]` 标明来源。上下文的主体仍是客户端自带的历史。
- **"分布式"** 指的是多个前端连同一台服务器，没有任何网络同步代码。
- **OneRingMemo**：用 LLM 把账本里近 3 天的消息压缩成一段客观时间线，注入系统提示词；手动触发，自动生成默认关闭；每次全量重算并覆盖旧结果。
- **与记忆系统的关系**：账本不进入日记，也不进入检索；VCP 自己的文档称它是"短期连续性，不替代永久记忆"。
- **宣称与实现之差**：VCP.md 宣称标注消息来自哪个会话、编辑作为新事件追加进统一时间线、旧消息"像推币机一样"不会无意义丢失、按 fuzzy diff 比对；实际上没有会话字段，编辑是原地覆写、时间不变、不留历史，超过 100 条就删除，fuzzy diff 的函数没有调用方。

**一份 VCP 社区讨论稿**

一份 2026-07-03 的社区讨论稿设想把一个"个体"拆成多个子 Agent：每个子 Agent 只负责一个领域，有自己的记忆分区与小上下文，由一个汇总者整合它们上报的结论。其中的术语多是 VCP 检索机制的比喻（第 3 轮调研：Tag 图实际是余弦召回加 Agent 自写 Tag 的共现图，图信号只做有上限的加分），引用的代码位置也早于 VCP 的 Rust 化，因此不作为依据。与 v0.8 设计讨论直接相关的内核已经并入[写入链路](../ideas/memory-flow-write-path.md)第 2.4 节、[库的形状](../ideas/memory-library-shape-and-index.md)第 2.1、3.2 节：按领域分区让检索信号更可靠；记录使用方实际采纳了哪些检索结果；从检索命中的稀疏程度发现知识缺口；额外的信号只在候选内重排。

## 4. Anthropic：The components of agent memory（2026-11-06）

Anthropic 工程团队的文章（[原文](https://www.anthropic.com/research/components-of-agent-memory)），2026-11-15 阅读。它把 agent 记忆定义为从经历中得到、跨会话保留、以可读上下文保存的知识，不含权重变化、单次对话内的学习与上下文压缩；主线是两种时机的分工：会话中由 agent 判断重要性并写笔记，离线时（文中称 dreaming，思路来自 Letta 与 UC Berkeley 的 sleep-time compute）回看日志与轨迹，修正、补充、重组与提升已有笔记。按[写入链路](../ideas/memory-flow-write-path.md)第 4 节的划分，这里只记写入一侧的要点；离线维护的要点记在[生命力分数长期演进](../ideas/VitalityScoringLongTermEvolutionIdeas.md)方向 6。

- **记忆是一种预测**：写下规则，是预测这个模式还会用到；写下验证过的事实，是预测以后的 agent 可以直接依赖、不必再查。在 CL-Bench 的数据库题上，几代模型的差别在于能否闭合学习回路：较早的模型只留下零散、未验证的猜测；之后的模型开始标出已确认与未确认、答错时写更正；Opus 5 起，每条笔记写明规则本身、怎么知道它成立，以及踩过的坑。
- **判断什么值得记**：在 Pokémon 实验中，Sonnet 3.7 什么都记（约一万步时 413 个文件、225 个文件夹，1 枚徽章），记录随游戏状态持续过时，翻找记忆还挤占了行动；Fable 5 只写 9 个文件加一个当仪表盘用的 `global.md`（当前目标、计划、自己的记忆规则），拿到 4 枚徽章。分界是：环境每一轮都会重新告诉你的（金钱、位置）不记；只有自己推出来、不写就会消失的（策略、计划、验证过的规则）才记。
- **只说明记忆的用途，不规定写法**：给强模型加上"只记失败"这类固定规则，记忆带来的收益大幅下降；引导对旧模型帮助最大（提示 Sonnet 4.6 先读记忆、再验证猜测，分数几乎翻倍）。对前沿模型，他们只给简单的指引：用户要求时，或者明显值得记时再写。
- **常驻的顶层要小**：顶层在每次会话开始时预先加载，占用 token，错误的笔记会带进每一次会话，指令越长越不容易被遵守；所以细节下沉、顶层只留链接。Claude Code 的自动记忆只加载 `MEMORY.md` 的前 200 行或 25 KB，作为索引。
- **多个写入者互相覆盖会丢事实，原文照引能保住事实**：多个 agent 同时写一张共享的合同条款表，57 条关键事实只留下 41 条；改为每份合同一页、由单个 agent 撰写、条款原文照引后，57 条全部保留。
- **轨迹搜索作为基础**：文章把轨迹搜索列为记忆的一种可能基础，再加 wiki 一类组织方式；后者的效果见方向 6。

## 5. Perplexity：Brain: Agentic memory as a knowledge wiki（2026-08-19）

Perplexity 工程团队的文章（[原文](https://www.perplexity.ai/hub/blog/brain-agentic-memory-as-a-knowledge-wiki)），讲其 Computer 产品的记忆系统，2026-11-15 阅读。

- **要解决的问题**：把静态记忆文件直接放进上下文，多了挤占窗口、少了缺上下文；让 agent 按需查外部库，又把导航的负担转给了 agent，向量库存的是互不相连的碎片，图数据库要求 agent 会写查询。
- **存储：`memory/` 下三个抽象层级**，有意冗余：`sessions/` 是原始历史（索引、摘要与完整轨迹）；`notes/` 是按主题分文件夹的提炼片段；`knowledge/` 即 Brain，一个综合 wiki，涵盖实体、概念、进行中的项目与学到的经验。单跳问题在 notes 里检索关键词就够；需要把几周、几个月的证据串起来的问题才用 knowledge。
- **wiki 的形态**：每页是对一个主题持续维护的视图，单独读也有用，又方便顺着链接探索。链接分两种：`[[wikilink]]` 是横向的上下文边（"还需要知道什么"）；`[cite:N]` 是向下的证据边，指向原始会话（精确到会话中的片段）或连接器来源（"怎么知道这是真的"）。整个 wiki 用 Git 管理，有版本、变更记录与 diff，也方便多个 agent 协同。
- **使用**：初始消息里放一份紧凑的 wiki 索引；agent 用 cat、grep、跟链接、查引用、比对 git 版本、下钻原始会话，自己决定查到什么程度，而不是走固定流水线；无关紧要的偏好直接采用，重要决定或来源冲突时才顺着引用读原始记录。全量记忆不复制进沙盒，只预载一份初始工作集；缺上下文时调用一个做语义检索的子 agent，它返回一段综合，并把支撑材料落成文件，工作集逐步扩大（远程挂载的路径上 grep 比本地慢四五百倍）。
- **后台维护（Dream）**：在沙盒中只读运行，每次从上一版 Brain 出发而不是从零重建；拿到的是可以自己探索的环境，而不是压平成一段提示词的输入；可以用只读连接器核实知识、把局部工作委派给子 agent；职责范围写成一份 Skill。四个阶段：定向（权威范围、长期指令、删除记录、额外输入与停止条件）；为新会话或有新轮次的会话写摘要；把每条值得记的观察挂到它该在的主题页上；更新 wiki（新建页面、修订综合、补链接与引用，或者什么都不改）。护栏：改动先写进一棵暂存的输出树，全部完成后才生效，从而把整张图当作整体更新；改动须通过确定性校验（格式、必备字段、引用格式）与语义核验（有证据支撑、与图的其余部分一致）；再由受控的同步步骤把差异应用到仓库，事后可在 git 历史中查看。
- **评估**：离线用 44 个合成用户、640 道题，答案与具体证据绑定；只去掉 wiki、其余记忆照常保留，正确率 0.600 升到 0.661，证据召回 0.573 升到 0.625，提升最大的是偏好类（+10.2 个百分点）、时间推理（+8.6）与过往活动细节（+6.9）。公开基准上，去掉 wiki 使 LoCoMo 降 4.6 个百分点，LongMemEval-S 无显著变化（单次会话的事实，原始轨迹本身就能答）。线上每天做配对评估，正确率 +9.3、时效性 +8.0、召回 +8.9，token 少约 15%、成本低 10%、速度快 10%。把索引直接放进初始上下文的随机对照实验中，wiki 的使用增加，与记忆相关的不满下降 6.9%。评估同时被当作自动改进的管线：agent 修改记忆子 agent、检索 skill 与提示词，只保留让指标变好的改动。

## 6. 原始历史优先的一派：Obelisk 与 Nowledge Mem（2026-11-15 阅读）

来源是一条推特帖子（作者 Yuu，2026-11-15）、[Obelisk 仓库](https://github.com/tommy0103/obelisk)的说明与设计文档、[演讲材料](https://github.com/tommy0103/talks/tree/main/2026-11-15-coscon26-magic)（提纲与此前一场演讲的文字稿）、[Nowledge Mem 网站](https://mem.nowledge.co)，以及帖子引用的三篇论文的摘要（只读了摘要，没有读正文）。

**帖子的三个论点与论文摘要的对照**：
- 原始历史上的朴素检索在 7 组设置中 6 组第一：与 *Is Complex Agentic Memory Always Needed?*（arXiv 2610.30755）的摘要一致，领先最强的复杂记忆系统 0.13 到 5.53 分；但测的是 LoCoMo、LongMemEval 等对话问答任务。摘要也指出，即使能完整访问加工过的记忆，准确率仍不如原文。
- 许多记忆系统的净收益为负：与 *Memory Tax*（arXiv 2610.34073）一致，论文把记忆的净值拆成相对直接检索的"收益"与"税"，税来自加工过程删去或遮蔽了证据。
- 只用 BM25 与 grep 的 harness 已基本解决准确率：与 *Context as Infrastructure*（arXiv 2610.41172）一致，但测的是 BrowseComp-Plus 与 FRAMES 这类文档检索问答。论文的结论是编译出的结构不是更好的检索器，而是供给层：以"结论加证据"为叶子的导航树平均少读 38% 的 token；图、wiki、时间线、记忆等产物在准确率基准看不到的地方（治理、连续性、时间定向）才有回报。帖子没有提这一点。

**Obelisk（第一阶段：让历史可查）**：把 11 个 harness 的原生会话日志只读地索引进一个 SQLite 文件（FTS5 全文检索），日志原样不动、索引随时可以重建；agent 通过 skill 现场写 JS 查询脚本（CodeAct），而不是调用固定的检索 API；"记忆层"只是人批准的结论加指回源会话的指针，是结论的缓存，不替代原始记录；人与 agent 读同一份索引，每条结论都能回到原文。演讲中的四个取舍：原生日志是事实来源（认为跨 harness 的统一格式有损）；全文检索是主路径、向量是补充（编码会话是有文件路径、报错原文、方案名等锚点的"执行记忆"，发散的社交情节记忆才是向量的主场）；查询是一等公民，注入不是；人要有观测面。一个实例：agent 在换窗交接中把一个早期未验证的判断一代代继承加固，最后写成"锁定设计"，只有站在完整历史上纵向回看才发现；修复是交接时把事实、推断、冲突、未验证项分栏，推断不能因为反复出现就升级为事实。

**Nowledge Mem（第二阶段：检索层之上的 view）**：分层为轨迹 → 单元 → 实体 → 演化 → 社群 → 结晶，原始轨迹是这张图的最底层；它赢在读得少、让 agent 先看到全貌并知道分母，而不是召回更准。维护（作者称 live-update）：按变化快慢分层更新；新结论进来先判断与旧结论的关系（取代、补充、印证或质疑），被取代的旧结论仍留在图上；有争议的取代降级为"质疑"；先有准入判断，再由定期回补接住漏掉的；更新是局部的，加一条边、改一个标志，而不是重写一整页。产品上有版本历史、批量的"记忆健康"复核（没有用户批准不改动），以及从几次重复的工作中起草 skill、只有在没见过的检查上胜过现有版本才上线。记忆类型是 DECISION、LEARNING、FACT 三种，另有实体、结晶、wiki 与 Artifact。
