# v0.7.1 记忆访问：Claude Code 经 MCP 工具检索与读取记忆

> 状态：Archived（2026-10-29，五个阶段实现、代码审查与实测验收完成后归档；当前事实见 [MCP 记忆访问](../../contracts/mcp.md)、[认证与访问登记](../../workspace/authentication.md)与 [Import Bus](../../system/import-bus.md)，实测验收结论见第 12 节）。以下为实施时的计划原文。原状态：Planned（2026-10-29；同日经 owner 复核，改为 harness 自有 principal 与接入凭据；阶段二实施后再经 owner 复核，actor API 只经操作入口，见第 5.3 节）。第 5 节中标为“计划选择”的细节不是 owner 决定，计划评审时可以调整，汇总见第 10.2 节。

v0.7.1 的版本目标是 plugin 模式接入 Claude Code（[ROADMAP](../../ROADMAP.md) 第 4.3、4.4 节）。plugin 模式由对话回流与记忆访问两部分组成：对话回流已由 [Import Bus 重设计](./v0.7.1-import-bus-redesign.md)完成，本计划完成记忆访问。

本计划同时让 Claude Code 以自己的身份接入。Claude Code 在接入登记中有自己的 principal 与接入凭据，记忆访问（`mcp` adapter）与对话回流（`import` adapter）都以它认证，统一认证网关第一阶段核对凭据。对话回流目前借用 server 的 principal，这偏离了“一个 harness 一份登记”的原设计（第 3.2 节），本计划一并纠正。

具体做法：HiveMemory 在现有 HTTP 服务上提供 MCP 端点，插件声明后，agent 经两个只读工具检索与读取记忆。访问不建进程：每次工具调用经统一认证网关取得一份请求级访问 context，按 Workspace 访问登记逐次授权，调用结束即撤销。两步合起来达到 ROADMAP 第 4.4 节的验收闭环。

设计依据：

- **owner 决定**：
  - [外部 Actor Idea](../../ideas/external-actor-registration-and-runtime-access.md#12-harness-登记的两个侧面owner2026-09-30) 1.2（2026-09-30）：一个外部 harness 只登记一份，它的接入侧面回答“以哪个 principal 接入、经哪种操作适配器、可以声称哪些用户身份”，装载进 System 接入登记。
  - 外部 Actor Idea [3.4](../../ideas/external-actor-registration-and-runtime-access.md#34-操作适配器的定义与边界) 的细化（2026-10-09）：操作适配器不直接调用能力层，而是把协议请求解析为固定类型的操作请求，经 workspace 的单一操作入口调用能力层。
  - Import Bus Idea D-8a（2026-10-20）选“经统一认证网关”，该选项的影响写明“输入来源需要作为 principal 登记”（删除前的最后版本见 commit `afbd7075` 的父提交）。
  - [身份与访问体系 Idea](../../ideas/identity-and-access-model.md#4-已登记的暂缓与例外)第 4 节（2026-10-20）：能以保留的 `system` 进入 root API 的只有用户经 HTTP 入口的管理访问；登记第一个外部 principal 之前在接入登记中落实。
  - 外部 Actor Idea 第 4 节（2026-10-29）：
    - E-2：多种传输各由操作适配器归一到同一能力层，支持 MCP 的 harness 以 MCP 访问记忆；
    - E-3b：MCP 的操作适配器放在与 `server` 同层的独立入口包，MTP 的留在 `agent_runtime`；
    - E-7：plugin 模式暂不提供主动预检索，记忆只经 MCP 工具，由 agent 自己选择使用；
    - P-1c：由统一认证网关证明身份；复核时决定接入证据采用每个外部 principal 一份本地共享密钥，Import Bus 在本计划中一并迁移；
    - P-9c：每次操作对应一份请求级访问 context；阶段二实施后复核调用路径：actor API 只经操作入口，入口另设只开放检索与读取的请求级提交，门面交出操作入口而不是 actor API，actor 操作的授权合并为一个方法。
- **背景 Idea**：外部 Actor Idea E-7 之后的“与对话回流及 harness 自带记忆的衔接”（回声与优先级），以及各项决定之后的候选设计；本计划采纳或调整的结果见第 5 节。
- **当前事实**：[能力层](../../workspace/capability.md)、[认证与访问登记](../../workspace/authentication.md)、[身份与授权](../../workspace/identity-and-authorization.md)、[Import Bus](../../system/import-bus.md)、[子系统公共契约](../../contracts/subsystem-contracts.md)第 4.6 节、[Patchouli 生成](../../patchouli/generation.md)第 2 节、[系统架构概览](../../architecture/overview.md)。
- **代码**：2026-10-29 在 commit `ac48db5a` 上的核对，见第 3 节。
- **外部资料**：Claude Code 插件的 MCP 声明与工具命名、MCP Python SDK 的挂载方式，按官方文档核对（2026-10-29，第 3.8 节）。它们不是 HiveMemory 的事实，实施时按所装版本再次核对。

## 1. 背景和问题

1. **版本验收缺少读取一半**：Claude Code 的对话已经回流并生成记忆，但 Claude Code 自己读不到任何记忆，这些记忆只有 Alice 能用。ROADMAP 第 4.4 节明确“只有回流、只有读取”都不足以证明 plugin 模式接入完成。
2. **外部 harness 没有自己的身份**：对话回流以 server 自己的 principal 与 `http` adapter 认证，连接器没有登记。
   - 任何能连到 HTTP 端口的程序，都能以任意 harness 的名义导入；接入登记既不能区分 harness，也不能单独停用某一个。
   - `adapters` 对外部来源失去了意义。
   - “只有 HTTP 管理访问能声明 `system`”这条规则也无法按来源落实。
   - 记忆访问若照此接入，同样的缺口会扩大到读取。
3. **principal 没有接入证据**：接入登记只核对 principal 是否登记、adapter 是否匹配、可否代表该用户，没有凭据。外部入口从请求中取得的 principal 只是声称，而 `CallerPrincipal` 的约束是“不能自封 principal”。
4. **actor 操作只接受线程 context**：操作入口与 actor API 的授权都只接受执行线程。plugin 模式下外部 harness 的任务对 HiveMemory 不可见，不建进程，也就没有执行线程；P-9c 决定改用请求级 context。
5. **没有 MCP 入口**：现有 HTTP 入口只调用 root API、任务进程与 Import Bus，项目也没有 MCP 依赖。
6. **访问登记不允许读取**：`claude_code` 的精确访问记录白名单为空，只能经 Import Bus 导入。
7. **回声**：经 MCP 取回的记忆会作为普通工具结果留在会话记录里，本轮结束时随对话回流再次导入。生成视图会渲染外部工具的结果，提取模型可能把已有记忆再提取一遍，形成重复记忆，并在之后的检索中自我强化。Alice 经 MTP 读回的记忆不渲染进生成，靠的是事件上的 `tool_kind`；导入的事件不允许携带它。
8. **优先级与时效**：对话回流生成的记忆描述的是生成当时的状态。2026-10-29 核对时，5 条记忆中有 2 条标为进行中，所述工作在生成前已经合并。Claude Code 自己还有项目指令与记忆文件，检索结果需要声明自己的地位。

## 2. 目标与非目标

### 2.1 目标

1. **Claude Code 的接入登记**：在 System 接入登记中有自己的 principal `harness:claude-code`，可用的 adapter 为 `mcp` 与 `import`，并登记接入凭据。
2. **凭据核对**：统一认证网关第一阶段核对外部 principal 的接入凭据；外部入口只携带凭据，不自行判定身份。
3. **root 的声明范围**：接入登记逐个声明能否声明 `system`，默认不能；server 与 Profile 注入脚本保持现状，Claude Code 不能。
4. **对话回流迁移**：Import Bus 以 Claude Code 的 principal、`import` adapter 与凭据认证，不再借用 server 的 principal。
5. **MCP 端点**：HiveMemory 在现有 HTTP 服务上提供 `/mcp`，只有两个只读工具：`memory_search`（SEARCH）与 `memory_read`（READ），分别归一为检索与读取的操作请求，经操作入口进入 actor API。
6. **每次调用一份 context**：每次工具调用以 Claude Code 的 principal、`mcp` adapter、凭据与 `(user, 具体 Agent)` 声明，经统一认证网关签发一份请求级访问 context，调用结束（含失败）时撤销；不建进程，不派生线程。
7. **能力层**：操作入口仍是 actor API 唯一的调用方，新增请求级提交，只开放检索与读取；actor 操作的授权合并为一个方法，接受线程或请求级 context，目标取驻留 Workspace，白名单照常逐次授权。
8. **代码位置**：MCP 入口位于与 `server` 同层的独立包，把工具调用归一为操作请求，经门面取得的操作入口提交；MTP 的操作适配器不迁移。
9. **访问登记**：`claude_code` 获准 `memory.read` 与 `memory.search`。
10. **插件**：Claude Code 插件声明该 MCP server；HiveMemory 不可用或凭据未配置时不阻塞 Claude Code 的工作，也不丢失待导入的轮次。
11. **回声**：连接器把插件自身两个工具的调用标为 SEARCH、READ 后导入，生成视图对它们与 MTP 的 SEARCH、READ 一样只保留一行摘要。
12. **优先级**：工具说明与服务说明声明仓库中的代码与文档、harness 自己的指令与记忆文件优先于检索结果；每条结果带记忆的更新时间。
13. **用语**：事实文档与代码注释中的“执行适配器”统一为“操作适配器”。
14. 真实使用验收（第 9.3 节）。

### 2.2 非目标

- **写入类 MCP 工具（WRITE、UPDATE）目前不开放**。写入意图的登记需要进程关联与派发话题，不建进程的写入如何取得它们是后续必须解决的问题，随外部 Actor Idea 第 4 节后续步骤“写入意图经 MCP 提交”设计，并需要先决定 E-4。
- **RUN 与 CALL**：RUN 的执行发生在执行单元的环境中，CALL 只属于 Alice。
- **主动预检索与注入**（E-7）。
- **凭据的签发、轮换、撤销与过期**：凭据由用户生成，写入两侧的环境变量，修改后重启生效。
- **用户身份的证明**：principal 经凭据证明，`X-User-ID` 等用户声明仍不做证明，沿用本地单用户部署的信任假设，由接入登记的 `allowed_user_ids` 收紧。
- **远程部署的传输安全**（TLS、OAuth）。
- **Profile 注入脚本的接入方式**：owner 于 2026-10-20 决定项目接入部署流程时再调整，本计划只为它显式声明可以声明 `system`。
- **MCP 的资源、提示、有状态会话与服务端通知**：只提供工具。
- **检索结果中的来源信息**（来源 Agent、交互 Artifact）：本计划只带更新时间。这是对 Idea 候选设计的收窄，见第 10.2 节。
- **与 harness 自带记忆的同步或去重**。
- **检索质量**：查重与材料截断由[生成查重的决策信号](../../todo/generation-dedup-decision-signal.md)与[生成材料的筛选与截断](../../todo/generation-material-filtering-and-truncation.md)跟踪。
- **第二个 harness**：端点与凭据机制是通用的，登记与插件只交付 Claude Code。
- **前端变化**。

## 3. 当前状态（2026-10-29 核对，commit `ac48db5a`）

### 3.1 接入登记与 Principal 认证

- `configs/system_principals.yaml` 装载为 `SystemActorAccessEntry`，字段为 `principal_id`、`kind`、`enabled`、`adapters`、`allowed_user_ids`，没有凭据字段。配置模型 `SystemPrincipalAccessEntry` 拒绝未知字段。现有两条登记：
  - `hivememory:http-server`：`http`；
  - `hivememory:profile-injector`：`local`。
- `SystemPrincipalAuthenticator`（网关第一阶段）依次检查：
  - 已登记且启用，否则 `unknown_principal`，不区分未登记与禁用；
  - adapter 在登记之内，否则 `adapter_mismatch`；
  - 用户在 `allowed_user_ids` 之内，否则 `actor_not_allowed_for_principal`。
- 网关入口为 `ActorAuthenticationGateway.authenticate(adapter, principal, actor, workspace, binding)`，端口为 `PrincipalAuthenticator.authenticate_principal(adapter, principal, actor)`；`CallerPrincipal` 的说明是“由受信 adapter 依据其接入证据构造”。
- 网关不限制谁能声明 `system`：任何已登记且可代表该用户的来源都能以 `system` 进入 root API。这是[身份与授权](../../workspace/identity-and-authorization.md#8-已知限制)第 8 节登记的已知限制。

### 3.2 对话回流的认证

- Import Bus 路由以 server 的 principal（`system.server_principal_id`）与 `http` adapter 认证，Agent 声明取请求体的 `agent_id`。导入授权返回认证通过的 principal 标识，参与 `interaction_id` 的推导。
- 这一做法来自 D-8a 决定之后的候选设计（“不为连接器另行登记 principal”），经 Import Bus 计划第 4.3 节写入当前事实（[认证与访问登记](../../workspace/authentication.md)：“外部 harness 的连接器不另行登记 principal”）。它与 D-8a 选项写明的影响、外部 Actor Idea 1.2 都不一致。
- 连接器对 413、422 以外的 4xx（身份声明不合法、未获准入等）按配置问题处理：保留游标、停止处理，修正配置后补发，不丢失轮次。

### 3.3 访问 context 与 actor API

- `WorkspaceAccessContext` 有三种运行绑定：任务进程、执行线程、请求（`AccessRunType.REQUEST`）。请求级 context 已有三个使用方：
  - server 的 root 管理与取消入口；
  - Import Bus，与上一项都经 `server/deps.py` 的 `request_access_for_claims`，请求结束时撤销；
  - Profile 注入脚本。
- actor API 经 `authorize_thread_operation` 授权：绑定不是执行线程即以 `ScopeRequiredError` 拒绝，已撤销的 context 以 `ThreadEndedError` 拒绝。架构测试限定它只被 `actor/memory.py` 与 `actor/agent_profiles.py` 调用。
- 底层的 `authorize_operation` 做准入、目标与白名单检查，不检查运行绑定。
- actor API 唯一的调用方是 `WorkspaceOperationEntry`。入口的 `execute` 先经线程表判定线程存活，进程 context 与请求级 context 在这里以 `ScopeRequiredError` 拒绝，再按请求类型分派到 actor API 方法。门面不暴露 actor API；[能力层](../../workspace/capability.md#1-三个调用面)第 1 节与 AGENTS.md 都写明“actor API 只经操作入口，不经门面”。
- 授权之后，READ 与 SEARCH 只使用 scope：READ 为交付的正式原子记录引用，SEARCH 预热缓存、不记录引用。WRITE 与 UPDATE 还要从线程取得 `process_id`、`thread_id` 与派发话题。

### 3.4 入口、门面与分层

- `server/app.py` 创建 FastAPI 应用，lifespan 中装配、启动并停止 `HiveMemorySystem`；业务路由挂在 `/api/v1` 下；提供前端构建产物时，末尾有兜底的 SPA 路由。
- 门面暴露 root 能力服务、任务进程服务、Import Bus 服务、认证网关与配置。
- `pyproject.toml` 没有 MCP 依赖。分层测试的 L5 只有 `server`。

### 3.5 身份声明与错误投影

- `server/deps.py` 的 `resolve_request_identity_claims` 是默认身份回退的唯一位置：
  - 用户取 `X-User-ID`，缺省回退到默认用户；
  - Workspace 取 `X-Workspace-ID`，只接受 `main_workspace`；
  - Agent action 必须显式给出具体 Agent，缺失返回 `request.agent_required`，给出 `system` 返回 `request.agent_reserved`。
- `request_access_for_claims(claims, gateway, principal_id)` 固定使用 `http` adapter。
- `server/error_handlers.py` 的 `project_error` 把领域错误投影为稳定的错误码、说明与 reason；reason 只在白名单内公开。

### 3.6 访问登记

`configs/workspace_actors.yaml` 有三条记录：

- `default` 用户的用户级记录，获准六项操作；
- `system` 的精确记录；
- `claude_code` 的精确记录：白名单为空，只能准入。Import Bus 只校验准入与目标，不经白名单。

### 3.7 记忆的呈现与回声

- MTP SEARCH 提交 `RetrieveRequest`，结果编译为检索上下文信封。
- MTP READ 提交 `ResolveReferencesRequest`，按请求顺序逐项编译：
  - 哪些解析结果可以交付，由 `agent_runtime/mtp/verbs/read.py` 的 `_readable` 判断；
  - 未解析的 alias 作为警告；全部未解析时报错。
- 编译器渲染记忆的更新时间。`MemoryCompiler()` 无参构造，位于 L2。
- `ImportedTurnEvent` 拒绝未知字段，不带 `tool_kind`。
- 共用封口用 `TraceReducer` 从动作归约轨迹：`tool_kind` 为 SEARCH 时，查询取自参数 `query`；为 READ 时，目标为工具名。
- 生成视图对带 `tool_kind` 的动作只渲染轨迹的一行摘要，不渲染结果；外部工具渲染工具名、参数摘要与截断后的结果。

### 3.8 Claude Code 插件与 MCP SDK（按官方文档核对，2026-10-29）

- 插件 `hivememory-connector`（`integrations/claude-code/`）目前只有 hooks。连接器从环境变量 `HIVEMEMORY_URL`、`HIVEMEMORY_USER_ID`、`HIVEMEMORY_AGENT_ID`（默认 `claude_code`）读取配置。
- 插件可以在根目录的 `.mcp.json` 中声明 MCP server。HTTP 类型带 `url` 与 `headers`，两者都支持 `${VAR}` 与 `${VAR:-default}` 环境变量展开。
- 插件 MCP 工具的调用名为 `mcp__plugin_<插件名>_<server 名>__<工具名>`，`A-Z`、`a-z`、`0-9`、`_`、`-` 以外的字符替换为 `_`。
- MCP Python SDK：
  - 把 streamable HTTP 应用挂进已有应用时，必须由宿主应用的 lifespan 运行 SDK 的会话管理器；
  - 工具处理函数可以读取 HTTP 请求头；
  - `ToolError` 返回 `isError` 的工具结果；
  - SDK v2 把 `FastMCP` 改名为 `MCPServer`。

## 5. 目标设计

### 5.1 链路总览

```text
Claude Code
  ├─ MCP（插件 .mcp.json）：POST /mcp
  │    请求头：X-Principal-ID、Authorization: Bearer <凭据>、X-User-ID、X-Agent-ID
  │    -> MCP 入口包：解析声明，携带凭据交给统一认证网关（adapter mcp）
  │    -> 第一阶段：principal 登记、adapter、凭据、用户、能否声明 system
  │    -> 第二阶段：Workspace 准入，签发请求级 context
  │    -> 门面取得的操作入口：请求级提交 RetrieveRequest / ResolveReferencesRequest
  │    -> actor API：retrieve / resolve_references（白名单逐次授权）
  │    -> MemoryCompiler 呈现为工具结果；调用结束撤销 context
  └─ 连接器（hooks）：POST /api/v1/import/turns
       同一 principal 与凭据，adapter import；其余流程不变
       插件自身两个工具的调用标为 SEARCH、READ -> 生成视图只留一行摘要
```

### 5.2 接入登记、凭据与 root 的声明范围

**登记**：`system_principals.yaml` 新增 Claude Code 的接入登记。这是外部 Actor Idea 1.2 中 harness 登记的接入侧面；同一个插件中的连接器与 MCP server 共用它：

```yaml
  - principal_id: "harness:claude-code"
    kind: "harness"
    enabled: true
    adapters:
      - "mcp"
      - "import"
    credential_env: "HIVEMEMORY_CLAUDE_CODE_TOKEN"
```

**adapter 标识**：表示调用来源经哪个入口接入，由入口代码固定传入，从不取自请求。

| 标识 | 入口 | 使用的 principal |
|:---|:---|:---|
| `http` | server 的管理、chat 与取消路由（前端） | server 自己的 principal |
| `local` | Profile 注入脚本 | 注入脚本的 principal |
| `mcp` | MCP 入口包（操作适配器） | 请求声明、经凭据核对的外部 principal |
| `import` | Import Bus 路由 | 请求声明、经凭据核对的外部 principal |

`mcp` 与 `import` 两个标识定义在 `system/access/`，与现有的 `local` 放在一起，入口包导入它们。

**凭据**：

- 配置只写环境变量名（`credential_env`），凭据本身不进入仓库。组合根装配接入登记时读取环境变量，凭据只存在于内存中的登记里，不进入日志与 `repr`。
- 外部入口（`mcp`、`import`）把请求声明的 principal 与 `Authorization: Bearer` 中的凭据交给网关。网关第一阶段在 adapter 检查之后核对凭据，用常量时间比较：
  - 登记了 `credential_env` 的 principal 必须提供一致的凭据，否则以 `invalid_credential` 拒绝；
  - 环境变量为空时，启动时记录一条警告，此后该 principal 的每次认证都以 `invalid_credential` 拒绝。HiveMemory 照常启动，不使用 Claude Code 的部署不受影响。
- 装配时校验：列出 `mcp` 或 `import` 的登记必须有 `credential_env`，否则启动失败。没有凭据的 principal（server、Profile 注入脚本）因此只能经进程内入口使用的 `http`、`local` 接入，外部请求无法借用它们的身份。

**端口与类型的变化**：

- `ActorAuthenticationGateway.authenticate` 与 `PrincipalAuthenticator.authenticate_principal` 增加 `credential: str | None` 参数。进程内入口传 `None`，外部入口传请求中的凭据，凭据为空时同样交给网关判定。这样身份证明发生在网关（P-1c），入口只携带证据。
- `CallerPrincipal` 的说明改为：外部入口传入的 principal 是声明，经第一阶段核对凭据后才成立；授予内容中的 principal 是核对通过的结果。

**root 的声明范围**：

- 登记新增 `allow_system_actor`，默认 `false`。第一阶段在用户检查之后，拒绝不允许的 principal 声明 `system`，reason 为 `system_actor_not_allowed`。
- server 与 Profile 注入脚本显式设为 `true`；后者按 owner 2026-10-20 的决定暂时保留现状。Claude Code 取默认值。
- 这消除身份与授权第 8 节的已知限制，落实身份 Idea 第 4 节“登记第一个外部 principal 之前”的要求。

**拒绝原因**：`invalid_credential` 与 `system_actor_not_allowed` 都是 `AdmissionDeniedError`（HTTP 403），加入 `project_error` 的 reason 白名单。凭据错误与未登记分开报告，用户才能区分“没登记”和“凭据不对”；两者都不泄露凭据本身。

### 5.3 操作入口与 actor 授权

**owner 复核（2026-10-29，阶段二实施后）**：本节最初的设计让门面直接交出 actor 记忆能力，供 MCP 入口以请求级 context 调用检索与读取，其余方法保留线程授权。阶段二照此实施后，actor API 有了两个出口：

- MCP 绕过操作入口，入口按请求类型的分派与分派前的存活判定对它都不生效，以后加在入口上的调用约束也一样；
- “请求级 context 能做哪些操作”散落在各个 actor API 方法选用的授权函数上；
- 门面交出了整个记忆能力，连写入方法也在内，只靠授权挡住。

这违背外部 Actor Idea 3.4 的细化（owner，2026-10-09）：操作适配器把协议请求解析为固定类型的操作请求，经 workspace 的单一操作入口调用能力层。owner 决定以下四项，原设计作废：

1. actor API 只经操作入口，门面不交出 actor API；
2. 操作入口新增请求级提交，只开放检索与读取；
3. 门面交出操作入口，MCP 入口只用其中的请求级提交；
4. actor 操作的授权合并为一个方法，接受线程或请求级 context。

由此 MCP 入口与 Alice 的 MTP 适配器形态相同：都把协议调用归一为 `OperationRequest`，交给同一个操作入口，由入口分派到同一组 actor API 方法。

**请求级提交**：`WorkspaceOperationEntry` 新增 `execute_request(request, *, access)`（**计划选择**：方法名）。

- 只接受 `RetrieveRequest` 与 `ResolveReferencesRequest`，经与 `execute` 相同的分派表交给 actor API 方法；其余请求类型在分派前以 `TypeError` 拒绝，没有副作用。MCP 入口只构造这两种请求，其他类型出现即是接线缺陷，与 `execute` 遇到未知请求类型的处理相同。
- “请求级 context 只开放检索与读取”只写在这一处。
- 不另做存活判定：请求级 context 只在本次调用内有效，调用结束即撤销，授权时检查撤销就够了。
- 暂不检查传入的是否为请求级 context：线程 context 只存在于 `ThreadOperationSubmitter` 内部，后者只调用 `execute`，生产路径上不会出现。架构测试限定 `execute_request` 只由 MCP 入口调用。

**线程提交不变**：`execute` 仍先经线程表判定存活，请求级 context 在这里以 `ScopeRequiredError` 拒绝；`derive_child_thread` 与 `end_thread` 不变。

**授权合并**：`WorkspaceOperationAuthorizer.authorize_thread_operation` 改为 `authorize_actor_operation(access, operation)`（**计划选择**：方法名），不另设第二个 actor 授权方法。

- 接受执行线程或请求级绑定，目标取授予内容中的驻留 Workspace，然后执行 `authorize_operation`；
- 进程绑定或类型不对时以 `ScopeRequiredError` 拒绝；
- 已撤销的 context 仍以 `ThreadEndedError` 拒绝，保持 MTP 读取在线程结束后的现有语义。请求级 context 只在调用结束或系统停止的最后一步被撤销，调用期间不会遇到；
- actor API 的五项记忆方法与 `ActorAgentService.resolve_call_target` 都使用它，不再按方法区分 context 的种类。

**请求级 context 到不了 RUN、WRITE、UPDATE 与 CALL**，由入口与线程解析保证，不靠授权：

- 经 `execute` 提交时被线程表拒绝，经 `execute_request` 提交时被类型表拒绝；
- WRITE 与 UPDATE 登记意图前要解析线程，取得进程关联与派发话题，即使绕过入口也登记不上；
- CALL 的派生先经线程表判定调用方存活。

### 5.4 门面

- `HiveMemorySystem` 新增 `operation_entry` 属性（**计划选择**：属性名），交出组合根装配的同一个操作入口，只供 MCP 入口调用 `execute_request`。
- 门面不暴露 actor API，现行规则“actor API 只经操作入口，不经门面”保持不变。

### 5.5 MCP 入口包

- **位置**：新包 `src/hivememory/mcp_server/`（**计划选择**：包名），位于 L5，分层测试的 `LAYERS` 加入它。
- **导入范围**：
  - MCP SDK；
  - `server/deps.py`：声明解析、请求级 context 与门面取得，沿用唯一的默认身份回退点，不复制；
  - `server/error_handlers.py` 的 `project_error`；
  - `system/access/` 的 adapter 标识；
  - `workspace.contracts` 的操作请求；
  - `engines.memory_compiler`；
  - core 错误类型。
  - 它不导入 actor API、root API、任务进程与 Import Bus。
- **挂载**：`server/app.py` 把 MCP 应用挂在 `/mcp`，位于 SPA 兜底路由之前。lifespan 在装配系统之前进入 SDK 的会话管理器，在 `shutdown_system` 之后退出。
- **无状态**：以无状态、JSON 响应方式运行，不保存 MCP 会话，每个 HTTP 请求独立；具体参数按选定的 SDK 版本核对。
- **每次调用的身份**：
  - 从请求头读取 `X-Principal-ID`、`Authorization`、`X-User-ID`、`X-Workspace-ID` 与 `X-Agent-ID`，缺少 `X-Principal-ID` 时返回 `request.principal_required`；
  - 以 `resolve_request_identity_claims(require_agent=True, agent_id=...)` 解析 actor 声明；
  - 经 `request_access_for_claims` 以声明的 principal、`mcp` adapter 与凭据取得请求级 context，把工具调用归一为操作请求，以门面取得的操作入口的 `execute_request` 提交，结束时撤销；
  - context 不离开本次调用，入口也不组装 `IdentityScope`；工具参数由模型生成，永远不作为身份来源。
- **共用函数的签名**：`request_access_for_claims` 增加 `adapter` 与 `credential` 参数。server 的管理路由传入自己的 principal、`http` 与 `None`，外部入口传入请求中的声明与凭据。
- **请求头的范围**：`X-Principal-ID` 与 `X-Agent-ID` 只有外部入口读取；HTTP 管理路由仍固定使用 server 的 principal 并声明 `system`。

### 5.6 对话回流改用 Claude Code 的 principal

- Import Bus 路由从请求头读取 `X-Principal-ID` 与 `Authorization`，以 `import` adapter 认证；Agent 声明仍取请求体的 `agent_id`。导入授权、编排与提交不变。
- 缺少 principal 声明返回 400 `request.principal_required`，凭据不对返回 403 `invalid_credential`。连接器把两者都按配置问题处理：保留游标、停止，修正配置后补发（3.2），不丢失轮次。
- `interaction_id` 的推导规则不变，但其中的 principal 从 server 变为 `harness:claude-code`，影响见第 7 节。
- server 的 principal 从此只用于前端的管理、chat 与取消路由。

### 5.7 工具

| 工具 | 参数 | 归一为 | 结果 |
|:---|:---|:---|:---|
| `memory_search` | `query`：非空字符串 | `RetrieveRequest(semantic_query=query)`，经 `execute_request` 分派到 `retrieve`，授权 `memory.search` | 检索上下文信封，含 alias 与更新时间；没有结果时返回说明文字，不算错误 |
| `memory_read` | `aliases`：非空的 alias 列表 | `ResolveReferencesRequest(aliases)`，经 `execute_request` 分派到 `resolve_references`，授权 `memory.read`；交付正式原子时记录引用 | 按请求顺序逐项编译；未解析的 alias 列在末尾；全部未解析时返回错误 |

- **参数**（**计划选择**）：不开放 `top_k`、过滤与关键词，使用检索的默认条数。参数名 `query` 与轨迹归约读取查询的字段一致，回声标记（5.11）因此能得到带查询的一行摘要。
- **读取的交付规则只有一份**：MTP READ 的 `_readable` 移到两个适配器都能导入的 `engines.memory_compiler`，MTP READ 改为调用它，不复制。
- **说明文字**：工具说明与 MCP 服务说明（instructions）写明以下几点：
  - 何时检索：回答涉及项目历史、此前的决定或用户偏好的问题之前；
  - 结果是带日期的历史证据，引用前先核实；
  - 仓库中的代码与文档、harness 自己的指令与记忆文件优先于检索结果；
  - 检索得到的 alias 可以用 `memory_read` 读取全文。
- **标注**：两个工具都标注为只读（MCP 的 `readOnlyHint`）。

### 5.8 错误

MCP 入口复用 `project_error` 的投影，不另建映射。投影得到的错误码、说明与 reason 写入 `isError` 的工具结果。

| 情况 | 来源 | 投影 |
|:---|:---|:---|
| 声明不合法 | `APIError`：`request.principal_required`、`request.agent_required`、`request.agent_reserved`、`request.identity_empty`、`request.workspace_not_found` | 原错误码 |
| 认证失败 | `AdmissionDeniedError`：`unknown_principal`、`adapter_mismatch`、`invalid_credential`、`actor_not_allowed_for_principal`、`system_actor_not_allowed`、`actor_not_owner`、`actor_not_admitted` | 拒绝访问，带 reason |
| 认证网关已关闭 | `AdmissionDeniedError`：`authentication_gateway_closed` | 服务不可用，可稍后重试 |
| 缺少操作许可 | `OperationDeniedError`：`operation_not_allowed` | 无权执行，带 operation |
| 存储不可用 | `StorageOfflineError`、`StorageReadError` | 存储不可用，可稍后重试 |
| 参数不合法 | SDK 的参数校验；空查询、空 alias 列表 | 参数错误 |
| 其他异常 | — | 投影为内部错误，像 HTTP 入口一样在本次调用边界记录一次完整异常栈 |

`asyncio.CancelledError` 不是 `Exception`，照常传播。

### 5.9 访问登记

`workspace_actors.yaml` 中 `claude_code` 的精确记录获准 `memory.read` 与 `memory.search`，并同步改写注释。Import Bus 不经白名单，导入不受影响。修改经重启生效。

### 5.10 插件与连接器的配置

插件根目录新增 `.mcp.json`：

```json
{
  "mcpServers": {
    "hivememory": {
      "type": "http",
      "url": "${HIVEMEMORY_URL:-http://localhost:8000}/mcp",
      "headers": {
        "X-Principal-ID": "harness:claude-code",
        "Authorization": "Bearer ${HIVEMEMORY_TOKEN}",
        "X-User-ID": "${HIVEMEMORY_USER_ID:-}",
        "X-Agent-ID": "${HIVEMEMORY_AGENT_ID:-claude_code}"
      }
    }
  }
}
```

- **连接器**：从 `HIVEMEMORY_TOKEN` 读取凭据，以常量 `harness:claude-code` 作为 principal，导入请求带上 `X-Principal-ID` 与 `Authorization`。
- **两侧的环境变量**：用户生成一份随机凭据，写入 Claude Code 一侧的 `HIVEMEMORY_TOKEN` 与 HiveMemory 一侧的 `HIVEMEMORY_CLAUDE_CODE_TOKEN`。服务端按 principal 区分变量名，为以后登记多个 harness 留出位置；插件只连接一个 principal，用通用名。
- **凭据未设置**：插件中的 `${HIVEMEMORY_TOKEN}` 原样发送，网关以 `invalid_credential` 拒绝；工具返回错误，导入保留游标等待补发。
- **插件命名**：插件名 `hivememory-connector` 不改，改名会改变工具调用名；插件说明改为同时覆盖导入与访问。
- **HiveMemory 不可用**：Claude Code 将该 server 标为连接失败，工具不出现，用户的工作照常进行。实施时按所装版本核对这一行为。

### 5.11 回声：导入时标记

**过滤与标记的分工**：

- **过滤只有一处**：生成材料的渲染，即 `prompts/transcript/actions.py` 的 `render_action_entries`。
  - 生成转写与折叠阈值的 token 统计都经它；带 `tool_kind` 的动作只保留一行轨迹摘要，不渲染结果。
  - 话题折叠的接力摘要只用轨迹、用户消息与最终回复，本来就不含工具结果。
  - Alice 的 MTP 与 MCP 共用这一处，本计划不新增过滤点。
- **标记由产生事件的一方负责**：
  - Alice 的 agent loop 按解析出的 MTP 动词写入 `tool_kind`；
  - 外部 harness 的会话记录只经连接器，由连接器按 MCP 契约写入。
- **不在其他位置剥除结果**：
  - 不在封口或 Import Bus 中剥除：交互记录与 Artifact 保留 agent 当时看到的原始内容，只有生成需要过滤；
  - 不在连接器中剥除：连接器不筛选内容；
  - 不在能力层中处理：能力层看不到会话记录。

**各部分的改动**：

- **连接器**：插件自身两个工具的调用名为 `mcp__plugin_hivememory-connector_hivememory__memory_search` 与 `…__memory_read`（3.8 的命名规则）。连接器在这两类工具调用事件上分别设置 `tool_kind` 为 `SEARCH`、`READ`；调用名前缀由插件名与 server 名两个常量按同一规则拼出，其他工具不设置。工具名与 SEARCH、READ 的对应写入 MCP 契约（5.13），连接器按契约映射。
- **Import Bus**：
  - `ImportedTurnEvent` 接受 `tool_kind: Literal["SEARCH", "READ"] | None`，其他取值以 422 拒绝，并原样写入 `TurnEvent.tool_kind`；
  - 契约说明改为：`tool_kind` 标记对 HiveMemory 能力层的记忆操作，包括 MTP 动词与 HiveMemory 自身 MCP 工具的读取，其他外部工具不设置。
- **封口与生成不改动**：共用封口归约出 SEARCH 与 READ 轨迹，生成视图只渲染一行摘要、不渲染取回的内容。交互 Artifact 仍保存包括结果在内的原始事件。
- **标记失效时的后果**：Claude Code 改变命名规则时标记会静默失效，回声恢复，表现为重复记忆，不丢失数据。由连接器单元测试（固定到文档给出的格式）与实测验收发现。

### 5.12 观测与关闭

- **日志**：现有请求日志记录每个 `POST /mcp`，只记录路径与状态。MCP 入口为每次工具调用记录一行：工具名、principal、Agent、结果条数或未解析数、耗时，不记录查询、记忆正文与凭据。不新增 RuntimeEvent。
- **关闭**：系统停止时先关闭认证网关，此后新的工具调用与导入都得到“服务不可用”。uvicorn 在执行 lifespan 关闭之前等待在途请求结束；会话管理器在系统停止后退出。

## 7. 兼容与迁移

- **服务端与插件需要一起更新**：
  - 服务端更新后，旧连接器的导入缺少 principal 声明，得到 400；连接器保留游标、停止，插件更新并配置凭据后补发，不丢失轮次。
  - 只更新插件、服务端仍是旧版本时，导入请求多出的请求头被忽略，照常以 server 的 principal 导入。
- **交互标识变化**：导入的 `interaction_id` 由 principal 参与推导，迁移后同一外部轮次得到新的标识。连接器只补发未确认的轮次，因此只有“已应用但确认在升级时丢失”的轮次会被再导入一次，形成一次重复交互。这个窗口极小，接受，不做转换。
- **重启生效**：`system_principals.yaml`、`workspace_actors.yaml` 与凭据环境变量的修改都需要重启 HiveMemory。
- **数据迁移**：不需要。

### 9.3 实测验收

1. **连接**：两侧配置同一份凭据，更新插件并重启 HiveMemory 后，Claude Code 的 `/mcp` 显示 `hivememory` 已连接，有两个工具。
2. **对话回流**：日常对话继续导入，交互标识按 `harness:claude-code` 推导，记忆照常生成。
3. **检索与读取**：在 Claude Code 会话中询问此前的某项决定，agent 调用 `memory_search`，结果同时包括对话回流与 Alice 会话形成的记忆（生成的记忆默认对 Workspace 内公开）。按 alias 调用 `memory_read` 能读到全文，被读取的记忆在生命周期中记录一次引用事件。
4. **凭据错误**：改错 Claude Code 一侧的凭据，工具返回 `invalid_credential`，导入保留游标停止；改回后工具恢复，未导入的轮次补发。
5. **白名单**：从 `claude_code` 的白名单移除 `memory.search` 并重启，工具返回 `operation_not_allowed`；验证后恢复。
6. **跨 Workspace**：把 `X-Workspace-ID` 设为其他值，调用以 `request.workspace_not_found` 被拒，跨 Workspace 的访问无法表达。
7. **回声**：用过 `memory_search` 的轮次结算后，对应话题的生成视图只有 `SEARCH: "…"` 一行，没有取回的内容，也没有生成重复的记忆。
8. **不可用**：停止 HiveMemory，Claude Code 照常工作；重新启动后工具恢复可用。
9. **观察样本**：观察期内把“该用而未用记忆”的情况记录到 [Import Bus 真实使用观察](../../todo/import-bus-real-use-observation.md)，作为 VISION 假设 H3 的样本。

## 10. 风险与待决问题

### 10.1 风险

- **凭据的保管**：凭据以环境变量存在于两侧，`.mcp.json` 中只写变量引用，不写明文。共享密钥只能防止本机其他程序冒用 harness 身份，不防止能读取用户环境的程序。日志与错误响应都不包含凭据。
- **两侧变量名不同**：服务端按 principal 命名，插件用通用名，用户可能只配一侧。安装文档写明两侧的对应关系；排障文档列出 `invalid_credential` 的处理。
- **检索精度**：生成查重的取证显示，无关记忆之间的 dense 相似度可达 0.49–0.65。查询对记忆的检索还经过融合与重排，但仍可能返回不相关的记忆。说明文字把结果定位为待核实的历史证据；真实表现记入观察 Todo，不在本计划中调参。
- **agent 不调用工具**：E-7 选择由 agent 自行决定。说明文字引导检索时机，第 9.3 节第 9 项收集样本。
- **过时记忆**：由优先级声明与更新时间缓解，来源信息不在本计划内。
- **工具命名依赖 Claude Code 的规则**：规则变化时回声标记静默失效（5.11）。
- **SDK 版本演进**：版本锁定在 `uv.lock`，入口包保持很薄，升级只影响这一个包。
- **编译文本中的 MTP 语法**：检索上下文与 READ 的编译文本若含只对 MTP 成立的指引，会误导外部 agent。阶段三核对，有则经编译选项去掉，不新增编译目标。
- **本地暴露面**：保留 SDK 默认的 Host 与 Origin 检查，防止 DNS 重绑定。
- **模型就绪**：模型仍在预热时首次检索要等待；空闲卸载计划落地后，检索也可能触发重新加载。
- **引用反馈**：经 MCP 读取的记忆会在生命周期中记录引用事件、提高生命力，这是预期行为，在观察中关注它对排序与归档的影响。

### 10.2 计划评审时确认的选择

以下是本计划给出的默认值，不是 owner 决定：

- principal 标识 `harness:claude-code`、`kind: harness`，凭据环境变量名 `HIVEMEMORY_CLAUDE_CODE_TOKEN`（服务端）与 `HIVEMEMORY_TOKEN`（插件）（5.2、5.10）；
- 外部入口以 `X-Principal-ID` 声明 principal、以 `Authorization: Bearer` 携带凭据（5.5）；
- 凭据环境变量为空时照常启动，只拒绝该 principal（5.2）；
- 凭据错误单独报告为 `invalid_credential`，不并入 `unknown_principal`（5.2）；
- 包名 `mcp_server`（5.5）；
- 工具名与参数：`memory_search(query)`、`memory_read(aliases)`，不开放条数与过滤（5.7）；
- 请求级提交只开放检索与读取（5.3）；
- 方法名 `execute_request`、`authorize_actor_operation` 与门面属性名 `operation_entry`（5.3、5.4）；
- 结果只带更新时间，不带来源信息（2.2）。
