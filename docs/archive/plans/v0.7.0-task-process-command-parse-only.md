# v0.7.0 任务进程：命令只解析不执行

> **文档状态**：Archived（2026-10-01 实施并通过验收，commit `fc8e350`）。本文保留实施前的设计、验收口径与文档更新清单作为历史追溯；当前事实以 [Gateway 全局命令](../../gateway/commands.md)、[子系统公共契约](../../contracts/subsystem-contracts.md)第 2 节与 [System 应用服务](../../system/application-services.md)为准。实施与计划一致，命令终态转换落在 `workspace/process/command_terminal.py`；实施评审只补充了测试（完成事件 `command_id` 的回退、被动模式下 `finalize()` 拒绝命令结果）。收尾时发现 [Topic `/compact` 系统指令接入 Todo](../../todo/conversation-compact-command.md) 依赖已删除的执行链路，已在该 Todo 中注明前提变化。

任务进程方向的第五批实施，也是这个方向在 v0.7.0 内的最后一批。版本目标第 4 条要求命令、主动请求与被动请求经同一入口注册：被动请求按 Q-6 在这一阶段不考虑；命令所在的请求已经登记为任务进程，但命令仍由 Gateway 在自己的工作流里直接执行。本批把 Gateway 的命令解析与执行分开，Gateway 只输出解析结果，现有的命令分发与执行删除，内置命令在 v0.7.0 内暂时不可用。

设计依据：
- [任务进程 Idea](../../ideas/task-process-table-and-registration-entry.md) Q-5a，以及 2026-10-01 的三条决定：
  - “暂时不可用”是命令仍被解析、但不会执行；
  - 解析与执行分开，Gateway 只输出解析结果；
  - 现有的分发与执行删除。
- Q-6：这一阶段不考虑被动请求。
- 当前事实文档与代码。

## 1. 背景和问题

Gateway 工作流（`gateway/workflow/`）在入口拦截识别出系统命令后，进入 `command_dispatch` 步骤，调用 `SystemCommandDispatcher.execute()`：
- 检查解析状态与权限；
- 按命令的目标类型调用本地 handler、全局路由，或返回客户端动作；
- 把执行结果放进公开结果 `GatewayCommandOutcome.command_execution_result`。

任务进程收到命令结果后以命令终态结束，流式交付发出 `command_result` 与 `done`。

问题：
- Q-5a 已决定命令的实际运行不在 Gateway：后续指令会与用户请求同时出现，不能让 Gateway 实际执行命令。现在 Gateway 既解析又执行；
- 命令在进程中何时、由谁运行尚未决定。现在保留执行代码，以后接回时它的位置一定会变；
- 解析结果模型 `CommandParseResult` 位于 `gateway.commands.models`，L2 的 `engines/gateway/models.py` 为了引用它登记了一条向上导入的已知例外。

## 2. 目标与非目标

**目标**：

1. **Gateway 的命令结果只携带解析结果**：`GatewayCommandOutcome` 改为携带 `CommandParseResult`，不再携带 `CommandExecutionResult`；工作流删除 `command_dispatch` 步骤，入口拦截识别出命令后直接以命令结果结束。
2. **公开解析模型移入 core**：`CommandParseResult` 与 `CommandParseStatus` 移到 `core.protocol.gateway`，与 `GatewayCommandOutcome` 放在一起，不另建第二个模型。`engines/gateway/models.py` 改为从 core 导入，删除它的向上导入例外。
3. **删除执行代码**：删除 `SystemCommandDispatcher`（`gateway/commands/dispatcher.py`）、内置 handler（`gateway/commands/handlers.py`）及其测试。保留：
   - 命令注册表、解析器与内置命令定义（解析需要它们）；
   - `gateway.commands.builtin` 覆盖表，它仍决定哪些命令能被识别。
4. **任务进程产生命令终态**：收到命令结果后，任务进程按解析状态产生用户可见的命令终态，不进入 prepare、CPU 分配与 Actor 执行。
   - 解析成功：命令暂不可用，状态 `not_implemented`，错误码 `command.unavailable`；
   - 解析失败（未知、参数无效、有歧义）：拒绝，状态 `rejected`，错误码 `command.parse.<解析状态>`，文案取解析错误。这与现在 dispatcher 对解析失败的处理相同。

   流式交付仍发出 `command_result` 与 `done`，非流式仍返回 `NonStreamingCommandOutcome`；`CommandExecutionResult` 继续作为命令终态的传输模型。
5. **删除只服务于执行的配置键**：`gateway.commands.expose_listing` 与 `enable_debug_commands`。该配置段设置了 `extra="ignore"`，现有配置文件中残留这两个键不会报错。

**非目标**：

- 命令在进程中何时、由谁运行，以及命令系统的接回（命令系统后置）；
- 被动请求（Q-6）；
- 命令定义中的目标类型与权限字段：解析不使用它们，本批原样保留，随命令系统接回时重新设计；
- `gateway.commands` 中本来就没有消费方的 `enabled` 与 `unknown_command_policy`；
- 前端：`command_result` 的结构不变。前端只在结果带 `clear_chat` 动作时清空聊天，否则只显示文案，所以不需要改动。

## 3. 当前状态（2026-10-01 核对）

| 位置 | 现状 |
|:---|:---|
| `engines/gateway/interceptors.py` | 入口拦截经命令注册表解析 slash 输入，产出带 `CommandParseResult` 的 `InterceptorResult`；被动模式不识别命令 |
| `gateway/workflow/state.py` | 执行状态同时持有 `command_parse_result` 与 `command_execution_result`；`finalize()` 要求命令流程有执行结果，并投影为 `GatewayCommandOutcome(command_execution_result=...)` |
| `gateway/workflow/topology.py`、`workflow.py` | `system_command` 分支在入口步骤之后运行 `command_dispatch` 步骤；`gateway.workflow.completed` 事件的数据带执行结果的 `command_id` |
| `gateway/runtime/core.py` | 装配 `SystemCommandDispatcher`，读取 `enable_debug_commands` 与 `expose_listing` |
| 内置命令 | `/help`、`/commands`、`/status`（本地 handler）与 `/clear`（客户端动作 `clear_chat`） |
| 任务进程 | `TaskProcess.run()` 收到命令结果后以 `CommandCompleted(command_result)` 结束；`chat.run.completed` 的数据带 `command_id` |
| 测试 | `tests/unit/gateway/commands/test_dispatcher.py`、`test_handlers.py`，以及 `tests/unit/gateway/test_phase3b_contracts.py`、`test_phase3c_workflow.py`、`test_phase3d_context_provider.py`、`tests/unit/system/services/passive/`、`tests/unit/workspace/process/test_gateway_chat_flow.py` 中的命令替身 |

## 4. 目标设计

### 4.1 core：公开的解析模型

- `CommandParseResult` 与 `CommandParseStatus` 从 `gateway/commands/models.py` 移到 `core/protocol/gateway.py`，字段与语义不变；
- `gateway.commands` 不再定义它们：解析器、注册表与入口拦截改为从 core 导入，不保留再导出；
- `GatewayCommandOutcome` 的字段由 `command_execution_result: CommandExecutionResult` 改为 `command_parse_result: CommandParseResult`；
- `CommandExecutionResult` 与 `CommandExecutionStatus` 保留，作为任务进程产生的命令终态与 SSE `command_result` 的模型。

### 4.2 Gateway 工作流

- 删除 `command_dispatch` 步骤、`CommandDispatchInput` 与执行状态中的 `command_execution_result`；
- 入口步骤设置 `system_command` 结束原因后，`finalize()` 直接以 `command_parse_result` 投影命令结果。不变量保持：
  - 被动模式不得产生命令结果；
  - 命令流程必须有解析结果；
  - 命令流程不得包含决策分析；
  - 决策流程不得包含解析结果。
- `gateway.workflow.completed` 事件中的 `command_id` 取自解析结果。解析失败时 `command_id` 为空，改用解析出的命令名（与现在 dispatcher 拒绝结果的取值一致）；
- `GatewayRuntime` 不再装配 dispatcher。

### 4.3 任务进程

- 收到命令结果后，任务进程用一个纯函数（暂名 `command_terminal`，放在 `workspace/process/`）把解析结果转换为 `CommandExecutionResult`，规则见第 2 节目标 4，然后照旧以 `CommandCompleted` 结束；
- 进程以 `completed` 结局结束。命令不可用是命令自身的终态，不是进程失败；`chat.run.completed` 的数据仍带 `command_id`；
- 命令短路仍发生在 Gateway 阶段之后，取消响应点不变。

### 4.4 依赖与分层

- `engines/gateway/models.py` 不再导入 `gateway.commands`，`tests/unit/architecture/test_package_layers.py` 中对应的已知例外删除；
- `engines/gateway/interceptors.py` 仍经 `gateway.commands` 的注册表解析，这条已知例外保留；
- 任务进程只依赖 core 中的解析模型，不导入 Gateway。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| Gateway 公开结果 | `GatewayCommandOutcome` 改为携带解析结果；`gateway.process` 路由的返回值随之变化 |
| Gateway 内部 | 删除 dispatcher、handler 与 `command_dispatch` 步骤 |
| core | 新增解析模型（从 Gateway 移入） |
| 任务进程 | 由解析结果产生命令终态 |
| 配置 | 删除 `gateway.commands.expose_listing` 与 `enable_debug_commands` |
| 用户可见行为 | 内置命令全部返回“暂不可用”；`/clear` 不再返回 `clear_chat`，前端不再因它清空聊天 |
| SSE、RuntimeEvent 类型、持久数据 | 结构不变 |

## 6. 兼容与迁移策略

- 模型与字段直接修改，不保留别名、转发或再导出；所有调用方在同一批内更新；
- 配置键删除后，残留的键被忽略；
- 回滚：一批一个提交序列，整体回退即可。

## 7. 实施步骤

1. core：移入解析模型，修改 `GatewayCommandOutcome`。
2. Gateway：解析器、注册表与入口拦截改为从 core 导入；工作流删除 `command_dispatch` 步骤；运行时不再装配 dispatcher；删除 dispatcher 与 handler。
3. 配置：删除两个配置键。
4. 任务进程：新增命令终态转换，`TaskProcess.run()` 改为由解析结果产生命令终态。
5. 分层测试删除对应的已知例外；更新测试（第 8 节），运行验证。

## 8. 测试和验收标准

测试遵循[测试设计规范](../../governance/testing/test-design-standards.md)。

**删除与调整的测试**：
- 删除 `tests/unit/gateway/commands/test_dispatcher.py` 与 `test_handlers.py`；

- `tests/unit/architecture/test_package_layers.py` 随已知例外的删除通过。

**新增的行为测试**：

1. **Gateway 工作流**（`tests/unit/gateway/`）：
   - 主动模式下，`/help` 产生命令结果，其中的解析结果为 `matched`，`command_id` 为 `system.help`，工作流不再运行任何执行步骤；
   - 未知 slash 输入产生解析状态为 `unknown` 的命令结果；
   - 被动模式下 slash 输入仍产生普通决策。
2. **命令终态转换**（`tests/unit/workspace/process/`）：
   - 解析成功：`not_implemented` 与 `command.unavailable`，`command_id` 保留；
   - 每种解析失败：`rejected`、`command.parse.<状态>` 与解析错误文案；
   - 结果不带客户端动作。
3. **任务进程**：
   - 命令请求不调用 prepare、Profile 解析与 CPU；
   - 流式交付发出 `command_result`（`not_implemented`）与 `done`，非流式返回 `NonStreamingCommandOutcome`；
   - `/clear` 的结果不带 `clear_chat`。

## 9. 风险与待决问题

| 风险 | 应对 |
|:---|:---|
| `/clear` 不可用后，用户无法用命令清空聊天；前端目前没有其他清空入口（`chatStore.clearMessages` 未接入界面） | 这是“命令暂时不可用”决定的预期结果；前端回归 session 模型后由“新建会话”操作承担清空（外部会话 Idea 0.1）。收尾时写入 Gateway 命令文档 |
| 删除 dispatcher 后，命令权限检查（可见性、白名单、确认）不再执行 | 命令不执行，就没有需要授权的副作用；权限字段保留在命令定义中，随命令系统接回时在新的运行位置重新实现 |
| 解析模型移入 core 后，core 中出现命令相关模型 | 它是 `GatewayProcessResult` 的组成部分，与 `GatewayCommandOutcome` 同属公开契约，放在 core 与现有约定一致 |

待决问题：无。命令终态转换函数的名称与位置可在实施评审时调整。
