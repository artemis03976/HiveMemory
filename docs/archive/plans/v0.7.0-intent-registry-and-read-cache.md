# v0.7.0 写入意图登记迁入 workspace 与读取缓存失效

> **文档状态**：Archived（2026-10-07）。本阶段实现、验收与 code review 已完成；实现仍在工作区，未提交、合并或发布。下文第 1～10 节保留实施前的设计与验收口径，最终实现及差异见第 11 节；当前事实以 [Workspace 架构](../../architecture/workspace.md)、[MTP 契约](../../contracts/mtp.md)与 [System 应用服务](../../system/application-services.md)为准。

本计划把三件事放在同一批完成：写入意图的登记从 Alice 迁入 workspace（写入意图迁移的第 1 步），workspace 读取缓存接上失效，Alice 的引用解析整体改由 workspace 读取视图承担。三者同批，是为了不出现“pending 在 workspace 解析、正式记忆仍在 Alice 解析”的割裂过渡状态（owner，2026-10-06）。

设计依据：
- [写入意图迁移 Idea](../../ideas/pending-intent-migration.md#01-owner-的决定2026-09-28) 0.1：登记位于 workspace、与任务进程解耦、落库前对全 workspace 可回读、能力层的提交方法；第 1 步的范围；第 4.1 节共同引用读取的候选设计与第 6 节行为约束；
- [总 Idea](../../ideas/workspace-network-task-process-architecture.md)：7.1.3–7.1.5 的事件协作与 D1–D3 纪律；13.6 读取视图的现状；15.5 的重新划分；15.11（P-11，写入意图第 1 步在前）及其 2026-10-06 的补充；
- [执行单元 Idea](../../ideas/execution-unit-thread-and-environment.md)：前提 4–6；T-4a、T-4c（主线程的回调通道）的决定；
- [身份与访问体系 Idea](../../ideas/identity-and-access-model.md)：记录分开携带归属与发起者，不保存 `IdentityScope`；
- 当前事实文档与代码。

## 1. 背景和问题

- **写入意图的登记在 Alice 内**：`PendingAtomRuntime` 由 `AliceRuntime` 进程级持有，生命周期跟随 Alice 的 run；回读要求整个 `IdentityScope` 相等。写入意图迁移 Idea 已决定登记位于 workspace、对全 workspace 可回读，生命周期与任务进程解耦。
- **两套解析器与缓存**：Alice 的 `RuntimeAliasResolver` 与自有原子缓存承担 MTP 的全部引用解析；workspace 的读取视图（`AliasResolver`、`AtomCache`、`ProfileCache`、失效代次）已装配，但没有生产调用方，也没有失效：`AtomCache.evict`、`ProfileCache.evict_source` 与 `WorkspaceEpochs.advance` 都没有调用方（总 Idea 13.6）。
- **顺序约束**：P-11 已决定写入意图第 1 步在 Alice 的能力层调用迁移之前完成。第 1 步要让 pending 读回经能力层；若正式记忆仍由 Alice 解析，会出现两处解析并存的过渡状态；若由 workspace 读取视图解析，就必须先接上失效，否则管理写入之后 agent 会读到旧内容。

## 2. 目标与非目标

**目标**：

1. **canonical 变更事件**：Patchouli 的中期库每次变更（`upsert`、`patch_payload`、`delete`、`delete_by_key`）都在全局总线发布一次变更事件；workspace 订阅后失效对应的原子缓存条目与 Profile 缓存条目，并推进该 workspace 的失效代次。遵循 D1–D3：内联发布、失效优先、只失效不携值。不处理重试与未送达（owner，2026-10-06）。
2. **写入意图登记迁入 workspace**：workspace 的共享设施中新建写入意图登记，取代 Alice 的 `PendingAtomRuntime`，成为写入意图状态的唯一所有者。登记记录分开保存归属（`belong_to`）、发起者（`from_actor`）与登记它的进程（`process_id`，只作关联，不参与授权）；对全 workspace 可回读；结算后的句柄不回收。
3. **统一的引用解析**：workspace 的 `AliasResolver` 接上 L0（写入意图登记），承担 pending、redirect、discarded、failed、atom、not_found 的全部解析结果；解析结果的中立模型移到 core，`engines/memory_compiler` 对 `agent_runtime.aliases` 的两处已知向上导入随之移除。
4. **能力层方法**：写入意图的提交（WRITE、UPDATE）绑定 `memory_intent.submit`；引用解析绑定 `resource.read`（W5）。
5. **进程的操作通道**（W2、W3）：`workspace.contracts` 定义一个不带访问 context 与目标参数的操作端口，作为 `CPUPort.execute` 的独立参数交给 CPU；实现位于 `workspace.process`，每个进程一个实例，绑定本进程主线程的访问 context 与任务注册时的目标 workspace，进程关闭即失效。
6. **Alice 改用操作端口**：MTP WRITE、UPDATE、READ、RUN 与 CALL 的 `context_refs` 经端口完成；Alice 删除 `PendingAtomRuntime`、`RuntimeAliasResolver`、自有原子缓存与结算事件的订阅。子线程沿用主线程的端口，与外部执行单元的语义相同（外部 Actor Idea E-5），直到执行线程层。
7. **任务进程**：
   - CPU 分配中的 Profile 解析改经能力层的 `get_agent_profile`，使 workspace 的 Profile 缓存进入生产；
   - 以 completed 结束时，进程从登记中认领本进程的写入意图，作为交互记录的物化任务；
   - 关闭时取消本进程仍处于 PENDING 的写入意图（W4）。
8. **访问登记**：默认的用户级记录加入 `memory_intent.submit`。
9. 其余对外行为不变：MTP 各动词的响应文本与 ACK 语义、物化在 finalize 时派发、`alice.events.pending_atom.*` 三个全局事件的名称与载荷。

**非目标**：

- 写入意图迁移的第 2 步：实时派发生成、收尾不再派发物化、移除 `InteractionPayload.materialize_tasks`、“取消与失败不再丢弃写入意图”；
- Alice 的 SEARCH、引用记录与 CALL 目标 Profile 解析改经能力层，删除 `cpu_execution_identity`（收窄后的 Alice 能力层调用迁移与执行线程层）；
- Agent Profile 权限并入 operation 控制（单独计划）；Alice 内部对 `allowed_mtp_verbs` 的检查保持不变；
- 事件丢失后的补齐与重试、负缓存（owner，2026-10-06）；写入意图的幂等键、结算后句柄的回收、跨重启持久化、`WriteFocus` 携带 policy；
- 重命名 `alice.events.pending_atom.*` 事件；
- 外部执行单元、MCP 操作适配器与执行环境的选择。

## 3. 当前状态（2026-10-06 核对）

### 3.1 写入意图

- `PendingAtomRuntime`（`agent_runtime/pending_atom/runtime.py`）由 `AliceRuntime` 持有。`register_write` 生成 `draft_{slug}_{4 位十六进制}`，`register_update` 生成 `rev_{base_alias}_{4 位十六进制}`，并各生成一个 `intent_id`。
- `PendingAtom`（`core/models/pending.py`）保存 `identity` 与 `runtime_scope`（含 `IdentityScope`、`run_id`、`frame_id`）；`PendingAtomMaterializeTask.from_pending_atom` 从 `runtime_scope` 取出归属与发起者。
- run 结束（`AgentRuntime.finalize_run`）：completed 时认领本 run 的 PENDING 意图并生成物化任务，再把上一轮已结束的意图标为 EXPIRED；否则取消本 run 的全部 in-flight 意图。物化任务随 `CPUExecutionResult.materialize_tasks` 交给进程，进程封口进 `InteractionPayload`。
- 结算：Patchouli 的 `PendingAtomSettler` 发布本地事件，Patchouli bridge 内联转发为全局事件 `alice.events.pending_atom.settled / failed / cancelled`；`AliceBridge` 订阅后更新 `PendingAtomRuntime`，并失效、回填 Alice 自有的原子缓存。
- 回读：Alice resolver 的 L0 命中按 `pending.runtime_scope.identity_scope` 与调用方完全相等判断可见性。

### 3.2 解析与缓存

- Alice 的 `RuntimeAliasResolver` 按 L0 写入意图、L1 自有缓存（`KoakumaAtomCache`）、L2 Patchouli 冷读解析，返回 `ResolveResult`（`agent_runtime/aliases/resolver.py`）。使用方：MTP READ、UPDATE、RUN（`agent_runtime/mtp/runtime.py`）与 CALL 的 `CallContextProvider`。
- Alice 自有缓存的写入点：SEARCH 结果与 prepare 检索结果的预热、结算后的回填；UPDATE 登记时失效基础 alias。
- workspace 的 `AliasResolver`（`workspace/resolution/alias.py`）有 L1/L2 与代次守护的回填，L0 恒为未命中；能力层的 actor 可见读取没有生产调用方。
- `engines/memory_compiler` 的 `compiler.py` 与 `builders/resolve_result.py` 导入 `agent_runtime.aliases.ResolveResult`，是分层测试登记的两处已知向上导入。

### 3.3 中期库

`MidTermMemoryStore`（`patchouli/memory_library/stores.py`）的变更方法为 `upsert`、`patch_payload`、`delete`、`delete_by_key`，先写 primary 再依次同步 secondary，不发布任何事件。`AsyncSystemBus.publish` 内联、顺序 await 全部订阅者，订阅者异常被吞并只记日志（总 Idea 7.1.3）。

### 3.4 任务进程与 CPU 端口

- `CPUPort.execute(manifest, *, generation_options, stream)`；`CPUExecutionResult` 含 `materialize_tasks`。
- `CPUAllocator.resolve_agent_profile` 以 `profile.read` 做阶段授权后直接请求 Patchouli 的 `get_agent_profile` 路由。
- 关闭流程 `TaskProcessRunner.close` 先同步释放附件租借，再 await 关闭 CPU 输出流与 prepare 补偿。

### 3.5 访问登记

`configs/workspace_actors.yaml` 的用户级记录持有 `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit`，没有 `memory_intent.submit`。Patchouli 的 `memory_intent.submit` 公开路由（实时派发的入口）没有生产调用方，本计划不使用它。

## 4. 目标设计

### 4.1 canonical 变更事件

- **事件**：在 `core.contracts` 登记一个全局事件，载荷为 `{belong_to: WorkspaceIdentity, memory_id: UUID, operation: "upsert" | "patch" | "delete"}`。事件名在实施评审时确定，按发布方命名（例如 `patchouli.events.memory.changed`）。
- **发布**：`MidTermMemoryStore` 接收一个注入的发布协议，在每个变更方法的提交调用完成时（`finally`，无论成败）内联 await 发布；store 不依赖总线。发布的实现位于 `patchouli/control`，与 `PendingAtomSettler` 同模式：发布到 Patchouli 本地总线，由 Patchouli bridge 内联转发到全局总线。`delete` 与 `delete_by_key` 无论是否删到条目都发布。
- **订阅**：workspace 读取视图订阅该事件，处理顺序固定为：失效 `AtomCache` 中该原子（连同其 alias 索引）、失效 `ProfileCache` 中由该原子解析出的条目、推进该 workspace 的失效代次。三步都是纯内存操作，之后不做任何可能失败的工作，也不回放事件中的值。
- **装配**：组合根在开始接受请求之前完成订阅，在关闭时取消订阅。
- **不处理**：重试、未送达的补齐、负缓存。订阅者异常由总线记录日志，此时条目已失效。

### 4.2 写入意图登记

- **位置**：workspace 的共享设施新增子包（暂名 `workspace/intents/`），只依赖 core 与 components；由组合根装配一个进程级实例。
- **记录**：`PendingAtom` 去掉 `identity` 与 `runtime_scope`，改为 `belong_to: WorkspaceIdentity`、`from_actor: ActorIdentity` 与 `process_id: str | None`。`PendingAtomMaterializeTask.from_pending_atom` 相应改为读取这两个字段。`RuntimeScope` 仍供 Alice 的 frame 使用，不在本计划修改。
- **操作**（同步方法，在单个事件循环内不跨 await，因此对单条记录原子）：
  - 登记 WRITE 与 UPDATE：alias 与 `intent_id` 的生成规则不变；生成的 alias 已被占用时重新生成后缀；
  - 按 alias 读取：只返回 `belong_to` 等于请求 workspace 的记录（全 workspace 可回读，不比较发起者）；返回独立副本；
  - 认领：把指定进程的 PENDING 记录迁为 MATERIALIZING，返回物化任务；
  - 取消：把指定进程仍为 PENDING 的记录迁为 CANCELLED，不触及 MATERIALIZING；
  - 结算：订阅三个 `alice.events.pending_atom.*` 全局事件，沿用现有状态机与 `intent_id` 校验。
- **生命周期**：与任务进程解耦；不再有“上一轮结束后标为 EXPIRED”的窗口，结算后的记录保留到进程重启（写入意图迁移 Idea 0.1：兼容期不回收）。`PendingAtomStatus.EXPIRED` 与解析结果的 `expired` 种类保留在模型中，但不再产生。

### 4.3 统一的引用解析

- **中立结果**：`ResolveResult` 的字段与种类原样移到 core（暂名 `ReferenceResolution`），`pending` 与 `atom` 均为独立副本。`engines/memory_compiler` 改为导入 core 中的模型，分层测试的 `KNOWN_UPWARD_IMPORTS` 删除对应两项。
- **解析顺序**（workspace `AliasResolver`）：
  1. L0：在登记中按 alias 查找；PENDING 与 MATERIALIZING 为 `pending`，FAILED 为 `failed`，CANCELLED 为 `not_found`，SETTLED 且结算结果为丢弃时为 `discarded`；
  2. SETTLED 且有 canonical 引用时为 `redirect`：经 L1/L2 读取 canonical 原子，并对请求方按原子 policy 授权；**不可读时清空 canonical 引用字段且不附原子**，不通过 redirect 泄露目标的身份或内容（写入意图迁移 Idea 4.1）；
  3. L0 未命中：L1 `AtomCache`、L2 冷读，与现有 workspace 实现相同。
- **缓存维护**：结算后不再回填，正式记忆由物化写入时的变更事件失效（4.1）；UPDATE 登记成功后失效基础原子，保持 [MTP 契约](../../contracts/mtp.md)第 3.5 节现有的行为；只有能力层的语义检索会预热缓存。Alice 的 SEARCH 在改经能力层之前不预热，prepare 检索结果也不再预热。

### 4.4 能力层

在能力层新增三个方法，均显式接收访问 context 与目标 workspace，先做操作授权：

| 方法 | operation | 行为 |
|:---|:---|:---|
| 提交 WRITE 意图 | `memory_intent.submit` | 以授权得到的归属、发起者与调用方给出的 `process_id` 登记，返回 pending alias 与 `intent_id` |
| 提交 UPDATE 意图 | `memory_intent.submit` | 先解析基础 alias：必须是请求方可读的正式原子，pending 基础与不存在分别以领域错误拒绝；登记后失效基础原子 |
| 解析引用 | `resource.read` | 按请求顺序为每个 alias 返回一个中立结果（含 `not_found`） |

授权失败时不产生任何登记或缓存副作用。

### 4.5 进程的操作通道

- **协议**：`workspace.contracts` 新增操作端口协议，方法与 4.4 一一对应，但不带访问 context、目标 workspace 与 `process_id`。
- **交付**：`CPUPort.execute` 增加一个关键字参数 `operations`。`AliceCPU` 把它传给 Alice 的统一执行路由；测试用的 `ScriptedCPU` 忽略它。
- **实现**：位于 `workspace.process`。Actor 阶段开始时由执行器创建，持有本进程主线程的访问 context、任务注册时声明的目标 workspace 与 `process_id`，调用能力层方法；进程关闭时同步失效，此后调用以明确的错误拒绝。
- **身份**：访问 context 的持有者因此多了这个通道对象，它属于进程，不离开 `workspace.process`；架构测试中对 context 持有者的限制相应更新。

### 4.6 任务进程

- **Profile 解析**：`CPUAllocator.resolve_agent_profile` 改为调用能力层的 `get_agent_profile`（`profile.read` 授权在能力层），解析时点不变。
- **Actor 阶段**：创建操作通道并交给 `CPUPort.execute`。
- **finalize（仅 completed）**：封口交互记录前，从登记中认领本进程的写入意图，作为 `InteractionPayload.materialize_tasks`。`CPUExecutionResult.materialize_tasks` 删除。
- **关闭**：在同步释放附件租借的同一步，失效操作通道，并取消本进程仍为 PENDING 的写入意图（W4）。以 completed 结束的进程此时已没有 PENDING 意图；finalize 失败时已认领的意图保持 MATERIALIZING，与现状相同。

### 4.7 Alice

- **改用端口**：Koakuma 的 WRITE、UPDATE 经端口提交；READ、RUN 的目标与 UPDATE 的基础解析、CALL 的 `context_refs` 经端口解析。端口返回的中立结果与能力层错误，在 Alice 内映射为现有的 MTP 响应与错误，即 Alice 一侧的 MTP 操作适配器。
- **删除**：`agent_runtime/pending_atom/`、`RuntimeAliasResolver`、`KoakumaAtomCache` 与 `AtomCachePort`、`AliceBridge` 对三个结算事件的订阅与 `AliceRuntime` 的处理器、`AgentRuntime` 中与写入意图相关的收尾逻辑、两处预热。
- **保留**：frame 产出的 alias 清单改由 Alice 记录本 frame 收到的 ACK；SEARCH、引用记录与 CALL 目标的 Profile 解析仍以输入清单中的 `IdentityScope` 直接请求 Patchouli；`cpu_execution_identity` 保留。

### 4.8 依赖与分层

- core：中立解析结果、变更事件的载荷与事件名、`PendingAtom` 的字段调整；
- `workspace/intents`：共享设施，不导入 process 与 capability；能力层依赖它与读取视图；process 依赖能力层；
- Alice 只导入 `workspace.contracts`；
- Patchouli 的 store 只依赖注入的发布协议。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| core | `PendingAtom` 字段；中立解析结果；变更事件 |
| Patchouli | 中期库发布变更事件；发布实现与 bridge 转发 |
| workspace | 写入意图登记；`AliasResolver` 的 L0 与 redirect；缓存订阅者；能力层三个方法；操作端口与通道；进程的认领、取消与 Profile 解析 |
| Alice | 改用端口；删除写入意图运行时、resolver 与自有缓存 |
| engines | `memory_compiler` 改为导入 core 的解析结果 |
| 公共契约 | 新增一个全局事件；`CPUPort.execute` 增加参数；`CPUExecutionResult` 删除 `materialize_tasks`；写入意图的回读范围放宽到全 workspace |
| 配置 | 默认用户级记录加入 `memory_intent.submit` |
| 数据 | 均为进程内状态，没有持久化数据迁移 |

## 6. 兼容与迁移策略

- 单一状态所有者一次切换：同一批内删除 Alice 的登记与 resolver，不让新旧登记或两套解析器同时作为成功来源（写入意图迁移 Idea 第 6 节）。
- 行为变化：写入意图对全 workspace 可回读（已决定）；不再产生 `expired`；结算后的句柄一直保留到重启。
- `CPUPort` 与 `CPUExecutionResult` 只有 `AliceCPU` 与 `ScriptedCPU` 两个实现方，同批修改。
- 进程重启后登记为空，与现状相同。

## 8. 测试和验收标准

测试遵循[测试设计规范](../../governance/testing/test-design-standards.md)。

**canonical 变更事件**：

1. 四个变更方法各发布一次事件，载荷正确；primary 写入失败时仍发布，异常照常抛出。
2. 管理更新一条已被 actor 可见读取缓存的记忆后，再次经能力层读取得到新内容（integration，真实 store 适配器以 fake 替代向量后端）。
3. 订阅者在失效之后抛出异常：条目已失效、代次已推进，后续读取不命中旧值，发布方的写入正常返回（D2）。
4. 写入调用返回时订阅者已经执行完毕（D1）。
5. 更新一个 Agent Profile 原子后，进程的下一次 Profile 解析得到新配置。

**写入意图登记与解析**：

6. 同一 workspace 的另一个 agent 能读回意图；另一个 workspace 读不到，结果与不存在相同。
7. 结算、失败、取消事件按 `intent_id` 匹配后更新状态；`intent_id` 不匹配时不改变状态。
8. 解析结果覆盖 pending、redirect、discarded、failed、atom、not_found；redirect 的目标对请求方不可读时，结果不含 canonical 引用与原子。
9. 返回的意图与原子是独立副本，修改它们不影响登记与缓存。
10. alias 冲突时重新生成，两个意图不会共用一个 alias。

**能力层与通道**：

11. 缺少 `memory_intent.submit` 或 `resource.read` 时以 `OperationDenied` 拒绝，且没有登记或缓存副作用。
12. UPDATE 的基础为 pending 或不存在时以对应的领域错误拒绝；成功后基础原子从缓存中失效。
13. 进程关闭后，通道的调用以明确的错误拒绝。

**任务进程**（以测试 CPU 驱动操作端口）：

14. completed：交互记录的物化任务来自登记中本进程的意图，并带有正确的归属与发起者；这些意图变为 MATERIALIZING。
15. 取消与失败：本进程仍为 PENDING 的意图变为 CANCELLED，其他进程的意图不受影响。

**Alice**：

16. MTP WRITE 返回登记中的 alias；下一轮任务进程中 READ 该 alias 得到 pending 内容；结算后 READ 得到 redirect 与正式内容。
17. UPDATE、RUN（`CODE_SNIPPET`）与 CALL 的 `context_refs` 经端口解析，响应与现有行为一致。

**架构**：

18. 分层测试的已知向上导入删除两项后通过；Alice 只导入 `workspace.contracts`；共享设施不导入 process 与 capability；访问 context 的持有者限制包含操作通道。

**端到端**：

19. 确定性 HTTP chat E2E：第一轮 MTP WRITE，第二轮 READ 该 alias 得到 pending 内容。

## 9. 风险与待决问题

| 风险 | 应对 |
|:---|:---|
| 事件未送达时缓存保留旧值 | 进程内总线内联发布，未送达只发生在订阅者装配缺失时；按 owner 决定不做补齐，装配顺序由组合根测试覆盖 |
| 写入路径要等订阅者执行完 | 订阅者只做纯内存失效，耗时可忽略；这是 D1 的明确取舍 |
| 结算后的句柄不回收，登记随运行时间增长 | 已决定的兼容期行为；规模在单用户本地部署下可接受，回收随写入意图后续设计处理 |
| 回读范围放宽后，其他 agent 可能看到 redirect 目标 | 目标不可读时清空引用字段（4.3） |
| 去掉两处预热后，首次 READ 预检索到的记忆要走 L2 冷读 | 只影响延迟；Alice 的 SEARCH 改经能力层后由语义检索预热 |
| finalize 失败后已认领的意图停在 MATERIALIZING | 与现状相同，随第 2 步实时派发一并处理 |

待决问题：事件名、登记与通道的类名在实施评审时确定。

## 11. 实施、验收与审查记录（2026-10-07）

本阶段完成第 7 节全部实施步骤。最终事件名为 `patchouli.events.memory.changed`，登记为 `WriteIntentRegistry`，操作端口与进程通道为 `ProcessOperations` / `ProcessOperationChannel`，中立解析结果为 `ReferenceResolution`。Alice 的旧写入意图运行时、引用 resolver 与原子缓存已删除；CPU 不再返回物化任务，任务进程从登记认领本进程意图后封口。

与实施前口径的核对：

- 第 8 节第 7 项沿用现有结算载荷：settled 校验 `intent_id`；failed/cancelled 的既有载荷只有 alias，继续按不可复用 alias 匹配，若提供 `intent_id` 则也校验。未扩展既有公开事件载荷。
- UPDATE 继续只接受正式 atom，settled redirect 不作为 UPDATE 基础；不可读 redirect 清空 canonical 引用与原子，并移除可能在 UPDATE focus 中含目标身份的 pending 快照。
- 操作通道关闭会取消在途冷读，避免进程已取消 PENDING 后才登记新意图；同步关闭通道、取消意图与释放租借均先于异步清理。
- FAILED 句柄没有 settlement 载荷时仍渲染失败状态，不再落入 expired 文案。
- CALL 目标 Profile 本地缓存、SEARCH 与引用记录的直接 Patchouli 调用、CPU 过渡身份均保留；实时派发、执行线程与事件重试/补齐仍属后续范围。finalize 失败后 MATERIALIZING 不补偿，结算句柄保留到重启。
