# v0.7.2 版本收尾审计

本记录冻结 2026-11-01 的版本范围、版本目标判定、收尾分支的改动、遗留事项与验证结果。核对基线为 master `505013f7`（v0.7.1 发布之后的 PR #149–#155），加上收尾分支 `release/v0.7.2` 的升版与文档收尾。当前实现从[项目总览](../../PROJECT.md)进入，生成链路的当前事实见 [Patchouli 生成](../../patchouli/generation.md)。

v0.7.2 内容收尾完成，Python 规范版本、运行时版本与前端包版本统一为 `0.7.2`。发布标签定为 `v0.7.2`，合并后创建；本次没有创建 tag，也没有发布产物。下文的“通过”只指所列的验证边界。

## 1. 版本目标与判定

版本目标（owner，2026-10-30）：生成质量。v0.7.1 让 Claude Code 的日常使用开始产生记忆，真实使用随即暴露出生成链路的问题，v0.7.2 由这些问题驱动 Patchouli 核心机制的改进。计划的准入（owner，2026-10-30）：计划之间不预设先后，各方向在阻塞问题决定、能够立即执行时建立计划。

验收方向要求以 Claude Code 的真实会话验收，不只依靠离线测试。生成材料修正与查重与更新两份计划的真实会话实测按 owner 决定（2026-10-31）随日常使用进行，不作为归档条件；多条提取的计划同样把真实会话中的结算定为随日常使用观察（该计划第 9.3 节）。ROADMAP 第 4.3 节的验收逐条判定：

| 验收 | 判定 | 依据 |
|:---|:---|:---|
| 生成材料没有单轮截断，结算来源可以回查到已折叠的轮次 | 不截断：达成，有真实结算样本；回查已折叠的轮次：由测试覆盖，真实会话中尚未出现折叠话题 | 生成材料修正上线后，本机常驻后端在 2026-11-01（UTC 02:43–06:36）对 Claude Code 会话结算了 4 个话题。各次记忆创建 Artifact 中生成视图的长度为来源交互记录 JSON 的 37%–56%（JSON 含结构开销），修正前生成视图只剩导入原文的 8%（[生成材料 Todo](../todo/generation-material-filtering-and-truncation.md)）。4 份来源 InteractionArtifact 的折叠记录都为空：本机 `fold_token_threshold` 为 131072，这些话题没有达到折叠规模。结算冻结全部交互与折叠记录、折叠过的话题经生成管线写出来源 Artifact，分别由结算任务的单元测试与生成管线的集成测试覆盖（[Artifacts](../../patchouli/artifacts.md)） |
| 一个话题中的多项决定分别形成可检索的记忆 | 离线验收达成；真实会话样本待日常使用 | [多条提取](./v0.7.2-multi-memory-extraction.md)第 12.1 节：以生产提取器与引擎处理三个真实话题，分别得到 15、12、4 条记忆，没有截断，别名互不冲突；G-1 的离线回放中，现行单条提取在 10 个话题上各只留下一条，一次调用输出列表得到 73 条。本机常驻后端仍运行 PR #155 之前的代码（`/health` 返回 `0.7.1`），真实会话还没有经过多条提取 |
| 两条覆盖链等真实样本在新的查重与更新机制下得到可解释的结果 | 回放达成；真实会话中尚未触发合并 | [查重与更新](./v0.7.2-dedup-merge.md)第 12.3 节：以真实 Librarian 模型依次合并两条链的各个版本，最初版本中被覆盖规则冲掉的内容都得到保留。本机后端以新查重规则重启后的两次真实查重相似度为 0.693 与 0.600，都判为新建 |
| Claude Code 显式写入与更新的结果经 Patchouli 生成链结算，能被之后检索到 | 达成 | [plugin 模式开放 WRITE 与 UPDATE](./v0.7.2-plugin-write-update.md)第 12 节阶段三：在交互式 Claude Code 中实测，写入返回 pending alias，生成约 0.6 秒完成，随后的读取重定向到正式记忆，检索能找到它；对它的更新经 Mode C 生成新版本，读取得到更新后的内容；带写入的轮次回流时落在写入派发的话题 |

四个方向都已实施并归档。多条提取与先落库再合并在真实会话中的表现，要在常驻后端以本版本代码重启后随日常使用积累；第 7 节列出由此带来的保留限制。

## 7. 保留限制

- 多条提取与先落库再合并还没有真实会话样本：本机常驻后端仍运行 PR #155 之前的代码，以新查重规则重启后的两次真实查重都判为新建。真实会话中也还没有出现折叠话题。
- 生成链路的已知限制写在 [Patchouli 生成](../../patchouli/generation.md#8-当前限制)第 8 节：
  - 同一次结算的多条草稿之间不互相查重；
  - 中途写入失败时这一批的合并不提交；
  - 一段话题的全部草稿共用一次调用的输出上限，截断时任务失败；
  - 拆分粒度没有校验；
  - 查重分不开同一工作与同项目的其他记忆，误判的两条也会被合并；
  - 同一工作的各阶段不断并入同一条记忆，正文持续变长；
  - 新建到合并完成之间，检索同时看到两条。
- G-1 回放与多条提取的验收样本都来自 Claude Code 开发 HiveMemory 的会话，内容高度同质，结论能否推广到其他领域未知。
- 任务进程表、会话与压缩检查点、写入意图登记、读取视图缓存、WorkspaceAsset working set 与本地 Work Queue 仍是进程内状态，不承诺跨重启恢复。
- 浏览器界面没有人工验收。
- 开发库中留有真实使用与验收写入的记忆、话题与交互 Artifact。
