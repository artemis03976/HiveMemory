# v0.7.0 任务进程拥有执行流

> **文档状态**：Archived（2026-10-19）。两个阶段均已实施、验收并完成 code review，实施记录见第 11 节。当前事实见 [任务进程](../../workspace/task-process.md)与[子系统公共契约](../../contracts/subsystem-contracts.md#4-cpu-端口与-alice-实现)第 4 节；本文冻结，不再演进。

**问题**：任务进程现在只是一份被动的状态容器。它的阶段由交付方逐项拉取一串异步生成器来推进，执行流属于 HTTP 连接。进程表、句柄与关闭协议都已经建好，但进程既不能独立于读取方运行，也没有唯一的退出路径。停止、断连、关闭与部分输出都要穿过这条拉取链路，于是出现了按拉取包装的子 task、结果槽、多出口收尾和时序不变量。

**本计划的做法**：让任务进程持有自己的 task 与输出通道，交付方只订阅通道，或等待进程结束。断连变成一次带原因的停止请求，和用户停止走同一条路径。进程无论以哪种结局结束，都在自己的 task 中收尾。CPU 端口改为“推送交互事件、返回终态结果”。

停止规则、阶段顺序、资源登记、SSE 契约与会话语义都保持不变。

## 1. 背景和问题

1. **进程不拥有执行流**。阶段推进的链路是：chat 路由的 pull task → `TaskProcessService._deliver_stream` → `TaskProcessRunner.run`（生成器）→ `AliceCPU._execute`（生成器）→ `AgentRunStream._events`（生成器）。没有人拉取，Gateway、prepare 与 Actor 都不会前进。`TaskProcess.owner_task` 记录的是首次拉取的 task；交付方每次拉取都可能换一个 task。
2. **停止要穿过拉取链**。
   - chat 路由每个事件新建一个 pull task，并每 0.1 秒检查一次断连。
   - 执行器每拉取一项，就用 `_run_interruptible` 再新建一个子 task，停止只能取消当时那个子 task。停止如果落在两次拉取之间，只会记录一个标志，要等下一次拉取才生效。
   - 生成器被关闭或取消时不能返回值，所以 CPU 的部分输出只能经 `CPURunHandle.result_slot` 从旁路回填。
3. **多出口收尾**。正常结束、拉取中停止、两次拉取之间停止、断连和异常各自收尾：
   - Actor 阶段与关闭流程中，`revoke_threads` 调用 4 处，`_accept_checkpoint` 调用 3 处，另有一个 `(CancelledError, GeneratorExit)` 分支。
   - `close()` 会从执行器收尾、交付收尾、路由收尾和 shutdown 多处到达，幂等只能靠工作集里的资源“只取出一次”保证。
   - 正确性依赖“封口、会话追加、进入 finalize 与登记提交任务之间没有 await/yield”这类时序不变量。
4. **关闭在请求的取消上下文中执行**。断连时，sse-starlette 会取消整个 anyio 任务组，交付生成器的 finally 运行在已取消的作用域中。anyio 是 level cancellation：作用域保持已取消状态时，其中每个 await 都会再次被取消。进程的关闭、finalize 等待与 cleanup 却运行在交付方的 finally、路由收尾和 pull task 里，现有实现只能依靠重复关闭的幂等和 shield 循环来兜底。
5. **系统关闭依赖交付方**。`TaskProcessService.shutdown` 只能发出停止，然后等待交付方自行收口（`TaskProcess.closed`），超过 `workspace.process.shutdown_wait_seconds` 后再并发兜底关闭；从未开始运行的进程要单独处理。
6. **推拉错配**。Alice 内部是推模型：runner task 把事件写进容量 256 的有界队列，压缩进度还要等消费方确认。进程层却是拉模型。停止信号要从拉取链传到 Alice 的 runner，执行结果要经结果槽从旁路传回来。
7. **与已定方向冲突**。被动请求没有交付方；controller 模式的外部 harness 要等产物回流（任务进程 Idea Q-8）；对话流式同步到 Patchouli（owner，2026-10-13）相当于第二个消费者。这些都要求进程能独立于读取方运行。
8. **历史原因**。Chat Run 生命周期 Idea 当年延后候选 A，理由是独立 Job “只增加 registry、task、队列和关闭协议”。如今进程表与句柄、关闭协议（`close_process`、`closed`、shutdown 等待、响应收尾兜底）都已实现，task 与队列也存在于 Alice 内部，延后要避免的代价已经付出。本计划只取候选 A 的“执行所有权”部分，产品部分仍按该 Idea 的启用条件处理（第 2.2 节）。

## 2. 目标与非目标

### 2.1 目标

1. 任务进程开始运行时创建并持有自己的 task，阶段推进不依赖交付方拉取。
2. 交付改为订阅：流式交付订阅进程的输出通道，非流式交付等待进程 task 交出终态。交付方离开时只退订，并以交付方给出的原因请求停止。
3. 进程只有一条退出路径。进程 task 自己完成关闭流程、撤销进程 context、从进程表注销并释放会话认领；外部只需要关闭从未启动的进程，以及在系统关闭超时后硬取消进程 task。
4. Actor 阶段只用一个可中断子 task。线程 context 的撤销与检查点的接受各只在一处发生，不再依赖时序不变量保护交付方离开的时机。
5. 系统关闭改为：停止全部进程 → 在等待上限内等待进程 task 结束 → 超时后硬取消。不再依赖交付方收口。
6. 阶段二把 CPU 端口改为推送交互事件、返回终态结果，删除运行句柄、结果槽与 CPU 输出联合类型；Alice 内部的队列、runner task 与进度确认随之删除。
7. 第 4.9 节列出的行为保持不变，有意的变化只有第 4.10 节所列几项。

### 2.2 非目标

- 断连后继续运行并保存本轮、断线重连、多订阅者、输出重放与进程状态查询。这些是候选 A 的产品部分与候选 B，仍按 Chat Run 生命周期 Idea 的启用条件处理。本计划保留“断连即停止并丢弃”的现行策略，但不阻止日后修改。
- 停止规则本身：可中断阶段、进入 Actor 前统一检查一次、FINALIZE 拒绝停止，都不改变。
- 进程跨重启持久化，以及交互被接纳后即关闭进程（任务进程 Idea Q-1）。
- CPU 边界的中立性：交互事件的词汇与输入清单的形状保持现状（成因基线第 3.2 节，未排期）。
- 访问 context、线程 context 与授权规则。
- RuntimeEvent 的事件名与载荷收敛（Chat Run 生命周期 Idea 候选 C），以及 `agent.run.cancelled` 的 `close_reason` 取值。
- 收敛清单第 3.3 条（`CPUExecutionResult` 的枚举值处理）。

## 4. 目标设计

### 4.1 对应关系

| 操作系统 | AE2 | 目标模型 | 现在 |
|:---|:---|:---|:---|
| 进程有自己的执行流，由内核调度 | 合成任务提交后在 Crafting CPU 中独立运行 | 进程 task，由进程持有、由事件循环调度 | 交付方的拉取 |
| 程序代码段与进程数据分离 | — | `TaskProcessRunner`（共享）与 `TaskProcess`（每个进程一份） | 已经如此，保留 |
| stdout 管道 | 合成状态界面 | 输出通道，交付方订阅 | 生成器链 |
| 读取方离开（SIGPIPE / SIGHUP） | 关闭合成终端不取消任务 | 退订，并以交付方给出的原因请求停止（现行策略） | 拆调用栈 |
| SIGINT | 状态界面的取消按钮 | `/chat/stop` 取消当前可中断阶段的子 task | 相同，保留 |
| 不可中断睡眠，挂起的信号在返回点处理 | — | prepare 与分配期间的停止，在进入 Actor 前生效 | 相同，保留 |
| do_exit：唯一退出路径并释放资源 | 取消时归还预留材料 | 进程 task 的收尾 | 多处关闭，靠幂等兜底 |
| wait() 取回退出码 | — | 非流式交付等待进程 task 的终态 | 拉完整条生成器 |
| SIGTERM，超时后 SIGKILL | — | 系统关闭：停止 → 等待 → 硬取消 | 等待交付方收口 |

### 4.2 进程 task 与输出通道

- **进程 task**：`TaskProcess` 持有进程 task 与输出通道，取代 `owner_task` 与 `closed`。注册入口在交付方首次运行进程时，以自己的驱动协程创建进程 task：先执行 `TaskProcessRunner.run(process)`，再在 `finally` 中撤销进程 context、从进程表注销、释放会话认领，最后结束输出通道。生命周期仍归注册入口，编排与资源关闭仍归执行器，两者都在进程 task 中运行。
- **输出通道**：放在 `workspace/process/outputs.py`，与阶段产出和交付投影同处一个模块，只允许一个订阅者。
  - **容量**：交互事件受容量限制，沿用 Alice 现有队列的容量 256 作为模块常量，不新增配置键。订阅者在线而通道已满时，进程的写入阻塞，保留现有背压。
  - **不阻塞收尾**：终态产出与结束标记不受容量限制，不会因订阅者慢而阻塞进程收尾。
  - **离开后**：订阅者离开时，唤醒阻塞在写入上的进程；此后的写入直接丢弃。
  - **订阅者看到的顺序**：阶段产出 → 终态产出 → 结束标记。结束标记在进程关闭完成之后才发出，因此正常结束时，SSE 响应仍在进程关闭之后结束，与现状一致。
- **启动时机**：沿用“首次运行时开始”。注册成功但交付生成器从未开始迭代时，进程 task 不会创建，仍由路由的响应收尾调用 `close_process` 关闭进程。

### 4.3 交付：订阅与等待

- **签名**：`run_process(handle, *, stream=True, detach_reason="stream_closed")`。`stream` 的含义不变；`detach_reason` 是交付方离开时使用的停止原因。
- **流式交付**：启动进程 task 后订阅通道，按现有 `stream_events` 投影产出，`ProcessFailed` 照旧翻译为 `error` 事件。
  - 生成器被关闭或被取消时，只退订；进程尚未记录终态时，以 `detach_reason` 经与 `cancel_process` 相同的实现请求停止，发布同样的事件。
  - 交付方不等待进程 task，也不在自己的取消上下文中执行任何关闭步骤。
- **非流式交付**：启动进程 task，通道从一开始就处于无订阅者状态，然后等待 task 的终态产出，按现有规则组装 `NonStreamingResult`，`ProcessFailed` 原样上抛。调用方在等待中被取消时，以 `detach_reason` 请求停止后传播取消。
- **chat 路由**：
  - 删除断连轮询、pull task 和 `_cancel_pull`，改为直接 `async for` 交付生成器，并传入 `detach_reason="client_disconnected"`。断连由 sse-starlette 取消生成器触发，不需要路由先行取消。
  - `_RegisteredProcessResponse` 的收尾兜底只保留“生成器从未开始迭代”这一种情形。
- **`close_process(handle)`**：
  - 进程未启动：直接执行关闭流程。
  - 进程已启动：仍在运行时以 `stream_closed` 请求停止，然后等待进程 task 结束。这个等待可以被调用方取消，取消不影响进程自身的收尾。
  - 句柄无效时仍是空操作。

### 4.4 编排骨架

- **形态**：`TaskProcessRunner.run(process)` 改为协程。阶段产出经 `await process.outputs.send(...)` 写入通道；终态产出既写入通道，也作为返回值。trace context 在进程 task 内设置，阶段顺序、阶段授权与事件发布位置不变。
- **可中断阶段**：Gateway 与 Actor 各用一个子 task。`_run_interruptible` 的入口检查与“停止取消子 task”的判定保留；“驱动方被取消”只剩一种来源，即系统关闭的硬取消，原样传播。
- **finalize**：提交任务由进程在发出 `Finalizing` 之前创建，并以 `join_shielded` 等待，所以只有硬取消会遇到它，而硬取消也要等提交结束。交付方离开打断不了 finalize，“没有 await/yield”只需要保证“提交任务在发出 finalizing 之前创建”。
- **工作集**：只保留关闭时仍需释放或补偿的资源，即 prepare 结果、附件租借、线程 context、派发话题与实际使用的附件。CPU 输出流、结果槽、执行结果与提交任务都改为阶段函数里的局部状态。
- **关闭流程**：`close(process)` 在进程 task 的 `finally` 中执行一次，依次是：
  1. 同步撤销仍登记的线程 context，同步释放附件租借；
  2. 对尚未交接的 prepare 结果重新阶段授权并请求 cleanup。

  终态兜底（`closed_before_terminal`）只用于硬取消。`close` 仍保持可重复执行，作为防御，但正确性不依赖重复关闭。

### 4.5 Actor 阶段

执行器抽出一个 Actor 阶段函数（取代 `run()` 中的三层嵌套），它在一个可中断子 task 中驱动 CPU，并在自己的 `finally` 中撤销全部线程 context。线程 context 的撤销只在这里发生，关闭流程中的撤销只是兜底。

- **阶段一，端口不变**：子 task 一次性迭代 CPU 的输出流，把交互事件写入通道，取得终态结果后关闭输出流。
  - **停止**：停止取消子 task 时，无论子 task 正在等 CPU 的下一项，还是阻塞在通道写入上，都会在 `finally` 中关闭输出流，促使 CPU 同步回填结果槽。
  - **结果**：Actor 阶段函数优先采用 CPU 交回的终态，其次采用槽中的结果，都没有时按无输出取消处理，与现状一致。
- **阶段二，端口改为推送 + 返回**：子 task 直接 `await` CPU 的 `execute`，交互事件经 sink 写入通道。
  - **停止**：CPU 以返回的结果表达停止后的结局（第 4.8 节）。Actor 阶段以这个结果为准，返回之后不再按停止标志改写为取消，与“停止晚于 CPU 终态时沿用 CPU 的结局”一致。
  - **CPU 原样传播取消时**：按无输出的取消处理。
- **检查点**：拿到结果（或确认没有结果）后，在判断丢弃与有无输出之前，同步接受一次检查点。普通执行异常不接受候选值，与现状一致。
- **硬取消**：进程 task 被硬取消时，子 task 会随之被取消。在 asyncio 中，如果被等待的子 task 吞下取消并返回结果，等待方的取消会丢失。因此 Actor 阶段函数在子 task 返回后，按进入时记录的 `cancelling()` 判断进程 task 自身是否已被取消：先撤销线程、接受检查点，再重新抛出取消。

### 4.6 停止、离开与关闭

- **停止**：`cancel_process` 的两种调用形式、进程控制授权、`request_stop` 的判定顺序、事件与 `not_found` 语义都不变。
- **交付方离开**：等同于以交付方给出的原因发出一次停止。
  - **原因**：HTTP 为 `client_disconnected`，其他交付方默认 `stream_closed`，两者都属于丢弃输出的原因（`DISCARDING_STOP_REASONS`）。
  - **生效**：在当前响应点生效——Gateway 或 Actor 子 task 立即被取消；处于 prepare 或分配时，进入 Actor 前生效；已进入 FINALIZE 时拒绝，提交照常完成。
  - **之后的流程**：进程沿 `_ProcessCancelled` 路径记录 cancelled 终态并发布 `chat.run.cancelled`（带生效阶段），然后在进程 task 中完成关闭。
- **关闭的完成者**：关闭由进程 task 完成，交付方的取消上下文不参与。断连时，SSE 响应可以早于进程关闭结束；进程的 cleanup 与会话认领的释放照常完成，系统关闭会等待它们。

### 4.7 系统关闭

`TaskProcessService.shutdown()` 的步骤：

1. 未启动的进程直接关闭；
2. 已启动的进程逐个以 `system_shutdown` 请求停止；
3. 在 `shutdown_wait_seconds` 内等待全部进程 task 结束；
4. 超时仍未结束的，取消并 join 其进程 task。

硬取消时，进程 task 照常执行收尾，finalize 中的提交仍要等它结束。返回之前，全部进程都已关闭，之后才清空会话服务，顺序不变。`TaskProcess.closed` 与“等待交付方收口”的逻辑删除。

### 4.8 CPU 端口（阶段二）

- **签名**：`async def execute(manifest, *, access, generation_options, events) -> CPUExecutionResult`。`events` 是 workspace 定义的交互事件 sink（`async (event) -> None`），事件仍是带 `event` 与 `data` 的字典，进程原样转交。`CPURunHandle`、`CPUResultSlot` 与 `CPUOutput` 删除。
- **取消语义**：CPU 收到原生取消后完成收尾，并返回 `cancelled` 结果，结果携带已产生的输出与已完成的检查点。内部各层仍原样传播取消，只在 CPU 的最外层转换为返回值；没有转换、直接传播取消的 CPU 按无输出取消处理。CPU 自报的结局仍由 `status` 表达，实现抛出的普通异常由进程按失败处理。
- **Alice**：
  - 运行服务在最外层把取消收尾得到的结果作为返回值，现有的结果槽逻辑改为局部状态；`AliceCPU.execute` 直接 await 运行服务。
  - 以一个转发到进程 sink 的运行输出端口，取代 `AgentRunStream`、`QueueAgentRunOutput` 与 `AgentRunStreamAdapter`。帧元数据、`stream_sequence`、CALL 起止事件与 `context_compaction` 事件的内容不变。
  - 压缩进度不再等消费方确认（第 4.10 节）。
  - `agent.run.*` 事件及其载荷不变。
  - 未启动或已停止时，在首次 await 时抛出 `AliceUnavailableError`。
- **测试 CPU**：`ScriptedCPU` 改为同一形态，继续覆盖事件、终态、挂起、异常、取消结果和不产出终态的情形。“不产出终态”在新端口下改为“取消时不返回结果、直接传播”。

### 4.9 必须保持的行为

- **SSE**：
  - 事件名、字段与顺序不变：`process_id` → `memory_refs` → CPU 交互事件 → `run_status(finalizing)` → `done`，命令路径为 `command_result` + `done`；
  - 每个进程至多一个 `done`；
  - 编排异常仍先记录失败终态并完成关闭，再翻译为 `error`。
- **停止**：
  - 只有 Gateway 与 Actor 两个阶段响应停止；prepare 与分配期间收到的停止在进入 Actor 前生效；FINALIZE 与 TERMINAL 拒绝停止；
  - 首次停止的原因固定，重复停止不重复取消；
  - 下游只传播原生 `CancelledError`，私有的 `_ProcessCancelled` 不进入子系统。
- **部分输出**：用户停止时保存有输出的轮次；交付方离开与系统关闭时丢弃本轮，不写会话、不提交；停止晚于 CPU 终态时沿用 CPU 的结局。
- **检查点**：CPU 关闭、线程撤销后，先接受已完成的检查点，再判断丢弃与有无输出；本轮无输出或被丢弃时也会接受；同一次执行只尝试一次。
- **线程 context**：CPU 执行结束、finalize 之前全部撤销；Actor 阶段提前结束时，在交付终态之前撤销；关闭兜底先于任何 await。
- **资源**：附件租借无论哪种结局都会释放；prepare 成功而 finalize 未成功时请求 cleanup；进程 context 随进程关闭撤销；会话认领在注销后释放。
- **finalize**：一旦发出 `finalizing`，提交就由进程持有并等待完成；有输出的 cancelled/failed 结局，其 `chat.run.*` 终态晚于 finalize。
- **观测**：`chat.run.*` 的事件类型与用户停止路径上的事件顺序不变；`agent.run.*` 不变。
- **非流式交付**：结果形态不变。
- **系统关闭**：`system_shutdown` 丢弃本轮；已进入 finalize 的进程等提交完成；返回之前全部进程已经关闭。

### 4.10 有意的行为变化

1. **进程按自己的节奏推进**：订阅者暂停时，进程最多先行一个通道容量（256 个交互事件）后才阻塞；停止在任何时刻都立即取消当前可中断阶段，不再等待下一次拉取。
2. **压缩进度不再暂停 CPU**：现在压缩开始与完成时，CPU 会停在消费方继续拉取之前；改为与其他交互事件一样只受通道容量背压。阶段一起进程持续拉取，这个暂停已经名存实亡；阶段二随适配器删除。
3. **交付方离开的观测形态统一**：发布 `chat.run.cancel_requested`（原因为 `client_disconnected` 或 `stream_closed`），停止生效后按阶段发布 `chat.run.cancelled`。带 `message` 与 `close_reason` 的“终态前关闭”形态只剩硬取消一种来源。`close_reason` 不在公开契约中。
4. **关闭不再运行在请求的取消上下文中**：断连时，SSE 响应不再等待进程关闭；系统关闭不再等待交付方。
5. **不再按事件创建 task**：每个事件少建两个 task，也不再做断连轮询。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| asyncio 中，被等待的子 task 吞下取消并返回结果时，等待方的取消会丢失 | 只有 Actor 阶段存在“CPU 把取消转为返回值”的情形；第 4.5 节以 `cancelling()` 判定，第 8 节第 9 项覆盖 |
| 进程 task 中出现未处理的异常，又没人取回 | `run` 把普通异常收口为 `ProcessFailed` 终态；进程 task 只会以终态或取消结束，取消由系统关闭取回 |
| 进程先行于订阅者，内存占用增加 | 交互事件受 256 容量限制，与 Alice 现有队列相同；终态与结束标记只有常数个 |
| 依赖拉取时机的测试改写量大，容易引入时序不稳 | 统一用测试 CPU 的事件同步注入点，不使用固定 sleep；阶段一先改进程测试，再改路由与集成测试 |
| 断连时 SSE 响应早于进程关闭结束，客户端立即对同一会话重发，可能遇到会话仍被认领 | 按现有会话忙碌规则显式拒绝，不排队、不抢占；阶段一核对前端断连后的重发路径，并在应用服务文档中写明 |
| 观测形态变化影响 Kernel Terminal 的展示 | 事件类型不变，只有交付方离开时的 cancelled 载荷改为带 phase 的常规形态；前端不读取 `close_reason`（2026-10-19 核对） |
| 阶段二修改端口，非 Alice CPU 的实现方式随之改变 | 端口只有 `AliceCPU` 与测试 CPU 两个实现；推送形态对外部 harness 的驱动更自然（Q-8），不为旧形态保留适配器 |

待决问题：无。通道容量沿用 256，交付方离开的原因沿用 `client_disconnected` 与 `stream_closed`，均为默认值，可以在计划评审时调整。

### 11.1 阶段一：进程拥有执行流（2026-10-19）

按第 7 节阶段一的四项完成实施，CPU 端口与 Alice 未改：

- **进程 task 与输出通道**：`TaskProcess` 以 `task` 与 `outputs` 取代 `owner_task` 与 `closed`；输出通道 `ProcessOutputChannel` 与容量常量 `OUTPUT_CHANNEL_CAPACITY`（256）位于 `workspace/process/outputs.py`。注册入口的驱动协程 `_drive` 是唯一退出路径：执行器的 `run`（收尾含 `close`）之后，同步撤销进程 context、注销、释放会话认领，最后结束通道。
- **执行器**：`run` 改为返回终态产出的协程，主路径拆为 `_run_stages`，Actor 阶段抽为 `_run_actor`，提交拆为 `_seal_and_finalize`；工作集只保留 prepare 结果、租借、派发话题、实际使用的附件与线程 context。
- **交付**：`run_process` 增加 `detach_reason`；流式交付订阅通道，离开时只退订并经 `_request_stop` 请求停止；非流式交付以 `asyncio.shield` 等待进程 task，被取消时请求停止后传播。非流式结果的组装移入 `outputs.non_streaming_result`。
- **chat 路由**：删除断连轮询、pull task 与 `_cancel_pull`，以 `aclosing` 包裹交付生成器并传入 `client_disconnected`；路由不再使用 `Request` 参数。
- **系统关闭**：未启动的进程直接关闭；已启动的以 `system_shutdown` 停止，等待上限后硬取消并等待结束。

实施中对第 4 节的细化（均不改变第 4.9 节的行为）：

1. **未启动进程的关闭也在进程 task 中执行**：`close_process` 与 `shutdown` 为从未运行的进程创建只执行关闭流程的进程 task，再与已启动的进程一样等待它结束。这样关闭从不运行在调用方的取消上下文中，`_start` 也能据 `task` 拒绝在关闭之后开始运行。
2. **CPU 输出流在子 task 结束后由 Actor 阶段关闭**：子 task 只迭代输出流并写入通道；停止取消子 task 后，Actor 阶段在等待子 task 的 `finally` 中关闭输出流，再读取结果槽。停止晚于 CPU 终态时只记录停止，不会打断 CPU 关闭输出流的收尾；子 task 交回的终态记在阶段局部状态中，停止被识别时仍优先采用。
3. **响应收尾还关闭停在 `yield` 处的路由生成器**：sse-starlette 在等待 send 时被断连取消，生成器停在 `yield` 处，其 `finally` 只会在垃圾回收时运行。`_RegisteredProcessResponse` 的收尾因此在生成器已经开始时关闭它（交付方随之以 `client_disconnected` 退订），未开始时经 `close_process` 关闭进程；两种情形都不等待进程关闭。
4. **硬取消遇到 finalize**：提交以 `join_shielded` 等待，硬取消要等提交结束；提交成功时照常记录 CPU 的结局再传播取消，失败时记录告警并由关闭流程按取消兜底。“终态前关闭”事件的 `close_reason` 取停止原因，缺失时记为 `system_shutdown`（硬取消只来自系统关闭）。
5. **线程撤销晚于 CPU 关闭**：按第 4.5 节，线程 context 在 CPU 关闭输出流之后撤销；原“断流时先撤销线程、再等待 CPU 关闭”的行为不再保留，交付方离开与用户停止走同一条路径。

前端核对（第 9 节风险一行）：断连后前端不自动重发；`endWithoutTerminal` 只提示连接错误，重发只经用户触发的 `retryMessage`，会话仍被认领时按现有会话忙碌规则显式拒绝。应用服务文档的相应说明在阶段二晋升时写入。

测试：验收测试写入归属层的现有文件。新增输出通道的容量、终态不受限与离开语义，订阅者暂停时进程仍完成，五种结局的唯一退出路径，交付方离开不等待进程关闭（`test_chat_run_control_contract.py`）；Actor 中停止在等 CPU 与阻塞于通道写入时均立即生效（`test_gateway_chat_flow.py`）；交付方离开的停止事件与硬取消的“终态前关闭”事件（`test_process_events.py`）；路由断连在两种取消时机下都以 `client_disconnected` 关闭交付（`test_chat.py`）；会话完成中的用户停止、finalize 后离开、CPU 收尾期间离开、系统关闭的停止、硬取消与 finalize 等待（`test_session_completion.py`）。删除只守护旧契约的测试：断连轮询与 pull task、“终态前关闭”的断流形态、两次拉取之间的停止、关闭被交付方取消后的再次关闭、断流时先撤销线程，以及与新用例重复的 CPU 拉取停止、交付结束收口与调用方取消用例。

### 11.2 阶段二：CPU 端口推送 + 返回，以及收尾（2026-10-19）

按第 7 节阶段二的三项完成实施：

- **CPU 端口**：`CPUPort.execute(manifest, *, access, generation_options, events) -> CPUExecutionResult`，`events` 为 `CPUEventSink`；`CPURunHandle`、`CPUResultSlot` 与 `CPUOutput` 删除。
- **Alice**：`AgentRunService.run_agent` 不再接收结果槽，是 Alice 作为 CPU 的最外层：收到原生取消时发布 `agent.run.cancelled`，把执行器已收口的帧终态（或只有已完成的检查点）组装为 cancelled 结果返回；两者都没有时没有可交回的内容，原样传播取消，与原结果槽为空时的进程行为一致（`chat.run.cancelled` 仍带 Actor 生效阶段）。`alice/interface/stream.py` 删除，由 `alice/interface/output.py` 的 `SinkRunOutput` 直接推送到进程的 sink；帧元数据、`stream_sequence`、CALL 起止与 `context_compaction` 的内容不变，`agent.run.cancelled` 的 `message` 与 `close_reason` 沿用原流式输出的取值。`AliceCPU` 不再接收流式适配器，未启动或已停止时在 await `execute` 时抛出 `AliceUnavailableError`。
- **Actor 阶段**：子 task 直接 await CPU 的 `execute`，交互事件经 sink 写入输出通道。CPU 的返回值记在阶段局部状态中：停止晚于 CPU 返回时仍以它为准，CPU 原样传播取消时按无输出取消。`_run_interruptible` 在子 task 正常结束后同样按进入时的 `cancelling()` 判断硬取消并重新抛出，Gateway 与 Actor 共用这一判定；Actor 阶段在 `finally` 中先撤销线程、接受检查点，硬取消因此也不丢检查点。

测试：测试 CPU 改为同一形态，取消时配置了 `cancelled_result` 就返回它、否则原样传播，`linger_on_cancel` 在硬取消到达后同样按此决定；新增 `result_returning` 同步点，用于在 CPU 返回之后、进程恢复之前注入停止。Alice 的测试辅助以 `CollectedEvents` sink 与 `run_with_events` 取代基于队列的 `stream_run`，sink 可在指定事件处暂停以注入取消。改写或删除只守护旧契约的测试：结果槽与输出流关闭、缺少终态的协议错误、队列背压与 runner 收尾、压缩进度暂停，以及流式与非流式两种运行入口的对照；`tests/unit/alice/interface/test_stream.py` 改为 `test_output.py`。验收第 8、9 项写入 `tests/integration/alice/`、`tests/unit/alice/interface/` 与会话完成测试的硬取消用例。
