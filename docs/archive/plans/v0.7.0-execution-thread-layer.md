# v0.7.0 执行线程层

> **文档状态**：Archived（2026-10-11）。三个阶段均已完成，事实文档已按最终代码更新。阶段一、二提交为 `33347f8`、`2f609c8`，审查修复为 `db46fad`。本文保存当时的设计、风险和验收证据，当前接口以 [执行线程](../../workspace/execution-threads.md)、[子系统契约](../../contracts/subsystem-contracts.md)第 4.6 节、[MTP 契约](../../contracts/mtp.md)第 3.6、4 节与 [Alice 编排](../../alice/orchestration.md)为准；不表示 v0.7.0 已发布。

本计划让 CALL 派生的子 agent 成为独立的执行线程：子线程以 CALL 目标 agent 的身份运行，按它自己的操作白名单与记忆可见性授权，写入记在它名下。子线程的线程 context 与主线程一样从进程 context 派生，派生请求就是 CALL 的 `agent.call` 操作请求，经操作入口到达进程，由进程完成被调用方的准入、签发与登记；CPU 驱动把它绑定为子帧的提交函数。全部线程 context 在 CPU 执行阶段结束时一起撤销。

设计依据：

- commit `a384688` 版本的执行单元 Idea“子线程的派生、身份与撤销”（2026-10-11 的决定：被调用方自己的白名单与可见性；与主线程一起在 CPU 执行结束时撤销；派生途径、派生授权、子线程认证与默认目标由已有决定推出）；T-1（子线程身份由派生调用确定，派生必须到达进程）；T-2（每个线程一份 context，进程 context 与线程 context 的分工）；T-9（操作请求与单一操作入口）；
- 当前事实：[执行线程](../../workspace/execution-threads.md)、[能力层](../../workspace/capability.md#1-三个调用面)第 1 节，[子系统契约](../../contracts/subsystem-contracts.md)第 4.5、4.6 节，[MTP 契约](../../contracts/mtp.md)第 4 节，[Alice 编排](../../alice/orchestration.md)；
- 已归档：[线程 context 取代执行凭据](../../archive/plans/v0.7.0-thread-context.md)、[Agent 操作白名单](../../archive/plans/v0.7.0-agent-operation-whitelist.md)。

## 1. 背景和问题

- **子 agent 只有名义上的身份**：CALL 派生的子帧沿用主线程的提交函数，它的读取、写入与引用都以主 agent 授权、记在主 agent 名下；被调用方 Profile 只提供人设、模型与语言，子帧的动词集合继承父帧（[Alice 文档](../../alice/README.md)第 9 节的已知限制）。被调用方读不到自己的 PRIVATE 记忆，却能读到调用方的。
- **派生不经过 workspace**：CALL 在 Alice 内部完成派生，workspace 只看到一次 `ResolveCallTargetRequest`，进程不知道出现了一个新的执行线程，也无法限定它的寿命。
- 执行单元 Idea T-2 已确定“每个执行线程一份 context”，线程 context 取代执行凭据后，主线程已按这一形态实现；本计划补上子线程。

## 2. 目标与非目标

### 2.1 目标

1. **子线程的 context**：认证一侧能以被调用方从进程 context 派生子线程 context：沿用进程的驻留 Workspace 与 principal，actor 换为被调用方，派生时做被调用方的 Workspace 准入。
2. **派生经操作入口到达进程**：CALL 的派生请求取代 `ResolveCallTargetRequest`，仍是 actor 操作 `agent.call`；actor API 授权并解析目标 Profile 后交给进程，进程只接受主线程在 CPU 执行阶段内发起的派生，签发、登记子线程 context 并读取被调用方的操作快照。
3. **CPU 驱动绑定子帧的提交函数**：派生结果中的子线程 context 只到 CPU 驱动为止，驱动把它绑定为子帧的提交函数交给 Alice。
4. **子线程按被调用方授权与记账**：子帧的动词集合来自被调用方的操作快照（去掉 CALL），操作以被调用方的白名单与可见性授权，写入意图的发起者是被调用方。
5. **统一撤销**：进程登记本进程的全部线程 context，CPU 执行结束时一起撤销，关闭流程兜底。

### 2.2 非目标

- 外部执行单元：不识别子线程（执行单元 Idea T-1、外部 Actor Idea E-5），本计划只涉及 Alice。
- 子线程在 CALL 返回时提前撤销（2026-10-11 决定与主线程一起撤销）。
- 递归 CALL：子线程仍不能 CALL。
- “谁能调用谁”的细粒度策略：派生的闸门只有调用方的 `agent.call` 与被调用方的准入。
- 跨 Workspace 的目标（执行单元 Idea T-5b）；子线程的目标是驻留 Workspace。
- 子帧的观测标签：子帧仍沿用注册时的 `ExecutionLabels`，标签只用于观测，不参与授权。
- CALL 的 `context_refs`：仍由调用方以自己的 READ 读取，是调用方选择共享的内容。

## 3. 当前状态（2026-10-11 核对）

- **CALL 编排**（`alice/orchestration/sub_agent/`）：`CallContextProvider` 经调用方的提交函数提交 `ResolveCallTargetRequest`（`agent.call`）读取目标 Profile，再逐项提交 READ 解析 `context_refs`；`CallCoordinator` 以 `FrameExecutionPolicy.from_verbs(父帧动词, denied_verbs={"CALL"})` 构造子帧策略，子帧的 `submit_operation` 与观测标签都取自调用方。子帧未成功结束时提交 `CancelIntentsRequest` 撤回它已登记的意图。
- **actor API**：`ActorAgentService.resolve_call_target(request, *, access)` 以 `authorize_thread_operation(access, AGENT_CALL)` 授权，再以调用方的 scope 经 `ProfileResolver` 读取目标 Profile。
- **线程 context**：`WorkspaceAuthenticator.derive_thread_context` 只从进程 context 派生主线程（线程标识固定为 `main`），复制原授予内容，不做准入；执行器经 `ThreadContextLifecycle` 端口派生与撤销，工作集只有一个 `thread_access` 槽位，CPU 执行结束与关闭流程撤销它。
- **操作授权者**：`get_stage_operations` 读取 actor 操作快照，调用面限定在 CPU 分配；`get_thread_process_id` 调用面限定在能力层。
- **提交函数**：`OperationSubmitter` 只有一个泛型 `__call__`；`AliceCPU` 以闭包把线程 context 绑定为提交函数，主、子帧共用。
- **装配**：`SystemAssembler` 先构建 actor API 与操作入口，再构建子系统与任务进程；进程表由 `TaskProcessService` 在内部创建。
- **结构守护**（`tests/unit/architecture/test_access_boundaries.py`）：派生与撤销线程 context 只由执行器调用；能力层与任务进程互不导入（`tests/unit/workspace/test_import_boundaries.py`）。

## 4. 目标设计

### 4.1 线程模型

| | 主线程 | 子线程 |
|:---|:---|:---|
| actor | 进程的 agent | CALL 的目标 agent（同一用户） |
| 派生时点 | 进入 CPU 执行阶段时，由执行器派生（不变） | 主线程的 CALL 派生请求到达进程时 |
| 派生前的检查 | 无（与进程是同一 actor） | 调用方的 `agent.call`；被调用方在驻留 Workspace 的准入 |
| 运行绑定 | 所属进程的 `process_id`，线程标识 `main` | 所属进程的 `process_id`，进程分配的线程标识 |
| 持有者 | CPU 驱动，绑定为主帧的提交函数 | CPU 驱动，绑定为子帧的提交函数 |
| 登记 | 进程工作集 | 进程工作集 |
| 授权 | 进程 agent 的白名单与可见性 | 被调用方的白名单与可见性 |
| 撤销 | CPU 执行结束时一起撤销，关闭流程兜底 | 同左 |

### 4.2 认证一侧：以被调用方派生

- 新增以被调用方派生线程 context 的能力：输入一份有效的进程 context、被调用方的 `agent_id` 与进程分配的线程标识；授予内容沿用进程的驻留 Workspace 与 principal，actor 为同一用户的被调用方。
- 派生时做被调用方的 Workspace 准入（与第 2 阶段相同的 owner 与准入记录检查）；准入失败以 `AdmissionDeniedError` 拒绝，不签发。被调用方不能是保留的 `system`。派生仍不是认证：不重新检查接入登记，不受网关关闭影响；准入与白名单仍在每次授权时即时检查。
- 新 context 记入已签发集合，System 停止时随撤销全部一起撤销。主线程的派生保持不变。
- `ThreadContextLifecycle` 端口相应扩展；派生方法与参数的名称在实施评审时确定。

### 4.3 进程侧：派生、登记与撤销

- 任务进程提供一个线程派生的实现，经端口交给 actor API（端口协议放在能力层与任务进程都可导入的位置，二者仍互不导入）。输入：调用方的线程 context、它的进程关联与被调用方的 `agent_id`。
- 进程按进程关联找到进程，依次检查：进程存在且处在 Actor 阶段；调用方的线程 context 就是本进程登记的主线程 context（按对象身份比较，不读取内容）。不满足时以 `ScopeRequiredError` 拒绝：只有主线程能派生，派生只在 CPU 执行阶段内发生。
- 检查通过后分配线程标识，经生命周期端口以被调用方从进程 context 派生子线程 context，登记进工作集，再以子线程 context 读取被调用方的操作快照（与 CPU 分配相同的快照查询）；返回子线程 context 与快照。
- 工作集改为登记本进程的全部线程 context；执行器在 CPU 返回终态并关闭输出流后一次撤销全部，异常与提前结束路径同样在交付终态前撤销，关闭流程先于任何 await 兜底。
- 装配：进程表由组合根在构建 actor API 之前创建，同时交给注册入口与进程侧的派生实现，避免 actor API 依赖之后才构建的注册入口。主线程与子线程的派生、登记集中在进程侧同一处实现。

### 4.4 CALL 请求与 actor API

- CALL 的派生请求取代 `ResolveCallTargetRequest`，参数仍是 `agent_alias`（未指定时为默认 Profile），对应 actor 操作 `agent.call`，名称在实施评审时确定。
- actor API 的处理顺序：以调用方的线程 context 授权 `agent.call`；以调用方的 scope 读取目标 Profile（目标对调用方不可见与不存在相同）；以 Profile 的 `agent_id` 调用进程侧的派生。任何一步失败都不签发、不登记。
- 入口在 workspace 一侧返回目标 Profile、被调用方的操作快照与子线程 context；入口仍只按请求类型分派。

### 4.5 CPU 驱动与提交函数

- 提交函数增加派生方法：CPU 驱动以发出调用的线程的 context 提交派生请求，取得子线程 context 后绑定为新的提交函数，再把目标 Profile、操作快照与子帧的提交函数交给 Alice。Alice 的运行层（frame、Agent loop、MTP、CALL 编排）不接触 context。
- 泛型 `__call__` 不接受派生请求（它的结果含 context），以 `TypeError` 拒绝。方法与结果类型的名称在实施评审时确定。
- `ScriptedCPU` 与测试辅助随之实现派生方法。

### 4.6 Alice 的 CALL 编排

- `CallContextProvider` 经调用方提交函数的派生方法取得目标 Profile、操作快照与子帧的提交函数；`context_refs` 仍以调用方的提交函数逐项提交 READ。
- `CallCoordinator` 以被调用方的操作快照经 `mtp_verbs_for_operations` 翻译为动词集合（RUN 始终可用），去掉 CALL 后构造子帧策略与提示词；子帧的 `submit_operation` 是子帧的提交函数，观测标签仍取注册标签。
- 子帧未成功结束时，以子帧的提交函数提交 `CancelIntentsRequest`：子线程 context 在 CPU 执行结束之前有效，撤回仍只作用于本进程仍为 PENDING 的意图。
- 错误：调用方缺少 `agent.call` 沿用现有 CALL 权限错误；被调用方未准入或为 `system` 时 CALL 准备失败，以结构化 MTP 错误回填（具体映射在实施评审时确定）；任何失败都不降级为以调用方身份运行子帧。

### 4.7 子线程的操作语义

- 子线程的每个 actor 请求以被调用方的白名单检查对应的 actor 操作，组装的 `IdentityScope` 以被调用方为发起者，资源 owner 按被调用方的可见性过滤：子线程能读被调用方的 PRIVATE 记忆，读不到调用方的。
- 写入意图的 `from_actor` 是被调用方，进程关联不变，completed 时照常由本进程认领并交给 finalize；引用记录同样以被调用方的 scope 记录。
- 已接受的风险（执行单元 Idea，2026-10-11）：调用方持有 `agent.call` 即可让被调用方读取它自己的 PRIVATE 记忆，并经 CALL 的返回值交给调用方。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| `core.access` / 认证一侧 | 以被调用方派生线程 context（含准入）；生命周期端口扩展 |
| `workspace.process` | 进程侧派生实现：查找进程、主线程与阶段检查、登记、快照；工作集登记多个线程 context，执行器统一撤销 |
| `workspace.capability` | actor API 的 CALL 方法改为派生；经端口调用进程侧派生 |
| `workspace.contracts` | 派生请求取代 `ResolveCallTargetRequest`；`OperationSubmitter` 增加派生方法 |
| Alice | `AliceCPU` 为子帧绑定提交函数；`CallContextProvider`、`CallCoordinator` 使用子帧的提交函数与被调用方的动词集合 |
| 组合根 | 进程表提前创建并共享；向 actor API 注入进程侧派生 |
| 行为 | 子帧以被调用方授权与记账；被调用方没有准入时 CALL 失败 |
| 公共路由与数据 | 无 HTTP 路由或持久化格式变化；写入意图与物化任务的 `from_actor` 对子帧写入改为被调用方 |

## 6. 兼容与迁移策略

- 进程内替换，不涉及持久化数据或 HTTP 接口；提交函数与 CALL 请求的契约有破坏性变化，当前只有 `AliceCPU`、`ScriptedCPU` 与测试辅助实现或使用它们，随阶段二一并修改。
- **访问登记**：被调用方必须在驻留 Workspace 有准入记录。随仓库发布的默认登记以用户级记录覆盖该用户的全部 Agent，行为不受影响；只为个别 Agent 配置精确记录的登记，需要为 CALL 目标补充记录，否则这些 CALL 会失败。收尾时在 [System 配置](../../system/configuration.md)补充升级说明。
- **权限变化**：子帧的动词集合由调用方的改为被调用方的，被调用方白名单更宽或更窄时，子帧可用的动词相应变化。

## 7. 实施阶段

三个阶段依次实施，每个阶段结束时全量后端测试通过、可单独审查。

**阶段一：workspace 侧的子线程派生**

1. 认证一侧以被调用方派生（准入、拒绝 `system`），生命周期端口扩展；
2. 进程侧派生实现：查找进程、主线程与阶段检查、分配线程标识、登记、操作快照；
3. 工作集登记多个线程 context，执行器统一撤销；
4. 组合根提前创建进程表并装配派生实现；架构测试更新调用面；
5. 生产 CALL 暂不使用新能力，行为不变。

验收：第 8 节 1–4、10 项。

2. 提交函数增加派生方法，`AliceCPU`、`ScriptedCPU` 与测试辅助实现；
3. `CallContextProvider`、`CallCoordinator` 使用子帧的提交函数与被调用方的动词集合，补充错误映射；
4. 删除 `ResolveCallTargetRequest` 及子帧沿用调用方提交函数与动词集合的路径。

## 8. 测试和验收标准

按[测试设计规范](../../governance/testing/test-design-standards.md)分类；认证一侧、操作授权者、任务进程、操作入口与 Alice 编排使用真实对象，外部 LLM 与存储使用既有替身。

1. 以被调用方派生：子线程 context 的发起者是被调用方，驻留 Workspace 与 principal 与进程相同，线程标识与主线程不同；被调用方准入记录缺失或被禁用、被调用方为 `system`、来源不是有效的进程 context 时拒绝且不签发。
2. 进程侧派生只接受本进程主线程在 Actor 阶段内发起的请求：以子线程 context 发起的派生、CPU 执行结束后（主线程 context 已撤销）的派生均被拒绝且不登记。
3. CPU 执行结束（正常终态、异常、停止、取消、断流）后，主线程与全部子线程的 context 均已撤销，迟到请求以 `ThreadContextRevokedError` 拒绝；finalize 与 cleanup 仍以进程 context 完成。
4. 被调用方的操作快照来自它自己的访问记录（精确记录优先于用户级记录）。
5. 子帧的操作以被调用方的白名单授权：调用方有、被调用方没有的操作被拒绝；被调用方有、调用方没有的操作可以执行。
6. 子帧的资源可见性按被调用方：能读被调用方的 PRIVATE 记忆，读不到调用方的 PRIVATE 记忆。
7. 子帧的 WRITE 登记的 `from_actor` 是被调用方，进程关联不变，completed 后被认领并交给 finalize；子帧失败时以子帧的提交函数撤回它的意图，只影响本进程仍为 PENDING 的记录。
8. 子帧的动词集合与提示词来自被调用方的快照并去掉 CALL；子帧不能派生。
9. 调用方缺少 `agent.call`、被调用方未准入或目标 Profile 对调用方不可见时，CALL 以结构化错误失败，不创建子帧、不以调用方身份运行。
10. 结构：派生与撤销线程 context 只在进程侧调用；能力层与任务进程仍互不导入；输入清单、frame 与 MTP 上下文不携带 context。
11. 结构：Alice 运行层不接收 context，泛型提交拒绝派生请求；生产代码不再引用 `ResolveCallTargetRequest`。
12. 确定性 HTTP chat E2E：被调用方与调用方的白名单不同，子帧按被调用方授权，子帧的 WRITE 记在被调用方名下并在 completed 后进入 finalize；现有 chat E2E 全部通过。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| 调用方经被调用方读取其 PRIVATE 记忆 | owner 已接受（执行单元 Idea，2026-10-11）；闸门是 `agent.call` 与被调用方准入，更细的策略不在本计划 |
| actor API 经端口调用任务进程，形成能力层到进程的运行时依赖 | 只经一个派生端口，由组合根注入；导入方向不变，调用面由架构测试限定 |
| 组合根装配顺序 | 进程表提前创建并共享，不引入延迟绑定 |
| 精确记录的登记中 CALL 目标没有准入 | 兼容说明与升级说明；失败为结构化 CALL 错误，不静默降级 |
| 派生结果含 context，可能经泛型提交泄漏给 Alice 运行层 | 泛型提交拒绝派生请求；架构测试守护 |
| 名称待定：派生方法与端口、派生请求与结果、提交函数的派生方法、线程标识的形式 | 实施评审时确定，不改变设计 |

## 11. 实施与收尾记录（2026-10-11）

**实施**：阶段一 `33347f8`、阶段二 `2f609c8`，内容见第 7 节各阶段的实施记录。

**实施评审时确定的名称与取舍**：

- 派生：`ThreadContextLifecycle.derive_child_thread_context(access, *, agent_id, thread_id)`；进程侧 `ProcessThreads.derive_main_thread` / `derive_child_thread` / `revoke_threads`；线程标识 `main` 与 `child-N`；
- 请求与结果：`DeriveCallThreadRequest` → `DerivedCallThread`（含子线程 context，只到 CPU 驱动）→ `CallThread`（目标 Profile、操作快照与子帧提交函数）；
- 线程提交函数：审查后移入 `workspace.contracts` 的通用实现 `ThreadOperationSubmitter`，任何 CPU 驱动复用，测试 CPU 不再依赖 Alice；
- 错误映射：被调用方未准入或为 `system` 时映射为 `mtp.permission.denied`，文案键 `mtp.call.agent_unavailable`（“agent 不可用”），与调用方缺少 `agent.call` 的 `mtp.permission.verb_denied` 区分；
- 进程侧前置检查失败（非主线程、不在 Actor 阶段、进程已请求停止）抛 `ScopeRequiredError`；经 actor API 的正常路径在 Profile 读取后先以 `get_thread_process_id` 复查线程寿命，CPU 执行结束后迟到的派生得到 `ThreadContextRevokedError`。
