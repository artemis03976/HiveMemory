# v0.7.0 能力层分层：root API 与 actor API

> **文档状态**：Archived（2026-10-10）。三个阶段均已完成实现、验收与 code review，事实文档已按最终代码更新。阶段一至三提交为 `33cac7f`、`4351928`、`d85b2bf`，审查修复为 `0ecb75e`；本次文档收尾保留在工作区供审阅。本文保存当时的设计、风险和验收证据，当前接口以 [Workspace 架构](../../architecture/workspace.md#45-三个调用面actor-apiroot-api-与任务进程的阶段调用)第 4.5 节、[子系统契约](../../contracts/subsystem-contracts.md#46-操作请求与线程-context)与[System 配置](../../system/configuration.md)为准；不表示 v0.7.0 已发布。

本计划把 workspace 能力层分为两个独立的 API 面：只对 root（保留的 `system` actor）开放的 root API，以及供任意 actor 经操作入口使用的 actor API；同时把 actor 操作对齐为 READ、SEARCH、RUN、WRITE、UPDATE 与只有 Alice 使用的 CALL，并把任务进程的阶段调用改为不检查 actor 操作的系统操作。Agent 操作白名单（Profile allow 字段的移除、白名单的存储与编辑）是下一份计划，不在本计划内。

设计依据：

- commit `6add90f` 版本的《Workspace 网络与任务进程架构》Idea 15.12（2026-10-10 的四项决定、受影响的设计与留给计划的细节）；7.1.6（in-process 的 workspace server API）；15.1、15.7、15.8、15.10 及其 2026-10-10 演进；15.4（白名单排在本计划之后）；
- [执行单元 Idea](../../ideas/execution-unit-thread-and-environment.md#t-9-操作请求与-workspace-的操作入口) T-9 及其补充（操作请求与能力方法一一对应，只描述 actor API）；
- [身份与访问体系 Idea](../../ideas/identity-and-access-model.md)：不变量 4、6；I-9（已删除的过渡方法与本计划阶段授权的区别）；I-11（`system` 的两种用途）；
- [外部 Actor Idea](../../ideas/external-actor-registration-and-runtime-access.md#34-操作适配器的定义与边界) 3.4（外部 Actor 只用 actor API，MCP 工具不含 CALL）；
- 已归档的 [Alice 的能力层调用迁移计划](./v0.7.0-alice-capability-migration.md)与当前事实文档、代码。

## 1. 背景和问题

能力层是计划重构前从 system 层的 API 原样搬入 workspace 的，没有按调用方分层（总 Idea 15.12）：

- 管理员方法与 actor 方法混放在同一批服务类中，`management.*` 是可以登记给任何 actor 的普通 operation，而管理能力不应暴露给任何 actor；
- actor 一侧的方法与 actor 应有的操作对不齐：读取有三个方法，Profile 读取单独成一个 operation，RUN 借用 READ，WRITE 与 UPDATE 共用一个 operation；
- 任务进程的阶段调用借用 actor 的 operation，没有检索权限的 agent 在 prepare 阶段即失败，而这些调用是系统做出的操作。

白名单（总 Idea 15.4）要在能力层提供的能力与 actor 应有的能力对齐之后才能讨论，因此本计划先于白名单。

## 2. 目标与非目标

### 2.1 目标

1. **阶段调用是系统操作**（阶段一）：任务进程的全部阶段调用（Gateway 读话题、话题池列表、预检索与 cleanup、CPU 分配的 Profile 解析与附件租借、交互提交）不再检查 actor 操作，只校验准入与目标；预检索照旧按进程 actor 的身份过滤记忆可见性。
2. **root API**（阶段二）：capability 目录中新建 root API 目录，承接全部管理方法；root 授权只认保留的 `system` actor，取代 `management.*` 与 `task.observe`；HTTP 管理入口只调用 root API。
3. **actor API**（阶段三）：capability 目录中新建 actor API 目录；actor 操作目录只含六项；每个 actor 操作对应一种请求与一个能力方法；RUN 与 CALL 有各自的请求；删除没有生产调用方的读取方法；撤回意图改为执行单元内部的补偿请求，不属于 actor 操作。
4. **结构守护**：两个 API 目录互不导入；server 只经门面取得 root API；操作入口只分派到 actor API；阶段授权只在 `workspace.process` 中调用。

### 2.2 非目标

- Agent 操作白名单：Profile 的 `allowed_mtp_verbs` / `allowed_sys_tools` 移除、白名单的存储与运行时编辑、按白名单生成 MTP/MCP 工具列表（总 Idea 15.4，下一份计划）。本计划中 Alice 仍按 Profile 字段检查 MTP 动词与系统工具，与能力层的 actor 操作授权并存（15.4 的“拆分后的过渡状态”）。
- 执行线程层：子线程独立凭据、派生经过进程与派生授权（执行单元 Idea T-1a、T-2a、T-3）；子线程继续共用主线程凭据。
- 读取 workspace store 中附件的 actor 操作（15.12：以后可能加入）。
- 执行本身是否经能力层（总 Idea P-3）。
- 进程控制（`/chat/stop`）的授权方式（P-7）；Import Bus `/ingest`（不在 v0.7.0）。
- 外部 Actor 的 MCP 操作适配器（v0.7.1）。

## 3. 当前状态（2026-10-10 核对）

- **operation 目录**（`core/access.py`）有 11 项：`resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit`、`memory_intent.submit`、`task.observe` 与四项 `management.*`。默认登记（`configs/workspace_actors.yaml`）：用户级记录持有前六项，`system` 记录持有四项 `management.*` 与 `task.observe`。配置中的未知 operation 在装载期失败（`SystemAssembler._parse_operation`）。
- **授权者**（`workspace/authorization.py`）：`authorize_operation(access, operation, target)` 兑现 context、检查目标与 owner（`_check_target`，要求传入 operation）并检查白名单，返回 `IdentityScope`；`authorize_process_control` 比对驻留坐标。
- **能力层**（`workspace/capability/`）：
  - `MemoryApplicationService` 同时包含 actor 方法（`resolve_references`、`retrieve`、`submit_write_intent`、`submit_update_intent`、`cancel_intents`）、无生产调用方的 `read`、`retrieve_by_aliases`，以及管理方法（`create_memory`、`list_memories`、`get_memory`、`update_memory`、`record_feedback`、`delete_memory`）；`resolve_references` 在交付正式原子时记录引用；
  - `AgentApplicationService`：管理方法 `create_agent_profile`、`list_agent_profiles`（`management.memory`）与 actor 方法 `get_agent_profile`（`profile.read`，CPU 分配也调用它）；
  - `TopicApplicationService`（`management.topic`）、`MemoryTaskApplicationService`（`task.observe` / `management.task`）、`WorkspaceAssetApplicationService.upload_asset`（`management.asset`）；
  - `BusCanonicalReadBackend`（读取视图的总线 backing，不是 API）与 `WorkspaceOperationEntry`（操作入口）也在该目录。
- **操作入口的请求**（`workspace/contracts/operations.py`）：`SubmitWriteIntentRequest`、`SubmitUpdateIntentRequest`、`CancelIntentsRequest`、`ResolveReferencesRequest`、`RetrieveRequest`、`GetAgentProfileRequest`。Alice 的 READ 与 RUN 都提交 `ResolveReferencesRequest`；CALL 先提交 `GetAgentProfileRequest`，再为每个 `context_refs` 提交 `ResolveReferencesRequest`；CALL 子帧未成功结束时提交 `CancelIntentsRequest`。RUN 的 `sys_*` 系统工具在 Alice 本地执行，不提交请求。
- **阶段调用**：`TaskProcessRunner` 以 `resource.read`（Gateway 读话题、结算后的话题池）、`resource.search`（prepare、cleanup）、`interaction.submit`（进入 Actor 前的预检与 finalize）做阶段授权；`CPUAllocator` 以 `profile.read`（经 `AgentApplicationService.get_agent_profile` 解析 Profile）与 `asset.acquire`（附件租借）授权。
- **入口与门面**：HTTP 管理路由经 `server/deps.py` 从门面取得 `memory_service`、`agent_service`、`topic_service`、`memory_task_service`、`workspace_asset_service`；非 Agent 动作以保留的 `system` actor 认证。`/chat/stop` 以请求级 context 经进程控制授权。
- **结构测试**：`tests/unit/architecture/test_access_boundaries.py`、`tests/unit/workspace/test_import_boundaries.py`（process 不导入能力层、共享设施不导入能力层、contracts 只依赖 core）。

## 4. 目标设计

### 4.1 授权者的三种授权

| 方法 | 用途 | 检查 | 调用面 |
|:---|:---|:---|:---|
| `authorize_operation(access, operation, target)` | actor API | 准入、目标与 owner、actor 操作白名单 | actor API |
| root 授权（新增） | root API | 准入、目标与 owner、actor 为保留的 `system` | root API |
| 阶段授权（新增） | 任务进程的阶段调用 | 准入、目标与 owner；不查 actor 操作 | `workspace.process` |

- 三者都返回授权点组装的 `IdentityScope`（不变量 4）；root 授权的 scope 发起者为 `system`，阶段授权的 scope 发起者为进程的 actor，因此预检索照旧按该 actor 过滤可见性。
- root 的判定是第 3 阶段的授权规则，不写进身份类型（不变量 6）；拒绝以 `OperationDeniedError` 表达，reason 为 `root_required`（名称在实施评审时确定）。
- 阶段授权与已删除的过渡方法（I-9）的区别：scope 只用于进程自己的阶段调用，不进入 CPU 输入清单或任何 CPU 可见的对象；调用面由架构测试限定在 `workspace.process`。
- `_check_target` 不再要求 operation，拒绝详情只在有 operation 时附带它。

### 4.2 actor 操作目录

`WorkspaceOperation` 只保留六项 actor 操作（名称为建议，实施评审时确定）：

| 操作 | MTP 动词 | 请求 | actor API 方法 | 结果 |
|:---|:---|:---|:---|:---|
| `memory.read` | READ（含 Agent Profile 原子与 CALL 的 `context_refs`） | `ResolveReferencesRequest` | 解析引用（原 `resolve_references`，含引用记录副作用） | 逐项 `ReferenceResolution` |
| `memory.search` | SEARCH | `RetrieveRequest` | 语义检索（原 `retrieve`） | `MemoryAtom` 列表 |
| `memory.run` | RUN（记忆中的用户态工具） | 新增：读取用于执行的记忆 | 解析单个执行目标（含引用记录副作用） | `ReferenceResolution` |
| `memory.write` | WRITE | `SubmitWriteIntentRequest` | 提交 WRITE 意图 | `PendingAtom` |
| `memory.update` | UPDATE | `SubmitUpdateIntentRequest` | 提交 UPDATE 意图 | `PendingAtom` |
| `agent.call` | CALL（只有 Alice 使用） | 新增：读取 CALL 目标（取代 `GetAgentProfileRequest`） | 解析 CALL 目标 Profile（经读取视图的 Profile 解析） | `AgentProfile` |

- 一个操作、一种请求、一个方法；CALL 的 `context_refs` 仍以 READ 请求逐项解析，因此持有 CALL 而没有 READ 的 actor 无法经 `context_refs` 共享记忆（与现状一致：解析失败的引用被跳过）。
- RUN 的 `sys_*` 系统工具不提交请求（白名单计划之前仍按 Profile 的 `allowed_sys_tools` 在 Alice 内检查）。
- `CancelIntentsRequest` 不是 actor 操作：操作入口直接以凭据绑定的 process_id 调用写入意图登记撤回 PENDING 记录，不检查 operation，不经 actor API。
- 删除 `read`、`retrieve_by_aliases`（无生产调用方）与 `GetAgentProfileRequest`。
- 原 `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit`、`memory_intent.submit`、`task.observe` 与 `management.*` 全部移除。

### 4.3 两个 API 目录

- `workspace/capability/root/`：root API。按资源拆分服务（记忆、Agent Profile、话题、记忆任务、资产），方法与现有管理方法一致，授权改为 root 授权；管理读取照旧直接经 Patchouli 路由，不进入读取缓存（15.7）。
- `workspace/capability/actor/`：actor API。只含 4.2 的六个方法，授权为 `authorize_operation`；读取经 workspace 读取视图。
- 非 API 的支撑模块（`BusCanonicalReadBackend` 与操作入口）留在 capability 目录顶层：操作入口只导入 actor API。
- 目录与类的命名在实施评审时确定；两目录互不导入。

### 4.4 进程的阶段调用

- `TaskProcessRunner` 的 Gateway 话题读取、prepare、cleanup、finalize 与话题池列表改用阶段授权；进入 Actor 前的 `interaction.submit` 预检删除（没有需要提前暴露的操作检查）。
- `CPUAllocator` 的 Profile 解析不再经能力层：以阶段授权得到的 scope 调用组合根注入的 Profile 读取端口（workspace 读取视图的 Profile 解析，仍按 actor 身份做可见性检查）；附件租借以阶段 scope 调用资产读取端口。
- 任务进程照旧不导入能力层。

### 4.5 入口、门面与配置

- 门面只向 server 暴露 root API 服务与任务进程服务；actor API 只由操作入口持有。
- HTTP 管理路由的路径、请求与响应不变，只改为依赖 root API；`system` 的认证方式不变。
- `configs/workspace_actors.yaml`：用户级记录持有六项 actor 操作；`system` 记录不再列出 operation。装载期规则新增：保留的 `system` 记录不得配置 operation（root 能力不经白名单）；未知 operation 照旧装载失败。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| `core/access.py` | `WorkspaceOperation` 改为六项 actor 操作 |
| 授权者 | 新增 root 授权与阶段授权；`_check_target` 的 operation 改为可选 |
| 访问登记 | `system` 记录不得配置 operation |
| `workspace.capability` | 分为 root API 与 actor API 两个目录；删除 `read`、`retrieve_by_aliases` |
| `workspace.contracts` | 新增 RUN 与 CALL 目标的请求，删除 `GetAgentProfileRequest`；`CancelIntentsRequest` 改为执行单元内部请求 |
| `workspace.process` | 阶段调用改用阶段授权；Profile 解析改用注入的读取端口 |
| Alice | RUN、CALL 改提交各自的请求；权限拒绝的映射不变（`mtp.permission.verb_denied`） |
| 组合根、门面与 server | 门面暴露 root API；server 依赖改名 |
| 配置 | `workspace_actors.yaml` 的 operation 名称变化，与旧配置不兼容 |
| 行为 | 缺少 actor 操作的 agent 仍能完成 chat 的全部阶段；RUN 与 CALL 受各自的操作约束；WRITE 与 UPDATE 可以分开授权；管理方法只对 `system` 开放 |
| 公共路由与数据 | 无 HTTP 路由、Patchouli 路由或持久化数据变化 |

## 6. 兼容与迁移策略

- 进程内替换，不涉及持久化数据；每个阶段一次性切换。
- 旧版 `workspace_actors.yaml` 使用的 operation 名称在阶段二、三之后装载失败并给出明确错误；仓库默认配置随阶段同步更新，[System 配置](../../system/configuration.md)补充升级说明（新名称与 `system` 记录不再列出 operation）。
- HTTP 管理接口与前端不变。

## 7. 实施阶段

三个阶段依次实施，每个阶段结束时全量后端测试通过、可单独审查。顺序使每一步只移除已经没有使用者的 operation。

**阶段一：阶段调用改为系统操作**

1. 授权者新增阶段授权，`_check_target` 的 operation 改为可选；
2. runner 的阶段调用与 CPU 分配改用阶段授权，删除 `interaction.submit` 预检；
3. CPU 分配改用注入的 Profile 读取端口；
4. 架构测试限定阶段授权的调用面。

验收：第 8 节 1–3 项。

**阶段二：root API**

1. 新建 root API 目录，迁入全部管理方法，授权改为 root 授权；
2. 门面、server 依赖与组合根改为 root API；
3. 移除 `management.*` 与 `task.observe`，更新默认登记与装载规则；
4. 架构测试：server 不导入 actor API，root API 不被操作入口导入。

验收：第 8 节 4–6 项。

**阶段三：actor API 与操作对齐**

1. 新建 actor API 目录，迁入 actor 方法，删除 `read`、`retrieve_by_aliases`；
2. 操作目录改为六项，新增 RUN 与 CALL 目标的请求，撤回意图改为内部请求；
3. Alice 的 RUN 与 CALL 改提交新请求；
4. 更新默认登记；架构测试守护两目录互不导入、操作入口只分派到 actor API。

验收：第 8 节 7–13 项；全量门槛与确定性 HTTP E2E 通过。

## 8. 测试和验收标准

按[测试设计规范](../../governance/testing/test-design-standards.md)分类；授权者、能力层与任务进程使用真实对象，外部 LLM 与存储使用既有替身。

1. 不持有任何 actor 操作的 agent 能完成一次 chat：Gateway、预检索、CPU 分配（含 Profile 解析与附件选择）与 finalize 都成功。
2. 预检索按进程 actor 的身份过滤可见性：其他 agent 的 PRIVATE 记忆不出现在预检索结果与输入清单中。
3. 阶段授权在准入失效或目标不符时拒绝；生产代码中只有 `workspace.process` 调用它（架构测试）。
4. 每个 root API 方法对非 `system` 的 actor 以 `root_required` 拒绝，且不触达 Patchouli（逐方法参数化）；`system` 照常成功。
5. `system` 记录配置 operation、或配置中出现已移除的 operation 时，装载期失败并给出明确错误。
6. HTTP 管理路由的行为与现状一致（沿用现有路由测试）；server 不导入 actor API（架构测试）。
7. 每种 actor 请求恰好检查表 4.2 中对应的操作：缺少该操作时拒绝且没有副作用，持有时成功（逐请求参数化）。
8. RUN 只需 `memory.run`：持有 READ 而没有 RUN 时 RUN 被拒绝、READ 成功，反之亦然；RUN 的系统工具不经能力层。
9. CALL 目标读取只需 `agent.call`；缺少它时 CALL 以准备失败结束、不创建子帧；`context_refs` 需要 `memory.read`，缺少时共享上下文中不出现这些记忆。
10. WRITE 与 UPDATE 分别受 `memory.write`、`memory.update` 约束。
11. 撤回意图不检查 operation，只作用于凭据绑定进程的 PENDING 记录（沿用现有测试）。
12. `system` 的 context 经操作入口提交任何 actor 请求都被拒绝。
13. 结构：两个 API 目录互不导入；操作入口只导入 actor API；`read`、`retrieve_by_aliases`、`GetAgentProfileRequest` 与已移除的 operation 不再存在。
