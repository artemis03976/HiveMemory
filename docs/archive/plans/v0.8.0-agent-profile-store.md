# v0.8.0 AgentProfileStore：Agent Profile 移出中期记忆库，以文件保存并热重载

> 状态：Archived（2026-11-18，已实施，日常与开发实例都已迁移，实施记录见第 11 节）。当前事实见 [MemoryLibrary 与存储层](../../patchouli/memory-library.md#15-agent-profile人偶图纸)第 1.5 节、[检索](../../patchouli/retrieval.md#24-agent-profile-解析)第 2.4 节与[任务进程](../../workspace/task-process.md#6-cpu-分配)第 6 节。v0.8.0 第一个方向“记忆类型的收敛”的第二份计划；第一份计划见[去掉 WORK_IN_PROGRESS、合并资源记忆与已有记忆的迁移](./v0.8.0-memory-type-convergence.md)（PR #225）。设计依据见[类型体系 Idea](../../ideas/memory-type-system.md)第 6.3 节。

## 1. 背景和问题

Agent Profile 现在是中期库里类型为 `AGENT_PROFILE` 的记忆原子：alias 是 agent id，标题与摘要组成调用方看到的子代理菜单项，正文是人设提示词，`agent_config` 存模型参数与是否启用。放进记忆库的两点理由一点没有实现：提示词在演化中修正需要反馈途径，现在没有；“能被检索发现”用固定列表即可替代（[类型体系 Idea](../../ideas/memory-type-system.md)第 6.3 节）。留在中期库带来的问题：

- 子代理菜单来自预检索的命中：只有语义命中、开启检索且执行者有 `memory.search` 时 Profile 才进菜单，停用的 Profile 也可能进菜单；同一段还出现在 MTP SEARCH 与 MCP `memory_search` 的结果里。
- Profile 与全部记忆共用 Workspace 内唯一的 alias 空间，agent 可以 READ 一个 Profile 的 alias 读到人设；actor 的 UPDATE 与被动结算的查重都没有拦住 Profile。
- 生成、合并、查重、归档、管理列表与 alias 生成器里散落着只因 Profile 放在中期库才存在的类型判断。
- Profile 的缓存、代次守护与失效订阅是为 Qdrant 读取设计的。

## 2. 目标与非目标

### 2.1 目标

1. AGENT_PROFILE 移出中期记忆库，单独成 AgentProfileStore；它属于 MemoryLibrary，但不在三层记忆存储之中（owner，2026-11-15）。
2. Agent Profile 不再作为记忆原子看待，也不再遵循记忆原子的结构（owner，2026-11-18）。
3. 文件存储，一个 Agent Profile 一个文件（owner，2026-11-17）；直接修改本地文件与经 Agent 页修改等同，运行中的后端热重载（owner，2026-11-18）。
4. 可用 agent 的列表固定载入提示词，不再靠检索发现（owner，2026-11-15）。
5. 日常库中现有的 Profile 原子迁到文件。

### 2.2 非目标

- 手动编辑的历史：不保留（owner，2026-11-18）。
- 不透明的 agent id：`agent_id` 保持为不可改的标识（owner，2026-11-18）；换成不透明的 id 归[身份与访问体系 Idea](../../ideas/identity-and-access-model.md)第 8 节，改名仍由 [Agent 别名改名 Todo](../../todo/agent-alias-rename.md) 跟踪。
- Profile 改用 ModelSelection 表达模型选择：仍由 [Todo](../../todo/agent-profile-model-selection.md) 另行处理。
- 关于 agent 的知识（擅长什么、做砸过什么）作为普通记忆生成：写入链路 Idea 的候选，不随这次。

## 3. 当前状态（2026-11-18 核对，commit `736ea2f9`）

- **模型**：`AgentProfile`（`core/models/agent.py`）有 `agent_id`、`persona`、`model_name`、`temperature`、`top_p`、`enabled`，由 `from_atom` 从原子取得：alias 作 `agent_id`，正文作 `persona`，`agent_config` 展开为其余字段，多余的旧键（`language`、`allowed_mtp_verbs` 等）忽略。`ResolvedAgentProfile`（`core/models/projections.py`）另带 `access_policy`、`source_memory_id`、`source_version`。内置的 `omni_doll` 不落库。
- **写入**：创建经 `POST /api/v1/agents` → root API → `AGENT_PROFILE_CREATE` → `MemoryGenerationFamiliar.create_external_memory`，策略一律 PUBLIC；编辑与删除没有 Profile 专用路由，前端走 `PATCH`、`DELETE /api/v1/memories/{id}`；每次编辑写一份 MANUAL_EDIT 版本 Artifact。
- **预设**：模型预热就绪后，若预设标记文件（`system.preset_agent_profiles_marker`）不存在，以 system 写入 coder_doll 与 reviewer_doll，已有同名 alias 的跳过，成功后写标记；删除记忆数据（`server/__main__.py` 的 `_delete_memory_data`）时删除标记，下次启动重新写入。
- **解析**：`RetrievalFamiliar.get_agent_profile` 对空、`default`、`omni_doll` 返回内置 agent，否则按 alias 从中期库读取，失败原因为 not found、`type_mismatch`、`invalid_config`、`profile_disabled`。workspace 的 `ProfileResolver` 以 L1 缓存、`ColdReadGuard` 代次守护与 `PATCHOULI_MEMORY_CHANGED` 失效订阅包住这次读取，交付时按 `access_policy_permits` 授权。
- **任务进程与 CALL**：任务进程以认证得到的执行者 `agent_id` 解析 Profile（管理语义，不按可见性过滤）；CALL 经 `DeriveCallThreadRequest` → `resolve_call_target`：先以 `agent.call` 授权，再按调用方的可见性读取被调用方，`derive_child` 要求被调用方在本 Workspace 有准入，子线程以被调用方的身份与白名单运行。
- **菜单**：预检索命中的 Profile 原子由 `memory_compiler` 拆进 `AGENT_PROFILE_MENU`，只渲染 alias、标题与摘要；CALL 的提示词文案指向这张菜单。
- **只因 Profile 在中期库才有的特例**：`memory_generation.py` 拒绝 Profile 参与合并、不补回退 alias、拒绝改策略、限定 `agent_config` 只能设在 Profile 上；`engines/generation/engine.py` 不提名与 Profile 合并；`garbage_collector.py` 免归档；`workspace/capability/root/memory.py` 的记忆列表排除 Profile；`memory_management_service.py` 拒绝经普通入口创建 Profile；alias 前缀 `agent`；MTP 过滤别名 `agent_profile` 与 `agent`；`MemoryAtom.payload.agent_config` 字段本身。
- **前端**：Agent 页编辑名称、摘要、启用、模型、温度、top_p、系统指令与标签，没有可见性编辑，也没有版本历史；alias 只在草稿中可改。
- **日常库**：3 条 Profile 原子（2026-11-18 只读核对）：`meal_assistant`（自建）、`coder_doll`、`reviewer_doll`，都是 PUBLIC；`meal_assistant` 与 `coder_doll` 的 `agent_config` 中带有已被忽略的旧键。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-15～18）：移出中期库、文件存储且一个 Profile 一个文件、不再是记忆原子、不保留编辑历史、手改与 Agent 页修改等同并热重载、`agent_id` 保持不变。

## 5. 目标设计

### 5.1 Profile 文件

- 一个文件就是一个 agent，位于 `<agent_profiles.root_dir>/<workspace_id>/<agent_id>.md`，`root_dir` 默认 `.hivememory/agent_profiles`（按数据根解析）。文件名就是 `agent_id`，创建后不可改。
- 正文是人设提示词；frontmatter 只有：

  | 字段 | 含义 | 原来的来源 |
  |:---|:---|:---|
  | `title` | 用户给它起的名字，Agent 页最主要的展示名 | `index.title` |
  | `summary` | 它负责的功能 | `index.summary` |
  | `model` | 模型注册表中的模型 id（owner，2026-11-18：沿用主流的字段名） | `agent_config.model_name` |
  | `temperature`、`top_p` | 采样参数，可空 | `agent_config` |
  | `enabled` | 是否启用 | `agent_config.enabled` |

- 不再有标签、访问策略、版本号、生命力与时间戳字段。Agent 页显示的保存时间取文件的修改时间。
- 三种名字各有用途（owner，2026-11-18）：`title` 是用户赋予它的名字，用于展示；`summary` 描述它的功能；`agent_id` 用于系统内部的流转，也是它的“昵称”。
- `AgentProfile` 改为直接描述这份文件（新增 `title`、`summary`，模型字段改名为 `model`），不再有 `from_atom`；`ResolvedAgentProfile` 去掉 `access_policy`、`source_memory_id`、`source_version`，若因此只剩 `AgentProfile` 本身，删除这个投影。

### 5.2 AgentProfileStore

- `MemoryLibrary` 新增 `agent_profiles` 角色，与 `artifact_store` 并列，由 Patchouli runtime 构造并持有；配置段 `patchouli.agent_profiles.root_dir`。
- 操作：列出一个 Workspace 的全部 Profile、按 `agent_id` 读取、保存、删除。读取与列出每次直接读目录，不设缓存：文件改动在下一次读取时生效，这就是热重载。
- 保存先校验，再写临时文件、替换原文件，写入是原子的。
- 校验只有一套，写入与读取都用：`agent_id` 合法（与现在 alias 的长度一致，限定为可以做文件名的字符）、frontmatter 只含 5.1 的字段且取值合法。读取时不合格的文件跳过并记一条带原因码的日志；解析到它时以结构化错误失败（沿用 `invalid_config`），不回退到内置 agent。
- Profile 不经 `MemoryGenerationFamiliar`：Familiar 是记忆的唯一写入者，Profile 已经不是记忆。

### 5.3 解析与 CALL

- `get_agent_profile` 改为读 AgentProfileStore；内置 `omni_doll` 的处理与 not found、`invalid_config`、`profile_disabled` 三种失败不变，`type_mismatch` 删除。
- workspace 的 `ProfileResolver` 只做读取与失败映射：删除 Profile 的 L1 缓存（`workspace/cache/profile.py`）、代次守护与失效订阅中针对 Profile 的部分，以及交付时的 `access_policy_permits`。
- CALL 的授权不变：调用方要有 `agent.call`，被调用方要在本 Workspace 有准入；只是不再按可见性读取被调用方。

### 5.4 可用 agent 的固定列表

- CPU 分配时从 AgentProfileStore 与访问登记组装：本 Workspace 有准入、已启用的 agent，每项是 `agent_id` 加上拼成“`title`: `summary`”的一句描述（owner，2026-11-18）。列表常驻提示词，`title` 与 `summary` 宜短；人设只在这个 agent 执行或被 CALL 时才载入；列表为空时不出现委托的一节。仍用现有的 `AGENT_PROFILE_MENU` 编译目标与文案。
- 预检索、MTP SEARCH 与 MCP `memory_search` 的结果里不再有 Profile 一节；CALL 的提示词文案继续指向这张列表。

### 5.5 管理入口与前端

- 管理接口：`GET /api/v1/agents`、`POST /api/v1/agents`，新增 `PATCH /api/v1/agents/{agent_id}` 与 `DELETE /api/v1/agents/{agent_id}`，都经 root API；`/api/v1/memories` 不再接受 Profile。
- 前端 Agent 页改用这组接口：名称（`title`）与摘要（`summary`）两栏照旧，去掉标签编辑；`agent_id` 只在新建时填写。

### 5.6 预设

- 预设的 coder_doll 与 reviewer_doll 改为在标记文件不存在时写成文件，已存在同名文件的跳过，写完写标记；写入不再等模型预热（不再需要向量）。

### 5.7 中期库里随之删除的特例

第 3 节列出的类型判断全部删除；`MemoryAtom.payload.agent_config` 字段删除。`AGENT_PROFILE` 与第一份计划的三个旧值一样留在 `MemoryType` 中，只作为历史取值：已有的版本记录里有 Profile 原子的快照。

### 5.8 迁移

- `scripts/migrate_agent_profiles.py`：读取中期库中的 Profile 原子，按 5.1 写成文件：标题与摘要原样写入 `title` 与 `summary`，`model_name` 写为 `model`，只保留 5.1 的字段、旧键丢弃；再从中期库删除这些原子；默认只打印将要执行的动作，加 `--apply` 才写入；目标文件已存在时整体拒绝执行。
- 日常实例由 owner 停机后执行；开发实例先演练。迁移完成后脚本在收尾时删除。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| 记忆数据模型 | `AGENT_PROFILE` 只作历史取值；`payload.agent_config` 删除 |
| MemoryLibrary | 新增 `agent_profiles` 角色与配置段 |
| Patchouli | Profile 的写入与解析改走 AgentProfileStore；生成、合并、查重、归档中的 Profile 特例删除 |
| Workspace | Profile 的缓存与失效删除；CPU 分配组装固定列表；CALL 不再按可见性读取被调用方 |
| 记忆编译 | `AGENT_PROFILE_MENU` 的来源从检索命中改为固定列表；检索信封中不再出现 |
| 管理接口与前端 | Profile 的编辑与删除改走 `/api/v1/agents/{agent_id}`；去掉标签 |
| 数据 | 日常实例 3 条 Profile 原子迁为文件；已有的版本 Artifact 不变 |

## 7. 兼容与迁移

- `agent_id` 不变，访问登记、外部接入声明、会话记录与记忆来源中的引用都不受影响。
- 已有的 Profile 版本 Artifact 原样保留，不再新增。
- 迁移之前部署新代码时，中期库里残留的 Profile 原子照常解码（`AGENT_PROFILE` 仍在枚举中），但不再被解析为 agent；迁移之后才有可用的 Profile 文件，所以日常实例应在部署后立即迁移。

### 8.3 迁移与实测

- 开发实例与日常实例：迁移后中期库中 `AGENT_PROFILE` 的计数为 0，`agent_profiles/` 下有对应的文件，Agent 页列出它们。
- 真实会话：在编辑器里直接改一个 Profile 的人设或停用它，不重启，下一轮对话即生效；停用的 agent 不出现在可用列表中；CALL 一个已启用的 agent 正常完成。

## 9. 风险与待决问题

- **删除记忆数据时 Profile 的去留**（候选，可在计划评审时调整）：Profile 不再是记忆，`_delete_memory_data` 默认不删除 `agent_profiles/`；删除标记后重新写入预设时跳过已有文件。另一种做法是一并删除，与现在把 Profile 当记忆数据删除的行为一致。
- **访问策略去掉之后**：现在不存在 PRIVATE 的 Profile（入口只建 PUBLIC，也改不了）；若将来需要“只有某个 agent 能调用”，由访问登记表达，不回到 Profile 上。
- **手改与 Agent 页同时修改同一个文件**：后写者覆盖先写者，不做合并；Agent 页保存时若文件的修改时间已变，提示重新载入（候选）。
- **部署与迁移之间的窗口**：部署后、迁移前，日常实例没有自建的 Profile 可用；迁移应紧接部署。

## 11. 实施记录

2026-11-18 在 `feat/v0.8.0-agent-profile-store` 上实施。计划之外或比计划更具体的决定：

- **Profile 文件**：`agent_id` 只用小写字母、数字、`_` 与 `-`（1～60 个字符）：Windows 文件名不分大小写，允许大写会让两个 id 指向同一个文件；内置的 `default`、`omni_doll` 与保留的 `system` 不能用作 `agent_id`，同名文件在列出时跳过。frontmatter 按严格模式校验（`temperature: "0.3"` 这类字符串数字不合格）；读取去掉 Windows 编辑器写入的 BOM，CRLF 按换行处理。`title`、`summary` 与人设去掉首尾空白，读写因此往返一致。读取时的原因码为 `invalid_agent_id`、`missing_frontmatter`、`invalid_frontmatter`、`unknown_field`、`invalid_value`、`unreadable`。
- **模型与投影**：`ResolvedAgentProfile` 删除；解析路由直接返回 `AgentProfile`，管理路由返回新增的 `StoredAgentProfile`（Profile 加文件的修改时间，Agent 页的“最近保存”用它）。`AgentProfileCreation` 删除，预设直接写成 `AgentProfile`。
- **错误**：新增 `InvalidAgentProfileError`（`workspace.agent_profile.invalid`，HTTP 422）与 `AgentProfileExistsError`（`workspace.agent_profile.exists`，409）。`PATCH /api/v1/agents/{agent_id}` 只改请求中出现的字段，`temperature`、`top_p` 为 `null` 表示沿用模型定义；请求中出现 `agent_id` 按未知字段以 422 拒绝。Patchouli 的创建与编辑路由以字段映射提交，与读取文件走同一个校验函数。
- **可用 agent 列表**：PREPARE 在存储健康之后、CPU 分配之前，以系统的 root 授权列出已启用的 Profile，再由线程表的 `admitted_profiles` 按派生子线程时的同一准入筛选；它只读取主线程登记的工作 actor、不判定存活，否则 PREPARE 期间收到的停止会以 `ThreadEndedError` 让进程失败，而不是在进入 Actor 之前按停止收口（测试发现）。列表放在 `instructions` 中人设之后，标题“可用子代理”加委托提示，每项为 `<agent_profile alias="agent_id">title: summary</agent_profile>`（只有一项时不带冒号）；检索上下文的头尾不再提到子代理，行为准则中的“若记忆上下文中列出了可用子代理”改为“若提示词中列出了可用子代理”。
- **版本快照**（计划没有写到）：版本快照的严格校验拒绝任一层级的未知字段，而删除 `payload.agent_config` 之前写下的快照都带着这个键（多为 `null`）。校验因此把 `payload.agent_config` 列为已删除的字段，不算未知字段，旧快照仍按 schema 解码；`payload.artifacts.agent_config` 这类旧布局仍被拒绝。`PayloadLayer` 显式忽略未知字段，中期库与冷库中的旧记录照常解码。
- **预设**：启动时在接受请求之前写入，不再等模型预热，预热改在后台单独进行。
- **随之没有使用方的代码**（登记在交付说明中，没有删除）：记忆列表的 `exclude_types` 只服务于排除 Profile，root API 不再传它，整条参数链现在没有生产调用方。
- **前端**：Agent 页改用 agent 接口，键为 `agent_id`，名称与摘要两栏照旧，标签卡片删除，`agent_id` 只在新建的草稿中可改；保存失败的提示带上后端原因，409 与 422 可以区分；新建草稿的摘要默认为空；聊天中名称为空的 Agent 显示 `agent_id`。
- **测试**：Profile 缓存、`ResolvedAgentProfile`、`from_atom`、按可见性解析被调用方、Profile 不参与合并与免归档、记忆列表排除 Profile、`type_mismatch` 与跳过可见性的架构测试随契约删除；新增 `tests/unit/memory_library/test_agent_profiles.py`，其余不变量并入归属层的现有测试文件。

### 11.3 收尾的顺序与日常迁移

日常实例现在安装的版本把 Profile 当作中期记忆，迁移之后读不到它们；新版本读不到原子，迁移之前没有可用的自建 Profile。迁移因此与换装新版本一起做。

桌面端只在启动后端时一起拉起 Qdrant，没有单独拉起 Qdrant 的入口（owner，2026-11-18 指出），所以迁移在旧版本仍在运行时做，紧接着换装：旧版本仍把这些原子当作 Profile，不合并、不归档，迁移期间没有别的写入方；新版本已经把它们当作普通记忆，可能合并或归档它们，不在新版本运行时迁移。迁移之后到新版本启动之前，旧版本解析不到这些 agent，这段时间只有换装的几分钟。顺序：从托盘退出旧版本，备份数据根下的 `.hivememory\qdrant`，重新打开旧版本；在数据根下运行迁移脚本（先试运行，再加 `--apply`）；从托盘退出，覆盖安装用本分支打包的新版本并启动，在 Agent 页核对三个 Agent。迁移完成后删除 `scripts/migrate_agent_profiles.py`。

### 11.4 Profile 不按 Workspace 分目录（owner，2026-11-18，归档之后）

实施时沿用了 [Idea 6.3](../../ideas/memory-type-system.md#63-agent_profile-移出中期库) 的候选“按 Workspace 分目录”。owner 随后指出它与 v0.7 引入 Workspace 时的设想不符：agent 是进入 Workspace 工作的工作者，独立于 Workspace 存在，不是 Workspace 的资产。按 Workspace 限定 Profile 来自 v0.6.2 把全部中期读取按 Workspace 限定时的连带结果，没有单独的决定。随之改动：

- **布局**：Profile 文件位于 `<root_dir>/<agent_id>.md`，`agent_id` 在实例内唯一；Store、Patchouli 的管理服务与解析都不再接收 Workspace。
- **路由**：`patchouli.public.agent_profile.*` 与 `get_agent_profile` 不再接收 `IdentityScope`，与存储健康一样；授权仍在调用方一侧：root API 以请求驻留的 Workspace 做 root 授权，CALL 仍以调用方的 `agent.call` 授权，可用 agent 列表与 CALL 仍按本 Workspace 的准入筛选。
- **第 9 节的去留**：删除记忆数据不删除 `agent_profiles/`，按第 9 节的候选执行；桌面端删除确认框与帮助把 Agent 移到“会保留”。
- **迁移脚本**：写成 `<root_dir>/<alias>.md`；两条原子的 alias 相同（例如分属两个 Workspace）时整体拒绝。开发实例 11.1 中写入的 3 个文件从 `main_workspace/` 移到根目录；日常库的 3 条原子都在 `main_workspace`（11.2），没有同名冲突，11.3 的步骤只改了顺序（旧版本运行时迁移，见 11.3）。
- **测试中发现**：真实 LLM 的 E2E 配置没有隔离 `agent_profiles.root_dir`，运行时会写进本检出的开发实例目录；已改为写入本次会话的临时目录，CALL 测试在会话级系统中只建立一次 `coder_doll`。
- **限制**：同一实例的全部用户共用一组 Profile；按用户区分 Profile 没有使用方，等出现再讨论。
