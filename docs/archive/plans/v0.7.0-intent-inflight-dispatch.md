# v0.7.0 写入意图实时派发

> **文档状态**：Archived。三个阶段均已完成实现、验收与 code review，阶段一提交 `9f8028c`、阶段二提交 `1f227fc`，阶段三与本归档同批提交（`de7b859`），合并前复审的修复另行提交。本计划保留实施前的问题与目标设计供历史追溯；当前行为以 [Workspace 架构](../../architecture/workspace.md)第 5.4 节、[MTP 契约](../../contracts/mtp.md)与 [Patchouli 生成](../../patchouli/generation.md)为准。

本计划让 actor 的 WRITE/UPDATE 在发出操作请求时就提交到 Patchouli 的记忆生成队列：能力层登记意图后，经 Patchouli 唯一的意图提交路由交给生成链，生成队列接纳之后才返回 ACK。收尾阶段不再派发物化，交互记录不再携带物化任务；提交一旦进入队列，之后的任何失败与取消都不影响它。

设计依据：

- 写入意图迁移 Idea 0.3（owner，2026-10-13；该节已从 Idea 删除，删除前版本见 commit `4b690d4` 的 `docs/ideas/pending-intent-migration.md`）：派发时机与路径、W6–W11；0.1 的“实时提交”“取消与失败”“生成材料”选项 A；
- [任务进程 Idea](../../ideas/task-process-table-and-registration-entry.md#12-任务进程的结构owner2026-09-28) 1.2：话题保留预建（2026-10-13）；Q-1、Q-14；
- 当前事实：[Workspace 架构](../../architecture/workspace.md)第 4.3、4.5、5.4 节，[子系统契约](../../contracts/subsystem-contracts.md)第 4.5、4.6 节，[公开路由与事件](../../contracts/routes-and-events.md)第 2.2 节，[Patchouli 生成](../../patchouli/generation.md)；
- 已归档：[写入意图登记与读取缓存失效](v0.7.0-intent-registry-and-read-cache.md)（第 1 步）、[执行线程层](v0.7.0-execution-thread-layer.md)。

## 1. 背景和问题

- **写入要等一轮结束才生成**：WRITE/UPDATE 现在只在 workspace 登记，Actor completed 后由任务进程认领本进程的意图，随交互记录交给 Patchouli finalize，finalize 等到交互 applied 才派发物化。一轮执行越长，写入进入生成越晚。
- **失败与取消会丢弃写入**：进程关闭时取消本进程仍为 PENDING 的意图，CALL 子帧未成功结束时撤回它的意图（第 1 步沿用的语义，Idea 0.1 W4）。agent 已经收到 ACK 的写入，会因为同一轮后来的失败而消失。
- **普通交互入口隐式携带物化**：`InteractionPayload.materialize_tasks` 让交互提交顺带执行主动物化；finalize 也因此必须等到 applied，这是任务进程 Q-1“交互被接纳后即退出”的前提障碍。
- **已有的意图提交路由没有生产调用方**：`patchouli.public.memory_intent.submit` 已经存在，但它按 intent_id 自行派生 pending 别名，与 workspace 登记的别名不是同一来源。
- **生成材料写死**：主动生成取话题最近 5 个 block，轮数不可配置。

## 2. 目标与非目标

### 2.1 目标

1. **实时派发**：执行线程（主线程与 CALL 子线程）发出 WRITE/UPDATE 时，在同一次 actor 操作内登记意图并提交到 Patchouli，生成队列接纳之后才返回 ACK。
2. **唯一提交路径**：能力层 actor API 的 `submit_write_intent` / `submit_update_intent` 是唯一的提交方，经全局路由 `patchouli.public.memory_intent.submit` 进入 `MemoryIntentSubmissionService.submit_memory_intent`；删除 finalize 派发、进程认领与 `InteractionPayload.materialize_tasks`。
3. **提交之后不受失败与取消影响**：删除进程关闭时的意图取消、CALL 子帧的意图撤回与操作入口的迟到登记补偿。
4. **派发话题跟随 Gateway 路由**：进程在 CPU 分配时补全本轮的派发话题，能力层派发时读取；actor 的操作请求不携带 topic_id。
5. **生成材料可配置**：材料为话题过去 N 个 block 与可能存在的 `state_summary`，N 是配置项；当前一轮有意不参与。
6. **ACK 之前的错误回到 agent**：登记、派发与接纳过程中的任何错误都以结构化错误交给 agent，由 agent 自行处理。
7. **记忆任务只经事件观察**：删除 SSE done 事件与进程完成事件中的 `memory_task_ids`，前端经 `memory.task.*` 事件捕获任务的创建与状态变化。

### 2.2 非目标

- 进程关闭时点：finalize 仍等到交互 applied 后返回，“交互被接纳后即退出”留给外部会话方向（Idea 0.3 W11）；话题保留预建，`cleanup_prepared_agent_run` 不变。
- 结算对账、句柄回收、保留期与容量（Idea 0.1 搁置）；结果未知时句柄可能长期停在 MATERIALIZING。
- 按预算编译话题的全部资料、对话流式同步到 Patchouli（[长时间运行 Idea](../../ideas/long-running-agent-intra-turn-context-folding.md)开头的 owner 方向）。
- 不经任务进程的写入（plugin 模式、外部 wire）：派发话题来自进程，本计划只覆盖进程内的执行线程。
- 意图 policy、`WriteFocus` 声明 policy；RuntimeEvent 按 Workspace 过滤（现状，搁置）。
- `patchouli.public.interaction.submit` 的生产调用方。

## 3. 实施前状态（2026-10-13 核对）

- **actor API**（`workspace/capability/actor/memory.py`）：`submit_write_intent` 授权 `memory.write` 后在 `WriteIntentRegistry` 登记并返回 PendingAtom；`submit_update_intent` 授权 `memory.update`、以本次 scope 冷读基础原子、登记后失效基础缓存。两者都不调用 Patchouli。
- **登记**（`workspace/intents/registry.py`）：登记生成 `draft_{slug}_{4 位十六进制}` / `rev_{base_alias}_{4 位十六进制}` 别名与 `intent_{12 位十六进制}`，状态为 PENDING；`claim_process` 把本进程 PENDING 推进为 MATERIALIZING 并产出 `PendingAtomMaterializeTask`；`cancel_process`、`cancel_aliases` 取消 PENDING。结算事件先按别名、再按 intent_id 匹配；FAILED、CANCELLED 事件只携带别名。
- **操作入口**（`workspace/capability/operations.py`）：WRITE/UPDATE 返回后复查线程 context，撤销时撤回本次登记；`CancelIntentsRequest` 是入口内部的撤回补偿。
- **任务进程**（`workspace/process/runner.py`）：completed 时 `claim_process` 的结果经 `seal_interaction` 进入 `InteractionPayload.materialize_tasks`；finalize 返回的记忆任务成为 `RunCompleted.memory_task_ids`、`chat.run.completed` 事件数据与 SSE done 事件的 `memory_task_ids`；关闭流程同步调用 `cancel_process`。CPU 输入清单的 `topic_id` 取自 prepare 结果。
- **Patchouli finalize**（`patchouli/service.py`）：交互 applied 后以 `GENERATION_SUBMIT_ACTIVE` 派发 `payload.materialize_tasks`，与引用命中记录并行，返回生成任务列表。
- **意图提交路由**：`MemoryIntentSubmissionService.submit_memory_intent` 接收 `MemoryIntent`（kind、topic_id、内容或修订指令、可选 intent_id），在内部构造物化任务，`pending_alias` 由 intent_id 确定性派生；只调用 `GENERATION_SUBMIT_ACTIVE`，以 `accepted=False` 同时表示确定性拒绝与结果未知。路由已绑定，没有生产调用方。
- **生成提交**：`MemoryGenerationCoordinator.submit_active` 读取话题，以 `recent_blocks(5)` 与 `state_summary` 构造材料；UPDATE 读取基础记忆构造 spec，确定性失败经 settler 发布 FAILED；`submit_generation_many` 以 `active:{intent_id}` 为任务标识逐项接纳，确定性拒绝发布 FAILED，结果未知不发布。
- **CALL 编排**（`alice/orchestration/sub_agent/call_coordinator.py`）：子帧未成功结束时以子帧的提交函数提交 `CancelIntentsRequest`。
- **MTP**（`agent_runtime/mtp/runtime.py`）：WRITE/UPDATE 处理器把登记返回的 PendingAtom 包装为 ACK；提交函数抛出的 `OperationDeniedError`、`ResourceUnavailableError`、`MTPError` 与其他异常都转为 MTP 错误响应交给 agent。
- **话题**：Gateway 路由到新话题时只给出占位值 `NEW_TOPIC`，真实 id 由 prepare 预建话题时生成；进程未以 completed 结束时，关闭流程经 cleanup 路由清理预建的空话题。
- **前端**：`chatStore` 在 done 后保存 `currentMemoryTaskIds` 并按 id 刷新任务；Memory Runtime 把本轮任务置顶；任务列表另由 `applyRuntimeEvent` 合并 `memory.task.*` 事件，挂载时调用任务列表 API。

## 4. 目标设计

### 4.1 一次 WRITE/UPDATE 的处理顺序

| 步骤 | 内容 | 失败时 |
|:---|:---|:---|
| 1 | 操作入口校验线程 context，按请求类型分派（不变） | 拒绝，不登记 |
| 2 | actor API 授权 `memory.write` / `memory.update`（不变） | 拒绝，不登记 |
| 3 | UPDATE：以本次 scope 冷读并验证基础原子（不变） | 拒绝，不登记 |
| 4 | 同步段：复查线程 context，读取进程的派发话题，登记意图并直接进入 MATERIALIZING；UPDATE 失效基础缓存 | 拒绝，不登记 |
| 5 | 经全局路由提交到 Patchouli，屏蔽调用方的取消 | 见下 |
| 6 | 接纳：返回 PendingAtom 作为 ACK | — |

- 第 4 步内没有挂起点：复查通过后登记不会再跨越线程撤销，不再需要迟到登记的补偿。
- 第 5 步的结果：
  - **接纳**：返回 ACK。
  - **确定性拒绝**（UPDATE 基础原子不存在、生成队列拒绝等）：句柄为 FAILED，以结构化错误交给 agent，不返回 ACK。
  - **结果未知**（总线异常、spec 构建的不确定异常）：句柄保持 MATERIALIZING，以结构化错误交给 agent；如果其实已被接纳，结算事件会把句柄推进到终态。
- 派发开始后线程被撤销、调用方被取消：提交照常完成，登记状态与生成队列保持一致，取消继续向调用方传播；不撤回、不补偿。
- ACK 的含义由“意图已在 workspace 登记”变为“意图已登记，并已被生成队列接纳”；ACK 不表示 canonical 记忆已经产生。

### 4.2 派发话题

- 本轮的派发话题是 CPU 输入清单的 `topic_id`：它是 prepare 按 Gateway 路由准备的话题，新话题已经预建，因此一定是真实 id。
- 进程在 CPU 分配时把派发话题记在进程一侧（例如工作集的一个槽位）；能力层经端口按线程 context 中的进程关联读取，只接受处在 Actor 阶段且仍在运行的进程，否则在登记之前拒绝。端口协议放在 `workspace.contracts`，由进程一侧实现、组合根注入，沿用执行线程层派生端口的做法，能力层与任务进程仍互不导入。
- CALL 子线程与主线程属于同一进程，使用同一话题。actor 的操作请求、MTP 指令与 CPU 都不能指定话题。

### 4.3 Patchouli 的意图提交

- `MemoryIntent` 接收登记产生的 `intent_id` 与 `pending_alias`，两者都必填；`submit_memory_intent` 不再派生别名，物化任务的别名、intent_id 与登记一致，结算事件（含只携带别名的 FAILED、CANCELLED）回到同一句柄。
- 提交结果区分接纳、确定性拒绝与结果未知。确定性拒绝沿用 settler 发布 FAILED；结果未知不发布事件。逐项结果需要从 controller 经 coordinator 交回，不再以空列表同时表示两者。
- 发起者取本次授权 scope 的 actor：主线程为进程 Agent，子线程为被调用方（与登记的 `from_actor` 一致）。生成任务以 `active:{intent_id}` 为标识，幂等语义不变。
- `GENERATION_SUBMIT_ACTIVE` 只剩意图提交服务一个调用方；Patchouli 不再有其他主动生成入口。

### 4.4 生成材料

- `submit_active` 取话题过去 N 个 block 与 `state_summary`；N 是 Patchouli 生成配置段的新配置项，默认 5，与现状一致，配置项随 `configs/config.yaml` 一同给出。
- 派发发生在交互封口之前，当前一轮天然不在材料中；新话题在派发时已预建但为空，材料只有 focus。话题读不到时沿用现有处理，按空材料生成。
- 现有的 `perception.fold_retain_recent_blocks` 服务于话题折叠，与本配置项无关。

### 4.5 登记与操作入口

- 登记提供“登记并进入 MATERIALIZING”与“标记确定性拒绝为 FAILED”的同步操作；删除 `claim_process`、`cancel_process`、`cancel_aliases`。结算事件订阅不变，FAILED 的同步标记与之后到达的事件按状态迁移规则幂等。
- `PendingAtom.process_id` 不再用于认领与取消；保留为观测关联还是删除，在实施评审时决定。
- 操作入口删除 `CancelIntentsRequest` 分支与返回后的补偿；线程 context 复查移入 actor API 的同步段（4.1 第 4 步）。
- `CancelIntentsRequest` 从 `workspace.contracts` 删除；`CallCoordinator` 不再撤回子帧的意图。

### 4.6 任务进程与 finalize

- completed 时不再认领意图；`seal_interaction` 与 `InteractionPayload` 删除 `materialize_tasks`，`InteractionSubmission` 的编码版本随之递增。
- Patchouli finalize 删除派发，仍等到交互 applied 后返回（W11），并照常记录预检索的引用命中；`FINALIZE_AGENT_RUN` 不再返回生成任务列表，返回类型在实施评审时确定。
- 关闭流程删除 `cancel_process`；线程 context 撤销、租借释放、CPU 输出流关闭与预建空话题清理不变。
- CPU 分配记录派发话题（4.2）。
- `RunCompleted.memory_task_ids`、`chat.run.completed` 事件数据中的 `memory_task_ids` 与 `ChatDoneEvent.memory_task_ids` 删除。

### 4.7 Alice

- MTP WRITE/UPDATE 的 ACK 在生成队列接纳后返回；ACK 文案是否改为说明“已进入生成队列”在实施评审时确定。
- 新增的派发错误映射为 MTP 错误：确定性拒绝与结果未知分别有错误类型与中英文案；错误类型名称、MTP 错误码与严重度在实施评审时确定。线程撤销、权限与资源不可用沿用现有映射。
- `CallCoordinator` 删除子帧失败时的撤回；子帧已提交的写入照常生成。

### 4.8 前端

- `types/chat.ts` 删除 `memory_task_ids`；`chatStore` 删除 `currentMemoryTaskIds` 与 done 后按 id 刷新任务。
- Memory Runtime 删除“本轮任务置顶”（记忆任务事件不携带 process_id），按创建时间排序；任务的创建与状态变化继续由 `applyRuntimeEvent` 合并 `memory.task.*` 事件，挂载时调用任务列表 API 补齐丢失的事件。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| workspace 能力层 | actor API 登记后经全局路由派发；同步段复查线程 context；读取派发话题；派发错误交给调用方 |
| workspace 登记 | 登记即进入 MATERIALIZING；同步标记 FAILED；删除认领、关闭取消与撤回 |
| workspace 契约 | 新增派发话题端口；删除 `CancelIntentsRequest` |
| 任务进程 | CPU 分配记录派发话题；completed 不认领；关闭不取消意图；删除 `memory_task_ids` |
| Patchouli | `MemoryIntent` 携带登记的别名与 intent_id；提交结果分三种；finalize 不再派发；材料轮数可配置 |
| core | `InteractionPayload` 删除 `materialize_tasks`；派发错误类型 |
| Alice | ACK 时点与派发错误映射；CALL 不再撤回 |
| server / 前端 | done 事件删除 `memory_task_ids`；前端改为只从事件捕获任务 |
| 配置 | Patchouli 生成配置新增材料轮数 |
| 公共路由与事件 | `memory_intent.submit` 有了生产调用方；`finalize_agent_run` 返回值变化；`chat.run.completed` 数据变化 |

## 6. 兼容与迁移策略

- 进程内替换，不涉及持久化数据：生成队列与交互提交队列都在进程内，`InteractionPayload` 删除字段后 `InteractionSubmission` 的编码版本递增即可。
- **SSE 与事件**：done 事件与 `chat.run.completed` 删除 `memory_task_ids`，仓库内只有前端消费，随阶段三一并修改。
- **MTP 语义**：ACK 返回得更晚；WRITE/UPDATE 可能收到派发错误；失败、取消的一轮与失败的 CALL 子帧已经提交的写入，现在都会生成记忆。
- **配置**：新增的轮数配置默认值与现状相同，默认行为不变。
- **话题清理**：进程未以 completed 结束时，预建的空话题仍会被清理，而本轮已派发的生成任务记着该 topic_id；记忆原子不保存 topic_id，影响只在任务记录与观测事件中。

## 7. 实施阶段

每个阶段结束时全量后端测试通过、可单独审查。

**阶段一：Patchouli 一侧**

1. `MemoryIntent` 携带登记的 `intent_id` 与 `pending_alias`，`submit_memory_intent` 删除别名派生；
2. 提交结果区分接纳、确定性拒绝与结果未知，逐项结果从 controller 经 coordinator 交回；
3. 生成配置新增材料轮数，`submit_active` 使用它；
4. finalize 派发与生产 chat 链路暂不改变，意图提交路由仍没有生产调用方。

验收：第 8 节 10、11 项。

实施记录（2026-10-13）：接纳结果为 `patchouli.contracts.memory_tasks` 的 `MemoryGenerationAdmission`（状态 `MemoryGenerationAdmissionStatus`：accepted、rejected、unknown；只有 accepted 携带任务快照）。`submit_generation_many` 与 `GENERATION_SUBMIT_ACTIVE` 返回与输入一一对应的接纳结果；intent 载荷冲突按结果未知处理（既有任务仍拥有结算权）。`MemoryIntent` 的 `intent_id`、`pending_alias` 必填，`MemoryIntentSubmissionResult` 以 `status` 区分三种结果。材料轮数配置为 `patchouli.generation.active_recent_blocks`（默认 5，可为 0），经 `MemoryGenerationCoordinator(recent_block_limit=...)` 注入。设计之外补充一项：读取话题材料失败时没有任何意图进入队列，逐项结算为 FAILED 并返回拒绝，不留下等不到结算的句柄。finalize 的派发暂时把接纳结果还原为任务列表，行为不变。

**阶段二：workspace 与 Alice 切换为实时派发**

1. 派发话题端口：CPU 分配记录派发话题，进程一侧实现端口，组合根注入；
2. 登记的同步操作；actor API 在同步段复查、读取话题、登记后经全局路由派发，屏蔽调用方取消，按结果返回 ACK 或抛出派发错误；
3. 操作入口删除撤回分支与返回后的补偿；删除 `CancelIntentsRequest` 与 CALL 的撤回；
4. 任务进程删除认领与关闭取消；`InteractionPayload` 与 `seal_interaction` 删除 `materialize_tasks`，编码版本递增；finalize 删除派发；
5. MTP 的派发错误映射与文案；
6. `allocation.py` 中“Topic 的新建与驱逐改到 interaction 提交之后”的说明按保留预建改写。

验收：第 8 节 1–9、12、13 项。

实施记录（2026-10-13）：`IntentDispatchTopicReader` 由 `ProcessThreads` 实现，CPU 分配把真实话题写入 `ProcessWorkingSet.dispatch_topic_id`；登记直接进入 MATERIALIZING，`process_id` 仅保留为观测关联。actor API 在同步段复查线程、读取话题并登记，持有 shield 保护的提交任务直至完成（含重复取消），随后向调用方传播取消。明确拒绝以 `IntentDispatchRejectedError` / `mtp.memory.intent_rejected`（AGENT_FAULT）返回，未知结果以 `IntentDispatchUnknownError` / `mtp.memory.intent_unknown`（SYSTEM_FAULT）返回。finalize 返回 `None`，仍等待 applied 并记录预检索命中；InteractionSubmission codec 升为 4。done 与完成事件的任务列表暂时为空，阶段三删除字段。

阶段二代码审查：已检查同步登记与撤销的竞态、取消任务持有与异常回收、CALL 身份与共享话题、失败事件与同步 FAILED 的幂等性、唯一主动生成入口及包依赖。修复了队列停止被误报为 unknown 的旧问题（改为 `WorkQueueStoppedError`），并将本地意图载荷校验失败同步结算为 FAILED，避免留下无法结算的句柄。完整后端验证已通过 3048 项、跳过 2 项，覆盖率 93.17%；新增边界用例另行定向验证。Ruff、Black、mypy 与差异检查通过。当前事实文档留待阶段三最终收尾晋升。


**阶段三：记忆任务的观察与收尾**

2. 前端删除 `currentMemoryTaskIds`、done 后刷新与本轮任务置顶；

## 8. 测试和验收标准

按[测试设计规范](../../governance/testing/test-design-standards.md)分类。能力层、登记、任务进程、Patchouli 生成链与 Alice MTP 使用真实对象，外部 LLM 与存储使用既有替身。

1. WRITE 的 ACK 在生成队列接纳之后返回：ACK 中的别名与生成任务的 `pending_alias`、intent_id 与登记一致；生成完成后同一句柄进入 SETTLED。
2. 只携带别名的 FAILED、CANCELLED 结算事件回到登记的同一句柄。
3. 确定性拒绝（UPDATE 基础原子不存在、生成队列拒绝）：agent 收到结构化错误，没有 ACK，句柄为 FAILED。
4. 结果未知：agent 收到结构化错误，句柄保持 MATERIALIZING；若其实已被接纳，之后的结算事件把它推进到终态。
5. 派发期间调用方被取消：提交照常完成，登记中不留下 PENDING，取消向调用方传播。
6. UPDATE 的基础冷读跨越 CPU 执行结束：不登记、不派发，以 `ThreadContextRevokedError` 拒绝；派发开始后线程被撤销：提交不被撤回。
7. ACK 之后 CPU 失败、停止或取消、进程关闭、CALL 子帧失败，意图都不被取消，生成照常完成。
8. CALL 子帧的 WRITE 以被调用方为发起者、与主线程同一话题，在提交时即派发。
9. 派发话题等于 CPU 输入清单的 `topic_id`（已有话题与预建的新话题两种情形）；进程不在 Actor 阶段时在登记之前拒绝；操作请求无法指定话题。
10. 生成材料为 `state_summary` 与过去 N 个 block，N 取自配置；默认值为 5。
11. 意图提交服务按传入的别名与 intent_id 构造物化任务，相同 intent_id 的重复提交复用原任务；提交结果区分接纳、确定性拒绝与结果未知，确定性拒绝发布 FAILED、结果未知不发布事件。
12. finalize 不再派发物化，`InteractionPayload` 没有 `materialize_tasks`；completed 的进程仍在交互 applied 后关闭，预检索引用命中照常记录；派发发生在交互封口之前，当前一轮不进入材料。
13. 结构：`GENERATION_SUBMIT_ACTIVE` 只由意图提交服务调用；生产代码不再引用 `claim_process`、`cancel_process`（登记）、`cancel_aliases`、`CancelIntentsRequest` 与 `materialize_tasks`；能力层与任务进程仍互不导入。
14. done 事件与 `chat.run.completed` 不再携带 `memory_task_ids`；前端 `npm run lint` 与 `npm run build` 通过。
15. 确定性 HTTP chat E2E：一轮内 WRITE 后 CPU 失败，记忆仍被生成；现有 chat E2E 按新语义通过。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| ACK 等待话题读取、UPDATE 的基础记忆读取与生成队列准入锁，延迟进入 agent 的执行循环 | owner 已接受；确定性 E2E 中观察 WRITE/UPDATE 的耗时 |
| 结果未知时句柄长期停在 MATERIALIZING | 归入搁置的结算对账；agent 收到错误后可自行重试 |
| agent 收到错误后重写，可能与其实已被接纳的前一次重复 | 生成侧的去重决策处理重复内容 |
| 失败、取消的一轮与失败的 CALL 子帧已提交的写入会生成记忆 | owner 已决定（W8） |
| 生成队列容量不足时，拒绝现在直接暴露给 agent | 沿用 `generation.queue_capacity`；拒绝为确定性错误 |
| 预建的新话题被清理后，生成任务记着已删除的 topic_id | 只影响任务记录与观测事件，记忆原子不保存 topic_id |
| 前端只靠 best-effort 事件观察任务 | 挂载时调用任务列表 API 补齐 |
| 能力层经端口读取进程状态 | 只经一个端口，由组合根注入，调用面由架构测试限定 |
| 实施命名与返回类型 | 已由阶段一、二记录确定：`IntentDispatchTopicReader`、`mark_failed`、三态接纳、两类派发错误、`active_recent_blocks`、finalize 返回 `None`，process_id 仅观测 |
