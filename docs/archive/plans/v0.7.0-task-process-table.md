# v0.7.0 任务进程表：落位与进程标识

> **文档状态**：Archived（阶段 A、阶段 B 已于 2026-09-28 实施并通过验收，commit `fa4fabd` 与 `c93657b`）。本文保留实施前的设计、验收口径与文档更新清单作为历史追溯；当前事实以[System 应用服务](../../system/application-services.md)、[系统边界与所有权](../../architecture/boundaries.md)及各子系统文档为准。

本计划是任务进程方向的第一批实施，只做两件事：

- **阶段 A 进程表落位**：把 chat run 注册表与 chat 编排从 `alice.application` 迁入 workspace 的 `process` 子包，改用进程的词汇；行为不变。
- **阶段 B 进程标识与取消收口**：以 `process_id` 取代 `interaction_id` 与 `generation_id` 作为进程标识，前后端契约同步修改；按已决定的取消规则收口。

两个阶段各自验收、各自提交。阶段 A 完成即可合并，阶段 B 在其之上进行。

设计依据：[任务进程 Idea](../../ideas/task-process-table-and-registration-entry.md) 第 1.2 节、Q-15、Q-16，[总 Idea](../../ideas/workspace-network-task-process-architecture.md) 第 10 节 D-9，以及当前代码。本计划不以其他活动计划为依据。

## 1. 背景和问题

1. **位置**：chat run 注册表（`ChatGenerationRunRegistry`）与 chat 编排（`ChatApplicationService`）在包分层重构时暂置于 `alice.application`（[System 应用服务](../../system/application-services.md)第 1 节、[AGENTS.md](../../../AGENTS.md) 第 3 节）。owner 已决定两者迁入 workspace 的 `process` 子包，分别演化为进程表与四阶段骨架（D-9）。
2. **标识**：一次 chat 同时有 `interaction_id` 与 `generation_id` 两个名字，后者只是前者的只读投影；命令请求不产生交互记录，也被分配了 `interaction_id`。owner 已决定以 `process_id` 作为任意任务进程的唯一标识（Q-16）。
3. **取消**：owner 已决定只有 Gateway 与 Actor 执行两个阶段可以取消，进入 Actor 执行前统一检查一次取消请求，其余位置不设取消响应点；外部取消必须带明确的 `process_id`，只有用户经唯一的 HTTP server 入口取消（Q-15）。

## 2. 目标与非目标

**目标**：

| 阶段 | 目标 |
|:---|:---|
| A | 进程表、进程记录与编排服务位于 `hivememory.workspace.process`；组合根、门面、入口与测试随之调整；workspace 内的依赖方向由测试守护；行为与对外契约不变 |
| B | `process_id` 是进程的唯一标识，贯穿 server 入口、进程表、SSE、停止请求、RuntimeEvent、Alice 路由参数与前端；传给 Patchouli 的 `interaction_id` 取 `process_id` 的值；取消只在 Gateway 与 Actor 执行两个阶段响应 |

**非目标**（留给后续批次，本计划不做）：

- Patchouli prepare/finalize 的拆分、`PreparedAgentRun` 的拆散、CPU 一侧编译记忆；
- 附件租借进入进程工作集、进程关闭时统一释放资源；
- Topic 按需创建与 SSE `topic_info` 的改造；
- CPU 端口、`workspace.contracts`、非 Alice 的 CPU；
- Alice 读取实现（resolver 与缓存）迁往 workspace；
- 写入意图迁移、ConversationSession 与前端会话模型；
- 命令系统的调整（包括内置命令暂时不可用）；
- A1 返工与生产入口接入认证网关；
- RuntimeEventType 的 `chat.run.*` 事件名、阶段取值 `alice` 的改名；
- Patchouli 内部 `interaction_id` 字段名、`InteractionPayload` 模型；
- Import Bus（现有 Passive Ingress）代码；
- workspace 其余子包的形成，以及 `workspace/runtime.py`、`workspace/registry.py` 的改名。

本计划不以 v0.7.0 的四条版本目标作为验收条件；版本目标在版本收尾时验收。

## 3. 当前状态（2026-09-28 核对）

### 3.1 代码位置与依赖

| 对象 | 位置 | 说明 |
|:---|:---|:---|
| `ChatRunPhase`、`ChatRunOutcome`、`StopResult`、`CancelResult`、`ChatRunStatusSnapshot`、`ChatGenerationRun`、`ChatGenerationRunRegistry` | `alice/application/chat_control.py`（247 行） | 注册表以 `interaction_id` 为键，`get`/`cancel`/`status` 只比较 `workspace_identity` |
| `ChatApplicationService`、`_ChatRunCancelled`、`_run_interruptible`、`NonStreamingChat*Outcome` | `alice/application/chat_service.py`（870 行） | 公开方法 `chat_scoped`、`chat_stream_scoped`、`cancel_generation_scoped`、`generation_status_scoped` |

- `chat_service.py` 只导入同目录的 `chat_control`、`components` 与 `core`；对 Gateway、Patchouli 与 Alice 的调用全部经 `GlobalSystemBus` 的全局路由（`GATEWAY_PROCESS`、`PATCHOULI_PREPARE_AGENT_RUN`、`PATCHOULI_FINALIZE_AGENT_RUN`、`PATCHOULI_CLEANUP_PREPARED_AGENT_RUN`、`ALICE_RUN_AGENT`、`ALICE_RUN_AGENT_STREAM`、`PATCHOULI_TOPIC_LIST_ACTIVE`）。因此迁入 workspace（L3）符合分层规则，不需要先建立 Alice 或 workspace 的 contracts。
- 装配与入口：`system/assembler.py` 构造 `ChatApplicationService`（`_ServicesBundle.chat`），`system/system.py` 以门面属性 `chat_service` 暴露，`server/deps.py` 的 `get_chat_service` 与 `server/routers/chat.py`（`POST /chat`、`POST /chat/stop`）消费。
- `alice/application/__init__.py` 只导出 `AgentRunService`，不导出 chat 相关对象。
- `tests/unit/workspace/test_import_boundaries.py` 规定：除 `capability` 与 `assets` 外，workspace 模块只能导入 `core` 与 workspace 自身。chat 编排导入 `components`（总线、运行时事件、trace context），迁入后必须在该测试中登记。

### 3.2 进程标识的现有用法

- server 的 chat 路由在进入服务前生成 `interaction_{uuid}` 作为 `interaction_id`；`ChatGenerationRun.generation_id` 是它的只读投影。
- SSE：首个事件 `generation_id` 在 Gateway 阶段之前发出；`run_status` 与 `done` 事件的数据携带 `generation_id`。
- 停止：`POST /chat/stop` 请求体为 `{generation_id}`，响应含 `generation_id`；客户端断开时路由以同一标识调用 `cancel_generation_scoped`（reason 为 `client_disconnected`）。
- Alice：`ALICE_RUN_AGENT` / `ALICE_RUN_AGENT_STREAM` 接收 `generation_id` 参数，存入 `RunSession.generation_id`，Alice 的运行事件以它同时填写 RuntimeEvent 的 `generation_id` 与 `interaction_id`。
- RuntimeEvent：`core/contracts/runtime_events.py`、`components/events/publisher.py` 的绑定上下文与 `server/models/runtime_event.py` 的响应模型都有 `generation_id` 与 `interaction_id` 两个字段；只有 chat 编排与 Alice 运行事件填写它们（Patchouli 记忆任务与 work queue 事件只填 `task_id`、`topic_id`）。
- Patchouli：`prepare_agent_run` 接收 `interaction_id`，用于 `AgentRunContext`、`InteractionPayload` 与提交；Qdrant 中的持久数据不保存 `interaction_id`（交互 Artifact 以 `turn_id` 与 `block_id` 记录）。没有代码校验 `interaction_` 前缀。
- 前端：`types/chat.ts`（`GenerationIdEvent` 与事件名 `generation_id`、done 与状态数据）、`services/chatApi.ts`（`stopGeneration` 请求体）、`stores/chat/streamHandlers.ts`、`stores/chat/chatStore.ts`（`_currentGenerationId`）、`types/kernel.ts` 与 `components/chat/KernelTerminalTab.tsx`（按 `generation_id` 分组）。

### 3.3 取消的现有行为

| 阶段 | 行为 |
|:---|:---|
| Gateway | 以 `_run_interruptible` 包装，停止请求直接取消阶段 task |
| Prepare | 不包装；在 prepare 之前与之后各检查一次停止请求 |
| Alice | 以 `_run_interruptible` 包装；进入时先检查停止请求 |
| Finalize | `request_stop` 返回 `already_finalizing`，拒绝取消 |

- prepare **之前**的检查紧跟 Gateway 结果之后，两者之间没有 await，其他 task 无法在此插入停止请求，而 `_run_interruptible` 在 Gateway task 结束时已经检查过一次；这次检查实际不可能触发。
- prepare 期间收到的停止请求被记录（`STOP_REQUESTED`），prepare 照常完成，随后在 prepare 之后的检查处生效，并经 `finally` 请求 Patchouli 清理 prepared run。
- 注册表只比较 `workspace_identity`。`IdentityScope` 要求 actor 的 `user_id` 等于 Workspace 的 `owner_user_id`，因此比较结果等价于“同一用户、同一 Workspace”；取消不是 Agent action，不比较 agent。

## 4. 目标设计

### 4.1 阶段 A：模块落位与命名

新建 `src/hivememory/workspace/process/`，删除 `alice/application/chat_control.py` 与 `chat_service.py`：

| 新模块 | 内容 | 来源 |
|:---|:---|:---|
| `workspace/process/__init__.py` | 导出下表的公开类型 | 新增 |
| `workspace/process/table.py` | 进程表与进程记录 | `chat_control.py` |
| `workspace/process/service.py` | 注册入口与四阶段骨架（编排） | `chat_service.py` |

命名映射（阶段 A 只改类型名与位置，方法名与字段名保持不变，留给阶段 B）：

| 现名 | 新名 |
|:---|:---|
| `ChatRunPhase` | `ProcessPhase`（取值不变） |
| `ChatRunOutcome` | `ProcessOutcome`（取值不变） |
| `ChatGenerationRun` | `ProcessRecord` |
| `ChatGenerationRunRegistry` | `ProcessTable` |
| `ChatRunStatusSnapshot` | `ProcessStatusSnapshot` |
| `ChatApplicationService` | `TaskProcessService` |
| `_ChatRunCancelled` | `_ProcessCancelled` |

| 门面属性 `HiveMemorySystem.chat_service` | `process_service` |
| `_ServicesBundle.chat` | `process` |
| `server.deps.get_chat_service` | `get_process_service` |

- 模块与类的 docstring 改为进程的表述，删除“位于 Alice、暂置”的说明。
- HTTP 路由路径（`/chat`、`/chat/stop`）与 `chat_scoped`、`chat_stream_scoped` 方法名不变：它们是主动请求的入口。
- 命名在实施评审时可以调整，但同一概念只用一个名字。

### 4.2 阶段 A：workspace 内的依赖方向

修改 `tests/unit/workspace/test_import_boundaries.py`：

1. `workspace/process` 与 `capability`、`assets` 一样，可以依赖更低层的机制（`components`）；
2. 新增规则：workspace 中 `process` 以外的模块不得导入 `hivememory.workspace.process`。这是 D-9“能力层与共享设施不得依赖 process”在本批次能落地的部分；其余子包形成时再补充方向规则。

### 4.3 阶段 B：`process_id`

- **生成**：server 的 chat 路由生成 `process_{uuid}` 作为 `process_id`，在进入服务前冻结，与现在生成 `interaction_id` 的位置相同。
- **进程表**：`ProcessRecord` 以 `process_id` 取代 `interaction_id` 字段与 `generation_id` 属性；`ProcessTable` 以 `process_id` 为键；`CancelResult`、`ProcessStatusSnapshot` 的 `generation_id` 字段改为 `process_id`。
- **服务方法**：`chat_scoped` 与 `chat_stream_scoped` 的参数 `interaction_id` 改为 `process_id`；`cancel_generation_scoped` 改为 `cancel_process_scoped`，`generation_status_scoped` 改为 `process_status_scoped`，参数均为 `process_id`。
- **Patchouli**：调用 `PATCHOULI_PREPARE_AGENT_RUN` 时传 `interaction_id=process_id`；Patchouli 侧签名与 `InteractionPayload.interaction_id` 字段名不变（Q-16）。
- **Alice**：`ALICE_RUN_AGENT` / `ALICE_RUN_AGENT_STREAM` 的参数 `generation_id` 改为 `process_id`；`RunSession.generation_id` 改为 `process_id`；Alice 运行事件绑定 `process_id`。
- **RuntimeEvent**：`RuntimeEvent`、`RuntimeEventPublisher` 的绑定上下文与 `RuntimeEventResponse` 去掉 `generation_id` 与 `interaction_id`，新增 `process_id`；chat 编排与 Alice 运行事件填写它。
- **SSE**：首个事件改名为 `process_id`，数据为 `{"process_id": ...}`，仍在 Gateway 阶段之前发出；`run_status` 与 `done` 的数据字段 `generation_id` 改为 `process_id`（`ChatDoneEvent` 同步）。
- **停止**：`POST /chat/stop` 请求体 `StopChatRequest.process_id`，响应字段 `process_id`；客户端断开时以 `process_id` 调用 `cancel_process_scoped`。
- **前端**：事件名与类型改为 `process_id`（`GenerationIdEvent` 改为 `ProcessIdEvent`，`onGenerationId` 改为 `onProcessId`，`_currentGenerationId` 改为 `_currentProcessId`，`stopGeneration` 改为 `stopProcess`）；`types/kernel.ts` 的 RuntimeEvent 字段改为 `process_id`，Kernel Terminal 按 `process_id` 分组。

### 4.4 阶段 B：取消收口

- 删除 prepare 之前的停止检查（流式与非流式两条路径）。依据 3.3，它实际不可能触发，删除后可观察行为不变，只让代码与规则一致。
- 保留：Gateway 与 Alice 阶段经 `_run_interruptible` 可取消；prepare 期间的停止请求在进入 Alice 前生效（prepare 之后的检查与 `_run_interruptible` 的入口检查）；finalize 拒绝取消；客户端断开由 server 路由以 `process_id` 发起取消。
- 授权保持现状：只比较 `workspace_identity`，即同一用户、同一 Workspace（3.3）；取消入口只有 `POST /chat/stop` 与路由内的断开处理。

## 6. 兼容与迁移策略

- **阶段 A**：纯结构迁移，不保留旧模块路径的转发 shim；所有导入在同一提交内更新。
- **阶段 B**：契约改名不设兼容期。前端在仓库内，与后端在同一阶段修改；`generation_id` 与 `interaction_id` 作为进程标识的用法直接删除，不保留别名字段。仓库外若有客户端调用 `/chat/stop` 或读取 RuntimeEvent 的 `generation_id`，需要随之修改。
- 不涉及数据迁移：标识只存在于进程内与传输契约中。
- 回滚：两个阶段各为独立提交，按阶段回退即可。

## 8. 测试和验收标准

测试遵循[测试设计规范](../../governance/testing/test-design-standards.md)。

### 阶段 A

- 迁移的测试只改导入与名称，不改断言；它们在新位置全部通过，即证明行为未变。
- 新增的依赖方向规则（4.2）需要能被违反场景击穿：在 workspace 的非 process 模块中加入对 `hivememory.workspace.process` 的导入时，测试应失败。实施时手动验证一次后撤销该改动，不提交。
- `tests/unit/architecture/test_package_layers.py` 通过，且 `KNOWN_UPWARD_IMPORTS` 不变。

### 阶段 B

- 进程记录与进程表：以 `process_id` 注册、查询、取消；同一 `process_id` 重复注册被拒绝；跨用户或跨 Workspace 的取消得到 `not_found`（已有断言改名）。
- SSE：首个事件为 `process_id`，在 Gateway 阶段之前发出；`done` 与 `run_status` 携带同一 `process_id`。
- 取消：Gateway 阶段取消立即生效；prepare 期间的取消在进入 Alice 前生效并清理 prepared run；Alice 阶段可取消；finalize 期间返回 `already_finalizing`（已有 `test_gateway_chat_flow` 的场景改名后保留）。
- 停止入口：`/chat/stop` 以 `process_id` 取消；客户端断开时以同一 `process_id` 发起取消（`tests/unit/server/routers/test_chat.py`）。
- RuntimeEvent：chat 编排与 Alice 运行事件携带 `process_id`（`tests/unit/components/events/test_publisher.py`、`tests/unit/alice/runtime/test_runtime_events.py`、`tests/integration/alice/runtime/test_runtime_events.py`）。
- Alice 路由以 `process_id` 接收并关联运行事件（`tests/integration/alice/application/test_agent_run_service.py`）。
- 前端：`npm run lint` 与 `npm run build` 通过；手动在开发环境发起一次 chat 并点击停止，确认停止请求携带 `process_id` 且收到取消终态。
