# v0.7.1 工具解析链路重写

> 状态：Archived（2026-10-30，三个阶段实现、代码审查与实测验收完成后归档；当前事实见[数据模型](../../architecture/data-model.md)、[感知与短期话题](../../patchouli/perception.md)、[Patchouli 生成](../../patchouli/generation.md)与 [Import Bus](../../system/import-bus.md)，实测验收结论见第 12 节）。以下为实施时的计划原文。原状态：Planned（2026-10-30；阶段一完成后 owner 决定把一次工具调用与它的结局合并为一个事件，第 5 节已按合并后的设计改写，见第 5.1 节）。

## 1. 背景和问题

Claude Code 接入后，Alice 的 MTP 指令与外部 harness 经 HiveMemory MCP 工具的调用并存于同一套下游。[工具调用数据形态调查基线](../../governance/baselines/tool-call-data-shapes-2026-10-30.md)（下文称“基线”）逐层核对了两条链路的数据形态，问题集中在两处：

- **工具调用进入 `TurnEvent` 时不同形**：
  - `tool_name` 在 MTP 一侧是指令目标，在外部一侧是工具名；MTP 的 `target` 与 `tool_name` 重复；读取方取值的优先级互相矛盾。
  - 两条链路写出的事件在 `role`、`content`、`target`、`tool_args`、`status`、`render_as` 上都不同。
  - MTP 调用事件的 `content` 含指令前正文，而这段正文已另存为一条 `assistant_message`；结果事件重复调用事件的字段；调用事件的状态在执行后被改写。
  - WRITE、UPDATE 的 ACK 中的 pending alias 只写进回填正文，Alice 的引用线索再用正则取回。
- **感知层解析分散、来源不一致**：
  - `InteractionPayload` 同时携带 `turn_events` 与由它派生的 `mtp_traces`；动作在封口与感知各归约一次，轨迹沿用载荷，生成视图按 `action_id` 把两者拼回去；
  - LLM 接力摘要只读轨迹，看不到思考与外部工具，被折叠的块在结算前失去这些材料的影响；
  - 生成视图把全部动作排在前、回复排在后，丢失了正文与动作的先后；
  - 渲染规则分散在生成视图、接力摘要与 token 统计中，渲染出的材料只在新建记忆时保存。

本计划并入原 Todo《导入的 MCP 读取在轨迹中显示 alias》（2026-10-29 由记忆访问计划阶段四审查登记）。该 Todo 记录的现象是：READ 轨迹的目标取动作的 `tool_name`；Claude Code 经 MCP 读取时，`tool_name` 是工具调用名 `mcp__plugin_hivememory-connector_hivememory__memory_read`，所读的 alias 在参数 `aliases` 中，生成视图因此只显示 `READ: mcp__plugin_…__memory_read`，看不出读了哪些记忆。基线第 8.1 节复现了这一现象。它是上面“`tool_name` 含义重叠”的一个表现，由本计划的第 5.1 节从根上处理。

owner 决定（2026-10-30）：整条工具解析链路重写，`TurnEvent` 必须承载唯一的 Agent 交互原子事件，分为工具调用统一进入 `TurnEvent` 与感知层解析这一份事件集两部分。设计讨论与各项决定的记录见 [工具解析链路重写 Idea](../ideas/tool-call-parsing-chain.md)；本计划采纳其中的候选设计。

## 2. 目标与非目标

### 2.1 目标

- 两种来源写出的 `TurnEvent` 同形：字段含义相同，来源之间真实存在的差异只体现为取值；下游不判断来源。
- 一个事实一个字段：一次工具调用与它的结局是一个事件，读取方不再配对；“调用了什么”只由 `verb` 或 `tool_name` 之一表达。
- `InteractionPayload` 只以 `turn_events` 表达交互内容，不携带派生的或与事件重复的表达。
- 感知层对事件集只解析一次，生成视图、LLM 接力摘要与 token 统计共用唯一的渲染函数。
- 导入的 MCP 读取在生成视图中显示所读的 alias，与 Alice 的 MTP READ 渲染相同。

### 2.2 非目标

- 新增事件种类、事件时间或来源元数据（[外部会话 Idea](../../ideas/external-session-and-topic-projection.md) 2.3 的候选扩展）；
- Alice 流式交付事件（`mtp_start`、`mtp_result` 等）的字段；
- 记忆价值策略，以及 Gateway 价值预判（`worth_saving`）的整体去留：本计划只把它移出载荷与逻辑块；
- MTP READ 截断正式记忆正文（[Todo](../../todo/mtp-read-content-truncation.md)）；
- 生成材料每轮上限的校准（[Todo](../todo/generation-material-filtering-and-truncation.md)）；
- 渲染材料的查看入口（按话题或交互 Artifact 输出材料）；
- 读取已持久化的旧交互快照或旧生成视图。

## 5. 目标设计

### 5.1 统一的 TurnEvent

owner 决定（2026-10-30，阶段一完成后）：一次工具调用与它的结局合并为一个事件。调用与结局一一对应，阶段一的事件形态下每个读取方（历史重放、减重、引用线索、感知层、前端会话历史、CALL 回填）都要按 `action_id` 把二者配回一起；拆开存放额外记下的只有结果的到达位置，没有读取方使用。

公共字段为 `kind` 与 `sequence`。各种事件可以出现的字段：

| kind | content | action_id | tool_name | verb | targets | tool_args | status | result | produced_aliases |
|:---|:---|:---|:---|:---|:---|:---|:---|:---|:---|
| user_message | 用户消息 | — | — | — | — | — | — | — | — |
| assistant_message | 助手正文的一段 | — | — | — | — | — | — | — | — |
| thought | 思考正文 | — | — | — | — | — | — | — | — |
| tool_call | 调用原文：MTP 为指令片段，结构化调用为空串 | 必填 | 外部工具的名字 | HiveMemory 能力动词 | 动词的作用对象 | 参数 | 结局 | 执行者收到的返回原文 | 本次调用产出的 alias |

字段语义：

- **`content`**：执行者写出的原文，重放据此还原。MTP 调用事件只存指令片段，指令前正文只在它前面那条 `assistant_message` 中。原文与结构化字段描述同一次调用：原文供重放，下游只按结构化字段解读；解析失败时只有原文（owner，2026-10-30）。
- **`action_id`**：调用事件必填且轮内唯一，标识一次调用：MTP 为 `action_{iteration}_{sequence}`，Claude Code 为 `tool_use.id`。不再用于配对；CALL 回填按它找到挂起的调用，CALL 编排的运行时状态也以它为键。思考与正文不带 `action_id`。
- **`verb` 与 `tool_name`**：二者互斥，共同回答“调用了什么”（owner，2026-10-30）。
  - `verb` 取 SEARCH、READ、RUN、WRITE、UPDATE、CALL：MTP 调用取指令动词；外部 harness 调用 HiveMemory 的 MCP 工具时取对应的动词，不记录 harness 的调用名。
  - `tool_name` 是外部工具的名字，例如 `Bash`、`Read`。
  - 不合并为一个字段：动词是封闭词表，外部工具名是开放词表，两者会重名。
  - MTP 指令无法解析时二者都为空。
- **`targets`**：动词的作用对象，元组。READ 为 alias 列表；RUN 为工具 alias 或代码记忆 alias；UPDATE 为被更新的 alias；CALL 为被调用 Agent；SEARCH 与 WRITE 的通配目标为空元组。
- **`tool_args`**：只放参数，不放作用对象。两种来源的 SEARCH 都从 `tool_args["query"]` 取查询。
- **`status`**：调用的结局，取 `success`、`ack`、`error`、`cancelled`。MTP 取回填的响应状态（`warning` 从不作为状态产生，`suspend` 不写入事件）；MCP 为 `error` 或 `success`。
- **`result`**：执行者收到的返回原文：MTP 为回填文本，CALL 为格式化的 CALL 响应，外部工具为结果正文。
- **没有结局**（`status` 与 `result` 都为空）表示结局没有记录：执行者拿到结果之前被取消或失败，或来源没有记下结果。后者真实存在：Claude Code 的会话记录有时只记下一批并行调用中最后一个的结果（2026-10-30 核对本机会话记录，2639 批并行调用中有 370 批），模型其实收到了全部结果。因此没有结局不等于调用没有完成，渲染不作这样的断言。
- **`produced_aliases`**：WRITE、UPDATE 的 ACK 为 pending alias，CALL 为子帧回填的 `artifact_aliases`，其他为空。

删除的字段：`role`（由 `kind` 决定）、`target`（由 `targets` 取代）、`tool_kind`（由 `verb` 取代）、`render_as`（回填正文已带标题）、`assistant_message` 上的 `status`；删除 `tool_result` 事件种类。

一轮事件集的不变量：

- 恰有一条 `user_message`，序号为 0；序号轮内唯一、严格递增；
- 每个调用的 `action_id` 轮内唯一；
- 字段只出现在上表允许的事件种类上；`verb` 与 `tool_name` 不同时出现；`verb` 为空时 `targets` 为空；`status` 与 `result` 同时出现或同时为空；没有结局时 `produced_aliases` 为空。

单个事件的字段规则由 `TurnEvent` 自身校验；一轮的不变量由 core 中的一个函数校验，`InteractionPayload` 构造时调用它。违反时显式失败，不修补。

**补全结局**：结局晚于调用写出时（Alice 的 CALL 挂起后回填），以带结局的新事件替换原调用事件，序号不变。补全由 `TurnEvent` 的一个方法统一执行，只对没有结局的调用事件进行，已有结局时显式失败。事件集因此不再严格只追加：没有结局的调用至多被替换一次。

### 5.2 Alice 写出事件

| 时机 | 写出的事件 |
|:---|:---|
| 生成中断于 MTP 指令，且指令前有正文 | `assistant_message`，content 为 `prefix_text` |
| 指令解析成功 | `tool_call`，没有结局：content 为指令片段，`verb` 为指令动词，`targets` 取 `MTPTarget.aliases`（通配为空），`tool_args` 为指令参数 |
| 指令解析失败 | `tool_call`，没有结局：content 为指令片段，`verb` 与 `tool_name` 为空；随后补全为 error 结局 |
| 指令执行完成（CALL 除外） | 补全调用的结局：`status` 为响应状态，`result` 为回填文本，`produced_aliases` 取 `pending_alias` |
| CALL 挂起 | 调用没有结局 |
| CALL 回填 | 按 `action_id` 找到挂起的调用并补全结局：`status` 为子帧结局，`result` 为格式化的 CALL 响应，`produced_aliases` 取 `artifact_aliases` |
| 取消或失败时的半截正文 | `assistant_message`，不带状态 |

- 除 CALL 外，调用在指令执行完成后连同结局一起写出，执行中被取消时这次调用不记录（与阶段一相同）；只有挂起后被取消的 CALL 留下没有结局的调用。
- 删除“执行器没有结果时写失败结果”的分支，遇到时显式失败。
- 运行时的 working history 不变。

### 5.3 连接器与 Import Bus

连接器（owner 决定 2026-10-30：HiveMemory MCP 工具的参数在连接器归一化）：

- 识别表由“调用名 → 动词”扩展为“调用名 → 动词与作用对象参数”：`memory_read` 为 READ，作用对象是 `aliases`；`memory_search` 为 SEARCH，没有作用对象。
- HiveMemory 的 MCP 工具：写 `verb` 与 `targets`，作用对象参数移出 `tool_args`，不上传调用名。外部工具：写 `tool_name` 与 `tool_args`。
- 工具结果按 `tool_use_id` 补全到同一轮的调用上：`status` 在 `is_error` 时为 `error`，否则为 `success`；`result` 为结果正文。会话记录中没有结果的调用不带结局；找不到调用的结果跳过，与读取器对不认识的结构一律跳过一致。
- 不再上传 `assistant_final_text`；思考、正文与跳过子代理内部过程等其余取舍不变。

Import Bus：

- 导入事件为 `assistant_message`、`thought`、`tool_call` 三种，接受第 5.1 节的字段，`produced_aliases` 除外（外部 harness 只能检索与读取，不产出 alias）。不再接受 `tool_result` 事件与 `tool_kind`、`role`、`target`、`render_as`，请求体不再接受 `assistant_final_text`。
- 只校验通用规则，不认识 MCP 工具的参数结构：导入的 `verb` 只能是 SEARCH 或 READ；READ 的 `targets` 非空；第 5.1 节的不变量。违反时返回 422。
- 服务端写出序号 0 的用户消息事件；是否有输出改为看用户消息之后有没有事件。
- MCP 工具的参数改名时，`mcp_server` 与连接器的识别表在同一次改动中修改。

### 5.4 载荷与封口

`InteractionPayload` 的字段处理（owner 决定 2026-10-30：只以 `turn_events` 表达交互内容）：

| 字段 | 处理 |
|:---|:---|
| `turn_events` | 保留，唯一的交互记录 |
| `outcome`、`model_used`、`used_attachments` | 保留：本轮结局、执行者使用的模型与实际使用的附件，不是对事件的解析 |
| `mtp_traces` | 删除：由事件派生 |
| `user_message`、`assistant_final_text` | 删除：与事件重复 |
| `rewritten_query` | 删除：Gateway 对用户消息的改写，感知层只有接力摘要使用，改用用户消息与本轮过程 |
| `worth_saving` | 删除：不参与任何决定；Import Bus 的观测事件直接取 Gateway 决定 |

- **两段文字**：用户消息（序号 0 的事件正文）与回复正文（全部 `assistant_message` 按序号以空行拼接）由 core 中两个函数从事件集得到，载荷与逻辑块以只读属性提供，不保存、不序列化。CPU 交给流式 `done` 的最终回复仍由 CPU 组装。
- **封口**：不再归约动作与轨迹，不再接收 `user_message` 与 Gateway 决定。序号 0 的用户消息事件由提交方写出：Alice 执行循环已经写出，Import Bus 由服务端写出。CPU 只返回正文、没有 `assistant_message` 事件时，仍由封口补一条。
- **chat 入口**：拒绝空消息（422），使 Alice 总会写出序号 0 的用户消息事件。

### 5.5 感知层的解析与渲染

- **位置**：解析与渲染放在 `engines/perception` 的同一个模块；`prompts/transcript/actions.py` 并入该模块；`engines/perception` 不再依赖 `prompts`，生成视图的组装（`prompts/transcript/generation.py`）调用它。
- **解析**：用户消息之后的事件按序号就是步骤，每一步是一段助手正文、一段思考，或一次工具调用（含结局，可能没有结局）。思考只按先后排列，不归属动作。
- **新增与删除的概念**：不新增类型。删除 `ActionReducer`、`TraceReducer`、`AgentAction`、`TraceItem`，以及 `TurnRecord` 上的 `actions`、`semantic_traces`、`user_query`、`rewritten_query`、`assistant_final_text`。
- **唯一的渲染**：生成视图、LLM 接力摘要与 token 统计共用一个渲染函数，输入只有事件集与截断配置（`patchouli.generation.transcript`）。规则：

  | 步骤 | 渲染 |
  |:---|:---|
  | 用户消息 | `[User]: …` |
  | 助手正文 | `[Assistant]: …`，按出现位置穿插在动作之间 |
  | 思考 | `- THOUGHT: …`，按 `max_thought_chars` 截断 |
  | 能力步骤 | 一行摘要，不渲染结果：`SEARCH: "查询"`、`READ: a, b`、`RUN: 目标 (状态)`，没有结局时状态为 `no result`；WRITE、UPDATE、CALL 不渲染 |
  | 外部工具步骤 | `- TOOL: 工具名 参数摘要`，有结局时其后逐行 `RESULT: …` 或 `RESULT (error): …`，按 `max_args_chars`、`max_result_chars` 截断 |
  | 无法解析的 MTP 指令 | 不渲染 |

  `max_turn_action_chars` 只约束思考、能力步骤与外部工具步骤，超出时的降级与省略顺序沿用现有规则；结局不是 completed 时在轮首标注 `[Outcome: …]`。
- **生成视图**：`GenerationTurn` 改为结局、用户消息、按顺序的材料条目（含助手正文）与来源身份；转写不再有单独的 `[Actions]` 段与末尾的 `[Assistant]` 行。
- **接力摘要**：LLM 接力的近期事件改用同一份材料，接力提示词中“近期事件”的说明随之修改；规则接力的请求计数取用户消息，工具列表取工具步骤（`verb` 的小写或 `tool_name`）。
- **token 统计**：逻辑块的 `total_tokens` 改为对渲染出的整轮材料估算。
- **逻辑块与快照**：`TurnRecord` 只保留 `outcome`、`turn_id`、`identity`、`turn_events`；`LogicalBlock` 删除 `worth_saving`、`gateway_intent`、`anchor_text`、`is_complete`；交互 Artifact 快照只保存事件以及块标识、时间、来源身份与结局。

### 5.6 其他读取方

|:---|:---|
| Alice 会话历史重放（`prompts/transcript/history.py`） | 用户消息与工具结局进入 user 消息，其余进入 assistant 消息；把紧邻的 `assistant_message` 与随后的 `tool_call` 合并成一条助手消息，与运行时一致；调用有结局时其后是一条结局的 user 消息；不再按 `render_as` 补前缀；删除没有事件时用文字拼历史的分支 |

- 会话与短期话题只保存在进程内存中，升级后从空开始，不存在旧形态的数据。

## 10. 风险与待决问题

### 10.1 风险

- **接力摘要变慢**：LLM 接力的输入加入思考与外部工具过程，单块最多约为单轮上限加上问答正文，可能更常超过 `summary_timeout_seconds` 而回退为规则摘要。实测验收记录耗时；必要时在[生成材料 Todo](../todo/generation-material-filtering-and-truncation.md) 中与每轮上限一并调整。
- **生成材料格式改变**：转写不再有单独的 `[Actions]` 段，提取提示词没有描述这一格式，但提取质量可能变化，随[真实使用观察](../todo/import-bus-real-use-observation.md)跟踪。
- **升级窗口丢失导入**：服务端先于插件升级时，这段时间的轮次被拒绝并跳过（第 7 节）。
- **阶段一的临时适配**：两个归约器在阶段一改读新字段、阶段二删除，阶段之间不发布。
- **事件被替换**：补全结局时调用事件被替换一次，事件集不再严格只追加。补全只经 `TurnEvent` 的一个方法，已有结局时显式失败；只在执行者自己的事件列表上进行，封口之后的事件集不再改变。

### 10.2 待决问题

无。第 5 节的候选细节在计划评审时确认。

### 阶段二：载荷边界、感知层与调用结局合并（2026-10-30，commit `7b3d545c`）

按第 5.4、5.5 节实施，感知层的解析与渲染集中在 `engines/perception/material.py`。阶段一完成后 owner 决定把一次工具调用与它的结局合并为一个事件（第 5.1 节），本阶段一并改写阶段一的事件形态、两侧写出与全部读取方。与计划描述不同或计划未写明的取舍：

- `action_id` 保留，只标识一次调用、不再用于配对：CALL 编排的运行时状态以它为键，回填据此找到挂起的调用；删除它需要为回填另加序号字段，或依赖“挂起的调用一定是最后一个事件”这一隐含前提。
- Alice 执行循环在指令执行完成后才写出调用事件，执行中被取消时这次调用不记录（与阶段一相同）；只有 CALL 挂起时先写出没有结局的调用，回填时补全。计划起初写成“调用在执行前写出”，已按代码更正。
- 核对本机 Claude Code 会话记录发现，同一条消息并行发出多个调用时，记录有时只记下最后一个调用的结果（2639 批并行调用中有 370 批），模型其实收到了全部结果。“没有结局”因此定义为结局没有记录，渲染不断言调用未完成（RUN 摘要写 `no result`）。
- 前端会话测试中 CALL 的数据仍使用阶段一已删除的 `tool_kind`、`target`，一并修正。
- 讨论中发现 Claude Code 的后台任务完成后以通知唤醒 Agent 续作，连接器把续作接在已经提交的上一轮之后，按代码推断不会被导入；owner 决定之后与 controller 模式的被动请求一并详细设计，记入[任务进程 Idea](../../ideas/task-process-table-and-registration-entry.md#26-被动请求q-6) 第 2.6 节。
