# v0.8.0 记忆类型的收敛：去掉 WORK_IN_PROGRESS、合并资源记忆与已有记忆的迁移

> 状态：Archived（2026-11-17，已实施，日常与开发实例都已迁移，实施记录见第 11 节）。当前事实见 [Patchouli 生成](../../patchouli/generation.md#3-三种生成模式)第 3 节、[MTP 契约](../../contracts/mtp.md#33-run)第 3.3 节与[生命周期](../../patchouli/lifecycle.md#2-生命力模型)第 2 节。v0.8.0 第一个方向“记忆类型的收敛”的第一份计划（owner，2026-11-17）。设计依据见[类型体系 Idea](../../ideas/memory-type-system.md)第 6、7 节；AGENT_PROFILE 移到 AgentProfileStore 是同一方向的下一份计划，本计划收尾之后建立。

## 1. 背景和问题

类型现在只是展示与过滤用的标签，外加一个衰减倍数；其中三个类型的问题在日常使用中已经暴露（[类型体系 Idea](../../ideas/memory-type-system.md)第 6.1、6.2、7.1 节）：

- **WORK_IN_PROGRESS**：一条 WIP 只在产生时决定一次类型，修订改不了它，也没有关闭的状态，于是成了名义上一直在进行的工作；外部会话回流时生成的 WIP 所述工作，在生成之前就已经合并。被动提取的拆分规则把“一项工作的当前状态”列为单独成条的一件事，所以只删标签不够。
- **CODE_SNIPPET 与 URL_RESOURCE**：两者都是对一个外部资源的记忆，同质；存下的副本会过时，读者需要的是它是什么、为什么重要、在哪里，真相留在源头。
- **CODE_SNIPPET 作为 RUN 的门槛**：RUN 只接受 CODE_SNIPPET，把整段正文当作 Python 在沙箱中执行；生成链写出的 CODE_SNIPPET 基本运行不了，能否运行本来是某一份内容的性质，不是类型的。

2026-11-17 只读计数，日常实例中带这三个类型的数据在三处：

- 中期库：WORK_IN_PROGRESS 55 条、CODE_SNIPPET 62 条、URL_RESOURCE 7 条；
- 冷库：归档的 16 条中有 CODE_SNIPPET 5 条；
- 版本记录：1125 份版本 Artifact 中，有 265 个快照（涉及 206 条记忆，含已删除的）记着这三个类型。

记忆原子、归档与版本快照都按 schema 2.1 严格解码，类型取值不在枚举中就读不出来。

## 2. 目标与非目标

### 2.1 目标

1. 去掉 WORK_IN_PROGRESS 类型，中期库不再收“当前进度”（owner，2026-11-15）。
2. CODE_SNIPPET 与 URL_RESOURCE 合并为统一的资源记忆类型（owner，2026-11-16）。
3. v0.8 关闭 RUN 的用户工具路径：解析记忆、把正文放进沙箱执行的那一条；`sys_*` 系统工具不受影响（owner，2026-11-16）。
4. 中期库与冷库中已有的这三类原子按 owner 逐条给出的去向改类型或删除（owner，2026-11-17）；版本记录保持原样。

### 2.2 非目标

- AGENT_PROFILE 移到 AgentProfileStore（文件存储，一个 Agent Profile 一个文件，owner，2026-11-17）：同一方向的下一份计划。
- FACT 的拆分、用户一侧的三类、REFLECTION 改为经历：已决定，但不进入首份计划，FACT、REFLECTION 与 USER_PROFILE 维持现状（owner，2026-11-16）。
- 可运行的轴、环境声明与 RUN 的重新打开：等可运行的轴或 MaaT 落地。
- “做到哪了”的新去处（短期记忆或经历节点上的状态）：本计划只删除，不提供替代的读取入口。
- 生成链路的结构（`GenerationRequest`、`GenerationOutcome`、提交）不变；馆长 agent、被动结算的复核与主动写入的材料都不在本计划。

## 3. 当前状态（2026-11-17 核对，commit `5853d8e3`）

- **类型枚举**：`MemoryType` 有七个值（`core/models/memory.py`）；服务端管理接口的类型清单（`server/models/memory.py`）与前端的类型列表、图标与创建表单（`frontend/src/constants/memories.ts`、`types/memory.ts`、`MemoryTypeTile.tsx`、`CreateMemoryModal.tsx`）各有一份。
- **生成提示词**：被动、写入与合并三份提示词的中英文版本都列出六个类型及说明，被动提示词的拆分规则包含“一项工作的当前状态”（`i18n/prompts.py`）。模型给出未知的类型时一律落为 FACT（`engines/generation/engine.py`）。合并由模型重选类型。
- **alias 前缀**：按类型取 `code`、`url`、`wip` 等前缀（`engines/generation/alias.py`），只影响新建的记忆。
- **MTP**：SEARCH 的 `type:` 过滤把 `code`、`url`、`wip` 等别名映射到类型，未知别名只给出警告、不加过滤（`core/mtp/parser.py`）。
- **RUN**：`run.py` 先查 `sys_*` 系统工具；否则经操作入口提交 `ResolveRunTargetRequest`，由 actor API 以 `memory.run` 授权并解析别名，`runnable_only` 只为 CODE_SNIPPET 记录引用（`workspace/capability/actor/memory.py`）；类型不是 CODE_SNIPPET 时以 `mtp.run.type_mismatch` 拒绝，否则 `execute_user_tool` 把正文交给沙箱执行（`agent_runtime/tools/user.py`）。
- **生命力**：固有价值权重按类型取配置（`code_snippet_weight` 1.0、`url_resource_weight` 0.8、`work_in_progress_weight` 0.5，`config/patchouli.py`、`configs/config.yaml`）。`VitalityCalculatorConfig` 没有禁止多余的键。
- **历史与冷库**：版本 Artifact 在运行时只写不读（回放脚本按原始 JSON 读取），其中的快照一旦被读回，要经 `validate_memory_atom_snapshot` 按 `MemoryAtom` 严格校验；冷库以文件保存整条原子，复活时经 `decode_memory_payload` 严格解码（`memory_library/adapters/long_term.py`），`persist` 允许覆盖写入同一条记忆。版本 Artifact 是只追加的，带内容哈希。
- **改类型**：修订与手动编辑都改不了类型（`patchouli/services/memory_generation.py` 的外部编辑没有类型参数）；版本记录的来源取值中 `SYSTEM_REWRITE` 存在，但没有写入方。
- **guide skill**：中英文版本都引导 agent 在工作中断时写下未完成工作的状态（`integrations/hivememory/`）。

  | CODE_SNIPPET（中期库 62） | 14 | 40 | 7 | 1 |
  | CODE_SNIPPET（冷库 5） | 3 | 1 | 1 | — |
  | URL_RESOURCE（中期库 7） | 1 | 6 | — | — |

## 5. 目标设计

### 5.1 类型集合与资源记忆

- 可以产生的类型：FACT、REFLECTION、USER_PROFILE 与新增的 `RESOURCE`（资源记忆），以及由下一份计划移出的 AGENT_PROFILE。
- `WORK_IN_PROGRESS`、`CODE_SNIPPET`、`URL_RESOURCE` 留在 `MemoryType` 中，只作为历史取值：版本记录不改写，其中的快照仍要能解码。生成提示词、MTP 过滤、alias 前缀、管理接口与前端的创建入口都不再给出这三个值，迁移之后中期库与冷库中也不再有它们。
- 资源记忆的含义（owner，2026-11-16）：对一个外部资源（网页、文件、代码、文档）的记忆，正文说明它是什么、为什么这样设计、在哪里，把读者引向源头；真相留在源头。资源记忆不叫导览（owner，2026-11-16）。
- 只存在于记忆中的代码（对话中写出、没有提交的脚本，控制台里执行过的查询）不是资源记忆；在内容类别重新划分之前落在 FACT，代码部分原样保住（类型体系 Idea 第 7 节开头的候选）。
- 新建的资源记忆 alias 前缀为 `res`；已有记忆的 alias 是对外的标识，迁移时不改。
- 固有价值权重：`resource_weight` 取 0.8（候选，理由见类型体系 Idea 第 7 节开头）；删除 `code_snippet_weight`、`url_resource_weight`、`work_in_progress_weight`。

### 5.2 生成提示词

- 被动、写入与合并提示词（中英文）的类型清单改为 FACT、REFLECTION、USER_PROFILE、RESOURCE；RESOURCE 的说明按 5.1 写，注明只存在于记忆中的代码归 FACT。
- 被动提取的拆分规则去掉“一项工作的当前状态”：结论、决定与尚未解决的问题本身照常成条，“做到哪了”不写成记忆。
- 模型仍可能给出已删除的类型名，沿用现有处理：未知类型落为 FACT。

### 5.3 去掉三个类型的其余入口

- **MTP**：`type:` 过滤删去 `code`、`code_snippet`、`url`、`url_resource`、`wip`、`work_in_progress`，新增 `resource` 与 `res`；删去的别名按未知别名处理（警告、不加过滤）。MTP 提示词中的类型与过滤说明同步。
- **管理接口与前端**：服务端类型清单、前端的类型列表、图标、筛选与创建表单改为新的类型集合。
- **guide skill**（中英文）：工作中断时写下得出的结论、决定与尚未解决的问题本身，不写“做到哪了”；类型说明同步。

### 5.4 关闭 RUN 的用户工具路径

- `sys_*` 系统工具的本地执行不变。
- 目标是记忆别名时，RUN 仍以 `ResolveRunTargetRequest` 经 actor API 以 `memory.run` 授权并解析别名（pending、重定向与已结束句柄的提示照旧），解析到的记忆一律以“不可运行”拒绝，不交付执行目标、不记录引用。六项 actor 操作与 MTP 动词的对应关系、`memory.run` 的访问登记都不变，可运行的轴落地时只需在这一处放开。
- `execute_user_tool` 删除（没有其他使用方）；`execute_sandboxed` 仍供 `sys_python_repl` 使用，保留。
- 拒绝的提示改写：说明 v0.8 暂不支持运行记忆，需要执行的代码请经 READ 取得后自行运行；`mtp.run.type_mismatch` 与 `MemoryTypeMismatchError` 若因此没有其他使用方，一并删除。

### 5.5 已有记忆的迁移

- **范围**：中期库与冷库中的原子；版本记录不改写，它们记的是当时的类型，版本 Artifact 也是只追加、带内容哈希的。
- **改类型的写入方**：在 `MemoryGenerationFamiliar` 中加一个只改 `index.memory_type` 的系统改写，Familiar 仍是唯一写入者。中期库中的原子经现有的提交路径写回：写版本记录（来源为 `SYSTEM_REWRITE`）、推进版本、随编译文本的变化重算向量。冷库中的原子读出后改写类型、覆盖写回冷库（旧文件随之删除），同样写一份版本记录。正文、alias、标签与访问策略都不变。
- **决定的来源**：owner 导出的决定文件（第 4 节），按 `memory_id` 对应，每条同时带 alias；文件中的 alias 与库中不一致时整体拒绝执行。
- **迁移脚本** `scripts/migrate_memory_types.py`：逐条改类型或删除（中期库走现有的管理删除入口，冷库从冷库删除）；默认只打印将要执行的动作，加 `--apply` 才写入。WIP 中有未决的条目时整体拒绝执行；记忆已被 owner 删除时报告为已移除；CODE_SNIPPET 与 URL_RESOURCE 未选时取默认去向。
- **执行时机**：旧取值留在枚举中，部署新代码之后旧原子照常可读，迁移不必赶在部署之前；停掉日常实例后执行，开发实例先演练一次。
- 迁移完成之后，脚本与改写入口没有其他使用方，在本计划收尾时删除；`SYSTEM_REWRITE` 回到没有写入方的状态。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| 记忆数据模型 | `MemoryType` 新增 `RESOURCE`，三个旧值只作为历史取值保留；schema 版本不变 |
| Patchouli 生成 | 提示词的类型清单与拆分规则；alias 前缀；迁移期间的系统改写入口 |
| 生命周期 | 三个权重键删除，新增 `resource_weight` |
| MTP 契约 | `type:` 过滤的别名；RUN 对记忆别名一律拒绝 |
| Workspace 能力层 | `resolve_run_target` 解析后一律拒绝，不再按类型判断；授权与操作对应关系不变 |
| 管理接口与前端 | 类型清单、图标、筛选与创建表单 |
| 外部插件 | guide skill 中英文版本 |
| 日常与开发实例的数据 | 日常实例删除 72 条（中期库 69、冷库 3）、改类型 57 条（中期库 55、冷库 2），每条改类型留下一条版本记录；已有的版本记录不变 |

## 7. 兼容与迁移

- 已有原子的迁移见 5.5；旧取值留在枚举中，部署与迁移没有先后约束。
- 版本记录中的旧类型保持原样：它们记的是当时的事实；以后读回历史的地方照常解码。
- 个人配置（`config.local.yaml`）中残留的三个权重键会被忽略，不会让启动失败；仓库中的 `configs/config.yaml` 同步删除并加上 `resource_weight`。
- 已有记忆的 alias 不变，外部 harness 与 agent 持有的 alias 照常可读。

### 8.3 迁移与回放验收

- 日常库与开发库：迁移后中期库与冷库中三类旧类型的只读计数为 0，版本记录的数量与内容不变；部署新代码后，中期库的全量读取（生命力维护的全量扫描 `list_all_for_maintenance`）不出现解码失败。
- 回放：以 `scripts/memory_replay.py extract` 在一批真实结算上运行新的被动提示词，产出只含新的类型集合，没有“当前进度”式的条目；资源记忆的正文指向源头，由 owner 抽查。
- 真实会话：经 MTP 或 MCP 对一条记忆发 RUN 得到“不可运行”的提示；日常使用中新产生的记忆不再出现 WIP，随日常使用观察，不作为归档条件。

## 9. 风险与待决问题

- **迁移的执行窗口**：日常实例需要停机迁移，开发实例先演练一次。
- **历史取值**：另一种做法是删除三个枚举值并改写版本记录中的快照，但版本记录是只追加的历史，改写会破坏内容哈希，也会抹掉“当时是什么类型”这一事实，不采用。
- **RUN 的关闭方式**（owner，2026-11-17 确认）：保留 RUN 的记忆分支与授权、一律拒绝。删除 `ResolveRunTargetRequest` 与 `memory.run` 的做法没有采用：它会改变六项 actor 操作与 MTP 动词的对应关系，已有访问登记中的 `memory.run` 也会在装载时被拒绝。
- **资源记忆与 FACT 的边界**：owner 手动归类时也不一定分得清资源与 FACT（知识侧），旧的生成内容本来就不是按新类型写的（owner，2026-11-17）。67 条旧 CODE_SNIPPET 中 52 条引用了仓库路径或网址，“是否指向源头”切不开这条边界。**已决定（owner，2026-11-17）：生成提示词按窄定义写**，资源记忆的主体是指出某样东西在哪里、是什么、为什么值得去看，陈述“怎样运作”的即使引用路径也归 FACT，与本计划 FACT 维持现状一致；宽定义按“真相在可以查看的源头”划分，需要与 FACT 的拆分一起做，没有采用。
- **资源记忆的名字与权重**：`RESOURCE`、前缀 `res` 与权重 0.8 都是候选，计划评审时可调整。
- **只存在于记忆中的代码落在 FACT**：内容类别重新划分之前的过渡，FACT 因此更大；回放中观察它的比例。
- 模型在合并时重选类型，可能把已迁移为资源记忆的原子改回 FACT 一类；按现有合并规则接受。

## 11. 实施记录

2026-11-17 在分支 `feat/v0.8.0-memory-type-convergence` 实施第 5 节，以 PR #225 合并。与计划不同，或计划没有写到的地方：

- **资源记忆的定义**：owner 选窄定义（第 9 节）。提示词中 RESOURCE 的说明是“对一个外部资源的记忆，正文说明它是什么、为什么值得去看、在哪里，不抄录源头”；FACT 的说明补上“陈述怎样运作的内容即使引用路径或网址也是 FACT，只存在于对话中的代码也归 FACT、原样保留”。
- **旧类型名**：`core/models/memory.py` 新增 `HISTORICAL_MEMORY_TYPES`。提取与写入时模型给出这三个名字，与未知类型名一样落为 FACT；合并沿用现有处理，类型无法采用时保留 M 的类型。
- **拆分规则**：被动提示词去掉“一项工作的当前状态”，另加一条“一项工作做到哪了（进度、下一步、待办）不写成记忆，其中的结论、决定与尚未解决的问题照常成条”；过程条目中 RUN 的说明从“运行记忆中的工具”改为“运行系统工具”。
- **RUN 的拒绝**：错误码 `mtp.argument.invalid`，文案键 `mtp.run.memory_not_runnable`。`mtp.run.type_mismatch` 的文案与 `MemoryTypeMismatchError` 没有了使用方，删除；错误码 `mtp.memory.type_mismatch` 仍由 CALL 目标不是 Profile 时使用。redirect 的 `mtp.run.alias_redirected` warning 只附在执行成功的响应上，随之删除，拒绝提示改为给出 canonical alias。`handle_run` 不再接收超时参数；workspace 的 `resolve_run_target` 不再记录引用，`runnable_only` 删除。

- **迁移脚本**：除 alias 外也核对类型，库中的类型既不是文件中的旧类型、也不是目标类型时整体拒绝（开发实例演练发现 `ref_d09_commit_split` 在开发库是 REFLECTION、在日常导出中是 WORK_IN_PROGRESS，加这项核对之前它被删掉了）。没有有效决定的条目一律拒绝：导出时 CODE_SNIPPET 与 URL_RESOURCE 的默认去向已经写进文件。Workspace 由带旧类型或在决定文件中的记忆推出，冷库的删除走 `LongTermMemoryStore.remove`。已改好的条目重跑时跳过。
