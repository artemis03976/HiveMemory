# HiveMemory 文档治理与维护规范

> 本文档定义 HiveMemory 文档库的分类、职责、状态、目录结构与维护流程。
> 它描述的是文档治理规则，而不是某个子系统的设计。

## 1. 目标

HiveMemory 的文档库应当帮助读者可靠地回答以下问题：

1. 项目当前是什么，已经具备哪些能力？
2. 系统目前如何划分，各子系统分别负责什么？
3. 某个模块当前采用什么设计，真实代码入口在哪里？
4. 子系统之间通过什么契约交互，哪些行为属于稳定约束？
5. 哪些内容正在计划、尚处于设想，或者已经成为历史？
6. 一项设计为什么形成，后续应当如何安全地修改它？

文档治理的最终目标不是保存尽可能多的设计文字，而是维护一套能够反映当前后端真实设计、支持项目理解与演进的统一知识结构。

## 2. 核心原则

### 2.1 当前设计只有一个权威入口

`docs/` 主干中的当前设计文档是项目设计的规范性说明。相同概念只能存在一个主要维护位置，其他文档应通过链接引用，不得各自维护不同版本的完整描述。

例如：

- Retrieval 的当前职责和数据流只在 Patchouli 对应模块文档中完整描述；
- MTP 的稳定协议只在跨子系统契约文档中定义；
- Alice 文档可以解释如何使用 MTP，但不复制一份完整协议；
- 代码目录不放 README，代码注释也不指向文档；模块设计只在 `docs/` 中维护，由文档指向代码（第 11 节）。

### 2.2 当前设计与运行事实必须收敛

当前设计文档是理解和演进系统的权威入口；代码、测试、配置和运行结果是实现行为的可执行证据。

当两者不一致时，应将其视为需要修复的文档或实现缺陷，而不是接受“两套真相”长期并存：

- 如果代码实现正确，应在同一开发周期内更新当前设计文档；
- 如果文档描述的是仍然有效的约束，应修改代码使其重新满足设计；
- 如果尚不能立即判断，应明确记录为已知偏差，并创建可追踪的修复项。

计划、设想和历史文档不得被用来推断当前系统已经具备某项能力。

“与实现一致”不等于“把代码目录改写成自然语言”。代码能够证明系统现在做了什么，却通常不能独立解释为什么要这样划分、它试图解决什么矛盾、曾经放弃了哪些路径，以及哪些约束一旦被破坏就会让设计重新失衡。当前设计文档必须同时保留这些仍然有效的设计语义。

因此，每次根据代码更新文档时，应区分两类内容：

- **可执行事实**：当前组件、数据流、状态、接口和错误行为，由代码与测试核验；
- **持续有效的设计理由**：问题背景、核心矛盾、所有权判断、关键取舍和安全边界，由文档负责完整表达。

如果实现改变但原设计理由仍然成立，应说明新的实现如何继续满足它；如果理由已经失效，则需要明确修正文档，必要时形成 ADR，而不是只替换类名和流程图。

### 2.3 当前事实、未来意图与历史记录必须分离

文档必须明确区分：

- **当前事实**：已经落地并正在生效的设计、契约和行为；
- **调研**：对外部系统、论文、协议或技术方案的证据、比较与适配分析；
- **计划**：目标较明确，但尚未完整进入当前事实的实现方案；
- **设想**：仍在探索的问题、假设和可能路径；
- **待办**：范围较小的缺陷、技术债或修复事项；
- **历史**：已经完成、被替代或不再生效的设计；
- **决策**：仍有长期解释价值的重要选择及其理由。

一篇文档不能同时作为当前设计和未来计划。当前文档可以记录“已知缺口”，但未来实现方案必须放入计划文档并通过链接关联。

### 2.4 目录按责任归属组织

当前设计优先按照稳定的系统责任边界组织，而不是完全复制代码目录。

- Patchouli、Alice、Gateway 是主要子系统；
- Workspace 是与它们同层、没有独立生命周期宿主的包，负责访问边界、能力层、任务进程与库外资源；
- System 负责顶层装配、应用服务和全局运行时能力；
- Contracts 负责跨子系统的稳定交互边界；
- Architecture 负责整个系统的结构、边界和重要决策。

模块文档应归属于对其语义、生命周期和变更负责的系统，而不是简单归属于调用方最多或当前文件所在的位置。

### 2.5 文档首先服务于导航和判断

读者应当能够在较短路径内找到答案，并判断答案是否仍然有效。文档应优先提供：

- 清晰的责任和非责任边界；
- 真实的数据流和控制流；
- 稳定契约、关键不变量与失败语义；
- 对应代码和测试入口；
- 已知限制与相关文档链接。

文档不应为了完整而逐文件复述代码，也不应使用大量尚未实现的细节制造虚假的完备感。

### 2.6 历史可追溯，但不能干扰当前阅读

历史设计应保留在 `archive/`（第 10 节），重要决策应保留在 ADR 中。历史内容的价值是解释演进过程，而不是继续指导当前实现。

### 2.7 开发分支设计稿晋升门禁

尚未明确收尾的开发分支不构成项目当前事实。分支中的完整目标模型、候选职责、接口形状、状态机、生命周期、失败语义、命名和跨系统边界，只能写入以下工作文档：

- `docs/ideas/`：仍在探索、尚未形成实施承诺的内容；
- `docs/plans/`：已经绑定版本或里程碑、正在实施和验收的设计；
- `docs/todo/`：小范围缺陷、技术债和后续事项。

`ROADMAP.md` 是规划层入口，不受下述事实性文档限制，写法见第 4.4 节。

在分支开发明确进入最终收尾之前，严禁把上述设计稿内容写入或提前同步到事实性文档，包括根 README、`PROJECT.md`、Architecture、System、各子系统、Contracts、Governance、Help、Frontend 与 Applications。即使某部分代码已经在开发分支中出现，也不得使用“候选设计”“计划中”“尚未实现”“未来将会”等措辞把它预告到这些事实文档；相关完整说明仍应留在对应 Idea、Plan 或 Todo 中，规划摘要则可以进入 Roadmap。Archive 也不能作为活动设计的临时存放区。

设计稿只有在同时满足以下条件后才能晋升为当前事实：

1. 分支约定范围内的实现、测试和必要迁移已经完成；
2. 计划验收项已经逐项核对，代码审查未留下会改变公共设计的未决问题；
3. 设计模型、命名、所有权和失败语义不再处于反复修订状态；
4. 开发工作已经明确进入最终收尾，准备合并、发布或形成等价的稳定基线；
5. 收尾者根据最终代码和测试重新编写事实文档，只晋升实际落地的内容，并同步归档已完成 Plan。

因此，开发期间事实文档可以暂时继续描述上一个已完成基线；Idea、Plan、Todo 是设计细节依据，Roadmap 是开发内容与顺序的规划入口。该暂时差异必须在分支合并或发布前的最终收尾中消除，不能把设计稿提前扩散到事实层来追求表面同步，也不能在工作已经收尾后继续让事实文档落后于实现。

### 2.8 收尾时的文档更新

改变系统行为的开发分支，收尾时检查是否：

- 改变子系统职责或所有权；
- 改变数据流、状态机或生命周期；
- 改变公开路由、事件、协议、配置或错误语义；
- 新增或移除主要能力；
- 改变可观测性和运维方式；
- 使某份当前文档、代码注释或示例失效。

任一项为是，就在同一个 PR 或等价变更的最终收尾中更新对应当前文档；实现、测试、验收和代码审查完成之前不提前执行。收尾时还应：

1. 将 Plan 中已经落地的设计合并进现有当前文档，而不是另建一份并行的“新设计”；
2. 将已完成 Plan 移入 `archive/plans/`（第 10 节）；
3. 将仍有长期价值的决策提炼为 ADR；
4. 更新 `PROJECT.md`、子系统 README 和 `ROADMAP.md` 中受影响的链接或状态；
5. 检查相关帮助文档与配置示例；
6. 确认验收测试已并入归属层的测试文件，没有遗留以计划命名的测试文件，也没有只守护旧契约的测试；
7. 确认实施期间写下的代码注释与 docstring 不引用本计划或其他文档（第 11.2 节）。

文档更新不是 PR 完成后的可选清理工作，而是设计变更完成定义的一部分。治理型工作同样如此，收尾时另外回写治理主题的成熟度。

## 3. 文档层级与职责

| 文档层级 | 回答的问题 | 主要载体 |
|:---|:---|:---|
| Vision | 项目为什么存在、相信什么、如何取舍 | `VISION.md` |
| Project Overview | 项目当前提供什么、如何理解整体系统 | `PROJECT.md` |
| Architecture | 当前系统如何划分、核心边界和数据关系是什么 | `architecture/` |
| System Design | 顶层系统、共享运行时机制、各子系统与前端当前如何工作 | `system/`、`components/`、`workspace/`、`patchouli/`、`alice/`、`gateway/`、`frontend/` |
| Protocol & Contract | 子系统如何稳定交互 | `contracts/` |
| Product & Evidence | 为谁解决什么问题、怎样验证价值 | `applications/` 及评估文档 |
| Help | 如何安装、配置、使用和排障 | `help/` |
| Roadmap | 接下来验证和交付什么、顺序如何 | `ROADMAP.md` |
| Governance | 跨版本必须达到哪些质量门槛、当前成熟度和工作包是什么 | `governance/` |
| Baseline | 某项治理判断建立在哪个时间点的调查证据上 | `governance/baselines/` |
| Research | 调研要回答什么，外部 Memory、Agent 系统及相关技术如何设计、哪些经验可供借鉴 | `research/` |
| Plan | 某项功能或重构准备如何落地 | `plans/` |
| Idea | 哪些方向值得探索、尚有哪些开放问题 | `ideas/` |
| Todo | 哪些小范围缺陷或技术债需要处理 | `todo/` |
| Decision | 为什么形成某项长期有效的重要设计选择 | `architecture/decisions/` |
| Archive | 哪些设计已经完成、失效或被替代 | `archive/` |

## 4. 核心入口文档

### 4.1 根 README

仓库根目录的 `README.md` 面向第一次接触项目的读者，只维护：

- 当前项目定位与已经可用的主要能力；
- 最短安装和运行路径；
- 最小使用示例；
- 指向 `PROJECT.md`、安装指南和路线图的入口。

README 不承担完整架构说明，不描述尚未实现的远期能力。

### 4.2 PROJECT.md

`PROJECT.md` 是 `docs/` 的全局索引和当前项目总览，主要包含：

1. 当前项目定位；
2. 已经成立的工程事实和能力边界；
3. 顶层架构图与关键数据流；
4. System、Workspace、Patchouli、Alice、Gateway 的职责摘要；
5. 当前开发阶段；
6. 面向不同读者的推荐阅读路径；
7. 当前设计、契约、帮助、计划和历史文档索引。

`PROJECT.md` 不再承载所有模块的详细设计，也不混合大段历史方案和未来构想。

### 4.3 VISION.md

`VISION.md` 维护长期定位、设计哲学、关键假设、决策门槛和明确非目标。

愿景可以指导接口和架构选择，但必须明确区分：

- 已经成立的工程事实；
- 近期需要验证的假设；
- 尚未实现的长期愿景。

愿景中的能力不得直接作为当前功能对外宣传。

### 4.4 ROADMAP.md

`ROADMAP.md` 维护版本或阶段的顺序、状态、目标、关键设计摘要、依赖关系和验收出口。它必须提供足够信息说明各阶段准备开发什么、解决什么问题以及为何采用当前顺序，不能为了避免未来内容而退化成只有名称和链接的目录。

每个路线图项目应链接：

- 对应计划文档；
- 受影响的当前设计文档；
- 完成后的归档计划、发布记录或 PR。

Roadmap 中的规划内容必须显式标记 `Planned`、`Candidate`、`Unscheduled` 等状态，并链接对应 Idea、Plan 或 Todo。它可以保留理解阶段关系所必需的模型边界和设计摘要；完整字段、逐组件落点、迁移步骤和测试矩阵仍由对应 Plan 维护，不应在路线图中形成第二份详细实施方案，也不得成为详细模型的唯一真相源。

### 4.5 子系统 README

`system/`、`components/`、`workspace/`、`patchouli/`、`alice/` 和 `gateway/` 下的 `README.md` 是各自的局部索引，负责说明：

- 子系统职责与非职责；
- 对外提供的主要能力；
- 上下游依赖；
- 模块文档列表；
- 跨子系统契约入口；
- 对应代码目录。

README 不重复各模块的完整实现设计。

## 5. 目录结构

`docs/` 的一级目录按第 3 节的文档层级划分，固定入口文档见第 4 节。System、Components、Workspace、Patchouli、Alice、Gateway 与 Frontend 的目录各以 README 作为局部索引，当前文档清单以这些 README 与 `PROJECT.md` 为准；归档区按类型分为 `archive/plans/`、`archive/todo/`、`archive/ideas/` 与旧文档的 `archive/legacy-*`。

目录可以随真实系统边界调整，但不得通过新增含义模糊的目录绕过现有分类。

## 6. 文档状态与元数据

### 6.1 状态定义

| 状态 | 含义 |
|:---|:---|
| `draft` | 正在编写，尚未成为正式依据 |
| `current` | 当前生效的规范性设计或帮助文档 |
| `governance` | 跨版本持续维护的工程质量目标、成熟度与工作包 |
| `baseline` | 已冻结的 point-in-time 调研证据，不持续追随实现更新 |
| `planned` | 已形成计划，但尚未开始实施 |
| `active` | 对应工作正在实施 |
| `idea` | 开放设想，未形成项目承诺 |
| `todo` | 已确认的小范围缺陷或技术债 |
| `accepted` | 已接受且仍有效的架构决策 |
| `completed` | 计划已经完成，等待或正在归档 |
| `superseded` | 已被另一项设计或决策替代 |
| `deprecated` | 决策已失效且没有替代，仅保留供追溯（用于 ADR） |
| `archived` | 仅供历史追溯，不描述当前系统 |

### 6.2 推荐元数据

新建或完成整理的文档应在文件开头使用 YAML Front Matter。当前设计文档的基本格式为：

```yaml
---
title: Retrieval
status: current
owner: patchouli
scope: retrieval
code_paths:
  - src/hivememory/engines/retrieval/
  - src/hivememory/patchouli/services/retrieval.py
related_contracts:
  - docs/contracts/subsystem-contracts.md
last_reviewed: YYYY-MM-DD
---
```

字段说明：

- `title`：稳定、可读的文档名称；
- `status`：文档当前状态；
- `owner`：负责维护其语义的系统或模块；
- `scope`：文档覆盖范围；
- `code_paths`：用于验证文档的主要代码入口，不要求枚举全部文件；
- `related_contracts`：相关稳定契约；
- `last_reviewed`：最近一次根据代码核对内容的日期。

Idea 文档还应包含 `horizon`，取值与含义见第 8.4 节；`horizon: current` 的 Idea 同时用 `serves_version` 写明服务的版本。

Governance、Baseline、Research 与 ADR 的状态和元数据见对应目录的 README（第 8.1、8.2、9 节）。

计划文档还应包含目标版本或阶段：

```yaml
---
title: Retrieval Index Refactor
status: planned
owner: patchouli
target: vX.Y.Z
updates:
  - docs/patchouli/retrieval.md
---
```

归档文档至少应包含：

```yaml
---
title: Legacy Retrieval Refactor Plan
status: archived
archived_at: YYYY-MM-DD
implemented_by: PR #000
superseded_by: docs/patchouli/retrieval.md
---
```

## 7. 当前设计文档的内容规范

一个模块的当前设计文档通常应包含以下内容：

1. **问题背景与设计动机**：为什么需要这个模块，它面对的核心矛盾是什么；
2. **定位与范围**：模块用什么方式解决问题；
3. **职责与非职责**：它负责什么，明确不负责什么；
4. **系统边界**：依赖谁，被谁调用，拥有哪部分状态，以及为什么这样分配所有权；
5. **核心组件**：稳定组件及其关系，不逐文件抄录代码；
6. **数据流与控制流**：关键请求、事件或任务如何流动；
7. **数据与状态**：重要模型、状态机、生命周期和持久化边界；
8. **公开契约**：路由、事件、输入输出及相关契约链接；
9. **设计取舍与细节处理**：重要 fallback、补偿、原子性、兼容或性能策略为什么存在；
10. **不变量与矛盾检查**：修改实现时必须继续满足的约束，以及如何识别所有权或流程开始冲突；
11. **错误与降级**：失败如何表达，哪些情况允许回退；
12. **配置与可观测性**：关键配置、日志、事件和指标；
13. **代码与测试入口**：用于验证描述的主要位置；
14. **已知限制**：当前确实存在但尚未解决的缺口；
15. **相关文档**：上游、下游、契约、计划和 ADR。

根据模块复杂度可以合并章节，但不得省略关键边界和实现验证入口。

### 7.1 当前文档不应包含的内容

- 已经失效但未明确标记的旧流程；
- 尚未实现却使用现在时描述的能力；
- 完整复制自另一篇文档的协议或数据模型；
- 只有类名、文件名和调用顺序，却没有问题背景、设计理由或取舍说明的代码清单；
- 仅供一次重构使用的逐步实施清单；
- 与当前行为无关的大段探索性讨论；
- 容易快速失效的逐文件目录快照，除非它确实帮助解释稳定边界。

## 8. 工作文档与低频文档类型

### 8.1 Governance 与 Baselines

跨版本的工程质量主题（`governance`）与冻结的调查快照（`baseline`），创建与维护规则见 [Governance](governance/README.md)。治理文档不描述某个版本的实施方案，不替代当前设计或公共契约，列出工作包不构成路线图承诺；基线冻结，不随实现改写。

### 8.2 Research

外部系统、论文与技术方案的调研需求和报告，编写规则见 [Research](research/README.md)。调研只提供外部证据与适配分析，不能证明 HiveMemory 已具备对应能力，也不能借此绕过第 2.7 节的晋升门禁。

### 8.3 Plans

Plan 用于描述一个可独立验收的功能、重构或迁移，至少包括：

- 背景和问题；
- 目标与非目标；
- 当前状态和缺口；
- 目标设计；
- 受影响的系统、契约和数据；
- 兼容与迁移策略；
- 测试和验收标准；
- 风险与待决问题；
- 完成时必须更新的当前文档。

“测试和验收标准”写明需要守住的不变量、各自的归属层与验证命令，不逐条预列测试函数、参数化矩阵或“某符号不再存在”式检查；实施时验收测试写入归属层的现有测试文件，不形成以计划命名的测试集合。测试归属、去重与随契约演进的规则由[测试设计规范](governance/testing/test-design-standards.md)第 4 节维护。

Plan 是实施过程的工作依据，但在功能落地后不能继续承担当前设计说明。

进入 `plans/` 还必须满足：

- 绑定明确版本或里程碑，不使用 `target: unscheduled`；
- 能作为一个独立交付切片完成和验收；
- 依赖与非目标已经基本明确；
- 包含迁移、测试、风险和完成后当前文档更新清单；
- 文档状态只能是 `planned` 或 `active`；
- 工作完成后立即合并当前事实并进入 `archive/plans/`。

计划只在能够立即执行时建立：阻塞问题已经决定、依赖已经成为事实（owner，2026-10-30）。不能立即实施的方向留在 Idea，计划之间不预设先后，一个版本由多份计划依次完成。不满足进入条件的工作另有去向：未排期的治理主题进入 Governance，尚需验证价值、样本或所有权的候选进入 Ideas，范围较小的缺陷和技术债进入 Todo。

计划之间的关系必须满足以下三条约束。它们用于防止多份计划互相引用对方仍在变化的设计，使一处设计变更不得不联动修改一组计划：

1. **同一目标方向只有一份生效计划，不设总分结构**：计划不使用 `parent_plan`，`plans/` 中不建立协调、冻结清单或宪章类文档；新工作的目标与现有计划重叠时，先改写或退役原计划，不另开并行计划。
2. **设计依据只来自稳定来源**：计划正文只能以当前事实文档、代码、ADR、已归档计划、已冻结的 Research 报告以及作为背景的 Idea 为依据；Research 只提供外部证据与当时的适配分析，不能证明 HiveMemory 已具备对应能力，也不能替代本项目的设计决定。不得以另一份活动计划的章节作为设计依据，也不得把自身事项交由另一份活动计划收口。
3. **计划之间只允许顺序依赖**：`depends_on` 以整份计划为粒度，只表达先后；后继计划在前驱完成收尾、相关设计晋升为事实文档之后，依据事实文档编写或修订。

`plans/README.md` 是当前开发版本的计划导航：列出仍然活动的计划与尚未建立计划的方向的状态与链接，不记录设计决定；计划归档后从这里删除，只登记在归档索引（第 10 节）。版本规划摘要由 `ROADMAP.md` 维护，设计讨论留在 Idea。

### 8.4 Ideas

Idea 用于开放探索，可以包含：

- 观察到的问题或机会；
- 假设与潜在价值；
- 若干可能路径；
- 主要未知项和验证方式；
- 升级为 Plan 所需满足的条件。

Idea 不代表路线图承诺，不使用确定语气宣称功能一定会实现。

Idea 以 frontmatter 的 `horizon` 字段分为三类，`ideas/README.md` 按此分区索引：

| `horizon` | 含义 | 额外要求 |
|:---|:---|:---|
| `current` | 当前版本方向的设计讨论，直接为下一份 Plan 供料 | 以 `serves_version` 写明服务的版本，并在 `plans/README.md` 对应版本下有入口；可以记录 owner 已作出的决定，须注明日期，未决定的问题只列选项及其影响；版本收尾时要么已形成 Plan，要么改为 `candidate` 或 `long-term` |
| `candidate` | 问题具体、尚未排期的功能或技术方向 | 进入某个版本的方向后改为 `current` |
| `long-term` | 长期方向、研究假设或概念性指导 | 不绑定版本 |

类别变化只修改该字段与索引，不移动文件。已经实现、被替代或不再跟踪的 Idea 整体移入 `archive/ideas/`，按第 10 节的归档要求处理。

尚未开始实施的计划，如果方向仍然成立但前提已经改变，退回 Idea：移入 `ideas/`，删除计划安排内容（阶段划分、交付与验收、跨计划依赖、文档更新清单），保留设计，并把原计划中的“决定”“冻结”改写为候选设计或开放问题；入链随之更新。作废且不再讨论的计划按第 10 节直接删除。

### 8.5 Todo

Todo 只适用于范围较小、排期灵活的缺陷或技术债。大型功能和跨系统重构必须形成 Plan。

如果项目 Issue 系统中已经存在对应事项，文档应链接 Issue，而不是重复维护两份详细状态。Todo 至少应包含影响范围、现象或证据、完成条件和追踪链接。

## 9. 架构决策记录（ADR）

ADR 保存已经做出、具有长期解释价值的架构决策，编写与状态规则见 [ADR 索引](architecture/decisions/README.md)。ADR 不得以活动计划为依据；当前设计文档可以链接 ADR 解释“为什么”，但仍应独立说明“现在是什么”。

## 10. Archive 规则

以下内容应进入 `archive/`：

- 已完成且内容已合并进当前设计的实施计划；
- 已被替代的旧设计；
- 仅用于某个历史迁移阶段的调查和清单；
- 已失效但仍具有追溯价值的架构说明；
- 文档重构前无法直接删除的历史材料。

归档时必须：

1. 将状态改为 `archived` 或 `superseded`；
2. 指出归档日期；
3. 链接替代它的当前文档；
4. 尽可能记录实现版本、PR 或决策；
5. 更新所有仍将其作为当前依据的入口链接。

归档文档原则上冻结。后续只修复严重错误、断链或补充追溯信息，不继续演进其设计内容。

索引只做导航，同一段历史只在被归档文档自身维护：

- 归档索引（`archive/plans/`、`archive/todo/` 与 `archive/ideas/` 的 README）每条登记一行：标题链接、归档日期、实现所在的 PR（尚未合并时写提交）与替代它的当前文档，当前文档至多两个链接；按版本或时间分节。实施过程、验收结果与决定只写在被归档文档的状态行与实施记录中，索引不复述；
- 工作区索引（`plans/`、`todo/` 与 `ideas/` 的 README）只列仍然活动的事项。条目归档后从工作区索引删除，只在对应的归档索引登记，工作区索引至多保留一行指向归档索引；
- 没有归档文件的事项（升级为计划、并入计划或直接删除）在对应的归档索引中各登记一行，写明去向与删除前最后版本所在的 commit。

未完成实施即作废的计划不进入 `archive/`，直接删除，历史由版本控制保留。删除时必须：

1. 确认其中已落地且保留的代码由当前事实文档描述，或在承接的 Idea/Plan 中登记为待重新调查；
2. 将所有入链改为指向替代文档；没有替代时改为纯文本，并注明删除前最后版本所在的 commit；
3. 为其他文档中交由该计划收口的事项重新指定归属，或明确标记为未排期。

## 11. 代码目录与代码注释规则

### 11.1 代码目录不放 README

`src/`、`tests/`、`scripts/` 与 `frontend/src/` 下不放 README 或其他说明文档。源码树中的 README 会随类名、目录结构和控制面迁移迅速失真。

模块用途写在包或模块的 docstring 中，并遵守第 11.2 节；跨模块职责、公共契约与已知限制只在 `docs/` 的当前文档中维护，由文档以 `code_paths` 或代码链接指向实现。仓库根目录的 `README.md` 是项目入口（第 4.1 节），不属于代码目录。本规则与第 11.2 节由同一个架构测试守护。

### 11.2 代码注释与说明文本

引用只能从文档指向代码：事实文档、Plan 与 Idea 以 `code_paths` 或代码链接指向实现，代码不反向指向任何文档。计划归档、Idea 删除或事实文档改写之后，指向它们的注释会失去意义，或与实现悄悄不一致；而注释与代码同处一次修改，只要它自己说清楚，就不会失效。

适用范围是 Python 与 TypeScript 源码中的注释、docstring、裸字符串说明与字段 `description`，包括测试代码。

- 直接写出行为、不变量、理由与边界。读者不打开任何文档也能理解；所有工作文档归档或删除、事实文档改写之后，内容仍然成立。
- 不引用文档：不写 `docs/` 路径、`.md` 文件名、文档标题或文档中的章节号、编号条目（如“第 4.4 节”“§3.1”“不变量 6”“证据 3”），事实文档同样不引用。
- 不写工作编号：计划与批次代号（如 A1、A2-P、W1-E、“返工”“第二批”“Phase 2”）、决定与问题编号（如 Q-15、D-4、I-10、AC-1）。原注释只靠编号表达理由时，把理由本身写出来。
- 不写依赖计划进度的措辞（如“暂时保留到下一批”“中间态”）：现状写成事实与理由；已知限制直接写限制本身，后续工作在 Todo 或 Idea 中跟踪，由文档指向这段代码。
- 迁移来源、版本历史（“从某版本起”“v0.6.2 收敛”）交给版本控制记录，不写进注释。
- 可以保留：领域术语（如两阶段认证的“第 2 阶段”、四阶段骨架、Gateway 的检索计划）、运行时事实中的版本号（如 codec 版本、schema 版本），以及指向其他代码的路径。

`tests/unit/architecture/test_self_contained_comments.py` 扫描可以机读的引用形式；新的计划命名多为自然语言，正则不能覆盖全部写法，其余由评审把关。

## 12. 命名与链接规范

### 12.1 文件命名

- 固定入口使用大写名称：`PROJECT.md`、`VISION.md`、`ROADMAP.md`、`DOCUMENTATION.md`、`README.md`；
- 当前模块文档使用稳定的英文小写 kebab-case，例如 `memory-compiler.md`；
- 当前文档名不包含版本号、日期、`new`、`final`、`latest` 等易失效标记；
- 计划可以使用目标版本或日期，例如 `v0.6.1-local-work-queue-runtime.md`；
- ADR 使用递增编号，例如 `0001-async-system-bus.md`。

### 12.2 链接

- 仓库内 Markdown 文档使用相对链接；
- 当前设计优先链接其他当前文档或 ADR；
- 指向 archive 的链接必须明确说明其历史性质；
- 引用代码时优先链接稳定目录、类或入口文件，避免依赖容易漂移的行号；
- 移动或重命名文档时必须同步修复所有入口和反向引用；
- 不复制内容来规避链接，应修复文档结构或补充局部摘要。

---

本规范以 `VISION.md` 中“当前事实、近期假设与长期愿景相分离”的原则为上位依据。若文档结构与真实系统责任边界发生冲突，应先澄清并记录新的架构决策，再更新本规范，不能仅为维持目录形式而扭曲系统设计。
