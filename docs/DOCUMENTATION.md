# HiveMemory 文档治理与维护规范

> 本文档定义文档库的分类、职责、状态、目录结构与维护流程，是文档治理规则，而不是某个子系统的设计。

## 1. 目标

文档库要让读者可靠地回答：项目当前是什么、具备哪些能力；系统如何划分、各子系统负责什么；某个模块采用什么设计、代码入口在哪里；子系统之间通过什么契约交互、哪些行为是稳定约束；哪些内容在计划、在设想或已成为历史；一项设计为什么形成、怎样安全地修改它。

目标不是保存尽可能多的设计文字，而是维护一套反映当前真实设计、支持理解与演进的统一知识结构。

## 2. 核心原则

### 2.1 当前设计只有一个权威入口

`docs/` 主干中的当前设计文档是项目设计的规范性说明。一个机制只由一份事实文档从头讲完，这份文档就是它的权威入口（第 2.4 节）。其他文档用到这个机制时，用一两句话说明它在自己这里起什么作用，不复述它的细节。契约文档只定义跨子系统的接口形状（路由、事件、协议），不重复机制：例如 MTP 协议只在契约文档中定义，Alice 的文档只讲 Alice 怎样使用它。代码目录不放 README，代码注释不指向文档（第 11 节）。

### 2.2 当前设计与运行事实必须收敛

代码、测试、配置和运行结果是实现行为的可执行证据。文档与实现不一致是需要修复的缺陷，不接受两套真相长期并存：代码正确，就在同一开发周期内更新文档；文档描述的约束仍然有效，就修改代码；暂时判断不了，就记为已知偏差并建立可追踪的修复项。计划、设想和历史文档不能用来推断系统已经具备某项能力。

与实现一致不等于把代码改写成自然语言。文档同时保留两类内容：

- **可执行事实**：组件、数据流、状态、接口与错误行为，由代码与测试核验；
- **持续有效的设计理由**：问题背景、核心矛盾、所有权判断、关键取舍与安全边界，由文档完整表达。

实现改变而理由仍然成立时，说明新实现怎样继续满足它；理由失效时明确修正文档，必要时形成 ADR，而不是只替换类名与流程图。

### 2.3 当前事实、未来意图与历史记录必须分离

文档区分当前事实、调研、计划、设想、待办、历史与决策，各自的载体见第 3 节。一篇文档不能同时作为当前设计和未来计划：当前文档可以记录已知缺口，未来的实现方案放进计划并通过链接关联。

### 2.4 事实文档按机制写，目录按主要归属存放

事实文档描述机制，而不是模块。机制是一件事从触发到结果的整个过程，例如短期记忆、一轮对话的执行、记忆的检索，它往往跨过好几个子系统。读者想知道的是这件事怎样发生、为什么这样做，而不是某个类有哪些方法。

按模块写的问题在于：一个机制的改动会穿过好几份文档，每一份都从自己的角度复述一段。读者要拼起来才看得懂，维护者也很容易漏改其中一份。按机制写，这个改动只落在一份文档里。

目录仍按系统划分，用来存放机制文档，每份放在机制主要发生的位置：

- 主要发生在一个子系统内的机制，放在它的目录里：Patchouli、Alice 与 Gateway 是主要子系统；Workspace 与它们同层，负责访问边界、能力层、任务进程与库外资源；System 负责顶层装配、应用服务与全局运行时能力。
- 跨多个子系统的机制，放在 `architecture/`。它同时收录整体结构、边界与重要决策。
- 跨子系统的接口形状，放在 Contracts。

现有按模块写的文档，在它描述的机制下次改动、或者需要时，改写为机制文档；改写时，删除被它取代的段落。改写之前，这些文档继续有效，与实现不符时照常修正。

### 2.5 文档首先让新读者看懂

任何一个第一次接触项目的人，打开任何一份事实文档，都应当立即明白它在描述什么。

- **介绍，而不是概括代码**：文档用清楚的语言介绍机制。先说它是什么、为什么需要，再用一个例子走一遍；概念先定义，再使用。
- **能判断是否仍然有效**：文档写出代码与测试入口和已知限制，让读者能核对、能判断它还对不对。
- **不制造完备感**：不为了完整而逐文件复述代码，也不用尚未实现的细节充数。

写法见第 7 节。

### 2.6 历史可追溯，但不能干扰当前阅读

历史由版本控制保留：完成的计划与 Todo 在收尾时删除，`archive/` 只保存此前归档的材料与其他类型的历史文档（第 10 节）；重要决策保留在 ADR 中。历史内容的价值是解释演进过程，而不是继续指导当前实现。

### 2.7 开发分支设计稿晋升门禁

尚未明确收尾的开发分支不构成当前事实。分支中的目标模型、候选职责、接口形状、状态机、生命周期、失败语义、命名与跨系统边界，只能写在 `docs/ideas/`（仍在探索）、`docs/plans/`（已绑定版本、正在实施和验收）或 `docs/todo/`（小范围缺陷、技术债与后续事项）中；`ROADMAP.md` 是规划层入口，写法见第 4.4 节。

进入最终收尾之前，这些内容不得写入或提前同步到事实性文档（根 README、`PROJECT.md`、Architecture、System、各子系统、Contracts、Governance、Help、Frontend 与 Applications）。即使代码已经出现在开发分支中，也不得用“候选设计”“计划中”“尚未实现”“未来将会”等措辞预告；Archive 也不能作为活动设计的临时存放区。设计稿同时满足以下条件后才能晋升为当前事实：

1. 分支约定范围内的实现、测试和必要迁移已经完成；
2. 计划验收项已逐项核对，代码审查未留下会改变公共设计的未决问题；
3. 设计模型、命名、所有权和失败语义不再反复修订；
4. 开发工作明确进入最终收尾，准备合并、发布或形成等价的稳定基线；
5. 收尾者根据最终代码和测试重新编写事实文档，只晋升实际落地的内容，并删除已完成的计划（第 10 节）。

开发期间事实文档可以继续描述上一个已完成的基线；这一差异必须在合并或发布前的收尾中消除，既不能提前把设计稿扩散到事实层，也不能在收尾之后让事实文档落后于实现。

### 2.8 收尾时的文档更新

改变系统行为的开发分支，收尾时检查是否改变了子系统职责或所有权，数据流、状态机或生命周期，公开路由、事件、协议、配置或错误语义，主要能力，可观测性与运维方式，或使某份当前文档、代码注释与示例失效。任一项为是，就在同一个 PR 的最终收尾中更新对应当前文档（实现、测试、验收和代码审查完成之前不提前执行），并且：

1. 把计划中已经落地的设计合并进它所属的机制文档，不另建一份并行的“新设计”。这个机制还没有机制文档时，新写一份，并删除被它取代的模块文档段落。收尾只更新受影响的机制文档与代码中的 docstring；其他文档对这个机制只有一两句说明，不为了一致而逐份同步细节；
2. 把仍有长期价值的决策提炼为 ADR；
3. 更新 `PROJECT.md`、子系统 README 与 `ROADMAP.md` 中受影响的链接或状态，检查相关帮助文档与配置示例；
4. 确认验收测试已并入归属层的测试文件，没有以计划命名的测试文件，也没有只守护旧契约的测试；
5. 确认实施期间写下的代码注释与 docstring 不引用计划或其他文档（第 11.2 节）；
6. 最后删除已完成的计划：实施记录中只解释当时怎样做到的部分写进这个收尾提交的说明，并在归档索引登记一行（第 10 节）。

文档更新是设计变更完成定义的一部分，不是 PR 之后的可选清理；治理型工作收尾时另外回写治理主题的成熟度。

## 3. 文档层级与职责

| Project Overview | 项目当前提供什么、如何理解整体系统 | `PROJECT.md` |
| Architecture | 当前系统如何划分、核心边界和数据关系是什么，跨子系统的机制怎样运作 | `architecture/` |
| System Design | 顶层系统、共享运行时机制、各子系统与前端当前如何工作 | `system/`、`components/`、`workspace/`、`patchouli/`、`alice/`、`gateway/`、`frontend/` |
| Protocol & Contract | 子系统如何稳定交互 | `contracts/` |
| Product & Evidence | 为谁解决什么问题、怎样验证价值 | `applications/` 及评估文档 |

| Roadmap | 接下来验证和交付什么、顺序如何 | `ROADMAP.md` |
| Governance | 跨版本必须达到哪些质量门槛、当前成熟度和工作包是什么 | `governance/` |

| Decision | 为什么形成某项长期有效的重要设计选择 | `architecture/decisions/` |
| Archive | 哪些设计与 Idea 已经失效或被替代；此前归档的计划与 Todo | `archive/` |

## 4. 核心入口文档

### 4.1 根 README

面向第一次接触项目的读者，只维护当前定位与已经可用的主要能力、最短的安装和运行路径、最小使用示例，以及指向 `PROJECT.md`、安装指南与路线图的入口；不承担完整架构说明，不描述尚未实现的能力。

### 4.2 PROJECT.md

`docs/` 的全局索引与当前项目总览：项目定位、已经成立的工程事实与能力边界、顶层架构图与关键数据流、System、Workspace、Patchouli、Alice、Gateway 的职责摘要、当前开发阶段、面向不同读者的阅读路径，以及当前设计、契约、帮助与计划的索引。它不承载各模块的详细设计，也不混合大段历史方案与未来构想。

### 4.3 VISION.md

维护长期定位、设计哲学、关键假设、决策门槛与明确非目标，并区分已经成立的工程事实、近期需要验证的假设与尚未实现的长期愿景。愿景中的能力不得作为当前功能对外宣传。

### 4.4 ROADMAP.md

维护版本或阶段的顺序、状态、目标、关键设计摘要、依赖关系与验收出口，说明各阶段准备开发什么、解决什么问题、为何采用当前顺序，不能退化成只有名称和链接的目录。

规划内容显式标记 `Planned`、`Candidate`、`Unscheduled` 等状态，并链接对应的 Idea、Plan 或 Todo、受影响的当前设计文档，以及完成后的 PR 或发布记录。它可以保留理解阶段关系所必需的模型边界与设计摘要；完整字段、逐组件落点、迁移步骤与测试矩阵由 Plan 维护，路线图不形成第二份详细实施方案，也不是详细模型的唯一真相源。

### 4.5 子系统 README

`system/`、`components/`、`workspace/`、`patchouli/`、`alice/` 与 `gateway/` 下的 `README.md` 是局部索引：职责与非职责、对外的主要能力、上下游依赖、文档列表、跨子系统契约入口与对应代码目录；不重复各机制的完整设计。

## 5. 目录结构

`docs/` 的一级目录按第 3 节的文档层级划分，固定入口文档见第 4 节。System、Components、Workspace、Patchouli、Alice、Gateway 与 Frontend 的目录各以 README 作为局部索引，当前文档清单以这些 README 与 `PROJECT.md` 为准；归档区按类型分为 `archive/plans/`、`archive/todo/`、`archive/ideas/` 与旧文档的 `archive/legacy-*`。

目录可以随真实系统边界调整，但不得通过新增含义模糊的目录绕过现有分类。

## 6. 文档状态与元数据

### 6.1 状态定义

| 状态 | 含义 |
|:---|:---|
| `draft` | 正在编写，尚未成为正式依据 |
| `current` | 当前生效的规范性设计或帮助文档 |
| `governance` | 跨版本持续维护的工程质量目标、成熟度与工作包 |
| `baseline` | 已冻结的 point-in-time 调研证据，不持续追随实现更新 |
| `planned` | 已形成计划，但尚未开始实施 |
| `active` | 对应工作正在实施 |
| `idea` | 开放设想，未形成项目承诺 |
| `todo` | 已确认的小范围缺陷或技术债 |
| `accepted` | 已接受且仍有效的架构决策 |
| `completed` | 计划已经完成，正在收尾（收尾时删除，第 10 节） |
| `superseded` | 已被另一项设计或决策替代 |
| `deprecated` | 决策已失效且没有替代，仅保留供追溯（用于 ADR） |
| `archived` | 仅供历史追溯，不描述当前系统 |

### 6.2 推荐元数据

新建或整理过的文档以 YAML Front Matter 开头。当前设计文档的格式：

```yaml
---
title: Retrieval              # 稳定、可读的名称
status: current
owner: patchouli              # 维护其语义的系统或模块
scope: retrieval
code_paths:                   # 用于核对文档的主要代码入口，不必穷举
  - src/hivememory/engines/retrieval/
  - src/hivememory/patchouli/services/retrieval.py
related_contracts:
  - docs/contracts/subsystem-contracts.md
last_reviewed: YYYY-MM-DD     # 最近一次按代码核对的日期
---
```

其他类型另加字段：

- Plan：`target`（目标版本或阶段）与 `updates`（完成时要更新的当前文档）；
- Idea：`horizon`，`horizon: current` 时另加 `serves_version`（[Ideas](ideas/README.md)）；
- 归档文档：`status: archived`、`archived_at`、`implemented_by` 与 `superseded_by`；
- Governance、Baseline、Research 与 ADR：见对应目录的 README（第 8.1、8.2、9 节）。

## 7. 事实文档的写法

本节适用于所有事实文档，包括机制文档、契约、帮助与前端文档。[短期记忆](architecture/short-term-memory.md)是一份按本节写成的机制文档，可以作为样例。

### 7.1 读者与风格

应当假定读者是第一次接触项目的人。他打开文档，应当立即明白文档在描述什么，读完能说清这件事怎样发生、为什么这样做。

- **介绍，而不是概括代码**：用平实、完整的句子讲事情怎样发生。不要把类、方法与调用顺序翻译成中文。
- **先定义，再使用**：每个术语第一次出现时，用一两句话说明它是什么，此后始终用同一个词。项目内部的名字（如 Gateway、Patchouli、Import Bus）第一次出现时，说明它是哪一部分、做什么。
- **代码名字放进参考**：正文用概念叙述，不出现字段名、方法名与配置键。维护者需要的名字，收在末尾的参考一节，按概念对照。
- **理由紧挨着行为**：每个不显然的做法，旁边用一句话说清为什么这样做，以及不这样做会出什么问题。
- **自述完备**：读者不点开任何链接，也能看懂这个机制。
  - 用到别的机制时，用一两句话说明它在这里起什么作用（第 2.1 节）。
  - 链接只指向代码入口，以及少量不影响理解的延伸阅读。
  - 一段话离开链接就读不懂，说明它该写进本文，或者不该出现在这里。

### 7.2 机制文档的结构

一份机制文档通常按下面的顺序写：

1. **开头**：本文介绍什么，读完能回答哪几个问题；
2. **要解决的问题**：为什么需要这个机制，它面对的核心矛盾，以及它与相邻部分的边界；
3. **一个例子**：用一个具体场景，从头到尾走一遍；
4. **基本概念**：后文用到的术语，各用一两句话说明；
5. **机制本身**：按事情发生的顺序讲。每一步写什么时候发生、怎样做、为什么这样做、出了问题会怎样，包括失败、取消、关闭与重启；
6. **必须守住的规则**：修改实现时要继续满足的约束，以及怎样发现它们开始被破坏；
7. **已知限制**；
8. **参考**：概念与代码名字的对照、重要的状态与位置、公开的路由与事件、配置、观测，以及代码与测试入口。

可以按机制的复杂度合并或省略章节，但不能省略为什么、必须守住的规则与代码入口。

### 7.3 事实文档不应包含的内容

- 已经失效却没有标记的旧流程；
- 尚未实现却用现在时描述的能力；
- 从另一篇文档完整复制的协议或机制；
- 按模块逐个复述类、方法与字段的代码清单；
- 只有类名、文件名与调用顺序，却没有背景、理由或取舍的段落；
- 离开链接就读不懂的段落；
- 只供一次重构使用的逐步实施清单；
- 与当前行为无关的大段探索；
- 容易快速失效的逐文件目录快照。

## 8. 工作文档与低频文档类型

各类工作文档与低频文档的规则写在各自目录的 README 中，与它们索引的文档放在一起；本节只说明每类文档是什么、规则在哪里。

### 8.1 Governance 与 Baselines

跨版本的工程质量主题（`governance`）与冻结的调查快照（`baseline`），创建与维护规则见 [Governance](governance/README.md)。治理文档不描述某个版本的实施方案，不替代当前设计或公共契约，列出工作包不构成路线图承诺；基线冻结，不随实现改写。

### 8.2 Research

外部系统、论文与技术方案的调研需求和报告，编写规则见 [Research](research/README.md)。调研只提供外部证据与适配分析，不能证明 HiveMemory 已具备对应能力，也不能借此绕过第 2.7 节的晋升门禁。

### 8.3 Plans

Plan 描述一个已经绑定版本或里程碑、能够立即执行并独立验收的功能、重构或迁移，是实施的工作依据，落地之后不承担当前设计说明。内容要求、进入 `plans/` 的条件与计划之间的约束见 [Plans](plans/README.md)；完成后的去向见第 2.8、10 节。

### 8.4 Ideas

Idea 记录尚未实施的设计：当前版本方向的设计、尚未排期的候选方向与长期假设，以及阻塞下一份计划的开放问题。它写的是设计现在是什么，不是设计怎样形成；讨论过程与搁置的想法不写进 Idea。它不代表路线图承诺。写法、`horizon` 分类、退回与升级为 Plan 的规则见 [Ideas](ideas/README.md)。

### 8.5 Todo

Todo 只适用于范围较小、排期灵活的缺陷或技术债；大型功能和跨系统重构必须形成 Plan。内容要求见 [Todo](todo/README.md)，完成后在收尾时删除（第 10 节）。

## 9. 架构决策记录（ADR）

ADR 保存已经做出、具有长期解释价值的架构决策，编写与状态规则见 [ADR 索引](architecture/decisions/README.md)。ADR 不得以活动计划为依据；当前设计文档可以链接 ADR 解释“为什么”，但仍应独立说明“现在是什么”。

## 10. 删除、归档与索引

计划与 Todo 不进入 `archive/`（owner，2026-11-18）。它们完成之后仍有价值的内容在收尾时分拣出去（见下文“删除”）；其余部分（阶段划分、实施步骤、测试矩阵、文档更新清单）不再有用，保留它们只会让归档区不断积累，还要维护索引与入链。`archive/` 收录什么、归档时怎样标记，以及归档索引的写法，见 [Archive](archive/README.md)。

**删除**。完成的计划与 Todo、未完成实施即作废的计划，以及升级为计划或并入计划的事项，直接删除，历史由版本控制保留。实施期间的记录照常写在计划的实施记录中；完成的计划与 Todo 在收尾时按一个标准分拣：删掉这条之后，读者还能不能看懂现在的设计为什么是这样。

- **看不懂：它仍然约束当前设计**。落地的设计、仍然有效的理由，以及实施中形成、改变或细化了设计的决定，写进当前事实文档；其中有长期解释价值的架构选择另写 ADR。
- **看得懂：它只解释当时怎样做到的**。验收结果、实施中的发现、试过又放弃的做法及原因，写进删除它的那个收尾提交的说明。主线以 squash 合并，同一个 PR 内的中间提交不留在主线上，只有写进提交说明的内容会随 squash 进入主线。

删除时必须：

1. 确认上述内容已经分拣到位；作废的计划则确认其中已落地且保留的代码由当前事实文档描述，或在承接的 Idea 或 Plan 中登记为待重新调查；
2. 把入链改为指向替代文档；没有替代时改为纯文本，并注明删除前最后版本所在的 commit；
3. 为其他文档中交由它收口的事项重新指定归属，或明确标记为未排期；
4. 在对应的归档索引登记一行。

文档的最后版本留在主线上删除它之前的 commit 中；与实施在同一个 PR 中建立又删除的文档，主线上没有它的版本，经该 PR 的提交取回。

**索引**只做导航，同一段历史只在一处维护：被归档文档自身，或删除时的收尾提交说明。归档索引的写法见 [Archive](archive/README.md)。工作区索引（`plans/`、`todo/` 与 `ideas/` 的 README）只列仍然活动的事项，每条一个标题链接加一句简短描述，说明它是什么；不复述状态、决定、日期与来源，它们只在被索引的文档中维护，索引因此不随每个决定同步。条目归档或删除后从工作区索引移除，只在归档索引登记，工作区索引至多保留一行指向归档索引。这三份 README 同时写有本类文档的规则，规则不属于索引条目。

## 11. 代码目录与代码注释规则

### 11.1 代码目录不放 README

`src/`、`tests/`、`scripts/` 与 `frontend/src/` 下不放 README 或其他说明文档：源码树中的 README 会随类名、目录结构和控制面迁移迅速失真。模块用途写在包或模块的 docstring 中，并遵守第 11.2 节；跨模块职责、公共契约与已知限制只在 `docs/` 的当前文档中维护，由文档以 `code_paths` 或代码链接指向实现。仓库根目录的 `README.md` 是项目入口（第 4.1 节），不属于代码目录。本规则与第 11.2 节由同一个架构测试守护。

### 11.2 代码注释与说明文本

引用只能从文档指向代码：事实文档、Plan 与 Idea 以 `code_paths` 或代码链接指向实现，代码不反向指向任何文档。文档删除、归档或改写之后，指向它们的注释会失去意义，或与实现悄悄不一致；而注释与代码同处一次修改，只要它自己说清楚，就不会失效。

适用范围是 Python 与 TypeScript 源码中的注释、docstring、裸字符串说明与字段 `description`，包括测试代码：

- 直接写出行为、不变量、理由与边界，读者不打开任何文档也能理解；所有工作文档删除、归档或事实文档改写之后，内容仍然成立。
- 不引用文档：不写 `docs/` 路径、`.md` 文件名、文档标题或文档中的章节号与编号条目（如“第 4.4 节”“§3.1”“不变量 6”“证据 3”），事实文档同样不引用。
- 不写工作编号：计划与批次代号（如 A1、A2-P、W1-E、“返工”“第二批”“Phase 2”）、决定与问题编号（如 Q-15、D-4、I-10、AC-1）。原注释只靠编号表达理由时，把理由本身写出来。
- 不写依赖计划进度的措辞（如“暂时保留到下一批”“中间态”）：现状写成事实与理由；已知限制直接写限制本身，后续工作在 Todo 或 Idea 中跟踪，由文档指向这段代码。
- 迁移来源与版本历史（“从某版本起”“v0.6.2 收敛”）交给版本控制，不写进注释。
- 可以保留：领域术语（如两阶段认证的“第 2 阶段”、四阶段骨架、Gateway 的检索计划）、运行时事实中的版本号（如 codec 版本、schema 版本），以及指向其他代码的路径。

`tests/unit/architecture/test_self_contained_comments.py` 扫描可以机读的引用形式；新的计划命名多为自然语言，正则不能覆盖全部写法，其余由评审把关。

## 12. 命名与链接规范

### 12.1 文件命名

- 固定入口使用大写名称：`PROJECT.md`、`VISION.md`、`ROADMAP.md`、`DOCUMENTATION.md`、`README.md`；
- 当前文档使用稳定的英文小写 kebab-case（如 `memory-compiler.md`），不含版本号、日期、`new`、`final`、`latest` 等易失效标记；
- 计划可以使用目标版本或日期（如 `v0.6.1-local-work-queue-runtime.md`）；ADR 使用递增编号（如 `0001-async-system-bus.md`）。

### 12.2 链接

- 仓库内 Markdown 文档使用相对链接；事实文档自述完备，链接只用于代码入口与延伸阅读（第 7.1 节），指向 archive 的链接要明确说明其历史性质；
- 引用代码时优先链接稳定目录、类或入口文件，避免依赖容易漂移的行号；
- 移动或重命名文档时同步修复所有入口和反向引用；不复制内容来规避链接，应修复文档结构或补充局部摘要。

---

本规范以 `VISION.md` 中“当前事实、近期假设与长期愿景相分离”的原则为上位依据。若文档结构与真实系统责任边界发生冲突，应先澄清并记录新的架构决策，再更新本规范，不能仅为维持目录形式而扭曲系统设计。
