# HiveMemory 文档治理与维护规范

> 本文档定义 HiveMemory 文档库的分类、职责、状态、目录结构与维护流程。
> 它描述的是文档治理规则，而不是某个子系统的设计。

## 1. 目标

HiveMemory 的文档库应当帮助读者可靠地回答以下问题：

1. 项目当前是什么，已经具备哪些能力？
2. 系统目前如何划分，各子系统分别负责什么？
3. 某个模块当前采用什么设计，真实代码入口在哪里？
4. 子系统之间通过什么契约交互，哪些行为属于稳定约束？
5. 哪些内容正在计划、尚处于设想，或者已经成为历史？
6. 一项设计为什么形成，后续应当如何安全地修改它？

文档治理的最终目标不是保存尽可能多的设计文字，而是维护一套能够反映当前后端真实设计、支持项目理解与演进的统一知识结构。

## 2. 核心原则

### 2.1 当前设计只有一个权威入口

`docs/` 主干中的当前设计文档是项目设计的规范性说明。相同概念只能存在一个主要维护位置，其他文档应通过链接引用，不得各自维护不同版本的完整描述。

例如：

- Retrieval 的当前职责和数据流只在 Patchouli 对应模块文档中完整描述；
- MTP 的稳定协议只在跨子系统契约文档中定义；
- Alice 文档可以解释如何使用 MTP，但不复制一份完整协议；
- 源码目录中的 README 只提供就近入口，不维护第二套模块设计。

### 2.2 当前设计与运行事实必须收敛

当前设计文档是理解和演进系统的权威入口；代码、测试、配置和运行结果是实现行为的可执行证据。

当两者不一致时，应将其视为需要修复的文档或实现缺陷，而不是接受“两套真相”长期并存：

- 如果代码实现正确，应在同一开发周期内更新当前设计文档；
- 如果文档描述的是仍然有效的约束，应修改代码使其重新满足设计；
- 如果尚不能立即判断，应明确记录为已知偏差，并创建可追踪的修复项。

计划、设想和历史文档不得被用来推断当前系统已经具备某项能力。

“与实现一致”不等于“把代码目录改写成自然语言”。代码能够证明系统现在做了什么，却通常不能独立解释为什么要这样划分、它试图解决什么矛盾、曾经放弃了哪些路径，以及哪些约束一旦被破坏就会让设计重新失衡。当前设计文档必须同时保留这些仍然有效的设计语义。

因此，每次根据代码更新文档时，应区分两类内容：

- **可执行事实**：当前组件、数据流、状态、接口和错误行为，由代码与测试核验；
- **持续有效的设计理由**：问题背景、核心矛盾、所有权判断、关键取舍和安全边界，由文档负责完整表达。

如果实现改变但原设计理由仍然成立，应说明新的实现如何继续满足它；如果理由已经失效，则需要明确修正文档，必要时形成 ADR，而不是只替换类名和流程图。

### 2.3 当前事实、未来意图与历史记录必须分离

文档必须明确区分：

- **当前事实**：已经落地并正在生效的设计、契约和行为；
- **计划**：目标较明确，但尚未完整进入当前事实的实现方案；
- **设想**：仍在探索的问题、假设和可能路径；
- **待办**：范围较小的缺陷、技术债或修复事项；
- **历史**：已经完成、被替代或不再生效的设计；
- **决策**：仍有长期解释价值的重要选择及其理由。

一篇文档不能同时作为当前设计和未来计划。当前文档可以记录“已知缺口”，但未来实现方案必须放入计划文档并通过链接关联。

### 2.4 目录按责任归属组织

当前设计优先按照稳定的系统责任边界组织，而不是完全复制代码目录。

- Patchouli、Alice、Gateway 是主要子系统；
- System 负责顶层装配、应用服务和全局运行时能力；
- Contracts 负责跨子系统的稳定交互边界；
- Architecture 负责整个系统的结构、边界和重要决策。

模块文档应归属于对其语义、生命周期和变更负责的系统，而不是简单归属于调用方最多或当前文件所在的位置。

### 2.5 文档首先服务于导航和判断

读者应当能够在较短路径内找到答案，并判断答案是否仍然有效。文档应优先提供：

- 清晰的责任和非责任边界；
- 真实的数据流和控制流；
- 稳定契约、关键不变量与失败语义；
- 对应代码和测试入口；
- 已知限制与相关文档链接。

文档不应为了完整而逐文件复述代码，也不应使用大量尚未实现的细节制造虚假的完备感。

### 2.6 历史可追溯，但不能干扰当前阅读

历史设计应保留在 `archive/`，重要决策应保留在 ADR 中。历史内容的价值是解释演进过程，而不是继续指导当前实现。

任何归档文档都必须显式标记为已归档，并尽可能指出替代它的当前文档、落地版本或相关 PR。

## 3. 文档层级与职责

| 文档层级 | 回答的问题 | 主要载体 |
|:---|:---|:---|
| Vision | 项目为什么存在、相信什么、如何取舍 | `VISION.md` |
| Project Overview | 项目当前提供什么、如何理解整体系统 | `PROJECT.md` |
| Architecture | 当前系统如何划分、核心边界和数据关系是什么 | `architecture/` |
| System Design | 顶层系统和各子系统当前如何工作 | `system/`、`patchouli/`、`alice/`、`gateway/` |
| Protocol & Contract | 子系统如何稳定交互 | `contracts/` |
| Product & Evidence | 为谁解决什么问题、怎样验证价值 | `applications/` 及评估文档 |
| Help | 如何安装、配置、使用和排障 | `help/` |
| Roadmap | 接下来验证和交付什么、顺序如何 | `ROADMAP.md` |
| Plan | 某项功能或重构准备如何落地 | `plans/` |
| Idea | 哪些方向值得探索、尚有哪些开放问题 | `ideas/` |
| Todo | 哪些小范围缺陷或技术债需要处理 | `todo/` |
| Decision | 为什么形成某项长期有效的重要设计选择 | `architecture/decisions/` |
| Archive | 哪些设计已经完成、失效或被替代 | `archive/` |

## 4. 核心入口文档

### 4.1 根 README

仓库根目录的 `README.md` 面向第一次接触项目的读者，只维护：

- 当前项目定位与已经可用的主要能力；
- 最短安装和运行路径；
- 最小使用示例；
- 指向 `PROJECT.md`、安装指南和路线图的入口。

README 不承担完整架构说明，不描述尚未实现的远期能力。

### 4.2 PROJECT.md

`PROJECT.md` 是 `docs/` 的全局索引和当前项目总览，主要包含：

1. 当前项目定位；
2. 已经成立的工程事实和能力边界；
3. 顶层架构图与关键数据流；
4. System、Patchouli、Alice、Gateway 的职责摘要；
5. 当前开发阶段；
6. 面向不同读者的推荐阅读路径；
7. 当前设计、契约、帮助、计划和历史文档索引。

`PROJECT.md` 不再承载所有模块的详细设计，也不混合大段历史方案和未来构想。

### 4.3 VISION.md

`VISION.md` 维护长期定位、设计哲学、关键假设、决策门槛和明确非目标。

愿景可以指导接口和架构选择，但必须明确区分：

- 已经成立的工程事实；
- 近期需要验证的假设；
- 尚未实现的长期愿景。

愿景中的能力不得直接作为当前功能对外宣传。

### 4.4 ROADMAP.md

`ROADMAP.md` 只维护版本或阶段的顺序、状态、目标和验收出口。

每个路线图项目应链接：

- 对应计划文档；
- 受影响的当前设计文档；
- 完成后的归档计划、发布记录或 PR。

详细实现方案不应长期堆积在路线图正文中。

### 4.5 子系统 README

`system/`、`patchouli/`、`alice/` 和 `gateway/` 下的 `README.md` 是各自的局部索引，负责说明：

- 子系统职责与非职责；
- 对外提供的主要能力；
- 上下游依赖；
- 模块文档列表；
- 跨子系统契约入口；
- 对应代码目录。

README 不重复各模块的完整实现设计。

## 6. 文档状态与元数据

### 6.1 状态定义

| 状态 | 含义 |
|:---|:---|
| `draft` | 正在编写，尚未成为正式依据 |
| `current` | 当前生效的规范性设计或帮助文档 |
| `planned` | 已形成计划，但尚未开始实施 |
| `active` | 对应工作正在实施 |
| `idea` | 开放设想，未形成项目承诺 |
| `todo` | 已确认的小范围缺陷或技术债 |
| `accepted` | 已接受且仍有效的架构决策 |
| `completed` | 计划已经完成，等待或正在归档 |
| `superseded` | 已被另一项设计或决策替代 |
| `archived` | 仅供历史追溯，不描述当前系统 |

### 6.2 推荐元数据

新建或完成整理的文档应在文件开头使用 YAML Front Matter。当前设计文档的基本格式为：

```yaml
---
title: Retrieval
status: current
owner: patchouli
scope: retrieval
code_paths:
  - src/hivememory/engines/retrieval/
  - src/hivememory/patchouli/services/retrieval.py
related_contracts:
  - docs/contracts/subsystem-contracts.md
last_reviewed: YYYY-MM-DD
---
```

字段说明：

- `title`：稳定、可读的文档名称；
- `status`：文档当前状态；
- `owner`：负责维护其语义的系统或模块；
- `scope`：文档覆盖范围；
- `code_paths`：用于验证文档的主要代码入口，不要求枚举全部文件；
- `related_contracts`：相关稳定契约；
- `last_reviewed`：最近一次根据代码核对内容的日期。

计划文档还应包含目标版本或阶段：

```yaml
---
title: Runtime Job Queue
status: planned
owner: system
target: v0.6.1
updates:
  - docs/system/runtime-and-bus.md
  - docs/contracts/routes-and-events.md
---
```

归档文档至少应包含：

```yaml
---
title: Legacy Retrieval Refactor Plan
status: archived
archived_at: YYYY-MM-DD
implemented_by: PR #000
superseded_by: docs/patchouli/retrieval.md
---
```

迁移完成前，尚未补充状态的旧文档不应仅因位于 `docs/` 主干就被自动视为当前真相；使用前需要结合代码和新的索引文档核对。

## 7. 当前设计文档的内容规范

一个模块的当前设计文档通常应包含以下内容：

1. **问题背景与设计动机**：为什么需要这个模块，它面对的核心矛盾是什么；
2. **定位与范围**：模块用什么方式解决问题；
3. **职责与非职责**：它负责什么，明确不负责什么；
4. **系统边界**：依赖谁，被谁调用，拥有哪部分状态，以及为什么这样分配所有权；
5. **核心组件**：稳定组件及其关系，不逐文件抄录代码；
6. **数据流与控制流**：关键请求、事件或任务如何流动；
7. **数据与状态**：重要模型、状态机、生命周期和持久化边界；
8. **公开契约**：路由、事件、输入输出及相关契约链接；
9. **设计取舍与细节处理**：重要 fallback、补偿、原子性、兼容或性能策略为什么存在；
10. **不变量与矛盾检查**：修改实现时必须继续满足的约束，以及如何识别所有权或流程开始冲突；
11. **错误与降级**：失败如何表达，哪些情况允许回退；
12. **配置与可观测性**：关键配置、日志、事件和指标；
13. **代码与测试入口**：用于验证描述的主要位置；
14. **已知限制**：当前确实存在但尚未解决的缺口；
15. **相关文档**：上游、下游、契约、计划和 ADR。

根据模块复杂度可以合并章节，但不得省略关键边界和实现验证入口。

### 7.1 当前文档不应包含的内容

- 已经失效但未明确标记的旧流程；
- 尚未实现却使用现在时描述的能力；
- 完整复制自另一篇文档的协议或数据模型；
- 只有类名、文件名和调用顺序，却没有问题背景、设计理由或取舍说明的代码清单；
- 仅供一次重构使用的逐步实施清单；
- 与当前行为无关的大段探索性讨论；
- 容易快速失效的逐文件目录快照，除非它确实帮助解释稳定边界。

## 8. Plans、Ideas 与 Todo

### 8.1 Plans

Plan 用于描述一个可独立验收的功能、重构或迁移，至少包括：

- 背景和问题；
- 目标与非目标；
- 当前状态和缺口；
- 目标设计；
- 受影响的系统、契约和数据；
- 兼容与迁移策略；
- 测试和验收标准；
- 风险与待决问题；
- 完成时必须更新的当前文档。

Plan 是实施过程的工作依据，但在功能落地后不能继续承担当前设计说明。

### 8.2 Ideas

Idea 用于开放探索，可以包含：

- 观察到的问题或机会；
- 假设与潜在价值；
- 若干可能路径；
- 主要未知项和验证方式；
- 升级为 Plan 所需满足的条件。

Idea 不代表路线图承诺，不使用确定语气宣称功能一定会实现。

### 8.3 Todo

Todo 只适用于范围较小、排期灵活的缺陷或技术债。大型功能和跨系统重构必须形成 Plan。

如果项目 Issue 系统中已经存在对应事项，文档应链接 Issue，而不是重复维护两份详细状态。Todo 至少应包含影响范围、现象或证据、完成条件和追踪链接。

## 9. 架构决策记录（ADR）

ADR 用于保存已经做出、具有长期解释价值的架构决策。适合记录：

- 子系统边界为何形成；
- 为什么选择某种数据所有权或通信模式；
- 为什么拒绝一个重要备选方案；
- 哪些约束导致当前设计；
- 什么条件变化后可以重新评估该决策。

ADR 应保持简短，通常包含：

1. Context；
2. Decision；
3. Consequences；
4. Alternatives；
5. Status；
6. Related documents。

被替代的 ADR 不删除，状态改为 `superseded` 并链接新的 ADR。当前设计文档可以链接 ADR 解释“为什么”，但仍应独立说明“现在是什么”。

## 10. Archive 规则

以下内容应进入 `archive/`：

- 已完成且内容已合并进当前设计的实施计划；
- 已被替代的旧设计；
- 仅用于某个历史迁移阶段的调查和清单；
- 已失效但仍具有追溯价值的架构说明；
- 文档重构前无法直接删除的历史材料。

归档时必须：

1. 将状态改为 `archived` 或 `superseded`；
2. 指出归档日期；
3. 链接替代它的当前文档；
4. 尽可能记录实现版本、PR 或决策；
5. 更新所有仍将其作为当前依据的入口链接。

归档文档原则上冻结。后续只修复严重错误、断链或补充追溯信息，不继续演进其设计内容。

## 11. 源码 README 规则

源码目录中的 README 可以保留，但只承担就近导航职责：

- 一句话说明模块用途；
- 指向当前设计文档；
- 指出主要公开入口；
- 提供必要且稳定的局部开发提示。

源码 README 不应维护完整架构、长期路线图、阶段完成度或另一套配置参考。如果相邻说明确实需要和代码同步变化，应保持很短，并避免复制主文档内容。

## 12. 命名与链接规范

### 12.1 文件命名

- 固定入口使用大写名称：`PROJECT.md`、`VISION.md`、`ROADMAP.md`、`DOCUMENTATION.md`、`README.md`；
- 当前模块文档使用稳定的英文小写 kebab-case，例如 `memory-compiler.md`；
- 当前文档名不包含版本号、日期、`new`、`final`、`latest` 等易失效标记；
- 计划可以使用目标版本或日期，例如 `v0.6.1-runtime-job-queue.md`；
- ADR 使用递增编号，例如 `0001-async-system-bus.md`。

### 12.2 链接

- 仓库内 Markdown 文档使用相对链接；
- 当前设计优先链接其他当前文档或 ADR；
- 指向 archive 的链接必须明确说明其历史性质；
- 引用代码时优先链接稳定目录、类或入口文件，避免依赖容易漂移的行号；
- 移动或重命名文档时必须同步修复所有入口和反向引用；
- 不复制内容来规避链接，应修复文档结构或补充局部摘要。

## 13. 开发与 PR 文档闭环

一项功能或重构的推荐生命周期为：

```text
Idea
  -> Plan
  -> Implementation
  -> 更新当前设计与契约
  -> 归档已完成 Plan
  -> 必要时保留 ADR
  -> 更新 ROADMAP 与索引
```

任何改变系统行为的 PR 都应检查：

- 是否改变子系统职责或所有权；
- 是否改变数据流、状态机或生命周期；
- 是否改变公开路由、事件、协议、配置或错误语义；
- 是否新增或移除主要能力；
- 是否改变可观测性和运维方式；
- 是否使某份当前文档、源码 README 或示例失效。

如果答案为是，应在同一个 PR 中更新对应的当前文档。实现完成时还应：

1. 将 Plan 中已经落地的设计合并进现有当前文档，而不是另建一份并行的“新设计”；
2. 将已完成 Plan 移入 `archive/plans/`；
3. 将仍有长期价值的决策提炼为 ADR；
4. 更新 `PROJECT.md`、子系统 README 和 `ROADMAP.md` 中受影响的链接或状态；
5. 检查相关帮助文档、配置示例和源码 README。

文档更新不是 PR 完成后的可选清理工作，而是设计变更完成定义的一部分。

## 14. 文档评审清单

新增或修改当前文档时，应至少确认：

- [ ] 文档状态和责任归属明确；
- [ ] 内容描述当前实现，没有把计划写成事实；
- [ ] 保留了仍然有效的问题背景、设计理念与关键取舍，而不是只复述代码；
- [ ] 职责、非职责和系统边界清晰；
- [ ] 读者能够据此判断一次新改动是否与原设计目标或所有权发生矛盾；
- [ ] 关键数据流、状态和错误语义与代码一致；
- [ ] 跨系统内容链接到唯一契约，而非重复定义；
- [ ] 提供了主要代码和测试验证入口；
- [ ] 已知缺口与未来方案相互分离；
- [ ] 相关 Plan、ADR、Roadmap 和 Archive 链接正确；
- [ ] 没有遗留指向旧设计的主入口；
- [ ] 文档内链接和目录索引有效。

## 15. 现有文档迁移规则

本规范生效后，现有文档按照以下顺序整理：

1. 建立现有文档清单，并将每篇标记为 `current`、`plan`、`idea`、`todo`、`decision`、`help`、`archive` 或 `merge`；
2. 收敛 `PROJECT.md` 和总体架构，建立可信的全局入口；
3. 整理跨子系统契约，确定协议、路由、事件和错误结构的唯一维护位置；
4. 按 System、Patchouli、Alice、Gateway 的责任边界重建当前设计文档；
5. 将 `docs/engines/` 和源码目录中仍有效的说明合并进对应当前文档；
6. 将 `docs/mod/` 中的文档分别迁入 Plans 或 Archive；
7. 拆分同时混合现状、迁移计划和路线图的文档；
8. 整理帮助文档、前端文档、应用规格和验证材料；
9. 完成全库链接、状态和索引检查。

迁移过程中，不应只移动文件而不核对内容。每篇被认定为 `current` 的文档都必须重新根据代码、测试和配置验证。

旧文档进入 Archive 前还必须通过逐篇迁移门禁：

1. 列出该文档可以独立成立的事实、设计主张、动机、取舍和未完成事项，不能只按章节标题粗略判断；
2. 将每一项分别归类为当前事实、长期决策、Plan、Todo、历史背景或明确拒绝/失效的设计；
3. 对当前事实、决策、Plan 和 Todo 指出实际承接文档，并核对承接内容保留了必要的“为什么”，而不只是类名与调用顺序；
4. 对未继承内容说明原因，例如代码从未落地、所有权已经改变、风险假设不再成立或存在更可靠的新决策；
5. 检查入口、反向链接和旧路径引用，确认没有文档仍把旧稿当作当前真相源；
6. 在迁移清单或独立审计记录中保存上述结论后，才允许执行物理移动。

审计通过不等于旧文档中的每句话都必须保留。迁移要保存仍有解释力的理念和细节，也要明确排除已经失效或从未实现的断言，避免 Archive 清理反而把未来设想写回当前事实。

## 16. 完成标准

文档体系重构在满足以下条件时可视为完成：

- `PROJECT.md` 能作为全局入口找到所有当前设计；
- System、Patchouli、Alice、Gateway 都有明确的职责说明和模块索引；
- 跨子系统契约拥有唯一维护位置；
- 主干文档只描述当前生效设计；
- Plan、Idea、Todo、ADR 和 Archive 的状态不会混淆；
- 旧 Engines 文档与源码 README 不再形成平行真相源；
- Roadmap 的每个主要阶段能够追溯到计划、当前设计和历史记录；
- 主要文档链接有效，归档内容不会被误认为当前依据；
- 后续 PR 已经能够按照本规范完成文档更新闭环。

---

本规范以 `VISION.md` 中“当前事实、近期假设与长期愿景相分离”的原则为上位依据。若文档结构与真实系统责任边界发生冲突，应先澄清并记录新的架构决策，再更新本规范，不能仅为维持目录形式而扭曲系统设计。
