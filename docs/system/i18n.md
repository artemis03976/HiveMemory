# 全局 i18n

HiveMemory 的 i18n 不只是把 UI 字符串翻译成两份。Gateway prompt、MTP 指令说明与错误、MemoryCompiler envelope、PendingAtom 状态和时间提示都会进入 Agent 可见上下文；语言选择因此必须是可追踪的运行时输入，而不能由每个组件各自猜测。

当前基础设施支持中文和英文，统一通过 `Language`、`normalize_language()`、`resolve_language()` 和按领域划分的 text getter 提供文本。文案本身仍属于各自领域：System 提供解析和配置入口，MTP、Gateway prompt、MemoryCompiler 和 syscall runtime 维护自己的 key 集合。

## 1. 语言类型与归一化

`Language` 当前包含 `zh`、`en` 及其别名成员。`normalize_language()` 接受 `zh-cn`、`zh-hans`、`cn`、`chinese`、`en-us`、`en-gb` 等输入；未知值返回 `None`，不会在这一层直接抛异常。

这种宽容归一化让配置和 Profile 的语言字段可以保持兼容，但也意味着严格的支持语言校验必须由配置或调用方另行负责。

## 2. 解析优先级

`resolve_language()` 当前优先级是：

```text
explicit
  > profile_language
  > component_language
  > 进程级 default
  > resolver fallback 参数
```

`HiveMemoryConfig` 的 model validator 会调用 `set_default_language(config.i18n.default_language)`，因此应用配置加载后会更新进程级默认语言。没有显式配置时，代码默认仍为 `zh`。

当前限制：`I18nConfig.fallback_language` 字段已经存在，但并没有自动传递到每次 `resolve_language()` 的 `fallback` 参数；因此不能把这个字段描述成已经贯穿所有 getter 的统一 fallback 真相源。未来若要统一 fallback，必须同时更新 resolver、配置语义和测试。

## 3. 文本领域

| 领域 | 当前入口 | 用途 |
|:---|:---|:---|
| Gateway | `get_gateway_prompt_text()` | Topic Router、Query Understanding 等 prompt 片段 |
| Relay | `get_relay_prompt_text()` | Agent relay/执行交接相关 prompt 片段 |
| Generation | `get_generation_prompt_text()` | 记忆生成与整理相关 prompt 片段 |
| System/MTP | `get_system_prompt_text()`、`get_mtp_prompt_text()`、`get_mtp_verb_text()` | Agent system prompt、协议说明和动词描述 |
| MTP runtime | `get_mtp_error_text()`、`get_mtp_info_text()`、`get_mtp_warning_text()` | 结构化错误、ACK、warning 的 Agent-facing 文本 |
| Syscall runtime | `get_syscall_error_text()`、`get_syscall_info_text()` | 文件、REPL、Web Search 等工具反馈 |
| MemoryCompiler | `get_memory_envelope_text()`、`get_memory_atom_text()`、`get_pending_atom_text()`、`get_resolve_result_text()` | Retrieval、READ、PendingAtom 和 alias resolve 输出 |
| TimeFormatter | `get_time_formatter_text()` | 相对时间和 stale warning |

getter 根据已解析语言选择文本表，并在未知 key 时抛 `KeyError`。key 是代码契约；不能通过解析本地化 message 来判断错误类别，错误机器语义仍由 Contracts 中的 code/severity 提供。

## 4. 设计边界

- i18n getter 负责文本选择，不负责权限、错误归因或 workflow 控制；
- Agent Profile language 可以覆盖组件语言，但不应修改进程级全局默认；
- MemoryCompiler 通过 `MemoryCompileOptions.language` 或 compiler default 接收语言，不应在内部偷偷读取 System config；
- MTP formatter 以 `message_key + params` 渲染错误，内部 `cause` 不进入 Agent 文本；
- 语言缺失时可使用 fallback 文本，但不能用 fallback 掩盖缺失 key 的程序错误。

只翻译自然语言模板，不翻译机器契约与业务数据。`⟪/⟫`、MTP verb、XML tag、response status、error code、route 和 alias 必须保持稳定；记忆正文、工具 stdout、文件内容和 URL 也不应被 i18n 层擅自改写。两类内容即使同时出现在 Agent 可见文本中，也有完全不同的所有权。

文本表按 prompt、MTP runtime、syscall 和 MemoryCompiler object family 分域，是为了让 key 与行为所有者一起演进，避免把所有字符串堆进一个全局 catalog。当前只有中英文，使用 Python 常量和小型 getter 是有意控制基础设施复杂度；在语言数量、翻译协作或运行期加载确有需求前，不提前引入 gettext/YAML/JSON catalog。

Agent-facing 文案会改变模型对错误、工具和记忆的理解，因此迁移必须小步进行，并保持协议结构、字段顺序、delimiter 与机器标识不变。i18n 测试不仅检查“有翻译”，还应检查翻译没有改变控制语义。

## 5. 当前限制与迁移边界

- 目前支持语言集合仍是 zh/en，新增语言需要同步类型、文本表、prompt、MemoryCompiler 和测试；
- `supported_languages` 主要是配置声明，当前不等于所有 getter 都自动校验该列表；
- 部分旧 i18n 设计文档同时包含已完成迁移和未来工作，不能直接作为当前状态引用；
- 文案中仍存在领域专有术语和协议标记，翻译不能改变 `⟪...⟫`、XML tag、error code 或 route 字符串。

## 6. 设计矛盾检查

1. 新组件是否自己维护了另一套语言 enum、默认值或 fallback 链？
2. 文案翻译是否改变了机器可解析的协议标记、error code、MTP verb 或 XML 结构？
3. 是否用 localized message 判断错误类别，而没有读取稳定 code/severity？
4. 是否把 Profile/component language 错误地写回进程级 default？
5. 新增语言是否只补了 UI 文案，却遗漏 Gateway、MTP、MemoryCompiler 或工具错误文本？
6. 未知 key 是应该补齐文案，还是被错误地降级为空字符串？
