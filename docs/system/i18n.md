# 全局 i18n

HiveMemory 的 i18n 不只是把 UI 字符串翻译成两份。Gateway prompt、MTP 指令说明与错误、MemoryCompiler envelope、PendingAtom 状态和时间提示都会进入 Agent 可见上下文；语言选择因此必须是可追踪的运行时输入，而不能由每个组件各自猜测。

当前支持中文和英文。HiveMemory 只有一个语言设置 `i18n.language`：HiveMemory 自己的提示词、外部 Agent 读到的 MCP 文字与插件 skill、HTTP 接口的错误说明都跟随它；前端界面与桌面客户端的文字不在其中。文本统一通过 `Language`、`resolve_language()` 和按领域划分的 text getter 提供；文案本身仍属于各自领域：System 提供语言设置，MTP、Gateway prompt、MemoryCompiler、MCP 入口与 HTTP 出口维护自己的 key 集合。

## 1. 语言类型与归一化

`Language` 当前包含 `zh`、`en` 及其别名成员。`normalize_language()` 接受 `zh-cn`、`zh-hans`、`cn`、`chinese`、`en-us`、`en-gb` 等输入；未知值返回 `None`，不会在这一层直接抛异常。它只用于调用链内部给出的显式语言（例如执行帧携带的语言）。

配置不经过这种宽容归一化：`i18n.language` 的类型就是 `Language`，只接受 `zh` 与 `en`，其他值在启动时被拒绝。

## 2. 语言设置与解析

语言设置由组合根（`SystemAssembler.assemble()`）在装配运行配置时以 `set_language(config.i18n.language)` 设置一次，先于 Gateway 的查询理解、话题路由与记忆抽取器等在构造时读取语言的组件。构造 `HiveMemoryConfig` 本身不改变它，因此配置路由为默认值查询或提交校验构造的临时配置对象不会让运行中的文本换语言；提交保存的新语言在下次启动时生效。代码与 `config.yaml` 的缺省值都是 `zh`。

旧键 `i18n.default_language` 已改名：配置段（含环境变量 `HIVEMEMORY__I18N__DEFAULT_LANGUAGE`）遇到它时启动失败，错误指出新键。

`resolve_language(explicit=...)` 只有两档：调用方给出可识别的显式语言时用它，否则用语言设置。组件、Agent 与请求都不另带语言：Agent Profile 没有语言字段，存量图纸中的 `language` 键在解析时忽略。

根帧提示词语言在任务进程的中立编译入口取一次语言设置，随 `CPUInputManifest.language` 交给 CPU。Alice 把它写入根帧的 `ExecutionFrame.language`：MTP 教学、会话摘要，以及执行期的 MTP 结果、错误与 CALL 响应回填都沿用该值，执行中不再重新读取；记忆与附件正文按各自编译结果原样保留。CALL 子帧由 `CallCoordinator` 沿用调用方帧的 `language`，同时用于子帧提示词、子帧的 `language` 与共享上下文的编译：CPU 内部的语言只来自输入清单，Alice 不读进程的语言设置，主帧与子帧因此总是同一种语言。

存储离线通知属于进程的 `instructions`：只要存储不可用就加入，与 MTP 教学开关无关。中英文模板都只说明记忆存储离线、依赖存储的操作会失败及可使用已有上下文，不假定执行者提供本地系统工具。

## 3. 文本领域

| 领域 | 当前入口 | 用途 |
|:---|:---|:---|
| Gateway | `get_gateway_prompt_text()` | Topic Router、Query Understanding 等 prompt 片段 |
| Relay | `get_relay_prompt_text()` | Agent relay/执行交接相关 prompt 片段 |
| Generation | `get_generation_prompt_text()` | 记忆生成与整理相关 prompt 片段 |
| Compaction | `get_compaction_prompt_text()` | 会话压缩：历史轮次的结局说明、工具结果减重的线索与省略标记、接力摘要指令与历史摘要段落 |
| System/MTP | `get_system_prompt_text()`、`get_mtp_prompt_text()`、`get_mtp_verb_text()` | Agent system prompt、协议说明和动词描述 |
| MTP runtime | `get_mtp_error_text()`、`get_mtp_info_text()`、`get_mtp_warning_text()` | 结构化错误、ACK、warning 的 Agent-facing 文本 |
| Syscall runtime | `get_syscall_error_text()`、`get_syscall_info_text()` | 文件、REPL、Web Search 等工具反馈 |
| MemoryCompiler | `get_memory_envelope_text()`、`get_memory_atom_text()`、`get_pending_atom_text()`、`get_resolve_result_text()` | Retrieval、READ、PendingAtom 和 alias resolve 输出 |
| TimeFormatter | `get_time_formatter_text()` | 相对时间和 stale warning |
| MCP | `get_mcp_text()` | MCP 入口的服务说明、工具与参数描述和结果文本（[MCP 记忆访问](../contracts/mcp.md)） |
| HTTP 错误 | `get_http_error_text()` | HTTP 出口与 MCP 工具错误结果中的安全说明与校验问题说明；错误码、状态与 `reason` 不在其中 |

MCP 服务的说明与工具描述在构造时注册，所以服务在 server 的 lifespan 读取配置之后才按语言设置构造，`/mcp` 路由在导入时登记，请求转交给 lifespan 中构造的应用。

插件 skill 不经过 getter：中英两份正文在插件目录的 `skill-languages/<语言>/SKILL.md`，受版本控制；harness 读取的 `skills/hivememory/SKILL.md` 不受版本控制，由插件服务在后端每次启动时按语言设置写入，内容相同时不改写，插件目录不存在时（Docker）不写。写入先于桌面模式下复制安装插件的自动更新（[桌面客户端](../frontend/desktop-client.md#3-后端的桌面模式)）。

getter 根据已解析语言选择文本表，并在未知 key 时抛 `KeyError`。key 是代码契约；不能通过解析本地化 message 来判断错误类别，错误机器语义仍由 Contracts 中的 code/severity 提供。

## 4. 设计边界

- i18n getter 负责文本选择，不负责权限、错误归因或 workflow 控制；
- 语言只来自语言设置；不为组件、Agent 或请求另设语言来源；
- MemoryCompiler 通过 `MemoryCompileOptions.language` 或 compiler default 接收语言，不应在内部偷偷读取 System config；
- MTP formatter 以 `message_key + params` 渲染错误，内部 `cause` 不进入 Agent 文本；params 由出口白名单构造，不接收原始异常 detail；
- 写入结果未知的中英文提示均禁止重复 WRITE/UPDATE，只在 READ 可用时建议查原句柄；线程已撤销提示停止原线程，不建议重试或重新获取身份；未知程序故障采用固定提示；
- 未知 key 是程序错误，不能用另一种语言的文本或空字符串掩盖。

只翻译自然语言模板，不翻译机器契约与业务数据。`⟪/⟫`、MTP verb、XML tag、response status、error code、route 和 alias 必须保持稳定；记忆正文、工具 stdout、文件内容和 URL 也不应被 i18n 层擅自改写。两类内容即使同时出现在 Agent 可见文本中，也有完全不同的所有权。

文本表按 prompt、MTP runtime、syscall 和 MemoryCompiler object family 分域，是为了让 key 与行为所有者一起演进，避免把所有字符串堆进一个全局 catalog。当前只有中英文，使用 Python 常量和小型 getter 是有意控制基础设施复杂度；在语言数量、翻译协作或运行期加载确有需求前，不提前引入 gettext/YAML/JSON catalog。

Agent-facing 文案会改变模型对错误、工具和记忆的理解，因此迁移必须小步进行，并保持协议结构、字段顺序、delimiter 与机器标识不变。i18n 测试不仅检查“有翻译”，还应检查翻译没有改变控制语义。

## 5. 当前限制与迁移边界

- 目前支持语言集合仍是 zh/en，新增语言需要同步类型、文本表、prompt、MemoryCompiler 和测试；
- 部分旧 i18n 设计文档同时包含已完成迁移和未来工作，不能直接作为当前状态引用；
- 文案中仍存在领域专有术语和协议标记，翻译不能改变 `⟪...⟫`、XML tag、error code 或 route 字符串。

## 6. 设计矛盾检查

1. 新组件是否自己维护了另一套语言 enum、默认值或 fallback 链？
2. 文案翻译是否改变了机器可解析的协议标记、error code、MTP verb 或 XML 结构？
3. 是否用 localized message 判断错误类别，而没有读取稳定 code/severity？
4. 是否又为组件、Agent 或请求引入了另一个语言来源？
5. 新增语言是否只补了 UI 文案，却遗漏 Gateway、MTP、MemoryCompiler 或工具错误文本？
6. 未知 key 是应该补齐文案，还是被错误地降级为空字符串？
