# v0.5.0 Data Durability 与 Async Cold Path 实现规划

**文档状态**: Draft
**适用范围**: `core/models/memory.py`、`core/protocol/models.py`、`prompts/transcript/`、`patchouli/service.py`、`patchouli/services/librarian.py`、`patchouli/services/memory_generation_tasks.py`、`patchouli/services/retrieval.py`、`system/runtime/bus/`、`system/runtime/scheduler/`、`infrastructure/storage/`、`engines/generation/`、`engines/retrieval/`
**核心目标**: 建立围绕 `MemoryAtom` 的 artifact 数据模型与本地存储，把原始对话片段、外源文档来源、首次创建输入、版本快照和 L3 冷存储复活线索沉淀为长期证据；同时收敛 generation/retrieval 的异步冷路径契约，为后续 MTP READ/RUN、多智能体编排与记忆 split/merge 提供稳定数据底座。

---

## 1. 版本定位

v0.4.0 已经把运行时控制面基本拉起来：

- `ChatApplicationService` 已有 `ChatGenerationRunRegistry`、结构化 cancel result、`generation_id` 注入、取消后跳过 finalize。
- `RuntimeEvent` / `RuntimeEventBus` / `/runtime-events/stream` 已经存在。
- `MemoryGenerationTask` / `MemoryGenerationTaskController` / `/memory-tasks` API 已经存在。
- `run_active_generation()` 已从 finalize 的纯同步子过程，升级为创建可查询、可取消、可观测的后台 memory task。
- `AsyncMaintenanceScheduler` / `GlobalMaintenanceScheduler` 已提供纯 asyncio 定时维护基础。

因此 v0.5.0 需要解决另一个更底层的问题：

> 系统中的每条长期记忆，是否能稳定追溯到它创建时依据的原始对话片段、外源文档来源、生成输入视图、后续版本变更，以及未来从 L3 冷存储中被唤起所需的 alias / revival keys。

v0.5.0 的主题可以概括为：

> 将 artifact 从 `MemoryAtom.payload.artifacts` 中的杂项存根，升级为围绕记忆原子组织的长期证据层，形成规范体系。

后续版本依赖关系：

| 后续能力 | 为什么依赖 v0.5.0 |
| :--- | :--- |
| System Gateway 与复合意图拆分 | 一个输入拆成多个记忆意图后，需要每个 MemoryAtom 都能绑定自己的原始对话片段、创建输入和来源 artifact |
| MTP READ 历史版本编译 | READ 需要读取版本快照、创建输入、外源文档引用，而不是只读 `payload.content` |
| MTP RUN executable asset | executable asset 必须能追溯原始来源、构建输入和版本快照 |
| Alice Phase 3 多智能体编排 | 多 Agent 产物需要把最终沉淀出的 MemoryAtom 与其对话来源、文档来源、创建输入绑定 |
| 记忆分裂与合并 | split/merge 必须能回溯原始对话片段、版本 artifact 和来源文档，否则无法安全回滚 |
| L3 冷存储复活 | 已归档记忆需要 alias、alias history、revival keys 与 archive artifact，才能在未来被 Agent 重新唤起 |

## 2. 当前状态调研

### 2.1 已有基础

#### 2.1.1 MemoryAtom 已有 artifacts 层

`MemoryAtom` 采用冰山模型：

- `meta`: 生命周期、身份、权限、版本。
- `index`: 检索摘要与 alias。
- `payload`: 注入上下文的核心内容。
- `payload.artifacts`: 原始存根、历史、agent config。

当前 `Artifacts` 已有字段：

- `raw_source_url`
- `file_path`
- `context_ref`
- `full_history`
- `agent_config`

这说明“原始数据层”在模型概念上已经存在，但还没有面向 chat run / memory task / transcript 的正式 artifact schema。

#### 2.1.2 Transcript 已经分为双视图

当前已有：

- `HistoryTranscriptBuilder`: 用 `LogicalBlock.turn_events` 重放历史消息视图。
- `GenerationTranscriptBuilder`: 用 `LogicalBlock` 生成适合记忆提取的 `GenerationContext`。
- `InteractionPayload`: 承载 `user_message`、`assistant_final_text`、`turn_events`、`mtp_traces`、`materialize_tasks`。

这意味着 v0.5.0 不需要再发明 transcript 主链路，而是需要把“原始事实 + 双视图产物 + metadata”保存为可引用 artifact。

#### 2.1.3 RuntimeEvent 与 memory task 已落地

当前 RuntimeEvent 类型包括：

- `chat.run.*`
- `agent.run.*`
- `memory.task.*`
- `event.stream.gap`

`MemoryGenerationTask` 已包含：

- `task_id`
- `topic_id`
- `label`
- `source`
- `pending_alias`
- `status`
- `canonical_alias`
- `error`
- `created_at` / `started_at` / `finished_at`
- `cancel_event`

这为 v0.5.0 提供了可绑定 provenance 的运行时 id。

#### 2.1.4 异步总线与调度器存在

当前已有：

- `AsyncSystemBus`: async RPC + async pub/sub。
- `GlobalSystemBus` / `PatchouliBus` / `AliceBus`。
- `PatchouliBridge` 已把 public routes 挂到全局总线。
- `AsyncMaintenanceScheduler` 已提供纯 asyncio 维护任务调度。
- `RetrievalFamiliar.retrieve_async()` 目前通过 `asyncio.to_thread()` 包裹同步检索。

这说明“总线入口异步化”已经开始，但还没有形成统一 job/request contract，也没有把 cold path 的耐久化、重试、backpressure 收束起来。

### 2.2 当前缺口

| 缺口 | 现象 | v0.5.0 处理方式 |
| :--- | :--- | :--- |
| Raw transcript 没有持久化 artifact | 长期记忆只保存提取后的 payload，原始对话细节丢失 | 新增 memory-bound `InteractionArtifact`，保存创建该记忆所依据的原始对话片段 |
| MemoryAtom 与生成任务缺少稳定 provenance | 只能从 alias/task/log 推断来源 | 新增轻量 `MemoryProvenance` 并写入 artifact manifest |
| 记忆生成链路没有 artifact 构建点 | artifact 不能从 chat runtime 旁路生成，必须与 MemoryAtom 创建/更新同步 | 在 `MemoryGenerationEngine` 附近新增 `MemoryArtifactGenerator` |
| Retrieval async 只是 to_thread 包装同步链路 | 缺少超时、取消、重试、事件状态 | 定义 `RetrievalJob` / request envelope 或至少统一 bus contract |
| Artifact 存储没有独立抽象 | 只能塞进 Qdrant payload，可能污染向量 payload 或造成大对象膨胀 | 新增 `ArtifactStore`，MemoryAtom 只保存 refs |

## 3. 本期目标与非目标

### 3.1 目标

1. **原对话全量冷保存**
   - 每次成功创建 memory atom 后，至少保存或关联一份 `InteractionArtifact`。
   - cancelled / failed / discarded task 不生成 memory-bound artifact。
   - artifact 绑定 `memory_id`、`memory_alias`、`topic_id`、`agent_id`、`user_id`。

2. **双视图 transcript artifact**
   - 保存 raw facts：`InteractionPayload`、`turn_events`、`mtp_traces`、retrieval refs。
   - 保存 history view：可重放给 Agent 的消息视图。
   - 保存 generation view：用于记忆生成的 `GenerationContext` 与渲染文本。
   - 明确三者不是同一个东西，避免后续继续用字符串互相逆推。

3. **MemoryAtom provenance**
   - 新建/更新/合并/触碰/丢弃的 generation result 均能指向来源 artifact。
   - `MemoryAtom.payload.artifacts` 不直接塞大块 raw transcript，而保存稳定 artifact refs。
   - `full_history` 中的每次版本变更附带来源 artifact/task/run。

4. **ArtifactStore v1**
   - 提供轻量本地 artifact store 抽象。
   - 支持 JSON artifact 写入、读取、hash 校验、按 id 查询。
   - 第一版可以使用本地文件系统，后续再替换为数据库或对象存储。

5. **Generation / Retrieval cold path async-native**
   - 把 generation task 和 retrieval request 的运行状态、超时、取消、重试、事件发布收敛为统一契约。
   - Retrieval 不再只是“同步函数外包一层 `to_thread`”，而有明确 request id、timeout、RuntimeEvent、failure policy。
   - Generation task 从“fire background task”升级为由 task runner / queue 统一调度。

6. **可重放与回归测试**
   - 给定 `InteractionArtifact`，可以找回创建该记忆时依据的原始对话片段。
   - 给定 memory atom，可以找到它的原始对话、创建输入、外源文档与版本 artifact。
   - 保证取消 run 默认不污染长期记忆，但可保存 debug/raw artifact。

### 3.2 非目标

本期不做以下工作：

- 不实现 Gateway 上移。
- 不实现复合意图识别。
- 不实现 MTP READ 历史编译的最终渲染，只为它准备数据。
- 不实现 MTP RUN executable asset，只准备 artifact/provenance 结构。
- 不实现记忆 split/merge 行为，只预留 provenance source type。
- 不持久化完整 RuntimeEvent 流；只持久化关键 run/task/artifact outcome。
- 不把 Qdrant 替换为新的主存储。

## 4. 目标数据模型

### 4.1 Artifact 设计原则

v0.5.0 引入新的 artifact 体系，但不把它设计成“任意 JSON 袋子”。Artifact 的职责是保存不应该进入 `MemoryAtom.payload.content` 的证据、来源、运行快照与冷资产；`MemoryAtom.payload.artifacts` 只保存简洁 manifest。

```text
MemoryAtom.index
  -> 可检索摘要、标签、alias

MemoryAtom.payload
  -> 可注入上下文的核心内容

MemoryAtom.payload.artifacts
  -> refs + provenance + cold archive hint

ArtifactStore
  -> InteractionArtifact
  -> DocumentArtifact
  -> MemoryCreationArtifact
  -> MemoryVersionArtifact
  -> MemoryArchiveArtifact
```

原则：

- 只维护一个顶层枚举 `ArtifactType` 分类，表达 artifact 自身是什么类型。
- `ArtifactType` 和 MemoryAtom 的关系由 `MemoryArtifactManifest` 的字段位置和 `MemoryProvenance` 表达。
- `ArtifactRef` 只有一种，不为不同 artifact 类型创建专用 ref。
- `BaseArtifact` 只放所有 artifact 共用的元信息；派生类必须声明自己的结构，不使用无边界 `payload: dict[str, Any]` 作为主模型。
- `MemoryArtifactManifest` 保持轻量，不为了适配所有 artifact 类型而创建大量特化字段。

### 4.2 ArtifactType 与 ArtifactRef

建议新增 `core/models/artifact.py`。

```python
class ArtifactType(str, Enum):
    INTERACTION = "interaction"
    DOCUMENT = "document"
    MEMORY_CREATION = "memory_creation"
    MEMORY_VERSION = "memory_version"
    MEMORY_ARCHIVE = "memory_archive"


class ArtifactRef(BaseModel):
    artifact_id: str
    artifact_type: ArtifactType
    uri: str | None = None
    sha256: str | None = None
    created_at: datetime | None = None
    summary: str | None = None
```

`ArtifactRef` 是轻引用，只解决“在哪里、是什么、如何快速识别”。不要在 ref 上挂载复杂业务语义；需要业务语义时读取对应 artifact 或 provenance。

### 4.3 BaseArtifact

```python
class BaseArtifact(BaseModel):
    artifact_id: str
    artifact_type: ArtifactType
    schema_version: str = "v1"

    created_at: datetime
    updated_at: datetime | None = None

    owner_user_id: str
    owner_agent_id: str | None = None

    title: str | None = None
    summary: str | None = None
    content_hash: str | None = None
```

`BaseArtifact` 不提供大而全的 `payload` 字段。各派生 artifact 自己声明数据结构，保证模型边界清晰。

### 4.4 InteractionArtifact

`InteractionArtifact` 保存某个 `MemoryAtom` 创建时所依据的原始对话片段冷备份。它不是一次 chat run 日志，也不是单条 user message 记录，而是与一个记忆原子绑定的一组原始消息。

```python
class InteractionMessage(BaseModel):
    role: Literal["user", "assistant", "system", "tool"]
    content: str
    timestamp: datetime | None = None
    turn_id: str | None = None
    message_id: str | None = None
    agent_id: str | None = None
    source: Literal["topic_buffer", "active_context", "manual"] | None = None


class InteractionArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.INTERACTION] = ArtifactType.INTERACTION

    memory_id: str
    memory_alias: str | None = None
    topic_id: str | None = None

    source_mode: Literal["topic_buffer", "active_context", "manual_import"]
    capture_policy: Literal["full_topic_buffer", "selected_context"]
    messages: list[InteractionMessage]

    captured_at: datetime
```

注意：

- 被动 ARCHIVE 链路下，它通常保存感知层累计的话题 buffer 消息。
- 主动 WRITE 链路下，它保存本次生成所使用的背景对话上下文。
- 它不保存 `generation_view`、task 状态、cancel/failed 状态或完整 retrieval result。
- 如果一次 topic buffer 生成多个 memory atom，第一版允许多个 memory atom 引用同一个 `InteractionArtifact`；后续可再细化为按选区拆分。

### 4.5 DocumentArtifact

`DocumentArtifact` 面向外源文档的信息易逝性问题。长期记忆的 `payload.content` 往往只是文档摘要或大纲，真实来源必须通过 document artifact 可追踪。

```python
class DocumentLocator(BaseModel):
    page: int | None = None
    heading_path: list[str] = Field(default_factory=list)
    section: str | None = None
    line_start: int | None = None
    line_end: int | None = None
    char_start: int | None = None
    char_end: int | None = None
    quote: str | None = None


class DocumentArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.DOCUMENT] = ArtifactType.DOCUMENT

    source_type: Literal["url", "file", "pdf", "markdown", "html", "repo", "unknown"]
    source_uri: str | None = None
    canonical_uri: str | None = None
    mime_type: str | None = None

    retrieved_at: datetime | None = None
    etag: str | None = None
    last_modified: str | None = None
    content_hash: str | None = None

    locators: list[DocumentLocator] = Field(default_factory=list)
    snapshot_ref: ArtifactRef | None = None
    extracted_text_ref: ArtifactRef | None = None
```

v0.5.0 不实现完整文档解析，但模型必须允许未来记录“这条记忆来自某个 URL/PDF/Markdown 的哪一页、哪一节、哪一段”。

### 4.6 MemoryCreationArtifact

`MemoryCreationArtifact` 保存某个 `MemoryAtom` 首次创建时，生成器看到的结构化输入与创建依据。它只在记忆原子创建成功后生成；failed/cancelled/pending/running task 不会产生该 artifact。

Retrieval 结果不作为独立 artifact。检索是运行时观测，结果会随着 query、活跃记忆集合、生命力分数和 alias 状态变化，不适合作为长期稳定资产保存。检索命中与主动引用继续进入 lifecycle event；只有当某批 memory 真的参与了一次 memory creation，才在 `MemoryCreationArtifact.source_memory_refs` 中保存轻量输入引用。

```python
class MemoryInputRef(BaseModel):
    memory_id: str
    alias: str | None = None
    title: str | None = None
    version: int | None = None
    used_as: Literal["context", "citation", "update_target"] = "context"


class MemoryCreationArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.MEMORY_CREATION] = ArtifactType.MEMORY_CREATION

    memory_id: str
    memory_alias: str | None = None
    source_intent: Literal["ARCHIVE", "WRITE", "IMPORT", "MANUAL", "SYSTEM"]

    generation_view: dict[str, Any]
    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    source_memory_refs: list[MemoryInputRef] = Field(default_factory=list)

    created_title: str
    created_summary: str
    created_tags: list[str]
    created_memory_type: str
```

`MemoryTaskArtifact` 不进入 v0.5.0 artifact 体系。memory task 是运行时调度实体；失败、取消、排队、超时等状态应由 `RuntimeEvent`、任务 registry 或未来的 `TaskRecord` 表达，不属于 MemoryAtom 的长期 artifact。

### 4.7 MemoryVersionArtifact 与 MemoryArchiveArtifact

`MemoryVersionArtifact` 用于保存某次更新前后的快照或差异；`MemoryArchiveArtifact` 用于增强当前 L3 归档机制。v0.5.0 不实现自动复活，但归档记录必须预留 alias 与 revival keys。

```python
class MemoryVersionArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.MEMORY_VERSION] = ArtifactType.MEMORY_VERSION

    memory_id: str
    memory_alias: str | None = None
    version_from: int
    version_to: int
    update_source: Literal["UPDATE", "MERGE", "MANUAL_EDIT", "SYSTEM_REWRITE"]

    previous_content: str
    new_content: str
    changelog: str | None = None

    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    source_memory_refs: list[MemoryInputRef] = Field(default_factory=list)
    changed_at: datetime


class MemoryArchiveArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.MEMORY_ARCHIVE] = ArtifactType.MEMORY_ARCHIVE

    memory_id: str
    canonical_alias: str | None = None
    alias_history: list[str] = Field(default_factory=list)

    title: str
    summary: str
    tags: list[str]
    memory_type: str

    archived_at: datetime
    original_vitality: float
    storage_uri: str
    compressed_size_bytes: int | None = None

    revival_keys: list[str] = Field(default_factory=list)
```

该模型对应当前 `ArchiveRecord` 的增强方向：旧记录只能 `uuid -> file_path`，新记录至少应允许未来 `alias/revival_key -> archive artifact -> resurrect`。

### 4.8 MemoryArtifactManifest 与 MemoryProvenance

`MemoryAtom.payload.artifacts` 应升级为 manifest，但保持简洁：

```python
class MemoryProvenance(BaseModel):
    action: Literal[
        "created",
        "updated",
        "merged",
        "touched",
        "archived",
        "resurrected",
        "manual_edit",
        "future_split",
        "future_merge",
    ]
    at: datetime
    source_intent: Literal["ARCHIVE", "WRITE", "UPDATE", "IMPORT", "MANUAL", "SYSTEM"] | None = None
    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    note: str | None = None


class Artifacts(BaseModel):
    # 兼容旧字段，v0.5.0 不删除
    raw_source_url: Optional[str] = None
    file_path: Optional[str] = None
    context_ref: list[dict[str, str]] = Field(default_factory=list)
    full_history: list[dict[str, Any]] = Field(default_factory=list)
    agent_config: Optional[dict[str, Any]] = None

    # 新 manifest 字段
    refs: list[ArtifactRef] = Field(default_factory=list)
    provenance: list[MemoryProvenance] = Field(default_factory=list)
    cold_archive: ArtifactRef | None = None
    revival_keys: list[str] = Field(default_factory=list)
```

迁移原则：

- 旧字段不删除，保证旧 Qdrant payload 仍能反序列化。
- 新代码优先写 `refs/provenance/cold_archive/revival_keys`。
- `raw_source_url` / `file_path` 后续可迁移为 `DocumentArtifact`，但 v0.5.0 只做兼容保留。
- `context_ref` 可继续兼容旧 `{session_id, msg_id}`，新链路优先使用 `InteractionArtifact`。

### 5.2 非入口：不扩展 chat / agent runtime 协议

v0.5.0 不扩展 `InteractionPayload`、`PreparedAgentRun` 或 chat/agent runtime 协议来承载 artifact refs。

原因：

- artifact 与 `MemoryAtom` 的创建/更新强绑定，只有进入 Patchouli generation 链路并实际生成或变更记忆后才有长期保存意义。
- chat run / agent run 中的大部分字段是运行时噪声，不应提前进入 artifact 体系。
- 真实参与记忆创建的上下文由 generation 输入决定，不应从外围 run metadata 推断。
- 真实使用过的历史记忆通常来自 Agent 运行时 MTP 访问轨迹，而不是普通 retrieval 命中结果。

因此，artifact 构建入口应位于 Patchouli 子系统内部，靠近 `MemoryGenerationEngine`，而不是位于 `system/application` 层。

### 5.3 MemoryArtifactGenerator

新增 `MemoryArtifactGenerator`，位置建议二选一：

```text
src/hivememory/engines/generation/artifacts.py
```

或在代码量增长后拆成并列引擎：

```text
src/hivememory/engines/artifacts/
  __init__.py
  models.py
  generator.py
```

职责：

- 根据创建成功的 `MemoryAtom` 与当前 `GenerationContext` 构建 `InteractionArtifact`。
- 根据创建成功的 `MemoryAtom` 与生成输入构建 `MemoryCreationArtifact`。
- 根据 UPDATE / MERGE / MANUAL_EDIT 前后的 memory 快照构建 `MemoryVersionArtifact`。
- 将 artifact 写入 `ArtifactStore`，得到 `ArtifactRef`。
- 在 memory 入库前将 refs/provenance 写入 `MemoryAtom.payload.artifacts`。

建议接口：

```python
class MemoryArtifactBundle(BaseModel):
    interaction_ref: ArtifactRef | None = None
    creation_ref: ArtifactRef | None = None
    version_ref: ArtifactRef | None = None
    document_refs: list[ArtifactRef] = Field(default_factory=list)


class MemoryArtifactGenerator:
    def build_for_create(
        self,
        *,
        memory: MemoryAtom,
        context: GenerationContext,
        source_intent: Literal["ARCHIVE", "WRITE", "IMPORT", "MANUAL", "SYSTEM"],
    ) -> list[BaseArtifact]: ...

    def build_for_update(
        self,
        *,
        memory_before: MemoryAtom,
        memory_after: MemoryAtom,
        changelog: str,
        update_source: Literal["UPDATE", "MERGE", "MANUAL_EDIT", "SYSTEM_REWRITE"],
    ) -> list[BaseArtifact]: ...
```

第一版可以先让 generator 返回 artifact models，由 `MemoryGenerationEngine` 调用 `ArtifactStore` 写入；后续再把 store 注入 generator，形成完整 artifact engine。

### 5.4 CREATE 链路 artifact 构建

CREATE 链路在 `_draft_to_memory()` 生成 `MemoryAtom` 后、`_save_memory()` 入库前安排 artifact。

推荐顺序：

```text
1. ExtractedMemoryDraft -> MemoryAtom
2. MemoryArtifactGenerator.build_for_create(...)
3. ArtifactStore 写 InteractionArtifact / MemoryCreationArtifact
4. ArtifactRef 写入 memory.payload.artifacts.refs
5. MemoryProvenance(action="created", source_intent=...) 写入 memory.payload.artifacts.provenance
6. _save_memory(memory)
```

`InteractionArtifact` 的来源：

- 被动 ARCHIVE：来自 `GenerationContext.turns` 对应的话题 buffer 消息。
- 主动 WRITE：来自 `GenerationContext.turns` 中携带的背景对话。
- 如果当前上下文不足以重建原始消息列表，v0.5.0 允许先保存可用的 `GenerationTurn` 语义消息，但必须在 artifact 中标记 `capture_policy="selected_context"`。

`MemoryCreationArtifact` 保存：

- `memory_id` / `memory_alias`。
- `source_intent`，由调用路径显式传入或在 controller 内部推断。
- `generation_view`，即当前 `GenerationContext.model_dump()`。
- 初始创建出的 title / summary / tags / memory_type。

### 5.5 UPDATE / MERGE 链路 artifact 构建

UPDATE / MERGE 链路由 `MemoryVersionArtifact` 记录版本变化，不复用 creation artifact。

推荐顺序：

```text
1. 复制 memory_before
2. 生成 memory_after
3. MemoryArtifactGenerator.build_for_update(...)
4. ArtifactStore 写 MemoryVersionArtifact
5. version_ref 写入 full_history item
6. provenance 追加 action="updated" 或 action="merged"
7. _save_memory(memory_after)
```

`full_history` item 从：

```python
{
  "timestamp": "...",
  "content": "...",
  "reason": "..."
}
```

扩展为：

```python
{
  "timestamp": "...",
  "content": "...",
  "reason": "...",
  "artifact_refs": [...]
}
```

`TOUCH` / `DISCARD` / `CANCELLED` / `FAILED` 不写 artifact：

- `TOUCH`: 走 lifecycle event。
- `DISCARD`: 留在 memory task 状态或 RuntimeEvent。
- `CANCELLED` / `FAILED`: 属于运行时状态，不属于 memory-bound artifact。

### 5.6 GenerationRequest 暂缓扩展

v0.5.0 不急于扩展 `GenerationRequest` 的 artifact 字段。

原因：

- 当前没有外源文档解析功能，提前增加 document source refs 会长期为空。
- 真实使用过的 memory refs 当前隐含在 `GenerationTurn.trace_summaries` / `mtp_traces` 中，不宜先用空的 `source_memory_refs` 字段占位。
- `source_intent` 可以从调用路径推断：`_run_archive_task()` 对应 `ARCHIVE`，主动 WRITE 对应 `WRITE`，未来 import/manual 再补充。

如果实现中确实需要显式传递创建意图，优先使用 generation engine 内部的轻量上下文对象，而不是污染 `GenerationRequest`：

```python
class MemoryArtifactContext(BaseModel):
    source_intent: Literal["ARCHIVE", "WRITE", "IMPORT", "MANUAL", "SYSTEM"]
```

### 5.7 MTP trace 与 source memory refs 暂缓策略

`MemoryCreationArtifact.source_memory_refs` 可以作为未来字段预留，但 v0.5.0 不要求填充。

真实使用到的记忆原子来自 Agent 运行时 MTP 指令访问轨迹，而不是普通 retrieval 结果。当前这些信息主要隐含在：

- `GenerationTurn.trace_summaries`
- `InteractionPayload.mtp_traces`
- `turn_events`

v0.5.0 策略：

- 不从字符串 trace summary 中脆弱解析 memory refs。
- 不把 retrieval hits 当作 source memory refs。
- 如果已有结构化 MTP trace 能稳定解析出 memory id / alias，可 best-effort 写入；否则留空。
- 后续版本再引入正式 `MemoryUsageRef` / `MemoryInputRef` 解析器。

### 5.8 Retrieval lifecycle 边界

Retrieval 不写独立 artifact。v0.5.0 只补齐 request id、timeout、RuntimeEvent 与 lifecycle 事件边界。

处理原则：

- `RetrievalFamiliar.retrieve_async()` 增加 request id，便于运行时观测和日志关联。
- 检索命中继续调用 lifecycle hit/citation 机制维护 vitality，不进入 ArtifactStore。
- 普通 retrieval hits 不进入 `MemoryCreationArtifact.source_memory_refs`。
- 只有 Agent 运行时真实 MTP 访问过的 memory，未来才有资格成为 source memory ref。

### 5.9 Patchouli 内部集成点

v0.5.0 的 artifact 集成点应位于 Patchouli generation 链路内部：

```text
MemoryGenerationTaskController
  -> build GenerationRequest / infer source_intent
  -> MemoryGenerationEngine.process()
      -> _draft_to_memory()
      -> MemoryArtifactGenerator.build_for_create()
      -> ArtifactStore.put(...)
      -> refs/provenance 写入 MemoryAtom
      -> _save_memory(memory)
```

UPDATE / MERGE：

```text
MemoryGenerationEngine._apply_update()
  -> memory_before snapshot
  -> merge/update content
  -> MemoryArtifactGenerator.build_for_update()
  -> ArtifactStore.put(...)
  -> full_history/provenance 写入
  -> _save_memory(memory_after)
```

`ChatApplicationService`、`PreparedAgentRun`、`InteractionPayload` 只保持现有职责，不承担 artifact 构建入口。

## 6. Async Cold Path 规划

### 6.1 当前边界

当前链路已经是 async 函数形态，但内部仍有几类同步核心：

- `MemoryGenerationEngine.process()` 是同步接口，内部调用 extractor / deduplicator / storage。
- `RetrievalFamiliar.retrieve_async()` 用 `asyncio.to_thread(self.retrieve, ...)` 包同步检索。
- `QdrantMemoryStore` 是同步 client。
- MemoryGenerationTaskController 直接 `asyncio.create_task()`，没有 queue/backpressure。

v0.5.0 不要求一次性替换所有同步底层，但要建立统一 async cold path contract。

### 6.2 ColdPathTaskRunner

新增通用 runner，建议位置：

```text
src/hivememory/system/runtime/tasks/
  runner.py
  models.py
```

职责：

- 并发限制。
- queue。
- timeout。
- retry。
- cancellation。
- RuntimeEvent 发布。

接口：

```python
class ColdPathTaskRunner:
    async def submit(
        self,
        task_type: str,
        coro_factory: Callable[[CancellationToken], Awaitable[Any]],
        *,
        task_id: str,
        timeout_seconds: float | None = None,
        max_retries: int = 0,
    ) -> TaskHandle: ...
```

第一版可只接管 memory generation task；retrieval job 可以先采用同一 envelope，但不强制排队。

### 6.3 MemoryGenerationTaskController 接入 runner

当前 `_create_and_run_task()` 直接 `asyncio.create_task()`。

v0.5.0 改为：

```python
handle = await runner.submit(
    "memory_generation",
    lambda token: coro_factory(memory_task, token),
    task_id=memory_task.task_id,
    timeout_seconds=config.memory_generation.timeout_seconds,
)
memory_task.attach_handle(handle)
```

新增行为：

- 达到并发上限时 task 留在 `PENDING` / `QUEUED`。
- 开始执行时进入 `RUNNING`。
- cancel 会取消 queue 中任务或正在运行任务。
- timeout 进入 failed 或 cancelled，按配置决定。

### 6.4 RetrievalRequestEnvelope

检索是 hot path，但目前 prepare 阶段会阻塞用户首 token，因此至少要有 request envelope 与超时。

```python
class RetrievalRequestEnvelope(BaseModel):
    request_id: str
    mode: str = "active"
    request: RetrievalRequest
    timeout_seconds: float = 10.0
    record_lifecycle_events: bool = True
```

`PatchouliService.retrieve_for_gaze()` 目标：

- 创建 request id。
- 发布 `retrieval.request.started/status/completed/failed` RuntimeEvent。
- 超时返回空 `RetrievalResponse` 或失败，按配置决定。
- 对命中的 memory 记录 lifecycle hit；对 Agent 明确引用的 memory 记录 citation。
- 如果后续触发记忆生成，source memory refs 仅在已有结构化 MTP trace 可稳定解析时 best-effort 写入。

RuntimeEventType 可扩展：

```python
RETRIEVAL_REQUEST_STARTED = "retrieval.request.started"
RETRIEVAL_REQUEST_COMPLETED = "retrieval.request.completed"
RETRIEVAL_REQUEST_FAILED = "retrieval.request.failed"
```

### 6.5 Bus contract 收敛

当前 GlobalSystemBus routes 是字符串 + 任意参数。v0.5.0 不需要完全重写 bus，但新 cold path route 应优先使用 envelope。

建议新增或迁移：

| Route | 输入 | 输出 |
| :--- | :--- | :--- |
| `patchouli.public.memory.retrieve.v2` | `RetrievalRequestEnvelope` | `RetrievalResponseEnvelope` |
| `patchouli.public.memory.generation.submit` | `MemoryGenerationTaskSpec` | `MemoryGenerationTask` |
| `patchouli.public.artifact.get` | `artifact_id` | `dict` |

旧 route 保留，内部适配到新 envelope。

## 8. 分阶段实施计划

### Phase 1: ArtifactStore 与数据模型

目标：建立 artifact/ref/provenance 的领域模型和本地存储。

任务：

1. 新增 `ArtifactType`、`ArtifactRef`、`BaseArtifact` 与派生 artifact models。
2. 扩展 `Artifacts`，增加 `refs`、`provenance`、`cold_archive`、`revival_keys`。
3. 实现 `FilesystemArtifactStore`。
4. 增加配置项 `artifacts.enabled/root_dir`。
5. 写入/读取/hash 校验测试。

验收：

- 可以写入并读取 JSON artifact。
- `ArtifactRef.sha256` 能校验内容。
- `MemoryAtom` 旧 payload 仍能反序列化。

### Phase 2: Memory-bound interaction artifact

目标：memory 创建成功后产生与 MemoryAtom 绑定的原始交互冷备份。

任务：

1. 新增 `MemoryArtifactGenerator`。
2. 将 generator 接入 `MemoryGenerationEngine` CREATE 链路。
3. 被动 ARCHIVE 链路创建 memory 成功后写 `InteractionArtifact`。
4. 主动 WRITE 链路创建 memory 成功后写 `InteractionArtifact`。
5. cancelled / failed / discarded task 不写 interaction artifact。
6. 多个 memory atom 可共享同一个 topic buffer `InteractionArtifact`。

验收：

- 被动 ARCHIVE 创建的 memory 能指向 topic buffer `InteractionArtifact`。
- 主动 WRITE 创建的 memory 能指向 active context `InteractionArtifact`。
- cancelled/failed/discarded task 不产生 memory-bound interaction artifact。

### Phase 3: Memory creation 与 version artifact 写入

目标：MemoryAtom 首次创建与后续更新均能追溯来源。

任务：

1. `MemoryArtifactGenerator.build_for_create()` 生成 `MemoryCreationArtifact`。
2. CREATE 入库前将 interaction/creation refs 写入 MemoryAtom manifest。
3. `MemoryArtifactGenerator.build_for_update()` 生成 `MemoryVersionArtifact`。
4. UPDATE/MERGE 入库前将 version ref 写入 full_history / provenance。
5. TOUCH/DISCARD 不写 artifact，只保留 lifecycle/task runtime 状态。
6. `GenerationRequest` 暂不扩展 artifact/source memory 字段。

验收：

- MTP WRITE 生成的 memory 能指向 `InteractionArtifact`。
- ARCHIVE 生成的 memory 能指向 `MemoryCreationArtifact`。
- UPDATE 后 `full_history[-1]` 包含 source artifact refs。
- DISCARD 不创建 memory，也不产生 memory artifact。

### Phase 4: Async cold path runner

目标：memory generation 进入统一 queue/runner。

任务：

1. 新增 `ColdPathTaskRunner`。
2. MemoryGenerationTaskController 从 `asyncio.create_task()` 迁移到 runner。
3. 增加并发限制、timeout、cancel、retry 配置。
4. RuntimeEvent 增加 queued/running/timeout/retry 信息。
5. 保持 `/memory-tasks` API 兼容。

验收：

- 并发 memory tasks 不超过配置上限。
- queued task 可取消。
- timeout task 进入 failed，不产生 memory artifact。
- 现有 memory task 测试全部通过。

### Phase 5: Retrieval request envelope 与 lifecycle event

目标：检索链路有可追踪 request id、超时与 lifecycle 事件，不写独立 artifact。

任务：

1. 新增 `RetrievalRequestEnvelope`。
2. `retrieve_for_gaze()` 使用 request id 和 RuntimeEvent。
3. 检索命中继续记录 lifecycle hit/citation。
4. source memory refs 仅在已有结构化 MTP trace 可稳定解析时 best-effort 写入。
5. 旧 `PATCHOULI_MEMORY_RETRIEVE` route 保持兼容。

验收：

- 检索超时有明确 RuntimeEvent 和 fallback 行为。
- 普通 retrieval 不产生 artifact store 写入。
- 普通 retrieval hits 不进入 `MemoryCreationArtifact.source_memory_refs`。
- 已有结构化 MTP trace 可解析时，真实 MTP 访问过的 memory 可进入 source memory refs。

## 10. 兼容性与迁移策略

### 10.1 MemoryAtom 兼容

- `Artifacts` 新增字段必须有 default factory。
- 旧 Qdrant payload 反序列化不应失败。
- `to_qdrant_payload()` 保持原格式，只是 payload 中多新字段。

### 10.2 API 兼容

- `/chat` SSE 原事件不删除。
- `/memory-tasks` 原字段不删除，只追加 artifact/provenance 字段。
- 新 `/artifacts` API 独立增加。
- 旧 GlobalSystemBus route 保留。

### 10.3 存储兼容

- ArtifactStore 默认本地文件系统。
- 如果 artifacts disabled，系统回退到 v0.4.0 行为。
- artifact 写失败不应导致主对话失败，但应影响 provenance 状态。

### 10.4 隐私与体积

Raw transcript 可能包含敏感数据。默认策略：

- 本地部署默认启用。
- 支持配置关闭 raw artifact。
- 支持最大 artifact size。
- 支持 future redaction hook，但 v0.5.0 不实现复杂脱敏。

## 11. 风险与决策点

### 11.1 Artifact 是否存 Qdrant

不建议把 raw transcript 大对象直接塞 Qdrant payload。

原因：

- Qdrant payload 应服务检索和轻量 metadata。
- 大 JSON 会增加 payload IO 与备份成本。
- raw transcript 不应参与向量检索。

建议采用本地 `ArtifactStore`，MemoryAtom 只保存 refs。

### 11.2 RuntimeEvent 是否全部持久化

v0.5.0 不持久化全部 RuntimeEvent。

原因：

- event 数量大，且很多只是瞬时状态。
- 真正需要长期追溯的是 MemoryAtom 的来源、创建输入、外源文档与版本快照；run/task outcome 属于运行时记录。

策略：

- RuntimeEvent 继续 ring buffer。
- MemoryAtom 创建/更新成功后的长期证据写 artifact。
- memory task 结果继续留在运行时状态或未来 TaskRecord。

### 11.3 Retrieval 是 hot path 还是 cold path

用户输入前的 retrieval 属于 hot path，因为它影响首 token 延迟；v0.5.0 不把检索结果归档为 artifact，只保留运行时事件、timeout/fallback 和 lifecycle hit/citation。

v0.5.0 策略：

- 检索请求本身保留同步等待，但有 timeout/fallback。
- 检索命中继续服务 vitality 维护，不进入 ArtifactStore。
- 普通检索上下文不写入 `MemoryCreationArtifact.source_memory_refs`；只有结构化 MTP trace 可稳定解析时才 best-effort 写入。
- vitality refresh 可以继续异步化/降级。

### 11.4 GenerationEngine 是否改为 async

短期不强制把 `MemoryGenerationEngine.process()` 改成 async。

策略：

- 由 task runner 统一包裹同步或异步 callable。
- 后续若 extractor/storage 全部 async，再将 process 改为 async。

## 12. v0.5.0 Done Definition

v0.5.0 可以发布的最低标准：

1. ArtifactStore v1 可写入/读取/校验 JSON artifact。
2. `ArtifactType`、`BaseArtifact`、`ArtifactRef`、派生 artifact models 落地。
3. memory 创建成功后生成与该 MemoryAtom 绑定的 `InteractionArtifact`。
4. cancelled/failed/discarded task 不产生 memory-bound artifact。
5. `MemoryCreationArtifact` 保存创建时的 generation view、source intent、source artifact refs 与 source memory refs。
6. `DocumentArtifact` 模型落地，MemoryAtom 可保存外源文档 artifact ref。
7. MTP WRITE 创建的 MemoryAtom 带 refs/provenance。
8. MTP UPDATE 的 `full_history` 带 source artifact metadata。
9. `MemoryVersionArtifact` 保存 UPDATE/MERGE/MANUAL_EDIT 的版本快照。
10. memory task API 保留运行时状态，不暴露 outcome artifact。
11. Memory generation 由统一 runner 管理并发、取消、timeout。
12. Retrieval request envelope、RuntimeEvent 与 lifecycle hit/citation 行为可验证。
13. `MemoryArchiveArtifact` / `revival_keys` 字段预留完成，不要求实现自动复活。
14. 旧数据、旧 API、旧 bus route 保持兼容。
15. 关键行为有自动化测试覆盖。

## 13. 建议提交顺序

1. `ArtifactType` / `BaseArtifact` / `ArtifactRef` / 派生 artifact models。
2. `FilesystemArtifactStore` 与配置。
3. `Artifacts` 模型扩展与兼容测试。
4. `MemoryArtifactGenerator` 写 interaction / creation / version artifacts。
5. `MemoryGenerationEngine` CREATE 链路接入 artifact generator。
6. `MemoryGenerationEngine` UPDATE/MERGE 链路接入 version artifact。
7. MemoryAtom refs / provenance 写入与兼容测试。
8. MTP trace source memory refs 暂缓或 best-effort 解析。
9. `/artifacts` API 与 `/memory-tasks` 响应扩展。
10. `ColdPathTaskRunner`。
11. memory generation task runner 迁移。
12. retrieval request envelope 与 lifecycle event。
13. 测试补齐与文档更新。

该顺序先建立可落盘的数据模型，再在 Patchouli generation 内部接入 artifact 构建，最后处理调度与检索异步化。这样 artifact 始终围绕 MemoryAtom 生命周期生成，不与 chat runtime 噪声耦合。
