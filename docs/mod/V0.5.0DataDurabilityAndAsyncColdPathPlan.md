# v0.5.0 Data Durability 与 Async Cold Path 实现规划

**文档状态**: Draft
**适用范围**: `core/models/memory.py`、`core/protocol/models.py`、`prompts/transcript/`、`patchouli/service.py`、`patchouli/services/librarian.py`、`patchouli/services/memory_generation_tasks.py`、`patchouli/services/retrieval.py`、`system/runtime/bus/`、`system/runtime/scheduler/`、`infrastructure/storage/`、`engines/generation/`、`engines/retrieval/`
**核心目标**: 建立 artifact 数据模型与本地存储，把原始对话片段、外源文档来源、MemoryAtom 首次创建输入、版本快照和 L3 冷存储复活线索沉淀为长期证据；同时收敛 generation/retrieval 的异步冷路径契约，为后续 MTP READ/RUN、多智能体编排与记忆 split/merge 提供稳定数据底座。

## 1. 版本定位

v0.4.0 已经把运行时控制面基本拉起来：

- `ChatApplicationService` 已有 `ChatGenerationRunRegistry`、结构化 cancel result、`generation_id` 注入、取消后跳过 finalize。
- `RuntimeEvent` / `RuntimeEventBus` / `/runtime-events/stream` 已经存在。
- `MemoryGenerationTask` / `MemoryGenerationTaskController` / `/memory-tasks` API 已经存在。
- `run_active_generation()` 已从 finalize 的纯同步子过程，升级为创建可查询、可取消、可观测的后台 memory task。
- `AsyncMaintenanceScheduler` / `GlobalMaintenanceScheduler` 已提供纯 asyncio 定时维护基础。

因此 v0.5.0 需要解决另一个更底层的问题：

> 系统中的每条长期记忆，是否能稳定追溯到它创建时依据的原始对话/话题片段、外源文档来源、生成输入视图、后续版本变更，以及未来从 L3 冷存储中被唤起所需的 alias / revival keys。

v0.5.0 的主题可以概括为：

> 将 artifact 从 `MemoryAtom.payload.artifacts` 中的杂项存根，升级为以 `ArtifactRef` 绑定到 MemoryAtom 的长期解释项体系。

后续版本依赖关系：

| 后续能力 | 为什么依赖 v0.5.0 |
| :--- | :--- |
| System Gateway 与复合意图拆分 | 一个输入拆成多个记忆意图后，需要每个 MemoryAtom 都能通过 creation artifact 追溯 raw interaction、创建输入和来源 artifact |
| MTP READ 历史版本编译 | READ 需要读取版本快照、创建输入、外源文档引用，而不是只读 `payload.content` |
| MTP RUN executable asset | executable asset 必须能追溯原始来源、构建输入和版本快照 |
| Alice Phase 3 多智能体编排 | 多 Agent 产物需要把最终沉淀出的 MemoryAtom 与其原始对话、文档来源、创建输入关联 |
| 记忆分裂与合并 | split/merge 必须能回溯原始对话、版本 artifact 和来源文档，否则无法安全回滚 |
| L3 冷存储复活 | 已归档记忆需要 alias、alias history、revival keys 与 archive artifact，才能在未来被 Agent 重新唤起 |

## 2. 当前状态调研

### 2.1 已有基础

#### 2.1.1 MemoryAtom 已有 artifacts 层

`MemoryAtom` 采用冰山模型：

- `meta`: 生命周期、身份、权限、版本。
- `index`: 检索摘要与 alias。
- `payload`: 注入上下文的核心内容。
- `payload.artifacts`: 原始存根、历史、agent config。

当前 `Artifacts` 已有字段：

- `raw_source_url`
- `file_path`
- `context_ref`
- `full_history`
- `agent_config`

这说明“原始数据层”在模型概念上已经存在，但还没有面向 chat run / memory task / transcript 的正式 artifact schema。

#### 2.1.2 Transcript 已经分为双视图

当前已有：

- `HistoryTranscriptBuilder`: 用 `LogicalBlock.turn_events` 重放历史消息视图。
- `GenerationTranscriptBuilder`: 用 `LogicalBlock` 生成适合记忆提取的 `GenerationContext`。
- `InteractionPayload`: 承载 `user_message`、`assistant_final_text`、`turn_events`、`mtp_traces`、`materialize_tasks`。

这意味着 v0.5.0 不需要再发明 transcript 主链路，而是需要把“原始事实 + 双视图产物 + metadata”保存为可引用 artifact。

#### 2.1.3 RuntimeEvent 与 memory task 已落地

当前 RuntimeEvent 类型包括：

- `chat.run.*`
- `agent.run.*`
- `memory.task.*`
- `event.stream.gap`

`MemoryGenerationTask` 已包含：

- `task_id`
- `topic_id`
- `label`
- `source`
- `pending_alias`
- `status`
- `canonical_alias`
- `error`
- `created_at` / `started_at` / `finished_at`
- `cancel_event`

这为 v0.5.0 提供了可绑定 provenance 的运行时 id。

#### 2.1.4 异步总线与调度器存在

当前已有：

- `AsyncSystemBus`: async RPC + async pub/sub。
- `GlobalSystemBus` / `PatchouliBus` / `AliceBus`。
- `PatchouliBridge` 已把 public routes 挂到全局总线。
- `AsyncMaintenanceScheduler` 已提供纯 asyncio 维护任务调度。
- `RetrievalFamiliar.retrieve_async()` 目前通过 `asyncio.to_thread()` 包裹同步检索。

这说明“总线入口异步化”已经开始，但还没有形成统一 job/request contract，也没有把 cold path 的耐久化、重试、backpressure 收束起来。

### 2.2 当前缺口

| 缺口 | 现象 | v0.5.0 处理方式 |
| :--- | :--- | :--- |
| Raw interaction 没有持久化 artifact | 长期记忆只保存提取后的 payload，原始话题对话、工具调用与执行细节丢失 | 新增 `InteractionArtifact`，保存话题原始交互 |
| MemoryAtom 与生成任务缺少稳定 provenance | 只能从 alias/task/log 推断来源 | 新增轻量 `MemoryProvenance` 并写入 artifact manifest |
| 记忆生成链路没有 artifact 构建点 | creation/version artifact 不能从 chat runtime 旁路生成，必须与 MemoryAtom 创建/更新同步 | 在 `MemoryGenerationEngine` 附近新增 `MemoryArtifactGenerator` |
| Retrieval async 只是 to_thread 包装同步链路 | 缺少超时、取消、重试、事件状态 | 定义 `RetrievalJob` / request envelope 或至少统一 bus contract |
| Artifact 存储没有独立抽象 | 只能塞进 Qdrant payload，可能污染向量 payload 或造成大对象膨胀 | 新增 `ArtifactStore`，MemoryAtom 只保存 refs |

## 3. 本期目标与非目标

### 3.1 目标

1. **原话题交互全量冷保存**
   - 对进入长期记忆生成候选范围的原始话题交互批次，保存或关联一份 `InteractionArtifact`。
   - `InteractionArtifact` 只保存原始对话/话题数据，不携带 memory 创建、更新、去重或生成链路语义。
   - `InteractionArtifact` 作为 MemoryAtom 的额外解释项存在，绑定关系由 `MemoryAtom.payload.artifacts.refs` 或 `MemoryCreationArtifact.source_artifacts` 中的 `ArtifactRef` 表达，而不是把归属 memory 信息写进 artifact 数据体。

2. **raw / history / generation 视图分层**
   - `InteractionArtifact` 只保存 raw topic interaction：`LogicalBlock.turn` 中的原始对话、`turn_events`、actions、semantic traces。
   - history view 由 `HistoryTranscriptBuilder` 从 raw interaction 回放，不作为 `InteractionArtifact` 的独立字段。
   - generation view 由 `GenerationTranscriptBuilder` 生成，并保存在 `MemoryCreationArtifact`。
   - 明确三者不是同一个东西，避免后续继续用字符串互相逆推。

3. **MemoryAtom provenance**
   - 新建/更新/合并/触碰/丢弃的 generation result 均能指向来源 artifact。
   - `MemoryAtom.payload.artifacts` 不直接塞大块 raw transcript，而保存稳定 artifact refs。
   - `full_history` 中的每次版本变更附带来源 artifact/task/run。

4. **ArtifactStore v1**
   - 提供轻量本地 artifact store 抽象。
   - 支持 JSON artifact 写入、读取、hash 校验、按 id 查询。
   - 第一版可以使用本地文件系统，后续再替换为数据库或对象存储。

5. **Generation / Retrieval cold path async-native**
   - 把 generation task 和 retrieval request 的运行状态、超时、取消、重试、事件发布收敛为统一契约。
   - Retrieval 不再只是“同步函数外包一层 `to_thread`”，而有明确 request id、timeout、RuntimeEvent、failure policy。
   - Generation task 从“fire background task”升级为由 task runner / queue 统一调度。

6. **可重放与回归测试**
   - 给定 `InteractionArtifact`，可以找回某个话题批次的原始对话、工具调用与执行轨迹。
   - 给定 memory atom，可以通过 creation artifact 找到 raw interaction artifact、创建输入、外源文档与版本 artifact。
   - 保证取消 run 默认不污染长期记忆，但可保存 debug/raw artifact。

### 3.2 非目标

本期不做以下工作：

- 不实现 Gateway 上移。
- 不实现复合意图识别。
- 不实现 MTP READ 历史编译的最终渲染，只为它准备数据。
- 不实现 MTP RUN executable asset，只准备 artifact/provenance 结构。
- 不实现记忆 split/merge 行为，只预留 provenance source type。
- 不持久化完整 RuntimeEvent 流；只持久化关键 run/task/artifact outcome。
- 不把 Qdrant 替换为新的主存储。

## 4. 目标数据模型

### 4.1 Artifact 设计原则

v0.5.0 引入新的 artifact 体系，但不把它设计成“任意 JSON 袋子”。Artifact 的职责是保存不应该进入 `MemoryAtom.payload.content` 的证据、来源、运行快照与冷资产；`MemoryAtom.payload.artifacts` 只保存简洁 manifest。

```text
MemoryAtom.index
  -> 可检索摘要、标签、alias

MemoryAtom.payload
  -> 可注入上下文的核心内容

MemoryAtom.payload.artifacts
  -> refs + provenance + cold archive hint

ArtifactStore
  -> InteractionArtifact
  -> DocumentArtifact
  -> MemoryCreationArtifact
  -> MemoryVersionArtifact
```

原则：

- 只维护一个顶层枚举 `ArtifactType` 分类，表达 artifact 自身是什么类型。
- `ArtifactType` 和 MemoryAtom 的关系由 `MemoryArtifactManifest` 的字段位置和 `MemoryProvenance` 表达。
- `ArtifactRef` 只有一种，不为不同 artifact 类型创建专用 ref。
- 所有 artifact 都是 `MemoryAtom` 的长期解释项，不作为独立运行时日志体系存在；严格绑定关系由 `MemoryAtom.payload.artifacts.refs` / `MemoryProvenance.source_artifacts` 等 `ArtifactRef` 持有。
- 派生 artifact 数据体只保存自身类型的纯数据，不反向内嵌归属它的 `MemoryAtom`，除非该 artifact 类型本身就是 creation/version/archive 等 memory 生命周期记录。
- `BaseArtifact` 只放所有 artifact 共用的元信息；派生类必须声明自己的结构，不使用无边界 `payload: dict[str, Any]` 作为主模型。
- `MemoryArtifactManifest` 保持轻量，不为了适配所有 artifact 类型而创建大量特化字段。

### 4.2 ArtifactType 与 ArtifactRef

建议新增 `core/models/artifact.py`。

```python
class ArtifactType(str, Enum):
    INTERACTION = "interaction"
    DOCUMENT = "document"
    MEMORY_CREATION = "memory_creation"
    MEMORY_VERSION = "memory_version"


class ArtifactRef(BaseModel):
    artifact_id: str
    artifact_type: ArtifactType
    uri: str | None = None
    sha256: str | None = None
    created_at: datetime | None = None
    summary: str | None = None
```

`ArtifactRef` 是轻引用，只解决“在哪里、是什么、如何快速识别”。不要在 ref 上挂载复杂业务语义；需要业务语义时读取对应 artifact 或 provenance。

### 4.3 BaseArtifact

```python
class BaseArtifact(BaseModel):
    artifact_id: str
    artifact_type: ArtifactType
    schema_version: str = "v1"

    created_at: datetime           # artifact 写入时间，写入后不再更新

    owner_user_id: str
    owner_agent_id: str | None = None

    title: str | None = None
    summary: str | None = None
    content_hash: str | None = None
```

`BaseArtifact` 不提供大而全的 `payload` 字段。各派生 artifact 自己声明数据结构，保证模型边界清晰。

所有 artifact 写入后不再修改（append-only）。`updated_at` 字段与此原则矛盾，不提供。若派生类型确实需要记录变更时间（如 `DocumentArtifact` 的 `retrieved_at`），由派生类自行声明。

### 4.4 InteractionArtifact

`InteractionArtifact` 保存某个 topic 范围内的原始交互冷备份。它不是一次 memory 生成日志，也不是单条 message 记录。

`InteractionArtifact` 不允许携带任何记忆生成相关信息或归属 memory 信息：

- 不保存 `memory_id`、`memory_alias`。
- 不保存 `source_intent`、`source_mode`、`capture_policy`。
- 不保存 `GenerationContext`、`WriteFocus`、`UpdateFocus` 或 extractor/dedup/update 结果。
- 不从 `GenerationContext.turns` 反推原始消息；`GenerationContext` 是给记忆生成使用的视图，已经丢弃或改写了部分工具调用细节。

```python
class InteractionTurnSnapshot(BaseModel):
    block_id: str
    turn_id: str
    created_at: float | None = None

    user_id: str = ""
    agent_id: str = ""
    team_id: str | None = None

    user_query: str = ""
    rewritten_query: str | None = None
    assistant_final_text: str = ""

    turn_events: list[dict[str, Any]] = Field(default_factory=list)
    actions: list[dict[str, Any]] = Field(default_factory=list)
    semantic_traces: list[dict[str, Any]] = Field(default_factory=list)


class InteractionArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.INTERACTION] = ArtifactType.INTERACTION

    topic_id: str
    topic_title: str = ""
    topic_summary: str = ""

    turns: list[InteractionTurnSnapshot] = Field(default_factory=list)
    captured_at: datetime
```

字段边界：

- `topic_id` 是 artifact 的主题边界标识。
- `topic_title` / `topic_summary` 是面向用户与前端展示的 topic metadata，尤其用于记录新建话题时的标题和摘要。
- `topic_summary` 不等同于 `state_summary`。前者是相对稳定的展示摘要，本阶段不因上下文压缩而修改；后者是 Patchouli 为维护长上下文而生成的可变压缩状态，会随着对话推进与折叠更新。
- `turns` 来自 `LogicalBlock.turn` 的快照，而不是来自 `GenerationContext`。

关于原始对话数据的存储形式：

- `LogicalBlock.turn` 是当前完整 interaction 历史的来源，包含 `turn_events`、agent actions、semantic traces 等原始链路信息。
- Artifact 不应直接长期依赖运行时 DTO 的完整对象结构，因此推荐新增 `InteractionTurnSnapshot` 作为稳定 artifact schema。
- `InteractionTurnSnapshot` 可以保留核心索引字段，并将 `turn_events` / `actions` / `semantic_traces` 以 JSON dict snapshot 形式保存，避免未来运行时模型小幅重构破坏历史 artifact 读取。

### 4.5 DocumentArtifact

`DocumentArtifact` 面向外源文档的信息易逝性问题。长期记忆的 `payload.content` 往往只是文档摘要或大纲，真实来源必须通过 document artifact 可追踪。

```python
class DocumentLocator(BaseModel):
    page: int | None = None
    heading_path: list[str] = Field(default_factory=list)
    section: str | None = None
    line_start: int | None = None
    line_end: int | None = None
    char_start: int | None = None
    char_end: int | None = None
    quote: str | None = None


class DocumentArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.DOCUMENT] = ArtifactType.DOCUMENT

    source_type: Literal["url", "file", "pdf", "markdown", "html", "repo", "unknown"]
    source_uri: str | None = None
    canonical_uri: str | None = None
    mime_type: str | None = None

    retrieved_at: datetime | None = None
    etag: str | None = None
    last_modified: str | None = None
    content_hash: str | None = None

    locators: list[DocumentLocator] = Field(default_factory=list)
    snapshot_uri: str | None = None       # 原始内容快照的物理存储地址
    snapshot_hash: str | None = None      # 快照内容的 sha256，用于完整性校验
    extracted_text_uri: str | None = None # 提取后纯文本的物理存储地址
```

`DocumentArtifact` 是**引用时刻的引用快照**（point-in-time citation）：记录”创建/更新记忆时，在 URI X 处看到了内容 hash 为 H 的文档”。写入后不可变；文档移动或内容变更时，下次使用该文档触发记忆更新时创建新的 `DocumentArtifact`，历史记录保持不变。

同一次生成批次中多条记忆引用同一份文档时，它们可以共享同一个 `DocumentArtifact`（以 `source_uri + content_hash + retrieved_at` 同时间窗口内去重）。`ArtifactRef` 的 N:1 关系由此产生，与 `InteractionArtifact` 的 per-topic-batch 1:N 关系方向相反。

v0.5.0 不实现完整文档解析，但模型必须允许未来记录”这条记忆来自某个 URL/PDF/Markdown 的哪一页、哪一节、哪一段”。

### 4.6 MemoryCreationArtifact

`MemoryCreationArtifact` 的语义是 **genesis provenance**：回答"这条记忆为何存在、从何而来、当时看到了什么输入"。它只在记忆原子创建成功后生成，且一旦写入不再更新。

`memory_alias`、`created_title`、`created_tags` 等可变字段**不**保存在此处——它们属于记忆原子的初始可变状态，由 `MemoryVersionArtifact`(v1) 的 `snapshot_after` 负责记录。`MemoryCreationArtifact` 通过 `initial_version_ref` 指向 v1，构成完整的创建记录入口。

```python
class MemoryInputRef(BaseModel):
    memory_id: str
    alias: str | None = None
    title: str | None = None
    version: int | None = None
    used_as: Literal["context", "citation", "update_target"] = "context"


class MemoryCreationArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.MEMORY_CREATION] = ArtifactType.MEMORY_CREATION

    memory_id: str
    source_intent: Literal["ARCHIVE", "WRITE", "IMPORT", "MANUAL", "SYSTEM"]

    generation_view: dict[str, Any]           # GenerationContext.model_dump()
    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    source_memory_refs: list[MemoryInputRef] = Field(default_factory=list)

    initial_version_ref: ArtifactRef          # 指向 MemoryVersionArtifact(v1)
```

### 4.7 MemoryVersionArtifact

`MemoryVersionArtifact` 是记忆原子的 **完整状态快照链**，语义类似 git commit。每次创建或更新均产生一个版本条目，`version_number` 单调递增。v1（`update_source="CREATE"`）对应初始创建状态，`snapshot_before=None`；后续更新的 `snapshot_before` 保存变更前的完整状态，`snapshot_after` 保存变更后的完整状态。

`snapshot_after` 包含所有可变字段的完整快照，保证任意版本可独立重建，无需重放 delta 链；这也是未来记忆 split/merge 安全回滚的基础。

`MemoryVersionArtifact` 的 `source_artifacts` 引用触发本次版本变更的 `InteractionArtifact`。InteractionArtifact 以 topic batch 为单位独立存在，天然只增不改；每次更新对应一个新的 topic 交互批次，因此 `source_artifacts` 引用不同的 interaction ref，无需复制 interaction 数据。

```python
class MemoryVersionSnapshot(BaseModel):
    """记忆原子某一版本下所有可变字段的完整快照。"""
    content: str
    alias: str | None = None
    title: str | None = None
    summary: str | None = None
    tags: list[str] = Field(default_factory=list)
    memory_type: str | None = None


class MemoryVersionArtifact(BaseArtifact):
    artifact_type: Literal[ArtifactType.MEMORY_VERSION] = ArtifactType.MEMORY_VERSION

    memory_id: str
    version_number: int                        # 单调递增；v1 = 初始创建状态
    update_source: Literal["CREATE", "UPDATE", "MERGE", "MANUAL_EDIT", "SYSTEM_REWRITE"]

    snapshot_before: MemoryVersionSnapshot | None   # v1 时为 None
    snapshot_after: MemoryVersionSnapshot           # 该版本的完整状态
    changelog: str | None = None

    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    source_memory_refs: list[MemoryInputRef] = Field(default_factory=list)
    changed_at: datetime
```

### 4.8 归档复活锚点

`MemoryArchiveArtifact` 不作为独立 Artifact 类型存在。归档事件的元数据分散到以下现有字段，由它们联合构成未来复活机制的数据基础：

- `Artifacts.cold_archive`（`ArtifactRef`）：`uri` 字段记录物理存储位置，`sha256` 用于完整性校验。
- `Artifacts.revival_keys`：可被未来检索系统命中的关键词列表，是复活查找的入口。
- `MemoryProvenance(action="archived").vitality`：归档时刻的生命值快照，用于复活后恢复衰减基线。
- 最新 `MemoryVersionArtifact.snapshot_after`：归档前记忆原子的完整可变字段状态，复活时直接还原。

归档复活查找链：

```text
revival_key → Artifacts.revival_keys 命中 MemoryAtom
  → Artifacts.cold_archive (ArtifactRef.uri) 定位物理存储
  → 最新 MemoryVersionArtifact.snapshot_after 恢复完整状态
  → MemoryProvenance(action="archived").vitality 恢复生命值
```

v0.5.0 不实现自动复活，但上述字段必须在归档时正确写入，以保证未来复活机制可以无需修改数据模型地接入。

### 4.9 MemoryArtifactManifest 与 MemoryProvenance

`MemoryAtom.payload.artifacts` 应升级为 manifest，但保持简洁：

```python
class MemoryProvenance(BaseModel):
    action: Literal[
        "created",
        "updated",
        "merged",
        "touched",
        "archived",
        "resurrected",
        "manual_edit",
        "future_split",
        "future_merge",
    ]
    at: datetime
    source_intent: Literal["ARCHIVE", "WRITE", "UPDATE", "IMPORT", "MANUAL", "SYSTEM"] | None = None
    source_artifacts: list[ArtifactRef] = Field(default_factory=list)
    vitality: float | None = None   # 归档、触碰等生命周期事件时记录当前生命值
    note: str | None = None


class Artifacts(BaseModel):
    # 兼容旧字段，v0.5.0 不删除
    raw_source_url: Optional[str] = None
    file_path: Optional[str] = None
    context_ref: list[dict[str, str]] = Field(default_factory=list)
    full_history: list[dict[str, Any]] = Field(default_factory=list)  # 向后兼容过渡字段，未来以 MemoryVersionArtifact 链为唯一版本真相
    agent_config: Optional[dict[str, Any]] = None

    # 新 manifest 字段
    refs: list[ArtifactRef] = Field(default_factory=list)
    provenance: list[MemoryProvenance] = Field(default_factory=list)
    cold_archive_uri: str | None = None       # 归档物理存储地址（文件路径或对象存储 URI）
    cold_archive_hash: str | None = None      # 归档内容 sha256，用于完整性校验
    revival_keys: list[str] = Field(default_factory=list)
```

迁移原则：

- 旧字段不删除，保证旧 Qdrant payload 仍能反序列化。
- 新代码优先写 `refs/provenance/cold_archive_uri/cold_archive_hash/revival_keys`。
- `raw_source_url` / `file_path` 后续可迁移为 `DocumentArtifact`，但 v0.5.0 只做兼容保留。
- `context_ref` 可继续兼容旧 `{session_id, msg_id}`，新链路优先使用 `InteractionArtifact`。
- `full_history` 是向后兼容过渡字段，v0.5.0 在每条 item 里追加 `artifact_refs`；后续版本以 `MemoryVersionArtifact` 链为唯一版本真相，`full_history` 将逐步废弃。

### 5.2 非入口：不扩展 chat / agent runtime 协议

v0.5.0 不扩展 `InteractionPayload`、`PreparedAgentRun` 或 chat/agent runtime 协议来承载 artifact refs。

原因：

- artifact 的长期语义属于 Patchouli 内部：raw interaction 属于 topic/perception 边界，creation/version 属于 memory generation 边界。
- chat run / agent run 中的大部分字段是运行时噪声，不应提前进入 artifact 体系。
- 真实 raw interaction 应从 `LogicalBlock.turn` 快照构建，不应从外围 run metadata 或 `GenerationContext` 反推。
- 真实参与记忆创建的 generation view 由 generation 输入决定，不应从外围 run metadata 推断。
- 真实使用过的历史记忆通常来自 Agent 运行时 MTP 访问轨迹，而不是普通 retrieval 命中结果。

因此，artifact 构建入口应位于 Patchouli 子系统内部，而不是位于 `system/application` 层。v0.5.0 拆分两类构建器：

- `InteractionArtifactBuilder`: 从 `topic_id`、topic display metadata 与 `LogicalBlock[]` 构建 raw interaction artifact。
- `MemoryArtifactGenerator`: 从 `MemoryAtom`、`GenerationContext`、source intent 与 source artifact refs 构建 creation/version artifact。

### 5.3 ArtifactEngine

各 artifact 类型的构建逻辑各自独立，但它们共享同一个 `ArtifactStore` 实例，且在部分链路中需要协同写入。因此引入 `ArtifactEngine` 作为统一的组合容器：它不试图统一各 builder 的输入接口（各类型输入字段差异过大，强行统一会退化为无边界参数包），而是提供单一的依赖注入点，并承载横切关注点（错误策略、指标上报等）。

模块建议位置：

```text
src/hivememory/engines/artifacts/
  __init__.py
  engine.py       # ArtifactEngine 容器
  interaction.py  # InteractionArtifactBuilder
  document.py     # DocumentArtifactBuilder
  memory.py       # MemoryArtifactBuilder
```

#### ArtifactEngine

```python
class ArtifactEngine:
    def __init__(self, store: ArtifactStore) -> None:
        self.interaction = InteractionArtifactBuilder(store)
        self.document = DocumentArtifactBuilder(store)
        self.memory = MemoryArtifactBuilder(store)
```

`ArtifactEngine` 是极薄的组合根，不包含业务逻辑。调用方只需注入一个 `ArtifactEngine`，无需分别管理三个独立 builder 的生命周期。

#### InteractionArtifactBuilder

职责：从 `LogicalBlock[]` 构建 `InteractionArtifact` 并写入 ArtifactStore，返回 `ArtifactRef`。

约束：
- 只读取 `LogicalBlock.turn`，不读取 `GenerationContext`。
- 不写入 memory id、memory alias、source intent、capture policy 或 generation result。

```python
class InteractionArtifactBuilder:
    def __init__(self, store: ArtifactStore) -> None: ...

    async def build_and_store(
        self,
        *,
        topic_id: str,
        topic_title: str = "",
        topic_summary: str = "",
        blocks: Sequence[LogicalBlock],
    ) -> ArtifactRef: ...
```

#### DocumentArtifactBuilder

职责：从外源文档元数据构建 `DocumentArtifact` 并写入 ArtifactStore，返回 `ArtifactRef`。

同一次生成批次中多条记忆引用同一份文档时，以 `source_uri + content_hash` 在时间窗口内去重，避免重复写入。

```python
class DocumentArtifactBuilder:
    def __init__(self, store: ArtifactStore) -> None: ...

    async def build_and_store(
        self,
        *,
        source_type: str,
        source_uri: str | None,
        content_hash: str | None,
        retrieved_at: datetime,
        locators: list[DocumentLocator] | None = None,
        **kwargs,
    ) -> ArtifactRef: ...
```

#### MemoryArtifactGenerator

职责：处理 `MemoryAtom` 创建与更新时的 artifact 写入。

`build_for_create` 需原子地产出两个强关联 artifact：`MemoryVersionArtifact`(v1) 先写入，再将其 ref 写入 `MemoryCreationArtifact.initial_version_ref`，两者作为一个整体返回。调用方不应将这两步拆开单独调用。

```python
class MemoryCreationBundle(BaseModel):
    creation_ref: ArtifactRef
    initial_version_ref: ArtifactRef   # MemoryVersionArtifact v1


class MemoryArtifactGenerator:
    def __init__(self, store: ArtifactStore) -> None: ...

    async def build_for_create(
        self,
        *,
        memory: MemoryAtom,
        context: GenerationContext,
        source_intent: Literal["ARCHIVE", "WRITE", "IMPORT", "MANUAL", "SYSTEM"],
        source_artifact_refs: list[ArtifactRef],
        source_memory_refs: list[MemoryInputRef] | None = None,
    ) -> MemoryCreationBundle: ...

    async def build_for_update(
        self,
        *,
        memory_before: MemoryAtom,
        memory_after: MemoryAtom,
        update_source: Literal["UPDATE", "MERGE", "MANUAL_EDIT", "SYSTEM_REWRITE"],
        changelog: str | None = None,
        source_artifact_refs: list[ArtifactRef] | None = None,
        source_memory_refs: list[MemoryInputRef] | None = None,
    ) -> ArtifactRef: ...  # 返回 MemoryVersionArtifact ref
```

#### 注入模式

`ArtifactEngine` 在 Patchouli 子系统内统一注入，不跨越到 `system/application` 层：

```text
MemoryGenerationTaskController
  └── ArtifactEngine
        ├── .interaction  (perception 阶段：topic blocks → InteractionArtifact)
        ├── .document     (外源文档解析阶段，v0.5.0 暂不激活)
        └── .memory       (generation 阶段：CREATE/UPDATE → Creation+Version artifacts)
```

### 5.4 CREATE 链路 artifact 构建

CREATE 链路不从 `GenerationContext` 反向构建 `InteractionArtifact`。`InteractionArtifact` 在进入 generation 之前，基于同一批 topic `LogicalBlock` 构建并写入；CREATE 成功后通过 `ArtifactRef` 将其作为 MemoryAtom 的解释项关联起来，引用位置可以是 `MemoryAtom.payload.artifacts.refs`，也可以是 `MemoryCreationArtifact.source_artifacts`。

推荐顺序：

```text
1. Patchouli 取得 topic blocks / active topic context
2. InteractionArtifactBuilder 从 LogicalBlock.turn 构建 InteractionArtifact
3. ArtifactStore 写 InteractionArtifact，得到 interaction_ref
4. GenerationTranscriptBuilder 从同一批 blocks + state_summary 构建 GenerationContext
5. MemoryGenerationEngine.process(...) 创建 MemoryAtom
6. _draft_to_memory() 生成 MemoryAtom
7. MemoryArtifactGenerator.build_for_create(..., source_artifact_refs=[interaction_ref])
8. ArtifactStore 写 MemoryCreationArtifact
9. interaction_ref / creation_ref 按 manifest 策略写入 memory.payload.artifacts.refs / provenance
10. _save_memory(memory)
```

边界要求：

- `InteractionArtifact` 的来源只能是 `LogicalBlock.turn`，不能是 `GenerationContext.turns`。
- `GenerationContext` 可以与 raw turns 不一致，因为它是专为记忆生成整理过的语义视图。
- `state_summary` 只参与 `GenerationContext` / generation view，不写入 `InteractionArtifact.topic_summary`。
- `topic_summary` 是 topic display metadata，本阶段不因 archive/generation 执行而更新。
- 如果 interaction artifact 写入失败，memory 主流程是否继续由调用方 failure policy 决定；即使继续，也不能写入无效 `interaction_ref`。

`MemoryCreationArtifact` 保存：

- `memory_id`。
- `source_intent`，由调用路径显式传入或在 controller 内部推断。
- `source_artifacts`，包含本次创建所依据的 `InteractionArtifactRef`，以及未来可能出现的 document refs。
- `generation_view`，即当前 `GenerationContext.model_dump()`。
- `initial_version_ref`，指向 `MemoryVersionArtifact`(v1)；v1 的 `snapshot_after` 保存初始的 alias / title / summary / tags / memory_type 等可变字段快照。

CREATE 链路 MemoryVersionArtifact(v1) 构建时机与 MemoryCreationArtifact 相同（记忆入库前），`update_source="CREATE"`，`snapshot_before=None`，`snapshot_after` 包含刚生成的完整可变字段状态。

### 5.5 UPDATE / MERGE 链路 artifact 构建

UPDATE / MERGE 链路由 `MemoryVersionArtifact` 记录版本变化，不复用 creation artifact。

推荐顺序：

```text
1. 复制 memory_before
2. 生成 memory_after
3. MemoryArtifactGenerator.build_for_update(...)
4. ArtifactStore 写 MemoryVersionArtifact
5. version_ref 写入 full_history item
6. provenance 追加 action="updated" 或 action="merged"
7. _save_memory(memory_after)
```

`full_history` item 从：

```python
{
  "timestamp": "...",
  "content": "...",
  "reason": "..."
}
```

扩展为：

```python
{
  "timestamp": "...",
  "content": "...",
  "reason": "...",
  "artifact_refs": [...]
}
```

`TOUCH` / `DISCARD` / `CANCELLED` / `FAILED` 不写 memory creation/version artifact：

- `TOUCH`: 走 lifecycle event。
- `DISCARD`: 留在 memory task 状态或 RuntimeEvent。
- `CANCELLED` / `FAILED`: 属于运行时状态，不属于 memory creation/version artifact。若 memory 未创建成功，不能把 interaction artifact ref 绑定到不存在的 MemoryAtom；是否保留未绑定 raw artifact 由后续 debug/archive policy 决定。

### 5.6 GenerationRequest 暂缓扩展

v0.5.0 不急于扩展 `GenerationRequest` 的 artifact 字段。

原因：

- 当前没有外源文档解析功能，提前增加 document source refs 会长期为空。
- 真实使用过的 memory refs 当前隐含在 `GenerationTurn.trace_summaries` / `mtp_traces` 中，不宜先用空的 `source_memory_refs` 字段占位。
- `source_intent` 可以从调用路径推断：`_run_archive_task()` 对应 `ARCHIVE`，主动 WRITE 对应 `WRITE`，未来 import/manual 再补充。

如果实现中确实需要显式传递创建意图，优先在 controller 调用 `MemoryGenerationEngine.process()` 时使用显式关键字参数，例如 `source_intent` 与 `source_artifact_refs`。不要新增携带 topic id 的 `MemoryArtifactContext`，也不要让 `InteractionArtifact` 依赖 generation request 的业务字段。

### 5.7 MTP trace 与 source memory refs 暂缓策略

`MemoryCreationArtifact.source_memory_refs` 可以作为未来字段预留，但 v0.5.0 不要求填充。

真实使用到的记忆原子来自 Agent 运行时 MTP 指令访问轨迹，而不是普通 retrieval 结果。当前这些信息主要隐含在：

- `GenerationTurn.trace_summaries`
- `InteractionPayload.mtp_traces`
- `turn_events`

v0.5.0 策略：

- 不从字符串 trace summary 中脆弱解析 memory refs。
- 不把 retrieval hits 当作 source memory refs。
- 如果已有结构化 MTP trace 能稳定解析出 memory id / alias，可 best-effort 写入；否则留空。
- 后续版本再引入正式 `MemoryUsageRef` / `MemoryInputRef` 解析器。

### 5.8 Retrieval lifecycle 边界

Retrieval 不写独立 artifact。v0.5.0 只补齐 request id、timeout、RuntimeEvent 与 lifecycle 事件边界。

处理原则：

- `RetrievalFamiliar.retrieve_async()` 增加 request id，便于运行时观测和日志关联。
- 检索命中继续调用 lifecycle hit/citation 机制维护 vitality，不进入 ArtifactStore。
- 普通 retrieval hits 不进入 `MemoryCreationArtifact.source_memory_refs`。
- 只有 Agent 运行时真实 MTP 访问过的 memory，未来才有资格成为 source memory ref。

### 5.9 Patchouli 内部集成点

v0.5.0 的 artifact 集成点应位于 Patchouli 内部，并按 artifact 类型拆分：

```text
MemoryGenerationTaskController
  -> load topic blocks / active topic context
  -> InteractionArtifactBuilder.build(topic_id, topic_title, topic_summary, blocks)
  -> ArtifactStore.put(InteractionArtifact) => interaction_ref
  -> build GenerationRequest / GenerationContext / infer source_intent
  -> MemoryGenerationEngine.process()
      -> _draft_to_memory()
      -> MemoryArtifactGenerator.build_for_create(source_artifact_refs=[interaction_ref])
      -> ArtifactStore.put(...)
      -> creation refs/provenance 写入 MemoryAtom
      -> _save_memory(memory)
```

UPDATE / MERGE：

```text
MemoryGenerationEngine._apply_update()
  -> memory_before snapshot
  -> merge/update content
  -> MemoryArtifactGenerator.build_for_update()
  -> ArtifactStore.put(...)
  -> full_history/provenance 写入
  -> _save_memory(memory_after)
```

`ChatApplicationService`、`PreparedAgentRun`、`InteractionPayload` 只保持现有职责，不承担 artifact 构建入口。

## 6. Async Cold Path 规划

### 6.1 当前边界

当前链路已经是 async 函数形态，但内部仍有几类同步核心：

- `MemoryGenerationEngine.process()` 是同步接口，内部调用 extractor / deduplicator / storage。
- `RetrievalFamiliar.retrieve_async()` 用 `asyncio.to_thread(self.retrieve, ...)` 包同步检索。
- `QdrantMemoryStore` 是同步 client。
- MemoryGenerationTaskController 直接 `asyncio.create_task()`，没有 queue/backpressure。

v0.5.0 不要求一次性替换所有同步底层，但要建立统一 async cold path contract。

### 6.2 ColdPathTaskRunner

新增通用 runner，建议位置：

```text
src/hivememory/system/runtime/tasks/
  runner.py
  models.py
```

职责：

- 并发限制。
- queue。
- timeout。
- retry。
- cancellation。
- RuntimeEvent 发布。

接口：

```python
class ColdPathTaskRunner:
    async def submit(
        self,
        task_type: str,
        coro_factory: Callable[[CancellationToken], Awaitable[Any]],
        *,
        task_id: str,
        timeout_seconds: float | None = None,
        max_retries: int = 0,
    ) -> TaskHandle: ...
```

第一版可只接管 memory generation task；retrieval job 可以先采用同一 envelope，但不强制排队。

### 6.3 MemoryGenerationTaskController 接入 runner

当前 `_create_and_run_task()` 直接 `asyncio.create_task()`。

v0.5.0 改为：

```python
handle = await runner.submit(
    "memory_generation",
    lambda token: coro_factory(memory_task, token),
    task_id=memory_task.task_id,
    timeout_seconds=config.memory_generation.timeout_seconds,
)
memory_task.attach_handle(handle)
```

新增行为：

- 达到并发上限时 task 留在 `PENDING` / `QUEUED`。
- 开始执行时进入 `RUNNING`。
- cancel 会取消 queue 中任务或正在运行任务。
- timeout 进入 failed 或 cancelled，按配置决定。

### 6.4 RetrievalRequestEnvelope

检索是 hot path，但目前 prepare 阶段会阻塞用户首 token，因此至少要有 request envelope 与超时。

```python
class RetrievalRequestEnvelope(BaseModel):
    request_id: str
    mode: str = "active"
    request: RetrievalRequest
    timeout_seconds: float = 10.0
    record_lifecycle_events: bool = True
```

`PatchouliService.retrieve_for_gaze()` 目标：

- 创建 request id。
- 发布 `retrieval.request.started/status/completed/failed` RuntimeEvent。
- 超时返回空 `RetrievalResponse` 或失败，按配置决定。
- 对命中的 memory 记录 lifecycle hit；对 Agent 明确引用的 memory 记录 citation。
- 如果后续触发记忆生成，source memory refs 仅在已有结构化 MTP trace 可稳定解析时 best-effort 写入。

RuntimeEventType 可扩展：

```python
RETRIEVAL_REQUEST_STARTED = "retrieval.request.started"
RETRIEVAL_REQUEST_COMPLETED = "retrieval.request.completed"
RETRIEVAL_REQUEST_FAILED = "retrieval.request.failed"
```

### 6.5 Bus contract 收敛

当前 GlobalSystemBus routes 是字符串 + 任意参数。v0.5.0 不需要完全重写 bus，但新 cold path route 应优先使用 envelope。

建议新增或迁移：

| Route | 输入 | 输出 |
| :--- | :--- | :--- |
| `patchouli.public.memory.retrieve.v2` | `RetrievalRequestEnvelope` | `RetrievalResponseEnvelope` |
| `patchouli.public.memory.generation.submit` | `MemoryGenerationTaskSpec` | `MemoryGenerationTask` |
| `patchouli.public.artifact.get` | `artifact_id` | `dict` |

旧 route 保留，内部适配到新 envelope。

## 8. 分阶段实施计划

### Phase 1: ArtifactStore 与数据模型

目标：建立 artifact/ref/provenance 的领域模型、本地存储和 ArtifactEngine 骨架。

任务：

1. 新增 `ArtifactType`、`ArtifactRef`、`BaseArtifact` 与派生 artifact models（含 `MemoryVersionSnapshot`）。
2. 扩展 `Artifacts`，增加 `refs`、`provenance`、`cold_archive_uri`、`cold_archive_hash`、`revival_keys`；`full_history` item 追加 `artifact_refs` 兼容字段。
3. 实现 `FilesystemArtifactStore`。
4. 增加配置项 `artifacts.enabled/root_dir`。
5. 写入/读取/hash 校验测试。
6. 实现 `ArtifactEngine` 容器，初始化 `InteractionArtifactBuilder`、`DocumentArtifactBuilder`、`MemoryArtifactBuilder` 三个骨架类并注入 `ArtifactStore`。

验收：

- 可以写入并读取 JSON artifact。
- `ArtifactRef.sha256` 能校验内容。
- `MemoryAtom` 旧 payload 仍能反序列化。
- `ArtifactEngine` 可实例化并持有三个 builder 引用。

### Phase 2: Raw InteractionArtifact

目标：保存 topic 范围内的原始交互冷备份，并通过 `ArtifactRef` 将其作为 MemoryAtom 的额外解释项关联。

任务：

1. 新增 `InteractionTurnSnapshot`。
2. 将 `InteractionArtifact` 重定义为 raw interaction artifact；其数据体不内嵌归属 memory 信息。
3. 实现 `InteractionArtifactBuilder.build_and_store()`：从 `LogicalBlock.turn` 构建 artifact，写入 ArtifactStore，返回 `ArtifactRef`。
4. 在 topic/archive context 中区分 `topic_summary` 与 `state_summary`。
5. 被动 ARCHIVE 与主动 WRITE 使用同一套 topic raw interaction 构建规则。
6. 不在 `InteractionArtifact` 数据体中写入 memory id、generation view、source intent、source mode 或 capture policy。

验收：

- artifact 包含 `topic_id`、`topic_title`、`topic_summary`。
- artifact 从 `LogicalBlock.turn` 保留 raw `turn_events`、tool call/tool result、actions 与 semantic traces。
- artifact 数据体不包含 `memory_id`、`memory_alias`、generation view、source intent、source mode、capture policy。
- `build_and_store()` 直接写入 ArtifactStore 并返回 `ArtifactRef`，调用方无需感知内部写入细节。
- MemoryAtom 可通过 manifest refs 或 creation artifact 的 `source_artifacts` 引用该 artifact。
- 当 `GenerationContext` 与 raw turns 不一致时，artifact 仍必须匹配 raw turns。

### Phase 3: Memory creation 与 version artifact 写入

目标：MemoryAtom 首次创建与后续更新均能追溯来源，版本快照链从 v1 起完整建立。

任务：

1. 实现 `MemoryArtifactBuilder.build_for_create()`：原子写入 `MemoryVersionArtifact`(v1) 与 `MemoryCreationArtifact`，v1 先写，其 ref 通过 `initial_version_ref` 写入 Creation Artifact，返回 `MemoryCreationBundle`。`MemoryCreationArtifact` 不保存 alias/title/tags 等可变字段，改由 v1 的 `snapshot_after` 持有全量初始状态。
2. CREATE 入库前将 interaction ref 写入 `MemoryCreationArtifact.source_artifacts`，将 creation ref 与 v1 version ref 按 manifest 策略写入 `MemoryAtom.payload.artifacts.refs` 与 `provenance`。
3. 实现 `MemoryArtifactBuilder.build_for_update()`：写入 `MemoryVersionArtifact`(v2+)，`snapshot_before` 保存更新前完整状态，`snapshot_after` 保存更新后全量可变字段（content/alias/title/summary/tags/memory_type），返回 `ArtifactRef`。
4. UPDATE/MERGE 入库前将 version ref 写入 `full_history` item 的 `artifact_refs`（兼容过渡）与 `provenance`。
5. TOUCH/DISCARD 不写 artifact，只保留 lifecycle/task runtime 状态。
6. `GenerationRequest` 暂不扩展 artifact/source memory 字段。

验收：

- `build_for_create()` 返回的 `MemoryCreationBundle` 中 `creation_ref` 与 `initial_version_ref` 均已写入 ArtifactStore。
- `MemoryCreationArtifact` 不含 alias/title/tags/memory_type；这些字段存在于 v1 `MemoryVersionArtifact.snapshot_after`。
- MTP WRITE 生成的 memory 能通过 `MemoryCreationArtifact.source_artifacts` 追溯到 `InteractionArtifact`。
- ARCHIVE 生成的 memory 能指向 `MemoryCreationArtifact`。
- UPDATE 后 `full_history[-1]` 包含 source artifact refs，`provenance` 追加版本条目。
- `MemoryVersionArtifact.snapshot_after` 包含全部可变字段，可独立重建 MemoryAtom 状态。
- DISCARD 不创建 memory，也不产生 memory artifact。

### Phase 4: Async cold path runner

目标：memory generation 进入统一 queue/runner。

任务：

1. 新增 `ColdPathTaskRunner`。
2. MemoryGenerationTaskController 从 `asyncio.create_task()` 迁移到 runner。
3. 增加并发限制、timeout、cancel、retry 配置。
4. RuntimeEvent 增加 queued/running/timeout/retry 信息。
5. 保持 `/memory-tasks` API 兼容。

验收：

- 并发 memory tasks 不超过配置上限。
- queued task 可取消。
- timeout task 进入 failed，不产生 memory artifact。
- 现有 memory task 测试全部通过。

### Phase 5: Retrieval request envelope 与 lifecycle event

目标：检索链路有可追踪 request id、超时与 lifecycle 事件，不写独立 artifact。

任务：

1. 新增 `RetrievalRequestEnvelope`。
2. `retrieve_for_gaze()` 使用 request id 和 RuntimeEvent。
3. 检索命中继续记录 lifecycle hit/citation。
4. source memory refs 仅在已有结构化 MTP trace 可稳定解析时 best-effort 写入。
5. 旧 `PATCHOULI_MEMORY_RETRIEVE` route 保持兼容。

验收：

- 检索超时有明确 RuntimeEvent 和 fallback 行为。
- 普通 retrieval 不产生 artifact store 写入。
- 普通 retrieval hits 不进入 `MemoryCreationArtifact.source_memory_refs`。
- 已有结构化 MTP trace 可解析时，真实 MTP 访问过的 memory 可进入 source memory refs。

## 10. 兼容性与迁移策略

### 10.1 MemoryAtom 兼容

- `Artifacts` 新增字段必须有 default factory。
- 旧 Qdrant payload 反序列化不应失败。
- `to_qdrant_payload()` 保持原格式，只是 payload 中多新字段。

### 10.2 API 兼容

- `/chat` SSE 原事件不删除。
- `/memory-tasks` 原字段不删除，只追加 artifact/provenance 字段。
- 新 `/artifacts` API 独立增加。
- 旧 GlobalSystemBus route 保留。

### 10.3 存储兼容

- ArtifactStore 默认本地文件系统。
- 如果 artifacts disabled，系统回退到 v0.4.0 行为。
- artifact 写失败不应导致主对话失败，但应影响 provenance 状态。

### 10.4 隐私与体积

Raw transcript 可能包含敏感数据。默认策略：

- 本地部署默认启用。
- 支持配置关闭 raw artifact。
- 支持最大 artifact size。
- 支持 future redaction hook，但 v0.5.0 不实现复杂脱敏。

## 11. 风险与决策点

### 11.1 Artifact 是否存 Qdrant

不建议把 raw transcript 大对象直接塞 Qdrant payload。

原因：

- Qdrant payload 应服务检索和轻量 metadata。
- 大 JSON 会增加 payload IO 与备份成本。
- raw transcript 不应参与向量检索。

建议采用本地 `ArtifactStore`，MemoryAtom 只保存 refs。

### 11.2 RuntimeEvent 是否全部持久化

v0.5.0 不持久化全部 RuntimeEvent。

原因：

- event 数量大，且很多只是瞬时状态。
- 真正需要长期追溯的是 MemoryAtom 的来源、创建输入、外源文档与版本快照；run/task outcome 属于运行时记录。

策略：

- RuntimeEvent 继续 ring buffer。
- MemoryAtom 创建/更新成功后的长期证据写 artifact。
- memory task 结果继续留在运行时状态或未来 TaskRecord。

### 11.3 Retrieval 是 hot path 还是 cold path

用户输入前的 retrieval 属于 hot path，因为它影响首 token 延迟；v0.5.0 不把检索结果归档为 artifact，只保留运行时事件、timeout/fallback 和 lifecycle hit/citation。

v0.5.0 策略：

- 检索请求本身保留同步等待，但有 timeout/fallback。
- 检索命中继续服务 vitality 维护，不进入 ArtifactStore。
- 普通检索上下文不写入 `MemoryCreationArtifact.source_memory_refs`；只有结构化 MTP trace 可稳定解析时才 best-effort 写入。
- vitality refresh 可以继续异步化/降级。

### 11.4 GenerationEngine 是否改为 async

短期不强制把 `MemoryGenerationEngine.process()` 改成 async。

策略：

- 由 task runner 统一包裹同步或异步 callable。
- 后续若 extractor/storage 全部 async，再将 process 改为 async。

## 12. v0.5.0 Done Definition

v0.5.0 可以发布的最低标准：

1. ArtifactStore v1 可写入/读取/校验 JSON artifact。
2. `ArtifactType`、`BaseArtifact`、`ArtifactRef`、派生 artifact models 落地。
3. topic raw interaction 批次可持久化为 `InteractionArtifact`，并可通过 `ArtifactRef` 作为 MemoryAtom 解释项关联。
4. `InteractionArtifact` 不携带 memory id、generation view、source intent、source mode 或 capture policy。
5. `MemoryCreationArtifact` 保存创建时的 generation view、source intent、source artifact refs 与 source memory refs，通过 `initial_version_ref` 指向 `MemoryVersionArtifact`(v1)；可变字段初始值（alias/title/tags 等）由 v1 的 `snapshot_after` 持有，不写入 Creation Artifact。
6. `DocumentArtifact` 模型落地，MemoryAtom 可保存外源文档 artifact ref。
7. MTP WRITE 创建的 MemoryAtom 带 refs/provenance。
8. MTP UPDATE 的 `full_history` 带 source artifact metadata。
9. `MemoryVersionArtifact` 维护从 v1（初始创建状态）起的完整状态快照链；`snapshot_after` 保存所有可变字段（content/alias/title/tags 等），支持任意版本独立重建；`update_source` 含 `"CREATE"`，覆盖记忆全生命周期。
10. memory task API 保留运行时状态，不暴露 outcome artifact。
11. Memory generation 由统一 runner 管理并发、取消、timeout。
12. Retrieval request envelope、RuntimeEvent 与 lifecycle hit/citation 行为可验证。
13. `Artifacts.cold_archive`（ArtifactRef）与 `revival_keys` 字段预留完成；`MemoryProvenance.vitality` 在归档事件时写入，为未来复活机制提供锚点，不要求实现自动复活。
14. 旧数据、旧 API、旧 bus route 保持兼容。
15. 关键行为有自动化测试覆盖。

## 13. 建议提交顺序

1. `ArtifactType` / `BaseArtifact` / `ArtifactRef` / 派生 artifact models。
2. `FilesystemArtifactStore` 与配置。
3. `Artifacts` 模型扩展与兼容测试。
4. `InteractionArtifactBuilder` 写 raw interaction artifact。
5. `MemoryArtifactGenerator` 写 creation / version artifacts。
6. `MemoryGenerationEngine` CREATE 链路接入 creation artifact generator。
7. `MemoryGenerationEngine` UPDATE/MERGE 链路接入 version artifact。
8. MemoryAtom refs / provenance 写入与兼容测试。
9. MTP trace source memory refs 暂缓或 best-effort 解析。
10. `/artifacts` API 与 `/memory-tasks` 响应扩展。
11. `ColdPathTaskRunner`。
12. memory generation task runner 迁移。
13. retrieval request envelope 与 lifecycle event。
14. 测试补齐与文档更新。

该顺序先建立可落盘的数据模型，再分别接入 topic raw interaction 与 MemoryAtom creation/version artifact 构建，最后处理调度与检索异步化。这样 raw interaction 不与 memory generation 语义耦合，memory provenance 也不与 chat runtime 噪声耦合。
