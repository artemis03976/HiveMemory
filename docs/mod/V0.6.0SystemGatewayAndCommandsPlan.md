# v0.6.0 System Gateway 与系统指令规划

**文档状态**: Draft  
**适用范围**: `system/`、`patchouli/`、`engines/gateway/`、`core/protocol/`、`server/routers/`、`frontend/src/`  
**前置版本**: v0.5.x 基础设施工作完成  
**核心目标**: 将 Gateway / TheEye 从 Patchouli 记忆系统上移到 System 级，建立全局系统指令库，并把 Gateway 改造为可扩展的多阶段决策 Workflow；复合意图分解作为后续 Phase 4 能力预留协议与扩展点。

---

## 1. 背景

### 1.1 当前状态

当前代码已经把 Gateway 的“纯分析引擎”与 Patchouli Runtime 分开，但还没有把 TheEye 的宿主身份从 Patchouli 中剥离出来。

现状分层如下：

```text
src/hivememory/engines/gateway/
  engine.py            # GatewayEngine，纯数据操作层
  interceptors.py      # RuleInterceptor / create_interceptor
  semantic_analyzer.py # LLMAnalyzer / create_semantic_analyzer
  models.py            # GatewayResult / GatewayIntent / SemanticAnalysisResult
  interfaces.py        # BaseInterceptor / BaseSemanticAnalyzer

src/hivememory/patchouli/
  eye.py               # TheEye，当前仍归属 Patchouli 包
  system.py            # PatchouliSystem 构造 GatewayEngine 与 TheEye
  service.py           # PatchouliService 持有 eye，并暴露 gaze()
```

当前主动 chat 调用链：

```text
ChatApplicationService
  -> GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN
  -> PatchouliService.prepare_agent_run()
  -> PatchouliLocalRoutes.GATEWAY_GAZE
  -> PatchouliService.gaze()
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> EyeGazeResult
  -> Topic prepare / Retrieval / Alice run / Patchouli finalize
```

当前被动接入调用链：

```text
PassiveIngressService
  -> PassiveMessageIngressor.route_event()
  -> GlobalRoutes.PATCHOULI_PASSIVE_ANALYZE_AND_RETRIEVE
  -> PatchouliService.analyze_and_retrieve()
  -> PatchouliLocalRoutes.GATEWAY_GAZE
  -> TheEye.gaze()
  -> retrieve_for_gaze()
```

当前职责划分：

- `GatewayEngine` 已经是独立 engine，不直接依赖 Patchouli。
- `TheEye` 负责处理 `GatewayEngine` 的业务包装：topic snapshot 渲染、耗时记录、异常 fallback、`GatewayResult -> EyeGazeResult` 转换。
- `PatchouliSystem._init_gateway()` 仍负责 gateway LLM、interceptor、semantic analyzer、`GatewayEngine` 的装配。
- `PatchouliSystem` 仍直接持有 `self.eye`。
- `PatchouliService` 仍通过构造参数持有 `eye: TheEye`，并将 `service.gaze()` 注册到 Patchouli local bus 的 `gateway.gaze`。
- gateway 配置当前仍位于 `config.patchouli.gateway`，LLM 凭证位于 `config.shared.llm.gateway`。

已知限制：

- TheEye 的包路径与生命周期宿主仍暗示它是 Patchouli 记忆系统的一部分。
- Gateway 装配代码位于 `PatchouliSystem`，导致未来系统指令库、Deep Research、附件任务等非记忆域能力若要复用 TheEye，仍必须经过 Patchouli。
- `PatchouliLocalRoutes.GATEWAY_GAZE = "gateway.gaze"` 是 Patchouli local route，语义上不适合作为全局入口长期存在。
- `EyeGazeResult` 已位于 `core.protocol.models`，但文档注释仍说“数据格式转换由 PatchouliRuntime 负责”，与当前代码不完全一致。

### 1.2 问题陈述

v0.6.0 的第一阶段要解决的是架构归属问题，而不是新增复杂智能行为。

TheEye 当前已经承担“系统入口分析器”的职责，但实现位置仍在 Patchouli 内。这会带来几个实际问题：

1. **依赖方向不清晰**
   - System 级应用服务通过 GlobalBus 请求 Patchouli public route，Patchouli 再转入 local bus 执行 `gateway.gaze`。
   - 从业务语义看，入口分析应发生在 System 层；从代码位置看，它仍被 Patchouli 托管。

2. **后续全局系统指令难以自然扩展**
   - `/clear`、后续 `/research`、`/ingest`、任务队列控制等指令不一定属于记忆域。
   - 若 TheEye 继续在 Patchouli 内，系统指令库会被迫放进 Patchouli 或通过 Patchouli 转发到其他系统能力，形成反向依赖。

3. **复合意图分解的下游不只 Patchouli**
   - 复合意图可能同时包含检索、规划、任务创建、Agent run、文档解析等片段。
   - 这些片段的消费方横跨 Patchouli、Alice、未来 Runtime Job Queue 和前端交互层。
   - TheEye 若仍属于 Patchouli，会让复合意图输出天然偏向记忆域。

4. **测试与文档命名会持续误导**
   - 现有测试集中在 `tests/unit/patchouli/test_eye.py`。
   - 顶层 `hivememory.__getattr__` 也从 `hivememory.patchouli.eye` 导出 `TheEye`。
   - 这些入口会让后续开发继续把 gateway 当作 Patchouli 私有能力。

### 1.3 版本定位

v0.6.0 是后续“全局任务入口”的铺垫版本：

- Phase 1 只解决 TheEye / Gateway 的 System 级归属问题。
- Phase 2 在 Phase 1 的基础上添加全局系统指令库。
- Phase 3 在稳定的 System Gateway 输出契约上重设计 Gateway Workflow，先完成单主意图路径的话题路由、记忆价值预判断与检索策略预判断。
- Phase 4 在 Phase 3 Workflow 基础上扩展复合意图分解、多分支消费与合并语义。
- v0.6.1 Runtime Job Queue 会消费 Phase 2/3/4 产生的 task dispatch 信息。
- v0.6.2 附件解析、v0.7.0 Document Ingestion、v0.7.2 Deep Research 都应通过 System Gateway 进入对应任务或工作流，而不是绕进 Patchouli 私有入口。

## 2. 目标与非目标

### 2.1 目标

1. 将 Gateway / TheEye 正式上移到 System 级，脱离 Patchouli 记忆系统。
2. 添加全局系统指令库，由 TheEye 进行拦截、解析与路由转发。
3. 增强 TheEye / Gateway 的解析架构，支持多阶段决策，并为复合意图分解预留协议与扩展点。
4. 为后续检索、规划、任务队列、Deep Research 提供统一的意图输出契约。

### 2.2 非目标

v0.6.0 不承担以下工作：

- 不实现完整 Alice Phase 3 顶层任务图编排。
- 不实现 Runtime Job Queue，只为后续 task dispatch 预留边界。
- 不实现附件上传、文档解析、Document Ingestion 或 Deep Research。
- 不实现 MTP RUN executable asset、沙箱执行或真取消。
- 不实现完整对话回档或记忆 rollback。
- Phase 1 不改变 GatewayEngine 的 L1/L2 语义分析行为。
- Phase 1 不改变 `EyeGazeResult` 对外字段。

### 2.3 优先级

1. **P0**: Gateway / TheEye 上移到 System 级。
2. **P1**: 全局系统指令库与路由转发。
3. **P2**: Gateway Workflow 单主意图架构重设计。
4. **P3**: 复合意图分解与多分支消费语义。

## 3. 术语与边界

### 3.1 术语

- **GatewayEngine**: 位于 `engines/gateway/` 的纯分析引擎，负责 L1 规则拦截与 L2 语义分析，不处理业务 fallback、不持有系统状态。
- **TheEye**: System 级入口分析服务，负责调用 `GatewayEngine`，并将结果包装为 `EyeGazeResult`。Phase 1 后不再属于 Patchouli。
- **Gaze**: TheEye 对单条用户输入执行入口分析的动作，输入为 query / topic snapshots / identity，输出为 `EyeGazeResult`。
- **EyeGazeResult**: 当前热路径使用的入口分析协议，承载 intent、rewritten query、search keywords、worth_saving、topic routing 等字段。
- **System Gateway**: System 层对 TheEye、GatewayEngine、配置、未来系统指令库与复合意图路由的总称。
- **System Command**: 全局系统指令，Phase 2 设计；Phase 1 仅预留归属边界。
- **Intent**: 用户输入的单一意图分类，当前主要为 `RAG` / `CHAT` / `SYSTEM`。
- **Composite Intent**: 复合意图分解结果，Phase 4 设计；Phase 3 仅预留检测信号和扩展点。
- **Route Target**: 意图或命令的下游目标，Phase 2/3/4 逐步设计；Phase 1 仅保留 gaze 结果给 Patchouli 消费。
- **Task Spec**: 未来 Runtime Job Queue 可消费的任务描述，v0.6.1 设计；v0.6.0 Phase 1 不生成 task spec。

### 3.2 子系统边界

Phase 1 目标边界：

- `engines/gateway/`：保留为纯引擎层，提供 L1/L2 分析能力，不知道 System、Patchouli、Alice。
- `system/gateway/`：新增 System 级 gateway 宿主层，持有 `TheEye`、gateway factory、未来 command registry / intent router 的扩展点。
- `system/`：负责构造 Gateway 子系统，并通过 `GlobalSystemBus` 注册/暴露跨子系统能力；顶层 application service 不直接持有子系统实例。
- `patchouli/`：只消费 `EyeGazeResult`，不构造、不拥有 TheEye。
- `alice/` 与 `agent_runtime/`：Phase 1 不直接接入 TheEye，只保持现有 chat run 调用链。

允许依赖方向：

```text
system/gateway -> engines/gateway
system/gateway -> core.protocol / core.models
system -> system/gateway
patchouli.service -> core.protocol models
patchouli.service -> system-level gaze route or injected gaze callable
```

禁止依赖方向：

```text
system/gateway -> patchouli
engines/gateway -> system
engines/gateway -> patchouli
patchouli.system -> system.gateway concrete composition root
```

说明：Patchouli 可以在类型层面依赖 `EyeGazeResult`、`GatewayIntent` 等协议模型，但不应再负责 TheEye 的创建、配置解析或生命周期托管。

### 3.3 输入输出边界

Phase 1 不改变现有输入输出模型。

输入：

- `query: str`
- `topic_snapshots: Optional[list[TopicSnapshot]]`
- `identity: Optional[Identity]`

输出：

- `EyeGazeResult`

Phase 1 的关键约束：

- `EyeGazeResult.intent`、`rewritten_query`、`search_keywords`、`worth_saving`、`target_topic`、`new_topic_title`、`new_topic_summary` 的行为保持兼容。
- fallback 行为保持兼容：`GatewayEngine` 或 LLM analyzer 异常时返回 `intent=RAG`、`rewritten_query=raw_query`、`worth_saving=False`、`target_topic="NEW_TOPIC"`、`is_fallback=True`。
- Topic snapshot 文本渲染在 Phase 1 可暂时沿用 `PerceptionContextConverter.snapshots_to_context_text()`，但需要在依赖方向上避免 `system/gateway` 直接依赖 perception engine 的具体实现。迁移时可先复制/抽出轻量 renderer，或在构造 TheEye 时注入 renderer callable。

## 4. 总体架构

### 4.1 目标结构

Phase 1 后的目标结构：

```text
system/
  config/
    gateway.py          # SystemGatewayConfig / RuleInterceptorConfig / LLMAnalyzerConfig
                        # 或从 patchouli.py 迁出的等价配置
  gateway/
    __init__.py
    eye.py              # TheEye 的新归属
    factory.py          # build_system_gateway() / build_gateway_engine()
    contracts.py        # 可选：SystemGatewayRoutes / Gaze callable type
    topic_context.py    # 可选：topic snapshots -> active_topics_menu renderer

engines/gateway/
  engine.py             # 保持纯引擎层
  interceptors.py
  semantic_analyzer.py
  models.py
  interfaces.py

patchouli/
  system.py             # 不再 _init_gateway，不再 self.eye = TheEye(...)
  service.py            # 不再拥有 TheEye concrete；改为通过 route/callable 请求 gaze
  eye.py                # 短期兼容 shim，可选；最终删除
```

推荐拆分：

- `system/gateway/eye.py`：从 `patchouli/eye.py` 迁移 `TheEye`。
- `system/gateway/factory.py`：承接原 `PatchouliSystem._init_gateway()` 的装配逻辑。
- `system/config/gateway.py`：从 `PatchouliConfig.gateway` 拆出 gateway 配置，使 gateway 不再属于记忆域配置。

可接受的第一步兼容：

- 保留 `hivememory.patchouli.eye.TheEye` 为 re-export shim：

```python
from hivememory.system.gateway.eye import TheEye
```

该 shim 仅为测试和外部导入过渡使用，不应包含逻辑。

### 4.2 总体数据流

Phase 1 后的主动 chat 数据流：

```text
User Input
  -> ChatApplicationService
  -> Patchouli prepare public route
  -> PatchouliService.prepare_agent_run()
  -> System Gateway gaze route/callable
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> EyeGazeResult
  -> Patchouli topic prepare + retrieval
  -> Alice run
  -> Patchouli finalize
```

Phase 1 不改变 `ChatApplicationService` 的 prepare/run/finalize 编排骨架，也不改变 `PatchouliService.prepare_agent_run()` 对 `EyeGazeResult` 的消费逻辑。

Phase 1 的主要变化是 gaze 能力的宿主与注册位置：

```text
Before:
  PatchouliSystem builds TheEye
  Patchouli local bus registers gateway.gaze -> PatchouliService.gaze -> self._eye.gaze

After:
  HiveMemorySystem or SystemGateway factory builds TheEye
  System-level route/callable exposes gateway.gaze
  PatchouliService requests/invokes system gaze
```

### 4.3 依赖方向

Phase 1 的依赖方向以“System 拥有 gateway，Patchouli 消费 gaze result”为准：

```text
HiveMemorySystem.build()
  -> build_system_gateway(config.gateway, config.shared.llm.gateway)
  -> PatchouliSystem(..., gateway_gaze=system_gateway.gaze)

PatchouliService
  -> gateway_gaze(query, topic_snapshots, identity)
  -> EyeGazeResult
```

不推荐让 `system/gateway` 直接请求 Patchouli route 获取 topic snapshots。Topic snapshot 的生产仍属于 Patchouli；TheEye 只接收调用方提供的 snapshots。

不推荐在 Phase 1 中新增大规模全局路由协议。如果需要路由，优先使用最小 `SYSTEM_GATEWAY_GAZE` route；更完整的系统指令路由留到 Phase 2。

## 5. Phase 1: Gateway / TheEye 上移到 System 级

### 5.1 现状

当前实现细节：

1. `TheEye` 位于 `src/hivememory/patchouli/eye.py`。
   - 构造参数：`engine: GatewayEngine`、`bus=None`。
   - 公开方法：`gaze(query, topic_snapshots=None, identity=None) -> EyeGazeResult`。
   - 内部职责：topic snapshots 渲染、调用 `GatewayEngine.process()`、耗时记录、日志、fallback。
   - 文件中已有 TODO：后续考虑上移至 system。

2. `GatewayEngine` 位于 `src/hivememory/engines/gateway/engine.py`。
   - 已经是纯数据操作层。
   - 执行 L1 interceptor 与 L2 semantic analyzer。
   - 不处理 fallback、日志、业务转换。

3. `PatchouliSystem` 当前负责 gateway 装配。
   - `PatchouliSystem.__init__()` 中先构造 `PatchouliRuntime`，再 `_init_gateway()`，再 `self.eye = TheEye(...)`。
   - `_init_gateway()` 使用 `config.shared.llm.gateway` 构造 gateway LLM service。
   - `_init_gateway()` 使用 `config.patchouli.gateway` 构造 interceptor 与 semantic analyzer。

4. `PatchouliService` 当前持有 `eye: TheEye`。
   - `service.gaze()` 是薄包装：调用 `self._eye.gaze(...)`。
   - `prepare_agent_run()` 与 `analyze_and_retrieve()` 并不直接调用 `self._eye.gaze()`，而是请求 `PatchouliLocalRoutes.GATEWAY_GAZE`。

5. `PatchouliRuntime.mount_local_routes()` 当前注册：
   - `PatchouliLocalRoutes.GATEWAY_GAZE -> service.gaze`
   - 这让 Patchouli local bus 成为 TheEye 的入口。

6. 顶层 `ChatApplicationService` 和 `PassiveIngressService` 不直接知道 TheEye。
   - 它们只通过 GlobalSystemBus 调 Patchouli public routes。
   - 因此 Phase 1 迁移理论上可以保持顶层 API 行为不变。

7. 测试现状：
   - `tests/unit/patchouli/test_eye.py` 直接测试 `hivememory.patchouli.eye.TheEye`。
   - E2E 测试中也有直接从 `hivememory.patchouli.eye` import `TheEye` 的路径。
   - 多个 Patchouli service 测试用 mock eye 或 local bus mock `GATEWAY_GAZE`。

### 5.2 目标

Phase 1 完成后，TheEye 应成为 System 级 gateway service，而不是 Patchouli 子系统组件。

目标状态：

1. `TheEye` 的真实实现移动到 `hivememory.system.gateway.eye`。
2. `PatchouliSystem` 不再构造 gateway LLM、interceptor、semantic analyzer、`GatewayEngine` 或 `TheEye`。
3. Gateway 装配逻辑移动到 System 层，例如：
   - `hivememory.system.gateway.factory.build_system_gateway(...)`
   - 或 `HiveMemorySystem.build()` 内部的私有构造函数。
4. `PatchouliService` 不再类型依赖 `hivememory.patchouli.eye.TheEye` concrete。
5. Patchouli 仍可在 prepare/analyze 流程中消费 `EyeGazeResult`，但 gaze 的来源是 System 级 gateway。
6. 现有主动 chat、被动 ingest、topic routing、retrieval 行为保持不变。

目标边界：

```text
TheEye owns:
  - GatewayEngine 调用
  - GatewayResult -> EyeGazeResult 转换
  - fallback
  - processing_time_ms
  - gateway 入口日志

Patchouli owns:
  - topic snapshots 获取
  - topic prepare / discard
  - retrieval_for_gaze
  - interaction submit / finalize
  - memory generation

System owns:
  - TheEye 构造与生命周期归属
  - gateway config 归属
  - 后续 command registry / route target 扩展点
```

### 5.3 模块迁移范围

建议迁移范围：

新增：

- `src/hivememory/system/gateway/__init__.py`
- `src/hivememory/system/gateway/eye.py`
- `src/hivememory/system/gateway/factory.py`
- `src/hivememory/system/gateway/topic_context.py`（可选）
- `src/hivememory/system/config/gateway.py`（推荐）
- `tests/unit/system/gateway/test_eye.py`

迁移：

- `src/hivememory/patchouli/eye.py` 的真实实现迁移到 `src/hivememory/system/gateway/eye.py`。
- `PatchouliSystem._init_gateway()` 的装配逻辑迁移到 `system/gateway/factory.py`。
- `MemoryGatewayConfig`、`RuleInterceptorConfig`、`LLMAnalyzerConfig` 从 `system/config/patchouli.py` 迁移到 `system/config/gateway.py`，或至少在 System config 层提供新的 `gateway` 字段。

调整：

- `HiveMemorySystem.__init__()` 增加 `gateway` 或 `the_eye` 字段。
- `HiveMemorySystem.build()` 在构造 PatchouliSystem 之前构造 System Gateway。
- `PatchouliSystem.__init__()` 接收 `gateway_gaze` callable 或 system gateway service 引用。
- `PatchouliService.__init__()` 接收 `gateway_gaze` callable，而不是 `eye: TheEye` concrete。
- `build_patchouli_route_bindings()` 中 `GATEWAY_GAZE` 可继续注册，但 handler 应来自注入的 system gateway callable，而非 Patchouli-owned eye。
- `hivememory.__getattr__("TheEye")` 改为从 `hivememory.system.gateway.eye` 导出。

保留：

- `src/hivememory/engines/gateway/*` 不迁移。
- `GatewayResult` / `GatewayIntent` / `SemanticAnalysisResult` 行为不改。
- `EyeGazeResult` 暂时仍保留在 `core.protocol.models`。
- `PatchouliLocalRoutes.GATEWAY_GAZE` 可短期保留，作为 Patchouli 内部 workflow 对 gaze 能力的兼容入口。

可选兼容 shim：

- `src/hivememory/patchouli/eye.py` 保留为：

```python
"""Deprecated compatibility import for TheEye."""

from hivememory.system.gateway.eye import TheEye

__all__ = ["TheEye"]
```

该 shim 应标注 deprecated，并在 v0.7 之后考虑删除。

### 5.4 兼容策略

Phase 1 应采用低风险兼容迁移，不一次性删除旧入口。

兼容策略：

1. **导入兼容**
   - 保留 `hivememory.patchouli.eye.TheEye` re-export，避免 E2E 与外部脚本立即失效。
   - 新代码必须使用 `hivememory.system.gateway.TheEye`。

2. **路由兼容**
   - 保留 `PatchouliLocalRoutes.GATEWAY_GAZE`，因为 `PatchouliService.prepare_agent_run()` 与 `analyze_and_retrieve()` 已经通过 local bus 请求它。
   - 但该 route 的 handler 不再绑定到 Patchouli-owned `self._eye`，而是绑定到 System 注入的 gaze callable。

3. **配置兼容**
   - 新增 `config.gateway` 作为 System Gateway 配置位置。
   - 短期允许从旧 `config.patchouli.gateway` 读取默认值，或者让 `PatchouliConfig.gateway` 成为 deprecated alias。
   - 文档与示例配置应优先使用 `gateway.*`。

4. **测试兼容**
   - 新增 `tests/unit/system/gateway/test_eye.py`。
   - 旧 `tests/unit/patchouli/test_eye.py` 可改为 shim import 兼容测试，或直接迁移到 system/gateway。
   - E2E 中直接 import `hivememory.patchouli.eye` 的位置应逐步改为 system path。

5. **行为兼容**
   - 不改 `EyeGazeResult` 字段。
   - 不改 fallback 值。
   - 不改 `prepare_agent_run()` 的输出结构。
   - 不改 chat stream 的 SSE prelude。

### 5.5 风险

主要风险：

1. **启动装配顺序风险**
   - 当前 `PatchouliSystem` 内部构造 TheEye，迁移后 `HiveMemorySystem.build()` 需要先构造 gateway，再注入 Patchouli。
   - 若 Patchouli local route 注册早于 gateway callable 注入，会导致 `gateway.gaze` route 缺失。

2. **配置路径迁移风险**
   - 当前代码读取 `config.patchouli.gateway`。
   - 若直接删除旧字段，会影响 YAML、测试 fixture 与默认配置加载。
   - 应先引入 `config.gateway`，再做兼容读取。

3. **topic snapshot renderer 依赖风险**
   - 当前 TheEye 内部 import `PerceptionContextConverter`。
   - 迁移到 `system/gateway` 后继续 import perception converter 会让 System Gateway 依赖 perception engine。
   - 推荐将 topic snapshot 渲染抽成 `system/gateway/topic_context.py`，或通过构造参数注入 renderer。

4. **测试路径风险**
   - 多个测试和 E2E 直接 import `hivememory.patchouli.eye.TheEye`。
   - 需要 shim 或批量迁移测试路径。

5. **局部总线路由语义风险**
   - `PatchouliLocalRoutes.GATEWAY_GAZE` 名称仍在 Patchouli 内，短期保留有利于兼容，但长期语义不理想。
   - Phase 1 不应为了命名洁癖同步改完整 bus 拓扑，避免扩大范围。

6. **公共导出风险**
   - `hivememory.__getattr__` 当前从 patchouli path 懒加载 `TheEye`。
   - 若忘记同步，会造成新旧路径实例不一致或导入失败。

### 5.6 验收

Phase 1 验收条件：

1. `TheEye` 的真实实现位于 `src/hivememory/system/gateway/eye.py`。
2. `src/hivememory/patchouli/eye.py` 不再包含真实逻辑，只保留兼容 re-export，或已被所有调用方移除。
3. `PatchouliSystem` 不再包含 `_init_gateway()`，也不再构造 `GatewayEngine` / `TheEye`。
4. System 层负责构造 gateway LLM、interceptor、semantic analyzer、`GatewayEngine` 与 `TheEye`。
5. `PatchouliService` 不再类型依赖 Patchouli TheEye concrete；它通过注入 callable 或 system route 获取 gaze 能力。
6. 主动 chat 路径仍可完成：
   - prepare
   - topic prepare
   - retrieval
   - Alice run
   - finalize
7. 被动 ingress 路径仍可完成：
   - user event analyze
   - retrieve
   - buffer

   - 正常结果字段不变
   - fallback 字段不变
   - topic routing 字段不变
9. 单元测试迁移完成：
   - `tests/unit/system/gateway/test_eye.py`
   - `tests/unit/engines/gateway/*`

10. 关键集成 / E2E 测试通过：
    - gateway component tests
    - pre-retrieval e2e
    - active chat path
    - passive ingest path

## 6. Phase 2: 全局系统指令库

### 6.1 Phase 2 启动前状态

Phase 2 启动前，`RuleInterceptor` 已经具备最小的系统指令快速拦截能力，但它只是硬编码正则列表：

- 旧系统指令正则列表直接包含 `/clear`、`/reset`、`/start`、`/help`、`/restart`。
- 命中后只返回 `InterceptorResult(intent=GatewayIntent.SYSTEM, reason=...)`。
- 结果中没有稳定的 command id、参数、权限需求、路由目标或执行策略。
- `GatewayEngine` 只知道这是 `SYSTEM` intent，不知道后续应该由哪个 system application service、Patchouli public route、Alice runtime 或 future job dispatcher 消费。
- 前端也无法从后端获得可补全的命令清单、帮助文本、参数 schema 或禁用原因。

因此当前状态只能回答“这是不是一个系统指令”，还不能回答“它是哪条指令、参数是什么、谁能执行、应该交给谁执行、执行结果如何对用户呈现”。

Phase 2 只解决系统指令的注册、解析、授权、路由和结果协议，不重排 active chat 的 `gaze -> prepare -> run -> finalize` 主时序。`prepare_agent_run` 中 Patchouli 反向调用 gaze 的问题保留到 Phase 3 前置重构处理。

### 6.2 目标

Phase 2 的目标是把系统指令从 `RuleInterceptor` 的硬编码正则中提升为 System Gateway 拥有的全局能力：

1. 新增 `CommandRegistry`，集中注册内置系统指令。
2. 每条指令有稳定 `command_id`、别名、匹配规则、参数 schema、权限策略、路由目标和展示元数据。
3. `RuleInterceptor` 不再维护系统指令正则常量，而是委托 registry 做 L1 快速匹配和初步解析。
4. `GatewayResult` / `EyeGazeResult` 在 `intent=SYSTEM` 时携带结构化 command parse result。
5. 新增 system-level command dispatcher，根据 parse result 将指令导向实际实现。
6. 指令执行结果有统一协议，供 chat / stream / frontend 呈现，不混入普通 Alice generation。
7. Phase 2 只支持单条明确系统指令；“系统指令 + 普通聊天/检索”的复合输入留给 Phase 4。

设计原则：

- `engines/gateway` 仍然是纯分析层，可以接收 registry 风格的 matcher，但不依赖 system service。
- `system/gateway` 拥有 command registry、command parse model 和 command dispatcher。
- Patchouli 只实现属于记忆域的 command handler，不拥有全局指令库。
- 指令执行的副作用必须发生在 dispatcher / handler，不发生在 `RuleInterceptor` 或 `TheEye.gaze()` 中。

### 6.3 指令分类

Phase 2 先定义分类，不要求一次实现所有指令。

| Category | 说明 | 典型指令 | Phase 2 建议 |
| --- | --- | --- | --- |
| `conversation` | 当前会话 UI / 生成控制，不直接改记忆 | `/help`, `/clear` | P0 |
| `gateway` | Gateway 调试与可观测能力 | `/gateway status`, `/commands` | P1 |
| `memory` | 记忆域操作，经由 Patchouli public route 执行 | `/memory search`, `/topic reset` | P1/P2 |
| `runtime` | 系统运行状态、模型 warmup、任务状态 | `/status`, `/models ready` | P1 |
| `debug` | 开发/诊断指令，仅 debug/admin 可见 | `/debug routes`, `/debug topics` | P2 |
| `future_job` | 未来 Runtime Job Queue 可消费的长任务 | `/research`, `/ingest` | 只预留 |

Phase 2 的首批推荐内置指令：

- `/help`：返回可用命令清单和简短帮助。
- `/commands`：返回结构化命令清单，供前端补全。
- `/clear`：清空当前前端会话显示或请求客户端重置上下文，具体副作用要通过结果协议表达，后端不直接操作浏览器状态。
- `/status`：返回 system / patchouli / alice 的基础健康摘要。
- `/models ready`：代理现有模型 ready 检查能力。

不建议 Phase 2 立即实现高风险指令：

- 删除记忆、批量 archive、清空 topic、取消所有任务等破坏性操作。
- 需要多步确认的命令。
- 需要 Runtime Job Queue 的长任务命令。

### 6.4 指令注册表

新增包建议：

```text
src/hivememory/system/gateway/commands/
  __init__.py
  models.py          # command definition / parse result / execution result
  registry.py        # CommandRegistry
  parser.py          # command line tokenizer / arg parser
  dispatcher.py      # route target dispatch
  builtins.py        # register_builtin_commands()
  handlers.py        # simple system-owned handlers
```

核心注册模型草案：

```python
class CommandDefinition(BaseModel):
    command_id: str                    # stable id, e.g. "system.help"
    category: CommandCategory
    primary_name: str                  # "/help"
    aliases: list[str] = []
    summary: str
    description: str | None = None
    argument_schema: dict[str, Any] = {}
    route_target: CommandRouteTarget
    permission: CommandPermissionPolicy
    enabled: bool = True
    hidden: bool = False
    priority: int = 100
```

解析结果模型草案：

```python
class CommandParseResult(BaseModel):
    command_id: str
    raw_input: str
    name: str
    args: dict[str, Any] = {}
    tokens: list[str] = []
    matched_alias: str | None = None
    parse_status: Literal["matched", "invalid_args", "unknown"]
    error: str | None = None
```

注册规则：

- 内置命令通过 `register_builtin_commands(registry)` 注册。
- 后续插件/模块可通过 composition root 注册扩展命令，但 Phase 2 不做动态插件加载。
- `command_id` 必须全局唯一，建议命名空间格式：`system.help`、`runtime.status`、`patchouli.topic.reset`。
- `primary_name` 和 `aliases` 必须全局唯一；冲突时启动失败，而不是运行期随机覆盖。
- registry 提供只读 listing 给前端和 `/help`，隐藏命令默认不出现在普通 listing。

匹配优先级：

1. 精确 alias/name 匹配优先于正则/前缀匹配。
2. 长命令名优先于短命令名，例如 `/models ready` 优先于 `/models`。
3. priority 值更小者优先。
4. 发生歧义时返回 `invalid_args` 或 `ambiguous`，不执行副作用。

参数解析：

- Phase 2 使用轻量 command-line tokenizer，支持 quoted string 和 `--key value` / `--flag`。
- 不支持 shell expansion、管道、重定向、子命令执行。
- 参数校验基于每条 command definition 的 schema 或 parser callable。

### 6.5 TheEye 拦截与路由

推荐处理链：

```text
User input
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> RuleInterceptor.intercept()
  -> CommandRegistry.match_and_parse()
  -> GatewayResult(intent=SYSTEM, command=CommandParseResult)
  -> TheEye wraps EyeGazeResult
  -> ChatApplicationService detects SYSTEM command
  -> SystemCommandDispatcher.execute()
  -> CommandExecutionResult
  -> HTTP/SSE response
```

关键边界：

- `RuleInterceptor` 只做匹配和解析，不执行命令。
- `TheEye` 只把 command parse result 带出，不根据 route target 调 handler。
- `ChatApplicationService` 或新的 system application service 是指令执行入口。
- `CommandDispatcher` 根据 `route_target` 调用本地 handler、GlobalSystemBus route 或未来 Job Queue。
- Phase 2 不让 Patchouli `prepare_agent_run()` 消费系统指令；系统指令应在进入普通 Alice run 前短路。

Route target 草案：

```python
class CommandRouteTarget(BaseModel):
    kind: Literal["local_handler", "global_route", "client_action", "future_job"]
    name: str
    payload_template: dict[str, Any] = {}
```

执行结果草案：

```python
class CommandExecutionResult(BaseModel):
    command_id: str
    status: Literal["completed", "rejected", "failed", "requires_confirmation", "not_implemented"]
    message: str
    data: dict[str, Any] = {}
    client_action: dict[str, Any] | None = None
    error_code: str | None = None
```

Chat/SSE 行为：

- 非流式 `/chat` 如果命中系统指令，直接返回 command result 包装后的 `AgentRunResult` 或新增稳定 command response envelope。
- 流式 `/chat/stream` 如果命中系统指令，发送 `command_result` 事件，然后发送 `done`。
- 不进入 Patchouli prepare，不创建新 topic，不触发 retrieval，不触发 Alice generation，不触发 active memory generation。

需要注意：当前 active chat 为了 topic routing 仍由 `prepare_agent_run()` 内部调用 gaze。Phase 2 如要实现“系统指令在 prepare 前短路”，可以在 `ChatApplicationService` 中增加轻量 pre-gaze 分支，但这会触碰 chat 时序。建议 Phase 2 先以最小改动落地 command parse/result 模型和 dispatcher，可选地只在现有 prepare 返回的 `gaze_result.intent == SYSTEM` 后短路；完整的 `GatewayContextProvider -> Gateway workflow -> prepare_agent_run(gateway_state=...)` 时序重置放到 Phase 3 前置重构。

### 6.6 权限与安全

权限模型先保持简单，但必须显式存在。

```python
class CommandPermissionPolicy(BaseModel):
    visibility: Literal["public", "debug", "admin"] = "public"
    allowed_agent_ids: list[str] | None = None
    allowed_user_ids: list[str] | None = None
    requires_confirmation: bool = False
    destructive: bool = False
```

Phase 2 权限检查输入：

- `Identity.user_id`
- `Identity.agent_id`
- system debug mode
- command definition permission policy

Phase 2 默认策略：

- public 指令普通用户可见可执行。
- debug 指令仅 `config.system.debug=true` 或测试环境可见。
- admin 指令先不开放；如实现，只允许显式 allowlist。
- destructive 指令即使注册，也必须返回 `requires_confirmation`，Phase 2 不执行二次确认链路。
- unknown command 不交给 LLM 猜测执行，应返回明确错误或作为普通聊天进入后续流程，具体策略由配置控制。

安全约束：

- 指令参数不进入 shell。
- 不允许 command alias 与普通 URL scheme 或 markdown link 混淆。
- 不允许 LLM analyzer 伪造 command parse result；系统指令只由 L1 registry/parser 产生。
- 所有执行结果必须进入 runtime events 或日志，至少包含 `command_id`、status、identity、trace_id。

### 6.7 前端协作

Phase 2 后端应提供足够协议，使前端可以选择增强体验，但不强制第一版完成完整命令面板。

前端可选能力：

- 输入框 `/` 触发命令补全。
- 展示命令 summary、参数提示和禁用原因。
- 对 `requires_confirmation` 展示确认 UI。
- 对 `command_result` SSE 事件展示非 token 类型结果。
- 对 `client_action` 执行本地 UI 行为，例如清空当前会话显示。

后端接口建议：

- 复用 `/chat` / `/chat/stream` 执行命令，不新增独立执行入口。
- 可新增只读命令 listing API，例如 `GET /system/commands`，也可以先通过 `/commands` 指令返回。
- SSE 新事件建议：

```text
event: command_result
data: CommandExecutionResult
```

第一版前端最低要求：

- 不把系统指令结果当作普通 assistant token 拼接。
- 能展示 `message`。
- 能处理 `client_action={"type": "clear_chat"}` 这类本地动作。

### 6.8 验收

Phase 2 完成条件：

1. `CommandRegistry` 可注册、列出、匹配、解析内置命令。
2. `RuleInterceptor` 的系统指令匹配来源从硬编码 regex 切换到 registry。
3. `GatewayResult` / `EyeGazeResult` 在 `SYSTEM` intent 下能携带结构化 command parse result。
4. `CommandDispatcher` 可执行至少 `/help`、`/commands`、`/status` 中的两类非破坏性指令。
5. 未知命令、参数错误、权限拒绝、未实现 route target 都有稳定错误结果。
6. 系统指令不会触发 retrieval、topic creation、Alice generation 或 active memory generation，除非该指令明确路由到对应能力。
7. 命令执行产生可观测日志或 runtime event。
8. 单元测试覆盖 registry、parser、interceptor、dispatcher、权限拒绝和 chat/stream 短路行为。

### 6.9 分阶段推进计划

Phase 2 内容较多，建议拆成可独立提交、可独立回归的 6 个小阶段。每个阶段只引入一个主要风险面，避免同时修改 Gateway、ChatApplicationService、前端协议和权限模型。

#### Phase 2.0: Command Core Foundation

目标：先落地纯数据与纯解析能力，不接入热路径。

实现范围：

- 新增 `hivememory.system.gateway.commands` 包。
- 新增 `CommandDefinition`、`CommandCategory`、`CommandParseResult`、`CommandPermissionPolicy`、`CommandRouteTarget`、`CommandExecutionResult`。
- 实现 `CommandRegistry.register()`、`get()`、`list()`、`match()`。
- 实现轻量 tokenizer，支持 `/cmd`、`/cmd sub`、quoted string、`--key value`、`--flag`。
- 实现 `register_builtin_commands()`，先注册 `/help`、`/commands`、`/clear`、`/status` 的 definition，但不执行真实副作用。

不做：

- 不改 `RuleInterceptor`。
- 不改 `GatewayResult` / `EyeGazeResult`。
- 不接入 chat / stream。

验收：

- registry/parser 单测通过。
- command id 和 alias 冲突会启动期失败或注册时报错。
- unknown / invalid args / ambiguous 有稳定 parse status。

#### Phase 2.1: Gateway L1 Integration

目标：把系统指令识别从硬编码 regex 切到 registry，但仍不执行命令。

实现范围：

- `RuleInterceptor` 接收可选 `CommandRegistry` 或 `CommandMatcher`。
- `create_interceptor()` 由 System Gateway factory 注入 registry。
- `InterceptorResult` 或 `GatewayResult` 扩展可选 `command` 字段。
- `GatewayEngine.process()` 在 L1 命中系统指令时保留 command parse result。
- `TheEye.gaze()` 将 command parse result 转入 `EyeGazeResult`。

不做：

- 不新增 command dispatcher。
- 不改变 chat prepare/run/finalize 时序。
- 不让 L2 analyzer 生成 command。

验收：

- `/help`、`/commands`、`/status` 命中 `GatewayIntent.SYSTEM`，并携带结构化 command。
- 非命令输入保持 RAG/CHAT 行为不变。
- L1 命中系统指令时不调用 L2。

#### Phase 2.2: Command Dispatcher and Built-in Handlers

目标：让系统指令有统一执行入口和统一结果协议。

实现范围：

- 新增 `SystemCommandDispatcher`。
- 支持 `local_handler` route target。
- 支持 `client_action` route target。
- 支持 `global_route` route target 的基本调用封装。
- 实现 `/help`、`/commands`、`/clear` 的 handler。
- `/status` 可以先返回 system 层摘要；跨子系统健康信息可后续扩展。
- 实现权限检查：public/debug/admin、allowlist、destructive、requires_confirmation。

不做：

- 不实现破坏性命令的确认执行链。
- 不实现 future job。
- 不新增复杂 memory mutation 命令。

验收：

- dispatcher 单测覆盖 completed/rejected/failed/requires_confirmation/not_implemented。
- `/clear` 返回 `client_action={"type": "clear_chat"}`，后端不直接操作前端状态。
- debug/admin 命令默认不可见或不可执行。

#### Phase 2.3: Chat / Stream Command Short-Circuit

目标：把 command dispatcher 接入用户可见入口，并确保系统指令不进入普通 Agent run。

可选实现路线：

- 保守路线：沿用当前 `prepare_agent_run()` 内部 gaze 时序，prepare 返回后若 `prepared.gaze_result.intent == SYSTEM`，ChatApplicationService 立即执行 command 并清理 prepared run。该路线改动小，但可能临时产生 topic prepare，需要额外保护。
- 推荐路线：在 ChatApplicationService 中增加 command-only pre-gaze。该 pre-gaze 不需要 topic routing，可只传入空 topic snapshots 或最小 identity；命中明确 command 后直接短路，未命中再走现有 Patchouli prepare。该路线更符合系统指令入口语义，但会引入一条轻量 gaze 分支。
- 最终路线：Phase 3 前置重构中改为 `GatewayContextProvider -> Gateway workflow -> prepare_agent_run(gateway_state=...)`，届时移除临时分支。

Phase 2 推荐采用“推荐路线”，但必须保持范围克制：

- 只用于 slash command 的 L1 快速识别。
- 不做普通自然语言 intent pre-gaze。
- 不处理复合输入。

实现范围：

- `ChatApplicationService.chat()` 命中系统指令时返回 command result。
- `ChatApplicationService.chat_stream()` 命中系统指令时发送 `command_result`，随后发送稳定 `done`。
- 系统指令短路时不调用 Patchouli prepare、Alice run、Patchouli finalize。
- 非系统指令继续走现有 prepare/run/finalize。

验收：

- `/help` 不触发 retrieval/topic prepare/Alice generation。
- `/chat/stream` 的 `command_result -> done` 顺序稳定。
- 非命令 chat stream 的 `topic_info -> memory_refs -> token -> done` 顺序保持不变。

#### Phase 2.4: Configuration, Observability, and Frontend Contract

目标：补齐配置、事件、HTTP/SSE 协议和前端最小协作面。

实现范围：

- 新增 `SystemCommandConfig` 并挂到 `SystemGatewayConfig.commands`。
- 支持 `enabled`、`unknown_command_policy`、`expose_listing`、`enable_debug_commands`、`builtin` overrides。
- command execution 记录日志或 runtime event，包含 `command_id`、status、identity、trace_id。
- SSE 支持 `command_result` 事件。
- 前端最小处理 `command_result.message` 和 `client_action.type == "clear_chat"`。

不做：

- 不要求完整命令面板。
- 不要求所有命令参数 UI 自动生成。

验收：

- 配置默认值单测通过。
- 禁用 commands 后系统指令不会短路执行。
- 前端不会把 command result 拼进 assistant token。

#### Phase 2.5: Cleanup and Compatibility Tightening

目标：收口临时兼容点，减少 Phase 3 前的技术债。

## 7. Phase 3: Gateway Workflow 架构重设计

> **注**：Phase 3 的范围不再包含复合意图分解的真实实现。Phase 3 只完成 Gateway Workflow 的单主意图路径重构，并为 Phase 4 的复合意图分解保留 placeholder、trace 字段和协议边界。

### 7.1 现状

当前 Gateway（`GatewayEngine` + `TheEye`）采用单次 LLM 多任务输出模型（”LLM Router”），在一次推理中同时完成意图分类、查询改写、话题路由、记忆价值判断等多项任务。

**核心限制：**

1. **决策粒度与信息时序错位**
   - 话题路由需要先完成语义理解，才能判断关联话题
   - 记忆价值判断需要先知道内容类型，才能评估写入收益
   - 复合意图分解需要先识别边界，才能分出子意图；该能力依赖下游多分支消费语义，推迟到 Phase 4
   - 这些任务存在自然依赖顺序，但单次推理将它们压缩到同一时刻，每项决策都缺乏前置信息

2. **”博而不精”效应**
   - 单个 Prompt 承载越多任务，每项任务的推理质量越低
   - 当前 L2 语义分析器使用同一段输出同时填充多个决策字段，其中最复杂的话题路由尤其受影响

3. **扩展性壁垒**
   - 现有 `GatewayResult` 字段已趋于饱和；若要加入检索模式预选择、规划信号、任务队列触发等维度，只能继续堆砌 JSON 字段，无法结构化地表达决策依赖关系
   - 未来的 Deep Research、文档解析等能力难以以自然方式接入现有单次输出模型

4. **可控性不足**
   - 自由文本的单次 LLM 输出无法在中间插入业务校验，每项决策的来源和置信度不透明
   - 当某项决策出错时，无法单独修正该决策点，只能重跑整个分析过程

### 7.2 目标

Phase 3 的目标是将 Gateway 从单次 LLM 路由器改造为一等子系统：`GatewaySystem` 实现 `SubsystemProtocol`，`GatewayRuntime` 承载运行时装配和本地总线，`GatewayService` 承载对外业务入口，内部以结构化的 **多阶段决策 Pipeline（Gateway Workflow）** 完成单主意图决策。

Phase 3 不再把 `GatewayFacade` dataclass、`GatewayBundle`、`TheEye.gaze()` 或 `EyeGazeResult` 兼容投影作为目标结构的一部分。此前 Phase 1/2 的兼容入口如果仍存在，应在 Phase 3 子系统化整理中删除或迁移为新结构的一部分；不再新增过渡 shim。

Phase 3 完成后，Gateway 应自然承担以下职责：

1. **话题路由**：上下文选择与话题切换判断
2. **记忆价值预判断**：写入信号提前生成，供下游感知层参考
3. **检索模式预选择**：dense / sparse / hybrid / skip 提前确定，减少检索层决策压力
4. **复合意图占位**：识别可疑复合输入并记录 deferred signal，但不拆分、不多分支执行
5. **规划路由（预留）**：复杂多步任务的前置规划，为未来 Planning 能力预留接入点

**设计原则：**

- **子系统契约优先**：Gateway 与 Patchouli、Alice 平级，必须遵守 `System/Runtime/Service/local bus/global bridge` 的工程约束。
- **结构固定、LLM 局部**：Pipeline 的阶段图（Stage Graph）由代码固定，只在特定 Stage 内注入 LLM 调用；整体流程可预测，不依赖 LLM 自由决定下一步。
- **一步到位迁移**：Phase 3 不保留“旧行为等价回退”或“新旧双入口并存”的过渡结构；行为变化接受为本次重构的一部分。
- **可观测**：每个 Stage 的输入、输出、耗时、fallback 标记都记录在 `GatewayState.stage_trace` 中。
- **只读下传**：`GatewayState` 在 Pipeline 执行完毕后封印（seal），传递给下游时不可变。
- **单主分支模型**：Phase 3 对下游始终输出一个 `GatewayState`，不输出 `list[GatewayState]`，避免提前要求 Patchouli / Alice 支持多分支合并。

Phase 3 明确不实现：

- 不实现 LLM 复合意图分解 Prompt。
- 不生成 `SubIntent` 列表。
- 不执行多分支 S1→S5。
- 不定义多分支结果合并、串并行调度或跨分支依赖语义。

#### 7.2.1 前置重构：Gateway 子系统化与 `prepare_agent_run()` 原地改造

Phase 3 的第一项前置工作不是继续加厚 `GatewayFacade`，而是把当前 Gateway 骨架整理成标准子系统，并同步修正 active chat 热路径中的 Gateway / Patchouli 时序问题。

目标子系统结构：

```text
GatewaySystem
  - 实现 SubsystemProtocol
  - 持有 GatewayRuntime / GatewayService
  - start() 挂载本地路由并注册公开路由
  - stop() 卸载公开路由和本地路由
  - health() 返回 pipeline、local routes、engine readiness 等状态

GatewayRuntime
  - 持有 GatewayBus
  - 构建 engines.gateway 决策原语
  - 构建 GatewayPipeline、Stage、GatewayContextProvider
  - 挂载 GatewayLocalRoutes
  - 通过 GatewayContextProvider 获取 Patchouli active topics 与路由后完整话题上下文等跨子系统只读能力

GatewayService
  - process(message, identity=...) -> GatewayState
  - execute_command(...) 或 command 相关入口
  - 不负责底层装配，不直接构建 engine / stage

GatewayPublicRoutes
  - PROCESS：global bus public route，handler 绑定到 GatewayService.process
  - COMMAND_EXECUTE / ANALYZE：如后续需要，可作为显式 public route 增加
```

当前 `prepare_agent_run()` 同时承担三类职责：

1. 为 Gateway 准备输入：构造 `Identity`，获取 active topic snapshots。
2. 调用 Gateway：通过 `PatchouliLocalRoutes.GATEWAY_GAZE` 请求 TheEye 或旧 Gateway。
3. 消费 Gateway 输出：prepare topic、预检索、编译 memory context、构造 `PreparedAgentRun`。

这会造成 Patchouli prepare 反向持有 Gateway 调用权，也会让“Gateway 是系统入口”的语义被 topic snapshots 获取流程打断。Phase 3 保留 `prepare_agent_run()` 作为公开 prepare 方法，并原地改变其契约：

```python
async def prepare_agent_run(
    self,
    user_message: str,
    user_id: str,
    *,
    gateway_state: GatewayState,
    agent_id: str = "omni_doll",
    session_id: str | None = None,
    enable_memory_retrieval: bool = True,
    generation_options: dict[str, Any] | None = None,
) -> PreparedAgentRun:
    ...
```

新的 active chat 时序：

```text
ChatApplicationService.chat_stream()
  -> identity = Identity(user_id, agent_id, session_id)
  -> gateway_state = GlobalSystemBus.request(
         GatewayPublicRoutes.PROCESS,
         message=user_message,
         identity=identity,
     )
     ├─ S0 CommandInterceptor 可先短路，无需加载 topic snapshots
     └─ 未短路时由 GatewayService 内部执行：
        1. GatewayContextProvider.prepare_candidate_topics(identity)
        2. S1 TopicRouter
        3. GatewayContextProvider.prepare_routed_topic(identity, topic_id)
        4. S2-S6 后续 Pipeline

         ...

  -> PatchouliService.finalize_agent_run(...)
```

其中 active topic snapshots 与完整话题上下文的获取都属于 **GatewayContextProvider 的跨子系统只读上下文准备能力**，不是独立 workflow Stage，也不是 `TopicRouter` Stage 的隐藏副作用，更不是 Patchouli prepare 的中间步骤。这里必须区分两类上下文：

- **候选话题上下文（CandidateTopics）**：路由前可获得的 `identity`、active topic snapshots、topic menu、provider 状态。它只能帮助 Gateway 判断“可能路由到哪里”，不能代表已经选定的话题上下文。
- **路由后完整话题上下文（RoutedTopicContext）**：S1 `TopicRouter` 选定 `topic_id` 后，Gateway 再通过 Patchouli public route 获取的完整短期话题上下文。它是后续意图分类、指代消解、记忆价值预判和检索策略预判断的必要输入。
- **Gateway 决策字段**：由后续 Stage 产出的 `intent_type`、`rewritten_query`、`search_keywords`、`memory_write_signal`、`retrieval_strategy` 等字段。下游 Patchouli prepare 应消费这些结果，而不是在 Gateway 前预先构造准确 session context。

```python
class GatewayContextProvider:
    async def prepare_candidate_topics(self, *, identity: Identity) -> CandidateTopics:
        topic_snapshots = await self._global_bus.request(
            GlobalRoutes.PATCHOULI_TOPIC_LIST_ACTIVE,
            identity=identity,
        )
        return CandidateTopics(
            identity=identity,
            topic_snapshots=topic_snapshots,
        )

    async def prepare_routed_topic(
        self,
        *,
        identity: Identity,
        topic_id: str,
    ) -> RoutedTopicContext:
        if topic_id == "NEW_TOPIC":
            return RoutedTopicContext.empty(identity=identity, topic_id=topic_id)
        return await self._global_bus.request(
            GlobalRoutes.PATCHOULI_TOPIC_GET_CONTEXT,
            identity=identity,
            topic_id=topic_id,
        )
```

`GatewayContextProvider` 的实现可以通过 System GlobalBus 调用 Patchouli public routes；但 Gateway Pipeline 和各 Stage 只接收 `CandidateTopics` / `RoutedTopicContext` 数据对象，不直接 import Patchouli，也不在路由 Stage 内部发总线请求。

为避免系统指令也触发 topic list I/O，`GatewayService.process()` 可以采用两段式入口：

1. 先执行轻量 S0 command parse，命中系统指令时直接短路。
2. 未命中 command 时调用 `GatewayContextProvider.prepare_candidate_topics(identity)`，随后进入 Pipeline。
3. S1 `TopicRouter` 提交 `topic_id` 后，`GatewayService` 或 Runner 调用 `GatewayContextProvider.prepare_routed_topic(identity, topic_id)`，再继续执行需要完整话题上下文的后续 Stage。

### 7.3 核心设计：Pipeline + Stage 模型

#### 7.3.1 Pipeline 结构

```
GatewayService.process(message, identity)
  │
  Stage 0  CommandInterceptor     ──轻量规则/模式匹配，命中即短路，~0ms
  │未命中 ↓
  GatewayContextProvider.prepare_candidate_topics(identity)
  │            ──获取 active topic snapshots；失败时空候选 fallback，不作为 workflow Stage
  │
  GatewayPipeline
  │
  Stage 1  TopicRouter            ──只做话题路由，LLM or 规则，~80ms
  │
  GatewayContextProvider.prepare_routed_topic(identity, topic_id)
  │            ──根据路由结果获取完整话题上下文；NEW_TOPIC 时返回空 RoutedTopicContext
  │
  Stage 2  IntentClassifier       ──基于路由后上下文分类意图类型 + 是否复合，~80ms
  │
  Stage 3  CompositePlaceholder   ──不调 LLM；记录复合意图延后信号，~0ms
  │
  ↓ [asyncio.gather 并发]
  Stage 4a MemoryValueJudge       ──基于完整话题上下文预判写入价值，生成 MemoryWriteSignal
  Stage 4b QueryUnderstanding     ──基于完整话题上下文做指代消解，生成 rewritten_query/search_keywords
  │
  ↓ [合并]
  Stage 5  RetrievalStrategyPicker──确定检索参数（模式/Top-K/权重），依赖意图与 query understanding
  │
  Stage 6  PlannerRouter          ──[预留] 复杂任务规划，Phase 3 不实现
  │
  ↓
  GatewayState (sealed) → 下游（Alice / Patchouli）
```

说明：S0 可以作为 `GatewayService` 的轻量前置短路阶段运行，也可以在实现上保留为 Pipeline 的第一个 Stage；关键约束是 command 命中时不得为了 topic routing 再加载 active topics。非 command 路径中，Gateway 先通过 `GatewayContextProvider.prepare_candidate_topics(identity)` 获取候选话题列表，再进行 TopicRouter。TopicRouter 只提交话题路由字段；`rewritten_query`、`search_keywords` 必须在路由后完整话题上下文可用后，由 QueryUnderstanding 类 Stage 生成。`IntentClassifier` 不应作为第一步，因为此时尚未完成话题路由，无法得到准确的路由后上下文；它应消费 `topic_id`、`RoutedTopicContext` 和候选话题信号。

#### 7.3.2 Stage 接口契约

每个 Stage 是一个无状态执行单元，只读取 `GatewayState`，并返回 `StageResult`：

```python
class GatewayStage(Protocol):
    """
    每个 Stage 是幂等的 GatewayState -> StageResult 适配器。
    - 正常路径：返回本 Stage 拥有字段的 GatewayPatch
    - 短路路径：通过 StageResult.flow_end_reason 请求终止后续 Stage
    - Fallback：Stage 内部处理异常，以默认 StageResult 返回保守值，并标记 is_fallback
    """
    stage_name: str
    writable_fields: frozenset[str]

    async def process(self, state: GatewayState) -> StageResult: ...
```

`GatewayState` 不允许 Stage 直接写字段。Runner / Service 是唯一提交点，调用 `GatewayState.apply_stage_result(stage_name, result, duration_ms, writable_fields)` 完成字段写入、字段所有权校验、trace 追加和 flow end 处理。`stage_trace` 不进入 `GatewayPatch`，也不允许由 Stage 手动追加。

#### 7.3.3 Pipeline Runner

```python
class GatewayPipeline:
    def __init__(self, stages: list[GatewayStage]) -> None: ...

    async def run(self, state: GatewayState) -> GatewayState:
        for stage in self.stages:
            start = monotonic()
            result = await stage.process(state)
            state.apply_stage_result(
                stage_name=stage.stage_name,
                result=result,
                duration_ms=(monotonic() - start) * 1000,
                writable_fields=stage.writable_fields,
            )
            if result.flow_ended:
                break
        return state.seal()  # 封印后返回，下游只读
```

### 7.4 GatewayState 数据结构

### 7.5 Stage 详细设计

#### Stage 0：EntryInterceptor

- **输入**：`GatewayState.raw_message`
- **处理**：复用 `RuleInterceptor` / `CommandRegistry`，统一处理系统指令与简单闲聊
- **输出**：命中 command 时写入 `l1_result`、`intent_type=UNKNOWN`、`command_parse_result`，通过 `flow_end_reason="system_command"` 终止；命中 simple chat 时只写 `l1_result`、`intent_type=CHAT`，通过 `flow_end_reason="simple_chat"` 终止
- **短路条件**：命中系统指令或明确无需后续 Gateway 决策的简单闲聊
- **Fallback**：无需 fallback，规则匹配不调 LLM；未命中时透明放行
- **关键约束**：S0 不拥有 `rewritten_query`、`search_keywords`、`memory_write_signal`、`retrieval_strategy` 等后续字段；simple chat 的 skip 检索/skip 写入语义由 `GatewayState` 的 effective 派生方法提供，不通过 S0 写后续字段实现

#### Stage 1：TopicRouter

- **输入**：`raw_message` + `candidate_topics.topic_snapshots`
- **处理**：只判断本轮输入应路由到已有话题还是新话题；可使用一次窄 Prompt 或规则/LLM 组合调用
- **输出**：`topic_id`、`new_topic_title`、`new_topic_summary`、`routing_reason`（仅 trace/debug 使用）
- **禁止输出**：`rewritten_query`、`search_keywords`、`retrieval_strategy`、`memory_write_signal`
- **Fallback**：话题路由失败时，写入 `topic_id="NEW_TOPIC"`，必要时生成空 `new_topic_title/new_topic_summary`；在 trace 中标记 fallback
- **说明**：TopicRouter 只承接旧 `L2 LLMAnalyzer` 中的话题选择能力。query rewrite、keywords 和检索策略不属于 TopicRouter，必须在完整 `RoutedTopicContext` 可用后由后续 Stage 处理

#### Provider Step：RoutedTopicContext Preparation

- **位置**：S1 TopicRouter 提交 `topic_id` 之后，S2 IntentClassifier 之前
- **输入**：`identity` + `topic_id`
- **处理**：`GatewayService` 或 Runner 调用 `GatewayContextProvider.prepare_routed_topic(identity, topic_id)`；`topic_id="NEW_TOPIC"` 时直接返回空 `RoutedTopicContext`
- **输出**：`routed_topic_context`
- **Fallback**：完整话题上下文获取失败时使用空 `RoutedTopicContext` 继续执行，并在 trace/event 中标记 context 缺失
- **关键约束**：这不是 workflow Stage，不参与 engine 决策，也不由 TopicRouter 发起总线请求；它是 Gateway 子系统对 Patchouli public route 的受控只读访问

#### Stage 2：IntentClassifier

- **输入**：`raw_message` + `topic_id` + `candidate_topics` + `routed_topic_context`
- **处理**：单次窄分类调用，只判断意图类型和是否复合，不做话题路由、不做查询改写、不判断检索策略
- **输出**：`intent_type`、`is_composite`
- **Fallback**：LLM 调用失败或解析失败时，写入 `intent_type=QUERY`、`is_composite=False`，在 trace 中标记 `is_fallback=True`；Pipeline 继续执行，不抛出异常
- **关键约束**：IntentClassifier 必须在 TopicRouter 之后执行。很多输入的意图依赖话题路由信号，例如“继续刚才那个”“把这个记下来”“查一下它的部署方式”，不能在候选上下文尚未收敛时做最终分类

#### Stage 3：CompositePlaceholder

- **触发条件**：始终执行，但不调用 LLM
- **输入**：`is_composite`、`raw_message`、`intent_type`、`topic_id`、`routed_topic_context`
- **处理**：
  - `is_composite=False`：透明通过，仅在 trace 中记录 `skipped`
  - `is_composite=True`：写入 `composite_deferred=True` 和 `composite_deferred_reason`，继续按单主意图处理
- **输出**：不生成 `sub_intents`，不改变下游输入形态
- **Fallback**：无需 fallback；该 Stage 为纯规则占位
- **关键约束**：Phase 3 不允许在此 Stage 引入多轮 LLM 分解或多分支执行。该 Stage 的价值是把 Phase 4 的接入点固定下来，同时保持 Phase 3 热路径可控

#### Stage 4a：MemoryValueJudge

- **并发运行**：与 Stage 4b 通过 `asyncio.gather` 同时执行
- **输入**：`intent_type` + `topic_id` + `routed_topic_context` + `raw_message`
- **处理**：轻量 LLM 分类或规则判断，评估本次交互的记忆写入价值
- **输出**：`memory_write_signal`（`WRITE` / `SKIP` / `UNKNOWN`）
- **Fallback**：调用失败时写入 `UNKNOWN`，由下游感知层使用其自身逻辑决策；不阻断 Pipeline

#### Stage 4b：QueryUnderstanding

- **并发运行**：与 Stage 4a 通过 `asyncio.gather` 同时执行
- **输入**：`intent_type` + `topic_id` + `routed_topic_context` + `raw_message`
- **处理**：基于完整话题上下文进行指代消解和检索锚点提取，处理“把它改一下”“继续刚才那个方案”等依赖历史上下文的输入
- **输出**：`rewritten_query`、`search_keywords`
- **Fallback**：调用失败或上下文缺失时写入 `rewritten_query=raw_message`、`search_keywords=[]`，并在 trace 中标记 fallback
- **关键约束**：这是 `rewritten_query/search_keywords` 的唯一写入者；TopicRouter、IntentClassifier 和 RetrievalStrategyPicker 均不得写入这两个字段

#### Stage 5：RetrievalStrategyPicker

- **输入**：`intent_type` + `topic_id` + `rewritten_query` + `search_keywords` + `routed_topic_context` + `retrieval_mode` hint（可选）
- **处理**：基于意图类型、话题路由结果和查询形态，通过规则或轻量 LLM 调用选择检索参数
- **输出**：`retrieval_strategy`（`mode`、`top_k`、`dense_weight`、`sparse_weight`）
- **Fallback**：调用失败时写入默认 `RetrievalStrategy(mode=HYBRID, top_k=5)`；不阻断 Pipeline

#### Stage 6：PlannerRouter（预留）

- **Phase 3 不实现**；仅在 Pipeline 构造时保留 noop Stage 或空 slot
- 未来用于：检测需要多步规划的复杂意图，生成 `ExecutionPlan` 交由 Alice 或 Job Queue 消费

### 7.6 并发模型

Stage 4a 和 Stage 4b 通过 `asyncio.gather` 并发执行。为避免两个并发 Stage 直接修改同一个 `GatewayState`，Phase 3 要求并发 Stage 返回 `StageResult` / `GatewayPatch`，再由 Pipeline Runner 统一提交：

```python
# GatewayPipeline 内部 _run_concurrent_stage_4 实现
async def _run_s4(self, state: GatewayState) -> GatewayState:
    results = await asyncio.gather(
        self._s4a.process(state),
        self._s4b.process(state),
        return_exceptions=True,
    )

    for stage, result in zip((self._s4a, self._s4b), results):
        if isinstance(result, Exception):
            # 单个 Stage 失败不影响另一个的结果；
            # 对应 Stage 的 fallback result 由 wrapper 生成并提交
            continue
        state.apply_stage_result(
            stage_name=stage.stage_name,
            result=result,
            duration_ms=result.metadata.get("duration_ms", 0.0),
            writable_fields=stage.writable_fields,
        )

    return state
```

并发安全保证：S4a 和 S4b 只读取提交前的 `GatewayState` 快照，不直接写入同一个对象。提交时校验 patch 的字段所有权：S4a 只能写 `memory_write_signal`，S4b 只能写 `rewritten_query/search_keywords`，`stage_trace` 由 Runner 追加。Stage 5 `RetrievalStrategyPicker` 必须在 S4b 提交后执行，因为它依赖最终的 query understanding 输出。

### 7.7 Fallback 策略

每个 Stage 的 fallback 均为"保守默认值 + trace 标记"，不向上抛出异常，确保 Pipeline 永远能走到底部并产出一个可用的 `GatewayState`：

| Stage | Fallback 触发条件 | 写入默认值 | 下游影响 |
| --- | --- | --- | --- |
| Provider `prepare_candidate_topics` | topic list 超时 / 失败 | 空 topic snapshots | TopicRouter 可退化为新话题路由 |
| S1 TopicRouter | LLM 调用失败 / 解析失败 | `topic_id="NEW_TOPIC"` | 后续使用空 `RoutedTopicContext` |
| Provider `prepare_routed_topic` | topic context 超时 / 失败 | 空 `RoutedTopicContext` | QueryUnderstanding 退化为原始 query |
| S2 IntentClassifier | LLM 调用失败 / 解析失败 | `intent_type=QUERY, is_composite=False` | S3 透明通过，继续单主意图路径 |
| S3 CompositePlaceholder | 无 LLM 调用 | `composite_deferred=True`（仅当 S2 判定复合） | 仍按单主意图路径处理 |
| S4a MemoryValueJudge | 调用失败 | `memory_write_signal=UNKNOWN` | 感知层使用自身策略判断，不新增破坏性行为 |
| S4b QueryUnderstanding | 调用失败 / 上下文缺失 | `rewritten_query=raw_message, search_keywords=[]` | 检索锚点退化，但不阻断流程 |
| S5 RetrievalStrategyPicker | 调用失败 | `mode=HYBRID, top_k=5` | 使用默认检索参数，效果轻微下降 |

**原则：** 只有当某个 Stage 的输出是下游业务正确性的绝对前提时，才允许该 Stage 的失败导致整个 Pipeline 中止。Phase 3 中没有这样的 Stage——所有 Stage 均允许 fallback 继续执行。

### 7.8 单主分支模型

Phase 3 始终只执行一条主 Pipeline：

```python
async def process(self, message: str, identity: Identity) -> GatewayState:
    state = GatewayState(
        raw_message=message,
        identity=identity,
        candidate_topics=await self._context_provider.prepare_candidate_topics(
            identity=identity,
        ),
    )
    state = await self._commit(self._s1_topic_router, state)
    state = await self._prepare_routed_topic_context(state)
    state = await self._commit(self._s2_intent_classifier, state)
    state = await self._commit(self._s3_placeholder, state)
    state = await self._run_s4_concurrent(state)
    state = await self._commit(self._s5_retrieval_strategy, state)
    state = await self._commit(self._s6_noop, state)
    return state.seal()
```

这里的 `process()` 表示 command 未命中后的主路径；S0 可以在 `GatewayService` 层提前执行。`prepare_candidate_topics()` 和 `prepare_routed_topic()` 是 Gateway 子系统的上下文准备动作，不注册为业务 Stage。即使 S2 判断 `is_composite=True`，Phase 3 也只记录 `composite_deferred=True`，然后继续使用 S1 的路由结果和路由后上下文作为单主意图输入。这样 Gateway Workflow 的结构、可观测性和配置边界都能先稳定下来，而不会提前把 Patchouli / Alice / Job Queue 拉入多分支协议设计。

Phase 4 再引入：

- `SubIntent` / `CompositeIntent` 输出模型。
- S4 `IntentDecomposer` 的 LLM Prompt 与置信度策略。
- 分支级 S2→S3→S5 执行模型。
- 多分支结果合并、串行/并行执行、依赖关系和失败处理策略。

### 7.9 下游消费与组件布局

#### 下游消费

Phase 3 完成后，下游组件消费路径如下：

- **ChatApplicationService**：只持有 `GlobalSystemBus`，先请求 `GatewayPublicRoutes.PROCESS` 获得 sealed `GatewayState`，再请求 `GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN` 并传入 `gateway_state`；禁止直接持有 `GatewaySystem`、`GatewayService`、`PatchouliSystem` 或 `PatchouliService`。
- **GatewaySystem**：在 `start()` 时把 `GatewayPublicRoutes.PROCESS` 注册到 `GlobalSystemBus`，handler 委托 `GatewayService.process()`；内部 Stage 仍只通过 `GatewayRuntime` 和 local bus 协作。
- **Patchouli**：通过自身 public prepare route 接收 `gateway_state`，`prepare_agent_run()` 原地改造为 Gateway 决策结果的消费者，直接消费 `GatewayState` 或从 `GatewayState` 派生的 `PatchouliPrepareDecision`；记忆写入判断读取 `memory_write_signal`，检索参数读取 `retrieval_strategy`。
- **Alice**：通过 Alice public run route 接收准备好的 Agent run context；如需读取 Gateway 决策字段，也应由上游通过协议模型显式传入，只读，不可修改。
- **未来 Job Queue（v0.6.1）**：Phase 3 仅预留 `execution_plan` 字段（S6 noop），不从 `sub_intents` 派发任务。
- **Phase 4 扩展**：复合意图、多分支消费和 `route_target=future_job` 的分支派发在 Phase 4 统一设计。

#### 组件布局

Phase 3 将 Gateway 升格为顶层独立子系统，与 `patchouli`、`alice` 平级，而不是 `system/` 的内部子目录，也不是一个裸露的 dataclass facade。

**理由：**
- `system/` 应是装配层，它依赖 `gateway`、`patchouli`、`alice`；将 `gateway` 嵌在 `system/` 内会暗示依赖方向错误
- Phase 3 后 Gateway 拥有独立的 Pipeline、Stage、State、Runtime、Service 和本地总线，体量足以支撑顶层模块地位
- Gateway 是每次请求的第一道关卡，架构上比 patchouli/alice 更"上游"，顶层平级更准确

同时，Phase 3 需要继续保持 `engines/gateway` 的纯分析层定位：

- **`hivememory.engines.gateway`**：放“决策原语”，即给定结构化输入后产出结构化判断结果的纯能力；不依赖 SystemBus、Patchouli、Alice、runtime state。
- **`hivememory.gateway`**：放“决策工作流与子系统宿主”，即 GatewaySystem、GatewayRuntime、GatewayService、local bus、GatewayContextProvider、Pipeline、Stage、trace、fallback 和系统接入。

判断标准：

- 适合下沉到 `engines/gateway`：`TopicRouter`、`QueryUnderstanding`、`IntentClassifier`、`MemoryValueJudge`、`RetrievalStrategyPicker`、Phase 4 `IntentDecomposer` 及其输入输出模型。
- 应留在 `hivememory.gateway`：`GatewaySystem`、`GatewayRuntime`、`GatewayService`、`GatewayBus`、`GatewayPipeline`、`GatewayState`、`GatewayContextProvider`、`CandidateTopics`、`RoutedTopicContext`、Stage wrapper、System command dispatcher / handler、active chat 接入适配。
- 不新增 `engines/gateway/prompts` 或专用 JSON parser 包；prompt 文本继续由 i18n 模板统一管理，JSON parsing / schema 解析复用项目已有通用工具函数。

`GatewayService` 是 Phase 3 后对外暴露的业务入口，持有 `GatewayRuntime` 或其必要能力引用：

```python
class GatewayService:
    """
    Gateway 子系统业务入口。
    调用方（ChatService 等）只与此类交互，不感知 Pipeline 内部 Stage 结构。
    """
    def __init__(self, runtime: GatewayRuntime) -> None:
        self._runtime = runtime

    async def process(
        self,
        message: str,
        *,
        identity: Identity,
    ) -> GatewayState:
        """
        执行 Gateway 决策流程，返回封印的 GatewayState。
        S0 命中 command 时直接短路；未命中时再加载 topic snapshots。
        """
        command_state = await self._runtime.command_interceptor.try_process(
            message=message,
            identity=identity,
        )
        if command_state is not None:
            return command_state.seal()

        candidate_topics = await self._runtime.context_provider.prepare_candidate_topics(
            identity=identity,
        )
        state = GatewayState(
            raw_message=message,
            identity=identity,
            candidate_topics=candidate_topics,
        )
        state = await self._runtime.pipeline.run_until_topic_routed(state)
        routed_context = await self._runtime.context_provider.prepare_routed_topic(
            identity=identity,
            topic_id=state.topic_id or "NEW_TOPIC",
        )
        state = state.apply_provider_result(
            provider_name="GatewayContextProvider.prepare_routed_topic",
            routed_topic_context=routed_context,
        )
        return await self._runtime.pipeline.run_after_topic_routed(state)
```

`GatewaySystem` 负责生命周期和路由挂载：

```python
class GatewaySystem(SubsystemProtocol):
    @property
    def name(self) -> str:
        return "gateway"

    @property
    def service(self) -> GatewayService:
        return self._service

    async def start(self) -> None:
        self._runtime.mount_local_routes(self._service)
        self._register_public_routes()

    async def stop(self) -> None:
        self._unregister_public_routes()
        self._runtime.unmount_local_routes()
```

### 7.10 可观测性

- **`stage_trace`**：每个 StageResult 被提交后由 `GatewayState.apply_stage_result()` 追加一条 `StageTrace`，记录 `stage_name`、`duration_ms`、`is_fallback`、`fallback_reason`、`flow_ended`
- **Runtime Events**：Pipeline 执行完成后，向 `event_bus` 发送 `GatewayPipelineCompleted` 事件，携带 `stage_trace` 摘要和关键决策字段
- **调试模式**：`config.gateway.debug_trace=true` 时，`stage_trace` 包含每个 Stage 的完整输入快照，供本地调试使用（不发往前端）
- **可读摘要**：`GatewayState.to_debug_summary() -> str` 提供人可读的单行摘要，格式如：`S0:pass ctx:candidates S1:T_01 ctx:routed S2:QUERY S4a:WRITE S4b:rewrite S5:HYBRID`

### 7.11 验收

Phase 3 验收条件：

1. `GatewaySystem` 实现 `SubsystemProtocol`，并提供 `GatewayRuntime` / `GatewayService` / local bus / public route bridge 的标准子系统结构
2. `GatewayService.process()` 能按 S0→Provider.prepare_candidate_topics→S1(TopicRouter)→Provider.prepare_routed_topic→S2(IntentClassifier)→S3(placeholder)→S4a/S4b(concurrent)→S5(RetrievalStrategy)→S6(noop) 顺序执行完整决策流程
3. S0 命中命令时，GatewayService 短路，`stage_trace` 中有 `flow_ended=True` 记录，且不执行 `prepare_candidate_topics()` / `prepare_routed_topic()`
4. S4a 和 S4b 通过 `asyncio.gather` 并发执行，单个失败不影响另一个结果
5. 所有 Stage 在调用失败时写入规定 fallback 默认值，不向 Pipeline Runner 抛出异常
6. `is_composite=True` 时，S4 只写入 `composite_deferred=True` 和 trace，不调用 LLM、不产出 `sub_intents`、不触发多分支
7. `GatewayState.seal()` 后字段不可修改；下游代码若尝试修改，应在测试中可检测到
8. `GatewayFacade`、`GatewayBundle`、`TheEye.gaze()` active chat 入口和 `EyeGazeResult` 兼容投影均已从 Phase 3 主路径删除
9. `src/hivememory/system/gateway/` 不再作为 Phase 3 兼容 shim 存在；相关代码迁入 `src/hivememory/gateway/`
10. `stage_trace` 在每次 Pipeline 执行后包含所有已执行 Stage 的完整记录
11. Phase 3 期间旧 Gateway/Patchouli/chat 测试不再作为行为兼容约束；新结构完成后按 `GatewaySystem` / `GatewayService` / `GatewayRuntime` 重写测试
12. 下游只接收单一 `GatewayState` 或明确的新决策视图，Phase 3 不出现 `list[GatewayState]` 输出

### 7.12 开放问题

1. S1 `TopicRouter` 是否复用现有 `LLMAnalyzer` + Dispatcher Prompt 中的话题路由思想，还是从零设计新 Prompt？复用更安全但抽象层次低；重设计风险更大但可以针对 Pipeline 语义优化。无论哪种方式，TopicRouter 都不得复用旧 Prompt 中的 query rewrite / keywords 输出职责。
2. `GatewayState.seal()` 的实现方式：使用 `__setattr__` 拦截（需要放弃 `dataclass` 的简洁性），还是通过 Protocol 约束下游只接收 frozen 副本？
3. S5 并发 patch 的字段所有权校验放在 Runner 层，还是放在 `GatewayState.apply_stage_result()` 内部？

## 8. Phase 4: 复合意图分解与多分支语义（规划）

Phase 4 的目标是在 Phase 3 已稳定的 Gateway Workflow 上补齐复合意图分解，而不是把复合意图作为单个 Stage 的孤立能力实现。这里需要同时设计 S4 的分解质量、下游消费方式和失败/合并语义。

### 8.1 Phase 4 范围

Phase 4 需要解决：

1. **S4 IntentDecomposer**：将 `CompositePlaceholder` 替换为真实分解 Stage，输出 `CompositeIntent` / `SubIntent`。
2. **分支执行模型**：定义每个 `SubIntent` 是否独立进入 S2→S3→S5，还是先合并同类意图后再进入下游。
3. **下游消费协议**：明确 Patchouli、Alice、Runtime Job Queue 如何接收多分支结果，避免直接把 `list[GatewayState]` 暴露给不支持多分支的调用方。
4. **合并与排序语义**：定义串行、并行、依赖、失败回退、结果展示和用户确认策略。
5. **系统指令混合输入**：处理“系统指令 + 普通聊天/检索”的复合消息，例如 `/research A，然后把结论写入记忆`。

### 8.2 Phase 4 设计约束

- S4 可以使用 LLM，但必须被固定 workflow 包裹，不能演化成自由 Agent Router。
- `CompositeIntent` 不能只表达“拆成几段”，还必须表达执行目标、依赖关系、置信度和 fallback 策略。
- 多分支协议必须先定义消费方，再决定 Gateway 输出形态；不能在 Gateway 层先输出 `list[GatewayState]` 再要求下游适配。
- 分支失败必须有稳定退路：低置信度、解析失败或合并失败时应回到 Phase 3 单主意图路径。

### 8.3 Phase 4 开放问题

1. `SubIntent` 是否直接绑定 `route_target`，还是只绑定 intent type，由后续 PlannerRouter 决定目标？
2. 多个 QUERY 子意图是分别检索后交给 Alice 合成，还是先在 Gateway 层生成统一 retrieval plan？
3. WRITE 子意图应在 Gateway 阶段生成 memory write request，还是只生成 `memory_write_signal` 供 Patchouli finalize 使用？
4. 复合输入中的系统指令是否允许和普通聊天共享一次响应，还是必须拆成 command result + chat result 两条事件？应由 S0 先拆命令，还是由 S4 统一分解后再路由？
5. Phase 4 是否需要引入 lightweight planner，还是只做 decomposition，不做 task graph？
6. S4 复合意图分解的 Prompt、置信度阈值和 golden dataset 如何设计，才能避免过度分解与漏分解？
7. 多分支结果是否需要一个 `CompositeGatewayResult` envelope，而不是直接暴露 `list[GatewayState]`？
8. 多分支并行时，各分支共享的 `session_context.topic_snapshots` 是否需要克隆（避免并发读取时被修改），还是保证只读即可？

## 9. 数据模型草案

### 9.1 Gateway Result

Phase 1 不扩展 `GatewayResult`，也不新增 system-level envelope。

原因：

- Phase 1 是归属迁移，不改变 GatewayEngine 行为。
- 当前 `GatewayResult -> EyeGazeResult` 的转换已经满足 chat / passive ingress 的兼容需求。
- 系统指令库、Gateway Workflow 与复合意图分解会引入新的 route target / segment 模型，但这属于 Phase 2/3/4。

Phase 1 约束：

- `GatewayResult` 继续属于 `engines/gateway/models.py`。
- `EyeGazeResult` 继续属于 `core/protocol/models.py`。
- `TheEye` 迁移到 System 后仍返回 `EyeGazeResult`。
- 若后续要新增 system-level envelope，应在 Phase 2/3/4 中设计，不在 Phase 1 混入。

### 9.2 System Command

Phase 2 新增系统指令模型，建议放在 `hivememory.system.gateway.commands.models`，不要放进 Patchouli 或 Alice。

核心模型：

```python
class CommandCategory(str, Enum):
    CONVERSATION = "conversation"
    GATEWAY = "gateway"
    MEMORY = "memory"
    RUNTIME = "runtime"
    DEBUG = "debug"
    FUTURE_JOB = "future_job"


class CommandParseStatus(str, Enum):
    MATCHED = "matched"
    UNKNOWN = "unknown"
    INVALID_ARGS = "invalid_args"
    AMBIGUOUS = "ambiguous"


class CommandExecutionStatus(str, Enum):
    COMPLETED = "completed"
    REJECTED = "rejected"
    FAILED = "failed"
    REQUIRES_CONFIRMATION = "requires_confirmation"
    NOT_IMPLEMENTED = "not_implemented"
```

`GatewayResult` 可新增可选字段：

```python
command: CommandParseResult | None = None
```

`EyeGazeResult` 可新增同名可选字段，默认 `None`，保证既有 RAG / CHAT 消费方不受影响。

约束：

- `command` 仅在 `intent == GatewayIntent.SYSTEM` 时有意义。
- `command.parse_status != "matched"` 时不得执行副作用。
- Phase 2 不把 command result 塞进 `rewritten_query` 或 `reason` 字符串中传递。

### 9.3 Intent Segment

单个意图片段是 Phase 4 `IntentDecomposer`（S4）的基本输出单元，也是复合意图分解的最小执行粒度。Phase 3 不实现该模型，只在文档中保留为 Phase 4 草案：

```python
class IntentType(str, Enum):
    QUERY = "query"           # 需要检索历史记忆的问答意图
    WRITE = "write"           # 主动写入/更新记忆的意图
    CHAT = "chat"             # 不需要检索的闲聊意图
    COMPOSITE = "composite"   # 复合意图（仅 S3 输出，S4 分解后不再出现）
    UNKNOWN = "unknown"       # S3 fallback 默认值


class SubIntent(BaseModel):
    """
    单个子意图片段。
    由 Phase 4 S4 IntentDecomposer 输出。
    """
    intent_type: IntentType
    content: str
    # 从原始消息中提取的子意图文本，已完成初步指代消解（相对于原消息）

    original_span: str | None = None
    # 该子意图在原始消息中的原始片段（用于调试和可观测性）

    order: int = 0
    # 建议执行顺序（0 = 第一个）；并行执行时仍可参考此字段决定结果合并优先级

    depends_on: list[int] = Field(default_factory=list)
    # 依赖的其他子意图 order；Phase 4 需要定义其调度语义

    confidence: float = 1.0
    # S4 对本条分解结果的置信度，0.0～1.0；低置信度子意图可在合并时降权
```

**说明：**
- Phase 3 单意图路径不生成 `SubIntent`，直接使用 `GatewayState.raw_message` 与 `intent_type`
- `content` 字段在 S4 内部已做粗粒度指代消解（相对于原始消息），精细改写由各分支内的 `QueryUnderstanding` 完成
- `depends_on` 的串并行调度语义由 Phase 4 定义

### 9.4 Composite Intent

复合意图是 Phase 4 S4 的完整输出，也是多分支执行模型的起点：

```python
class CompositeIntent(BaseModel):
    """
    复合意图分解结果。
    由 Phase 4 IntentDecomposer (S4) 输出。
    Phase 3 不写入 GatewayState，也不向下游暴露该模型。
    """
    sub_intents: list[SubIntent]
    decomposition_confidence: float = 1.0
    # 对整体分解结果的置信度；低于阈值时可降级为单意图处理

    is_fallback: bool = False
    # True 表示 S4 分解失败，使用了 fallback 单子意图

    raw_reasoning: str | None = None
    # S4 的原始推理摘要（调试用，仅在 debug_trace 模式下保留）
```

**结果合并（Phase 4 待设计）：**

多分支执行完毕后的输出形态待 Phase 4 设计，不能默认暴露为 `list[GatewayState]`。以下为规划中的合并方向：

| 合并场景 | 暂定方向 |
| --- | --- |
| 多个 QUERY 子意图 | 分别检索，结果在 Alice 层拼装上下文 |
| QUERY + WRITE 子意图 | QUERY 先执行，WRITE 在 Alice generation 后由 Patchouli finalize 触发 |
| CHAT + 其他 | CHAT 子意图不触发检索，其他子意图独立执行 |
| 分支执行失败 | 失败分支丢弃，其余分支结果继续使用；若所有分支失败则降级到单意图处理 |

### 9.5 Route Target

Phase 2 先设计系统指令使用的 `CommandRouteTarget`，Phase 3 为单主意图路径预留通用 intent route target，Phase 4 再扩展到多分支子意图。

```python
class CommandRouteTargetKind(str, Enum):
    LOCAL_HANDLER = "local_handler"
    GLOBAL_ROUTE = "global_route"
    CLIENT_ACTION = "client_action"
    FUTURE_JOB = "future_job"


class CommandRouteTarget(BaseModel):
    kind: CommandRouteTargetKind
    name: str
    payload_template: dict[str, Any] = Field(default_factory=dict)
```

建议含义：

- `local_handler`：由 `SystemCommandDispatcher` 内部 handler 直接处理，例如 `/help`。
- `global_route`：通过 `GlobalSystemBus` 请求已有 public route，例如模型 ready 检查。
- `client_action`：后端只返回动作请求，由前端执行，例如清空当前聊天面板。
- `future_job`：Phase 2 只返回 `not_implemented` 或 `requires_confirmation`，为 v0.6.1 Job Queue 预留。

禁止在 route target 中放 Python import path 或 shell command。handler 绑定必须由 composition root 显式注册。

## 12. 迁移计划

> **Phase 3 修订说明**：12.1-12.4 记录的是 Phase 1/2 时期的迁移路线，包含若干低风险兼容策略。当前 Phase 3 实现以 12.5 为准：Gateway 直接升格为 `GatewaySystem/GatewayRuntime/GatewayService` 子系统，不再保留 `system/gateway` shim、`GatewayFacade`、`GatewayBundle` 或旧 gaze 主路径。

### 12.1 文件迁移

Phase 1 推荐文件迁移顺序：

1. 新建 `src/hivememory/system/gateway/` 包。
2. 将 `src/hivememory/patchouli/eye.py` 的真实实现移动到 `src/hivememory/system/gateway/eye.py`。

### 12.5 Phase 3 / Phase 4 推进计划

Phase 3 和 Phase 4 的实现应按“先子系统结构、再工作流内核、再热路径迁移、最后重写测试”的顺序推进。Phase 3 不再承担旧行为兼容目标，也不保留过渡 facade / shim；旧 Gateway 相关测试在结构迁移期间可以断开，待新系统结构完成后按新契约整体重写。Phase 4 再在稳定的 Gateway 子系统上扩展复合意图分解和多分支消费。

#### Phase 3A: Gateway 子系统骨架

目标：先建立标准子系统形态，使后续代码有明确落点。

实现范围：

1. 新建或整理 `src/hivememory/gateway/` 顶层包。
2. 新增 `GatewaySystem(SubsystemProtocol)`，提供 `name/start/stop/health/service/runtime`。
3. 新增 `GatewayRuntime`，持有 `GatewayBus`、engine 实例、pipeline、candidate context hydrator、command interceptor 和 route bindings。
4. 新增 `GatewayService`，提供 `process(message, identity=...) -> GatewayState` 作为 active chat 决策入口。
5. 新增 `gateway/contracts/local_routes.py`、`gateway/contracts/public_routes.py`、`gateway/runtime/bus.py`、`gateway/runtime/route_bindings.py`。
6. 调整 factory：构造 `GatewaySystem`，不再构造 `GatewayFacade` 或 `GatewayBundle`。
7. 删除 `src/hivememory/system/gateway/` 的 Phase 3 过渡定位；其中仍有价值的代码直接迁入 `src/hivememory/gateway/`。

验收焦点：

- `GatewaySystem` 可被系统装配根构造，并满足 `SubsystemProtocol`。
- `GatewayRuntime.mount_local_routes()` / `unmount_local_routes()` 可重复调用且有明确状态。
- `GatewayService.process()` 已存在，但可以先跑最小空 pipeline。
- 代码中不再新增 `GatewayFacade`、`GatewayBundle` 或 `system/gateway` re-export。

#### Phase 3B: Engine 原语与 State 契约

目标：稳定新 Gateway 的内部决策契约，不再围绕旧 `EyeGazeResult` 做兼容投影。

实现范围：

1. 在 `src/hivememory/engines/gateway/` 下整理 Phase 3 决策原语：`context_router.py` / `topic_router.py`、`intent_classifier.py`、`memory_value_judge.py`、`retrieval_strategy.py`、`models.py`。
2. 定义 `GatewayState`、`StageTrace`、`CandidateTopics`、`RoutedTopicContext`、`GatewayPatch`、`StageResult` 等核心模型。
3. 定义 Patchouli prepare 所需的新决策视图，例如 `PatchouliPrepareDecision` 或等价 helper，而不是 `GatewayState.to_eye_gaze_result()`。
4. 定义 `retrieval_strategy -> RetrievalRequest` 的新映射规则。
5. 定义 `memory_write_signal -> InteractionPayload.worth_saving` 的新映射规则。
6. 不新增 engine 专用 prompt / parser 子包；prompt 继续走 i18n，JSON parsing 复用项目通用工具。

验收焦点：

- engine 原语可独立 import，不依赖 SystemBus / Patchouli / Alice。
- `GatewayState` 可表达 Phase 3 所需的单主意图决策。
- 新映射规则不依赖 `EyeGazeResult`。

#### Phase 3C: Pipeline Runner 与 Stage 骨架

目标：让新 Gateway Workflow 在新子系统内完整跑通，而不是适配 Phase 2 行为。

实现范围：

1. 实现 `GatewayPipeline` runner，支持顺序 Stage、short-circuit、seal、trace。
2. 新增 S0 `CommandInterceptor`，复用 Phase 2 command registry / dispatcher，但迁入 `hivememory.gateway.commands`。
3. 新增 S1 / S2 / S3 / S4 / S5 / S6 Stage；除 S0 外，Stage 只做 `GatewayState <-> engine input/output` 适配。
4. S1 实现 `TopicRouter`，先于意图分类完成话题路由，但只写 `topic_id/new_topic_title/new_topic_summary`。
5. S2 实现 `IntentClassifier`，消费 S1 路由结果和 `RoutedTopicContext` 后再判断 `intent_type/is_composite`。
6. S3 实现 `CompositePlaceholder`，只记录 `composite_deferred`，不调 LLM、不生成 `SubIntent`。
7. S4a / S4b 分别实现 `MemoryValueJudge` 与 `QueryUnderstanding`，通过 `StageResult/GatewayPatch` 返回结果，由 Runner 统一合并。
8. S5 实现 `RetrievalStrategyPicker`，在 `QueryUnderstanding` 提交 `rewritten_query/search_keywords` 后执行。
9. S6 保持 noop。

验收焦点：

- `GatewayService.process()` 可完整跑通并输出 sealed `GatewayState`。
- Stage wrapper 不直接依赖 Patchouli / Alice / GlobalBus。
- S4 不做复合分解，Phase 4 前不引入多分支。
- S1 TopicRouter 必须早于 S2 IntentClassifier 执行。
- TopicRouter 不允许写入 `rewritten_query/search_keywords`。

#### Phase 3D: GatewayContextProvider 与全局总线桥接

目标：把 Gateway 决策所需上下文从 Patchouli prepare 副作用中拆出来，并放入 GatewayRuntime 管理。

实现范围：

1. 新增 `GatewayContextProvider`、`CandidateTopics` 和 `RoutedTopicContext`。
2. `GatewayContextProvider.prepare_candidate_topics(identity) -> CandidateTopics` 通过 global bus 请求 Patchouli active topic public route。
3. `GatewayContextProvider.prepare_routed_topic(identity, topic_id) -> RoutedTopicContext` 在 TopicRouter 提交 `topic_id` 后，通过 global bus 请求 Patchouli 完整话题上下文 public route；`topic_id="NEW_TOPIC"` 时返回空上下文。
4. `GatewayService.process()` 在 S0 command 未命中后调用 `prepare_candidate_topics()`；在 S1 TopicRouter 后调用 `prepare_routed_topic()`。
5. 两个 provider 方法分别设置 timeout 与 fallback；失败时使用空 candidate topics / 空 routed topic context 继续执行，并记录 trace/event。

验收焦点：

- S0 command 命中时不加载 active topic snapshots。
- 非 command 路径中，S1 TopicRouter 执行前 candidate topic snapshots 已准备好。
- S1 `TopicRouter` 不直接发总线请求。
- S2 IntentClassifier、S4a MemoryValueJudge、S4b QueryUnderstanding 执行前 `routed_topic_context` 已准备好。

#### Phase 3E: Active Chat 迁移与 `prepare_agent_run()` 原地改造

目标：将 active chat 热路径切到新 Gateway 子系统，并删除旧 Gateway 主路径。

实现范围：

1. `PatchouliService.prepare_agent_run()` 改为必传 `gateway_state: GatewayState`。
2. 删除 `prepare_agent_run()` 内部对 `PatchouliLocalRoutes.GATEWAY_GAZE`、`gateway_gaze` callable、`gaze_result` 兼容参数的依赖。
3. `prepare_agent_run()` 继续负责 topic prepare、pool topics、topic context、retrieval、memory compile、`AgentRunContext` 和 `StreamPrelude` 构造职责。
4. `ChatApplicationService` active chat 主路径改为先通过 `GlobalSystemBus.request(GatewayPublicRoutes.PROCESS, ...)` 获取 `gateway_state`，再通过 Patchouli public prepare route 调用 `prepare_agent_run(gateway_state=...)`。
5. command 短路路径直接由 Gateway 决策结果返回，不触发 Patchouli topic prepare、retrieval 或 Alice run。
6. 被动接入若仍需分析能力，应显式设计新的 Gateway public route，不再借用 Patchouli local `GATEWAY_GAZE`。

迁移后的 active chat 伪代码：

```python
identity = Identity(user_id=user_id, agent_id=agent_id, session_id=session_id)
gateway_state = await global_bus.request(
    GatewayPublicRoutes.PROCESS,
    message=user_message,
    identity=identity,
)

if gateway_state.command_result is not None:
    return await command_response(gateway_state.command_result)

prepared = await global_bus.request(
    GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN,
    user_message=user_message,
    user_id=user_id,
    agent_id=agent_id,
    session_id=session_id,
    gateway_state=gateway_state,
    enable_memory_retrieval=enable_memory_retrieval,
    generation_options=generation_options,
)
```

验收焦点：

- active chat 主路径调用顺序固定为 `GlobalSystemBus.request(GatewayPublicRoutes.PROCESS)` → `GlobalSystemBus.request(GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN, gateway_state=...)` → Alice run → finalize。
- `prepare_agent_run()` 不请求 `PatchouliLocalRoutes.GATEWAY_GAZE`，也不接受 `gaze_result` 兼容输入。
- 旧 Gateway 主路径代码被删除或迁移，不再作为 fallback 存在。

#### Phase 3F: S2 / S3 / S5 职责拆分与旧引擎迁移

目标：把现有单次 LLM router 中仍有价值的逻辑拆入 engine 原语，而不是继续作为旧 router 被新系统调用。

实现范围：

1. `TopicRouterEngine` 只承接话题路由；`QueryUnderstandingEngine` 承接 query rewrite、keywords；可以复用旧 prompt 思想，但不包裹旧 `GatewayEngine.process()` 作为长期实现。
2. `IntentClassifierEngine` 只做意图类型和 `is_composite` 判断；S2 Stage 只负责写入 state。
3. `MemoryValueJudgeEngine` 负责产出 `memory_write_signal`；S4a Stage 不执行写入。
4. `RetrievalStrategyEngine` 负责产出最终 `retrieval_strategy`；S5 Stage 不执行检索。
5. 移除或重命名旧 `TheEye`、`GatewayEngine` 中已经被新 engine 原语吸收的职责。

验收焦点：

- 每个 Stage 的字段写入所有权明确。
- S4a / S4b 单侧失败不影响另一侧结果。
- 新 Gateway 主路径不再委托旧 `TheEye.gaze()` 或旧 `GatewayEngine.process()`。

#### Phase 3G: Observability 与测试重写

目标：在新 Gateway 子系统结构稳定后，重建可调试、可评估的测试与观测体系。

实现范围：

1. `stage_trace` 覆盖每个 Stage 的耗时、fallback、short-circuit、关键决策摘要。
2. 增加 `GatewayPipelineCompleted` 或等价 runtime event。
3. 增加 context provider、S4a、S4b、S5 等分层开关；不提供回退旧 Gateway 行为的 `pipeline.enabled=false`。
4. 断开旧 Gateway/Patchouli/chat 兼容测试，按新结构重写：
   - engine 原语单测
   - Stage wrapper 单测
   - GatewayRuntime route binding 测试
   - GatewaySystem lifecycle 测试
   - active chat 新时序集成测试
5. 建立新的 Gateway golden scenarios，覆盖单意图、topic routing、command 短路、复合意图 deferred、fallback。
6. 收集 `composite_deferred=True` 的真实样本，作为 Phase 4 decomposition dataset 的来源。

验收焦点：

- 测试断言基于新结构和新行为，不再要求 Phase 2 输出等价。
- trace 足以定位是哪个 Stage 造成了错误决策。
- Gateway 子系统生命周期、路由和 active chat 时序均有新测试覆盖。

#### Phase 4A: Composite Envelope 与消费协议

目标：先定义复合意图的输出 envelope 和下游消费协议，再实现 LLM 分解。

实现范围：

1. 设计 `CompositeGatewayDecision` 或等价 envelope，不直接把 `list[GatewayState]` 暴露给下游。
2. 明确 `parent_state`、`branches`、`merge_policy`、`fallback_policy`。
3. 定义 Patchouli、Alice、Runtime Job Queue 对 QUERY、WRITE、SYSTEM、FUTURE_JOB 组合的消费边界。
4. 定义多分支排序、依赖、失败、用户确认和展示策略。

验收焦点：

- 下游消费方先能识别 envelope，再考虑并发执行。
- 低置信度、合并失败或下游不支持时可稳定回退到 Phase 3 单主意图路径。
- 不以 `list[GatewayState]` 作为公开协议。

#### Phase 4B: S4 IntentDecomposer

目标：在已有 envelope、消费协议和 golden dataset 的基础上引入真实复合意图分解。

实现范围：

1. 将 S4 `CompositePlaceholder` 替换为可开关的 `IntentDecomposerStage`，内部调用 `IntentDecomposerEngine`。
2. 设计窄 prompt 模板：只负责边界识别、子意图类型、顺序、依赖、置信度，不做 topic routing 或 retrieval planning；模板文本仍由 i18n 系统统一管理。
3. 引入 `confidence_threshold` 和 fallback 策略；低置信度直接回退单主意图路径。
4. 用 Phase 3 收集的 `composite_deferred` 样本构建 decomposition golden dataset。

验收焦点：

- 能区分“看似复合但不该拆”和“确实需要拆”的场景。
- S4 失败或关闭时行为等价 Phase 3。
- 分解结果不会绕过 Phase 4A 定义的 envelope 与消费协议。

6. `/chat/stream` 可输出 `command_result` 事件，且不把结果混入 assistant token。
7. 权限拒绝、参数错误、未知命令、未实现路由都有可测试的稳定返回。
8. 非破坏性命令可执行；破坏性命令不会在 Phase 2 无确认执行。
9. 系统指令不会隐式触发 Patchouli retrieval、topic prepare、Alice run 或 active memory generation。
10. Phase 2 专项单元测试和关键 chat workflow 回归通过。

### 14.3 Phase 3 验收

1. `GatewaySystem` 实现 `SubsystemProtocol`，与 Patchouli / Alice 一样拥有 `System/Runtime/Service` 分层。
2. `GatewayRuntime` 持有 local bus、route bindings、engine 原语、GatewayContextProvider、pipeline 和 stage 装配。
3. `GatewayService.process()` 能按 S0→Provider.prepare_candidate_topics→S1(TopicRouter)→Provider.prepare_routed_topic→S2(IntentClassifier)→S3(placeholder)→S4a/S4b(并发)→S5(RetrievalStrategy)→S6(noop) 顺序完整执行。
4. S0 命中 command 时 `GatewayService.process()` 短路，`stage_trace` 记录 `flow_ended=True`，`prepare_candidate_topics()`、`prepare_routed_topic()` 和后续 Stage 不执行。
5. `prepare_candidate_topics()` fallback 路径：active topics 获取失败时使用空 snapshots，Pipeline 继续执行。
6. S1 TopicRouter fallback 路径：LLM 失败时只写入 `topic_id="NEW_TOPIC"`。
7. `prepare_routed_topic()` fallback 路径：完整话题上下文获取失败时使用空 `RoutedTopicContext`，Pipeline 继续执行。
8. S2 fallback 路径：LLM 失败时写入 `intent_type=QUERY, is_composite=False`，Pipeline 继续执行。
9. S3 占位路径：S3 不调 LLM；`is_composite=True` 时只写入 `composite_deferred=True` 和 trace。
10. S4a/S4b 通过 `asyncio.gather` 并发，各自 fallback 独立，不互相影响。
11. 复合意图路径：`is_composite=True` 时 Phase 3 仍按单主意图继续处理，不产出 `SubIntent`，不返回 `list[GatewayState]`。
12. `GatewayState.seal()` 后下游修改字段可被检测到（只读保证）。
13. `GatewayFacade` dataclass、`GatewayBundle`、`TheEye.gaze()` active chat 入口、`EyeGazeResult` 兼容投影和 `pipeline.enabled=false` 旧行为回退均已移除。
14. `debug_trace=true` 时 `stage_trace` 包含每个 Stage 的输入快照。
15. 单元测试覆盖：每个 engine 原语与 Stage wrapper 的正常路径 + fallback 路径 + 超时路径。
16. 子系统测试覆盖：`GatewaySystem.start/stop/health`、`GatewayRuntime` local route mount/unmount、global bus bridge。
17. 集成测试覆盖：单意图 chat 路径、复合意图延后占位路径、command 短路路径的新行为 golden scenario。
18. `GatewayService.process()` 在非 command 路径中通过 `GatewayContextProvider.prepare_candidate_topics()` 获取 active topic snapshots，S1 不直接发总线请求。
19. `GatewayService.process()` 在 S1 TopicRouter 后通过 `GatewayContextProvider.prepare_routed_topic()` 获取完整话题上下文，S2/S4a/S4b 不直接发总线请求。
20. command 短路路径不触发 active topic snapshots 或 routed topic context 加载。
21. `PatchouliService.prepare_agent_run()` 原地改造为必传并消费 `gateway_state`，不再主动调用 `PatchouliLocalRoutes.GATEWAY_GAZE`，不再接受 `gaze_result` 兼容输入。
22. active chat 主路径调用顺序固定为 `GlobalSystemBus.request(GatewayPublicRoutes.PROCESS)` → `GlobalSystemBus.request(GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN, gateway_state=...)` → Alice run → finalize。
23. `ChatApplicationService` 只依赖 `GlobalSystemBus` 和协议模型，不直接持有 `GatewaySystem`、`GatewayService`、`PatchouliSystem` 或 `PatchouliService`。

### 14.4 Phase 4 验收（规划）

1. S4 `IntentDecomposer` 能基于固定 workflow 输出稳定的 `CompositeIntent` / `SubIntent`，并在低置信度时降级为 Phase 3 单主意图路径
2. Gateway 不直接向不支持多分支的下游暴露 `list[GatewayState]`；多分支结果必须通过明确 envelope 或消费协议传递
3. Patchouli、Alice、Runtime Job Queue 的多分支消费边界明确，包含 QUERY、WRITE、SYSTEM、FUTURE_JOB 的组合策略
4. 系统指令 + 普通聊天/检索的混合输入有稳定短路、拆分、执行与响应协议
5. 分支依赖、排序、失败回退和结果展示策略有 golden scenario 覆盖
6. Phase 4 关闭或 S4 fallback 时，行为退回 Phase 3 单主意图路径

### 14.5 v0.6.0 总体验收

1. Phase 1 完成 TheEye / Gateway 的 System 层级归属。
2. Phase 2 完成全局系统指令 registry、解析、路由和执行结果协议。
3. Phase 3 完成 Gateway Workflow 单主意图架构重设计，并明确将复合意图分解延后到 Phase 4。
4. 主动 chat、流式 chat、passive ingest、retrieval、topic routing 的既有行为有回归测试覆盖。
5. 文档、配置示例和公开导出不再暗示 Gateway 属于 Patchouli 记忆子系统。

## 15. 风险与开放问题

### 15.1 Phase 3 架构风险

1. **GatewayState 字段膨胀**
   - 每个新 Stage 都会在 `GatewayState` 上新增字段，长期可能导致状态对象过于臃肿。
   - 规避：不同 Stage 写入的字段域严格隔离，用注释分节；Phase 3 内不允许跨 Stage 写入他方字段。

2. **Pipeline 延迟叠加**
   - S2→S3 是两次串行 LLM 调用，即使每次 80ms，加上 S5 并发 2×50ms，最差路径约 200ms～300ms。
   - 规避：为每个 Stage 设置独立 `timeout_ms`，超时即触发 fallback；监控 `stage_trace` 中各 Stage 耗时，及时识别性能退化。Phase 3 不通过旧 Gateway 回退解决延迟问题。

3. **旧入口残留风险**
   - `GatewayFacade`、`GatewayBundle`、`TheEye.gaze()`、`PatchouliLocalRoutes.GATEWAY_GAZE` 如果继续存在于 active chat 主路径，会让新 Gateway 子系统继续依托旧实现，复杂度不会真正下降。
   - 规避：Phase 3 以删除或迁移旧入口为验收条件；旧测试先断开，待新结构完成后按 `GatewaySystem/GatewayRuntime/GatewayService` 重写。

4. **复合意图延后带来的能力空窗**
   - Phase 3 即使识别到 `is_composite=True`，也只按单主意图处理，复杂输入的拆分收益不会立刻体现。
   - 规避：通过 `composite_deferred` 和 `stage_trace` 收集真实样本，为 Phase 4 的 decomposition golden dataset 提供数据；明确将可见行为变化纳入 Phase 3 重构范围。

5. **TopicRouter 与 QueryUnderstanding / RetrievalStrategy 职责重叠**
   - TopicRouter 只应负责话题路由；如果它同时决定 query rewrite、keywords 或 retrieval mode，会倒退回旧的一步 LLM router。
   - 规避：S1 只输出 `topic_id/new_topic_title/new_topic_summary`；S4b 独占 `rewritten_query/search_keywords`；S5 独占最终 `retrieval_strategy` 字段。

6. **GatewayContextProvider 成为隐性前置瓶颈**
   - Gateway 入口需要 active topic snapshots；路由后还需要完整 topic context。如果 provider 延迟高或失败，Gateway 可能在进入 S1 或 S2 前被阻塞。
   - 规避：S0 command 短路必须早于 `prepare_candidate_topics()`；两个 provider 方法分别设置独立 timeout 和 fallback，失败时使用空 `CandidateTopics` / 空 `RoutedTopicContext` 继续执行，并在 `stage_trace` / gateway event 中标记。
