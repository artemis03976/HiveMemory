# v0.6.0 System Gateway 与系统指令规划

**文档状态**: Draft  
**适用范围**: `system/`、`patchouli/`、`engines/gateway/`、`core/protocol/`、`server/routers/`、`frontend/src/`  
**前置版本**: v0.5.x 基础设施工作完成  
**核心目标**: 将 Gateway / TheEye 从 Patchouli 记忆系统上移到 System 级，建立全局系统指令库，并增强 TheEye 对复杂用户输入的复合意图分解能力。

---

## 1. 背景

### 1.1 当前状态

当前代码已经把 Gateway 的“纯分析引擎”与 Patchouli Runtime 分开，但还没有把 TheEye 的宿主身份从 Patchouli 中剥离出来。

现状分层如下：

```text
src/hivememory/engines/gateway/
  engine.py            # GatewayEngine，纯数据操作层
  interceptors.py      # RuleInterceptor / create_interceptor
  semantic_analyzer.py # LLMAnalyzer / create_semantic_analyzer
  models.py            # GatewayResult / GatewayIntent / SemanticAnalysisResult
  interfaces.py        # BaseInterceptor / BaseSemanticAnalyzer

src/hivememory/patchouli/
  eye.py               # TheEye，当前仍归属 Patchouli 包
  system.py            # PatchouliSystem 构造 GatewayEngine 与 TheEye
  service.py           # PatchouliService 持有 eye，并暴露 gaze()
```

当前主动 chat 调用链：

```text
ChatApplicationService
  -> GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN
  -> PatchouliService.prepare_agent_run()
  -> PatchouliLocalRoutes.GATEWAY_GAZE
  -> PatchouliService.gaze()
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> EyeGazeResult
  -> Topic prepare / Retrieval / Alice run / Patchouli finalize
```

当前被动接入调用链：

```text
PassiveIngressService
  -> PassiveMessageIngressor.route_event()
  -> GlobalRoutes.PATCHOULI_PASSIVE_ANALYZE_AND_RETRIEVE
  -> PatchouliService.analyze_and_retrieve()
  -> PatchouliLocalRoutes.GATEWAY_GAZE
  -> TheEye.gaze()
  -> retrieve_for_gaze()
```

当前职责划分：

- `GatewayEngine` 已经是独立 engine，不直接依赖 Patchouli。
- `TheEye` 负责处理 `GatewayEngine` 的业务包装：topic snapshot 渲染、耗时记录、异常 fallback、`GatewayResult -> EyeGazeResult` 转换。
- `PatchouliSystem._init_gateway()` 仍负责 gateway LLM、interceptor、semantic analyzer、`GatewayEngine` 的装配。
- `PatchouliSystem` 仍直接持有 `self.eye`。
- `PatchouliService` 仍通过构造参数持有 `eye: TheEye`，并将 `service.gaze()` 注册到 Patchouli local bus 的 `gateway.gaze`。
- gateway 配置当前仍位于 `config.patchouli.gateway`，LLM 凭证位于 `config.shared.llm.gateway`。

已知限制：

- TheEye 的包路径与生命周期宿主仍暗示它是 Patchouli 记忆系统的一部分。
- Gateway 装配代码位于 `PatchouliSystem`，导致未来系统指令库、Deep Research、附件任务等非记忆域能力若要复用 TheEye，仍必须经过 Patchouli。
- `PatchouliLocalRoutes.GATEWAY_GAZE = "gateway.gaze"` 是 Patchouli local route，语义上不适合作为全局入口长期存在。
- `EyeGazeResult` 已位于 `core.protocol.models`，但文档注释仍说“数据格式转换由 PatchouliRuntime 负责”，与当前代码不完全一致。

### 1.2 问题陈述

v0.6.0 的第一阶段要解决的是架构归属问题，而不是新增复杂智能行为。

TheEye 当前已经承担“系统入口分析器”的职责，但实现位置仍在 Patchouli 内。这会带来几个实际问题：

1. **依赖方向不清晰**
   - System 级应用服务通过 GlobalBus 请求 Patchouli public route，Patchouli 再转入 local bus 执行 `gateway.gaze`。
   - 从业务语义看，入口分析应发生在 System 层；从代码位置看，它仍被 Patchouli 托管。

2. **后续全局系统指令难以自然扩展**
   - `/clear`、后续 `/research`、`/ingest`、任务队列控制等指令不一定属于记忆域。
   - 若 TheEye 继续在 Patchouli 内，系统指令库会被迫放进 Patchouli 或通过 Patchouli 转发到其他系统能力，形成反向依赖。

3. **复合意图分解的下游不只 Patchouli**
   - 复合意图可能同时包含检索、规划、任务创建、Agent run、文档解析等片段。
   - 这些片段的消费方横跨 Patchouli、Alice、未来 Runtime Job Queue 和前端交互层。
   - TheEye 若仍属于 Patchouli，会让复合意图输出天然偏向记忆域。

4. **测试与文档命名会持续误导**
   - 现有测试集中在 `tests/unit/patchouli/test_eye.py`。
   - 顶层 `hivememory.__getattr__` 也从 `hivememory.patchouli.eye` 导出 `TheEye`。
   - 这些入口会让后续开发继续把 gateway 当作 Patchouli 私有能力。

### 1.3 版本定位

v0.6.0 是后续“全局任务入口”的铺垫版本：

- Phase 1 只解决 TheEye / Gateway 的 System 级归属问题。
- Phase 2 在 Phase 1 的基础上添加全局系统指令库。
- Phase 3 在稳定的 System Gateway 输出契约上扩展复合意图分解。
- v0.6.1 Runtime Job Queue 会消费 Phase 2/3 产生的 task dispatch 信息。
- v0.6.2 附件解析、v0.7.0 Document Ingestion、v0.7.2 Deep Research 都应通过 System Gateway 进入对应任务或工作流，而不是绕进 Patchouli 私有入口。

## 2. 目标与非目标

### 2.1 目标

1. 将 Gateway / TheEye 正式上移到 System 级，脱离 Patchouli 记忆系统。
2. 添加全局系统指令库，由 TheEye 进行拦截、解析与路由转发。
3. 增强 TheEye 解析能力，支持针对复杂用户请求的复合意图分解。
4. 为后续检索、规划、任务队列、Deep Research 提供统一的意图输出契约。

### 2.2 非目标

v0.6.0 不承担以下工作：

- 不实现完整 Alice Phase 3 顶层任务图编排。
- 不实现 Runtime Job Queue，只为后续 task dispatch 预留边界。
- 不实现附件上传、文档解析、Document Ingestion 或 Deep Research。
- 不实现 MTP RUN executable asset、沙箱执行或真取消。
- 不实现完整对话回档或记忆 rollback。
- Phase 1 不改变 GatewayEngine 的 L1/L2 语义分析行为。
- Phase 1 不改变 `EyeGazeResult` 对外字段。

### 2.3 优先级

1. **P0**: Gateway / TheEye 上移到 System 级。
2. **P1**: 全局系统指令库与路由转发。
3. **P2**: 复合意图分解。

## 3. 术语与边界

### 3.1 术语

- **GatewayEngine**: 位于 `engines/gateway/` 的纯分析引擎，负责 L1 规则拦截与 L2 语义分析，不处理业务 fallback、不持有系统状态。
- **TheEye**: System 级入口分析服务，负责调用 `GatewayEngine`，并将结果包装为 `EyeGazeResult`。Phase 1 后不再属于 Patchouli。
- **Gaze**: TheEye 对单条用户输入执行入口分析的动作，输入为 query / topic snapshots / identity，输出为 `EyeGazeResult`。
- **EyeGazeResult**: 当前热路径使用的入口分析协议，承载 intent、rewritten query、search keywords、worth_saving、topic routing 等字段。
- **System Gateway**: System 层对 TheEye、GatewayEngine、配置、未来系统指令库与复合意图路由的总称。
- **System Command**: 全局系统指令，Phase 2 设计；Phase 1 仅预留归属边界。
- **Intent**: 用户输入的单一意图分类，当前主要为 `RAG` / `CHAT` / `SYSTEM`。
- **Composite Intent**: 复合意图分解结果，Phase 3 设计；Phase 1 不实现。
- **Route Target**: 意图或命令的下游目标，Phase 2/3 设计；Phase 1 仅保留 gaze 结果给 Patchouli 消费。
- **Task Spec**: 未来 Runtime Job Queue 可消费的任务描述，v0.6.1 设计；v0.6.0 Phase 1 不生成 task spec。

### 3.2 子系统边界

Phase 1 目标边界：

- `engines/gateway/`：保留为纯引擎层，提供 L1/L2 分析能力，不知道 System、Patchouli、Alice。
- `system/gateway/`：新增 System 级 gateway 宿主层，持有 `TheEye`、gateway factory、未来 command registry / intent router 的扩展点。
- `system/`：负责构造 System Gateway，并通过 GlobalSystemBus 或直接服务注入把 gaze 能力提供给应用服务与子系统。
- `patchouli/`：只消费 `EyeGazeResult`，不构造、不拥有 TheEye。
- `alice/` 与 `agent_runtime/`：Phase 1 不直接接入 TheEye，只保持现有 chat run 调用链。

允许依赖方向：

```text
system/gateway -> engines/gateway
system/gateway -> core.protocol / core.models
system -> system/gateway
patchouli.service -> core.protocol models
patchouli.service -> system-level gaze route or injected gaze callable
```

禁止依赖方向：

```text
system/gateway -> patchouli
engines/gateway -> system
engines/gateway -> patchouli
patchouli.system -> system.gateway concrete composition root
```

说明：Patchouli 可以在类型层面依赖 `EyeGazeResult`、`GatewayIntent` 等协议模型，但不应再负责 TheEye 的创建、配置解析或生命周期托管。

### 3.3 输入输出边界

Phase 1 不改变现有输入输出模型。

输入：

- `query: str`
- `topic_snapshots: Optional[list[TopicSnapshot]]`
- `identity: Optional[Identity]`

输出：

- `EyeGazeResult`

Phase 1 的关键约束：

- `EyeGazeResult.intent`、`rewritten_query`、`search_keywords`、`worth_saving`、`target_topic`、`new_topic_title`、`new_topic_summary` 的行为保持兼容。
- fallback 行为保持兼容：`GatewayEngine` 或 LLM analyzer 异常时返回 `intent=RAG`、`rewritten_query=raw_query`、`worth_saving=False`、`target_topic="NEW_TOPIC"`、`is_fallback=True`。
- Topic snapshot 文本渲染在 Phase 1 可暂时沿用 `PerceptionContextConverter.snapshots_to_context_text()`，但需要在依赖方向上避免 `system/gateway` 直接依赖 perception engine 的具体实现。迁移时可先复制/抽出轻量 renderer，或在构造 TheEye 时注入 renderer callable。

## 4. 总体架构

### 4.1 目标结构

Phase 1 后的目标结构：

```text
system/
  config/
    gateway.py          # SystemGatewayConfig / RuleInterceptorConfig / LLMAnalyzerConfig
                        # 或从 patchouli.py 迁出的等价配置
  gateway/
    __init__.py
    eye.py              # TheEye 的新归属
    factory.py          # build_system_gateway() / build_gateway_engine()
    contracts.py        # 可选：SystemGatewayRoutes / Gaze callable type
    topic_context.py    # 可选：topic snapshots -> active_topics_menu renderer

engines/gateway/
  engine.py             # 保持纯引擎层
  interceptors.py
  semantic_analyzer.py
  models.py
  interfaces.py

patchouli/
  system.py             # 不再 _init_gateway，不再 self.eye = TheEye(...)
  service.py            # 不再拥有 TheEye concrete；改为通过 route/callable 请求 gaze
  eye.py                # 短期兼容 shim，可选；最终删除
```

推荐拆分：

- `system/gateway/eye.py`：从 `patchouli/eye.py` 迁移 `TheEye`。
- `system/gateway/factory.py`：承接原 `PatchouliSystem._init_gateway()` 的装配逻辑。
- `system/config/gateway.py`：从 `PatchouliConfig.gateway` 拆出 gateway 配置，使 gateway 不再属于记忆域配置。

可接受的第一步兼容：

- 保留 `hivememory.patchouli.eye.TheEye` 为 re-export shim：

```python
from hivememory.system.gateway.eye import TheEye
```

该 shim 仅为测试和外部导入过渡使用，不应包含逻辑。

### 4.2 总体数据流

Phase 1 后的主动 chat 数据流：

```text
User Input
  -> ChatApplicationService
  -> Patchouli prepare public route
  -> PatchouliService.prepare_agent_run()
  -> System Gateway gaze route/callable
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> EyeGazeResult
  -> Patchouli topic prepare + retrieval
  -> Alice run
  -> Patchouli finalize
```

Phase 1 不改变 `ChatApplicationService` 的 prepare/run/finalize 编排骨架，也不改变 `PatchouliService.prepare_agent_run()` 对 `EyeGazeResult` 的消费逻辑。

Phase 1 的主要变化是 gaze 能力的宿主与注册位置：

```text
Before:
  PatchouliSystem builds TheEye
  Patchouli local bus registers gateway.gaze -> PatchouliService.gaze -> self._eye.gaze

After:
  HiveMemorySystem or SystemGateway factory builds TheEye
  System-level route/callable exposes gateway.gaze
  PatchouliService requests/invokes system gaze
```

### 4.3 依赖方向

Phase 1 的依赖方向以“System 拥有 gateway，Patchouli 消费 gaze result”为准：

```text
HiveMemorySystem.build()
  -> build_system_gateway(config.gateway, config.shared.llm.gateway)
  -> PatchouliSystem(..., gateway_gaze=system_gateway.gaze)

PatchouliService
  -> gateway_gaze(query, topic_snapshots, identity)
  -> EyeGazeResult
```

不推荐让 `system/gateway` 直接请求 Patchouli route 获取 topic snapshots。Topic snapshot 的生产仍属于 Patchouli；TheEye 只接收调用方提供的 snapshots。

不推荐在 Phase 1 中新增大规模全局路由协议。如果需要路由，优先使用最小 `SYSTEM_GATEWAY_GAZE` route；更完整的系统指令路由留到 Phase 2。

## 5. Phase 1: Gateway / TheEye 上移到 System 级

### 5.1 现状

当前实现细节：

1. `TheEye` 位于 `src/hivememory/patchouli/eye.py`。
   - 构造参数：`engine: GatewayEngine`、`bus=None`。
   - 公开方法：`gaze(query, topic_snapshots=None, identity=None) -> EyeGazeResult`。
   - 内部职责：topic snapshots 渲染、调用 `GatewayEngine.process()`、耗时记录、日志、fallback。
   - 文件中已有 TODO：后续考虑上移至 system。

2. `GatewayEngine` 位于 `src/hivememory/engines/gateway/engine.py`。
   - 已经是纯数据操作层。
   - 执行 L1 interceptor 与 L2 semantic analyzer。
   - 不处理 fallback、日志、业务转换。

3. `PatchouliSystem` 当前负责 gateway 装配。
   - `PatchouliSystem.__init__()` 中先构造 `PatchouliRuntime`，再 `_init_gateway()`，再 `self.eye = TheEye(...)`。
   - `_init_gateway()` 使用 `config.shared.llm.gateway` 构造 gateway LLM service。
   - `_init_gateway()` 使用 `config.patchouli.gateway` 构造 interceptor 与 semantic analyzer。

4. `PatchouliService` 当前持有 `eye: TheEye`。
   - `service.gaze()` 是薄包装：调用 `self._eye.gaze(...)`。
   - `prepare_agent_run()` 与 `analyze_and_retrieve()` 并不直接调用 `self._eye.gaze()`，而是请求 `PatchouliLocalRoutes.GATEWAY_GAZE`。

5. `PatchouliRuntime.mount_local_routes()` 当前注册：
   - `PatchouliLocalRoutes.GATEWAY_GAZE -> service.gaze`
   - 这让 Patchouli local bus 成为 TheEye 的入口。

6. 顶层 `ChatApplicationService` 和 `PassiveIngressService` 不直接知道 TheEye。
   - 它们只通过 GlobalSystemBus 调 Patchouli public routes。
   - 因此 Phase 1 迁移理论上可以保持顶层 API 行为不变。

7. 测试现状：
   - `tests/unit/patchouli/test_eye.py` 直接测试 `hivememory.patchouli.eye.TheEye`。
   - E2E 测试中也有直接从 `hivememory.patchouli.eye` import `TheEye` 的路径。
   - 多个 Patchouli service 测试用 mock eye 或 local bus mock `GATEWAY_GAZE`。

### 5.2 目标

Phase 1 完成后，TheEye 应成为 System 级 gateway service，而不是 Patchouli 子系统组件。

目标状态：

1. `TheEye` 的真实实现移动到 `hivememory.system.gateway.eye`。
2. `PatchouliSystem` 不再构造 gateway LLM、interceptor、semantic analyzer、`GatewayEngine` 或 `TheEye`。
3. Gateway 装配逻辑移动到 System 层，例如：
   - `hivememory.system.gateway.factory.build_system_gateway(...)`
   - 或 `HiveMemorySystem.build()` 内部的私有构造函数。
4. `PatchouliService` 不再类型依赖 `hivememory.patchouli.eye.TheEye` concrete。
5. Patchouli 仍可在 prepare/analyze 流程中消费 `EyeGazeResult`，但 gaze 的来源是 System 级 gateway。
6. 现有主动 chat、被动 ingest、topic routing、retrieval 行为保持不变。

目标边界：

```text
TheEye owns:
  - GatewayEngine 调用
  - GatewayResult -> EyeGazeResult 转换
  - fallback
  - processing_time_ms
  - gateway 入口日志

Patchouli owns:
  - topic snapshots 获取
  - topic prepare / discard
  - retrieval_for_gaze
  - interaction submit / finalize
  - memory generation

System owns:
  - TheEye 构造与生命周期归属
  - gateway config 归属
  - 后续 command registry / route target 扩展点
```

### 5.3 模块迁移范围

建议迁移范围：

新增：

- `src/hivememory/system/gateway/__init__.py`
- `src/hivememory/system/gateway/eye.py`
- `src/hivememory/system/gateway/factory.py`
- `src/hivememory/system/gateway/topic_context.py`（可选）
- `src/hivememory/system/config/gateway.py`（推荐）
- `tests/unit/system/gateway/test_eye.py`

迁移：

- `src/hivememory/patchouli/eye.py` 的真实实现迁移到 `src/hivememory/system/gateway/eye.py`。
- `PatchouliSystem._init_gateway()` 的装配逻辑迁移到 `system/gateway/factory.py`。
- `MemoryGatewayConfig`、`RuleInterceptorConfig`、`LLMAnalyzerConfig` 从 `system/config/patchouli.py` 迁移到 `system/config/gateway.py`，或至少在 System config 层提供新的 `gateway` 字段。

调整：

- `HiveMemorySystem.__init__()` 增加 `gateway` 或 `the_eye` 字段。
- `HiveMemorySystem.build()` 在构造 PatchouliSystem 之前构造 System Gateway。
- `PatchouliSystem.__init__()` 接收 `gateway_gaze` callable 或 system gateway service 引用。
- `PatchouliService.__init__()` 接收 `gateway_gaze` callable，而不是 `eye: TheEye` concrete。
- `build_patchouli_route_bindings()` 中 `GATEWAY_GAZE` 可继续注册，但 handler 应来自注入的 system gateway callable，而非 Patchouli-owned eye。
- `hivememory.__getattr__("TheEye")` 改为从 `hivememory.system.gateway.eye` 导出。

保留：

- `src/hivememory/engines/gateway/*` 不迁移。
- `GatewayResult` / `GatewayIntent` / `SemanticAnalysisResult` 行为不改。
- `EyeGazeResult` 暂时仍保留在 `core.protocol.models`。
- `PatchouliLocalRoutes.GATEWAY_GAZE` 可短期保留，作为 Patchouli 内部 workflow 对 gaze 能力的兼容入口。

可选兼容 shim：

- `src/hivememory/patchouli/eye.py` 保留为：

```python
"""Deprecated compatibility import for TheEye."""

from hivememory.system.gateway.eye import TheEye

__all__ = ["TheEye"]
```

该 shim 应标注 deprecated，并在 v0.7 之后考虑删除。

### 5.4 兼容策略

Phase 1 应采用低风险兼容迁移，不一次性删除旧入口。

兼容策略：

1. **导入兼容**
   - 保留 `hivememory.patchouli.eye.TheEye` re-export，避免 E2E 与外部脚本立即失效。
   - 新代码必须使用 `hivememory.system.gateway.TheEye`。

2. **路由兼容**
   - 保留 `PatchouliLocalRoutes.GATEWAY_GAZE`，因为 `PatchouliService.prepare_agent_run()` 与 `analyze_and_retrieve()` 已经通过 local bus 请求它。
   - 但该 route 的 handler 不再绑定到 Patchouli-owned `self._eye`，而是绑定到 System 注入的 gaze callable。

3. **配置兼容**
   - 新增 `config.gateway` 作为 System Gateway 配置位置。
   - 短期允许从旧 `config.patchouli.gateway` 读取默认值，或者让 `PatchouliConfig.gateway` 成为 deprecated alias。
   - 文档与示例配置应优先使用 `gateway.*`。

4. **测试兼容**
   - 新增 `tests/unit/system/gateway/test_eye.py`。
   - 旧 `tests/unit/patchouli/test_eye.py` 可改为 shim import 兼容测试，或直接迁移到 system/gateway。
   - E2E 中直接 import `hivememory.patchouli.eye` 的位置应逐步改为 system path。

5. **行为兼容**
   - 不改 `EyeGazeResult` 字段。
   - 不改 fallback 值。
   - 不改 `prepare_agent_run()` 的输出结构。
   - 不改 chat stream 的 SSE prelude。

### 5.5 风险

主要风险：

1. **启动装配顺序风险**
   - 当前 `PatchouliSystem` 内部构造 TheEye，迁移后 `HiveMemorySystem.build()` 需要先构造 gateway，再注入 Patchouli。
   - 若 Patchouli local route 注册早于 gateway callable 注入，会导致 `gateway.gaze` route 缺失。

2. **配置路径迁移风险**
   - 当前代码读取 `config.patchouli.gateway`。

4. **测试路径风险**
   - 多个测试和 E2E 直接 import `hivememory.patchouli.eye.TheEye`。
   - 需要 shim 或批量迁移测试路径。

5. **局部总线路由语义风险**
   - `PatchouliLocalRoutes.GATEWAY_GAZE` 名称仍在 Patchouli 内，短期保留有利于兼容，但长期语义不理想。

6. **公共导出风险**
   - `hivememory.__getattr__` 当前从 patchouli path 懒加载 `TheEye`。
   - 若忘记同步，会造成新旧路径实例不一致或导入失败。

## 6. Phase 2: 全局系统指令库

### 6.1 现状

当前 `RuleInterceptor` 已经具备最小的系统指令快速拦截能力，但它只是硬编码正则列表：

- `RuleInterceptor.SYSTEM_PATTERNS` 直接包含 `/clear`、`/reset`、`/start`、`/help`、`/restart`。
- 命中后只返回 `InterceptorResult(intent=GatewayIntent.SYSTEM, reason=...)`。
- 结果中没有稳定的 command id、参数、权限需求、路由目标或执行策略。
- `GatewayEngine` 只知道这是 `SYSTEM` intent，不知道后续应该由哪个 system application service、Patchouli public route、Alice runtime 或 future job dispatcher 消费。
- 前端也无法从后端获得可补全的命令清单、帮助文本、参数 schema 或禁用原因。

因此当前状态只能回答“这是不是一个系统指令”，还不能回答“它是哪条指令、参数是什么、谁能执行、应该交给谁执行、执行结果如何对用户呈现”。

Phase 2 只解决系统指令的注册、解析、授权、路由和结果协议，不重排 active chat 的 `gaze -> prepare -> run -> finalize` 主时序。`prepare_agent_run` 中 Patchouli 反向调用 gaze 的问题保留到 Phase 3 前置重构处理。

### 6.2 目标

Phase 2 的目标是把系统指令从 `RuleInterceptor` 的硬编码正则中提升为 System Gateway 拥有的全局能力：

1. 新增 `CommandRegistry`，集中注册内置系统指令。
2. 每条指令有稳定 `command_id`、别名、匹配规则、参数 schema、权限策略、路由目标和展示元数据。
3. `RuleInterceptor` 不再维护系统指令正则常量，而是委托 registry 做 L1 快速匹配和初步解析。
4. `GatewayResult` / `EyeGazeResult` 在 `intent=SYSTEM` 时携带结构化 command parse result。
5. 新增 system-level command dispatcher，根据 parse result 将指令导向实际实现。
6. 指令执行结果有统一协议，供 chat / stream / frontend 呈现，不混入普通 Alice generation。
7. Phase 2 只支持单条明确系统指令；“系统指令 + 普通聊天/检索”的复合输入留给 Phase 3。

设计原则：

- `engines/gateway` 仍然是纯分析层，可以接收 registry 风格的 matcher，但不依赖 system service。
- `system/gateway` 拥有 command registry、command parse model 和 command dispatcher。
- Patchouli 只实现属于记忆域的 command handler，不拥有全局指令库。
- 指令执行的副作用必须发生在 dispatcher / handler，不发生在 `RuleInterceptor` 或 `TheEye.gaze()` 中。

### 6.3 指令分类

Phase 2 先定义分类，不要求一次实现所有指令。

| Category | 说明 | 典型指令 | Phase 2 建议 |
| --- | --- | --- | --- |
| `conversation` | 当前会话 UI / 生成控制，不直接改记忆 | `/help`, `/clear` | P0 |
| `gateway` | Gateway 调试与可观测能力 | `/gateway status`, `/commands` | P1 |
| `memory` | 记忆域操作，经由 Patchouli public route 执行 | `/memory search`, `/topic reset` | P1/P2 |
| `runtime` | 系统运行状态、模型 warmup、任务状态 | `/status`, `/models ready` | P1 |
| `debug` | 开发/诊断指令，仅 debug/admin 可见 | `/debug routes`, `/debug topics` | P2 |
| `future_job` | 未来 Runtime Job Queue 可消费的长任务 | `/research`, `/ingest` | 只预留 |

Phase 2 的首批推荐内置指令：

- `/help`：返回可用命令清单和简短帮助。
- `/commands`：返回结构化命令清单，供前端补全。
- `/clear`：清空当前前端会话显示或请求客户端重置上下文，具体副作用要通过结果协议表达，后端不直接操作浏览器状态。
- `/status`：返回 system / patchouli / alice 的基础健康摘要。
- `/models ready`：代理现有模型 ready 检查能力。

不建议 Phase 2 立即实现高风险指令：

- 删除记忆、批量 archive、清空 topic、取消所有任务等破坏性操作。
- 需要多步确认的命令。
- 需要 Runtime Job Queue 的长任务命令。

### 6.4 指令注册表

新增包建议：

```text
src/hivememory/system/gateway/commands/
  __init__.py
  models.py          # command definition / parse result / execution result
  registry.py        # CommandRegistry
  parser.py          # command line tokenizer / arg parser
  dispatcher.py      # route target dispatch
  builtins.py        # register_builtin_commands()
  handlers.py        # simple system-owned handlers
```

核心注册模型草案：

```python
class CommandDefinition(BaseModel):
    command_id: str                    # stable id, e.g. "system.help"
    category: CommandCategory
    primary_name: str                  # "/help"
    aliases: list[str] = []
    summary: str
    description: str | None = None
    argument_schema: dict[str, Any] = {}
    route_target: CommandRouteTarget
    permission: CommandPermissionPolicy
    enabled: bool = True
    hidden: bool = False
    priority: int = 100
```

解析结果模型草案：

```python
class CommandParseResult(BaseModel):
    command_id: str
    raw_input: str
    name: str
    args: dict[str, Any] = {}
    tokens: list[str] = []
    matched_alias: str | None = None
    parse_status: Literal["matched", "invalid_args", "unknown"]
    error: str | None = None
```

注册规则：

- 内置命令通过 `register_builtin_commands(registry)` 注册。
- 后续插件/模块可通过 composition root 注册扩展命令，但 Phase 2 不做动态插件加载。
- `command_id` 必须全局唯一，建议命名空间格式：`system.help`、`runtime.status`、`patchouli.topic.reset`。
- `primary_name` 和 `aliases` 必须全局唯一；冲突时启动失败，而不是运行期随机覆盖。
- registry 提供只读 listing 给前端和 `/help`，隐藏命令默认不出现在普通 listing。

匹配优先级：

1. 精确 alias/name 匹配优先于正则/前缀匹配。
2. 长命令名优先于短命令名，例如 `/models ready` 优先于 `/models`。
3. priority 值更小者优先。
4. 发生歧义时返回 `invalid_args` 或 `ambiguous`，不执行副作用。

参数解析：

- Phase 2 使用轻量 command-line tokenizer，支持 quoted string 和 `--key value` / `--flag`。
- 不支持 shell expansion、管道、重定向、子命令执行。
- 参数校验基于每条 command definition 的 schema 或 parser callable。

### 6.5 TheEye 拦截与路由

推荐处理链：

```text
User input
  -> TheEye.gaze()
  -> GatewayEngine.process()
  -> RuleInterceptor.intercept()
  -> CommandRegistry.match_and_parse()
  -> GatewayResult(intent=SYSTEM, command=CommandParseResult)
  -> TheEye wraps EyeGazeResult
  -> ChatApplicationService detects SYSTEM command
  -> SystemCommandDispatcher.execute()
  -> CommandExecutionResult
  -> HTTP/SSE response
```

关键边界：

- `RuleInterceptor` 只做匹配和解析，不执行命令。
- `TheEye` 只把 command parse result 带出，不根据 route target 调 handler。
- `ChatApplicationService` 或新的 system application service 是指令执行入口。
- `CommandDispatcher` 根据 `route_target` 调用本地 handler、GlobalSystemBus route 或未来 Job Queue。
- Phase 2 不让 Patchouli `prepare_agent_run()` 消费系统指令；系统指令应在进入普通 Alice run 前短路。

Route target 草案：

```python
class CommandRouteTarget(BaseModel):
    kind: Literal["local_handler", "global_route", "client_action", "future_job"]
    name: str
    payload_template: dict[str, Any] = {}
```

执行结果草案：

```python
class CommandExecutionResult(BaseModel):
    command_id: str
    status: Literal["completed", "rejected", "failed", "requires_confirmation", "not_implemented"]
    message: str
    data: dict[str, Any] = {}
    client_action: dict[str, Any] | None = None
    error_code: str | None = None
```

Chat/SSE 行为：

- 非流式 `/chat` 如果命中系统指令，直接返回 command result 包装后的 `AgentRunResult` 或新增稳定 command response envelope。
- 流式 `/chat/stream` 如果命中系统指令，发送 `command_result` 事件，然后发送 `done`。
- 不进入 Patchouli prepare，不创建新 topic，不触发 retrieval，不触发 Alice generation，不触发 active memory generation。

需要注意：当前 active chat 为了 topic routing 仍由 `prepare_agent_run()` 内部调用 gaze。Phase 2 如要实现“系统指令在 prepare 前短路”，可以在 `ChatApplicationService` 中增加轻量 pre-gaze 分支，但这会触碰 chat 时序。建议 Phase 2 先以最小改动落地 command parse/result 模型和 dispatcher，可选地只在现有 prepare 返回的 `gaze_result.intent == SYSTEM` 后短路；完整的 `TheEye.gaze -> prepare_from_gaze` 时序重置放到 Phase 3 前置重构。

### 6.6 权限与安全

权限模型先保持简单，但必须显式存在。

```python
class CommandPermissionPolicy(BaseModel):
    visibility: Literal["public", "debug", "admin"] = "public"
    allowed_agent_ids: list[str] | None = None
    allowed_user_ids: list[str] | None = None
    requires_confirmation: bool = False
    destructive: bool = False
```

Phase 2 权限检查输入：

- `Identity.user_id`
- `Identity.agent_id`
- system debug mode
- command definition permission policy

Phase 2 默认策略：

- public 指令普通用户可见可执行。
- debug 指令仅 `config.system.debug=true` 或测试环境可见。
- admin 指令先不开放；如实现，只允许显式 allowlist。
- destructive 指令即使注册，也必须返回 `requires_confirmation`，Phase 2 不执行二次确认链路。
- unknown command 不交给 LLM 猜测执行，应返回明确错误或作为普通聊天进入后续流程，具体策略由配置控制。

安全约束：

- 指令参数不进入 shell。
- 不允许 command alias 与普通 URL scheme 或 markdown link 混淆。
- 不允许 LLM analyzer 伪造 command parse result；系统指令只由 L1 registry/parser 产生。
- 所有执行结果必须进入 runtime events 或日志，至少包含 `command_id`、status、identity、trace_id。

### 6.7 前端协作

Phase 2 后端应提供足够协议，使前端可以选择增强体验，但不强制第一版完成完整命令面板。

前端可选能力：

- 输入框 `/` 触发命令补全。
- 展示命令 summary、参数提示和禁用原因。
- 对 `requires_confirmation` 展示确认 UI。
- 对 `command_result` SSE 事件展示非 token 类型结果。
- 对 `client_action` 执行本地 UI 行为，例如清空当前会话显示。

后端接口建议：

- 复用 `/chat` / `/chat/stream` 执行命令，不新增独立执行入口。
- 可新增只读命令 listing API，例如 `GET /system/commands`，也可以先通过 `/commands` 指令返回。
- SSE 新事件建议：

```text
event: command_result
data: CommandExecutionResult
```

第一版前端最低要求：

- 不把系统指令结果当作普通 assistant token 拼接。
- 能展示 `message`。
- 能处理 `client_action={"type": "clear_chat"}` 这类本地动作。

### 6.8 验收

Phase 2 完成条件：

1. `CommandRegistry` 可注册、列出、匹配、解析内置命令。
2. `RuleInterceptor` 的系统指令匹配来源从硬编码 regex 切换到 registry。
3. `GatewayResult` / `EyeGazeResult` 在 `SYSTEM` intent 下能携带结构化 command parse result。
4. `CommandDispatcher` 可执行至少 `/help`、`/commands`、`/status` 中的两类非破坏性指令。
5. 未知命令、参数错误、权限拒绝、未实现 route target 都有稳定错误结果。
6. 系统指令不会触发 retrieval、topic creation、Alice generation 或 active memory generation，除非该指令明确路由到对应能力。
7. 命令执行产生可观测日志或 runtime event。
8. 单元测试覆盖 registry、parser、interceptor、dispatcher、权限拒绝和 chat/stream 短路行为。

### 6.9 分阶段推进计划

Phase 2 内容较多，建议拆成可独立提交、可独立回归的 6 个小阶段。每个阶段只引入一个主要风险面，避免同时修改 Gateway、ChatApplicationService、前端协议和权限模型。

#### Phase 2.0: Command Core Foundation

目标：先落地纯数据与纯解析能力，不接入热路径。

实现范围：

- 新增 `hivememory.system.gateway.commands` 包。
- 新增 `CommandDefinition`、`CommandCategory`、`CommandParseResult`、`CommandPermissionPolicy`、`CommandRouteTarget`、`CommandExecutionResult`。
- 实现 `CommandRegistry.register()`、`get()`、`list()`、`match()`。
- 实现轻量 tokenizer，支持 `/cmd`、`/cmd sub`、quoted string、`--key value`、`--flag`。
- 实现 `register_builtin_commands()`，先注册 `/help`、`/commands`、`/clear`、`/status` 的 definition，但不执行真实副作用。

不做：

- 不改 `RuleInterceptor`。
- 不改 `GatewayResult` / `EyeGazeResult`。
- 不接入 chat / stream。

验收：

- registry/parser 单测通过。
- command id 和 alias 冲突会启动期失败或注册时报错。
- unknown / invalid args / ambiguous 有稳定 parse status。

#### Phase 2.1: Gateway L1 Integration

目标：把系统指令识别从硬编码 regex 切到 registry，但仍不执行命令。

实现范围：

- `RuleInterceptor` 接收可选 `CommandRegistry` 或 `CommandMatcher`。
- `create_interceptor()` 由 System Gateway factory 注入 registry。
- `InterceptorResult` 或 `GatewayResult` 扩展可选 `command` 字段。
- `GatewayEngine.process()` 在 L1 命中系统指令时保留 command parse result。
- `TheEye.gaze()` 将 command parse result 转入 `EyeGazeResult`。

不做：

- 不新增 command dispatcher。
- 不改变 chat prepare/run/finalize 时序。
- 不让 L2 analyzer 生成 command。

验收：

- `/help`、`/commands`、`/status` 命中 `GatewayIntent.SYSTEM`，并携带结构化 command。
- 非命令输入保持 RAG/CHAT 行为不变。
- L1 命中系统指令时不调用 L2。

#### Phase 2.2: Command Dispatcher and Built-in Handlers

目标：让系统指令有统一执行入口和统一结果协议。

实现范围：

- 新增 `SystemCommandDispatcher`。
- 支持 `local_handler` route target。
- 支持 `client_action` route target。
- 支持 `global_route` route target 的基本调用封装。
- 实现 `/help`、`/commands`、`/clear` 的 handler。
- `/status` 可以先返回 system 层摘要；跨子系统健康信息可后续扩展。
- 实现权限检查：public/debug/admin、allowlist、destructive、requires_confirmation。

不做：

- 不实现破坏性命令的确认执行链。
- 不实现 future job。
- 不新增复杂 memory mutation 命令。

验收：

- dispatcher 单测覆盖 completed/rejected/failed/requires_confirmation/not_implemented。
- `/clear` 返回 `client_action={"type": "clear_chat"}`，后端不直接操作前端状态。
- debug/admin 命令默认不可见或不可执行。

#### Phase 2.3: Chat / Stream Command Short-Circuit

目标：把 command dispatcher 接入用户可见入口，并确保系统指令不进入普通 Agent run。

可选实现路线：

- 保守路线：沿用当前 `prepare_agent_run()` 内部 gaze 时序，prepare 返回后若 `prepared.gaze_result.intent == SYSTEM`，ChatApplicationService 立即执行 command 并清理 prepared run。该路线改动小，但可能临时产生 topic prepare，需要额外保护。
- 推荐路线：在 ChatApplicationService 中增加 command-only pre-gaze。该 pre-gaze 不需要 topic routing，可只传入空 topic snapshots 或最小 identity；命中明确 command 后直接短路，未命中再走现有 Patchouli prepare。该路线更符合系统指令入口语义，但会引入一条轻量 gaze 分支。
- 最终路线：Phase 3 前置重构中改为 `topic snapshots -> TheEye.gaze -> prepare_from_gaze`，届时移除临时分支。

Phase 2 推荐采用“推荐路线”，但必须保持范围克制：

- 只用于 slash command 的 L1 快速识别。
- 不做普通自然语言 intent pre-gaze。
- 不处理复合输入。

实现范围：

- `ChatApplicationService.chat()` 命中系统指令时返回 command result。
- `ChatApplicationService.chat_stream()` 命中系统指令时发送 `command_result`，随后发送稳定 `done`。
- 系统指令短路时不调用 Patchouli prepare、Alice run、Patchouli finalize。
- 非系统指令继续走现有 prepare/run/finalize。

验收：

- `/help` 不触发 retrieval/topic prepare/Alice generation。
- `/chat/stream` 的 `command_result -> done` 顺序稳定。
- 非命令 chat stream 的 `topic_info -> memory_refs -> token -> done` 顺序保持不变。

#### Phase 2.4: Configuration, Observability, and Frontend Contract

目标：补齐配置、事件、HTTP/SSE 协议和前端最小协作面。

实现范围：

- 新增 `SystemCommandConfig` 并挂到 `SystemGatewayConfig.commands`。
- 支持 `enabled`、`unknown_command_policy`、`expose_listing`、`enable_debug_commands`、`builtin` overrides。
- command execution 记录日志或 runtime event，包含 `command_id`、status、identity、trace_id。
- SSE 支持 `command_result` 事件。
- 前端最小处理 `command_result.message` 和 `client_action.type == "clear_chat"`。

不做：

- 不要求完整命令面板。
- 不要求所有命令参数 UI 自动生成。

验收：

- 配置默认值单测通过。
- 禁用 commands 后系统指令不会短路执行。
- 前端不会把 command result 拼进 assistant token。

#### Phase 2.5: Cleanup and Compatibility Tightening

目标：收口临时兼容点，减少 Phase 3 前的技术债。

实现范围：

- 删除 `RuleInterceptor.SYSTEM_PATTERNS` 或标记为测试 fixture，不再作为生产来源。
- 更新 `docs/engines/gateway.md` 与相关注释，说明系统指令由 registry 提供。
- 更新测试命名，把 command 测试归到 `tests/unit/system/gateway/commands`。

## 8. 数据模型草案

### 8.1 Gateway Result

Phase 1 不扩展 `GatewayResult`，也不新增 system-level envelope。

原因：

- Phase 1 是归属迁移，不改变 GatewayEngine 行为。
- 当前 `GatewayResult -> EyeGazeResult` 的转换已经满足 chat / passive ingress 的兼容需求。
- 系统指令库与复合意图分解会引入新的 route target / segment 模型，但这属于 Phase 2/3。

Phase 1 约束：

- `GatewayResult` 继续属于 `engines/gateway/models.py`。
- `EyeGazeResult` 继续属于 `core/protocol/models.py`。
- `TheEye` 迁移到 System 后仍返回 `EyeGazeResult`。
- 若后续要新增 system-level envelope，应在 Phase 2/3 中设计，不在 Phase 1 混入。

### 8.2 System Command

Phase 2 新增系统指令模型，建议放在 `hivememory.system.gateway.commands.models`，不要放进 Patchouli 或 Alice。

核心模型：

```python
class CommandCategory(str, Enum):
    CONVERSATION = "conversation"
    GATEWAY = "gateway"
    MEMORY = "memory"
    RUNTIME = "runtime"
    DEBUG = "debug"
    FUTURE_JOB = "future_job"


class CommandParseStatus(str, Enum):
    MATCHED = "matched"
    UNKNOWN = "unknown"
    INVALID_ARGS = "invalid_args"
    AMBIGUOUS = "ambiguous"


class CommandExecutionStatus(str, Enum):
    COMPLETED = "completed"
    REJECTED = "rejected"
    FAILED = "failed"
    REQUIRES_CONFIRMATION = "requires_confirmation"
    NOT_IMPLEMENTED = "not_implemented"
```

`GatewayResult` 可新增可选字段：

```python
command: CommandParseResult | None = None
```

`EyeGazeResult` 可新增同名可选字段，默认 `None`，保证既有 RAG / CHAT 消费方不受影响。

约束：

- `command` 仅在 `intent == GatewayIntent.SYSTEM` 时有意义。
- `command.parse_status != "matched"` 时不得执行副作用。
- Phase 2 不把 command result 塞进 `rewritten_query` 或 `reason` 字符串中传递。

### 8.5 Route Target

Phase 2 先设计系统指令使用的 `CommandRouteTarget`，Phase 3 再推广为通用 intent route target。

```python
class CommandRouteTargetKind(str, Enum):
    LOCAL_HANDLER = "local_handler"
    GLOBAL_ROUTE = "global_route"
    CLIENT_ACTION = "client_action"
    FUTURE_JOB = "future_job"


class CommandRouteTarget(BaseModel):
    kind: CommandRouteTargetKind
    name: str
    payload_template: dict[str, Any] = Field(default_factory=dict)
```

建议含义：

- `local_handler`：由 `SystemCommandDispatcher` 内部 handler 直接处理，例如 `/help`。
- `global_route`：通过 `GlobalSystemBus` 请求已有 public route，例如模型 ready 检查。
- `client_action`：后端只返回动作请求，由前端执行，例如清空当前聊天面板。
- `future_job`：Phase 2 只返回 `not_implemented` 或 `requires_confirmation`，为 v0.6.1 Job Queue 预留。

禁止在 route target 中放 Python import path 或 shell command。handler 绑定必须由 composition root 显式注册。

### 9.3 前端接口

Phase 2 前端接口以“可选增强、协议先行”为原则。

新增或调整类型建议：

```ts
type CommandExecutionStatus =
  | "completed"
  | "rejected"
  | "failed"
  | "requires_confirmation"
  | "not_implemented";

interface CommandExecutionResult {
  command_id: string;
  status: CommandExecutionStatus;
  message: string;
  data?: Record<string, unknown>;

    type: string;
```

## 14. 风险与开放问题

### 14.1 架构风险

Phase 1 架构风险：

- System Gateway 若继续 import perception converter，会把 perception 细节泄漏到 System 层。
- Patchouli local bus 继续保留 `gateway.gaze` 会形成短期命名不一致。
- 若 `PatchouliSystem` 和 `HiveMemorySystem` 同时能构造 TheEye，可能出现双实例与配置漂移。

规避策略：

- topic snapshot renderer 抽到 System 可接受的位置，或通过 callable 注入。
- Phase 1 保留 `gateway.gaze` 作为兼容 route，但文档标记为过渡状态。
- 最终只允许 System composition root 构造 TheEye。

### 14.2 行为风险

Phase 1 行为风险：

- fallback 行为改变会影响 chat 首轮 topic 创建与 retrieval。
- `identity=None` 默认值改变会影响旧测试与匿名场景。
- topic snapshot 渲染文本改变会影响 LLM routing 稳定性。

规避策略：

- `TheEye.gaze()` 迁移后先保持逐行等价。
- topic snapshot renderer 迁移必须有单元测试锁定输出。
- pre-retrieval 与 golden scenario 作为回归测试。

### 14.3 体验风险

Phase 1 理论上不改变用户可见体验。若迁移后出现体验变化，通常说明热路径行为被误改。

需要重点观察：

- 首轮对话是否仍正确创建 topic。
- 已有话题是否仍能被 TheEye 正确路由。
- chat stream 的前置信息是否仍按原顺序发送。
- passive ingest 的返回字段是否仍保持兼容。
