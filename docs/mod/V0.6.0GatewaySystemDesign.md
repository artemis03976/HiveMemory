# v0.6.0 新 Gateway 系统设计

**文档状态**: Draft  
**适用范围**: `gateway/`、`engines/gateway/`、`system/`、`patchouli/`、`alice/`、`core/protocol/`  
**前置版本**: v0.5.x 基础设施完成；全局指令库可并行推进  
**核心目标**: 将 Gateway 从 Patchouli 私有能力重构为顶层独立子系统，并用固定 workflow 取代旧的一步 LLM router。

---

## 1. 背景

旧 Gateway 的主要问题不是能否工作，而是归属和职责混在一起：

- `GatewayEngine` 虽然位于 `engines/gateway/`，但装配由 `PatchouliSystem` 完成。
- `TheEye` 位于 `patchouli/eye.py`，实际却承担系统入口分析职责。
- active chat 通过 `PatchouliService.prepare_agent_run()` 内部请求 `PatchouliLocalRoutes.GATEWAY_GAZE`，导致 Gateway 被 Patchouli prepare 时序反向托管。
- 旧 LLM router 在一次输出里同时完成话题路由、指代消解、关键词提取、记忆价值判断等任务，容易出现“博而不精”的决策退化。

v0.6.0 的新设计将 Gateway 定义为独立决策子系统。Patchouli 和 Alice 是执行/记忆/调度系统，Gateway 是入口决策系统。

---

## 2. 目标与非目标

### 2.1 目标

1. `GatewaySystem` 实现 `SubsystemProtocol`，与 Patchouli、Alice 平级。
2. 建立标准分层：`GatewaySystem` / `GatewayRuntime` / `GatewayService`。
3. Gateway 内部使用 local bus；跨子系统通信通过 global bus public route。
4. `ChatApplicationService` 禁止持有子系统实例，只通过 `GlobalSystemBus` 调用 Gateway/Patchouli/Alice。
5. active chat 主路径改为先进入 Gateway；Gateway workflow 终止后产出只读 `GatewayProcessResult`，下游只消费其中的公共决策，不接触内部执行状态。
6. 删除 active chat 主路径中的 `GatewayFacade`、`GatewayBundle`、`TheEye.gaze()`、`EyeGazeResult` 兼容投影和旧 `PatchouliLocalRoutes.GATEWAY_GAZE` 依赖。
7. 将旧一步 LLM router 拆为两个稳定边界：Topic Routing 只负责话题选择，User Query Analysis 统一负责从用户查询派生意图识别与分解、记忆价值、query rewrite 和检索相关决策。
8. User Query Analysis 的内部实现保持可替换，不在顶层 Gateway workflow 中预先固定 Engine 数量、调用顺序或并发关系。
9. Passive ingress 定位为外部对话记忆中间件：复用 Gateway 的 topic/query 决策和 Patchouli 的记忆读写能力，但不执行 HiveMemory command、Alice、MTP 或响应生成。

### 2.2 非目标

- 不实现完整 Alice Phase 3 顶层任务图编排。
- 不实现 Runtime Job Queue。
- 不实现 Planner、Planner Routing 或 `execution_plan` 占位。
- 不实现附件上传、文档解析、Document Ingestion 或 Deep Research。
- 不实现 MTP RUN executable asset、沙箱执行或真取消。
- 不保持旧 Gateway 行为等价；Phase 3 接受行为变化。
- 不提供 `workflow.enabled=false` 回退旧 Gateway。

## 3. 子系统边界

### 3.1 目标结构

```text

  analysis/

  commands/             # 全局指令库，详见独立文档
  workflow/
    workflow.py          # GatewayWorkflow: 固定拓扑与执行协调

src/hivememory/engines/gateway/

  intent_decomposer.py

src/hivememory/core/protocol/
  gateway.py            # GatewayDecision / GatewayProcessResult 公共只读契约
```

### 3.2 依赖方向

允许：

```text
gateway -> engines.gateway
gateway -> core models/protocol
gateway -> system contracts/routes
gateway.runtime -> GlobalSystemBus
system assembler -> gateway / patchouli / alice
patchouli -> core protocol models
```

禁止：

```text
engines.gateway -> gateway
engines.gateway -> system
engines.gateway -> patchouli
gateway -> patchouli concrete service
ChatApplicationService -> GatewaySystem/PatchouliSystem/AliceSystem concrete
PatchouliSystem -> gateway concrete composition root
PatchouliSystem -> gateway.workflow / GatewayExecutionState
ChatApplicationService -> gateway.workflow / GatewayExecutionState
```

Gateway 可以通过 `GlobalSystemBus` 请求 Patchouli public route，但不能 import Patchouli service 或 short-term store concrete。

`core.protocol.gateway` 是 Gateway 跨子系统输出的依赖中立契约层，不得 import `gateway`、`engines.gateway`、Patchouli 或 Alice。Gateway 在 `finalize()` 时负责把内部 engine/state 类型转换为公共协议类型。除 Gateway 自身外，任何模块都不得 import `gateway.workflow`。

## 4. GatewayContextProvider

Gateway 的上下文获取是两阶段、渐进式的，不能合并成 workflow 前的一次性获取。

### 4.1 数据对象

```python
class CandidateTopics(BaseModel):
    model_config = ConfigDict(frozen=True)

    topic_snapshots: tuple[TopicSnapshot, ...] = ()
    active_topics_menu: str = ""
```

`Identity`、`TopicSnapshot` 和 `TopicData` 本身就是跨模块使用的只读领域模型，不再为 Gateway 创建 `IdentitySnapshot`、`TopicSnapshotView` 或 `TopicDataView` 等平行类型。它们的定义方和提供方必须保证对象及全部嵌套字段在构建完成后递归只读：集合使用 tuple 或等价不可变结构，嵌套模型同样 frozen，不能只冻结最外层模型。

`CandidateTopics` 不重复保存 execution state 已有的 identity。Routed Topic Preparation 不创建只有一个字段的包装模型，直接把规范只读 `TopicData | None` 写入 state。Provider 获取失败、`NEW_TOPIC` 和正常无数据都使用 `None`，失败原因只发布到 runtime event sink。

规范类型归属固定如下：

- `Identity`、`TopicSnapshot`、`TopicData` 及 `TopicData` 直接引用的 block/state/value object 由依赖中立的 `core.models` 领域模块定义。
- 当前位于 `patchouli.memory_library` 或 `engines.perception`、但进入 `TopicData` 公共对象图的 `LogicalBlock`、buffer state 等类型，必须迁移为 core canonical type，或替换为依赖中立的规范定义；不能让 `core.models.TopicData` 反向 import Patchouli/Engine。
- `TopicSnapshot.last_turn` 不再使用可变 dict，改为 frozen `TopicLastTurn` 或等价只读值对象；所有嵌套 event/action/trace 集合使用 tuple，嵌套模型同样 frozen。
- `TopicData.recent_blocks()` 等只读查询不得返回可变内部集合引用；返回 tuple 或新的只读值。
- Patchouli、Perception 和旧导入路径可以在迁移期重导出 canonical type，但不得继续维护第二份模型定义。

Gateway Provider 只接收这些 canonical object，不创建镜像 DTO，也不执行 defensive copy/freeze。生产方若返回可变对象，属于公共协议实现错误。

### 4.2 Patchouli Topic 公开读取契约

Gateway 的两阶段 Context Preparation 依赖两个 Patchouli public route：

```python
class PatchouliRoutes:
    TOPIC_LIST_ACTIVE = "patchouli.public.topic.list_active"
    TOPIC_GET_DATA = "patchouli.public.topic.get_data"


class TopicReadPublicApi(Protocol):
    async def list_active_topics(
        self,
        *,
        identity: Identity,
        include_empty: bool = False,
    ) -> tuple[TopicSnapshot, ...]: ...

    async def get_topic_data(
        self,
        *,
        identity: Identity,
        topic_id: str,
    ) -> TopicData | None: ...
```

读取规则：

- `identity` 必须参与 ownership/visibility 校验；不存在、已驱逐和调用方不可见统一返回 `None`，不通过不同响应泄漏 topic 是否存在。
- `TOPIC_GET_DATA` 是无副作用只读操作，不更新 LRU、`last_accessed_at`、活跃状态或 topic 生命周期；真正使用 topic 的 touch/prepare 仍由 Patchouli active/passive 业务流程负责。
- 返回当前短期存储已经施加容量约束的完整 canonical `TopicData`，不能通过该 route 拼接无界历史 transcript、返回 lazy store entity 或暴露可变 `SemanticBuffer`。
- `topic_id="NEW_TOPIC"` 时 Gateway Provider 不调用 route，直接返回 `None`。
- 可预期的 unavailable/timeout 错误由 Provider adapter 转换为 `RecoverableGatewayError`，交给 Routed Topic Preparation Step fallback；权限协议错误和可变返回值属于 invariant failure。

### 4.3 Provider 接口

```python
class GatewayContextProvider(Protocol):
    async def prepare_candidate_topics(
        self,
        *,
        identity: Identity,
    ) -> CandidateTopics: ...

    async def prepare_routed_topic(
        self,
        *,
        identity: Identity,
        topic_id: str,
    ) -> TopicData | None: ...
```

设计决策：

- `prepare_candidate_topics()` 在 Topic Routing Step 前执行。
- `prepare_routed_topic()` 在 Topic Routing Step 提交 `topic_id` 后、User Query Analysis 分支前执行。
- Provider 本身不是 Engine 或决策组件；两个方法只提供上下文数据。
- Workflow 分别通过 Candidate Topics Preparation Step 和 Routed Topic Preparation Step 调用这两个方法。把 Provider 调用纳入 Step 只表示它参与一次原子状态转换，不把 Provider 重新定义为决策能力。
- 两个方法通过 `GlobalSystemBus` 请求 Patchouli public route。
- `topic_id="NEW_TOPIC"` 时 `prepare_routed_topic()` 直接返回 `None`，不请求完整上下文。
- 两个 Context Preparation Step 分别配置 timeout/fallback；失败后继续 workflow。
- Entry Interception command 命中时不得调用任何 provider 方法。
- `GatewayContextProvider` 只负责编排 public route、把响应转换为 Gateway 只读上下文对象，以及构造 Gateway 所需的派生展示文本；它不重复实现 Workflow Step 已负责的 timeout/fallback。
- Patchouli public route 返回的 `TopicSnapshot/TopicData` 必须在提供方边界内已经满足只读契约；若返回可变对象，属于提供方违反协议，不由 Gateway 防御性找补。

## 5. 执行状态、只读快照与公共结果

Gateway workflow 内部状态与跨子系统输出是两类不同对象：

- `GatewayExecutionState` 是 GatewayRuntime 私有、执行期可变的工作状态。
- `GatewayStateSnapshot` 是 Workflow Step 读取的递归只读快照。
- `GatewayProcessResult` 是 `GatewayService.process()` 返回的公共终态结果。
- `GatewayDecision` 是普通决策流程面向下游的依赖中立业务输出。

`GatewayExecutionState` 不得进入 `GlobalSystemBus`，也不得被 Patchouli、Alice、`ChatApplicationService` 或 API 层持有。workflow 结束时由 `GatewayWorkflow` 调用 `finalize()` 构造公共结果；这是一条序列化和依赖边界，而不是内部 state 的只读镜像。

### 5.1 统一写入

Workflow Step 不直接修改 `GatewayExecutionState` 字段。Step 的 Engine/Provider/Resolver 输出被投影为字段更新，并直接放入 `GatewayStepResult`：

```python
from dataclasses import dataclass, field
from types import MappingProxyType
from typing import Any, Mapping


@dataclass(frozen=True)
class GatewayStepResult:
    updates: Mapping[str, Any] = field(default_factory=dict)
    flow_end_reason: str | None = None
    is_fallback: bool = False
    fallback_reason: str | None = None

    def __post_init__(self) -> None:
        object.__setattr__(
            self,
            "updates",
            MappingProxyType(dict(self.updates)),
        )


@dataclass(frozen=True)
class UserQueryAnalysisResult:
    intent_type: IntentType
    rewritten_query: str
    search_keywords: tuple[str, ...]
    memory_write_signal: MemoryWriteSignal
    retrieval_plan: RetrievalPlan
```

`GatewayStepResult` 在构造时快照并只读化 updates mapping，避免调用方在 apply 前修改字段集合；updates 中的领域值仍由其生产方保证递归只读。

`UserQueryAnalysisResult` 是 Routed Topic Preparation 之后唯一写入 execution state 的分析结果。意图分解是 Resolver 私有中间结果，可以在 Resolver 内部影响 `intent_type`、query rewrite、记忆价值和检索决策，但没有明确下游消费者前不写入 execution state 或公共协议。当前版本仍只 finalize 一个 `GatewayDecision`，不输出多个 state 或 decision。

`GatewayExecutionState._apply_step_result()` 是 Workflow 内部唯一字段提交入口，负责：

- 拒绝 updates 中不存在的 state 字段。
- 写入 updates。
- 设置 flow end。
- state 完成后拒绝任何新提交。

顶层 Step 从一个只读 `GatewayStateSnapshot` 开始，完成后产生一个 `GatewayStepResult`。Step 通过显式 input selector 从 snapshot 构造自身的 typed input，不能获得内部 state 的可变引用，也不能把完整 snapshot 直接传给 Engine、Provider 或 Resolver 以隐藏真实输入依赖。

### 5.2 GatewayExecutionState 草案

```python
@dataclass
class GatewayExecutionState:
    raw_message: str
    identity: Identity
    ingress_mode: GatewayIngressMode

    # Entry Interception 在 context preparation 之前执行，因此初始化时允许为空
    candidate_topics: CandidateTopics | None = None

    # Entry Interception Step
    l1_result: InterceptorResult | None = None
    command_parse_result: CommandParseResult | None = None
    command_execution_result: CommandExecutionResult | None = None
    flow_end_reason: str | None = None

    # Topic Routing Step
    topic_id: str | None = None
    new_topic_title: str | None = None
    new_topic_summary: str | None = None

    # Routed Topic Preparation Step
    routed_topic_data: TopicData | None = None

    # User Query Analysis / Simple Chat Defaults 分支
    user_query_analysis: UserQueryAnalysisResult | None = None

    status: ExecutionStateStatus = ExecutionStateStatus.RUNNING
```

约束：

- `raw_message`、`identity` 和 `ingress_mode` 是 workflow 初始化输入，任何 Step updates 都不得覆盖。
- state 的顶层字段可以在 `GatewayWorkflow` apply updates 时被替换，但 Step 不持有 state 本身。
- 写入 state 的值必须由其生产方按只读契约构建完成；Provider、Engine、Resolver 和 Step 都不得把可变 list/dict 或可变嵌套模型放入 updates/state。
- `_apply_step_result()` 不执行 defensive copy/freeze 或通用运行时类型反射；projector 和契约测试负责产出正确类型，违反只读或类型契约属于实现错误。
- `candidate_topics=None` 只允许出现在 Entry Interception 尚未完成或 command 已短路的状态；进入 Topic Routing Step 前必须提交 `CandidateTopics`。
- `status=COMPLETED` 表示 workflow 生命周期结束，不等价于 Python 对象已经递归冻结；外部不可变性由公共结果契约保证。

### 5.3 GatewayStateSnapshot

```python
@dataclass(frozen=True)
class GatewayStateSnapshot:
    raw_message: str
    identity: Identity
    ingress_mode: GatewayIngressMode
    candidate_topics: CandidateTopics | None
    routed_topic_data: TopicData | None
    topic_id: str | None
    new_topic_title: str | None
    new_topic_summary: str | None
    user_query_analysis: UserQueryAnalysisResult | None
```

快照不要求机械复制 state 的全部字段；`GatewayWorkflow` 可以按 Step 的 input selector 需要生成浅层投影，并直接复用已经只读的领域对象引用。它必须满足：

- snapshot 外壳 frozen，且所有引用值在进入 state 前已经由其生产方保证递归只读。
- snapshot 构建不执行 defensive deep copy，也不创建 `IdentitySnapshot/TopicSnapshotView/TopicDataView`。
- list 使用 tuple，映射使用只读值对象，嵌套 Pydantic/dataclass 同样 frozen；仅冻结最外层但内部仍包含 list/dict，不符合上游模型契约。
- 每个 Step 读取提交前创建的只读快照；顶层 Workflow 严格串行，不提供额外的乐观锁机制。

### 5.4 公共终态契约

公共协议位于依赖中立的 `core.protocol.gateway`。其中的枚举和值对象不得复用可变 engine model；Gateway 在 finalize 边界显式转换。

```python
class GatewayIngressMode(str, Enum):
    ACTIVE_CHAT = "active_chat"
    PASSIVE_MEMORY = "passive_memory"


@dataclass(frozen=True)
class GatewayDecision:
    target_topic_id: str
    new_topic_title: str | None
    new_topic_summary: str | None
    rewritten_query: str
    search_keywords: tuple[str, ...]
    memory_write_signal: MemoryWriteSignal
    retrieval_plan: RetrievalPlan
    intent_type: IntentType


@dataclass(frozen=True)
class GatewayCommandOutcome:
    kind: Literal["command"] = "command"
    command_execution_result: CommandExecutionResult


@dataclass(frozen=True)
class GatewayDecisionOutcome:
    kind: Literal["decision"] = "decision"
    decision: GatewayDecision


GatewayProcessResult = GatewayCommandOutcome | GatewayDecisionOutcome
```

公共契约规则：

- `GatewayIngressMode` 是固定的入口策略枚举，不扩展为调用方任意组合的 capability flags；新增 mode 必须同时定义 Entry Interception、terminal outcome 和下游消费规则。
- `ingress_mode` 不进入 `GatewayDecision`；它只约束本次 Gateway 执行策略，消费方根据自身调用入口决定后续编排。
- `GatewayProcessResult` 使用 `kind` 判别，不使用 command/decision 多个 nullable 字段表达终态。
- `CommandExecutionResult` 也必须定义为依赖中立、递归不可变的公共 command protocol；`core.protocol.gateway` 不得为复用该类型而反向 import `gateway.commands`。
- `GatewayDecision` 只包含稳定业务决策，不包含 candidate topics、routed topic data、GatewayStepResult、runtime event、fallback 细节、原始 LLM 输出或 Gateway workflow step 名称。
- `RetrievalPlan` 表达 Gateway 的检索决策，不直接包含 Patchouli 执行用的 `RetrievalRequest`；Patchouli 在自身边界内根据 decision、identity 和调用参数构造请求。
- `memory_write_signal` 是唯一记忆价值信号；Patchouli 需要 `worth_saving` 时在适配层按 `WRITE -> True`、`SKIP -> False`、`UNKNOWN -> None` 派生。
- User Query Analysis 的 decomposition 结果只作为 Resolver 私有中间值；`UserQueryAnalysisResult.intent_type` 直接投影到公共 `GatewayDecision.intent_type`。
- 所有嵌套公共类型必须递归不可变并可稳定序列化。
- Phase 3 的直接消费方是 Patchouli；Alice 继续消费 `AgentRunContext`。只有出现明确的 Alice 直连需求时，才从 `GatewayDecision` 派生 Alice 专用视图。

### 5.5 Finalize

`GatewayExecutionState.finalize()` 由 `GatewayWorkflow` 调用，且是内部 state 转为公共结果的唯一出口，负责：

- 校验 command outcome 与 decision outcome 的互斥关系。
- 校验当前 flow 所需字段是否完整。
- command flow 构造 `GatewayCommandOutcome`。
- 普通 flow 构造 `GatewayDecisionOutcome`。
- 把内部 engine model 显式转换为公共 frozen value object。
- 把 state 标记为 `COMPLETED`，拒绝后续 updates。
- 通过 `RuntimeEventSink` 发布 workflow completed event；runtime event 不进入 `GatewayProcessResult`。

普通 decision 的派生规则：

- 所有普通 flow，包括 simple chat，都必须在进入 finalize 前已有完整 `UserQueryAnalysisResult`；finalize 只负责投影 `intent_type`、`rewritten_query`、`search_keywords`、`memory_write_signal` 和 `retrieval_plan`，不再包含 simple-chat 特判。
- simple chat 的完整分析结果由 workflow 中的 Simple Chat Defaults Step 提前构造，而不是由 finalize 临时补齐。
- `user_query_analysis.retrieval_plan.mode == SKIP` 时保持 `RetrievalPlan(mode=SKIP)`；是否执行检索还要由 Patchouli 与 `enable_memory_retrieval` 共同决定。
- finalize 缺少普通 flow 必需字段属于 Gateway 实现错误，不使用隐式 `None` 继续跨子系统传播。

## 6. Workflow 执行模型

### 6.1 Workflow Step

Gateway 不再以“一串逐阶段业务对象”描述执行过程。顶层执行单位统一为 Workflow Step：

- **Workflow Step**：一次原子状态转换，从一个 `GatewayStateSnapshot` 开始，调用 Engine、Provider、Resolver 或 Gateway 本地纯逻辑，并提交一个 `GatewayStepResult`。
- **Engine / Provider**：Step 背后的能力实现，不感知 Workflow state、updates、fallback、event 或 apply。
- **Resolver**：Gateway 内部的能力组合边界，可以在不改变顶层 Workflow 的前提下组织一个或多个 Engine。

Step 的含义不是“调用一次底层 Engine”，而是“一次原子调度和状态提交”。Resolver 是否使用单次 LLM、多个 Engine、串行或并发执行，都不改变顶层 Step 数量和提交语义。

每个 Step 必须满足：

1. 从一个只读 snapshot 开始。
2. 明确声明输入选择器、能力调用、结果投影、timeout 和 fallback。
3. Step 只返回 `GatewayStepResult`，不持有和修改 execution state。
4. 整个 Step 只调用一次 `_apply_step_result()`。
5. Resolver 内部实现变化不得改变 Step 的输入输出契约和外层提交语义。

### 6.2 通用 Step 定义

Workflow 只提供一种通用 Step，不为每个业务步骤建立 wrapper 子类，也不再建立一对一的 Operation 对象：

```python
class RecoverableGatewayError(Exception):
    """Provider/Engine/Resolver adapter 的预期能力失败。"""


@dataclass(frozen=True)
class GatewayWorkflowStep(Generic[InputT, OutputT]):
    step_id: str
    select_input: Callable[[GatewayStateSnapshot], InputT]
    invoke: Callable[[InputT], Awaitable[OutputT]]
    project: Callable[[OutputT], Mapping[str, Any]]
    timeout_ms: int | None = None
    fallback: Callable[[InputT, Exception], Mapping[str, Any]] | None = None
    resolve_flow_end: Callable[[OutputT], str | None] | None = None
```

`select_input` 必须把 snapshot 投影为明确的 typed input。禁止为了减少适配代码而把完整 `GatewayStateSnapshot` 直接传给 Engine、Provider 或 Resolver，否则能力组件的真实数据依赖会重新变成隐式依赖。

`project` 是 Gateway workflow 边界的显式适配：Engine、Provider 或 Resolver 返回自己的领域结果，Step 再把结果转换为 updates mapping。它们不得直接返回 `GatewayStepResult`。

Step fallback 只覆盖 `invoke` timeout 或明确的 `RecoverableGatewayError`。Provider/Engine/Resolver adapter 负责把预期能力错误转换为该异常；`select_input`、`project`、未知字段和只读契约错误属于 invariant failure，不进入 fallback。

`GatewayWorkflow` 自身负责 `_run_step()`，不额外暴露通用 Executor 组件。该方法统一处理 snapshot、计时、timeout/fallback、result apply 和 runtime event；`GatewayWorkflow` 通过构造参数接收 `RuntimeEventSink`。

### 6.3 固定拓扑

Phase 3 是“一个显式终止分支 + 一个显式分析旁路”，不引入通用 DAG、节点注册表或动态拓扑解释器：

```text
GatewayService.process(message, identity, ingress_mode)
  ↓
Entry Interception Step
  ├─ system command → Command Dispatch → finalize()
  └─ continue（包括 simple chat）
       ↓
Candidate Topics Preparation Step       [Provider]
       ↓
Topic Routing Step                      [Engine]
       ↓
Routed Topic Preparation Step           [Provider]
       ↓
Is Simple Chat?
  ├─ yes → Simple Chat Defaults Step     [Gateway local pure logic]
  └─ no  → User Query Analysis Step      [Resolver]
       ↓
GatewayExecutionState.finalize()
       ↓
GatewayProcessResult
```

`GatewayWorkflow` 在装配时持有 Entry Step、固定的 `decision_prefix`、Simple Chat Defaults Step 和 User Query Analysis Step。Entry Step 之后只有 system command 是 terminal branch；simple chat 信号由 `l1_result` 明确承载，并在完成固定前缀后选择分析旁路。该分支直接写在 `GatewayWorkflow` 控制流中，不扩展为通用 predicate、条件 Step 或动态节点机制。

旁路条件固定为 Entry Interceptor 命中且 `l1_result.intent == GatewayIntent.CHAT`；未命中或其他非终止 intent 一律进入 standard User Query Analysis。Workflow 不通过 `flow_end_reason`、metadata 字符串或 `intent_type` 的提前写入推断该条件。

装配结构示例：

```python
workflow = GatewayWorkflow(
    entry_step=GatewayWorkflowStep(
        step_id="entry_interception",
        select_input=select_entry_input,
        invoke=entry_interceptor.intercept,
        project=project_entry_result,
        resolve_flow_end=resolve_entry_flow_end,
    ),
    decision_prefix=(
        prepare_candidate_topics_step,
        topic_routing_step,
        prepare_routed_topic_step,
    ),
    simple_chat_defaults_step=GatewayWorkflowStep(
        step_id="simple_chat_defaults",
        select_input=select_simple_chat_defaults_input,
        invoke=build_simple_chat_analysis_result,
        project=project_user_query_analysis,
    ),
    user_query_analysis_step=user_query_analysis_step,
)
```

`resolve_flow_end` 只把能力输出解释为 Step 级控制信号；它不执行副作用。Phase 3 只有 Entry Interception Step 使用该能力，并且只有 system command 产生 `flow_end_reason`。simple chat 是分析选择信号，不是 flow-end signal。

### 6.4 Entry Interception Step

- 调用：复用 `RuleInterceptor` / `CommandRegistry`，统一处理系统指令与简单闲聊。
- 输入：`raw_message` + `ingress_mode`。
- command 输出：`l1_result`、`command_parse_result`、`flow_end_reason="system_command"`。
- simple chat 输出：只写携带 CHAT 命中的 `l1_result`，不设置 `flow_end_reason`。
- 约束：不写 topic routing、context preparation 或 `user_query_analysis` 字段。
- command dispatcher 的副作用由 workflow 的显式 terminal branch 执行，不放进 RuleInterceptor Engine。
- simple chat 必须继续执行 Candidate Topics Preparation、Topic Routing 和 Routed Topic Preparation；Entry Interception 不负责 topic 选择。
- `ACTIVE_CHAT` 启用 HiveMemory command 识别和 dispatch；`PASSIVE_MEMORY` 完全禁用 command 规则，外部 `/command` 作为普通对话文本继续 workflow，但仍启用 simple-chat 识别。
- `PASSIVE_MEMORY` 不得产生 `GatewayCommandOutcome`；违反该约束属于 Gateway invariant failure。

### 6.5 Candidate Topics Preparation Step

- 调用：`GatewayContextProvider.prepare_candidate_topics()`。
- 输入：`identity`。
- 输出：`candidate_topics`。
- fallback：空 `CandidateTopics`。
- 约束：只准备 Topic Routing 所需上下文，不承担任何路由决策。

### 6.6 Topic Routing Step

- 调用：`TopicRouterEngine.route()`。
- 输入：`raw_message` + `candidate_topics.topic_snapshots`。
- 输出：`topic_id`、`new_topic_title`、`new_topic_summary`；routing reason 只进入 event sink。
- 禁止输出：`user_query_analysis` 或其中的任何分析决策。
- fallback：`topic_id="NEW_TOPIC"`。

TopicRouterEngine 只承接旧 LLMAnalyzer 中的话题选择能力。query rewrite、keywords 和检索策略不属于 Topic Routing Step。

### 6.7 Routed Topic Preparation Step

- 调用：`GatewayContextProvider.prepare_routed_topic()`。
- 输入：`identity` + `topic_id`。
- 输出：`routed_topic_data: TopicData | None`。
- fallback：`None`。
- 约束：只准备后续分析需要的完整话题上下文，不参与 Engine 决策，也不由 TopicRouterEngine 发起总线请求。

### 6.8 User Query Analysis 分支

Routed Topic Preparation 完成后，Workflow 根据 `l1_result` 显式选择且只选择一个 Step。两个分支都只写一次 `user_query_analysis`，因此后续 finalize 和下游消费保持完全一致。

#### Standard User Query Analysis Step

未命中 simple chat 时，User Query Analysis 是唯一的顶层分析 Step：

```python
@dataclass(frozen=True)
class UserQueryAnalysisContext:
    raw_message: str
    identity: Identity
    candidate_topics: CandidateTopics
    topic_id: str
    new_topic_title: str | None
    new_topic_summary: str | None
    routed_topic_data: TopicData | None


class UserQueryAnalysisResolver(Protocol):
    async def resolve(
        self,
        context: UserQueryAnalysisContext,
    ) -> UserQueryAnalysisResult: ...
```

- 调用：`UserQueryAnalysisResolver.resolve()`。
- 输入：路由完成后的完整 `UserQueryAnalysisContext`。
- 输出：只写 `user_query_analysis: UserQueryAnalysisResult`。
- 职责范围：从 User Query 派生意图识别与分解、记忆价值判断、query rewrite、search keywords 和检索计划。
- fallback：生成完整、保守的 `UserQueryAnalysisResult`，使用 `intent_type=QUERY`、`rewritten_query=raw_message`、空 keywords、`MemoryWriteSignal.UNKNOWN` 和默认 HYBRID retrieval plan。
- 约束：不重新选择 topic，不执行实际检索或记忆写入。

顶层 Workflow 只依赖 Resolver 的输入输出契约。Resolver 内部可以暂时复用旧单次 LLM analyzer，也可以在后续重设计后组合 IntentClassifier、IntentDecomposer、MemoryValueJudge、QueryUnderstanding 和 RetrievalStrategy 等 Engine。具体调用顺序、共享 Prompt、串并行关系、中间结果和局部 fallback 都属于 Resolver 私有实现，不是顶层 Workflow 契约。

#### Simple Chat Defaults Step

命中 simple chat 时，不调用 `UserQueryAnalysisResolver` 或任何候选分析 Engine。Workflow 运行一个由通用 `GatewayWorkflowStep` 装配的 Gateway 本地纯逻辑 Step，构造：

```python
UserQueryAnalysisResult(
    intent_type=IntentType.CHAT,
    rewritten_query=raw_message,
    search_keywords=(),
    memory_write_signal=MemoryWriteSignal.SKIP,
    retrieval_plan=RetrievalPlan(mode=RetrievalMode.SKIP),
)
```

设计约束：

- 该结果是预期业务旁路，不是 fallback，`GatewayStepCompleted.is_fallback` 必须为 `False`。
- Step 不读取 `routed_topic_data` 来执行分析，但它在 Routed Topic Preparation 之后运行，以保持 topic routing 和上下文准备时序一致。
- Step 不发布 `GatewayAnalysisCapabilityCompleted`，因为没有调用 Resolver capability。
- `RetrievalPlan(mode=SKIP)` 使 Patchouli 跳过实际检索；`MemoryWriteSignal.SKIP` 使下游不为该输入触发记忆价值写入，但不阻止正常 topic prepare、Alice 响应和 Patchouli finalize。
- simple chat 最终仍返回普通 `GatewayDecisionOutcome`，不新增 direct-response 或 terminal outcome。

## 7. Engine 原语

`engines/gateway` 只放纯决策原语，不依赖 SystemBus/Patchouli/Alice/runtime state。

`TopicRouterEngine` 是当前顶层 Workflow 已确定使用的独立原语，只产出 topic routing。User Query Analysis 内部可能使用的能力包括但不限于：

| 候选 Engine | 能力边界 |
| --- | --- |
| `IntentClassifierEngine` | primary/composite intent 识别 |
| `IntentDecomposerEngine` | 复合意图分解 |
| `MemoryValueJudgeEngine` | 记忆价值信号 |
| `QueryUnderstandingEngine` | 指代消解、query rewrite 和 search keywords |
| `RetrievalStrategyEngine` | 检索相关性、模式和参数建议 |

该表只描述候选能力边界，不规定 User Query Analysis Resolver 必须把每项能力实现为独立类、独立 LLM 调用或固定顺序。Resolver 契约确认前，不以顶层 Workflow、execution state 字段或测试用例固化这些候选 Engine 的组合形式。

不新增 engine 专用 prompt/parser 子包：

- prompt 文本继续由 i18n 模板统一管理。
- JSON parsing / schema 解析复用项目已有通用工具函数。

## 8. User Query Analysis 演进边界与 Fallback

### 8.1 稳定边界与可变实现

当前版本只冻结以下内容：

- `UserQueryAnalysisContext` 的路由后输入边界。
- `UserQueryAnalysisResult` 的完整只读输出边界。
- User Query Analysis 在顶层 Workflow 中只占一个 Step、只 apply 一次结果。
- Resolver 不修改 topic route，不执行检索、记忆写入或 planning。

以下内容在 Engine 实现验证前保持可变：

- 使用一次 LLM 还是多个 Engine。
- 意图识别与分解是否共享 Prompt。
- 记忆价值、query rewrite 和检索相关判断之间的依赖方向。
- 内部是否串行、并发或分阶段执行。
- Resolver 私有中间状态和局部 fallback。

内部实现变化只能修改 Resolver 及其装配，不能要求 `GatewayService`、顶层 `GatewayWorkflow`、`GatewayExecutionState` 或公共 `GatewayDecision` 感知内部 Engine 顺序。

### 8.2 Engine 契约确认

实现或拆分候选 Engine 前，必须先记录并验证：

| 项目 | 必须回答的问题 |
| --- | --- |
| Required inputs | 能力必须依赖 User Query Analysis Context 中哪些字段？ |
| Optional inputs | 上下文缺失时能否降级？ |
| Outputs | 输出是事实、建议还是 Resolver 最终决策？ |
| Consumer | 哪个后续判断实际消费该输出？ |
| Latency/cost | 是否值得独立调用模型？ |
| Failure policy | timeout、模型错误和解析失败分别如何处理？ |
| Ordering | 是否存在经过验证的先后依赖？ |
| Concurrency | 是否能读取同一 immutable input 独立执行？ |
| Side effects | 是否严格只做分析，不执行写入或检索？ |

只有这些依赖被测试或原型验证后，才在 Resolver 内确定组合方式；不得先按设想建立 Engine wrapper 和固定调用顺序。

### 8.3 Workflow Fallback

| 位置 | 触发条件 | 默认值 |
| --- | --- | --- |
| Candidate Topics Preparation Step | topic list 超时/失败 | 空 `CandidateTopics` |
| Topic Routing Step | LLM/解析失败 | `topic_id="NEW_TOPIC"` |
| Routed Topic Preparation Step | topic context 超时/失败 | `None` |
| User Query Analysis Step | overall timeout/可恢复分析失败 | 完整保守的 `UserQueryAnalysisResult` |

User Query Analysis 的外层 fallback 必须一次性补齐 finalize 所需字段，不能把部分 `None` 传播到公共结果。Resolver 内部将来可以保留局部成功结果，但这是 Resolver 实现策略，不改变 Step 的提交契约。

Simple Chat Defaults Step 不调用外部能力，不配置业务 fallback；其 selector/projector 或默认结果构造错误属于 invariant failure。

Phase 3 中可预期的 Provider、LLM、timeout 和解析失败不得中止 normal flow，必须落入声明的 Step fallback。selector/projector 错误、未知 state 字段、返回值类型错误和违反递归只读契约等 invariant failure 属于 Gateway 实现错误，必须终止 workflow 并暴露错误，不能用业务 fallback 掩盖。

## 9. Active Chat 新时序

在新 Gateway 系统落地后，streaming 与 non-streaming active chat 使用相同的 Gateway → Patchouli prepare → Alice → Patchouli finalize 业务时序，只在对外结果承载形式上不同。

### 9.1 Streaming Active Chat

目标调用链：

```text
ChatApplicationService.chat_stream()
  -> identity = Identity(user_id, agent_id, session_id)
  -> gateway_result = GlobalSystemBus.request(
         GatewayPublicRoutes.PROCESS,
         message=user_message,
         identity=identity,
         ingress_mode=GatewayIngressMode.ACTIVE_CHAT,
         cancel_event=run.cancel_event,
         request_timeout_ms=gateway_timeout_ms,
     )
     ├─ Entry Interception command 命中时短路
     └─ 其他输入由 GatewayService 完成 Gateway workflow；simple chat 仅旁路 User Query Analysis
  -> if gateway_result.kind == "command":
       emit command_result(gateway_result.command_execution_result)
       emit done
       stop
  -> gateway_decision = gateway_result.decision
  -> prepared = GlobalSystemBus.request(
         GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN,
         user_message=user_message,
         user_id=user_id,
         agent_id=agent_id,
         session_id=session_id,
         gateway_decision=gateway_decision,
         enable_memory_retrieval=enable_memory_retrieval,
         generation_options=generation_options,
     )
  -> Alice run
  -> PatchouliService.finalize_agent_run(...)
```

`PatchouliService.prepare_agent_run()` 原地改造：

```python
async def prepare_agent_run(
    self,
    user_message: str,
    user_id: str,
    *,
    gateway_decision: GatewayDecision,
    agent_id: str = "omni_doll",
    session_id: str | None = None,
    enable_memory_retrieval: bool = True,
    generation_options: dict[str, Any] | None = None,
) -> PreparedAgentRun:
    ...
```

约束：

- `gateway_decision` 必传；未传入或收到 command outcome 是调用方错误。
- Patchouli 只 import `core.protocol.gateway.GatewayDecision`，不得 import `gateway.workflow`。
- `GatewayExecutionState`、snapshot 和 runtime event 不得进入 Patchouli prepare。
- `prepare_agent_run()` 不再获取 active topic snapshots 供 Gateway 使用。
- `prepare_agent_run()` 不再调用 gaze。
- `prepare_agent_run()` 根据 `GatewayDecision` 构造 Patchouli 自身的 `RetrievalRequest` 和记忆写入派生值，并继续负责 topic prepare、pool topics、topic context、retrieval、memory context、`AgentRunContext` 和 `StreamPrelude`。

### 9.2 Non-streaming Active Chat

`ChatApplicationService.chat()` 同样必须先调用 Gateway，不能继续直接进入 `PATCHOULI_PREPARE_AGENT_RUN`。由于 system command 与 Agent run 是两种互斥的正常结果，原来固定返回 `AgentRunResult` 的签名改为应用层判别联合：

```python
@dataclass(frozen=True)
class NonStreamingChatCommandOutcome:
    kind: Literal["command"] = "command"
    command_execution_result: CommandExecutionResult


@dataclass(frozen=True)
class NonStreamingChatAgentOutcome:
    kind: Literal["agent"] = "agent"
    agent_run_result: AgentRunResult


NonStreamingChatResult = (
    NonStreamingChatCommandOutcome | NonStreamingChatAgentOutcome
)
```

该联合属于 System application chat contract，不放入 Gateway protocol；它表达完成整个应用编排后的结果，而不是 Gateway 自身的决策结果。

规则：

- command outcome 直接映射为 `NonStreamingChatCommandOutcome`，不得调用 Patchouli prepare、Alice 或 Patchouli finalize。
- decision outcome 使用与 streaming 完全相同的 prepare/run/finalize 路径，最终包装为 `NonStreamingChatAgentOutcome`。
- simple chat 属于 decision outcome，继续运行 Alice，但 retrieval plan 为 SKIP。
- cancellation 在 Alice 前发生时仍构造 status=cancelled 的 `AgentRunResult` 并放入 agent outcome；业务失败继续抛出异常，不增加 nullable error 字段。
- HTTP/API 层按 `kind` 稳定序列化，不直接返回内部 `GatewayProcessResult` 或 `PreparedAgentRun`。
- streaming 与 non-streaming 的 Gateway decision、topic、retrieval 和 memory-write 行为必须一致，不能维护两套 prepare 逻辑。

### 9.3 Gateway 请求控制

Active chat 在调用 Gateway 前已经创建并注册 `ChatGenerationRun`，因此 Gateway public process 接受运行时控制参数：

```python
async def process(
    message: str,
    *,
    identity: Identity,
    ingress_mode: GatewayIngressMode,
    cancel_event: asyncio.Event | None = None,
    request_timeout_ms: int | None = None,
) -> GatewayProcessResult: ...
```

`cancel_event` 和 deadline 是运行时控制句柄，不进入 `GatewayExecutionState`、snapshot、Engine/Provider/Resolver 输入或公共业务结果。Gateway 在入口、每个 Step 前和等待 `invoke` 期间检查取消。

控制规则：

- 用户取消时取消当前可取消的 invoke，发布 `GatewayWorkflowCancelled`，并抛出专用 `GatewayCancelledError`；取消不是业务 fallback，也不构造部分 `GatewayProcessResult`。
- `ChatApplicationService` 将该控制异常映射为现有 cancelled chat result/done，并且不调用 Patchouli/Alice。
- `request_timeout_ms` 转换为 workflow 绝对 deadline；每个 Step 的有效 timeout 为自身 timeout 与剩余 deadline 的较小值。
- deadline 触发 normal Step timeout 时仍使用该 Step 已声明的业务 fallback；deadline 已耗尽后不再发起新的 Provider/Engine/Resolver IO，只运行本地 fallback 以补齐可 finalize 的保守 decision。
- 若 deadline 命中的 Step 没有 fallback，或本地 fallback 无法补齐终态不变量，则抛出 `GatewayTimeoutError`，不能传播部分 decision。
- selector/projector/invariant failure 不因 deadline 或 cancel 改写为 fallback。

## 10. Passive Conversation Memory Ingress

Passive ingress 的完整设计已拆分到独立文档：[`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。

主文档只保留 Gateway 侧的契约约束：

- `GatewayIngressMode.PASSIVE_MEMORY` 是 Gateway `process()` 的必传策略枚举值，复用同一 Gateway workflow、state 和 `GatewayDecision`。
- `PASSIVE_MEMORY` 下禁用 HiveMemory command 识别，只返回 `GatewayDecisionOutcome`；simple-chat bypass、Topic Routing、User Query Analysis 和 finalize 契约与 `ACTIVE_CHAT` 保持一致。
- Passive ingress 不把外部 HTTP disconnect 直接作为 Gateway cancel；它使用 request timeout 和降级 decision，确保已接受的外部 user event 仍可进入 turn buffer。
- Passive ingress 的实现不阻塞 Gateway 核心迁移；Gateway 核心流程（Phase 3A–3F）稳定后，Passive ingress 可并行设计或延后实现。

## 11. 配置

```python
class GatewayWorkflowConfig(BaseModel):
    default_request_timeout_ms: int = 8000


class GatewayContextPreparationConfig(BaseModel):
    candidate_topics_timeout_ms: int = 1000
    routed_topic_timeout_ms: int = 1000
    include_empty_topics: bool = False


class TopicRouterConfig(BaseModel):
    enabled: bool = True
    timeout_ms: int = 3000
    model_override: str | None = None


class UserQueryAnalysisConfig(BaseModel):
    overall_timeout_ms: int = 5000
    default_mode: Literal["dense", "sparse", "hybrid", "skip"] = "hybrid"
    default_top_k: int = 5
```

User Query Analysis 的顶层配置只表达整体 deadline 和外层 fallback 默认值。候选 Engine 的模型、Prompt、timeout 和并发配置由具体 Resolver 实现拥有，在 Resolver 契约稳定前不提升为 Gateway 顶层配置。`GatewayIngressMode` 是 Gateway 识别的唯一入口策略；Passive ingress 自身的配置属于 System application 层，见 [`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。

调用方未传 `request_timeout_ms` 时使用 `GatewayWorkflowConfig.default_request_timeout_ms`；显式请求值只能收紧本次 deadline，不能绕过系统配置允许无限执行。

## 12. 可观测性

`RuntimeEventSink` 是 Gateway 可观测性的唯一来源。Gateway 不在 `GatewayExecutionState` 中保存 trace，不定义平行的 StepTrace/OperationTrace 模型，也不直接写日志、metrics 或 tracing span；具体后端由 event sink adapter 决定。

Gateway 至少发布以下结构化事件：

| Event | 关键字段 |
| --- | --- |
| `GatewayWorkflowStarted` | workflow/request correlation、`ingress_mode`、开始时间 |
| `GatewayStepCompleted` | `step_id`、`step_index`、`duration_ms`、`is_fallback`、`fallback_reason`、`flow_ended` |
| `GatewayWorkflowCompleted` | 总耗时、完成 Step 数、outcome kind、关键决策摘要 |
| `GatewayWorkflowCancelled` | 当前 `step_id`、`ingress_mode`、总耗时 |
| `GatewayWorkflowFailed` | 当前 `step_id`、错误分类、总耗时 |
| `GatewayAnalysisCapabilityCompleted` | Resolver 内部 capability ID、耗时、fallback/error 摘要 |

Passive ingress 自身的事件发布规则见 [`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。

规则：

- `GatewayWorkflow` 在顺序执行 Step 时维护局部 `step_index`，只写入 event，不进入 execution state。
- Provider、Engine 和 Resolver fallback 统一通过 `GatewayStepCompleted` 表达。
- cancellation 单独发布 `GatewayWorkflowCancelled`，不伪装成 Step fallback 或 `GatewayWorkflowFailed`。
- User Query Analysis Resolver 的内部 Engine 调用只通过 `GatewayAnalysisCapabilityCompleted` 表达，不把内部顺序编码进顶层 Step 或 State。
- `debug_trace=true` 时可以向 event sink 增加经过脱敏的输入/输出摘要，但不在 state 中缓存完整 snapshot，也不默认发往前端。
- event sink 使用失败不得改变 Gateway 的业务结果；生产环境必须提供 non-throwing adapter，测试使用 recording/null sink。
- runtime event、debug 摘要和错误细节不得附加到 `GatewayProcessResult/GatewayDecision`。

## 13. 实现计划

实现计划按"先恢复 active chat 基本可用性、再补齐请求控制和观测、最后处理 passive ingress"的顺序编排。Phase 3A–3F 是 Gateway 核心迁移，必须顺序执行；Phase 3G 起为后续阶段，可在核心稳定后并行或延后。

### Phase 3A: Gateway 子系统骨架

- 新增 `src/hivememory/gateway/` 顶层包。
- 实现 `GatewaySystem`、`GatewayRuntime`、`GatewayService`。
- 新增 local/public routes、runtime bus、route bindings。
- 系统装配根构造 `GatewaySystem`，不再构造 `GatewayFacade/GatewayBundle`。

验收：

- `GatewaySystem` 满足 `SubsystemProtocol`。
- local route mount/unmount 幂等。
- `GatewayService.process()` 可跑最小空 workflow。

### Phase 3B: Engine 原语、执行 State 与公共结果契约

- 整理 `engines/gateway` 原语。
- 收敛 `Identity`、`TopicSnapshot`、`TopicLastTurn`、`TopicData` 及其嵌套 block/state 类型的递归只读不变量；规范类型位于依赖中立的 core domain，由提供方直接构造，Patchouli/Perception 只做迁移期重导出。
- 定义 Gateway 私有的 `GatewayExecutionState`、`GatewayStateSnapshot`、`CandidateTopics`、`UserQueryAnalysisContext`、`UserQueryAnalysisResult`、`GatewayStepResult`。
- 在依赖中立的 core protocol 中定义 `GatewayIngressMode`、`GatewayDecision`、`GatewayCommandOutcome`、`GatewayDecisionOutcome`、`GatewayProcessResult`。
- 定义 retrieval/memory 派生规则。
- 不依赖 `EyeGazeResult`。

### Phase 3C: GatewayWorkflow 与 Step

- 实现 `GatewayWorkflow`、command short-circuit、simple-chat analysis bypass、snapshot、step result apply、finalize 和 runtime event。
- 实现单一通用 `GatewayWorkflowStep`；不新增逐业务步骤 wrapper 类或一对一 Operation 对象。
- 用显式 command terminal branch、固定 `decision_prefix` 和显式 analysis branch 表达拓扑，不实现通用 DAG、通用条件 Step 或动态节点注册表。
- Topic Routing Step 只做 topic routing。
- standard flow 通过 User Query Analysis Step 调用 Resolver；simple chat 通过 Simple Chat Defaults Step 跳过 Resolver。两个分支都一次 apply 完整 `UserQueryAnalysisResult`。

### Phase 3D: GatewayContextProvider 与 Global Bus

- 新增 `GatewayContextProvider`。
- 实现 `prepare_candidate_topics()`。
- 实现 `prepare_routed_topic()`。
- 在 Patchouli public API 新增无副作用 `TOPIC_GET_DATA(identity, topic_id) -> TopicData | None`，并实现 ownership/visibility 校验。
- 分别通过 Candidate Topics Preparation Step 和 Routed Topic Preparation Step 接入 workflow。
- 两个 Context Preparation Step 有独立 timeout/fallback，Provider adapter 用 `RecoverableGatewayError` 表达预期失败。
- Entry Interception command 命中时不调用 provider。

### Phase 3E: User Query Analysis Resolver 与旧引擎迁移

- 定义并冻结 `UserQueryAnalysisResolver` 的 Context/Result 契约。
- 先为意图识别与分解、记忆价值、query rewrite 和检索相关能力记录输入、输出、消费者、失败策略、延迟和依赖关系。
- 使用原型和契约测试验证依赖后，再决定复用旧单次 LLM analyzer，还是组合 `IntentClassifierEngine`、`IntentDecomposerEngine`、`MemoryValueJudgeEngine`、`QueryUnderstandingEngine`、`RetrievalStrategyEngine`。
- Resolver 内部组合形式不得反向改变顶层 Gateway Workflow 和 execution state schema。
- 新主路径不委托旧 `TheEye.gaze()` 或 `GatewayEngine.process()`；迁移期若复用旧 analyzer，只能放在 Resolver 实现内部并输出新的 `UserQueryAnalysisResult`。

### Phase 3F: Active Chat 迁移与请求控制

本阶段合并 active chat 主路径迁移与请求控制，目标是恢复 active chat 基本可用性并补齐 cancel/deadline 语义。这是 Gateway 核心迁移的最后一步，完成后 active chat 主路径恢复端到端可用。

- `ChatApplicationService.chat_stream()` 和 `chat()` 都先以 `ACTIVE_CHAT` 请求 `GatewayPublicRoutes.PROCESS`，并传递 chat cancel event 与 request timeout。
- `ChatApplicationService` 按 `GatewayProcessResult.kind` 分发 command/decision outcome。
- non-streaming `chat()` 返回 `NonStreamingChatCommandOutcome | NonStreamingChatAgentOutcome`，不再固定返回裸 `AgentRunResult`。
- `PatchouliService.prepare_agent_run()` 必传 `gateway_decision`。
- 删除 prepare 内部 gaze 和兼容参数。
- command 短路不触发 Patchouli/Alice。
- simple chat 仍作为普通 decision 进入 Patchouli/Alice，但 retrieval plan 为 SKIP。
- Gateway cancellation 映射为 chat cancelled 终态；overall deadline 只触发声明的 Step fallback，不产生部分 decision。
- 新增 Gateway workflow/step event。
- 建立新的 Gateway golden scenarios。
- 旧 Gateway/Patchouli/chat 兼容测试先断开，再按新结构重写。
- Gateway 与 User Query Analysis Resolver 的观测信息只发布到 `RuntimeEventSink`。

---

以下为后续阶段，在 Phase 3A–3F 核心迁移稳定后启动，可并行设计或延后实现。

### Phase 3G: Passive Conversation Memory Ingress 迁移

Passive ingress 的完整实现计划已拆分到 [`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。Gateway 侧的改动要点：

- 为 Gateway public process 增加必传 `GatewayIngressMode`，实现 `PASSIVE_MEMORY` 下 command 规则禁用与 decision-only invariant。
- `PASSIVE_MEMORY` 复用同一 Gateway workflow、state 和 `GatewayDecision`，不建立 Passive 专用类型或 Engine 组合。
- Passive ingress 的 event 发布、配置、测试和验收清单均在独立文档中定义。

## 14. 测试计划

- engine 原语单测。
- Step input selector、Engine/Provider/Resolver 调用和 updates projector 单测。
- `GatewayWorkflowStep` 通用执行契约测试，不为每个业务步骤建立 wrapper 类单测。
- `Identity/TopicSnapshot/TopicData` 及其嵌套集合在构建后不可修改测试。
- `TopicSnapshot.last_turn` 和 `TopicData` block/state 对象图递归只读，read helper 不返回可变内部集合测试。
- canonical topic models 不 import Patchouli/Engine，旧路径只重导出同一类型测试。
- `GatewayContextProvider` 直接消费规范只读类型、不创建 shadow snapshot/view 类型测试。
- `CandidateTopics` 不重复携带 identity 或 fallback/debug 元数据测试。
- `prepare_routed_topic()` 直接返回规范 `TopicData | None`、不创建 Gateway 包装类型测试。
- `GatewayStateSnapshot` 递归只读测试。
- `_apply_step_result()` 未知字段和完成后拒绝提交测试。
- selector/projector、未知字段和只读契约等 invariant failure 不得被 Step fallback 捕获测试。
- `UserQueryAnalysisResolver` Context/Result 契约测试；不同 Resolver 实现必须返回完整、递归只读的同构结果。
- User Query Analysis Step 只写 `user_query_analysis`、只 apply 一次结果，并在 overall timeout 时生成完整 fallback 测试。
- simple chat 不设置 `flow_end_reason`，仍执行两个 Context Preparation Step 和 Topic Routing Step 测试。
- Simple Chat Defaults Step 不调用 `UserQueryAnalysisResolver` 或任何分析 Engine，并只写一次完整 `UserQueryAnalysisResult` 测试。
- Simple Chat Defaults Step 产出 CHAT、raw message、空 keywords、SKIP memory signal 和 SKIP retrieval plan，且 `is_fallback=False` 测试。
- simple chat 与 standard analysis branch 互斥，任一请求只执行其中一个 Step 测试。
- Resolver 内部 Engine 顺序或实现替换不改变 `GatewayWorkflow` 测试。
- `finalize()` command/decision 判别、终态不变量和完成后拒绝提交测试。
- `finalize()` 直接投影 `UserQueryAnalysisResult.intent_type`，Resolver 私有 decomposition 不泄漏测试。
- `GatewayProcessResult/GatewayDecision` 递归不可变和序列化测试。
- `GatewaySystem` lifecycle 测试。
- `GatewayRuntime` route binding 测试。
- `GatewayService.process()` 测试：
  - `GatewayIngressMode` 必传并进入 state/snapshot，但不传给普通 Engine/Provider/Resolver。
  - command 命中不调用 provider。
  - `PASSIVE_MEMORY` 下 `/command` 不调用 registry/dispatcher、不产生 command outcome，并作为普通文本继续 workflow。
  - Topic Routing Step 前有 `CandidateTopics`。
  - User Query Analysis input 直接接收 Provider 返回的 `TopicData | None`。
  - simple chat 返回普通 `GatewayDecisionOutcome`，保留 Topic Routing 结果且不调用 Resolver。
  - command flow 返回 `GatewayCommandOutcome`。
  - 普通 flow 返回 `GatewayDecisionOutcome`，不返回 internal state。
- `GatewayContextProvider` 测试：
  - candidate topics route 响应转换。
  - routed topic route 响应转换。
  - `NEW_TOPIC` 返回空 context。
- Patchouli `TOPIC_GET_DATA` public route 测试：
  - identity 可见 topic 返回 canonical `TopicData`。
  - 不存在、已驱逐和不可见 topic 均返回 `None`。
  - 读取不更新 LRU、last-accessed 或 topic lifecycle。
  - route 不返回 `SemanticBuffer`、lazy entity 或无界历史 transcript。
- 两个 Context Preparation Step 的独立 timeout、`RecoverableGatewayError` 和 fallback 测试。
- recording event sink 接收 started、每步 completed、workflow completed/failed 和 analysis capability event 测试。
- event sink adapter 失败不改变 Gateway 业务结果测试。
- `PatchouliService.prepare_agent_run(gateway_decision=...)` 测试，并断言不 import/消费 Gateway internal state。
- active chat 新时序集成测试；simple chat 继续执行 Patchouli prepare、Alice run 和 Patchouli finalize，但不发起 retrieval。
- non-streaming chat command/agent 判别联合、与 streaming decision/prepare 行为一致测试。
- Gateway 请求控制测试：
  - chat cancel event 在 Gateway invoke 期间触发时取消调用、发布 cancelled event、不执行 fallback/finalize/Patchouli/Alice。
  - request deadline 将剩余 Step 转入本地 fallback，不再发起新外部 IO，并产出完整保守 decision。
  - 无 fallback 或无法满足终态不变量时抛出 `GatewayTimeoutError`，不返回部分 decision。
  - selector/projector/invariant failure 不被 cancel/deadline fallback 掩盖。
- 旧入口删除测试。

Passive ingress 的测试计划见 [`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。

## 15. 验收清单

1. `GatewaySystem` 实现 `SubsystemProtocol`。
2. `GatewayRuntime` 持有 local bus、route bindings、`RuntimeEventSink`、Engine 原语、GatewayContextProvider 和 `GatewayWorkflow` 装配。
3. `GatewayService.process()` 按 Entry Interception → Candidate Topics Preparation → Topic Routing → Routed Topic Preparation → analysis branch 执行普通 flow。
4. Entry Interception command 短路不触发 provider/Patchouli/Alice。
5. Entry Interception simple chat 不设置 flow end，仍完成 Context Preparation 和 Topic Routing。
6. simple chat 只旁路 User Query Analysis Resolver；Simple Chat Defaults Step 一次写入完整 CHAT/SKIP `UserQueryAnalysisResult`，且不标记为 fallback。
7. simple chat 返回普通 `GatewayDecisionOutcome`，下游仍执行 topic prepare、Alice run 和 Patchouli finalize，但不执行 retrieval。
8. Candidate Topics Preparation Step fallback 使用空 `CandidateTopics`。
9. Topic Routing fallback 只写 `topic_id="NEW_TOPIC"`。
10. Routed Topic Preparation Step 直接写 `TopicData | None`，fallback 使用 `None`。
11. standard User Query Analysis 只写一个完整、递归只读的 `UserQueryAnalysisResult`，整个 Step 只 apply 一次结果。
12. User Query Analysis fallback 同时提供 intent type、rewritten query、keywords、memory signal 和 retrieval plan，不传播部分 `None`。
13. IntentClassifier、IntentDecomposer、MemoryValueJudge、QueryUnderstanding 和 RetrievalStrategy 的组合形式不进入顶层 Workflow 契约。
14. `Identity/TopicSnapshot/TopicData` 由定义方和提供方保证递归只读，Gateway Provider 不创建 shadow type 或执行 defensive copy/freeze。
15. `CandidateTopics` 不重复保存 identity 或 fallback/debug 元数据；Gateway 不为 routed topic data 定义额外包装类型。
16. `GatewayExecutionState` 不跨 Gateway 边界；完成后拒绝任何 updates。
17. active chat 主路径不再调用 `TheEye.gaze()` / `PatchouliLocalRoutes.GATEWAY_GAZE`。
18. `ChatApplicationService` 只依赖 `GlobalSystemBus` 和协议模型。
19. `GatewayService.process()` 只返回判别明确、递归不可变的 `GatewayProcessResult`。
20. `PatchouliService.prepare_agent_run()` 必传并消费 `GatewayDecision`，且不依赖 `gateway.workflow`。
21. `GatewayDecision` 不包含内部 context、runtime event、fallback 或 downstream executable request。
22. `RuntimeEventSink` 是唯一可观测性来源，event 不进入 execution state 或业务结果。
23. Phase 3 不输出 `list[GatewayExecutionState]` 或多个 decision。
24. Gateway 不存在逐业务步骤的 wrapper 类或一对一 Operation 对象；固定拓扑只由通用 `GatewayWorkflowStep` 装配表达。
25. `GatewayIngressMode` 是必传固定策略；`ACTIVE_CHAT` 与 `PASSIVE_MEMORY` 复用同一 Gateway workflow 和公共 decision。
26. Patchouli 暴露无副作用 `TOPIC_GET_DATA(identity, topic_id) -> TopicData | None`；不存在、已驱逐和不可见不产生可区分响应。
27. `Identity/TopicSnapshot/TopicData` 及全部公共嵌套类型由 core domain 规范定义并递归只读，Patchouli/Perception 不维护平行模型。
28. streaming 与 non-streaming active chat 共享同一 Gateway/prepare/run/finalize 语义；non-streaming 使用 command/agent 判别联合。
29. command 型 non-streaming chat 不触发 Patchouli/Alice；decision 型返回 agent outcome，simple chat 仍运行 Alice 且跳过 retrieval。
30. Gateway cancel 不进入 fallback 或业务结果，ChatApplicationService 将其映射为 cancelled chat 终态。
31. Gateway request deadline 不再启动超时后的外部 IO，只使用已声明的本地 fallback 补齐完整 decision；不能补齐时明确失败。

Passive ingress 的验收清单见 [`V0.6.0PassiveIngressDesign.md`](./V0.6.0PassiveIngressDesign.md)。
