# v0.6.0 新 Gateway 系统设计

**文档状态**: Draft  
**适用范围**: `gateway/`、`engines/gateway/`、`system/`、`patchouli/`、`alice/`、`core/protocol/`  
**前置版本**: v0.5.x 基础设施完成；全局指令库可并行推进  
**核心目标**: 将 Gateway 从 Patchouli 私有能力重构为顶层独立子系统，并用固定多阶段 workflow 取代旧的一步 LLM router。

---

## 1. 背景

旧 Gateway 的主要问题不是能否工作，而是归属和职责混在一起：

- `GatewayEngine` 虽然位于 `engines/gateway/`，但装配由 `PatchouliSystem` 完成。
- `TheEye` 位于 `patchouli/eye.py`，实际却承担系统入口分析职责。
- active chat 通过 `PatchouliService.prepare_agent_run()` 内部请求 `PatchouliLocalRoutes.GATEWAY_GAZE`，导致 Gateway 被 Patchouli prepare 时序反向托管。
- 旧 LLM router 在一次输出里同时完成话题路由、指代消解、关键词提取、记忆价值判断等任务，容易出现“博而不精”的决策退化。

v0.6.0 的新设计将 Gateway 定义为独立决策子系统。Patchouli 和 Alice 是执行/记忆/调度系统，Gateway 是入口决策系统。

---

## 2. 目标与非目标

### 2.1 目标

1. `GatewaySystem` 实现 `SubsystemProtocol`，与 Patchouli、Alice 平级。
2. 建立标准分层：`GatewaySystem` / `GatewayRuntime` / `GatewayService`。
3. Gateway 内部使用 local bus；跨子系统通信通过 global bus public route。
4. `ChatApplicationService` 禁止持有子系统实例，只通过 `GlobalSystemBus` 调用 Gateway/Patchouli/Alice。
5. active chat 主路径改为先进入 Gateway；Gateway workflow 终止后产出只读 `GatewayProcessResult`，下游只消费其中的公共决策，不接触内部执行状态。
6. 删除 active chat 主路径中的 `GatewayFacade`、`GatewayBundle`、`TheEye.gaze()`、`EyeGazeResult` 兼容投影和旧 `PatchouliLocalRoutes.GATEWAY_GAZE` 依赖。
7. 将旧一步 LLM router 拆为固定 workflow：话题路由、意图分类、记忆价值预判、查询理解、检索策略预判。
8. 复合意图只做占位和样本收集，真实分解机制见独立文档。

### 2.2 非目标

- 不实现完整 Alice Phase 3 顶层任务图编排。
- 不实现 Runtime Job Queue。
- 不实现附件上传、文档解析、Document Ingestion 或 Deep Research。
- 不实现 MTP RUN executable asset、沙箱执行或真取消。
- 不保持旧 Gateway 行为等价；Phase 3 接受行为变化。
- 不提供 `pipeline.enabled=false` 回退旧 Gateway。

### 3.2 依赖方向

允许：

```text
gateway -> engines.gateway
gateway -> core models/protocol
gateway -> system contracts/routes
gateway.runtime -> GlobalSystemBus
system assembler -> gateway / patchouli / alice
patchouli -> core protocol models
```

禁止：

```text
engines.gateway -> gateway
engines.gateway -> system
engines.gateway -> patchouli
gateway -> patchouli concrete service
ChatApplicationService -> GatewaySystem/PatchouliSystem/AliceSystem concrete
PatchouliSystem -> gateway concrete composition root
PatchouliSystem -> gateway.pipeline / GatewayExecutionState
ChatApplicationService -> gateway.pipeline / GatewayExecutionState
```

Gateway 可以通过 `GlobalSystemBus` 请求 Patchouli public route，但不能 import Patchouli service 或 short-term store concrete。

`core.protocol.gateway` 是 Gateway 跨子系统输出的依赖中立契约层，不得 import `gateway`、`engines.gateway`、Patchouli 或 Alice。Gateway 在 `finalize()` 时负责把内部 engine/state 类型转换为公共协议类型。除 Gateway 自身外，任何模块都不得 import `gateway.pipeline`。

## 4. GatewayContextProvider

Gateway 的上下文获取是两阶段、渐进式的，不能合并成 workflow 前的一次性获取。

### 4.1 数据对象

```python
class CandidateTopics(BaseModel):
    model_config = ConfigDict(frozen=True)

    identity: Identity
    topic_snapshots: tuple[TopicSnapshot, ...] = ()
    active_topics_menu: str = ""
    is_fallback: bool = False
    fallback_reason: str | None = None


class RoutedTopicContext(BaseModel):
    model_config = ConfigDict(frozen=True)

    identity: Identity
    topic_id: str
    topic_data: TopicData | None = None
    is_empty: bool = False
    is_fallback: bool = False
    fallback_reason: str | None = None
```

`Identity`、`TopicSnapshot` 和 `TopicData` 本身就是跨模块使用的只读领域模型，不再为 Gateway 创建 `IdentitySnapshot`、`TopicSnapshotView` 或 `TopicDataView` 等平行类型。它们的定义方和提供方必须保证对象及全部嵌套字段在构建完成后递归只读：集合使用 tuple 或等价不可变结构，嵌套模型同样 frozen，不能只冻结最外层模型。

如果某个模型当前位于具体子系统包中而跨子系统契约需要直接引用，应把该模型的规范定义迁移到 `core models/protocol` 等依赖中立位置，而不是由 Gateway Provider 创建镜像 DTO。具体子系统可以重导出该规范类型以保持迁移期兼容。

### 4.2 Provider 接口

```python
class GatewayContextProvider(Protocol):
    async def prepare_candidate_topics(
        self,
        *,
        identity: Identity,
    ) -> CandidateTopics: ...

    async def prepare_routed_topic(
        self,
        *,
        identity: Identity,
        topic_id: str,
    ) -> RoutedTopicContext: ...
```

设计决策：

- `prepare_candidate_topics()` 在 S1 TopicRouter 前执行。
- `prepare_routed_topic()` 在 S1 TopicRouter 提交 `topic_id` 后、S2 IntentClassifier 前执行。
- 两个方法不是 workflow Stage，不承担 engine 决策。
- 两个方法通过 `GlobalSystemBus` 请求 Patchouli public route。
- `topic_id="NEW_TOPIC"` 时 `prepare_routed_topic()` 返回空 `RoutedTopicContext`，不请求完整上下文。
- 两个方法分别有 timeout/fallback；失败后继续 workflow。
- S0 command 命中时不得调用任何 provider 方法。
- `GatewayContextProvider` 只负责编排 public route、timeout/fallback 和 Gateway 所需的派生展示文本。
- Patchouli public route 返回的 `TopicSnapshot/TopicData` 必须在提供方边界内已经满足只读契约；若返回可变对象，属于提供方违反协议，不由 Gateway 防御性找补。

## 5. 执行状态、只读快照与公共结果

Gateway workflow 内部状态与跨子系统输出是两类不同对象：

- `GatewayExecutionState` 是 GatewayRuntime 私有、执行期可变的工作状态。
- `GatewayStateSnapshot` 是 Stage 读取的递归只读快照。
- `GatewayProcessResult` 是 `GatewayService.process()` 返回的公共终态结果。
- `GatewayDecision` 是普通决策流程面向下游的依赖中立业务输出。

`GatewayExecutionState` 不得进入 `GlobalSystemBus`，也不得被 Patchouli、Alice、`ChatApplicationService` 或 API 层持有。workflow 结束时由 Runner 调用 `finalize()` 构造公共结果；这是一条序列化和依赖边界，而不是内部 state 的只读镜像。

### 5.1 统一写入

Stage 不直接修改 `GatewayExecutionState` 字段。所有字段写入通过 `StageResult/GatewayPatch` 提交：

```python
@dataclass(frozen=True)
class GatewayPatch:
    updates: Mapping[str, Any] = field(default_factory=dict)


@dataclass(frozen=True)
class StageResult:
    patch: GatewayPatch = field(default_factory=GatewayPatch.empty)
    flow_end_reason: str | None = None
    is_fallback: bool = False
    fallback_reason: str | None = None
    metadata: Mapping[str, Any] = field(default_factory=dict)
```

`GatewayExecutionState.apply_stage_result()` 是唯一 Stage 字段提交入口，且只由 Runner/Service 调用，负责：

- 校验字段所有权。
- 校验提交所基于的 state revision。
- 写入 patch。
- 设置 flow end。
- 追加 `stage_trace`。
- 拒绝 Stage 手动写 `stage_trace`。
- 增加 state revision。
- state 完成后拒绝任何新提交。

Stage 的输入类型是 `GatewayStateSnapshot`，而不是 `GatewayExecutionState`。Stage 只能读取快照并返回 `StageResult`，不能获得内部 state 的可变引用。

### 5.2 GatewayExecutionState 草案

```python
@dataclass
class GatewayExecutionState:
    raw_message: str
    identity: Identity

    # S0 在 provider 之前执行，因此初始化时允许为空
    candidate_topics: CandidateTopics | None = None

    # S0
    l1_result: InterceptorResult | None = None
    command_parse_result: CommandParseResult | None = None
    command_execution_result: CommandExecutionResult | None = None
    flow_end_reason: str | None = None

    # S1 TopicRouter
    topic_id: str | None = None
    new_topic_title: str | None = None
    new_topic_summary: str | None = None

    # Provider after S1
    routed_topic_context: RoutedTopicContext | None = None

    # S2 IntentClassifier
    intent_type: IntentType | None = None
    is_composite: bool = False

    # S3 CompositePlaceholder
    composite_deferred: bool = False
    composite_deferred_reason: str | None = None

    # S4a MemoryValueJudge
    memory_write_signal: MemoryWriteSignal | None = None

    # S4b QueryUnderstanding
    rewritten_query: str | None = None
    search_keywords: tuple[str, ...] = ()

    # S5 RetrievalStrategyPicker
    retrieval_strategy: RetrievalStrategy | None = None

    # S6 PlannerRouter
    execution_plan: ExecutionPlan | None = None

    stage_trace: list[StageTrace] = field(default_factory=list)
    revision: int = 0
    status: ExecutionStateStatus = ExecutionStateStatus.RUNNING
```

约束：

- state 的顶层字段可以在 Runner 提交 patch 时被替换，但 Stage 不持有 state 本身。
- 写入 state 的值必须由其生产方按只读契约构建完成；Provider、engine 和 Stage 都不得把可变 list/dict 或可变嵌套模型放入 patch/state。
- Runner 负责校验 patch 的字段所有权、revision 和声明类型，不负责复制、包装或冻结生产方返回值；违反只读类型契约属于生产方实现错误。
- `candidate_topics=None` 只允许出现在 S0 尚未完成或 command 已短路的状态；进入 S1 前必须提交 `CandidateTopics`。
- `status=COMPLETED` 表示 workflow 生命周期结束，不等价于 Python 对象已经递归冻结；外部不可变性由公共结果契约保证。

### 5.3 GatewayStateSnapshot

```python
@dataclass(frozen=True)
class GatewayStateSnapshot:
    revision: int
    raw_message: str
    identity: Identity
    candidate_topics: CandidateTopics | None
    routed_topic_context: RoutedTopicContext | None
    topic_id: str | None
    intent_type: IntentType | None
    is_composite: bool
    rewritten_query: str | None
    search_keywords: tuple[str, ...]
    memory_write_signal: MemoryWriteSignal | None
    retrieval_strategy: RetrievalStrategy | None
```

快照不要求机械复制 state 的全部字段；Runner 可以按 Stage 声明的读取字段生成浅层投影，并直接复用已经只读的领域对象引用。它必须满足：

- snapshot 外壳 frozen，且所有引用值在进入 state 前已经由其生产方保证递归只读。
- snapshot 构建不执行 defensive deep copy，也不创建 `IdentitySnapshot/TopicSnapshotView/TopicDataView`。
- list 使用 tuple，映射使用只读值对象，嵌套 Pydantic/dataclass 同样 frozen；仅冻结最外层但内部仍包含 list/dict，不符合上游模型契约。
- 同一并发 wave 的 Stage 必须读取同一 revision 的快照。
- Runner 提交并发结果时使用 `commit_batch(expected_revision=...)`；先校验全部 patch，再按确定顺序一次性提交，并把整个 batch 视为一次原子 revision 迁移。

### 5.4 公共终态契约

公共协议位于依赖中立的 `core.protocol.gateway`。其中的枚举和值对象不得复用可变 engine model；Gateway 在 finalize 边界显式转换。

```python
@dataclass(frozen=True)
class GatewayDecision:
    target_topic_id: str
    new_topic_title: str | None
    new_topic_summary: str | None
    rewritten_query: str
    search_keywords: tuple[str, ...]
    memory_write_signal: MemoryWriteSignal
    retrieval_plan: RetrievalPlan
    intent_type: IntentType
    execution_plan: ExecutionPlan | None = None


@dataclass(frozen=True)
class GatewayCommandOutcome:
    kind: Literal["command"] = "command"
    command_execution_result: CommandExecutionResult


@dataclass(frozen=True)
class GatewayDecisionOutcome:
    kind: Literal["decision"] = "decision"
    decision: GatewayDecision


GatewayProcessResult = GatewayCommandOutcome | GatewayDecisionOutcome
```

公共契约规则：

- `GatewayProcessResult` 使用 `kind` 判别，不使用 command/decision 多个 nullable 字段表达终态。
- `CommandExecutionResult` 也必须定义为依赖中立、递归不可变的公共 command protocol；`core.protocol.gateway` 不得为复用该类型而反向 import `gateway.commands`。
- `GatewayDecision` 只包含稳定业务决策，不包含 candidate topics、routed context、StageResult、StageTrace、fallback 细节、原始 LLM 输出或 Gateway stage 名称。
- `RetrievalPlan` 表达 Gateway 的检索决策，不直接包含 Patchouli 执行用的 `RetrievalRequest`；Patchouli 在自身边界内根据 decision、identity 和调用参数构造请求。
- `memory_write_signal` 是唯一记忆价值信号；Patchouli 需要 `worth_saving` 时在适配层按 `WRITE -> True`、`SKIP -> False`、`UNKNOWN -> None` 派生。
- 所有嵌套公共类型必须递归不可变并可稳定序列化。
- Phase 3 的直接消费方是 Patchouli；Alice 继续消费 `AgentRunContext`。只有出现明确的 Alice 直连需求时，才从 `GatewayDecision` 派生 Alice 专用视图。

### 5.5 Finalize

`GatewayExecutionState.finalize()` 由 Runner 调用，且是内部 state 转为公共结果的唯一出口，负责：

- 校验 command outcome 与 decision outcome 的互斥关系。
- 校验当前 flow 所需字段是否完整。
- command flow 构造 `GatewayCommandOutcome`。
- 普通 flow 构造 `GatewayDecisionOutcome`。
- 把内部 engine model 显式转换为公共 frozen value object。
- 把 state 标记为 `COMPLETED`，拒绝后续 patch。
- 单独发布 trace/runtime event；trace 不进入 `GatewayProcessResult`。

普通 decision 的派生规则：

- `effective_rewritten_query()` 返回 `rewritten_query or raw_message`。
- `effective_search_keywords()` 返回 tuple。
- simple chat short-circuit 派生 `MemoryWriteSignal.SKIP` 和 `RetrievalPlan(mode=SKIP)`。
- `retrieval_strategy.mode == SKIP` 时生成 `RetrievalPlan(mode=SKIP)`；是否执行检索还要由 Patchouli 与 `enable_memory_retrieval` 共同决定。
- finalize 缺少普通 flow 必需字段属于 Gateway 实现错误，不使用隐式 `None` 继续跨子系统传播。

## 6. Pipeline

### 6.1 总体结构

```text
GatewayService.process(message, identity)
  │
  S0 EntryInterceptor
  │ command/simple chat 命中则短路
  ↓
  GatewayContextProvider.prepare_candidate_topics(identity)
  ↓
  S1 TopicRouter
  ↓
  GatewayContextProvider.prepare_routed_topic(identity, topic_id)
  ↓
  S2 IntentClassifier
  ↓
  S3 CompositePlaceholder
  ↓
  S4a MemoryValueJudge ┐
                       ├─ asyncio.gather
  S4b QueryUnderstanding ┘
  ↓
  S5 RetrievalStrategyPicker
  ↓
  S6 PlannerRouter noop
  ↓
  GatewayExecutionState.finalize()
  ↓
  GatewayProcessResult
```

### 6.2 S0 EntryInterceptor

- 输入：`raw_message`。
- 处理：复用 `RuleInterceptor` / `CommandRegistry`，统一处理系统指令与简单闲聊。
- command 输出：`l1_result`、`command_parse_result`、`flow_end_reason="system_command"`。
- simple chat 输出：`l1_result`、`intent_type=CHAT`、`flow_end_reason="simple_chat"`。
- 约束：不写 `rewritten_query/search_keywords/memory_write_signal/retrieval_strategy`。

### 6.3 S1 TopicRouter

- 输入：`raw_message` + `candidate_topics.topic_snapshots`。
- 处理：只判断路由到已有 topic 还是 `NEW_TOPIC`。
- 输出：`topic_id`、`new_topic_title`、`new_topic_summary`、routing reason(trace/debug)。
- 禁止输出：`rewritten_query`、`search_keywords`、`retrieval_strategy`、`memory_write_signal`。
- fallback：`topic_id="NEW_TOPIC"`。

该 Stage 只承接旧 LLMAnalyzer 中的话题选择能力。query rewrite、keywords 和检索策略不属于 TopicRouter。

### 6.4 Provider Step: RoutedTopicContext

- 位置：S1 之后，S2 之前。
- 输入：`identity` + `topic_id`。
- 输出：`routed_topic_context`。
- fallback：空 `RoutedTopicContext`。
- 约束：不是 workflow Stage，不参与 engine 决策，不由 TopicRouter 发起总线请求。

### 6.5 S2 IntentClassifier

- 输入：`raw_message` + `topic_id` + `candidate_topics` + `routed_topic_context`。
- 处理：只判断 `intent_type` 和 `is_composite`。
- 输出：`intent_type`、`is_composite`。
- fallback：`intent_type=QUERY`、`is_composite=False`。
- 约束：不做话题路由、不做查询改写、不判断检索策略。

### 6.6 S3 CompositePlaceholder

- Phase 3 始终执行，但不调用 LLM。
- `is_composite=False` 时透明通过。
- `is_composite=True` 时写入 `composite_deferred=True` 和原因，继续按单主意图处理。
- 不生成 `SubIntent`，不输出 `list[GatewayExecutionState]` 或多个 decision。

### 6.7 S4a MemoryValueJudge

- 与 S4b 并发。
- 输入：`intent_type` + `topic_id` + `routed_topic_context` + `raw_message`。
- 输出：`memory_write_signal`。
- fallback：`MemoryWriteSignal.UNKNOWN`。
- 不执行实际写入。

### 6.8 S4b QueryUnderstanding

- 与 S4a 并发。
- 输入：`intent_type` + `topic_id` + `routed_topic_context` + `raw_message`。
- 处理：基于完整话题上下文进行指代消解和检索锚点提取。
- 输出：`rewritten_query`、`search_keywords`。
- fallback：`rewritten_query=raw_message`、`search_keywords=[]`。
- 这是 `rewritten_query/search_keywords` 的唯一写入者。

### 6.9 S5 RetrievalStrategyPicker

- 输入：`intent_type` + `topic_id` + `rewritten_query` + `search_keywords` + `routed_topic_context`。
- 输出：`retrieval_strategy`。
- fallback：`RetrievalStrategy(mode=HYBRID, top_k=5)`。
- 不执行检索。

### 6.10 S6 PlannerRouter

- Phase 3 noop。
- 预留 `execution_plan`，供未来 Alice / Job Queue / planning 使用。

## 7. Engine 原语

`engines/gateway` 只放纯决策原语，不依赖 SystemBus/Patchouli/Alice/runtime state。

| Engine | 职责 |
| --- | --- |
| `TopicRouterEngine` | 只产出 topic routing |
| `QueryUnderstandingEngine` | 产出 `rewritten_query/search_keywords` |
| `IntentClassifierEngine` | 产出 `intent_type/is_composite` |
| `MemoryValueJudgeEngine` | 产出 `memory_write_signal` |
| `RetrievalStrategyEngine` | 产出 `retrieval_strategy` |
| `IntentDecomposerEngine` | Phase 4 复合意图分解 |

不新增 engine 专用 prompt/parser 子包：

- prompt 文本继续由 i18n 模板统一管理。
- JSON parsing / schema 解析复用项目已有通用工具函数。

## 8. 并发与 Fallback

S4a 和 S4b 并发执行：

```python
snapshot = state.snapshot()
results = await asyncio.gather(
    s4a_memory.process(snapshot),
    s4b_query.process(snapshot),
    return_exceptions=True,
)

state.commit_batch(
    expected_revision=snapshot.revision,
    results=normalize_with_fallbacks(results),
)
```

提交规则：

- 并发 Stage 只读同一 revision 的 `GatewayStateSnapshot`。
- S4a 只能写 `memory_write_signal`。
- S4b 只能写 `rewritten_query/search_keywords`。
- Runner 先校验整个 batch 的字段所有权与冲突，再按固定顺序提交 patch 和 trace。
- 并发完成顺序不得影响 state、trace 或最终 decision。
- S5 必须在 S4b 提交后执行。

Fallback 表：

| 位置 | 触发条件 | 默认值 |
| --- | --- | --- |
| Provider `prepare_candidate_topics` | topic list 超时/失败 | 空 topic snapshots |
| S1 TopicRouter | LLM/解析失败 | `topic_id="NEW_TOPIC"` |
| Provider `prepare_routed_topic` | topic context 超时/失败 | 空 `RoutedTopicContext` |
| S2 IntentClassifier | LLM/解析失败 | `intent_type=QUERY, is_composite=False` |
| S3 CompositePlaceholder | 无 LLM | 仅复合时 `composite_deferred=True` |
| S4a MemoryValueJudge | 调用失败 | `memory_write_signal=UNKNOWN` |
| S4b QueryUnderstanding | 调用失败/上下文缺失 | raw message + 空 keywords |
| S5 RetrievalStrategyPicker | 调用失败 | HYBRID + top_k=5 |

原则：Phase 3 没有任何 Stage 的失败应中止整个 Pipeline。

## 9. Active Chat 新时序

在新 Gateway 系统落地后，原有的 active chat 调用链需要做出时序的改动。

目标调用链：

```text
ChatApplicationService.chat_stream()
  -> identity = Identity(user_id, agent_id, session_id)
  -> gateway_result = GlobalSystemBus.request(
         GatewayPublicRoutes.PROCESS,
         message=user_message,
         identity=identity,
     )
     ├─ S0 command/simple chat 可短路
     └─ 未短路时由 GatewayService 完成 Gateway workflow
  -> if gateway_result.kind == "command":
       emit command_result(gateway_result.command_execution_result)
       emit done
       stop
  -> gateway_decision = gateway_result.decision
  -> prepared = GlobalSystemBus.request(
         GlobalRoutes.PATCHOULI_PREPARE_AGENT_RUN,
         user_message=user_message,
         user_id=user_id,
         agent_id=agent_id,
         session_id=session_id,
         gateway_decision=gateway_decision,
         enable_memory_retrieval=enable_memory_retrieval,
         generation_options=generation_options,
     )
  -> Alice run
  -> PatchouliService.finalize_agent_run(...)
```

`PatchouliService.prepare_agent_run()` 原地改造：

```python
async def prepare_agent_run(
    self,
    user_message: str,
    user_id: str,
    *,
    gateway_decision: GatewayDecision,
    agent_id: str = "omni_doll",
    session_id: str | None = None,
    enable_memory_retrieval: bool = True,
    generation_options: dict[str, Any] | None = None,
) -> PreparedAgentRun:
    ...
```

约束：

- `gateway_decision` 必传；未传入或收到 command outcome 是调用方错误。
- Patchouli 只 import `core.protocol.gateway.GatewayDecision`，不得 import `gateway.pipeline`。
- `GatewayExecutionState`、snapshot 和 trace 不得进入 Patchouli prepare。
- `prepare_agent_run()` 不再获取 active topic snapshots 供 Gateway 使用。
- `prepare_agent_run()` 不再调用 gaze。
- `prepare_agent_run()` 根据 `GatewayDecision` 构造 Patchouli 自身的 `RetrievalRequest` 和记忆写入派生值，并继续负责 topic prepare、pool topics、topic context、retrieval、memory context、`AgentRunContext` 和 `StreamPrelude`。

## 11. 可观测性

- `stage_trace` 记录每个 Stage 的 `stage_name`、`duration_ms`、`is_fallback`、`fallback_reason`、`flow_ended`。
- provider fallback 也应记录 trace/event，虽然 provider 不是业务 Stage。
- `GatewayPipelineCompleted` 或等价 runtime event 携带 stage trace 摘要、state revision 和关键决策字段。
- `debug_trace=true` 时记录完整输入快照，仅供本地调试，不默认发往前端。
- `GatewayExecutionState.to_debug_summary()` 示例：`S0:pass ctx:candidates S1:T_01 ctx:routed S2:QUERY S4a:WRITE S4b:rewrite S5:HYBRID`。
- trace/debug snapshot 属于 observability 通道，不得附加到 `GatewayProcessResult/GatewayDecision`。

## 12. 实现计划

### Phase 3A: Gateway 子系统骨架

- 新增 `src/hivememory/gateway/` 顶层包。
- 实现 `GatewaySystem`、`GatewayRuntime`、`GatewayService`。
- 新增 local/public routes、runtime bus、route bindings。
- 系统装配根构造 `GatewaySystem`，不再构造 `GatewayFacade/GatewayBundle`。

验收：

- `GatewaySystem` 满足 `SubsystemProtocol`。
- local route mount/unmount 幂等。
- `GatewayService.process()` 可跑最小空 pipeline。

### Phase 3B: Engine 原语、执行 State 与公共结果契约

- 整理 `engines/gateway` 原语。
- 收敛 `Identity`、`TopicSnapshot`、`TopicData` 及其嵌套类型的递归只读不变量；规范类型位于依赖中立层，由提供方直接构造。
- 定义 Gateway 私有的 `GatewayExecutionState`、`GatewayStateSnapshot`、`StageTrace`、`CandidateTopics`、`RoutedTopicContext`、`GatewayPatch`、`StageResult`。
- 在依赖中立的 core protocol 中定义 `GatewayDecision`、`GatewayCommandOutcome`、`GatewayDecisionOutcome`、`GatewayProcessResult`。
- 定义 retrieval/memory 派生规则。
- 不依赖 `EyeGazeResult`。

### Phase 3C: Pipeline Runner 与 Stage 骨架

- 实现 runner、short-circuit、revision、snapshot、batch commit、finalize、trace。
- 新增 S0-S6 Stage。
- S1 只做 topic routing。
- S4a/S4b 并发。
- S5 在 query understanding 后执行。
- S3 只做 composite placeholder。

### Phase 3D: GatewayContextProvider 与 Global Bus

- 新增 `GatewayContextProvider`。
- 实现 `prepare_candidate_topics()`。
- 实现 `prepare_routed_topic()`。
- 两个 provider 方法有独立 timeout/fallback。
- S0 command 命中时不调用 provider。

### Phase 3E: Active Chat 迁移

- `ChatApplicationService` 先请求 `GatewayPublicRoutes.PROCESS`。
- `ChatApplicationService` 按 `GatewayProcessResult.kind` 分发 command/decision outcome。
- `PatchouliService.prepare_agent_run()` 必传 `gateway_decision`。
- 删除 prepare 内部 gaze 和兼容参数。
- command 短路不触发 Patchouli/Alice。

### Phase 3F: 旧引擎迁移

- `TopicRouterEngine` 只承接话题路由。
- `QueryUnderstandingEngine` 承接 query rewrite/keywords。
- `IntentClassifierEngine` 只做 intent/composite。
- `MemoryValueJudgeEngine` 只产出 signal。
- `RetrievalStrategyEngine` 只产出 strategy。
- 新主路径不委托旧 `TheEye.gaze()` 或 `GatewayEngine.process()`。

### Phase 3G: Observability 与测试重写

- 新增 Gateway pipeline event。
- 建立新的 Gateway golden scenarios。
- 旧 Gateway/Patchouli/chat 兼容测试先断开，再按新结构重写。
- 收集 `composite_deferred=True` 样本，供 Phase 4 使用。

## 14. 验收清单

1. `GatewaySystem` 实现 `SubsystemProtocol`。
2. `GatewayRuntime` 持有 local bus、route bindings、engine 原语、GatewayContextProvider、pipeline 和 stage 装配。
3. `GatewayService.process()` 按 S0→Provider→S1→Provider→S2→S3→S4→S5→S6 执行。
4. S0 command 短路不触发 provider/Patchouli/Alice。
5. `prepare_candidate_topics()` fallback 使用空 snapshots。
6. S1 fallback 只写 `topic_id="NEW_TOPIC"`。
7. `prepare_routed_topic()` fallback 使用空 `RoutedTopicContext`。
8. S2 fallback 写 `intent_type=QUERY, is_composite=False`。
9. S3 只写 composite deferred，不分解。
10. S4a/S4b 读取同一 revision 的递归只读 snapshot，字段所有权明确，batch 提交结果与协程完成顺序无关。
11. S4b 是 `rewritten_query/search_keywords` 唯一写入者。
12. S5 是 `retrieval_strategy` 唯一写入者。
13. `Identity/TopicSnapshot/TopicData` 由定义方和提供方保证递归只读，Gateway Provider 不创建 shadow type 或执行 defensive copy/freeze。
14. `GatewayExecutionState` 不跨 Gateway 边界；完成后拒绝任何 patch。
15. active chat 主路径不再调用 `TheEye.gaze()` / `PatchouliLocalRoutes.GATEWAY_GAZE`。
16. `ChatApplicationService` 只依赖 `GlobalSystemBus` 和协议模型。
17. `GatewayService.process()` 只返回判别明确、递归不可变的 `GatewayProcessResult`。
18. `PatchouliService.prepare_agent_run()` 必传并消费 `GatewayDecision`，且不依赖 `gateway.pipeline`。
19. `GatewayDecision` 不包含内部 context、trace、fallback 或 downstream executable request。
20. `debug_trace=true` 时 trace 足以定位每个 Stage 决策，但 trace 不进入业务结果。
21. Phase 3 不输出 `list[GatewayExecutionState]` 或多个 decision。
