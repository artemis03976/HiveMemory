# 生成查重的决策信号

## 问题

Mode A/B 生成的草稿按入库的嵌入文本形态编译为查询（2026-11-01 起；此前只拼接 `title summary`），对中期库做 dense top-1 检索，再按原始余弦与固定阈值判断：大于 0.95 时按内容是否一致判为 IDENTICAL 或 SIMILAR，0.75～0.95 判为 SIMILAR，其余判为 DISTINCT（[Patchouli 生成](../patchouli/generation.md#4-查重与合并)第 4 节）。2026-10-31 之前，SIMILAR 的两个区间判为 UPDATE，用草稿整体覆盖已有记忆；之后改为先新建、再由合并任务把两条记忆融合为一条。

Claude Code 接入后的真实使用中，登记时（2026-10-29）查重从未做出 CREATE 以外的决策，其中包括 owner 有意制造的一次同一工作的跨话题拆分。离线复现表明，用当前的嵌入模型做"记忆对记忆"的比较时，dense 余弦区分不了"同一件事"与"同一项目里的其他事"，固定阈值也够不到。同一项目的记忆增多后，UPDATE 开始发生，并按现行规则整体覆盖了已有记忆（2026-10-30 补充的证据）。

## 证据（2026-10-29）

真实使用：2026-10-27 至 10-28，Claude Code 共导入 31 轮，形成 5 个话题，生成 5 条记忆，查重全部判为 CREATE，Top-1 相似度在 0.493～0.653 之间。

离线复现：使用与服务端相同的嵌入配置（`Xenova/bge-m3` 的 `onnx/model_int8.onnx`，CLS 池化并归一化），对查重当时的中期库重算。当时的库包含现存 30 条和已归档 10 条，其中多数是早期测试数据。5 次查重的 Top-1 与日志一致，分数相差不超过 0.012。

- **噪声底**：40 条记忆按入库文本两两比较，余弦的 p50 为 0.451、p90 为 0.542、p99 为 0.655。日志中的 0.493 与 0.567 就是"库里没有相关记忆"时的 Top-1。
- **有意拆分的一组**：同一项工作（话题折叠移出交互应用）的前后两段相隔超过空闲时限，分别生成「话题折叠耗时不计入交互提交时限的设计决定」与「HiveMemory 感知层折叠与 journal 重构」。
  - 后者查重时前者已经在库中，但相关对只得 0.572，排第 2；Top-1 是不相关的「HiveMemory 推理模型常驻内存分析与空闲卸载方案」（0.653）。
  - 相关对的得分落在无关对的 p90 与 p99 之间。
  - 查询也套用入库模板（0.605）或两边都去掉模板（0.560），排名都不变。
- **自相似够不到 TOUCH**：查询文本 `title summary` 与入库文本 `Title/Type/Tags/Summary` 模板形态不同，同一条记忆拿自己来比只有 0.925～0.953，内容完全相同也难以超过 0.95。
- **交叉编码器**：已常驻的 bge-reranker-base 对同一组候选给出的分数（sigmoid）为：相关对 0.850，其余最高 0.485，其余中位数 0.002。但在 5 个问题式短查询上，它只把 3 个目标排在第 1，「InteractionApplyJournal 为什么删掉了」排到第 5。记忆对的样本只有一组，只能说明方向。
- **对照**：同样 5 个问题式短查询，dense 检索在这 30 条记忆中都把目标排在第 1（0.556～0.744）。问题集中在记忆对记忆的比较，不是检索整体失效；但库很小，结论不能外推到同项目记忆增多之后。
- **未测**：int8 与 fp32 嵌入模型的差异。

## 补充证据（2026-10-30）

插件接入（10-27）以来共 19 次查重决策：15 次 CREATE、4 次 UPDATE、没有 TOUCH。4 次 UPDATE 都发生在 10-29 晚至 10-30，相似度 0.81～0.85，构成两条链，每条被连续覆盖两次，当前版本丢掉了最初记忆的主要内容：

- 「v0.7.1 记忆访问设计决定：P-1c/P-9c/E-2/E-3b/E-7 与 harness principal 复核」两次被后续实现阶段的草稿覆盖，当前正文只剩阶段二的返工；
- 「v0.7.1 版本剩余工作梳理与收尾建议」两次被收尾阶段的草稿覆盖，当前正文是提交与开 PR 的记录。

两条链都出自同一会话中先后进行的几段工作，被空闲结算拆成不同话题。被覆盖的版本保留在 MemoryVersionArtifact 中，检索与读取只看到最新版本。逐条对照见已归档的[多条提取与查重 Idea](../archive/ideas/settlement-multi-memory-extraction-and-dedup.md#22-查重分不开相关记忆命中后整体覆盖)第 2.2 节。

## 补充证据（2026-11-01）

一个话题提取多条记忆的计划决定前，用 10 个真实结算原文离线回放提取（都是 Claude Code 开发 HiveMemory 的会话），一次调用输出草稿列表的做法共得到 73 条草稿。把它们两两比较，模拟全部入库之后再查重：

- 73 条中有 18 条（25%）在其他话题中有高于 0.75 的近邻。其中 17 对是同一件事或同一工作的不同阶段，1 对是不同的 PR（#148 与 #153）。
- 阈值附近两侧都有例外：低于阈值的真重复（0.744），以及刚低于阈值的误配（0.748）。
- 在拆细的记忆上，现行阈值大体能区分，但边界两侧仍有重叠；合并任务的数量随之增加。
- 样本全部来自同一项目的开发会话，内容高度同质，结论能否推广到其他领域未知。

回放方法与逐话题结果见已归档的[多条提取与查重 Idea](../archive/ideas/settlement-multi-memory-extraction-and-dedup.md#g-1-一个话题的多条记忆怎样提取) G-1 一节。

## 查询对齐入库文本（2026-11-01）

owner 决定把查询与入库文本形态不一致作为缺陷修复（2026-11-01）：查询改为按入库的 `DENSE_EMBEDDING` 目标编译草稿，判定方式与阈值不变。2026-10-29 证据中“自相似够不到 TOUCH”一条由此解决；相关对与无关对没有分数间隔的问题不受影响。

- **固定样本**：内容与已有记忆相同的草稿由 0.902 升至 0.983，判为 IDENTICAL；内容演进的样本由 0.763 升至 0.863；无关样本由 0.455 升至 0.527。
- **真实库的最近邻**：当时中期库的 90 条记忆各按入库文本查询（排除自身），落在 0.75～0.95 的由 10 条增至 19 条，平均上移 0.032，没有超过 0.95 的。新进入合并区间的多为近似重复（两条快速排序实现，0.738 → 0.827）与同一工作的不同阶段，也有关联但不同的事（调研用 MCP 的配置实测与选型方案，0.685 → 0.791）。

## 可能的方向（分析，未决定）

| 方向 | 内容 | 影响 |
|:---|:---|:---|
| A | 保留 dense top-1 与固定阈值，在已对齐的嵌入文本上重新标定 | 不增加模型调用；嵌入文本已于 2026-11-01 对齐，只解决了自相似够不到 TOUCH；离线复现显示相关对与无关对没有分数间隔 |
| B | dense top-k 召回后由已常驻的交叉编码器打分，按分数判定 | 不增加 LLM 调用；唯一一组记忆对样本中分开了相关与无关，问题式短查询上排序不稳定；原始分数会随重排模型量化改变（int8 暂不做） |
| C | dense 宽门槛召回 top-k，由 LLM 判定新建、更新、合并或只建立关联 | 每条草稿多一次模型调用；判定理由可以记录；需要输出契约与提供商失败时的回退 |

比较之前先整理标注样本，覆盖四类关系：重复、同一工作的不同阶段、同项目但无关、完全无关。

## 影响

- 同一工作被空闲结算或会话切换拆到不同话题时，后续阶段总是新建记忆，同一件事在库中分散成多条。Claude Code 的长任务常有较长间隔，这种拆分会是常态。
- 单靠调低阈值无法解决：dense 分数在相关对与无关对之间没有间隔，任何阈值在放进相关对的同时也会放进无关记忆。合并落地后，误判的代价从覆盖丢失内容变为把无关记忆融进同一条记忆，只能经版本记录与人工编辑纠正。
