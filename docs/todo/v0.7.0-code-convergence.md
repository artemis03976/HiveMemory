## 1. 与顶层设计不一致（P1）

### 1.1 已删除的“意图撤回”仍写在注释与当前文档中

写入意图实时派发之后，CPU 失败、取消、进程关闭或 CALL 子帧失败都不撤回已提交的写入（AGENTS.md 第 4 节），操作入口也没有撤回路径。以下文字仍描述撤回：

- `WorkspaceOperation` 的 docstring 把“执行单元的意图撤回补偿”列为非 actor 操作（`core/access.py:35`）；

AgentRuntime 与 MTP 文档已修正，剩余 `WorkspaceOperation` 注释待清理。**建议**：删除剩余撤回描述。**完成**：代码与当前文档中不再出现意图撤回的描述（Archive 中的历史记录不改）。

### 1.2 子帧动词集合的说明仍是“继承父 frame”

执行线程层之后，子帧的动词集合由被调用方自己的操作快照翻译并去掉 CALL（`call_coordinator.py` 按 `callee.allowed_operations` 构造策略）。`AgentPromptAssembler.build_sub_agent_messages` 的 docstring 仍写“使用父 frame 继承的动词集合”（`prompts/assembler.py:72`），同一方法还再去掉一次 CALL，与调用方 `denied_verbs={"CALL"}` 重复。

**已移交**：[提示词编译前移计划](../plans/v0.7.0-cpu-prompt-compilation.md)删除组装器并由 CALL 编排直接组装子帧提示词，本条随之处理。

### 1.3 “当前 Topic”概念的前后端残留

v0.7.0 回归会话模型后取消了“当前 Topic”，Topic 也不再提供对话上下文（[Workspace 架构](../architecture/workspace.md)第 5.5 节），但以下代码仍为它服务：

- **手动结算的缺省话题**：`PerceptionFamiliar.manual_settle_topic(topic_id=None)` 回落到 `_last_active_topic_ids`（`patchouli/services/perception.py:72、235-248、474-480`），这张表只为该回落维护；公开路由 `MANUAL_SETTLE_TOPIC`、`TopicManagementService.settle_topic` 与 `RootTopicService.settle_topic`（`workspace/capability/root/topic.py:45-49`）都把 `topic_id` 声明为可选，而唯一的生产入口 `POST /topics/{topic_id}/settle` 总是传入话题。回落失败抛 `ValueError`，HTTP 层只捕获 `KeyError`，会变成 500；
- **话题状态提示词**（→ 提示词计划）：`SystemPromptBuilder.with_topic_state`（`prompts/system_prompt.py:92`）与 i18n key `topic_state_header` 没有生产调用方；
- **前端**：`mapTopic(raw, activeTopicId?)` 的第二个参数没有调用方传入，`activeNow` 恒为 `true`，`TopicCard` 因此对所有话题显示“在线”而不是相对时间（`frontend/src/services/topicApi.ts:31-41`、`components/chat/TopicCard.tsx:102`）；`last_accessed_at` 后端从不返回，`lastActive` 恒为 `Date.now()`。

**建议**：`topic_id` 在公开路由、root API 与 Patchouli 中改为必填，删除 `_last_active_topic_ids`；删除 `with_topic_state` 与对应 i18n key；前端删除 `activeTopicId`/`activeNow`，相对时间改用后端实际返回的字段，或在 `ActiveTopicResponse` 中补出最近访问时间。**完成**：后端不再保存“最近活跃话题”，话题卡片显示真实时间。

### 1.4 写入意图全局事件的命名与载荷

- 三个全局事件仍是 `alice.events.pending_atom.{settled,failed,cancelled}`（`core/contracts/events.py:24-26`），但发布方是 Patchouli、订阅方是 workspace 的 `WriteIntentRegistry`，Alice 已与写入意图无关。改名在写入意图登记计划中被列为非目标，收尾时可以处理。
- `settled` 携带 `intent_id`，`failed` 与 `cancelled` 只带 `pending_alias`：`PendingAtomSettler` 不传、bridge 的 `_forward_pending_atom_failed/_cancelled` 也只接收 alias（`patchouli/runtime/bridge.py:263、271`）。登记侧 `on_failed/on_cancelled` 的可选 `intent_id` 与 `_matching` 中按 intent_id 回查的分支（`workspace/intents/registry.py:135-159`）因此永远走不到。

**建议**：事件改名到发布方的命名空间（如 `patchouli.events.pending_atom.*`），同步 [路由与事件契约](../contracts/routes-and-events.md)第 147-149 行；三个事件统一携带 `intent_id`，登记侧改为必填。若暂不改名，至少删除登记侧走不到的可选分支。

### 1.5 server 层 SSE 事件模型与真实投影脱节

`server/models/chat.py` 中的 `StreamNamespace`、`ChatTokenEvent`、`MTPStartEvent`、`MTPResultEvent`、`TopicInfoEvent`、`ChatDoneEvent`、`CommandResultEvent`、`ChatErrorEvent` 在后端没有任何使用方，只经 `server/models/__init__.py` 导出。其中 `TopicInfoEvent` 与 `ChatDoneEvent.pool_topics` 是已删除的概念，`ChatDoneEvent` 又缺少实际下发的 `topic_id`、`failure_reason`、`model_used`。真实的 SSE 投影在 `workspace/process/outputs.py` 的 `stream_events` 与 Alice 的流式适配器中。前端 `types/chat.ts` 的文件头声称与这个 Python 模块一一对应，`ChatDoneEvent.mtp_commands_executed` 也是后端不再产生的字段。

**建议**：删除这组无人使用的后端模型（或让 `stream_events` 改用它们做类型化投影，二选一，默认删除）；前端文件头改为指向[路由与事件契约](../contracts/routes-and-events.md)，删除 `mtp_commands_executed`。

**已移交**：[异常体系与边界错误呈现收敛计划](../plans/v0.7.0-error-model-convergence.md)。目标方案与验收由计划维护，本条不再独立实施。

## 2. 结构冗余与死代码（P2）

### 2.1 写入意图状态机中从不产生的状态与无人使用的辅助

登记直接进入 MATERIALIZING，也没有过期机制，因此：

- `PendingAtomStatus.PENDING` 与 `EXPIRED` 从不产生，状态迁移表中相关的边全部是死边；`is_terminal` 只把 EXPIRED 视为终态（`core/models/pending.py:30-84`），与 SETTLED/FAILED/CANCELLED 实际不再迁移的事实不符；
- `ReferenceResolution.kind` 的 `"expired"`（`core/models/reference.py:16`）只被消费、从不产生：读取视图把 EXPIRED 映射为 not_found（`workspace/resolution/alias.py:93`），MTP READ/RUN（`agent_runtime/mtp/verbs/read.py:68`、`verbs/run.py:88`）与 MemoryCompiler 的 builders/handlers（`resolve_result.py:23`、`pending_atom.py:17`、`handlers/common.py:53-90`）仍保留分支和 `resolve_expired` 文案；
- `allowed_transitions`、`InvalidStateTransition`、`PendingAtomSnapshot`、`PendingAtomMaterializeTask.from_pending_atom` 在 `src/` 中无人使用。

[写入意图后续方向 Idea](../ideas/pending-intent-migration.md)把“结算后保留期满转为 EXPIRED”列为可能路径之一，但它没有排期。

**建议**：删除 PENDING 与上述无人使用的辅助；EXPIRED 与 `"expired"` 种类一并删除，句柄保留期的设计排期时再按当时的方案加回。同步 [数据模型](../architecture/data-model.md)第 113 行、[MTP 契约](../contracts/mtp.md)第 92 行、[PendingAtom](../alice/pending-atom.md)第 61 行、[MemoryCompiler](../patchouli/memory-compiler.md)第 49 行与 [Alice 编排](../alice/orchestration.md)第 148 行中“保留兼容枚举”的描述。

### 2.2 主动生成的单元素批量与三次表示转换

finalize 时批量派发的设计已被逐条实时派发取代，接口仍是批量形态：`PatchouliLocalRoutes.GENERATION_SUBMIT_ACTIVE(tasks: list[...])`（`patchouli/contracts/local_routes.py:155`）的唯一调用方传 `tasks=[task]` 并解包单个结果（`memory_intent_submission_service.py:54`），`MemoryGenerationCoordinator.submit_active` 仍按列表循环、按列表返回接纳结果。同一个意图在链路上换了三种表示：actor API 把 `WriteFocus/UpdateFocus` 拍平成 `MemoryIntent`（`workspace/capability/actor/memory.py:205`），Patchouli 再拼回同样的 Focus 并包成 `PendingAtomMaterializeTask`（`memory_intent_submission_service.py:74`）。

**建议**：本地路由与 `submit_active` 改为单个任务、单个接纳结果。`MemoryIntent` 是否直接携带 core 中立的 Focus 由实施者权衡：拍平后公共契约不依赖 Focus 的演进，代价是两处逐字段映射。
