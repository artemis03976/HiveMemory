# v0.7.0 A2：Patchouli 共同 API 与业务职责收敛

Patchouli 已经拥有按处理领域组织的 application 层和 `GlobalSystemBus` 路由。A2 不为 Workspace 再包一层 provider，也不按 Actor 类型复制 API；它要做的是从 System、Alice 和外部 Actor 的共同行为中确认必要的业务操作，让三种 adapter 进入相同的总线路由，并把旧 `PatchouliService` 的运行编排与领域能力分开。

A2 独立交付读取、Topic 辅助 API、使用报告与结果观察的公共能力，并维护整个 Patchouli API 的操作目录。交互应用及数据投影的实现由[A4](./v0.7.0-a4-conversation-session-and-topic-projection.md)负责，主动意图与 Pending 的实现由[A5](./v0.7.0-a5-pending-memory-intents.md)负责；A2 只核对它们是否满足共同调用边界，不重复实现。依赖[A1](./v0.7.0-a1-workspace-access-boundary.md)的 access 契约，生产消费者切换交给[A6](./v0.7.0-a6-actor-adapters-and-integration.md)。

## 1. API 与 adapter 的边界

API 是 Patchouli 提供的稳定业务操作、输入、授权、结果、失败和生命周期语义；总线路由是其在 `GlobalSystemBus` 上的地址；application service 按处理领域实现 API；adapter 只转换协议、取得 access、决定触发时机和呈现结果。

主动工具调用和自动交接是触发方式，不是两套业务 API：SEARCH 工具和交互开始的自动 context 使用相同检索；完整交互在可靠的完成/封口/flush 信号后由 adapter 自动提交，不依赖模型选择“保存对话”工具。只提供 MCP search/write 工具不等于实现自动交接。

## 2. 三方共通操作

| 共通操作 | System adapter | Alice adapter | 外部 adapter | Patchouli 语义 |
|:---|:---|:---|:---|:---|
| memory search | Passive context 或管理应用查询 | prepare、MTP SEARCH | 自动 context、search 工具 | 同条件同 policy 的可见检索与来源 |
| profile/read | 管理和应用读取 | Root/CALL、MTP READ | Profile/read 工具 | 解析引用、检查可见性、返回 snapshot |
| Topic 资料 | 摄入关联和读取 | prepare 读取 | Session/Segment 的 Topic 资料 | Patchouli 持有 Topic 路由和快照；不要求 Alice run |
| Pending 登记 | 应用主动写入 | MTP WRITE/UPDATE | write/update 工具 | 登记可读意图，不等同 Memory |
| memory intent submit | 应用策略提交 | settlement adapter | 工具立即或延迟提交 | 接纳 `PendingAtomMaterializeTask`，读取全部可用 Topic 资料并生成/修订 |
| interaction submit | Passive seal/flush | run 结束归约 | 外部完成回调/封口 | 去重、应用 Segment/Topic/证据；不隐式物化 intent |
| result/usage observe | 展示与反馈 | 引用、使用与结算 | 结果查询和反馈 | 分开表达接收、应用、物化、canonical 与实际使用 |

共同操作不表示相同权限或相同触发信号；统一的是领域语义和业务链路。

## 3. 三个入口如何收敛

**管理员读取 Memory**：受信管理入口建立 `CallerPrincipal`，A1 签发 `management.memory` context，System application service 调用 `PATCHOULI_MEMORY_GET`，Patchouli application 重验 grant、Workspace ownership 和管理读取 policy，再由 MemoryLibrary 返回 copy-on-read 结果。

**Alice 执行 SEARCH**：MTP adapter 为 Alice principal 请求 `resource.search`，AliceBridge 原样透传 context 到 `PATCHOULI_MEMORY_RETRIEVE`，Patchouli 执行 PRIVATE/TEAM/PUBLIC 与检索规则，MemoryCompiler 再把结果转换为 MTP/SSE。外部 harness 只替换 principal 和 wire adapter，仍调用该路由。

**Passive 提交完整交互**：Passive adapter 累积事件，在完成回调、封口或显式 flush 后形成 A4 的 `ConversationSegment`，请求 `interaction.submit` context，调用 `PATCHOULI_INTERACTION_SUBMIT`。application 验证 segment、scope 和去重键后才创建内部 `InteractionSubmission`，队列再应用 Topic/证据。接纳前不能清空 buffer，重复完成不能重复应用；interaction.submit 不隐含 resource.search。

三条链路使用同一四阶段授权、同一 application 语义和同一领域实现；返回的 HTTP、MTP/SSE 或 Passive receipt 由 adapter 分别呈现。

同一交互提交的收敛更直接：

```text
System/Passive：实际事件 -> 累积/封口 -> ConversationSegment
Alice：AgentRunResult -> 运行侧转换 -> ConversationSegment
外部 adapter：完成回调/完整记录 -> wire 转换 -> ConversationSegment
                       |
           各自取得 interaction.submit access
                       |
GlobalSystemBus.request(PATCHOULI_INTERACTION_SUBMIT, access=..., segment=...)
                       |
Patchouli application -> 内部 InteractionSubmission -> queue -> Topic 应用
```

`segment` 参数名是目标示意，最终 Python 签名在 A4-0 冻结。adapter 不导入内部 queue envelope，不据 `origin=alice/passive` 选择另一条领域算法。外部 Actor 看到 B 的 HTTP/JSON 等协议；同进程 adapter 同样请求全局路由，不直接调用 Patchouli application 对象。System 顶层 service 可按需保留封装；不要求 Alice 为形式一致绕行 HTTP。

## 4. PatchouliService 的收缩

| 旧职责 | 目标承担方 |
|:---|:---|
| prepare 中的 Profile、Topic、检索 | 调用侧 prepare adapter 组合共同路由；Patchouli 保留领域解析、Topic 准备和检索 |
| `AgentRunContext`、stream prelude、运行参数 | Alice/Chat 执行侧 |
| 附件选择、编译、lease | 调用侧协调 System-owned Asset API 与 AttachmentCompiler |
| finalize 的事件归约和提交时机 | Alice/System adapter；分别调用 interaction 和 memory_intent 路由 |
| 交互应用、Topic 路由、生成、Pending 结算 | Patchouli application/领域服务的唯一实现 |
| citation、feedback、Topic 条件清理 | Patchouli 领域 API；adapter 只报告事实和请求操作 |

旧方法可以在迁移期委托新 API，但不再直接提交内部 queue、controller 或 generation local route。取消、continuation、lease release 和 shutdown drain 必须由新的调用侧 coordinator 和领域 application 分别承接；不能因为拆分而丢失这些保障。

调用侧负责尚未交接的运行工作，application 接纳后负责领域工作。Alice 为纳入本轮资料而等待 interaction apply 属于运行策略，不使两条提交成为原子事务。后置主动物化失败不能把已应用交互改判失败。Topic 清理必须由领域侧检查“仍为空且允许清理”，不能由 adapter 先查再无条件 evict。生成材料读取、预算编译、controller 选择和结算留在 Patchouli，不要求 adapter 拼生成规范或额外调用一串内部步骤。

## 5. 路由与输入冻结

继续复用现有 `patchouli.public.memory.retrieve/read/retrieve_by_aliases`、Profile snapshot、管理 API 和 `patchouli.public.interaction.submit`。对缺口补充明确的 Profile source projection、Topic prepare/conditional cleanup、interaction result observation、usage/citation/feedback 和 `patchouli.public.memory_intent.submit`。

`interaction.submit` 的共同输入是 A4 的 `ConversationSegment`；队列内部的 `InteractionSubmission` 是 envelope。`memory_intent.submit` 的共同输入是 A5 冻结的 `PendingAtomMaterializeTask`。不能把 `materialize_tasks` 留在普通交互提交里并隐式执行，也不能为外部 Actor 新造 `MemoryIntent` 领域模型来复制 Pending。

所有公开 application 方法接收 A1 的 access context。没有 context 的旧调用只能在受信内部适配窗口内存在；A6 收口时删除或限制它们。Patchouli application 不回调 Workspace 业务 service，Workspace cache miss 也不能重新进入 public route 形成递归。

### 5.1 已有 API 与缺口的实施清单

以下沿用原计划与 WRX-0 的 2026-09-17 分支调查，表示可复用的代码入口，不宣称消费者切换或最新目标已经通过验收。实施前按当前分支核对签名差额。

| API | 已有入口/实现 | 责任与剩余差额 |
|:---|:---|:---|
| 管理 Memory | `patchouli.public.memory.get/list/create/update/delete`；MemoryManagementService | A2 保留管理语义；A1/A6 禁止普通 read grant 走 owner bypass |
| Actor 点读/alias | `patchouli.public.memory.read/retrieve_by_aliases` | A2 完成 copy-on-read、当前 visibility 与来源投影 |
| 检索 | `patchouli.public.memory.retrieve` | A2 统一结果语义；A6 把 prepare 内部检索转向同一路由，支持主动和自动触发 |
| Profile | `patchouli.public.get_agent_profile`、`get_agent_profile_snapshot`；AgentProfileManagementService | A2 唯一 builtin/alias/type/解析；裸 Profile 只作兼容投影，source UUID/revision 一次返回 |
| Topic 准备/资料 | `patchouli.public.topic.list_active/get_data`；prepare_topic 尚未独立挂载的调查记录 | A2 补公开签名与 operation；A4-0 冻结路由关联/handle，不能把 session_id 当 topic_id |
| 交互提交 | `patchouli.public.interaction.submit`；InteractionSubmissionService | A4 实现 Segment 契约/投影；A6 切换旧 finalize 和 Passive 直调 queue 的路径 |
| 主动物化提交 | `patchouli.public.memory_intent.submit`；MemoryIntentSubmissionService | A5 收敛共同输入与单一生成链；独立方法不要求独立类 |
| Pending 登记/读/解析 | 原 Alice PendingAtomRuntime/resolver | A5 冻结资源侧公开方法、operation、可见性与生命周期 |
| 任务与交互结果 | `patchouli.public.memory_task.list/get/cancel`；MemoryTaskManagementService | A2 补 interaction apply 观察；当前无公开 `memory_task.wait`，需要时另冻结等待/关闭语义 |
| 使用/引用/反馈 | `patchouli.public.record_memory_citation`、`memory.record_feedback`；usage 隐藏在 finalize | A2 区分返回、实际使用、引用、评价；冻结普通 Actor 报告权限，不借管理 bypass |
| Topic 清理/管理 | `patchouli.public.manual_settle_topic/evict_topic` | A2 保留管理；新增准备失败条件清理契约，A6 保留补偿和 lease 保障 |
| Asset | System WorkspaceAssetApplicationService、reader/command ports | A1/A3/A6 沿用 READY/lease；不因统一 Patchouli API 改变 System 所有权 |

### 5.2 快照与兼容规则

- Profile builtin/source atom UUID/revision 必须在领域解析结果中明确；Root/CALL/外部读取复用相同解析和可见性，profile.read 不等于执行或冒充该 Agent。
- Memory alias 索引按 Workspace 分区；UUID 索引可全局加速，返回前仍验证 ownership/visibility。cache miss、不可见、不存在和 unavailable 各自遵循稳定错误，不回退到别的 Workspace 或旧值。
- 读取返回不可变或 copy-on-read 快照，具体 cache key/source/epoch 只由 A3 维护；管理读取不能给 Agent cache 带入永久授权。
- 调用方提交使用报告是 provenance 声明；返回过 ref 不等于实际使用过。附件使用只承接已有编译确认的 ref 快照，不能回查当前 UI 选择替代。
- HTTP/MTP/SSE 兼容由 adapter 维护，内部签名变更记录 access、DTO、错误及删除窗口。旧 Alice 专属 prepare/finalize/cleanup 不在“全部路由永久保留”范围内。

## 6. 实施、测试和完成条件

| 阶段 | 产出 | 验收 |
|:---|:---|:---|
| A2-0 | 共通操作清单、已有路由/缺口、旧复合职责交接表 | 任何新增 API 都能说明三方共同语义和唯一领域 owner |
| A2-1 | 读取、Topic、结果和使用 API | 无 Alice 的真实 application 可用；管理读取不授予普通 Actor |
| A2-2 | 与 A4/A5 的操作目录和签名交接 | 两个提交由各领域计划实现；各自授权、收据与无 Alice 要求没有冲突，不重复开发 |
| A2-3 | 旧 PatchouliService 职责/调用方/退出窗口清单，交 A6 | 每项职责均有已验证的公共领域入口或调用侧接收方；A6 验收实际删除 |

integration 使用真实 GlobalSystemBus、PatchouliBridge、application、queue 和 domain collaborator；fake 只能替换外部模型/网络。测试覆盖三种 adapter 的相同路由、自动 context 与主动 SEARCH、重复 interaction、结果观察、Topic 条件清理和错误阶段。完成后更新 contracts、Patchouli、System/Alice 当前事实；未收尾的设计继续留在 A2/A4/A5，不提前晋升。

A2-0 的关键待决是 Topic 准备/条件清理、交互 apply 查询、普通 Actor usage/feedback 的签名和 operation；它们必须在对应实现前关闭。A2 本身可先用稳定领域 API 验收，不等待全部消费者装配。回滚仅保留委托同一领域实现的受信 adapter，不恢复旧 queue/generation 旁路；任何兼容入口写明调用方与删除时点。
