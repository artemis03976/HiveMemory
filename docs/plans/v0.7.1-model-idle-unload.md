# v0.7.1 推理模型的空闲卸载与按需加载

> 状态：Planned（owner，2026-10-27）。进入条件见第 4 节。第 5 节中标为“候选”的细节不是 owner 决定，计划评审时可以调整。

## 1. 背景和问题

v0.7.1 的版本目标是 plugin 模式接入 Claude Code（[ROADMAP](../ROADMAP.md) 第 4.3 节）。plugin 模式下，后端与 Qdrant 需要随用户的日常使用常驻。

2026-10-27 在开发机上观察到：常驻运行的后端进程峰值常驻内存（VmHWM）为 3.0 GB；同一时刻 Qdrant 的活跃内存约 80 MB。后端内存主要来自两个推理模型：

| 组成 | 常驻内存（实测） |
|:---|:---|
| Python 与依赖导入 | 约 300 MB |
| 嵌入模型 bge-m3（int8） | 约 850 MB |
| 重排模型 bge-reranker-base（fp32） | 约 1.36 GB |

两个模型在启动预热后一直驻留到进程结束，不使用时也占用内存。plugin 模式下的使用并不连续：

- 对话经 Import Bus 回流时不检索记忆，不用重排模型；
- 嵌入模型用于检索、记忆生成的去重候选检索和记忆写入。记忆生成在后台队列中进行，对延迟不敏感。

一台 16 GB 内存的笔记本或小主机若要常驻 HiveMemory，就要为不在使用的模型长期付出 2 GB 以上的内存。

## 2. 目标与非目标

### 2.1 目标

- 嵌入模型与重排模型分别支持空闲卸载与按需重新加载，卸载后内存实际归还给操作系统；
- 驻留方式可配置：常驻（与当前行为相同）或空闲卸载；
- 尽量不让重新加载的耗时落在请求的关键路径上：
  - chat 任务进程在 Gateway 阶段之前发出预取，加载与 Gateway 的 LLM 调用并行；
  - 检索时重排模型尚未就绪，则这一次跳过重排，并触发后台加载；
- 卸载之后，就绪检查仍能反映服务是否可用；
- 推理进行中不卸载；加载与卸载互斥；服务关闭时不留下在途的加载任务。

### 2.2 非目标

- 按系统内存压力卸载：先以空闲时限观察效果；
- 把模型放到独立子进程：实测进程内释放后调用 `malloc_trim(0)` 即可把内存还给操作系统（第 3.3 节）；
- 更换嵌入模型或改用远程嵌入 API：需要对全部记忆重新计算向量；
- 重排模型精度、ONNX 内存池与截断长度：由 [重排模型 int8 与 ONNX 内存池](../todo/reranker-int8-and-onnx-memory.md) Todo 处理；
- 推理移出事件循环：是本计划的进入条件（第 4 节）；
- 为尚不存在的入口（MCP 记忆访问）接入预取：本计划只提供预取能力；
- Qdrant 的内存配置。

## 3. 当前状态（2026-10-27 核对，commit `d4220de7`）

### 3.1 模型服务

- 嵌入服务与重排服务各自继承一个 `SingletonModelService` 基类（`infrastructure/embedding/base.py`、`infrastructure/rerank/base.py`），两份基类逻辑相同：
  - 实例为进程级单例；
  - 首次访问 `model` 属性时在锁内加载；
  - `warmup()` 触发加载，`is_loaded()` 判断模型是否存在；
  - 没有卸载能力。
- 推理在 async 函数中同步执行（`VectorStore.search_memories`、`VectorStore.upsert_memory`、`RetrievalEngine.retrieve`），懒加载也随之发生在事件循环上。把它们移出事件循环是第 4 节的进入条件。
- 重排计算抛出异常时，`CrossEncoderReranker.rerank` 记录 warning 并返回召回结果；重排关闭或未装配服务时由 `NoopReranker` 顶替（[Patchouli 检索](../patchouli/retrieval.md)）。

### 3.2 预热与就绪

- 服务启动后，`server/app.py` 以后台任务调用 `SystemReadinessService.warmup_models`，经 `patchouli.public.models.warmup` 到 `PatchouliRuntime.warmup_models`，以 `asyncio.to_thread` 依次加载两个模型。预热失败只记录错误，之后退化为首次使用时加载。
- `PatchouliRuntime.is_models_ready` 在两个模型都已加载时为真，`/health/ready` 据此返回 `ready`，否则返回 503 `warming_up`（[安装指南](../help/setup.md)、[故障排查](../help/troubleshooting.md)）。

### 3.3 卸载与重新加载的实测

2026-10-27 开发机实测，16 核，fastembed 0.8.0，onnxruntime 1.30.0，关闭 ONNX CPU 内存池，模型文件已在页缓存中：

- 两个模型加载并各推理一次后，常驻约 2.3～2.6 GB；
- 删除模型对象并 `gc.collect()` 后仍有 1.3～1.6 GB，glibc 没有把释放的内存还给操作系统；
- 再调用 `malloc_trim(0)` 后降到约 105 MB；连续三轮“加载、推理、卸载”没有增长。Docker 镜像基于 `python:3.12-slim`（glibc）；
- 重新加载耗时：
  - bge-m3 1.0～1.4 秒；
  - 重排模型 fp32 1.5～1.8 秒，int8 约 0.9 秒；
  - 模型文件不在页缓存、核数更少的机器上更慢；
- 推理耗时：短查询嵌入约 0.04 秒；重排 20 条 0.8～1.2 秒。

### 3.4 维护调度与 Gateway 阶段

- Patchouli 经 `PatchouliSystem.register_maintenance_tasks` 向全局 `AsyncMaintenanceScheduler` 登记周期任务（`MaintenanceTaskSpec` 的 `interval_seconds` 与 `enabled` 来自 `SchedulerConfig.tasks`），已有话题空闲结算与记忆整理两项。
- `TaskProcessRunner` 在 Gateway 阶段经 `GatewayPublicRoutes.PROCESS` 调用 Gateway；Gateway 分析包含 LLM 调用，之后才进入 Patchouli prepare 与检索。

## 4. 进入条件

- [推理移出事件循环](../todo/inference-off-event-loop.md)已完成：推理与模型加载不在事件循环上执行（owner，2026-10-27）。开始实施时按当时的代码重新核对第 3 节。
- [重排模型 int8 与 ONNX 内存池](../todo/reranker-int8-and-onnx-memory.md)不是进入条件。它只改变各项的内存与耗时数值，验收时按当时的模型重新测量。

## 5. 目标设计

### 5.1 模型驻留

每个模型服务持有一个驻留状态：未加载、加载中、已加载、加载失败。规则如下：

- 每次推理前取得模型、结束后归还，服务记录在途推理数与最近一次使用时间。时间取自注入的单调时钟，与 `TopicWorkingSet` 的做法相同。
- 推理时模型未加载，就在推理线程中加载，调用方等待；加载与卸载互斥。
- 卸载只在没有在途推理、也没有正在进行的加载时进行。卸载时释放模型对象，执行 `gc.collect()`；运行库提供 `malloc_trim` 时再调用 `malloc_trim(0)`，不提供时跳过并记录一次 debug 日志。
- 加载失败进入“加载失败”状态，下一次推理或预取时重试。

候选：驻留逻辑合并为嵌入与重排共用的一份实现，取代现在的两份 `SingletonModelService` 基类。

### 5.2 驻留配置与空闲卸载

- 嵌入配置（`shared.embedding.default`）与重排配置（`patchouli.retrieval.reranker`）各自增加：
  - 驻留方式：`resident` 或 `idle_unload`；
  - 空闲时限：秒数。
- Patchouli 向全局维护调度器登记“模型空闲卸载”周期任务，检查周期与开关放在 `SchedulerConfig.tasks`，与已有任务一致。任务对每个 `idle_unload` 模型检查空闲时间，超过时限就卸载。
- 候选默认值：重排模型 `idle_unload`、600 秒；嵌入模型 `idle_unload`、1800 秒；检查周期 60 秒。`resident` 保留当前行为，适合内存充足的机器。

### 5.3 预取

- Patchouli 新增公开预取 route。调用后立即返回，只保证加载已经开始；加载任务由 Patchouli runtime 持有，服务关闭时取消。已加载或正在加载时不做任何事。
- `TaskProcessRunner` 在调用 Gateway 之前发出预取，同时请求两个模型。预取失败只记录日志，不影响任务进程。代价是 Gateway 判定不需要检索时也会加载，这部分内存由空闲卸载回收。
- 启动预热保留。`idle_unload` 模型同样在启动时加载一次，以便尽早发现模型文件或配置错误，之后按空闲时限卸载。

### 5.4 就绪时的降级

- **重排模型**：`CrossEncoderReranker` 发现模型不是“已加载”时，不等待加载。这一次按召回顺序截取 top-k，记录 warning，并触发后台加载。这与已有的重排失败降级结果相同。
- **嵌入模型**：不降级，调用方等待加载。dense 召回与记忆写入都依赖它；后台生成对延迟不敏感，检索最多多等约 1 秒。

### 5.5 就绪语义

- `is_models_ready` 的含义从“模型已加载”改为“每个启用的模型自进程启动后至少成功加载过一次，且当前不处于加载失败状态”。空闲卸载不会让服务变为未就绪。
- `/health/ready` 的返回形状不变。启动预热尚未完成时仍是 503 `warming_up`；重新加载失败时变为未就绪，直到下一次成功加载。

### 5.6 观测

模型加载与卸载各记录一条 info 日志，包含模型名、耗时，以及运行平台提供 `/proc/self/status` 时卸载前后的常驻内存。重排降级沿用 warning 日志。本计划不新增 RuntimeEvent。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| infrastructure：嵌入与重排服务 | 驻留状态、在途计数、卸载与内存归还 |
| engines/retrieval：`CrossEncoderReranker` | 模型未就绪时跳过重排并触发加载 |
| Patchouli runtime 与 system | 空闲卸载维护任务、预取 route、就绪语义、关闭时取消加载 |
| Patchouli contracts | 新增公开预取 route；`patchouli.public.models.ready` 含义变化 |
| workspace.process：`TaskProcessRunner` | Gateway 阶段之前发出预取 |
| 配置 | 嵌入与重排的驻留方式与空闲时限；调度任务的周期与开关 |
| server | `/health/ready` 形状不变，含义随就绪语义变化 |
| 数据 | 无持久化数据变化 |

依赖方向：workspace 只导入 Patchouli 的 `contracts`；驻留机制位于 infrastructure，不导入上层。

## 7. 兼容与迁移

- 新增的配置项都有默认值，旧配置无需修改即可加载。若采用第 5.2 节的候选默认值，升级后模型默认空闲卸载；想保持原行为，把驻留方式设为 `resident`。
- 就绪语义的变化写入[安装指南](../help/setup.md)与[故障排查](../help/troubleshooting.md)。依赖 `/health/ready` 判断“模型已在内存中”的外部脚本需要改为只把它当作服务可用的信号。
- 无数据迁移。

## 9. 测试和验收标准

### 9.1 不变量与归属层

| 不变量 | 归属层 |
|:---|:---|
| 推理进行中不卸载；加载与卸载互斥；卸载后的下一次推理重新加载；加载失败可在下一次重试 | infrastructure 模型服务的单元测试（`tests/unit/infrastructure/`），使用假加载器与注入时钟 |
| 空闲时间按注入时钟判定；`resident` 从不卸载；`idle_unload` 只在超过时限后卸载 | 同上 |
| 重排模型未就绪时这一次按召回顺序截取 top-k，并触发一次加载 | `tests/unit/engines/retrieval/` 中已有的重排测试 |
| 预取立即返回、重复预取不重复加载、服务关闭时取消在途加载 | Patchouli runtime 的单元测试 |
| 首次成功加载后就绪，空闲卸载不改变就绪，加载失败时未就绪 | Patchouli runtime 的单元测试；server readiness 至多一个代表用例 |
| 任务进程在 Gateway 调用之前发出预取，预取失败不影响进程 | workspace process runner 的一个代表用例 |

测试不以固定 sleep 等待状态，时间推进经注入时钟完成。

### 9.3 实测验收

使用真实模型，以 `scripts/hivememory-dev.sh` 启动服务，把空闲时限调短后验证：

- 空闲卸载后，后端进程的 `VmRSS` 回落到不含模型的水平，并记录数值；
- 卸载后的首次 chat：重排降级日志出现，或预取已经让模型就绪；之后的检索恢复重排；
- 卸载后的首次记忆生成：嵌入模型重新加载，写入成功；
- 多轮“空闲卸载、重新加载”后常驻内存没有持续增长；
- 结果记入实施记录，并注明机器配置。

## 10. 风险与待决问题

### 10.1 风险

- **其他平台的内存归还**：`malloc_trim` 只在 glibc 上有效，其他分配器或平台上释放的内存可能不归还。验收只覆盖 Linux，其他平台的表现要单独观察。
- **冷启动更慢**：页缓存被回收或使用机械硬盘时，重新加载比第 3.3 节的数值慢。预取与重排降级可以覆盖 chat 路径，但覆盖不了嵌入模型的等待。
- **检索质量波动**：卸载后首次检索可能跳过重排，排序质量在这一次下降，只在日志中可见。
- **长期碎片**：实测只做了三轮加载与卸载，长期运行中的碎片要在实测验收与日常使用中观察。

### 10.2 待决问题

无。第 5 节的候选细节在计划评审时确认。
