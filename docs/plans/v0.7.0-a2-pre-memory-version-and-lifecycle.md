# v0.7.0 A2-P：记忆内容版本与 Lifecycle 状态重构

本计划是 [A2 资源读取、Runtime 与派生缓存](./v0.7.0-a2-workspace-resource-reads-and-caches.md)的独立前置工作，简称 A2-P；不调整 A2–A6 的编号，也不与 A2 内部的 A2-0 冻结阶段混用。实施阶段使用 MVL 编号。本文唯一维护完整 MemoryAtom、内容版本、lifecycle 动态状态、历史记录与受控写入的目标契约；A2 消费这些成果并交付缓存协作。

目标版本仍为 v0.7.0。后续 v0.7.3 MTP READ 专项消费这里保存的历史数据，负责版本选择、片段、差异、引用与预算编译。不能等到编译器实现时才开始正确保存历史：此前丢失的嵌套内容无法从当前原子可靠补回。

本文是 Planned 设计，不表示代码已经采用结构化 provenance、嵌套 lifecycle、Memory schema `2.1`、新的 `agent_config` 位置或强制版本记录。当前调查依据为 2026-09-20 工作树；A1 已完成，A2-P 尚未实施。

## 1. 问题与当前证据

| 当前实现 | 证据入口 | 需要改变的行为 |
|:---|:---|:---|
| `meta.version` 描述为乐观锁，内容更新递增它，但没有对应的比较交换契约 | [Memory 模型](../../src/hivememory/core/models/memory.py)、[生成引擎](../../src/hivememory/engines/generation/engine.py)、[生成服务](../../src/hivememory/patchouli/services/memory_generation.py) | 固定为内容修订序号；不能承担所有字段的变化标记或并发锁 |
| 强化和批量评分修改 metadata 后整颗 upsert；引用还重置 `updated_at` | [Lifecycle](../../src/hivememory/engines/lifecycle/)、[中期 adapter](../../src/hivememory/patchouli/memory_library/adapters/mid_term.py) | 动态状态只经受限更新提交；内容修订时间与衰减基准分离 |
| 普通 upsert 重新编译 embedding 输入并计算向量 | [向量存储](../../src/hivememory/infrastructure/storage/vector_store.py) | 访问、反馈和评分不进入内容/向量重写路径 |
| `MemoryVersionSnapshot` 只保存正文与部分 Index 字段，遗漏 `agent_config`、Relations 等结构 | [Artifact 模型](../../src/hivememory/core/models/artifact.py) | 历史保存完整原子结构；撤回“现有裁剪记录支持完整重建”的假设 |
| `MemoryProvenance` 已有实现但位于 generation 层，`MetaData` 与 Artifact 又各自平铺来源字段 | [生成模型](../../src/hivememory/engines/generation/models.py)、[Memory 模型](../../src/hivememory/core/models/memory.py)、[Artifact 模型](../../src/hivememory/core/models/artifact.py) | 沿用现有 `MemoryProvenance` 类型和字段，不创建第二个 provenance 模型；将其依赖中立的数据定义放入 `core.models`，generation 只保留上下文相关的构造逻辑 |
| `history_summary` 仍在生成更新和 MemoryCompiler 中作为轻量 fallback | [生成引擎](../../src/hivememory/engines/generation/engine.py)、[MemoryCompiler](../../src/hivememory/engines/memory_compiler/) | 从新 Memory schema 删除；正式历史只由 `MemoryVersionArtifact` 承担，旧值迁移时报告其遗留和完整性 |
| `agent_config` 位于 `payload.artifacts`，但它是可更新的 Agent Profile 内容 | [AgentProfile](../../src/hivememory/core/models/agent.py)、[Memory 模型](../../src/hivememory/core/models/memory.py) | 移至 `payload.agent_config`；Artifact 聚合只保留 append-only 引用、事件和存储定位 |
| 版本 Artifact 可禁用；构建失败被捕获后，原子仍可写入 | [Artifact builder](../../src/hivememory/engines/artifacts/memory.py)、[生成服务](../../src/hivememory/patchouli/services/memory_generation.py) | 新内容提交成功必须有对应的完整版本记录，失败不能静默降级 |
| 新增 `MemorySnapshot` 为裁剪投影；现有编译器消费完整 MemoryAtom | [读取投影](../../src/hivememory/core/models/projections.py)、[MemoryCompiler](../../src/hivememory/engines/memory_compiler/) | 删除裁剪原子读取模型及导出，保留完整对象与引用隔离 |
| codec 只接纳 Memory schema v2，存储过滤和服务投影直接读取平铺 metadata | [codec](../../src/hivememory/engines/retrieval/memory_codec.py)、[MemoryLibrary](../../src/hivememory/patchouli/memory_library/)、[服务端投影](../../src/hivememory/server/models/memory.py) | 显式迁移 schema、过滤字段与消费者，不能只改 Pydantic 模型 |

问题根源是内容修订、使用状态、资源策略和存储迁移共享了过宽的写入路径。字段分组与写入边界必须一起修改；只移动字段无法防止旧对象覆盖新内容，也不能消除无意义的向量重算。

## 2. 目标、非目标与依赖

本计划交付：

1. 完整 MemoryAtom 与结构化 `meta.provenance`、`meta.lifecycle` 聚合；内容版本、内容时间、衰减基准各自独立。
2. 内容修订、动态状态更新、资源策略更新和存储迁移的受控写入边界，覆盖当前所有正式写入者。
3. 完整、不可变的 MemoryVersionArtifact 历史与可辨认的旧裁剪历史；新内容提交和历史记录的一致性。
4. Memory schema `2.1` 的新格式 codec、结构化 provenance 和 `agent_config` 位置调整、`history_summary` 移除、现有读写消费者适配，以及交付 A2 的同步变更协作点。现有 Memory 原子的批量转换不在 A2-P 实施过程中执行；A2-P 完成后另写一次性临时脚本，只迁移 Memory 原子，不迁移 Artifact。

不交付 WorkspaceRuntime/cache 迁移、Actor adapter 重排、Pending 状态机、MTP READ 新模式、历史 diff/预算编译、生命力算法重新调参、worth_saving 重设计、独立 lifecycle 数据库或通用事件溯源平台。`meta.session_id` 的新承载位置也不在 A2-P 内决定；A2-P 删除并丢弃旧值，待 A3 完成 Session/Interaction 设计后另行安排。归档/复活沿用 MemoryLibrary 责任，不扩展为长期记忆检索功能。

依赖 A1 已有授权边界和当前 MemoryLibrary/ArtifactStore，不等待 A2 缓存、A3 Session、A4 Pending、A5 API 目录、A6 生产装配或 B wire。独立组合真实 Patchouli 组件验收；已有消费者因字段变更所需的适配属于本计划，不以提前创建新 WorkspaceRuntime 或装配未稳定系统为条件。

首版假设当前已有的串行写入方式：不新增并发协调、乐观锁、自动重试、未决提交状态或跨存储恢复协议。单次提交失败直接向调用方传播；留下的孤立 Artifact 不是 canonical 版本，由后续运维清理，不在 A2-P 内自动补偿。

## 3. 数据模型与不变量

### 3.1 完整原子与 Lifecycle 聚合

保留 MemoryAtom 的 `meta / index / payload / relations` 结构。在 MetaData 内持有两个结构化领域对象：现有 `MemoryProvenance` 由 `meta.provenance` 持有，`MemoryLifecycleState` 由 `meta.lifecycle` 持有。不为每种更新另建投影或第二份原子模型。`MemoryProvenance` 的字段和归一化规则沿用现有实现；为消除 core 对 generation 的反向依赖，只迁移其依赖中立的数据定义，generation 的 `GenerationContext` 构造逻辑继续留在 generation 层，不复制第二个类型。

| 字段 | 目标位置与语义 |
|:---|:---|
| `schema_version` | MemoryAtom 顶层；新 canonical 格式为字符串 `"2.1"`，旧整数 `2` 只作为有期限的迁移输入；与 MemoryVersionArtifact 的 Artifact schema 独立 |
| `version` | `meta.version`；从 1 开始的内容修订序号，同一资源每次实际内容提交推进一次 |
| `created_at` / `updated_at` | 留在 meta；分别是创建时间与内容最后修订时间，访问、反馈、策略修改、schema 迁移不刷新它们 |
| `access_count` / `last_accessed_at` | 迁入 `meta.lifecycle`；沿用既有事件计数口径，不在本计划顺带改变 HIT/CITATION/FEEDBACK 含义 |
| `event_vitality_boost` | 迁入 `meta.lifecycle`；强化事件累计影响 |
| `vitality_score` | 迁入 `meta.lifecycle`；最近一次计算并保存的派生分数，不保证随时间自动保持实时值 |
| `decay_anchor_at` | 新增于 `meta.lifecycle`；遗忘衰减的时间基准，创建时取创建时间，主动复习和内容修订按既有/本计划规则推进 |
| `confidence_score` / `verification_status` | 迁入 `meta.lifecycle`；对当前内容的评估，可独立变化，不因评估变化创建内容版本 |
| `provenance` | `meta.provenance`；使用从 `core.models` 复用的 `MemoryProvenance`，记录 `source_agent_id`、`source_team_id` 和 `contributing_agent_ids`；来源事实不参与授权 |
| ownership / `access_policy` | 仍留在 meta 原职责位置，不混入 lifecycle；Workspace 归属和读取授权语义沿用 A1 |

`MemoryLifecycleState` 只收纳表中当前已经存在或本次明确新增的生命周期字段：`access_count`、`last_accessed_at`、`event_vitality_boost`、`vitality_score`、`confidence_score`、`verification_status` 和 `decay_anchor_at`。A2-P 同时从 Memory `meta` 移除 `session_id`：不把它移入 lifecycle，不迁移旧值，也不提供兼容双写；后续承载位置待 A3 完成 Session/Interaction 设计后另行安排。不把 provenance、Workspace 归属、访问策略、内容版本或 Artifact 引用移入该对象，也不为首版增加独立的 lifecycle revision、锁字段或事件溯源字段。

既有数值范围、初始值和事件调整幅度保持现有规则。只有衰减时间源从 `updated_at` 改为 `decay_anchor_at`；时间输入统一为 UTC 并可在测试中控制。需要准确现时评分的排序或 GC 在决策时计算，不能把缓存中的物化分数误作任意时刻的实时结果。

不同操作仅能维护其负责的状态：评分计算只产生分数；HIT/普通访问维护计数和 `last_accessed_at`，但不推进 `decay_anchor_at`；CITATION 这种主动复习按既有规则推进 `last_accessed_at`、`decay_anchor_at` 和事件加成；内容修订按提交规则推进 `decay_anchor_at`；反馈/验证维护相应评估结果。聚合字段不授予任何调用方整体覆盖其他字段的权力。

### 3.2 内容版本覆盖范围

版本覆盖 Index、Payload 中的记忆正文与 `agent_config`、Relations 等内容事实。`history_summary` 从新 Memory schema 删除，正式历史只由 `MemoryVersionArtifact` 承担。实际内容相同的重复更新不创建新版本。alias、title、tags 等 Index 变化也属于内容修订。

`payload.agent_config` 是可更新的 Agent Profile 内容，变化要版本化；它不属于 embedding 输入，只有 Index 中实际参与编译的字段变化时才需要重算向量。`payload.artifacts` 只保留 append-only 的 Artifact 引用、生命周期事件和冷存储/复活定位；新增版本引用、CREATED/VERSIONED/ARCHIVED/REVIVED 事件以及存储定位维护不递归触发内容版本。MVL-0 按现有字段列出分类；后续新增字段必须指定类别，不允许因位于 Payload 或 Artifacts 就自动递增版本，也不能排除整个嵌套结构。

`meta.provenance` 是治理元数据，不因来源字段单独变化创建版本。`source_agent_id` 和 `source_team_id` 在创建时确定；`contributing_agent_ids` 只能随受控内容提交按既有规则合并，并与该次内容版本一同保存，不允许成为独立的整颗对象覆盖入口。

`MemoryCreationArtifact` 与 `MemoryVersionArtifact` 的来源字段也改为复用 `core.models.MemoryProvenance` 的结构化值，不在 Artifact 模型中继续维护另一组平铺 `source_agent_id`、`source_team_id` 和 `contributing_agent_ids`。Artifact 记录的 provenance 是写入时不可变的事实；它可以复制本次提交所使用的 `meta.provenance`，但不反向修改 canonical Memory，也不把 Artifact 的来源记录当作当前授权依据。

同一 `meta.version` 下 lifecycle、访问策略和运维引用可以变化，因此版本号不能比较整个 MemoryAtom 是否相等。AGENT_PROFILE 原子的解析结果可由缓存内部关联 source UUID 与内容版本，不新增配置版本，也不为此保留 `ProfileSnapshot.source_revision` 公共字段。`schema_version` 表达数据格式，cache epoch 表达运行时变更代次，三者不能互相替代。

### 3.3 引用隔离

由 A2-P 完整删除 `core/models/projections.py` 中的 `MemorySnapshot`、相关导出和只服务于该模型的说明。canonical 读取、缓存以及历史完整记录使用完整 MemoryAtom；版本历史在捕获时直接复制其完整 JSON 序列化结果。隔离通过深拷贝和历史存储不可变性实现，不能摊平、挑选字段再拼回原子。

AGENT_PROFILE 同样保存完整 MemoryAtom；已有 `AgentProfile.from_atom()` 解析的是运行配置，不是第二份 canonical 资源，也不替代完整历史。A2-P 不删除 `ProfileSnapshot` 或 Profile snapshot 路由；A2 仍负责其读取侧迁移。这里保留 `payload.agent_config`、正文和来源，A2 再消费完整原子完成类型/可见性检查与解析缓存；源 UUID/version 仅需内部关联，builtin 无需伪造源原子。

修改调用方持有的 index、嵌套 `payload.agent_config`、relations、provenance、lifecycle 或 ArtifactRef 列表，不得影响缓存、canonical 状态或已保存历史。仅冻结外层 Pydantic 模型不足以证明嵌套对象已隔离。

## 4. 受控更新与职责分工

| 操作类别 | 负责边界 | 允许的变化 | 版本与向量行为 |
|:---|:---|:---|:---|
| 创建/内容修订 | 现有 `MemoryGenerationFamiliar` 完整写入路径 | 内容字段、对应来源和历史关联；明确的内容更新后状态规则 | 创建 v1 或推进一次版本；保存完整历史；仅 embedding 输入变化时需要重算向量 |
| 生命周期维护 | Lifecycle 算法与服务，经 MemoryLibrary 受限状态更新 | 该业务操作允许的 lifecycle 字段 | 不改内容 version/updated_at，不生成版本 Artifact，不调用整原子 upsert 或 embedding |
| 资源策略修改 | 现有资源管理边界 | 访问策略 | 不制造内容版本；立即发布新的授权依据，不复用延迟统计刷新 |
| 归档/复活/删除 | MemoryLibrary 既有资源存储操作 | 所在层级、状态与运维引用 | 保留内容版本；物理迁移可保存完整原子，复活重建必要索引不等于内容修订 |

完整内容写入由现有 `MemoryGenerationFamiliar` 统一承载；它不负责 Lifecycle mutation，也不是新增的提交协调器：`MemoryGenerationEngine` 只产生 CREATE/UPDATE 结果，Familiar 负责调用 Artifact builder、挂载 refs/events，并通过 `MidTermMemoryStore` 完成 `upsert()`。`create_external_memory()`、`update_external_memory()` 和生成结果的批量处理都沿用这条路径。Lifecycle state 另走受限的局部更新路径。A2-P 修改这些现有路径的内部顺序和数据形状，不新增另一个 content commit facade。

Lifecycle state 更新保持独立。`VitalityCalculator` 保持纯计算职责。`refresh_vitality`、reinforce、批量维护以及 generation DISCARD 后的访问强化全部切换到受限状态更新；现有 `update_access_info` 调用点迁移到 `patch_payload` 后删除该专用入口。禁止状态维护拿到旧 MemoryAtom 后，通过完整内容 `upsert()` 回写；也禁止把局部更新伪装成“加载旧对象再整颗保存”。存储 adapter 应使用真正的局部 payload 更新，保留原有向量和非目标字段。

不新增对外 lifecycle facade、Patchouli provider 或 Workspace 业务 service。继续沿 application → 现有领域服务/算法 → MemoryLibrary 的依赖方向修改。维护任务可使用已有内部可信资源键，Actor 操作仍通过 A1；内部维护不伪造 Actor 身份，也不因此开放无授权公共更新入口。

### 4.1 最小存储 mutation 接口

不为 lifecycle、访问、评分和资源策略分别新增专用 DTO 或存储方法。`MidTermStoragePort` 继续承担唯一的 Memory CRUD 和 mutation 入口；`MidTermMemoryStore` 只负责把调用转发到该 Port，不允许调用方绕过 Port 直接访问 Qdrant 或其他具体存储。Port 保留完整原子提交，并增加一个受限的局部 payload patch 原语；现有 `update_access_info()` 迁移为该原语的调用方，完成后从 Port 删除：

```python
async def upsert(
    self,
    memory: MemoryAtom,
    *,
    recompute_vectors: bool = True,
) -> None:
    """提交完整 canonical Memory；必要时重建 embedding。"""

async def patch_payload(
    self,
    key: WorkspaceMemoryKey,
    patch: Mapping[str, Any],
) -> MemoryAtom | None:
    """原子地更新允许的持久化字段并返回更新后的 Memory。"""
```

`patch` 使用 canonical dotted field path 到值的 mapping，由 adapter 映射为后端的局部 payload 更新；一次调用中的所有字段必须对同一资源一起提交。它不是公开的任意字段写入口，只允许：

- `meta.lifecycle.*`：生命周期状态的受控字段；
- `meta.access_policy`：资源读取策略的完整替换。

`meta.version`、`meta.created_at`、`meta.updated_at`、`meta.provenance`、`index.*`、`payload.content`、`payload.agent_config`、`payload.artifacts.*` 和 `relations.*` 不得通过 patch 更新。内容提交、来源变更、Artifact 引用/事件和关系变化都必须构造完整 MemoryAtom，由 `MemoryGenerationFamiliar` 的现有完整写入路径调用 `upsert()` 完成。`patch_payload()` 不增加内容版本、不刷新内容时间、不写 MemoryVersionArtifact，也不重算向量；资源不存在时返回 `None`，存储错误直接传播。

首版不把 `meta.lifecycle.*` 作为无限通配符：adapter 必须逐项白名单校验 `access_count`、`last_accessed_at`、`event_vitality_boost`、`vitality_score`、`confidence_score`、`verification_status` 和 `decay_anchor_at`；值是本次串行提交后的完整替换值，`access_count` 的增量由调用方先基于当前原子计算。`meta.access_policy` 允许整体替换；任何未知路径、类型错误、禁止路径或 Workspace 不匹配都直接拒绝。

`recompute_vectors=False` 只用于完整内容提交中 embedding 输入未变化的情况，例如仅修改 `payload.agent_config`；adapter 必须保留现有向量并替换完整 payload。CREATE、Index embedding 输入变化的内容 UPDATE 和从冷存储重新建立中期点时使用 `True`。生命周期、访问和策略路径必须使用 `patch_payload()`，不能以 `upsert(recompute_vectors=False)` 伪装局部更新。

`MidTermMemoryStore` 负责把同一 patch 转发给已配置的 secondary，并沿现有 primary/secondary 顺序传播存储错误。调用方不新增 mutation result 模型，使用 `MemoryAtom | None` 和现有结构化存储错误。首版不增加资源锁、版本比较、幂等键或提交协调器；`MidTermStoragePort` 仍是所有 Memory CRUD 和局部 mutation 的唯一存储入口。

### 4.2 串行提交假设与内容更新后的状态

首版沿用当前串行写入假设：不提供并发写入合并、乐观锁、自动重试或跨进程一致性保证。调用方不得把 `meta.version` 当作 compare-and-swap 版本；多个写入者同时修改同一资源时，结果不属于 A2-P 的保证范围。协调责任、幂等和重试留待后续独立计划。

- 批量评分和生命周期任务处理其读取到的当前原子；不承诺在另一个写入者同时提交时保留双方增量。
- 内容候选只携带本次内容变更；`MemoryGenerationFamiliar` 在现有完整写入路径中发布当前候选，不能把长任务开始时的整颗旧原子另行写回。内容版本的分配与发布由 Familiar 的 CREATE/UPDATE 路径承担，`MemoryGenerationEngine` 不直接持久化。
- 内容修订继承累计访问与事件状态；由于原有内容更新会重启衰减，目标用推进 `decay_anchor_at` 保留该效果。生成 UPDATE 的置信度重置沿用已有明确规则，人工编辑与验证状态的继承/失效规则须在 MVL-0 逐项列出；只改变经该规则授权的字段，不顺带清空全部 lifecycle。
- 删除、归档与维护在现有串行调用顺序内执行；不额外承诺交错调用的协调结果。

## 5. 完整历史记录

### 5.1 历史结构与捕获时点

MemoryVersionArtifact 保留 memory ID、版本号、来源、changelog 和证据引用等职责。新格式中的原子历史值直接复制捕获时的完整 MemoryAtom JSON 对象及其 schema，不再使用裁剪型 MemoryVersionSnapshot，也不建立第二个快照模型或手工字段映射。Artifact 的 `schema_version` 是独立于 MemoryAtom 的版本轴：本计划目标为 MemoryVersionArtifact schema `"2"`，内嵌 MemoryAtom schema 为 `"2.1"`；`version_number` 仍表示该 Memory 的内容修订号，不能与任一 schema 版本混用。

捕获时点固定为：完成内容候选与最新 lifecycle 合并、确定版本及内容时间之后，追加本次版本记录自身的 refs/events 之前。此时直接复制完整 MemoryAtom 的 canonical JSON 对象并写入历史，随后 canonical 原子增加本次记录引用。这样不产生“记录包含自身 hash”的循环，也不是裁掉原子已有字段。记录已有 ArtifactRef，不递归内嵌它指向的所有 Artifact。历史恢复的是该捕获时点的完整对象，不声称与追加运维引用后的存储字节完全相同。

`snapshot_before` 若保留，来自受控提交时真实的修改前完整原子；`snapshot_after` 保存完整候选。v1 没有 before。嵌套配置、Relations、既有 refs/events 和生命周期均保留。写后不可变，后续统计或配置变化不能修改旧历史。

新 MemoryVersionArtifact 使用区别于旧裁剪格式的 schema（目标 `"2"`）；内嵌 MemoryAtom 使用自身 schema `"2.1"`。复用 ArtifactStore，不创建另一套历史仓库。`snapshot_before` 和 `snapshot_after` 的字段值就是 3.4 节所示的完整 canonical JSON object；Artifact 持久化时将外层 Artifact 与这两个对象一起序列化为 JSON，读取时按内嵌 Memory schema 校验。Artifact 模型不再引用 `MemoryVersionSnapshot`，也不通过循环类型引用 MemoryAtom；快照字段使用受约束的 JSON object 表达，不做无约束的 `Any` 投影。未知字段、缺失必需字段或 schema 不匹配直接拒绝，不退回精简原子。

### 5.2 内容历史与状态时点

历史生命周期仅表示版本捕获时的状态，不是对每次访问的事件溯源。例如 v7 捕获时 access_count=10，当前 v7 已为 30，两份记录仍属于同一内容版本；状态维护不追加 v8，也不改写 v7 历史。

历史读取以相应版本保存的内容为依据。未来 READ 如附带当前评估或当前状态，必须标明时点，不能将当前置信度伪装成历史评估。历史原子中的旧访问策略只是一项历史事实；资源所有者根据当前有效权限授权历史访问，不得恢复旧策略获得读取许可。归档、删除后是否提供历史读取由后续 READ 契约明确，本计划不新增绕过当前授权的公开历史入口。

### 5.3 版本记录与内容提交一致性

新创建/内容修订的成功条件是：完整版本记录已持久化，canonical 原子已发布对应内容版本并关联该记录。`version_number` 与 `meta.version` 一致，记录与原子同属一个 Workspace 和 memory ID。版本历史不是可以在异常时省略的附加日志。

沿现有 `MemoryGenerationFamiliar` 顺序落实：Familiar 先调用 Artifact builder 完成版本记录，再把版本 refs/events 挂载到 MemoryAtom，最后通过 `MidTermMemoryStore` 发布 canonical Memory，并返回成功。两个存储并非同一数据库事务，不能把多个 await 声称为原子事务。

| 失败或中断位置 | 必须成立的结果 |
|:---|:---|
| 版本记录写入失败 | 不发布新 canonical 内容；不能捕获异常后返回无历史的成功 |
| Artifact 成功，canonical 确定未写入 | 旧 canonical 仍有效；未关联 Artifact 不能被当成已经提交的历史版本 |
| canonical 写入失败或提交被取消 | 向调用方传播失败；已写入但未关联的 Artifact 保留为孤立记录，不视为已提交版本，不自动重试或补偿 |
| canonical 已发布，同步读侧协作失败 | 保留真实提交事实并传播协作错误；A2 再按其缓存契约处理失效，不在 A2-P 内重复写入内容 |
| 重启后有孤立 Artifact | 不作为 canonical head；后续运维清理，不在 A2-P 内提供自动恢复 |

本计划不设计同一次提交的自动重试、提交关联 ID 或未决结果模型。调用方收到失败后是否重新发起操作属于后续治理；重新发起可能产生新的 Artifact/版本，A2-P 不承诺幂等合并。

新的内容写入要求版本存储可用。现有 `NoOpMemoryArtifactBuilder` 和捕获异常后继续提交的分支不得再绕过这一条件：未配置或关闭版本存储时，内容 create/update 明确失败；已有资源读取和仅 lifecycle 更新仍可使用。其他可选来源 Artifact 的开关不应被误解释为允许跳过必需版本记录。配置兼容和启动诊断由本计划修改现有配置入口，不要求提前装配 A2 Runtime。

## 6. 交付给 A2 的变更协作契约

本计划在 `MemoryGenerationFamiliar` 的完整内容写入路径和 `MidTermStoragePort.patch_payload()` 的独立状态写入路径上交付可组合的同步读侧协作点，表达资源键、变更类别与已返回的权威结果；无缓存配置时仍能独立工作。可以复用函数/现有组件接口，不为通知包装新增公共路由、provider、总 facade 或裁剪 DTO。异步 RuntimeEvent 只用于观测，不能承担提交正确性。

| 已提交变化 | 本计划保证 | A2 消费方式 |
|:---|:---|:---|
| 内容修订 | 内容版本、完整原子与完整历史一致 | 更新/失效 Atom、alias 及受影响的 Profile 解析结果 |
| lifecycle 更新 | 只更新允许状态，完整原子内容与版本保持；串行提交结果可观察 | 同步刷新完整缓存原子的状态，Profile 解析输入不变则保留；提交失败时按 A2 的缓存错误语义处理 |
| 资源策略更新 | 新 policy 生效且不制造内容版本 | 替换授权依据；源原子无效时解析结果不能单独放行 |
| 删除/归档/复活 | 操作结果及资源可读性明确，不制造内容修订 | 更新可读性与相关索引，阻止旧冷读恢复已失效资源 |

A2 负责运行时 epoch、在途冷读取、缓存失败时的禁用/恢复与 close；本计划不实现 cache，也不提前增加持久化 lifecycle revision。A2 不再重新定义生命周期字段、版本分配、历史格式或 schema 迁移，不把所有 metadata 变化一律处理成内容版本变更或 Profile 重解析。

## 7. 兼容与数据迁移

### 7.1 当前 Memory 数据

结构化 provenance、嵌套 lifecycle、移除 `meta.session_id`、`history_summary` 移除和 `agent_config` 位置调整共同构成持久化结构变化，目标 Memory schema 从旧的整数 `2` 升为字符串 `"2.1"`。A2-P 实现阶段先提供有期限的旧 schema 兼容读取和新格式正式写入；兼容窗口内旧 Memory 原子只允许读取，不由新 mutation 路径回写，避免新旧布局混写。不在 A2-P 尚未完全收口时改写现有生产数据。A2-P 完成后再编写一次性临时迁移脚本，逐条将现有 Memory 原子转换为 `"2.1"`，校验通过后切换为单一新格式并移除临时兼容入口。Artifact 不参加这次迁移：已有 Artifact 保持原 schema 和原始 JSON，等待后续新写入自然产生 schema `"2"`；迁移脚本不得创建、重写、补造或升级任何 Artifact。`meta.session_id` 不做值迁移：生成新 canonical JSON 时直接丢弃旧字段，不映射到其他 Memory 字段，也不提供兼容双写；A3 完成 Session/Interaction 设计后再安排新的承载位置。不能用新模型默认值吞掉其他旧字段，也不恢复已删除的 v1 隐式解释。Memory schema 与 MemoryVersionArtifact schema 独立演进；MemoryVersionArtifact 目标 schema `"2"` 不改变内嵌 Memory 的 `"2.1"`。

- 保持原有 ID、Workspace、内容 version、策略、Index、Payload 和 Relations；平铺 provenance 字段原值迁入 `meta.provenance`，平铺动态字段原值迁入 `meta.lifecycle`，不重新生成向量。
- 旧 `payload.artifacts.agent_config` 迁入 `payload.agent_config`；新旧位置同时存在且值不一致时拒绝，只有新位置进入正式写入。旧 `history_summary` 不写入新模型；迁移报告记录其存在和无法恢复的历史范围，不读取或补造 Artifact 来恢复它。
- 旧 `updated_at` 可能已经被 CITATION 修改。临时 Memory 迁移脚本以旧值初始化 `decay_anchor_at` 保持衰减行为；仅在存在可验证内容版本时间时恢复内容 `updated_at`，否则保留旧值并在迁移报告明确时间语义不确定，不能猜测历史内容时间。
- 元数据重排本身不增加内容版本、不生成伪造内容修改记录。活跃向量 payload、冷存储、备份/导出入口和已有服务消费者都纳入迁移核对。
- 同步调整过滤、排序、编译器、AgentProfile 解析、服务端响应投影和测试 fixture 对新 metadata、`history_summary` 和 `agent_config` 路径的使用。现有外部响应中的平铺展示字段可以由 adapter 从结构化对象映射，不能因此保留两份可写的领域状态。旧过滤参数和旧 schema 读侧兼容窗口须列入 MVL-0 兼容表。
- 新旧字段并存且值冲突、未知 schema、跨 Workspace 数据或 provenance/agent_config 位置冲突必须明确拒绝；不能按字段存在顺序任选。Memory schema `2` 的兼容解码只作为有期限的迁移入口，不允许长期双写。

临时 Memory 迁移脚本在 A2-P 完全完成、实现和测试已冻结后单独编写和执行。脚本只读取并重写 Memory 原子：执行只读预检、备份、暂停受影响写入、转换、校验、恢复写入与报告；必须可断点核对和安全重跑，记录已转换/失败/无法完整恢复的范围。脚本不得读取后重写 Artifact，不得为现有原子补造 MemoryVersionArtifact 或 MemoryCreationArtifact。回滚先恢复与旧程序匹配的 Memory 备份；旧 Artifact 数据保持原样。脚本执行完成并核验后，删除临时脚本或将其移入归档，不作为运行时依赖。

### 7.2 旧 Artifact 与历史边界

旧 MemoryVersionArtifact schema `"1"` 和其他已有 Artifact 保持原始 schema、字段布局和 JSON，不参加 A2-P 后的 Memory 临时迁移。若现有 READ 或运维工具需要读取它们，使用按 schema 区分的只读解码并明确其完整性；不得把缺失配置/Relations/`agent_config` 填成默认值后声称完整，不得把 `MemoryVersionSnapshot` 升级标记后伪装成完整原子，也不得把旧平铺 provenance 写回成 schema `"2"`。新 Artifact schema `"2"` 只由 A2-P 完成后的新内容写入产生。

现有 Memory 原子即使没有完整版本记录，临时迁移脚本也只转换该原子本身，不生成合成的基线 Artifact，不递增内容版本，不改写旧 Artifact。迁移后的原子从后续首次实际内容修订开始，由正常 `MemoryGenerationFamiliar` 路径按新 schema `"2"` 创建版本记录；迁移前的历史缺口继续按旧 Artifact 的可用性和完整性表达，不能承诺恢复。

### MVL-0 边界冻结结论

本节是 MVL-0 的冻结交付物，实施以本节为准。时间字段（owner、当前表示、目标类型、更新触发、旧数据迁移、跨重启）的逐字段清单由[时间边界计划附录 A](./v0.7.0-time-semantics-and-controllable-clock.md) 承接并同样对本计划全部切片生效，此处不复制，两处冲突时以时间边界计划为准。

**M0.1 逐字段 mutation 分类与现有写入者**

| 字段（目标位置） | 类别 | 现有写入者（2026-09-22 代码证据） | 目标写入边界 |
|:---|:---|:---|:---|
| `meta.created_at` | 内容事实 | default_factory；创建提交路径 | 仅 `MemoryGenerationFamiliar` CREATE 路径在提交边界赋值（一次 now） |
| `meta.updated_at` | 内容事实 | engines/generation/engine.py（:328/:351/:399 naive）、patchouli/services/memory_generation.py:139（UTC）、engines/lifecycle/reinforcement.py:161（CITATION 违规写点）、mid_term adapter 整颗写回 | 仅 Familiar CREATE/UPDATE 提交边界赋值；reinforcement 与 adapter 写点随 MVL-2 移除 |
| `meta.version` | 内容事实 | engine.py:353、memory_generation.py:140（artifacts/memory.py:99 是读取方，填入 Artifact 的 `version_number`） | 仅 Familiar CREATE/UPDATE 提交边界分配；不充当比较交换锁 |
| `meta.provenance` | 治理元数据 | 现 MetaData 平铺字段（创建路径）与 generation engine 构造 | 结构化迁移；`contributing_agent_ids` 仅随受控内容提交合并，不单独成版本 |
| `meta.lifecycle.*`（7 个白名单字段） | 动态状态 | reinforcement.py:125-130（HIT/CITATION/反馈）、mid_term.py:113-114（访问计数）、engines/lifecycle/engine.py:55（refresh） | 仅 `patch_payload()` 白名单路径；MVL-2 后禁止整原子 upsert 回写 |
| `meta.access_policy` | 资源策略 | 创建路径（`MemoryAccessPolicy.public()`，system/application/memory_service.py:86） | `patch_payload()` 整体替换；当前无其他写入方 |
| `payload.content` / `index.*` / `payload.agent_config` / `relations.*` | 内容事实 | engine 内容合并、外部编辑、创建路径 | 仅 Familiar 完整写入（`upsert()`）；`agent_config` 单独更新用 `recompute_vectors=False` |
| `payload.artifacts.*`（refs/events/归档定位） | 运维引用 | Familiar 挂载（memory_generation.py:449-473）、MemoryLibrary（library.py:74/:93） | append-only；不触发内容版本 |

**M0.2 内容更新操作的置信度/验证状态规则（沿用现有明确规则）**

- CREATE：`confidence_score` = 草稿值（fallback 草稿固定 1.0，engine.py:223/:529）；`verification_status` = UNVERIFIED。
- UPDATE（含外部编辑与 dedup merge）：`confidence_score` 重置 1.0（engine.py:352 现状保留为规则）；`verification_status` 不变。
- NEG 反馈：`confidence_score` × 0.5、下限 0（reinforcement.py:164-168 现状保留），经 lifecycle patch 提交。
- HIT/CITATION/TOUCH/评分刷新：不改 confidence 与 verification。
- `verification_status` 当前全仓库无写入方（恒 UNVERIFIED）；本计划不新增写入规则。

**M0.3 顺序失败传播契约（§5.3 表的代码落点）**

- 版本 Artifact builder 失败（含版本存储未配置/禁用）：Familiar 不得调用 `upsert()`，错误向调用方传播；不得捕获后返回无历史成功。
- canonical `upsert()` 失败或提交被取消：错误传播；已写入 Artifact 保留为孤立记录，不视为已提交版本。
- `patch_payload()`：资源不存在返回 `None`；存储错误直接传播。
- 删除/归档/复活：按现有串行顺序执行；同步协作点回调失败随操作错误一起传播，不静默吞掉。

**M0.4 兼容表**

| 数据 | 兼容窗口内策略 | 出口条件 |
|:---|:---|:---|
| Memory schema 整数 `2` | codec 只读解码（平铺→聚合、`agent_config` 移位、丢弃 `session_id`/`history_summary`，冲突拒绝）；`get_for_mutation` 与 `patch_payload` 对旧记录拒绝——旧记录只读，不由新 mutation 回写 | A2-P 验收后一次性临时脚本转换为 `"2.1"`；完成后移除兼容入口 |
| MemoryVersionArtifact / MemoryCreationArtifact 旧 schema `"1"` | 永久只读原样，按 schema 区分的只读解码；不升级、不补值、不补造 | 无；schema `"2"` 仅由新内容写入产生 |
| InteractionArtifact / DocumentArtifact schema `"1"` | 布局不变；仅新写入的时间值转 UTC-aware | 保持 `"1"`，不参与版本轴变更 |

**M0.5 补充实施决定**

1. `MemoryVersionArtifact` 与 `MemoryCreationArtifact` 都升 schema `"2"`（结构化 provenance + 完整原子快照），共享独立于 Memory 的 Artifact schema 轴。
2. TOUCH（内容相同的重复访问）从"改 `updated_at` + 整颗 upsert"改为 lifecycle patch：`access_count` +1、`last_accessed_at` = patch 路径 now；不推进 `decay_anchor_at`、不改 `updated_at`、不升版本、不写版本 Artifact、不重算向量。
3. 旧 schema 只读的统一拒绝点：adapter 的 `get_for_mutation` 与 `patch_payload` 在存储侧检查原始 payload 的 `schema_version`。
4. 当前不存在策略更新调用方（access_policy 仅创建时设置）；MVL-2 只交付 `patch_payload` 对 `meta.access_policy` 的白名单支持，不新增公共策略修改 API。
5. 删除/归档/复活与内容写入、状态 patch 的同步读侧协作点复用 `workspace/projections.py` 的 `CanonicalResourceChange` 形状，以可注入回调列表实现；无缓存配置时默认空列表 no-op。

## 9. 测试与验收

遵循[测试设计规范](../governance/testing/test-design-standards.md)。测试保护持久化、版本、失败传播和权限边界，不以字段赋值、类名或目录数量作为证据。时钟可控；本计划不新增并发或自动重试测试。

| 场景 | 必须观测的结果 |
|:---|:---|
| HIT、CITATION、正负反馈、评分刷新与批量 GC 前评分 | 正确动态状态落库；内容、version、内容时间和历史记录不变；无需可用 embedding 即可完成状态更新 |
| 顺序执行的访问、评分、内容修订与反馈 | 各操作只改变其授权字段；内容修订生成一个新版本，Lifecycle 更新不生成版本 |
| 无变化更新、agent_config/Relations/Index 修改 | 无变化不增版本；真实内容变化生成完整可重建的新版本，嵌套配置保留 |
| 历史记录后继续使用记忆或修改返回对象 | 历史完整值不变；当前状态正常推进；嵌套对象无共享引用污染 |
| Artifact 失败、canonical 写入失败和取消 | 失败向调用方传播；无历史的新内容不成功；孤立记录不成为 head；不验证自动重试或幂等 |
| 顺序执行的归档/复活/删除与状态维护 | 内容版本保持；完整结构跨层保存，维护不恢复已删除资源 |
| A2-P 完成后的临时 Memory 迁移脚本 | 仅将旧 Memory 原子转换为 schema `"2.1"`，移除 `meta.session_id`，完成 provenance/lifecycle/`agent_config` 布局转换；当前内容及向量不变，冲突输入拒绝，安全重跑不重复改写；旧 Artifact 不读取、不改写、不补造 |
| 两个 Workspace 中的资源及 Artifact 引用 | 版本、状态与提交关联不串扰；历史旧 policy 不成为新授权依据 |
| 局部 mutation 接口 | lifecycle/策略 patch 只改变白名单字段，不增加内容版本、不改向量；`upsert(recompute_vectors=False)` 保留向量；secondary 协作遵循统一失败策略 |

unit 覆盖确定性状态规则、schema/完整性判断、完整内容写入和独立 Lifecycle patch 行为；integration 使用真实 generation/lifecycle、MemoryLibrary、Artifact builder/codec 和临时文件存储验证协作。外部模型可替换，不能 mock 掉声称被验证的内部提交链。实际 Qdrant 局部更新与向量保留需 `integration + real_infra` 证据；未运行时明确作为待验收项，不能用内存 store 宣称数据库契约已验证。不要求 live LLM 才能验证本次重构。

A2-P 独立验收不依赖缓存存在：验证真实资源写入和同步协作点，A2 再验证命中状态更新、Profile 保留及 epoch 防旧回填。实际运行命令在实现时按 `pyproject.toml` 与 CI 配置选取，不预写未经核对的测试命令。临时 Memory 迁移脚本在 A2-P 完全验收后单独执行，不作为实现阶段的伪成功证据。

## 10. 风险、交接与收口

主要风险是跨存储提交并非事务、旧历史不可恢复、字段迁移漏掉过滤/冷存储消费者，以及失败后留下孤立 Artifact。MVL-0 需要冻结的具体实现决定为：各内容更新操作的置信度/验证状态规则、顺序失败传播、旧 schema 与旧 Artifact 的只读兼容窗口；不为本计划增加并发协调、自动重试或幂等协议。A2-P 完全完成后，临时脚本另行核对 Memory 原子转换结果，不把旧 Artifact 迁移或补造基线混入本计划。

交付 A2 的清单必须包含新 schema/完整原子样例（含 `payload.agent_config`）、`upsert(recompute_vectors=...)` 与受限 `patch_payload()` 的正式入口、patch 白名单和向量保留保证、同步读侧协作契约、失败后可读性、当前写入者覆盖与迁移结果。A2 消费这些数据完成公共读取和缓存维护，不重新引入已由 A2-P 删除的 `MemorySnapshot`，也不把 `ProfileSnapshot`、内容 version 乐观锁或 lifecycle 整原子 upsert 重新作为 A2-P 的替代品；列表/AgentProfile 返回与旧 envelope 迁移由其独立验收。

交付后续 READ 的清单包括完整版本定位与有效关联、历史原子解码、旧裁剪/缺失辨认、捕获时间语义和当前资源授权要求。历史编译与协议呈现后置，可靠历史的保存和读取基础不能后置。

仅在实现、测试、审查和本计划验收完成后，按[文档治理](../DOCUMENTATION.md)更新 frontmatter 中列出的事实文档，将本计划归档，并同步 A2、计划协调入口、plans/README 与 ROADMAP。随后再编写并执行一次性的 Memory 原子迁移脚本；该脚本不迁移 Artifact，执行报告单独留存。本次制定计划不修改当前架构事实、ADR-0004 状态或 A1 的已完成结论。
