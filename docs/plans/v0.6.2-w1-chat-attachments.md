# v0.6.2 W1：Chat Attachments

本文是建立在 v0.6.2 W0 Workspace MVP 之上的初步实施计划框架，覆盖附件从上传、解析、表示可用，到用户在 Chat 中选择并编译进上下文，再到 Interaction binding 和按需 Artifact promotion 的完整链路。

计划按六步拆分组织：W1-A 至 W1-C 对应上传、确定性解析和 representation `READY`；W1-D 至 W1-F 对应 ref 选择与后端交接、上下文编译，以及对话成功后的 Topic/Materialization 流转。

本文以当前代码和已经归档的 W0 Plan 为事实基线。Idea 文档中与当前实现冲突的内容以当前实现为准；尚未冻结的 API 字段、解析器实现方式和 Artifact 映射在本计划的开放问题关闭前不得作为公共契约使用。

## 1. 背景与问题

W0 已经建立 System-owned 的进程内 `WorkspaceAssetStore`，以及 `WorkspaceAsset`、`AssetRepresentation`、opaque `WorkspaceAssetRef`、READY-only 使用、删除和 lease 语义。W0 明确不实现真实上传、解析、Context Compiler 和 Artifact promotion。

当前 Chat 还缺少一条完整的附件工作流：用户上传文件后，系统不能稳定地产生可用的文字 representation，Chat 也不能把用户显式选择的 attachment ref 纳入上下文，更不能在成功 Interaction 后保留真实使用关系和来源证据。

本计划首先解决附件作为 Workspace 运行时资产的生命周期和用户选择后的上下文使用。它不把附件直接视为 Memory，也不把上传动作解释为 Topic binding 或 Artifact creation。

## 2. 目标

本计划完成以下闭环：

```text
upload
  -> WorkspaceAsset + opaque ref
  -> RAW representation
  -> deterministic parser
  -> EXTRACTED_TEXT representation READY / FAILED
  -> user selects ref
  -> resolve + acquire READY representation
  -> Context Compiler
  -> successful Interaction commit
  -> TopicAssetBinding
  -> optional Materialization Artifact promotion
```

具体目标：

1. 提供 Chat 附件上传入口，创建属于当前 Workspace 的 `WorkspaceAsset` 并返回进程内 opaque ref；
2. 建立确定性解析器的窄接口和第一方实现，解析器只消费明确的 RAW representation；
3. 通过 `WorkspaceAssetStore` 的命令完成 representation 与 asset 聚合状态迁移；
4. 支持用户显式选择、重复使用和取消选择附件；
5. 将实际选择的 READY representation 编译为本轮 Agent 上下文，并保留 revision、hash、locator 和编译诊断；
6. 在 Interaction 成功完成后，以现有 Topic 所有者流程建立 `TopicAssetBinding`；
7. 在 Materialization 阶段按冻结的 representation ref、revision 和 hash 进行可选 Artifact promotion，并保持 retry 幂等；
8. 为 remove、lease、解析失败、无效 ref、编译失败和 representation 版本变化提供稳定失败语义。

## 3. 非目标

本计划不包含：

- Agent 通过 MTP `RUN` 自主决定页码、区域或解析操作；
- MemoryCompiler 的 `RUNNABLE_TOOL` target 实现；
- Memory 内容直接执行、Memory-backed Plugin 或任意用户代码执行；
- 外部 parser package、Provider Registry、插件安装和插件生命周期；
- 强隔离沙箱、网络/进程权限降级、跨重启恢复和分布式任务执行；
- OCR、图像、多模态输入和图像记忆化；
- WorkspaceAsset 的持久化、跨进程共享、对象存储、保留策略和垃圾回收；
- 新增 MemoryType，或改变 Memory schema v2 的 ownership、visibility 和 lifecycle 语义；
- 上传、选择或普通 Context 编译自动创建 Topic binding 或 Artifact。

PDF 是否进入本计划的首个可用格式集合，需要通过解析器依赖和资源限制门槛后裁定。若当前环境不能安全处理 PDF，首个交付至少支持纯文本或 Markdown，并保留同一 parser port 供后续 PDF 实现接入。

## 4. 当前状态与缺口

### 4.1 已成立的实现基础

- `WorkspaceIdentity`、`IdentityScope` 和 Workspace-owned resource 边界已经成立；
- `WorkspaceAssetStore` 是 System 进程级唯一 working set；
- `WorkspaceAsset` 聚合已有 `PROCESSING`、`READY`、`FAILED`、`REMOVED` 状态；单个 `AssetRepresentation` 已有 `PENDING`、`PROCESSING`、`READY`、`FAILED` 状态，`REMOVED` 只属于 asset 聚合；
- `WorkspaceAssetRef` 是当前 Store 存活期内 opaque token，不是物理路径、永久 ID 或授权凭证；
- READY representation 的读取通过 reader port 建立 lease，并在消费期间保持有效；
- Topic binding 由 Patchouli Perception 的 Topic 所有者在成功 Interaction 后提交；
- `PerceptionFamiliar.apply_interaction` 与 `TopicData` 合并逻辑已经支持接收 `(asset_id, asset_ref)`，但当前 `InteractionPayload`、`InteractionSubmission` 和 `PatchouliService.finalize_agent_run` 尚未把这份附件选择接入主动 Chat 的完整链路；
- Artifact、DocumentArtifact 和 Memory generation provenance 基础已经存在，但完整附件摄入和 promotion 尚未接入；
- 当前 MTP `RUN` 只处理 Kernel syscall 和 `CODE_SNIPPET`，不能作为本计划的通用 parser 执行环境。

### 4.2 本计划需要补齐的能力

| 缺口 | 责任边界 | 结果 |
|:---|:---|:---|
| 上传入口与请求响应 | Chat/System | 资产创建、元数据校验、opaque ref 返回 |
| RAW 内容接入 | System WorkspaceAssetStore | RAW representation READY |
| 确定性解析器 | System parser adapter | 解析结果或安全错误摘要 |
| 表示状态提交 | WorkspaceAssetStore | representation 与 asset 聚合状态原子落定 |
| 选择和解析 | Chat/System | ref 按 scope 解析并 acquire lease |
| 附件使用交接 | Chat/Patchouli submission | 将已校验的 asset ref 从 Chat 传到 Interaction apply，并保留 canonical/retry 语义 |
| Context Compiler | Chat 上下文组装边界 | 局部内容、预算、locator 和诊断 |
| Interaction binding | Patchouli Perception | 成功使用后的 TopicAssetBinding |
| Artifact promotion | Patchouli Materialization | 冻结来源快照，按需生成 Artifact |

## 5. 目标数据流与所有权

```text
Chat upload request
  -> System WorkspaceAssetStore
  -> WorkspaceAsset + RAW representation
  -> parser adapter
  -> WorkspaceAssetStore complete/fail command
  -> Chat selection of WorkspaceAssetRef
  -> IdentityScope resolve + READY representation lease
  -> Context Compiler
  -> Chat Interaction
  -> Patchouli TopicData commit
  -> Materialization task
  -> optional source Artifact promotion
```

| 资产或行为 | 权威所有者 | 本计划的边界 |
|:---|:---|:---|
| WorkspaceAsset、representation、opaque ref、lease | System `WorkspaceAssetStore` | 复用 W0 port 和命令，不复制第二套状态机 |
| 上传请求和用户选择 | Chat/System application | 只提交显式选择，不推测 Topic 关系 |
| parser 调用 | System parser adapter | 只允许本计划规定的确定性第一方实现 |
| Context 编译结果 | Chat 上下文组装流程 | 使用 reader port，不直接访问 Store 私有状态 |
| TopicAssetBinding | Patchouli Perception / Topic owner | 只在成功 Interaction commit 中建立 |
| Materialization promotion | Patchouli generation/artifact flow | 使用 task 冻结的 ref、revision、hash |
| Agent 主动解析和外部 Plugin | 后续 Alice/MTP 执行能力 | 不属于本计划 |

本文所说的附件 `Context Compiler` 是待实现的附件上下文组装步骤。当前 Patchouli `MemoryCompiler` 负责 `MemoryAtom` 的既有 target；W1-E 必须明确二者是扩展同一编译边界还是由独立组件承载，不能因为名称相近就改变现有 `MemoryCompiler` 的职责。

## 6. W1-A：上传与 WorkspaceAsset 注册

W1-A 只负责把浏览器中的一个文件接收到当前 `IdentityScope` 对应的
`WorkspaceAssetStore`，并形成一个带 opaque ref 的逻辑资产和一个初始 RAW
representation。它不负责解析文本，也不把 RAW `READY` 误认为资产已经可供 Chat
使用：文档资产的 required representation 是 `EXTRACTED_TEXT`，因此在 W1-B/W1-C
完成前，asset 聚合仍可处于 `PROCESSING`。

#### A1. HTTP 入口与应用服务

采用独立的上传应用服务承接 HTTP 与 Store 之间的边界，router 不直接编排多个 Store
命令。建议的代码落点为：

- `src/hivememory/server/routers/workspace_assets.py`：注册
  `POST /api/v1/workspace/assets`，解析统一的 `x-user-id` / `x-workspace-id` 请求头，
  并调用应用服务；
- `src/hivememory/server/models/workspace_asset.py`：定义上传结果和 representation
  摘要 DTO，不把领域模型或原始内容直接暴露为 HTTP 契约；
- `src/hivememory/system/application/workspace_asset_service.py`：执行身份作用域下的
  校验、受限读取、哈希计算和上传专用 Store 命令；
- `src/hivememory/server/deps.py`、`src/hivememory/system/assembler.py` 和
  `src/hivememory/server/app.py`：装配并注入进程级唯一的上传服务和路由。

请求契约冻结为单文件 `multipart/form-data`：

- 文件字段名为 `file`，一个请求只处理一个文件；多文件拖入由前端建立逐文件队列；
- 请求头 `Idempotency-Key` 是本次上传的稳定 operation identity，服务层将其映射为
  当前 Store 的 `client_operation_id`；同一文件重试必须沿用同一个值；
- 用户和 Workspace 仍只由现有统一身份请求头表达，上传 body 不重复携带身份字段；
- 采用 FastAPI `UploadFile` 时，在 `pyproject.toml` 增加 `python-multipart` 运行依赖，
  并在服务启动或测试环境验证 multipart 解析可用。

路由只负责 HTTP 解析、依赖注入和错误翻译。默认身份回退仍由
`resolve_request_identity_scope` 完成，应用服务接收已经冻结的 `IdentityScope`，不得
再次从文件字段或 body 推导 Workspace。

#### A2. 文件校验与受限接收

应用服务在创建 asset 前完成所有不会产生副作用的输入校验：

- 拒绝空文件；
- 对文件名做 Unicode/空白规范化，去除路径分隔符和控制字符，并限制长度；文件名只
  作为 `display_name`，不能成为 Store 寻址或物理路径；
- 使用服务端允许的媒体类型/扩展名集合；客户端提供的 MIME 只能作为提示，不能作为
  唯一判断依据；该集合必须与 W1-B parser 的批准格式集合保持一致，PDF 是否属于首轮
 允许集合在 parser 依赖和资源门槛通过后冻结；
- 以配置的最大字节数为硬上限，分块读取并计算 SHA-256，使用有界内存缓冲或受控的
  spool；不得对 `UploadFile` 做无上限的一次性 `read()`，也不得先创建没有内容的孤儿
  asset；
- `size_bytes` 使用实际读取字节数，`content_hash` 使用实际 bytes 计算；编码探测和
  文本解码属于 W1-B parser，不在上传路由内偷偷完成。

读取完成后，服务层只向 Store 提交不可变 bytes、规范化 metadata、content hash、稳定
的 upload producer 名称和 producer version。服务层和 router 都不能保存物理临时路径，
也不能把原始 bytes 写入日志、错误 message 或 HTTP 响应。

#### A3. Asset 与 RAW 的原子注册

当前 `create_asset` 和 `register_raw_representation` 分别持有幂等和内容写入的一半
语义：前者只按 metadata 比较，后者没有 upload operation identity。W1-A 必须扩展
`WorkspaceAssetCommandPort`/`InMemoryWorkspaceAssetStore`，增加一个上传专用的等价原子
命令（名称可按代码风格确定，例如 `register_uploaded_asset`），一次完成：

1. 在 `IdentityScope` 下检查 Store 未关闭，并以 `(workspace_identity, client_operation_id)`
   定位幂等记录；
2. 将 metadata 与原始 content hash 纳入 operation fingerprint；相同 operation 重放且
   fingerprint 相同，返回原先的同一 `WorkspaceAssetHandle`；fingerprint 不同，返回
   `workspace.asset.operation_conflict`，不能创建第二个 asset；
3. 创建一个新的 `WorkspaceAsset` 和一个当前 Store 生命周期内有效的
   `WorkspaceAssetRef`；
4. 注册 `RAW`、revision `1`、状态 `READY` 的 representation，并冻结 bytes；
5. 根据 `required_representation_kind` 更新 asset 聚合状态。对文档资产，RAW 不满足
   `EXTRACTED_TEXT`，所以聚合保持 `PROCESSING`；只有 required representation 后续进入
   `READY` 才能转为 asset `READY`。

上述步骤必须在 Store 的同一临界区内线性化。router 或应用服务不得先调用
`create_asset`、再调用 `register_raw_representation` 并自行猜测失败补偿；若实现选择
其他命名，必须保留同样的原子性、Workspace 隔离和重放语义。上传 operation 的幂等记录
应能区分“同一 operation 的同一内容重试”和“同一 operation 携带了另一份文件”，不能
只比较文件名或客户端 MIME。

#### A4. HTTP 响应与错误语义

首次创建返回 `201`，同一 `Idempotency-Key` 且 fingerprint 相同的重放返回同一逻辑资产
（可用 `200` 表示 replay，但响应 DTO 必须相同）。响应至少包含：

- `asset_ref`：opaque ref 的序列化值；
- `asset_id`、`display_name`、`media_type`、`size_bytes` 和 asset `state`；
- RAW representation 的 `representation_id`、`revision`、`state`、`content_hash`、
  `producer` 和 `producer_version`；
- 表示当前 asset 是否仍在 `PROCESSING` 的可观察字段，供前端显示“已上传/处理中”。

响应不得包含原始 bytes、绝对路径、Store 内部对象、未过滤的异常文本或可被当作永久
授权凭证的 ref 解释。错误按当前 HTTP router 的局部翻译方式返回，并在
`docs/contracts/error-model.md` 和 `docs/contracts/routes-and-events.md` 中登记稳定机器
类别。至少要能区分：缺少/非法文件元数据（`400`）、大小超限（`413`）、不支持的媒体类型
（`415`）、同一 operation 输入冲突（`409`）、Store 已关闭或运行时不可用（`503`），以及
当前 Workspace 不匹配或 scope 缺失。错误 message 只返回安全摘要，不能泄露临时路径或
解析栈。

上传成功只表示 RAW 已注册：不自动创建 TopicAssetBinding、Interaction、Context
AttachmentUse 或 Artifact，也不把新 asset 自动附加到当前消息。用户必须在后续 W1-D
明确选择该 ref；required representation 尚未 `READY` 时，前端不得把它列为可用附件。

#### A5. Chat 工作区与 composer 的文件入口

`ChatWorkspace`、`OmniInput` 和附件选择对话框共用同一份“文件进入上传队列”逻辑，避免
三个入口产生不同的校验和状态：

- 在当前 Chat 页面工作区监听 `dragenter`、`dragover`、`dragleave` 和 `drop`，拖入文件时
  显示明确的 drop 状态；所有 drag/drop handler 都 `preventDefault`，避免浏览器直接打开
  文件；只接收 `DataTransfer.files`，目录和无文件 payload 直接忽略；
- composer 的 Paperclip 按钮打开隐藏的 `<input type="file">`，并提供键盘可达的选择
  方式；对话框中的 drop 与页面 drop 进入同一处理器；通过事件归属或传播控制，避免同一
  文件被工作区和 composer 重复入队；
- 一次上传请求只发送一个文件。多文件拖入后按照文件顺序建立队列，W1-A 默认逐项提交，
  每项拥有独立的 `queued`、`uploading`、`uploaded`、`failed` 状态和重试入口；
- 文件首次进入队列时生成稳定 operation ID，重试沿用该 ID；成功响应中的 opaque ref
  只保存在当前运行时的附件状态中，不写入 `localStorage`，不持久化 raw bytes，也不把
  ref 当作本地路径；
- 上传是独立于 Chat SSE run 的资产命令，可以在生成期间继续接收文件，但不会修改已经
  开始的 run。当前 Paperclip 在 `isStreaming` 时默认禁用，需在实现时移除该限制或把上传
  入口移到仍可用的工作区区域，并用测试证明两种操作不会互相取消；
- `uploaded` 只表示服务端已返回 asset/RAW 摘要。前端可显示“处理中”，但在 W1-C 收到
  required representation `READY` 之前，不得把该项作为 Chat 选择器中的可用附件；单项
  上传失败只清理该项的临时状态，不影响同一队列中的其他文件和当前对话。

建议新增 `frontend/src/services/attachmentApi.ts` 负责 `FormData`、
`identityHeaders()` 和 `Idempotency-Key`；不要手工设置 multipart 的 `Content-Type`，让
浏览器生成 boundary。附件运行态可由独立的非持久化 store 承载，或由 Chat store 的
非持久化 slice 承载，但必须明确 ref 的生命周期，不得沿用当前 Chat store 仅持久化 Agent
选择的配置语义。

#### A6. W1-A 联调顺序

1. 前端将拖入/选择的文件规范化为队列项并生成 operation ID；
2. `attachmentApi` 以 `multipart/form-data` 调用上传路由，附带统一身份请求头和
   `Idempotency-Key`；
3. router 解析请求并冻结 `IdentityScope`，应用服务执行大小、文件名和媒体类型校验，
   分块读取并计算实际 hash；
4. 上传专用 Store 命令在一次临界区内创建 asset、生成 ref 和注册 RAW；
5. 服务返回安全 DTO，前端将该项标记为 `uploaded` 或 `failed`；
6. W1-A 的联调只验证 ref 返回、Workspace 隔离、RAW revision/hash 和幂等重放；解析
   `EXTRACTED_TEXT`、Chat 选择与 Context 编译分别由 W1-B 至 W1-E 验收。

#### A7. W1-A 阶段验收

- 页面工作区、composer 和附件对话框的拖拽/点击入口都进入同一逐文件上传流程，浏览器不会
  因 drop 导航或打开文件；
- 一个合规文件的上传能在所属 Workspace 创建一个 asset、一个 RAW `READY` representation
  和一个 opaque ref；文档 asset 在 required text 尚未生成时保持 `PROCESSING`；
- 相同 Workspace、相同 `Idempotency-Key` 和相同文件内容的重试不会生成重复 asset 或
  重复 RAW；相同 key 携带不同 metadata、size 或 hash 会稳定返回冲突；
- 不同 Workspace 即使使用相同文件名和 operation ID 也完全隔离，跨 Workspace 使用 ref
  得到统一的 not-found/mismatch 结果；
- 空文件、非法/过长文件名、超限文件、不支持媒体类型、Store 关闭和上传冲突都有稳定的
  HTTP 状态与前端可见提示；
- 响应和日志不包含 raw bytes、物理路径或内部异常栈；前端不持久化 raw bytes 或 opaque
  ref；
- 上传成功不会创建 TopicAssetBinding、Interaction 或 Artifact，且不会把附件偷偷加入
  当前 Chat run；
- W1-A 的 unit、integration 和最小 browser/e2e 测试覆盖队列状态、drop 行为、Store 原子
  注册、幂等重放和 Workspace 隔离；异步上传使用事件或有界等待，不使用固定 sleep。

## 7. W1-B：确定性解析器

W1-B 将 W1-A 产生的 RAW representation 转换为供后续上下文编译使用的确定性表示。
解析器属于 System 侧的 parser adapter，不直接改变 `WorkspaceAsset`，也不通过
MTP `RUN`、MemoryCompiler 或外部 Plugin 执行。

### 7.1 输入边界

- parser 只能接收由 `WorkspaceAssetReaderPort` 读取的、属于当前 `IdentityScope` 的
  RAW `READY` representation；
- 输入快照必须包含 asset ref、asset id、representation id、revision、content hash、
  media type、display name 和原始 bytes；parser 不从文件名推断 Workspace，也不读取
  物理路径；
- parser adapter 需要有明确的 producer name 和 producer version，调用方据此区分
  解析实现变更；相同 RAW revision、parser version 和配置应产生相同的输出或相同的
  安全错误类别。

### 7.2 输出边界

解析成功返回可冻结的内容对象、content hash、producer、producer version 和必要的
locator 元数据。解析失败只返回 `AssetSafeError` 所允许的 code/message 摘要，不把
traceback、临时路径或原始内容带入 WorkspaceAsset。解析器输出通过 W1-C 的 Store 命令
提交，不能持有或修改 Store 内部对象。

首个批准格式集合需要在实现前冻结。纯文本和 Markdown 可作为低依赖基线；PDF 是否进入
W1 首轮，取决于解析库、资源上限和不受信任输入评估。若 PDF 需要沙箱、原生库或更高
配额，则保留同一 parser port，延后接入而不改变 RAW 和 representation 契约。未批准格式
返回稳定的 unsupported 错误，不回退为猜测性文本读取。

### 7.3 幂等与资源边界

解析调用使用独立的 parse operation identity，不复用上传 operation。相同 RAW revision
和 parser version 的重试不得生成多个有效 representation；不同输入 revision 或 parser
version 的结果不能覆盖已经提交的版本。实现需要限制解析耗时、输出字节数和中间内存，
并在超限时返回可分类的失败摘要。

## 8. W1-C：Representation 状态与 Asset 可用性

W1-C 负责把 parser 结果安全地提交回 `WorkspaceAssetStore`，并决定 asset 何时可以被
Chat 使用。它是 representation 状态迁移和 asset 聚合状态迁移的唯一提交边界。

### 8.1 状态流程

对文档 asset，Store 先注册 `EXTRACTED_TEXT` representation 为 `PENDING`，随后以
parse operation token 启动为 `PROCESSING`。解析成功时通过 revision/token guard 提交
冻结内容和 content hash，representation 进入 `READY`，required representation 满足后
asset 聚合进入 `READY`。解析失败时 representation 和 asset 按既有 Store 失败语义进入
`FAILED`，只保留安全错误摘要。

RAW representation 在 W1-A 中已经是 `READY`，但它不替代文档所需的
`EXTRACTED_TEXT`。因此 W1-C 不能仅凭 RAW 存在就开放 Chat 选择。

### 8.2 原子提交与过期结果

完成和失败命令必须在同一 Store 临界区中检查 asset 未被 remove、representation 仍处于
`PROCESSING`，并匹配预期 revision 或 parse operation token。过期、重复或来自另一轮解析
的结果返回 `workspace.asset.stale_result`，不得覆盖当前表示。representation 提交和 asset
聚合状态更新必须作为一次线性化操作完成，避免出现 representation 已 READY 而 asset 仍
错误标记为可用，或反向的半完成状态。

### 8.3 可用性与失败恢复

只有 required representation `READY` 的 asset ref 才能进入 W1-D。解析失败不在本计划中
自动无限重试；前端应展示稳定失败摘要，用户重新上传形成新的逻辑资产。asset remove、
Store shutdown 和 required representation 未就绪都必须保留既有稳定错误语义。

## 9. W1-D：Chat 选择、resolve 与 lease

W1-D 将用户在 Chat 中选择的附件交接给主动对话请求。选择本身不是 Topic binding，也
不应因为上传顺序、当前 Topic 或最近资产列表而被系统隐式推导。

### 9.1 选择模型

前端提交 opaque `WorkspaceAssetRef`，可同时提交用户选择的 representation 标识、预期
revision 和 content hash。后端以当前 `IdentityScope` 重新 resolve ref，并确认 asset、
representation、required 状态和 revision/hash 一致；客户端不能提交物理路径、任意内容
或跨 Workspace 的 asset id 作为替代。

同一轮请求中重复选择同一 asset/representation 的去重规则必须明确并写入请求的
canonical 表示；取消选择意味着该 ref 不进入本轮 Context Compiler，不产生 binding。新
上传的 asset 只有在 required representation `READY` 后才出现在可选列表。

### 9.2 Chat 到 Interaction 的交接

通过校验的 `(asset_id, asset_ref)` 以及必要的 representation revision/hash 作为本轮
finalize 的显式输入，沿 `InteractionSubmission`/Perception apply path 传递，并纳入
canonical codec 和 retry digest。handler 不得在提交时重新查询“当前选中的附件”或根据
同名文件重新推导关系，否则重试可能替换原始来源。

在 Context 编译和 Interaction 使用期间持有 representation lease。remove 早于 acquire
时，本轮附件使用失败且不建立 binding；acquire 早于 remove 时，已有 lease 按既有语义
完成本轮使用，但后续 resolve/acquire 必须拒绝该 ref。

## 10. W1-E：Context Compiler

W1-E 将 W1-D 已验证的 representation 内容编译为当前 Agent 请求的上下文片段。它是
附件上下文组装边界，不拥有 WorkspaceAsset 生命周期，也不改变现有 Patchouli
`MemoryCompiler` 对 `MemoryAtom` target 的职责。

### 10.1 输入与输出

Compiler 输入包括一个或多个已 acquire 的 representation lease、用户选择顺序、当前消息
和上下文预算。输出必须包含编译后的上下文、实际使用的 attachment/representation、
revision、content hash、locator、分片信息和 token 统计；输出还应携带被跳过项、超限和
降级诊断，不能静默丢失用户明确选择的附件。

### 10.2 选择和预算规则

实现前需要冻结多附件排序、重复选择去重、分片边界、最大 token/字节预算和超限处理。
不可用 representation、无效 locator、内容为空或预算不足时，返回可解释的编译失败或
明确 warning，不能将未验证的 raw ref 直接拼入 prompt。编译结果只服务于当前 run，不
自动创建 TopicAssetBinding 或 Artifact。

### 10.3 与现有编译边界的关系

如果附件编译复用现有 `MemoryCompiler`，必须新增明确的 target 或 envelope，并说明
附件 representation 如何进入 `AgentRunContext`；如果使用独立 compiler，则必须定义其
与 Chat application、lease 生命周期和 InteractionSubmission 的交接点。不得因为名称相近
而改变现有 MemoryCompiler 的 ownership、visibility 或 Memory schema 语义。

## 11. W1-F：Interaction binding 与 Materialization promotion

W1-F 负责在成功 Interaction 后保存附件使用关系，并为确实参与 Memory CREATE/UPDATE 的
内容提供按需 Artifact promotion 来源。它不把“上传过”或“选择过”当成使用事实。

### 11.1 Topic binding 条件

只有同时满足以下条件时，Patchouli Topic 所有者才建立 `TopicAssetBinding`：用户显式选择
了 ref、required representation 已 READY、representation 实际通过 Context Compiler 进入
本轮上下文、lease 在使用期间有效，并且 Interaction 成功提交。binding 继续作为 Topic
级“真实使用过”事实写入不可变 TopicData；同一 Topic 重复使用同一资产保持幂等。

### 11.2 来源版本冻结

`TopicAssetBinding` 只表达 asset 关系，不足以冻结 representation revision/hash。W1-F 必须
通过 `ContextAttachmentUse` 或等价的 Interaction/settlement 明细保存实际使用的
representation、revision、content hash 和 locator。该明细不能与 binding 竞争“是否使用过”
的真相源，但必须在 Topic settlement 清理短期 buffer 前被复制进 Materialization task。

### 11.3 Artifact promotion

Materialization 只使用 task 中冻结的 opaque ref、representation revision 和 content hash，
不回查附件最新表示。只有附件内容实际参与 Memory CREATE/UPDATE 时才允许 promotion；
纯上传、解析、选择或编译不生成 Artifact。promotion 重试必须幂等，失败沿用
Materialization 的错误语义。是否映射为 `DocumentArtifact` 需在实现前冻结，不能把非文档
附件强制转换为该类型。

## 12. 契约与数据变更

首轮实现需要冻结以下契约，具体字段名称可以在实现前根据现有 port 命名统一：

1. 上传请求、上传结果和用户选择请求；
2. parser adapter 的输入、输出和安全错误；
3. representation complete/fail 命令的 revision/token guard；
4. Context Compiler 的 attachment selection、locator、budget 和诊断；
5. `ContextAttachmentUse` 或等价的不可变附件使用明细是否进入本轮公共快照/settlement task，以及它的保留边界；如果不采用该明细，必须给出其他能冻结 revision/hash 的载体，否则 Artifact promotion 不进入本轮完成范围；
6. Materialization task 使用的 ref/revision/hash 冻结结构；
7. 文件大小、媒体类型、文本编码、解析耗时和解析输出上限。

本计划不修改 `MemoryAtom` schema，不新增 MemoryType，不改变当前 `ArtifactType` 枚举，也不改变 MTP `RUN` 当前只允许系统注册工具（Kernel syscall）和 `CODE_SNIPPET` 的公共契约。若实现证明必须改变这些边界，应先拆出独立 ADR 或 Plan。

## 13. 兼容与迁移

- W0 已存在的 WorkspaceAsset 模型、reader/command port、opaque ref、lease 和 Topic binding 语义保持兼容；
- 当前没有可恢复的附件持久化数据，因此本计划不包含历史附件迁移；
- WorkspaceAsset、representation、ref 和 lease 仍只在当前进程 Store 生命周期内有效；
- 服务重启后旧 ref 失效，用户必须重新上传；
- 已有 Memory、Artifact、Topic 和 Chat run 不因附件功能上线而批量改写；
- MTP `RUN` 的现有 `CODE_SNIPPET` 行为保持不变；附件 parser 不通过该路径执行；
- 若后续接入 PDF 或其他 parser，新增 parser 不得改变已经成立的 RAW、READY、lease 和 binding 语义。

## 14. 实现阶段安排

实现按“先建立资产入口，再建立表示可用性，最后接入对话使用和物化”的顺序推进。
每一阶段都应先完成本阶段需要冻结的跨边界契约，再实现代码和测试；阶段之间通过可观测
的 Store 状态或交接对象衔接，不以未定义的临时字段跨阶段传递。

### 14.1 阶段顺序与依赖

| 阶段 | 主要工作 | 可开始条件 | 阶段出口 |
|:---|:---|:---|:---|
| W1-A | 上传路由、上传应用服务、前端拖拽/选择、RAW 原子注册 | W0 WorkspaceAssetStore、IdentityScope 和 opaque ref 契约可用 | 合规文件能生成 asset、RAW `READY` 和 ref；幂等与 Workspace 隔离通过 |
| W1-B | parser port、首批确定性 parser、解析资源限制 | W1-A 能稳定读取 RAW 快照 | parser 能对批准格式输出确定性结果或安全失败摘要 |
| W1-C | required representation 注册/启动/完成/失败和 asset 可用性 | W1-B 已确定 parser 输出和版本身份 | `EXTRACTED_TEXT` `READY` 才开放 asset；过期结果不能覆盖 |
| W1-D | Chat 附件选择、resolve、lease 和 InteractionSubmission 交接 | W1-C 能提供 READY representation | 显式选择能进入本轮交接，retry 不替换来源 |
| W1-E | Context Compiler、预算、分片、locator 和诊断 | W1-D 的选择与 lease 交接已冻结 | Agent run 能消费编译结果并报告实际来源 |
| W1-F | Topic binding、settlement 冻结和 Artifact promotion | W1-E 能输出不可变使用明细 | 只有成功 Interaction 建立 binding，promotion 使用冻结来源且幂等 |

W1-A 的后端 Store 命令、HTTP DTO 和前端运行态模型需要先共同冻结；后端路由与前端
拖拽队列可以在契约冻结后并行开发，但必须以同一个 multipart 字段、operation identity
和响应 DTO 联调。W1-B 与 W1-C 可以在 parser port 确定后由不同协作者并行推进，但
representation 状态转换和 parser 输出提交必须先约定 revision/token guard。W1-D 之后的
阶段依赖真实的 READY representation 和可重放的 Interaction 交接，不能用只返回文本的
测试捷径代替这些边界。

### 14.2 每阶段实施活动

1. **W1-A 实施**：先增加上传专用的 Store command 和应用服务测试，再接入 HTTP router；
   前端同时建立统一的文件入口、非持久化队列和 `attachmentApi`。后端单元测试证明
   原子注册与幂等，路由集成测试证明 multipart、错误状态和 scope 隔离，最小浏览器测试
   证明页面 drop 不导航。
2. **W1-B/W1-C 实施**：先以批准的低依赖格式打通 parser adapter，再接入
   `register_representation`、`start_representation`、`complete_representation` 和
   `fail_representation`。使用固定样本验证 hash、producer version、重复解析和 stale
   result；确认 required representation `READY` 前 Chat 入口不会放行。
3. **W1-D 实施**：先扩展 Chat 请求和 `InteractionSubmission` 的 canonical codec，再
   接入前端选择状态和发送请求。通过 acquire/lease 集成测试验证 remove race、重复选择
   去重和重试 digest，确保附件关系不由 handler 临时回查或重算。
4. **W1-E 实施**：在真实 representation 快照上确定单附件、多附件、预算和 locator
   行为，再把 compiler 输出接入 Agent run context。编译诊断先在应用服务和测试中稳定，
   然后再添加前端的选择反馈，避免 UI 先假定未冻结的截断规则。
5. **W1-F 实施**：最后接入 Perception 的 binding 参数、settlement task 的冻结明细和
   Materialization promotion。先验证成功 Interaction、取消/失败 Interaction 不产生
   错误 binding，再验证 remove、retry 和 Artifact 映射；DocumentArtifact 映射未冻结前
   不把它作为实现默认值。

### 14.3 联调与阶段门

每个阶段完成后进行一次从上一阶段真实出口开始的联调，不跨过中间状态直接调用末端
组件：

- A 门：HTTP 上传结果可以被同一 Workspace 的 reader resolve，RAW revision/hash 与响应
  一致；
- B/C 门：parser 结果通过 Store 命令提交，asset 从 `PROCESSING` 到 `READY` 的条件与
  失败语义可观察；
- D 门：Chat 请求携带的附件选择经过 canonical codec 后仍保持相同 ref 和版本摘要；
- E 门：Agent context 能报告实际纳入的 locator、revision/hash 和预算诊断；
- F 门：成功 Interaction 才产生 binding，settlement 后的 Materialization 不依赖已清理
  的 Topic buffer，并能在 retry 时使用同一来源版本。

阶段门未通过时，后续阶段只能继续完善不依赖失败出口的代码和测试，不得通过在调用方
增加隐式 fallback、直接访问 Store 私有状态或自动选择附件来绕过门槛。

## 15. 测试与验收

### 15.1 Unit

放置于 `tests/unit/`，验证单一行为单元，协作者使用真实的轻量对象或手写 fake：

- 上传元数据规范化和格式限制；
- parser 的确定性输出、unsupported 格式和安全错误摘要；
- representation revision/token 校验；
- READY/FAILED 状态迁移和 required representation 规则；
- Context Compiler 的单附件、多附件、去重、预算和 locator 行为；
- invalid ref、remove、过期 revision 和编译失败的稳定错误。

### 15.2 Integration

放置于 `tests/integration/`，使用真实 WorkspaceAssetStore、TopicData/Perception 和 Materialization 协作边界：

- 上传到 RAW、解析到 READY 的完整内部链路；
- parser 结果通过 Store 命令提交，而不是直接修改模型；
- acquire lease、Context 编译、Interaction 成功后的 TopicAssetBinding；
- remove-before-acquire 与 acquire-before-remove；
- settlement 在 buffer 清理前冻结 binding 及选定的附件使用明细，Materialization retry 使用同一 revision/hash；
- `InteractionSubmission` 的 canonical codec 能原样保留已校验的 asset ref，重试或重复提交不会重新推导或替换附件关系；
- 两个 Workspace 的同名资产、ref 和 binding 隔离；
- Artifact promotion 成功、失败和幂等重试。

### 15.3 E2E

放置于 `tests/e2e/`，从公开 Chat/上传入口进入，使用确定性协议 fake，断言用户可观察响应、状态和持久化结果：

- 上传、选择附件、完成对话并观察上下文使用和 Topic binding；
- 上传或解析失败时用户收到稳定错误且不会生成错误 binding；
- 取消选择或 remove 后，后续 Chat 不会继续使用不可用 representation；
- 成功 Interaction 后的 Materialization 能看到冻结的来源 revision/hash。

新增测试必须能够在对应生产行为被破坏时失败，断言输入输出、状态迁移和持久化副作用，不以 mock 调用次数或刚注入的 mock 返回值作为主要证据。涉及异步状态使用事件或有界轮询，不使用固定 sleep；使用临时文件时使用 `tmp_path`。

## 16. 风险与开放问题

- 当前 WorkspaceAsset 是进程内 working set；长解析、服务重启和后台恢复不在本计划承诺内；
- PDF 解析库可能带来资源消耗或不受信任输入风险，是否进入首个交付取决于运行时限制和安全评估；
- parser 版本变化可能产生不同 extracted text，需要冻结 producer/version 和 revision 语义；
- Context Compiler 的 token 预算、分片和 locator 需要真实附件样本校准；
- `ContextAttachmentUse` 是诊断明细还是长期 provenance 事实，需要避免与 TopicAssetBinding 形成第二个“是否使用过”真相源；
- 当前 `InteractionPayload`/`InteractionSubmission` 尚未携带附件 ref，且其 codec 需要保持 canonical；附件关系、revision/hash 明细应挂在哪个交接层必须先冻结；
- attachment promotion 是否统一使用 DocumentArtifact，需要根据内容语义和 v0.7.0 Document Ingestion 边界裁定；
- Materialization 开始前 ref 已被 remove 时，应按既有 task 语义选择跳过并记录诊断，还是令本次 Materialization 失败；
- 上传 operation、parse operation 和 materialization operation 的幂等身份需要保持领域命名，不建立通用的隐式 operation key；
- 本计划不解决 Agent 主动解析的工具调用、沙箱、外部 Plugin 和 Memory 引用层执行问题。

## 17. 完成定义

本计划完成时，必须能够证明：

1. 用户可以在当前 Workspace 上传至少一种批准格式的附件，并获得有效的 opaque ref；
2. parser 可以生成稳定的 READY representation，失败时进入 FAILED 且不会伪装成可用资产；
3. 用户显式选择的 ref 能在当前 Chat 中解析、获取 lease 并进入 Context Compiler；
4. Context Compiler 能报告实际使用的 representation revision/hash 和定位信息；
5. 成功 Interaction 才会建立 TopicAssetBinding，上传和选择本身不会建立 binding；
6. Topic settlement 和 Materialization 不依赖已经消失的 Topic 内容，并且通过已明确的不可变交接载体使用冻结的 ref/revision/hash；
7. Artifact promotion 只在确有 Memory CREATE/UPDATE 时发生，且 retry 幂等；
8. Workspace 隔离、remove、lease、解析失败、编译失败和版本冲突均有测试证据；
9. 当前设计文档、Artifact 文档、Roadmap 和 Plan 索引在完成收尾时同步更新，已完成 Plan 移入 `archive/plans/`。
