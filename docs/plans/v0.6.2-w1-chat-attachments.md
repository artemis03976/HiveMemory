# v0.6.2 W1：Chat Attachments

本文是建立在 v0.6.2 W0 Workspace MVP 之上的初步实施计划框架，覆盖附件从上传、解析、表示可用，到用户在 Chat 中选择并编译进上下文，再到 Interaction binding 和按需 Artifact promotion 的完整链路。

计划按六步拆分组织：W1-A 至 W1-C 对应上传、确定性解析和 representation `READY`；W1-D 至 W1-F 对应 ref 选择与后端交接、`AttachmentCompiler` 编译，以及对话成功后的 Topic/Materialization 流转。

本文以当前代码和已经归档的 W0 Plan 为事实基线。Idea 文档中与当前实现冲突的内容以当前实现为准；尚未冻结的 API 字段、解析器实现方式和 Artifact 映射在本计划的开放问题关闭前不得作为公共契约使用。

## 1. 背景与问题

W0 已经建立 System-owned 的进程内 `WorkspaceAssetStore`，以及 `WorkspaceAsset`、`AssetRepresentation`、opaque `WorkspaceAssetRef`、READY-only 使用、删除和 lease 语义。W0 明确不实现真实上传、解析、AttachmentCompiler 和 Artifact promotion。

当前 Chat 还缺少一条完整的附件工作流：用户上传文件后，系统不能稳定地产生可用的文字 representation，Chat 也不能把用户显式选择的 attachment ref 纳入上下文，更不能在成功 Interaction 后保留真实使用关系和来源证据。

本计划首先解决附件作为 Workspace 运行时资产的生命周期和用户选择后的上下文使用。它不把附件直接视为 Memory，也不把上传动作解释为 Topic binding 或 Artifact creation。

## 2. 目标

本计划完成以下闭环：

```text
upload
  -> WorkspaceAsset + opaque ref
  -> RAW representation
  -> deterministic parser
  -> EXTRACTED_TEXT representation READY / FAILED
  -> user selects ref
  -> resolve + acquire READY representation
  -> AttachmentCompiler
  -> successful Interaction commit
  -> TopicAssetBinding
  -> optional Materialization Artifact promotion
```

具体目标：

1. 提供 Chat 附件上传入口，创建属于当前 Workspace 的 `WorkspaceAsset` 并返回进程内 opaque ref；
2. 建立确定性解析器的窄接口和第一方实现，解析器只消费明确的 RAW representation；
3. 通过 `WorkspaceAssetStore` 的命令完成 representation 与 asset 聚合状态迁移；
4. 支持用户显式选择、重复使用和取消选择附件；
5. 将实际选择的 READY representation 编译为本轮 Agent 上下文，并保留 revision、hash、locator 和编译诊断；
6. 在 Interaction 成功完成后，以现有 Topic 所有者流程建立 `TopicAssetBinding`；
7. 在 Materialization 阶段沿 `TopicAssetBinding.asset_ref` 重新取得可用 representation，按需进行 Artifact promotion，并保持 retry 幂等；
8. 为 remove、lease、解析失败、无效 ref、编译失败和 representation 版本变化提供稳定失败语义。

## 3. 非目标

本计划不包含：

- Agent 通过 MTP `RUN` 自主决定页码、区域或解析操作；
- MemoryCompiler 的 `RUNNABLE_TOOL` target 实现；
- Memory 内容直接执行、Memory-backed Plugin 或任意用户代码执行；
- 外部 parser package、Provider Registry、插件安装和插件生命周期；
- 强隔离沙箱、网络/进程权限降级、跨重启恢复和分布式任务执行；
- OCR、图像、多模态输入和图像记忆化；
- WorkspaceAsset 的持久化、跨进程共享、对象存储、保留策略和垃圾回收；
- 新增 MemoryType，或改变 Memory schema v2 的 ownership、visibility 和 lifecycle 语义；
- 上传、选择或普通 Context 编译自动创建 Topic binding 或 Artifact。

本计划的附件格式限定为 `.txt`、`.md`、`.markdown` 和 `.docx`，解析结果为纯文本或保留语法的 Markdown。Word 首轮只支持 `.docx`；旧版 `.doc` 提示另存为 `.docx` 后上传。PDF、RTF、宏文档和其他格式不进入本轮，具体规则见第 7 章。

## 4. 当前状态与缺口

### 4.1 已成立的实现基础

- `WorkspaceIdentity`、`IdentityScope` 和 Workspace-owned resource 边界已经成立；
- `WorkspaceAssetStore` 是 System 进程级唯一 working set；
- `WorkspaceAsset` 聚合已有 `PROCESSING`、`READY`、`FAILED`、`REMOVED` 状态；单个 `AssetRepresentation` 已有 `PENDING`、`PROCESSING`、`READY`、`FAILED` 状态，`REMOVED` 只属于 asset 聚合；
- `WorkspaceAssetRef` 是当前 Store 存活期内 opaque token，不是物理路径、永久 ID 或授权凭证；
- READY representation 的读取通过 reader port 建立 lease，并在消费期间保持有效；
- Topic binding 由 Patchouli Perception 的 Topic 所有者在成功 Interaction 后提交；
- `PerceptionFamiliar.apply_interaction` 与 `TopicData` 合并逻辑已经支持接收 `(asset_id, asset_ref)`，但当前 `InteractionPayload`、`InteractionSubmission` 和 `PatchouliService.finalize_agent_run` 尚未把这份附件选择接入主动 Chat 的完整链路；
- Artifact、DocumentArtifact 和 Memory generation provenance 基础已经存在，但完整附件摄入和 promotion 尚未接入；
- 当前 MTP `RUN` 只处理 Kernel syscall 和 `CODE_SNIPPET`，不能作为本计划的通用 parser 执行环境。

### 4.2 本计划需要补齐的能力

| 缺口 | 责任边界 | 结果 |
|:---|:---|:---|
| 上传入口与请求响应 | Chat/System | 资产创建、元数据校验、opaque ref 返回 |
| RAW 内容接入 | System WorkspaceAssetStore | RAW representation READY |
| 确定性解析器 | System parser adapter | 解析结果或安全错误摘要 |
| 表示状态提交 | WorkspaceAssetStore | representation 与 asset 聚合状态原子落定 |
| 选择和解析 | Chat 请求 + Patchouli prepare | Chat 只传递选择；Patchouli 按 scope 校验 READY 并 acquire lease |
| 附件使用交接 | Chat/Patchouli submission | 将已校验的 asset ref 从 Chat 传到 Interaction apply，并保留 canonical/retry 语义 |
| AttachmentCompiler | 附件内容编译边界 | prompt section、预算、locator 和诊断 |
| Interaction binding | Patchouli Perception | 成功使用后的 TopicAssetBinding |
| Artifact promotion | Patchouli Materialization | 沿 binding.asset_ref 重新取得内容，按需生成 Artifact |

## 5. 目标数据流与所有权

```text
Chat upload request
  -> System WorkspaceAssetStore
  -> WorkspaceAsset + RAW representation
  -> parser adapter
  -> WorkspaceAssetStore complete/fail command
  -> Chat selection of WorkspaceAssetRef
  -> IdentityScope resolve + READY representation lease
  -> AttachmentCompiler
  -> Chat Interaction
  -> Patchouli TopicData commit
  -> Materialization task
  -> optional source Artifact promotion
```

| 资产或行为 | 权威所有者 | 本计划的边界 |
|:---|:---|:---|
| WorkspaceAsset、representation、opaque ref、lease | System `WorkspaceAssetStore` | 复用 W0 port 和命令，不复制第二套状态机 |
| 上传请求和用户选择 | Chat/System application | 只提交显式选择，不推测 Topic 关系 |
| parser 调用 | System parser adapter | 只允许本计划规定的确定性第一方实现 |
| 附件编译结果 | AttachmentCompiler / Chat 上下文组装流程 | 使用 reader port，不直接访问 Store 私有状态 |
| TopicAssetBinding | Patchouli Perception / Topic owner | 只在成功 Interaction commit 中建立 |
| Materialization promotion | Patchouli generation/artifact flow | 沿 binding.asset_ref 重新取得内容，通过 reader port 使用 lease |
| Agent 主动解析和外部 Plugin | 后续 Alice/MTP 执行能力 | 不属于本计划 |

### 5.1 W1-A 至 W1-C 的交接不变量

三阶段只沿一条资产链交接，不为资产可用性再建一套状态机；前端本地上传队列仍可记录
请求是否已提交、是否需要重试：

| 阶段 | 输入 | 本阶段唯一输出 | 输出后的可用性 |
|:---|:---|:---|:---|
| W1-A | 一个文件和冻结的 `IdentityScope` | 一个 `WorkspaceAsset`、一个 `RAW READY` representation 和 opaque ref | RAW 注册瞬间文档 asset 为 `PROCESSING`；HTTP 返回时可已由 W1-C 推进到终态 |
| W1-B | W1-C 从 Store 命令快照交接的 RAW bytes | `EXTRACTED_TEXT` 的确定性内容结果，或 `AssetSafeError` | parser 结果本身不改变 asset 状态 |
| W1-C | W1-B 结果与目标 representation 的 revision/token | Store 原子提交后的 `EXTRACTED_TEXT READY` 或 `FAILED` 快照 | 仅 `asset READY` 且 required representation READY 时，W1-D 才能 resolve/acquire |

因此，W1-A 不等待 W1-B 的正文，也不把上传成功等同于附件可选；W1-B 不通过
READY-only reader 读取 PROCESSING asset，也不直接修改 Store；W1-C 不重新解析或另建
资产状态，只负责执行和提交。W1-D 之后的 Chat 选择只能接收 W1-C 的 READY 快照，不能
绕过该门槛直接使用 RAW。

本文所说的附件 `AttachmentCompiler` 是待实现的独立附件编译组件。它读取 W1-D 冻结的
representation lease，生成附件内容片段和实际使用明细；当前 Patchouli `MemoryCompiler`
继续只负责 `MemoryAtom` 的既有 target。两者不共享编译入口、source 类型、target 枚举或
ownership。二者的产出最终由 Alice 侧 `AgentPromptAssembler` 统一组装为 Agent messages，
不能因为都使用“compile”一词而合并职责。

## 6. W1-A：上传与 WorkspaceAsset 注册

W1-A 只负责把浏览器中的一个文件接收到当前 `IdentityScope` 对应的
`WorkspaceAssetStore`，并形成一个带 opaque ref 的逻辑资产和一个初始 RAW
representation。它不负责解析文本，也不把 RAW `READY` 误认为资产已经可供 Chat
使用：文档资产的 required representation 是 `EXTRACTED_TEXT`，因此在 W1-B/W1-C
完成前，asset 聚合仍可处于 `PROCESSING`。

#### A1. HTTP 入口与应用服务

采用独立的上传应用服务承接 HTTP 与 Store 之间的边界，router 不直接编排多个 Store
命令。建议的代码落点为：

- `src/hivememory/server/routers/workspace_assets.py`：注册
  `POST /api/v1/workspace/assets`，解析统一的 `x-user-id` / `x-workspace-id` 请求头，
  并调用应用服务；
- `src/hivememory/server/models/workspace_asset.py`：定义上传结果和 representation
  摘要 DTO，不把领域模型或原始内容直接暴露为 HTTP 契约；
- `src/hivememory/system/application/workspace_asset_service.py`：执行身份作用域下的
  校验、受限读取、哈希计算和上传专用 Store 命令；
- `src/hivememory/server/deps.py`、`src/hivememory/system/assembler.py` 和
  `src/hivememory/server/app.py`：装配并注入进程级唯一的上传服务和路由。

请求契约冻结为单文件 `multipart/form-data`：

- 文件字段名为 `file`，一个请求只处理一个文件；多文件拖入由前端建立逐文件队列；
- 重复的 `file` part、多文件 part 或额外业务字段按非法请求拒绝，不能只取第一份文件
  而忽略其余内容；
- 请求头 `Idempotency-Key` 是本次上传的稳定 operation identity，服务层将其映射为
  当前 Store 的 `client_operation_id`；同一文件重试必须沿用同一个值；
- 用户和 Workspace 仍只由现有统一身份请求头表达，上传 body 不重复携带身份字段；
- 采用 FastAPI `UploadFile` 时，在 `pyproject.toml` 增加 `python-multipart` 运行依赖，
  并在服务启动或测试环境验证 multipart 解析可用。

路由只负责 HTTP 解析、依赖注入和错误翻译。默认身份回退仍由
`resolve_request_identity_scope` 完成，应用服务接收已经冻结的 `IdentityScope`，不得
再次从文件字段或 body 推导 Workspace。

#### A2. 文件校验与受限接收

应用服务在创建 asset 前完成所有不会产生副作用的输入校验：

- 拒绝空文件；
- 对文件名做 Unicode/空白规范化，去除路径分隔符和控制字符，并限制长度；文件名只
  作为 `display_name`，不能成为 Store 寻址或物理路径；
- 使用第 7.1 节确定的媒体类型/扩展名集合；客户端提供的 MIME 只能作为提示，不能作为
  唯一判断依据。W1-A 只负责扩展名和媒体类型的初步分派，W1-B 负责严格文本解码和
  DOCX 包内容校验；上传路由不复制 parser 的内容判断，也不因 parser 尚未运行而提前
  声称文件有效；
- 以配置的最大字节数为硬上限，分块读取并计算 SHA-256，使用有界内存缓冲或受控的
  spool；不得对 `UploadFile` 做无上限的一次性 `read()`，也不得先创建没有内容的孤儿
  asset；
- `size_bytes` 使用实际读取字节数，`content_hash` 使用实际 bytes 计算；编码探测和
  文本解码属于 W1-B parser，不在上传路由内偷偷完成。

文件的 10 MiB 上限见第 7.7 节。应用层的文件字节计数仍是最终判断，不能只相信
`Content-Length`；使用框架已有的受控 multipart spool，并在读取超限时立即中止该文件。
所有拒绝和断连路径都关闭上传流及框架临时文件。本轮不建设通用上传平台；如果部署层
已经提供请求体上限，直接复用，不另增附件专用 middleware。

读取完成后，服务层只向 Store 提交不可变 bytes、规范化 metadata、content hash、稳定
的 upload producer 名称和 producer version。服务层和 router 都不能保存物理临时路径，
也不能把原始 bytes 写入日志、错误 message 或 HTTP 响应。

#### A3. Asset 与 RAW 的原子注册

当前 `create_asset` 和 `register_raw_representation` 分别持有幂等和内容写入的一半
语义：前者只按 metadata 比较，后者没有 upload operation identity。W1-A 必须扩展
`WorkspaceAssetCommandPort`/`InMemoryWorkspaceAssetStore`，增加一个上传专用的等价原子
命令（名称可按代码风格确定，例如 `register_uploaded_asset`），一次完成：

1. 在 `IdentityScope` 下检查 Store 未关闭，并以 `(workspace_identity, client_operation_id)`
   定位幂等记录；
2. 将 metadata 与原始 content hash 纳入 operation fingerprint；相同 operation 重放且
   fingerprint 相同，返回同一 asset/ref 的当前 `WorkspaceAssetHandle`；fingerprint 不同，返回
   `workspace.asset.operation_conflict`，不能创建第二个 asset；
3. 创建一个新的 `WorkspaceAsset` 和一个当前 Store 生命周期内有效的
   `WorkspaceAssetRef`；
4. 注册 `RAW`、revision `1`、状态 `READY` 的 representation，并冻结 bytes；
5. 根据 `required_representation_kind` 更新 asset 聚合状态。对文档资产，RAW 不满足
   `EXTRACTED_TEXT`，所以聚合保持 `PROCESSING`；只有 required representation 后续进入
   `READY` 才能转为 asset `READY`。

上述步骤必须在 Store 的同一临界区内线性化。router 或应用服务不得先调用
`create_asset`、再调用 `register_raw_representation` 并自行猜测失败补偿；若实现选择
其他命名，必须保留同样的原子性、Workspace 隔离和重放语义。上传 operation 的幂等记录
应能区分“同一 operation 的同一内容重试”和“同一 operation 携带了另一份文件”，不能
只比较文件名或客户端 MIME。上传专用命令的结果同时携带新建/重放标记；现有通用
`WorkspaceAssetHandle` 无需因此增加上传专属字段。

#### A4. HTTP 响应与错误语义

首次创建返回 `201`，同一 `Idempotency-Key` 且 fingerprint 相同的重放返回同一逻辑资产（重放返回 `200`，复用同一 DTO 结构；状态取当前快照，且由于第 8.2 节的同 key 串行化，该快照只会是 READY/FAILED 终态或下文错误之一，不会返回 PROCESSING 中间态）。上传应用服务需要从上传专用 Store 命令得到“新建/重放”的结果标记，不能根据 asset 状态猜测 HTTP 状态。响应至少包含：

- `asset_ref`：opaque ref 的序列化值；
- `asset_id`、`display_name`、`media_type`、`size_bytes` 和 asset `state`；
- RAW representation 的 `representation_id`、`revision`、`state`、`content_hash`、
  `producer` 和 `producer_version`；
- 通过 asset `state` 及 required representation 摘要显示“已上传/可用/失败”，不另设可漂移的
  `is_ready` 标志；与 W1-C 联调后共用同一份安全摘要 DTO。

响应不得包含原始 bytes、绝对路径、Store 内部对象、未过滤的异常文本或可被当作永久
授权凭证的 ref 解释。如果原 operation 对应的 asset 已被移除，重放返回既有
`workspace.asset.removed` 的安全错误，不重新创建资产；Store 关闭返回既有
`workspace.asset.operation_conflict` 的 `store_closed` 详情。其他错误按当前 HTTP router 的
局部翻译方式返回。上传前能够确定的请求错误只需要现有 HTTP 状态和局部 message：
缺少/非法文件元数据（`400`）、大小超限（`413`）、不支持的媒体类型（`415`）、同一
operation 输入冲突（`409`）、原资产已移除（`410`）、Store 已关闭或运行时不可用（`503`），
以及非法身份选择。缺省身份沿用现有回退，公共入口对未开放 Workspace 返回现有 `404`；
跨 Workspace 的内部 ref 访问沿用 `workspace.asset.not_found`。本计划不扩展 Workspace
错误码表。错误 message 只返回安全摘要，不能泄露临时路径或解析栈。

上传成功只表示 RAW 已注册：不自动创建 TopicAssetBinding、Interaction、Context
AttachmentUse 或 Artifact，也不把新 asset 自动附加到当前消息。用户必须在后续 W1-D
明确选择该 ref；required representation 尚未 `READY` 时，前端不得把它列为可用附件。

#### A5. Chat 工作区与 composer 的文件入口

`ChatWorkspace`、`OmniInput` 和附件选择对话框共用同一份“文件进入上传队列”逻辑，避免
三个入口产生不同的校验和状态：

- 在当前 Chat 页面工作区监听 `dragenter`、`dragover`、`dragleave` 和 `drop`，拖入文件时
  显示明确的 drop 状态；所有 drag/drop handler 都 `preventDefault`，避免浏览器直接打开
  文件；只接收 `DataTransfer.files`，目录和无文件 payload 直接忽略；
- composer 的 Paperclip 按钮打开隐藏的 `<input type="file">`，并提供键盘可达的选择
  方式；对话框中的 drop 与页面 drop 进入同一处理器；通过事件归属或传播控制，避免同一
  文件被工作区和 composer 重复入队；
- 一次上传请求只发送一个文件。多文件拖入后按照文件顺序建立队列，W1-A 默认逐项提交，
  每项拥有独立的 `queued`、`uploading`、`uploaded`、`failed` 状态和重试入口；
- 文件首次进入队列时生成稳定 operation ID，重试沿用该 ID；成功响应中的 opaque ref
  只保存在当前运行时的附件状态中，不写入 `localStorage`，不持久化 raw bytes，也不把
  ref 当作本地路径；
- 上传是独立于 Chat SSE run 的资产命令，可以在生成期间继续接收文件，但不会修改已经
  开始的 run。当前 Paperclip 在 `isStreaming` 时默认禁用，需在实现时移除该限制或把上传
  入口移到仍可用的工作区区域，并用测试证明两种操作不会互相取消；
- `uploading` 表示请求仍在执行解析；服务端响应返回 `READY` 后才将附件标记为可用，
  返回 `FAILED` 则显示解析失败。响应只会是终态或稳定错误，前端不需要处理 PROCESSING
  中间响应；同一 operation 的并发重复提交由第 8.2 节的后端串行化兜底，前端仍应避免
  同一队列项在 `uploading` 期间重复发送。单项上传失败只清理该项的临时状态，不影响
  同一队列中的其他文件和当前对话；W1-C 不要求前端轮询服务端 PROCESSING 状态。

建议新增 `frontend/src/services/attachmentApi.ts` 负责 `FormData`、
`identityHeaders()` 和 `Idempotency-Key`；不要手工设置 multipart 的 `Content-Type`，让
浏览器生成 boundary。附件运行态可由独立的非持久化 store 承载，或由 Chat store 的
非持久化 slice 承载，但必须明确 ref 的生命周期，不得沿用当前 Chat store 仅持久化 Agent
选择的配置语义。

#### A6. W1-A 联调顺序

1. 前端将拖入/选择的文件规范化为队列项并生成 operation ID；
2. `attachmentApi` 以 `multipart/form-data` 调用上传路由，附带统一身份请求头和
   `Idempotency-Key`；
3. router 解析请求并冻结 `IdentityScope`，应用服务执行大小、文件名和媒体类型校验，
   分块读取并计算实际 hash；
4. 上传专用 Store 命令在一次临界区内创建 asset、生成 ref 和注册 RAW；
5. 独立验收 W1-A 时服务返回 RAW 摘要；接入 W1-C 后先完成第 8.2 节的解析接纳，再返回
   共享摘要 DTO。前端按 HTTP 结果记录 `uploaded` 或上传 `failed`，解析 FAILED 仍属于
   uploaded 项的服务端状态；
6. W1-A 的联调只验证 ref 返回、Workspace 隔离、RAW revision/hash 和幂等重放；解析
   `EXTRACTED_TEXT`、Chat 选择与 Context 编译分别由 W1-B 至 W1-E 验收。

#### A7. W1-A 阶段验收

- 页面工作区、composer 和附件对话框的拖拽/点击入口都进入同一逐文件上传流程，浏览器不会
  因 drop 导航或打开文件；
- 一个合规文件的上传能在所属 Workspace 创建一个 asset、一个 RAW `READY` representation
  和一个 opaque ref；文档 asset 在 required text 尚未生成时保持 `PROCESSING`；
- 相同 Workspace、相同 `Idempotency-Key` 和相同文件内容的重试不会生成重复 asset 或
  重复 RAW；相同 key 携带不同 metadata、size 或 hash 会稳定返回冲突；
- 不同 Workspace 即使使用相同文件名和 operation ID 也完全隔离，跨 Workspace 使用 ref
  得到统一的 not-found/mismatch 结果；
- 空文件、非法/过长文件名、超限文件、不支持媒体类型、Store 关闭和上传冲突都有稳定的
  HTTP 状态与前端可见提示；
- 响应和日志不包含 raw bytes、物理路径或内部异常栈；前端不持久化 raw bytes 或 opaque
  ref；
- 上传成功不会创建 TopicAssetBinding、Interaction 或 Artifact，且不会把附件偷偷加入
  当前 Chat run；
- W1-A 的 unit、integration 和最小 browser/e2e 测试覆盖上传响应、drop 行为、Store 原子
  注册、幂等重放和 Workspace 隔离；同步解析使用有界等待，不使用固定 sleep。

## 7. W1-B：确定性解析器

W1-B 将 W1-A 保存的原始 bytes 转为可冻结的文字内容，交给 W1-C 注册为
`EXTRACTED_TEXT`。这里区分输入文件格式与输出文字格式：DOCX 是包含 XML 的文档包，
需要提取正文；TXT 和 Markdown 主要需要确定性解码。三者使用同一种 representation kind，
不增加 Word、Markdown 等 asset 状态或 representation 枚举。

解析器只负责内容转换。System 应用服务负责选择解析器、提供输入和交接结果；Store
负责状态与 ref；W1-E 负责按本轮请求选择内容、控制 token 预算和组装上下文。

### 7.1 格式范围与分派规则

| 输入 | 扩展名 | 服务端规范化 media type | 输出 `format` | 首轮保证 |
|:---|:---|:---|:---|:---|
| 纯文本 | `.txt` | `text/plain` | `plain_text` | 解码后的全文、空白和行号 |
| Markdown | `.md`、`.markdown` | `text/markdown` | `markdown` | 保留 Markdown 源码及行号 |
| Word | `.docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | `plain_text` | 正文段落文字与段落级定位；表格按行文字降级 |

以上格式统一由 W1-A 登记为 `kind="document"`，required representation 为
`EXTRACTED_TEXT`。TXT 也经过同一条转换与状态提交链路，不将 RAW 直接当作可用正文。

扩展名大小写不敏感。前端 file input 的 `accept`、W1-A 上传白名单和后端 parser 分派
必须使用同一格式集合。浏览器 MIME 缺失、为 `application/octet-stream`，或把 Markdown
报告为 `text/plain` 时，结合扩展名及内容校验规范化；明确冲突的格式声明返回稳定错误。
不凭 MIME 选择任意解析器，也不在 DOCX 解析失败后回退为 TXT。

`.doc`、`.docm`、`.dotx`、`.rtf`、PDF、图片和任意 ZIP 不属于本轮。旧版 `.doc`
提示“请另存为 .docx 后上传”，不安装或调用 Office、LibreOffice、在线转换服务。
即便文件名为 `.docx`，也必须验证其 Word 包结构，不能把 ZIP 签名当成完整的格式证明。

### 7.2 RAW 输入与调用边界

当前 `resolve_asset()` 和 `acquire_ready_representation()` 都先检查 asset 聚合为
`READY`。文档在提取文本前仍为 `PROCESSING`，即便 preference 指定 RAW，也不能通过
这两个接口读取。因此解析输入采用 **Store 命令返回的冻结快照**，不放宽 Chat reader：

1. W1-A 返回的内部 `WorkspaceAssetHandle` 已包含 RAW；后续 W1-C 的
   `register_representation()` / `start_representation()` 也返回完整资产快照。
2. 应用服务在同一 `IdentityScope` 下启动目标 `EXTRACTED_TEXT` representation，从
   `start_representation()` 返回值中取得 RAW 快照和目标 parse operation token。
3. 应用服务核对 Workspace、asset 归属、RAW kind/state、bytes 类型、实际大小与 RAW
   content hash，再把解析必需的数据交给 parser。ref、目标 representation id 和 token
   由调用方保留，用于 W1-C 提交；parser 不自行生成这些标识。
4. parser 在 Store 锁外运行，只读取本次冻结 bytes。处理期间发生 remove 时，已有快照
   不会原地变化；晚到结果仍须被 Store 拒绝，不能恢复已删除资产。

输入至少包含 RAW bytes、RAW revision/hash、规范化媒体类型和本次固定的解析限制。
parser 不依赖 HTTP `UploadFile`、临时路径、Store 对象、Agent 或 LLM。展示文件名不参与
内容生成，也不参与解析器权限判断。快照只在本次进程内处理期间保留，任务结束释放引用；
不写入持久化任务载荷。解析执行和结果提交按第 8 章 W1-C 的请求内交接安排执行。

这一交接方式以当前 [Store 实现](../../src/hivememory/system/runtime/workspace/store.py)
和 [文档 READY 条件测试](../../tests/unit/system/runtime/workspace/test_store.py) 为基线，
无需为 parser 新建一套绕过 asset 状态的通用 reader。

### 7.3 TXT 与 Markdown 解码规则

TXT 和 Markdown 共用解码逻辑，首轮采用以下固定顺序：

- 带 UTF-8 BOM：移除文件开头的 BOM，严格按 UTF-8 解码；
- 带 UTF-16 LE/BE BOM：按 BOM 确定端序并严格解码；
- 无 BOM：只按 UTF-8 严格解码，不尝试 GBK/GB18030 或无 BOM 的 UTF-16；无法解码时归入
  `content_unreadable`，内部参数记录 `unsupported_encoding`，提示转存 UTF-8。UTF-32 BOM
  显式拒绝，不能误认作 UTF-16；
- 不使用系统默认编码、概率探测或 `errors="ignore"` / `errors="replace"`，避免把乱码
  或损坏内容伪装成解析成功。

输出将 CRLF 和 CR 统一为 LF，保留其他空白、缩进、空行和末尾换行，不执行全文
`strip()`、Unicode 兼容归一化或自动重排。规范化后，U+0000–U+001F 中除 TAB、LF、FF
外的字符，以及 U+007F–U+009F 归入 `content_unreadable`，内部参数记录 `invalid_text`；FF 作为文字中的换页符保留。
空文件由 W1-A 拒绝，解码后
只有 BOM/空白的内容由 W1-B 归入 `content_unreadable`，内部参数记录 `empty_content`。

Markdown 保留标题、列表、代码围栏、表格、链接、frontmatter 和内嵌 HTML 的原始文本。
首轮不构建 Markdown AST、不生成 HTML、不执行代码、不展开 include 或抓取链接/图片；
后续 UI 若预览，按文字展示或使用自己的安全渲染边界。纯文本解析也不解释文件中的指令。

### 7.4 DOCX 正文提取规则

首轮使用标准库 `zipfile` 读取内存中的 DOCX 包，使用 `defusedxml` 解析必要 XML，作为
第一方的窄范围正文提取器。`defusedxml` 需在实现时加入 `pyproject.toml` 的运行依赖，
并锁定经过样本验证的版本范围。这里不引入通用文档转换框架，也不依赖桌面 Word。

包校验读取 `[Content_Types].xml`、包关系及其指向的内部正文 part，验证其为非宏 Word
文档；限定内部 part 寻址，拒绝路径逃逸、重复成员名、加密包、损坏 ZIP/XML 和正文缺失。
正文命名空间按 Office Open XML 的 Transitional/Strict URI 显式识别，不只匹配标签的
local name。禁止 DTD、实体展开和外部 XML 资源；不将压缩包解压到文件系统。

正文按 XML 文档顺序提取。首轮只承诺“段落级正文”，不承诺表格网格、单元格级定位或
排版还原；转换规则如下：

| 正文元素 | 转换规则 |
|:---|:---|
| 段落、标题、列表项 | 合并段落内 run 的可见文字，保留 run 间原有空白；段落间使用 LF 分隔；标题和列表只保留文字，不臆造 Markdown 标记或编号 |
| 段内制表符与换行 | 分别输出 TAB、LF；分页符转为 LF，不据此生成 Word 页码 |
| 表格 | 与段落按出现顺序交错输出，整体降级为文字行：行间 LF、单元格间 TAB；只保证行级文字顺序，不承诺单元格级 locator，也不为合并单元格补造虚拟网格 |
| 超链接与字段 | 超链接保留显示文字、不访问目标地址；字段只取文档内已保存的显示结果，不计算字段、不输出字段指令 |

这是一份“正文文字表示”，不承诺还原 Word 排版、自动编号、页码、样式、字体或目录
计算结果。页眉页脚、脚注尾注、批注、图片、图表、文本框和嵌入对象不参与首轮正文
提取；检测到这些内容或自动编号时，输出稳定的 warning record，供后续显示覆盖范围。
它们存在不必使有有效正文的文档失败，但只包含图片等未覆盖内容时归入
`content_unreadable`，内部参数记录 `empty_content`。

会使正文读取顺序或内容版本不明确的结构，如未接受的修订、嵌套表格、`altChunk`、
正文内容控件及 `AlternateContent`，首轮归入 `content_unreadable`，内部参数记录
`unsupported_structure`，不静默跳过。
超限、损坏或不支持结构都不能以截断正文加成功状态返回。样本验收须覆盖段落—表格—段落
交错，防止先读完所有段落再读表格；单元格级表格语义不在本轮承诺内。

### 7.5 输出内容、定位与 hash

所有 parser 使用相同的成功结果结构：`producer`、`producer_version`、`content_object`
和 `content_hash`。producer/version 在 W1-C 注册目标 representation 之前确定，完成时
验证仍是同一解析实现；Store 现有 complete 命令不会重新写入 producer/version。

正文与 locator 校验、大小累计和 canonical hash 生成只在 W1-B 的共享结果模型中实现
一次；parser 返回前完成构造。W1-C 复用该结果并核对来源，不再次解释附件正文。

`content_object` 使用 Store 已支持的可递归冻结的 JSON 风格对象，第一版内容约定为：

| 字段 | 语义 |
|:---|:---|
| `schema_version` | 内容结构版本，首轮为 `1` |
| `format` | `plain_text` 或 `markdown`，不改变 representation kind |
| `text` | 转换后的完整正文；分片和 token 预算留给 W1-E |
| `source_raw` | 当前 asset 的唯一 RAW 的 `revision`、`content_hash`；结合 asset/ref 定位原始版本 |
| `locators` | 正文字符区间与源位置的映射，按正文顺序排列 |
| `warnings` | `message_key` 与受控 `params` 组成的 warning record；去重且排序稳定，无 warning 时为空列表 |

`locators` 使用 `start` / `end` 表示 `text` 中从零开始、左闭右开的 Unicode 码点区间，
不使用 UTF-8 字节偏移或浏览器 UTF-16 下标。TXT/Markdown 每个非空行记录一条
`line` locator，行号从 1 开始且计入空行。DOCX 按正文段落记录段落级 locator，表格
降级后的每个文字行同样按段落记录，序号从 1 开始并计入空元素；首轮不承诺单元格级或
单元格内段落级定位，位置属于源文档结构而非页面坐标。
分隔符可不归属某条 locator，有正文文字的区间不能失去定位，禁止以文件名或绝对路径定位。

RAW hash 继续表示上传 bytes。提取结果的 hash 使用完整 `content_object` 的 canonical
JSON UTF-8 编码计算 SHA-256：键排序、紧凑分隔符、非 ASCII 字符直接编码、无额外换行，
数组顺序按上述规则固定。hash 保存为小写十六进制；它覆盖正文、format、locator、warning
和 RAW 来源版本，不仅覆盖 `text`。后续 W1-E 使用该 hash 进行本轮编译诊断时必须复用同一编码规则。

结果不含时间戳、随机 ID、operation token、运行耗时或本地化 message。这些值不能影响
内容 hash。可预期失败单独返回 `AssetSafeError(code, message)`，不生成半份成功
`content_object`，也不向 Store 提交空文本冒充 READY。具体定位字段通过固定样例冻结，
不在本轮建立独立的文档 AST 或新的资产聚合模型。

### 7.6 确定性、版本和提交语义

同一 RAW bytes/revision、parser producer/version 和固定转换规则，在资源充足时应产生
相同内容、locator、warning 和 hash。超时、取消和资源不足属于运行结果，不承诺跨机器
每次都发生相同失败。升级依赖或改变解码、DOCX 提取、定位、序列化规则时必须更新
producer version；同一服务运行期固定实现和配置，不热替换已开始的解析。

确定性转换和 Store 幂等是不同责任：parser 不创建 representation、不维护去重缓存。W1-C 使用 Store 签发的目标 parse operation token 提交；同一 asset 仍只有一个 `EXTRACTED_TEXT` kind，revision 由 Store 决定，parser 不能自己增加版本。重复 complete 继续按现有 stale-result 语义拒绝，不能宣称它是幂等成功。上传响应丢失后的原 operation 重放复用原资产，由应用服务避免重复启动解析（并发同 key 请求按第 8.2 节串行化）；解析失败后用户重新上传使用新的上传 operation，形成新资产。同 hash 的不同上传或不同 Workspace 不合并为一个资产。

### 7.7 资源限制与错误

以下为首轮建议默认限制，在实现时纳入 System 配置并用边界样例校准；W1-A 上传限制
与 parser 共用同一个 RAW 输入上限。输出、解压和结构上限独立计算，因此上传合规的
文件仍可能在解析阶段因输出超限进入 FAILED，这不属于上传状态回滚：

| 限制 | 建议默认值 | 执行位置 |
|:---|:---|:---|
| RAW 字节数 | 10 MiB | W1-A 分块接收；W1-B 再核对 |
| 提取正文 UTF-8 大小 | 8 MiB | 解码/提取过程中累计 |
| 完整 canonical 内容大小 | 16 MiB | 包含 locator/warning，受限序列化 |
| locator 数量 | 50,000 | 提取过程中累计，超限整体失败 |
| DOCX 包成员数 | 1,024 | ZIP 目录预检 |
| DOCX 单成员/全包声明解压大小 | 16 MiB / 32 MiB | 目录预检，并对实际读取字节计数 |
| DOCX 声明压缩比 | 100:1 | 按成员预检，覆盖零压缩长度异常 |
| XML 深度/节点数 | 128 / 200,000 | XML 流式遍历累计 |
| 单次解析预算 | 5 秒 | 可注入单调时钟，在读取和遍历检查点检测 |

只读取必要的包成员，不解压图片和嵌入对象；目录声明不足以代替实际读取上限。
实现使用增量读取、XML 遍历后释放已处理元素及输出计数，避免整包展开或反复复制正文。
这些是进程内输入和工作量限制，不是进程内存硬配额；协作式预算也不能中止卡住的库调用。
解析在 Store 锁外执行，必要时通过标准线程转交避免阻塞 HTTP/SSE 事件循环；本轮不承诺
强制终止、沙箱隔离或断连后的后台继续执行。

本轮不为每一种解析原因创建公共错误码。解析器返回内部的受控失败类别和安全文案参数，
W1-C 提交 `AssetSafeError(code="workspace.asset.failed", message=<safe message>)`；
`workspace.asset.failed` 是现有 Workspace 终态错误，表示 required representation 生成
失败。内部原因至少需要能区分以下情况，供日志、RuntimeEvent 和前端文案选择使用，但
不能作为客户端机器分支的稳定 code。首轮只需要三类内部失败类别：

| 内部失败类别 | 覆盖范围与用户可见处理 |
|:---|:---|
| `content_unreadable` | 覆盖非法编码、控制字符、损坏/加密 DOCX、不支持结构和空正文；提示转换为 UTF-8 或上传更简单、未损坏的 `.docx`，不回退为 TXT |
| `resource_limit` | 覆盖输入/解压/输出上限和协作式解析预算；提示文件过大或结构复杂，需要缩小后重新上传 |
| `execution_failure` | 覆盖 parser 异常、结果不符合契约和其他内部交接故障；返回通用解析失败文案，完整 cause 只进入受控日志 |

解析失败摘要的 `message` 只能是安全、可本地化的文案，不携带 traceback、路径、XML
片段或原始异常文本。内部原因可作为 RuntimeEvent 的摘要字段或受控日志字段，但事件
丢失不能改变 asset 已提交的 `FAILED` 事实。上传前已能确定的扩展名、媒体类型、空文件
和总字节数错误仍由 W1-A 的 HTTP 局部错误处理；解析器不重复创建 HTTP 错误语义。
身份/ref 归属不符、Store 已关闭/removed/stale 等交接问题沿用相应 Workspace 错误；
冻结 RAW 的实际 hash 与交接摘要不符属于内部交接故障，使用 `execution_failure` 收尾，
不包装成损坏文件。扩展名或媒体类型在上传前已由 W1-A 以 HTTP 415 拒绝；W1-B 不再
产生 `unsupported_format` 解析错误。如只能确定 DOCX 容器无效，则使用
`content_unreadable`，不能仅凭 ZIP 打开失败断言为加密。

### 7.8 实现落点与阶段出口

建议在 `src/hivememory/system/services/attachments/` 中放置窄 parser port、共享结果模型、
文本解码器、DOCX 提取器和固定格式分派。三个格式不需要 Provider Registry 或插件安装
生命周期；依赖由 assembler 注入应用服务。Store 只接收通用的冻结内容和提交命令，
不引入 DOCX/XML 依赖。

W1-B 的独立出口是：TXT、Markdown、DOCX 的真实 bytes 能转为符合第 7.5 节的内容，
或者得到第 7.7 节的受控失败原因和安全文案。W1-C 再验证这些结果如何进入 READY/FAILED；W1-E 消费同一正文和 locator，W1-E 复用来源 hash 作为本轮诊断坐标；W1-F 只持久化 binding.asset_ref。实施顺序见第 14 章，具体验收矩阵见第 15.4 节。

本轮实现时应先冻结上述成功结果、来源 hash、正文区间和安全错误这四个跨阶段契约，
再按真实 `.docx` 样本补齐包关系、命名空间和未覆盖结构。Transitional/Strict、压缩比、
XML 深度、warning record 和段落级 locator 是解析器的安全与可诊断实现约束；它们不应
被扩展为完整 OOXML 兼容层、版式还原器或独立文档 AST。表格网格、单元格级定位、合并
单元格语义和字段计算不在首轮承诺内；若样本证明某个结构无法在首轮稳定提取，应整体
归入 `content_unreadable`，而不是为了扩大覆盖范围引入新的资产类型。

## 8. W1-C：同步解析与 Asset 可用性

W1-C 接续 W1-A 的 RAW 注册和 W1-B 的内容转换，完成一次请求内的解析执行、结果提交和资产可用性确认。资产与 representation 的状态真相仍由 Store 持有；应用服务负责交接，parser 只返回内容或受控失败，HTTP/前端只展示 Store 快照。

本轮采用**同步、受控解析**：文件 RAW 注册后，在同一次上传请求中执行 W1-B parser，直到 `EXTRACTED_TEXT` 进入 `READY` 或 `FAILED` 才返回。W1-A 的前端 `uploading` 状态覆盖这段短暂等待；服务端不新增解析队列、任务 ID、状态查询路由或自动轮询。10 MiB RAW 上限、输出上限、结构计数和协作式预算共同限制单次请求的工作量。若真实样本证明同步解析会影响服务响应能力，再单独拆出异步队列计划，不在本轮预先引入。

### 8.1 状态与现有命令

本轮 TXT、Markdown、DOCX 都是 `kind="document"`，required kind 为 `EXTRACTED_TEXT`。沿用 [Store 命令](../../src/hivememory/system/runtime/workspace/store.py) 及 [现有模型](../../src/hivememory/core/models/workspace_asset.py)，不新增资产状态：

| 操作/时点 | RAW | EXTRACTED_TEXT | asset 聚合 |
|:---|:---|:---|:---|
| W1-A 原子注册完成 | READY | 尚未注册 | PROCESSING |
| `register_representation` | READY | PENDING，revision 1 | PROCESSING |
| `start_representation` | READY | PROCESSING，签发 parse token | PROCESSING |
| `complete_representation` | READY | READY，有内容与 hash，清除 token | READY |
| `fail_representation` | READY | FAILED，无内容/hash，清除 token | FAILED，有安全错误摘要 |
| `remove_asset` | 资产记录清除全部 representation | 同左 | REMOVED |
| `close_and_clear` | 进程内记录清空 | 同左 | Store 不可再访问，不新增 EXPIRED 状态 |

READY/FAILED 两行中 required representation 和 asset 是同一次临界区提交。RAW 在解析失败后仍留在 asset 中，但普通 reader 仍拒绝 FAILED asset；保留原文不代表它可用于 Chat。

revision 在当前 Store 的注册、启动、完成/失败过程中保持为 1，不是状态更新序号。`parse_operation_id` 只存在于 PROCESSING 快照，用作提交 guard，不作为前端任务 ID。同一 asset 不创建第二个 EXTRACTED_TEXT，也不支持将 FAILED 或 READY 原地重置为 PENDING。

### 8.2 请求内解析交接

W1-C 扩展 W1-A 的 `WorkspaceAssetApplicationService`，在同一个上传应用服务中完成解析，不再增加独立的 parser service、队列 runtime 或活动任务 registry。接纳顺序如下：

1. W1-A 完成文件校验和 RAW 原子注册，取得内部 `WorkspaceAssetHandle` 及新建/重放标记。重放如果已经存在目标 representation，则直接返回当前终态；不能重复 register/start。
2. 对 PROCESSING asset 检查 RAW READY 和 required kind。若尚无目标，依次调用 `register_representation()` / `start_representation()`；两条同步命令之间不插入 await。
3. 从 `start_representation()` 返回的完整快照取得 RAW bytes、RAW revision/hash、目标 representation id/revision/token 和固定 parser/version。解析输入来自该冻结快照，不调用只接受 READY asset 的 `resolve_asset()` 或 `acquire_ready_representation()`。
4. 在 Store 锁外执行 W1-B parser。parser 可以是同步函数；若其实现会阻塞事件循环，应用服务使用 `asyncio.to_thread` 等标准转交方式等待其结果，但不建立附件专用线程池、队列 lane 或独立任务状态。解析器只持有冻结 bytes，不持有 Store。
5. 成功结果经 W1-B 结果模型校验后，使用原 token 调用 `complete_representation()`；预期解析失败使用 `fail_representation(..., safe_error=AssetSafeError(code="workspace.asset.failed", ...))`。结果、失败或 token 竞争都由 Store 再次核对 scope、目标状态和 token。
6. 返回当前 Store 摘要。解析很快时直接返回 READY；解析失败返回 FAILED；请求处理期间前端只显示本地 `uploading`，不需要读取服务端 PROCESSING 状态。

上传请求的生命周期不再延伸为独立后台工作：HTTP 响应返回前，应用服务拥有这次 register/start/parse/complete-or-fail 交接；响应返回后不保留 parser 上下文。客户端断连、服务停止或 Store remove 与解析竞争时，仍由 token guard 防止晚到结果覆盖或复活资产；本轮不承诺断连后继续解析，也不提供恢复、取消或重试解析的专用接口。若解析已在独立线程中开始而外层等待被取消，应用服务必须在可执行的收尾点以原 token 尝试提交安全失败；无法取得结果时保留 Store 的既有状态错误，不通过新任务或第二个 representation 补偿。

同一 `(workspace_identity, client_operation_id)` 的并发上传请求在应用服务入口按 operation key 进程内串行化：等待方在持有方请求到达 READY/FAILED 终态或以错误收尾后才继续执行，随后命中既有重放或冲突路径。锁 key 与 Store 幂等索引同构，只包含 Workspace 与 operation identity，不包含文件内容；串行化是请求内 in-flight 互斥，不是持久化任务、队列 lane 或可恢复状态。由此任何上传响应只可能是终态快照或 A4 节定义的错误，不会出现 PENDING/PROCESSING 中间快照；等待时长以持有方请求的剩余解析预算为上界，等待方在等待期间被客户端断开时直接按取消收尾，不影响持有方提交。

PENDING 只是 register/start 之间的短过渡，不表示排队。Store 不变量被破坏属于内部故障，不能通过直接改模型或后台扫描恢复协议掩盖。

### 8.3 结果校验与原子提交

W1-B 的共享结果模型在 parser 返回前统一校验正文、format、locator、warning、内容大小和 canonical hash。W1-C 只核对结果来自本次冻结 RAW 且 producer/version 匹配，再提交；不实现第二套正文遍历、locator 校验或 canonical 序列化。结果类型或来源不符时使用内部 `execution_failure` 类别，并提交通用 `workspace.asset.failed`。

成功使用原 token 调用 `complete_representation()`；失败使用 `fail_representation(..., safe_error=...)`。W1-C 使用 token guard，不以恒为 1 的 revision 代替操作身份。Store 原子提交 required representation 与 asset 聚合状态，READY/FAILED 保留原 revision 和 producer/version 并清除 parse token。

| 场景 | 结果 |
|:---|:---|
| complete 与 fail 并发 | 首个有效提交决定终态，后者 stale，不能覆盖 |
| 重复 complete/fail 或 token 不匹配 | `workspace.asset.stale_result`，终态及内容不变 |
| remove 已先提交 | `workspace.asset.removed`，不能恢复内容 |
| 不同 Workspace 或未知 ref | 同为 `workspace.asset.not_found`，不泄露资产是否存在 |
| Store 已关闭 | `workspace.asset.operation_conflict`，details.reason 为 `store_closed` |

stale/removed/closed 后结束本次请求，不换 token 重试，也不把这些拒绝包装成文档损坏。

### 8.4 失败、资源预算与 HTTP 反馈

解析器和解析编排错误都以现有 `workspace.asset.failed` 作为 asset 的公共终态 code；具体原因只作为安全 message 的选择依据、RuntimeEvent 摘要或受控日志字段。首轮内部类别仍为：

| 内部类别 | 覆盖范围 |
|:---|:---|
| `content_unreadable` | 非法编码、控制字符、损坏/加密 DOCX、不支持结构和空正文 |
| `resource_limit` | 输入/解压/输出上限和协作式解析预算 |
| `execution_failure` | parser 异常、结果不符合契约或 Store 交接故障 |

上传前已能确定的扩展名、媒体类型、空文件和总字节数错误仍由 W1-A 的 HTTP 局部错误处理。RAW 注册成功后发生的 parser 失败，在同一上传响应中以 `asset.state=failed` 和安全摘要返回；不另设 `workspace.asset.parse.*` code。HTTP 只在请求尚未完成资产注册时返回上传错误或服务错误，不能把已经成功保存 RAW 的解析失败改写成“上传失败”。

本轮不新增 `GET /api/v1/workspace/assets` 的解析状态用途。W1-D 如需列出当前 Workspace 资产，可以复用既有 `list_workspace_assets()` 建立选择入口，但不依赖轮询来等待解析。前端在请求等待期间显示本地 `uploading`；收到 READY/FAILED 响应后更新附件项。页面刷新后，由于 Store 和 ref 本来只在进程内有效，是否恢复列表属于 W1-D 的资产选择设计，不由 W1-C 新增状态缓存解决。

### 8.5 System 生命周期与阶段出口

本轮不装配附件专用 `WorkQueueRuntime`、lane、executor、任务 registry 或 parser shutdown 步骤。`HiveMemorySystem.start/stop` 继续使用现有顺序；`WorkspaceAssetStore.close_and_clear()` 仍在已有消费者收尾之后执行。上传请求在 System 关闭接纳后不再开始新的解析，正在执行的请求由 HTTP/应用服务完成或在 Store 关闭时按既有错误收尾。

W1-C 的代码落点为 W1-A 的资产应用服务、`system/services/attachments/` 的 parser adapter 和结果模型，以及共享上传 DTO；不修改 `system/runtime/work_queue/`。阶段出口是：一个上传请求能在有界时间内得到 READY 或 FAILED，失败保留 RAW，重复请求不重复解析，Chat reader 只接受 READY asset。未来若实测请求时延、并发或 CPU 占用超过 MVP 目标，再以新的 Plan 引入后台队列和状态查询，不把本轮的同步契约悄悄改成异步。

## 9. W1-D：Chat 选择、resolve 与 lease

W1-D 把用户在当前 Chat 回合明确选中的附件交给主动对话链路。它只负责“选中了哪些
已经可用的 representation，以及这些选择如何安全地走到 Interaction”；正文如何进入
Agent prompt 留给 W1-E，成功 Interaction 后是否建立 binding 和如何物化留给 W1-F。
选择本身不是 Topic binding，也不能由上传顺序、当前 Topic 或最近资产列表隐式推导。

### 9.1 选择入口与本地状态

前端附件状态分为两种用途：上传队列保存文件和服务端回执，Chat 回合选择只保存
当前消息准备使用的已完成附件。两者不能用同一个布尔值表达：上传成功但解析
`FAILED` 的项仍可留在历史队列中，却不能进入选择集合。

附件选择入口应满足以下规则：

- 只有 `assetState=ready` 且 `required_representation.state=ready` 的队列项显示为可选；
- 用户可在发送前逐项选择、取消选择和重新排序；取消选择立即从本轮选择集合移除，
  不调用 Store，不创建 binding，也不删除已经上传的 asset；
- 发送期间冻结选择集合。发送后再上传或修改选择不会改变已经开始的 Chat run；
- 页面刷新不恢复旧 ref。当前 ref 与 Store 都是进程内 working set，刷新后必须重新
  上传或重新选择当前仍有效的资产；
- 多个入口（工作区附件条、composer 附件条和选择对话框）使用同一选择状态，避免
  UI 显示的选择与真正提交的选择不一致。

前端提交的是一个有序的附件选择数组，而不是正文或本地路径。建议请求字段固定为
`attachments`，每项至少包含 `asset_ref`；若 UI 已持有 representation 摘要，则一并
带上 `representation_id`、`revision` 和 `content_hash` 作为预期版本。客户端生成的
`asset_id` 只能作为显示或去重辅助，不能替代 opaque ref。

### 9.2 Chat 请求契约

`ChatRequest` 在现有 `message`、`agent_id`、`session_id` 和生成选项之外增加可选的
`attachments` 字段。首轮不接受任意 JSON 内容，字段采用严格对象数组并拒绝未知字段：

| 字段 | 语义 | 校验方式 |
|:---|:---|:---|
| `asset_ref` | 当前 Store 存活期内的 opaque ref | 必填，非空字符串，按请求 `IdentityScope` resolve |
| `representation_id` | 用户选择时看到的表示 ID | 可选；提供时必须命中该 asset 的 representation |
| `revision` | 客户端看到的表示 revision | 可选；提供时必须与当前表示相同 |
| `content_hash` | 客户端看到的表示 hash | 可选；提供时必须与当前表示相同 |

后端在 Chat 入口一次性冻结 `IdentityScope`。HTTP 层只校验字段类型与数组结构；ref、
Workspace 归属、asset 聚合状态、required representation 是否 `READY`、representation
kind/state 以及客户端提供的版本摘要，按第 9.3/9.6 节在 Patchouli prepare 边界经
`WorkspaceAssetReaderPort` 校验，不在 HTTP 层读取 Store。任何一项失败都拒绝整个 Chat
请求，不把部分选择静默降级为成功请求；使用现有 `workspace.asset.not_found`、
`workspace.asset.not_ready`、`workspace.asset.failed`、`workspace.asset.removed` 和
Store 已关闭时的 `workspace.asset.operation_conflict` 语义，由 HTTP/Chat 顶层按现有
错误边界翻译。`stale_result` 只属于 W1-C 的 parse token guard，`expired` 当前无生产
抛出点，均不适用于选择校验。

`attachments` 为空表示本轮不使用附件，与缺少该字段等价。相同
`asset_ref` 只能出现一次；若同一资产重复但指定不同 representation 或版本，视为
请求冲突而不是自动选择其中一项。顺序属于用户输入，必须在请求 canonical 表示中
保留；后续 W1-E 再决定内容编译时是否需要调整顺序。

### 9.3 resolve 与 lease 的所有权

上传应用服务继续拥有 `WorkspaceAssetStore` 的命令端口；Chat HTTP 路由和
`ChatApplicationService` 只负责冻结请求并通过现有 Global Bus 传递选择，不能直接读取
Store 私有状态。由于 `PreparedAgentRun`、finalize continuation 和
`InteractionSubmission` 都由 Patchouli 持有，resolve/acquire 应在 Patchouli 的 prepare
边界完成：由 `PatchouliService` 依赖注入已有的 `WorkspaceAssetReaderPort`，或由等价的
窄化 System adapter 完成读取。装配时传入进程级唯一 Store；不能让 Patchouli 自己创建
Store，也不能由 Perception 在 Interaction 提交时临时回查“当前选中的附件”。

prepare 按请求顺序逐项调用 reader 的 `acquire_ready_representation()`；该现有端口已经
在同一 Store 临界区完成 Workspace/ref、asset READY 和 representation READY 校验并建立
lease，因此不再先做一次独立的 `resolve_asset()` 读取。应用服务或 Patchouli 只检查返回
lease 的 asset ref、asset ID、representation ID、revision、hash 与请求摘要一致；检查失败
时释放已经取得的 lease，并拒绝整个 run。`resolve_asset()` 只用于需要展示完整 READY
asset 快照的列表/诊断入口，不能作为 acquire 前的授权检查。返回的 lease 集合按用户顺序
冻结，随本次 prepared run 传给后续编译边界；W1-D 不在此处拼接正文或估算 token。

lease 的生命周期覆盖从 prepare acquire、W1-E `AttachmentCompiler` 到主动
`InteractionSubmission` 完成或放弃的整个区间。prepare 失败时由 Patchouli 立即释放；
prepare 成功但未进入 finalize 时由 `cleanup_prepared_agent_run` 释放；进入 finalize 后由
finalization continuation 在 Interaction 和后置工作完成后释放。Chat application 的
统一 `finally` 只负责调用 prepared cleanup，不能在 stream 断开时抢先释放已被
continuation 接管的 lease。正常运行期的重复释放沿 Store 现有幂等语义处理；Store 已
关闭时，清理应容忍既有关闭错误并记录摘要，不改变已经确定的 Chat 终态。Chat run
结束后不得把 lease 留在全局状态或前端。

remove 早于 acquire 时，reader 按现有 Store 语义拒绝本轮，不建立任何 binding；acquire
早于 remove 时，已有 lease 保存冻结 representation，允许本轮继续使用，但同一 ref 的
后续 resolve/acquire 必须失败。W1-D 不修改 `remove_asset()` 或 lease 的底层语义。

### 9.4 Prepared run 与 AttachmentCompiler 的交接

当前 `PreparedAgentRun`/`AgentRunContext` 只包含消息、Topic、记忆检索结果和 Agent
profile。W1-D 应增加一个明确的附件选择载体，至少保留：用户选择顺序、asset ref、
asset ID、representation ID、revision、content hash，以及当前进程内的 lease 关联。
该载体是本轮运行快照，不是新的 WorkspaceAsset 状态，也不写入 `MemoryAtom`。

`ChatApplicationService` 将 `attachments` 作为 prepare route 的显式参数传入
`PatchouliService.prepare_agent_run`；后者把已验证的选择/lease 写入
`PreparedAgentRun`/`AgentRunContext` 的附件载体，不在 Alice 或 Perception 再次解析 ref
或创建第二个 lease。W1-E 将使用同一快照读取 representation 内容并生成 Agent
context；若 `AttachmentCompiler` 决定跳过或截断某项，必须显式记录诊断，不能修改 W1-D 已冻结的用户
选择。W1-D 的阶段出口只要求选择、版本坐标和 lease 关联完整到达编译边界。

### 9.5 InteractionSubmission 交接与 retry

W1-D 为 `PreparedAgentRun` 到 `InteractionSubmission` 冻结一份有序的附件选择坐标，
至少包括 `asset_id`、`asset_ref`、representation ID、revision 和 content hash；只传坐标，
不复制正文。该字段用于让 W1-E/F 在 finalize 中继续使用同一份选择事实，不能让 handler
根据文件名、asset 列表或“当前选择”重新推导。

`InteractionSubmissionCodec` 必须把这份附件选择数组纳入 exact-key canonical JSON；
decode 后重新编码必须与原始 payload 完全相等。由于当前 codec 的 `schema_version=1`
和 exact-key 约束，增加字段时应提升 submission schema version（或明确提供只读的 v1
兼容 codec），并同步更新 queue 注册和 passive submission 的空数组投影；不能在 v1
payload 中偷偷加入可选键。W1-D 不把选择数组直接作为
`asset_id_and_refs` 传给 `PerceptionFamiliar.apply_interaction()`，因为该参数会在当前
实现中立即建立 `TopicAssetBinding`，而此时尚未知道哪些 representation 实际进入了
`AttachmentCompiler`。W1-F 在拥有 W1-E 的实际使用集合后，才把对应的
`(asset_id, asset_ref)` 交给 Perception；W1-D 只冻结并保留可供该步骤使用的坐标。

实现时必须把两个概念分开命名：`selected_attachments` 是 Chat 请求中用户选择并由
W1-D 冻结的数组；`used_attachments` 是 W1-E 根据实际进入上下文的 representation 生成
的数组。前者可以包含因预算、内容为空或编译策略而未进入上下文的项目，后者才允许投影
为 `asset_id_and_refs` 并参与 `compute_apply_digest()`。如果实现只保留一个数组，必须
证明编译跳过项目不会被误绑定，否则不得进入 W1-F。

同一 `interaction_id` 的 retry 必须携带完全相同的附件选择顺序、ref 和版本摘要；这些
字段先通过 submission 的 canonical payload 保持等价。当前 `compute_apply_digest()` 只
接收用于 binding 的 `(asset_id, asset_ref)` 且会按 ref 排序，因此 W1-D 不把它描述为
representation 版本或用户顺序的校验器；W1-E/F 在确定 `used_attachments` 后，retry
只须保持同一份 ref 坐标，不能重新推导、替换 ref 或按当前 Store 列表重算选择。representation
版本是否固定由 `WorkspaceAssetRef` 的独立语义决定。这样既复用现有 `TopicAssetBinding` 语义，也不在 W1-D 新增 binding 类型或提前产生 binding。

### 9.6 失败、取消与资源竞争

请求字段和数组结构在 HTTP body 校验阶段拒绝；ref、READY 状态和版本摘要校验发生在
Patchouli prepare、Alice 尚未启动且 Interaction 尚未提交之前。当前 Chat 主链路会先创建
`ChatGenerationRun` 并执行 Gateway，因此附件拒绝不应被描述为“没有创建任何 Chat run”；
它必须保证没有 Alice agent run、Interaction、Topic binding 或资产状态改写。现有
prepare 若已经为 `NEW_TOPIC` 创建空 Topic，失败路径必须沿既有 prepared cleanup 删除该
空 Topic。acquire 之后的异常按已取得 lease 的数量逐项释放，原始错误沿现有
Chat/Workspace 边界传播，不把附件问题伪装成空消息或自动移除选择。

用户取消或 Chat stream 断开时，Chat application 仍按现有 run cancellation/cleanup
流程收尾，并保证 lease 在该流程结束前释放；在尚未 admission 时取消不会提交
Interaction。Interaction 已被 queue 接纳后，现有 finalize continuation 仍可能完成已接管
的业务义务，lease 释放点由 continuation 持有，不能因为 HTTP stream 提前结束而提前释放。

### 9.7 实现落点与阶段出口

实现集中在现有边界：扩展 `server/models/chat.py` 与 `frontend/src/types/chat.ts` 的
请求模型，扩展 Chat application 和 Patchouli public prepare route 的参数，在 Patchouli
prepare/finalize 生命周期中使用 `WorkspaceAssetReaderPort` 完成 resolve/acquire/release，
扩展 `PreparedAgentRun`、`AgentRunContext`、`InteractionSubmission` 及其 codec，并在
前端附件队列之上增加选择状态和发送时冻结逻辑。不新增附件专用 Store、持久化 ref、
状态查询路由或第二套 Interaction 队列。

W1-D 的阶段出口是：

- Chat 只能提交当前 Workspace 内、required representation 为 `READY` 且版本摘要一致
  的附件；无效、过期、removed、failed 或 processing 选择会拒绝整个请求；
- 选择顺序、ref 和版本摘要从 Chat 请求进入 prepared run，再进入 canonical
  `InteractionSubmission`，retry 不重新推导或替换来源；
- lease 覆盖 prepare acquire、AttachmentCompiler 和 Interaction finalize，所有成功、失败、
  取消和竞态路径均释放；
- 选择坐标能完整交给 W1-E/F，但 W1-D 自身不调用 `asset_id_and_refs`，因此取消选择、
  仅上传或仅解析不会产生 `TopicAssetBinding`。

### 9.8 W1-D 不在本阶段完成的内容

- representation 正文的 `AttachmentCompiler` 编译、分片、token 预算、locator 选择和编译诊断；
- 成功 Interaction 后 binding 的实际建立条件、ref 传递和 Artifact promotion；
- 附件 ref 的持久化、跨进程恢复、服务重启恢复和页面刷新恢复；
- Agent 主动解析、MTP `RUN`、沙箱执行和外部 Plugin 接入。

## 10. W1-E：AttachmentCompiler

W1-E 将 W1-D 已验证的 representation lease 编译为本轮 Agent 可消费的附件上下文产物。`AttachmentCompiler` 是独立于 `MemoryCompiler` 的组件：它不接收 `MemoryAtom`，不使用 `MemoryCompileTarget`/`MemoryEnvelopeTarget`，不产生 Memory artifact，也不负责 WorkspaceAsset 状态迁移。它的职责是把已选中的附件内容转换为受约束、可定位、可追溯的 prompt 片段，并明确哪些选择实际进入了 Agent 上下文。

### 10.1 组件边界与调用位置

`AttachmentCompiler` 的输入来自 `PreparedAgentRun` 中冻结的附件选择和 lease。本轮固定由
Patchouli prepare 阶段调用：这样 representation 读取、lease 持有和附件编译处于同一条
prepared-run 生命周期内，且 Patchouli 可以在进入 Alice 前确定 `used_attachments`。Alice
侧的 `AgentPromptAssembler` 只接收编译产物并负责最终组装，不直接读取 Store 或调用
`AttachmentCompiler`。

组件之间的调用关系固定为：

```text
W1-D selected_attachments + leases
  -> AttachmentCompiler
  -> AttachmentCompileResult
       ├─ attachment_context (prompt-ready attachment section)
       ├─ used_attachments (actual source coordinates)
       └─ diagnostics
  -> AgentRunContext.attachment_compile_result
  -> AgentPromptAssembler
       ├─ MemoryCompiler output: memory_context
       └─ AttachmentCompiler output: attachment_context
  -> Agent messages
```

`AgentPromptAssembler` 是最终文本/消息组装者，不负责解析附件、读取 lease、重新分片或
重新计算 token。`MemoryCompiler` 仍在 Patchouli 侧生成
`AgentRunContext.memory_context`；`AttachmentCompiler` 只生成一份
`AttachmentCompileResult`。`AgentRunContext` 不再另设独立的附件文本字段，
`AgentPromptAssembler` 从结果中的 `attachment_context` 读取附件 section，并按冻结的 section
顺序与 memory context 汇合。

### 10.2 输入契约

输入至少包含：

| 输入 | 来源 | 约束 |
|:---|:---|:---|
| `selected_attachments` | W1-D Chat/prepare snapshot | 保留用户顺序；不可由 compiler 修改 |
| `RepresentationLease` | W1-D Patchouli prepare | 必须对应 selected ref、asset、representation、revision 和 hash |
| `AttachmentCompileLimits` | Patchouli/System 配置 | 明确最大附件字节、片段数、单片段长度和总 token/字符预算 |

compiler 不接受裸 ref、asset id、本地路径或 RAW bytes 作为独立输入；所有正文必须来自
lease 中冻结的 READY representation。缺少 lease 或坐标不一致属于编译前置契约错误，不能
自动重新 acquire 或回退读取 Store。

### 10.3 内容编译与分片

首轮 representation 是纯文本或 Markdown，因此 `AttachmentCompiler` 不做 PDF/OCR、版面
重建或语义摘要，只执行确定性的文本组装：

1. 按 `selected_attachments` 顺序处理每个 lease；
2. 为每个附件生成稳定的附件 section，包含受控的 display name、media type 和来源坐标；
3. 保留 TXT 原文和 Markdown 语法，不把 Markdown 渲染成 HTML，也不把正文解释为指令；
4. 按固定规则切分过长正文；chunk 只是 compiler 内部处理步骤，只有实际保留内容的
   locator 进入 `used_attachments`；
5. 生成适合 `AgentPromptAssembler` 使用的 prompt-ready section，不把完整内容复制到
   `InteractionPayload` 或 `InteractionSubmission`。

附件 section 的外层标记、字段顺序、换行和转义规则必须是确定性的；display name 只作为
展示元数据，不能成为寻址依据。正文中可能包含类似 MTP/XML/Markdown 指令的文本时，
compiler 只保留其字面内容，并由 section 边界明确它是附件资料，不提升为系统指令。

### 10.4 预算、选择和降级规则

实现前需要冻结以下规则：

- 多附件严格沿用户选择顺序处理；同一 asset 在 W1-D 已去重，compiler 不重新排序；
- 预算至少包括单附件最大内容、单 chunk 最大长度、全部附件总长度和总 token/字符预算；
- 超出预算时按固定策略处理：首轮建议在可安全切分时保留前部完整 chunk，并返回明确
  `truncated` diagnostic；如果连一个完整 chunk 都无法保留，则返回编译失败，不静默生成空
  section；
- 内容为空、locator 无效、lease 内容类型错误或版本摘要不一致时，该附件不能进入
  `used_attachments`；若其他附件仍可安全编译，返回 warning 与被跳过明细；若用户选择的
  附件全部被跳过，则返回错误而不是空成功；
- compiler 不因“无法理解正文”而调用 LLM，不做自动摘要、翻译或意图推断；
- compiler 只生成本轮产物，不创建 TopicAssetBinding、Artifact 或 MemoryAtom。

warning 只能表示仍有可消费的附件上下文；全部选择无法编译时应按现有 Chat/控制异常边界
失败。具体公共错误 code 复用现有 Workspace/Chat 错误语义，不新增 `attachment.compile.*`
错误码；编译诊断使用结构化 `message_key + params` 或内部诊断字段，不能把正文、路径或
异常栈写入公共错误 message。

### 10.5 输出契约

`AttachmentCompileResult` 只保留三类信息；chunk、逐项预算计数等只是 compiler 内部实现
细节，不单独成为跨组件数据模型：

| 输出 | 语义 |
|:---|:---|
| `attachment_context` | 供 `AgentPromptAssembler` 注入的一段确定性附件 section；仅当本轮未选择任何附件时为空，已选择但全部被跳过属于第 10.4 节的编译失败 |
| `used_attachments` | 实际进入 `attachment_context` 的 asset/ref/representation/revision/hash 坐标；需要引用定位时附带 parser locator |
| `diagnostics` | skipped、truncated、warning 和必要的预算摘要等安全结构化信息 |

`used_attachments` 是 W1-F 投影 binding 的唯一输入，不等同于 `selected_attachments`。
它可以携带 lease 提供的 representation 元数据和 locator 供本轮诊断使用，但这些信息不进入
长期 Topic 或 Interaction binding；后续内容读取始终沿 `asset_ref` 完成。结果对象应不可变，
retry 只序列化其中的 ref 坐标和必要诊断摘要，不把 `attachment_context` 写入长期记录。

### 10.6 AgentPromptAssembler 交接

扩展 `AgentRunContext` 时只增加可选的 `attachment_compile_result`，保留现有
`memory_context` 不变。`AgentPromptAssembler.build_main_agent_messages()` 从结果读取
`attachment_context`，按固定顺序调用 prompt builder：MTP/系统通知、persona、`memory_context`、
附件 `attachment_context`、topic state。具体 section 顺序必须在实现前冻结并有快照测试。附件
section 只能作为普通上下文注入，不改变 MTP 权限、工具白名单或 MemoryCompiler target。

`AgentPromptAssembler` 不需要知道 WorkspaceAssetStore、WorkspaceAssetRef 的解析规则或
lease API；它只消费 `AttachmentCompileResult.attachment_context`。子 Agent 是否继承附件
上下文不在 W1-E 默认范围内，除非后续明确把该产物加入 `shared_context`，不能通过隐式
复制主 Agent prompt 扩大范围。

### 10.7 lease、finalize 与 W1-F 交接

AttachmentCompiler 成功或部分成功后，lease 继续由 prepared-run/finalization continuation
持有，直到 Interaction apply 和必要的 settlement 交接完成。compiler 失败、Chat 取消、
Alice 启动失败或 finalize 未接纳时，沿 W1-D 的统一 cleanup 释放 lease。

W1-E 只输出 `used_attachments` 和编译诊断，不调用 `PerceptionFamiliar.apply_interaction`或创建 binding。W1-F 在 Interaction 成功边界取得这份临时结果后，只把对应的 `(asset_id, asset_ref)` 投影给 Perception；不另建使用明细，也不把 representation revision/hash/locator 复制到 settlement 载荷。

### 10.8 实现落点与阶段出口

建议新增独立组件目录 `src/hivememory/engines/attachment_compiler/`（或同责任边界的
等价目录），包含 compiler、输入/输出模型、chunk/locator 处理和资源限制。它不得放入
`engines/memory_compiler/`，也不得复用 `MemoryCompiler` 的 source 校验和 target 枚举。
Patchouli prepare 负责调用并把结果写入 `AgentRunContext`；Alice prompt assembler 负责
最终注入；W1-F 负责消费 `used_attachments`。前端不接触 compiler 内部结果，只在需要时
显示安全诊断。

W1-E 阶段出口：

- `AttachmentCompiler` 能对单附件和多附件生成确定性、可分片、可定位的 prompt section，并在 Patchouli prepare 阶段完成；
- `selected_attachments` 与 `used_attachments` 明确分离，预算截断/跳过不会错误建立 binding；
- `AgentRunContext` 同时携带 `memory_context` 和单一的 `attachment_compile_result`，二者由
  `AgentPromptAssembler` 统一组装；
- compiler 不读取 Store 私有状态、不执行 Agent/MTP/Plugin、不创建 Topic/Artifact/Memory；
- lease 覆盖 compiler、Alice run 和 finalize 交接，所有错误、取消和 retry 路径均有收尾；
- 输出中的 ref 坐标能被 W1-F 投影为 binding；revision/hash/locator 仅供本轮编译诊断，
不形成长期 provenance。

## 11. W1-F：Interaction binding 与 Materialization promotion

W1-F 将 W1-E 的实际使用结果接入现有 Interaction、Topic settlement 和 Memory generation
链路。`TopicAssetBinding` 是 Topic 范围内“附件已被使用”的唯一持久化记录；
`selected_attachments` 和 `used_attachments` 只属于本次运行的临时交接，不得再写入第二份
长期使用明细。

### 11.1 成功 Interaction 建立唯一 binding

`AttachmentCompiler` 在 finalize 阶段返回的 `used_attachments` 只携带附件引用坐标，
不携带正文。Patchouli handler 从这份结果一次性投影现有
`PerceptionFamiliar.apply_interaction()` 的 `asset_id_and_refs` 参数；调用方不能另行提交
一份可能不一致的附件集合。

Perception 仅在 Interaction 成功 apply 的同一 Topic 快照更新中，把去重后的
`(asset_id, asset_ref)` 写入现有 `TopicAssetBinding`。binding 继续由 Topic 所有者维护，
按 `asset_id` 幂等去重，并保留现有的首次交互和绑定时间语义。取消选择、编译跳过、预算
未保留、Interaction admission/apply 失败和 retry 冲突均不建立新 binding。

`used_attachments` 可以参与本次 Interaction 的 canonical digest，以保证同一
`interaction_id` 的 retry 不能替换 ref；但 digest 和运行日志都不能把正文或 lease 写入
长期载荷。成功 Interaction 之后，附件使用事实只从 `TopicData.bindings` 读取。

### 11.2 Settlement 只冻结 binding，ref 是后续读取入口

`TopicMaterializeTask` 在删除 Topic 前复制 `TopicData.bindings`，并通过现有 queue codec 传入 `InteractionArtifactInput.asset_bindings`。W1-F 不新增 `attachment_uses`、版本明细集合或第二套 provenance 记录；也不把正文、representation snapshot、lease_id、临时路径或文件 bytes 写入 Topic、task、queue 或 Memory 数据。

`TopicAssetBinding.asset_ref` 是附件内容的唯一后续读取入口：任何 Materialization、Artifact promotion 或其他需要正文的步骤，都必须在其自身处理范围内通过
`WorkspaceAssetReaderPort` 按 ref resolve/acquire READY representation，使用 lease 读取，并在完成后 release。不得根据 asset 列表、display name 或当前选择状态重新推导 ref，也不
得直接访问 Store 私有状态。

ref 是当前 WorkspaceAssetStore 生命周期内的 opaque 引用，不是永久 ID 或物理路径。当前
binding 只保存 asset/ref，不冻结 representation revision；因此 W1-F 不宣称跨版本的
revision/hash provenance。若后续要求 retry 必须读取同一 representation，应先单独调整
`WorkspaceAssetRef` 的快照语义或建立明确的 representation 引用契约，而不能通过新增第二
份使用记录绕过该问题。

### 11.3 Memory generation 与可选 Artifact promotion

Generation queue/Coordinator 继续只传递 `InteractionArtifactInput.asset_bindings`；
Memory generation 仍由现有 `MemoryCompiler` 和 `MemoryGenerationFamiliar` 负责，附件
binding 不改变 MemoryAtom schema、MemoryType 或生成判定。只有确实产生 Memory
CREATE/UPDATE 时，Artifact 流程才考虑对相关 binding 做 promotion；上传、解析、选择、
编译、TOUCH 和 DISCARD 不生成附件 Artifact。

promotion 复用已有 `DocumentArtifactBuilder`/`ArtifactStore` 的 append-only 接口。实现前需冻结从 binding/ref 取得的 representation 元数据到 `DocumentArtifact` 的最小映射；映射必须包含源 asset/representation 标识、representation revision、content hash 与 parser producer/version，使提升产物自身钉住来源版本（与 ROADMAP 的 promotion metadata 要求及 [ADR-0003](../architecture/decisions/0003-memory-as-a-tool-and-mtp-run-boundary.md) 的消费版本冻结不变量一致）。若映射尚未确定，W1-F 仍可完成 binding 和 settlement，但不把 promotion 计为已完成。

promotion 的执行步骤固定为：读取 task 中的 binding ref、在当前 Workspace scope 下
acquire READY representation、构建 Artifact、释放 lease。promotion retry 复用现有
Materialization/Memory generation operation identity 和同一 binding payload，不通过当前选择或最新 asset 列表替换来源。Artifact 写入失败沿现有 best-effort 语义记录 warning，
不回滚已经成功的 Interaction、binding 或 Memory 结果。

若 Interaction 成功后 asset 被 remove，或 Materialization 时 Store 已关闭，已提交的
binding 保持不变；promotion 不尝试使用旧 ref 恢复正文。无法重新取得内容时跳过该
promotion 并记录结构化 warning，沿用现有 Workspace/Artifact 错误语义，不新增附件专用
错误码。prepare 阶段尚未成功使用前发生 remove/expired，则仍按 W1-D 的
`workspace.asset.*` 错误终止本轮。

### 11.4 实现落点与阶段出口

实现集中在现有结构化交互与结算边界：扩展 `InteractionPayload` 以承载本轮
`used_attachments`；它随 submit 进入 canonical submission payload，受第 9.5 节的
exact-key 与 schema version 规则约束，不是旁路短期字段。扩展 `TopicMaterializeTask`、
`InteractionArtifactInput` 及其 queue codec 以传递已有 `asset_bindings`；Perception 在
apply 时由实际使用结果投影 binding，Generation Coordinator 和 ArtifactEngine 通过 ref
完成后续读取。不得在
`WorkspaceAssetStore`、`TopicAssetBinding` 或 `MemoryAtom` 上复制另一套附件使用状态。

W1-F 阶段出口：

- 只有成功 Interaction 且实际进入上下文的附件才建立 `TopicAssetBinding`；
- Topic settlement 和 generation queue 只传递 binding，附件正文始终留在 WorkspaceAssetStore；
- Materialization/Artifact promotion 通过 `asset_ref` acquire 内容并正确释放 lease；
- ref 失效或 Store 关闭时不破坏已提交的 binding，promotion 按既有 best-effort 语义降级；
- 不新增附件使用记录、MemoryType、Topic binding 类型、WorkspaceAsset 状态或 MTP/Plugin 执行路径。

## 12. 契约与数据变更

首轮实现需要冻结以下契约，具体字段名称可以在实现前根据现有 port 命名统一：

1. 上传请求、上传结果和用户选择请求；
2. 第 7 章定义的 parser 输入/输出、内容 canonical hash、locator、内部失败类别和 warning record；
3. 第 8 章的请求内解析接纳、token 提交 guard、资源预算及上传结果 DTO；
4. AttachmentCompiler 的 attachment selection、locator、budget 和诊断，以及 `AgentRunContext.attachment_compile_result` 与 `AgentPromptAssembler` 的交接；
5. W1-F 不新增第二份附件使用记录；需冻结的仅是 `TopicAssetBinding` 字段形状、ref 传递和后续 acquire 语义。若未来要求固定 representation 版本，应先形成独立 ref/representation 契约，否则不纳入本轮 Artifact promotion 承诺；
6. Materialization task 使用的 `TopicAssetBinding.asset_ref` 传递结构和 reader acquire 语义；
7. 文件大小、媒体类型、文本编码、解析耗时和解析输出上限。

本计划不修改 `MemoryAtom` schema，不新增 MemoryType，不改变当前 `ArtifactType` 枚举，也不改变 MTP `RUN` 当前只允许系统注册工具（Kernel syscall）和 `CODE_SNIPPET` 的公共契约。错误语义遵循 [Error Model](../contracts/error-model.md)：解析原因不注册为新的公共 `workspace.asset.parse.*` code，asset 终态统一使用现有 `workspace.asset.failed`；因此实现收尾时无需为解析原因扩展 `error-model.md` 的稳定 code 表。若未来调用方需要按解析原因改变机器行为，应先形成独立契约或 ADR。若实现证明必须改变这些边界，应先拆出独立 ADR 或 Plan。

## 13. 兼容与迁移

- W0 已存在的 WorkspaceAsset 模型、reader/command port、opaque ref、lease 和 Topic binding 语义保持兼容；
- 当前没有可恢复的附件持久化数据，因此本计划不包含历史附件迁移；
- WorkspaceAsset、representation、ref 和 lease 仍只在当前进程 Store 生命周期内有效；
- 服务重启后旧 ref 失效，用户必须重新上传；
- 已有 Memory、Artifact、Topic 和 Chat run 不因附件功能上线而批量改写；
- MTP `RUN` 的现有 `CODE_SNIPPET` 行为保持不变；附件 parser 不通过该路径执行；
- 若后续接入 PDF 或其他 parser，新增 parser 不得改变已经成立的 RAW、READY、lease 和 binding 语义。

## 14. 实现阶段安排

实现按“先建立资产入口，再建立表示可用性，最后接入对话使用和物化”的顺序推进。
每一阶段都应先完成本阶段需要冻结的跨边界契约，再实现代码和测试；阶段之间通过可观测
的 Store 状态或交接对象衔接，不以未定义的临时字段跨阶段传递。

### 14.1 阶段顺序与依赖

| 阶段 | 主要工作 | 可开始条件 | 阶段出口 |
|:---|:---|:---|:---|
| W1-A | 上传路由、上传应用服务、前端拖拽/选择、RAW 原子注册 | W0 WorkspaceAssetStore、IdentityScope 和 opaque ref 契约可用 | 合规文件能生成 asset、RAW `READY` 和 ref；幂等与 Workspace 隔离通过 |
| W1-B | TXT/Markdown 解码、DOCX 正文提取、统一文字内容与资源限制 | W1-A 可返回冻结 RAW 快照，应用服务交接已明确 | 三类格式均输出确定性正文、locator、hash 或安全失败摘要 |
| W1-C | 请求内解析、required representation 状态提交和上传结果返回 | W1-B 已确定 parser 输出和版本身份 | `EXTRACTED_TEXT` `READY` 才开放 asset；过期结果不能覆盖；上传响应可观察终态 |
| W1-D | Chat 附件选择、resolve、lease 和 InteractionSubmission 交接 | W1-C 能提供 READY representation | 显式选择能进入本轮交接，retry 不替换来源 |
| W1-E | AttachmentCompiler、预算、分片、locator 和诊断 | W1-D 的选择与 lease 交接已冻结 | Agent run 能消费编译结果并报告实际来源 |
| W1-F | Topic binding、settlement 和 Artifact promotion | W1-E 能输出本轮实际使用的附件 ref | 只有成功 Interaction 建立 binding，promotion 沿 binding.asset_ref 读取且幂等 |

W1-A 的后端 Store 命令、HTTP DTO 和前端运行态模型需要先共同冻结；后端路由与前端
拖拽队列可以在契约冻结后并行开发，但必须以同一个 multipart 字段、operation identity
和响应 DTO 联调。W1-B 与 W1-C 可以在 parser port 确定后由不同协作者并行推进，但
representation 状态转换和 parser 输出提交必须先约定 revision/token guard。W1-D 之后的
阶段依赖真实的 READY representation 和可重放的 Interaction 交接，不能用只返回文本的
测试捷径代替这些边界。

### 14.2 每阶段实施活动

1. **W1-A 实施**：先增加上传专用的 Store command 和应用服务测试，再接入 HTTP router；
   前端同时建立统一的文件入口、非持久化队列和 `attachmentApi`。后端单元测试证明
   原子注册与幂等，路由集成测试证明 multipart、错误状态和 scope 隔离，最小浏览器测试
   证明页面 drop 不导航。
2. **W1-B 实施**：先冻结第 7 章的格式表、转换规则、结果样例、canonical 编码和限制配置，
   实现 TXT/Markdown 共享解码及 locator；随后增加 DOCX 包校验、XML 正文提取及
   `defusedxml` 依赖。以固定 bytes 样本逐项验证文字、顺序、locator、warning 和错误，
   最后让固定格式分派接入应用服务；本阶段不依赖 LLM 或 Word 环境。
3. **W1-C 实施**：接入 `register_representation`、`start_representation` 返回快照与 token
   的解析交接，以及 `complete_representation` / `fail_representation`；在 Store 锁外执行
   真实 parser，必要时使用 `asyncio.to_thread`，再通过原 token 原子提交 READY/FAILED。
   随后联调上传响应、重复请求、断连、remove 和资源预算，证明 RAW 输入可处理而 Chat
   reader 仍拒绝提前使用，所有用户可见状态来自 Store。
4. **W1-D 实施**：先冻结 `selected_attachments` 的 Chat/prepare 契约和 submission
   schema version，再把进程级 Store reader 注入 Patchouli prepare 生命周期；随后扩展
   `PreparedAgentRun`、`AgentRunContext` 与 `InteractionSubmission` 的 canonical codec，
   接入前端选择状态和发送请求。通过 acquire/lease 集成测试验证 remove race、重复选择
   去重和重试 digest，并用编译跳过样例证明 `selected_attachments` 不会被误投影为
   `used_attachments` 或 Topic binding。
5. **W1-E 实施**：先实现独立 `AttachmentCompiler` 的输入/输出模型、确定性 section 和
   chunk/locator 规则，在真实 representation 快照上确定单附件、多附件、预算和诊断行为；
   再由 Patchouli prepare 调用并把结果接入 `AgentRunContext`，最后扩展
   `AgentPromptAssembler`，将 `memory_context` 与 `attachment_compile_result.attachment_context` 按固定顺序统一组装。
   编译诊断先在应用服务和测试中稳定，然后再添加前端的选择反馈，避免 UI 先假定未冻结
   的截断规则。
6. **W1-F 实施**：最后接入 Perception 的 binding 参数、settlement task 的 binding 快照和
   Materialization promotion。先验证成功 Interaction、取消/失败 Interaction 不产生
   错误 binding，再验证 ref acquire、remove、retry 和 Artifact 映射；DocumentArtifact 映射
   未冻结前不把它作为实现默认值。

### 14.3 联调与阶段门

每个阶段完成后进行一次从上一阶段真实出口开始的联调，不跨过中间状态直接调用末端
组件：

- A 门：HTTP 上传结果与同一 Workspace 的 Store 命令快照及资产列表一致，RAW revision/hash
  与响应一致；只有 RAW 的文档仍为 PROCESSING，reader resolve/acquire 必须拒绝；
- B/C 门：三类批准格式通过冻结 RAW 快照交给 parser，结果经 Store 命令提交；只有
  required representation READY 后 reader 才开放；上传重放不重复解析，解析失败和资源
  超限有终态收尾，上传响应能直接观察 READY/FAILED；
- D 门：Chat 请求携带的附件选择经过 canonical codec 后仍保持相同 ref 和版本摘要；
- E 门：Agent context 能报告实际纳入的 locator、revision/hash 和预算诊断；
- F 门：成功 Interaction 才产生 binding，settlement 后的 Materialization 不依赖已清理
  的 Topic buffer，并能通过 binding.asset_ref 重新 acquire；ref 失效时按既有降级语义收尾。

阶段门未通过时，后续阶段只能继续完善不依赖失败出口的代码和测试，不得通过在调用方
增加隐式 fallback、直接访问 Store 私有状态或自动选择附件来绕过门槛。

## 15. 测试与验收

### 15.1 Unit

放置于 `tests/unit/`，验证单一行为单元，协作者使用真实的轻量对象或手写 fake：

- 上传元数据规范化和格式限制；
- parser 的确定性输出、unsupported 格式和安全错误摘要；
- representation revision/token 校验；
- READY/FAILED 状态迁移和 required representation 规则；
- AttachmentCompiler 的单附件、多附件、去重、预算和 locator 行为；
- invalid ref、remove、过期 revision 和编译失败的稳定错误。

### 15.2 Integration

放置于 `tests/integration/`，使用真实 WorkspaceAssetStore、TopicData/Perception 和 Materialization 协作边界：

- 上传到 RAW、解析到 READY 的完整内部链路；
- parser 结果通过 Store 命令提交，而不是直接修改模型；
- acquire lease、AttachmentCompiler 编译、Interaction 成功后的 TopicAssetBinding；
- remove-before-acquire 与 acquire-before-remove；
- settlement 在 buffer 清理前冻结 binding，Materialization 通过 `binding.asset_ref` 重新 acquire；
- `InteractionSubmission` 的 canonical codec 能原样保留已校验的选择坐标，重试或重复提交不会重新推导或替换附件关系；只有 W1-E 产出的 `used_attachments` 才能在 W1-F 投影为唯一 binding；
- 两个 Workspace 的同名资产、ref 和 binding 隔离；
- Artifact promotion 成功、失败和幂等重试。

### 15.3 E2E

放置于 `tests/e2e/`，从公开 Chat/上传入口进入，使用确定性协议 fake，断言用户可观察响应、状态和持久化结果：

- 上传、选择附件、完成对话并观察上下文使用和 Topic binding；
- 上传或解析失败时用户收到稳定错误且不会生成错误 binding；
- 取消选择或 remove 后，后续 Chat 不会继续使用不可用 representation；
- 成功 Interaction 后的 Materialization 能通过 `binding.asset_ref` 取得附件，失效时按既有降级语义收尾。

新增测试必须能够在对应生产行为被破坏时失败，断言输入输出、状态迁移和持久化副作用，不以 mock 调用次数或刚注入的 mock 返回值作为主要证据。涉及请求内解析使用 parser 返回事件或有界等待，不使用固定 sleep；使用临时文件时使用 `tmp_path`。

### 15.4 W1-B 解析专项验收

本节用小型、可审阅的固定内容验证第 7 章的设计。正文、locator 和 canonical JSON/hash
采用独立确认的预期值，不在测试中调用生产转换逻辑计算期望。DOCX 样本包含最小包和
少量真实 Word 导出文件，确保 ZIP/XML 测试替身没有掩盖实际格式差异。

| 测试边界 | 输入/场景 | 必须区分的正确行为与缺陷 |
|:---|:---|:---|
| Unit：格式分派 | 大小写扩展名、MIME 缺失/通用类型/明确冲突、旧版 DOC/PDF | 批准格式进入确定分支，不支持格式稳定拒绝，DOC 提示另存为 DOCX |
| Unit：文本解码 | UTF-8、UTF-8 BOM、带 BOM 的 UTF-16 LE/BE、中文和非 BMP 字符 | 输出正文精确一致；换行规范化后 locator 按码点定位，不能误用 UTF-16 下标 |
| Unit：解码拒绝 | 非法 UTF-8、UTF-32 BOM、NUL、仅 BOM/空白 | 返回对应具体错误；不能忽略坏字节或以空文本成功 |
| Unit：Markdown | frontmatter、缩进代码、代码围栏、表格、链接、HTML、尾部双空格 | 语法和空白完整保留，不渲染或重排源码 |
| Unit：结果编码 | 固定正文/定位/warning 和 RAW 来源，重复执行或改变字典插入顺序 | canonical bytes/hash 稳定；改变任一参与 hash 的字段可被发现 |
| Unit：失败投影 | 各类 parser 失败原因、内部异常 cause | 均投影为 `workspace.asset.failed`；只返回安全文案，内部 cause 和原始异常不进入公共 message 或 content |
| Integration：DOCX adapter + ZIP/XML 依赖 | Transitional/Strict 文档、多个 run、段落—表格—段落、空元素、表格行与单元格分隔 | 顺序正确、不丢空格，段落级定位能返回相应正文区间 |
| Integration：DOCX 提取范围 | 标题、自动列表、超链接、字段结果、图片/页眉脚注等未覆盖内容 | 提取已承诺的正文；warning record 稳定，字段指令不进入正文，仅图片文档返回空内容错误 |
| Integration：拒绝路径 | 改后缀的非 Word ZIP、损坏/加密文件、修订、嵌套表格、内容控件 | 内部失败原因准确映射到通用 `workspace.asset.failed`，不回退为 TXT 或用部分内容冒充成功 |
| Integration：包与 XML 限制 | 小配额下的成员数、解压字节、压缩比、重复路径、实体声明、深层 XML | 在配置边界拒绝；不解压到磁盘、不读取外部引用 |
| Unit / Integration 分文件验证预算 | 阈值恰好满足与超一单位、parser 检查点跨过预算 | 不静默截断；返回 limit/timeout，无固定 sleep 或巨型耗内存样本 |
| Integration：应用服务 + 真实 Store + parser | 同一 Workspace 的 PROCESSING 文档、跨 Workspace、重复启动、remove 后结果 | 前者能通过命令快照解析，Chat reader 仍阻止提前使用；其余按 Store 契约拒绝且不生成错误 READY |
| E2E：公开上传到可用性 | 分别上传 TXT、Markdown、DOCX，再上传损坏 DOCX | 前三者得到可用文字表示；损坏文件保留 RAW 并通过 W1-C 反馈解析失败，不产生 binding |

timeout 的工作量边界通过可注入时钟和小限额验证；不以真实等待 5 秒作为测试条件，也不
测试线程强制终止。
这些测试不依赖 Office、LLM、外部网络或真实向量数据库；W1-B 独立验收以转换测试为准，
Store 协作与公开入口终态在 W1-C 联调完成后验收。

### 15.5 W1-C 同步解析专项验收

W1-C 的协作测试必须使用真实 `WorkspaceAssetStore` 和上传应用服务；单元测试只需保持
各自的被测边界真实。竞态测试使用可控 parser 协议 fake 和事件屏障，转换正确性由
第 15.4 节的真实 parser 样本另行验证。断言资产快照和 HTTP 响应，
不以 RuntimeEvent 数量或 mock 调用次数作为主要证据。

| 测试边界 | 输入/场景 | 必须区分的正确行为与缺陷 |
|:---|:---|:---|
| Unit：状态接纳 | 文档 asset 依次执行 register/start，检查返回快照 | 只产生一个 `EXTRACTED_TEXT`，目标携带 token，RAW 仍保持 READY，不能重复注册或直接跳 READY |
| Unit：结果提交 | 使用固定 parser 成功/失败结果调用 complete/fail | READY 携带内容/hash 且 asset READY；FAILED 不携带内容且 asset 有安全错误；不能只改 representation 不改聚合状态 |
| Unit：过期与重复 | 错 token、错 revision、重复 complete/fail、已终态目标 | 返回具体 stale/operation conflict，已提交内容和状态保持不变 |
| Integration：解析交接 | 真实 Store + 应用服务 + 确定性 parser，asset 尚为 PROCESSING | parser 只能得到冻结 RAW 快照；Chat reader 仍拒绝 PROCESSING；结果只经 Store command 提交 |
| Integration：失败收尾 | parser 抛异常、返回非法结果或请求取消 | 目标不会遗留 PROCESSING/PENDING；RAW 保留；asset 使用通用 `workspace.asset.failed`，错误为安全摘要，不泄露异常正文 |
| Integration：竞态 | complete/fail 与 remove、重复触发并发 | 首个有效提交胜出；晚到结果分别为 removed 或 stale；不能复活资产或覆盖内容 |
| Integration：重放 | 并发同 key 重放、移除后重放 | 同 key 并发被串行化，两个响应均为终态且指向同一 asset/ref（首次 201、重放 200），不重复 register/start/parse；已 READY/FAILED 不再 parse；已移除返回 410，不创建新资产 |
| E2E：公开链路 | 上传 TXT/Markdown/DOCX，等待上传响应 | HTTP 响应包含 READY 或 FAILED；损坏/解析超限可见 FAILED，不自动发送 Chat 或建立 binding |
| Integration：资源边界 | 小限额、协作式预算和请求取消 | 不静默截断；返回资源失败；取消或 remove 后不能写回 READY |

同步解析测试使用 parser 返回事件、可控时钟或有界请求等待，不使用固定 sleep。请求取消、
remove 和 Store close 的测试必须验证晚到结果不会变成 READY；测试直接断言 Store 资产状态，
不把 HTTP 请求是否仍存在当作持久化事实。

## 16. 风险与开放问题

- 当前 WorkspaceAsset 是进程内 working set；服务重启和后台恢复不在本计划承诺内；同步解析
  只适用于本轮 10 MiB 以内的受控输入，长耗时或高并发场景需要后续异步方案；
- DOCX 正文提取不还原布局及自动编号；覆盖范围和不支持结构需用真实 Word 样本验证，避免静默缺失；PDF 与旧版 DOC 不进入本轮；
- 表格网格、单元格级定位、合并单元格语义、字段计算和版式还原不在首轮承诺内，留待 v0.7.0 Document Ingestion 或独立 Plan 按真实样本裁定；
- 第 7.7 节的默认限制需结合样本校准；协作式检查不能强制中止库调用；硬超时、进程隔离
  和异步队列另行规划；
- parser 依赖版本、warning message_key/params 与 locator 字段须在实现时按第 7 章样例冻结，变更转换规则同步提升 producer version；
- AttachmentCompiler 的 token 预算、分片和 locator 需要真实附件样本校准；
- TopicAssetBinding 是唯一使用记录；binding.asset_ref 的 representation 版本语义仍需独立冻结，不能通过新增第二份使用记录解决；
- 当前 `InteractionPayload`/`InteractionSubmission` 尚未携带附件选择，且其 codec 需要保持 canonical；实现必须按第 9.5 节把冻结的选择坐标挂在交接载体上，再由 W1-F 投影实际使用集合，不得让 handler 临时回查或直接把全部选择变成 binding；
- attachment promotion 是否统一使用 DocumentArtifact，需要根据内容语义和 v0.7.0 Document Ingestion 边界裁定；
- Materialization 开始前 ref 已被 remove 或 Store 已关闭时，promotion 按第 11.3 节跳过并记录结构化 warning，已提交的 binding 保持不变；该降级对 v0.7.0 provenance 契约的衔接需在真实样本中继续观察；
- 上传 operation 和 materialization operation 的幂等身份需要保持领域命名，不建立通用的隐式 operation key；本轮没有独立 parse operation，Store 的 parse token 只用于请求内提交 guard；
- 本计划不解决 Agent 主动解析的工具调用、沙箱、外部 Plugin 和 Memory 引用层执行问题。

## 17. 完成定义

本计划完成时，必须能够证明：

1. 用户可以在当前 Workspace 上传 TXT、Markdown、DOCX 附件并获得有效 opaque ref，旧版 DOC 和其他不支持格式有明确提示；
2. parser 可以生成稳定的 READY representation，失败时进入 FAILED 且不会伪装成可用资产；
3. 用户显式选择的 ref 能在当前 Chat 中解析、获取 lease 并进入 AttachmentCompiler；
4. AttachmentCompiler 能在本轮 Agent context 中报告实际使用的 representation revision/hash 和定位信息；
5. 成功 Interaction 才会建立 TopicAssetBinding，上传和选择本身不会建立 binding；
6. Topic settlement 和 Materialization 不依赖已经消失的 Topic 内容，并且通过 binding 中的
`asset_ref` 重新取得附件；正文不进入任何 Topic 或 queue 载荷。
7. Artifact promotion 只在确有 Memory CREATE/UPDATE 时发生，且 retry 幂等；
8. Workspace 隔离、remove、lease、解析失败、编译失败和版本冲突均有测试证据；
9. 当前设计文档、Artifact 文档、Roadmap 和 Plan 索引在完成收尾时同步更新，已完成 Plan 移入 `archive/plans/`。
