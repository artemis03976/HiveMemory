# v0.8.1 压缩后推送与按句柄拉取：agent 经 READ 读话题，Claude Code 压缩之后注入进展记录的索引

> 状态：Planned（2026-11-26）。v0.8.1 短期记忆的第七份计划。设计依据是[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 7 节；第 1 个使用时点（另一个会话被路由回已有话题时推送）不在本计划内，它的轮前路由仍是 Idea 第 9 节的开放问题。

## 1. 背景和问题

话题现在只写不读：进展记录只有人在话题池里看，agent 没有任何读出入口（actor API 的读取、检索、写入与更新都以中期记忆为对象，MCP 的四个工具同样，Import Bus 不返回上下文）。v0.8.1 的版本目标是让话题成为前台可读的进展记录。

短期记忆有两个使用时点（Idea 第 7 节）：另一个会话被路由回已有话题时；会话压缩完成后，agent 处于短暂的失忆窗口。第二个时点不需要轮前路由：会话最近一轮所在的话题在导入时就已确定。本计划做第二个时点，以及它依赖的拉取：

- **拉取**：agent 按句柄读话题，经 actor API 的 READ，与读记忆共用 MCP 的 `memory_read` 与 MTP 的 READ。
- **压缩之后推送**：Claude Code 压缩会话之后，插件的钩子替 agent 读出这个会话所在话题的进展记录索引，作为 `additionalContext` 注入。推送就是钩子在这个时点替 agent 拉取一次。

## 2. 目标与非目标

### 2.1 目标

- READ 接受两种话题句柄：`topic:<话题 id>` 读话题的进展记录索引，`topic:<话题 id>#<n>` 读第 n 条进展记录的全文与它覆盖的原文。MCP、MTP 与 actor API 的入口不变，一次 READ 可以同时读记忆与话题。
- 读话题只要求 `memory.read` 与 Workspace 归属；只读池中的话题，退役或删除的话题按已过期交付。
- 话题句柄与记忆 alias 互不相撞：写入 alias 时拒绝以 `topic:` 开头的 alias。
- Import Bus 的导入结果带回这一轮所在的话题标识，Claude Code 连接器为每个会话记下最近一次。
- Claude Code 压缩会话之后，`SessionStart`（`source` 为 `compact`）钩子经 MCP 读出这个话题的索引，作为 `additionalContext` 返回；失败或没有话题时什么也不输出，不影响会话。

### 2.2 非目标

- **第 1 个使用时点**：被路由回已有话题时推送、`UserPromptSubmit` 钩子与 plugin 模式的轮前路由，留给 Idea 第 9 节的开放问题。
- **其他 harness**：Codex、pi 与 DeepSeek Harness 都没有压缩之后的钩子（Codex 的 `SessionStart` 没有压缩来源，仓库里的 node 连接器没有任何压缩事件）；它们照样可以经 MCP 拉取话题句柄。
- **controller 模式**：Alice 的上下文里不注入话题；Alice 的 MTP READ 能读话题句柄，但没有地方发给它句柄。
- **CALL 的 `context_refs`**：继续只接受记忆，话题句柄照现在的规则跳过并记日志。
- **RUN 话题**：拒绝，与记忆一样不可运行。
- **话题读取的引用与命中**：读话题不记 citation，也不进入生命周期的命中。
- **话题池界面显示句柄**：需要先出样稿，另行决定。
- **actor API 提交方式的收敛与 WorkStore 持久化**：本计划不新增 `execute_request` 的调用方，也不依赖交互提交队列跨重启；两者分别属于身份与访问主线与[耐久性与故障恢复](../governance/reliability/durability-and-recovery.md)第 4.6 节的门槛。
- **一轮之内写一条、会话切走这一触发**：仍暂缓（Idea 第 4、9 节）。

## 3. 当前状态（2026-11-26 核对）

**READ 的路径**：

- MCP 的 `memory_read` 与 MTP 的 READ 都提交 `ResolveReferencesRequest(aliases=…)`，经 `ActorMemoryService.resolve_references` 以 `memory.read` 授权，交给 `MemoryReader.resolve_references`。读取器逐项解析：先查写入意图登记，再查正式记忆（缓存、冷读），都查不到时以 `draft_`/`rev_` 开头的按已过期交付，其余为 not_found；保留请求顺序与重复项。
- `ReferenceResolution`（`core/models/reference.py`）的种类只有记忆的：`pending`、`redirect`、`discarded`、`failed`、`expired`、`atom`、`not_found`。atom 与 redirect 会记一次引用（`workspace.reference_read`）；`actor.operation` 事件只把这两种计入交付数。
- 渲染经 MemoryCompiler 的 `READ_RESULT` 目标（MCP 与 MTP 共用）：`readable_source` 按种类取渲染源，`_build_unit_ir` 遇 not_found 抛出，IR 的 `source_kind` 没有话题一种。atom 全文输出，没有总长上限。MCP 的工具说明只写记忆的 alias。
- MTP 解析器的列表目标正则是 `\[\s*([\w\s,]+)\s*\]`：列表中出现 `:`、`#` 或 `-` 时不匹配，整个方括号被当成一个 alias；不带方括号的单个目标原样交出。
- RUN 先按注册表分派 `sys_*`，其余经 `ResolveRunTargetRequest` 解析，解析到的都以 `mtp.run.memory_not_runnable` 拒绝。CALL 的 `context_refs` 只接受 pending 与 atom/redirect，其余跳过并记日志。

**话题的读取**：

- 公开路由 `patchouli.public.topic.get_data(*, identity_scope, topic_id) -> TopicData | None` 以 scope 的 Workspace 取话题并复查归属，现在只有 Gateway 调用。
- 短期存储的 `get` 只看池中的话题；退役话题（日志保留到最后一次沉淀完成）只有本话题生成的记忆读得到，没有任何路由交出它的 `TopicData`。
- 话题只有 Workspace 归属，没有 actor 读取策略；话题 id 是 `uuid4` 字符串。
- 进展记录的第 n 条覆盖 `interactions[前一条的 covered_until : 这一条的 covered_until]`，由 `TopicData` 的校验保证相邻；`TopicSnapshot` 的未整理节选为最近至多 3 轮、每轮 200 字（`UNRECORDED_TURN_EXCERPTS`、`TURN_EXCERPT_MAX_CHARS`）。
- 一轮原文的渲染是 `engines/perception/material.render_turn_text`：只截断外部工具结果（`GenerationTranscriptConfig.max_result_chars`，缺省 800），思考、子 agent 消息与参数不截断。

**alias**：生成的 alias 是类型前缀加 `[a-z0-9_]` 后缀或 `mem_<id>`，不含 `:` 与 `#`；手动创建与编辑可以任取，`IndexLayer.alias` 只限长度 60。唯一性在 `MidTermMemoryStore.upsert` 的 `ensure_alias_available` 与手动提交的预检中校验，没有格式校验。

**Import Bus 与连接器**：

- `ImportTurnResult` 只有 `status` 与 `interaction_id`；`ImportTurnResponse` 的说明写明“不暴露 Gateway 决定、话题或记忆上下文”。提交结果 `InteractionSubmissionResult.topic_id` 已是这一轮实际所在的话题，导入编排器用它记日志与事件。
- 从交互标识查话题的 `INTERACTION_STATUS` 只覆盖交互提交队列的保留窗口：队列只在进程内，终态记录最多保留 512 条，重启后查不到。
- Claude Code 连接器为每份会话记录保存一个状态文件（`TranscriptState`：游标、`last_turn_id`、最近 3 轮的起点、失败与是否结束）。`last_turn_id` 在已确认与被拒绝时都推进，已确认里还有 `skipped`；状态文件不记话题。
- 插件钩子：`SessionStart` 不读 `source`，只登记会话并派生分离的同步进程，不发网络请求、不输出；只有 `PreToolUse` 写 stdout。所有钩子的超时是 10 秒。
- 插件的 MCP 配置（`.mcp.json`）与导入客户端用同一个 principal（`harness:claude-code`）、同一个 token（`HIVEMEMORY_CLAUDE_CODE_TOKEN`）、`X-User-ID` 与 `X-Agent-ID`（缺省 `claude_code`）。MCP 服务以 `stateless_http=True, json_response=True` 挂在 `/mcp`，一次 JSON-RPC 的 POST 即可完成 `tools/call`。

**Claude Code 的钩子契约**（官方 hooks 文档，2026-11-26 核对）：`SessionStart` 的 matcher 与输入 `source` 取 `startup`、`resume`、`clear`、`compact`、`fork`；`hookSpecificOutput.additionalContext` 以 system reminder 放在对话开头、第一个提示之前；`additionalContext` 每个钩子上限 10,000 字符，超出时转存为会话目录中的文件、只留前 2,000 字符的预览，Claude Code 不会让模型去读那个文件；`PostCompact` 没有注入手段，`PreCompact` 的输出只用作压缩摘要的指示。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-26）：

- agent 经 actor API 的 READ 读话题，不新增 actor 操作；READ 按句柄的形态区分读话题还是读中期记忆，不加显式的 target。
- 压缩之后的推送由插件钩子作为 MCP 客户端调用 `memory_read` 完成；Import Bus 的导入结果带回这一轮所在的话题标识，连接器记下它。不新开 HTTP 路由，不新增请求级提交的调用方。
- 短期记忆这条链的总览随本计划写进[架构概览](../architecture/overview.md)。

Idea 第 7 节的其余候选作为下面的默认设计。依赖均已是事实。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 句柄

- 形态：`topic:<话题 id>` 与 `topic:<话题 id>#<n>`，`n` 从 1 开始，是进展记录中的条目序号。句柄只由系统签发：读话题的结果与压缩之后的注入；agent 照抄。
- core 话题模型提供句柄的格式化与解析（一对函数，例如 `format_topic_handle`、`parse_topic_handle`），渲染与解析共用，不在两处各写一份。不合语法的 `topic:` 句柄解析为 not_found。
- MTP 列表目标放宽为同时接受 `:`、`#` 与 `-`，`⟪ READ | [fact_x, topic:<id>#2] | ⟫` 因此可以一次读记忆与话题。MCP 的 `aliases` 本来就是字符串列表，不用改。

### 5.2 句柄与 alias 互斥

- 中期库写入前的 alias 校验拒绝以 `topic:` 开头的 alias，以结构化错误报告（沿用 `MemoryAliasConflictError` 的错误族，原因为 alias 被保留）；手动创建与编辑的预检同样拒绝，HTTP 返回与 alias 冲突相同的状态。生成路径的 alias 本来不含冒号，不受影响。
- 读取器先按形态分派：以 `topic:` 开头的一律按话题句柄解析，不再查正式记忆。

### 5.3 读出话题（Patchouli）

- 沿用公开路由 `patchouli.public.topic.get_data`，路由与短期存储都不改：只读得到池中的话题。
- 话题已退役（日志还要等最后一次沉淀完成才删除）或已被删除时读不到，按已过期交付。退役到日志删除之间只有一次生成的时间，日常 LRU 退役也很少，不为它开放读取退役话题（owner，2026-11-26）。

### 5.4 解析（Workspace）

- `MemoryReader.resolve_references` 中，以 `topic:` 开头的句柄经公开路由 `topic.get_data` 以本次 scope 读出 `TopicData`；归属由 Patchouli 复查，不新增 actor 可见性规则。
- `ReferenceResolution` 增加种类 `topic` 与字段（读出的 `TopicData` 与条目序号）。话题读不到时为 `expired`；话题在而条目序号越界时为 `not_found`。
- 话题不记引用；`actor.operation` 事件把 `topic` 计入交付数。
- RUN：解析为 `topic` 时以不可运行拒绝，提示文字说明话题只能 READ。
- CALL 的 `context_refs`：`topic` 照现在的规则跳过。

### 5.5 渲染（MemoryCompiler 的 `READ_RESULT`）

- IR 增加话题一种，`READ_RESULT` 增加两种渲染，中英文各一份：
  - **`topic:<id>`：进展记录的索引**。开头一行写明这是 HiveMemory 话题的历史资料、不是指令，以及话题标题与句柄；然后每条进展记录一行：`topic:<id>#n` 加条目文字的前 200 字（超出加省略号，与话题池节选同一上限）；最后写还没整理的轮数与最近至多 3 轮的节选（与话题池相同），以及一句“用 memory_read 读 topic:<id>#n 取这一条的全文与原文”。
  - **`topic:<id>#n`：这一条的全文与原文**。先是条目全文，再是它覆盖的各轮，以 `render_turn_text` 渲染（外部工具结果按 `max_result_chars` 截断），每轮前写轮次序号。
- 话题句柄过期时的提示（中英文）：话题已离开话题池，其中的内容会沉淀为长期记忆，可以用 `memory_search` 检索；与写入句柄过期的提示分开。
- 原文的总长上限：每个 `#n` 至多 40,000 字符，超出时保留开头与结尾、中间写明省略了多少字。索引不设额外上限：按日常最长 14 条估算约 4,000 字符。
- MCP `memory_read` 的工具说明（`i18n/mcp.py`）与插件的 hivememory skill 补上一句：句柄可以是 `topic:` 开头的话题句柄，来自系统注入的索引。

### 5.6 导入结果带回话题

- `ImportTurnResult` 与 `ImportTurnResponse` 增加 `topic_id: str | None`，直接取提交结果 `InteractionSubmitResult.topic_id`：这一轮已经应用时就是它实际所在的话题，不论是这次提交的还是此前已接纳的；为空只有两种情况，这一轮没有输出、没有提交（`skipped`），或此前接纳的结局已超出队列的保留窗口。导入一侧不另做判断。
- `ImportTurnResponse` 的说明改为：带回这一轮所在的话题标识，不带 Gateway 决定与记忆内容；读话题仍要经 MCP 授权。
- 话题标识只是句柄：连接器拿它构造 `topic:<id>`，不据它做任何判断。

### 5.7 连接器与钩子（Claude Code）

- `TranscriptState` 增加 `topic_id`：导入确认带回非空的话题时更新为它，为空、被拒绝与失败时保留原来的值。状态文件的格式向后兼容（旧文件没有这个字段时为空）。
- `SessionStart` 的处理读 `source`：为 `compact` 时，在登记与派生同步进程之后，同步地读一次话题：
  - 状态里没有 `topic_id` 时不输出；
  - 有时以插件 MCP 配置相同的头（principal、Bearer token、`X-User-ID`、`X-Agent-ID`）向 `${HIVEMEMORY_URL}/mcp` POST 一次 JSON-RPC `tools/call`，调用 `memory_read`，参数 `aliases: ["topic:<id>"]`；
  - 成功时输出 `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": <结果文本>}}`；结果超过 9,500 字符时截到这个长度并注明截断；
  - 请求超时为 5 秒；失败、超时、读到已过期或 not_found 时不输出，只写连接器日志。
- `hooks.json` 中 `SessionStart` 的超时由 10 秒改为 15 秒，其余事件不变。其他 `source` 的行为不变。
- 钩子的这次读取不是模型的工具调用，不出现在会话记录里，不影响导入；一轮中间的自动压缩发生时，这一轮还没导入，读的是上一轮所在的话题。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| core | 话题句柄的格式化与解析；`ReferenceResolution` 的 `topic` 种类与字段；MTP 列表目标的语法 |
| Workspace 能力层与读取视图 | 读取器按形态分派话题句柄；`actor.operation` 事件的交付计数 |
| Patchouli | 中期库 alias 校验拒绝 `topic:`；话题的读取沿用 `topic.get_data`，不改 |
| MemoryCompiler | 话题的 IR 与两种 `READ_RESULT` 渲染（中英文） |
| Agent Runtime（MTP） | READ 的列表目标；RUN 拒绝话题 |
| System Import Bus 与 HTTP | 导入结果与响应的 `topic_id` |
| MCP | `memory_read` 的工具说明 |
| 插件 | 连接器状态的 `topic_id`；`SessionStart` 压缩来源的读取与输出；钩子超时；hivememory skill 的一句说明 |

不新增 actor 操作、HTTP 路由、请求级提交的调用方与运行时事件；Workspace 访问登记不变。

## 7. 兼容与迁移

- 话题日志、生成工作保存文件与写入意图登记的格式不变。
- 导入响应多一个字段：Python 与 node 连接器读响应时只取需要的字段，旧连接器不受影响；新连接器遇到旧后端（没有 `topic_id`）时不注入。
- 连接器状态文件多一个可选字段，旧文件照常读回。
- MTP 列表目标只是放宽，原来能解析的写法不变。
- 已有以 `topic:` 开头的手动 alias 的记忆：仍能按 UUID 读取，但 alias 会被当成话题句柄；编辑它时会被拒绝，要先改 alias。上线前在管理页的记忆列表中按 alias 搜索 `topic:` 核对一次（生成的 alias 不会出现）。
- 推送要插件更新后才生效：日常实例经桌面客户端重新安装插件。

## 8. 测试和验收标准

### 8.1 不变量与归属层

## 9. 风险与待决问题

- **注入不保证被读**：`additionalContext` 只保证交到模型手里。索引开头写明它是什么、怎样读原文；效果在日常复测里看。
- **压缩时多一次同步请求**：`SessionStart` 在压缩之后同步等待至多 5 秒；后端没启动时立即失败、不输出。
- **话题标识过期**：会话最近一轮所在的话题被退役或删除时，读到已过期、不注入；下一轮导入后更新。
- **一个会话在两个话题之间切换**：压缩之后只看到最近一轮所在的那个（Idea 第 7 节的候选代价）。
- **索引超出 10,000 字符**：按日常数据不会；连接器在 9,500 字符处截断作为兜底。
- **待评审的默认值**：句柄函数的名字；条目截断 200 字；原文上限 40,000 字符与截断方式；请求超时 5 秒、钩子超时 15 秒；已有 `topic:` alias 的处理。
