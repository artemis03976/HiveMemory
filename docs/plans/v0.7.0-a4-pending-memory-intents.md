# v0.7.0 A4：共享 Pending 与主动记忆写入

PendingAtom 解决的是所有 Actor 共有的资源问题：Actor 明确提出 WRITE/UPDATE，而正式 Memory 由后台异步生成时，如何在物化前读回意图、在结算后定位 canonical 结果，并避免读写不一致。它不是 Alice 专属机制，但现有 PendingAtomRuntime 还混合了 run/frame/action 关联，因此不能整体搬入 WorkspaceRuntime，也不能给外部 Actor 复制状态机。

本计划依赖 A1 access、A2 已交付的 canonical 读取/快照/失效，以及 [A3 第 4 节](./v0.7.0-a3-conversation-session-and-topic-projection.md#4-topic-路由指令与交接)已交付的 Topic 资料与生命周期能力。Pending 模型、operation 绑定、公共路由和共同引用扩展均在本计划冻结并实现，不依赖 A5 的完整 API 目录。独立验收不运行 Alice，也不要求 B transport；运行时主动意图可以没有 Session 或交互，这与实施时消费 A3 的 Topic 能力是不同关系。Alice 延迟提交与运行收尾的实际切换归 A6。旧 WRX-0/1 的快照、任务归属、错误和主动提交路由继续复用，新 Pending 归属/输入差额不回写成已完成事实。

## 1. 目标边界

| 能力 | 目标权威 | 说明 |
|:---|:---|:---|
| Pending 意图登记、内容、状态、结算关联 | Patchouli 资源侧 | 唯一状态机，不依赖 Alice |
| Pending/canonical 引用分派与结算跟随 | Patchouli 共同读取实现 | 在 A2 canonical 读取上扩展中立状态结果与 Pending 分支；不留 Alice 专属三级 resolver |
| 物化任务与 canonical 生成 | Patchouli generation/domain | 任务进度和 Pending 可读内容分开 |
| run/frame/action 关联、延迟提交、取消策略 | Alice workset/settlement adapter | 只持有引用和执行关联 |
| 外部输入/结果 wire | B 或 MTP adapter | 不复制 Pending 状态 |

Pending 不是 canonical Memory、也不是可淘汰 cache；资源侧持有不等于整个 Workspace 的 Actor 默认可读。全局 intent ID 负责定位，提交者、Workspace、operation 和内容可见性分别判断。

## 2. 共同流程与独立路由

```text
WRITE/UPDATE -> Pending 登记 -> 受权 Pending READ
  -> memory_intent.submit(PendingAtomMaterializeTask)
  -> 读取目标 Topic 的全部可用资料（允许空 blocks）
  -> 物化任务接纳 -> canonical revision / discarded / failed
  -> 失效派生 cache -> Pending 解析真实结果 -> 重新授权读取 canonical
```

`interaction.submit` 和 `memory_intent.submit` 是独立路由方法、独立 operation 和独立收据；可以由同一个 application service 承接，不要求两个类。旧 `InteractionPayload.materialize_tasks` 只作兼容迁移字段，最终不能让普通交互入口隐式执行主动物化。

共同输入继续使用 `PendingAtomMaterializeTask`：它的 pending alias、intent_id、source verb、identity scope 和 WriteFocus/UpdateFocus 具有跨 Actor 语义；`from_pending_atom()` 不能成为外部客户端前置依赖。ACK 必须区分 Pending 已登记、物化任务已接纳和 canonical Memory 已产生。

登记和物化提交是两个业务阶段，不强制两个客户端往返。Alice 可先登记、返回 ACK，稍后按运行策略提交；外部工具可组合登记和提交，但接纳失败时需说明已登记的意图如何读回/重试，不能返回模糊的整体 success。输入 scope 必须同时匹配 access 和已登记 Pending 的归属；不可借提交方法挪用别人的 intent_id。模型名的 Task 表示请求，不表示已经入队。

## 3. Topic 资料和 Session 关系

主动生成需要读取对应 Topic 在共同契约确定的资料读取时点的全部可用 blocks、summary 和 provenance，再按领域预算编译；不能隐式退化为“最近五条”。Topic 为空时，有效 WRITE/UPDATE 仍可进入生成；Topic 读取失败、越权、scope 冲突和成功取得空资料必须区分。没有 Topic 或没有交互不等于没有有效主动意图。

A4 只定义资料消费与生成预算，Topic 输入分类、prepare handle 是否可用、省略 Topic 的行为、资料绑定/快照时点与重试保留均遵循 [A3 第 4.4/4.5 节](./v0.7.0-a3-conversation-session-and-topic-projection.md#44-向主动意图交接资料)。A4-0 提供生成侧约束，但不另行决定是否创建空 Topic；如契约要求准备/释放，消费共同领域能力，不复制 prepare/cleanup 算法或跟随 Session cursor 重选资料。UPDATE 仍须验证目标 Memory、授权和已知基版本；空交互不免除这些条件。

“全部可用”指 A3 契约所选读取时点的实际资料快照；已折叠且未保存的原始 blocks 无法凭空恢复，原文保全由折叠专项负责。应先取得该时点全部可用材料，再按生成预算编译，不让 adapter 截取最近几条代替领域读取。

分支调查依据：`patchouli/control/memory_generation/coordinator.py` 的 `submit_active()` 曾使用 `recent_blocks(5)`；MemoryGenerationEngine 在没有上下文且没有 WRITE/UPDATE focus 时才跳过。A4 应保留生成引擎支持意图独立生成的方向，修正上游资料获取，而非让 adapter 自行拉 blocks。实施前复核代码差额及相关测试，不能把计划目标写成已具备能力。

Session/Segment 是可选来源，交互资料交接遵循 A3 第 4.4 节：需要纳入某个 Segment 时确认 applied 及其 assignment；assignment 本身不证明内容已应用。A4 接纳后使用契约规定的资料绑定，不因物化失败回滚已应用交互，也不让 Topic 清理影响仍被已接纳任务依赖的资料；保留/释放方式由 A3 第 4.5 节统一冻结。

## 4. Pending 读取、结算和生命周期

| 阶段 | 对外语义 |
|:---|:---|
| WRITE 未物化 | 返回登记内容/焦点和 Pending 状态，不标成 Memory |
| UPDATE 未物化 | 返回修订意图、目标引用和已知内容；只有 instruction 时不伪造最终正文 |
| 接纳后 | 返回真实任务/领域阶段；Actor 断连不取消已接纳工作 |
| canonical 已产生 | 原 Pending 引用可解析真实结果，canonical 读取再次授权 |
| 原 canonical 引用 | 返回当前已提交版本；是否提示调用者自己的未完成修订另行冻结，不静默叠加 Pending 正文 |
| discard/fail/cancel/expire | 明确区别，不伪造成功引用、不自动重建意图 |

`task.observe` 不自动授予 Pending 内容或最终 Memory 的读取权。稳定 intent identity 用于响应丢失后的查询/重试；相同 identity 不同 payload 返回 conflict。通知事件仅作观测，不能作为唯一终态真相。当前实现不承诺跨重启恢复；若要引入持久化必须另立迁移计划。

Pending snapshot、materialization task、task result 和 settlement projection 分别保存交接信息，不复制终态推进器。结算须可从权威任务/领域结果核对，不能等待 Alice 订阅事件才变正确。提交前取消与接纳后取消有不同承诺，cancel 只开放领域支持的范围。并发 UPDATE 的版本冲突仍由 canonical 更新规则判断；Pending 的原意图可读不等于所有 search 已能看到最终 Memory，也不默认加入全局搜索。

### 4.1 共同引用读取与 alias resolver 归属

2026-09-17 补充裁定：`RuntimeAliasResolver` 中 Pending/canonical 分派、结算跟随、终态解释和 canonical 读取协作是 Patchouli 领域责任，在本计划随通用 Pending 一起退出 Alice。共同读取 API 对相同 access、引用和资源状态给出相同领域结果；MTP、管理 UI 和外部协议只改变输入转换与呈现。管理操作仍使用自己的 operation/policy，不能把结果一致理解为权限相同。

当前 `agent_runtime/aliases/resolver.py` 依赖 `MTPExecutionContext`、Alice Pending runtime、Atom cache 和 MTP 异常；它在命中时直接返回。这些是迁移源，不能作为共享实现的依赖。资源侧接收 A1 access 与资源引用，返回中立的内容/状态快照、来源和版本；领域错误由 adapter 映射为 MTP 或外部错误。已有 `ResolveResult` 的语义可以复用，但不得跨边界返回可变 PendingAtom/MemoryAtom 或要求调用方创建 RuntimeScope。

```text
System / Alice MTP / 外部 read adapter
    -> 相同的共同引用读取总线路由（带 access）
    -> Patchouli application
         ├─ Pending ref -> 授权读取意图/终态
         │                  └─ 已结算 -> 目标引用 -> 当前授权下的 canonical 读取
         └─ canonical ref -> ownership/policy/freshness -> cache / storage
    -> 内容与状态快照 -> 各 adapter 呈现
```

原 L0/L1/L2 是历史查找顺序，不是三层等价缓存：Pending 是尚未物化意图的权威状态，cache 才是可丢弃派生副本。alias resolver 不迁入 WorkspaceRuntime，不新增 Workspace resolve service，也不从 Patchouli 内部递归调用自己的 public route。已有 application 方法承接共同入口，内部复用领域读取即可；不强制增加独立 service 类。

| 读取对象/状态 | 共同语义 |
|:---|:---|
| canonical alias/UUID/ref | 返回当前可读的已提交版本；命中缓存与冷读语义一致 |
| Pending 未物化 | 返回授权范围内的原意图、已知内容和阶段；不伪造最终正文 |
| Pending 已结算 | 保留请求引用和 settlement 关系，经当前授权读取真实 canonical；知道 Pending 不授予目标内容读取权 |
| discarded/failed/cancelled/expired | 明确领域终态；只有通过相应可见性检查后才能披露，不伪装为已生成 Memory |
| 未知或不可见引用 | 遵循 A1 访问边界和本计划的防泄露错误投影；不回退到别的 Workspace，也不改查同名的另一种资源 |
| 原 Memory 有未完成 UPDATE | 仍读取已提交 Memory；读对应 Pending 才看到修订意图，不默认为正文叠加 Pending |

A4-0 在 A2 canonical 读取基线上冻结扩展部分：引用种类/命名空间、现有 read 与 retrieve_by_aliases 的签名兼容、批量逐项结果、Pending 内容读取与 canonical 读取所需 grant、目标不可见时可披露的 settlement 字段。优先复用现有地址；如果旧返回类型不容纳状态联合，必须明确兼容投影或新方法及退出窗口，不按调用方建立两套语义，也不要求外部先调用 Pending 查询再自行读取 Memory。

READ、RUN、UPDATE 和 Profile 类型读取可以复用同一资源解析事实，但各自继续校验操作条件。解析到代码不授予执行权，解析到 Profile 不授予身份切换；UPDATE 的目标/基版本规则归主动写入。Profile 定义只从正式可读资源解析，未物化 Pending 不能被当作可执行 Profile；若接受结算后的引用，须沿共同跟随规则取得正式资源后再验证类型。不同操作的错误映射由兼容矩阵记录，不能把“统一解析”误作所有操作都接受所有 Pending 状态。

A2 已交付 canonical/Profile 读取、快照与缓存协作。本计划在同一领域读取链增加 Pending/settlement 分支，并负责状态联合结果、批量逐项结果和旧返回类型的兼容扩展；保持 A2 已验收的 canonical 结果与授权语义。A4 自行完成所有跨状态验收，再向后续消费者交付，不要求 A2 回头等待本计划冻结其基础签名，也不存在必须由 Alice 拼装多个领域计划的中间业务层。

Pending 终态不被当作普通 Memory 负缓存淘汰；其保留与过期按本计划的权威状态生命周期处理。失效和结算推进不依赖 Alice 订阅者。

当前 resolver 以 `pending.runtime_scope.identity_scope == context.identity_scope` 判断可见性。迁移时按 A1/A4 冻结的提交者、Workspace、operation 与 Pending policy 校验，不能要求外部构造 RuntimeScope，也不能照搬整个 scope 相等而把兼容 session 字段变为权限条件。Pending 引用类型或命名空间必须明确，未知/不可见 Pending 不回落为同名 canonical；Pending 与 canonical 的可见性分别处理，不能通过 redirect 泄露不可读目标的内容或未获准披露的元数据。

结算指向应以权威 canonical identity 定位，alias 用于展示或兼容查找；若 alias 已被重新绑定，不得让旧 Pending 跟随到另一份资源。缓存丢失、失效或没有可用 alias 时，仍能按已结算的目标 identity 经授权读取；不存在和不可见不能被伪装为物化仍在进行。具体错误投影与 legacy settlement 缺失 identity 的处理在 A4-0 冻结。

## 5. 实施、测试与回滚

| 阶段 | 产出 | 验收 |
|:---|:---|:---|
| A4-0 | Pending 包边界、共同输入、operation、可见性、登记/提交收据及第 4.1 节共同引用扩展 | 无 Alice run/frame 必填；session 可选；引用无歧义；明确结算目标不可见/缺失的投影 |
| A4-1 | 资源侧登记和 Pending/终态共同读取分支，Alice 关联交接 | 无 Alice 读回 WRITE/UPDATE；只存在一份权威状态机和领域解析实现 |
| A4-2 | memory_intent.submit，按 A3 第 4 节取得资料绑定并读取全部可用内容 | 按统一省略/空/非法 Topic 规则处理；多于五个 blocks 不被静默截断；读取失败不当空 |
| A4-3 | generation、invalidation、共同读取的 settlement 跟随、结果观察、取消和关闭 | 重复提交不产生第二 canonical；原引用在 cache hit/miss 时定位同一真实结果并重新授权；接纳后断连/关闭可解释 |

integration 使用真实 Patchouli application、generation task/result、A2 invalidation 和 A1 access；覆盖无交互主动写入、Topic 缺失/越权/空、UPDATE 目标、Pending READ、重复键、响应丢失、过期和 Alice stop。共同解析还须覆盖 Pending/canonical 权限不同、失败/取消/丢弃终态、alias 重绑定、缓存清空后的 UUID 冷读、同名引用不跨类型回落，以及原 Memory 在 UPDATE Pending 存在时仍返回已提交版本。旧/新状态机和领域 resolver 不得同时作为成功来源；回滚只切换 adapter，不删除已接纳 Pending。

### 5.1 实现前必须关闭的接口和迁移决定

| 决定 | 阶段与验收要求 |
|:---|:---|
| 资源侧包与运行时聚合 | A4-0 明确 Patchouli 权威实现及生命周期，是否物理参与 WorkspaceRuntime 聚合；不得含 Alice run/frame 管理或新增 Workspace 业务转发层 |
| 登记/read/resolve/submit | A4-0 给出独立签名、operation、提交者可见范围和 Session 仅作来源的规则；外部不依赖 RuntimeScope |
| 共同读取/引用与结果 | A4-0 按第 4.1 节冻结引用区分、批量逐项结果、grant、redirect 目标身份和可披露字段；A4-1/3 在同一内部实现接入并验收，交付消费者退出清单 |
| intent identity 与幂等 | A4-0 冻结 ID 签发、客户端键映射、直接提交时登记关系、同键异载荷 conflict 与未知接纳查询 |
| 状态与收据 | A4-1/3 明确登记、任务接纳、结算的阶段、权威结果关联、内容读与观察权的差异 |
| Topic 与预算 | A4-0 核对 A3 第 4.5 节唯一契约，A4-2 消费；本计划仅冻结全部材料的预算编译，不另定省略 Topic、handle 或快照保留规则 |
| 运行清理与切换 | A4-1 给出单一状态所有者下的兼容引用/委托入口和旧 run drain 要求；真实 run/frame 提交策略及旧调用方删除交付 A6，不反向成为 A4 门禁 |
| 保留期与关闭 | A4-3 冻结容量拒绝、期限、expired/unknown、关闭未完成任务的结果；不声称跨进程耐久性 |

这些是局部实现门禁，不重新讨论 Pending 的通用资源归属。接口冻结后按单一状态所有者逐步切换，必要兼容 shim 只委托同一实现并写清删除时点。`PendingAtomMaterializationTask` 是讨论时的泛称，实际共同模型沿用代码中的 `PendingAtomMaterializeTask`，不再创建同义类型。

## 6. 完成后的文档边界

本计划以公开登记/读取/主动提交/结果观察及结算解析的真实证据独立完成，相关事实文档按稳定收尾门禁更新。A5 后续核对全局 API 目录，A6 迁移 Alice/MTP adapter，B 映射外部协议；这些消费工作不推迟本计划完成。A4 不宣称 MCP、沙箱、耐久化或跨重启恢复已经交付。
