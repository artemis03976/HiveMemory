# V1 Memory 与 Artifact Legacy 数据迁移及 legacy 分支删除

## 1. 背景与问题

v0.6.2 身份收敛（[归档 Plan](../archive/plans/v0.6.2-identity-projection-cleanup.md)）冻结了 V2 身份与策略语义：Memory 的唯一持久化归属是 `meta.workspace_identity`，Workspace 内可见性由 `MemoryAccessPolicy`（`PUBLIC/PRIVATE/TEAM`）表达，来源（`source_agent_id`）只作 provenance、不参与授权。历史 Qdrant 记录仍以 V1 形状存储：payload 中存在平铺 `meta.user_id`，缺少 `workspace_identity` 与 `access_policy`。历史 Artifact 也可能使用旧模型：归属通过旧的 `owner_agent_id` 或 legacy Workspace 投影表达，InteractionArtifact 的 turn 可能仍使用平铺 `user_id/agent_id/team_id`，MemoryCreation/VersionArtifact 没有 V2 provenance 字段。

当前代码为这些历史记录保留了受控兼容分支（W0/v0.6.2 裁定的临时状态）：

1. `memory_codec.py _legacy_workspace_identity`：读取时从平铺 `meta.user_id` 重建 `WorkspaceIdentity`（映射到该用户的 `main_workspace`）；`user_id` 与投影 owner 冲突或缺失时 fail closed 抛 `MemoryDecodeError`；
2. `filter_adapter.py _ownership_filter`：查询条件在 `meta.owner_user_id + meta.workspace_key` 之外保留对 `meta.user_id` 的 legacy OR 分支，保证旧记录仍可被检索；
3. `InteractionTurnSnapshot` 的旧平铺 actor JSON 读升级分支（缺 `actor_identity` 时从 `user_id/agent_id/team_id` 重建，缺用户归属 fail closed）。
4. 当前 Artifact 模型已经不再声明 `BaseArtifact.owner_agent_id`：Artifact 的归属统一由 `workspace_identity` 表达；`MemoryCreationArtifact` 与 `MemoryVersionArtifact` 记录 `source_agent_id` 和 `contributing_agent_ids`；InteractionArtifact 只在 block/turn 内记录 `actor_identity`。这改变了历史 Artifact 的规范形状，不能因为 ArtifactStore 使用 append-only 写入就跳过迁移。

这些分支让历史数据继续可用，但也让"一条记录是否 V2"成为运行时分支判断，且 legacy OR 分支使查询语义长期携带第二套归属字段。V1 Memory 与 Artifact 全量迁移是删除上述 legacy 解释分支和 Artifact 读取升级分支的前置条件。

## 2. 目标与非目标

### 2.1 目标

1. 一次性、可审计地把存储中全部 V1 Memory 记录迁移到 V2 形状（补齐 `workspace_identity`、`access_policy`、缺省的 `contributing_agent_ids`，移除平铺 `meta.user_id` 权威语义）；
2. 一次性、可审计地把历史 Artifact 转换为当前 Artifact 形状：Workspace 归属由 `workspace_identity` 表达，MemoryCreation/VersionArtifact 具备 `source_agent_id` 与 `contributing_agent_ids`，InteractionArtifact 的每个 turn 具备 `actor_identity`；
3. 迁移过程 fail closed：无法安全推断归属、策略或 provenance 的记录不写入 canonical 记录，进入诊断清单；
4. 输出迁移报告（Memory/Artifact 扫描总数、canonical 替换数、保留旧记录数、fail-closed 数、逐条原因和旧新 ID 映射）；
5. 迁移后经观察窗口验证，删除 legacy codec/filter/快照读升级分支及其测试白名单。

### 2.2 非目标

1. 不原位覆盖或删除旧 Artifact。Artifact 仍然 append-only；迁移通过写入 canonical replacement、更新 MemoryAtom 和 Artifact 内部引用、保留旧 Artifact 供审计追溯来完成；
2. 不改变 V2 身份/策略语义，不引入新的归属字段；
3. 不实现跨用户 Workspace 授权、认证或多租户（属 [Identity and Execution Safety Governance](../governance/security/identity-and-execution-safety.md) 工作包）；
4. 不在本 Plan 内清理短期 Topic（进程内存态，无持久化 legacy 数据）。

## 3. 当前状态与缺口

| 项 | 现状 | 缺口 |
|:---|:---|:---|
| 新写入 | 全部为 V2（`MetaData.workspace_identity` 必填，`to_qdrant_payload` 只投影 owner/workspace 键） | 无 |
| 历史读取 | codec 兼容分支按 `meta.user_id` 重建归属并 fail closed | 依赖分支长期共存 |
| 历史检索 | `_ownership_filter` legacy OR 分支 | 查询语义携带第二归属字段 |
| InteractionTurnSnapshot | 旧平铺 JSON 读升级，fail closed on 缺归属 | 需要写入 canonical `actor_identity` Artifact replacement |
| MemoryCreation/VersionArtifact | 新写入已使用 Workspace 归属、`source_agent_id` 与 `contributing_agent_ids`；旧记录可能有 `owner_agent_id` | 需要追加 canonical replacement，并重写 MemoryAtom/ref 链接 |
| Document/InteractionArtifact | 新写入不再使用 Agent owner；Interaction 来源在 block 内 | 旧 owner/旧 actor 形状需要按类型转换或进入诊断 |

## 4. 目标设计

### 4.1 V1 → V2 字段映射

| V1（历史 payload） | V2（目标形状） | 规则 |
|:---|:---|:---|
| `meta.user_id` | `meta.workspace_identity = WorkspaceIdentity(owner_user_id=user_id, workspace_key="main_workspace", workspace_id="main_workspace")` | 唯一合法归属来源；缺失或与既有投影冲突 → fail closed |
| （无） | `meta.access_policy` | 已带可见性字段的记录按其值映射；缺失 `visibility` 时是否按当前 reader 的 `PUBLIC` 兼容默认迁移，必须作为显式脚本策略和报告分类，不能静默放宽可见性；证据不足时 fail closed |
| `meta.source_agent_id`（如存在） | 保持不变 | provenance 展示，不参与授权 |
| `meta.contributing_agent_ids`（无） | `meta.contributing_agent_ids = ()` 或由可信 Interaction block 聚合 | 不得仅凭最后访问 Agent 猜测；无法证明时保留空集合并记录报告 |
| 其余 index/payload/relations 字段 | 原样保留 | 迁移不重写业务内容 |

### 4.2 Artifact 目标形状与来源映射

| 历史 Artifact | canonical replacement | 迁移规则 |
|:---|:---|:---|
| `InteractionArtifact` | 相同 Workspace 下的新 InteractionArtifact | 将每个 turn 的平铺 `user_id/agent_id/team_id` 转为 `actor_identity`；缺 `user_id` fail closed；缺具体 Agent 使用 `SYSTEM_AGENT_ID`；不添加顶层 `source_agent_id` |
| `MemoryCreationArtifact` | 新 MemoryCreationArtifact | Workspace 只取 `workspace_identity`；删除 Agent owner 语义；`source_intent=SYSTEM` 时 `source_agent_id=SYSTEM_AGENT_ID`，否则从可信旧来源迁移；贡献者优先从关联 InteractionArtifact 聚合，无法证明时为空并报告 |
| `MemoryVersionArtifact` | 新 MemoryVersionArtifact | Workspace 只取 `workspace_identity`；删除 Agent owner 语义；迁移 `source_agent_id` 与贡献者集合；无法区分历史系统结算与具体 Agent 更新时不得猜测，进入诊断或按批准的保守规则处理 |
| `DocumentArtifact` | 新 DocumentArtifact | 删除 Agent owner 语义；保留文档自身的 URI、快照和定位信息，不新增当前模型没有定义的 Agent provenance 字段，也不补造 Agent 来源 |

Artifact 仍然是 append-only。迁移不得用旧 `artifact_id` 覆盖旧内容，也不得直接删除旧文件。脚本必须为内容发生变化的 Artifact 写入新的 canonical record（使用迁移命名空间或确定性新 ID），保存 `old_artifact_id → new_artifact_id` 映射，并把以下引用改到新 ref：MemoryAtom 的 `payload.artifacts.refs/events`、MemoryCreationArtifact 的 `initial_version_ref`、MemoryCreation/VersionArtifact 的 `source_artifacts` 与其他 ArtifactRef 列表。旧记录保留为历史证据，迁移报告记录其状态为 superseded。

Artifact replacement 的 canonical schema version、迁移命名空间和旧记录的审计标记必须在脚本实现前冻结；当前代码的 Artifact `schema_version` 仍为独立于 Memory `schema_version=2` 的值，不能把两者混为一个版本，也不能通过重新使用旧 ID 绕过 append-only 约束。

`SYSTEM_AGENT_ID` 在迁移中只表示“没有具体 Agent 作为操作来源主体”：它可以作为 MemoryCreation/VersionArtifact 的 `source_agent_id`，也可以作为旧 Interaction turn 缺少具体 Agent 时的 `actor_identity.agent_id`；它不是内容贡献者，也绝不能写入 PRIVATE/TEAM 策略的 target 字段。历史字段缺失本身不等于已经证明“无具体 Agent”；只有显式的 `SYSTEM`/外部创建语义或其他可信证据成立时才可填入 `system`，否则仍按 provenance 不可确定处理。

### 4.3 迁移执行方式

1. 离线脚本（一次性维护工具，不进入请求链路）：冻结写入或按高水位标记迁移批次，分别扫描 Qdrant Memory 和 ArtifactStore；
2. 先对两类存量记录校验 Workspace 归属并完成 Artifact replacement 与旧新 ID 映射，再构造重写了所有 ArtifactRef 的 Memory canonical payload；先发布所有 replacement，确认 hash/ref 可解析后再切换 MemoryAtom 根记录。Qdrant 与 ArtifactStore 当前没有跨存储事务，所谓“切换”必须由 checkpoint、映射表和可恢复的发布顺序保证，不能宣称跨存储原子提交；
3. 每个 replacement 先通过当前 Pydantic 模型校验，再写入目标存储；单条失败不中断批次，记录资源类型、旧 ID、原因、原始位置和是否存在部分 replacement；
4. Memory 与 Artifact 的更新必须支持 checkpoint/resume。脚本在每个 Workspace 或批次完成后持久化进度，重跑时按旧 ID、内容 hash 和映射表幂等跳过，不产生重复 canonical replacement；
5. 脚本输出结构化迁移报告（JSON + 人类可读摘要），包含 Memory/Artifact 数量、旧新 ID 映射、ref 重写数、保留旧记录数、失败原因和校验摘要。

### 4.4 fail-closed 条件

- `meta.user_id` 缺失或为空，且无 `workspace_identity`；
- `meta.user_id` 与 payload 中已投影的 `owner_user_id` 冲突；
- `access_policy` 可见性值不在 `PUBLIC/PRIVATE/TEAM` 枚举内，或 PRIVATE/TEAM 缺少合法 target（含保留 `system` target，V2 模型校验会拒绝）；
- InteractionArtifact 缺少可靠 Workspace 或 block 用户归属；
- Memory Artifact 缺少可靠 Workspace、`source_agent_id` 无法确定，或旧 owner 与 Memory/Workspace 来源互相冲突；
- 贡献者集合只能由不可信的最后访问 Agent、artifact owner 或其他单值字段猜测；此类记录不得自动回填贡献者，必须为空并进入报告，或直接 fail closed，取决于该记录是否仍能形成合法 canonical Artifact；
- replacement 已写入但引用链无法完整重写或校验 hash 不一致。

### 4.5 观察窗口与 legacy 删除门槛

迁移完成并生成报告后进入观察窗口：期间 legacy 分支保留，运行时统计 legacy 读命中数（codec 分支触发次数）。删除 legacy 分支需同时满足：

1. 报告中 V1 Memory 与 legacy Artifact 存量迁移数为全量（fail-closed 清单已逐条处置或显式豁免归档）；
2. 观察窗口内 Memory legacy codec/filter、Interaction actor 读升级和 Artifact legacy decoder 的命中数均为 0；
3. 双 Workspace 隔离与管理可见性测试在无 legacy 分支时保持通过；
4. 删除改动本身附带 Qdrant/ArtifactStore 索引重建或全量扫描证据（证明 canonical 记录和引用链完整）；
5. ArtifactStore 中旧记录虽保留用于审计，但不再被 canonical MemoryAtom 或新 ArtifactRef 引用；旧记录只通过迁移报告的 superseded 映射访问。

## 5. 测试与验收标准

- legacy 分支删除后：全量既有单测/集成通过，删除 `meta.user_id` OR 查询分支不影响双 Workspace 隔离测试；
- 验收出口：
  - [ ] V1 存量迁移完成且报告归档；
  - [ ] 观察窗口结束且 legacy 命中为 0；
  - [ ] legacy codec/filter/Interaction actor 读升级分支与相关白名单删除；
  - [ ] Artifact legacy owner/actor 解释路径删除，canonical replacement 映射归档；
  - [ ] §7 当前文档更新完成。

## 6. 风险与待决问题

1. **PRIVATE/TEAM 历史记录的策略推断**：当前 `_decode_v1()` 在缺失 `visibility` 时默认 `PUBLIC`，但这可能放宽历史可见性。迁移脚本必须把“缺失 visibility 的默认 PUBLIC”作为显式策略选项和报告计数，不能静默扩大权限；如果历史证据不足，应 fail closed。不得仅凭 `source_agent_id` 推导 V2 PRIVATE，也不得把来源字段重新用于新授权。
2. **Artifact provenance 不可逆推断**：旧 `owner_agent_id` 既不能作为 Workspace owner，也不能自动证明内容贡献者。`source_intent=SYSTEM` 可以确定 `source_agent_id=system`；其他来源和贡献者必须依据可信关联数据转换，不能把最后访问 Agent 当作作者。无法证明时保留空贡献者集合并进入诊断，或拒绝该 replacement。
3. **Append-only 引用链迁移**：MemoryAtom、MemoryCreationArtifact、MemoryVersionArtifact 和 InteractionArtifact 之间存在嵌套 ArtifactRef。必须先建立完整映射再切换根引用，避免出现 canonical record 指向旧 record 或部分迁移的链。
4. **旧 Artifact 的兼容读取**：当前 `ArtifactStore.get()` 返回原始字典，但任何 typed decode 都会受到新必填 provenance 字段影响。迁移完成前必须保留明确的 legacy decoder/diagnostic path，不能让旧记录静默变成“找不到”。
