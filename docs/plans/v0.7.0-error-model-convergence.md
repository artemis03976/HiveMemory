# v0.7.0 异常体系与边界错误呈现收敛

> **文档状态**：Planned（2026-10-17）。本计划属于 v0.7.0 发布前收敛，尚未实施；目标结构和错误呈现规则不能作为当前事实使用。

本计划建立一套能够从“错误在哪里产生”追踪到“调用方如何处理、Agent 与 HTTP 客户端看到什么”的规则。实施重点是异常类型收敛、错误语义、所有权和边界转换，目录整理随之进行。保留局部异常、业务结果、warning 和控制流各自的用途，清理重复定义和仅为构造响应而存在的异常类；不以异常类数量下降代替语义与兼容验收。

## 1. 依据、顺序与工作归属

设计依据为当前[错误模型](../contracts/error-model.md)、[MTP 契约](../contracts/mtp.md)、[Workspace 架构](../architecture/workspace.md)、[运行时与总线](../components/runtime-and-bus.md)，以及 2026-10-17 分支 `refactor/v0.7.0-cleaning` 的代码（调查起点为提交 `147e672a`，路径与清单已按前驱收尾后的代码修订）。代码位置是调查入口，实施时以符号与行为核对。

本计划整份依赖 [Alice 与 agent_runtime 结构重构](../archive/plans/v0.7.0-alice-agent-runtime-restructure.md)与[提示词编译前移至任务进程](../archive/plans/v0.7.0-cpu-prompt-compilation.md)。两份前驱均已于 2026-10-17 完成验收、事实文档更新和归档，本计划尚未开始实施。依赖只规定顺序，不以前驱的候选目录、接口或章节作为本计划的设计依据。结构重构收尾后已按其最终代码与事实文档修订一次路径和错误清单；进入实施前再按届时的稳定代码复核。

[代码收敛清单](../todo/v0.7.0-code-convergence.md)第 1.6、3.9 条移交本计划，原条目只保留调查证据与导航；第 3.10 条（编排层直接依赖提供商异常）不由本计划承接。稳定代码已在 LLM 客户端边界提供中立的 `ModelProviderError`（与 `ModelContextWindowExceededError` 并列，原始异常保留在原因链），本计划直接复用并核对其跨出口语义，不重复建立客户端或等价错误类型。其余结构、命名、死代码清理仍按各自归属处理。

## 2. 当前状态与问题

项目已有三项可复用基础：`WorkspaceDomainError.code/details`、`MTPErrorInfo` 与唯一 formatter、CPU 与业务结果中的判别状态。缺口集中在这些机制的衔接。

2026-10-17 对 `src/hivememory/` 的 AST 盘点识别出 100 个自定义异常类，包含基类和私有控制异常；其中 `core/errors.py` 为 27 个，`core/mtp/exceptions.py` 为 25 个，`components/work_queue/exceptions.py` 为 12 个。前驱收尾后同口径为 102 个，新增 `agent_runtime/model/client.py` 的 `ModelProviderError` 与 `alice/interface/cpu.py` 的 `AliceUnavailableError`。这是调查快照，不是认定全部类型过多的依据，也不是实施时必须达到的数量上限；阶段一按届时代码重新盘点。

| 现状与证据 | 问题 | 本计划处理 |
|:---|:---|:---|
| `core/errors.py` 混合访问、资产、会话、意图、Memory 输入和模型查找错误；部分类型没有 code | 定义位置和稳定程度难以判断 | 按依赖层与语义所有者拆分，明确公共错误与局部异常 |
| `infrastructure/storage/vector_store.py` 抛 `core.mtp.exceptions.StorageOfflineError/StorageReadError/StorageWriteError`，retriever 直接捕获它们 | 基础设施已经绑定 Agent 协议的归因与文案 | 中立存储错误贯穿服务调用，MTP 在出口转换 |
| `workspace/resolution/profile.py` 与 `patchouli/services/retrieval.py` 抛 alias、类型和参数类 MTP 错误 | 普通 Profile 读取和 CALL 呈现耦合；缓存命中与回源两条路径都受影响 | owner 与读取视图返回中立语义，CALL 与 CPU 分配分别处理 |
| `RootMemoryService.record_feedback` 把宽泛的 `RuntimeError/ValueError` 转成服务不可用或记忆不存在；Topic 路由捕获 `KeyError` 转 404 | 程序缺陷与预期失败无法可靠区分 | 在做出判断的 owner 处定义明确错误，消费者按类型映射 |
| `ThreadContextRevokedError` 是无 code 的 `RuntimeError`，普通 MTP 走未知故障兜底 | 生命周期拒绝缺少稳定分类，修改继承也可能改变其他捕获点 | 明确中立分类，审查全部消费者，保留迟到操作拒绝语义 |
| `server/app.py` 与 routers 分别映射错误；全局 500 和部分路由返回 `str(exc)` | 响应结构不一，内部诊断文本进入公共接口 | 集中 HTTP 投影，区分安全文案与内部诊断 |
| `agent_runtime/mtp/runtime.py`、CALL 准备和响应映射分别转换异常 | 操作上下文不同，但共享分类缺少明确维护位置 | 每种边界有单一转换入口，共享确实相同的映射 |
| `alice/orchestration/call/response.py` 构造 `SubAgentBudgetExhaustedError`、`AgentModelUnavailableError` 后立即调用 `to_error_info()`，没有抛出这两个对象 | 用异常类承载已经确定的响应数据，形成额外维护层 | 保留协议类别，通过具名函数直接构造错误信息 |
| MTP 的 `MemoryNotFoundError`、`SubAgentUnexpectedSuspendError` 在仓库源码与测试检索中只有定义和导出；两者的 code 仍列于当前错误模型，后者另有中英文模板 | 遗留类型与正在使用的协议契约混杂，契约列出从不产生的 code | 检查公开导出兼容性后清理类型，code 是否移出契约单独决定；不凭仓库内无调用直接推断外部无消费者 |
| `components/work_queue/runtime.py` 与 `system/services/passive/memory_context.py` 以 `type(exc).__name__` 记录 `error_class`，随工作队列 RuntimeEvent 的 `data.error_class`、submission 终态与 `ActiveInteractionFinalizationError` 传出；Passive 事件还把类名写入 RuntimeEvent 的 `reason` | Python 类名成为可观察值，合并、改名或迁移异常会改变这些输出；`reason` 被类名占用，与原因码语义不符 | 明确类名只作诊断还是投影为稳定 code，类型处置时同批审查这些输出 |
| `alice/interface/cpu.py` 的 `AliceUnavailableError(RuntimeError)` 在 CPU 宿主未启动或已停止时由首次拉取抛出，仿照 Workspace 领域错误携带 `code=alice.unavailable` 与 `details.reason=not_running`；类型不在可跨子系统导入的契约中，任务进程按未分类异常投影，当前文档把这两个字段写为诊断用 | 结构化字段没有消费者，同形字段容易被误认为 Workspace 机器码；执行准入拒绝与程序缺陷在进程侧不可区分 | 阶段一决定所有者与处置：纳入中立的不可用类别并由进程按类型收尾，或保留为只作诊断的局部异常并记录理由 |
| `frontend/src/services/` 同时读取 `detail`、`message`、嵌套字段或原始响应文本 | 后端收敛后仍可能无法展示稳定错误 | 同步统一错误解析，保留各 API 的业务结果处理 |

调查并不意味着所有 `except Exception` 都有问题。例如 `workspace/capability/actor/memory.py` 在派发开始后的异常表示接纳结果未知；该边界必须保留句柄和不确定性。Gateway 的保守降级、队列策略、清理与观测隔离也需要按各自不变量审查。

## 3. 目标与非目标

### 3.1 目标

1. 公共错误有明确所有者、稳定机器类别与消费者；同一语义不重复定义。
2. 基础设施、资源 owner 和读取视图不依赖 MTP 异常或面向 Agent 的文案。
3. HTTP、普通 MTP、CALL、CPU 终态与后台任务在各自边界决定呈现和恢复策略。
4. 预期失败、程序缺陷、取消、超时、部分降级和结果未知可以分别判断。
5. Agent 能获得可执行的修正建议，公共内容不包含内部异常正文或未筛选的诊断字段。
6. 保留现有身份隔离、写入接纳、取消清理、部分输出与 finalize 不变量。
7. 对现有异常逐项决定保留、合并、改为响应构造或删除；新增中立错误时同步处理对应旧类型，避免迁移后两套等价异常长期并存。

### 3.2 非目标

- 不改变四阶段编排、身份和操作授权、资源可见性、会话与写入意图所有权。
- 不把所有异常强制纳入一棵继承树，不替换局部模型校验所需的原生 `ValueError/TypeError`。
- 不设异常类数量或压缩比例指标，不把具名类型机械改成一个接受任意 code/reason 字符串的万能异常。
- 不把业务拒绝、warning、CALL 挂起、取消与 RuntimeEvent 改成同一种 error envelope。
- 不新增全局自动重试、熔断、持久化审计、分布式追踪或错误码注册服务。
- 不改造 LLM 客户端和工具执行基座，不扩展 RUN 的沙箱或权限能力。
- 不升级 Memory、Artifact、队列 payload 等持久化 schema，不借此修改模型与 Provider 配置。
- 不整体重写前端业务流程；只修改错误传输、解析和必要展示。

## 4. 目标设计

### 4.1 先决定表达机制

| 情形 | 表达方式 | 决策所有者 |
|:---|:---|:---|
| 正常状态空间内的拒绝、取消或失败终态 | 现有结果模型与状态 | 对应业务服务或运行持有者 |
| 跨边界、调用方需要区别处理的失败 | 中立异常与稳定 code；类型粒度按第 4.3 节决定 | 资源 owner、授权点或依赖适配器 |
| 参数修正、alias 未命中等 Agent 可理解的失败 | `MTPErrorInfo` | 普通 MTP 或 CALL 适配边界 |
| 有可安全消费的部分成果 | 现有 warning/部分结果 | 有权决定该降级的服务 |
| 外层任务取消、CALL 挂起 | 原生取消或既有控制信号 | 运行持有者 |
| 程序缺陷、投影或装配不变量破坏 | 原异常传播至负责收尾的边界 | 运行持有者与入口 |
| 旁路事件发布失败 | 隔离并记录，业务返回不变 | 观测设施 |

`TimeoutError` 不自动等于可重试错误。必须区别依赖超时、阶段 deadline 和可能已经提交副作用后的等待超时；同样的技术原因可以对应不同的业务处理。

### 4.2 定义与代码落位

目标组织如下；具体文件名可在实施审查中调整，依赖方向和所有权必须保持：

```text
core/errors/
  __init__.py           # 共享中立错误的公开导出
  base.py               # 结构化错误的最小基类
  access.py             # 访问上下文、准入与授权
  resources.py          # 跨层共享的资源、Memory 与资产错误
  storage.py            # 中立存储失败
  model.py              # 确有跨层消费者的模型错误
core/mtp/
  exceptions.py         # 确实参与抛出、传播或捕获的 MTP 异常
  models.py
  formatter.py
workspace/contracts/errors.py  # 仅子系统及上层使用的 Workspace 公共错误
patchouli/contracts/errors.py  # Patchouli 公共业务错误
agent_runtime/mtp/error_mapping.py
server/error_handlers.py
server/models/errors.py
```

- 下层也需要构造或捕获的错误放在 L0；不能因名称含 Workspace 就移入 L3。例如 AttachmentCompiler 使用的资产错误应先检查 L2 消费者。
- 会话、意图等错误仅在依赖图允许时迁入 `workspace.contracts`；Patchouli 的公开业务错误经其 `contracts` 暴露。每个类型只有一个定义，允许必要的公开重导出。
- 私有的摘要拒绝、队列机制错误、解析器内部异常可以留在其内聚模块。`components` 不导入子系统错误或业务重试判断。
- 普通 MTP 映射位于执行适配边界；CALL 映射留在 Alice 的 CALL 编排边界。CPU 失败原因投影仍归 Alice，进程只消费中立结果。
- 前驱完成后的实际接口与目录用于确定 Alice/agent_runtime 的落点；不依照本调查时的路径重新建立已删除模块。

### 4.3 中立错误的最小结构

共享基类只统一稳定 `code` 和内部 `details` 的承载方式，异常 message 用于诊断，因果关系使用 `raise ... from exc`。既有 `details.reason` 若被消费者使用，就保留其稳定含义；不另加一份需要同步的 reason 状态。

基类不携带 HTTP status、MTP severity、i18n key、日志等级或全局 `retryable`。这些判断依赖调用上下文，分别留在出口与业务策略中。新增类型按下述粒度规则决定，只有文案差异时使用已有机器类别和具体呈现键。

`WorkspaceDomainError` 及其现有 code 保持含义。修改父类前检索全部 `except/isinstance`，尤其是 `RuntimeError/ValueError` 捕获点；目录移动不应悄悄改变异常匹配。`ThreadContextRevokedError` 增加稳定中立 code，但不新增独立 HTTP API，也不把迟到请求视为新的可重试任务。

#### 4.3.1 异常类、机器类别与呈现粒度

- **异常类**表达需要跨调用栈传播的失败边界、独立处理策略、有差异的必要上下文，或值得类型保护的领域不变量与公共契约。
- **code 与受约束的 reason**表达机器可识别的类别；一个异常类型可以承载同一失败边界内的多个原因。已有公开 code 可以由受约束原因投影，不要求一个 code 对应一个 Python 类。
- **message_key 与 params**表达文案与场景差异，不据此增加叶子异常类。

新建或保留独立类型时，必须指出其消费者、不同处理、必要上下文、不变量或公共契约中的至少一项依据。没有独立 `except` 不是删除的充分条件；同一 HTTP 状态码或相同日志等级也不能证明领域语义相同。

合并使用 `Literal`、枚举或具名构造限制原因取值；若不同原因需要不同必填上下文，应使用可检查的模型或继续保留具名类型，不把约束转移到任意 `dict[str, Any]`。既有 `details.reason` 可保留 wire 取值，由所有者验证；代码中的分支不解析异常正文。

只负责呈现的边界直接构造 `MTPErrorInfo` 等现有结果对象。用具名纯函数集中选择 code、severity、message_key 和允许的 params，调用方传入业务上下文；不先创建异常再转成结果，也不在各调用点重复拼写错误码。异常传播与响应构造可以复用相同的呈现定义，不建立一份与现有模型重复的 DTO 或全局注册表。

#### 4.3.2 类型处置规则与首批候选

| 处置 | 判断依据 | 迁移要求 |
|:---|:---|:---|
| 保留 | 独立处理、必要上下文、不变量或公开契约需要明确类型 | 记录理由；实际结构已合适时保持局部定义 |
| 合并 | 同一失败边界重复定义，或叶子类型只区分诊断原因且处理与上下文约束一致 | 迁移生产者、捕获与分类消费者，保留必要的 code/reason 和兼容行为 |
| 改为响应构造 | 对象只用于序列化/呈现，没有异常传播职责 | 使用现有结果模型与具名构造函数，验证 wire、行动建议和内部信息筛选 |
| 删除 | 没有有效生产用途，且公开兼容义务已核对或完成迁移 | 清理失效定义、导出和旧契约测试；保留仍被承诺的协议类别，不用墓碑测试守护删除历史 |

当前已定位的候选如下；阶段一结合前驱后的稳定实现确认，不能按表名机械删除：

| 候选 | 默认处理方向 | 必须保留或核对的语义 |
|:---|:---|:---|
| root 的 `MemoryNotFoundError` 与共享的 `ResourceNotFoundError` | 合并重复领域表达 | Workspace 内的资源查找语义、HTTP 404 与消费者兼容 |
| `SubAgentBudgetExhaustedError`、`AgentModelUnavailableError` | 改为 CALL 响应构造 | 既有 MTP code、severity、文案键、参数与 cause 不公开 |
| `WorkPayloadEncodeError`、`WorkPayloadDecodeError` | 评估合并为 codec 失败及受约束的原因 | 编码/解码诊断、kind/version 上下文、接纳前后失败路径与队列策略；工作记录中的 `error_class` 取异常类名，合并会改变工作队列事件与 submission 终态中的取值，按第 5 节的观测输出规则处理；发现独立契约时保留 |
| MTP 的 `MemoryNotFoundError`、`SubAgentUnexpectedSuspendError` | 核对公开导出后删除无用途类型；对应 code 是否移出契约单独决定 | `mtp.memory.not_found`、`mtp.call_response.unexpected_suspend` 列于当前错误模型，后者另有中英文模板，但没有生产路径产生：子 frame 没有 CALL，被调方的挂起终态由 `CallCoordinator.complete_call` 与 CALL 响应映射作为不变量破坏抛 `ValueError`。Python 导入兼容与协议 code 分别审查；不能因类被删除顺带取消仍有效的 wire 契约 |

默认保留明确拒绝与结果未知、缺少上下文与线程已撤销、资源缺失/不可见/不可用等具名语义。队列容量不足、停止接纳与状态迁移冲突也需保持可分别处理；不能为缩减类数量合并其恢复条件。

新增中立存储或资源错误时，同一迁移切片必须说明旧 MTP 异常的去向：仍参与协议解析或工具执行控制流的可保留；仅剩出口映射用途的转为响应构造；无用途的清理。不得按现有 MTP 叶子类逐个复制一套中立异常。

### 4.4 依赖和领域边界

1. **存储**：SDK/连接失败在适配器边界转换为中立的不可达、读取失败或写入失败；检索与资源服务消费中立类型。只在有证据时声明“未写入”，写入失败不自动代表副作用未发生。内部程序异常不通过宽泛捕获假装成存储离线。
2. **资源与 Profile**：缺失、不可见、类型不适用和配置无效在 owner 处判定，读取视图遵循同一语义；按现有保密规则合并呈现的缺失与不可见不能重新泄露存在性。CALL 转为 MTP 错误，CPU 分配按中立失败收尾，均不回退到默认 Profile。
3. **管理服务**：Memory 不存在、lifecycle 不可用、Topic 不存在/忙碌/接纳失败使用明确类型。消费方不再用整段调用中的任意 `KeyError/ValueError/RuntimeError` 推断业务结果。
4. **模型服务**：复用 LLM 客户端已有的 `ModelProviderError`，保留上下文超窗等需要不同处理的分类；摘要器只降级预期提供商失败，程序错误和取消继续传播。
5. **总线与队列**：route 缺失和参数接线错误不包装成空成功；只有既有契约允许的边界才转换为服务不可用。队列仍由 lane 的业务失败策略决定重试，机制层不猜测资源语义。
6. **Gateway 与 Passive**：局部 fallback 仍仅覆盖已声明的可恢复失败；投影、终态不变量与被动模式契约违约不能进入相同降级分支。

### 4.5 HTTP 错误投影

`server/error_handlers.py` 负责注册处理器与类型到响应的映射，`app.py` 只接线；路由保留传输层输入解析，不重复包装领域错误。

API 错误响应采用以下目标结构，复用既有字段名：

```text
error       稳定机器码
detail      安全、可展示的字符串
reason      可选，仅公开契约允许的原因码
issues      可选，输入校验的字段位置、类别和安全说明
```

- 访问、会话等已有机器码及已确认的状态码保持含义；未分类异常返回 500 与通用内部错误码、固定安全文案。
- 输入校验与显式 HTTP 错误也纳入 API 响应映射。请求校验仍为 422，字段错误放入 `issues`，不返回原始 input、任意校验 context 或嵌入的异常对象。
- 将默认校验响应的 `detail` 列表改为字符串属于有意的 wire 变化，必须和消费者迁移、API schema 更新及兼容说明同批完成，不能声称完全向后兼容。
- 显式 HTTP 错误按已知传输场景映射；未知的 `HTTPException.detail` 也不自动认定为可公开文案。保留必需的 HTTP headers。
- 已开始的 SSE 流不能靠全局 HTTP handler 改写状态码；流内错误走专用投影，保留既有事件名和终态契约。CPU `failure_reason` 保持原有原因语义，通用异常正文不进入交互原文或 done。
- 静态文件响应、readiness 状态模型及正常业务 outcome 不强制套入此结构；WebSocket 保留自身连接与关闭语义。
- 前端统一解析上述结构，并在迁移期间接受已知旧形态；各服务不再自行读取原始异常文本。兼容读取不意味着后端继续输出不安全细节。

### 4.6 Agent 可见错误与恢复指导

保留 MTP 的 code、severity、`message_key + params`、warning 和 formatter。内部中立错误迁移后，已有 MTP code 的含义继续保持；普通动词与 CALL 在各自唯一入口完成转换，需 verb、alias 或调用阶段的映射显式传入上下文。

协议信息可由真实抛出的 MTP 异常转换，也可由已确定的业务终态直接构造。两条路径共用适用的呈现定义；保留协议字段和错误码不要求保留对应 Python 异常类。

| 失败情形 | Agent 应得到的行动指导 |
|:---|:---|
| 参数或语法错误 | 修正明确指出的参数后重试 |
| 引用不存在 | 调整引用或重新检索，保持既有不可见资源的隐藏规则 |
| 权限拒绝 | 停止被拒绝操作，使用已获许可的能力 |
| 临时依赖故障 | 明示能力暂不可用，是否重试由操作策略决定 |
| 写入明确拒绝 | 本次未接纳，根据原因修正或稍后重新提交 |
| 写入结果未知 | 原句柄可能继续结算，优先读取已有句柄状态，不能自动重复提交；没有可用查询能力时明确说明无法确认 |
| 线程已撤销 | 原线程不再接受操作，不建议继续重试或重新获取身份 |
| 未分类程序错误 | 固定系统故障文案，不根据异常正文生成恢复建议 |

本轮不新增全局行动枚举或自动重试开关。行动指导先落实到已有错误类别和中英文模板；`agent_fault/system_fault` 不单独充当重试许可。保留 cause 不序列化的规则，并对白名单 params 逐项构造，禁止直接将内部 `details` 全量转为公开参数。

### 4.7 捕获、日志与控制流

- `try` 尽量贴近有明确失败契约的调用；局部模型校验与外部输入包装按现有领域边界处理。
- 资源收尾、任务终态和传输兜底可以捕获未知异常，但必须保留失败事实。清理中的次生失败不能覆盖主异常，也不能跳过其他必须释放的资源。
- 原生 `CancelledError` 继续传播；已接纳写入的取消屏蔽和等待、线程撤销、附件释放、部分输出及历史检查点接受顺序保持原状。
- 派发开始后的结果未知边界保留广泛故障捕获及句柄；不得为了缩小 `except` 而把未知写入改成确定拒绝或直接删除登记。
- 为每条失败链确定一次负责记录根因的边界；上层只补充需要的关联信息，避免重复 traceback。日志和 RuntimeEvent 也不记录凭据、完整输入或无边界的上下文。
- 内部诊断与公共 message 分开；RuntimeEvent 继续 best-effort，不作为业务成功或失败的唯一事实。

## 5. 影响范围与兼容策略

| 面向 | 处理 |
|:---|:---|
| Python 类型与导入 | 同批更新定义、抛出方、捕获方和测试；合并/删除需核对公开导出、动态分类与按类名持久化的消费者。若存在外部公开导入消费者，记录兼容方案与退出条件；不能用简单别名假装保留原本不同的捕获语义 |
| 中立错误码 | 保留既有公开 code/reason；新增机器类别在实施清单中记录所有者、产生条件和消费者，代码作为定义源 |
| MTP | 保留已公开 code、XML 格式、error/warning 边界；调整行动建议与参数筛选，同步中英文模板 |
| HTTP 与前端 | 统一 API 错误结构；保留已确认状态语义，列明有意变化并更新前端、schema 和相关契约 |
| CPU、SSE 与后台任务 | 复用现有结果状态和失败原因；不把缺少映射误写成成功，不扩展自动重试 |
| 观测输出中的类名 | 工作队列与 Passive 的 `error_class`、Passive 事件的 `reason` 当前取 Python 类名。阶段一决定类名继续只作诊断（合并、改名或迁移后的取值变化写入迁移说明并改写相应断言），还是改为投影稳定 code；Passive 的 `reason` 改用原因码，或明确保留并记录理由。RuntimeEvent 仍为 best-effort，不因此成为可靠契约 |
| 持久化 | 本计划不改 schema；检查是否存在按异常类名、错误文本持久化后分支的消费者，有则先显式解决兼容问题 |

阶段内允许为可审查迁移保留短期重导出，收尾时删除无消费者的兼容层。不得同时维护两份等价异常类、两套 HTTP 映射表或独立错误码配置文件。

## 6. 实施阶段

### 阶段一：复核稳定基线与建立错误清单

前驱完成后，重新核对公开接口、提供商错误和测试位置。在本计划实施记录中维护一份精简矩阵：产生方、类型/code/reason、生产用途（抛出、捕获、分类或仅构造响应）、消费者、出口映射、恢复动作、副作用确定性、权威测试归属。对每个异常类型标明保留、合并、改为响应构造或删除，并记录依据、目标位置与兼容义务。扫描跨边界捕获、对外 `str(exc)`、fallback、失败事件以及以异常类名为值的观测输出；无关缺陷另记 Todo。

优先冻结访问、资源、存储、Profile、意图、CPU 与 HTTP 的行为差异。HTTP 校验结构、现有导入消费者和前端迁移清单在进入下一阶段前明确。

出口：每个异常类型都有可追踪处置，每项范围内的公共失败均有所有者和处理依据；记录同口径类型数量作为对比，不设压缩配额。设计基于稳定代码，清单不成为第二个运行时注册表。

### 阶段二：中立异常与 owner 边界

按处置清单合并重复类型、清理确认无用途的类型，再按所有权拆分定义；在存储、资源/Profile、管理服务产生中立失败，联动修改全部消费者。保留 MTP wire 语义作为过渡投影，收窄会误判程序错误的捕获；复用已有提供商适配。每次新增中立类型同步确认旧协议类型的去向。

出口：中立服务不抛 MTP 错误，缺失、不可见、不可用和接线缺陷不会互相冒充；权限、接纳与取消行为保持不变。

### 阶段三：出口映射与 Agent/客户端呈现

集中普通 MTP、CALL 与 HTTP 映射，将只用于响应的异常对象改为具名响应构造，审查 params、流内错误和事件输出；统一 HTTP 模型并同步前端消费、schema 与迁移说明；改写固定原始异常文本的旧测试。检查 Agent 修正建议与明确拒绝/结果未知/生命周期拒绝之间的对应关系。

出口：各出口只有一个负责呈现的入口，未知异常安全失败；公开错误内容足以指导下一步，取消和业务状态保持独立。

### 阶段四：传播、降级与收尾验收

按错误清单核对 Gateway、Passive、work queue、CPU 和进程收尾，修正遗漏的误分类、吞错与重复日志。复核每项类型处置与必要保留理由，记录前后数量及新增类型依据，清理没有兼容义务的旧定义。扩展既有架构守卫和归属层测试，审查兼容层与文档；全部验收完成后晋升事实并归档。

各阶段独立审查。定向检查通过后再执行对应跨边界回归，最终执行完整门槛；不能通过更改预期来隐藏未声明的语义变化。

## 8. 风险与待决问题

| 风险或待决点 | 处理与决定时点 |
