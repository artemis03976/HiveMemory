# v0.8.0 馆长 agent：结算时先探索本话题的写入与库中相关记忆，再写记忆

> 状态：Planned（2026-11-19）。v0.8.0 的第三个方向“馆长 agent”的计划。设计依据见[写入链路 Idea](../ideas/memory-flow-write-path.md)第 3.1 节。

## 1. 背景和问题

话题结算时，被动生成现在是一次性提取加事后规则：模型看不到本话题已经写入的记忆，也看不到库，只从材料里尽量多地提取草稿；之后逐条以 dense top-1 查重，完全相同的只触碰，相似的新建并提名合并，命中本话题写入的直接丢弃；合并以较新的一条作骨架。复述、误丢与合并改写主动写入，都由这一串规则在补前一层的漏洞（[生成](../patchouli/generation.md)第 3.1、4 节）。

owner 于 2026-11-19 决定：结算时 Patchouli 尽量不与本话题主动写入过的记忆重叠，尽量不与库中相关记忆重叠，在此前提下写记忆；前两步是两个阶段的探索，由馆长 agent 完成，用 agent 的主动探索代替规则拦截与生成；最后仍有重叠就接受，不加复核、去重或兜底的逻辑。工具与循环由 Patchouli 内部自己定义。同日 owner 补充：一次性生成与 agent 式生成两种方式同时保留，作为用户选项，因为 agent 式生成显然更慢、开销更大；一次性生成按现状冻结，等有更好的解决办法时再尝试优化（写入链路 Idea 第 3.1 节）。

## 2. 目标与非目标

### 2.1 目标

1. 话题结算的生成方式成为用户选项：一次性生成（现在的被动提取及其后的规则）或馆长（agent 式生成）。
2. 选馆长时，结算运行一个由 Patchouli 定义的工具循环。它先查看本话题主动写入结算到的记忆，再检索并阅读库中相关的记忆，然后写入新记忆，草稿引用材料中的段。
3. 馆长的产出不经过查重、触碰、合并提名或丢弃。
4. 馆长的工具只操作 Patchouli 自己拥有的数据，不经过 Workspace 的 actor API，也不使用 MTP。

### 2.2 非目标

- **改动一次性生成**：按现状冻结（owner，2026-11-19）。Mode A 的提取、查重、触碰、合并提名与命中本话题写入即丢弃都照旧；它的重复问题不在这里处理，等有更好的办法时再优化。
- **修订或合并已有记忆**：馆长只新建；不修订本话题的写入，也不修订别的话题留下的记忆（owner 2026-11-19 否掉了结算时对账全库）。
- **读其他话题的原始轨迹**：经旧记忆的段引用回到原文需要一个读取交互快照的组件，现在没有；第一版只读记忆本身，当前话题的材料已经在上下文中。
- **主动写入（Mode B）与修订（Mode C）**：行为不变，查重与合并照旧。
- **同一 Workspace 的结算串行**：两次结算可以同时运行，残余的重叠接受。
- **原生工具调用**：模型服务只有文本接口，第一版用 JSON 动作协议（第 5.2 节）。

## 3. 当前状态（2026-11-19 核对 master）

- **结算链路**：感知冻结话题、构建 `TopicMaterializeTask`，生成接纳之后删除短期话题（`patchouli/services/perception.py`）；协调器以没有焦点的 `GenerationRequest` 提交 SETTLE（`control/memory_generation/coordinator.py`）；控制器执行时把本话题主动写入结算到的记忆并入 `topic_write_memory_ids`，SETTLE 成功后清除（`control/memory_generation/controller.py`）；Familiar 先捕获交互快照，再调用引擎，提交在不可中断的一段里完成（`patchouli/services/memory_generation.py`）。
- **被动生成**：引擎的 Mode A 渲染材料后调用 `extractor.extract`，对每条草稿调用 `_dedup_and_resolve`：dense top-1，命中本话题写入即丢弃，IDENTICAL 触碰，其余新建，SIMILAR 且访问策略相同时提名合并（`engines/generation/engine.py`）。被动提示词与 `ExtractionResult` 只服务 Mode A。
- **模型服务**：Patchouli 共用一个 `LiteLLMService`，唯一入口是文本的 `complete(messages, params)`，没有原生工具调用（`infrastructure/llm/base.py`）；提取器失败最多重试一次，输出无法解析时返回空列表、任务照常完成。
- **可用的读取**：中期库 `search`（dense 或 sparse，单向量、不融合、不重排，返回带分数的记忆）、`get`、`get_by_alias`（`memory_library/stores.py`），都按 `from_actor` 检查可见性；结算以 Workspace 的 system actor 运行，只读得到 PUBLIC 记忆。`RetrievalFamiliar` 的检索会刷新生命力。没有任何代码读回交互快照。
- **并发与超时**：生成 lane 并发 2、超时 300 秒，不按话题或 Workspace 串行；没有步数或 token 预算。
- **配置**：`patchouli.generation` 下有 `extractor.enabled`、`deduplicator` 阈值、`transcript`、队列参数与 `active_recent_blocks`。`extractor.enabled` 关闭时装配 NoOp 提取器（`engines/generation/extractor.py`）。生成配置都不在立即生效的字段中，保存后重启生效（`system/running_config.py`）。
- **设置页**：常用页“记忆”一节以开关显示 `extractor.enabled`（“自动从对话中提取记忆”）；设置项按 schema 渲染，已支持下拉选择（`frontend/src/constants/settingsSchema.ts`）；调试模式读不到后端时使用 `MOCK_CONFIG`（`frontend/src/constants/settings.ts`）。
- **持久化编码**：生成队列信封 1.3，编码整个 `GenerationRequest`。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-19，写入链路 Idea 第 3.1 节）：结算时的三步；由馆长 agent 完成，代替规则拦截与生成；残余的重叠接受；工具与循环由 Patchouli 内部定义，不复用 Alice 的执行循环与 MTP；一次性生成与馆长并存，作为用户选项，一次性生成按现状冻结。依赖已成为事实：生成的记忆指向交互轮次（PR #228）。

## 5. 目标设计

### 5.1 位置

馆长放在 `engines/generation/` 之下（与提取器同层）：它可以使用中期库与模型服务的接口，不依赖 Workspace 与 Alice。引擎对 SETTLE 按配置的结算方式分派：一次性生成走现有的 `_process_mode_a`，馆长走馆长；Familiar 的提交管线不变。

### 5.2 循环与动作协议

- 每一步，馆长把对话历史交给 `complete`，模型输出一个 JSON 动作：`{"tool": "<名称>", "args": {…}}`；Patchouli 执行工具，把结果作为下一条消息交回。
- 动作无法解析或工具不存在时，把错误作为结果交回，计入步数，不中止。
- 结束条件：模型调用 `finish`；步数到达上限（初值 12）；lane 超时。步数用完时照常提交已暂存的记忆，并记一行日志。
- 模型服务失败照旧传播为 `model_provider_failed`；超过上下文窗口传播为 `model_context_window_exceeded`。

### 5.3 工具

| 工具 | 作用 |
|:---|:---|
| `list_topic_writes` | 列出本话题主动写入结算到的记忆：别名、标题、摘要；system actor 读不到的跳过 |
| `search_memories` | 以一句查询检索中期库，`mode` 为 dense 或 sparse，返回别名、标题、摘要、类型与分数（每次最多 5 条） |
| `read_memory` | 按别名读一条记忆的全文 |
| `write_memory` | 暂存一条新记忆：标题、摘要、标签、类型、正文、引用的段 |
| `finish` | 结束 |

- 材料（话题状态与带段标签的各轮）在第一条消息中给出，不需要工具读取。
- 读取与检索都以结算的 system actor 进行，不刷新生命力。
- 暂存的记忆在循环结束后一次性交给 Familiar，按 CREATE 提交：分配别名、写版本记录（带 `cited_segments`）、入库；不查重、不触碰、不提名合并。

### 5.4 提示词

新增馆长的系统提示词（中英文）：说明三步的顺序，即先看本话题写过什么、再查库里相关的，再写；只写既不与本话题的写入、也不与库中相关记忆重叠的内容；草稿引用段作为依据；动作的 JSON 格式与工具说明。被动提示词与 `ExtractionResult` 照旧服务一次性生成。

### 5.5 配置与设置页

- `patchouli.generation.settle_mode`：`one_shot`（一次性生成，默认）或 `librarian`（馆长）。
- `patchouli.generation.librarian`：`max_steps`（12）、`search_top_k`（5），只在选馆长时使用。
- `extractor.enabled` 保留原义，是两种方式共同的开关：关闭时结算不产生记忆，两种方式都不运行。`deduplicator` 服务主动写入与一次性生成。
- 两项都不加入立即生效的字段，保存后重启生效，与 `extractor.enabled` 一致。
- 设置页常用页“记忆”一节，在“自动从对话中提取记忆”之后加一个下拉“话题结算时的生成方式”，选项为“一次性生成”与“馆长探索”；说明写明两者的代价：一次性生成更快，但写之前看不到本话题的写入与库，可能留下较多重复；馆长先查看本话题的写入与库中相关记忆再写，更慢、模型调用次数是一次性生成的数倍。`MOCK_CONFIG` 与 `configs/config.yaml` 补上 `settle_mode`。

### 5.6 保留的部分

- 引擎的 Mode A、`dropped_on_hit`、`extractor.extract`、被动提示词与结算产生的合并提名都保留，作为一次性生成；这个计划不删除代码。
- 控制器的话题写入记录照旧，同时服务两种方式：一次性生成用它丢弃命中的草稿，馆长用它列出本话题的写入。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| 生成引擎 | SETTLE 按 `settle_mode` 分派到 Mode A 或馆长；Mode A 不变 |
| 馆长（新） | 循环、JSON 动作协议、五个工具、预算 |
| 提示词 | 新增馆长提示词（中英文）；被动提示词不变 |
| Patchouli 装配 | 引擎拿到结算方式与馆长的配置 |
| 配置 | 新增 `patchouli.generation.settle_mode` 与 `patchouli.generation.librarian` |
| 前端设置页 | “记忆”一节新增一个下拉 |
| 路由、事件、持久化编码 | 不变（`GenerationRequest` 不变，生成队列信封仍为 1.3） |
| 数据 | 不迁移；选馆长时，新结算的记忆不再与库中记忆合并 |

## 7. 兼容与迁移

- 没有数据迁移。关闭时保存的 SETTLE 下次启动后按当时配置的结算方式执行。
- 旧配置文件中没有这两项时取默认值，升级后的行为不变（一次性生成）。
- 回退：把 `settle_mode` 改回 `one_shot` 并重启，不需要回滚代码；已建成的记忆不受影响。

### 8.3 实测

- **开发实例**：选馆长，带主动写入与不带写入的话题各结算几次，日志显示每次结算的步数、各工具的调用次数与新建的条数；抽看新建的记忆与本话题写入、库中相关记忆的关系。改回一次性生成后结算一次，确认行为与现在相同。

## 9. 风险与待决问题

- **模型不按协议输出动作**：错误作为结果交回、计步；用完步数时提交已暂存的记忆。频繁出现时再考虑原生工具调用（要改模型服务的接口）。
- **成本**：一次结算从一次调用变为若干次，token 随步数增长；这是两种方式并存、由用户选择的原因。步数上限与 `search_top_k` 是第一道约束，实测中记录每次结算的调用次数与 token。
- **两条结算路径并存**：引擎同时维护一次性生成与馆长两条 SETTLE 路径，一次性生成的规则链照旧需要维护。两种方式产出的记忆在库中混合；改用馆长之后，它不会合并一次性生成留下的相近记忆。
- **私有记忆**：system actor 读不到 PRIVATE 与 TEAM 的记忆，本话题由 UPDATE 修订过的私有记忆不会被列出；这避免私有内容被写进公开记忆，代价是馆长可能与它们重叠。
- **并发结算的重叠**：同一 Workspace 两次结算同时运行时，彼此看不到对方暂存的记忆；按 owner 的决定接受。
- **候选默认**（不是 owner 决定，可在计划评审时调整）：JSON 动作协议、步数上限 12、`search_top_k` 5、工具的名称与返回字段、馆长的位置在 `engines/generation/`；配置键 `settle_mode` 及取值 `one_shot` / `librarian`、默认一次性生成、改选后重启生效、设置页的标签与说明文字。
