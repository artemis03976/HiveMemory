## 1. 背景

项目中已经出现两类具有“排队执行”特征的能力：

1. **Interaction Submission Queue**  
   在 active/passive mode 形成完整 `InteractionPayload` 后，负责缓存、提交、失败重试与成功确认，最终将 interaction 可靠地应用到 Patchouli 感知层。
2. **Memory Generation Task Queue**  
   承载 `MemoryGenerationTaskSpec`，限制昂贵记忆生成任务的并发，支持取消、超时、失败状态与结果查询。

两者都会需要 enqueue、claim、并发控制、retry、cancel、timeout、backpressure、shutdown drain 和 RuntimeEvent 等机械能力。如果各自直接维护 `deque`、`asyncio.create_task()`、锁、重试计数和状态字典，会逐渐形成两套不一致的后台运行时。

但两者的业务语义并不相同：interaction submission 强调不丢失、幂等应用和会话内顺序；memory generation 强调昂贵任务的并发控制和用户取消。将它们强行塞入同一个全局 FIFO 或统一业务任务模型，同样会造成错误抽象。

本计划采用以下核心原则：

> 共享队列机制，不共享业务队列；一套 Local Work Queue Runtime，多条相互隔离的业务 lane。

## 2. 当前状态

### 2.1 Passive interaction submission

Passive ingress 已迁移到 Patchouli `InteractionSubmissionQueue`：

- accumulator prepare 后构建 versioned `InteractionSubmission`；
- queue admission 成功后才 commit/reset；
- admission 失败保留 payload 与稳定 `interaction_id`；
- apply retry、per-key FIFO、capacity 与 shutdown 由通用 runtime 接管；
- 原 `SealedTurnOutbox` 与 `SealedTurnSubmitter` 已退出主链路。

当前限制是 store 仍为 in-memory，进程退出后不能恢复 pending/retry work；Passive 的 conversation-local ordering 也不能重排 connector 已经乱序送达的源事件。

### 2.2 Memory generation runtime

`MemoryGenerationTaskController` 已通过 `MemoryGenerationQueue` 接入通用 runtime，并保持以下领域能力：

- `MemoryGenerationTask` 运行时句柄；
- `PENDING / RUNNING / COMPLETED / CANCELLED / FAILED` 状态；
- list/get/wait/cancel；
- RuntimeEvent 与 Patchouli local event；
- shutdown wait/drain；
- pending queue、并发限制、backpressure、timeout 与 retry classifier。

`WorkRecord` 作为执行状态真相源，`MemoryGenerationTask` 保持为 Patchouli 领域投影；当前同样只提供进程内恢复语义。

### 2.3 Maintenance scheduler

现有 `AsyncMaintenanceScheduler` 解决“何时触发 callback”，不负责持久化业务 work item，也不以 RuntimeEvent 驱动重试。它不应与当前工作队列合并；scheduler/hook/command 若未来产生真实长任务，应先独立冻结业务契约再决定是否接入 runtime。

## 3. 目标与非目标

### 3.1 目标

1. 提供一套进程内优先、可替换存储实现的 Local Work Queue Runtime。
2. 统一 enqueue、claim、状态迁移、并发控制、retry 调度、timeout、cancel、backpressure 和 shutdown drain 的机械实现。
3. 允许 Interaction Submission 与 Memory Generation 使用独立 lane、独立 policy 与独立 handler。
4. 业务模型、成功条件、错误分类、幂等语义和领域事件继续由各自应用组件拥有。
5. 首期不依赖 Redis、RabbitMQ、Celery 等外部消息中间件。
6. 通过 `WorkStore` port 支持从进程内 store 平滑迁移到 SQLite 等轻量持久化实现。
7. 保持现有 `MemoryGenerationTask` 与 active/passive public response 的领域表达，不向调用方暴露通用 runtime 内部模型。
8. 为进程崩溃恢复、任务 schema 版本和 handler registry 预留清晰扩展点。

### 3.2 非目标

1. 不在本计划首期引入分布式队列或多节点 worker 协调。
2. 不实现 DAG、任务图、父子 work 编排或跨任务事务。
3. 不将 interaction 与 memory generation 合并为同一个业务 `TaskSpec`。
4. 不让 infrastructure 层理解 `InteractionPayload`、`MemoryGenerationTaskSpec` 或 Patchouli/Alice 模型。
5. 不回溯改写已发布 v0.6.0 Passive ingress 的公共契约。
6. 不承诺进程内 store 在进程崩溃后的耐久性。
7. 不把 `AsyncMaintenanceScheduler` 改造成业务任务队列。
8. 不在没有真实长任务负载和稳定 Agent 执行能力前建立用户发布任务、后台 Agent workflow、priority 或 outcome artifact API。

## 4. 术语

### 4.1 Work Item

进入通用 runtime 的单个可执行工作项。它只包含稳定执行元数据与不透明/泛型业务 payload，不定义具体业务成功语义。

### 4.2 Lane

一组共享 policy、store namespace、并发配额与 handler 的隔离执行通道。不同 lane 不共享 FIFO 头部，不相互产生 head-of-line blocking。

首批预期 lane：

- `interaction_submission`
- `memory_generation`

### 4.3 Work Handler

业务模块提供的执行适配器。它负责解释 payload、调用领域能力、定义成功结果并分类异常；通用 runtime 不检查业务 payload 内容。

### 4.4 Work Store

保存 work record、状态和调度时间的基础设施 port。首期实现 `InMemoryWorkStore`，后续可实现 `SQLiteWorkStore`。

### 4.5 Domain Projection / Receipt

应用对外公开的领域句柄，例如 `MemoryGenerationTask` 与 `InteractionSubmissionReceipt`。它们不是 `WorkItem` 的别名，而是通用执行状态的领域投影。

### 4.6 Queue 与 Scheduler

- Scheduler 回答“什么时候触发”。
- Queue 回答“触发后什么时候获得执行资源”。
- Handler 回答“具体执行什么以及何时算成功”。

## 5. 两类业务队列的语义差异

| 维度 | Interaction Submission | Memory Generation |
| --- | --- | --- |
| 核心目的 | interaction 最终进入感知层 | 限制昂贵记忆生成任务并发 |
| 典型 payload | `InteractionPayload` + target topic | `MemoryGenerationTaskSpec` |
| 顺序 | 同 conversation/topic 严格 FIFO | 通常无需全局 FIFO |
| 并发 | 跨 ordering key 并发 | 全局/模型级低并发 |
| 取消 | 默认不允许 | 允许 queued/running 取消 |
| Retry | 强调最终提交与模糊失败恢复 | 只重试瞬态模型/存储错误 |
| 幂等 | 必须使用稳定 `interaction_id` | generation spec/intent 级幂等 |
| 成功 | interaction 被幂等应用 | MemoryAtom 创建/更新完成 |
| 用户可见 | 通常只暴露 accepted/applied 状态 | task list/get/cancel |
| 失败终态 | retry wait / dead letter | failed/cancelled |
| 存储优先级 | 最优先持久化 | 初期可进程内 |

结论：两者只复用执行骨架，不复用单一物理队列、payload、retry policy 或公共 API。

### 6.2 `system/runtime/work_queue` 职责

该层定义系统如何理解和推进一个后台 work item：

- `WorkItem` / `WorkRecord` / `WorkState`；
- `WorkQueuePort` / `WorkStorePort`；
- lane policy；
- 状态机与 transition guard；
- worker/lane 生命周期；
- timeout、cancel、retry-after、shutdown drain 编排；
- handler registry；
- 通用 RuntimeEvent 语义。

它属于系统运行时控制面，而不是外部技术适配层。

### 6.3 `infrastructure/work_queue` 职责

该层只实现可替换技术细节：

- `deque` / `heapq` / `asyncio.Condition`；
- SQLite schema、事务、atomic claim 与 lease recovery；
- work payload 的编码/解码；
- 存储容量实现；
- worker wakeup；
- 后续 Redis 等外部 adapter。

### 6.4 业务层职责

业务组件负责：

- 构造领域 spec；
- 选择 lane 与 ordering key；
- 定义是否允许取消；
- 识别 retryable exception；
- 实现幂等；
- 定义领域成功结果；
- 发布 Patchouli/Alice/System 领域事件；
- 将通用 work 状态投影为对外 domain task/receipt。

### 6.5 依赖规则

```text
Patchouli/System application
        -> system.runtime.work_queue ports/models

system.runtime.work_queue runtime
        -> WorkStorePort / WorkHandlerPort

infrastructure.work_queue adapters
        -> system.runtime.work_queue ports/models
```

禁止以下反向依赖：

- `system/runtime/work_queue` import Patchouli、Alice 或 server 模型；
- `infrastructure/work_queue` import `InteractionPayload` 或 `MemoryGenerationTaskSpec`；
- 业务 controller 直接 import `InMemoryWorkStore` / `SQLiteWorkStore`；
- infrastructure 根据 `work_kind` 编写业务分支。

composition root 负责实例化 store、runtime、lane 与 handler，并注入对应应用组件。

## 7. 通用运行时契约草案

以下模型仅表达目标边界，字段可在实现阶段收敛。

### 7.1 Work state

```python
class WorkState(str, Enum):
    QUEUED = "queued"
    RUNNING = "running"
    RETRY_WAIT = "retry_wait"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    DEAD_LETTER = "dead_letter"
    CANCELLED = "cancelled"
```

基本迁移：

```text
QUEUED -> RUNNING -> SUCCEEDED
                  -> RETRY_WAIT -> QUEUED
                  -> FAILED
                  -> DEAD_LETTER

QUEUED/RUNNING/RETRY_WAIT -> CANCELLED（仅 lane policy 允许时）
```

规则：

- 终态不可回退到非终态；
- retry 必须更新 `available_at` 和 attempts；
- cancellation 不得由通用 runtime 强行中断不支持取消的 handler；
- expired running lease 的恢复规则由 store/runtime 共同实现；
- RuntimeEvent 是观测事实，不作为状态推进命令。

### 7.2 Work item

```python
@dataclass(frozen=True)
class WorkItem:
    work_id: str
    lane: str
    kind: str
    schema_version: int
    payload: bytes
    ordering_key: str | None = None
    priority: int = 0
    correlation_id: str | None = None
    idempotency_key: str | None = None
```

运行字段保存在 `WorkRecord` 或 store row 中，而不是反向修改不可变的业务 spec：

- `state`
- `attempt_count`
- `enqueued_at`
- `available_at`
- `started_at`
- `finished_at`
- `lease_until`
- `last_error_class`
- `last_error_message`（脱敏）
- `result_ref` / `outcome_ref`

### 7.3 Lane policy

```python
@dataclass(frozen=True)
class QueuePolicy:
    capacity: int
    max_concurrency: int
    ordered_by_key: bool = False
    priority_enabled: bool = False
    cancellable: bool = True
    timeout_seconds: float | None = None
    max_attempts: int = 1
    terminal_retention: int = 100
```

retry backoff、jitter 和 error classification 不应全部塞入固定字段，可通过独立 `RetryPolicy` 与 handler decision 组合。

### 7.4 Failure decision

```python
class FailureAction(str, Enum):
    RETRY = "retry"
    FAIL = "fail"
    DEAD_LETTER = "dead_letter"
    TREAT_AS_SUCCESS = "treat_as_success"


@dataclass(frozen=True)
class FailureDecision:
    action: FailureAction
    retry_after_seconds: float | None = None
    reason: str | None = None
```

通用 runtime 负责执行 decision；handler 负责生成 decision。

### 7.5 Handler

```python
class WorkHandler(Protocol[PayloadT, ResultT]):
    async def execute(
        self,
        payload: PayloadT,
        context: WorkExecutionContext,
    ) -> ResultT: ...

    def classify_failure(
        self,
        error: Exception,
        context: WorkExecutionContext,
    ) -> FailureDecision: ...
```

通用 runtime 不捕获并解释 Patchouli 领域异常，也不直接发布 pending atom、interaction 或其他业务结果事件。

### 7.6 Work store

```python
class WorkStore(Protocol):
    async def enqueue(self, item: WorkItem) -> None: ...
    async def claim_ready(
        self,
        lane: str,
        *,
        limit: int,
        lease_seconds: float,
    ) -> list[WorkRecord]: ...
    async def mark_succeeded(self, work_id: str, result_ref=None) -> None: ...
    async def schedule_retry(
        self,
        work_id: str,
        *,
        available_at: datetime,
        error: WorkErrorSnapshot,
    ) -> None: ...
    async def mark_failed(self, work_id: str, error: WorkErrorSnapshot) -> None: ...
    async def cancel(self, work_id: str) -> bool: ...
    async def get(self, work_id: str) -> WorkRecord | None: ...
```

首期接口可以更小，但必须保持“状态真相源由 store/runtime 持有”的方向。

## 8. 一套 Runtime，多条 Lane

计划中的 `WorkQueueRuntime` 是 worker 生命周期宿主；每个业务能力注册独立 lane：

```python
interaction_lane = runtime.register_lane(
    "interaction_submission",
    handler=interaction_submission_handler,
    policy=QueuePolicy(
        capacity=1024,
        max_concurrency=8,
        ordered_by_key=True,
        cancellable=False,
        max_attempts=0,  # 0 可约定为由业务策略决定，不直接表示无限重试
    ),
)

memory_lane = runtime.register_lane(
    "memory_generation",
    handler=memory_generation_handler,
    policy=QueuePolicy(
        capacity=128,
        max_concurrency=2,
        ordered_by_key=False,
        cancellable=True,
        timeout_seconds=300,
        max_attempts=3,
    ),
)
```

lane 隔离要求：

- 每条 lane 独立 capacity、concurrency、ordering 与 retry policy；
- interaction backlog 与长时间 memory generation 不得相互占据 worker 或产生 head-of-line blocking；
- shutdown 可按 lane 设定不同 drain timeout；
- runtime 可统一 start/stop 与状态聚合，但不能将所有 work item 放入一个全局 FIFO。

## 9. Infrastructure adapter 规划

### 9.1 InMemoryWorkStore

首期默认实现，建议使用：

- 按 lane 分桶；
- ready queue 使用 `deque` 或按 `available_at/priority` 排序的 heap；
- `asyncio.Condition` 用于 worker wakeup；
- `asyncio.Lock` 保护状态迁移；
- ordering key 使用占用表或 per-key lock；
- terminal record 使用有界 retention；
- pending work 达到 capacity 时明确拒绝 enqueue，不静默丢弃已接受项目。

限制必须公开：

- 进程退出后 pending/running work 丢失；
- 不承诺跨进程 exactly-once；
- 仅适合单 event loop / 单进程运行；
- RuntimeEvent 不能替代 store 恢复。

### 9.2 SQLiteWorkStore

在需要跨重启恢复时优先实现 SQLite，而不是直接引入 Redis。目标能力：

- 单机零额外服务；
- transaction-protected enqueue/claim/ack；
- `available_at` 与 retry 调度；
- running lease 与进程崩溃恢复；
- idempotency key 唯一约束；
- lane/order key 索引；
- terminal retention 清理；
- 稳定 JSON bytes + schema version；
- outcome/artifact ref，而不是任意 Python 对象持久化。

SQLite adapter 不负责业务 schema migration；每个 `work kind` 的 codec 由 handler registry 或业务 adapter 提供。

### 9.3 `asyncio.Queue` 的定位

`asyncio.Queue` 可以作为 worker wakeup 或 ready item 的短期传递工具，但不应成为可靠队列的唯一状态真相源，因为它不适合：

- 按 work ID 查询与取消；
- 更新 retry 时间；
- dead letter；
- per-key FIFO claim；
- 持久化恢复；
- terminal history；
- atomic status transition。

## 10. Handler Registry 与可持久化任务

纯进程内实现可以把 coroutine closure 直接交给 runner，但 closure 无法序列化，会阻碍后续 SQLite 恢复。

建议从第一版开始使用稳定 `kind + schema_version + payload`：

```text
patchouli.interaction_submission.v1
patchouli.memory_generation.v1
```

启动时注册 versioned payload codec，并把同一 registry 注入 runtime：

```python
payload_codecs = WorkPayloadCodecRegistry()
payload_codecs.register(MemoryGenerationPayloadCodec())

runtime = WorkQueueRuntime(
    store=store,
    payload_codecs=payload_codecs,
)

payload_bytes = payload_codecs.encode(
    "patchouli.memory_generation.v1",
    1,
    generation_spec,
)
item = WorkItem(
    work_id=work_id,
    lane="memory_generation",
    kind="patchouli.memory_generation.v1",
    schema_version=1,
    payload=payload_bytes,
)
```

要求：

- kind 在版本内保持稳定；
- schema version 显式保存；
- codec 只把业务 DTO 投影为 JSON 基础类型，UUID、datetime、enum 等值必须显式规范化；
- registry 在 encode 边界使用 UTF-8、排序 key、紧凑分隔符与有限浮点数生成稳定 JSON bytes；
- `WorkItem` 只确认 payload 是不可变 `bytes`，不在每次构造时重复解析或重新编码；
- JSON 格式与业务 schema 在 codec decode / 持久化恢复边界验证，失败时安全进入 dead-letter；
- runtime 在每次 attempt 中重新解码，handler 对本次输入的修改不得污染 retry；
- enqueue 遇到未知 kind/version 时明确拒绝；已持久化 work 解码失败时进入 dead-letter；
- payload 不保存无法序列化的 coroutine、lock、event loop object、service instance 或领域实体；
- handler 依赖通过 composition root 注入，不放进 payload。

## 11. Interaction Submission Queue 集成

### 11.1 应用边界

```text
Passive turn accumulator --------┐
                                 ├-> InteractionSubmissionQueue
Active finalize -----------------┘       -> interaction lane
                                         -> InteractionSubmissionHandler
                                         -> Perception apply
```

Passive 专属能力继续保留在 `system/services/passive/`：

- external event normalization；
- `source + external_event_id` dedup；
- turn accumulator；
- final/next-user/idle/manual/shutdown seal；
- Passive public acknowledgement 与 memory context。

通用 submission queue 接管：

- payload snapshot；
- interaction idempotency key；
- pending/retry state；
- per-ordering-key FIFO；
- Patchouli apply；
- success acknowledgement；
- dead letter / backpressure；
- 通用 submission observability。

### 11.2 Submission envelope

```python
@dataclass(frozen=True)
class InteractionSubmission:
    interaction_id: str
    payload: InteractionPayload
    requested_topic_id: str
    ordering_key: str
    origin: Literal["active_chat", "passive_memory"]
    correlation: Mapping[str, str]
```

要求：

- enqueue 时对 payload 做深快照或规范化序列化；
- `interaction_id` 在所有 retry 中保持稳定；
- consumer 必须幂等，不能只依赖 producer dedup；
- `NEW_TOPIC` 的真实 topic 解析结果写入 receipt/work outcome；
- ambiguous failure（已经 add block 但调用方未收到成功）重试不得产生重复 block。

### 11.3 Active finalize continuation

Active `finalize_agent_run()` 当前包含：

1. interaction ingestion；
2. active materialization task dispatch；
3. retrieval hit record。

v0.6.1 选择 **同步 applied gate**：`finalize_agent_run()` 将 interaction 提交到共用 submission queue，并等待该 work 进入终态；只有 `SUCCEEDED` 才继续 active materialization task dispatch 与 retrieval hit record。`QUEUED`、`RUNNING`、`RETRY_WAIT` 和单纯拿到 receipt 都不构成 finalize success。

本阶段不引入后台 continuation 或多阶段 Finalization Job。当前 store 仍是 in-memory，也没有用户可查询的 finalization 状态；若在此时把后续步骤移出请求栈，会制造无法跨重启恢复、又难以向调用方解释的“已接管”状态。同步 gate 可以直接复用现有 `InteractionSubmissionQueue.submit()/wait()`，并保持当前 `finalize_agent_run()` 的返回契约。

若 interaction apply 进入 `FAILED/DEAD_LETTER`，finalize 明确失败，且不得执行后续 materialization/hit record。若 interaction 已成功 apply 而后续步骤失败，错误必须标明具体阶段；retry 不得重新生成 interaction identity，也不得重复追加 block。

### 11.4 Interaction 与 Topic 时序边界

Interaction 的时序保证不是 Passive 或 Active 任一链路的局部问题，而是两者向同一 Topic 提交对话事实时共同遵守的领域约束。所谓“绝对时间线”在当前系统中应拆成三层，避免过早引入一个承担所有语义的全局序列：

| 层级 | 顺序语义 | 当前所有者 |
| --- | --- | --- |
| Interaction timeline | 单个 interaction 内严格全序，`TurnEvent.sequence` 只在本 interaction 内有意义 | interaction producer 在 enqueue 前冻结 |
| Topic append order | 同一 topic 内 interaction/block 的权威提交顺序 | Patchouli/topic owner 在成功 apply 时确定；当前以实际 append 顺序作为临时权威投影 |
| Multi-Agent causality | 多个 Agent、frame 或 run 之间的 happens-before/causal relation，通常是偏序而非全序 | 当前不建模；未来由显式 causal metadata 表达 |

`occurred_at`、`received_at`、`enqueued_at` 和 `applied_at` 分别描述业务发生、入口接收、队列接纳和领域提交时间，只用于观测与诊断，不能合并为一个业务排序字段。未来若需要稳定持久化 topic 顺序，应由 topic owner 原子分配 `topic_position`，而不是从任一时间戳推导。

Work Queue 的 ordering key 只保证**已经成功入队**的 work 按 key 串行执行：

- 它不能恢复尚未到达或已经乱序到达的 Passive 源事件顺序；
- 它不能证明两个并发 Active run 在 prepare/LLM input 阶段看见过彼此的结果；
- idempotency journal 只负责识别重复提交，不负责决定业务顺序；
- `topic:{topic_id}` key 可以保护同 topic 的 finalize/apply 临界区，但不能倒推并修复此前读取 snapshot 时的并发。

例如 A、B 都基于 topic revision 10 完成 prepare，B 先成功提交为 position 11，A 后提交为 position 12。最终 topic append order 是 B -> A，但 A、B 都没有读取到对方的结果，因此该顺序不能被解释为 Agent 因果顺序。Active 与 Passive 共享 topic append 顺序问题；Active 额外存在 LLM input 所依据 snapshot 的一致性问题。

v0.6.1 采用以下轻量约束：

- interaction 内继续使用 `TurnEvent.sequence`，入队后不得改写；
- topic 当前以成功 apply 的 append 顺序作为权威投影，不新增全局序号；
- Active 在真实 topic 已知时使用 `topic:{topic_id}` ordering key；
- 暂时接受并发 Active run 读取同一 topic snapshot，不宣称 finalize ordering 已解决 prepare 并发；
- SQLite/topic 持久化阶段再评估原子 `topic_position` 和 `base_topic_revision`；
- 多 Agent 阶段再评估 `causal_parent_ids` 或等价的 run/frame 关系，并由 prompt/display 层进行确定性线性化；
- 本版本不实现全系统总序、向量时钟或完整事件溯源。

因此，当前系统需要的是 **topic-local authoritative log 与 multi-Agent causal relation**，而不是一个全系统绝对时间线。本节先冻结边界，不要求立即增加 `topic_position`、revision 或 causal relation 等时序字段。

### 11.5 Passive accumulator 交接策略

- Passive 不再保留 `SealedTurnOutbox` 与专属 submitter；
- accumulator 先 prepare 快照，queue admission 成功后再 commit/reset；
- admission 失败时保留当前 payload 与稳定 `interaction_id`，并向调用方施加背压；
- 若还要求 admission 失败后无条件开启下一 accumulator，就必须重新引入 pending store，本阶段不采用该语义。

## 12. Memory Generation Task 集成

### 12.1 保持领域 API

以下 Patchouli API 保持不变或保持兼容：

- submit generation；
- submit many；
- list/get；
- wait/wait many/wait all；
- cancel；
- RuntimeEvent；
- pending atom settlement/failure/cancellation event。

`MemoryGenerationTaskController` 继续作为 Patchouli 控制面，不被通用 queue runtime 替代。

### 12.2 替换直接 `create_task()`

目标链路：

```text
MemoryGenerationTaskController
  -> create MemoryGenerationTask domain handle
  -> enqueue patchouli.memory_generation.v1
  -> WorkQueueRuntime memory_generation lane
  -> MemoryGenerationHandler
  -> GENERATION_EXECUTE_SPEC
  -> project result/status back to MemoryGenerationTask
```

预期收益：

- 达到并发上限时任务真实停留在 queued/pending；
- queued 与 running 均可取消；
- timeout/retry/backpressure 机制不再由 Controller 重复实现；
- shutdown drain 与 Interaction Submission 使用同一机械骨架；
- memory generation policy 仍由 Patchouli 持有。

### 12.3 单一状态真相源

接入期间避免同时维护两套独立状态机：

- `WorkRecord` 是执行状态真相源；
- `MemoryGenerationTask` 是 Patchouli 领域投影；
- Controller 负责状态映射与 Patchouli event；
- 最终不应由 runner 和 Controller 分别、无协调地修改终态。

可采用 listener/projection adapter 过渡，但必须测试状态一致性。

### 12.4 Retry policy

Memory generation 默认只重试明确的瞬态失败，例如：

- 模型限流/临时不可用；
- 可恢复网络错误；
- 明确标记为 transient 的存储错误。

以下失败通常直接终止：

- invalid generation spec；
- schema/contract violation；
- 非幂等步骤已经产生不可确认副作用；
- 用户取消；
- 权限或 identity 不合法。

具体分类由 Patchouli handler 实现，通用 runner 只执行 decision。

## 13. Active 链路迁移设计

### 13.1 迁移目标与最小链路

Active 只迁移 interaction ingestion，不把整条 chat 编排改造成后台任务。目标链路为：

```text
Patchouli prepare（生成稳定 interaction_id 与真实 topic_id）
  -> Alice run completed
  -> Patchouli finalize 构造 InteractionPayload 快照
  -> InteractionSubmissionQueue.submit(origin="active_chat")
  -> InteractionSubmissionQueue.wait()
  -> SUCCEEDED: dispatch active materialization tasks
  -> record retrieval hits
  -> finalize 返回
```

`PatchouliSystem` 在 composition root 创建唯一的 `InteractionSubmissionQueue`，同时注入 Passive ingress 与 `PatchouliService`。Active 不再绕过 queue 直接调用 `INGESTION_SUBMIT_INTERACTION`；两种来源复用同一个 handler、幂等 apply 和 RuntimeEvent 语义。

### 13.2 稳定身份与 payload

- `prepare_agent_run()` 生成一次稳定 `interaction_id`，由 `PreparedAgentRun` 携带到 finalize；不得在每次 enqueue attempt 时重新生成；
- work ID 继续使用 `interaction:{interaction_id}`，idempotency key 使用同一 `interaction_id`；
- payload、target topic 和 ordering key 在第一次 submission 前完成规范化快照；重复提交相同 ID 但 payload 不同时必须拒绝；
- Active prepare 已获得真实 topic，因此 `requested_topic_id` 使用该 ID，`ordering_key` 使用 `topic:{topic_id}`；
- `origin` 固定为 `active_chat`，correlation 只保存安全的 topic/session/run 关联值，不写入正文。

若 Passive 已经解析出真实 topic，也应使用相同的 `topic:{topic_id}` key；仍处于 `NEW_TOPIC` 解析阶段时继续使用 conversation-local key。v0.6.1 不为极少发生的跨来源重叠增加全局锁，最终 topic 顺序仍以成功 apply 的 append order 为准。

### 13.3 共享容量与 admission

Active 与 Passive 共用 `interaction_submission` lane 的 capacity、worker concurrency 和 retry policy。默认单用户通常不会同时进行外部 Passive chat/import 与系统内 Active chat，因此本阶段：

- 不拆分 active/passive lane；
- 不设置来源配额、Active 保留槽位或来源优先级；
- capacity 统一统计 `QUEUED/RUNNING/RETRY_WAIT`，terminal retention 不占 active capacity；
- `origin` 必须保留在 submission 与领域观测中，以便分别统计 rejection、queue wait、apply latency 和 retry；
- 只有出现批量导入、持续 Active rejection、显著 wait latency 或多用户并发后，才重新评估配额或优先级。

该使用假设不能写成“运行时绝不并发”的不变量，因为 Passive backlog、retry 或 idle flush 仍可能与新 Active chat 短暂重叠。当前 runtime 在 capacity 满时采用明确的 `REJECT_NEW`：

- Passive 保留尚未 commit 的 accumulator，由入口返回 backpressure；
- Active admission 失败时 finalize 明确失败，不执行 materialization/hit record，也不能把已生成回复标记为已完整提交；
- 本阶段不增加 admission 等待队列或自动抢占；如果上层在同一 prepared run 内重试，必须复用原 `interaction_id`。

### 13.4 Applied gate 与后续副作用

Active 在 admission 成功后等待 `InteractionSubmissionOutcome`：

| Outcome | Active 行为 |
| --- | --- |
| `SUCCEEDED` | 校验结果 topic 与 prepared topic 一致，然后继续 materialization 与 hit record |
| `FAILED/DEAD_LETTER` | finalize 失败，不执行后续副作用 |
| `QUEUED/RUNNING/RETRY_WAIT` | 继续等待；不得提前返回完整成功 |
| outcome 缺失或 runtime shutdown | 返回明确的 finalization unavailable/error，不猜测 apply 是否完成 |

interaction lane 必须配置有限的 per-attempt timeout 与 `max_attempts`，让正常请求最终进入明确终态；应用层不再增加一个更短的 wait timeout，从而避免产生调用方无法查询的 pending finalization。进程 shutdown 或 owner task 取消仍可中断等待，但不得取消已接纳 work。

interaction apply、materialization dispatch 和 retrieval hit record 仍按现有请求内顺序执行，不在 v0.6.1 增加 checkpoint 状态机。interaction 已 apply 后若后续步骤失败，不能通过 cleanup 回滚 topic，也不自动重跑整个 finalize；应记录失败阶段。materialization 继续复用稳定 intent identity，retrieval hit 当前只保证单次调用内 dedup，跨调用幂等留给 I2 领域操作治理。

### 13.5 Cancellation、cleanup 与边界

- Alice 在 admission 前 cancelled/failed：不创建 submission，并按现有规则 cleanup prepared empty topic；
- admission 失败且新 topic 仍为空：可以执行现有有限 cleanup；已有 topic 不做补偿性删除；
- admission 成功后：queue 已接管 interaction，客户端断开或等待协程取消不得自动取消该 work，也不得 cleanup 它的 target topic；
- `cleanup_prepared_agent_run()` 必须先用 `PreparedAgentRun.interaction_id` 查询 submission；只要该 ID 已被 queue 接纳，就返回 no-op，不能只依赖 `ChatApplicationService.prepared_finalized`；
- apply 成功后：cleanup 不能撤销已提交 interaction；
- ordering key 只保护 apply，不保护 prepare/LLM input snapshot；并发 Active run 读取同一 snapshot 仍是本版本接受的限制。

## 14. Retry、幂等与模糊失败

### 14.1 投递保证

通用 runtime 默认提供 at-least-once execution，而不是声称 exactly-once。业务上的单次生效依赖：

```text
at-least-once delivery + stable idempotency key + idempotent consumer
```

### 14.2 Idempotency key

- Interaction: stable `interaction_id`；
- Memory generation: stable intent/spec/task identity；

store 可以为 `(lane, idempotency_key)` 提供唯一约束，但是否将重复视为成功由 handler 决定。

### 14.3 模糊失败

以下场景必须测试：

1. handler 完成副作用后、返回 success 前异常；
2. store mark-succeeded 失败；
3. worker 在 RUNNING 中退出；
4. RuntimeEvent 发布失败；
5. Active interaction 已 apply，但 materialization dispatch 或 hit record 未全部完成；
6. retry 时目标 topic 状态已经变化。

解决方向：

- consumer 幂等；
- side effect 与幂等记录尽量原子；
- 事件发布默认 best-effort，不反向推翻已提交业务终态；
- 持久化 store 使用 lease 恢复 abandoned RUNNING；
- 多阶段业务使用 checkpoint，而不是重跑整个不可分辨流程。

---

## 15. Backpressure 与容量

v0.6.1 固定使用 `REJECT_NEW`：capacity 达到上限时拒绝新 work 并返回明确错误，不允许静默丢弃已经 accepted 的旧 work item。本阶段不实现 `BLOCK_WITH_TIMEOUT`、自动抢占或 `DEAD_LETTER_NEW`；真实流量证明需要后再扩展 admission policy。

入口行为：

- Interaction Submission：持久化前不得返回 durable accepted；进程内版本满时明确失败/降级并发布高优先级事件；
- Memory Generation：拒绝或保持上游 pending，不丢弃现有任务；

lane capacity 和 concurrency 必须独立配置，避免某一类任务耗尽全部系统资源。

## 16. Cancellation、Timeout 与 Shutdown

### 16.1 Cancellation

- queue runtime 负责取消 queued item 和传递 cancellation token；
- handler 决定运行中是否可安全中断；
- interaction lane 默认禁止用户取消；
- memory generation 按 policy 支持取消；
- cancellation 必须幂等。

### 16.2 Timeout

- timeout 是 runtime 控制信号，不等价于业务副作用未发生；
- timeout 后是否 retry 由 handler 的幂等能力与 failure classifier 决定；
- 对不可确认副作用不能盲目重试。

### 16.3 Shutdown

`WorkQueueSupervisor.stop()` 目标流程：

1. 停止接受新 work（或切换为 rejecting）；
2. 停止 claim 新 item；
3. 等待各 lane running work 到各自 drain timeout；
4. 可安全取消的 work 发出 cancellation；
5. 持久化 store 中未完成 work 保留供重启恢复；
6. 进程内 store 报告 pending/running 丢失风险；
7. 输出按 lane 聚合的 shutdown summary。

## 17. 可观测性

### 17.1 通用 RuntimeEvent

至少提供：

- `work.queued`
- `work.started`
- `work.retry_scheduled`
- `work.succeeded`
- `work.failed`
- `work.dead_lettered`
- `work.cancel_requested`
- `work.cancelled`
- `work.rejected`

公共字段：

- work/lane/kind/schema version；
- correlation/idempotency key 的安全摘要；
- state/attempt；
- queue latency/execution latency；
- ordering key 的脱敏摘要；
- error class 与脱敏 reason；
- next retry time；
- outcome ref；
- capacity/concurrency snapshot。

### 17.2 领域事件

通用事件不替代：

- `PassiveTurnSubmitted/Failed`；
- memory task created/completed/failed/cancelled；
- pending atom settlement；

业务 controller 根据 work transition 发布领域投影事件。RuntimeEvent 发布失败不得作为默认业务 retry 依据。

### 17.3 敏感数据

默认不记录：

- 完整 `InteractionPayload` 文本；
- tool args；
- memory content；
- document content；
- 完整 exception payload。

事件只记录 ID、安全摘要、计数、耗时和错误分类。

## 18. 配置边界

建议配置按 runtime 默认值和 lane override 分层：

```yaml
work_queue:
  store: memory
  worker_poll_interval_seconds: 0.2
  shutdown_wait_seconds: 10
  lanes:
    interaction_submission:
      capacity: 1024
      max_concurrency: 8
      ordered_by_key: true
    memory_generation:
      capacity: 128
      max_concurrency: 2
      timeout_seconds: 300
      max_attempts: 3
```

配置所有权：

- store 技术配置属于 infrastructure/system runtime；
- lane capacity/concurrency 属于 system runtime composition；
- retryable error、业务 timeout 默认值可由对应 subsystem config 提供；
- Passive ingress 不再长期持有通用 submission queue 容量配置；迁移完成后只保留 accumulator/dedup/idle flush 配置。

## 19. 实现阶段

### Phase Q0：契约冻结与现状隔离（已完成）

- 创建 `system/runtime/work_queue` 的 models/ports/policy 草案。
- 明确 WorkState、lane、handler、store 和 receipt 边界。
- 明确 scheduler 不是 queue。
- 给当前 Passive outbox 标注进程内 best-effort 限制。
- 不修改 active/passive 业务时序。

验收：

- 公共 runtime 模型不 import Patchouli/Alice/server；
- 文档明确两类队列的不同成功与失败语义；
- v0.6.0 Passive 实现已独立完成并保持当前 outbox 契约。

### Phase Q1：In-memory Runtime MVP（已完成）

- 实现 `InMemoryWorkStore`。
- 实现 lane registry、enqueue、claim、ack、retry wait、capacity 与 shutdown drain。
- 实现 per-key FIFO 和 lane concurrency。
- 实现通用 RuntimeEvent。
- 暂不实现 SQLite、priority、复杂 progress 或 DAG。

验收：

- 不同 lane 不相互阻塞；
- 同 ordering key 严格 FIFO，不同 key 可并发；
- retry 保持 work ID 与原顺序约束；
- capacity 满时不静默丢弃；
- shutdown summary 准确。

### Phase Q2：Passive Interaction Submission Queue 迁移（已完成）

- 增加稳定 `interaction_id` 与 payload snapshot。
- 实现 Patchouli `InteractionSubmissionQueue/Handler`。
- Passive accumulator 结束后直接构建通用 submission work item。
- admission 成功后才 reset accumulator，删除 Passive outbox/submitter。
- raw perception apply 支持幂等。
- 增加 ambiguous failure 测试。
- 将通用 retry/config/observability 从 passive 移出。

Q2 只迁移 Passive 链路；Active 继续保持原 finalize 路径，待 Q4 按 §13 的同步 applied gate 独立迁移。

验收：

- passive 原有 public response 与 accumulator 行为不变；
- admission 失败不丢 payload，且下一 accumulator 不得覆盖它；
- admission retry 复用同一 `interaction_id`；
- retry 不产生重复 block；
- Passive 走通用 Patchouli submission handler，Active 保持原 finalize 路径；
- 同 conversation/topic 保持顺序。

### Phase Q3：Memory Generation 接入（已完成）

- `MemoryGenerationTaskController` 用 memory lane 替换直接 `create_task()`。
- 保持现有 public/local API 与事件兼容。
- 接入并发限制、queued cancel、running cancel、timeout 与 retry classifier。
- 将 WorkRecord 映射为 `MemoryGenerationTask` 领域状态。

验收：

- concurrency 达上限时任务保持 queued/pending；
- queued/running 均按策略可取消；
- wait/list/get 返回一致投影；
- retry 不重复产生不可接受副作用；
- shutdown drain 保持当前契约。

### Phase Q4：Active Interaction Submission 迁移（下一阶段）

- 在 prepare 阶段生成稳定 `interaction_id`，由 `PreparedAgentRun` 传递到 finalize。
- 将唯一 `InteractionSubmissionQueue` 注入 Passive ingress 与 `PatchouliService`。
- Active 构建 `origin="active_chat"` submission，并以 `topic:{topic_id}` 作为 ordering key。
- admission 成功后同步等待 work 终态；只有 `SUCCEEDED` 才继续 materialization 与 hit record。
- 为 interaction handler 配置有限 per-attempt timeout 与 `max_attempts`，不额外制造短于 work 生命周期的 pending response。
- cleanup 在删除 prepared empty topic 前查询稳定 `interaction_id`；已接纳的 submission 禁止 cleanup。
- capacity 满、terminal failure、outcome 缺失和 shutdown 分别返回明确 finalize error。
- 保持 Active/Passive 共享 interaction lane，不增加来源配额、priority 或 reserved capacity。

验收：

- Active 不再绕过 submission queue 直接 apply interaction；
- receipt/queued/retry-wait 不会被误报为完整 finalize success；
- admission/apply 失败时不执行 materialization 与 hit record；
- apply 成功后仍按现有顺序执行后续副作用；
- 重复 finalize 复用同一 `interaction_id`，不产生重复 block；
- 客户端在 admission 后断开不会取消已接管 interaction；
- Active/Passive backlog 重叠时满载行为明确且不静默丢弃；
- 不宣称 ordering key 已解决 prepare/LLM input snapshot 并发。

### Phase Q5：SQLite 持久化（后置）

- 实现 `SQLiteWorkStore`。
- 增加 schema migration、atomic claim、lease recovery 和唯一 idempotency key。
- 允许按 lane 选择 memory/sqlite store。
- 实现 terminal retention/cleanup maintenance。

验收：

- 重启后 queued/retry-wait work 可恢复；
- expired running lease 可安全重新 claim；
- 重复 idempotency key 不产生重复业务副作用；
- SQLite 不可用时 readiness/health 明确降级；
- 无需 Redis 等外部服务。

## 21. 迁移兼容与发布策略

1. 新 runtime 首先以内部 feature flag 或仅 interaction lane 方式启用。
2. 用 accumulator prepare/admission/commit 测试替换 Passive outbox 测试。
3. MemoryGenerationTask public API 不因底层 runner 迁移改变字段含义。
4. Active 接入可独立 feature flag；关闭时保留现有 finalize 路径，开启后最终成功受 applied gate 约束。
5. store 从 memory 切换 SQLite 时不改变应用 service method signature。
6. 所有迁移先确保 event/status projection 一致，再删除旧 registry/submitter。
7. 旧实现删除前必须覆盖 shutdown、cancel、模糊失败和幂等测试。

## 22. 风险与开放问题

### 22.1 Active applied gate 的可用性边界

v0.6.1 已选择同步 applied gate，不建立可恢复 finalization workflow。它保持实现简单，但 Active finalize 会直接受到 interaction lane wait latency、terminal failure 与 in-memory shutdown 的影响；必须通过明确错误和阶段观测暴露，而不能返回虚假的 durable accepted。

### 22.2 InteractionPayload 序列化与不可变性

Q2 已通过 versioned codec 把 `InteractionPayload` 显式投影为 JSON 基础类型，并在 registry encode 边界生成 canonical JSON bytes。`WorkItem` 只持有 bytes；handler 每次 attempt 都重新 decode，避免业务 DTO 的可变引用跨 attempt 泄漏。

### 22.3 Topic resolution

Passive `NEW_TOPIC` 在提交延迟时如何稳定映射真实 topic，是否需要 admission 时预留 topic ID，需要在 interaction queue 迁移设计中解决。

### 22.4 Interaction chronology 与 topic causal order

当前以成功 apply 的 append 顺序作为 topic-local 权威投影，但尚未持久化独立 `topic_position`，也没有表达并发 Agent 基于哪个 topic snapshot 执行。SQLite/topic 持久化阶段需要评估原子位置分配与 `base_topic_revision`；多 Agent 阶段需要评估 causal parents。评审中不得把 queue FIFO、topic append order 和 Agent causal order 混为同一种保证。

### 22.5 Store 粒度

是所有 lane 共享一个 store 实例、按 namespace 隔离，还是允许 lane 独立 store，需要由配置与 shutdown 复杂度权衡。建议接口允许两者，但首期采用单 runtime + 按 lane 分桶的 in-memory store。

### 22.6 Active partial finalize

interaction 已 apply、但 materialization dispatch 或 retrieval hit record 失败时，不能回滚 topic。当前以阶段化错误和“不自动重跑整个 finalize”限制扩大副作用；materialization 复用稳定 intent identity，retrieval hit 的跨调用幂等仍属于 I2 待办。只有真实出现跨请求恢复需求后，才重新评估 checkpoint continuation。

### 22.7 Dead letter 操作面

是否提供 list/replay/drop dead-letter work 的管理 API，首期可以只提供内部查询与 RuntimeEvent，持久化阶段再补正式操作面。

### 22.8 Shared interaction capacity

默认单用户不并行使用 Active/Passive，足以支持当前共享 capacity 决策，但 backlog、retry 和 idle flush 仍可能造成短暂重叠。若出现持续 rejection、Active wait latency 或批量导入需求，再以观测数据决定是否拆分配额或优先级。

## 23. 验收清单

1. 队列公共协议与状态机位于 `system/runtime/work_queue`，不依赖具体业务模型。
2. 内存、SQLite 等存储适配位于 `infrastructure/work_queue`，通过 port 注入。
3. Interaction Submission 与 Memory Generation 是独立业务组件与独立 lane。
4. 两类业务不共享单一全局 FIFO、payload、成功条件或 retry classifier。
5. queue runtime 统一实现 enqueue、claim、并发、retry、timeout、cancel、backpressure 和 shutdown 骨架。
6. scheduler 只负责触发，handler 负责业务执行，queue 负责任务获得执行资源。
7. 通用 runtime 不 import Patchouli、Alice 或 server 模型。
8. capacity 满时不静默丢弃已接受 work item。
9. RuntimeEvent 只用于观测，不反向驱动业务状态。
10. at-least-once delivery 与业务幂等边界有明确测试。
11. MemoryGenerationTask 迁移后 public API 与领域事件保持兼容。
12. Active finalize 使用同步 applied gate，只有 interaction work `SUCCEEDED` 才执行后续副作用并返回完整成功。
13. queue ordering、topic append order 与 Agent causal order 的所有者和保证范围不得混同。
14. 首期不依赖 Redis；未来可使用 SQLite 提供单机跨重启恢复。
15. v0.6.0 Passive ingress 的公共行为保持兼容，v0.6.1 已将其内部提交迁移到通用 queue adapter。

## 24. 决策摘要

本计划不建立一个理解所有业务的“万能任务队列”。最终目标是：

```text
应用层
  InteractionSubmissionQueue
  MemoryGenerationTaskController
          │
          ▼
系统运行时
  Local Work Queue Runtime
  - state machine
  - lanes
  - concurrency
  - retry / timeout / cancel
  - backpressure / shutdown
          │
          ▼
基础设施
  InMemoryWorkStore
  SQLiteWorkStore (future)
```

一句话原则：

> `infrastructure` 提供队列数据“如何保存和唤醒”的技术实现；`system/runtime` 定义工作项“如何推进生命周期”的公共运行时；各业务模块继续决定“执行什么、何时成功、何时重试以及发布什么领域结果”。
