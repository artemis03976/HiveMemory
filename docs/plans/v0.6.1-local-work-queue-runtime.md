## 1. 背景

项目中正在或即将出现三类具有“排队执行”特征的能力：

1. **Interaction Submission Queue**  
   在 active/passive mode 形成完整 `InteractionPayload` 后，负责缓存、提交、失败重试与成功确认，最终将 interaction 可靠地应用到 Patchouli 感知层。
2. **Memory Generation Task Queue**  
   承载 `MemoryGenerationTaskSpec`，限制昂贵记忆生成任务的并发，支持取消、超时、失败状态与结果查询。
3. **Runtime User Job Queue**  
   面向未来 document ingestion、Deep Research、后台 Agent workflow、定时任务与 hook-triggered job，提供用户可见的任务生命周期和 outcome artifact。

三者都会需要 enqueue、claim、并发控制、retry、cancel、timeout、backpressure、shutdown drain 和 RuntimeEvent 等机械能力。如果各自直接维护 `deque`、`asyncio.create_task()`、锁、重试计数和状态字典，会逐渐形成三套不一致的后台运行时。

但三者的业务语义并不相同：interaction submission 强调不丢失、幂等应用和会话内顺序；memory generation 强调昂贵任务的并发控制和用户取消；Runtime Job 强调用户可见状态、优先级、定时/hook 触发和 outcome artifact。将它们强行塞入同一个全局 FIFO 或统一业务任务模型，同样会造成错误抽象。

本计划采用以下核心原则：

> 共享队列机制，不共享业务队列；一套 Local Work Queue Runtime，多条相互隔离的业务 lane。

## 2. 当前状态

### 2.1 Passive interaction outbox

v0.6.0 Passive ingress 当前拥有进程内 `SealedTurnOutbox` 与 `SealedTurnSubmitter`：

- turn seal 后先进入 pending outbox；
- Patchouli submit 成功后移除；
- 失败时按会话顺序放回并等待重试；
- accumulator 与 sealed turn 分离，失败不阻塞下一轮外部对话。

该实现满足 v0.6.0 的局部交付目标，但它耦合了 `PassiveConversationKey`、`SealReason` 和 passive event emitter，不能直接充当 active mode、memory generation 或 Runtime Job 的公共队列。

### 2.2 Memory generation runtime

`MemoryGenerationTaskController` 已有以下能力：

- `MemoryGenerationTask` 运行时句柄；
- `PENDING / RUNNING / COMPLETED / CANCELLED / FAILED` 状态；
- list/get/wait/cancel；
- RuntimeEvent 与 Patchouli local event；
- shutdown wait/drain。

但任务提交后仍直接通过 `asyncio.create_task()` 启动，没有真正的 pending queue、并发配额、backpressure 或公共 retry runner。

### 2.3 Runtime Job Queue

Runtime Job Queue 仍属于 v0.6.1 路线图能力，尚未形成稳定实现。未来计划覆盖：

- 即时、定时和 hook-triggered job；
- list/get/cancel/retry/timeout；
- 用户可见失败原因；
- outcome artifact；
- document ingestion、Deep Research 与后台 Agent workflow。

### 2.4 Maintenance scheduler

现有 `AsyncMaintenanceScheduler` 解决“何时触发 callback”，不负责持久化业务 work item，也不以 RuntimeEvent 驱动重试。它不应与工作队列合并；未来 scheduler/hook/command 只作为 work item 的触发来源。

## 3. 目标与非目标

### 3.1 目标

1. 提供一套进程内优先、可替换存储实现的 Local Work Queue Runtime。
2. 统一 enqueue、claim、状态迁移、并发控制、retry 调度、timeout、cancel、backpressure 和 shutdown drain 的机械实现。
3. 允许 Interaction Submission、Memory Generation 和 Runtime Job 使用独立 lane、独立 policy 与独立 handler。
4. 业务模型、成功条件、错误分类、幂等语义和领域事件继续由各自应用组件拥有。
5. 首期不依赖 Redis、RabbitMQ、Celery 等外部消息中间件。
6. 通过 `WorkStore` port 支持从进程内 store 平滑迁移到 SQLite 等轻量持久化实现。
7. 保持现有 `MemoryGenerationTask`、Passive public response 和未来 `RuntimeJob` API 的领域表达，不向调用方暴露通用 runtime 内部模型。
8. 为进程崩溃恢复、任务 schema 版本和 handler registry 预留清晰扩展点。

### 3.2 非目标

1. 不在本计划首期引入分布式队列或多节点 worker 协调。
2. 不实现 DAG、任务图、父子 job 编排或跨任务事务。
3. 不将 interaction、memory generation 和 Runtime Job 合并为同一个业务 `TaskSpec`。
4. 不让 infrastructure 层理解 `InteractionPayload`、`MemoryGenerationTaskSpec`、Patchouli/Alice 模型或用户 job 语义。
5. 不回溯改写已发布 v0.6.0 Passive ingress 的公共契约。
6. 不承诺进程内 store 在进程崩溃后的耐久性。
7. 不把 `AsyncMaintenanceScheduler` 改造成业务任务队列。

## 4. 术语

### 4.1 Work Item

进入通用 runtime 的单个可执行工作项。它只包含稳定执行元数据与不透明/泛型业务 payload，不定义具体业务成功语义。

### 4.2 Lane

一组共享 policy、store namespace、并发配额与 handler 的隔离执行通道。不同 lane 不共享 FIFO 头部，不相互产生 head-of-line blocking。

首批预期 lane：

- `interaction_submission`
- `memory_generation`
- `runtime_job`

### 4.3 Work Handler

业务模块提供的执行适配器。它负责解释 payload、调用领域能力、定义成功结果并分类异常；通用 runtime 不检查业务 payload 内容。

### 4.4 Work Store

保存 work record、状态和调度时间的基础设施 port。首期实现 `InMemoryWorkStore`，后续可实现 `SQLiteWorkStore`。

### 4.5 Domain Task / Job

应用对外公开的领域句柄，例如 `MemoryGenerationTask`、`InteractionSubmissionReceipt`、未来 `RuntimeJob`。它们不是 `WorkItem` 的别名，而是通用执行状态的领域投影。

### 4.6 Queue 与 Scheduler

- Scheduler 回答“什么时候触发”。
- Queue 回答“触发后什么时候获得执行资源”。
- Handler 回答“具体执行什么以及何时算成功”。

## 5. 三类业务队列的语义差异

| 维度 | Interaction Submission | Memory Generation | Runtime User Job |
| --- | --- | --- | --- |
| 核心目的 | interaction 最终进入感知层 | 限制昂贵记忆生成任务并发 | 管理用户可见后台工作 |
| 典型 payload | `InteractionPayload` + target topic | `MemoryGenerationTaskSpec` | versioned job spec |
| 顺序 | 同 conversation/topic 严格 FIFO | 通常无需全局 FIFO | 按 priority、用户配额或 job kind |
| 并发 | 跨 ordering key 并发 | 全局/模型级低并发 | 按 job 类型配置 |
| 取消 | 默认不允许 | 允许 queued/running 取消 | 必须允许，具体阶段由 handler 决定 |
| Retry | 强调最终提交与模糊失败恢复 | 只重试瞬态模型/存储错误 | 由 job kind 决定 |
| 幂等 | 必须使用稳定 `interaction_id` | generation spec/intent 级幂等 | `job_id` 与 handler 自定义幂等 |
| 成功 | interaction 被幂等应用 | MemoryAtom 创建/更新完成 | outcome artifact 或业务结果完成 |
| 用户可见 | 通常只暴露 accepted/applied 状态 | task list/get/cancel | 完整 job 状态、进度、失败原因 |
| 失败终态 | retry wait / dead letter | failed/cancelled | failed/cancelled/dead letter |
| 存储优先级 | 最优先持久化 | 初期可进程内 | 用户可见后应持久化 |

结论：三者只复用执行骨架，不复用单一物理队列、payload、retry policy 或公共 API。

### 6.1 推荐目录

```text
src/hivememory/system/application/
  runtime_job_service.py          # v0.6.1 后续阶段
```

### 6.2 `system/runtime/work_queue` 职责

该层定义系统如何理解和推进一个后台 work item：

- `WorkItem` / `WorkRecord` / `WorkState`；
- `WorkQueuePort` / `WorkStorePort`；
- lane policy；
- 状态机与 transition guard；
- worker/lane 生命周期；
- timeout、cancel、retry-after、shutdown drain 编排；
- handler registry；
- 通用 RuntimeEvent 语义。

它属于系统运行时控制面，而不是外部技术适配层。

### 6.3 `infrastructure/work_queue` 职责

该层只实现可替换技术细节：

- `deque` / `heapq` / `asyncio.Condition`；
- SQLite schema、事务、atomic claim 与 lease recovery；
- work payload 的编码/解码；
- 存储容量实现；
- worker wakeup；
- 后续 Redis 等外部 adapter。

### 6.4 业务层职责

业务组件负责：

- 构造领域 spec；
- 选择 lane 与 ordering key；
- 定义是否允许取消；
- 识别 retryable exception；
- 实现幂等；
- 定义领域成功结果；
- 发布 Patchouli/Alice/System 领域事件；
- 将通用 work 状态投影为对外 domain task/job。

### 6.5 依赖规则

```text
Patchouli/System application
        -> system.runtime.work_queue ports/models

system.runtime.work_queue runtime
        -> WorkStorePort / WorkHandlerPort

infrastructure.work_queue adapters
        -> system.runtime.work_queue ports/models
```

禁止以下反向依赖：

- `system/runtime/work_queue` import Patchouli、Alice 或 server 模型；
- `infrastructure/work_queue` import `InteractionPayload` 或 `MemoryGenerationTaskSpec`；
- 业务 controller 直接 import `InMemoryWorkStore` / `SQLiteWorkStore`；
- infrastructure 根据 `work_kind` 编写业务分支。

composition root 负责实例化 store、runtime、lane 与 handler，并注入对应应用组件。

## 7. 通用运行时契约草案

以下模型仅表达目标边界，字段可在实现阶段收敛。

### 7.1 Work state

```python
class WorkState(str, Enum):
    QUEUED = "queued"
    RUNNING = "running"
    RETRY_WAIT = "retry_wait"
    SUCCEEDED = "succeeded"
    FAILED = "failed"
    DEAD_LETTER = "dead_letter"
    CANCELLED = "cancelled"
```

基本迁移：

```text
QUEUED -> RUNNING -> SUCCEEDED
                  -> RETRY_WAIT -> QUEUED
                  -> FAILED
                  -> DEAD_LETTER

QUEUED/RUNNING/RETRY_WAIT -> CANCELLED（仅 lane policy 允许时）
```

规则：

- 终态不可回退到非终态；
- retry 必须更新 `available_at` 和 attempts；
- cancellation 不得由通用 runtime 强行中断不支持取消的 handler；
- expired running lease 的恢复规则由 store/runtime 共同实现；
- RuntimeEvent 是观测事实，不作为状态推进命令。

### 7.2 Work item

```python
@dataclass(frozen=True)
class WorkItem:
    work_id: str
    lane: str
    kind: str
    schema_version: int
    payload: bytes
    ordering_key: str | None = None
    priority: int = 0
    correlation_id: str | None = None
    idempotency_key: str | None = None
```

运行字段保存在 `WorkRecord` 或 store row 中，而不是反向修改不可变的业务 spec：

- `state`
- `attempt_count`
- `enqueued_at`
- `available_at`
- `started_at`
- `finished_at`
- `lease_until`
- `last_error_class`
- `last_error_message`（脱敏）
- `result_ref` / `outcome_ref`

### 7.3 Lane policy

```python
@dataclass(frozen=True)
class QueuePolicy:
    capacity: int
    max_concurrency: int
    ordered_by_key: bool = False
    priority_enabled: bool = False
    cancellable: bool = True
    timeout_seconds: float | None = None
    max_attempts: int = 1
    terminal_retention: int = 100
```

retry backoff、jitter 和 error classification 不应全部塞入固定字段，可通过独立 `RetryPolicy` 与 handler decision 组合。

### 7.4 Failure decision

```python
class FailureAction(str, Enum):
    RETRY = "retry"
    FAIL = "fail"
    DEAD_LETTER = "dead_letter"
    TREAT_AS_SUCCESS = "treat_as_success"


@dataclass(frozen=True)
class FailureDecision:
    action: FailureAction
    retry_after_seconds: float | None = None
    reason: str | None = None
```

通用 runtime 负责执行 decision；handler 负责生成 decision。

### 7.5 Handler

```python
class WorkHandler(Protocol[PayloadT, ResultT]):
    async def execute(
        self,
        payload: PayloadT,
        context: WorkExecutionContext,
    ) -> ResultT: ...

    def classify_failure(
        self,
        error: Exception,
        context: WorkExecutionContext,
    ) -> FailureDecision: ...
```

通用 runtime 不捕获并解释 Patchouli 领域异常，也不直接发布 pending atom、interaction 或 job outcome 事件。

### 7.6 Work store

```python
class WorkStore(Protocol):
    async def enqueue(self, item: WorkItem) -> None: ...
    async def claim_ready(
        self,
        lane: str,
        *,
        limit: int,
        lease_seconds: float,
    ) -> list[WorkRecord]: ...
    async def mark_succeeded(self, work_id: str, result_ref=None) -> None: ...
    async def schedule_retry(
        self,
        work_id: str,
        *,
        available_at: datetime,
        error: WorkErrorSnapshot,
    ) -> None: ...
    async def mark_failed(self, work_id: str, error: WorkErrorSnapshot) -> None: ...
    async def cancel(self, work_id: str) -> bool: ...
    async def get(self, work_id: str) -> WorkRecord | None: ...
```

首期接口可以更小，但必须保持“状态真相源由 store/runtime 持有”的方向。

## 8. 一套 Runtime，多条 Lane

计划中的 `WorkQueueRuntime` 是 worker 生命周期宿主；每个业务能力注册独立 lane：

```python
interaction_lane = runtime.register_lane(
    "interaction_submission",
    handler=interaction_submission_handler,
    policy=QueuePolicy(
        capacity=1024,
        max_concurrency=8,
        ordered_by_key=True,
        cancellable=False,
        max_attempts=0,  # 0 可约定为由业务策略决定，不直接表示无限重试
    ),
)

memory_lane = runtime.register_lane(
    "memory_generation",
    handler=memory_generation_handler,
    policy=QueuePolicy(
        capacity=128,
        max_concurrency=2,
        ordered_by_key=False,
        cancellable=True,
        timeout_seconds=300,
        max_attempts=3,
    ),
)
```

lane 隔离要求：

- 每条 lane 独立 capacity、concurrency、ordering 与 retry policy；
- interaction backlog 不应阻止 Runtime Job 调度；
- 长时间 memory generation 不应占据 interaction worker；
- shutdown 可按 lane 设定不同 drain timeout；
- runtime 可统一 start/stop 与状态聚合，但不能将所有 work item 放入一个全局 FIFO。

## 9. Infrastructure adapter 规划

### 9.1 InMemoryWorkStore

首期默认实现，建议使用：

- 按 lane 分桶；
- ready queue 使用 `deque` 或按 `available_at/priority` 排序的 heap；
- `asyncio.Condition` 用于 worker wakeup；
- `asyncio.Lock` 保护状态迁移；
- ordering key 使用占用表或 per-key lock；
- terminal record 使用有界 retention；
- pending work 达到 capacity 时明确拒绝 enqueue，不静默丢弃已接受项目。

限制必须公开：

- 进程退出后 pending/running work 丢失；
- 不承诺跨进程 exactly-once；
- 仅适合单 event loop / 单进程运行；
- RuntimeEvent 不能替代 store 恢复。

### 9.2 SQLiteWorkStore

在需要跨重启恢复时优先实现 SQLite，而不是直接引入 Redis。目标能力：

- 单机零额外服务；
- transaction-protected enqueue/claim/ack；
- `available_at` 与 retry 调度；
- running lease 与进程崩溃恢复；
- idempotency key 唯一约束；
- lane/order key 索引；
- terminal retention 清理；
- 稳定 JSON bytes + schema version；
- outcome/artifact ref，而不是任意 Python 对象持久化。

SQLite adapter 不负责业务 schema migration；每个 `work kind` 的 codec 由 handler registry 或业务 adapter 提供。

### 9.3 `asyncio.Queue` 的定位

`asyncio.Queue` 可以作为 worker wakeup 或 ready item 的短期传递工具，但不应成为可靠队列的唯一状态真相源，因为它不适合：

- 按 work ID 查询与取消；
- 更新 retry 时间；
- dead letter；
- per-key FIFO claim；
- 持久化恢复；
- terminal history；
- atomic status transition。

## 10. Handler Registry 与可持久化任务

纯进程内实现可以把 coroutine closure 直接交给 runner，但 closure 无法序列化，会阻碍后续 SQLite 恢复。

建议从第一版开始使用稳定 `kind + schema_version + payload`：

```text
patchouli.interaction_submission.v1
patchouli.memory_generation.v1
system.runtime_job.document_ingestion.v1
system.runtime_job.deep_research.v1
```

启动时注册 versioned payload codec，并把同一 registry 注入 runtime：

```python
payload_codecs = WorkPayloadCodecRegistry()
payload_codecs.register(MemoryGenerationPayloadCodec())

runtime = WorkQueueRuntime(
    store=store,
    payload_codecs=payload_codecs,
)

payload_bytes = payload_codecs.encode(
    "patchouli.memory_generation.v1",
    1,
    generation_spec,
)
item = WorkItem(
    work_id=work_id,
    lane="memory_generation",
    kind="patchouli.memory_generation.v1",
    schema_version=1,
    payload=payload_bytes,
)
```

要求：

- kind 在版本内保持稳定；
- schema version 显式保存；
- codec 只把业务 DTO 投影为 JSON 基础类型，UUID、datetime、enum 等值必须显式规范化；
- registry 在 encode 边界使用 UTF-8、排序 key、紧凑分隔符与有限浮点数生成稳定 JSON bytes；
- `WorkItem` 只确认 payload 是不可变 `bytes`，不在每次构造时重复解析或重新编码；
- JSON 格式与业务 schema 在 codec decode / 持久化恢复边界验证，失败时安全进入 dead-letter；
- runtime 在每次 attempt 中重新解码，handler 对本次输入的修改不得污染 retry；
- enqueue 遇到未知 kind/version 时明确拒绝；已持久化 work 解码失败时进入 dead-letter；
- payload 不保存无法序列化的 coroutine、lock、event loop object、service instance 或领域实体；
- handler 依赖通过 composition root 注入，不放进 payload。

## 11. Interaction Submission Queue 集成

### 11.1 应用边界

```text
Passive turn accumulator --------┐
                                 ├-> InteractionSubmissionQueue
Active finalize -----------------┘       -> interaction lane
                                         -> InteractionSubmissionHandler
                                         -> Perception apply
```

Passive 专属能力继续保留在 `system/services/passive/`：

- external event normalization；
- `source + external_event_id` dedup；
- turn accumulator；
- final/next-user/idle/manual/shutdown seal；
- Passive public acknowledgement 与 memory context。

通用 submission queue 接管：

- payload snapshot；
- interaction idempotency key；
- pending/retry state；
- per-ordering-key FIFO；
- Patchouli apply；
- success acknowledgement；
- dead letter / backpressure；
- 通用 submission observability。

### 11.2 Submission envelope

```python
@dataclass(frozen=True)
class InteractionSubmission:
    interaction_id: str
    payload: InteractionPayload
    requested_topic_id: str
    ordering_key: str
    origin: Literal["active_chat", "passive_memory"]
    correlation: Mapping[str, str]
```

要求：

- enqueue 时对 payload 做深快照或规范化序列化；
- `interaction_id` 在所有 retry 中保持稳定；
- consumer 必须幂等，不能只依赖 producer dedup；
- `NEW_TOPIC` 的真实 topic 解析结果写入 receipt/work outcome；
- ambiguous failure（已经 add block 但调用方未收到成功）重试不得产生重复 block。

### 11.3 Active finalize continuation

Active `finalize_agent_run()` 当前包含：

1. interaction ingestion；
2. active materialization task dispatch；
3. retrieval hit record。

在 interaction 只进入 `QUEUED/RETRY_WAIT` 而未 `SUCCEEDED` 时，不得直接继续依赖已摄入 topic context 的后续步骤。

未来迁移必须选择并固定一种语义：

- **同步 applied gate**：只有 interaction applied 后 active finalize 才继续；或
- **可恢复 continuation**：submission succeeded event/checkpoint 恢复 active materialization 与 hit record；或
- **Active Finalization Job**：用多阶段 job 保存 `INGESTED -> TASKS_DISPATCHED -> HITS_RECORDED` checkpoint。

在 continuation 方案确定之前，不应仅为了复用 queue 就让 active finalize 在 interaction pending 时提前标记完整成功。

### 11.4 Passive accumulator 交接策略

- Passive 不再保留 `SealedTurnOutbox` 与专属 submitter；
- accumulator 先 prepare 快照，queue admission 成功后再 commit/reset；
- admission 失败时保留当前 payload 与稳定 `interaction_id`，并向调用方施加背压；
- 若还要求 admission 失败后无条件开启下一 accumulator，就必须重新引入 pending store，本阶段不采用该语义。

## 12. Memory Generation Task 集成

### 12.1 保持领域 API

以下 Patchouli API 保持不变或保持兼容：

- submit generation；
- submit many；
- list/get；
- wait/wait many/wait all；
- cancel；
- RuntimeEvent；
- pending atom settlement/failure/cancellation event。

`MemoryGenerationTaskController` 继续作为 Patchouli 控制面，不被通用 queue runtime 替代。

### 12.2 替换直接 `create_task()`

目标链路：

```text
MemoryGenerationTaskController
  -> create MemoryGenerationTask domain handle
  -> enqueue patchouli.memory_generation.v1
  -> WorkQueueRuntime memory_generation lane
  -> MemoryGenerationHandler
  -> GENERATION_EXECUTE_SPEC
  -> project result/status back to MemoryGenerationTask
```

预期收益：

- 达到并发上限时任务真实停留在 queued/pending；
- queued 与 running 均可取消；
- timeout/retry/backpressure 机制不再由 Controller 重复实现；
- shutdown drain 与 Runtime Job 使用同一机械骨架；
- memory generation policy 仍由 Patchouli 持有。

### 12.3 单一状态真相源

接入期间避免同时维护两套独立状态机：

- `WorkRecord` 是执行状态真相源；
- `MemoryGenerationTask` 是 Patchouli 领域投影；
- Controller 负责状态映射与 Patchouli event；
- 最终不应由 runner 和 Controller 分别、无协调地修改终态。

可采用 listener/projection adapter 过渡，但必须测试状态一致性。

### 12.4 Retry policy

Memory generation 默认只重试明确的瞬态失败，例如：

- 模型限流/临时不可用；
- 可恢复网络错误；
- 明确标记为 transient 的存储错误。

以下失败通常直接终止：

- invalid generation spec；
- schema/contract violation；
- 非幂等步骤已经产生不可确认副作用；
- 用户取消；
- 权限或 identity 不合法。

具体分类由 Patchouli handler 实现，通用 runner 只执行 decision。

## 13. Runtime User Job 集成

### 13.1 应用模型

未来 `RuntimeJobService` 负责：

- 创建用户可见 job；
- 用户身份、权限和确认；
- list/get/cancel/retry；
- job progress 与失败原因；
- outcome artifact；
- command/timer/hook 到 job spec 的转换。

通用 queue runtime 不直接成为 server public API。

### 13.2 触发链路

```text
Gateway command / HTTP request / timer / hook
  -> RuntimeJobService
  -> validate + build versioned JobSpec
  -> runtime_job lane
  -> handler registry
  -> business handler
  -> outcome artifact
  -> RuntimeJob projection/event
```

### 13.3 Scheduler 边界

定时 job 的 scheduler callback 只创建/提交 work item，不直接长期占用 scheduler callback 执行业务：

```text
AsyncMaintenanceScheduler tick
  -> enqueue RuntimeJob or maintenance work
  -> return
```

现有轻量且必须在 scheduler 内执行的维护 callback 可以保留，不要求全部队列化。只有需要 backpressure、重试、用户观察或长时间运行的任务才迁移到 queue。

### 13.4 Outcome artifact

通用 runtime 只保存 `result_ref/outcome_ref`，不保存任意大型业务结果。Runtime Job handler 负责把结果写入 ArtifactStore，再将引用写回 work/job record。

## 14. Retry、幂等与模糊失败

### 14.1 投递保证

通用 runtime 默认提供 at-least-once execution，而不是声称 exactly-once。业务上的单次生效依赖：

```text
at-least-once delivery + stable idempotency key + idempotent consumer
```

### 14.2 Idempotency key

- Interaction: stable `interaction_id`；
- Memory generation: stable intent/spec/task identity；
- Runtime Job: `job_id` 或 job-kind-specific business key。

store 可以为 `(lane, idempotency_key)` 提供唯一约束，但是否将重复视为成功由 handler 决定。

### 14.3 模糊失败

以下场景必须测试：

1. handler 完成副作用后、返回 success 前异常；
2. store mark-succeeded 失败；
3. worker 在 RUNNING 中退出；
4. RuntimeEvent 发布失败；
5. result artifact 已写入但 outcome ref 未回填；
6. retry 时目标 topic/job 状态已经变化。

解决方向：

- consumer 幂等；
- side effect 与幂等记录尽量原子；
- 事件发布默认 best-effort，不反向推翻已提交业务终态；
- 持久化 store 使用 lease 恢复 abandoned RUNNING；
- 多阶段业务使用 checkpoint，而不是重跑整个不可分辨流程。

---

## 15. Backpressure 与容量

通用 runtime 必须显式定义 capacity 达到上限时的行为：

- `REJECT_NEW`：拒绝新任务并返回明确错误；
- `BLOCK_WITH_TIMEOUT`：等待容量并支持超时；
- `DEAD_LETTER_NEW`：仅适合部分外部导入场景；
- 不允许静默丢弃已 accepted 的最旧 work item。

建议默认：

- Interaction Submission：持久化前不得返回 durable accepted；进程内版本满时明确失败/降级并发布高优先级事件；
- Memory Generation：拒绝或保持上游 pending，不丢弃现有任务；
- Runtime Job：创建失败应向用户返回 capacity/backpressure 状态。

lane capacity 和 concurrency 必须独立配置，避免某一类任务耗尽全部系统资源。

---

## 16. Cancellation、Timeout 与 Shutdown

### 16.1 Cancellation

- queue runtime 负责取消 queued item 和传递 cancellation token；
- handler 决定运行中是否可安全中断；
- interaction lane 默认禁止用户取消；
- memory generation/runtime job 按 policy 支持取消；
- cancellation 必须幂等。

### 16.2 Timeout

- timeout 是 runtime 控制信号，不等价于业务副作用未发生；
- timeout 后是否 retry 由 handler 的幂等能力与 failure classifier 决定；
- 对不可确认副作用不能盲目重试。

### 16.3 Shutdown

`WorkQueueSupervisor.stop()` 目标流程：

1. 停止接受新 work（或切换为 rejecting）；
2. 停止 claim 新 item；
3. 等待各 lane running work 到各自 drain timeout；
4. 可安全取消的 work 发出 cancellation；
5. 持久化 store 中未完成 work 保留供重启恢复；
6. 进程内 store 报告 pending/running 丢失风险；
7. 输出按 lane 聚合的 shutdown summary。

## 17. 可观测性

### 17.1 通用 RuntimeEvent

至少提供：

- `work.queued`
- `work.started`
- `work.retry_scheduled`
- `work.succeeded`
- `work.failed`
- `work.dead_lettered`
- `work.cancel_requested`
- `work.cancelled`
- `work.rejected`

公共字段：

- work/lane/kind/schema version；
- correlation/idempotency key 的安全摘要；
- state/attempt；
- queue latency/execution latency；
- ordering key 的脱敏摘要；
- error class 与脱敏 reason；
- next retry time；
- outcome ref；
- capacity/concurrency snapshot。

### 17.2 领域事件

通用事件不替代：

- `PassiveTurnSubmitted/Failed`；
- memory task created/completed/failed/cancelled；
- pending atom settlement；
- Runtime Job progress/outcome。

业务 controller 根据 work transition 发布领域投影事件。RuntimeEvent 发布失败不得作为默认业务 retry 依据。

### 17.3 敏感数据

默认不记录：

- 完整 `InteractionPayload` 文本；
- tool args；
- memory content；
- document content；
- 完整 exception payload。

事件只记录 ID、安全摘要、计数、耗时和错误分类。

## 18. 配置边界

建议配置按 runtime 默认值和 lane override 分层：

```yaml
work_queue:
  store: memory
  worker_poll_interval_seconds: 0.2
  shutdown_wait_seconds: 10
  lanes:
    interaction_submission:
      capacity: 1024
      max_concurrency: 8
      ordered_by_key: true
    memory_generation:
      capacity: 128
      max_concurrency: 2
      timeout_seconds: 300
      max_attempts: 3
    runtime_job:
      capacity: 256
      max_concurrency: 4
      priority_enabled: true
```

配置所有权：

- store 技术配置属于 infrastructure/system runtime；
- lane capacity/concurrency 属于 system runtime composition；
- retryable error、业务 timeout 默认值可由对应 subsystem config 提供；
- Passive ingress 不再长期持有通用 submission queue 容量配置；迁移完成后只保留 accumulator/dedup/idle flush 配置。

## 19. 实现阶段

### Phase Q0：契约冻结与现状隔离

- 创建 `system/runtime/work_queue` 的 models/ports/policy 草案。
- 明确 WorkState、lane、handler、store 和 receipt 边界。
- 明确 scheduler 不是 queue。
- 给当前 Passive outbox 标注进程内 best-effort 限制。
- 不修改 active/passive 业务时序。

验收：

- 公共 runtime 模型不 import Patchouli/Alice/server；
- 文档明确三类队列的不同成功与失败语义；
- v0.6.0 Passive 实现已独立完成并保持当前 outbox 契约。

### Phase Q1：In-memory Runtime MVP

- 实现 `InMemoryWorkStore`。
- 实现 lane registry、enqueue、claim、ack、retry wait、capacity 与 shutdown drain。
- 实现 per-key FIFO 和 lane concurrency。
- 实现通用 RuntimeEvent。
- 暂不实现 SQLite、priority、复杂 progress 或 DAG。

验收：

- 不同 lane 不相互阻塞；
- 同 ordering key 严格 FIFO，不同 key 可并发；
- retry 保持 work ID 与原顺序约束；
- capacity 满时不静默丢弃；
- shutdown summary 准确。

### Phase Q2：Interaction Submission Queue 迁移

- 增加稳定 `interaction_id` 与 payload snapshot。
- 实现 Patchouli `InteractionSubmissionQueue/Handler`。
- Passive accumulator 结束后直接构建通用 submission work item。
- admission 成功后才 reset accumulator，删除 Passive outbox/submitter。
- raw perception apply 支持幂等。
- 增加 ambiguous failure 测试。
- 将通用 retry/config/observability 从 passive 移出。

Active mode 接入前置条件：

- active finalize continuation 语义已确定；
- interaction applied 与 materialization/hit record 顺序有测试保护。

因此 Q2 当前只迁移 Passive 链路；Active 接入作为独立后半部分任务，不在本阶段实现。

验收：

- passive 原有 public response 与 accumulator 行为不变；
- admission 失败不丢 payload，且下一 accumulator 不得覆盖它；
- admission retry 复用同一 `interaction_id`；
- retry 不产生重复 block；
- Passive 走通用 Patchouli submission handler，Active 保持原 finalize 路径；
- 同 conversation/topic 保持顺序。

### Phase Q3：Memory Generation 接入

- `MemoryGenerationTaskController` 用 memory lane 替换直接 `create_task()`。
- 保持现有 public/local API 与事件兼容。
- 接入并发限制、queued cancel、running cancel、timeout 与 retry classifier。
- 将 WorkRecord 映射为 `MemoryGenerationTask` 领域状态。

验收：

- concurrency 达上限时任务保持 queued/pending；
- queued/running 均按策略可取消；
- wait/list/get 返回一致投影；
- retry 不重复产生不可接受副作用；
- shutdown drain 保持当前契约。

### Phase Q4：Runtime Job Queue

- 定义 versioned `RuntimeJobSpec` 与 `RuntimeJob` projection。
- 实现 `RuntimeJobService` 与 handler registry。
- 接入 Gateway command、timer 和 hook trigger。
- 支持 priority、用户可见状态、retry/cancel/timeout。
- outcome 写入 ArtifactStore，queue 只保存 ref。

验收：

- job list/get/cancel/retry 稳定；
- scheduler 只触发 enqueue；
- 未知 job kind/version 安全失败；
- handler 失败不破坏 queue worker；
- outcome artifact 可追溯。

### Phase Q5：SQLite 持久化

- 实现 `SQLiteWorkStore`。
- 增加 schema migration、atomic claim、lease recovery 和唯一 idempotency key。
- 允许按 lane 选择 memory/sqlite store。
- 实现 terminal retention/cleanup maintenance。

验收：

- 重启后 queued/retry-wait work 可恢复；
- expired running lease 可安全重新 claim；
- 重复 idempotency key 不产生重复业务副作用；
- SQLite 不可用时 readiness/health 明确降级；
- 无需 Redis 等外部服务。

## 22. 风险与开放问题

### 22.1 Active finalize 的事务边界

interaction apply、active memory task dispatch 与 retrieval hit record 是否组成一个可恢复 finalization job，仍需独立设计。该问题是 active 接入 submission lane 的前置决策。

### 22.2 InteractionPayload 序列化与不可变性

Q2 已通过 versioned codec 把 `InteractionPayload` 显式投影为 JSON 基础类型，并在 registry encode 边界生成 canonical JSON bytes。`WorkItem` 只持有 bytes；handler 每次 attempt 都重新 decode，避免业务 DTO 的可变引用跨 attempt 泄漏。

### 22.3 Topic resolution

Passive `NEW_TOPIC` 在提交延迟时如何稳定映射真实 topic，是否需要 admission 时预留 topic ID，需要在 interaction queue 迁移设计中解决。

### 22.4 Store 粒度

是所有 lane 共享一个 store 实例、按 namespace 隔离，还是允许 lane 独立 store，需要由配置与 shutdown 复杂度权衡。建议接口允许两者，但首期采用单 runtime + 按 lane 分桶的 in-memory store。

### 22.5 Progress

通用 WorkState 不包含业务 progress 百分比。Runtime Job progress 应作为领域投影/event，还是作为通用可选 metadata，需要在 v0.6.1 Runtime Job API 设计中决定。

### 22.6 Dead letter 操作面

是否提供 list/replay/drop dead-letter work 的管理 API，首期可以只提供内部查询与 RuntimeEvent，持久化阶段再补正式操作面。

### 22.7 Fairness

同 lane 内 priority 与 per-key ordering 同时启用时的公平策略，以及长时间高优先级任务是否导致 starvation，需要在 Runtime Job lane 启用 priority 前定义。

## 23. 验收清单

1. 队列公共协议与状态机位于 `system/runtime/work_queue`，不依赖具体业务模型。
2. 内存、SQLite 等存储适配位于 `infrastructure/work_queue`，通过 port 注入。
3. Interaction Submission、Memory Generation 和 Runtime Job 是独立业务组件与独立 lane。
4. 三类业务不共享单一全局 FIFO、payload、成功条件或 retry classifier。
5. queue runtime 统一实现 enqueue、claim、并发、retry、timeout、cancel、backpressure 和 shutdown 骨架。
6. scheduler 只负责触发，handler 负责业务执行，queue 负责任务获得执行资源。
7. 通用 runtime 不 import Patchouli、Alice 或 server 模型。
8. capacity 满时不静默丢弃已接受 work item。
9. RuntimeEvent 只用于观测，不反向驱动业务状态。
10. at-least-once delivery 与业务幂等边界有明确测试。
11. MemoryGenerationTask 迁移后 public API 与领域事件保持兼容。
12. Active finalize 在 continuation/事务边界确定前不提前将 pending interaction 当作完整 finalization success。
13. 首期不依赖 Redis；未来可使用 SQLite 提供单机跨重启恢复。
14. v0.6.0 Passive ingress 已独立交付，后续通过 adapter 渐进迁移。

## 24. 决策摘要

本计划不建立一个理解所有业务的“万能任务队列”。最终目标是：

```text
应用层
  InteractionSubmissionQueue
  MemoryGenerationTaskController
  RuntimeJobService
          │
          ▼
系统运行时
  Local Work Queue Runtime
  - state machine
  - lanes
  - concurrency
  - retry / timeout / cancel
  - backpressure / shutdown
          │
          ▼
基础设施
  InMemoryWorkStore
  SQLiteWorkStore (future)
  RedisWorkStore (optional future)
```

一句话原则：

> `infrastructure` 提供队列数据“如何保存和唤醒”的技术实现；`system/runtime` 定义工作项“如何推进生命周期”的公共运行时；各业务模块继续决定“执行什么、何时成功、何时重试以及发布什么领域结果”。
