# v0.7.0 计划 A：Workspace 资源平面重构协调计划

本文是 v0.7.0 计划 A 的协调入口。原计划 A 已覆盖访问边界、Patchouli application API、WorkspaceRuntime、缓存、Pending、MTP 和最终装配、Session/Topic 数据模型，已经不适合单个实施切片验收。本次拆分保留原有设计结论，把每个可独立交付的责任交给下列子计划。本文只维护共同不变量、依赖关系、跨计划出口和版本收口，不再重复维护子计划的完整字段或实现步骤。

计划 A 落实 [VISION](../VISION.md) 与 [AE2 类比](../ideas/ae2-hivememory-architecture-analogy.md) 的核心方向：Workspace 是独立存在的资源平面，Actor 是可以替换的执行者。Patchouli 继续拥有记忆领域的 canonical 数据和算法；Alice 是一个参考 Actor，不是资源系统的所有者。子计划仍属于 v0.7.0，不改变 v0.6.2 的版本归属。

本次是计划结构调整和新设计补充，不是重新验收实现。用户已完成的 WRX-0/1 工作作为现有成果承接；冻结清单的调查日期和当时验收记录保留。本次重排后 A1/A2/A5 保留 Active：A2 承接既有读取契约工作，A5 承接 API 收敛差额；新增缓存迁移不因并入 A2 而被宣称已实现。A3/A4/A6 为 Planned。状态仅说明承接工作，不表示原阶段作废或新增范围已经验收。frontmatter 的两个提交保留原计划调查时点，不是本次拆分的新代码审计结果。

## 2. 所有子计划共同遵守的边界

### 2.1 资源平面与执行平面

```text
System / Alice / Passive / 外部 Actor adapter
        -> System 统一 Actor Authentication 网关
             -> Principal authentication + Workspace authentication
             -> WorkspaceAccessContext（有效期间可复用，不绑定单次 operation）
        -> workspace 能力边界
             -> 逐次行为授权（operation）
             -> resolver：L0 pending registry / L1 cache / L2 Patchouli backing 路由
                  -> 资源归属与资源 policy 校验（纵深防御）
             -> canonical resource or domain work
```

`WorkspaceRuntime` 聚合 Workspace 访问注册、内部准入判定与行为检查、派生 cache、pending registry、alias resolver 与 profile 读取 resolver、失效、资源副本隔离和生命周期基础设施；System 的统一认证网关使用这些能力，保持唯一对外认证入口。Runtime 不是第二个 Patchouli application，也不取得 Patchouli 的私有 provider、store、familiar、controller 或 local route。A1 网关与访问设施可独立组合，不等待 Runtime 装配。Workspace 侧禁止复制记忆领域语义（检索排序、去重、内容合并、类型行为、编译与任何写路径），承担引用解析、逐次行为授权、缓存与失效事件订阅；双向精确边界由[边界宪章 §5.1](./v0.7.0-plan-a-boundary-charter.md)冻结。

三种调用主体的差异只在 principal 来源、adapter 触发时机、输入输出协议和 operation 上。管理员、Alice 与外部 Actor 对同一业务操作必须使用同一全局路由和 Patchouli application；System application service、AliceBridge 和外部 adapter 可以承担各自的协议编排，但不能形成第二个领域实现。具体示例集中在 A5，避免在多个文档维护不同版本。

### 2.2 两次身份认证与两类运行时授权

```text
System 统一 Actor Authentication 网关
  [Principal authentication → Workspace authentication / admission]
  -> 两项均通过，返回 WorkspaceAccessContext
每次业务动作
  [Operation authorization → Resource authorization]
  -> 领域处理
```

2026-09-19 修订后的详细职责以[A1（已归档）](../archive/plans/v0.7.0-a1-workspace-access-boundary.md)为准，当前事实见 [Workspace 架构](../architecture/workspace.md)第 4 节：System 网关验证接入登记后委托 Workspace guard 完成内部准入，调用侧不分别访问两个认证服务。principal 归 System；最小 context、签发生命周期及逐次行为检查归 Workspace，公共 application 不依赖 System 认证实现。Patchouli 提交继续使用自身已有的来源记录，不从认证 context 重复传递来源字段。原 `Domain operation policy` 与 `Operation authorization` 合并，资源 owner 独立授权；输入有效性和资源状态仍由领域实现判断。A1 第 7 节维护约束承接清单，wait/关闭和内部失效通知等原约束不因流程重排消失。

`MemoryAccessPolicy` 的 PRIVATE/TEAM/PUBLIC 是资源读取规则，不决定 Actor 能执行哪些操作，也不能代替 Workspace 准入。缓存命中、全局 UUID、`system` 标记和 task ID 都不是访问凭证。同一 principal 可以服务多个 Actor，行为权限按 Actor + Workspace 登记，不按接入来源全局授予。

### 2.3 Session、Topic、Pending 和 cache 的所有权

- 新增 `ConversationSession` 记录会话连续性、顺序和生命周期；演进 `InteractionPayload` 承接一次封口交互，扩展 `TurnEvent` 保存消息、工具调用和工具结果等事件，不并行新建 Segment/Part 正文模型。
- Patchouli 消费 InteractionPayload，产生 Topic 路由、`LogicalBlock` 和 `TopicData` 投影；路由关联复用应用记录与授权结果投影。Session 不在事务上拥有 Topic，也不要求把完整 Session 历史送入模型。详细模型、状态和迁移只在 A3 维护。
- Pending registry 是 workspace 持有的主动写入权威意图（[边界宪章 §6.2](./v0.7.0-plan-a-boundary-charter.md)）。Alice 只保存 run/frame/action 关联、提交时机和取消策略；外部 Actor 也可以通过同一能力面使用 Pending。详细状态机只在 A4 维护。
- Profile/Atom cache 是 WorkspaceRuntime 的可重建资源副本，不能保存永久授权或成为第二 canonical truth。2026-09-20 修订：资源 key 只按 Workspace 与引用寻址，Atom cache 保存完整 MemoryAtom，命中时按 Actor 判断资源可见性并免于回源查询；当前性由受控写入同步更新/失效保证。详细 key、Profile 源原子与解析结果、epoch、负缓存和并发约定只由 [A2 第 2 节](./v0.7.0-a2-workspace-resource-reads-and-caches.md#2-cache-契约)维护。
- 内容版本、`meta.lifecycle`、完整历史与受控写入只由 [A2-P](../archive/plans/v0.7.0-a2-pre-memory-version-and-lifecycle.md)维护；状态更新不推进内容版本、不整颗重写，A2 按变更影响更新缓存，不把状态维护等同于 Profile 重解析。完整原子的 schema 与历史完整性不能留给 READ 编译器补救。

Workspace 归属、Patchouli/System 的领域责任和 Runtime 的实例持有是三个维度。共同读取由 workspace 能力面编排，canonical 数据有效性由 Patchouli 在 backing 边界保证；归属判据由[边界宪章](./v0.7.0-plan-a-boundary-charter.md)冻结，ADR 继承表仍由 A2 第 1.1 节维护（其归属结论已由宪章取代）。

### 2.4 两条独立业务路由

`interaction.submit` 接收已经发生的完整交互，由 adapter 在封口信号后自动交接；`memory_intent.submit` 接收明确的 WRITE/UPDATE 意图，输入可以是 `PendingAtomMaterializeTask`。二者可以由同一个 application service 承接，但必须是独立路由方法、独立授权和独立阶段语义。普通交互不隐式触发主动写入；主动意图也不要求先存在交互 block。

### 2.5 共同引用读取与 Profile 应用

System、Alice 与外部 adapter 的资源读取进入同一 workspace 读取能力面（resolver），不各自拼装 Pending→cache→storage 的三级查询；L2 冷读调用 Patchouli backing 路由（宪章 §4.4）。[A2 第 1.3 节](./v0.7.0-a2-workspace-resource-reads-and-caches.md#13-canonical-读取结果与公开路由)固定 canonical 点读为完整 MemoryAtom/None、alias 与检索为 list[MemoryAtom]、Profile 读取为 AgentProfile；MemorySnapshot/ProfileSnapshot 退出，RetrievalResponse 仅可作为 adapter/本地运行上下文包装。A4 第 4.1 节定义共同引用的状态结果与 Pending 结算扩展，其 canonical 内容仍是完整原子，不改变 A2 基础方法返回类型；A5 核对全局目录，A6 删除 Alice 的独立解析路径。运行侧只保留本地引用关联和协议呈现；解析成功不等于获得执行或更新权限。

Profile 定义的查找、解析与缓存是资源能力；选择和应用定义、模型/工具绑定与完整 system prompt 组装属于 Actor。A2 第 1.4 节维护详细边界，A6 承接 Alice 的执行应用，B 暴露定义读取而不要求外部 harness 能接收动态 system prompt。不支持动态 Profile 的 Actor 仍可完整使用共同记忆 API。

| A5 | A1–A4 已交付的公开路由、模型与行为证据 | A6 删除旧入口、生产装配及 B 发布 |
| A6 | A1–A5 的稳定接口和完整交付记录 | B 的独立协议出口；两者在版本发布时联合核对 |

因此 `interaction.submit` 的共同输入由 A3 定义并实现，`memory_intent.submit(PendingAtomMaterializeTask)` 由 A4 定义并实现；A5 引用它们时已处于依赖下游。共同 canonical 读取由 A2 提供，Pending 状态结果扩展由 A4 在同一领域链实现，不再要求两个计划相互等待冻结。Topic prepare/handle、assignment、条件清理和资料绑定只维护在 [A3 第 4 节](./v0.7.0-a3-conversation-session-and-topic-projection.md#4-topic-路由指令与交接)，其公开方法也由 A3 交付。

靠前计划可以说明后续交付去向，但不能把靠后计划待冻结的约定或验收作为自身完成条件。后续新增 operation、状态结果或 mutation 路径由引入方按已交付基础契约扩展并验证；消费时发现缺陷应修复其领域实现，不意味着前置计划原本需要等待所有未来消费者才算完成。

实现可以复用既有成果并提前研究后续差额，但不能把“提前冻结后面契约”当成消除循环依赖的办法。各计划用真实总线/application 独立组合验证；稳定生产装配属于 A6。A6 可按就绪能力提前迁移消费者，其完整完成仍依赖前置全部出口。

B EMS-0 的场景调查可先行，EMS-1 按 A2–A4 实际交付的模型分批冻结 wire，EMS-2 消费 A3，EMS-3/4 消费 A2/A4，完整操作映射核对 A5。B 的无 Alice 组合不以 A6 全部执行侧重排为前置；旧 Passive 生产路径的替换与 A6 对齐。A 系列任何计划都不等待 B 的协议完成，v0.7.0 发布才合并检查两组出口。

## 4. 跨计划兼容和迁移规则

1. W0 的 `WorkspaceIdentity`、`IdentityScope`、WorkspaceAsset READY/lease、MTP/SSE 名称和既有错误分类继续作为兼容基线；任何变化都进入明确迁移矩阵。
2. `ActorIdentity.session_id` 只作为兼容读取字段保留。目标是在交互输入中直接携带 session_id，结合可信 access 校验，不要求新增 SessionRef/InteractionContext，不得将其重新当作 Workspace、Topic 或授权身份。
3. `InteractionPayload` 当前混合会话内容、Alice 结构化事件、主动物化任务、worth_saving 和附件使用信息。A3 演进该模型为共同领域输入，以 TurnEvent 为唯一事件正文，封口/提交复用同一 interaction_id；`InteractionSubmission` 继续是队列内部 envelope，`materialize_tasks` 从新版本普通交互输入中移出，旧混合输入不能静默丢任务。
4. 旧 `PatchouliService.prepare_agent_run/finalize_agent_run/cleanup_prepared_agent_run` 可以在迁移期委托新 API，但不能与新 API 并行拥有领域成功路径。A6 逐项关闭旧职责。
5. 旧 Alice cache、Pending runtime 和 resolver 入口可以有期限的 adapter/re-export，但不得保留第二份可独立命中的 cache、第二个 Pending 状态机或绕过 admission 的公共成功路径。
6. 已接纳的领域工作不能因 adapter 断连、通知丢失或 Alice 停止而被改判失败；回滚不得删除已接纳 Pending、Session、交互记录或 canonical 结果。
7. Memory schema 与版本 Artifact 格式迁移由 A2-P 交付，保留内容版本及旧历史的真实完整性；A2 只迁移缓存，不能用缓存回滚退回旧数据格式或 lifecycle 整原子写入。后续 A4/A5 新写入者复用前置的受控提交。
8. 公共读取结果按 A2 固定，旧 envelope 仅在调用侧包装；A2 删除 ProfileSnapshot 及其路由，A6 退出旧消费者依赖。源原子 UUID/version 属缓存内部关联，完整资源来源通过 Memory API 读取，不新增 Profile 包装 DTO 或按调用方变化的返回类型。

## 5. A 系列共同验收出口

A 系列完成需要同时具备以下证据：

- 无 Alice 的真实 GlobalSystemBus → Patchouli application → canonical 资源链能够完成 Profile/Memory/Attachment 读取、交互提交和主动意图提交；
- 两个 Workspace 的身份、资源 policy、缓存 key、Topic/Session 关联、Pending 读取和任务结果不串扰；
- System、Alice、Passive 和参考外部 adapter 对同一操作进入同一业务路由，领域结果和错误阶段可解释；
- 普通交互提交和主动意图提交各自独立，空 Topic 仍可接纳有效 WRITE/UPDATE，物化前可读回意图，结算后可解析真实 canonical 结果；
- 相同访问条件下三类 adapter 的 Pending/canonical 读取有一致领域结果；Alice 不再自行命中资源 cache 或解释 settlement；Profile 定义与执行应用分别验收，无法注入 system prompt 的客户端仍可使用记忆服务；
- Session 历史能够承载外部确定性会话，Topic 仍只承担记忆侧工作集；外部摘要/检查点带 provenance，不覆盖 canonical Topic summary；
- 内容修订有完整历史，lifecycle 维护不改内容版本或重写内容；合法 mutation 按影响同步更新/失效 cache，Alice 停止不清理 Workspace cache，shutdown 按“停收 → drain → detach → close”完成；
- 没有新的 Workspace 业务 port/provider 层，Patchouli application 仍是业务 API 唯一实现；
- 文档、契约和 ADR 只有在实现、测试、审查收尾后才晋升为当前事实，完成的子计划分别归档。

## 6. 风险与版本收口

主要风险是把拆分误解为增加转发层、把 Session 历史误作 Topic 工作集、把 Pending 再次绑定 Alice、或以 fake route 验证替代真实业务链。每个子计划必须以行为和状态所有权验收，不能以目录数量、类名或转发次数验收。

计划 A 不包含外部厂商 connector、强沙箱、完整历史导入、Deep Research 编排或跨重启的通用任务恢复。它为这些工作提供资源、来源、Session/Topic 和主动意图边界；具体实现按 [ROADMAP](../ROADMAP.md) 后续计划推进。v0.7.0 发布前，A 系列与计划 B 分别完成自己的出口；任一子计划完成都不代表整个版本完成。

实现收口时，更新 `docs/plans/README.md`、`ROADMAP.md` 和相关当前事实文档。ADR-0004 的正式替代须满足 A2 第 5 节门禁：A6 完成共同读取、Pending 解析、消费者和生命周期的联合验收后，以最终实现建立后继 ADR 并记录 supersede 关系；不能仅因 A2 移完实例就宣布替代完成。原协调计划及各子计划在对应切片完成后分别归档，不把仍在调整的设计提前写入架构事实文档。
