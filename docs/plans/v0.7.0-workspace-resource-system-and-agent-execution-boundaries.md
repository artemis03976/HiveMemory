# v0.7.0 计划 A：Workspace 资源平面重构协调计划

本文是 v0.7.0 计划 A 的协调入口。原计划 A 已覆盖访问边界、Patchouli application API、WorkspaceRuntime、缓存、Pending、MTP 和最终装配、Session/Topic 数据模型，已经不适合单个实施切片验收。本次拆分保留原有设计结论，把每个可独立交付的责任交给下列子计划。本文只维护共同不变量、依赖关系、跨计划出口和版本收口，不再重复维护子计划的完整字段或实现步骤。

计划 A 落实 [VISION](../VISION.md) 与 [AE2 类比](../ideas/ae2-hivememory-architecture-analogy.md) 的核心方向：Workspace 是独立存在的资源平面，Actor 是可以替换的执行者。Patchouli 继续拥有记忆领域的 canonical 数据和算法；Alice 是一个参考 Actor，不是资源系统的所有者。子计划仍属于 v0.7.0，不改变 v0.6.2 的版本归属。

本次是计划结构调整和新设计补充，不是重新验收实现。用户已完成的 WRX-0/1 工作作为现有成果承接；冻结清单的调查日期和当时验收记录保留。A1/A2 的 Active 表示继续处理新增差额，不表示原阶段整体作废。新增 A3–A6 标记 Planned，不凭目录和文档状态推断实现进度。frontmatter 的两个提交保留原计划调查时点，不是本次拆分的新代码审计结果。

## 2. 所有子计划共同遵守的边界

### 2.1 资源平面与执行平面

```text
System / Alice / Passive / 外部 Actor adapter
        -> CallerPrincipal
        -> WorkspaceAccessBoundary
        -> operation-specific GlobalSystemBus route
        -> Patchouli application
        -> ownership / visibility / domain policy
        -> canonical resource or domain work
```

`WorkspaceRuntime` 只聚合 access context、派生 cache、失效、快照和生命周期基础设施；它不是第二个 Patchouli application，也不取得 Patchouli 的私有 provider、store、familiar、controller 或 local route。Workspace service 只能承担准入、缓存、lease 和失效等基础设施职责，不能复制 `get_memory`、`search`、`submit_interaction` 或任意 action dispatch。

三种调用主体的差异只在 principal 来源、adapter 触发时机、输入输出协议和 operation 上。管理员、Alice 与外部 Actor 对同一业务操作必须使用同一全局路由和 Patchouli application；System application service、AliceBridge 和外部 adapter 可以承担各自的协议编排，但不能形成第二个领域实现。具体示例集中在 A2，避免在多个文档维护不同版本。

### 2.2 统一的四阶段访问检查

```text
CallerPrincipal 建立
  -> Workspace admission
  -> operation authorization
  -> resource ownership / visibility
  -> domain policy
```

前两阶段由 A1 的 `WorkspaceAccessBoundary` 提供，后两阶段由资源所有者和 Patchouli application 重验。`MemoryAccessPolicy` 的 PRIVATE/TEAM/PUBLIC 可作为资源读取 policy 的共同词汇，但不等于 admission，也不能推出写入、删除、取消或管理权限。缓存命中、全局 UUID、`system` 标记和 task ID 都不是访问凭证。

### 2.3 Session、Topic、Pending 和 cache 的所有权

- `ConversationSession` 记录外部会话连续性、顺序和生命周期；`ConversationSegment` 是一次封口的共同交互输入；`ConversationPart` 保存消息、工具调用和工具结果等原始事件。
- Patchouli 消费 Segment，产生 Topic 路由、`LogicalBlock` 和 `TopicData` 投影。Session 不在事务上拥有 Topic，也不要求把完整 Session 历史送入模型。详细模型、状态和迁移只在 A4 维护。
- Pending 是主动写入的资源侧权威意图。Alice 只保存 run/frame/action 关联、提交时机和取消策略；外部 Actor 也可以通过同一主动意图路由使用 Pending。详细状态机只在 A5 维护。
- Profile/Atom cache 是 WorkspaceRuntime 的可重建派生值，不能保存永久授权或成为第二 canonical truth。A3 维护 key、revision、epoch、负缓存、并发和失效。

### 2.4 两条独立业务路由

`interaction.submit` 接收已经发生的完整交互，由 adapter 在封口信号后自动交接；`memory_intent.submit` 接收明确的 WRITE/UPDATE 意图，输入可以是 `PendingAtomMaterializeTask`。二者可以由同一个 application service 承接，但必须是独立路由方法、独立授权和独立阶段语义。普通交互不隐式触发主动写入；主动意图也不要求先存在交互 block。

## 3. 依赖图与执行顺序

```text
WRX-0/1 成果 -> A1 访问契约 + A2 共同 API 目录
                              |
              +---------------+---------------+
              |               |               |
        A3 Runtime/cache  A4 Session/Topic  A5 Pending/intent
              |               |               |
              +---------------+---------------+
                              |
                    A6 消费者切换与稳定装配

A1/A2 先复用旧契约并关闭差额；A3/A4 可按已冻结接口并行。
A5-0 与 A4-0 对齐 Topic 来源引用；A5 的 mutation 失效使用 A3。
A6 按读取、交互、Pending 分别切换稳定能力，最后才接入完整生产组合。
B EMS-0/1 可先行；EMS-2 消费 A4，EMS-3/4 消费 A5，最终验证真实公共链路。
```

依赖只表示公共契约和行为证据，不要求一个不稳定的完整系统提前进入 `SystemAssembler`。A3 的 cache 不依赖 A4；A4 的公共数据模型不依赖 B 的 wire；A5 不要求 Session 或交互存在，但必须冻结已提供 Topic 时的资料读取规则。A6 按已就绪能力迁移消费者，整体完成需要 A1–A5 的相应出口。B 的无 Alice 组合只依赖真实资源 API，不以 Alice/MTP 的全部重排为前置；版本收口才合并验证两组结果。

近期执行顺序是：先对 A1/A2 的既有成果做差额核对，再冻结 A4-0 的输入/排序/路由和 A5-0 的 Pending 权限/资料接口；A3 可在资源快照签名稳定后实施。不要先按旧 `InteractionPayload` 继续切换全部 finalize，再返工为 Segment。

## 4. 跨计划兼容和迁移规则

1. W0 的 `WorkspaceIdentity`、`IdentityScope`、WorkspaceAsset READY/lease、MTP/SSE 名称和既有错误分类继续作为兼容基线；任何变化都进入明确迁移矩阵。
2. `ActorIdentity.session_id` 只作为兼容读取字段保留。目标模型把会话标识放入 `SessionRef`/`InteractionContext`，不得将其重新当作 Workspace、Topic 或授权身份。
3. `InteractionPayload` 当前混合会话内容、Alice 结构化事件、主动物化任务、worth_saving 和附件使用信息。A4 把 `ConversationSegment` 定为共同领域输入；`InteractionPayload` 仅作兼容投影，`InteractionSubmission` 继续是队列内部 envelope，`materialize_tasks` 从普通交互提交中移出。
4. 旧 `PatchouliService.prepare_agent_run/finalize_agent_run/cleanup_prepared_agent_run` 可以在迁移期委托新 API，但不能与新 API 并行拥有领域成功路径。A6 逐项关闭旧职责。
5. 旧 Alice cache、Pending runtime 和 resolver 入口可以有期限的 adapter/re-export，但不得保留第二份可独立命中的 cache、第二个 Pending 状态机或绕过 admission 的公共成功路径。
6. 已接纳的领域工作不能因 adapter 断连、通知丢失或 Alice 停止而被改判失败；回滚不得删除已接纳 Pending、Session、Segment 或 canonical 结果。

## 5. A 系列共同验收出口

A 系列完成需要同时具备以下证据：

- 无 Alice 的真实 GlobalSystemBus → Patchouli application → canonical 资源链能够完成 Profile/Memory/Attachment 读取、交互提交和主动意图提交；
- 两个 Workspace 的身份、资源 policy、缓存 key、Topic/Session 关联、Pending 读取和任务结果不串扰；
- System、Alice、Passive 和参考外部 adapter 对同一操作进入同一业务路由，领域结果和错误阶段可解释；
- 普通交互提交和主动意图提交各自独立，空 Topic 仍可接纳有效 WRITE/UPDATE，物化前可读回意图，结算后可解析真实 canonical 结果；
- Session 历史能够承载外部确定性会话，Topic 仍只承担记忆侧工作集；外部摘要/检查点带 provenance，不覆盖 canonical Topic summary；
- 合法 mutation 能使派生 cache 失效，Alice 停止不清理 Workspace cache，shutdown 按“停收 → drain → detach → close”完成；
- 没有新的 Workspace 业务 port/provider 层，Patchouli application 仍是业务 API 唯一实现；
- 文档、契约和 ADR 只有在实现、测试、审查收尾后才晋升为当前事实，完成的子计划分别归档。

## 6. 风险与版本收口

主要风险是把拆分误解为增加转发层、把 Session 历史误作 Topic 工作集、把 Pending 再次绑定 Alice、或以 fake route 验证替代真实业务链。每个子计划必须以行为和状态所有权验收，不能以目录数量、类名或转发次数验收。

计划 A 不包含外部厂商 connector、强沙箱、完整历史导入、Deep Research 编排或跨重启的通用任务恢复。它为这些工作提供资源、来源、Session/Topic 和主动意图边界；具体实现按 [ROADMAP](../ROADMAP.md) 后续计划推进。v0.7.0 发布前，A 系列与计划 B 分别完成自己的出口；任一子计划完成都不代表整个版本完成。

实现收口时，更新 `docs/plans/README.md`、`ROADMAP.md`、相关当前事实文档和 ADR-0004 的 supersede 关系。原协调计划及各子计划在对应切片完成后分别归档，不把仍在调整的设计提前写入架构事实文档。
