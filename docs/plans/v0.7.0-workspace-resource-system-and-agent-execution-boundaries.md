# v0.7.0 计划 A：Workspace 资源体系与 Agent 执行边界重构

本文是 v0.7.0 的基础重构计划。它建立在 v0.6.2 W0 Workspace MVP、Identity 投影收敛、V1 Memory 迁移和 W1 Chat Attachments 已完成的结果之上，目标是把代码结构重新对齐到 [VISION.md](../VISION.md) 与 `ae2-hivememory-architecture-analogy.md` 的基本模型：持久化资源是跨执行周期的主状态，Workspace 是独立存在的资源体系，Actor/Agent 进入该体系读取资源、执行任务并提交结果。

本计划原目标为 v0.6.2，随后独立排入 v0.7.0。现拆为两份同版本计划：本文（计划 A）负责资源体系与内部执行边界；[计划 B：外部记忆服务与 Actor 交互契约](./v0.7.0-external-memory-service-and-actor-interaction.md)负责外部接口、Passive Ingress 升级及参考客户端闭环。W0/W1 与旧缓存迁移保留原版本归属。具体 harness connector、执行基座、完整历史导入、文档摄入和 Research 继续按 [ROADMAP](../ROADMAP.md) 推进。

这不是一次把两个字典从 `AliceRuntime` 移到另一个类的局部搬家，也不是为每个 Workspace 创建一个 Runtime。计划建立一个进程级 `WorkspaceRuntime` 作为资源平面的聚合入口；它内部按 Workspace、身份和资源类型进行隔离，但不保存可变的 `current_workspace`，也不复制 Agent 执行状态。

计划状态为 `active`（实施已随 WRX-0 启动）。实现完成前，本文是设计与实施入口；当前架构、契约和 ADR 继续描述已落地事实。实现、测试、迁移和审查全部完成后，按文档治理规则更新事实文档并将本文归档。

### 本次边界修订（2026-09-16）

本计划不再把 `WorkspaceResourcePort`、`DomainMutationPort` 或
`DomainResultPort` 作为 Actor 的第二套业务 API。Patchouli 已经拥有负责
用例编排的 application 层，并通过 `GlobalSystemBus` 暴露跨子系统公开路由；
Workspace 不新增一层 provider，也不让自己的 service 直接取得 Patchouli
store、familiar、controller 或 local route。统一目标是：所有入口先经过
`WorkspaceAccessBoundary`，再调用对应的 application service/公开路由，由
Patchouli application 继续处理资源 ownership、visibility 和领域 policy。

WorkspaceRuntime 的资源服务只承担访问上下文、派生 cache、失效和快照投影等
基础设施职责。组合根的完整接入不作为 WRX-1 或本次边界修订的前置条件；在
系统装配稳定前，WorkspaceRuntime 可以独立构造并通过现有 application/route
边界验证。

## 1. 背景和问题

### 1.1 理念基线

AE2 类比中，Workspace（主网）提供稳定资源、能力和策略；Agent（CPU）是临时执行器。Agent 可以进入一个 Workspace，读取 Memory/Profile/Topic/Attachment 等资源，执行一轮或一组动作，再把结果提交回资源平面。资源的存在不应依赖某一个 Agent 是否正在运行，也不应随着某个执行器的替换而丢失。

Patchouli 是资源存储和领域算法的权威持有者，Alice 负责 run 编排和执行工作集，MTP 是把模型产生的动作接入两侧的协议适配层。`WorkspaceRuntime` 是组合和资源访问边界，不取代 Patchouli 的事实存储，也不变成第二个 Agent 框架。

这也落实了 VISION.md 的双轨策略：Patchouli 应能通过 passive ingress、API、MCP、skill 或其他适配器独立服务外部 harness；Alice 是验证 memory-native runtime 的参考 Actor，而不是 Patchouli 的唯一使用者。计划的架构成功不以 Alice 追平 Codex、Claude Code 等通用 harness 为条件，而以资源系统能否被不同 Actor 稳定使用、以及 Alice 是否能在可比较实验中证明额外的 memory-native 优势为判断依据。

### 1.2 当前结构的矛盾

当前 W0/W1 已经把 Memory、Topic 和 WorkspaceAsset 语义上放入 Workspace，但资源读取仍由 Alice 侧的派生缓存和 resolver 组织：

- `AliceRuntime` 构造并清理 `AgentProfileCache`、`KoakumaAtomCache` 和 `PendingAtomRuntime`；
- `AgentProfileResolver`、`RuntimeAliasResolver` 同时承担授权坐标解释、缓存命中、Patchouli 冷查找和 MTP 错误翻译；
- Alice settlement 成功后才触发缓存失效和重新填充，来自管理服务、生命周期或其他入口的 canonical 变化可能没有同等的失效路径；
- `AgentRuntime.finalize_run` 还直接负责 PendingAtom 的 materialization 和按 run 驱逐；
- MTP runtime 同时持有资源查找、执行动作、工具目录和环境绑定，导致“Agent 能调用什么”与“Workspace 提供什么”混在同一文件和生命周期中；
- 根 Profile 与 CALL Profile 走不同解析入口，容易出现缓存坐标、授权重验和错误语义不一致。

这些问题不是通过继续增加 `agent_runtime` 子目录就能解决的。需要先区分五个维度：资源的权威所有权、资源访问的服务边界、缓存的派生实现、执行工作集的生命周期，以及全局 ID/索引/授权的不同职责。

### 1.3 旧计划和 ADR 的位置

旧的 `v0.6.2-workspace-runtime-cache-migration` 已完成并归档。ADR-0004 记录了当前“派生缓存由 AliceRuntime 持有、WorkspaceRuntime 解体、PendingAtomRuntime 保持 Alice 所有”的事实决定。本计划不回写历史，也不把旧计划的实现结果当作目标架构；它提出一个新的、可验证的边界重构，并在收口阶段明确 ADR-0004 的 supersede/update 方式。

### 1.4 与 VISION.md 的对应关系

本计划不是把项目重新定位为通用 Agent harness。它落实的是 VISION.md 中的双轨策略和可比较实验原则：

| VISION.md 命题 | 本计划的结构含义 |
|:---|:---|
| Patchouli 具有独立的 Memory Infrastructure 价值 | 统一 application API 与 Workspace 访问/缓存基础设施可在没有 Alice 时提供 Memory/Profile/Asset 能力，并可被 Passive Ingress 或其他 adapter 使用 |
| Alice 是 memory-native reference runtime | Alice 继续保留执行 loop、工作集、模型调用和提交协调，但不再拥有资源 canonical truth 或正式资源 cache |
| 模型和 harness 可以替换，长期资产继续存在 | application API、scope、snapshot、submission、status、error 和 provenance 契约与具体 Actor、模型和 transport 无关 |
| 需要比较外部 harness + Patchouli 与 Alice + Patchouli | 计划验收同时覆盖无 Alice 的资源链和 Alice 的原生执行链；不把 Alice 的存在本身当成系统正确性的证明 |
| Passive ingress 是开放生态的现实入口 | A 提供独立资源能力；B 负责 Passive、主动交互与未来导入的接入契约，Passive 本身保留被动对话服务定位 |

因此，“Workspace 资源平面”是本计划的长期结构目标，“Alice 参考 Actor 的额外优势”是后续需要通过实验验证的假设。二者不能互相替代。

### 1.5 两份计划的分工

资源可供其他消费者使用是 A 的出口；将其交付为外部客户端可使用的交互协议是 B 的出口。本表是拆分责任和最小交接面的规划入口，B 通过链接引用，不再复制内部资源模型。

| 工作 | 计划 A | 计划 B |
|:---|:---|:---|
| Workspace 归属、Patchouli 领域权威、缓存、资源生命周期 | 设计与实现责任 | 消费并验证，不另建资源状态 |
| 可信调用上下文中的 IdentityScope、资源引用与领域结果 | 提供 WorkspaceAccessBoundary 和稳定 DTO；不复制 application API | 从外部身份映射，定义请求/响应序列化 |
| Memory/Profile/Asset 读取与既有领域写入能力 | 通过既有 application service/GlobalSystemBus 使用；只补齐缺失的 Actor-visible 用例 | 定义主动操作的外部权限、提交及结果协议 |
| Alice、MTP 与 PendingAtom | 资源依赖注入、单一工作集、run 收尾重排 | 不复刻 Alice 工作集；映射相关领域语义 |
| Passive Ingress | 资源依赖变动所需的最小内部适配；保持现有行为 | 实时会话、结果观察、兼容与协议升级 |
| 历史导入 | 不实现 | 参与协议场景验证；完整批次与格式产品留给 v0.7.2 |
| 外部认证映射、connector、统一交互体验 | 不实现 | B 冻结适用范围；厂商 connector 留给 v0.7.1 |

A 的独立验收使用真实公开 application 链路和 Workspace 基础设施，不以 B 的 transport、身份协议、结果查询服务或客户端完成为条件。B 的协议设计可并行，最终集成依赖 A 的对应能力就绪；共同发布 v0.7.0 时分别核对两份计划的出口。

## 2. 目标、非目标和完成定义

### 2.1 目标

1. 建立进程级 `WorkspaceRuntime`，作为 Workspace 资源访问、缓存、授权重验、失效和生命周期的统一聚合入口。
2. 将 Profile cache 和 Atom cache 作为 Workspace 资源服务的派生实现，使其不依赖 Alice 是否运行，且按完整资源访问坐标隔离。
3. 让根 Profile、CALL Profile、MTP SEARCH/READ、管理和外部读取复用统一访问边界及对应 application API，并共享 Workspace 派生缓存。
4. 让 Alice 只保留 run 编排、frame/loop、模型调用、执行信号、工作历史、临时结果和提交动作。
5. 保留 Patchouli 对 Memory、Profile、Topic、Artifact 的权威存储、可见性策略和领域变更算法；WorkspaceRuntime 不建立第二套 canonical 记录。
6. 让 MTP 变成跨边界适配层：资源读取、领域提交和结果查询都先经过 WorkspaceAccessBoundary，再调用既有 application service/GlobalSystemBus；工具环境由独立 provider 提供。
7. 明确 PendingAtom 的暂留边界，避免把复杂的执行状态机盲目迁移到 Workspace，也避免让单帧 AgentRuntime 独占 run 级结算。
8. 在不改变 v0.6.2 已冻结的外部成功/失败、scope、MTP/SSE 和 WorkspaceAsset 语义的前提下，逐阶段完成内部结构切换。
9. 提供不携带 Alice frame、PendingAtom 或 MTP 类型的 Workspace 访问上下文和 DTO，供既有 application API 与计划 B 使用；不在 A 新增第二套领域业务端口，也不冻结通用外部 Actor 协议。
10. 在所有 Actor→Workspace 入口建立统一的 admission/operation authorization 边界，并让资源 ownership、MemoryAccessPolicy 与领域规则在其后分层执行；不得把授权结论藏在资源 cache 或请求字段中。

### 2.2 非目标

- 不为每个 Workspace 创建一个 Runtime 实例，不引入可变的 `current_workspace`。
- 不重写 Memory、Topic、Artifact 的持久化模型，不新增 Workspace 的第二个事实存储。
- 不在本计划中实现 Workspace 创建、跨 Workspace 通信、子网/Mount/DAG、持久化 Agent workflow 或分布式调度。
- 不把所有内部对象都改成带 Workspace 前缀的 ID；全局唯一性、资源归属、索引和授权分别处理。
- 不将 `PendingAtomRuntime` 整体迁移为 Workspace 资产，不复制其状态机，也不在本计划内重写 UUID/alias 生成和耐久化。
- 不把 MTP RUN 的强沙箱、资源配额和不可信代码执行作为本次边界重构的隐含前提。
- 不因为“当前只有 Alice 使用”就把资源服务重新归还 Alice；消费者数量不是资源所有权判据。
- 不在 A 实现外部 Actor 协议、身份认证映射、operation 查询服务或 Passive 新交互模式；这些由计划 B 负责。具体厂商连接器、批次导入产品和强沙箱不属于两份计划的当前交付。

与后续工作的交接范围：A 的 WRX-1/2 向 B 提供统一访问边界、application 契约和资源基础设施；B 实施外部交互。A 的 WRX-6 只拆分 MTP 与工具 provider 的依赖，执行故障诊断、进程可靠性和沙箱基线留给 v0.7.1；具体外部 harness 接入也在 v0.7.1 独立验证。

### 2.3 完成定义

计划完成时必须同时满足：

- 停止或替换 Alice 后，仍可通过经统一授权的 application API 读取 Memory、Profile 和附件表示；
- 同一进程中两个 Workspace 的资源读取、缓存命中、失效和附件 resolve 不串扰；
- 一个 Agent 可在两个 Workspace scope 下并发运行，run/frame/history/pending 不互相泄漏；
- 所有正式 Profile/Memory 读取都经过统一的 scope 和可见性检查；缓存本身不能作为授权证明；
- 所有资源、领域提交和任务结果入口都经过统一的 Workspace admission 与 operation authorization；准入成功后仍执行资源 ownership/visibility 和领域 policy；
- canonical Memory 通过任意受支持的管理、生成、生命周期入口改变后，旧资源缓存不会继续作为成功结果返回；
- Alice 不再直接拥有 Workspace 资源缓存，也不再通过单帧 finalize 直接决定所有 run 级 materialization；
- 删除 WorkspaceRuntime 的全部派生 cache 后，既有 application API、canonical 资源授权和领域结果语义仍保持不变；
- Workspace 的缓存/失效基础设施可以在没有 Alice 的情况下运行；业务提交和结果查询仍通过 Patchouli application/GlobalSystemBus 完成；
- MTP 的资源动作、执行动作和工具动作可分别替换测试适配器，而无需把 Workspace service 变成第二套业务 API；
- 现有外部路由、MTP 结果、SSE 事件、错误分类和 shutdown drain 行为保持兼容，除非在契约变更清单中明确记录。

## 3. 目标模型和边界

### 3.1 资源体系与执行体系

```text
HTTP 管理入口 / Alice / Passive / 外部 Actor
                    |
          CallerPrincipal 建立
                    |
          WorkspaceAccessBoundary
       admission + operation authorization
                    |
       已有 System application service（按需）
                    |
        GlobalSystemBus 公开用例路由
                    |
          PatchouliBridge → application layer
       ownership / visibility / domain policy
                    |
          Patchouli local bus / runtime
                    |
             canonical 资源

WorkspaceRuntime：只提供 access context、派生 cache、失效和快照等基础设施，
不再作为第二套 Memory/Profile/Domain application API。
```

Workspace 是资源归属与访问边界，Patchouli 是其中记忆领域的权威实现；二者不各自保存一份 canonical 状态。不同入口共享同一个 admission、operation 和 application/GlobalSystemBus 业务链路；它们只在 principal 来源、Actor 形态和 operation 上不同。System 在后续装配阶段持有进程级 WorkspaceRuntime，主要承载缓存、失效和访问上下文基础设施；MTP 是 Alice 的协议适配路径之一，外部消费者无需经由 MTP 才能访问资源。

A 只定义已有可信 `CallerPrincipal` 经 Workspace admission 后形成的内部交接能力。外部 Actor 如何建立 principal、使用协议、获得 operation receipt，由计划 B 定义；A 不把外部认证材料写入资源模型。

### 3.2 责任矩阵

| 能力 | 权威持有者 | WorkspaceRuntime 暴露 | Alice 持有 | 禁止的耦合 |
|:---|:---|:---|:---|:---|
| Memory/Profile canonical 数据 | Patchouli / MemoryLibrary | application 内部使用的版本快照、资源缓存与失效设施 | 无 | Alice 不能直接访问 Patchouli store 或私有 cache |
| Topic、短期快照 | Patchouli Perception | 无独立读取用例；正式资源视图由 Patchouli application 提供 | 本轮上下文中的临时引用 | WorkspaceRuntime 不复制 Topic 状态机 |
| WorkspaceAsset / Representation | System WorkspaceAssetStore | resolve、READY 检查、lease、编译输入 | 仅持有本轮使用结果 | Alice 不管理全局 asset 生命周期 |
| Profile/Atom cache | WorkspaceRuntime 内部派生实现 | scope-aware read/invalidate/close | 无所有权 | cache 不能绕过授权或成为第二事实源 |
| PendingAtom | 当前 Actor execution workset（Alice 暂实现） | 不持有 | 创建、frame/run 关联、执行侧可见性 | Workspace 不复制 Pending 状态机 |
| Memory materialization | Patchouli 领域服务；run settlement consumer 协调 | canonical change 后的派生缓存失效协调 | 提交意图和 run 结果 | AgentRuntime 不直接编排所有跨域副作用 |
| 模型调用、frame、loop | Alice / AgentRuntime | 不参与 | 权威执行状态 | Workspace 不保存模型会话状态 |
| MTP 语法、结果、SSE | MTP adapter | 提供访问边界；资源用例走公开 application | 注入执行 capability | MTP runtime 不同时拥有两侧状态 |
| 工具目录和环境 | 独立 tool provider | 绑定资源/环境配置 | 请求执行 | 不用 prompt 或隐式全局路径表示权限 |

### 3.3 WorkspaceRuntime 的性质与资源范围

`WorkspaceRuntime` 是进程级资源基础设施聚合器，不是新的 canonical store、按 Workspace 复制的子系统，也不是一个请求时 service locator。它只组合访问上下文、派生 cache、失效协调和生命周期；Memory/Profile/Topic/Artifact 的事实仍由 Patchouli，WorkspaceAsset 的 working set 仍由 System-owned AssetStore 持有。业务资源读取、提交和结果查询继续使用既有 application service 与 GlobalSystemBus；WorkspaceRuntime 不新增平行的领域用例层，也不要求在本阶段改造尚未稳定的 System 组合根。

| 资源或状态 | canonical/事实所有者 | WorkspaceRuntime 的责任 | 本计划是否迁移所有权 |
|:---|:---|:---|:---:|
| Memory/Atom | Patchouli MemoryLibrary | 为 application 提供 atom cache、快照与失效基础设施 | 否 |
| Agent Profile | Patchouli Profile/Memory domain | profile cache、快照存储；读取解析与授权仍由 Patchouli 执行 | 否 |
| Topic 与短期 working set | Patchouli Perception | 不复制 Topic 状态；通过 Patchouli application 使用正式投影 | 否 |
| Artifact 与 provenance | Patchouli Artifact domain | 不复制 Artifact 状态；引用读取由 Patchouli application 承接 | 否 |
| WorkspaceAsset/Representation/lease | System WorkspaceAssetStore | resolve/acquire/release facade | 否 |
| PendingAtom 与 run-local alias | Alice execution workset | 不持有、不复制、不提供 Workspace key | 否 |
| Profile/Atom 派生 cache | WorkspaceRuntime | key、命中、epoch、失效、close | 是，迁移运行时实现归属 |

因此，本计划的资源运行时所有权迁移针对两个派生 cache，不把 Patchouli 的 Memory/Profile 事实或 System 的 AssetStore 搬入 WorkspaceRuntime；整体重构还包括统一访问边界、application 契约和执行侧职责调整。删除 WorkspaceRuntime 的全部 cache 后，canonical 资源、授权流程和资源生命周期仍必须保持不变。

### 3.4 生命周期和实例规则

- `WorkspaceRuntime` 的实例由后续稳定的组合入口持有；本计划先冻结其依赖和生命周期，不把修改 `SystemAssembler` 作为 WRX-1 或 application 边界重构的前置条件。测试可以独立构造它，并通过现有 application/route 边界验证；不要求 Patchouli 暴露新的 provider 层。
- `WorkspaceIdentity` 和 `IdentityScope` 是调用时数据，不改变 Runtime 的实例身份；公开 application 方法显式接收 access，内部缓存方法接收已验证的 scope/key。
- AliceRuntime 可创建多个 run，但不能创建或清空 WorkspaceRuntime；停止 Alice 不应清除资源缓存。
- 系统关闭时先停止接纳新的 Actor 请求，再等待需要读取 Workspace 资源的 in-flight 操作和 settlement consumer 完成，最后关闭 WorkspaceRuntime、AssetStore 和 Patchouli runtime。不得以“先卸载 Alice bridge”代替 drain。
- cache 的清理是资源运行时生命周期操作，与某个 Agent run 的完成、取消或重启分开；缓存是否跨进程持久化仍由后续计划决定，本计划不承诺重启恢复。

实际落地时可以按现有包名分阶段迁移；上图表达的是依赖方向，不要求一次性创建所有空目录。若保留 `system/runtime/workspace/` 作为组合入口，必须让它只组合 `workspace` 访问/缓存基础设施，不把业务实现继续塞入 System bundle。

### 4.2 允许的依赖方向

1. `workspace` 只负责 `WorkspaceAccessBoundary`、access context、派生 cache、失效和快照等基础设施；不能导入 AliceRuntime、AgentRuntime、MTP handler 或 Patchouli 内部 store/familiar/controller/local route。
2. `alice`、`agent_runtime`、Passive 和外部 adapter 在取得 access context 后，调用既有 System/Patchouli application service 或其 `GlobalSystemBus` 公开路由；不能依赖 Workspace cache 的具体类、复制资源授权逻辑或创建第二套业务 service。
3. `patchouli.application` 是跨子系统业务用例边界，由 PatchouliBridge 挂载到 global route，向内通过 local bus 调用 Patchouli runtime；不得反向调用 Workspace 业务服务形成递归。
4. `mtp` 负责协议适配、错误和输出格式；资源访问先经过 Workspace admission，再按操作调用既有 application route，执行权限仍由 Alice/Policy 完成。
5. System application service 是顶层 API 的薄封装，管理员与 Agent 共享同一 access boundary 和 application/GlobalSystemBus 交互方式；差异由 principal、operation 和 Patchouli domain policy 表达，不通过重复的 Workspace domain service 表达。
6. System composition 负责最终的实例装配和 shutdown 顺序，不作为请求时 service locator，也不保存当前 Workspace；组合根尚未稳定时，WorkspaceRuntime 和访问边界可独立构造、测试和回滚。
7. 计划 B 的外部适配服务先建立 principal 并请求 admission，再调用同一 application/GlobalSystemBus 业务链路；不反向依赖 Workspace 内部 cache 或外部 wire model。

### 4.3 当前实现到目标边界的迁移映射

| 当前对象/职责 | 当前持有者或入口 | 目标位置 | 过渡约束 |
|:---|:---|:---|:---|
| `AgentProfileCache` | AliceRuntime / ProfileResolver | Workspace profile service/cache | 由统一 application 读取路径接入，收口后删除 Alice 的 cache 实例和清理责任 |
| `KoakumaAtomCache` | AgentRuntime alias resolver | Workspace atom service/cache | L0 Pending 仍由 Alice resolver 处理；正式 Memory alias 不再从执行侧 cache 直接命中 |
| `AgentProfileResolver` | Alice runtime | admission 后调用 Patchouli profile application route；Workspace cache 作为透明基础设施 | 保留调用方兼容方法，但不得继续持有授权 cache 或复制 profile 解析逻辑 |
| `RuntimeAliasResolver` | AgentRuntime MTP path | Pending/redirect adapter + Patchouli actor-visible memory application route | 同一 alias 的 L0 与正式资源 lookup 必须在边界上分开 |
| `PendingAtomRuntime` | AliceRuntime | Alice execution workset | 不迁移、不复制状态机；只交接 snapshot/task/result projection |
| `AgentRuntime.finalize_run` 中的 materialization 协调 | AgentRuntime | Alice settlement coordinator + Patchouli application/domain service | coordinator 不拥有 canonical Memory，不直接操作 Workspace cache |
| Profile/Memory mutation 后的 cache refresh | Alice settlement 或局部入口 | 统一 Workspace invalidation port | 所有受支持 mutation ingress 必须调用同一正确性路径 |

迁移完成的判断以依赖和行为为准，而不是目录是否已经移动：旧入口可以短期存在，但不能再拥有第二个 cache、第二套正式 alias lookup 或独立的 invalidation 真相。

## 5. 统一 application 访问与数据契约

### 5.1 Frozen scope

所有正式资源、领域提交和结果查询的 application 入口接收由 `WorkspaceAccessBoundary` 签发的 `WorkspaceAccessContext`，其中包含已验证的身份坐标、目标 Workspace 和本次 operation grant。System service、AliceBridge 和 GlobalSystemBus 转发时必须保留该 context；不得在调用 Patchouli public route 前只提取裸 `IdentityScope`，使接收方失去验证授权的依据。

Patchouli application 使用统一的 context 校验函数确认 grant 与当前用例匹配，再向内部 local bus/store 传递必要的已验证 scope。接收方消费 grant 不等于重复请求 admission，也不要求每一层重新签发。请求 DTO 若仍含 scope，必须与 access context 一致；不得由 DTO 覆盖可信坐标。run/frame/action 等执行坐标仍属于 RuntimeScope 或关联信息，不是正式资源访问的强制参数。

返回值使用不可变快照或明确的 copy-on-read DTO，不泄漏共享的可变 canonical/cache 引用。沿用既有公开路由承载这些契约；不为同一业务方法另建 `WorkspaceResourcePort` 实现。

### 5.2 Profile 读取

- Root Profile 和 CALL Profile 都经过 admission 后调用 Patchouli profile application API；区别只体现在当前访问主体、目标 profile ref 和调用方 provenance。builtin 判断、alias 查找、类型校验和 profile 解析只维护在 Patchouli，Workspace 不复制一份。
- profile cache 的逻辑 key 至少包含 WorkspaceIdentity、用户/Agent/team/alias 等现有授权坐标，并保留 source atom UUID、source revision/content identity 和 policy projection。不能把裸 `AgentProfile` 当作永久授权证明。
- application API 每次正式读取必须返回“当前授权下的 source snapshot”或明确的不可用错误。缓存命中只有在 source revision/freshness 和 scope 仍有效时才可返回。既有 API 只返回裸 Profile 时，需补齐 source atom UUID/revision 的结果投影；不能由 Workspace 再查一次内部 store 来拼接来源。
- 现有 default/omni_doll 等内建 Profile 仍走同一 application 入口，以显式 built-in source 标识返回；不把常量 alias 当作跨 Workspace 的授权旁路。

### 5.3 Memory/Atom 读取

- alias 索引按 `(WorkspaceIdentity, normalized_alias)` 分区；UUID 索引可以在实现内部保持全局，但只有在 Patchouli 验证 source ownership 和 scope 可读后才可返回。
- 对外不暴露 L0/L1/L2 层级和 cache dictionary。Alice resolver 处理 Pending/redirect，解析为正式资源引用后调用 Patchouli actor-visible application API；Workspace 提供其内部使用的缓存基础设施，不访问 Pending 工作集，也不负责冷查询路由。
- alias 替换、跨 alias 引用、删除和失效必须在同一 service 内维护反向引用关系；不能只删除一个 map 项而留下可返回的旧快照。
- cache miss、存储/检索故障、scope mismatch 和 source not found 必须映射为稳定的资源错误。禁止在授权失败时回退到另一个 Workspace 或旧缓存。

### 5.4 WorkspaceAsset 读取

Attachment 和其他 WorkspaceAsset 仍由 System-owned AssetStore 持有。WorkspaceRuntime 只提供 scope-aware resolve/acquire/lease facade，复用 READY-only、representation revision/hash、删除和 lease 语义。AttachmentCompiler 仍属于上下文编排链路；它接收资源 service 返回的 lease/snapshot，不直接读取 store 私有字典。

### 5.5 Authorization、ownership、index 的分离

资源归属由 WorkspaceIdentity 和 canonical owner 字段定义；全局 ID 只保证寻址唯一；alias/UUID index 只负责加速；Patchouli 的 `memory_is_readable` 等 policy 决定当前 caller 是否可读。任何一项都不能单独替代另外三项。管理读取语义由显式 management operation 授权的 application 用例实现，Actor 不能通过请求参数选择 `enforce_actor_visibility=False`。

### 5.6 Workspace 访问边界：统一准入与分层授权

Workspace 与 Actor 解耦后，资源服务不能再把“请求里带来的 `agent_id`”当成完整的授权依据。所有 Actor 到 Workspace 的交互都必须先经过一个统一的访问边界，再进入具体 application 用例。这个边界是最小、可执行的安全网关，不是新的通用 IAM 平台，也不取代资源所有者的领域规则。

#### 5.6.1 身份和授权上下文

以下四个概念必须分开，不能由一个 `IdentityScope` 或一个请求 DTO 兼任：

| 概念 | 回答的问题 | 是否由调用方自行声明 |
|:---|:---|:---:|
| `CallerPrincipal` | 哪个已经被接入层信任的进程、connector、安装实例或本地调用方正在发起请求？ | 否。由受信入口建立；请求体中的字符串只是声明 |
| `ActorIdentity` | 该调用方代表哪个用户以及可选的具体 Agent？ | 用户和 Agent 代表关系由准入确认；管理操作不要求具体 Agent |
| `WorkspaceIdentity` | 目标资源归属域是哪一个？ | 只能请求目标，必须由准入策略确认 |
| `IdentityScope` | 当前 W0 兼容模型中的 Actor + Workspace 冻结坐标是什么？ | 由已验证的 principal/actor/workspace 组合构造 |

在 `IdentityScope` 之外增加不持有缓存授权的 `WorkspaceAccessContext`（名称可按实现调整），至少包含 `CallerPrincipal`、已验证的 `IdentityScope`、请求的 operation 以及本次准入得到的 capability/grant。grant 是一次请求或有限生命周期的授权结果，不能写入 Profile/Atom cache，也不能因为 cache 命中而跳过重新校验。`IdentityScope` 继续只表达坐标；不得把 principal、run/frame、policy cache 或“当前 Workspace”塞回该值对象。

#### 5.6.2 四层检查顺序

```text
受信入口建立 CallerPrincipal
  -> Workspace admission：principal 是否能代表该用户/Agent、进入该 Workspace
  -> Operation authorization：该访问主体在此 Workspace 能执行哪些操作
  -> Resource ownership / visibility：目标资源属于哪个 Workspace、当前是否可见
  -> Domain policy：本领域是否允许本次读取、提交、修订或观察
```

任何一层失败都拒绝该请求。准入通过不等于资源可读，资源可读也不等于拥有写入、删除或管理权限。顶层管理员、Alice、Passive 和未来外部 adapter 均经过同一四阶段流程。前两阶段由 WorkspaceAccessBoundary 完成，后两阶段由资源所有者的 application/领域实现完成；四次逻辑检查不要求四层转发 service。管理用例可以有不同的 operation 与资源 policy，但仍验证用户及 Workspace 归属。

首版 operation 采用窄能力而不是任意 action envelope：

| capability | 语义 | 不能推导出的权限 |
|:---|:---|:---|
| `resource.read` / `resource.search` | 读取或搜索当前 Workspace 内仍需通过资源 policy 的资源 | 不授予写入、删除或管理 |
| `profile.read` | 读取 Profile projection | 不代表可以实例化、冒充或修改该 Actor |
| `asset.acquire` | 获取已授权的 READY asset representation/lease | 不授予上传、删除或改变 asset revision |
| `interaction.submit` | 提交已发生的交互给领域入口 | 不保证生成 Memory |
| `memory_intent.submit` | 提交中立的记忆意图，由 Patchouli 决定生成、合并、修订或丢弃 | 不等于管理 CRUD 或直接 upsert |
| `task.observe` | 观察该 caller/Actor 有权观察的领域任务投影 | 知道 task ID 不等于可读；不授予取消或读取最终资源 |
| `management.memory` | 已获授权的用户在目标 Workspace 内使用 Memory 管理用例 | 不授予其他 Workspace、Topic/Asset/Task 管理或冒充 Agent 的权限 |

其他既有管理用例（Profile、Topic、Asset、任务取消等）需在迁移清单中绑定各自明确的 operation，不能借用 `management.memory` 或 `task.observe` 泛化放行。具体枚举在对应签名迁移时冻结，不因此新增一套管理 service。

`system` 等保留标记也不自动成为管理员身份。请求中的 `agent_id`、`team_id`、`role`、owner 或 capability 只能作为待验证的 claim；不能用来改变已建立的 principal 或 grant。

WorkspaceAccessBoundary 根据受信 principal、所代表用户/Agent、目标 Workspace 与请求 operation 签发受控 access context，随后由既有 application API 消费。边界不接收任意 action 代为分发业务；GlobalSystemBus 继续负责路由，Patchouli application 验证当前方法所需的 operation。公共入口拒绝裸 scope、“看起来像 grant”的字典、错误 operation 和不匹配的 scope。受控工厂约束可信进程内调用纪律，不是对任意进程内恶意代码的密码学隔离。

管理入口不要求用户填写具体 agent_id。兼容 W0 时，可以由受信入口构造 `ActorIdentity(user_id=u1, agent_id=SYSTEM_AGENT_ID)`，保留 user/Workspace 校验；`system` 只是缺少具体 Agent 的来源标记，权限必须来自 grant。Alice principal 也不能仅因进程受信就任意声明用户或 Agent，仍需验证受信映射及当前运行的代表关系。内部 canonical mutation 的失效通知不再次做 Actor admission。

#### 5.6.3 MemoryAccessPolicy 的泛化边界

`MemoryAccessPolicy` 的 `PRIVATE`、`TEAM`、`PUBLIC` 是 Workspace 内资源可见性的良好共同参考，但首版应将其定义为**资源读取层的 policy**：

- `PUBLIC` 表示对已进入该 Workspace 且满足 operation authorization 的 Actor 可见，不表示互联网公开或跨 Workspace 可见；
- `PRIVATE` 表示只对目标 Actor 可见；`TEAM` 表示只对满足团队关系的 Actor 可见。团队关系必须来自可信映射，不能由请求字段自封；
- 通过 owner/admission 进入 Workspace 不能绕过 `PRIVATE/TEAM` 的 Actor visibility；显式管理 operation 才能使用管理读取语义；
- 可见性只决定该资源是否可读，不能自动推导 write/update/delete/admin/task/cancel 权限；
- Profile、Asset、Task 等资源可以复用相同的 visibility 词汇，但不应为了形式统一而强行共享 Memory 的字段和状态机。没有通用 policy 的资源必须有自己的最小检查，并明确其与 admission 的关系。

Workspace owner 校验、资源 ownership、Actor visibility、operation grant 和领域 mutation policy 必须分别可测试。任何“先命中 cache 再授权”或“知道全局 UUID 就能读取”的路径都违反本计划。

#### 5.6.4 当前版本的可信映射与职责

v0.7.0 先支持明确的本地/受信配置映射，不建设完整成员目录、远程 token/IAM、跨 Workspace 委托或公网多租户。Alice 的本地调用可以使用类似 `local-process:alice-runtime` 的 principal；外部 adapter 由计划 B 将 connector 安全上下文映射为 principal，再请求代表某个 Actor 进入某个 Workspace。A 提供 admission、operation grant 和资源检查的内部平台；B 负责外部认证材料、source 到 principal 的映射、会话协议和 wire 错误，不把外部身份模型下沉为 WorkspaceRuntime。

W0 当前 `IdentityScope` 的“Actor user 必须等于 Workspace owner”约束继续作为兼容基线。它不应被解释为最终成员模型；若要支持非 owner Actor、团队成员或 delegated access，必须先扩展准入映射和资源 policy 契约，而不能在请求体中放宽该校验。该扩展不阻塞本计划先统一边界。

任务结果必须特别处理：任务记录或等价的权威投影需要保留其 Workspace scope、提交 principal/Actor 和可观察 operation 关系；`get(task_id)`、`wait(task_id)`、`cancel(task_id)` 不能继续作为无 scope 的公共用例。缺少这些归属信息时，统一网关无法凭空补出授权，WRX-1 必须先补齐投影或明确拒绝外部/跨 scope 查询。

#### 5.6.5 三种入口如何收敛到同一业务链路

以下为目标设计示例，不表示当前代码已经支持 `access=` 参数或新的交互提交路由。示例中的 principal 名称只是受信配置标识，不是客户端可以自行声明的凭证；`ws1` 表示内部测试 Workspace，不扩大 W0 公共 HTTP 入口只开放 `main_workspace` 的范围。

共同调用方式为：

```text
入口适配：管理员 HTTP / Alice MTP / Passive 或外部 adapter
  -> 受信入口建立 CallerPrincipal，确认请求代表的用户/Agent
  -> WorkspaceAccessBoundary：Workspace admission + operation authorization
  -> WorkspaceAccessContext
  -> 已有 System application service（有顶层封装或编排需要时）
  -> GlobalSystemBus 的具体公开路由
  -> Patchouli application：消费 access，校验当前用例所需 operation
  -> Patchouli 内部 resource ownership/visibility + domain policy
  -> local bus / runtime / store 或提交队列
```

Alice 可以继续通过 AliceBus → AliceBridge 代理上述全局路由。该代理只透传请求和 access，不增加领域用例层，也不能丢弃 grant。三个入口不必为保持形式一致而全部绕行 System 的 HTTP 用例封装；它们从全局公开路由起共享同一 application 实现、契约和四阶段检查。

**例一：顶层管理员读取一条 Memory**

受信的本地管理入口确认用户为 `u1`，请求读取该用户 `ws1` 中的 Memory：

```text
管理员入口：principal=local-user:u1，user_id=u1，无具体 Agent
  -> WorkspaceAccessBoundary.admit(..., operation=management.memory)
     验证 principal → u1 → ws1 及管理能力
     W0 兼容坐标由入口构造为 (u1, SYSTEM_AGENT_ID, ws1)
  -> MemoryApplicationService.get_memory(access, memory_id)
  -> GlobalSystemBus.request(PATCHOULI_MEMORY_GET, access=access, ...)
  -> Patchouli MemoryManagementService.get_memory
     验证 management.memory grant
     检查资源属于 ws1，按显式管理策略读取
  -> Patchouli local bus → MemoryLibrary
  -> copy-on-read 结果 → 管理 HTTP 响应
```

管理员仍经过四阶段检查；第三阶段采用获准的 owner-management 策略，不因 `agent_id=system` 自动豁免。跨 Workspace 读取仍拒绝。普通 `resource.read` grant 即使请求同一管理路由，也必须在 application 入口失败。

**例二：Alice Agent 执行 MTP SEARCH**

Alice 中 `agent-a` 在 `u1/ws1` 的运行上下文中搜索“项目架构”：

```text
MTP parser/filter → SEARCH(query="项目架构")
  -> 保留 Alice Profile/frame 的执行权限检查
  -> WorkspaceAccessBoundary.admit(
       principal=local-process:alice-runtime,
       actor=(u1, agent-a), workspace=ws1, operation=resource.search)
  -> AliceBus → AliceBridge（原样保留 access）
  -> GlobalSystemBus.request(PATCHOULI_MEMORY_RETRIEVE,
       access=access, request=该 scope 下的 RetrievalRequest)
  -> Patchouli MemoryManagementService.retrieve
     验证 resource.search grant 与请求 scope 一致
  -> Patchouli local bus → RetrievalFamiliar
     执行 Workspace ownership、PRIVATE/TEAM/PUBLIC 与检索规则
  -> 授权结果/快照 → MemoryCompiler → 原有 MTP 结果与 SSE
```

`access` 必须随总线请求传递，不能仅传 `access.identity_scope`。Profile/frame 的执行限制可以进一步收窄动作，不能扩大 Workspace grant。将同一搜索换成外部 harness 发起时，只替换 principal 建立和输入输出适配，仍调用同一个 `PATCHOULI_MEMORY_RETRIEVE` application 用例。

**例三：Passive 外部 Actor 提交已发生的对话**

受信 connector 代表 `(u1, external-agent)` 向 `ws1` 发送“今天完成了数据库迁移”等对话事件。事件先按既有 turn 规则累积，满足 seal/flush 条件后提交：

```text
Passive HTTP / Connector 入口建立 principal=connector:discord-bot
  -> WorkspaceAccessBoundary 校验用户、Agent、Workspace 与 interaction.submit
  -> PassiveIngressService / ingressor：事件去重、累积、seal
  -> 携带该 operation 的有效 access 与稳定 interaction_id
  -> GlobalSystemBus 的 Patchouli interaction-submit 公开路由（待补齐）
  -> Patchouli application 的交互提交用例：验证 access、scope 和载荷
  -> Patchouli 内部 InteractionSubmissionQueue 接纳
  -> Passive 取得收据后才 commit/reset accumulator
  -> queue → PerceptionFamiliar.apply_interaction → 按领域规则决定后续生成
```

公开 interaction-submit API 的具体路由名在 WRX-1 冻结。队列继续是 Patchouli 的内部协作者，Passive 不直接持有或调用它。单条事件接收、队列接纳、交互应用和 Memory 物化是不同事实；示例不改变原有 dedup、背压、重试和收据语义。延迟 flush 应保留受信调用关联，并在领域提交时获得或确认有效授权，不能把早先事件的 grant 当作无限期权限。

如果该请求还需要记忆 context，则另行取得 `resource.search` access，调用与 Alice 完全相同的 `PATCHOULI_MEMORY_RETRIEVE`。没有检索权限时不得调用检索；可选 context 如何降级继续由 Passive/计划 B 的协议约定处理。`interaction.submit` 不隐含检索权，搜索成功也不授予交互提交权。

| 对比项 | 顶层管理员 | Alice Agent | Passive / 外部 Actor |
|:---|:---|:---|:---|
| principal 来源 | 受信用户入口/本地管理映射 | Alice 受信运行上下文 | 受信 connector/harness 映射 |
| 必须确认的身份 | user + Workspace；无需具体 Agent | user + Agent + Workspace | user + 映射后的 Agent + Workspace |
| 示例 operation | `management.memory` | `resource.search` | `interaction.submit`；检索另需 `resource.search` |
| 业务承接 | Patchouli 管理读取 application | Patchouli 检索 application | Patchouli 交互提交 application；检索复用左列 |
| 返回适配 | 管理 HTTP DTO | MTP / SSE / compiled context | 接收收据、结果协议、可选 context |

收敛的是调用机制、授权流程和同一操作的实现，不是把管理读取、Agent 检索与领域提交强行合成同一方法或同一权限。WorkspaceAccessBoundary 不承接下游业务转发，System service 不复制 Patchouli 的领域规则，Workspace 不再增加一套 resource/domain service。

#### 5.6.6 Workspace service 与外部 Actor 的调用形式

本计划仍然保留 Workspace 侧的 service，但必须区分其性质：

- `WorkspaceAccessBoundary` 是准入与 operation grant 服务；
- Profile/Atom cache、invalidation、snapshot 和 Asset lease service 是 WorkspaceRuntime 的基础设施协作者；
- 这些 service 不提供 `get_memory`、`search`、`submit_interaction` 或通用 `dispatch(action)` 等业务方法，也不直接调用 Patchouli store、queue 或 local route。

业务调用从调用者侧进入既有 application API。System 的 `ApplicationService` 可以作为 HTTP/管理入口的薄封装；Alice 的 MTP handler/AliceBridge 可以作为执行侧适配；外部 Actor 则由计划 B 的 connector/Actor adapter 负责协议转换。三者都先建立受信 `CallerPrincipal`、向 `WorkspaceAccessBoundary` 请求 `WorkspaceAccessContext`，再把完整 context 传给同一个 System application 方法或 `GlobalSystemBus` 公开用例路由。Patchouli application 消费 context、校验 operation，并在内部调用 WorkspaceRuntime 的缓存/失效基础设施。

```text
外部 harness / bot
  -> connector：验证外部凭据，映射 CallerPrincipal 与 Actor
  -> Actor adapter/application service：按 wire 用例建立 access
  -> WorkspaceAccessBoundary.admit(...)
  -> System application service（若需要顶层封装）
  -> GlobalSystemBus 公开用例路由
  -> Patchouli application → domain/local bus/store
  -> adapter 将快照、收据或错误转换为外部协议
```

远程外部 Actor 看到的是版本化 HTTP/JSON、MCP 或其他公开协议，不会看到 `WorkspaceRuntime`、`WorkspaceAccessContext`、缓存 key 或内部 queue。与系统同进程的受信 adapter 可以直接调用同一 application 方法或公开总线路由，但这只是部署优化，不能因此直接访问 Workspace cache、Patchouli queue 或内部 store。若现有 System application 尚无 Actor-visible 用例，应补充窄的 Patchouli application 用例及其公开路由；不能为此重新建立 Workspace 业务 service 或 Patchouli provider 层。

Passive 的 `PassiveIngressService` 仍可作为会话、去重、buffer、seal 和收据关联的 adapter service；它提交交互时调用 Patchouli 的公开 application 用例，不能直接调用 `InteractionSubmissionQueue`。需要记忆 context 时，Passive adapter 另行取得 `resource.search` grant，并复用与 Alice 相同的检索 application 路由。

### 5.7 向计划 B 交付的最小内部接口

A 交付统一访问边界和既有 application API 的契约，不建立第二套 Workspace 业务端口或任意 action envelope。双方在 WRX-0/EMS-0 用被动会话、主动资源操作、历史材料三个场景核对以下交接面；它们与第 5.6.5 节的三类调用主体是不同维度。

| 交接项 | A 承诺 | B 承担 |
|:---|:---|:---|
| 身份上下文 | WorkspaceAccessBoundary 签发 context，application 消费并验证 operation | 受信外部 principal 与用户/Actor 的映射 |
| 资源引用与读取 | 公开路由、正式 ID/alias、快照、新鲜度和来源信息；不暴露 store/cache | wire schema、引用回传、编译视图和错误映射 |
| 领域提交 | Patchouli application 的 interaction/intent 用例可脱离 Alice 调用 | 外部提交协议、收据关联、重试/冲突呈现 |
| 结果与状态 | 带归属的真实任务/WorkRecord 投影与查询用例 | 外部 operation 查询与保留期约定，不复制领域状态机 |
| 生命周期 | 访问边界停收、资源/cache 关闭、领域 drain 契约 | connector 停收、Passive flush 与外部 operation drain |

A 不承诺统一所有领域状态或建立外部 status store，也不要求外部 Actor 构造 PendingAtomMaterializeTask。中立意图参数由 Patchouli application 承接并转换为内部任务；Alice 负责把自己的 Pending 投影适配到该参数。提交 API 必须区分接纳、应用、canonical revision 和结果可读性，不得只返回无法定位权威结果的布尔成功值。

#### 5.7.1 既有 API 的承接和缺口

| 用例 | 现有承接 | 本次契约修订 |
|:---|:---|:---|
| 管理 Memory GET/LIST/CRUD | System MemoryApplicationService → Patchouli MemoryManagementService | 同一 access boundary；显式管理 operation，不接受 Agent 读取 grant |
| Agent UUID/alias 读取 | Patchouli retrieval 及公开 alias retrieval | 复用符合语义的公开 API；补齐缺失的 Actor-visible 点读，不能直接复用关闭 visibility 的管理 GET |
| 语义检索 | `PATCHOULI_MEMORY_RETRIEVE` → MemoryManagementService.retrieve | 增加 access 消费、scope 一致性和快照语义；Alice/外部共用 |
| Profile 读取 | `PATCHOULI_GET_AGENT_PROFILE` → AgentProfileManagementService | 复用唯一解析规则，补齐 source identity/revision 投影 |
| 交互提交 | 已有 InteractionSubmissionQueue/apply_interaction，公开独立提交用例不足 | 在 Patchouli application 增加最小提交 API/公开路由，封装 queue 接纳和收据 |
| Memory intent | 已有 generation coordinator/controller，入口仍带 Pending 投影 | 在 Patchouli application 承接中立 intent，内部转换并调用生成链；不映射成管理 CRUD |
| 任务观察/等待/取消 | MemoryTaskManagementService 与已有公开任务路由 | 补齐 access、归属与各操作授权；task.observe 不授予 cancel 或最终 Memory 读取 |
| Asset 操作 | 既有 WorkspaceAssetApplicationService 与 reader/command ports | 复用 System-owned 用例与 READY/lease 约束，经过相同访问边界，不为统一而绕到 Patchouli |

`WorkspaceResourcePort`、`DomainMutationPort`、`DomainResultPort` 及其 Workspace service 实现退出业务入口设计。已有 WRX-1 中有价值的 access、快照、错误和归属字段可保留；Memory/Profile 领域逻辑回归 Patchouli application/领域层，`PatchouliDomainGateway` 的意图转换与队列调用移至 Patchouli application，不新增 provider 包装层。System 已有顶层 service 保留其 API 适配与编排职责。

`WorkspaceAdmissionPort` 可作为同一访问边界的类型声明；`ResourceInvalidationPort`、cache 协议及 Asset lease ports 仍是内部基础设施协作接口。它们不构成必须逐层调用的业务服务栈。DTO 放在现有依赖中立的共享契约或领域契约中，不能为取得 DTO 而导入另一方的 runtime 实现。

#### 5.7.2 迁移期间的兼容规则

- 优先沿用既有 GlobalRoutes；缺少用例时补充明确路由，不为每类 Actor 复制同一个方法。
- System service、AliceBridge、MTP 和外部 adapter 透传 access；Patchouli application 校验后才向 local bus 派生 scope。迁移中的旧裸 scope 入口必须限于明确的可信适配，最终不能保留无 grant 的公共成功路径。
- GlobalRoutes 的内部签名变更须记录 access、operation、输入输出投影与错误；HTTP/MTP/SSE 兼容由入口 adapter 维持，不声称所有 Python 签名都不变。
- 读取返回不可变快照或 copy-on-read；Profile 的 builtin/source UUID/revision 一次投影，Workspace 不为补字段另查 store。
- 任务句柄和错误可脱离 Alice 解析；无归属查询 fail closed。B 可重新组织 wire model，但不得下沉到 WorkspaceRuntime。
- 业务调用路径的集成测试使用真实 GlobalSystemBus、PatchouliBridge 和 application/local route 协作，不用直接注入内部 store 的测试冒充公开边界验收。WRX-1 无需启动完整 HiveMemorySystem 或提前接入未稳定的 SystemAssembler。

## 6. 缓存一致性和失效策略

### 6.1 目标语义

缓存由 WorkspaceRuntime 持有，作为统一 application 读取路径的派生加速层。它可以被清空、重建或替换而不改变 canonical Memory/Profile；它也不能把一次曾经成功的读取变成永久授权。缓存隔离首先保证数据和访问边界，跨 Workspace 的独立容量配额留作后续治理，不在本计划中虚构完整性能隔离。

### 6.2 失效来源

所有受支持的 canonical mutation ingress 都必须产生资源失效信号或调用统一 invalidation port，包括：

- Memory create/update/delete、archive/revive；
- Materialization/settlement 产生 canonical Memory 后的提交；
- Profile source atom 或其 visibility/policy 改变；
- 资源删除、WorkspaceAsset representation revision 改变；
- 测试和管理工具使用的显式 mutation service。

Alice settlement 只是其中一个 consumer，不能再是唯一失效入口。若某一 mutation 暂时不能发布事件，必须在同一提交路径同步调用 invalidation，而不是依靠最终一致的 PubSub 猜测正确性。

| 变更来源 | canonical owner | 需要失效的派生视图 | 正确性边界 |
|:---|:---|:---|:---|
| Memory create/update/delete、archive/revive | Patchouli MemoryLibrary | Atom cache、相关 profile projection、alias index | canonical revision 提交成功后同步失效 |
| Memory materialization / settlement | Patchouli generation/lifecycle | Atom cache、引用该 source 的 profile projection | 产生可读 canonical revision 后失效 |
| Profile source atom、visibility 或 policy 改变 | Patchouli Profile/Memory domain | Profile cache | source revision/policy revision 变更与 mutation 同一提交边界 |
| WorkspaceAsset representation revision 或 remove | System AssetStore | Asset read projection、lease resolve 快照 | representation 状态改变后禁止旧 revision 新命中 |
| 管理工具或测试 mutation service | 对应领域 owner | 对应资源 cache/index | 必须调用同一 invalidation port，不允许旁路字典 |

失效通知可以同时被 RuntimeEvent 观测，但事件投递失败不能改变 cache 正确性。若实现采用异步通知，mutation 提交路径仍需先完成同步 epoch 更新或等价的读侧 revalidation；“最终会收到事件”不能成为返回新结果的前提。

### 6.3 并发和新鲜度

- invalidation 增加 scope/resource 的 epoch 或等价代次；失效前启动的 in-flight fetch 回来后必须重新检查代次，旧结果不能覆盖新缓存。
- Patchouli application 返回 source revision/content identity；profile projection 和 atom snapshot 记录该身份。
- source revision 不可用时，不得宣称永久新鲜；采用同步 canonical revalidation 或明确的短暂 no-cache 路径，不能静默使用旧值。
- cache failure 不改变 canonical 操作结果；资源读取可报告暂时不可用，但不能把旧值伪装成当前值。

### 6.4 两个 cache 的正式契约

| 项目 | Profile cache | Atom cache |
|:---|:---|:---|
| 逻辑 key | Workspace + actor/user/team 投影 + profile alias/ref | Workspace + normalized memory alias/ref |
| value | `ProfileSnapshot`，含 source identity、revision 和 policy projection | `MemorySnapshot`，含 canonical identity、revision、owner 和 provenance refs |
| 授权 | 命中后仍校验 scope 与 policy freshness | 命中后仍校验 Workspace ownership 与 actor visibility |
| 负缓存 | 只可短暂保存且必须绑定 scope、revision/epoch 和错误类别 | 只可短暂保存 not-found/invisible；不得缓存授权失败为跨 scope 结论 |
| canonical 读取失败 | 返回 unavailable/degraded，不回退到旧授权值 | 同左；旧快照不能伪装成当前成功 |
| 并发 fetch | 共享同一 key 的请求可合并，但失效代次变化后旧 fetch 不得回填 | 同左 |
| close 行为 | 关闭后拒绝新读，完成中的请求按生命周期契约结束 | 同左 |

两个 cache 都只保存可重建的派生值，不保存外部调用方的永久授权。默认不承诺跨进程恢复、固定 TTL 或 Workspace 独立容量配额；这些能力若需要另立计划。实现必须提供 hit/miss、revalidation、invalidation、stale reject 和 close 拒绝的最小观测计数，不能通过日志内容推断 cache 正确性。

### 6.5 清理和容量

WorkspaceRuntime 关闭时统一关闭两个 cache。单个 run 结束不清理资源 cache；run-specific working set 由 Alice 清理。现有全局 LRU 可以先保留，只要 key 和授权语义正确；若后续需要每 Workspace 容量配额，再另立计划，不把“有统一 Runtime”误写为配额隔离。

## 7. 端到端流程调整

三种调用主体的完整示例见第 5.6.5 节；本节补充 Alice 内部迁移和附件协作。

### 7.1 Root Profile 和 Agent 启动

```text
受信入口确认用户/目标 Agent/Workspace
  -> WorkspaceAccessBoundary：profile.read
  -> GlobalSystemBus：PATCHOULI_GET_AGENT_PROFILE（携带 access）
  -> Patchouli AgentProfileManagementService：验证 grant
  -> 唯一 Profile 读取/解析逻辑（含 ownership、visibility、builtin、source revision）
  -> 返回独立 ProfileSnapshot
  -> Alice 建立 run/frame/model 配置
```

ProfileResolver 保留为入口适配器，删除缓存持有与 Profile 解析职责。Profile 读取授权不意味着可以执行或冒充该 Agent；运行和动作权限另行判断。

### 7.2 CALL Profile 和子 Agent

CALL 的 caller actor、callee profile 和 Workspace scope 分开建模。CallContextProvider 使用与 Root 相同的 profile application API，按当前主体取得 profile.read access，不能把 caller 的缓存命中当作 callee 授权。CALL/frame 执行限制仍由 Alice 负责。本计划不因目录迁移擅自改变 actor_id 重分配语义。

### 7.3 MTP SEARCH/READ

```text
MTP parser/filter + Alice 执行动作约束
  -> WorkspaceAccessBoundary：resource.search / resource.read
  -> AliceBridge → GlobalSystemBus（完整 access）
  -> Patchouli 对应 application 读取用例
  -> 授权快照 + citation metadata
  -> MemoryCompiler / formatter → 原有 MTP 结果与 SSE
```

SEARCH/READ 的领域语义由 Patchouli 负责，缓存由 WorkspaceRuntime 提供并在相同 application 路径内使用。READ 不接受内部 cache key，不通过 UUID 绕过 ownership/visibility；Pending/redirect 仍先由 Alice 解析，正式资源分支再进入该链路。

### 7.4 WRITE/UPDATE 和提交

MTP WRITE/UPDATE 的 Pending 创建和 run 内 ACK 仍是 Alice 执行工作集行为。到正式领域提交时，settlement coordinator 取得 memory_intent.submit access，经全局公开路由调用 Patchouli 意图提交 application。读取 base snapshot 与提交修订分别授权，读权限不推出写权限；意图仍由生成链决定生成、更新、合并或丢弃，不能转成管理 CRUD。成功条件、幂等 identity 和错误分类继续复用既有契约。

### 7.5 Attachment 选择和编译

Asset 由 System 持有，Actor-facing Asset 用例经过同一 WorkspaceAccessBoundary，沿用 WorkspaceAssetApplicationService/reader/command 能力，不强行经过 Patchouli Memory API。AttachmentCompiler 消费已获授权的 READY representation lease，W1 的 revision、删除、release 和 Topic/Artifact promotion 约束保持。内部 lease 协作不是新增 Actor 业务端口。

### 7.6 缓存如何接入共同业务路径

Patchouli application 在验证 access 后使用 WorkspaceRuntime 提供的派生缓存，返回前由 Patchouli 的唯一 policy 实现完成当前资源校验；cache miss 在 Patchouli 内部沿原有 local bus 读取 canonical 资源。Workspace cache 只提供快照存取、索引、epoch 和失效，不接收全局路由来执行冷读取，也不复制 Profile/Memory 领域判断。因此没有 application → Workspace service → application 的往返。

命中也必须满足当前 ownership/visibility、领域规则和 freshness。管理读结果不能作为 Agent 的授权证明；共享内容缓存时，每个访问仍重新判断，带授权含义的派生视图则须包含相应访问坐标。具体 cache helper 形状在 WRX-3 冻结，不在 WRX-1 再造 provider 或额外业务层。

## 8. Alice 和 Agent Runtime 的收缩

### 8.1 Alice 保留的内容

- run/frame/loop 生命周期、取消、超时和模型调用；
- working history、frame output、临时上下文和本轮 action 结果；
- PendingAtom 的执行侧创建、claim、cancel、settlement intent 和 run 关联；
- 将 MTP action 转换为 Patchouli submission 或资源操作的执行协调；
- 对 WorkspaceAccessBoundary、公开 application 路由和执行侧能力的依赖注入，以及 run scope 冻结。

### 8.2 Alice 移出的内容

- Profile/Atom cache 的实例、字典、LRU、填充和清理；
- 通过缓存实现的正式资源授权判断；
- 对 Patchouli 私有 store/local route 的依赖；经授权使用 GlobalRoutes 继续保留；
- 把 Alice stop 当作资源 cache 生命周期的唯一清理点。

### 8.3 AgentRuntime 的边界

`agent_runtime/runtime.py` 聚焦 frame/loop/model invocation、CALL history response、execution signals 和输出。`finalize_frame` 可以完成 frame 级 pending 收束；`finalize_run` 不再直接承担所有跨域 materialization policy，而是发出 run settlement/harvest action，由 Alice workset/settlement coordinator 和 Patchouli consumer 协作完成。

`agent_runtime/aliases/resolver.py` 只保留执行侧 Pending alias、redirect 和 run-local view。正式 Memory alias 解析经统一访问边界调用 Patchouli application API；如果同名方法为兼容性保留，必须标注 adapter，并禁止重新引入独立 cache。

## 9. PendingAtom 的处理决定

PendingAtom 目前跨越模型执行、短期工作集、materialization 和跨系统 settlement，具有比两个 cache 更高的耦合复杂度。本计划采取“边界先行、所有权暂留”的决定：

1. `PendingAtomRuntime` 暂不迁移进 WorkspaceRuntime；它仍是 Alice execution workset 的状态机。
2. WorkspaceRuntime 不接受 PendingAtom 作为正式 Workspace 资源，也不为 PendingAtom 增加 workspace 分区键来替代现有 run/frame/action scope。
3. PendingAtom 的 canonical/settlement projection 可以被 Patchouli consumer 读取，但提交和观察必须通过授权后的 Patchouli application API，不得让 Patchouli 或 Workspace 直接操作 Alice 状态机。
4. 将单帧 `AgentRuntime.finalize_run` 中的 run-level harvesting 与任务投影移至明确的 Alice workset/settlement coordinator。materialization 和 Artifact promotion 继续由 Patchouli 执行，cache invalidation 由资源服务承接；不把这些领域职责集中到新的执行协调器。
5. 原有 Pending alias、intent_id、RuntimeScope 和跨 run 可见性语义在迁移阶段保持不变，除非单独冻结新的安全/可见性契约。不能因为 Workspace 重构顺手把所有 Pending ID 改成 Workspace 命名域。
6. 只有在未来证明 PendingAtom 是 Workspace 中跨 Agent 共享、可独立恢复的资源，并完成持久化、claim、租约和恢复设计后，才另立计划评估迁移。B 的外部收据不引入另一套 Pending 状态机，也不要求外部 Actor 注册 Pending 才能提交领域意图。

### 9.1 Pending settlement 的目标状态流

计划 A 只拆分责任，不把 PendingAtom 变成 Workspace 资源。目标交接如下：

```text
Alice 创建/推进 PendingAtom
  -> Alice workset 维持 alias、claim、cancel、terminal 状态
  -> frame/run 结束后生成 PendingAtomSnapshot / MaterializeTask
  -> settlement coordinator 适配中立 intent，取得 memory_intent.submit access
  -> GlobalSystemBus → Patchouli application 的意图提交用例
  -> Patchouli 应用 materialization，产生 canonical revision 或明确 discarded/failed 结果
  -> canonical 提交路径同步调用 ResourceInvalidationPort 失效旧 cache
  -> application 结果查询用例在 task.observe 授权下返回真实结果
  -> Alice 只更新 Pending 的执行侧 terminal/redirect view
```

其中 `PendingAtom` 是唯一可变状态机；`PendingAtomSnapshot`、`PendingAtomMaterializeTask` 和 `PendingAtomSettlement` 是跨边界的不可变或只读投影。Patchouli 不持有 Pending 的可变副本，WorkspaceRuntime 不读取 Pending alias，也不根据 Pending 状态生成正式资源命中。

必须分别定义以下结果：取消或超时发生在提交前、提交已接纳但尚未应用、materialization 已产生 canonical revision、领域明确丢弃、领域失败，以及进程关闭导致无法继续处理。重复 settlement 只能按既有 operation/intent identity 得到同一领域结果或明确 conflict，不能重新创建第二个 canonical Memory。进程内队列仍不承诺跨重启恢复；若要承诺恢复，另立持久化任务计划。

settlement coordinator 的最终包路径可以在 Alice workset 或 System application layer 中选择，但它必须只协调交接，不拥有 Pending 状态机、canonical Memory 或 Workspace cache。WRX-5 的完成证据是上述状态流可独立测试，而不是某个类名被移动到指定目录。

## 10. MTP 和工具边界

当前 MTP runtime 近千行，包含 parser/filter/formatter、alias resolver、compiler、kernel registry、SEARCH/READ/RUN/WRITE/UPDATE/CALL 和环境绑定。本计划只冻结调用方向和 provider seam，不把 v0.7.1 的执行可靠性或沙箱实现提前纳入 A；不做机械文件搬移，而按调用方向拆分：

- protocol adapter：保留语法、参数校验、结果模型、错误码和 SSE 输出；
- resource adapter：取得对应 access，将 SEARCH/READ/Profile 请求转给 Patchouli public routes，Attachment 转给既有 System 资源用例；
- execution adapter：把 RUN/CALL 和 Pending 动作交给 Alice 执行侧；正式意图提交适配为授权后的 Patchouli application 请求；
- tool provider seam：维护 syscall catalog、环境配置和 `workspace_path` 绑定的注入接口，执行时显式传入 scope/config；具体进程可靠性、取消、配额和沙箱由 v0.7.1 另行实施。

`workspace_path` 的现有默认值只能作为兼容映射。第二个 Workspace 不得静默复用第一个文件根；缺失环境绑定时返回明确错误。A 只验收 resource/execution/tool 三类 capability 可以分别注入和拒绝越界调用；RUN/CALL 的真实进程行为、工具清理、超时取消、强隔离和资源配额不属于本计划。

## 11. 组合、切换和关闭顺序

### 11.1 分阶段装配

WRX-1 只交付访问边界、公开 application 契约及其实现修正，不要求修改生产 SystemAssembler、切换全部调用方或提前启动不稳定系统。先通过可独立构造的组件和真实公开路由协作验收。

WRX-2 建立 WorkspaceRuntime 聚合和关闭接口，WRX-3 完成 cache 接入，WRX-4/5 切换读取与提交消费者。相关接口稳定后再由 System 组合根接入：创建全局总线、资源所有者和 Workspace 基础设施，注入缓存/失效依赖，挂载 Patchouli application routes，最后接入 Alice/Passive/HTTP 消费者。最终接入仍需在 WRX-7 收口前完成；不得将这一终态要求提前当作 WRX-1 的缺陷。

WorkspaceRuntime 不取得 Patchouli 内部 provider；Patchouli 持有 canonical 组件并消费 Workspace cache/失效设施。System 只装配，不成为请求时 service locator。

### 11.2 无 Alice 的装配验收

无 Alice 验收采用独立测试组合，无需提前调用生产 HiveMemorySystem.build()：

```text
测试入口 → WorkspaceAccessBoundary → GlobalSystemBus
  → 真实 PatchouliBridge/application → local bus/runtime → canonical 资源
                              |
                     WorkspaceRuntime cache/invalidation

Asset application → WorkspaceAssetStore/READY lease
```

不得创建 AgentRuntime、PendingAtomRuntime、MTP parser 或 Alice local bus。WRX-1 验证统一访问与公开 API；后续阶段再加入 cache、Asset 和关闭验证：

1. 在两个授权 scope 下通过相同 application API 读取 Profile、Memory 和 READY Attachment；
2. 跨 Workspace 的 alias、profile ref、asset ref 拒绝访问；
3. 通过公开 application API 提交 interaction/intent 并观察真实结果，不直接调用内部 controller 冒充公开边界；
4. canonical revision 变化后旧 cache 不再命中，去掉 cache 不改变领域结果；
5. 停收后拒绝新请求，在无 Alice 情况下完成领域 queue/store 与 WorkspaceRuntime drain/close。

集成验收使用真实总线、bridge、application 和领域协作；模型、网络、存储连接等进程外依赖可使用确定性实现。仅使用 fake route handler 的测试可保护单个 adapter，但不能作为共享业务链路已完成的证据。

### 11.3 shutdown/drain

关闭时按“停止接纳 → 停止新执行 → 等待 settlement/resource reads → drain producers → detach consumers → close resource runtime/store”执行。当前若先 unmount bridge 再关闭 Alice，可能丢失最后的 settlement；迁移阶段必须把 producer drain 和 consumer detach 的顺序写成可测试的 contract。默认 unmount 不等于 drain，不能依赖隐式行为。

## 12. 实施阶段

### WRX-0：冻结资源边界与两计划交接面

**产出**：资源归属/领域权威矩阵、现有调用与 mutation 入口清单、目录落点、兼容矩阵、Pending 保留决定，以及第 5.6 节访问边界和第 5.7 节交接面。

**验收**：可判断每项状态的权威所有者和生命周期；冻结 CallerPrincipal→Workspace admission→operation grant→resource policy→domain policy 的检查顺序，并核对管理员、Alice、Passive/外部 Actor 三类主体入口；与 B 的 EMS-0 核对被动会话、主动资源、历史材料三种使用场景，不让 application/资源契约依赖外部 wire model；外部 wire 身份、会话和状态协议不再作为 A 的实施前置。

### WRX-1：统一访问边界与 application 契约

**产出**：WorkspaceAccessBoundary、access context、immutable/copy-on-read 快照；明确各公开用例所需 operation；补齐 Actor-visible 点读/Profile 来源、交互提交、意图提交及带归属结果查询。保留已实现的快照、错误、版本和任务归属字段，将 Workspace service 中的领域逻辑回归 Patchouli application，撤销三类平行业务 port 和直接 provider 依赖。

**验收**：独立路由协作测试证明 admission、operation、ownership/visibility、domain policy 顺序；裸 scope/错误 grant 被拒绝，管理操作不泄漏给 Agent，交互提交不隐含检索权；无 Alice 的真实 application 提交/结果可用；source/failure 语义稳定。不要求本阶段修改生产组合根；消费者实际切换在 WRX-4/5 验收。

### WRX-2：引入进程级 WorkspaceRuntime

**产出**：Runtime 聚合入口、cache key/invalidation 内部接口、Asset 基础设施与关闭契约；独立测试组合。稳定后再接入生产组合根，不将完整系统装配提前作为前置。

**验收**：不创建 per-Workspace Runtime；不保存 current scope；WorkspaceRuntime 可脱离 Alice 启动、读取、失效和关闭。

### WRX-3：迁移 Profile/Atom cache

**产出**：两个 cache 的实现移入 WorkspaceRuntime；冻结 key、snapshot、负缓存、epoch、并发 fetch、close 和观测契约；Alice 通过授权后的公开 application 路由使用资源；旧 cache 属性、构造和 clear 入口进入兼容适配或删除清单。

**验收**：两个 Workspace 的 alias/profile 访问隔离；缓存命中不绕过 admission、operation grant 或 resource policy；canonical mutation 后旧 revision 不可返回；in-flight fetch 不能覆盖新 epoch；负缓存不跨 scope 污染；Alice stop 不清除 Workspace cache。

### WRX-4：统一 Root/CALL/SEARCH/READ 和附件读取

**产出**：ProfileResolver、CallContextProvider、RuntimeAliasResolver、MTP、管理 API、任务查询、Asset 和 Passive 读取的 access/公开路由切换；Passive 提交改用 Patchouli application 路由。覆盖三种主体及各既有操作，不仅迁移 Agent 读取。

**验收**：根与 CALL 的 source/policy/failure 语义一致；SEARCH/READ 仍保留 MTP 输出；附件仍满足 READY-only、lease 和 scope 约束；所有入口的 admission/operation/resource policy 顺序一致；Passive 既有请求/响应与会话行为兼容，新外部协议由 B 实施。

### WRX-5：收缩 AgentRuntime，拆出 run settlement

**产出**：删除 AgentRuntime 对资源 cache 的直接依赖；建立 workset/settlement coordinator；实现第 9.1 节的 snapshot/task/result 交接；保留单一 Pending 状态机。

**验收**：frame finalize、run finalize、materialization、result projection 和 invalidation 的责任可分别测试；提交前取消、接纳后断连、超时、重复 settlement 和失败重试保持既有行为；不得出现第二份可变 Pending 状态机。

### WRX-6：MTP 执行动作和工具 provider 解耦

**产出**：resource/execution/tool capability 的注入 seam；kernel registry 的显式环境绑定；兼容 `workspace_path` 错误语义。真实 RUN/CALL 执行可靠性、取消、清理和沙箱留给 v0.7.1。

**验收**：resource、execution、tool 三类 capability 可分别替换并拒绝越界调用；第二个 Workspace 不复用错误的文件根；现有 SSE/error envelope 不变；不以真实进程沙箱结果作为 A 的完成前提。

### WRX-7：删除旧入口、收口文档和 ADR

**产出**：删除或标记 Alice cache 兼容入口、绕过 access 的旧路径、重复 resolver；更新当前架构/契约文档，说明 ADR-0004 被何决策 supersede；归档本计划。

**验收**：稳定接口的生产组合根接入完成；静态依赖检查无反向 import；完整测试和 shutdown/drain 场景通过；文档中的所有“cache 属于 Alice/WorkspaceRuntime 已解体”表述与最终代码一致。

阶段之间可以有小步提交，但 WRX-3 之后不得同时保留两个可独立命中的正式资源 cache。过渡期间若必须双写，旧路径只能作为观测/对比，不得作为第二成功来源。

## 13. 既有契约和内部迁移兼容

### 保持不变

- `IdentityScope`、WorkspaceIdentity、默认 `main_workspace` 和 W0/W1 WorkspaceAsset/lease/READY 语义；
- MTP method 名称、成功结果结构、SSE 事件类型和既有错误分类，除非迁移矩阵明确列出；
- Patchouli canonical mutation、Artifact provenance、Topic binding 和 operation identity；
- Pending alias/intent/run/frame 字段形状及当前跨 run 可见性，直到另有安全契约。

### 需要内部适配

- Alice 构造函数不再接收具体 cache；通过访问边界和既有公开路由取得资源；
- ProfileResolver/RuntimeAliasResolver 的旧 public 方法转为委托 adapter；
- 旧 `agent_runtime.aliases.cache` import 在一个明确过渡窗口内可 re-export，但测试不能依赖 re-export 或私有字段；
- Patchouli public routes 保持为业务边界，迁移 access 参数和快照/结果投影；缺少用例才新增路由，不回调 Workspace 业务 service。

### 必须显式失败

- 缺失或冲突 Workspace scope；
- 试图使用另一个 Workspace 的 asset/alias/profile ref；
- cache 命中但 source revision 或授权无法重新确认；
- 第二 Workspace 没有对应工具环境绑定却要求复用默认 filesystem root；
- 关闭阶段仍有未排空的 settlement consumer。

## 15. 风险、决策门和回滚

### 15.1 主要风险

- **平行用例层与递归**：把 Workspace cache 包装成另一套业务 service，或 cache miss 再调用当前 public route。门槛是业务始终由 application 承接，cache 只保存派生值，冷读取在 Patchouli 内部完成。
- **旧缓存双真相**：迁移期间 Alice 和 Workspace 同时可命中。门槛是单一成功来源；双写只用于观测，完成 WRX-3 后删除旧命中路径。
- **授权陈旧**：profile/atom cache 保存裸对象。门槛是 source revision/policy freshness 和 invalidation race 测试，不接受永久授权缓存。
- **关闭丢失 settlement**：consumer 先卸载。门槛是可重复的 drain 顺序测试和明确 stop contract。
- **边界过度膨胀**：把 Pending、DAG、持久化 workflow 一起迁移。门槛是坚持本计划非目标和 WRX-5 的单一状态机。
- **性能回退**：所有读取都绕过 cache。门槛是先保证正确性，再用可观测 hit/miss 指标优化；不以隐式旧值换性能。

### 15.2 保留的开放决定

以下问题在实现前必须由 WRX-0/1 关闭，但不应阻塞整体方向：

1. Patchouli application 快照的 source revision 如何复用既有字段；
2. invalidation 使用同步调用、进程内事件还是两者组合；正确性不得依赖异步事件最终到达；
3. 旧 resolver/import 的兼容窗口长度和删除版本点；
4. Profile projection 是否需要区分配置 revision 与 atom content revision；
5. run settlement coordinator 的最终包路径（Alice workset 或独立 system coordinator），只要不复制 Pending 状态机；
6. 第 5.7 节领域提交入口中哪些签名需要去除 Alice 专属类型，以及其无 Alice 调用的验证范围；
7. source revision/content identity 缺失时，profile/atom 读取是否采用同步 revalidation 还是明确 no-cache；不得静默接受旧快照；
8. cache 负缓存的最短保留窗口、容量上限和观测字段；这些参数可以实现阶段确定，但 scope 绑定、epoch 校验和错误类别不可省略。
9. 四阶段访问顺序保留；按本次修订重新验收 access 在 System/AliceBridge/GlobalSystemBus/Patchouli application 中的完整传递，并冻结各管理操作和新增提交用例的 operation/路由签名。任务投影字段与工厂已有工作可复用，不得把原 port 局部验收等同于统一边界完成。

这些是局部接口选择，不得被解释为“是否建立 Workspace 资源平面”仍未决定。

### 15.3 回滚

每个阶段保持可单独回滚的构造开关或装配分支，但不得长期双写两个 canonical store/cache。若 WRX-3 后发现授权/一致性回归，回滚目标是恢复旧 adapter 的调用入口，同时保留已验证的访问边界和 application 授权规则；不得把新资源数据复制回 Alice 私有字典。没有持久化 schema migration，因此无需数据回填回滚；若发现已有 source ownership 不一致，应 fail closed 并单独建立数据修复计划。

## 17. 计划完成后的验收问题

审查者应能直接回答：

- 没有 Alice 进程时，谁能读取一个 Workspace 的 Profile、Memory 和附件？
- 一个 Agent 同时进入两个 Workspace 时，哪些状态共享，哪些状态必须隔离？
- 哪个组件拥有 PendingAtom 状态机，哪个组件负责最终 materialization？
- canonical Memory 由管理服务修改后，哪条路径保证缓存不返回旧值？
- MTP READ、WRITE、RUN、CALL 分别跨过哪一个 capability？
- 关闭时为什么不会丢失最后一个 settlement？
- 如果删除所有 cache，系统是否仍保留同样的 canonical 资源和授权语义？
- 一个外部或本地 CallerPrincipal 如何被验证为可代表某个 Actor 进入某个 Workspace？
- 准入成功但资源为 PRIVATE/TEAM 或 operation 未授权时，是否仍能明确拒绝？
- 任务 ID 被单独拿到时，系统能否根据权威 scope/提交者关联拒绝越权查询？

如果这些问题仍需通过“当前只有某个 Agent 使用”来解释，说明边界尚未完成；如果答案可以只引用 Workspace 访问/缓存基础设施、Alice 执行侧和 Patchouli application/canonical 资源，则代码结构已经开始反映主网与 CPU 的分离。
