# v0.7.0 计划 A：Workspace 资源体系与 Agent 执行边界重构

本文是 v0.7.0 的基础重构计划。它建立在 v0.6.2 W0 Workspace MVP、Identity 投影收敛、V1 Memory 迁移和 W1 Chat Attachments 已完成的结果之上，目标是把代码结构重新对齐到 [VISION.md](../VISION.md) 与 `ae2-hivememory-architecture-analogy.md` 的基本模型：持久化资源是跨执行周期的主状态，Workspace 是独立存在的资源体系，Actor/Agent 进入该体系读取资源、执行任务并提交结果。

本计划原目标为 v0.6.2，随后独立排入 v0.7.0。现拆为两份同版本计划：本文（计划 A）负责资源体系与内部执行边界；[计划 B：外部记忆服务与 Actor 交互契约](./v0.7.0-external-memory-service-and-actor-interaction.md)负责外部接口、Passive Ingress 升级及参考客户端闭环。W0/W1 与旧缓存迁移保留原版本归属。具体 harness connector、执行基座、完整历史导入、文档摄入和 Research 继续按 [ROADMAP](../ROADMAP.md) 推进。

这不是一次把两个字典从 `AliceRuntime` 移到另一个类的局部搬家，也不是为每个 Workspace 创建一个 Runtime。计划建立一个进程级 `WorkspaceRuntime` 作为资源平面的聚合入口；它内部按 Workspace、身份和资源类型进行隔离，但不保存可变的 `current_workspace`，也不复制 Agent 执行状态。

计划状态为 `planned`。实现完成前，本文是设计与实施入口；当前架构、契约和 ADR 继续描述已落地事实。实现、测试、迁移和审查全部完成后，按文档治理规则更新事实文档并将本文归档。

## 1. 背景和问题

### 1.1 理念基线

AE2 类比中，Workspace（主网）提供稳定资源、能力和策略；Agent（CPU）是临时执行器。Agent 可以进入一个 Workspace，读取 Memory/Profile/Topic/Attachment 等资源，执行一轮或一组动作，再把结果提交回资源平面。资源的存在不应依赖某一个 Agent 是否正在运行，也不应随着某个执行器的替换而丢失。

Patchouli 是资源存储和领域算法的权威持有者，Alice 负责 run 编排和执行工作集，MTP 是把模型产生的动作接入两侧的协议适配层。`WorkspaceRuntime` 是组合和资源访问边界，不取代 Patchouli 的事实存储，也不变成第二个 Agent 框架。

这也落实了 VISION.md 的双轨策略：Patchouli 应能通过 passive ingress、API、MCP、skill 或其他适配器独立服务外部 harness；Alice 是验证 memory-native runtime 的参考 Actor，而不是 Patchouli 的唯一使用者。计划的架构成功不以 Alice 追平 Codex、Claude Code 等通用 harness 为条件，而以资源系统能否被不同 Actor 稳定使用、以及 Alice 是否能在可比较实验中证明额外的 memory-native 优势为判断依据。

### 1.2 当前结构的矛盾

当前 W0/W1 已经把 Memory、Topic 和 WorkspaceAsset 语义上放入 Workspace，但资源读取仍由 Alice 侧的派生缓存和 resolver 组织：

- `AliceRuntime` 构造并清理 `AgentProfileCache`、`KoakumaAtomCache` 和 `PendingAtomRuntime`；
- `AgentProfileResolver`、`RuntimeAliasResolver` 同时承担授权坐标解释、缓存命中、Patchouli 冷查找和 MTP 错误翻译；
- Alice settlement 成功后才触发缓存失效和重新填充，来自管理服务、生命周期或其他入口的 canonical 变化可能没有同等的失效路径；
- `AgentRuntime.finalize_run` 还直接负责 PendingAtom 的 materialization 和按 run 驱逐；
- MTP runtime 同时持有资源查找、执行动作、工具目录和环境绑定，导致“Agent 能调用什么”与“Workspace 提供什么”混在同一文件和生命周期中；
- 根 Profile 与 CALL Profile 走不同解析入口，容易出现缓存坐标、授权重验和错误语义不一致。

这些问题不是通过继续增加 `agent_runtime` 子目录就能解决的。需要先区分五个维度：资源的权威所有权、资源访问的服务边界、缓存的派生实现、执行工作集的生命周期，以及全局 ID/索引/授权的不同职责。

### 1.3 旧计划和 ADR 的位置

旧的 `v0.6.2-workspace-runtime-cache-migration` 已完成并归档。ADR-0004 记录了当前“派生缓存由 AliceRuntime 持有、WorkspaceRuntime 解体、PendingAtomRuntime 保持 Alice 所有”的事实决定。本计划不回写历史，也不把旧计划的实现结果当作目标架构；它提出一个新的、可验证的边界重构，并在收口阶段明确 ADR-0004 的 supersede/update 方式。

### 1.4 与 VISION.md 的对应关系

本计划不是把项目重新定位为通用 Agent harness。它落实的是 VISION.md 中的双轨策略和可比较实验原则：

| VISION.md 命题 | 本计划的结构含义 |
|:---|:---|
| Patchouli 具有独立的 Memory Infrastructure 价值 | Workspace 资源服务可在没有 Alice 运行时的情况下读取、授权和失效 Memory/Profile/Asset，并可被 Passive Ingress 或其他 adapter 使用 |
| Alice 是 memory-native reference runtime | Alice 继续保留执行 loop、工作集、模型调用和提交协调，但不再拥有资源 canonical truth 或正式资源 cache |
| 模型和 harness 可以替换，长期资产继续存在 | 资源端口、scope、snapshot、submission、status、error 和 provenance 契约与具体 Actor、模型和 transport 无关 |
| 需要比较外部 harness + Patchouli 与 Alice + Patchouli | 计划验收同时覆盖无 Alice 的资源链和 Alice 的原生执行链；不把 Alice 的存在本身当成系统正确性的证明 |
| Passive ingress 是开放生态的现实入口 | A 提供独立资源能力；B 负责 Passive、主动交互与未来导入的接入契约，Passive 本身保留被动对话服务定位 |

因此，“Workspace 资源平面”是本计划的长期结构目标，“Alice 参考 Actor 的额外优势”是后续需要通过实验验证的假设。二者不能互相替代。

### 1.5 两份计划的分工

资源可供其他消费者使用是 A 的出口；将其交付为外部客户端可使用的交互协议是 B 的出口。本表是拆分责任和最小交接面的规划入口，B 通过链接引用，不再复制内部资源模型。

| 工作 | 计划 A | 计划 B |
|:---|:---|:---|
| Workspace 归属、Patchouli 领域权威、缓存、资源生命周期 | 设计与实现责任 | 消费并验证，不另建资源状态 |
| 可信调用上下文中的 IdentityScope、资源引用与领域结果 | 提供内部窄端口；保留 owner 校验 | 从外部身份映射，定义请求/响应序列化 |
| Memory/Profile/Asset 读取与既有领域写入能力 | 与 Alice 解耦，提供领域服务入口 | 定义主动操作的外部权限、提交及结果协议 |
| Alice、MTP 与 PendingAtom | 资源依赖注入、单一工作集、run 收尾重排 | 不复刻 Alice 工作集；映射相关领域语义 |
| Passive Ingress | 资源依赖变动所需的最小内部适配；保持现有行为 | 实时会话、结果观察、兼容与协议升级 |
| 历史导入 | 不实现 | 参与协议场景验证；完整批次与格式产品留给 v0.7.2 |
| 外部认证映射、connector、统一交互体验 | 不实现 | B 冻结适用范围；厂商 connector 留给 v0.7.1 |

A 的独立验收使用真实资源服务和既有领域入口，不以 B 的 transport、身份协议、结果查询服务或客户端完成为条件。B 的协议设计可并行，最终集成依赖 A 的对应能力就绪；共同发布 v0.7.0 时分别核对两份计划的出口。

## 2. 目标、非目标和完成定义

### 2.1 目标

1. 建立进程级 `WorkspaceRuntime`，作为 Workspace 资源访问、缓存、授权重验、失效和生命周期的统一聚合入口。
2. 将 Profile cache 和 Atom cache 作为 Workspace 资源服务的派生实现，使其不依赖 Alice 是否运行，且按完整资源访问坐标隔离。
3. 让根 Profile、CALL Profile、MTP SEARCH/READ、附件读取和其他正式资源读取复用同一 Workspace 资源服务。
4. 让 Alice 只保留 run 编排、frame/loop、模型调用、执行信号、工作历史、临时结果和提交动作。
5. 保留 Patchouli 对 Memory、Profile、Topic、Artifact 的权威存储、可见性策略和领域变更算法；WorkspaceRuntime 不建立第二套 canonical 记录。
6. 让 MTP 变成跨边界适配层：资源读取经过 Workspace capability，执行和写入动作经过 Alice/提交端口，工具环境由独立 provider 提供。
7. 明确 PendingAtom 的暂留边界，避免把复杂的执行状态机盲目迁移到 Workspace，也避免让单帧 AgentRuntime 独占 run 级结算。
8. 在不改变 v0.6.2 已冻结的外部成功/失败、scope、MTP/SSE 和 WorkspaceAsset 语义的前提下，逐阶段完成内部结构切换。
9. 提供不携带 Alice frame、PendingAtom 或 MTP 类型的内部资源与领域交接接口，供计划 B 及其他消费者使用；不在 A 冻结通用外部 Actor 协议。

### 2.2 非目标

- 不为每个 Workspace 创建一个 Runtime 实例，不引入可变的 `current_workspace`。
- 不重写 Memory、Topic、Artifact 的持久化模型，不新增 Workspace 的第二个事实存储。
- 不在本计划中实现 Workspace 创建、跨 Workspace 通信、子网/Mount/DAG、持久化 Agent workflow 或分布式调度。
- 不把所有内部对象都改成带 Workspace 前缀的 ID；全局唯一性、资源归属、索引和授权分别处理。
- 不将 `PendingAtomRuntime` 整体迁移为 Workspace 资产，不复制其状态机，也不在本计划内重写 UUID/alias 生成和耐久化。
- 不把 MTP RUN 的强沙箱、资源配额和不可信代码执行作为本次边界重构的隐含前提。
- 不因为“当前只有 Alice 使用”就把资源服务重新归还 Alice；消费者数量不是资源所有权判据。
- 不在 A 实现外部 Actor 协议、身份认证映射、operation 查询服务或 Passive 新交互模式；这些由计划 B 负责。具体厂商连接器、批次导入产品和强沙箱不属于两份计划的当前交付。

与后续工作的交接范围：A 的 WRX-1/2 向 B 提供资源服务和领域端口；B 实施外部交互。A 的 WRX-6 只拆分 MTP 与工具 provider 的依赖，执行故障诊断、进程可靠性和沙箱基线留给 v0.7.1；具体外部 harness 接入也在 v0.7.1 独立验证。

### 2.3 完成定义

计划完成时必须同时满足：

- 停止或替换 Alice 后，仍可通过 Workspace 资源服务读取已授权的 Memory、Profile 和附件表示；
- 同一进程中两个 Workspace 的资源读取、缓存命中、失效和附件 resolve 不串扰；
- 一个 Agent 可在两个 Workspace scope 下并发运行，run/frame/history/pending 不互相泄漏；
- 所有正式 Profile/Memory 读取都经过统一的 scope 和可见性检查；缓存本身不能作为授权证明；
- canonical Memory 通过任意受支持的管理、生成、生命周期入口改变后，旧资源缓存不会继续作为成功结果返回；
- Alice 不再直接拥有 Workspace 资源缓存，也不再通过单帧 finalize 直接决定所有 run 级 materialization；
- MTP 的资源动作、执行动作和工具动作可分别替换测试 provider，而无需启动完整 Alice；
- 现有外部路由、MTP 结果、SSE 事件、错误分类和 shutdown drain 行为保持兼容，除非在契约变更清单中明确记录。

## 3. 目标模型和边界

### 3.1 资源体系与执行体系

```text
Alice / AgentRuntime -- MTP 内部适配 --+
                                      |
计划 B 外部服务 ---------------------+--> Workspace 资源端口
                                             |
                                  Patchouli 领域 provider / AssetStore
                                             |
                                  canonical 资源 / 派生 cache
```

Workspace 是资源归属与访问边界，Patchouli 是其中记忆领域的权威实现；二者不各自保存一份 canonical 状态。System 创建进程级 WorkspaceRuntime，资源服务不依赖某个执行器。MTP 是 Alice 的协议适配路径之一，外部消费者无需经由 MTP 才能访问资源。

A 只定义已有可信 IdentityScope 下的内部交接能力。外部 Actor 如何建立身份、使用协议、获得 operation receipt，由计划 B 定义。

### 3.2 责任矩阵

| 能力 | 权威持有者 | WorkspaceRuntime 暴露 | Alice 持有 | 禁止的耦合 |
|:---|:---|:---|:---|:---|
| Memory/Profile canonical 数据 | Patchouli / MemoryLibrary | 授权读取、版本快照、资源缓存 | 无 | Alice 不能直接访问 Patchouli store 或私有 cache |
| Topic、短期快照 | Patchouli Perception | 只提供正式读取所需的资源视图 | 本轮上下文中的临时引用 | WorkspaceRuntime 不复制 Topic 状态机 |
| WorkspaceAsset / Representation | System WorkspaceAssetStore | resolve、READY 检查、lease、编译输入 | 仅持有本轮使用结果 | Alice 不管理全局 asset 生命周期 |
| Profile/Atom cache | WorkspaceRuntime 内部派生实现 | scope-aware read/invalidate/close | 无所有权 | cache 不能绕过授权或成为第二事实源 |
| PendingAtom | 当前 Actor execution workset（Alice 暂实现） | 不持有 | 创建、frame/run 关联、执行侧可见性 | Workspace 不复制 Pending 状态机 |
| Memory materialization | Patchouli 领域服务；run settlement consumer 协调 | 提供资源读取/失效通知 | 提交意图和 run 结果 | AgentRuntime 不直接编排所有跨域副作用 |
| 模型调用、frame、loop | Alice / AgentRuntime | 不参与 | 权威执行状态 | Workspace 不保存模型会话状态 |
| MTP 语法、结果、SSE | MTP adapter | 注入资源 capability | 注入执行 capability | MTP runtime 不同时拥有两侧状态 |
| 工具目录和环境 | 独立 tool provider | 绑定资源/环境配置 | 请求执行 | 不用 prompt 或隐式全局路径表示权限 |

### 3.3 生命周期和实例规则

- 进程启动时由 System composition root 创建一个 `WorkspaceRuntime`，并注入 Patchouli 的窄 provider、WorkspaceAssetStore 及资源服务实际需要的依赖。
- `WorkspaceIdentity` 和 `IdentityScope` 是调用时数据，不改变 Runtime 的实例身份；服务方法必须显式接收 scope。
- AliceRuntime 可创建多个 run，但不能创建或清空 WorkspaceRuntime；停止 Alice 不应清除资源缓存。
- 系统关闭时先停止接纳新的 Agent 请求，再等待需要读取 Workspace 资源的 in-flight 操作和 settlement consumer 完成，最后关闭 WorkspaceRuntime、AssetStore 和 Patchouli provider。不得以“先卸载 Alice bridge”代替 drain。
- cache 的清理是资源运行时生命周期操作，与某个 Agent run 的完成、取消或重启分开；缓存是否跨进程持久化仍由后续计划决定，本计划不承诺重启恢复。

## 4. 目标代码组织和依赖规则

### 4.1 目标包结构

```text
src/hivememory/
  workspace/
    __init__.py
    runtime.py                 # 进程级聚合入口
    ports.py                   # 资源 provider/capability 端口
    services/
      memory.py               # scope-aware formal memory reads
      profile.py              # profile projection + cache
      assets.py               # WorkspaceAsset facade/lease adapter
      invalidation.py         # canonical change -> derived cache invalidation
    cache/
      atom.py                 # private atom cache implementation
      profile.py              # private profile cache implementation
      keys.py                 # explicit scope/resource key types
    projections.py             # immutable resource snapshots
  alice/
    runtime/
      core.py                 # run orchestration and execution wiring
      profile_resolver.py      # compatibility adapter, delegates to Workspace
      ...
    workset/                    # Pending/run working-set coordination
  agent_runtime/
    runtime.py                 # frame/loop/model/execution signals
    aliases/
      resolver.py              # execution pending/redirect view only
    mtp/
      adapter.py               # protocol dispatch and result mapping
      resources.py             # Workspace capability adapter
      execution.py             # Alice action adapter
      tools.py                  # tool provider adapter
  patchouli/
    ports/                      # low-level provider ports where needed
    services/                   # canonical stores and domain algorithms
```

实际落地时可以按现有包名分阶段迁移；上图表达的是依赖方向，不要求一次性创建所有空目录。若保留 `system/runtime/workspace/` 作为组合入口，必须让它只组合 `workspace` 资源服务，不把业务实现继续塞入 System bundle。

### 4.2 允许的依赖方向

1. `workspace.services` 只能依赖资源端口、scope/DTO、Policy 和明确的 Patchouli provider；不能导入 AliceRuntime、AgentRuntime 或 MTP handler。
2. `alice` 可以依赖 Workspace capability 和执行侧 ports；不能依赖 Workspace cache 的具体类、Patchouli 私有 store 或资源路由常量。
3. `agent_runtime` 只能依赖执行协议、Workspace capability 和注入的 action/tool ports；不能自行创建 profile/atom cache。
4. `patchouli` 继续拥有 canonical store 和领域算法；当公共 route 委托 Workspace facade 时，底层 provider 必须绕过 facade，避免递归。
5. `mtp` 负责协议适配、错误和输出格式；资源授权由 Workspace 服务完成，执行权限由 Alice/Policy 完成。
6. System composition 负责一次性装配和 shutdown 顺序，不作为请求时 service locator，也不保存当前 Workspace。
7. 计划 B 的外部适配服务依赖资源与领域端口；Workspace service 不反向依赖外部协议、特定 Actor、模型、loop 或 transport。

## 5. 资源端口和数据契约

### 5.1 Frozen scope

所有正式资源操作接收完整 `IdentityScope`，其中冻结 actor identity 与 WorkspaceIdentity。run/frame/action 等执行坐标属于 RuntimeScope 或单独关联信息，不是资源读取的强制参数。资源服务可显式派生较窄视图，不能从全局当前执行上下文猜测 scope；外部身份如何映射到该 scope 由计划 B 负责。

```python
class WorkspaceResourcePort(Protocol):
    async def get_memory(self, scope: IdentityScope, ref: MemoryRef) -> MemorySnapshot: ...
    async def get_profile(self, scope: IdentityScope, ref: ProfileRef) -> ProfileSnapshot: ...
    async def search_memory(self, scope: IdentityScope, query: MemoryQuery) -> tuple[MemorySnapshot, ...]: ...
    async def resolve_asset(self, scope: IdentityScope, ref: WorkspaceAssetRef) -> AssetReadLease: ...
```

该伪接口用于说明边界，不要求照抄命名。返回值必须是不可变或明确快照语义的 DTO，不能把可变 canonical atom 引用直接泄漏给 Agent/MTP。

### 5.2 Profile 读取

- Root Profile 和 CALL Profile 都调用同一个 `ProfileResourceService`；区别只体现在传入的 scope、目标 profile ref 和调用方 provenance。
- profile cache 的逻辑 key 至少包含 WorkspaceIdentity、用户/Agent/team/alias 等现有授权坐标，并保留 source atom UUID、source revision/content identity 和 policy projection。不能把裸 `AgentProfile` 当作永久授权证明。
- provider 每次正式读取必须返回“当前授权下的 source snapshot”或明确的不可用错误。缓存命中只有在 source revision/freshness 和 scope 仍有效时才可返回。
- 现有 default/omni_doll 等内建 Profile 仍走同一 service，但以显式 built-in source 标识返回；不把常量 alias 当作跨 Workspace 的授权旁路。

### 5.3 Memory/Atom 读取

- alias 索引按 `(WorkspaceIdentity, normalized_alias)` 分区；UUID 索引可以在实现内部保持全局，但只有在 provider 验证 source ownership 和 scope 可读后才可写入或返回。
- 对外不暴露 L0/L1/L2 层级和 cache dictionary。Alice resolver 处理 Pending/redirect，解析为正式资源引用后调用 Workspace 服务；Workspace 内部只负责正式资源的缓存和 provider 查找，不访问 Pending 工作集。
- alias 替换、跨 alias 引用、删除和失效必须在同一 service 内维护反向引用关系；不能只删除一个 map 项而留下可返回的旧快照。
- cache miss、provider failure、scope mismatch 和 source not found 必须映射为稳定的资源错误。禁止在授权失败时回退到另一个 Workspace 或旧缓存。

### 5.4 WorkspaceAsset 读取

Attachment 和其他 WorkspaceAsset 仍由 System-owned AssetStore 持有。WorkspaceRuntime 只提供 scope-aware resolve/acquire/lease facade，复用 READY-only、representation revision/hash、删除和 lease 语义。AttachmentCompiler 仍属于上下文编排链路；它接收资源 service 返回的 lease/snapshot，不直接读取 store 私有字典。

### 5.5 Authorization、ownership、index 的分离

资源归属由 WorkspaceIdentity 和 canonical owner 字段定义；全局 ID 只保证寻址唯一；alias/UUID index 只负责加速；`memory_is_readable` 等 policy 决定当前 caller 是否可读。任何一项都不能单独替代另外三项。管理服务的 owner bypass 必须留在显式 management port，不能通过 Agent resource port 暴露 `enforce_actor_visibility=False`。

### 5.6 向计划 B 交付的最小内部接口

A 交付语义明确的窄端口，不建立一个接收任意 Actor 动作的统一 envelope。双方在 WRX-0/EMS-0 用被动会话、主动资源操作、历史材料三种样例核对以下边界；内部 DTO 由其领域所有者维护，外部 wire model 由 B 维护。

| 交接项 | A 承诺 | B 承担 |
|:---|:---|:---|
| 身份上下文 | 接收显式 IdentityScope；资源 owner 仍校验归属/可见性 | 外部 principal、connector、Actor 与 scope 的可信映射 |
| 资源引用及读取结果 | 正式 ID/alias、快照、新鲜度与已有来源信息；不暴露 store/cache | 请求/响应格式、错误映射、引用回传与使用体验 |
| 领域提交 | Interaction apply、Memory intent/mutation 等既有业务端口可以脱离 Alice 调用 | 选择操作语义、收据关联、重复/冲突处理及外部提交协议 |
| 结果与状态 | 提供该领域真实结果；已有任务句柄/WorkRecord 按原契约投影 | 向外部解释事件接收、交互应用、物化结果，定义查询范围 |
| 生命周期 | consumer 关闭前所需资源/provider 可用；资源关闭与 Alice 分开 | 外部入口停收、会话 flush、请求/operation drain |

A 不承诺统一所有任务状态或新增外部 status store；也不把 PendingAtomMaterializeTask 定为所有调用方的唯一提交类型。若现有领域端口含 Alice 私有类型，A 提取语义等价的领域参数，Alice 自行适配，B 在其上建立外部操作。

该交接面由无 Alice 的资源及领域服务集成测试验收；经外部入口提交并查询结果的协议闭环由 B 验收。A 的整体完成仍须满足第 2.3 节及第 14 节。接口变更由两份计划共同审查，但不会令 A 的 cache/生命周期实施依赖 B 的全部产品能力。

## 6. 缓存一致性和失效策略

### 6.1 目标语义

缓存是 Workspace 资源服务的派生加速层。它可以被清空、重建或替换而不改变 canonical Memory/Profile；它也不能把一次曾经成功的读取变成永久授权。缓存隔离首先保证数据和访问边界，跨 Workspace 的独立容量配额留作后续治理，不在本计划中虚构完整性能隔离。

### 6.2 失效来源

所有受支持的 canonical mutation ingress 都必须产生资源失效信号或调用统一 invalidation port，包括：

- Memory create/update/delete、archive/revive；
- Materialization/settlement 产生 canonical Memory 后的提交；
- Profile source atom 或其 visibility/policy 改变；
- 资源删除、WorkspaceAsset representation revision 改变；
- 测试和管理工具使用的显式 mutation service。

Alice settlement 只是其中一个 consumer，不能再是唯一失效入口。若某一 mutation 暂时不能发布事件，必须在同一提交路径同步调用 invalidation，而不是依靠最终一致的 PubSub 猜测正确性。

### 6.3 并发和新鲜度

- invalidation 增加 scope/resource 的 epoch 或等价代次；失效前启动的 in-flight fetch 回来后必须重新检查代次，旧结果不能覆盖新缓存。
- provider 返回 source revision/content identity；profile projection 和 atom snapshot 记录该身份。
- source revision 不可用时，不得宣称永久新鲜；采用同步 provider revalidation 或明确的短暂 no-cache 路径，不能静默使用旧值。
- cache failure 不改变 canonical 操作结果；资源读取可报告暂时不可用，但不能把旧值伪装成当前值。

### 6.4 清理和容量

WorkspaceRuntime 关闭时统一关闭两个 cache。单个 run 结束不清理资源 cache；run-specific working set 由 Alice 清理。现有全局 LRU 可以先保留，只要 key 和授权语义正确；若后续需要每 Workspace 容量配额，再另立计划，不把“有统一 Runtime”误写为配额隔离。

## 7. 端到端流程调整

### 7.1 Root Profile 和 Agent 启动

```text
入口解析 IdentityScope
  -> Alice 请求 WorkspaceResourcePort.get_profile
  -> Workspace cache/provider 做 scope + policy 校验
  -> 返回 immutable ProfileSnapshot(source revision)
  -> Alice 建立 run/frame/model 配置
```

Alice 不再预热或直接读取 profile cache。ProfileResolver 可以保留为过渡适配器，但内部只能委托 Workspace port，并在迁移收口后删除其资源缓存职责。

### 7.2 CALL Profile 和子 Agent

CALL 的 caller actor、callee profile 和 Workspace scope 分开建模。CallContextProvider 通过同一个 ProfileResourceService 解析 callee；它不能把 caller profile 的缓存结果当作 callee 授权。除结构重构外，本计划不擅自改变现有 actor_id 重分配语义；若审查发现身份 provenance 问题，单独建立后续契约任务。

### 7.3 MTP SEARCH/READ

```text
MTP parser/filter
  -> Workspace resource capability.search/get
  -> authorized snapshots + citation metadata
  -> MemoryCompiler / formatter
  -> existing MTP result/SSE envelope
```

SEARCH 的 Patchouli provider 仍是检索事实来源，Workspace service 负责 scope、cache 和资源边界。READ 不接受调用者传入的内部 cache key，也不能通过 UUID lookup 绕过 alias/ownership 验证。

### 7.4 WRITE/UPDATE 和提交

MTP WRITE/UPDATE 产生 Alice execution action 或 Patchouli mutation intent。资源读取和 mutation authority 分离：Workspace service 可以提供当前 snapshot，Patchouli management/generation service 负责写入和 canonical revision，invalidation 由统一端口触发。成功条件、幂等 operation identity、错误分类继续复用 v0.6.1 契约。

### 7.5 Attachment 选择和编译

Chat 选择、lease、AttachmentCompiler 和 Topic binding 继续遵守 W1 契约。编译器从 WorkspaceAsset capability 获得 READY representation；Alice 只保存本轮实际使用的 ref、compiled context 和结果。成功 Interaction 后的 Topic/Artifact promotion 仍由 Patchouli 所有者完成，WorkspaceRuntime 不复制 binding 或 artifact 状态机。

## 8. Alice 和 Agent Runtime 的收缩

### 8.1 Alice 保留的内容

- run/frame/loop 生命周期、取消、超时和模型调用；
- working history、frame output、临时上下文和本轮 action 结果；
- PendingAtom 的执行侧创建、claim、cancel、settlement intent 和 run 关联；
- 将 MTP action 转换为 Patchouli submission 或资源操作的执行协调；
- 对 Workspace capability 的依赖注入和 run scope 冻结。

### 8.2 Alice 移出的内容

- Profile/Atom cache 的实例、字典、LRU、填充和清理；
- 通过缓存实现的正式资源授权判断；
- Patchouli canonical retrieval 的直接路由拼接；
- 把 Alice stop 当作资源 cache 生命周期的唯一清理点。

### 8.3 AgentRuntime 的边界

`agent_runtime/runtime.py` 聚焦 frame/loop/model invocation、CALL history response、execution signals 和输出。`finalize_frame` 可以完成 frame 级 pending 收束；`finalize_run` 不再直接承担所有跨域 materialization policy，而是发出 run settlement/harvest action，由 Alice workset/settlement coordinator 和 Patchouli consumer 协作完成。

`agent_runtime/aliases/resolver.py` 只保留执行侧 Pending alias、redirect 和 run-local view。正式 Memory alias 解析委托 Workspace resource service；如果同名方法为兼容性保留，必须标注 adapter，并禁止重新引入独立 cache。

## 9. PendingAtom 的处理决定

PendingAtom 目前跨越模型执行、短期工作集、materialization 和跨系统 settlement，具有比两个 cache 更高的耦合复杂度。本计划采取“边界先行、所有权暂留”的决定：

1. `PendingAtomRuntime` 暂不迁移进 WorkspaceRuntime；它仍是 Alice execution workset 的状态机。
2. WorkspaceRuntime 不接受 PendingAtom 作为正式 Workspace 资源，也不为 PendingAtom 增加 workspace 分区键来替代现有 run/frame/action scope。
3. PendingAtom 的 canonical/settlement projection 可以被 Patchouli consumer 读取，但读取必须通过窄的 settlement/task port，不得让 Patchouli 或 Workspace 直接操作 Alice 状态机。
4. 将单帧 `AgentRuntime.finalize_run` 中的 run-level harvesting 与任务投影移至明确的 Alice workset/settlement coordinator。materialization 和 Artifact promotion 继续由 Patchouli 执行，cache invalidation 由资源服务承接；不把这些领域职责集中到新的执行协调器。
5. 原有 Pending alias、intent_id、RuntimeScope 和跨 run 可见性语义在迁移阶段保持不变，除非单独冻结新的安全/可见性契约。不能因为 Workspace 重构顺手把所有 Pending ID 改成 Workspace 命名域。
6. 只有在未来证明 PendingAtom 是 Workspace 中跨 Agent 共享、可独立恢复的资源，并完成持久化、claim、租约和恢复设计后，才另立计划评估迁移。B 的外部收据不引入另一套 Pending 状态机，也不要求外部 Actor 注册 Pending 才能提交领域意图。

## 10. MTP 和工具边界

当前 MTP runtime 近千行，包含 parser/filter/formatter、alias resolver、compiler、kernel registry、SEARCH/READ/RUN/WRITE/UPDATE/CALL 和环境绑定。本计划不做机械文件搬移，而按调用方向拆分：

- protocol adapter：保留语法、参数校验、结果模型、错误码和 SSE 输出；
- resource adapter：把 SEARCH/READ/正式 Profile/Attachment 请求转给 Workspace capability；
- execution adapter：把 RUN/WRITE/UPDATE/CALL 转给 Alice action/submission ports；
- tool provider：维护 syscall catalog、环境配置和 workspace_path 绑定，执行时显式传入 scope/config。

`workspace_path` 的现有默认值只能作为兼容映射。第二个 Workspace 不得静默复用第一个文件根；缺失环境绑定时返回明确错误。完整沙箱、插件框架和资源配额不属于本计划。

## 11. 组合、切换和关闭顺序

### 11.1 分阶段装配

1. 创建 Identity/policy 和 Patchouli canonical stores。
2. 创建 WorkspaceAssetStore。
3. 创建低层 Patchouli resource providers，确保它们不调用 Workspace public facade。
4. 创建 WorkspaceRuntime 及其 memory/profile/asset services、cache 和 invalidation ports。
5. 创建 Alice workset/settlement coordinator，并注入 Workspace capability。
6. 创建 AgentRuntime、MTP adapter 和 server routes。
7. mount routes/subsystems，开始接纳请求。

组合根必须能在测试中只装配 WorkspaceRuntime + Patchouli provider，而不启动 Alice；也必须能用 fake Workspace capability 启动 Alice 资源无关的执行单元。

### 11.2 shutdown/drain

关闭时按“停止接纳 → 停止新执行 → 等待 settlement/resource reads → drain producers → detach consumers → close resource runtime/store”执行。当前若先 unmount bridge 再关闭 Alice，可能丢失最后的 settlement；迁移阶段必须把 producer drain 和 consumer detach 的顺序写成可测试的 contract。默认 unmount 不等于 drain，不能依赖隐式行为。

## 12. 实施阶段

### WRX-0：冻结资源边界与两计划交接面

**产出**：资源归属/领域权威矩阵、现有调用与 mutation 入口清单、目录落点、兼容矩阵、Pending 保留决定，以及第 5.6 节交接面。

**验收**：可判断每项状态的权威所有者和生命周期；与 B 的 EMS-0 核对三种使用场景，不让资源端口依赖外部 wire model；外部身份、会话和状态协议不再作为 A 的实施前置。

### WRX-1：建立资源端口和低层 provider

**产出**：Workspace resource ports、immutable snapshots、Patchouli low-level retrieval adapter、统一 policy 调用点，以及第 5.6 节既有领域提交/结果端口的清单与 Alice 私有类型解耦。

**验收**：provider 不递归调用 Workspace facade；提供 root/CALL 可共同消费的 profile service；既有领域提交/结果入口可在无 Alice 工作集时调用；scope mismatch、not found、visibility denied 语义稳定，消费者切换在 WRX-4 验收。

### WRX-2：引入进程级 WorkspaceRuntime

**产出**：Runtime 聚合入口、cache key/invalidation ports、Asset facade、组合根装配和关闭接口。

**验收**：不创建 per-Workspace Runtime；不保存 current scope；WorkspaceRuntime 可脱离 Alice 启动、读取、失效和关闭。

### WRX-3：迁移 Profile/Atom cache

**产出**：两个 cache 的实现移入 Workspace resource services；Alice 只接收 capability；旧 cache 属性、构造和 clear 入口进入兼容适配或删除清单。

**验收**：两个 Workspace 的 alias/profile 访问隔离；缓存命中不绕过 policy；canonical mutation 后旧 revision 不可返回；Alice stop 不清除 Workspace cache。

### WRX-4：统一 Root/CALL/SEARCH/READ 和附件读取

**产出**：ProfileResolver、CallContextProvider、RuntimeAliasResolver、MTP resource adapter 和 AttachmentCompiler 的注入切换；既有 Passive memory context 链路所需的内部资源依赖适配。

**验收**：根与 CALL 的 source/policy/failure 语义一致；SEARCH/READ 仍保留 MTP 输出；附件仍满足 READY-only、lease 和 scope 约束；Passive 既有请求/响应与会话行为兼容，新外部协议由 B 实施。

### WRX-5：收缩 AgentRuntime，拆出 run settlement

**产出**：删除 AgentRuntime 对资源 cache 的直接依赖；建立 workset/settlement coordinator；保留单一 Pending 状态机。

**验收**：frame finalize、run finalize、materialization 和 invalidation 的责任可分别测试；取消、超时、重复 settlement 和失败重试保持既有行为。

### WRX-6：MTP 执行动作和工具 provider 解耦

**产出**：resource/execution/tool adapter；kernel registry 的显式环境绑定；兼容 workspace_path 错误语义。

**验收**：用 fake Workspace capability 测试 RUN/CALL；用 fake Alice action 测试 SEARCH/READ；第二个 Workspace 不复用错误的文件根；现有 SSE/error envelope 不变。

### WRX-7：删除旧入口、收口文档和 ADR

**产出**：删除或标记 Alice cache 兼容入口、旧 direct route、重复 resolver；更新当前架构/契约文档，说明 ADR-0004 被何决策 supersede；归档本计划。

**验收**：静态依赖检查无反向 import；完整测试和 shutdown/drain 场景通过；文档中的所有“cache 属于 Alice/WorkspaceRuntime 已解体”表述与最终代码一致。

阶段之间可以有小步提交，但 WRX-3 之后不得同时保留两个可独立命中的正式资源 cache。过渡期间若必须双写，旧路径只能作为观测/对比，不得作为第二成功来源。

## 13. 既有契约和内部迁移兼容

### 保持不变

- `IdentityScope`、WorkspaceIdentity、默认 `main_workspace` 和 W0/W1 WorkspaceAsset/lease/READY 语义；
- MTP method 名称、成功结果结构、SSE 事件类型和既有错误分类，除非迁移矩阵明确列出；
- Patchouli canonical mutation、Artifact provenance、Topic binding 和 operation identity；
- Pending alias/intent/run/frame 字段形状及当前跨 run 可见性，直到另有安全契约。

### 需要内部适配

- Alice 构造函数不再接收具体 cache；短期可接收 Workspace capability；
- ProfileResolver/RuntimeAliasResolver 的旧 public 方法转为委托 adapter；
- 旧 `agent_runtime.aliases.cache` import 在一个明确过渡窗口内可 re-export，但测试不能依赖 re-export 或私有字段；
- Patchouli public route 可以继续存在，但其实现统一经过底层 provider/Workspace service，避免两套授权和冷查找逻辑。

### 必须显式失败

- 缺失或冲突 Workspace scope；
- 试图使用另一个 Workspace 的 asset/alias/profile ref；
- cache 命中但 source revision 或授权无法重新确认；
- 第二 Workspace 没有对应工具环境绑定却要求复用默认 filesystem root；
- 关闭阶段仍有未排空的 settlement consumer。

## 14. 测试和验证矩阵

测试保护可观察行为和跨边界不变量，不断言类名、私有字段或目录数量。实现阶段按仓库测试分类放置，使用真实内部 collaborator；只有外部边界才使用受控 fake。

| 层级 | 必须覆盖 | 关键反例 |
|:---|:---|:---|
| unit | scope/key normalization、profile projection、cache epoch、alias replacement、invalidation race、error mapping | 旧 in-flight fetch 覆盖新 revision；同 alias 在两个 Workspace 命中错误 UUID |
| integration | WorkspaceRuntime + Patchouli provider、AssetStore、policy、Alice capability wiring | 不启动 Alice 仍能读 Profile/Memory/Asset；management bypass 不污染 Agent cache |
| execution integration | Alice + fake Workspace capability、Pending/workset、settlement coordinator | 两个并发 run 不串 history/pending；取消、timeout、retry 不重复 materialize |
| resource independence integration | 独立装配 Workspace 服务、真实 Patchouli 领域适配和 AssetStore，无 Alice/MTP/外部协议 | 资源可读，既有领域提交可用；删除 cache 不改变 canonical 结果；外部协议闭环另由 B 验收 |
| MTP integration | adapter + real resource/execution ports、SSE/error envelope、tool provider | READ 通过 UUID 绕过授权；第二 Workspace 静默使用第一 filesystem root |
| lifecycle integration | composition startup、admission stop、producer/consumer drain、shutdown | 先 detach consumer 导致最后 settlement 丢失；Alice stop 清掉 resource cache |
| e2e | 真实 Chat root/CALL、SEARCH/READ、attachment selection、Memory mutation 后再次读取 | root/CALL profile source 不一致；跨 Workspace 资产或 alias 泄漏 |
| static | import boundary/lint、旧 direct cache import 清单、公共 route 递归检查 | Workspace service import Alice；Patchouli provider 重新进入 Workspace facade |

按 CI 现有约束运行 unit/integration 快速集（排除 `live_llm`、`e2e`、`slow`，覆盖率门槛保持 85%），再运行标记为 `e2e` 的端到端集。新增测试不得只检查 `WorkspaceRuntime._cache` 存在，也不得用一组与实现完全相同的 mock 断言转发次数。

## 15. 风险、决策门和回滚

### 15.1 主要风险

- **递归路由**：Workspace public facade 与 Patchouli public route 互相调用。门槛是先建立低层 provider，并在 integration test 中检测调用链只能单向穿越。
- **旧缓存双真相**：迁移期间 Alice 和 Workspace 同时可命中。门槛是单一成功来源；双写只用于观测，完成 WRX-3 后删除旧命中路径。
- **授权陈旧**：profile/atom cache 保存裸对象。门槛是 source revision/policy freshness 和 invalidation race 测试，不接受永久授权缓存。
- **关闭丢失 settlement**：consumer 先卸载。门槛是可重复的 drain 顺序测试和明确 stop contract。
- **边界过度膨胀**：把 Pending、DAG、持久化 workflow 一起迁移。门槛是坚持本计划非目标和 WRX-5 的单一状态机。
- **性能回退**：所有读取都绕过 cache。门槛是先保证正确性，再用可观测 hit/miss 指标优化；不以隐式旧值换性能。

### 15.2 保留的开放决定

以下问题在实现前必须由 WRX-0/1 关闭，但不应阻塞整体方向：

1. Patchouli source revision 是复用现有字段还是增加窄的 provider DTO 字段；
2. invalidation 使用同步调用、进程内事件还是两者组合；正确性不得依赖异步事件最终到达；
3. 旧 resolver/import 的兼容窗口长度和删除版本点；
4. Profile projection 是否需要区分配置 revision 与 atom content revision；
5. run settlement coordinator 的最终包路径（Alice workset 或独立 system coordinator），只要不复制 Pending 状态机；
6. 第 5.6 节领域提交入口中哪些签名需要去除 Alice 专属类型，以及其无 Alice 调用的验证范围。

这些是局部接口选择，不得被解释为“是否建立 Workspace 资源平面”仍未决定。

### 15.3 回滚

每个阶段保持可单独回滚的构造开关或装配分支，但不得长期双写两个 canonical store/cache。若 WRX-3 后发现授权/一致性回归，回滚目标是恢复旧 adapter 的调用入口，同时保留已验证的 Workspace provider；不得把新资源数据复制回 Alice 私有字典。没有持久化 schema migration，因此无需数据回填回滚；若发现已有 source ownership 不一致，应 fail closed 并单独建立数据修复计划。

## 17. 计划完成后的验收问题

审查者应能直接回答：

- 没有 Alice 进程时，谁能读取一个 Workspace 的 Profile、Memory 和附件？
- 一个 Agent 同时进入两个 Workspace 时，哪些状态共享，哪些状态必须隔离？
- 哪个组件拥有 PendingAtom 状态机，哪个组件负责最终 materialization？
- canonical Memory 由管理服务修改后，哪条路径保证缓存不返回旧值？
- MTP READ、WRITE、RUN、CALL 分别跨过哪一个 capability？
- 关闭时为什么不会丢失最后一个 settlement？
- 如果删除所有 cache，系统是否仍保留同样的 canonical 资源和授权语义？

如果这些问题仍需通过“当前只有某个 Agent 使用”来解释，说明边界尚未完成；如果答案可以只引用 Workspace 资源端口、Alice 执行端口和 Patchouli canonical provider，则代码结构已经开始反映主网与 CPU 的分离。
