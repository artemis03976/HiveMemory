# Workspace Runtime 聚合与缓存所有权迁移

## 1. 背景与问题

v0.6.2 W0 建立 Workspace 后，MemoryAtom、Topic、Artifact 和 WorkspaceAsset 已经具备 Workspace ownership。W1 附件链路又增加了一个由 System 装配、跨 Patchouli/Alice 使用的 Workspace-owned working set。与此同时，Agent profile cache 和 Koakuma atom cache 仍由 AliceRuntime 直接创建，PendingAtomRuntime 也与它们处在同一组 Agent runtime 依赖中。

这张对象图能够工作，但没有清楚区分三类状态：Workspace 资源的派生缓存、Agent 执行期间的可变状态机，以及仅负责组合这些资源的进程级运行时。尤其是两个 cache 当前没有完整的 Workspace 维度：Agent profile cache 按 `ActorIdentity + alias` 缓存，atom cache 的 alias 索引是全局的。Workspace 之间存在同名 alias 或不同 profile 时，缓存会出现错误命中、无效覆盖或不必要的冷查询。

本计划建立一个进程级唯一的 `WorkspaceRuntime` 聚合，迁移两个 Workspace-oriented cache 的持有关系，并重新定义它们的 key、命中校验和生命周期。`PendingAtomRuntime` 是否成为 Workspace 基础设施保留为独立议题，本计划不将其迁移。

## 2. 目标

1. 创建一个由 System 组合根装配的单实例 `WorkspaceRuntime`，用于聚合 Workspace-owned working set 及其派生 cache。
2. 将 `AgentProfileCache` 与 `KoakumaAtomCache` 的创建和持有关系从 AliceRuntime 解耦，改由 WorkspaceRuntime 提供明确的 cache port。
3. 使两个 cache 的索引能够区分 Workspace，同时继续在最终 resolver/owner 边界执行完整 `IdentityScope` 校验。
4. 保持一个 WorkspaceRuntime 实例，不按 Workspace 复制 Runtime，不读取或保存 `current_workspace`。
5. 保持附件 Store、cache、Alice、Patchouli 的关闭顺序和各自的生命周期语义，不用一个统一 `clear()` 隐藏跨系统 drain 依赖。
6. 通过跨 Workspace、跨 Actor、同 alias 和 settlement 回填测试，证明迁移后不会产生缓存串扰。

## 3. 非目标

- 不把 `PendingAtomRuntime` 从 Alice/Agent Runtime 迁移到 WorkspaceRuntime。
- 不改变 PendingAtom 状态机、alias/intent settlement 协议、materialize task 或事件名称。
- 不把 WorkspaceRuntime 变成业务控制器、授权服务、队列、调度器或新的资源事实源。
- 不为每个 Workspace 建立独立的 Alice、Patchouli、Agent loop、EventBus 或 cache 实例。
- 不承诺 cache 跨进程持久化、重启恢复、跨进程失效或 Profile 版本订阅。
- 不在本计划中修改 Memory、Topic、Artifact 或 WorkspaceAsset 的持久化模型。

## 4. 当前基线

当前 AliceRuntime 直接创建以下对象：

```text
AliceRuntime
├── AgentProfileResolver ── AgentProfileCache
├── PendingAtomRuntime
├── KoakumaAtomCache
├── RuntimeAliasResolver ── PendingAtomRuntime + KoakumaAtomCache
└── AgentRuntime ── PendingAtomRuntime
```

其中：

- `AgentProfileResolver` 从 Patchouli 读取 Workspace-owned Agent Profile，但 cache key 不包含 Workspace，且 cache hit 不重新执行 Profile owner/policy 校验；
- `KoakumaAtomCache` 维护全局 `alias -> UUID` 与 `UUID -> MemoryAtom` 索引，resolver 在 L1 命中后重新检查 Workspace ownership 与 actor policy；
- `PendingAtomRuntime` 保存可变 PendingAtom、状态迁移、run/frame 认领、settlement 和回收，是 Alice 执行链的状态真相；
- W0/W1 的当前文档把 cache、queue、registry、scheduler、runtime 和 EventBus 定义为进程级共享基础设施。本计划只对两个明确需要 Workspace-aware 索引的派生 cache 建立例外，并记录该设计变化。

## 5. 目标设计

```text
SystemAssembler
└── WorkspaceRuntime                 # 进程级唯一聚合
    ├── WorkspaceAssetStore          # 既有 System-owned working set
    ├── AgentProfileCache            # Workspace + Actor + alias
    └── KoakumaAtomCache             # Workspace + alias / UUID

AliceRuntime
├── AgentProfileResolver ─────────── WorkspaceRuntime.profile_cache_port
├── RuntimeAliasResolver ─────────── WorkspaceRuntime.atom_cache_port
├── PendingAtomRuntime               # 继续由 Alice 持有
└── AgentRuntime ──────────────────── PendingAtomRuntime
```

`WorkspaceRuntime` 只负责组合、访问入口和分阶段清理；每个子组件仍拥有自己的数据结构、容量、失效和错误语义。WorkspaceRuntime 不接收一个可变的当前 Workspace，也不根据 scope 创建子 Runtime。

### 5.1 Agent profile cache

第一版采用完整授权坐标作为 key：

```text
(WorkspaceIdentity, ActorIdentity, agent_alias) -> AgentProfile
```

这样可以表达同一 Actor 在不同 Workspace 使用同名但不同内容的 profile，也能避免私有/团队 profile 在不同 Actor 之间复用。`default`、`omni_doll` 和空 alias 继续直接返回内置 `OMNI_DOLL_PROFILE`。

后续若需要减少按 Actor 的重复缓存，可以改为缓存带来源元数据的 MemoryAtom，并在命中时重新执行 owner/policy 校验；这不属于本次迁移的必需出口。

### 5.2 Atom cache

alias 索引改为 Workspace-aware：

```text
(WorkspaceIdentity, alias) -> UUID
UUID -> MemoryAtom
```

UUID 仍然是全局资源 ID，但所有对外 alias 读取都必须带 WorkspaceIdentity。resolver 命中 UUID 后继续检查 Memory ownership 和 actor policy；缓存 key 不能替代授权。写入时若同一 `(WorkspaceIdentity, alias)` 指向不同 UUID，必须按既有失效/替换语义处理，不能留下两个相互矛盾的 alias 反查结果。

### 5.3 Resolver 与边界

`RuntimeAliasResolver` 继续留在 Agent runtime 侧，因为它编排 L0 Pending、L1 Atom cache 和 L2 Patchouli retrieval 三层语义。迁移只替换 L1 cache 的依赖来源，并将 `IdentityScope` 传入 cache 查询所需的 Workspace 坐标；L0 仍由 PendingAtomRuntime 提供，L2 仍由 Patchouli 作为最终资源 owner。

`AgentProfileResolver` 仍负责调用 Patchouli profile route、错误映射和并发 miss 合并。WorkspaceRuntime 不直接调用 GlobalSystemBus，也不绕过 Patchouli 的 profile ownership 校验。

## 6. 跨系统契约变更

### 6.1 组合与依赖注入

- `SystemAssembler._build_runtime()` 新建并返回 `WorkspaceRuntime`；`WorkspaceAssetStore` 作为其子组件或显式 port 暴露。
- `AliceSystem` / `AliceRuntime` 接收 WorkspaceRuntime 提供的 profile/atom cache port，不再自行实例化两个 cache。
- `AgentProfileResolver`、`RuntimeAliasResolver` 的构造函数改为依赖抽象 port，避免 Alice import WorkspaceRuntime 的具体实现。
- `System` 停止流程保留 Patchouli drain、Alice stop、AssetStore close 的先后关系；WorkspaceRuntime 必须提供分阶段 shutdown，而不是提前清空仍被消费者使用的状态。

### 6.2 Cache API

profile cache 的 `get/store` 必须接受 WorkspaceIdentity 和 ActorIdentity；atom cache 的 alias 查询、写入和失效必须接受 WorkspaceIdentity。所有兼容入口在迁移完成前只允许由内部 adapter 使用，不能恢复无 scope 的公共读取。

### 6.3 MTP 与 Pending 契约

MTP 的公开 payload、`PendingAtomMaterializeTask`、`PendingAtomSettlement`、PendingAtom 事件和 `pending_alias` 格式不变。PendingAtom 的 Workspace 信息继续从 `RuntimeScope.identity_scope` 派生，并在 resolver 边界校验；本计划不增加 Workspace 复合 pending key。

## 7. 实施阶段

### WRT-0：冻结设计与兼容面（2026-09-13 完成）

- 明确 `WorkspaceRuntime`、profile cache port、atom cache port 的最小接口；
- 确认 `WorkspaceIdentity` / `ActorIdentity` 作为 cache key 组成，而不是使用 `IdentityScope` 中的关联 ID；
- 列出所有直接实例化 cache 的生产代码、测试 fixture 和导入路径；

#### WRT-0 实施记录

本节冻结后续阶段的接口与兼容面结论，实施以本节为准。

**1. Key 与可哈希性确认**

- profile cache key 冻结为 `(WorkspaceIdentity, ActorIdentity 投影, alias)`，其中 Actor 投影沿用既有 `AgentProfileCache.key` 语义，只取 `(user_id, agent_id, team_id)` 并剔除 `session_id`（`session_id` 是兼容字段，不作为资源身份，参与 key 会造成按会话的缓存碎片化）；atom cache alias 索引冻结为 `(WorkspaceIdentity, alias) -> UUID`，`UUID -> MemoryAtom` 保持全局索引。
- `WorkspaceIdentity` / `ActorIdentity` 均为 `frozen=True` 的 pydantic 模型，已验证按字段值生成稳定 `__hash__` 与值相等，可作为 tuple key 组成；其中 `ActorIdentity` 必须先做上述投影再入 key，不能整体入 key。
- 说明：当前 `IdentityScope` 模型（W0 后）已不携带 interaction/generation 等关联 ID，只由 `actor_identity + workspace_identity` 组成。WRT-0 条目中“不使用 `IdentityScope` 中的关联 ID”按现状理解为：key 由两个身份 value object 显式组成，不将整个 `IdentityScope` 对象或任何关联坐标作为 key。

**2. 最小接口冻结**

- `WorkspaceRuntime`（WRT-1 引入，`system/runtime/workspace/`）：进程级唯一聚合，内部创建且仅创建一份 `InMemoryWorkspaceAssetStore`、`AgentProfileCache`、`KoakumaAtomCache`；对外只暴露 `asset_store`、`profile_cache_port`、`atom_cache_port` 三个窄化入口与幂等的分阶段 `shutdown()`。`shutdown()` 只清理两个派生 cache，AssetStore 的 `close_and_clear()` 仍由 `HiveMemorySystem.stop()` 在 Alice/Patchouli stop 之后显式调用；cache 清理阶段的调用时点不得早于其消费者（Alice run 链路）停止，具体挂接位置在 WRT-1 结合 §8 生命周期验收确定。其中 `asset_store` 入口与 `shutdown()` 在 WRT-1 落地；`profile_cache_port`、`atom_cache_port` 及聚合内的两个 cache 成员随 WRT-2/WRT-3 迁移分阶段引入，WRT-1 不预留无消费者的空 port。
- `ProfileCachePort`（alice runtime 侧消费）：`get(workspace_identity, actor_identity, alias)` / `store(workspace_identity, actor_identity, alias, profile)`。
- `AtomCachePort`（agent runtime 侧消费）：`ingest_atom(s)(atom(s), *, workspace_identity)`、`get_atom_by_alias(alias, *, workspace_identity)`、`get_atom_by_uuid(uuid)`（UUID 全局读取保留）、`has_alias(alias, *, workspace_identity)`、`invalidate_alias(alias, *, workspace_identity)`、`clear()`、`size`。
- 两个 cache 的实现类保留在既有模块（`agent_runtime/aliases/cache.py`、`alice/runtime/profile_resolver.py`）原位演进 key 语义，仅创建与持有关系迁移到 WorkspaceRuntime；消费方一律依赖上述 port，不 import 具体实现。

#### WRT-2 实施记录

- `AtomCachePort`（`agent_runtime/aliases/ports.py`）：仅暴露生产消费者所需的 5 个方法（`ingest_atom(s)` / `get_atom_by_alias` / `get_atom_by_uuid` / `invalidate_alias`），`workspace_identity` 为 keyword-only；`has_alias`/`clear`/`size`/命中统计保留在具体类上，不进入窄化 port。

- 测试：WRT-0 标记的 `test_same_alias_keeps_existing_global_cache_semantics` 反转为 `test_same_alias_resolves_per_workspace`；原“无分区”resolver 测试拆分为分区回填与授权重验两条；新增同分区替换、共享 UUID invalidate、无 scope 拒绝、命中统计、shutdown 清理幂等与组合根 settlement 分区刷新断言（含 isolation 分区变体：刷新写入 PendingAtom 原始分区且默认分区无条目、L2 查询坐标断言）；新增组合根对象图测试（经聚合 port 写入、Alice 侧注入引用可读同一条目）；集成 mtp/Alice 测试的 cache 预热与断言全部携带显式 Workspace 坐标。

## 8. 测试与验收标准

| 范围 | 验收条件 |
|:---|:---|
| 组合根 | System 只创建一个 WorkspaceRuntime；其内部只创建一份 AssetStore、profile cache 和 atom cache |
| Profile key | 同 Actor + 同 alias 在不同 Workspace 可缓存不同 profile；同 scope 重复解析只加载一次 |
| Profile policy | 同 Workspace 不同 Actor 的 private/team profile 不因 cache hit 绕过 owner/policy；失败结果不进入 cache |
| Atom alias | 同 alias 在不同 Workspace 可同时命中各自 atom；同 Workspace 的 alias 替换不会留下旧 UUID 反查 |
| Atom authorization | L1 命中仍执行 Workspace ownership 和 actor policy 重验；越权命中不触发 READ/RUN/citation |
| L2 回填 | 冷查询按调用方 scope 回填正确 Workspace 条目，不污染其他 Workspace 的 alias 索引 |
| Settlement refresh | Pending settlement 刷新 L1 时使用 PendingAtom 原始 scope，不能写入当前调用方或默认 Workspace |
| Pending 保持 | PendingAtom 状态、settlement、claim、cancel、evict 和事件回归测试全部保持通过；其所有权仍为 Alice |
| 生命周期 | Alice/Patchouli drain 完成前，WorkspaceRuntime 不清空仍会被读取的 cache 或 AssetStore；重复 stop 幂等 |
| 兼容边界 | 无 scope 的 cache 公共读取不存在；旧 fixture 只能通过显式 adapter 构造，并最终删除 |

## 9. 风险与待决问题

1. **Profile stale**：Workspace 分区解决错误 Workspace 命中，但不自动解决 Profile 更新后的陈旧值。需要在实施阶段决定继续使用 LRU、增加 TTL，或接入明确的 profile mutation invalidation。
2. **MemoryAtom 可变引用**：atom cache 当前返回原始 `MemoryAtom` 引用。迁移不自动改变可变性；若后续需要深冻结，应另立数据模型治理任务。
3. **缓存容量**：按 Workspace 分区后，单一全局容量与每 Workspace 配额会产生选择。第一版保持现有容量语义，新增可观测的命中/淘汰统计，再依据真实负载调整。
4. **WorkspaceIdentity 作为 key**：WorkspaceIdentity 当前是 frozen value object，W0 仍要求 `workspace_key == workspace_id`。若未来身份模型改变，必须提供稳定的 cache key 投影，不能直接拼接可变字段。
5. **文档基线冲突**：当前事实文档仍声明共享 cache 不按 Workspace 分区。该冲突在实现收尾前保持显式；不得把本 Plan 的目标设计提前写入当前事实文档。
6. **PendingAtom 后续方向**：若未来引入 Workspace 级取消、配额、恢复或持久化 ledger，应另建 Plan，重新评估 PendingAtom 的资源归属和跨系统契约，不把本次 cache 迁移当作前置承诺。
