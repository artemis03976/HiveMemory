# v0.7.2 查重与更新：先落库再合并

> 状态：Active（2026-10-31 开始实施）。设计讨论与 owner 决定见[多条提取与查重 Idea](../ideas/settlement-multi-memory-extraction-and-dedup.md)第 1、4 节，本计划的设计以该 Idea 第 5.1 节的候选设计为起点；证据见[查重 Todo](../todo/generation-dedup-decision-signal.md)。

## 1. 背景和问题

v0.7.2 的版本目标是生成质量（[ROADMAP](../ROADMAP.md#43-v072生成质量)第 4.3 节）。查重判出 UPDATE 时，草稿内容会整体覆盖已有记忆。同一项目的记忆增多后，这种情况开始发生。

Claude Code 插件接入以来，查重共判出 4 次 UPDATE，构成两条覆盖链，每条都被连续覆盖了两次。当前版本丢掉了最初记忆的主要内容：
- 一条丢掉了 E-2、E-3b、E-7 等设计决定；
- 一条丢掉了剩余工作的分析与建议。

逐条对照见 Idea 第 2.2 节。两条链都出自同一会话中先后进行的几段工作，被空闲结算拆成了不同话题。

owner 决定（2026-10-31）：

- **合并方式**：查重判定合并时，先照常把草稿落库为一条新记忆，再向生成队列提交合并任务，由 Patchouli 把两条相似的记忆融合为一条，不再整体覆盖已有记忆。这种合并接近原本为记忆生命周期安排的合并，输入是两条正式记忆。
- **不复用 Mode C**：Mode C 的输入是一条记忆加修改指令与新素材，强制它接收两条记忆，会让它失去对 UPDATE 的支持。
- **判定信号不动**：查重的判定信号暂不改动，不阻塞本计划。现行信号姑且能达成查重的目的，之后另行调研。

## 2. 目标与非目标

### 2.1 目标

1. 查重命中已有记忆时不再修改它：落在合并区间的草稿照常新建为一条记忆，并提名与命中的记忆合并。
2. 合并任务把两条相似的正式记忆合并为一条：
   - 保留较早的一条，写入它的新版本，删除被吸收的一条；
   - 任何一步失败，最多留下重复，不丢失内容。
3. 主动 WRITE 的句柄先指向新建的记忆，合并完成后改指保留下来的记忆；读到自己写入的内容这一保证，在合并前后都成立。
4. 合并写出的版本记录以 `MERGE` 为来源，能追溯到被吸收记忆的来源与版本。
5. 用合并回放 Idea 第 2.2 节的两条覆盖链，最初版本的内容得以保留。

### 2.2 非目标

- 查重的判定信号（G-2）：dense top-1 检索与固定阈值不变。
- Mode C 的行为：只改内部命名（第 5.6 节），输入、提示词与回退都不变。
- 一个话题提取多条记忆（G-1）。
- 被吸收记忆的重定向记录：不经句柄、直接按它的 alias 或 UUID 访问时得不到结果，与访问已归档的记忆相同。
- 以下三项不做：
  - Lifecycle 的定期合并扫描；
  - 合并失败后的重新提名；
  - 并发合并的重试。
- 写入意图的持久化、结算对账与句柄过期（[写入意图 Idea](../ideas/pending-intent-migration.md)）。
- 恢复此前已被整体覆盖的记忆：历史版本仍在版本记录中，本计划不自动恢复。
- 前端：任务来源的类型中已有 `MERGE`，本计划不改前端。

## 3. 当前状态（2026-10-31 核对，commit `33af7d84`）

### 3.1 查重与查重判出的 UPDATE

- **检索与判定**：生成引擎以 `title summary` 对中期库做 dense top-1 检索，候选不按类型过滤。Deduplicator 按阈值判定：
  - 大于 0.95 且内容一致：TOUCH；
  - 大于 0.95 但内容不一致：UPDATE；
  - 0.75～0.95：UPDATE；
  - 其余：CREATE。

  （[Deduplicator](../../src/hivememory/engines/generation/deduplicator.py)，阈值见 `configs/config.yaml` 的 `patchouli.generation.deduplicator`）
- **UPDATE 的写法**：`_dedup_and_resolve` 以草稿正文构造 `MergeResult`，经 `_apply_update` 覆盖已有记忆的正文；`_merge_dedup_index` 同时用草稿覆盖标题、摘要、标签与类型（[生成引擎](../../src/hivememory/engines/generation/engine.py)）。
- **提交**：Familiar 为 UPDATE 推进版本与内容时间、重置置信度，再写版本记录。版本记录的来源取 `MemoryGenerationSource.version_update_source`，恒为 `"UPDATE"`（[任务契约](../../src/hivememory/patchouli/contracts/memory_tasks.py)）。[Artifacts](../patchouli/artifacts.md) 第 2.4 节写的是"去重合并使用 `MERGE` 来源"，与代码不符。
- **WRITE 的结算**：查重判出 UPDATE 时结算为 `MERGED`，CREATE 时结算为 `CREATED`（Familiar 的 `_resolution_for`）。

### 3.2 Mode C

- `extractor.merge(old_content, metadata)` 返回 `MergeResult(new_content, changelog)`，提示词键为 `update`；标题、摘要与标签不变。
- 基础记忆由 Coordinator 在构建任务时读取，冻结进任务。
- 合并失败时：有新内容就追加，没有就保留旧正文。

### 3.3 生成任务控制面

- **任务规范**：`MemoryGenerationTaskSpec` 携带归属、发起者、话题、来源、`GenerationRequest`、交互输入，以及成对出现的 `intent_id` / `pending_alias`。来源只有 `WRITE`、`UPDATE`、`SETTLE`。
- **任务标识**：主动任务以 `active:{intent_id}` 为任务标识，其余来源用一次性标识。
- **工作信封**：codec（schema `"1.1"`）以 `model_dump` 编码整个 `GenerationRequest`，解码后重新编码比对。队列以 `topic_id` 为顺序键，并发上限为 2（`patchouli.generation.queue_max_concurrency`）。
- **终态处理**：任务成功后，Controller 发布结果中的结算；失败或取消时，为规范携带的意图发布失败或取消事件。
- **结算的发布**：`PendingAtomSettler` 对每个 pending alias 只发布一次终态，之后同一 alias 的事件一律忽略（[结算发布](../../src/hivememory/patchouli/control/pending_atom_settler.py)）。

### 3.4 写入句柄与读取

- **登记**：只接受 MATERIALIZING → SETTLED / FAILED / CANCELLED 的迁移，已结算的句柄只能转入 EXPIRED（[登记](../../src/hivememory/workspace/intents/registry.py)、[PendingAtom 模型](../../src/hivememory/core/models/pending.py)）。
- **读取视图**：读取已结算句柄时，先按结算中的 `canonical_uuid` 读取正式记忆，没有 UUID 时按 alias 读取；正式记忆不存在时，交付不带原子的重定向（[读取视图](../../src/hivememory/workspace/resolution/memory.py)）。
- **编译**：编译只单独处理 `DISCARDED`，其余分类一律按重定向编译。

### 3.5 存储与 Artifact

- **删除**：`MidTermMemoryStore.delete` 无论是否命中都发布 `delete` 变更，workspace 的读取缓存随之失效；删除即释放 alias（[MemoryLibrary](../patchouli/memory-library.md#12-中期当前可检索书库)第 1.2 节）。记忆没有"已被合并"的状态。
- **版本记录**：`MemoryVersionArtifact.update_source` 已包含 `MERGE`，`source_artifacts` 可以引用任意 Artifact；版本记录构建器接受这两项。
- **TOUCH**：经受限的 `patch_payload` 只推进访问统计。

## 5. 目标设计

本计划中，“合并”专指把两条正式记忆融合为一条；Mode C 对一条记忆的修改称为“修订”。

### 5.1 链路

```text
草稿 -> 查重（信号与阈值不变）
  ├─ 低于下限 ----------------> CREATE
  ├─ 高于上限且内容一致 ------> TOUCH
  └─ 其余命中 ----------------> MERGE：新建记忆 N，提名与命中的 M 合并（不满足合并条件时为普通 CREATE）
                                  -> 第一个任务成功，Controller 提交合并任务（M, N）
                                       -> 读取 M、N -> 模型合并 -> 版本校验 -> 写回 M 的新版本 -> 删除 N
                                       -> N 来自主动 WRITE 时，Controller 发布改指，句柄指向 M
```

| 步骤 | 位置 | 内容 |
|:---|:---|:---|
| 提名 | 生成引擎 | 查重判为 `SIMILAR` 且满足合并条件时，像 CREATE 一样构造 N，outcome 携带命中的 M |
| 新建 | Familiar | 与 CREATE 完全相同：alias、v1 版本记录、来源引用、附件提升；结果携带提名；WRITE 结算为 `CREATED` |
| 提交 | Controller | 第一个任务成功并发布结算后，按提名构造合并任务并提交；提交失败只记录 warning |
| 合并 | Familiar + 生成引擎 | Familiar 读取两条记忆，引擎以模型合并并构造 M 的新内容，Familiar 校验版本、写回 M、删除 N |
| 改指 | Controller → workspace 登记 | 合并任务成功后发布改指事件，登记把指向 N 的句柄改为指向 M |

### 5.2 查重：新建并提名合并

- **新决策**：按 owner 在阶段二审查后的修正，查重结论与提交动作分开。
  - `DuplicateDecision` 只表达查重器对草稿与最相似候选的判断，取值为 `DISTINCT`、`SIMILAR`、`IDENTICAL`，只由生成引擎消费。Deduplicator 对原来判为 UPDATE 的两种情况都改为返回 `SIMILAR`：相似度高于上限但内容不一致，以及落在两个阈值之间；原来的 CREATE、TOUCH 区间分别为 `DISTINCT`、`IDENTICAL`。查重器从不产生的 DISCARD 删除。
  - `GenerationOutcome.action` 使用 `GenerationAction` 表达 CREATE、UPDATE、TOUCH；UPDATE 用于 Mode C 修订、合并写回与手动编辑，不属于查重决策。随查重 DISCARD 一起失去生产者的 DISCARD 动作与 Familiar 的对应分支删除。
- **生成引擎的处理**：遇到 `SIMILAR` 时，按 CREATE 的规则构造 N，并检查合并条件：
  - M 与 N 的访问策略相同；
  - 两者都不是 `AGENT_PROFILE`。

  满足时，outcome 携带 M 作为合并目标；不满足时就是普通 CREATE。生成的记忆都是 PUBLIC，策略不同只会出现在经管理入口改过策略的记忆上。
- **删除覆盖路径**：`_dedup_and_resolve` 的 UPDATE 分支、`_merge_dedup_index`、`_apply_update` 的 `dedup_draft` 参数与那条 TODO 注释一并删除。
- **Familiar**：照常提交 N。`MemoryGenerationResult` 增加一个可选的合并提名，内容为 M 与 N 的 ID；N 来自主动 WRITE 时，提名同时携带这次写入的 `pending_alias` 与 `intent_id`。WRITE 的结算是 `CREATED`；`_resolution_for` 中“非 UPDATE 来源的 UPDATE 结算为 MERGED”的分支删除。
- **docstring**：Deduplicator 的类与模块 docstring 中，这一区间改写为“新建并提名合并”。

### 5.3 合并任务

- **来源**：`MemoryGenerationSource` 增加 `MERGE`，`version_update_source` 对 `MERGE` 返回 `"MERGE"`、其余来源仍返回 `"UPDATE"`；任务快照与 `memory.task.*` 事件随之出现 `MERGE`，前端类型已包含这一值。
- **规范**：
  - 由 Controller 在第一个任务成功、发布完结算之后构造：沿用第一个任务的归属、发起者与话题；
  - `GenerationRequest` 增加 `merge_focus`，携带保留与吸收两条记忆的 ID，以及可选的改指对象（`pending_alias`、`intent_id`）；
  - 没有交互输入，`intent_id` / `pending_alias` 为空：合并任务不持有任何写入意图的终态，任务失败或取消时不发布句柄事件；
  - 任务标识是一次性的。

  工作信封继续以 `model_dump` 编码请求，`merge_focus` 只含字符串，不需要额外的类型恢复。
- **提交失败**：队列已停止或容量不足时，Controller 记录 warning，两条记忆都保留。关闭排空不等待合并任务；尚未执行的合并任务在关闭时丢失，结果同样是两条都保留。
- **执行**（Familiar 的合并路径）：
  1. 以发起者的可见性读取 M 与 N，再次检查合并条件；
  2. 生成引擎调用模型合并，构造 M 的新内容（第 5.4 节）。按 owner 在阶段二的判断，模型融合两条记忆的结果不会与 M 完全相同，因此不设“结果与 M 一致时跳过写回”的分支，每次合并都产生 M 的新版本；
  3. 写回前按复合键重新读取两者，确认都还存在且版本未变，然后提交 M：
     - 按内容修订的现行规则推进版本、内容时间、衰减基准，重置置信度；
     - 写版本记录：来源 `MERGE`，`changelog` 为模型给出的变更说明，`source_artifacts` 包含 N 的来源引用与 N 的版本记录引用；
     - 追加 VERSIONED 事件；把 N 的交互来源引用并入 M 的来源引用；
     - 向量输入文本变化时重算向量，然后写回；
  4. 删除 N；
  5. 返回带改指信息的结果。
- **先写 M 再删 N**：删除失败时 N 作为重复留下，M 已包含它的内容；N 的完整内容始终保存在它自己的 v1 版本记录中。
- **失败**：以下情况以结构化错误让任务失败，两条记忆都保留，不回退为追加或覆盖：
  - 任一记忆缺失或不可见、合并条件不再满足、写回前版本已变；
  - 模型输出无法解析；
  - 提供商失败（重试一次后仍失败，原样传播 `ModelProviderError`）。

  新增 `MemoryMergeAbortedError`（`workspace.memory.merge_aborted`），以 `details.reason` 区分 `memory_missing`、`not_mergeable`、`version_changed`、`model_output_invalid`。版本检查与写回之间的竞态不在保证范围内，与 alias 唯一性的“检查→写入”相同（ADR-0002：有证据再加保护）。
- **来源记录**：M 的来源主体字段不变，贡献者取 M 与 N 的并集。访问统计保留 M 自己的值。

### 5.4 合并提示词与输出

- **提示词**：新增生成提示词 `merge`（中英文各一份），输入两条记忆的标题、摘要、标签、类型与正文，并标明哪一条较新。要求如下：
  - 两条记忆描述同一件事，或同一工作的不同阶段；保留两边仍然有效的内容；状态、结论或进度冲突时以较新的为准，并保留被取代的决定曾经存在的事实；
  - 不整体替换任何一方；
  - 标题与摘要覆盖合并后的全部要点，因为检索只编译标题、类型、标签与摘要；
  - 敏感信息的规则与其他生成提示词相同。
- **输出**：JSON，字段为 `title`、`summary`、`tags`、`memory_type`、`content`、`changelog`，解析为新的 `MergeResult`。
  - 越界长度按草稿的规则截断；
  - 未知类型保留 M 的类型；
  - alias 不由模型给出，保持 M 的 alias。
- **调用方式**：抽取器新增合并方法，经同一 LLM 服务与 `shared.llm.librarian` 参数调用。失败语义与提取相同：只对提供商失败重试一次；模型输出为空或无法解析时返回 `None`，由 Familiar 转为 `model_output_invalid`。
- **NoOp 抽取器**：合并方法返回 `None`，合并任务因此失败，两条记忆保留。

### 5.5 写入句柄的改指

- **事件**：新增全局事件 `patchouli.events.pending_atom.merged`，由 PatchouliBridge 从同名本地事件转发。载荷是一份结算与被吸收记忆的 UUID：
  - 结算沿用原 `pending_alias` 与 `intent_id`，分类为 `MERGED`，正式身份为 M；
  - 被吸收记忆的 UUID 即 N 的 UUID。
- **登记**：订阅这一事件。只有同时满足以下条件时，才用新结算替换旧结算：
  - 句柄的 `intent_id` 匹配；
  - 句柄状态为 SETTLED，旧结算分类为 `CREATED`；
  - 旧结算的 `canonical_uuid` 等于被吸收记忆的 UUID。

  其余情况忽略。替换不是状态迁移，SETTLED 只能转入 EXPIRED 的规则不变。
- **发布**：`PendingAtomSettler` 增加改指发布，不占用“每个 alias 只发布一次终态”的保留。发布失败只记录 warning，不降级为失败事件，因为这次写入已经成功落库。
- **读取**：沿用现有的重定向读取与提示文案，读取句柄因此跟随到 M。改指事件到达之前，N 已经删除的短暂窗口内，读取得到不带原子的重定向。
- **`MERGED` 的含义**：从“查重判出 UPDATE”改为“新建后被合并”，枚举注释随之改写。

### 5.6 命名

- **Mode C 改名**：`extractor.merge` 改为 `revise`，`MergeResult` 改为 `RevisionResult`，`MergeResult` 这个名字让给第 5.4 节的合并输出。Mode C 的提示词键仍为 `update`，生成引擎中的局部变量与日志随之改名。理由是同一个词不表示两个概念（AGENTS.md 第 1.2 节）。
- **事件、错误与决策的名称**：如上文，在计划评审时可以调整（第 10.2 节）。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|

## 10. 风险与待决问题

### 10.1 风险

- **误判的合并**：判定信号不变，误判的两条无关记忆也会被合并。离线复现中，无关对余弦的 p99 为 0.655，低于合并下限 0.75；已观察到的 4 次命中都是同一工作的前后阶段。误判只能经版本记录与人工编辑纠正。
- **合并后的记忆越来越长**：同一工作的各阶段不断并入一条记忆，正文持续变长，摘要难以覆盖全部要点；正文过长时，合并提示词可能超出模型窗口，任务失败，两条记忆都保留。
- **改指事件丢失**：改指与结算事件属于同一可靠性等级，没有补偿；丢失时句柄指向已删除的 N，读取得到不带原子的重定向。
- **同一条 M 上的并发合并**：生成队列并发为 2，两个话题同时结算并命中同一条 M 时，后写回的一方版本冲突失败，留下重复。
- **短暂的重复**：新建到合并完成之间，检索与前端会同时看到 M 与 N。
- **调用成本**：每次合并多一次 Librarian 调用，与 chat 共用提供商配额；限流时合并任务失败，两条记忆保留。
- **多条提取落地之后**：一次结算的多条草稿可能命中同一条记忆，并发合并的冲突会更常见。

### 10.2 待决问题

没有阻塞问题。以下候选细节在计划评审时确认：

- 名称：查重判断 `SIMILAR`、事件 `patchouli.events.pending_atom.merged`、错误 `MemoryMergeAbortedError`；Mode C 改名为 `revise` / `RevisionResult`（第 5.6 节）。
- 改指的方式：以独立事件替换结算（第 5.5 节）。另一种做法是复用结算事件，同时放宽登记与结算发布的“一次终态”规则；Idea 第 5.1 节的候选设计没有区分这两种做法。

另外记录一项不在本计划处理的发现：前端任务来源的类型没有 `SETTLE`，未知来源会显示为 `WRITE`，所以结算任务在前端显示成了写入。
