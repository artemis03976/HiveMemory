# v0.7.0 A1：Workspace 访问边界与授权

本文把已有 WRX-0/1 的边界决定收敛为一个可以独立实施和验收的计划。它解决的不是再造一个 IAM 平台，而是在 Actor 与 Workspace 的交互边界建立统一安全网关：先判断调用者能否代表某用户/Agent 进入 Workspace，再判断 operation，最后由资源 owner 和领域 application 判断具体资源是否可见、是否允许本次业务操作。

## 1. 目标、非目标与依赖

目标是交付 `CallerPrincipal`、`WorkspaceAccessContext`、Workspace admission、operation grant、四阶段检查、错误分类和跨 System/Alice/外部 adapter 的可信传播。A1 不复制 Patchouli 业务 API，不实现 cache、Session、Pending、外部 wire 或完整认证。本计划冻结访问规则、operation 定义/绑定方式和已存在路由的基线清单，以真实现有 application 验证。后续领域计划自行增加其 operation、绑定方法并验证资源 policy，不要求 A1 预先穷尽尚未设计的 API；最终生产消费者切换另行验收。

WRX-0 的资源矩阵、入口清单和兼容证据继续作为现状依据；A1 不重新调查已经冻结的事实，只补齐其未覆盖的公开入口和行为验收。

代码入口是 `workspace/access.py`、System application services、AliceBridge、PatchouliBridge 与 `patchouli/application/`。既有 access 工厂、operation 枚举、Memory/Profile 快照和任务 `identity_scope/submitted_by` 成果见[WRX-0 第 7/8 节](./v0.7.0-plan-a-wrx0-boundary-freeze.md#8-开放决定的关闭状态)。实施时只核对新签名与尚未消费 access 的路径，不因拆分重建这些模型。

## 2. 访问上下文

四个概念必须分开：

| 概念 | 语义 | 不能由请求体自行决定 |
|:---|:---|:---|
| `CallerPrincipal` | 哪个受信进程、connector、安装实例或本地调用方正在发起请求 | principal 身份和可代表关系 |
| `ActorIdentity` | principal 代表哪个用户和可选 Agent | 用户/Agent 代表关系 |
| `WorkspaceIdentity` | 目标资源归属域 | 是否能进入该 Workspace |
| `IdentityScope` | 已验证的 Actor + Workspace 坐标 | 授权结果、当前 Workspace、Session、run/frame |

`WorkspaceAccessContext` 至少包含受信 principal、已验证 scope、请求 operation 和有限生命周期的 grant。grant 不写入 Profile/Atom cache，不能由 cache 命中替代重新检查。请求 DTO 若携带 scope，只能作为一致性校验，不能覆盖 context；Session、source、agent_id、owner、team_id 和 `system` 只能是待验证 claim。

System service、AliceBridge 和 GlobalSystemBus 必须透传完整 context，不能只取出 `identity_scope`。Patchouli application 用同一个校验函数确认 context 来自受控工厂、operation 与方法匹配后，再向 local bus 派生 scope；这不等于向网关重复申请 admission。访问边界不接收任意 action 代为执行业务，也不承担总线路由职责。受控工厂约束可信进程内调用纪律，不宣称能隔离任意进程内恶意代码。

## 3. 四阶段检查

```text
受信入口建立 CallerPrincipal
  -> Workspace admission：principal 是否能代表该用户/Agent 进入该 Workspace
  -> Operation authorization：该主体能执行哪些 operation
  -> Resource ownership / visibility：目标资源属于谁、当前是否可见
  -> Domain policy：本领域允许本次读取、提交、修订或观察吗
```

前两阶段由 A1 边界完成，后两阶段由 Patchouli 或 WorkspaceAsset 的 application 完成；四阶段不意味着四层 service 转发。管理员可以没有具体 Agent，但仍要验证 user + Workspace；Alice 不能仅因是本地进程就任意声明 user/Agent。W0 owner hard boundary 继续有效，未来成员/委托模型必须另行扩展，不从请求字段放宽。

以 WRX-0/1 已有公开方法为首版授权基线，operation 至少覆盖：`resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit`、`memory_intent.submit`、`task.observe` 和明确的管理 operation。每个 operation 写清不能推出的权限；例如 interaction.submit 不授予 search，task.observe 不授予 Pending 内容、cancel 或 canonical Memory 读取。

管理用户的兼容坐标可由受信入口构造为 `(user_id, SYSTEM_AGENT_ID, workspace)`，权限来自管理 grant。Profile 的管理写入若复用 Memory 管理 operation，应沿用并说明 WRX-0 已冻结的 AGENT_PROFILE atom 语义；其他 Topic/Asset/Task 管理不能因名称相似而全部借用 `management.memory`。新增 operation 的登记必须包含名称、允许主体、不能推出的权限、application 方法绑定、资源 policy 与拒绝阶段；未登记或未绑定的方法默认拒绝。Pending、Topic、usage 等具体扩展由引入它们的领域计划维护并验收，不成为本计划基线关闭条件。

## 4. MemoryAccessPolicy 的使用边界

`PRIVATE`、`TEAM`、`PUBLIC` 可作为 Workspace 内资源读取 policy 的共同词汇：PUBLIC 只表示已进入该 Workspace 且通过 operation 检查的 Actor 可见；PRIVATE 只对目标 Actor；TEAM 依赖可信团队关系。它们不表示互联网公开，也不自动授予 write/update/delete/admin/cancel。

Profile、Asset、Task 可以复用“可见性”概念，但不强行复制 Memory 的字段或状态机。Workspace owner、resource ownership、Actor visibility、operation grant 和 domain mutation policy 必须分别测试。先命中 cache 再授权、知道 UUID 就可读取、使用 system 标记绕过 owner 都是错误。

## 5. 实施切片与验收

| 阶段 | 产出 | 完成条件 |
|:---|:---|:---|
| A1-0 | 核对 WRX-0/1 证据，固定已有路由的授权基线与剩余访问缺口 | 不重做既有快照/错误工作，不把旧 port 测试当作全链完成 |
| A1-1 | access context、operation 目录、主体验证、失败语义 | 裸 scope、伪造 grant、错误 operation、冲突 scope、跨 Workspace 均 fail closed |
| A1-2 | System service、AliceBridge、GlobalSystemBus、Patchouli application 的传播和重验 | 真实总线协作中 context 不丢、不被 DTO 覆盖，也不重复签发 |
| A1-3 | 基线 operation 绑定、现有任务归属投影及新增 operation 的登记约束 | 基线每个入口都有四阶段检查；未知/未绑定 operation 拒绝；后续新增模型无需重开 A1 |

测试使用真实 application/bridge 和当前已存在的输入模型，覆盖管理员读、普通 Actor search、现有 interaction/主动意图路由、PRIVATE/TEAM/PUBLIC、task ID 越权和延迟提交。以中立调用方证明不要求 Alice 运行，但不等待新的 Segment、共享 Pending 或外部 wire。缓存新鲜度、新模型身份隔离及具体领域权限随各自引入计划验收；这些扩展不计入 A1 未完成项。

## 6. 迁移、回滚与文档

内部受信旧入口可以在明确窗口内委托 A1，但最终不能保留无 grant 的公共成功路径。A1 失败时可恢复受信 adapter 的兼容调用，不开放裸 scope，也不删除已接纳领域工作。A1 的实际结果晋升到 frontmatter 所列事实文档必须等待 A 系列实现、测试和审查收尾；未冻结的成员目录、远程认证和跨 Workspace 委托留在后续计划。

| A1-1/3 前需核对的决定 | 最小要求 |
|:---|:---|
| grant 生命周期 | 即时请求、延迟 flush 和后台接纳各自说明授权校验时点；已接纳工作不把旧 grant 当成后续任意调用权限 |
| 资源及结果错误 | scope 冲突与输入错误按现有 error envelope；不可见/不存在遵循领域防泄漏规则，不返回受保护元数据 |
| 任务与提交归属 | interaction、intent、task 的权威记录能关联 Workspace 与提交 principal/Actor；无归属时拒绝，不能从 ID 猜测 |
| 查询和取消 | observe、Pending 内容读、canonical 读、cancel 分开；如公开 wait，冻结等待上限与 shutdown 行为 |
| 最小观测 | 记录 operation、关联 ID、安全的 scope 投影与拒绝阶段；不记录凭据或原始敏感内容 |

上述表只跟踪访问基线差额和扩展规则。具体领域的内容可见范围、输入模型、外部认证材料与序列化由对应领域或协议计划决定；本计划不以这些后续约定作为自身实施和验收前置。基线清单与真实授权证据完成后即可独立关闭，事实文档晋升仍遵守版本稳定收尾门禁。
