# v0.7.0 A1：Workspace 访问边界与授权

本文定义 Actor 如何被系统识别、进入 Workspace，以及进入后如何取得行为权限和资源权限。System 提供一个统一的 Actor Authentication 网关，内部完成 Principal authentication 和 Workspace authentication；两项均通过后返回可信访问上下文。Actor 执行动作时，再检查其在此 Workspace 的行为白名单，并由资源 owner 检查具体资源权限。

2026-09-19 修订：本节及下文替代初稿和 WRX-0 中“principal 建立前置，再执行 admission / operation / resource / domain 四次检查”的划分。此前的 `Domain operation policy` 与 `Operation authorization` 合并为同一项行为授权，不再作为独立的第五层。两项认证收敛到同一系统网关，认证上下文与单次 operation 解耦；第 7 节逐项记录既有约束的承接。这是目标设计修订，不表示现有代码或旧验收记录已符合新规则。

同日所有权补充：基于 `ebce0f15` 的重新实现，进一步收敛 context 与 guard 的责任。`CallerPrincipal` 留在 `system/access`；`WorkspaceAccessContext` 归 Workspace，只持有已准入的 `IdentityScope`。签发跟踪、有效期和逐次行为检查统一由 Workspace guard 负责，删除 grant、独立有效期锚点、签发工厂与凭据自检协议。Patchouli 不重复承载调用来源，继续使用自身已有的来源记录。下文为本轮实施依据，A1 整体验收与 A6 生产消费者切换仍需各自收口。

## 1. 目标、非目标与依赖

目标是交付统一 Actor Authentication 网关、系统接入登记与 Workspace Actor 访问注册表、可信 `WorkspaceAccessContext`、公共 application 使用的统一行为检查，以及资源 owner 检查的调用约定。网关统一完成来源认证、身份解析和 Workspace 准入；System/Alice/外部 adapter 使用同一认证入口及业务链路。A1 使用已存在的 API 验证完整链路；后续领域计划增加自己的 operation、方法绑定和资源规则。

A1 不复制 Patchouli 业务 API，不实现 cache、Session、Pending 或新业务路由，不建设远程凭据协议、通用 IAM、角色继承、成员管理 UI 或注册表管理 API。首版采用明确的本地配置和独立组合验证；计划 B 实现具体外部协议与接入适配，A6 负责稳定生产装配。系统接入注册与 Workspace 行为白名单本身属于 A1 的必要内容，不能整体推迟到 B。

WRX-0 的资源矩阵、入口和兼容证据继续作为历史调查基线；其旧授权顺序不再是实施依据。第 1.1 节保留撤销时的历史起点，第 1.2 节与第 2.4 节描述重新实现后的调整目标。快照、版本和任务 `identity_scope` 成果继续复用，不重建数据模型。

历史起点中的 `LocalTrustedAdmissionService` 用 `principal_id → operations` 同时承担接入与操作许可，再以 Actor user 等于 Workspace owner 代替 Workspace 准入。重新实现已引入统一网关与两类登记，本轮进一步解决准入结果与校验责任被拆散的问题：System 网关统一编排两项认证，接入登记归 System，准入结果、有效性管理及行为白名单归 Workspace。配置所有权不同不要求拆成两个对外认证入口。operation 的定义目录也不等于某个 Actor 已获准的行为集合。

### 1.2 基于现有分层的实现落点

以下只冻结责任与依赖方向，不要求按每个概念新增一套 service、provider 或 DTO：

- **System 接入层**：`system/access` 持有 `CallerPrincipal`、接入注册表与 `ActorAuthenticationGateway`。网关完成来源检查后，调用注入的 Workspace guard 的内部准入方法；首版通过构造注入即可独立验证。现有 `ProviderRegistry` / `ModelRegistry` 管理 LLM 凭证与模型，不能充当 Actor 接入注册表；本认证网关也不属于负责对话分析的 Gateway 子系统。
- **Workspace 访问基础设施**：`workspace/access.py` 持有最小 `WorkspaceAccessContext`、操作枚举与 `WorkspaceAccessGuard`，后者统一负责内部准入、签发状态及公共行为检查；`workspace/registry.py` 持有准入与行为白名单。不增加第二套认证 service、凭据自检协议或配置对象绑定层。
- **`patchouli/application/` 与各资源公共入口**：在既有方法中消费 context、执行统一行为检查，随后保留各资源 owner 的授权与 local bus 领域处理。`access_consumption.py` 是已有的接入位置，不再包一层 Workspace 业务 service。
- **System application 与桥接**：补齐缺少的 access 参数和传播，并验证错误不被包装成服务不可用；AliceBridge/GlobalSystemBus 已支持的通用参数透传继续复用。System 调用 Patchouli 的管理门面与其他 Actor 一样，在资源 application 落实最终行为检查。
- **server、Alice/MTP、Passive 与生产组合根**：A1 使用显式配置和中立调用侧验证入口与传播能力；A6 再切换真实生产消费者并删除已登记的旧兼容入口。具体外部协议由 B 转换后进入同一网关。

因此 A1 需要新增认证与权限配置能力，修改已有访问检查和调用签名；不重建业务总线、资源 provider 或 Patchouli application 分类。

## 2. 身份、注册表与访问上下文

### 2.1 身份坐标

| 概念 | 回答的问题 | 建立方式 |
|:---|:---|:---|
| `CallerPrincipal` | 本次请求来自哪个已注册的调用来源 | 统一网关根据启用的接入登记和对应 adapter 的受信接入信息确认 |
| `ActorIdentity` | 本次操作由哪个用户和 Agent 执行 | 统一网关使用登记的 adapter 身份解析规则确认；消息作者只是 provenance |
| `WorkspaceIdentity` | 本次请求访问哪个资源归属域 | 解析目标并核对 Workspace 登记，不接受请求体改写 owner |
| `IdentityScope` | 本次访问冻结的 Actor + Workspace 坐标 | Workspace guard 在网关内部准入步骤构造；不承载来源信息或行为白名单 |

同一个 principal 可以通过既定接入方式服务多个 Actor；同一个 Actor 也可以通过多个已登记入口访问。Workspace 权限以 Actor 与 Workspace 为依据，不因换成 Alice、System 或外部 adapter 而扩大。A1 不新增一套 principal 委托权限模型；同时，Actor 身份必须由受信入口解析，不能把未经验证的 body/header、`system` 或消息说话者直接当作认证结果。

### 2.2 两类注册配置及其所有者

| 配置 | 负责方 | 最小内容 | 不承担的职责 |
|:---|:---|:---|:---|
| 系统 Actor 接入注册表 | System | 稳定调用来源标识、是否启用、连接/接收方式、可用 adapter 及身份解析规则 | 不以 principal 配置授予 Workspace operation |
| Workspace Actor 访问注册表 | Workspace 访问基础设施，由 System 装载配置 | Workspace 坐标、Actor 键、是否允许进入、`allowed_operations` | 不保存 Memory 可见性，不执行 Patchouli 业务 |

“已注册”要求该请求能够匹配启用的接入登记及相应 adapter，仅凭一个与配置同名的请求字段不能通过。Alice 和本地管理入口也有显式的内置接入登记，无需模拟远程连接；具体外部凭据与协议转换由 B 提供。

Workspace 注册表中，一条访问记录即可同时承载准入状态和行为白名单，不强制拆成两个 store。记录存在且启用表示该 Actor 可以进入；`allowed_operations` 是进入后的行为上限，允许为空。空集合代表可进入但未获准执行资源操作，不应被误报为身份认证失败。

首版键使用完整 Workspace 归属坐标（至少 `owner_user_id + workspace_id`）与 Actor 的 `user_id + agent_id`；不能只用非全局唯一的 workspace key、principal 或 agent_id。`session_id`、run/frame 和调用协议不进入权限键。`team_id` 由可信身份关系提供给资源 policy，不能靠请求声明获得团队权限。

Workspace 访问注册表由 `workspace/` 中的 guard 持有和查询，供内部准入与公共行为检查共用；System 网关只依赖该 guard，不直接持有 Workspace 配置。System 接入注册表由 System 持有。System composition 负责装载配置，将同一个 guard 注入网关与资源 application；System 网关负责运行期认证编排，不能将“composition 只装配”扩展为整个 System 不承担认证。注册表不属于 Alice、Agent Profile、资源 cache 或 Patchouli store；不为每个 Workspace 创建 Runtime，也不等待 A2 的 Runtime 装配。首版采用进程内不可变本地配置，配置修改经重启生效；不要求实现热更新、持久化数据库或管理 API。

首版继续保留 W0 的 `actor.user_id == workspace.owner_user_id` 约束，但还要检查该 Workspace 的 Actor 访问记录。相同 owner 不表示其所有 Agent 自动获准进入；跨 owner 成员模型仍不在 A1 中。管理员兼容坐标 `(user_id, SYSTEM_AGENT_ID)` 也需有相应登记，不能因 `system` 标记自动放行。

### 2.3 operation 目录与行为白名单的区别

操作定义目录表达“系统有哪些操作、哪个 application 方法需要哪个操作”，以当前 `workspace/access.py` 中的 `WorkspaceOperation` 和 application 方法内绑定为起点补齐。Workspace Actor 访问注册表表达“这个 Actor 在这个 Workspace 被配置允许哪些操作”。前者是代码契约，后者是授权配置，必须分开；这里的“目录”不要求新增独立的目录模型或路由框架。

例如，同一用户的 Actor `researcher` 在 Workspace `notes` 中可配置 `{resource.search, resource.read, memory_intent.submit}`，在 `archive` 中可配置 `{resource.read}`；Actor `reviewer` 即使通过同一 principal 接入，也按自己的记录取得权限。未知 operation、未知 Actor、未登记 Workspace 及缺失访问记录均默认拒绝；新增 operation 不自动加入已有白名单。

### 2.4 访问上下文及受控构造

`WorkspaceAccessContext` 归属 `workspace/access.py`，只公开不可变的 `identity_scope`。它回答“哪个 Actor 已通过认证进入哪个 Workspace”，不携带 `CallerPrincipal`、访问记录对象、行为白名单或单次 operation。它仍是有实际有效性约束的准入结果，不能将所有公共 API 简化为接受任意裸 `IdentityScope`。

历史 `operation` 字段和“为每个 operation 重新申请 context”的签名退出目标契约。实际需要的 operation 由 application 方法绑定，在调用共享行为检查时传入。同一有效 context 可以先后执行不同的获准操作，不能因换了操作就重建 Actor 身份，也不能因一次操作成功而获得其他权限。

删除 `_AccessGrant`、`AccessContextValidity`、独立 `issue_access_context` 工厂、`IssuedWorkspaceAccess` 协议和 context 自检方法，并移除 `system/access/credentials.py`。`WorkspaceAccessGuard` 在内部准入成功后构造 context，私有弱引用表按对象身份记录签发及到期时间；context 本身不保存第二份身份或权限数据。直接构造、复制、序列化重建或替换 scope 所得的新对象不继承准入，另一个 guard 即使复用同一条配置对象也不能接受它。无引用的 context 自动释放，关闭时清空签发跟踪，不建立持久化凭据平台。该约束维护可信进程内调用纪律，不宣称隔离任意进程内恶意 Python 代码。

每次行为检查先确认本实例签发和生命周期，再根据 context 的完整坐标查询 Workspace Actor 注册表。配置记录的对象地址不作为凭据有效性的依据，白名单也不固化到 context；检查通过返回可信 `IdentityScope` 供 application 使用。准入、生命周期和行为授权属于同一 guard，System 与 Patchouli 均依赖 Workspace；Workspace 和 Patchouli 的访问类型注解也不得反向导入 `system/access`。

请求 DTO 若携带 scope，只能作一致性校验，不能覆盖 context。Profile/Atom cache 不保存 context、行为白名单或可复用授权结论。System service、AliceBridge 和 GlobalSystemBus 原样透传完整 context；Patchouli application 完成公共边界检查后，才向 local bus 派生内部 scope。

Patchouli 不重复承载调用来源：`CallerPrincipal` 只在 System 网关完成接入认证，认证成功后不进入 Workspace context，也不进入 Patchouli 提交 API。交互和生成链沿用 Patchouli 既有的内部来源记录；`WorkspaceAccessContext.identity_scope` 只提供 Actor/Workspace 授权坐标。

## 3. 两次身份认证与两类运行时授权

```text
统一 Actor Authentication 网关（System；唯一对外认证入口）
  1. Principal authentication
     匹配接入登记与 adapter，确认 CallerPrincipal 和 ActorIdentity
        |
  2. Workspace authentication / admission
     委托 Workspace guard 核对 Actor 准入记录并登记准入结果
        |
  两项均通过 → 返回 WorkspaceAccessContext
        |
   Actor 已进入 Workspace；每次 API 动作仍须通过以下两类授权
        |
3. Operation authorization（公共 application 调用统一检查）
   按实际方法确定 operation，检查该 Actor 在此 Workspace 的行为白名单
        |
4. Resource authorization（resource owner）
   检查具体资源的归属、可见性及资源自身访问规则
        |
   执行领域处理，产生结果或领域状态错误
```

前两项回答身份与准入问题，后两项回答“Actor 能做什么”和“资源允不允许用”。本计划将此前 `Domain operation policy` 的权限职责统一归入第三项；资源状态、输入有效性、版本冲突、生成是否接纳等仍是正常领域处理，不再设立另一层重复的行为授权。

### 3.1 统一认证网关的入口与职责

所有调用侧只调用一个 Actor Authentication 网关：输入受信接入信息、待解析的 Actor 身份和目标 Workspace；网关内部完成两项认证，全部成功后返回一个 `WorkspaceAccessContext`。认证入口不要求提供待执行的 operation，也不向调用方返回“只完成第一项认证”的可访问上下文。

网关由 System 接入层提供。adapter 负责协议解析、接入证据及其特定身份映射，网关负责按登记规则统一验证并作出认证结论。历史 `LocalTrustedAdmissionService` 和 `WorkspaceAdmissionPort` 中可复用的坐标校验移入内部准入检查，principal→operations 的旧授权方式退出。`WorkspaceAccessBoundary` 是原计划对访问边界的称呼，不应写成当前已有且可直接接入的网关实现；不要求为两项检查各建一层 service 或在现有实现外再包业务转发层。

网关统一流程不改变数据所有权：它查询 System 接入登记，再调用同一 `WorkspaceAccessGuard._admit(actor, workspace)` 完成内部准入。`_admit` 不暴露给 adapter，不是第二个对外认证入口；只有 System 网关先通过来源认证后才调用。网关不执行 search/read/submit，不接受任意 action 代执行业务，也不替代全局总线路由。认证成功后，调用侧沿既有 adapter/service/bridge 发起业务调用。

### 3.2 行为授权的承载对象与调用位置

**Workspace Actor 访问注册表是行为权限的权威来源；Workspace 访问基础设施提供共享行为检查；公共 application 是每次业务动作的强制检查点。** 这些职责可以复用 `access.py` 和现有 access-consumption helper，不要求新建一层转发 service。Patchouli 只依赖中立的 context 与行为检查能力，不反向依赖 System 认证网关的实现，也不在每次动作中重新执行两项认证。

进入 Workspace 时只确认访问记录存在且启用，空白名单也可获得 context；进入成功不代表后续任意动作已获授权。公共 application 在资源读取或业务副作用之前调用 `authorize_operation(access, operation)`：确认 context 是本 guard 实际签发且仍有效，从有效注册配置取出该 Actor 的记录，确认包含方法所需 operation，返回可信 scope。请求体不能自行决定方法所需权限，认证结果也不能替代动作授权。

同一有效 context 的透传或复用不要求各层重复认证或重新签发。调用侧可以提前检测未许可动作，但最终检查不能只存在于 adapter，否则不同入口会得到不同权限。切换 Actor/Workspace 或 context 失效后，调用侧才重新经过统一网关；不能在 application 内自行修补身份并继续执行。

公共 API 授权后按原业务链调用 local bus。内部查询和生成步骤由该公开操作的领域实现负责，不把每一次内部方法调用变成新的 Actor API；另一次独立的公开 API 调用则必须执行自己的授权检查。

### 3.3 统一业务链路

```text
System / Alice / 外部 adapter
  -> 统一 Actor Authentication 网关
       -> Principal authentication
       -> Workspace authentication / admission
       -> 返回可在有效期内复用的 WorkspaceAccessContext
  -> 调用侧封装 → 同一 GlobalSystemBus 公开路由
  -> Patchouli application
       -> 共享访问检查：context + 方法 operation + Workspace Actor 行为白名单
       -> resource owner：该资源的权限检查
       -> 原有 local bus / 领域处理
```

WorkspaceAsset 等不属于 Patchouli 的资源在自己的公共入口调用同一行为检查，再执行自己的资源规则。访问边界不接收任意 action 代执行业务，也不查找资源或取代总线路由。三类 adapter 的差异限于接入、触发和协议呈现，不能各自维护一份业务授权规则。

已接纳操作中的 canonical mutation、同步 cache invalidation 及相关内部失效通知不重新经过 Actor 认证网关，也不要求伪造管理 Actor。它们依照已授权领域工作的内部契约执行；此规则仅适用于可信内部协作，不能使外部请求直接调用内部入口或免除独立公共 API 的授权。

### 3.4 生命周期、拒绝与观测

- 首版 context 仅在其签发的运行实例及认证有效区间内复用，不持久化为跨重启凭据。`context_ttl_seconds` 与单调时钟统一注入 Workspace guard，避免签发和校验使用不同时间源；`None` 表示不设固定 TTL。System 网关 `close()` 委托同一 guard 关闭，拒绝既有 context 和新认证。有效区间最长不超过运行实例生命周期；接入可选择更短范围，但不因 operation 不同而强制重新认证。切换 Actor/Workspace 必须重新认证。A6 在生产 shutdown 中落实网关关闭时机，不能提前中断已授权领域工作的 drain。
- 首版本地配置在运行实例内不可变，修改通过重启生效。若实现配置重载，须同时冻结旧 context 的失效机制，并让调用侧经网关重新认证；不得继续使用旧白名单或把热更新无条件视为已支持。缓存命中和会话持续时间不能代替每次动作的授权。
- 延迟 flush 在真正提交时检查 context 有效性并执行行为授权；context 仍有效可复用，已失效则经统一网关重新认证。不沿用早期消息到达时某个 operation 的允许结论。领域队列接纳后，任务依照已授权提交范围继续执行，不因 Actor 离开而删除或改判失败；查询、取消和新资源请求各自重新授权。
- `observe`、Pending 内容读、canonical Memory 读和 `cancel` 分开授权。若公开 `wait`，必须冻结等待上限、超时结果及 shutdown 时的结束行为，并验证不因等待而扩大可见范围；此要求不意味着 A1 必须新增公开 wait 路由。
- 接入未登记/禁用/adapter 不匹配是第一层失败；Workspace 无有效 Actor 记录是准入失败；缺少行为许可是 `OperationDeniedError`。实现须通过稳定错误类型或 reason 区分阶段，复用既有 error envelope，不强制另造整套错误模型。
- context 缺失、伪造、过期或实例关闭使用 `ScopeRequiredError`；未登记签发对象为 `context_not_issued`，到期为 `context_expired`，关闭为 `authentication_gateway_closed`。请求 scope 冲突仍使用 `WorkspaceMismatchError`。资源不可见与不存在按该资源的防泄漏规则呈现。访问错误必须沿 System/application 传播，不能被通用 `RuntimeError` 捕获包装成服务不可用。
- principal 标识只在 System/adapter 认证和诊断范围内使用；Workspace/资源侧记录 Actor/Workspace 安全投影、operation、关联 ID 与拒绝阶段。Patchouli 领域提交沿用已有内部来源记录，不从 context 或公开 API 重复派生来源字段；不记录接入凭据和原始对话。删除只写入旧 grant 且无消费者的 `issued_by` 配置，不能把签发器标签当作请求来源。

## 4. 行为目录与资源授权规则

### 4.1 既有 operation 的绑定基线

以 WRX-0/1 已有公开方法为基线，维护 `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit`、`memory_intent.submit`、`task.observe` 和明确的管理 operation。定义目录记录名称、业务语义、application 方法绑定、不能推出的权限及负责资源规则的组件；历史 `trusted_principals` 中的来源级操作集合须迁移，实际授权名单只在 Workspace Actor 访问注册表中维护。

第 1.1 节历史基线中的枚举含上述七项和 `management.memory`、`management.task`；重新实现已补充 Topic 管理的 `management.topic` 和附件上传的 `management.asset`，`asset.acquire` 不能自动授权上传。枚举存在不表示整个入口已验收，附件 scope 问题仍按第 5.1 节单独追踪。A1 逐项核对 `PatchouliBridge` 挂载的方法及 Asset 公共入口，维护最小权限绑定与兼容清单，不改变 Topic/Asset 业务模型。A2–A5 引入的新方法由各自计划补充绑定，不能反过来成为 A1 完成的前置条件。

不同 operation 互不隐含：`resource.read` 不授予主动写入或管理写入，`interaction.submit` 不授予检索，`task.observe` 不授予取消、Pending 内容或 canonical Memory 读取。方法必须绑定所需 operation，未知 operation 和未绑定公共方法默认拒绝。新方法引入方同步维护目录、配置与行为测试，不让 A1 等待未来 API 全集。

既有 `management.memory` 是完整的 Memory 管理能力，包含其已经绑定的管理方法，不能当作“只读管理”权限授予；管理权限同样来自当前 Workspace 的 Actor 访问记录。Profile 管理写入/列表沿用 AGENT_PROFILE atom 的既有绑定例外，Topic/Asset/Task 不得借此泛化放行。若后续需要更细管理权限，应拆分相应 operation 和方法绑定，不根据 principal 类型暗中改变同一 operation 的含义。

### 4.2 资源 owner 的授权责任

`PRIVATE`、`TEAM`、`PUBLIC` 可作为 Workspace 内资源读取 policy 的共同词汇：PUBLIC 只表示已进入该 Workspace 且通过 operation 检查的 Actor 可见；PRIVATE 只对目标 Actor；TEAM 依赖可信团队关系。它们不表示互联网公开，也不自动授予 write/update/delete/admin/cancel。

行为许可与资源许可必须同时满足：允许 `resource.read` 仍可能被 private memory 拒绝；一条 public memory 也不能使没有读取许可的 Actor 获得读取能力。检索按资源 policy 过滤集合，更新/删除检查目标资源，新增操作检查目标 Workspace 及所引用资源，不要求先虚构一个已存在的目标资源。

Profile、Asset、Task 由自己的 owner 定义资源规则，不强行复制 Memory 字段。管理读取继续由资源 owner 执行显式的 owner-management policy；其生效前必须通过 Workspace 管理行为授权，不能只看到 `system` 或 owner 相等就跳过 Agent 可见性。任务按权威 `identity_scope` 判断归属；知道任务 ID 不构成权限。

### 4.3 独立结果示例

同一受信 adapter 服务用户 U 的 Actor A、B；Workspace W1 为 A 登记 `{resource.read}`，没有 B 的准入记录；W2 为 A 登记 `{resource.read, memory_intent.submit}`。各 Workspace 均满足 W0 的 owner 约束。

| 请求 | 结果及负责阶段 |
|:---|:---|
| 未登记来源请求任意 Workspace | 系统接入认证拒绝，尚未查询资源 |
| B 经已登记来源进入 W1 | Workspace 准入拒绝，不能因与 A 共用 principal 或 owner 而放行 |
| A 在 W1 读取对自己可见的 Memory | 两次认证及两类授权均通过 |
| A 在 W1 读取只对 B 可见的 private Memory | 行为许可通过，资源 owner 拒绝 |
| A 在 W1 提交主动写入意图 | 已进入 Workspace，但缺少 `memory_intent.submit`，行为授权拒绝 |
| A 在 W2 提交有效主动写入意图 | 行为许可通过，再按目标及引用资源规则接纳；不保证必然生成 Memory |
| A 经另一已登记 adapter 执行同一操作 | 使用同一 Workspace Actor 记录，业务权限不随接入方式变化 |

## 5. 实施切片与验收

| 阶段 | 产出 | 完成条件 |
|:---|:---|:---|
| A1-0 | 以第 1.1 节代码为起点，冻结网关入口、配置、context 有效区间、已有方法绑定及兼容清单 | 区分复用/修改/新增；按第 7 节核对约束承接；不存在以撤销代码或未来 API 为前提的步骤 |
| A1-1 | 统一认证网关、Workspace Actor 注册表、运行时行为检查、context 完整性 | 一次认证调用完成两项检查；未知接入、非成员、未许可动作、伪造上下文分别拒绝 |
| A1-2 | 补齐 System service 的 context 传播，复用桥接，接入 Patchouli/Asset 公共检查 | 独立组合的真实总线协作中 context 不丢、不被 DTO 覆盖；方法授权先于资源访问和副作用，不以生产 assembler 接线作为门禁 |
| A1-3 | 基线方法覆盖、资源 owner 规则及错误验收 | 三类调用侧共用行为检查；资源权限独立生效；后续新增 operation 由引入方验收 |

必要行为证据：

1. 未登记、禁用或 adapter 不匹配的接入在系统层拒绝；已登记来源的合法 Actor 可继续准入。同一 principal 服务多个 Actor 本身不是失败条件。
2. 同一 owner 下两个 Actor 有不同准入结果；同一 Actor 在两个 Workspace 有不同白名单；两个 owner 使用相同 workspace_id 时记录不串扰。
3. 空行为集合可通过准入但所有资源动作被拒绝；仅有 read 的 Actor 无法写入；task.observe 无法 cancel；新增 operation 不自动赋权。
4. 有行为权限但目标资源不可见时拒绝；资源 public 但无行为权限时也拒绝。PRIVATE/TEAM/PUBLIC 与 owner-management 分别验证，不以一种通过结果代替其他检查。
5. 系统管理、AliceBridge 和中立 adapter 使用同一认证网关及真实 GlobalSystemBus/application 得到相同语义；任一认证步骤失败都不产生成功 context，行为授权拒绝时不调用资源后端或产生副作用。配置和存储可用最小本地实现，不用 fake 成功路由替代授权证据。
6. context/DTO 冲突、同值重建、复制、替换 scope、自报合法的协议对象及跨实例 context 均被拒绝；同一有效 context 可先后执行 read/search 等已许可动作，无许可的 write 仍拒绝。context 不再含 principal 或配置对象，不能以它们的对象地址判定签发事实。伪造 operation 或允许行为不能改变实际方法要求。提交来源继续由 Patchouli 内部链路记录，不从 access context 或公开 API 参数重复派生。
7. 延迟 flush 在提交时重验有效性和行为许可，已接纳工作保持原结果语义；context 到期、运行实例结束后拒绝新动作，若支持配置重载则旧 context 失效并需重新认证。授权拒绝不会转换为服务不可用，资源错误遵循既有 envelope。
8. canonical mutation 及内部失效通知不重新走 Actor 认证，不暴露新的外部成功旁路；若公开 wait，覆盖等待上限、超时和 shutdown 结束语义。

测试使用当前已存在的 interaction/意图/任务输入，不等待 A3/A4/B；缓存新鲜度、未来资源模型的具体授权和生产消费者切换随所属计划验收。A1 完成须有基线真实行为证据，不能以配置表、operation 字符串或静态绑定测试齐全代替。

验证入口为 [Workspace guard 测试](../../tests/unit/workspace/test_access.py)、[System 网关测试](../../tests/unit/system/access/test_gateway.py)、[依赖边界测试](../../tests/unit/workspace/test_import_boundaries.py) 与 [真实总线/application 集成测试](../../tests/integration/workspace/test_application_access_boundary.py)。本轮移除旧 `system/access/test_credentials.py` 中的工厂与自检结构断言，将仍有效的不可变性、伪造拒绝、TTL 和关闭行为迁入 guard 测试。集成证据还需保护延迟提交拒绝、已接纳工作继续执行和来源追踪；不能以旧测试记录或这份计划修订代替本轮运行结果，也不表示 A1 整体已验收。

## 6. 迁移、回滚与文档

源码与测试按下表实施并验证；生产消费者切换仍由 A6 收口，不能因文档更正而标为完成。前几项保留历史迁移要求，context 与来源条目补充本轮调整：

| 既有内容 | 迁移要求 |
|:---|:---|
| `LocalTrustedAdmissionService` / `WorkspaceAdmissionPort` | 将可复用认证和准入逻辑收敛到 System 统一认证入口；Workspace 侧提供内部准入判定与行为检查，不保留调用方需分别访问的两个认证服务 |
| `trusted_principals` 配置 | 接入名单转入 System 注册配置；操作许可改为显式的 Workspace Actor 记录。旧 principal 级配置无法推导 Actor/Workspace 范围时拒绝迁移，不批量授权所有同 owner Actor |
| `access.py` 中的 `WorkspaceOperation` / application 方法绑定 | 保留可复用操作语义，补齐已有方法映射；不假设已有独立 operation 目录。本地管理员也使用 Workspace Actor 登记权限 |
| `WorkspaceAccessContext` / grant / 消费 helper | context 移入 Workspace，只持有 scope；删除 grant、自检协议、有效期锚点及独立工厂。guard 内部签发并跟踪对象有效性，授权返回可信 scope；消费者及类型注解改用 Workspace 导出 |
| 网关/guard 组合与配置 | 网关注入同一个 Workspace guard；TTL/时钟由 guard 持有，网关 close 委托 guard。删除 `issued_by`，保留显式两类登记，不以配置对象地址绑定凭据 |
| System application / bridge | Memory、Agent、Topic 等服务从仅传 scope 改为接收并透传 access，Task 服务补齐访问参数；保留已有桥接结构，验证访问错误不会被吞掉或误包装 |
| Patchouli 与 Asset 公共入口 | 在现有 application 调用统一检查，再由各资源 owner 授权；不增加 Workspace 业务 service 或 provider |
| 旧受信调用、测试与 composition | A1 使用显式配置独立组合验证，兼容清单须写出保留入口、已有调用方和 A6 删除点；无 access 的旧分支只供这些既有调用，不能让新公开入口因缺失 context 自动进入兼容分支。A6 切换生产入口并关闭兼容窗口 |
| 任务与后台提交 | 交互与生成链沿用 Patchouli 内部来源记录；已接纳工作只持有内部 scope 和既有收据。查询/取消分别授权，不把调用来源或提交许可传成后台通用权限 |

回滚可以恢复已声明的受信 adapter 兼容链，不开放新的裸 scope 入口，也不删除已接纳领域工作。基线关闭不依赖完整远程认证、非 owner 成员模型、未来资源操作或 B 的 wire 完成。

## 7. 既有约束承接清单
