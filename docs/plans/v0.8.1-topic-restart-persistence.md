# v0.8.1 话题跨重启保存：关闭时保存话题池，本话题的写入记录交还给话题

> 状态：Planned（2026-11-24）。v0.8.1 短期记忆的第二份计划；设计依据见[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 5 节。

## 1. 背景和问题

结算拆成沉淀与退役之后，空闲不再让话题离开话题池，但进程关闭仍让全部话题沉淀并退役。日常实例 11 天关闭 11 次，话题的实际寿命上限就是一次进程运行：断断续续回来的工作在重启处仍被切开，拆分换来的连续性只做到一半；之后的工作记录也建在话题上，话题不跨重启，工作记录同样活不过重启。

“本话题的写入”记录与话题脱节：它由生成控制器在进程内按话题保存（`_topic_write_memory_ids`），只随关闭时保存的结算任务写盘。话题退役却没有生成任务时（例如为写入建立、却没有接收交互的空话题），或者话题退役之后才完成的同话题写入，留下的记录一直保留到进程结束。话题跨重启之后，这份记录必须和话题一起保存，否则恢复的话题再沉淀时看不到此前的写入，一次性生成的“命中即丢弃”与 Mode B 的 `kept_apart_from` 随之失效。

## 2. 目标与非目标

### 2.1 目标

- 关闭时把整个话题池写成一份快照，下次启动读回：交互记录、折叠记录、沉淀进度与本话题的写入记录，话题重启后照常续写、沉淀与读取，仍是 Gateway 的候选话题。
- 进程关闭不再让话题退役：关闭时对全部驻留话题做一次与空闲相同的处理，有未沉淀交互的沉淀，从没接收过交互的空话题退役。
- 本话题的写入记录成为话题的字段：随话题保存，随话题退役而消失；生成执行时从话题读取，完成后记回话题。控制器不再持有这份记录。

### 2.2 非目标

- **崩溃恢复**：快照只在正常关闭时写出，进程崩溃时话题池与生成工作、任务历史和写入意图登记一起丢失。要扛崩溃，得让这几份运行时状态一起进入同一个事务存储，另行立项。
- **会话、Import Bus 已确定话题的登记、合并的吸收关系**：都在进程内，本计划不改。写入时建立话题、这一轮却在重启之后才回流时，登记已经不在，回流的轮次重新路由。
- **附件**：话题的附件绑定随话题保存，但 WorkspaceAsset 在关闭时清理，重启后提升附件照现有的尽力而为逻辑跳过。
- **工作记录、推送与拉取、折叠摘要的结构化**：短期记忆 Idea 第 3、4、6、7 节，各自另行计划。
- **空闲计时的时间语义**：驻留集合的访问时间仍用单调时钟，不持久化。

## 3. 当前状态（2026-11-24 核对）

- **短期存储**：`ShortTermMemoryStore` 经 `ShortTermStoragePort` 存取话题，生产上只有内存实现 `InMemoryShortTermStorage`（Patchouli runtime 装配时创建）。`TopicData` 是不可变快照，只经三个写函数 `merge_interaction_into_topic`、`fold_topic` 与 `mark_topic_settled` 产生新快照，`Store.put` 整条替换；跨 await 的占用由 `TopicWorkingSet` 的 lease 表达，lease 是非阻塞的，取不到就报 `TopicBusyError`（[感知与短期话题](../patchouli/perception.md)）。
- **写回前读到的快照**：应用交互在同一段没有 await 的代码里读取并写回。折叠在 lease 内读取话题、等待摘要模型、再把 await 之前读到的快照套上 `fold_topic` 写回；结算在 lease 内冻结材料、等待生成队列接纳、再把 await 之前读到的快照套上 `mark_topic_settled` 写回。
- **驻留与空闲**：`TopicWorkingSet` 按 Workspace 计容量（`max_resident_topics`，随附配置 5），访问时间取单调时钟；空闲候选按访问时间判断，LRU 按访问顺序选择。
- **关闭**：`PatchouliSystem.stop` 先关闭折叠并排空提交队列，再执行 `shutdown_drain`：生成队列停止取新工作 → `flush_all_for_shutdown` 让全部驻留话题退役（有未沉淀交互的先沉淀）→ 保存未执行的生成工作到 `patchouli.shutdown.pending_work_file` → 停止生成队列 → 写任务历史（[记忆生成](../patchouli/generation.md#62-提交阶段关闭时保存与启动时继续)）。
- **启动**：`PatchouliSystem.start` 依次读回任务历史、启动生成队列、读回保存的生成工作。保存文件的写法一致：`write_atomically` 原子写入，读回即删除，读不回的整份文件或单项改存同目录的 rejected 文件，记错误日志并继续启动。
- **本话题的写入记录**：控制器以 `topic_id` 为键保存在 `_topic_write_memory_ids`。WRITE 与 SETTLE 执行时并入 `GenerationRequest.topic_write_memory_ids`；执行之后按结果记下（WRITE、UPDATE 的结算目标；不退役的沉淀新建的记忆；合并吸收记录中的某条时改指保留的那条）；随退役执行的 SETTLE 成功后清除；关闭时保存的 SETTLE 经 `_spec_to_save` 带上记录（[记忆生成](../patchouli/generation.md#42-本话题的写入)）。
- **本地路由**：`topic.get` 返回完整的 `TopicData`，纯读、不刷新访问时间；控制器经 Patchouli 本地总线调用数据面（`generation.execute_spec`）。
- **配置**：`patchouli.shutdown` 的两个文件路径只有代码缺省，随附配置不列出，说明在[记忆生成](../patchouli/generation.md)第 6 节。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-24）：持久化整个话题；保存方式与生成工作等运行时状态相同，正常关闭时写一份快照、启动时读回；本话题的写入记录交还给话题（短期记忆 Idea 第 5 节）。依赖均已是事实：结算拆成沉淀与退役已经合并。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 本话题的写入记录成为话题的字段

- `TopicData` 新增 `topic_write_memory_ids: frozenset[str]`，缺省为空，与生成请求的同名字段是同一个概念。
- core 话题模型新增第四个写函数 `record_topic_writes`，只改这个字段，不改内容、沉淀进度与 `last_update`。记录规则与现在相同；合并改指按写回时话题的最新记录判断。
- **读取**：沉淀在 lease 内冻结材料时，把当时的记录一起冻结进 `TopicMaterializeTask`，SETTLE 的生成请求因此带着接纳时的记录。WRITE 与 SETTLE 执行时，控制器经 `topic.get` 读取话题，把话题当前的记录并入请求；话题已经不在（退役之后执行的结算）时只用冻结的那份。
- **记录**：执行之后，控制器把这次要记下的写入与改指经新的本地路由 `topic.record_writes` 交给感知，感知在最新快照上套用 `record_topic_writes`；话题已经不在时不记，退役的话题不会再沉淀。
- 删除控制器的 `_topic_write_memory_ids`、随退役结算清除记录的分支与 `_spec_to_save`：保存的 SETTLE 已经带着冻结的记录。

### 5.2 写回总是套用在最新快照上

记录的写入不取 lease：它只改一个与交互、折叠和沉淀进度互不相交的字段，不需要跨 await 占用话题。为此，感知的每次写回都在同一段没有 await 的代码里读取最新快照、套用写函数、写回：折叠与结算接纳之后的写回改为先重新读取话题，不再写回 await 之前读到的快照；lease 仍然保证这期间交互记录与折叠记录不变，`fold_topic` 的前缀校验与冻结的交互数照样成立。正确性依赖的前提（读取与写回之间没有 await）在代码旁写明。

随退役执行的结算被接纳之后、执行之前完成的同话题写入，不在它冻结的记录里，与被动草稿之间照旧按查重处理；这与“结算开始时仍在执行的同话题写入不在记录中”是同一种情况。

### 5.3 关闭

- `flush_all_for_shutdown` 对全部驻留话题执行与空闲扫描相同的处理：有未沉淀交互的沉淀（不退役），空话题退役，接收过交互、已经全部沉淀的不处理。沉淀的接纳失败只记入报告，话题带着未沉淀的交互照常保存，下次启动后由空闲扫描沉淀。
- `shutdown_drain` 的顺序：生成队列停止取新工作 → 关闭时的沉淀 → 保存未执行的生成工作（其中会等已开始提交的任务写完，它们的写入因此先记回话题）→ 保存话题池。
- `TopicShutdownFlushReport` 随语义调整：沉淀的、退役的（空话题）与失败的话题；`shutdown_drain` 的完成事件另报告保存的话题数与快照是否写出。

### 5.4 启动

- 读回话题池放在读回任务历史与保存的生成工作之前：读回的结算执行时，它的话题已经在存储里。
- 读回的话题逐个写入存储，并按 `last_update` 从旧到新登记驻留，访问顺序因此与关闭前一致；空闲计时从读回时重新开始。关闭时已经沉淀过的话题不会因此重复沉淀；沉淀失败的话题在一个空闲超时之后沉淀。
- 同一 Workspace 读回的话题超过 `max_resident_topics`（配置在两次运行之间调小）时，只读回最近的若干个，其余写进 rejected 文件并记错误日志。

### 5.5 快照文件

- 新配置 `patchouli.shutdown.topic_pool_file`，默认 `.hivememory/topic_pool.json`，相对路径按工作目录解析，与 `pending_work_file`、`task_history_file` 并列。
- 文件带 `format_version`，每个话题以 `TopicData` 的 JSON 形式保存；读回时以完整构造校验（折叠前缀、沉淀进度不超过交互数）。不另设序列化。
- 话题池为空时不写文件；原子写入；读回即删除，崩溃之后不会读回过时的话题池。整份文件读不回或格式版本不认识时改名为 rejected 文件、话题池从空开始；单个话题校验失败时，这些话题写进 rejected 文件，其余照常读回。
- 写不出时记录原因码 `topic_pool_write_failed`；关闭时的沉淀已经把未沉淀的交互交给生成，丢失的只是话题池本身。
- 读回作为一次 `patchouli.restore_topic_pool` 操作发布开始与完成事件，报告读回与写进 rejected 文件的数量，写法与 `patchouli.restore_saved_generation` 相同。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| core 话题模型 | `TopicData.topic_write_memory_ids`；写函数 `record_topic_writes` |
| Patchouli 感知 | 关闭时只沉淀与让空话题退役；写回前重新读取话题；`topic.record_writes` 的处理；读回话题池并登记驻留 |
| 感知引擎 | `TopicMaterializeTask` 冻结记录 |
| Patchouli 本地路由 | 新增 `topic.record_writes` |
| 生成控制器 | 执行时经 `topic.get` 读取记录、执行后经 `topic.record_writes` 记下；删除进程内的记录与 `_spec_to_save` |
| Patchouli runtime 与 system | 关闭与启动的顺序；话题池快照的写入与读回 |
| 配置 | `patchouli.shutdown.topic_pool_file`，与另外两个文件路径一样只有代码缺省 |
| 观测 | `shutdown_drain` 完成事件的话题字段；新操作 `patchouli.restore_topic_pool` |

不涉及 Workspace 能力层、公开 route 与 HTTP 响应：话题列表与话题池界面不变，重启之后照常列出读回的话题。生成队列的工作信封不变（1.4），SETTLE 的生成请求本来就带 `topic_write_memory_ids`。

## 7. 兼容与迁移

- 升级后第一次启动没有快照文件，话题池为空，与现在相同；此后每次正常关闭写出快照。
- 旧版本关闭时保存的 SETTLE 带着控制器当时的记录，读回后照常并入；它们的话题已经退役，执行时只用冻结的那份。
- 降级到旧版本时快照文件不会被读取或删除；再次升级时会读回那份过时的话题池，按其中的沉淀进度再次沉淀，可能产生重复的记忆。降级之后应手动删除这个文件，由帮助文档说明。
- 开发实例与日常实例各有自己的工作目录，快照互不影响。

## 9. 风险与待决问题

- **快照大小**：话题在退役之前保存全部交互记录，单个话题可能有几 MB，整个话题池在几十 MB 以内；关闭时整份写出、启动时整份解析，耗时随话题池增长。现在关闭时所有话题的未沉淀材料本来就写进生成工作文件，量级相同。
- **话题活得更久**：话题的寿命不再受重启限制，只受容量与手动结算约束，单个话题的交互记录、每次沉淀的材料与来源 InteractionArtifact 随之增长。
- **退役结算的记录窗口**：第 5.2 节所述的窗口按查重兜底；退役只由 LRU 与手动结算触发，被退役的话题眼下很少还有写入在执行。
- **降级再升级**：第 7 节所述的过时快照。
- 待评审的默认值：第 5 节中的名字与文件名；关闭时空话题退役；超出容量时写进 rejected 文件而不是全部读回；读回时空闲计时重新开始。
