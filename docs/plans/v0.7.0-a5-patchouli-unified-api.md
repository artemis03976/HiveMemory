# v0.7.0 A5：Patchouli 共同 API 与业务职责收敛

Patchouli 已经拥有按处理领域组织的 application 层和 `GlobalSystemBus` 路由。A5 不为 Workspace 再包一层 provider，也不按 Actor 类型复制 API；它要做的是从 System、Alice 和外部 Actor 的共同行为中确认必要的业务操作，让三种 adapter 进入相同的总线路由，并把旧 `PatchouliService` 的运行编排与领域能力分开。

A5 在 A1–A4 的公共能力交付后进行整体收敛。A2 已交付 canonical/Profile 读取和快照，A3 已交付 Session/交互模型、Topic 生命周期与交互路由，A4 已交付 Pending、主动意图和完整共同引用读取。本计划核对三方共通操作、补齐尚未覆盖的检索/使用报告/结果呈现差额，并为旧 PatchouliService 的职责退出准备已验证的替代入口。

A2–A4 各自负责模型、operation 绑定、公共总线路由和领域行为；A5 不承担它们的前置“API 发布平台”，不新增总 facade、转发 service 或第二份 DTO。领域规则仍引用前置计划，本文只维护全局操作目录、三方调用示例和职责交接清单。真实消费者删除、运行编排和最终生产装配由 A6 验收。

本计划承接原 A2 的 API 收敛差额，保留 Active；编号后移不否定已完成的 WRX-0/1 工作。原 A2 的 canonical/Profile 契约移交 A2，完整 Pending 引用契约移交 A4，Topic API 暴露并入 A3，避免这里再反向成为它们的依赖。

## 1. API 与 adapter 的边界

API 是 Patchouli 提供的稳定业务操作、输入、授权、结果、失败和生命周期语义；总线路由是其在 `GlobalSystemBus` 上的地址；application service 按处理领域实现 API；adapter 只转换协议、取得 access、决定触发时机和呈现结果。

主动工具调用和自动交接是触发方式，不是两套业务 API：SEARCH 工具和交互开始的自动 context 使用相同检索；完整交互在可靠的完成/封口/flush 信号后由 adapter 自动提交，不依赖模型选择“保存对话”工具。只提供 MCP search/write 工具不等于实现自动交接。

## 2. 三方共通操作

| 共通操作 | System adapter | Alice adapter | 外部 adapter | Patchouli 语义 |
|:---|:---|:---|:---|:---|
| memory search | Passive context 或管理应用查询 | prepare、MTP SEARCH | 自动 context、search 工具 | 同条件同 policy 的可见检索与来源 |
| resource read/resolve | 应用引用读取 | MTP READ、CALL context_refs | read 工具 | 统一 Pending/canonical 引用解析与授权结果，cache/storage 是内部选择 |
| profile read | 管理和应用读取 | Root/CALL | 可选读取 Profile 定义 | 解析定义、检查类型/可见性、返回 snapshot；不等于应用执行配置 |
| Topic 资料 | 摄入关联和读取 | prepare 读取 | Session/交互关联的 Topic 资料 | Patchouli 持有 Topic 路由和快照；不要求 Alice run |
| Pending 登记 | 应用主动写入 | MTP WRITE/UPDATE | write/update 工具 | 登记可读意图，不等同 Memory |
| memory intent submit | 应用策略提交 | settlement adapter | 工具立即或延迟提交 | 接纳 `PendingAtomMaterializeTask`，读取全部可用 Topic 资料并生成/修订 |
| interaction submit | Passive seal/flush | run 结束后的事件整理与封口 | 外部完成回调/封口 | 去重、领域投影并应用交互到 Topic/证据；不隐式物化 intent |
| result/usage observe | 展示与反馈 | 引用、使用与结算 | 结果查询和反馈 | 分开表达接收、应用、物化、canonical 与实际使用 |

共同操作不表示相同权限或相同触发信号；统一的是领域语义和业务链路。

## 3. 三个入口如何收敛

以下示例消费[A1 的统一认证网关与运行时授权](./v0.7.0-a1-workspace-access-boundary.md)。三类入口都经同一个网关完成两项认证；有效 context 不绑定单次 operation，实际行为许可由 application 逐次检查。

**管理员读取 Memory**：管理 adapter 调用 System 统一认证网关，由网关确认接入登记、含 user 的管理 Actor 身份及目标 Workspace 准入，取得 context。System application service 携带 context 调用 `PATCHOULI_MEMORY_GET`，Patchouli application 通过共享检查确认其 Workspace 行为白名单包含 `management.memory`，资源 owner 再执行 Workspace ownership 和显式管理读取 policy，最后返回 copy-on-read 结果。`system` 标记本身不授予管理权限。

**Alice 执行 SEARCH**：Alice adapter 经同一认证网关确认来源、Actor 和 Workspace 准入，取得 context；已有 context 仍有效时可直接复用。AliceBridge 原样透传至 `PATCHOULI_MEMORY_RETRIEVE`，Patchouli application 按方法要求检查 `resource.search`，资源 owner 再按 PRIVATE/TEAM/PUBLIC 过滤检索结果，MemoryCompiler 转换为 MTP/SSE。后续 READ 可以复用同一 context，但独立检查 `resource.read`。外部 harness 更换接入和 wire adapter 后仍使用同一网关、路由与 Workspace Actor 行为白名单。

**Passive 提交完整交互**：已登记的 Passive adapter 经统一网关认证，累积 TurnEvent，在完成回调、封口或显式 flush 后形成 A3 演进后的 `InteractionPayload`。实际提交时确认 context 仍有效，失效则重新经过同一网关，再调用 `PATCHOULI_INTERACTION_SUBMIT`。application 通过共享检查验证 `interaction.submit`，按资源规则核对 Session/scope 和引用，再验证 payload、interaction_id 并创建内部 `InteractionSubmission`，队列应用 Topic/证据。接纳前不能清空 buffer，重复完成复用同一 interaction_id，不能重复应用；有效认证上下文不代替延迟提交的行为授权，interaction.submit 也不隐含 resource.search。

三条链路使用同一认证与授权规则、同一 application 语义和同一领域实现；返回的 HTTP、MTP/SSE 或 Passive receipt 由 adapter 分别呈现。

同一交互提交的收敛更直接：

```text
System/Passive：实际事件 -> TurnEvent 累积/封口 -> InteractionPayload
Alice：AgentRunResult -> 保留 TurnEvent 与来源关联 -> InteractionPayload
外部 adapter：完成回调/完整记录 -> wire 归一化为 TurnEvent -> InteractionPayload
                       |
           同一认证网关完成两项认证，取得或复用有效 access
                       |
GlobalSystemBus.request(PATCHOULI_INTERACTION_SUBMIT, access=..., payload=...)
                       |
Patchouli application -> 内部 InteractionSubmission -> queue -> Topic 应用
```

示例中的 `payload` 承载 A3 演进后的 `InteractionPayload`；进入 A5 实施时，实际 Python 签名以 A3 已交付并验证的接口为准。adapter 不导入内部 queue envelope，不据 `origin=alice/passive` 选择另一条领域算法。外部 Actor 看到 B 的 HTTP/JSON 等协议；同进程 adapter 同样请求全局路由，不直接调用 Patchouli application 对象。System 顶层 service 可按需保留封装；不要求 Alice 为形式一致绕行 HTTP。

## 4. PatchouliService 的收缩

| 旧职责 | 目标承担方 |
|:---|:---|
| prepare 中的 Profile、Topic、检索 | 调用侧 prepare adapter 组合共同路由；Patchouli 保留领域解析、Topic 准备和检索 |
| `AgentRunContext`、stream prelude、运行参数 | Alice/Chat 执行侧 |
| 附件选择、编译、lease | 调用侧协调 System-owned Asset API 与 AttachmentCompiler |
| finalize 的运行事件整理、交互封口和提交时机 | Alice/System adapter；保留 TurnEvent 及来源关联，形成 InteractionPayload，分别调用 interaction 和 memory_intent 路由 |
| TurnEvent → AgentAction/TurnRecord 领域投影、交互应用、Topic 路由、生成、Pending 结算 | Patchouli application/领域服务的唯一实现；投影规则按 A3 第 5 节，不由各 adapter 重复归约 |
| citation、feedback、Topic 条件清理 | Patchouli 领域 API；adapter 只报告事实和请求操作 |

旧方法可以在迁移期委托新 API，但不再直接提交内部 queue、controller 或 generation local route。取消、continuation、lease release 和 shutdown drain 必须由新的调用侧 coordinator 和领域 application 分别承接；不能因为拆分而丢失这些保障。

调用侧负责尚未交接的运行工作，application 接纳后负责领域工作。后置主动物化失败不能把已应用交互改判失败。Topic 准备交接与补偿使用 A3 第 4.3 节生命周期，交互资料向主动意图的交接使用第 4.4 节；A5 不将其合并为复合提交。生成材料读取、预算编译、controller 选择和结算留在 Patchouli，不要求 adapter 拼生成规范或额外调用一串内部步骤。

## 5. 路由目录与输入依据

目录继续沿用 `patchouli.public.memory.retrieve/read/retrieve_by_aliases`、Profile snapshot、管理 API 和两条提交路由。Profile source projection、Topic prepare/conditional cleanup、interaction result observation 和主动提交由 A2–A4 完成；本计划核对其覆盖及一致性，实际新增差额集中在检索、usage/citation/feedback 和跨操作职责。

`interaction.submit` 的共同输入是 A3 演进后的 `InteractionPayload`，其中 TurnEvent 是唯一事件正文；队列内部的 `InteractionSubmission` 是 envelope，复用同一个 interaction_id。`memory_intent.submit` 的共同输入是 A4 冻结的 `PendingAtomMaterializeTask`。不能把 `materialize_tasks` 留在新版本普通交互提交里并隐式执行，也不能为外部 Actor 新造 `MemoryIntent` 领域模型来复制 Pending。

所有公开 application 方法接收 A1 的 access context。没有 context 的旧调用只能在受信内部适配窗口内存在；A6 收口时删除或限制它们。Patchouli application 不回调 Workspace 业务 service，Workspace cache miss 也不能重新进入 public route 形成递归。

### 5.1 已有 API 与缺口的实施清单

以下沿用原计划与 WRX-0 的 2026-09-17 分支调查，表示可复用的代码入口，不宣称消费者切换或最新目标已经通过验收。表中的“已交付/已实现”表示进入 A5 实施时必须具备的前置出口，并非当前实现状态；实施前按各计划证据核对。

| API | 已有入口/实现 | 责任与剩余差额 |
|:---|:---|:---|
| 管理 Memory | `patchouli.public.memory.get/list/create/update/delete`；MemoryManagementService | 沿用 A1/A2 管理授权和读侧契约；本计划核对管理 mutation 的职责及与普通资源操作的差异 |
| Actor 点读/alias | `patchouli.public.memory.read/retrieve_by_aliases` | A2 交付 canonical 分支，A4 交付完整 Pending/settlement 解析；A5 核对同一公共入口与兼容，无 adapter 三级查询 |
| 检索 | `patchouli.public.memory.retrieve` | A5 统一结果语义；A6 把 prepare 内部检索转向同一路由，支持主动和自动触发 |
| Profile | `patchouli.public.get_agent_profile`、`get_agent_profile_snapshot`；AgentProfileManagementService | 沿用 A2 已交付的 builtin/alias/type/定义解析和 source UUID/revision；A5 只核对目录及兼容，应用配置由 Actor 负责 |
| Topic 准备/资料 | `patchouli.public.topic.list_active/get_data`；prepare_topic 尚未独立挂载的调查记录 | A3 已实现 prepare/资料读取及 operation；A5 核对入口映射，handle 与资料快照按 A3 第 4.2 节区分 |
| 交互提交 | `patchouli.public.interaction.submit`；InteractionSubmissionService | A3 演进 Payload 契约/投影与授权结果查询；A6 切换旧 finalize 和 Passive 直调 queue 的路径 |
| 主动物化提交 | `patchouli.public.memory_intent.submit`；MemoryIntentSubmissionService | A4 收敛共同输入与单一生成链；独立方法不要求独立类 |
| Pending 登记/读/解析 | 原 Alice PendingAtomRuntime/resolver | A4 已实现资源侧状态、operation/可见性及共同读取；A5 核对目录，不重开领域契约 |
| 任务与交互结果 | `patchouli.public.memory_task.list/get/cancel`；MemoryTaskManagementService | interaction apply/assignment 观察由 A3 交付，Pending/task 由 A4 交付；A5 核对结果层次；不因目录完整而新增 `memory_task.wait` |
| 使用/引用/反馈 | `patchouli.public.record_memory_citation`、`memory.record_feedback`；usage 隐藏在 finalize | A5 区分返回、实际使用、引用、评价；冻结普通 Actor 报告权限，不借管理 bypass |
| Topic 清理/管理 | `patchouli.public.manual_settle_topic/evict_topic` | 沿用 A3 已交付的管理/条件清理区分；A5 核对 operation 与退出旧 cleanup 的职责映射 |
| Asset | System WorkspaceAssetApplicationService、reader/command ports | A1/A2/A6 沿用 READY/lease；不因统一 Patchouli API 改变 System 所有权 |

### 5.2 兼容与输入来源

- canonical/Profile 快照、source revision、copy-on-read 与缓存行为以 [A2 第 1–3 节](./v0.7.0-a2-workspace-resource-reads-and-caches.md)为准。
- InteractionPayload/TurnEvent、交互接纳与应用结果、Topic prepare/handle/路由关联/cleanup 及资料绑定以 [A3 第 2–4 节](./v0.7.0-a3-conversation-session-and-topic-projection.md)为准，不要求独立 assignment 实体。
- `PendingAtomMaterializeTask`、Pending 内容/状态及完整引用读取以 [A4 第 2–4 节](./v0.7.0-a4-pending-memory-intents.md)为准。
- 调用方提交使用报告是 provenance 声明；返回过 ref 不等于实际使用过。附件使用只承接已有编译确认的 ref 快照，不能回查当前 UI 选择替代。
- HTTP/MTP/SSE 兼容由 adapter 维护，内部签名变更记录 access、DTO、错误及删除窗口。旧 Alice 专属 prepare/finalize/cleanup 不在“全部路由永久保留”范围内。

本计划从这些已交付接口核对完整操作目录，不再冻结它们的输入模型或共同状态机。若发现领域行为缺陷，在所属实现修复并更新其唯一设计记录；这属于消费阶段发现的缺陷，不预设前置计划必须等待 A5 才能完成。

## 6. 实施、测试和完成条件

| 阶段 | 产出 | 验收 |
|:---|:---|:---|
| A5-0 | 基于 A1–A4 已交付接口的三方共通操作目录、缺口与旧职责交接表 | 每项模型/生命周期均有前置领域依据；没有这里先冻结才能完成的 A2–A4 接口 |
| A5-1 | 检索、usage/citation/feedback 与管理操作的剩余差额 | 自动 context 与主动 SEARCH 使用同一领域语义；返回、实际使用、引用、评价分开；普通 Actor 不借管理 bypass |
| A5-2 | 全操作路由、access、输入、结果与错误的组合核对 | 两条提交独立；三方中立样例到达相同领域入口；无重复 DTO、状态机或共同 resolver |
| A5-3 | 旧 PatchouliService 职责/调用方/退出窗口清单 | 每项领域职责有已验证公共入口；调用侧职责有明确接收方；清单交 A6 验收实际迁移与删除 |

integration 使用真实 GlobalSystemBus、PatchouliBridge、application、queue 和 domain collaborator；fake 只能替换外部模型/网络。复用 A2–A4 的读取、Topic、Pending 行为证据，这里补检索/使用报告差额、跨操作授权、输入结果映射和三方相同路由的组合验证，不重复实现整套领域测试。A5 的中立 adapter 样例不替代 A6 的生产消费者验收。

完成条件是目录与实际公共路由一致、剩余业务差额有真实实现和证据、旧职责都有接收方；不等待 A6 删除旧入口或 B 发布外部协议。事实文档仍按版本稳定收尾门禁更新，未收尾设计留在计划中。

A5-0 只关闭本计划新增差额，例如普通 Actor usage/feedback 的签名和 operation；不重新决定 Topic handle、InteractionPayload 或 Pending 输入。回滚仅保留委托同一领域实现的受信 adapter，不恢复旧 queue/generation 旁路；任何兼容入口写明调用方与删除时点。
