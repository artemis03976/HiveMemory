# v0.8.0 写入时的更新：馆长修订、主动 UPDATE 与合并改用编辑集

> 状态：Planned（2026-11-20）。v0.8.0 的方向“写入时的更新”的计划，并入了原来的合并中止 Todo（“合并中止并留下重复”，删除前最后版本在 `9ab2b431`）。设计见[写入链路 Idea](../ideas/memory-flow-write-path.md)第 2.1、3.1 节；第一次评测的结果见[评测集 Idea](../ideas/memory-evaluation-benchmarks.md)第 6 节。

## 1. 背景和问题

写入链路的设计中，被动结算是话题的终态收尾者：它对已有记忆作出修订、补上缺少的记忆，或者什么都不改（写入链路 Idea 第 5 节）。现在三条改动已有记忆的路径各用一种语义，没有一条既能改对、又不漂移：

| 路径 | 由什么触发 | 改正文 | 改索引（标题、摘要、标签） |
|:---|:---|:---|:---|
| 馆长 | 话题结算 | 不改，只新建 | 不改 |
| Mode C | 主动 UPDATE（MTP UPDATE、MCP `memory_update`） | 整篇重写 | 不改 |
| 合并 | 查重判为相似（一次性生成、主动 WRITE） | 整篇重写 | 整条重写 |

检索与查重的稠密、稀疏向量只由标题、类型、标签与摘要编译，不含正文（`memory_compiler/handlers/embedding.py`）。不改索引的修订在检索中等于没有修订；整条重写的索引会漂移。

第一次 HaluMem 评测（5 人子集，`c0a9fcc5`）量出了这两种后果：

- 馆长的更新正确 48.1%、幻觉 3.9%、遗漏 47.4%；库只增不改，用户 06 结束时馆长的库有 208 条，一次性生成 117 条。被判为更新幻觉的 70 个样本中，20 个是新值写了、库里别的记忆还留着旧说法，34 个是新值没有写进库（一部分是数据本身的问题：数值类更新要点中 22/60 的新值不在该次会话的对话里）。
- 一次性生成的 628 次合并有 98% 改了标题、全部改了摘要，前后文本相似度的中位数为 0.69 与 0.53；同一条记忆合并 15 次之后，标题成了逐次累加的关键词清单。模型拿到“给出新的标题与摘要”这种格式时，没有“有限度地改”的选项。

HaluMem 不覆盖主动 UPDATE，但它的问题相同：agent 经 `memory_update` 改了一条记忆之后，检索看到的仍是旧标题与旧摘要。

同一次评测还量出了第三种后果：合并的结局取决于时序。一次性生成的 1,385 个生成任务中 82 个因合并中止失败，按后端日志与运行时事件逐个还原：

- 58 个是合并目标正等着被吸收：另一个话题的草稿命中了刚落库、还在等着被并进别处的新记忆 N，提名把 N′ 并入 N。N→M 先执行、删除 N 时，N′→N 读不到 N（`memory_missing` 51 个，其中 43 个在开始时、8 个在模型调用期间）；N′→N 先写回时，N→M 发现 N 的版本变了（`version_changed` 7 个）。
- 20 个是两个合并同时写同一条保留记忆（`version_changed`），其中 18 个来自同一次结算的几条草稿。
- 4 个是合并模型的输出无法解析（`model_output_invalid`）。
- 中止都发生在写入之前，内容没有丢，留下 82 对没有整合的相似记忆；在模型调用之后才中止的 39 个白花一次合并调用。777 个合并提名中 64 个在提名时指向正等着被吸收的记忆，合并在队列中等待的中位数 32 秒、p90 75 秒。

生成 lane 不按任何键排序、并发为 2，查重只取 dense top-1：同一批结算中描述同一主题的草稿，最近的往往是刚落库的兄弟记忆，几次提名因此串成一串。同一条链路上，结局取决于哪个先执行，就是行为不一致。

owner 已决定（2026-11-20）：

- 修订以结构化判定加编辑集落地；索引层纳入修订，标题与摘要只做片段替换、标签逐个增删、类型不变；落地之前做漂移拦截。
- 三条更新路径在同一份计划中改用编辑集，以免分开实施时漏掉条件之间的联系。
- 写入时的合并是以保留记忆为底的修订：把被吸收那条独有的内容写成对保留记忆的编辑集；表达不了或被拦截时合并中止、两条都保留，两条记忆是否融合是维护的决策。
- 合并中止的 Todo 在同一条链路上，不是独立的问题，与本方向一起处理：要保证的是同一条链路上的更新结局只由内容决定，不取决于执行顺序与时机。

设计见写入链路 Idea 第 2.1、3.1 节。

## 2. 目标与非目标

### 2.1 目标

1. **编辑集**：三条更新路径共用一种编辑集与一个应用它的纯函数：正文、标题与摘要的片段替换，正文的追加与整篇改写，标签逐个增删；类型不在其中。
2. **漂移拦截**：一个共用的组件，比较修改前后两版的稠密向量，余弦相似度低于阈值时拒绝；阈值是一个配置项，按真实数据校准后设定缺省值。
3. **馆长修订**：新增工具 `revise_memory`，在循环中校验编辑集，原文对不上、越界与漂移拦截都作为工具错误交回模型；结算的结果里除了新建，还有修订，Familiar 在提交前重读、必要时重放。
4. **Mode C 改用编辑集**：修订提示词输出编辑集，输入带上摘要与标签；编辑集不合格时带着错误再调用一次，仍不合格时走现有的回退；外部契约不变。
5. **合并改用编辑集**：合并提示词输出对保留记忆的编辑集；编辑集不合格时带着错误再调用一次，仍不合格或被拦截时合并中止、两条都保留；`MergeResult` 由编辑集取代，类型沿用保留记忆。
6. **结局不取决于时序**：同一 Workspace 的合并依次执行；合并目标已被吸收时沿吸收关系改指仍然存在的那条；三条路径在提交前用同一条基础变化规则（版本变了就按原文重放，重放不了才按各自路径失败）。第一次评测中因时序产生的 78 个中止不再出现。
7. **提示词**：馆长的工作顺序改为三种判断（保持、修订、新建），写明助手正文中的用户事实怎样对待；Mode C 与合并的提示词改为编辑集的写法。
8. **评测**：在第一次评测的同一子集上重跑馆长与一次性生成，分别与第一次的两次运行对照，跑前写下预注册；Mode C 由集成测试与日常使用验收。

### 2.2 非目标

- **一次性生成的提取**：它的被动提示词（包括“用户明确陈述高、AI 推理低”的核心原则）不改；提取按现状冻结，变的只有它的合并。
- **两条记忆的对称融合**：写入时只做以保留记忆为底的修订；两条讲的不是同一件事时是否融合，留给维护。
- **查重**：哪些草稿提名合并（dense top-1 与阈值）不变。
- **同批草稿互相查重**：不做；合并依次执行并沿吸收关系改指之后，同一次结算的几条草稿命中同一条记忆，结局已是内容依次补进那一条。
- **外部 UPDATE 契约**：MTP UPDATE 与 MCP `memory_update` 仍只传指令与内容，不开放片段替换。
- **吸收关系的持久化**：只记在进程内，重启后改指不到时按目标缺失中止（第 5.7 节）。
- **什么值得写、不记干扰**：写入链路 Idea 第 2.4 节，在孵化中。
- **修订以外的维护**：提议归档、拆分、跨经历的归纳。
- **读的范围**：馆长仍只读中期库中的记忆本身，不读冷藏库、版本记录与其他话题的原始轨迹。
- **同一 Workspace 的馆长串行**：两次结算仍可同时运行，冲突由提交时的重放处理（第 5.4 节）。
- **管理页的手动编辑**：用户直接改的标题、摘要与标签不经过编辑集与漂移拦截。

## 3. 当前状态（2026-11-20 核对 master `9ab2b431`）

- **馆长**（`engines/generation/librarian.py`）：五个工具 `list_topic_writes`、`search_memories`、`read_memory`、`write_memory`、`finish`；以结算的 system actor 直接读中期库，只看得到 PUBLIC 记忆；`write_memory` 只暂存草稿，循环结束后返回草稿列表。动作无法解析、工具不存在或参数不合格时，把错误作为工具结果交回模型并计一步。预算是 `LibrarianConfig.max_steps`（缺省 12）与 `search_top_k`（缺省 5）；第一次评测中馆长平均每次结算约 8 步。
- **引擎**（`engine.py`）：`_process_librarian` 把暂存的草稿全部按新建交给 Familiar，不查重、不触碰、不提名合并。`_process_mode_c` 调用 `extractor.revise`，得到 `RevisionResult`（只有 `new_content`、`changelog` 与段），由 `_apply_update` 捕获修改前的完整快照、覆盖正文、并入贡献者，产出 `UPDATE`；结果与原文相同时降为 `TOUCH`；提供商失败或输出无法解析时回退：focus 带内容就把内容作为带日期的更新段追加到正文，只有指令就保留正文、记一条无内容变更的变更说明。
- **Mode C 的提示词**（`i18n/prompts.py` 的 `update`，中英文）：输入是标题、alias、当前正文、指令、新材料与参考上下文，没有摘要与标签；输出要求 `new_content` 是“完整的最终内容，不是 diff”，并按指令推断替换、细化或追加三种方式。
- **合并**（记忆生成第 4.1 节）：一次性生成与主动 WRITE 的草稿查重判为相似时先新建，再由合并任务把被吸收的记忆 N 并入保留的记忆 M。`extractor.merge` 让模型看两条记忆的标题、摘要、标签、类型与正文，并告诉它哪一条较新，输出完整的标题、摘要、标签、类型、正文与变更说明（`MergeResult`），较新的一条在实际中成了骨架；写回前重读两条，任一缺失、条件不满足或版本已变就以 `MemoryMergeAbortedError` 中止（原因 `memory_missing`、`not_mergeable`、`version_changed`、`model_output_invalid`），两条都保留；成功时写 M 的新版本（`update_source` 为 `"MERGE"`），再删除 N。提供商失败重试一次。
- **Familiar 的提交**（`patchouli/services/memory_generation.py`）：`_run_generation` 先调用引擎，对每个 `UPDATE` 结果执行 `_recheck_update_base`：它要求任务带 `update_focus`，否则抛出 `RuntimeError`；基础的内容版本与登记 UPDATE 时不同，就以 `MemoryUpdateBaseChangedError` 让整个任务失败。随后逐个提交；版本记录的 `update_source` 由任务来源决定，SETTLE 与 UPDATE 都映射为 `"UPDATE"`。
- **向量**：`vector_store._encode_vectors` 编译 `DENSE_EMBEDDING`（`Title / Type / Tags / Summary`）与 `SPARSE_EMBEDDING`；编译文本不变时只替换 payload、保留向量（`recompute_vectors`）。嵌入服务在 Patchouli 运行时中（`runtime/core.py` 的 `self.storage.embedding_service`），引擎与馆长都拿不到。
- **馆长的提示词**（`librarian`，中英文）：第三步写着“已有记忆缺少的新事实、决定或结论另写一条新记忆”，被推翻的说法因此成为新记忆；置信度一节写着“用户明确陈述或工具结果证实的高，主要由 AI 推理得出的低”。
- **观测**：每次馆长结算结束记一行 `馆长结算结束: end=…, steps=…, staged=…, total_tokens=…, tool_calls=…`，评测脚本按 `steps=` 与 `total_tokens=` 解析。

## 5. 目标设计

### 5.1 编辑集

```json
{
  "edits": [
    {"op": "replace", "field": "content", "old": "原文片段", "new": "新文"},
    {"op": "replace", "field": "title", "old": "5000 USD", "new": "3000 USD"},
    {"op": "append", "text": "追加到正文末尾的一段"},
    {"op": "rewrite", "text": "整篇新正文"}
  ],
  "add_tags": ["..."],
  "remove_tags": ["..."],
  "changelog": "一句话说明改了什么、为什么",
  "source_segments": ["2.3"]
}
```

- `replace` 用于 `content`、`title` 与 `summary`：`old` 必须在当前文本中逐字出现且只出现一次。`append` 与 `rewrite` 只用于正文：正文不进入索引，大段改写不会让检索漂移，整篇改写也不必逐字抄出全文。标题与摘要只有 `replace`，标签只有逐个增删。
- 编辑按顺序应用，后一处在前一处的结果上查找原文。应用编辑集是一个纯函数，放在 `engines/generation` 中，馆长的校验、馆长提交时的重放与 Mode C 共用它。它检查：原文逐字且唯一；结果的标题与摘要不超过索引上限（`MEMORY_TITLE_MAX_LENGTH`、`MEMORY_SUMMARY_MAX_LENGTH`），越界时拒绝而不是截断；`remove_tags` 必须是现有标签，`add_tags` 不与现有标签重复，结果至少保留一个标签；至少改了一处。不满足时返回指出第几处、什么原因的错误。
- 编辑集为空表示不需要改：Mode C 照旧降为 `TOUCH`，馆长不暂存。
- 类型、访问策略、alias 与来源主体沿用原记忆。

### 5.2 漂移拦截

- 一个共用组件：按 `DENSE_EMBEDDING` 编译修改前后两版；两段文本相同（只改了正文）时相似度为 1，不编码；否则用中期库编码向量的同一个嵌入服务编码两段文本，计算余弦相似度，低于阈值即拒绝。
- 阈值是 `patchouli.generation.revision_min_index_similarity`，馆长与 Mode C 共用。组件在组合时装配，嵌入服务取 `runtime/core.py` 的 `self.storage.embedding_service`，交给引擎（Mode C）与馆长。
- 比较的是这一次修改的前后两版，不与最初的版本比较。

### 5.3 阈值的校准

实施中、启用之前：

- 用第一次评测一次性生成的 628 次合并，按同一编译与嵌入计算合并前后的稠密相似度分布，作为“整条重写”的参照；
- 用试跑（第 8.3 节）中馆长的修订，计算替换数值、偏好、职位这类修改的分布；
- 取一个让后者基本通过、前者大部分被拒的值作为缺省值，分布与取值写进实施记录。

### 5.4 馆长修订

- **工具 `revise_memory`**：参数是 `alias` 加第 5.1 节的编辑集。校验在循环中完成，任何一条不满足都返回工具错误、计一步、不暂存：
  1. 这条记忆在本次运行中经 `read_memory` 读过（只改读过、能给出依据的记忆）；
  2. 本次结算还没有修订过它（一条记忆一次结算只修订一次，几处修改放进同一个编辑集）；
  3. 编辑集以读到的版本为底应用成功（第 5.1 节）；
  4. 漂移拦截通过（第 5.2 节）。

  通过后暂存一条修订：记忆 ID、读到的内容版本、编辑集与段；结果交回 `{"revised": alias, "index_similarity": …}`。
- **引擎**：馆长返回暂存的草稿与修订；修订以读到的版本为底应用编辑集，成为带修改前快照、结算贡献者与引用段的 `UPDATE` 结果，结果携带编辑集与读到的内容版本。
- **提交时的重放**（第 5.7 节的基础变化规则在馆长上的落法）：Familiar 对带编辑集、没有 `update_focus` 的 `UPDATE` 结果（只来自馆长）提交前重读这条记忆：
  - 已删除或对 system actor 不可读：丢弃这条修订；
  - 内容版本与读到时相同：照常提交；
  - 内容版本变了：把编辑集重放到当前版本上，成功就以当前版本为底提交（期间别处改的不是同一处），失败就丢弃；重放时不再做漂移拦截；
  - 丢弃只影响这一条，同一次结算的新建与其他修订照常提交；丢弃以 warning 日志记下记忆 ID 与原因（`missing`、`base_changed`）；
  - 访问策略沿用此刻的值，与 Mode C 相同。
- 提交沿用现有路径：推进版本与内容时间，重置置信度；版本记录的 `update_source` 沿用 `"UPDATE"`，来源是 system 结算，引用的段写入版本记录；编译文本变化时重算向量。

### 5.5 Mode C 改用编辑集

- **提示词**：输入加上摘要与标签；输出改为第 5.1 节的编辑集，删去“`new_content` 必须是完整内容”与三种更新方式的推断，改为：只改变化的部分，追加用 `append`，大部分内容都变了才用 `rewrite`；标题与摘要只在其中的说法变了时改。
- **校验与重试**：编辑集不合格或被漂移拦截时，把错误作为一条消息附上，再调用一次；仍不合格时走现有的回退（带内容就追加带日期的更新段、只有指令就记无内容变更），回退只改正文、不改索引。提供商失败与输出无法解析的处理不变。理由：UPDATE 的 ACK 表示意图已被接纳，内容不应因为模型没能写成编辑集而丢失；Mode C 没有工具循环，一次带错误的重试是它能有的最小反馈。
- **基础版本**：按第 5.7 节的基础变化规则：编辑集以执行时读到的版本为底计算；提交前重读，版本没变就提交，变了就把编辑集重放到当前版本上，成功就以当前版本为底提交，重放不了以 `MemoryUpdateBaseChangedError` 失败（原因码与读取句柄时的提示不变）。现在“登记时的版本与提交时不同就失败”的检查随之取消：那条检查是为整篇重写设的，写回会静默覆盖期间的修改；编辑集只改它引用的片段，期间别处的修改得以保留，改的是同一处时重放失败、照样失败。
- **外部契约**：MTP UPDATE 与 MCP `memory_update` 的参数、ACK 与句柄语义不变。agent 能观察到的变化只有：修订之后标题、摘要与标签可能随之更新。

### 5.6 合并改用编辑集

- **提示词**：输入是保留记忆 M 与被吸收记忆 N 的标题、摘要、标签、类型与正文，以及哪一条较新；输出改为对 M 的编辑集：补入 N 中 M 没有的事实，改掉 M 中被 N 推翻的说法（以较新的一条为准），标签只增加；N 已被 M 覆盖时输出空编辑集。删去“输出完整的标题、摘要、标签、类型与正文”，类型不再由模型重选，沿用 M。
- **校验与重试**：编辑集以合并开始时读到的 M 为底应用；不合格或被漂移拦截时，把错误作为一条消息附上，再调用一次；仍不合格以 `model_output_invalid` 中止，被拦截以新的原因 `index_drift` 中止，两条都保留。提供商失败的重试不变。
- **空编辑集**：N 的内容 M 都已有。M 的内容不变，仍按现在的规则写一个新版本记下这次吸收（贡献者取并集、N 的来源引用并入、变更说明写明已被覆盖），再删除 N；编译文本不变，向量保留。
- **写回**：写回前重读两条（第 5.7 节）：M 的版本变了就把编辑集重放到当前的 M 上，重放不了以 `version_changed` 中止；N 的版本变了直接以 `version_changed` 中止，要吸收的内容已经不同；任一条缺失或条件不满足照旧中止。成功时写 M 的新版本（`update_source` 仍为 `"MERGE"`），贡献者取并集，N 的全部来源引用并入 M，再删除 N，并记下“N 已被 M 吸收”；编译文本变化时重算向量。
- **来源**：合并提名来自一次性生成与主动 WRITE 的查重，两者都按这一规则执行；馆长不提名合并。

### 5.7 结局不取决于时序

- **合并依次执行**：Familiar 的合并路径以 Workspace 为键持有 `KeyedSerialGate`（`components/serial_gate.py`，Import Bus 与附件已在使用），从读取两条记忆到写回、删除都在门内。同一 Workspace 的两个合并不再同时写同一条保留记忆，也不会在模型调用期间删掉对方的目标；新建、修订与其他 Workspace 的任务不受这道门约束。
- **沿吸收关系改指**：合并成功时在进程内记下“N 已被 M 吸收”。合并开始时保留记忆不存在、而吸收关系里有它，就沿关系找到仍然存在的那条作为保留记忆，再检查合并条件（同一访问策略、不吸收自身）；找不到时按 `memory_missing` 中止。几次提名串成一串时，无论 N→M 与 N′→N 谁先执行，结局都是 M 依次吸收 N 与 N′ 的内容。
- **基础变化规则，三条路径同一条**：

  | | 基础的版本没变 | 版本变了、编辑集重放成功 | 重放不了 | 基础已删除或不可读 |
  |:---|:---|:---|:---|:---|
  | 馆长修订 | 提交 | 以当前版本为底提交 | 丢弃这一条修订 | 丢弃这一条修订 |
  | Mode C | 提交 | 以当前版本为底提交 | 以 `MemoryUpdateBaseChangedError` 失败 | 以 `ResourceNotFoundError` 失败（与现在相同） |
  | 合并的保留记忆 | 写回 | 以当前版本为底写回 | 以 `version_changed` 中止 | 先沿吸收关系改指，找不到以 `memory_missing` 中止 |

  失败的方式随路径不同，是因为三条路径对调用方的承诺不同：馆长的一次结算里有多条结果，一条失败不应连累其余；Mode C 对应 agent 的一次请求，失败要让 agent 知道；合并中止时两条都保留，不丢内容。
- **第一次评测中的 82 个中止**：串行与改指消除合并目标正等着被吸收的 58 个与同时写同一条记忆的 20 个；输出无法解析的 4 个由带错误的重试覆盖。剩下的中止应只有漂移拦截、合并条件不满足与重启后改指不到。

### 5.8 馆长提示词（中英文）

- **工作顺序**：前两步不变（先看本话题写过什么，再查库里相关的）；第三步按三种判断处理每一件事：已有记忆足以支持下次使用就不动；材料改变了某条读过的记忆的结论、适用条件或当前状态，就用 `revise_memory` 修订那一条；只有已有记忆承载不了的内容才 `write_memory` 新建。删去“已有记忆缺少的新事实另写一条”。
- **怎样写编辑**：修订前先读全文；逐字抄出原文片段，只改变化的部分；标题与摘要只在其中的说法变了时改；标签只增删受影响的；`rewrite` 只在大部分内容都变了时用。
- **工具说明与错误文本**：新增 `revise_memory` 的说明，以及“先读再改”“已经修订过”“编辑集不合格”“索引变化过大”四种错误。
- **助手正文中的事实**（候选默认）：助手转述的用户事实按用户的事实记，出处由段引用与置信度表达，正文不写“用户没有确认”之类的出处说明；助手自己的建议与结论，用户采纳了才记；与用户的说法矛盾时以用户为准。改动之后在提示词工作台上用日常的结算材料与 HaluMem 的材料各对照一次，日常材料上不应把助手编造的事实写成用户事实。

### 5.9 观测

- 馆长结算结束的日志行加上 `revised=` 与 `revise_rejected=`，原有字段与顺序不变（评测脚本按 `steps=` 与 `total_tokens=` 解析）。
- 馆长提交时丢弃的修订各记一行 warning（第 5.4 节）；Mode C 重试后仍走回退时记一行 warning，带原因（编辑集不合格或漂移）。
- 合并被拦截以 `merge_aborted.index_drift` 出现在生成 lane 的 `work.failed.reason` 与 `memory.task.failed.reason` 中，与其他中止原因相同。
- 评测脚本不需要改：驱动已把“本次会话更新过的记忆”记为 `updated`；合并前后的标题、摘要相似度与正文增长用实施记录中的一次性分析计算。

## 7. 兼容与迁移

- 不迁移数据：已有记忆照常可被修订，包括一次性生成写下、合并过的记忆。
- 不设开关：`settle_mode: librarian` 的实例升级后馆长即可修订；所有实例的主动 UPDATE 与合并都改用编辑集。阈值配置有缺省值，个人覆盖可以调整。
- 外部 harness 不需要更新：`memory_update` 的参数与返回不变；“基础已变”的失败只在改的是同一处时出现，比现在少。
- 选一次性生成的实例，提取不变，合并的结果变了：保留记忆的标题与摘要只做片段替换，原有细节不被覆盖；被拦截的合并留下两条；同一 Workspace 的合并依次执行。
- 关闭时保存、升级后继续执行的合并任务按新规则计算，载荷不变。

## 8. 测试和验收标准

### 8.1 不变量与归属层

1. 编辑集的应用：原文逐字且唯一、按顺序应用、`append` 与 `rewrite` 只用于正文、长度上限、标签增删、空编辑集；归属为应用编辑集的纯函数，单元测试在 `tests/unit/engines/generation/` 的现有文件中扩展。
2. 漂移拦截：只改正文时不编码、相似度为 1；低于阈值时拒绝；以假嵌入服务覆盖。
3. 馆长的校验：没读过、已修订过、编辑集不合格、漂移低于阈值时返回工具错误、不暂存、计一步；通过时暂存；`test_librarian.py` 以脚本化模型与假嵌入服务覆盖。
4. 引擎：馆长暂存的修订成为带修改前快照、贡献者与引用段的 `UPDATE` 结果，新建不受影响；Mode C 解析编辑集，不合格时带错误重试一次，仍不合格时走回退且不改索引，空编辑集降为 `TOUCH`；`test_engine.py` 与 `test_extractor.py`。
5. 基础变化规则（三条路径同一条）：版本没变时提交；变了且重放成功时以当前版本为底提交；重放不了时馆长只丢弃这一条修订、同一次结算的其余结果照常提交，Mode C 以 `MemoryUpdateBaseChangedError` 失败，合并以 `version_changed` 中止；基础已删时按第 5.7 节的表处理；`tests/unit/patchouli/services/test_memory_generation.py`。Mode C 现有“登记版本不同就失败”的用例随契约改写。
6. 合并：编辑集以 M 为底应用，类型沿用 M；不合格时带错误重试一次，仍不合格以 `model_output_invalid` 中止，被拦截以 `index_drift` 中止，两条都不变；空编辑集时 M 内容不变、写一个记下吸收的版本并删除 N；N 的版本变了时中止；`test_engine.py`、`test_extractor.py` 与 `test_memory_generation.py` 中现有的合并用例随契约改写。
7. 合并的结局不取决于时序：同一 Workspace 的两个合并不重叠执行；N→M 与 N′→N 以两种顺序执行时，结局都是 M 吸收了 N 与 N′；保留记忆已被吸收而进程内没有记录时以 `memory_missing` 中止；`test_memory_generation.py`。
8. 只改正文时保留向量，索引编译文本变化时重算；在第 5、6、9 条的用例中断言。
9. 端到端：一次馆长结算修订了一条已有记忆，库中是这条记忆的新版本、没有多出一条重复；一次主动 UPDATE 改了标题中的一个值，检索按新标题命中；同一次结算的两条草稿命中同一条记忆时，两次合并都落在这条记忆上，没有中止；`tests/integration/patchouli/test_memory_generation_pipeline.py`。
10. 提示词：中英文的键齐全，英文提示词不含中文字符；在 `tests/unit/prompts/test_generation_prompt.py` 中扩展。

### 8.3 实测与预注册

- **校准**：第 5.3 节，结果写进实施记录。
- **试跑**：用户 15 的前 10 次会话，馆长与一次性生成各一遍；馆长核对每次结算的修订数、被拒的次数与原因、提交时丢弃的修订，一次性生成核对合并被拦截与中止的次数；各人工看 10 条修订或合并是否只改了变化的部分、标题与摘要是否只动了那一处。
- **基线的评判输入**：第一次评测中完整度的输入没有编号；重判 `eval1-one-shot` 与 `eval1-librarian` 的完整度与准确度，让基线与新运行用同一种评判输入（共约 8,800 次调用）。
- **评测**：同一 5 人子集、同一生成与评判设置，馆长与一次性生成各跑一遍。跑之前在账本写下预注册（候选，计划评审时可以调整）：
  - 馆长：更新的正确率上升、幻觉率与遗漏率下降，“更新正确”逐用户至少 4/5 更高；完整度与全部记忆的准确度下降不超过 2 个百分点；不记干扰不下降；每次会话的新建条数下降。
  - 一次性生成：合并前后标题与摘要的文本相似度中位数明显高于第一次（0.69 与 0.53），每次合并后正文的增长倍数下降；`memory_missing` 与 `version_changed` 的中止接近 0（第一次是 51 与 27）；更新的幻觉率下降；完整度与全部记忆的准确度下降不超过 2 个百分点；报告合并被拦截与各类中止的次数。
  - 读数时参照评判本身的波动：更新类复判时有 7–13% 的判分会变。
- **Mode C**：HaluMem 没有主动写入，Mode C 由第 8.1 节第 4、5、9 条与日常使用验收：owner 的 harness 经 `memory_update` 改过的记忆，标题与摘要随之更新、没有漂移成另一件事。
- **日常使用**：owner 在日常实例上用馆长方式、主动 UPDATE 与主动 WRITE 的合并验收，不作为收尾的条件。

## 9. 风险与待决问题

- **模型写不准原文**：片段必须逐字匹配，馆长的错误会消耗步数，Mode C 与合并只有一次重试；先读再改与错误提示可以缓解。试跑中看错误率与步数，必要时调高 `max_steps`。
- **阈值的误拦与漏拦**：由第 5.3 节的分布决定；试跑中人工核对被拒的修订与合并。Mode C 被拒后走回退，索引不更新，回退的比例要看日常使用。
- **合并中止增多，重复留在库中**：讲的不是同一件事的两条记忆不再在写入时融合；一次性生成的库中留下的成对相似记忆可能增多，由评测报告的中止次数衡量，融合交给以后的维护。
- **合并等门占着 lane 的位置**：生成 lane 并发为 2，同一 Workspace 的第二个合并在门外等待时仍占着一个执行位，结算可能排在合并之后；评测中记录结算的等待时间，必要时把等门的合并放回队列而不是原地等待。
- **重启后改指不到**：吸收关系只在进程内；关闭时保存的合并若以已被吸收的记忆为目标，下次启动后按 `memory_missing` 中止，两条都保留。需要合并链跨过一次关闭才会出现。
- **两次结算同时修订同一条**：提交时重放；改的是同一处时后提交的那条被丢弃。
- **主动 UPDATE 的行为变化**：所有实例的 agent 修订之后，标题与摘要都可能改变；漂移拦截与片段替换限制了改动的幅度。登记版本不再必须不变，agent 的指令针对的是它当时读到的版本，执行时作用在之后的版本上；改的是同一处时重放失败，照样以“基础已变”失败。
- **提示词对助手正文的放宽**：可能让日常编码会话中助手编造的“用户事实”进入记忆；第 5.8 节的对照检查这一点。
- **花费**：修订要先读全文，馆长的 token 会上升；Mode C 与合并的重试多一次调用。评测中记录。
- 候选默认（不是 owner 的决定，计划评审时可以调整）：编辑集的形状与三种操作；工具名；一条记忆一次结算只修订一次；只改读过的记忆；馆长提交冲突时丢弃而不是让结算失败；Mode C 一次带错误的重试后走现有回退；合并一次带错误的重试后中止，新增原因 `index_drift`；空编辑集的合并仍写一个记下吸收的版本；合并的标签只增加；基础变化规则与三条路径各自的失败方式；Mode C 取消登记版本必须不变的检查；合并以 Workspace 为键串行、在门内原地等待；吸收关系只记在进程内；`update_source` 沿用 `"UPDATE"` 与 `"MERGE"`；不设开关；阈值的校准方法；助手正文的规则；重判基线的评判输入。
