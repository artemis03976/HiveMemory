# v0.8.1 话题的进展记录：话题停顿时写一条，话题池展示

> 状态：Planned（2026-11-25）。v0.8.1 短期记忆的第五份计划；设计依据见[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 3、4 节。

## 1. 背景和问题

话题现在只写不读：交互从会话流进话题，只被 Patchouli 用来生成记忆，回到这个话题的人或会话读不到“进行到哪一步”。短期记忆 Idea 第 3 节定下了话题的进展：已整理的部分（只往后追加的进展记录，每一条写自上一条以来推进了什么，并指回原文）加上未整理的原始交互记录。进展记录的一条怎样写也已经定下：输入是旧进展记录加新交互记录原文，输出是一段总结。

话题现在已经是一条只追加的日志（[MemoryLibrary 与存储层](../patchouli/memory-library.md#11-短期话题工作台)），进展记录的一条就是日志中的一种记录，写下即落盘。

这份计划先把进展记录写出来，并让它有第一个读者：话题池界面。owner 在日常使用中直接看到进展记录写得怎么样，用真实使用检验写法；agent 一侧的读取（按句柄拉取、两个时点的推送）各自另做计划。

## 2. 目标与非目标

### 2.1 目标

- 话题停顿时写一条进展记录：话题有自上一条以来还没整理的交互，且停顿超过阈值时，以旧进展记录加新交互记录原文生成一段总结，作为一条记录追加到话题的日志上，并附上指回原文的区间。
- 进展记录是话题的一部分：只往后追加，随话题的日志跨重启，随话题退役而消失。
- 话题池界面展示话题的进展：进展记录逐条列出，以及还没整理的交互。

### 2.2 非目标

- **会话切走这一触发**：多个会话并发进行时，一个会话离开话题不等于话题停下，判断逻辑还没有设计（短期记忆 Idea 第 9 节搁置项）。
- **agent 一侧的读取**：按句柄拉取、另一个会话回到话题时的推送、会话压缩之后注入索引，各自另做计划；每一条一句话的索引也随推送的计划再定。
- **一轮之内写一条**：暂缓设计（Idea 第 9 节搁置项）。
- **进展记录进入记忆生成**：结算材料不变，进展记录不作为生成材料。
- **长话题的旧条目**：全部保留、全部展示，怎样合并或截取是搁置项。
- **折叠**：折叠摘要的结构化另做计划；本计划只把折叠的调度与写一条的调度合成“话题的维护工作”（第 5.3 节）。

## 3. 当前状态（2026-11-25 核对）

- **话题**：每个话题是一条只追加的日志，有六种记录（`created`、`interaction`、`fold`、`settled`、`generated_memories`、`retired`），定义与套用函数在 `memory_library/topic_log.py`。短期存储为每种记录提供一个写入方法，在锁内读当前值、套用记录、追加一行、替换内存中的读取值；写入方法不检查话题的状态，同一话题的写入由 `TopicWorkingSet` 的 lease 串行。`TopicData` 是由日志组装的读取值，core 只保留模型与读取侧的派生（[感知与短期话题](../patchouli/perception.md#13-话题原始数据与工作视图)）。启动时重放全部日志（同一文档[第 7 节](../patchouli/perception.md#7-维护存储与启动时读回)）。
- **停下与空闲**：驻留话题的访问时间取单调时钟，交互应用与为写入确定话题时刷新，重启读回后从读回时重新计时。全局调度器每 30 秒（`perception_idle_flush_interval_seconds`）调用 `scan_idle_topics_once`，空闲超过 `idle_timeout_seconds`（随附配置 3600）的话题沉淀。没有“停顿”的触发。
- **折叠的调度**：交互应用后需要折叠时，交互提交队列排入一个折叠项（`TopicCompaction`），它与该话题的交互提交共用排序键，排在同一话题之后的提交前面；同一话题已有未结束的折叠项时不再排入；关闭时先关闭折叠。折叠在生成摘要期间持有 lease，写回经 `append_fold`。
- **模型**：折叠摘要经 `LLMRelayController` 调用 `patchouli.llm`，时限 `summary_timeout_seconds`（默认 60 秒）；提示词按语言取自 `i18n/prompts.py`。
- **话题池界面**：`GET /api/v1/topics` 经 root API 返回 `ActiveTopicResponse`（标题、话题摘要、折叠摘要、最后一轮、片段数、tokens、模型、最后写入时间、是否有未沉淀的交互）；详情展示“在聊什么”“较早内容的摘要”“最近一轮”。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-25）：进展记录的一条以旧进展记录加新交互记录原文生成一段总结（Idea 第 3 节）；第一份计划只带话题池界面这一个读者；会话切走的触发暂不实现。依赖均已是事实：话题的存储介质已经合并（PR #243）。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 进展记录的数据

- **读取值**：core 新增不可变模型 `TopicProgressEntry`，即进展记录的一条：`text`（正文）、`from_turn_id`、`to_turn_id`、`to_event_seq`（指回的区间：首轮标识 #0 到末轮标识 #末事件序号）、`covered_until`（这一条覆盖到第几个交互，即交互记录的前缀长度）、`written_at`。`TopicData` 新增 `work_record: tuple[TopicProgressEntry, ...]`，即整份进展记录，缺省为空。派生 `recorded_interaction_count`（最后一条的 `covered_until`，没有时为 0）；未整理的原始交互记录是它之后的交互。
- **日志记录**：`topic_log.py` 新增第七种记录 `progress_entry`（`TopicProgressEntryRecord`），内容是这一条的正文、区间与覆盖位置，时间取记录的 `at`。套用函数 `apply_progress_entry` 把它追加到读取值上，要求这一条从当前的 `recorded_interaction_count` 开始、`covered_until` 大于它且不超过交互数，否则构造失败。
- **写入方法**：store 新增 `append_progress_entry`，与其他写入方法一样在锁内完成；只认池中的话题，退役的话题不记（进展的读者是前台，退役话题对前台不可见）。
- 已有的日志没有这种记录，读回时进展记录为空。

### 5.2 什么时候写一条

- 新的维护扫描 `scan_paused_topics_once`，与空闲扫描一样由全局调度器定期调用（默认每 30 秒，可单独开关）：驻留话题的访问时间超过停顿阈值、且有未整理的原始交互记录时，为它排入一个“写一条进展记录”的维护项。
- 停顿阈值是新配置 `patchouli.perception.progress_record_pause_seconds`，默认 1800（30 分钟）。它小于空闲沉淀的 3600 秒，所以空闲时通常已经写过一条，空闲这一触发由停顿涵盖，不另外再写。
- 同一话题已有未结束的维护项时不再排入。某一条生成失败后，`TopicWorkingSet` 在进程内记下这次的覆盖位置，同一位置不再重试，等话题有了新交互再判断，避免提供商故障时每 30 秒重试一次。
- 关闭时不为停下的话题写一条（退出不等待模型调用）；重启读回之后，停顿计时从读回时重新开始，到时再写。
- 退役、丢弃的话题不写；进展记录随话题一起消失。

### 5.3 话题的维护工作：折叠与写一条共用一套调度

- 交互提交队列中的折叠项泛化为“话题的维护项”，分两种：折叠与写一条进展记录。两种都与该话题的交互提交共用排序键：生成期间到达的交互排在后面等待，不报占用冲突；同一话题同时至多一个未结束的维护项。
- 关闭时与现在的折叠一样先关闭维护项：排队中的直接结束，进行中的被取消，不改动话题。
- **写一条的执行**：读取话题的最新读取值，取旧进展记录与第 `recorded_interaction_count` 之后的交互（按生产的生成材料渲染，带话题内的轮次号），调用模型生成一段总结，再以 `append_progress_entry` 追加。
- **写一条不取 lease**：折叠持有 lease，是因为它折叠的是此刻工作视图的前缀，交互与结算都会改变它。写一条的前提只有“从当前的覆盖位置开始”，这个位置只有写进展记录会改，同一话题同时至多一个维护项，交互只往后追加，所以前提不会被别的写入破坏；`apply_progress_entry` 的位置校验兜住违反这一点的错误。模型调用期间，空闲沉淀与 LRU 照常取得 lease；期间话题被退役或删除时，`append_progress_entry` 找不到它，这一条不记。
- 写一条在完成时才追加：进程在生成中途退出时什么都没有写下，重启后停顿到时再写，不需要在途状态。
- 模型：`patchouli.llm`，时限沿用 `summary_timeout_seconds`。失败（提供商错误、超时、输出不合格）只记日志，原因码 `progress_record_failed`，不改动话题。

### 5.4 生成的提示词

提示词由 owner 定稿（方案一：输入是旧进展记录加新交互记录原文），放在 `i18n/prompts.py`；下面是中文版，英文版按它翻译，意思与结构不变：

```text
你在为一个进行中的话题总结并编写进展记录。话题是按语义内容聚合在一起的一段交互事件：可能是完成一项工作，也可能是一段讨论或闲聊。进展记录按时间排列、只往后追加，每一条写这个话题自上一条以来有了什么新进展。任何一个希望继续这个话题的人，在阅读进展记录之后，应当能够知道当前话题进行到了哪一步，并自然的将话题继续下去。当使用者需要更详细的背景信息时，你写出的进展记录应当能够起到指引的作用。

话题进入了阶段性总结环节，你会看到：
- [旧进展记录]：这个话题此前写下的进展记录，只作上下文，不改写，也不重复；
- [新交互记录原文]：自上一条以来的交互，每一轮标有轮次号。

请以[旧进展记录]（如有）作为参考，并依据[新交互记录原文]中发生的事件写出新的一条进展记录，用一段话写清：
- 这一段谈了什么、做了什么，得出了什么结果、结论或看法；
- 用户提出了什么要求、表达了什么想法，定下了什么。agent 提出、用户还没有确认的，写成 agent 的提议，不写成决定；agent 自己的分析与推论，也不写成用户的决定或已经确定的事实。

写法要求：
- 沿用原文中的说法与名称，不另起名字；具体的名称、编号与数值照原文写（例如文件路径、命令、书名、人名）；
- 旧进展记录写过的，不再写一遍；这一段里新出现的信息，即使与旧进展记录有关，也要写出来；
- 只写原文里有的事，不评价，不提建议。

只输出一个 JSON 对象：{"entry": "<这一条的正文>"}
```

提示词只有一份。没有旧进展记录时，用户消息中的 [旧进展记录] 一节渲染为“暂无”（英文版 “None”）。

### 5.5 话题池界面

- **先出样稿**：在设计画布“HiveMemory 运行页样稿”上加话题详情中进展的样稿，owner 审定之后再写前端代码。
- 候选：详情中加“进展记录”一节，逐条列出正文、写下的时间与覆盖的轮数；后面一句“还有 N 轮没有整理”，可展开为这些轮的用户消息与回复的节选。话题卡片可加一个进展记录条数的小标记。
- HTTP：`ActiveTopicResponse` 增加 `progress_record`（每一条的正文、指回的区间、覆盖的轮数与写下的时间）与 `unrecorded_turn_count`；领域快照 `TopicSnapshot` 同样增加这两项。Gateway 读快照但不渲染它们，行为不变。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| core 话题模型 | `TopicProgressEntry`；`TopicData.progress_record` 与派生量；`TopicSnapshot` 两个字段 |
| memory_library | 第七种日志记录 `progress_entry` 与套用函数 `apply_progress_entry`；store 的写入方法 `append_progress_entry` |
| Patchouli 感知 | `scan_paused_topics_once`；写一条的执行 |
| `TopicWorkingSet` | 写一条失败时的覆盖位置 |
| 感知引擎 | 写一条的模型调用与输出校验 |
| 交互提交队列 | 折叠项泛化为话题的维护项（折叠、写一条） |
| 调度与配置 | 新维护任务及其开关与间隔；`patchouli.perception.progress_record_pause_seconds` |
| 提示词 | 写一条进展记录的中英文提示词 |
| HTTP 与前端 | 话题列表响应的两个字段；话题池详情的进展 |

不涉及 Workspace 能力层的授权、公开 route 与事件：写一条以 Work Queue 的 `work.*` 事件出现在运行页，与折叠相同；记忆生成与结算材料不变。

## 7. 兼容与迁移

- 升级后已有的话题没有进展记录，停顿之后从第 1 个交互开始写第一条。
- 日志多一种记录，已有的记录与格式版本不变；话题列表响应只增字段。生成工作信封不变。
- 降级到不认识 `progress_entry` 的版本时，读到它的日志会整个移进 rejected 文件、话题不读回；降级本来就要求先删除话题目录（[安装与启动](../help/setup.md)）。
- 写一条会增加模型调用：只在话题停顿时、且有未整理的原始交互记录才调用，按日常数据，话题内停顿约每 11 天 41 次，加上空闲前的最后一次。

### 8.1 不变量与归属层

## 9. 风险与待决问题

- **写法要靠日常使用检验**：试验场的实验没有成立，写法只按设计固定；条目可能偏长，或漏掉回来时需要的细节。进展记录只追加，改提示词之后，新的条目按新写法，旧条目不必迁移。
- **成本**：每次停顿一次模型调用，输入随旧进展记录增长；长话题的旧条目暂不截取。
- **交互等待生成**：维护项与交互提交共用排序键，写一条的模型调用期间（至多 `summary_timeout_seconds`），同一话题新到的交互排队等待，与现在的折叠相同。写一条不取 lease，本身不需要排在交互之间；若等待成为问题，可以把写一条移出交互提交队列，由停顿扫描自己执行。
- **停顿计时近似**：访问时间在为写入确定话题时也会刷新；跨重启后计时重新开始。
- 待评审的默认值：第 5 节中的名字（一条是 `TopicProgressEntry`，整份进展记录是 `TopicData.progress_record`，日志记录因此叫 `TopicProgressEntryRecord`）；停顿阈值 1800 秒；空闲由停顿涵盖、不另写；失败后同一位置不重试；写一条不取 lease；界面的样式以样稿为准。

### 11.1 计划之外补上的实现细节

- **字段名**：第 5.1 节正文写 `TopicData.work_record`，是改名之前的残留；按第 9 节实现为 `TopicData.progress_record`。
- **一条的数据与校验**：`TopicProgressEntry` 不存起点，起点是上一条的 `covered_until`（第一条为 0）。`TopicData` 的构造校验逐条检查：`covered_until` 大于起点且不超过交互数；`from_turn_id`、`to_turn_id` 是起点与终点那两轮的轮次标识，`to_event_seq` 是终点那一轮最后一个事件的序号。第 5.1 节“从当前的 `recorded_interaction_count` 开始”因此由记录里的 `from_turn_id` 校验：写的一方按它生成这一条时所用的交互填写。违反时抛出 `ValidationError`，读回时这份日志整个移进 rejected。`recorded_interaction_count` 与快照的 `unrecorded_turn_count` 都在 core 派生。
- **不改写入时间**：`apply_progress_entry` 不改 `last_update`，与沉淀完成相同：进展记录整理的是已经接收的交互，不是话题接收的写入，话题卡片上的最近写入时间与读回时的驻留顺序都不因它变化。
- **Store 签名**：`append_progress_entry(belong_to, topic_id, *, text, covered, covered_until)`：`covered` 是这一条覆盖的那几轮，指回原文的区间由它们得出；`covered_until` 是覆盖之后的位置。
- **写一条的模型与开关**：新组件 `ProgressRecordWriter`（`engines/perception/progress_record.py`）由 Engine 持有，`generate_progress_entry` 委托给它，与 `generate_fold_summary` 委托给接力的写法相同；Engine 的 `writes_progress_record` 为假时停顿扫描什么都不排。第 5.3 节的“时限沿用 `summary_timeout_seconds`”：这个时限只在 `relay.engine.type` 为 `llm` 时存在，所以 Runtime 只在接力为 `llm`、且 `patchouli.llm` 配置了模型时创建写作者，接力为 `simple` 或没有模型时不写进展记录（`relay.enable=false` 只关折叠摘要，不影响它）。要求 JSON 输出；提供商失败重试一次（`complete_with_provider_retry`），整体在时限之内；输出不是带非空 `entry` 的 JSON 对象时抛出。失败不回退为规则摘要。
- **模型输入的渲染**：新交互每一轮写成 `[Turn N]`（N 是这一轮在话题中的轮次号，从 1 数起）加感知层的材料文本（`render_turn_text`），结局不是 completed 的轮次多一行 `[Outcome: …] This turn did not complete normally.`，与记忆生成视图相同，不印段标签。旧进展记录每条一行 `- 正文`，还没有写过一条时这一节写“暂无”（英文 “None”）。用户提示词的两段标题与系统提示词里的名字一致：`[旧进展记录]`、`[新交互记录原文]`（英文 `[Previous progress record]`、`[New interaction transcript]`）。
- **提示词**：第 5.4 节的中文版逐字放进 `i18n/prompts.py` 的 `_PROGRESS_RECORD_PROMPT_TEXT_ZH["system_prompt"]`（已用脚本与本计划原文逐字比对），英文版逐行翻译，行数与结构相同。提示词只有一份：起草时第一条要去掉两行，去掉之后“请以[旧进展记录]作为参考”一句仍指向不存在的输入，owner 决定改为“请以[旧进展记录]（如有）作为参考”（英文 “(if any)”），没有旧进展记录时那一节写 `previous_record_empty`（“暂无” / “None”）；第 5.4 节的正文与其后一句随之改写，写作者不再按语言删行。
- **停顿扫描的接线**：`scan_paused_topics_once(schedule_progress_entry)` 以参数取得排入函数，`PatchouliSystem` 用 `functools.partial` 把交互提交队列的 `schedule_progress_entry` 交给它再注册：感知在 runtime 中先于队列构造，队列又以感知为维护端口，扫描因此不持有队列。候选复用 `TopicWorkingSet.list_idle_candidates`（阈值换成停顿阈值），正被 lease 占用的话题这一轮跳过。新维护任务 `perception_progress_record`，配置 `scheduler.tasks.perception_progress_record_interval_seconds`（默认 30）与 `enable_perception_progress_record`（默认开启）；返回排入了的话题 ID，没有排入时调度器不发事件。
- **失败的位置**：`TopicWorkingSet.mark_progress_entry_failed` 与 `progress_entry_failed_until`，话题离开驻留时一并清除。生成抛出的任何异常都先记下位置再照常抛出，包括程序错误，避免同一缺陷每 30 秒重来一次；取消（关闭时）不是 `Exception`，不记。
- **维护项**：`TopicCompaction`、`TopicCompactionCodec`、`TopicCompactionPort` 改为 `TopicMaintenance`（`task` 为 `compaction` 或 `progress_entry`）、`TopicMaintenanceCodec`（kind `patchouli.topic_maintenance`，v1）、`TopicMaintenancePort`（多一个 `write_progress_entry`）；队列参数 `compaction=` 改为 `maintenance=`，`close_compactions()` 改为 `close_topic_maintenance()`，新增返回是否排入的 `schedule_progress_entry`。工作标识按种类保留前缀：折叠仍是 `topic_compaction:`（运行页按它归组为话题折叠），写一条是 `topic_progress_entry:`，运行页现在把它显示为单独的系统运行。失败分类的原因码改为 `topic_maintenance_busy`（只有折叠会遇到）与 `topic_maintenance_failed`：分类器只看得到工作的 kind；按种类区分的原因码 `topic_compaction_failed` 与 `progress_record_failed` 写在失败日志里（`reason=…, topic_id=…`）。
- **日志**：写下一条记 info（`topic_id`、覆盖的轮数、`covered_until`、正文字数，不记内容）；生成期间话题离开话题池时记 info，不报错。
- **HTTP**：`ActiveTopicResponse.progress_record` 的每一条是 `TopicProgressEntryResponse`：`text`、`from_turn_id`、`to_turn_id`、`to_event_seq`、`covered_until`、`turn_count`（这一条覆盖的轮数，由相邻两条的覆盖位置之差得出）与 `written_at`；`unrecorded_turn_count` 直接取快照。另加 `unrecorded_turns`（owner 2026-11-26 选择扩展话题列表响应，而不是另开接口）：还没有整理的交互中最近至多 3 轮的节选（`TopicTurnExcerptResponse`：`turn_number`、`user`、`assistant`），由 core 的 `TopicData.to_topic_snapshot` 取自交互记录（被折叠、还没有整理的轮次也在内），用户消息与回复各截到 200 个字符，超出时加“…”；条数与长度是 core 的常量 `UNRECORDED_TURN_EXCERPTS` 与 `TURN_EXCERPT_MAX_CHARS`。200 与 Gateway 渲染候选话题最后一轮时的截断长度相同，界面每段只显示两行。三项都是必有的响应字段；`TopicSnapshot` 同样带它们，Gateway 不渲染。
