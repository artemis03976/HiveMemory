# v0.7.0 A5：共享 Pending 与主动记忆写入

PendingAtom 解决的是所有 Actor 共有的资源问题：Actor 明确提出 WRITE/UPDATE，而正式 Memory 由后台异步生成时，如何在物化前读回意图、在结算后定位 canonical 结果，并避免读写不一致。它不是 Alice 专属机制，但现有 PendingAtomRuntime 还混合了 run/frame/action 关联，因此不能整体搬入 WorkspaceRuntime，也不能给外部 Actor 复制状态机。

本计划依赖 A1 access 与 A2 操作目录；与 A4-0 对齐 Topic 来源和 assignment，资源失效消费 A3。独立验收不运行 Alice，不要求 B 的 transport 或完整 Session 服务；Alice 延迟提交与运行收尾的实际切换归 A6。旧 WRX-0/1 的快照、任务归属、错误和主动提交路由继续复用，新 Pending 归属/输入差额不回写成已完成事实。

## 1. 目标边界

| 能力 | 目标权威 | 说明 |
|:---|:---|:---|
| Pending 意图登记、内容、状态、结算关联 | Patchouli 资源侧 | 唯一状态机，不依赖 Alice |
| 物化任务与 canonical 生成 | Patchouli generation/domain | 任务进度和 Pending 可读内容分开 |
| run/frame/action 关联、延迟提交、取消策略 | Alice workset/settlement adapter | 只持有引用和执行关联 |
| 外部输入/结果 wire | B 或 MTP adapter | 不复制 Pending 状态 |

Pending 不是 canonical Memory、也不是可淘汰 cache；资源侧持有不等于整个 Workspace 的 Actor 默认可读。全局 intent ID 负责定位，提交者、Workspace、operation 和内容可见性分别判断。

## 2. 共同流程与独立路由

```text
WRITE/UPDATE -> Pending 登记 -> 受权 Pending READ
  -> memory_intent.submit(PendingAtomMaterializeTask)
  -> 读取目标 Topic 的全部可用资料（允许空 blocks）
  -> 物化任务接纳 -> canonical revision / discarded / failed
  -> 失效派生 cache -> Pending 解析真实结果 -> 重新授权读取 canonical
```

`interaction.submit` 和 `memory_intent.submit` 是独立路由方法、独立 operation 和独立收据；可以由同一个 application service 承接，不要求两个类。旧 `InteractionPayload.materialize_tasks` 只作兼容迁移字段，最终不能让普通交互入口隐式执行主动物化。

共同输入继续使用 `PendingAtomMaterializeTask`：它的 pending alias、intent_id、source verb、identity scope 和 WriteFocus/UpdateFocus 具有跨 Actor 语义；`from_pending_atom()` 不能成为外部客户端前置依赖。ACK 必须区分 Pending 已登记、物化任务已接纳和 canonical Memory 已产生。

登记和物化提交是两个业务阶段，不强制两个客户端往返。Alice 可先登记、返回 ACK，稍后按运行策略提交；外部工具可组合登记和提交，但接纳失败时需说明已登记的意图如何读回/重试，不能返回模糊的整体 success。输入 scope 必须同时匹配 access 和已登记 Pending 的归属；不可借提交方法挪用别人的 intent_id。模型名的 Task 表示请求，不表示已经入队。

## 3. Topic 资料和 Session 关系

主动生成需要读取对应 Topic 在构建上下文时的全部可用 blocks、summary 和 provenance，再按领域预算编译；不能隐式退化为“最近五条”。Topic 为空时，有效 WRITE/UPDATE 仍可进入生成；Topic 读取失败、越权、scope 冲突和成功取得空资料必须区分。没有 Topic 或没有交互不等于没有有效主动意图。

已提供 Topic 时必须查询全部已应用的可用资料；没有提供 Topic 时，是允许无辅助 Topic 还是由领域准备空 Topic，在 A5-0 与 A4/A2 冻结。不能把“不存在或没有读取权限的 Topic”当成可省略 Topic。UPDATE 仍必须验证目标存在、授权和已知基版本；空交互不会免除这些前提。已折叠且未保存的原始 blocks 无法凭空恢复，原文保全由折叠专项负责，完整资料指当时实际可用的快照。

分支调查依据：`patchouli/control/memory_generation/coordinator.py` 的 `submit_active()` 曾使用 `recent_blocks(5)`；MemoryGenerationEngine 在没有上下文且没有 WRITE/UPDATE focus 时才跳过。A5 应保留生成引擎支持意图独立生成的方向，修正上游资料获取，而非让 adapter 自行拉 blocks。实施前复核代码差额及相关测试，不能把计划目标写成已具备能力。

Session/Segment 是可选的来源关联，不是 Pending 的必需执行容器。若调用方要求使用某个已应用 Segment，adapter 明确先提交/等待 A4 assignment，再提交 intent；不要把所有主动写入变成等待未来交互的全局屏障。待处理任务应固定其辅助资料引用，后续 Session 路由变化不能改写同一任务的上下文来源。

## 4. Pending 读取、结算和生命周期

| 阶段 | 对外语义 |
|:---|:---|
| WRITE 未物化 | 返回登记内容/焦点和 Pending 状态，不标成 Memory |
| UPDATE 未物化 | 返回修订意图、目标引用和已知内容；只有 instruction 时不伪造最终正文 |
| 接纳后 | 返回真实任务/领域阶段；Actor 断连不取消已接纳工作 |
| canonical 已产生 | 原 Pending 引用可解析真实结果，canonical 读取再次授权 |
| 原 canonical 引用 | 返回当前已提交版本；是否提示调用者自己的未完成修订另行冻结，不静默叠加 Pending 正文 |
| discard/fail/cancel/expire | 明确区别，不伪造成功引用、不自动重建意图 |

`task.observe` 不自动授予 Pending 内容或最终 Memory 的读取权。稳定 intent identity 用于响应丢失后的查询/重试；相同 identity 不同 payload 返回 conflict。通知事件仅作观测，不能作为唯一终态真相。当前实现不承诺跨重启恢复；若要引入持久化必须另立迁移计划。

Pending snapshot、materialization task、task result 和 settlement projection 分别保存交接信息，不复制终态推进器。结算须可从权威任务/领域结果核对，不能等待 Alice 订阅事件才变正确。提交前取消与接纳后取消有不同承诺，cancel 只开放领域支持的范围。并发 UPDATE 的版本冲突仍由 canonical 更新规则判断；Pending 的原意图可读不等于所有 search 已能看到最终 Memory，也不默认加入全局搜索。

## 5. 实施、测试与回滚

| 阶段 | 产出 | 验收 |
|:---|:---|:---|
| A5-0 | Pending 包边界、operation、可见性、登记/提交/解析收据 | 无 Alice run/frame 必填；session 可选；不默认 Workspace 全员可读 |
| A5-1 | 资源侧登记/read/resolve，Alice 只保存关联 | 无 Alice 读回 WRITE/UPDATE；只存在一份权威状态机 |
| A5-2 | memory_intent.submit 与全部 Topic 资料读取 | 空 blocks 可写；多于五个 blocks 不被静默截断；读取失败不当空 |
| A5-3 | generation、invalidation、结果观察、取消和 shutdown | 重复提交不产生第二 canonical；接纳后断连和关闭可解释；结算关联真实结果 |

integration 使用真实 Patchouli application、generation task/result、A3 invalidation 和 A1 access；覆盖无交互主动写入、Topic 缺失/越权/空、UPDATE 目标、Pending READ、重复键、响应丢失、过期和 Alice stop。旧/新状态机不得同时作为成功来源；回滚只切换 adapter，不删除已接纳 Pending。

### 5.1 实现前必须关闭的接口和迁移决定

| 决定 | 阶段与验收要求 |
|:---|:---|
| 资源侧包与运行时聚合 | A5-0 明确 Patchouli 权威实现及生命周期，是否物理参与 WorkspaceRuntime 聚合；不得含 Alice run/frame 管理或新增 Workspace 业务转发层 |
| 登记/read/resolve/submit | A5-0 给出独立签名、operation、提交者可见范围和 Session 仅作来源的规则；外部不依赖 RuntimeScope |
| intent identity 与幂等 | A5-0 冻结 ID 签发、客户端键映射、直接提交时登记关系、同键异载荷 conflict 与未知接纳查询 |
| 状态与收据 | A5-1/3 明确登记、任务接纳、结算的阶段、权威结果关联、内容读与观察权的差异 |
| Topic 与预算 | A5-0 冻结缺失/省略 Topic、快照时点、完整资料获取及超预算编译；不等待未来交互 |
| 运行清理与切换 | A5-1 与 A6-2 冻结旧 run drain/旧引用转接、alias/intent 兼容、延迟提交/取消策略；不修改其他 Actor 的 Pending |
| 保留期与关闭 | A5-3 冻结容量拒绝、期限、expired/unknown、关闭未完成任务的结果；不声称跨进程耐久性 |

这些是局部实现门禁，不重新讨论 Pending 的通用资源归属。接口冻结后按单一状态所有者逐步切换，必要兼容 shim 只委托同一实现并写清删除时点。`PendingAtomMaterializationTask` 是讨论时的泛称，实际共同模型沿用代码中的 `PendingAtomMaterializeTask`，不再创建同义类型。

## 6. 完成后的文档边界

Patchouli generation/pending 当前事实只在 A5 实现收尾后更新；A2 维护 API 入口，A6 维护 Alice/MTP adapter，B 维护外部协议。A5 不宣称 MCP、沙箱、耐久化或跨重启恢复已经交付。
