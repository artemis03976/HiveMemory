# v0.7.0 计划 A · WRX-0 边界冻结清单

本文是[计划 A 协调入口](./v0.7.0-workspace-resource-system-and-agent-execution-boundaries.md) WRX-0 阶段的配套实施文档，承载该阶段要求的产出：资源归属/领域权威矩阵、现有调用入口清单、canonical mutation 入口清单与失效缺口、目录落点、兼容矩阵、Pending 资源/执行边界决定，以及访问边界和 A 系列交接面到现有代码的映射。初始现状矩阵基于 `snapshot.commit` 所指提交核对；后续 WRX-1 分支进度在第 8 节单独记录，不反写为快照事实。目标设计由[A1 访问边界](./v0.7.0-a1-workspace-access-boundary.md)、[A2 资源读取与缓存](./v0.7.0-a2-workspace-resource-reads-and-caches.md)、[A3 Session/Topic](./v0.7.0-a3-conversation-session-and-topic-projection.md)、[A4 Pending](./v0.7.0-a4-pending-memory-intents.md)和[A5 API 收敛](./v0.7.0-a5-patchouli-unified-api.md)分别维护，本文只记录落到代码的证据与阶段决定。

本文属于计划工作文档（非当前事实）：实现完成并通过 WRX-7 收口后，其中仍然有效的边界结论应合并进事实文档，本文随父计划归档。

### 2026-09-17 计划拆分后的使用方式

本清单保留原调查时点、WRX 编号和当时的关闭/待验收记录，便于复用既有实现；本次未重新审计用户已经完成的 WRX-0/1。下文的“待 WRX-*”按[协调入口的阶段映射](./v0.7.0-workspace-resource-system-and-agent-execution-boundaries.md#1-子计划与旧阶段映射)转交 A1–A6，不再作为另一套活动排期。后续新决定和最新实施证据在所属子计划维护；本清单只做来源引用、严重错误更正和拆分追溯。

新增 Session、扩展 InteractionPayload/TurnEvent、排序、Topic 路由关联、结构化投影与 `ActorIdentity.session_id` 迁移由[A3](./v0.7.0-a3-conversation-session-and-topic-projection.md)承接，不属于原 WRX-0/1 的已完成范围。TopicData/LogicalBlock 的既有领域模型继续复用；新提交载荷不能强制外部 Actor 构造 Alice run 或内部 queue envelope。访问基线归 A1，读取与 cache 归 A2，完整 API 收敛归 A5，Pending 归 A4，消费者与旧 WRX-7 收口归 A6。

## 3. canonical mutation 入口清单与失效缺口

### 3.1 入口清单

以下为 canonical mutation 的全部入口。M1–M4 走 `MemoryManagementService` / `AgentProfileManagementService`，是面向用户管理的直写入口（调用方提供完整内容、Patchouli 直接 upsert）：它们是统一 invalidation 必须覆盖的失效来源，但**不承接** Memory intent 语义——Actor 的意图提交必须走第 7 节的生成提交链，由 Patchouli 决定生成、更新、合并或拒绝。

| # | mutation | 入口链 | 最终落点 |
|:--|:---|:---|:---|
| M1 | Memory create | `POST /memories` → `MemoryApplicationService.create_memory` → `PATCHOULI_MEMORY_CREATE` → `MemoryManagementService.create_memory` → 局部 `MEMORY_CREATE` → `memory_generation_familiar.create_external_memory` → `mid_term.upsert` | canonical revision 提交后**无任何派生 cache 失效** |
| M2 | Memory update | `PATCH /memories/{id}` → `update_memory` → … → `update_external_memory` → `mid_term.upsert` | 同上，无失效 |
| M3 | Memory delete | `DELETE /memories/{id}` → `delete_memory` → `memory_library.mid_term.delete`（route_bindings.py:73 直接绑定） | 同上，无失效 |
| M4 | AgentProfile create | `POST /agents` → `AgentApplicationService.create_agent_profile` → `PATCHOULI_AGENT_PROFILE_CREATE` → `AgentProfileManagementService` → 局部 `MEMORY_CREATE` → `mid_term.upsert` | profile cache 无失效（Profile update 经 M2 的通用 PATCH 发生，同样无失效） |
| M5 | Memory archive | 无用户入口；`engines/lifecycle/garbage_collector.py:143` 内部触发 → `MemoryLibrary.archive` | 无失效 |
| M6 | Memory revive | 局部 `MEMORY_REVIVE` 已绑定（route_bindings.py:94）但 **src 内无任何 requester，是死入口** | 无失效 |
| M7 | Materialization/settlement | active：ChatService → `PATCHOULI_FINALIZE_AGENT_RUN` → `PatchouliService.finalize_agent_run` → `GENERATION_SUBMIT_ACTIVE`；passive/generation 内部走 `GENERATION_SUBMIT_SETTLEMENT` → controller → `PendingAtomSettler.publish(PENDING_ATOM_SETTLED)` → 全局事件 → `AliceRuntime.on_pending_atom_settled`（alice/runtime/core.py:108） | **当前仅有的两条失效路径之一，且是唯一由 canonical 变化事件驱动、跨 run 生效的失效**：`_refresh_l1_cache_for_settlement`（core.py:145）按原 scope invalidate + 回填 |
| M8 | WorkspaceAsset 写入/revision | 上传 HTTP → `WorkspaceAssetApplicationService` / `AttachmentParseService` 直接持 `WorkspaceAssetCommandPort`（不经总线） | Store 即事实源，无派生 cache，语义自洽 |
| M9 | MTP UPDATE（run 内） | `KoakumaRuntime._handle_update`（mtp/runtime.py:775）→ `atom_cache.invalidate_alias`（注册 Pending 延迟捕获前防脏读） | 走 Alice 私有 cache 入口，非统一 port |

### 3.2 失效缺口结论（WRX-1/3 的正确性范围）

1. 调查时管理 API（M1–M4）改变 canonical Memory/Profile 后，Alice 侧两个派生 cache 会继续返回旧值，直到 settlement（仅覆盖 Pending canonical alias）或 LRU/进程重启；这与[A2](./v0.7.0-a2-workspace-resource-reads-and-caches.md)“任意受支持入口改变后旧缓存不得返回”的完成定义冲突。
2. 调查时仅有的两条失效路径（src 内 `invalidate_alias` 恰有两个调用点）：M7（settlement 事件驱动，跨 run 生效，覆盖 settlement 的 canonical alias）与 M9（MTP UPDATE 同 run 防脏读，只失效本次更新的 alias，不响应 canonical 变化）。两条都实现在 Alice 侧私有路径上（settlement consumer / MTP 执行器），不是统一 port，且都不覆盖 M1–M4 的管理入口；A2 承接统一失效的正确性要求。
3. M6（revive 死入口）与 M5（archive 无用户入口）暂无消费者，不需要本计划新增外部入口；但它们的实现路径必须接入统一 invalidation port，避免未来接入时绕过。
4. Asset 侧（M8）无派生 cache，失效需求为空；WorkspaceAsset facade 只需复用 Store 的 READY/revision/lease 语义。

## 4. 目录落点

以下保留原目录冻结结果，由 A2/A6 分阶段承接，依赖方向优先于目录搬迁：

```text
src/hivememory/workspace/          # 新包：进程级 Workspace 资源平面
  __init__.py
  runtime.py                       # WRX-2：聚合入口
  access.py                        # WRX-1：统一 admission / operation / access context
  ports.py                         # admission/cache/invalidation 内部协议
  projections.py                   # immutable cache snapshot；业务 DTO 归共享/领域契约
  services/
    memory.py                      # WRX-3：派生快照/cache 协作，可合并到 cache
    profile.py                     # WRX-3：派生快照/cache，不复制领域解析
    assets.py                      # WRX-2：WorkspaceAsset facade（委托 reader port）
    invalidation.py                # WRX-3：canonical change → derived cache invalidation
  cache/
    keys.py                        # WRX-3：显式 scope/resource key 类型
    atom.py                        # WRX-3：自 agent_runtime/aliases/cache.py 迁移
    profile.py                     # WRX-3：自 alice/runtime/profile_cache.py 迁移
```

组合入口保持 `system/assembler.py` + `system/runtime/workspace/`（AssetStore 原地不动）；`alice/workset/`（A4/A6 执行关联/提交适配）与 `agent_runtime/mtp/{adapter,resources,execution,tools}.py`（A6）在对应阶段创建。资源侧 Pending 的包与物理聚合方式按[A4](./v0.7.0-a4-pending-memory-intents.md)另行冻结；现有 `system/runtime/workspace/` 只保留 AssetStore 语义，不接收领域业务实现。

依赖方向按协调入口与 A1/A2/A5 执行：`workspace` 不导入 `alice`/`agent_runtime` 或 Patchouli 私有 store/familiar/controller/local route；消费者经统一 admission 使用既有 application/GlobalRoutes；Patchouli application 向内调用 local bus 并使用 Workspace 缓存设施。删除新增 Patchouli provider 层的要求。

## 6. Pending 资源与执行边界决定

完整设计只维护在[A4](./v0.7.0-a4-pending-memory-intents.md)，本清单记录迁移落点与证据：

1. 当前 PendingAtom 强制携带 `RuntimeScope`，登记、claim、结算和按 run 驱逐集中在 `agent_runtime/pending_atom/runtime.py`。目标是提炼资源侧通用状态，由 Patchouli 维护领域权威；run/frame/action 关联留在 Alice，不整体搬运现类或复制状态机。
2. `core/models/pending.py` 的 `PendingAtomMaterializeTask` 已不含 run/frame，继续作为共同提交输入。`from_pending_atom()` 不是唯一构造方式；不要求外部客户端创建 Alice PendingAtomRuntime，也不因复用 Pending 模型就认定存在 Alice 依赖。
3. Alice 的 `pending_aliases_by_run → claim_for_materialization → evict_by_run` 不能原样成为资源侧生命周期。WRX-5 将其改为执行关联管理与公开登记/提交/取消调用；已接纳意图不因 Alice run 清理而丢失。
4. `src/hivememory/alice/workset/` 可保留为执行适配落点；原“与 PendingAtomRuntime 同生命周期”的冻结结论撤回。资源侧包、登记/读取权限、可见范围和收据/保留期仍需按[A4](./v0.7.0-a4-pending-memory-intents.md)冻结。
5. 交互与主动意图分别路由，不强制两个 service。生成须取 Topic 全部可用 blocks，空资料不阻断有效 WRITE/UPDATE；[A4](./v0.7.0-a4-pending-memory-intents.md)记录现有 `recent_blocks(5)` 与目标的差异。
6. 无 Alice 验收增加 Pending 物化前读取和结算解析；只返回 task_id/任务状态不够。外部协议由 B 映射，耐久化和完整 MCP transport 不作为 A 前置。

## 7. 访问边界与 application 交接映射

管理员、Alice 与 Passive/外部 Actor 都先取得 WorkspaceAccessContext，由各自 adapter 完整透传给同一操作的 GlobalSystemBus 路由，再进入 Patchouli application。System 封装与 AliceBridge 只作调用侧适配，同进程不直接调用 Patchouli application 对象。WorkspaceResourcePort、DomainMutationPort、DomainResultPort 不再作为第二套业务入口。保留 ResourceInvalidationPort 等基础设施接口，不增加 Patchouli provider 包装。

### 7.2 四阶段检查与入口迁移

```text
受信入口建立 CallerPrincipal
  -> Workspace admission：可否代表该用户/Agent 进入此 Workspace
  -> Operation authorization
  -> Resource ownership / visibility
  -> Domain policy
```

前两项由 WorkspaceAccessBoundary 完成，后两项由资源所有者执行；application 验证 grant 与当前方法匹配。四个检查不要求四个 service。grant 不能仅在入口检查后丢弃，也不能让一次 interaction.submit 授权扩展成检索或管理能力。

| 入口 | 基线证据 | 目标路径与迁移检查 |
|:---|:---|:---|
| 管理 HTTP / 顶层 service | server/deps.py 为非 Agent 操作构造 system 标记；MemoryManagementService GET/LIST 采用 owner-management | 确认 principal → user → Workspace；显式 management operation → System service → 全局路由 → Patchouli application。无需具体 Agent，system 不是管理员凭证 |
| Alice/MTP | scope 经 run/frame/MTPExecutionContext 传递；AliceBridge 代理 Patchouli public routes | 根据可信运行代表关系取得对应 operation 的 access；代理完整透传；MTP/frame 权限只能收窄；不能把 run admission 当作永久通用 grant |
| Passive / 外部 Actor | ingest.py 冻结 scope；ingressor 直接提交 InteractionSubmissionQueue | 交互与检索分别授权；提交改走全局公开 application 路由；保留 dedup、backpressure、稳定 interaction_id 与延迟 flush 授权关联 |
| 任务查询/取消 | 基线 task API 仅凭 task_id；WRX-1 增加 task scope/submitted_by | 对所有 list/get/wait/cancel 入口绑定明确 operation；public API 缺 grant/归属时拒绝；任务可见不自动表示 canonical 资源可读 |

基线中 MemoryGenerationTask 投影缺 scope/actor 的问题，WRX-1 已补 identity_scope/submitted_by；这解决了结果归属信息缺口，不等于既有 application/全局路由已消费这些字段。剩余修正是沿统一入口落实授权检查，并由真实 bridge/application 集成测试验证。
