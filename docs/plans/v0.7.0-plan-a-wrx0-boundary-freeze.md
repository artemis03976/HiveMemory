## 3. canonical mutation 入口清单与失效缺口

### 3.1 入口清单

以下为 canonical mutation 的全部入口。M1–M4 走 `MemoryManagementService` / `AgentProfileManagementService`，是面向用户管理的直写入口（调用方提供完整内容、Patchouli 直接 upsert）：它们是统一 invalidation 必须覆盖的失效来源，但**不是** `DomainMutationPort` 的承接——Actor 的意图提交必须走第 7 节的生成提交链，由 Patchouli 决定生成、更新、合并或拒绝。

| # | mutation | 入口链 | 最终落点 |
|:--|:---|:---|:---|
| M1 | Memory create | `POST /memories` → `MemoryApplicationService.create_memory` → `PATCHOULI_MEMORY_CREATE` → `MemoryManagementService.create_memory` → 局部 `MEMORY_CREATE` → `memory_generation_familiar.create_external_memory` → `mid_term.upsert` | canonical revision 提交后**无任何派生 cache 失效** |
| M2 | Memory update | `PATCH /memories/{id}` → `update_memory` → … → `update_external_memory` → `mid_term.upsert` | 同上，无失效 |
| M3 | Memory delete | `DELETE /memories/{id}` → `delete_memory` → `memory_library.mid_term.delete`（route_bindings.py:73 直接绑定） | 同上，无失效 |
| M4 | AgentProfile create | `POST /agents` → `AgentApplicationService.create_agent_profile` → `PATCHOULI_AGENT_PROFILE_CREATE` → `AgentProfileManagementService` → 局部 `MEMORY_CREATE` → `mid_term.upsert` | profile cache 无失效（Profile update 经 M2 的通用 PATCH 发生，同样无失效） |
| M5 | Memory archive | 无用户入口；`engines/lifecycle/garbage_collector.py:143` 内部触发 → `MemoryLibrary.archive` | 无失效 |
| M6 | Memory revive | 局部 `MEMORY_REVIVE` 已绑定（route_bindings.py:94）但 **src 内无任何 requester，是死入口** | 无失效 |
| M7 | Materialization/settlement | active：ChatService → `PATCHOULI_FINALIZE_AGENT_RUN` → `PatchouliService.finalize_agent_run` → `GENERATION_SUBMIT_ACTIVE`；passive/generation 内部走 `GENERATION_SUBMIT_SETTLEMENT` → controller → `PendingAtomSettler.publish(PENDING_ATOM_SETTLED)` → 全局事件 → `AliceRuntime.on_pending_atom_settled`（alice/runtime/core.py:108） | **当前仅有的两条失效路径之一，且是唯一由 canonical 变化事件驱动、跨 run 生效的失效**：`_refresh_l1_cache_for_settlement`（core.py:145）按原 scope invalidate + 回填 |
| M8 | WorkspaceAsset 写入/revision | 上传 HTTP → `WorkspaceAssetApplicationService` / `AttachmentParseService` 直接持 `WorkspaceAssetCommandPort`（不经总线） | Store 即事实源，无派生 cache，语义自洽 |
| M9 | MTP UPDATE（run 内） | `KoakumaRuntime._handle_update`（mtp/runtime.py:775）→ `atom_cache.invalidate_alias`（注册 Pending 延迟捕获前防脏读） | 走 Alice 私有 cache 入口，非统一 port |

### 3.2 失效缺口结论（WRX-1/3 的正确性范围）

1. 管理 API（M1–M4）改变 canonical Memory/Profile 后，Alice 侧两个派生 cache 会继续返回旧值，直到 settlement（仅覆盖 Pending canonical alias）或 LRU/进程重启；这与父计划 2.3 节"任意受支持入口改变后旧缓存不得返回"的完成定义直接冲突。
2. 当前仅有的两条失效路径（src 内 `invalidate_alias` 恰有两个调用点）：M7（settlement 事件驱动，跨 run 生效，覆盖 settlement 的 canonical alias）与 M9（MTP UPDATE 同 run 防脏读，只失效本次更新的 alias，不响应 canonical 变化）。两条都实现在 Alice 侧私有路径上（settlement consumer / MTP 执行器），不是统一 port，且都不覆盖 M1–M4 的管理入口——即父计划 6.2 节"Alice settlement 不能是唯一失效入口"所指的现状：失效正确性目前既不统一、也不完整。
3. M6（revive 死入口）与 M5（archive 无用户入口）暂无消费者，不需要本计划新增外部入口；但它们的实现路径必须接入统一 invalidation port，避免未来接入时绕过。
4. Asset 侧（M8）无派生 cache，失效需求为空；WorkspaceAsset facade 只需复用 Store 的 READY/revision/lease 语义。

## 6. Pending 保留决定

按父计划第 9 节执行，落到本仓库现状的具体含义：

1. `PendingAtomRuntime`（`agent_runtime/pending_atom/runtime.py`）不迁移、不复制状态机；WorkspaceRuntime 不为其提供 Workspace 分区键，也不接受它作为正式资源。Pending 路径若访问正式资源，仍必须先经过对应 Workspace admission；这不改变 Pending 的 Alice 所有权。
2. 跨边界只交接不可变投影：`PendingAtomSnapshot`、`PendingAtomMaterializeTask`、`PendingAtomSettlement`（`core/models/pending.py` 已具备）；Patchouli consumer 经既有 settlement/task 路由读取，不直接操作 Alice store。
3. `AgentRuntime.finalize_run`（runtime.py:264）中的 `pending_aliases_by_run → claim_for_materialization → evict_by_run` 序列在 WRX-5 移入 Alice workset/settlement coordinator；coordinator 只协调交接，不拥有 Pending 状态机、canonical Memory 或 Workspace cache。
4. coordinator 包路径（父计划 15.2 开放决定 5）定为 `src/hivememory/alice/workset/`：它是 Alice 执行工作集的协调者，与 PendingAtomRuntime 同生命周期；不放在 system application layer，避免 System 层出现第二份执行状态。
5. Pending alias/intent_id/RuntimeScope/跨 run 可见性语义保持不变，本计划不改写 UUID/alias 生成与耐久化。

## 7. 第 5.6/5.7 节访问边界与交接面到现有代码的映射

所有入口先经过父计划第 5.6 节的 `CallerPrincipal`、Workspace admission 和 operation grant，再进入资源 ownership/visibility 与领域规则；内部端口（`WorkspaceResourcePort` / `DomainMutationPort` / `DomainResultPort` / `ResourceInvalidationPort`）不得合并，参数类型不得含 `PendingAtom`、Alice frame、MTP parser 或外部 wire model。与现有入口的对应关系：

| 端口 | 现有承接（无 Alice 可调用性） | 需要的解耦（WRX-1） |
|:---|:---|:---|
| `WorkspaceAccessBoundary` | 当前各入口临时解析 `IdentityScope`，尚无统一 admission/operation grant 服务 | 新建最小内部边界；建立 `CallerPrincipal` → 已验证 `WorkspaceAccessContext`，覆盖 Alice、Passive、主动资源和结果查询；外部认证材料由 B 映射，不下沉为资源模型 |
| `WorkspaceResourcePort` | 读取侧复用 `RetrievalFamiliar`（R1–R6）与 `WorkspaceAssetReaderPort`（R5）作为低层 provider | 新建端口与 immutable snapshot；provider 直接绑定 Patchouli 服务实例，不经 Workspace facade 递归；只接受已验证 access context |
| `DomainMutationPort.apply_interaction` | `PerceptionFamiliar.apply_interaction`（patchouli/services/perception.py:76）；passive 链已经过 `InteractionSubmissionQueue` 脱离 Alice 调用（system/assembler.py:244） | 提取语义等价的请求/结果 DTO（现签名直接使用内部模型；确认其无 Alice 私有类型后原样暴露） |

### 7.1 访问边界冻结记录与三种入口核对（2026-09-16 复核）

对应父计划 5.6 节设计与 WRX-0 验收项"冻结检查顺序并核对 Alice/Passive/主动资源三种入口"。冻结的检查顺序（父计划 5.6.2）：

```text
受信入口建立 CallerPrincipal
  -> Workspace admission：principal 能否代表该 Actor 进入该 Workspace
  -> Operation authorization：该 operation 是否在 grant 能力内
  -> Resource ownership / visibility
  -> Domain policy
```

四次检查层之外，principal 建立是受信入口的前置动作；canonical mutation 的内部失效通知不做 Actor admission（父计划 5.6.2）。access-context 受控工厂、operation 枚举与 admission 代码落点由 WRX-1 确定（父计划 15.2 第 9 项；4.1 目标树未指定 admission 文件名，允许在 `workspace/` 包内按实现命名）。任务投影必须补齐归属信息或显式拒绝无 scope 查询（父计划 5.6.4），证据见下。

三种入口的当前状态与目标核对：

| 入口 | 当前 IdentityScope 来源（代码证据） | 当前缺失 | 目标路径 |
|:---|:---|:---|:---|
| Alice 进程内执行链 | HTTP 路由层 `resolve_request_identity_scope`（server/deps.py:149；chat.py:56,150 等）冻结 scope → `AgentRunContext` → `runtime_scope` → `MTPExecutionContext`；CALL 复用 caller scope | 无 `CallerPrincipal`/admission/operation 概念，进程内调用直接携带裸 `IdentityScope` | `local-process:alice-runtime` 类 principal 经同一 admission 工厂换取 access context（父计划 5.6.4），run scope 冻结时一并冻结 grant |
| Passive ingress | `server/routers/ingest.py:36,59` 路由层解析 → `PassiveIngressService` → Gateway/retrieval → `InteractionSubmissionQueue` | 同上；消息 provenance（"某用户说过"）与 authenticated Actor 未分层 | 受信入口建立 principal → admission → `interaction.submit` 能力；provenance 仍只作来源声明 |
| 主动资源操作（管理 HTTP + 任务查询） | memories/agents/topics 路由同样经 deps 解析；`MemoryManagementService` 读取无条件 owner-management 语义（见 R7 修正）；任务查询仅凭 task_id | 管理读取与 Agent 读取共用 `RetrievalFamiliar` 入口；任务 list/get/cancel/wait 无 scope | 管理操作走显式 management operation；任务查询走 `task.observe` 能力 + 带 scope/提交者投影的查询入口 |

任务投影缺口的代码证据（对应父计划 5.6.4）：`MemoryGenerationTaskSpec` 持有 `identity_scope` 且注释声明其为"唯一的身份/ownership 来源"（control/memory_generation/models.py:77-91），但对外投影 `MemoryGenerationTask`（models.py:108-127）不含 scope/actor 字段；`MemoryTaskManagementService` 的 list/get/cancel/wait 全部只接收 task_id（application/memory_task_management_service.py:19-50）；全局路由 `PATCHOULI_MEMORY_TASK_LIST/GET/CANCEL` 由 `system/application/memory_task_service.py:27-37` 无 scope 调用。WRX-1 必须补齐投影或在查询入口显式拒绝跨 scope/无 scope 请求，二者择一不得含糊。
