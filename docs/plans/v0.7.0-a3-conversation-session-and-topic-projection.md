# v0.7.0 A3：Conversation Session 与 Topic 投影边界

外部 harness 通常拥有确定性的 session/conversation，而 Patchouli 需要根据内容把交互分配到 Topic，以便组织记忆生成资料。两者都是有意义的分桶，但回答不同问题：Session 负责对外会话连续性、顺序和展示；Topic 负责记忆侧的相关性划分和短期工作集。A3 冻结这个数据模型和交接时机，不在本计划内完成完整折叠算法；折叠和原始证据专项由[独立计划](./topic-folding-context-and-raw-evidence.md)承接。

## 1. 目标与非目标

目标是让 System、Alice、Passive 和外部 adapter 都能提交同一种 `ConversationSegment`，让 Patchouli 内部继续产生 `LogicalBlock`、`TopicData` 和 Topic assignment；让 Session 历史可以跨多个 Topic，而不把全部历史自动送入模型。非目标包括：把 Session 变成 Topic 的另一份 canonical store、要求外部 Actor 构造 Alice 的 `TurnRecord`、在本计划内决定摘要算法、实现全历史导入或替换外部 harness 的上下文压缩。

本计划仅依赖 A1 的访问基线与既有 Topic/队列/Asset 契约，交付公共模型、最小 Session 记录/封口协作、Patchouli 内部投影、Topic/interaction 公共路由及真实组件验证；不交付完整会话管理 UI、耐久历史库、分支编辑器或通用事件重排平台。既有 Alice/Passive 的内部输入转换在本计划提供，生产运行路径切换由 A6 实施；B 负责外部 wire schema、完成信号和兼容接口。第 4 节是 Topic prepare/handle、assignment、条件清理和资料引用交接的唯一生命周期定义；A3-0 冻结、A3-2 实现并公开对应 API，模型与路由在本计划内完整交付。后续主动生成和 API 目录消费这份成果，不参与决定 A3 能否完成。

代码依据：`core/models/identity.py` 保留兼容 `session_id`；`core/protocol/models.py` 的 `InteractionPayload` 混合事件、物化任务和价值信号；`core/models/interaction.py` 已有可选 `action_id` 的 TurnEvent、ActionReducer 和 TurnRecord；`core/models/topic.py` 的 LogicalBlock 内嵌 TurnRecord。`patchouli/application/interaction_submission_service.py` 使用 `topic:{requested_topic_id}` 排序；`system/services/passive/models.py` 已有 source、external event/turn、occurred_at、sequence、is_final。以上是分支调查入口，不能据此声称新的 Session 模型已实现。

## 2. 数据模型

下列字段是目标语义草案，A3-0 须冻结类型、必需性、长度/容量、缺省和兼容样例后实施；不是已发布 schema。`ConversationPart` 暂作最小事件的概念名，应优先检查能否扩展或复用现有 TurnEvent 的中立字段，避免同时维护两套等价事件类。`ConversationSegment` 作为共同交互概念；若最终保留 `InteractionPayload` 类名，必须承载相同语义且退出旧混合职责，不长期保留两份内容真相。

### 2.1 ConversationSession

```text
ConversationSession
  session_id
  source
  external_conversation_id
  workspace_ref
  state: open | paused | closed
  ordered_segment_refs
  optional route_cursor_projection
  created_at / updated_at
```

Session 是由用户或调用软件控制的会话总容器，维护稳定来源、顺序、生命周期和历史引用。它作为 Workspace 归属的会话资源，由 System 会话服务持有本地记录，adapter 负责输入与生命周期触发；Patchouli 不持有第二份完整历史。外部 harness 仍拥有自己原生历史，本地只记录它交付的部分，不能宣称获得未提供的完整会话。Session 的管理/读取同样经过 A1 与资源 policy。

`ordered_segment_refs` 表达逻辑顺序，不要求把全部历史装进一个无限增长对象；分页、记录保留范围和容量在 A3-0 冻结。进程内首版只承诺实际保存窗口。会话资源不能当派生 cache 随便淘汰；删除/关闭 Session 不默认级联删除已形成的 Topic 或 Memory，provenance 引用过期时明确不可回查。

Session 不在事务上拥有 Topic，也不把 `session_id` 继续塞进 `ActorIdentity` 作为身份事实。目标是在 `SessionRef`/`InteractionContext` 中携带 session；现有 `ActorIdentity.session_id` 仅做兼容读取，最终迁移由契约和代码一起完成。不同来源相同 external_conversation_id 不合并；受信 source namespace 与 Workspace、用户的映射构成 Session 定位坐标，消息声称的 speaker 不授予 Session 访问权。

### 2.2 ConversationSegment

```text
ConversationSegment
  segment_id
  session_ref
  ordinal / sequence
  started_at / completed_at
  completion_state: completed | partial | cancelled | failed
  seal_reason
  parts
  topic_routing_directive
  source_metadata
  optional execution_reference
  optional execution_projection
```

Segment 是已经完成或明确封口的一次完整交互，是跨 Actor 的共同提交输入。它可以包含普通消息、助手回复、工具调用和工具结果；它不是 Alice run，也不要求一个特定 prompt history。`segment_id` 是交互幂等和 provenance 的稳定关联，Session 顺序由 Session key/segment sequence 保证，不能继续简单使用 `topic:{topic_id}` 作为外部会话排序键。

开放段是 accumulator 的可变工作记录，公开提交的是封口后的不可变快照。`completion_state` 描述该交互的实际结束结果，`seal_reason` 描述为何封口，两者都不表示 Patchouli 已接纳。取消/失败也可有可保存内容，不应因没有成功 final reply 而丢弃全部记录。一个 Segment 不硬性要求恰好一条 user 和一条 assistant；可包含多条消息或不完整工具事件。

### 2.3 ConversationPart

```text
ConversationPart
  part_id / sequence
  kind: user_message | assistant_message | system_message
         | thought | tool_call | tool_result | external_summary | unknown
  role / content / occurred_at
  tool_name / tool_args / call_id / parent_call_id
  status
  source_metadata
```

Part 是外部事件的最小通用表示。未知或缺少关联的工具事件必须保留为 Part，不因无法构造完整 action 而丢弃或伪造关系。source、occurred_at、received_at、外部 event id 和 connector provenance 是来源元数据，不是 Actor 认证凭证。

工具相关字段只适用于相应 kind，schema 应按类型约束，避免所有字段随意可空。`call_id` 用于关联原始工具调用，不要求等于 Alice action_id；delta/chunk 在开放段合并为消息或显式分片后才投影，不把每个 token 伪装成独立动作。附件沿用 ref、revision 与实际使用快照，不把图片/文件强制塞进文本。`thought` 仅保留调用方实际提供的信息，不要求外部 harness 暴露内部推理。

## 3. Session 与 Topic 的边界

| 对象 | 负责 | 不负责 |
|:---|:---|:---|
| ConversationSession | 对外连续性、历史顺序、open/paused/closed、展示索引 | 记忆生成的相关性、Topic 摘要和模型工作集 |
| ConversationSegment | 一次封口交互、Part 顺序、来源、提交幂等 | 直接决定最终 Memory 或强制绑定一个用户 Topic |
| Topic | Patchouli 内的记忆材料分桶、blocks、summary、working set | 外部 session 生命周期和全量对话展示 |
| LogicalBlock | Segment 转换后的 Patchouli 内容投影 | 保存整个 Session 或代替原始来源 |
| TopicData | Topic 内容事实、blocks、summary、bindings 的不可变快照 | 保存执行器 prompt history |

一个 Session 可以跨多个 Topic；首版 Segment 默认只应用一个 primary Topic，避免拆分一次工具动作并重复记忆生成。跨 Topic 拆分 Segment 属于后续算法决定，不自动进入本计划。Topic 的资源归属仍是 Workspace；Session→Topic 只保存路由关联，不新增 Topic 的 Session owner。

新 Session 的自动路由候选默认限制在已关联 Topic；需要复用另一 Session 的 Topic 时显式选择并授权 attach。这个默认方向必须在 A3-0 用现有 Alice/Passive 样例确认：不能把它误做新的资源硬隔离，也不能直接重写旧 Workspace 范围 Topic 的归属。迁移期保留 legacy 路由规则并明确版本；跨 Session 关联只改变可选路由范围，不合并 Session 历史。

`LogicalBlock` 可以保存 `session_ref`、`segment_id` 和 source provenance 引用，但不复制整个 Session。既有 blocks/summary/bindings 和 TopicData 快照保持 Patchouli 领域语义；新增关联优先使用兼容字段或独立关系记录，不能为此重写整个 Topic 存储模型。

## 4. Topic 路由指令与交接

本节集中定义 Topic 交接生命周期，包含没有 Session 的 prepare/主动意图场景，不意味着 Topic 属于 Session。本计划同时维护这部分的公开方法、总线路由映射、operation 绑定和领域实现；后续目录与生成侧只引用本节，不另行决定 handle/assignment 的有效性、清理或来源绑定。

首版指令采用窄判别模型：`auto`、`continue(topic_id)`、`explicit(topic_id)` 和 `new`。交互路由处理产出独立的关联结果：

```text
TopicAssignment
  segment_id
  topic_id
  route_reason
  router_revision
  confidence
  manual_override
```

这些是待 A3-0 冻结的内部指令，不意味着当前已提供同名外部接口。`auto` 在允许的候选中判断；`continue` 将上次 Topic 作为提示，允许明确的改路由；`explicit` 在通过授权后固定目标；`new` 强制新建并排除自动并回相似 Topic。若 `continue/explicit` 在真实调用中没有不同语义，应合并枚举，不能留下两个同义分支。confidence/router_revision 只有路由器实际提供时才返回，不伪造精度和版本。

用户新建 Session 只创建会话容器；显式新 Topic 才约束内层路由。清空 Actor prompt context 也不等同删除 Session 历史或 Topic，adapter 若还要强制新 Topic 须另发 `new`。这让手动选择和自动路由遵循显式优先级，避免“标题相似”覆盖用户选择。UI 按钮、会话分支与批量重路由另行规划。

若在 prepare 阶段已经得出路由，应返回稳定的 prepare handle，submit 时携带该引用，避免前后重新路由造成不一致；它与交互路由结果 TopicAssignment 的区别见第 4.2 节。未调用 prepare 的 Segment 可按携带的路由指令在提交后处理；handle 失效不能被偷偷改写成“未提供 handle”。adapter 不把外部 session_id 伪装成 topic_id。

交互流程是：

```text
外部事件 -> Session 开放 Segment -> seal/flush
  -> A1 access + 本计划的 interaction.submit 公共路由
  -> Patchouli 接纳 Segment、路由 Topic
  -> Segment -> LogicalBlock / TopicData
  -> 返回 TopicAssignment 与交互收据
```

Session 服务保证输入去重和开放段的本地顺序；Patchouli application 必须独立验证 Segment 提交幂等与顺序，不能完全相信 adapter。重试复用稳定 segment/interaction identity，服务端绑定 Workspace、来源及规范化载荷，同键不同内容报 conflict。Session 序列化与 Topic mutation 串行是两种约束：同 Session 跨 Topic 仍按交互顺序路由，不同 Session 显式 attach 同一 Topic 后仍由 Patchouli 的 Topic 占用/lease 保证安全，不为此引入第二套通用队列拓扑。

二者不使用跨领域大事务，而通过稳定 ID、assignment、幂等和关联记录交接。接纳时可能还没有最终 assignment，初始收据只报告 accepted；路由后可关联 assignment，是否已应用仍由交互收据单独表达。已接纳且应用成功的重试必须定位同一结果，不能重新创建 Topic/block。prepare、接纳、应用和清理之间的约束统一见第 4.3 节；具体待决项只在第 4.5 节冻结。

### 4.1 分开维护的状态与迟到事件

| 对象 | 状态由谁推进 | 与其他状态的关系 |
|:---|:---|:---|
| Session | System 会话服务；open/paused/closed | 不等于 Actor 正在运行或 Topic 已 settle |
| 开放段/封口快照 | adapter + Session accumulator；open→sealed，附 completion outcome | sealed 不等于已接纳或成功回复 |
| interaction 提交 | Patchouli application/queue；accepted→applied/failed | applied 不保证生成 Memory |
| Topic assignment | Patchouli 路由/应用结果 | 对同一已应用 Segment 稳定，不成为访问凭证 |
| Memory/Pending 物化 | Patchouli 领域任务；属于后续消费 | 独立于 Session 关闭和普通交互结果 |

同一结束信号重复到达返回已有封口/提交关联。未接纳时保留封口快照，响应丢失后用同一 ID 查询或受控重试。迟到消息/工具结果不能改写已接纳 Segment：首版显式拒绝/报告迟到，或由调用方以新 Segment 带来源引用补交；具体支持方式在 A3-0 选择，不隐式 reopen 或重放整个交互。sequence 缺口、乱序和时间戳冲突需定义可接受窗口/拒绝策略，不承诺任意自动重排。

### 4.2 Topic 引用词汇与责任

下表统一既有计划中 handle、assignment reference 和 Topic 快照的含义，不要求为每个概念新增一个服务或 Python 类。

当前 `TopicManagementService.prepare_topic()` 返回 topic_id 字符串，旧 `cleanup_prepared_agent_run()` 还依赖 PreparedAgentRun、新建标记与交互接纳状态。本节 handle 是目标交接语义；旧字段如何承接它在第 4.5 节冻结，不宣称现有实现已有 handle 注册、预留或过期机制。

| 对象 | 表达什么 | 不代表什么 |
|:---|:---|:---|
| Topic identity/ref | Workspace 中的具体 Topic 身份 | 访问许可、资料版本或某次交互已应用 |
| prepare handle（原 route handle） | 一次准备操作的稳定路由交接引用，绑定原 scope、路由决定及必要关联 | TopicAssignment、内容快照或永久有效的访问凭证；是否预创建/预留 Topic 仍待冻结 |
| TopicAssignment | Segment 与 Topic 的路由关联及可用路由来源信息；对已应用 Segment 稳定 | prepare handle 的别名；存在 assignment 不单独证明 blocks 已应用 |
| interaction receipt | 交互接纳、应用或失败及其关联结果 | Topic 的整个生命周期，也不等于 Memory 已生成 |
| TopicData/资料快照 | 某一读取时点实际可用的 blocks、summary、bindings/provenance | 永远新鲜的内容、全部 Session 历史或完整原文档案；router_revision 也不是内容版本 |
| 主动意图的 Topic 资料绑定 | 该意图实际选择的 Topic 来源及资料快照关联 | Session 的可变 route cursor；不默认依赖 prepare handle 持续存活 |

Patchouli 拥有 handle 的验证、路由关联、资料读取及条件清理语义；本计划负责 Topic 领域实现，后续 API 目录和主动生成只是消费者，不产生新的运行时所有者。System/Actor adapter 持有引用并请求操作，不能凭“由我 prepare”绕过后续授权，不能从 handle 字符串自行推断 Topic 身份和清理权限。handle 也不默认等同于 Asset lease 或 Topic 排他锁。

### 4.3 prepare → submit/apply → cleanup 生命周期

以下是行为约束和责任转移，不是提前增加一套固定状态枚举。prepare 是需要预先选定 Topic 的调用方可使用的步骤；普通交互和主动意图不因本表被强制增加一次 prepare 往返。

| 阶段/触发 | 必须保持的行为 | 后续责任 |
|:---|:---|:---|
| prepare 成功 | 通过当前访问检查；以稳定 handle 交接路由决定；记录本次是否创建了资源的真实结果 | 是否预创建/预留、重复 prepare 的关联键与有效期由第 4.5 节冻结 |
| 尚未提交或接纳结果未知 | 调用方保留原 handle、封口内容和提交 identity；响应丢失先查询/受控重试 | 结果未知不能推断为未接纳并清理；不悄悄换 Topic |
| interaction.submit 校验与接纳 | 验证 handle 的 scope、关联、有效性及与请求指令的一致性；无 handle 按公开路由指令处理 | 接纳后由 Patchouli 接管已承诺的领域工作和必要 Topic 保护；adapter 断连不撤销 |
| interaction apply | 使用已确认的路由关联应用 blocks；重试复用同一交互结果 | 路由结果与 applied 分别观察；应用成功固定关联，不重复创建 Topic/block |
| prepare 放弃、调用方失败或 handle 到期 | 可请求释放准备关联；若曾预创建 Topic，是否回收由领域条件检查决定 | handle 失效/释放不等于删除 Topic，不撤销已接纳工作 |
| 领域处理失败后的补偿 | Patchouli 根据实际应用、接纳和占用事实判断是否可回收 | adapter 不以通用 evict 代替条件清理；已经应用的交互与后置物化结果仍各自成立 |

条件清理只面向本次准备可回收的资源：复用的既有 Topic 不因当前调用方失败被删除；预创建 Topic 也须在同一领域并发边界检查仍为空、没有已接纳工作或其他有效占用需要它，满足条件才清理。不能由 adapter 先读取“为空”再无条件 evict。具体占用/保留实现和“空”的判定在第 4.5 节冻结，不要求新增通用 lease 系统。重复释放/清理必须有可解释的幂等结果；不可清理与失败须可区分。

Topic 条件清理与管理员主动 settle/evict 是不同操作语义，不能借管理权限替代 prepare 补偿。附件 lease 的持有与释放仍按既有 W1 契约处理；Topic 无法清理不意味着附件 lease 可以泄漏，释放附件也不意味着 Topic 可以删除。

### 4.4 向主动意图交接资料

Topic 身份、prepare handle、assignment 和资料快照分别交接。主动意图不要求先有 Session、Segment 或 prepare；若调用方明确要求纳入某个 Segment，先确认该交互 applied，并取得其实际 assignment，再提交意图。只收到 prepare handle、accepted 或路由结果不能证明该交互内容已进入 Topic。两条提交不合并事务，也不建立等待未来交互的全局屏障。

| 输入情形 | 共同处理要求 |
|:---|:---|
| 明确指定已有 Topic | 校验存在、Workspace 归属和当前读取权限，再交付真实资料；失败不当作空资料 |
| Topic 合法但 blocks 为空 | 返回成功的空资料；不把内容为空视为意图无效或读取失败 |
| 只提供 prepare handle | 按已冻结的 handle 契约验证；若允许用于主动意图，领域侧转换为稳定资料绑定；是否接受该输入在第 4.5 节决定 |
| 来源为已应用 Segment | 按实际 assignment 选 Topic，不使用当前 Session cursor 重选 |
| 未提供 Topic/交互 | 保留意图独立生成；采用无辅助 Topic，还是由领域准备空 Topic，在第 4.5 节统一裁定 |

资料读取与绑定须固定本次任务的来源，后续 Session 路由或 handle 状态变化不能让同一任务重试悄悄切换 Topic。若处理需要继续访问活 Topic，应明确保护何时取得和释放；若已取得独立资料快照，则按快照保留约定处理，不靠临时 handle 充当无限期资料保留。选择哪种绑定、取样时点、Topic 内容变化后的重试行为以及可用版本证据在第 4.5 节一次冻结，不假定现有 Topic 已有可持久化 revision 或通用 pin 能力。

本节交付资料身份、全部可用内容的读取/绑定和保留/释放能力；生成侧的预算编译与 Pending 状态不属于本计划。资料为空、原文已经折叠而不可恢复、读取失败和无权读取必须区分。交付与测试不要求实际运行主动生成任务。

### 4.5 唯一冻结清单与跨计划交付

Topic 生命周期的下列决定统一在 **A3-0 本节**记录最终选择与签名，按 A1 的授权登记规则实施。冻结和实现均由本计划负责，不等待后续计划共同冻结；已有 WRITE/UPDATE 独立生成及 Topic 读取需求作为输入约束，后续消费者负责遵守交付契约。

| 待冻结内容 | 必须明确的出口 | 本计划实施/后续交付 |
|:---|:---|:---|
| prepare 副作用与引用 | 是否预创建/预留 Topic；handle 的 scope/调用关联、引用编码及 Segment 携带方式；与指令冲突的行为 | A3-2 公开 prepare 并实现路由/关联 |
| handle 存续与交接 | 有效期、一次/多次使用、重复 prepare、接纳时保护转移、过期后的查询/冲突/显式重新准备 | A3-2 公开查询/错误并实现接纳/应用保护 |
| 条件清理 | 本次创建的证据、空/占用判定、与并发 submit/资料读取的协调、幂等结果、关闭时收尾 | A3-2 公开条件清理并验证领域并发边界 |
| 资料来源与保留 | 省略 Topic 的唯一行为；是否接受 prepare handle；快照时点/版本证据、重试绑定及必要保护释放 | A3-2 交付完整资料读取/绑定；后续生成只消费结果 |
| API/授权/兼容 | prepare、资料读取、assignment/apply 查询、条件清理、interaction.submit 的参数/结果、operation 与旧 prepare_topic 返回 topic_id 的迁移 | A3-0 冻结具体签名/路由；A3-2 按 A1 实现 application 授权和公开暴露 |

复用 `TopicManagementService`、`InteractionSubmissionService` 与现有全局路由地址，对尚未公开的方法补齐明确地址和 operation；不另包一层 provider 或 Workspace service。`ConversationSegment` 是公开提交输入，`InteractionSubmission` 仍是内部 queue envelope。apply/assignment 观察在本计划内可用，不能等完整 API 收敛后才获得测试出口。

A3-0 的决定未关闭前不实现依赖它们的 Topic 方法；A3-2 同时验证公开访问/参数/结果映射与 prepare/submit/apply/cleanup 生命周期、竞态和资料读取。后续主动生成验证真实资料消费，最终 adapter 集成验证调用方交接；这两项不构成 A3 完成门禁。

## 5. 结构化事件的构建时机

外部 adapter 接收阶段只构造 ConversationPart。Segment 封口可以由完成回调、assistant 结束、工具结果完整、显式 flush、shutdown 或取消信号触发；缺少结束信号不能推断成功完成，partial/cancelled 必须保留其状态。

以阶段而非定时器确定构建时机：接收时建立最小事件，封口时冻结内容，Patchouli 在应用前建立领域投影。已有足够结构可以直接复用，只有依赖完整交互才延后处理：

1. Part 序列和角色足够明确时投影为 `TurnEvent`；
2. 有可靠调用关联时聚合为 `AgentAction`；调用已知而结果缺失可形成显式 incomplete action，不能虚构成功结果或凭相邻位置强配工具事件；
3. 需要生成 Topic block 时形成 `TurnRecord`，并保留 Part/Segment provenance；
4. 关联不完整时保留原始 Part，不能为了满足 `TurnRecord` 而伪造 action。

因此外部 Actor 不需要自行提供完整 `TurnEvent`、`AgentAction` 或 `TurnRecord`。Alice adapter 可以把已有结构化运行事件作为 execution projection 提交，Patchouli 仍使用同一投影规则。`TurnRecord.identity` 不再承担 session 身份；资源授权只使用 A1 的 access context。

现有 TurnEvent 本来就允许无 action_id，外部事件的困难主要是缺失关联和不同封口信号，不能误判为必须完全重建事件模型。A3-0 对照 ActionReducer 的相邻 thought 吸附规则，限制它在未知外部结构下的推断；TraceReducer 生成的摘要不能代替原始 Part。可选 execution projection 必须绑定同一 Segment/Part 来源并做一致性校验，冲突不能两边各自当真相。

目标上 Session/Segment 记录接收内容，TurnRecord 是 Topic 内的结构化内容投影；现有代码将 TurnRecord 称为“单轮内容真相”，迁移时明确它在 Topic 领域内的含义，不让两份正文相互回写。未知 kind/多模态 ref 无法进入旧 TurnRecord 时保留在共同记录及 provenance，并标明投影缺口。

## 6. InteractionPayload、队列 envelope 与主动意图

当前 `InteractionPayload` 混合 user/assistant 文本、turn_events、mtp_traces、worth_saving、附件使用和 `materialize_tasks`，不适合作为最终跨 Actor 模型。迁移目标是：

- `ConversationSegment` 成为正式共同领域输入；
- `InteractionPayload` 作为兼容投影，逐项映射 Part、执行投影、附件 provenance 和价值信号；
- `InteractionSubmission` 继续是进入 Patchouli submission lane 的内部 envelope，携带 scope、interaction/segment 关联和 ordering；
- `materialize_tasks` 不进入新的 Segment/interaction 输入；主动 WRITE/UPDATE 保持独立提交责任，后续 Pending 计划完善其公共模型。

| 现有字段 | 目标承接 | 兼容要求 |
|:---|:---|:---|
| user_message / assistant_final_text | 对应消息 Part；旧文本视图由投影产生 | 不凭只有两段文本伪造工具调用；已有结构时不能丢掉顺序 |
| turn_events | 中立事件/Part 或绑定来源的执行投影 | Alice 原 action 关联保留；外部缺失允许表达 |
| mtp_traces | 内部派生 trace/兼容投影 | 不作为完整原始事件或独立提交命令 |
| rewritten_query / worth_saving | 标注来源的分析提示 | 不覆盖原话、不代替 Patchouli 最终领域判断；价值体系重设另行计划 |
| used_attachments | 已实际编译使用的 ref/revision 快照与 provenance | retry 原样重用；应用成功后才建立 binding，不回查 UI 或上传列表 |
| model_used | 来源展示信息/可选执行元数据 | 外部未提供时未知，不要求绑定本地模型注册表 |
| materialize_tasks | 调用侧独立保留的主动任务，不进入 Segment | 新输入拒绝混入任务；混合旧载荷不静默丢任务，消费者切换时分别提交一次 |

一个 Segment 可以没有主动意图；一个主动意图可以没有 Segment 或 Session。交互结果向主动意图交接 Topic 资料的条件统一见第 4.4 节。A3 只验证纯交互入口与转换结果；尚未切换的混合旧入口在受信兼容窗口内保留，不能将任务丢弃后冒充转换成功。独立主动任务的提交与旧入口删除属于后续交付，不要求在本计划内实现新的 Pending 输入或合并两条路由。

## 7. RelayController 与外部上下文

RelayController 的新边界是 Topic working set 的折叠器：管理 Topic 侧的 token/block 预算、折叠原文的引用和供 Patchouli 生成使用的摘要。它不负责 ConversationSession 生命周期，也不应替外部 harness 压缩 prompt history。外部 harness 提供的 summary/checkpoint 作为带 provenance 的 `ConversationPart(kind=external_summary)` 或辅助材料进入系统，不自动覆盖 Topic canonical `state_summary`。

更细的 page folding、raw evidence、长 turn checkpoint、容量和恢复设计只在[折叠专项计划](./topic-folding-context-and-raw-evidence.md)中冻结。A3 只提供其必须依赖的 Session/Segment/Topic 关联和来源边界。

Session 完整历史的展示与 prompt 预算是两件事。Alice 可以继续选 Topic 工作集、短期窗口和检索结果组织 prompt；外部 harness 自主管理 prompt 与厂商缓存。A3 不把所有 Session 内容自动注入模型，也不以重构为由删除现有记忆侧短期工作集。只有 A6 必须解除“接收记录就替外部 Actor 改写执行上下文”的耦合，折叠质量算法本身继续保留现有实现直到专项替换。

### 8.1 A3-0 的冻结出口

进入 A3-1/2 前提交字段/样例和决定记录，至少关闭：

1. ConversationPart 与 TurnEvent 的复用/扩展方式、Segment 与旧 Payload 的单一内容来源及投影覆盖限制。
2. System Session 记录的物理位置、公开生命周期方法及 A1 operation、保留期/容量/溢出行为；不要求创建新的大子系统。
3. 旧 Passive `source + external_conversation_id + actor` key 的兼容映射、scope/Actor 漂移规则；移除 identity.session_id 对 equality/hash/cache key 的影响。
4. 无 session 的旧 Alice/单次调用如何映射为明确的临时 Session，不能静默合并全用户历史；旧 Topic 只保存可证来源，不能编造完整 Session。
5. 封口信号、partial/cancel/failed、迟到/重复/sequence 缺口策略；Session 与 Topic 两种序列化约束。
6. 路由指令优先级、默认候选范围和显式 attach；Topic prepare/handle、条件清理、资料绑定与 API 决定逐项完成第 4.5 节清单，唯一记录留在该节；跨 Session 复用不改变 Workspace ownership。

回滚可停用新入口并保留既有记录和结果查询；不可丢弃已接纳 Segment、把它们重新路由或抹去新 provenance 后盲目交给旧 queue。仅当兼容转换能表达原内容时才退回旧载荷，否则明确失败。历史导入样例用于确认未知时间/说话者/分支可表达，不在 A3 内执行批量导入。
