# v0.7.2 生成材料修正与 Topic 之后的原始证据保存

## 1. 背景和问题

v0.7.2 的版本目标是生成质量（[ROADMAP](../ROADMAP.md#43-v072生成质量)第 4.3 节）。v0.7.1 让 Claude Code 的日常使用开始产生记忆。2026-10-29 对真实导入做了逐段对账，证据见[生成材料的筛选与截断 Todo](../todo/generation-material-filtering-and-truncation.md)，主要结论如下：

- 生成视图只剩导入原文的 8%：进入生成的 17 轮中，12 轮顶到单轮上限；257 次工具调用只有 68 次保留了结果，另有 38 个条目被整条省略；
- 结算曾按 `worth_saving` 整轮丢弃 39% 的材料，被丢掉的是“请提交”“继续”背后工作量最大的几轮。2026-10-29 已停用筛选，但信号仍在计算和传递。

从 Topic 往后，原文还有两处在资料层消失：

- **折叠**：`compact_topic` 把保留后缀之前的旧 blocks 合成为 `state_summary`，然后裁剪掉这段前缀，被裁剪的原文没有任何留存；
- **结算**：结算只冻结当时还在的 blocks，来源 InteractionArtifact 因此只覆盖未折叠的轮次。

owner 决定（2026-10-30，记录见 [Raw Evidence Idea](../ideas/PatchouliPageFoldingRawEvidenceDesign.md#01-owner-决定2026-10-30)第 0.1 节）：

1. 一轮交互的内容不得被任何一个上限数字截断，最多只允许单次工具调用的结果受限。现行的单轮、思考与参数上限属于实现漂移。
2. `worth_saving` 只做移除，价值体系由 owner 重新设计。
3. 本计划同步完成从 Topic 往后所有链路的原始证据保存覆盖面。
4. R-1：不采用分片读取；生成继续读取话题的工作视图。单个超大轮次照常接收，照常触发折叠，更有效的方案留到流式交互接收实现时处理。
5. R-2：Topic 在原始数据上按顺序保存全部接收到的交互记录列表，以及一份话题折叠的记录列表，作为之后来源 Artifact 的数据。

## 2. 目标与非目标

### 2.1 目标

- 生成材料只截断单条工具结果：思考、工具参数与一轮的全部条目原样渲染，不再降级或省略。生成视图、LLM 接力摘要与 token 统计共用的渲染随之改变。
- Topic 保存全部接收到的交互记录与全部折叠记录。折叠只推进工作视图，不再丢弃原文。
- 话题结算冻结全部交互记录与折叠记录。来源 InteractionArtifact 覆盖话题接收到的全部轮次（包括已折叠的轮次），并带上折叠记录。
- 移除 `worth_saving`，以及只为它计算的传递链。

### 2.2 非目标

- **材料超出提取模型窗口**：按 R-1，不分片、不截断，也不另做降级。单个超大轮次可能使这次结算超窗失败（第 10.1 节）。
- **交到 Topic 之前的环节**：Session 侧的保存、进程与入口向 Topic 的交接、会话持久化与流式接收。
- **来源 Artifact 写入失败**：保持现状，捕获失败只记录 warning，生成照常进行。更强的承诺作为可选项列在第 10.2 节。
- **进程内资料的容量上限与背压、跨重启持久化**：Topic 仍是进程内资源，结算前的全部记录随进程存续。
- **主动 WRITE/UPDATE 的来源范围**：保持话题最近 `active_recent_blocks` 个 block。话题的全部记录在结算时冻结，主动生成不重复冻结全部历史。
- 价值体系的重新设计；多条提取、查重与更新（各有计划方向，见 ROADMAP 第 4.3 节）。
- 话题 HTTP 视图与前端展示的字段语义（`block_count`、`total_tokens` 仍指工作视图）。
- 连接器读取 Claude Code 会话记录的取舍。

## 3. 当前状态（2026-10-30 核对，commit `251e9f38`）

### 3.1 生成材料的渲染

- `engines/perception/material.py` 是一轮材料的唯一渲染：
  - 用户消息与助手正文原样渲染；
  - 能力调用（SEARCH、READ、RUN）渲染为一行摘要，WRITE、UPDATE、CALL 不渲染；
  - 思考按 `max_thought_chars`（1000）截断；
  - 外部工具的参数按 `max_args_chars`（300）截断，结果按 `max_result_chars`（800）截断；
  - 一轮的思考、能力与工具条目合计受 `max_turn_action_chars`（8000）约束：超出时较早的工具步骤降为一行，仍超出时按优先级整条省略，并写一行 `OMITTED`。
- 使用这一渲染的有：
  - 生成视图（`GenerationTranscriptBuilder`），也就是 MemoryCreationArtifact 中 `generation_view` 记录的内容；
  - LLM 接力摘要的近期事件（`LLMRelayController`）；
  - 写入 block 时的 token 估算（`MemoryPerceptionEngine.build_block`），折叠阈值据此判断。
- 四个上限都在 `GenerationTranscriptConfig`（`patchouli.generation.transcript`）中，该模型 `extra="forbid"`。
- 提取与修改提示词（`i18n/prompts.py`）说明了 `…[N chars omitted]…` 与 `OMITTED` 两种省略标记。

### 3.2 话题数据与折叠

- `LogicalBlock` 持有完整的 `TurnRecord`。事件集在写入时不截断，截断只发生在渲染时。
- `TopicData` 中存储的字段有：
  - `blocks`：工作视图；
  - `state_summary`；
  - `total_tokens`：写入时累加；
  - `bindings`：资产绑定。

  `merge_interaction_into_topic` 追加 block 并累加 token。
- `compact_topic` 持有 lease，选出保留后缀（`fold_retain_recent_blocks`，默认 2）之前的旧 blocks，交给 RelayController 生成新的 `state_summary`，然后一次写回：只保留后缀，重算 `total_tokens`。被折叠的 blocks 不再存在于任何地方。
- RelayController 只返回摘要文本。LLM 实现遇到提供商失败（包括超窗）或超时，回退为规则摘要。
- 读取工作视图的有：
  - 感知折叠的选择；
  - Gateway 查询分析（`recent_blocks`）；
  - 主动生成（`recent_blocks(active_recent_blocks)` 与 `state_summary`）；
  - 话题快照（`last_turn`、`block_count`、`total_tokens`）；
  - 关闭时的 `resident_block_count`；
  - 空话题判断。

  TopicData 只在短期存储的 `create` 与感知的写回中构造，测试中另有 11 个文件直接构造。

### 3.3 结算与来源 Artifact

- `TopicMaterializeTask.from_topic_data` 冻结 `blocks`、`state_summary` 与 `bindings`。
- `MemoryGenerationCoordinator.submit_settlement` 用 `blocks + state_summary` 构建生成上下文，并把同一组 `blocks` 放进 `InteractionArtifactInput`。生成队列的 codec 编码 `interaction_input`，队列只在进程内。
- `MemoryGenerationService.execute` 在生成之前捕获 InteractionArtifact：每个 block 对应一份 `InteractionTurnSnapshot`，包含完整事件集。捕获失败只记录 warning。CREATE 与 UPDATE 挂载来源引用；TOUCH、DISCARD 与生成失败时，Artifact 已经写入，但没有记忆引用它。
- 主动生成的 `InteractionArtifactInput` 是话题最近 `active_recent_blocks` 个 block。

### 3.4 `worth_saving` 的传递链

- `GatewayDecision.memory_write_signal`（`WRITE`、`SKIP`、`UNKNOWN`）是公共决定字段；`worth_saving` 是从它派生的只读属性。
- 信号的来源有：
  - 查询分析：提示词第 4 项要求模型输出 `memory_write_signal`；
  - 前置规则：显式记忆指令同时得到 `IntentType.WRITE` 与 `WRITE`；与上一轮重复的输入只得到 `SKIP`；
  - 简单寒暄默认 `SKIP`，保守回退 `UNKNOWN`，不调用模型的解析器默认 `WRITE`。
- 唯一的消费方是 Import Bus：`import.turn.accepted` 事件的 `data.worth_saving`，只供观测。
- `PASSIVE_MEMORY` 同样运行查询分析。Import Bus 只使用决定中的话题落位与新话题元数据，二者都来自话题路由，不来自查询分析。

## 4. 进入条件

阻塞问题 R-1、R-2 已于 2026-10-30 由 owner 决定，本计划不依赖其他计划，可以立即执行。开始实施时按当时的代码重新核对第 3 节。

## 5. 目标设计

### 5.1 生成材料只截断单条工具结果

- `GenerationTranscriptConfig` 只保留 `max_result_chars`（默认 800）。删除 `max_thought_chars`、`max_args_chars` 与 `max_turn_action_chars`，`configs/config.yaml` 同步删除。
- 渲染规则：
  - 思考原样渲染；
  - 外部工具的参数以完整 JSON 渲染；
  - 外部工具的结果按 `max_result_chars` 截断，沿用保留首尾、标出省略字符数的写法；
  - 能力调用的一行摘要不变。
- 删除单轮上限及其降级、整条省略与 `OMITTED` 行。
- 提示词删除关于 `OMITTED` 行的说明，保留关于 `…[N chars omitted]…` 的说明（只剩工具结果会出现这个标记）。
- 生成视图、LLM 接力摘要与 token 统计继续共用这一渲染：block 的 token 估算随之反映完整材料，折叠阈值不变。

### 5.2 Topic 的原始数据：交互记录与折叠记录

`TopicData` 存储两份原始数据，工作视图由它们派生，不再单独存储：

| 字段 | 内容 |
|:---|:---|
| `interactions` | 全部接收到的交互，按接收顺序排列，类型为 `tuple[LogicalBlock, ...]`；只追加，话题结束前不移除 |
| `folds` | 话题折叠的记录列表，每次折叠追加一条 `TopicFold` |

`TopicFold` 记录一次折叠：

- `folded_block_ids`：这一次被折叠的 block 标识，按顺序排列；
- `summary`：这一次折叠后的状态摘要；
- `folded_at`：折叠时间。

派生的工作视图如下，均为只读属性：

- `blocks`：`interactions` 中最后一次折叠之后的部分，即未被折叠的 blocks；
- `state_summary`：最后一次折叠的 `summary`，没有折叠时为空串；
- `total_tokens`：`blocks` 的 token 之和。

读取工作视图的消费方（第 3.2 节）继续读 `blocks`、`state_summary` 与 `total_tokens`，含义不变。工作视图不再单独存储，是为了不让同一事实有两份表达：两份存储的副本需要在每次写入与折叠时维持“工作视图是交互记录的后缀”这一不变量。

写入话题只有两条路径，都由 core 的话题模型提供：

- **写入一轮**：`merge_interaction_into_topic`（已有）只向 `interactions` 追加，不再累加 `total_tokens`；
- **折叠**（新增的写函数）：接收这一次被折叠的块与摘要，追加一条 `TopicFold`，不删除任何记录。`compact_topic` 的选择、摘要生成与 lease 规则不变，摘要返回后调用它写回一次；摘要失败或取消时不调用，话题保持原样。

两个函数都以完整构造（`TopicData.model_validate`）产生新快照，不使用 `model_copy(update=...)`。Pydantic v2 的 `model_copy` 不运行校验器，现有的两处写回都用它，构造时的校验在写回时会被绕过。感知服务只经这两个函数写入话题，不再直接 `model_copy`；短期存储 adapter 中关于写入方式的说明随之改写。

构造 `TopicData` 时校验折叠记录：全部折叠记录的 `folded_block_ids` 依次拼接，必须等于 `interactions` 开头同样数量的块标识，也就是每次折叠的都是当时工作视图的前缀。选择规则本身保证这一点，校验用来挡住写函数之外的错误构造。

`TopicData` 改为 `extra="forbid"`，以 `blocks=`、`state_summary=` 或 `total_tokens=` 构造时显式失败，不会被静默忽略。

### 5.3 结算冻结全部记录，来源 Artifact 覆盖全部轮次

- `TopicMaterializeTask` 改为携带 `interactions` 与 `folds`（连同标题、摘要与 `asset_bindings`），工作视图用与 `TopicData` 相同的派生得到；派生逻辑放在 core 的话题模型中，两处共用。
- 结算的生成材料保持原样，仍是 `state_summary` 与工作视图的 blocks（R-1）。
- `InteractionArtifactInput` 增加 `folds`。结算时放入全部 `interactions` 与 `folds`；主动生成仍放最近的 blocks，`folds` 为空。生成队列的 codec 同步编码。
- `InteractionArtifact` 增加 `folds` 字段，每条对应一条 `TopicFold`，默认空列表：
  - `turns` 来自全部交互记录，覆盖已折叠的轮次；
  - 新增字段只追加不改名，没有该字段的旧文件读作空列表，`schema_version` 不变；
  - 完整性校验仍以文件原文为输入。
- 捕获时机与失败语义不变：在生成之前捕获，失败只记录 warning。因此提取超窗或失败、结果为 TOUCH 或 DISCARD 时，原文仍保存在来源 Artifact 中，只是没有记忆引用它。

### 5.4 移除 `worth_saving`

- 删除以下内容：
  - `GatewayDecision.worth_saving` 与 `memory_write_signal`；
  - `MemoryWriteSignal` 枚举；
  - 查询分析结果模型（Gateway 与 engines 各一处）中的同名字段；
  - 查询分析提示词（中英文）的第 4 项与输出字段；
  - `import.turn.accepted` 事件的 `worth_saving` 数据。
- 前置规则：显式记忆指令仍然判为 `IntentType.WRITE`。重复输入检测只用于产出 `SKIP`，随之删除。
- 简单寒暄、保守回退与不调用模型的解析器，不再填写该字段。
- **`PASSIVE_MEMORY` 不再运行查询分析**（候选设计，计划评审时确认）：价值信号移除之后，导入的轮次不再使用查询分析的任何输出。决定中的检索相关字段按简单寒暄的默认值填写（不检索），每个导入轮次因此少一次 LLM 调用。`ACTIVE_CHAT` 不变。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| core 模型 | `TopicData` 改为交互记录与折叠记录，新增 `TopicFold`、工作视图的派生与折叠写函数，两个写函数经完整构造校验；`InteractionArtifact` 增加 `folds` |
| core 协议 | `GatewayDecision` 删除 `memory_write_signal`、`worth_saving`；删除 `MemoryWriteSignal` |
| Patchouli 感知 | 只经两个写函数写入话题，不再直接 `model_copy`；折叠追加记录；结算冻结全部记录 |
| Patchouli 生成 | `InteractionArtifactInput` 与队列 codec 增加 `folds`；结算的来源覆盖全部交互记录 |
| engines | 材料渲染只截断工具结果；接力摘要与 token 统计随之改变；Gateway 查询分析模型删除信号字段 |
| Gateway | 前置规则与工作流默认值删除信号；`PASSIVE_MEMORY` 不运行查询分析（候选） |
| System Import Bus | `import.turn.accepted` 删除 `worth_saving` |
| 配置 | 删除 `patchouli.generation.transcript` 的三个键 |
| 提示词 | 提取与修改提示词删除 `OMITTED` 说明；查询分析提示词删除价值初判 |

公共契约的变化：`GatewayDecision` 的字段（子系统契约）、`import.turn.accepted` 的事件数据（路由与事件契约）、配置键。`TopicSnapshot` 与话题 HTTP 视图不变。

## 7. 兼容与迁移

- **配置**：仓库中的 `configs/config.yaml` 同步删除三个键。本地自定义配置若保留这些键，启动时按 `extra="forbid"` 显式失败，需要手动删除；配置文档写明这一点。
- **进程内数据**：话题与生成队列都只在进程内，重启后为空，不需要迁移。
- **来源 Artifact 文件**：已有文件缺少 `folds` 时读作空列表，不改写。
- **事件消费方**：`worth_saving` 只供观测，仓库内的前端与连接器都不读取它。
- **测试**：直接构造 `TopicData` 的测试改用新字段；旧的单轮上限、整条省略与价值信号测试随契约变更删除或改写，不保留墓碑测试。

## 8. 实施阶段

1. **生成材料与 `worth_saving`**：渲染与配置；提示词；Gateway、engines 与 core 协议中的信号；Import Bus 事件；`PASSIVE_MEMORY` 的查询分析。
2. **Topic 原始数据与来源 Artifact**：`TopicData`、`TopicFold` 与工作视图派生；写入与折叠；结算任务；`InteractionArtifactInput` 与队列 codec；`InteractionArtifact.folds`。
3. **实测验收与收尾**：按第 9.3 节实测并记录结果；事实文档收尾；计划与[生成材料 Todo](../todo/generation-material-filtering-and-truncation.md)归档。

## 9. 测试和验收标准

### 9.1 不变量与归属层

| 不变量 | 归属层 |

### 9.3 实测验收

用 serve 模式的后端、真实记忆库与 LLM，配合 Claude Code 连接器，在日常使用中核对以下各项，并把结果记入实施记录：

- 新生成记忆的 MemoryCreationArtifact 中，`generation_view` 含完整的思考与参数，只有工具结果带截断标记；
- 至少一个发生过折叠的话题结算后，来源 InteractionArtifact 的 `turns` 包含已折叠的轮次，`folds` 中的摘要与折叠次数一致；
- 记录每个话题的提取 token、折叠次数与接力摘要回退为规则摘要的次数，与 Todo 中 2026-10-29 的数据对比；
- `import.turn.accepted` 不含 `worth_saving`；导入轮次的日志中没有查询分析调用；
- 如果遇到超窗导致的结算失败，记录轮次规模，并确认来源 Artifact 已写入。

## 10. 风险与待决问题

### 10.1 风险

- **提取超窗**：工作视图中保留的 blocks 很大时（例如单轮 78 次工具调用、23.6 万字符），结算的提取可能超出模型窗口。按 R-1，这时任务以 `memory_generation_failed` 失败（超窗不重试），原文仍在来源 Artifact 中，更有效的方案留到流式交互接收实现时处理。实测中记录发生的频率。
- **开销上升**：生成视图接近导入原文，提取 token 与成本上升。token 统计变大使折叠更频繁；接力摘要的输入变大，更容易超时或超窗，从而回退为规则摘要。
- **内存与磁盘**：Topic 在结算前保存全部交互记录，折叠不再释放内存；生成队列保留最近的终态工作记录（`terminal_retention`），记录中含编码后的载荷，结算载荷随之变大。来源 Artifact 文件会达到 MB 级。实测中记录后端常驻内存与 Artifact 目录的增长。
- **查询分析**：`PASSIVE_MEMORY` 不再运行查询分析之后，导入一侧不再有入口阶段的任何价值判断；新的价值体系需要时重新设计入口，不恢复旧信号。

### 10.2 待决问题

无阻塞问题。以下候选细节在计划评审时确认：

- `PASSIVE_MEMORY` 不再运行查询分析（第 5.4 节）；
- `TopicFold` 的字段，以及 `InteractionArtifact.folds` 不升 `schema_version`（第 5.2、5.3 节）。

可选的更强做法，owner 选择后再纳入，本计划不实施：

- 来源 Artifact 写入失败时结算任务失败、话题内容交还重试，类似记忆版本 Artifact 的“无历史不成功”。代价是 Artifact 存储故障会挡住记忆生成。
