# v0.7.0 身份与访问体系第二批：Patchouli 的归属与发起者

> **文档状态**：Planned（2026-10-04 建立）。实施分支 `refactor/identity-access-batch-2`，起点 commit `f9dc3ce`。设计依据见第 2 节；本计划不以任何活动计划为依据。

## 1. 背景与问题

身份与访问体系的第一批（[A1 访问边界返工](../archive/plans/v0.7.0-a1-access-boundary-rework.md)，2026-10-04 归档）建立了 workspace 一侧的边界：访问 context 是密封凭据，`IdentityScope` 只由授权点组装，Patchouli 与 Gateway 的公开路由只接收 `IdentityScope`。第一批没有处理 `IdentityScope` 进入 Patchouli 之后的去向。代码核对（2026-10-04，第 4 节）发现：

1. **记录与后台任务保存 `IdentityScope`**：交互提交、生成任务、写入意图物化任务、话题结算任务与 `PreparedAgentRun` 等 8 个类把“一次操作”的发起者与目标 workspace 保存下来，而它们的寿命长于那次操作。
2. **Patchouli 内部全程传递 `IdentityScope`**：Patchouli 的 25 个模块与它驱动的 5 个引擎包中的 12 个模块共有约 470 行涉及 `IdentityScope`；其中只有 6 处读取 actor，其余只用 workspace。归属与发起者性质不同，却一直打包传递。
3. **finalize 与 cleanup 的身份不来自授权点**：两者从 prepare 冻结在 `PreparedAgentRun` 中的 `IdentityScope` 取身份；任务进程在进入 Actor 前做了 `interaction.submit` 授权，但丢弃了返回的 scope。
4. **非主动生成路径的发起者不对**：PR #96 把 SETTLE 的来源字段统一为 `system`，但结算任务的发起者仍是话题最后一次被访问的 actor，或触发 LRU 驱逐的调用方；查重按这个 actor 的可见性进行，可能把结算内容并入非 PUBLIC 的记忆。
5. **`ActorIdentity.session_id` 参与身份的相等性**：它是兼容字段，只有一个读取方，却会随身份进入相等判断、hash 与持久记录。

## 3. 目标与非目标

**目标**

1. Patchouli 的公开路由仍只接收 `IdentityScope`，在公共边界拆为归属（`belong_to: WorkspaceIdentity`）与发起者（`from_actor: ActorIdentity`）；Patchouli 内部（应用服务之下的本地路由、服务、控制面、记忆库端口与存储）以及它驱动的 generation、perception、retrieval、lifecycle、artifacts 引擎不再传递或组装 `IdentityScope`。
2. 记录与后台任务不再保存 `IdentityScope`，以独立字段携带归属与（需要时）发起者；`MemoryGenerationTask` 拆出 `from_actor` 与 `belong_to`。
3. finalize 与 cleanup 的身份来自任务进程的阶段授权；`PreparedAgentRun` 只携带归属。
4. SETTLE 的四种触发（手动、空闲超时、LRU、关闭）都以 `system` 为发起者，查重只看得到 PUBLIC 记忆。
5. 从 `ActorIdentity` 移除 `session_id`。
6. Patchouli 应用服务的 `identity_scope` 参数改为必填。
7. 以架构测试守护第 1 条。

**非目标**

- **Gateway**：处理路由仍接收 `IdentityScope`；`GatewayExecutionState` 等工作流状态只存在于一次处理之内，符合 AGENTS.md 的规则，不在本批修改。
- **Alice 与 CPU**：`RuntimeScope`、`AgentRunContext`、`CPUInputManifest` 与 `cpu_execution_identity`（Idea 6.1 第一类、I-9）随 Alice 的能力层调用迁移处理；Alice 继续以 `IdentityScope` 调用 Patchouli 的公开路由。
- **写入意图的回读可见性**：`agent_runtime/aliases/resolver.py` 按整个 `RuntimeScope.identity_scope` 相等判断可见性，归[写入意图迁移 Idea](../ideas/pending-intent-migration.md)；本批只改 `PendingAtomMaterializeTask` 的字段。
- **workspace 自身的资源 owner**：`WorkspaceAssetStore` 与解析服务内部仍以 `IdentityScope` 做归属检查，是否纳入本批见第 9 节待决事项。
- **Import Bus（`/ingest`）**：仍在认证前组装 `IdentityScope`；Passive Ingress 只随构造函数机械适配。
- **chat 请求体的 `session_id` 字段**：照常接受，不再进入身份；字段本身的语义归[外部会话 Idea](../ideas/external-session-and-topic-projection.md)。
- 资源的受限穿透访问；资源边界的修改与执行授权（总 Idea P-8）。
- 事实文档在实施期间不提前更新，只在最终收尾时按最终代码改写（第 10 节）。

## 4. 当前状态（2026-10-04 核对，`f9dc3ce`）

### 4.1 Patchouli 的公共边界

Patchouli 的公开路由在 [`patchouli/runtime/bridge.py`](../../src/hivememory/patchouli/runtime/bridge.py) 的 `_public_route_bindings` 中绑定到两类处理者：

- 应用服务（[`patchouli/application/`](../../src/hivememory/patchouli/application/)）：记忆管理、记忆任务、Agent Profile、话题、交互提交、写入意图提交与模型就绪；
- `PatchouliService`（[`patchouli/service.py`](../../src/hivememory/patchouli/service.py)）：prepare、finalize、cleanup 与引用记录等 chat 阶段路由。

两者之下经 Patchouli 本地总线（[`patchouli/runtime/route_bindings.py`](../../src/hivememory/patchouli/runtime/route_bindings.py)）调用服务、控制面与记忆库，`identity_scope` 作为关键字参数一路传递。应用服务中 20 个方法的签名写作 `identity_scope: IdentityScope | None = None`，运行时由 `require_identity_scope` 拒绝缺省值。

### 4.2 内部对 actor 的使用

Patchouli 与上述引擎中从 `IdentityScope` 读取 actor 的只有 6 处（Idea 6.5）：

| 类别 | 位置 |
|:---|:---|
| 读取时的可见性判断 | 中期库冷读与检索的 `_readable`（`memory_library/adapters/mid_term.py`）；检索的可见性过滤（`engines/retrieval/filter_adapter.py`） |
| 来源与关联字段 | `provenance_from_actor`（`engines/generation/models.py`）；感知写入 `TurnRecord.identity`（`engines/perception/memory_perception_engine.py`）；`PreparedAgentRun.agent_id`；finalize 写入关联字段的 `session_id` |

其余方法只使用 workspace，例如记忆库端口与存储、Topic 存储与驻留集、lifecycle 的强化（`get_by_key`，只校验归属）、Artifact 存储。

### 4.3 保存 `IdentityScope` 的记录与后台任务

| 类 | 位置 | 生产者 | 消费者 |
|:---|:---|:---|:---|
| `PreparedAgentRun` | `patchouli/contracts/prepare.py` | prepare | 任务进程（Topic 与检索结果、一致性检查）、finalize、cleanup |
| `InteractionSubmission` | `patchouli/control/interaction_submission.py` | finalize、交互提交服务、Passive Ingress | 交互提交队列、apply（感知） |
| `TopicMaterializeTask` | `engines/perception/models.py` | 话题结算 | `submit_settlement` |
| `FlushEvent` | `engines/perception/models.py` | 无生产调用方（只被导出与测试使用） | 无 |
| `MemoryGenerationTaskSpec` | `patchouli/control/memory_generation/models.py` | `submit_settlement`、`submit_active` | 生成队列、生成服务 |
| `MemoryGenerationTask` | `patchouli/contracts/memory_tasks.py` | 生成队列 | 记忆任务的观察与取消（只比对 workspace；字段可为 `None`，查询一律拒绝） |
| `PendingAtomMaterializeTask` | `core/models/pending.py` | Alice（`from_pending_atom`，取自 `RuntimeScope`） | `submit_active` |
| `LeaseToken` | `patchouli/services/topic_working_set.py` | 话题驻留集 | 话题结算 |

`TopicWorkingSet` 的驻留表还按 `(workspace, topic_id)` 保存最后一次访问时的完整 `IdentityScope`，供空闲超时与关闭时的结算使用。

### 4.4 chat 阶段路由的身份来源

任务进程的执行器（[`workspace/process/runner.py`](../../src/hivememory/workspace/process/runner.py)）：

- prepare：以 `resource.search` 授权得到的 scope 调用，返回的 `PreparedAgentRun` 由 `_require_prepared_scope` 比对整个 scope；
- 进入 Actor 前做 `interaction.submit` 授权，丢弃返回的 scope；
- finalize：只传 `prepared_run` 与交互记录，Patchouli 从 `prepared_run.identity_scope` 取身份；
- cleanup：在关闭流程中只传 `prepared_run`，不做阶段授权；关闭流程在执行器 `close` 完成之后才使 context 失效（`workspace/process/service.py` 的 `_close`）；
- 结算后的话题池：以 `resource.read` 授权得到的 scope 调用。

### 4.5 SETTLE 的发起者

见 Idea 6.7。手动结算经 HTTP 管理路由得到 `system`；空闲超时与关闭取驻留表中冻结的 scope；LRU 驱逐取触发驱逐的调用方的 scope。结算路径上只有查重使用发起者（`engines/generation/engine.py` 的 `_dedup_and_resolve`，`enforce_actor_visibility` 为默认值 `True`）。

### 4.6 `session_id`

- 写入：server 把 chat 请求体中的 `session_id` 放进 actor 声明（`server/deps.py`、`server/routers/chat.py`）；前端发送该字段。
- 读取：只有 finalize 把它写入交互提交的关联字段（`patchouli/service.py`）。
- 持久化：感知把完整的 `ActorIdentity` 写入 `TurnRecord.identity`，并作为 `InteractionTurnSnapshot.actor_identity` 写入交互 Artifact。Artifact 以 JSON 文件保存，完整性 hash 按读到的原始 JSON 计算，读取时不重新编码；`ActorIdentity` 未设置 `extra`，按 Pydantic 默认忽略未知键。

### 4.7 序列化与持久化

- `InteractionSubmissionCodec` 当前为 v2，另有只读的 v1 codec；记忆生成队列的 codec 为 v1；两条队列都使用 `InMemoryWorkStore`，这是仓库中唯一的 work store 实现，重启后没有遗留的编码载荷。
- interaction apply 的摘要（`compute_apply_digest`）把 `identity_scope` 整体纳入 canonical 输入。
- Topic 存储在进程内（`InMemoryShortTermStorage`）；中期记忆不保存 `IdentityScope`。
- 记忆任务的 REST 投影（`server/models/memory_task.py` 的 `MemoryTaskResponse`）不包含身份字段。

## 5. 目标设计

### 5.1 公共边界的拆分

- 公开路由的处理者（应用服务与 `PatchouliService` 的阶段路由）是唯一接收 `IdentityScope` 的地方：入口先以 `require_identity_scope` 校验，再拆为 `belong_to = identity_scope.workspace_identity` 与 `from_actor = identity_scope.actor_identity`，此后只传递这两者之一或两者。
- 只用归属的方法只接收 `belong_to`；需要可见性判断的读取（中期库冷读与检索、检索过滤）另外接收 `from_actor`，作为可见性主体。owner 视角的管理读取保持 `enforce_actor_visibility=False` 的现有语义。授权谓词 `memory_is_readable` 本来就分别接收两者，不需要修改。
- 命名：记录、任务与内部方法统一使用 `belong_to` 与 `from_actor`（与 owner 为 `MemoryGenerationTask` 指定的字段名一致）。
- 公开输入 DTO 保持不变：`RetrievalRequest`（`core/protocol`）仍携带 `identity_scope`，由公开路由的处理者转换为内部查询；引擎内部的 `RetrievalQuery` 改为 `belong_to` 与 `from_actor`。
- core 中三个资源键的 `from_identity_scope`（`WorkspaceMemoryKey`、`WorkspaceArtifactKey`、`WorkspaceTopicKey`）只取其中的 workspace，删除后由调用方直接以 `WorkspaceIdentity` 构造键；现有调用方都在 Patchouli 与 lifecycle 引擎内。

### 5.2 记录与后台任务

| 类 | 改为 | 说明 |
|:---|:---|:---|
| `MemoryGenerationTask` | `from_actor: ActorIdentity`、`belong_to: WorkspaceIdentity`，均必填 | owner 指定；观察与取消比对 `belong_to`；删除“字段为 `None` 时查询一律拒绝”的旧分支（队列只有进程内存储，不存在旧快照） |
| `MemoryGenerationTaskSpec` | `from_actor`、`belong_to` | SETTLE 的 `from_actor` 为 `system`（5.4）；WRITE、UPDATE 取写入意图的 `from_actor` |
| `InteractionSubmission` | `from_actor`、`belong_to` | `from_actor` 是本轮交互的 actor，感知据此写入 `TurnRecord.identity` |
| `PendingAtomMaterializeTask` | `from_actor`、`belong_to` | `from_pending_atom` 从 `RuntimeScope` 拆出；`RuntimeScope` 本身不变 |
| `TopicMaterializeTask` | `belong_to` | 结算的发起者固定为 `system`，由 `submit_settlement` 给出，不随任务携带 |
| `FlushEvent` | 删除 | 没有生产调用方；若实施时发现调用方，改为 `belong_to` |
| `LeaseToken` | `belong_to` | 驻留与占用本来按 `(WorkspaceIdentity, topic_id)` 键控 |
| `PreparedAgentRun` | `belong_to` | 删除 `agent_id` 属性；finalize 与 cleanup 的身份来自路由参数（5.3） |

`TopicWorkingSet` 的驻留表只保存最后访问时间；空闲超时与关闭的候选返回 `(belong_to, topic_id)`。

### 5.3 chat 阶段路由

| 路由 | 参数 | 执行器的授权 | Patchouli 的检查 |
|:---|:---|:---|:---|
| prepare | 不变 | `resource.search`（不变） | 返回 `PreparedAgentRun(belong_to=...)`；执行器比对 `belong_to` 与任务目标 workspace，取代 `_require_prepared_scope` |
| finalize | 增加 `identity_scope` | 紧接 finalize 之前做 `interaction.submit` 授权，并把返回的 scope 传入；进入 Actor 前的同一检查保留，用于提前拒绝 | `prepared_run.belong_to` 不等于 scope 的 workspace 时抛出 `WorkspaceMismatchError`，不提交；交互提交的 `from_actor` 取自 scope；关联字段的 `agent_id` 取自 scope；物化派发与检索命中记录只用归属 |
| cleanup | 增加 `identity_scope` | 关闭流程中以 `resource.search`（被补偿的 prepare 所绑定的 operation）授权后调用；授权失败与现有的 cleanup 失败一样记录警告并跳过 | `prepared_run.belong_to` 与 scope 的 workspace 不一致时不清理 |

再次授权而不是保留进入 Actor 前得到的 scope：`IdentityScope` 只存在于一次操作的调用链内（AGENTS.md 第 3 节），不应保存在进程工作集中等待之后使用。访问登记在运行期间不变（外部 Actor Idea E-1），context 在进程关闭前有效，因此再次授权的结果与先前一致；cleanup 发生在 context 失效之前（4.4）。

### 5.4 非主动生成路径的发起者

- core 提供唯一的 `system` actor 构造函数：`user_id` 取归属的 owner，`agent_id` 为 `SYSTEM_AGENT_ID`，`team_id` 为 `None`。函数名在实施时确定。
- `submit_settlement` 为所有 SETTLE 任务规范设置 `from_actor` 为该归属对应的 `system` actor，不论触发方式；话题结算（手动、空闲超时、LRU、关闭）只以 `belong_to` 调用结算流程。
- 查重以 `from_actor` 为可见性主体：`system` 不能作为 PRIVATE 的 target，`team_id` 为 `None`，因此只看得到 PUBLIC 记忆；不新增参数或分支。
- 来源字段沿用 PR #96 的 `system_settlement_provenance`；WRITE、UPDATE 的发起者与来源不变。

### 5.5 移除 `ActorIdentity.session_id`

- 删除字段与示例；server 的请求身份解析不再接收或传递 `session_id`；chat 路由不再把请求体的 `session_id` 传入声明；`ChatRequest.session_id` 保留，照常接受但不使用，并在字段说明中注明。
- finalize 的关联字段不再写入 `session_id`。
- 清理把 `session_id` 当作身份字段的注释与说明（Alice Profile 缓存的键投影说明、`workspace/registry.py` 的模块说明）。
- 已保存的交互 Artifact 中可能带有 `session_id` 键：读取时按 Pydantic 默认忽略，完整性 hash 不受影响（4.6），不做数据迁移。

### 5.6 序列化

M-4（迁移期间的兼容范围）尚未形成统一规则，本批按接口逐项决定：

- `InteractionSubmissionCodec` 升为 v3，以 `from_actor`、`belong_to` 取代 `identity_scope`；删除 v2 编码与只读的 v1 codec。依据是两条队列只有进程内存储，旧版本的载荷不会在重启后出现。
- 记忆生成队列的 codec 升为 v2，同样处理。
- apply 摘要的 canonical 输入以 `belong_to` 取代 `identity_scope`（actor 已在 turn 中）。

### 5.7 架构测试

在 `tests/unit/architecture/` 增加守护：

- `patchouli/` 中只有公开路由的处理者（`patchouli/application/` 与 `patchouli/service.py`）可以引用 `IdentityScope` 或 `require_identity_scope`；
- `engines/` 的 generation、perception、retrieval、lifecycle、artifacts 不引用 `IdentityScope`；
- `patchouli/contracts/` 的公开模型与 `core/models/pending.py` 中的 `PendingAtomMaterializeTask` 不以 `IdentityScope` 作为字段。

## 6. 受影响的系统与契约

- **core**：`ActorIdentity` 去掉 `session_id`；`PendingAtomMaterializeTask` 的字段；以 `IdentityScope` 为参数的辅助构造；新增 `system` actor 构造函数。
- **Patchouli**：公开路由的处理者在入口拆分；本地路由、服务、控制面、记忆库端口与存储的签名；记录与任务的字段；两个队列 codec 的版本；话题驻留集；SETTLE 的发起者。
- **engines**：generation、perception、retrieval、lifecycle、artifacts 的签名与模型。
- **workspace**：执行器的 finalize 与 cleanup 授权、prepare 结果的一致性检查。
- **server**：请求身份解析与 chat 路由不再处理 `session_id`。
- **system**：Passive Ingress 构造 `InteractionSubmission` 的方式。
- **公共契约**：`PATCHOULI_FINALIZE_AGENT_RUN` 与 `PATCHOULI_CLEANUP_PREPARED_AGENT_RUN` 增加 `identity_scope` 参数；`PreparedAgentRun`、`MemoryGenerationTask`、`PendingAtomMaterializeTask` 的字段。HTTP API 不变（记忆任务的 REST 投影不含身份；`ChatRequest.session_id` 保留）。
- **行为变化**：SETTLE 的查重只看得到 PUBLIC 记忆，结算内容不再并入非 PUBLIC 的记忆（I-11 的修正）。其余对外行为保持不变。

## 7. 迁移步骤

自底向上切换，每一步结束时单元测试可以运行：

1. **core**：`system` actor 构造函数；移除 `session_id`；`PendingAtomMaterializeTask` 的字段；辅助构造。
2. **记录与后台任务**：5.2 的各类、两个队列 codec 与 apply 摘要。

4. **公共边界**：应用服务与 `PatchouliService` 在入口拆分；应用服务签名改为必填；`RetrievalRequest` 在边界转换。

## 8. 测试与验收

**单元测试**

- 记录与任务：5.2 各类不再有 `IdentityScope` 字段；`MemoryGenerationTask` 以 `belong_to` 判定观察与取消，跨 workspace 返回不存在。
- SETTLE：四种触发得到的任务规范 `from_actor` 都是 `system`；存在与草稿相似的 PRIVATE 或 TEAM 记忆时，SETTLE 查重不命中它并新建 PUBLIC 记忆；WRITE 的查重仍按提交者的可见性进行。
- 话题驻留集：驻留表不保存 actor；空闲与关闭候选返回归属。
- finalize：缺少 `identity_scope` 被拒绝；`prepared_run.belong_to` 与 scope 不一致时抛出 `WorkspaceMismatchError` 且不提交；交互提交的 `from_actor` 等于 scope 的 actor。
- 执行器：finalize 之前进行 `interaction.submit` 授权，此时被拒绝按进程失败收口且不调用 finalize；cleanup 以 `resource.search` 授权后调用，授权失败时记录警告、跳过清理且关闭照常完成；prepare 返回的归属与目标 workspace 不一致时失败。
- codec：v3 与 v2 往返一致；旧版本未注册，解码被拒绝。
- apply 摘要：同一交互在不同 workspace 下摘要不同，等价重试摘要相同。
- `ActorIdentity`：没有 `session_id` 字段；带 `session_id` 键的已保存交互 Artifact 可以读取，完整性校验通过。
- server：chat 请求体带 `session_id` 时照常处理，声明中的 actor 不含会话信息。
- 架构测试：5.7 的三条守护。

**集成测试**

- 真实认证网关下的 `/chat` 全链路（模拟 CPU）：prepare、finalize、物化派发与结算后的话题池读取。
- 经 HTTP 管理路由观察与取消记忆任务。
- 话题空闲超时结算：在已有相似 PRIVATE 记忆时新建 PUBLIC 记忆（使用进程内的中期库替身）。
- Passive Ingress 的交互提交照常进入感知。

**门槛**：CI 等价的 `pytest tests/unit tests/integration`（覆盖率不低于 85%）、`ruff check .`、`black --check .` 通过；`mypy src` 不新增错误（起点 `f9dc3ce` 为 209 个既有错误）；分层测试与 5.7 的架构测试通过。
