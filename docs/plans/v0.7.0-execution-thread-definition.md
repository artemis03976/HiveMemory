# v0.7.0 执行线程的正式定义

> **文档状态**：Planned（2026-10-19）。两个阶段均未开始实施。

**问题**：执行线程是为 actor 的操作权限逐步加进来的，从未被定义成一个对象。
- 线程的数据分散在凭据、`ExecutionThread`、输入清单与工作集字典中。
- 线程只有撤销，没有结束。
- 存活条件分散在两处，大半冗余；停止后读取放行、写入与派生却被拒绝，而且用的是表示接线缺陷的错误。
- 能力层要经两个回流端口取得线程的进程属性。
- 派生被建模成返回凭据的 actor 操作。
- 线程身份在任何地方都观测不到。

**本计划的做法**：以线程表把执行线程定义为任务进程在 Actor 阶段内的执行主体。
- 派生、结束与解析都只经过线程表。
- 存活只有一个判定：线程未结束，且进程仍在运行。
- 派生从 `agent.call` 中分出来；主线程与子线程以同一种线程描述交给 CPU。
- 落实 owner 的三项决定：
  - Alice 的子线程随 CALL 返回而结束；
  - 子帧的观测标签取自己的身份；
  - 停止时先停止生成，线程随停止结束。

授权规则、写入意图的派发语义、停止规则、SSE 契约与会话语义保持不变。

## 1. 背景和问题

1. **没有线程对象**。主线程与子线程都要得到“图纸、操作快照、凭据”三样，但创建路径不对称：
   - 主线程的图纸与快照在输入清单里，凭据是 `CPUPort.execute` 的 `access` 参数；
   - 子线程的三样打包成 `ExecutionThread`，交给 CALL 编排时再换成去掉凭据的 `Callee`；
   - 工作集只用一个 `thread_id → context` 字典登记线程。
2. **只有撤销，没有结束**。子线程在 CALL 返回后仍然有效，直到 Actor 阶段结束；派生成功、子帧准备失败的子线程也一样。执行线程层的取舍理由是“另设结束路径的实现成本”，不是语义上的理由。
3. **存活判定分散，且大半冗余**。
   - 一次 WRITE 要经过 5 个条件：context 未撤销、进程存在、阶段为 ACTOR、结局为 RUNNING、context 在登记中。这些条件分布在 `WorkspaceOperationAuthorizer._thread_grant` 与 `ProcessThreads` 两处。
   - 其中三个条件已被“未撤销”蕴含。
   - 唯一多出来的“结局为 RUNNING”只在写入与派生上检查：停止被接受后，READ、SEARCH、RUN 仍能通过，WRITE、UPDATE、CALL 却以 `ScopeRequiredError` 拒绝。
4. **能力层经回流取得线程的进程属性**。actor API 先经授权者读出 `process_id`，再经 `ChildThreadSpawner` 与 `IntentDispatchTopicReader` 回到 `ProcessThreads` 查进程表。
5. **派生被建模为返回凭据的 actor 操作**。`DeriveCallThreadRequest` 是 `OperationRequest[ExecutionThread]`，结果含 context，所以 `ThreadOperationSubmitter` 的泛型调用必须拒绝它，另开 `derive_call_thread`。
6. **线程身份不可观测**。
   - `thread_id` 只出现在运行绑定与字典键里；写入意图只记录 `from_actor` 与 `process_id`，同一进程两次 CALL 同一个 Agent 时无法区分。
   - 子帧沿用调用方的观测标签，`agent.context.budget_exceeded` 因此报告调用方的 `agent_id`。
7. **线程与帧是同一棵树，却没有共同标识**。Alice 以 `frame_id` 与 CALL 记录维护帧树，workspace 以 `main`/`child-N` 维护线程，两者一一对应，但互相找不到对方。

## 2. 目标与非目标

### 2.1 目标

1. 进程以线程表登记自己的全部线程；派生、结束与解析的唯一入口是线程表。
2. 线程的生命周期为“派生 → 运行 → 结束”，结束即撤销凭据，没有“停止中”状态。三个结束时点：子线程随 CALL 返回结束；进程的停止被接受时全部结束；Actor 阶段结束时全部兜底结束。
3. 每个 actor 操作都只按“线程未结束且进程仍在运行”这一个判定决定可否执行；不满足时统一以生命周期错误拒绝，`ScopeRequiredError` 只留给接线缺陷。
4. 能力层凭线程 context 向线程表做一次解析，得到进程关联、线程标识与派发话题；两个回流端口合并为一个。
5. `agent.call` 只负责权限检查与解析目标图纸；派生与结束是线程表的生命周期动作，由操作入口的专用方法提交。
6. 主线程与子线程以同一种线程描述（标识、观测标签、图纸、操作快照）交给 CPU；`Callee` 删除。
7. 子帧的观测标签取子线程自己的身份；写入意图记录 `thread_id`。
8. 第 4.9 节列出的行为保持不变，有意的变化只有第 4.10 节所列几项。

### 2.2 非目标

- **外部 harness 的子线程**：无法探测子 agent 的结束时点，创建时点也不一定能取得（执行线程 Idea 第 3.1、3.3 节），随接入外部 harness 一并考虑。E-5“外部执行单元不识别子线程”不变。
- **观测出口**：RuntimeEvent 信封与 SSE 不增加线程标识字段，也不新增线程生命周期事件。交互事件的词汇见[执行环境 Idea](../ideas/execution-environment.md#t-10-cpu-输出与会话历史的词汇归属) T-10，RuntimeEvent 的收敛见 [Chat Run 生命周期 Idea](../ideas/chat-run-lifecycle-follow-ups.md) 候选 C。
- **授权规则**：CALL 需要 `agent.call`、以调用方的可见性读取图纸、被调用方准入，子线程按被调用方的白名单授权，只有主线程能派生，不得递归 CALL。这些都不变。
- **跨 Workspace 的目标**：见[身份与访问体系 Idea](../ideas/identity-and-access-model.md) T-5b。
- **访问 context 本身**：密封、签发与撤销的机制，以及进程 context 的生命周期。
- **写入意图**：派发、shield 与“已提交的写入不撤回”的规则。
- **停止**：停止规则、部分输出与检查点接受的规则。

## 4. 目标设计

### 4.1 定义与对应关系

> **执行线程**：任务进程在 Actor 阶段内的一个执行主体，回答“这一步是谁在执行”。它恰好属于一个进程，共享进程的资源，有自己的身份、凭据、能力与生命周期；CPU 在内部把它对应到自己的执行上下文（Alice 的帧）。

| 操作系统 | 目标模型 | 现在 |
|:---|:---|:---|
| 进程的线程列表 | 进程的线程表 | 工作集里的凭据字典 |
| 凭据按线程存放 | 每个线程一份线程 context，身份只在凭据内 | 已经如此，保留 |
| 线程共享地址空间 | 驻留 Workspace、principal、派发话题、会话归进程所有，线程只引用 | 已经如此，保留 |
| `clone` 必须经过内核 | 派生经线程表，凭据只由认证一侧签发 | 派生藏在一个 actor 操作里 |
| `pthread_exit` | 子线程随 CALL 返回结束 | 子线程一直有效到 Actor 阶段结束 |
| 进程收到终止信号，全部线程终止 | 停止被接受时全部线程结束 | 读取放行，写入与派生被拒绝 |
| 栈与寄存器归 CPU | 帧归 CPU，帧持有所属线程的描述 | 帧与线程没有共同标识 |

### 4.2 线程表与线程对象

**进程与线程的对应**：

| | 进程 | 线程 |
|:---|:---|:---|
| 登记表 | `ProcessTable`：全系统一份，按 `process_id` 登记全部进程 | `ProcessThreadTable`：每个进程一份，即 `TaskProcess.threads`，按 `thread_id` 登记本进程的线程；取代 `ProcessWorkingSet.thread_contexts` |
| 被登记的对象 | `TaskProcess`：进程容器，不离开注册入口 | `ProcessThread`：线程对象，不离开 `ProcessThreads` |
| 可变的控制状态 | `ProcessRecord`：访问 context、阶段与结局、绑定了标签的事件 | `ProcessThread` 自己的字段：线程 context、状态、父线程 |
| 冻结的参数 | `ProcessRequest`：任务参数 | `ThreadDescriptor`（阶段二）：标识、观测标签、图纸、操作快照 |
| 待释放的资源 | `ProcessWorkingSet` | 无：唯一要释放的是线程 context，已在线程对象中 |
| 执行流与输出 | 进程 task、输出通道 | 无：线程在 CPU 内执行（Alice 的帧），交互事件经进程的输出通道 |
| 交给外部的视图 | `ProcessHandle`：交付方持有 | `ExecutionThread`：CPU 驱动持有，即描述与线程 context；`ResolvedThread`：能力层的一次解析结果 |

**线程不另设“记录”一层**：进程单独设 `ProcessRecord`，是因为控制状态有自己的使用方。停止请求、事件发布、可中断阶段的 task 绑定与进程控制授权都只读写记录，而容器还要容纳生命周期各不相同的任务参数、工作集、task 与输出通道。线程只有两部分，即可变的控制状态与冻结的描述，也没有哪个使用方只需要控制状态。再拆一层只会多出一个没有独立使用方的类型，所以由 `ProcessThread` 一个对象承担 `TaskProcess` 的角色，它冻结的部分就是线程描述。

**线程对象** `ProcessThread`（`workspace/process/threads.py`）：
- `thread_id`：主线程为 `main`，子线程按派生顺序为 `child-1`、`child-2`……；阶段二起由线程描述携带；
- `parent_id`：主线程为空，子线程为 `main`；
- `access`：线程 context。线程的身份只在其中，线程对象不另存 actor 字段；
- `state`：`RUNNING` 或 `ENDED`；
- `descriptor`：线程描述（阶段二，见第 4.6 节）。

**线程表登记的内容**：
- 每个派生成功的线程登记一个 `ProcessThread`，以 `thread_id` 为键。派生的各步（签发线程 context、读取操作快照）全部成功后才登记，失败时不留下登记；
- 下一个子线程标识的计数器；
- 已结束的线程留在表中，直到进程关闭：标识不复用，已结束的线程仍可按标识识别。

**线程表不登记的内容**：
- **进程的资源**：驻留 Workspace 与 principal 在进程 context 中，派发话题在工作集中，会话属于会话服务。线程只经所属进程引用它们；
- **CPU 一侧的执行状态**：帧与提交函数归 CPU 驱动；
- **写入意图**：属于意图登记，只以 `thread_id` 归因。

**生命周期**：线程表随进程创建，创建时为空；只在 Actor 阶段内有登记；随进程一起丢弃。

**唯一入口**：`ProcessThreads`（共享，持有进程表、`ThreadContextLifecycle` 与授权者）是派生、结束与解析的唯一入口，线程表与线程对象的写方法只由它调用。执行器、CPU 分配与能力层都不直接读写线程表。

### 4.3 生命周期与存活判定

- **状态**：派生 → 运行 → 结束。结束是同步动作：撤销线程 context，线程对象的状态置为 `ENDED`。重复结束是空操作。
- **结束时点**：
  1. **子线程随 CALL 返回结束**（阶段二）：CPU 驱动在 CALL 收尾时经操作入口提交结束，见第 4.5、4.7 节。
  2. **停止被接受时全部结束**：存活判定读取进程记录的结局，停止被接受即生效，停止路径不需要通知线程表。凭据的撤销仍在 Actor 阶段收尾时执行，两者之间的提交按线程已结束拒绝。
  3. **Actor 阶段结束时全部兜底结束**：`ProcessThreads.end_all(process)` 取代 `revoke_threads`，仍只在 `_run_actor` 的 `finally` 中调用一次；关闭流程先于任何 await 兜底调用。
- **存活判定**只在 `ProcessThreads.resolve` 中做一次，依次检查：
  1. 线程 context 未撤销，且运行绑定是执行线程；
  2. 进程存在于进程表，线程已登记在该进程的线程表中，且登记的 context 就是这一个（按对象身份比较）；
  3. 线程状态为 `RUNNING`，进程结局为 `RUNNING`。

  不检查阶段：线程只在 Actor 阶段内存在，Actor 阶段结束时全部结束。
- **拒绝**：
  - 线程已结束（context 已撤销、线程状态为 `ENDED`，或进程已收到停止）时，以 `ThreadEndedError` 拒绝；
  - context 类型或运行绑定不对、线程未登记、进程不在进程表中，属于接线缺陷，仍以 `ScopeRequiredError` 拒绝；
  - 只有主线程能派生、主线程不能被 CPU 结束，违反时同样以 `ScopeRequiredError` 拒绝。
- **生命周期错误**：`ThreadContextRevokedError` 更名为 `ThreadEndedError`，code 改为 `workspace.thread.ended`，仍在 `core.errors`，由 `workspace.contracts` 重新导出。MTP 文案键随之改为 `mtp.system.thread_ended`；错误码 `mtp.system.fault` 与文案不变。错误名与现有文案一致：它覆盖的是“线程已结束”，而不只是“凭据已撤销”。

### 4.4 一次解析与能力层端口

- **授权者**：`validate_thread_context` 与 `get_thread_process_id` 合并为一个只读查询 `get_thread_binding(access) -> RunBinding`。它读出运行绑定，context 已撤销时以 `ThreadEndedError` 拒绝，不是线程 context 时以 `ScopeRequiredError` 拒绝。架构测试限定它只由 `workspace/process/threads.py` 调用。`authorize_thread_operation` 只随错误更名修改。
- **解析结果**：`ProcessThreads.resolve(access) -> ResolvedThread`。`ResolvedThread` 带 `process_id`、`thread_id` 与 `dispatch_topic_id`，只在 workspace 内部使用，不进入 CPU 可见的对象。
- **端口**：`workspace/thread_ports.py` 的 `ChildThreadSpawner` 与 `IntentDispatchTopicReader` 合并为一个端口 `ExecutionThreadTable`，由 `ProcessThreads` 实现、组合根注入：
  - `resolve(access)`；
  - `derive_child(parent, profile)`；
  - `end_child(access)`（阶段二）。
- **操作入口**：`WorkspaceOperationEntry.execute` 在分派前调用 `resolve`，取代 `validate_thread_context`。全部 actor 操作因此共用同一个存活判定，拒绝时没有副作用。
- **写入**：WRITE 与 UPDATE 在登记前的同步段中调用一次 `resolve`，从结果取得 `process_id`、`thread_id` 与派发话题，取代 `get_thread_process_id` 与 `get_dispatch_topic` 两次调用。UPDATE 的基础冷读仍在同步段之前；冷读跨越线程结束或停止时，在同步段中拒绝，不产生意图。
- **意图归因**：`PendingAtom` 增加只作观测的 `thread_id: str | None`。`WriteIntentRegistry.register_write` 与 `register_update` 接收它，回读与授权不读取它。

### 4.5 派生与 `agent.call` 分开（阶段二）

- **请求**：`DeriveCallThreadRequest(agent_alias)` 仍是 MTP CALL 对应的请求，但不再继承 `OperationRequest`。`execute` 只接受五项记忆请求；提交函数的泛型调用不再需要在运行时拒绝派生请求，由类型约束保证。
- **`agent.call`**：`ActorAgentService.derive_call_thread` 改为 `resolve_call_target(request, *, access) -> AgentProfile`：以调用方的线程 context 授权 `agent.call`，再以调用方的 scope 读取目标图纸。结果只有图纸，不含凭据，actor API 也不再依赖线程端口。
- **操作入口的生命周期方法**（`OperationEntry` 协议增加两项）：
  - `async derive_child_thread(request, *, access) -> ExecutionThread`：
    1. `resolve(access)` 确认调用方存活；
    2. 调用 `resolve_call_target`；
    3. 调用线程表的 `derive_child(parent=access, profile)`。`derive_child` 在冷读之后重新判定调用方存活，确认调用方是主线程，再以被调用方准入后派生、以子线程 context 读取操作快照并登记；快照读取失败时撤销，不登记。
  - `end_thread(*, access) -> None`：同步调用线程表的 `end_child`。已结束的线程是空操作；主线程以 `ScopeRequiredError` 拒绝。
- **为什么只在入口组合**：被调用方的身份必须来自 workspace 自己的解析。如果拆成“先取图纸、再凭图纸派生”两次提交，CPU 就能交回一份伪造的图纸，执行单元等于自报了子线程的身份。入口依次调用 actor 操作与生命周期动作，两者在代码上分开，但在一次提交内完成。

### 4.6 线程描述与 CPU 端口（阶段二）

- **线程描述** `ThreadDescriptor`（`workspace.contracts`，冻结，CPU 可见）：`thread_id`、`labels: ExecutionLabels`、`agent_profile`、`allowed_operations`。
- **执行线程** `ExecutionThread`：只交给 CPU 驱动，主线程与子线程同用。字段改为 `descriptor` 与 `access`。
- **观测标签**：取线程自己的身份。主线程为注册标签；子线程为 `ExecutionLabels(agent_id=被调用方, workspace_id=注册标签的 workspace_id)`。标签由线程表在派生时生成并放进线程描述，Alice 不从图纸推导。`ExecutionLabels` 的说明随之修改，标签仍只用于观测与提示词。
- **主线程的派生**：执行器把 prepare 之前解析的图纸交给 `derive_main(process, profile) -> ExecutionThread`。`derive_main` 派生主线程 context，以它读取操作快照并登记，与子线程相同。CPU 分配不再读取操作快照；读取失败时，`derive_main` 撤销刚签发的 context，不登记。
- **CPU 端口**：签名改为 `execute(manifest, *, thread: ExecutionThread, generation_options, events) -> CPUExecutionResult`，以 `thread` 取代 `access`。
- **输入清单**：`CPUInputManifest` 删除 `agent_profile` 与 `allowed_operations`，改由主线程描述携带。清单保留：
  - `labels`：进程级的注册标签，供运行级观测与历史归属使用，与主线程的标签相同；
  - 本轮材料、语言与会话历史。

  清单回答“处理什么”，线程描述回答“谁来处理”。
- **提交函数**：`ThreadOperationSubmitter(entry, thread)` 是 CPU 侧唯一的线程句柄：
  - `.thread` 返回线程描述；
  - 泛型调用提交记忆请求；
  - `async derive_child(request)` 返回子线程的提交函数；
  - `end()` 同步结束本线程。

  `OperationSubmitter` 协议随之修改，`Callee` 删除。帧持有所属线程的提交函数，帧与线程的对应关系由此建立，`RuntimeScope` 不增加字段。
- **CPU 端口契约**补充一条：收到取消后的收尾不得依赖 actor 操作，只能用已经产生的内容组装结果。

### 4.7 Alice（阶段二）

- **AliceCPU**：以 `thread` 构造主线程的提交函数。运行服务从主线程描述取得图纸与操作快照，用于模型解析、根帧与 MTP 动词；注册标签仍取自清单，用于 `agent.run.*` 与历史中的 `current_agent_id`。
- **CALL 的被调用方**：`CallContext.callee` 改为子线程的提交函数。编排从 `callee.thread` 读取图纸、操作快照与标签。子帧的 `RuntimeScope.labels` 取 `callee.thread.labels`，策略仍由被调用方的快照翻译并去掉 CALL。
- **子线程的结束**：以下情形都调用子线程提交函数的 `end()`：
  - `complete_call`：子帧以任何终态结束，包括完成、失败、取消与预算耗尽；
  - `cancel_call`：取消沿递归栈清理 CALL；
  - 派生成功之后、子帧开始运行之前的任何失败：共享上下文读取失败、子帧创建失败。

  `end()` 是同步调用，可以在取消收尾中执行，不引入新的 await。Alice 不结束主线程。
- **随标签改变的观测**：
  - 子帧的 `agent.context.budget_exceeded` 改为报告被调用方的 `agent_id`；
  - 帧事件的 `agent_id` 仍优先取 Profile 的来源 alias，只有回退值随之改变；
  - `sub_agent_start`、`sub_agent_end` 的 `agent_id` 仍取 CALL 请求的目标 alias，不变。

### 4.8 停止

- **处理顺序**（执行线程 Idea 第 3.3 节）：
  1. 停止请求同步记录停止，并取消 Actor 子 task，全部线程随之结束；
  2. CPU 只用已产生的内容组装 cancelled 结果；
  3. Actor 阶段收尾撤销凭据、接受检查点，之后的封口、会话写入、finalize 与 cleanup 都经进程 context 完成。
- **代码改动**：`ProcessRecord.request_stop` 不变。“线程随停止结束”由存活判定读取进程结局实现，不新增停止到线程表的通知。
- **停止那一刻已在途的操作**：读取随子 task 的取消中断；已开始派发的写入受 shield 保护照常完成，与现行规则一致。
- **Alice**：取消路径不提交 actor 操作，已经满足 CPU 端口契约的新增条款。阶段一以测试 CPU 覆盖“停止后提交被拒绝”，阶段二的端口契约把这一点写成 CPU 的义务。

### 4.9 必须保持的行为

- **CALL 授权链**：
  - 调用方须持有 `agent.call`；图纸按调用方的可见性读取，不可见与不存在相同；
  - 被调用方须通过准入，不能是保留的 `system`；
  - 子线程按被调用方的白名单与可见性授权，写入记在被调用方名下，派发到与主线程相同的话题；
  - 只有主线程能派生，子帧策略去掉 CALL；
  - 快照读取失败不留下凭据或登记。
- **写入意图**：
  - ACK 表示已登记并被生成队列接纳；
  - 同步段内复查、读取话题并登记；
  - 派发开始后由 shield 保护直到完成；
  - 停止、线程结束、进程终态与 CALL 子帧失败都不撤回已提交的写入。
- **撤销**：
  - 全部线程 context 在 finalize 之前撤销；
  - Actor 阶段的兜底结束只在 `finally` 中执行一次，关闭流程的兜底先于任何 await；
  - 进程 context 最后由注册入口撤销。
- **停止、部分输出与检查点**：规则与事件均不变。
- **身份数据**：
  - CPU 读不出 context，也不持有进程 context；
  - 请求不携带身份、目标 Workspace 或 process_id；
  - context 不进入输入清单、记录或事件；
  - 标签与操作快照不是授权依据。
- **观测**：SSE 的事件名、字段与顺序不变；`chat.run.*` 与 `agent.run.*` 仍使用注册标签。
- **呈现**：线程结束仍以 `mtp.system.fault` 与“[Thread Ended] 原线程已结束”的文案呈现给 agent。
- **其他调用面**：root API 与阶段授权不受影响。

### 4.10 有意的行为变化

1. **停止之后全部 actor 操作被拒绝**：停止被接受后，READ、SEARCH、RUN 也以 `ThreadEndedError` 拒绝；WRITE、UPDATE、CALL 的拒绝由 `ScopeRequiredError` 改为 `ThreadEndedError`。对 Alice 没有可观察的差别：Actor 子 task 立即被取消，取消路径不提交操作。
2. **子线程随 CALL 返回结束**：Alice 的子线程凭据在 CALL 收尾时撤销，不再等到 Actor 阶段结束。子线程已提交的写入不受影响。
3. **子帧标签取被调用方的身份**：子帧的 `agent.context.budget_exceeded` 报告被调用方；帧事件 `agent_id` 的回退值随之改变。
4. **错误更名**：`ThreadContextRevokedError` 更名为 `ThreadEndedError`，code 改为 `workspace.thread.ended`，MTP 文案键改为 `mtp.system.thread_ended`。它们没有 HTTP 映射；会话历史记录的是错误码 `mtp.system.fault` 与渲染后的文案，不受影响。
5. **意图记录 `thread_id`**：只作观测。
6. **主线程快照的读取时点**：主线程的操作快照改在进入 Actor 阶段时、以主线程 context 读取。准入在 prepare 与进入 Actor 之间被撤销时，进程失败的阶段由 PREPARE 变为 ACTOR，结局仍是失败。

## 8. 测试和验收标准

按[测试设计规范](../governance/testing/test-design-standards.md)分类。每条不变量只在作出判断的归属层写权威测试，上层与 E2E 只保留代表性链路；验收测试写入归属层的现有文件。

1. **线程表与生命周期**：
   - 派生登记线程，标识按派生顺序分配、结束后不复用；
   - 结束撤销凭据并且幂等；
   - Actor 阶段结束与关闭流程都结束全部线程；
   - 派生失败不留下登记。

   归属：进程线程管理，`tests/integration/workspace/test_process_threads.py`。
2. **统一的存活判定**：
   - 停止被接受后，六项 actor 操作都以 `ThreadEndedError` 拒绝，且没有副作用（不登记意图、不派生子线程）；
   - 线程结束后的提交同样被拒绝；
   - 接线缺陷仍以 `ScopeRequiredError` 拒绝。

   归属：进程线程管理与操作入口，`test_process_threads.py`、`tests/integration/workspace/test_operation_requests.py`。
3. **一次解析与写入**：
   - WRITE、UPDATE 的进程关联、线程标识与派发话题都来自解析结果；
   - UPDATE 的基础冷读跨越停止或线程结束时拒绝，不产生意图；
   - 已开始派发的写入不受停止影响。

   归属：`test_process_intents.py`、`test_inflight_dispatch.py`。
4. **意图归因**：登记记录 `thread_id`，回读不受它影响（`tests/unit/workspace/intents/test_registry.py`）；主线程与子线程的写入分别记录各自的标识（进程意图测试中的一个代表性用例）。
5. **派生与 `agent.call` 分开（阶段二）**：
   - `agent.call` 只返回图纸；
   - 缺少 `agent.call`、图纸不可见、被调用方未准入或为 `system` 时都不派生；
   - 只有主线程能派生；
   - 冷读期间调用方结束或进程收到停止时不派生。

   归属：actor API 与进程线程管理，`tests/unit/workspace/capability/actor/test_agent_profiles.py`、`test_process_threads.py`、`test_thread_context.py`。
6. **子线程随 CALL 返回结束（阶段二）**：
   - CALL 以完成、失败、取消结束，以及派生之后的准备失败，都会结束子线程；
   - 之后用子线程提交函数提交，以 `ThreadEndedError` 拒绝；
   - 子线程已派发的写入照常完成。

   归属：Alice CALL 编排，`tests/unit/alice/orchestration/call/test_coordinator.py`、`test_context.py`；链路代表性用例在 `tests/integration/alice/orchestration/call/test_operation_requests.py`。
7. **子帧标签（阶段二）**：子帧的观测标签为被调用方；子帧的 `agent.context.budget_exceeded` 报告被调用方的 `agent_id`（`tests/unit/alice/orchestration/test_executor.py`）。
8. **CPU 端口（阶段二）**：
   - 主线程以执行线程交给 CPU，描述中的图纸、快照与标签和派生结果一致；
   - 测试 CPU 采用同一形态；
   - Alice 从描述取得图纸与动词，交互事件与终态结果不变。

   归属：`tests/unit/workspace/process/`、`tests/integration/alice/run/`、`tests/unit/alice/interface/`。
9. **架构守卫**：
   - `get_thread_binding` 只由线程管理调用；
   - 线程生命周期端口只由线程管理使用；

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| 停止后拒绝读取，会让收尾时仍要读取的 CPU 失败 | 第 4.6 节把“收尾不依赖 actor 操作”写进端口契约；Alice 的取消路径不提交操作，测试 CPU 覆盖停止后的拒绝 |
| 取消路径中结束子线程引入新的挂起点 | `end()` 是同步调用；结束幂等，与 Actor 阶段的兜底结束不冲突 |
| 子线程结束时仍有它发起的在途操作 | CALL 只在子帧到达终态后收尾；取消时，子帧的在途操作先随取消中断。已登记的写入在派发时不再复查线程 |
| 子线程标识复用，导致归因混淆 | 计数器分配，已结束的线程对象保留到进程关闭 |
| 输入清单删除两个字段，测试改动较多 | 清单只在 CPU 分配与 `tests/helpers/chat_handoff.py` 中构造，生产读取点集中在 Alice 运行服务与上下文构建；断言清单图纸与快照的测试（CPU 分配单元测试、操作白名单 E2E）改为断言主线程描述 |
| 主线程快照改在 Actor 入口读取，失败阶段改变 | 只影响准入在 prepare 与 Actor 之间被撤销的情形，结局仍是失败；列为第 4.10 节第 6 项 |
| 错误更名影响错误呈现 | 错误码 `mtp.system.fault` 与文案不变，只改类型名、code 与文案键；没有 HTTP 映射，前端不读取这些值 |

- 线程表的位置、线程对象的字段，以及线程不另设记录一层；
- `ThreadEndedError` 与 `workspace.thread.ended` 的命名；
