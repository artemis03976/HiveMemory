# v0.8.1 馆长改用原生工具调用：动作不再从文本中解析

> 状态：Planned（2026-11-28）。修的是馆长的动作协议。owner 的决定（2026-11-28）：所有模型统一改用模型服务的原生工具调用，不为某个模型单独适配。依据是当前代码与[记忆生成](../patchouli/generation.md)第 4 节“馆长”，问题的核实记录在试验场 `.hivememory/lab/librarian-action-parse/FINDINGS.md`（不受版本控制）。

## 1. 背景和问题

馆长是话题沉淀的一种生成方式：一个会使用工具的 agent，先看本话题生成的记忆、检索库中相关的记忆，再决定新建或修订。它的动作现在写在文本里：每一步，馆长要求模型输出一个 JSON 对象 `{"tool": "<名称>", "args": {…}}`，用宽松的 JSON 解析器读出来，再执行工具。

2026-11-21 随附配置的生成模型从 `deepseek/deepseek-chat` 换成 `deepseek/deepseek-flash`（PR #237）之后，这个协议出了两个问题：

1. **无法解析**：这个模型在馆长这种像工具调用的对话里，会改用它自己的原生工具调用格式。馆长的请求开着 JSON 模式，DeepSeek 在 JSON 模式下把不是 JSON 的部分换成空格，于是输出只剩空白、只剩参数对象，或混着残留的标记。每次计一步。日常实例换模型之前 81 步中 0 次，之后 804 步中 77 次（9.6%），73 次结算中 14 次步数用完。
2. **静默丢弃**：模型常在一次输出里连着写好几个动作。`_parse_action` 调用的 `parse_llm_json` 只取第一个 JSON 对象，其余不报错地丢掉，整步算一次成功的动作。探针中有一次输出连着 7 条写入加一个 `finish`，只暂存了第一条，模型下一步就结束了。进展记录目录实验中“只写 1～2 条就结束”的运行，在同一模型与提示词的探针里以这种方式复现（17 次运行中 6 次）。

探针的对照（核实记录第 4 节）：同一个 `deepseek-flash` 改用原生工具调用，131 步没有一次格式错误，一次返回的多个调用都能执行；`gpt-6-luna` 在文本协议与原生工具调用下都是 0 次。所以问题在于协议与模型训练出的习惯冲突，不在某个模型的偶然失误。静默丢弃则与模型无关：任何模型输出了两个相连的 JSON 对象，都会被吞掉。

## 2. 目标与非目标

### 2.1 目标

- 馆长的动作改为模型服务的原生工具调用，所有模型同一条路径，没有按模型的分支。
- 模型一次返回的多个工具调用按顺序全部执行，不再有被吞掉的动作。
- 模型没有调用工具、或参数不是合法 JSON 时，作为错误交回、计一步，与现在“无法解析”的处理相同，并在日志中区分。

### 2.2 非目标

- **MTP 不变**：Alice 的记忆工具协议仍是文本协议（[MTP 契约](../contracts/mtp.md)）。馆长不是 MTP：它的工具只读写 Patchouli 自己的数据，不经过 actor API。
- **其他模型调用不变**：一次性生成、Mode B / Mode C、合并、折叠摘要、进展记录、Gateway 都是一问一答，仍按文本与 JSON 模式输出，日志中没有同类问题。
- 不处理核实中顺带发现的问题：Gateway 话题路由在换模型之后开始超时；思考模式下温度设置无效；`gpt-6-luna` 在推理开启时不接受 0.3 的温度。
- 不改馆长的工具集合、工作顺序、预算数值与写入、修订的规则。

## 3. 当前状态（2026-11-28 核对）

- `infrastructure/llm/base.py`：`complete(messages, params)` 的消息类型是 `list[dict[str, str]]`；`LLMRequestParams` 没有工具定义，有 `json_output`；`LLMCompletion` 只有 `text`、`finish_reason` 与 `usage`，文档写明“提供商没有返回文本时实现显式失败，不构造本结果”。
- `infrastructure/llm/litellm_service.py`：`_complete` 取 `choices[0].message.content`，不是字符串时抛 `ModelProviderError`；不读 `tool_calls`，也不读 `reasoning_content`。`LiteLLMService` 是 `BaseLLMService` 的唯一生产实现。
- `engines/generation/librarian.py`：构造时把 `json_output` 设为真；每步把 `completion.text` 作为 assistant 消息追加，用 `_parse_action`（`parse_llm_json`，取第一个对象）读出一个动作，执行之后把结果连同 `steps_left` 作为一条 user 消息交回。六个工具的参数模型是 `_SearchArgs`、`_ReadArgs`、`ExtractedMemoryDraft`（写入时补上 `has_value`）、`_ReviseArgs`，另两个没有参数。
- `i18n/prompts.py` 的 `librarian`（中英文）：系统提示词有“动作格式”一节与带 JSON 写法的工具说明；`error_unparsable` 文案要求“每次只输出一个 JSON 对象”。
- 测试：`tests/unit/engines/generation/test_librarian.py` 用 `tests/helpers/llm.py` 的 `ScriptedLLMService` 按文本脚本驱动循环；`tests/unit/infrastructure/test_litellm_service.py` 覆盖 litellm 的参数构造与结果读取。

## 4. 进入条件

- owner 已选定原生工具调用、所有模型统一（2026-11-28）。
- 核实记录的探针已经在 DeepSeek 与 OpenAI 上用 litellm 走通工具调用（含 DeepSeek 要求的思考内容回传）。

## 5. 目标设计

### 5.1 LLM 接口：携带工具，交回工具调用

- **请求**：`LLMRequestParams` 加 `tools`，是工具定义的元组（名称、一句说明、参数的 JSON Schema），缺省为空。带工具时 `tool_choice` 固定为 `auto`，不开放配置：DeepSeek 在思考模式下不接受 `required`，`auto` 对各家都成立。`tools` 与 `json_output` 同时给出时构造失败。
- **结果**：`LLMCompletion` 加两项：
  - `tool_calls`：模型返回的工具调用，每个带 id、名称与参数原文（未解析的 JSON 字符串），缺省为空；
  - `assistant_message`：模型服务返回的 assistant 消息原样（litellm 归一之后的字典），调用方把它追加进对话。DeepSeek 带工具时要求把前面各轮的思考内容原样传回，Anthropic 的思考模式也有类似要求；原样追加让调用方不需要知道是哪一家。
- **文本可以为空**：带工具调用的结果可以没有文本。只有既没有文本、也没有工具调用时，才以 `ModelProviderError` 结束。
- **消息类型**放宽为 `list[dict[str, Any]]`，以容纳带 `tool_calls` 的 assistant 消息与 `tool` 消息；只改类型标注，其他调用方的消息不变。
- **流式调用**不支持工具：`stream=True` 且带工具时构造失败，显式拒绝。馆长只用完整调用。
- **不在装配时检查模型是否支持工具调用**：最简单的做法是不支持的模型由提供商返回错误，转为 `ModelProviderError`，结算任务以 `model_provider_failed` 失败，这已经是结构化的失败。暂不处理的是“装配时就报错”，需要时再加。

### 5.2 馆长：按工具调用执行

- **工具定义**由已有的参数模型生成 JSON Schema，作为唯一来源：`_SearchArgs`、`_ReadArgs`、`_ReviseArgs`；写入用 `ExtractedMemoryDraft` 去掉 `has_value`；`list_generated_memories` 与 `finish` 没有参数。每个工具的说明是一句话，工作顺序与语义仍写在系统提示词里。
- **循环**：每次请求模型，把返回的 `assistant_message` 追加进对话。
  - 结果带工具调用时，按顺序逐个执行，每个调用计一步，每个调用都交回一条 `tool` 消息（OpenAI 形态要求每个调用 id 都有回应），内容是工具结果连同 `steps_left`。
  - 一批调用执行到一半步数用完时，余下的调用各交回“步数已用完”的错误，不执行，循环结束。
  - `finish` 之后同一批中的调用交回“已经结束”的错误，不执行。
  - 结果没有工具调用时，交回一条 user 消息说明要调用工具，计一步。
  - 参数不是合法 JSON 时作为参数错误交回、计一步；参数不合格、工具不存在、修订不能落地，与现在一样作为工具错误交回。
- **不再设 `json_output`**，删除 `_parse_action` 与 `_Action`。
- **日志**：每次结算一行的 `tool_calls` 中，`unparsable` 换成 `no_tool_call` 与 `invalid_json` 两项；另记模型请求的次数，步数多于请求次数，说明有请求返回了多个调用。其余字段不变。
- **预算与失败语义不变**：步数上限仍是 `max_steps`（每个执行的调用一步）；提供商失败在同一步内重试一次；重试耗尽或超窗原样传播。

### 5.3 提示词

中英文两份同改：

- 删去“动作格式”一节；
- 工具一节保留每个工具的作用与参数含义，去掉字面的 JSON 写法；
- 步数一句改为“每个工具调用算一步”；
- `error_unparsable` 换成“没有调用工具”的文案；新增参数不是合法 JSON、步数已用完与已经结束三条错误文案。

## 7. 兼容与迁移

- 没有数据迁移，没有配置键变化。
- 已经排队的结算任务在新版本启动后照常由新的馆长执行；任务里保存的是材料，不是对话。
- 换用不支持工具调用的模型时，馆长的结算会以 `model_provider_failed` 失败；一次性生成不受影响。这一点写进记忆生成文档的馆长一节。

## 9. 风险与待决问题

- **思考内容的回传**：原样追加 litellm 归一之后的 assistant 消息，要确认 litellm 把 DeepSeek 的 `reasoning_content` 带回请求。核实记录的探针 C1 是手动传回的；实施时先用一次真实调用核对，不行就在 LLM 服务里显式保留这一字段（仍不分提供商）。
- **提示词改动会改变馆长的行为**：去掉动作格式、工具说明改写之后，写出的条数与修订可能变化。真实环境验收中并排看一次。
- **一步多个调用的步数**：模型一次返回很多调用时，一步的模型调用可能用掉多个步数，结算更早结束。这是按调用计步的直接结果，与现在“每个动作一步”的含义相同；探针中 C1 每次运行暂存 6～7 条，没有更早结束。

默认做法（实施时直接采用，不阻塞）：`tool_choice` 固定 `auto`；不做装配时的能力检查；`finish` 之后的调用不执行；工具说明一句话、语义留在提示词。

## 11. 实施记录

2026-11-28 在分支 `docs/v0.8.1-librarian-native-tool-calls-plan` 实施第 5 节，改动没有提交，留给 owner 在本地审阅。计划没有写到的细节与所作的选择：

- **两个新类型**：`base.py` 新增 `LLMTool`（名称、一句说明、参数的 JSON Schema）与 `LLMToolCall`（id、名称、参数原文）。`infrastructure/llm/__init__.py` 的导出不变，唯一的使用方馆长从 `base` 导入。
- **`tools` 与 `json_output` 互斥**：由 `LLMRequestParams` 上的校验保证。馆长不再用 `model_copy`（它不经校验），改为以原参数加上工具重新校验，传入的参数要求 JSON 输出时在装配时失败。其他调用方的 `model_copy(update={"json_output": True})` 不变，它们不带工具。
- **流式带工具的拒绝**放在 `BaseLLMService.complete` 的入口，以 `ValueError`（调用方的程序错误）拒绝、不发请求，对所有实现都成立。
- **“没有文本”的含义不变**：返回的 `content` 不是字符串才算没有文本，空串仍是文本，所以不带工具的调用方行为不变。只有工具调用时 `text` 为空串。
- **assistant 消息**取 litellm 归一之后的消息的 `model_dump()`。`LLMCompletion` 上它缺省为空字典，只为测试替身与脚本里的服务不必提供；唯一的生产实现总是给出。litellm 发请求前去掉值为 None 的键，所以 `function_call`、空的 `provider_specific_fields` 不会发出。
- **参数 Schema 去掉说明文字**：参数模型上的说明是中文（草稿模型的字段说明与 docstring、三种编辑的 docstring），原样交给英文提示词时，模型会跟着用中文写记忆；一次性生成为此给格式说明配了译文表。馆长的参数含义按第 5.3 节写在提示词里，所以 Schema 一律去掉值为文字的 `description`，只留结构，不为编辑类型另加译文。写入的 Schema 再从属性与 `required` 中去掉 `has_value`。pydantic 生成的 `title`、`$defs`、`oneOf` 与 `discriminator` 保留，第 11.1 节的真实调用确认 DeepSeek 接受。
- **工具说明**放在 `prompts.py` 的 `librarian` 下，键为 `tool_<工具名>`，中英文各六条，与其他交给模型的文字一样随语言切换。
- **参数是合法 JSON、但不是对象**（例如一个数组）：与不是合法 JSON 一样计为 `invalid_json`，交回同一条错误，不执行。空串参数不做容错：探针中 DeepSeek 与 luna 对没有参数的工具都返回 `"{}"`。
- **tool 消息的内容**只有工具结果（`result` 或 `error`）与 `steps_left`；原来 user 消息中的工具名去掉，调用由 `tool_call_id` 对应。没有执行的调用（步数已用完、`finish` 之后）的错误回应同样带 `steps_left`。
- **日志**：`steps=` 之后加 `requests=`；`tool_calls=` 中的 `unparsable` 换成 `no_tool_call` 与 `invalid_json`。没有执行的调用不计入 `tool_calls`（见第 11.3 节）。`LiteLLMService` 的调试日志另记工具调用的个数。
- **用户提示词**结尾“输出第一个动作”改为“调用第一个工具”，英文同改；英文工具出错一句的 “fix the action” 改为 “fix the call”。没有工具调用时的错误写“每次回复都要调用工具”，不写“每一步调用一个工具”，因为一次回复可以带多个调用。
- **测试的构造**：`tests/helpers/llm.py` 新增 `tool_call_completion`，以 `LLMCompletion` 表达只有工具调用的一次回应（调用 id 各不相同，assistant 消息是 OpenAI 形态），馆长单元测试、引擎单元测试与流水线集成测试共用；`ScriptedLLMService` 只放宽了消息类型。

与计划不同的地方：

### 11.5 下沉到 LLM 接口的两处（2026-11-28）

owner 问馆长的逻辑中有没有可以下沉到 LLM 接口的通用部分。消息格式属于接口一层，循环与它的规则（步数怎样算、`finish`、预算用完的处理、错误文案、参数 Schema 去掉说明文字）是馆长的任务决定的，现在用原生工具调用的只有馆长，不抽通用循环。按 owner 的决定下沉两处：
