# v0.7.2 plugin 模式开放 WRITE 与 UPDATE

> 状态：Active（2026-10-31 建立并开始实施，进度见第 12 节）。设计讨论与 owner 决定见[外部 Actor Idea](../ideas/external-actor-registration-and-runtime-access.md#v072plugin-模式开放-write-与-update)第 4 节的 v0.7.2 一步与 E-8。

## 1. 背景和问题

v0.7.2 的版本目标是生成质量（[ROADMAP](../ROADMAP.md#43-v072生成质量)第 4.3 节）。plugin 模式下 Claude Code 经 MCP 只能检索与读取记忆，显式的写入与更新从未发生；主动链路中显式的 UPDATE 能正常更新记忆。owner 判断，真实使用中暴露的生成问题约有一半源于此（2026-10-30）。

开放这两项能力，要解决三个问题：

- **请求级访问到不了写入**：actor API 的写入与更新在登记前解析执行线程，从线程取得进程关联与派发话题；MCP 入口以请求级 context 提交，没有线程。
- **交互进行中没有目标话题**（E-8）：主动链路在用户消息到达时由 prepare 按 Gateway 路由准备本轮话题，写入的话题就是本轮最终所在的话题；原 Passive Ingress 也在收到 user 消息时做 Gateway 分析。退化为 Import Bus 之后，Gateway 分析改在一轮交互完整结束后进行，写入恰好发生在这段没有话题挂载的时间内。
- **记忆编译按 MTP 编写**：记忆编译是 Alice 与 MCP 共用的引擎，命名与文案却写着 MTP 的调用方式，Claude Code 读到的提示让它“使用 READ 指令”“重新发出 WRITE/UPDATE 指令”。

owner 决定（2026-10-30、2026-10-31）：

- plugin 模式开放 WRITE 与 UPDATE，与主动链路共享同一记忆更新逻辑；
- 记忆能力属于 workspace 的 actor API，不为 MTP 独占；WRITE 与 UPDATE 始终产生 PendingAtom 句柄交还前台 actor，记忆生成完成后由结算事件触发重定向；
- E-8 采用选项 D：写入时就地落位；
- 计划同时清理 MTP 命名与文案残留，包括记忆编译文本的调整。

## 2. 目标与非目标

### 2.1 目标

1. Claude Code 经 MCP 工具 `memory_write`、`memory_update` 显式写入与更新记忆：经操作入口的请求级提交进入 actor API 的同一写入与更新操作，按访问登记逐次授权，派发到 Patchouli 的 Mode B、Mode C，与主动链路是同一条链路。
2. 写入时就地落位：一轮中第一次写入时为这一轮做话题路由并登记落点，写入以该话题派发；轮次结束回流时 Import Bus 沿用落点，写入的话题就是这一轮最终所在的话题。
3. 工具结果交还 PendingAtom 句柄；`memory_read` 回读在途句柄，结算后重定向到正式记忆。
4. 写入与更新的调用随对话回流时不被 Mode A 再提取一遍。
5. 记忆编译的命名与文案不再按 MTP 编写：指引下一步操作的句子只写能力，Alice 与 MCP 得到同一份文案。

### 2.2 非目标

- 查重与更新机制（G-2、G-3）：显式写入经过现行的查重，查重判出的 UPDATE 仍整体覆盖；见[多条提取与查重 Idea](../ideas/settlement-multi-memory-extraction-and-dedup.md)。
- 一个话题提取多条记忆（G-1）。
- 生成材料包含当前一轮：材料仍是话题过去若干轮与状态摘要（W10），对话流式接收之后再改变。
- 写入意图的持久化、结算对账、句柄过期与意图 policy（[写入意图 Idea](../ideas/pending-intent-migration.md)第 2–6 节）。
- 用户消息时点的落位（E-8 选项 E）与流式接收；没有写入的轮次与现在完全相同。
- controller 模式；Claude Code 以外的 harness。

## 3. 当前状态（2026-10-31 核对，commit `c7b032ae`）

### 3.1 MCP 入口与操作入口

- MCP server 只有 `memory_search`、`memory_read` 两个只读工具（[MCP server](../../src/hivememory/mcp_server/server.py)）。每次调用以请求头声明经统一认证网关签发请求级 context，经门面取得的操作入口的 `execute_request` 提交，结束时撤销。
- `execute_request` 只接受 `RetrieveRequest` 与 `ResolveReferencesRequest`，其余类型以 `TypeError` 拒绝（[操作入口](../../src/hivememory/workspace/capability/operations.py)）。
- 架构守护：`execute_request` 只由 MCP 入口调用；MCP 入口不导入 actor API、root API、任务进程与 Import Bus（`tests/unit/architecture/test_access_boundaries.py`）。
- `claude_code` 的访问登记只有 `memory.read` 与 `memory.search`（`configs/workspace_actors.yaml`）。

### 3.2 actor API 与写入意图登记

- `submit_write_intent` / `submit_update_intent` 授权后经 `_resolve_for_dispatch` 解析线程，取得 `process_id`、`thread_id` 与 `dispatch_topic_id`，同步登记后派发，生成队列接纳后返回 PendingAtom（[actor API](../../src/hivememory/workspace/capability/actor/memory.py)）。
- `WriteIntentRegistry.register_write` / `register_update` 要求 `process_id` 与 `thread_id`（[登记](../../src/hivememory/workspace/intents/registry.py)）；`PendingAtom` 上二者已是可选字段，只作观测归因。
- 登记订阅结算事件；读取视图对在途句柄交付登记中的状态，结算后重定向到正式原子并重新授权；`memory_read` 已经经这一读取视图交付 pending 句柄。
- `MemoryIntent.topic_id` 必填；`MemoryGenerationCoordinator.submit_active` 以该话题的状态摘要与最近 `active_recent_blocks` 个 block 为材料，并据此构造来源，话题不存在时按空材料生成。

### 3.3 Import Bus

- `ImportBusIngestor.ingest` 在按外部会话的 `KeyedSerialGate` 内：查进度、`PASSIVE_MEMORY` 路由、封口、经 `interaction.submit` 提交（新话题携带标题与摘要，由应用时创建）、等待应用（[编排器](../../src/hivememory/system/services/import_bus/ingestor.py)）。
- 交互标识由（principal、user、Agent、来源、外部会话、外部轮次）推导；路由输入是本轮用户消息与请求中的最近几轮，最近一轮带外部标识时查出它实际落位的话题。
- 导入事件的 `verb` 只接受 `SEARCH`、`READ`，不接受 `produced_aliases`（[导入模型](../../src/hivememory/system/services/import_bus/models.py)）。
- 应用失败时返回 `import_bus.apply_failed`，连接器有限次重发，重发时重新路由并再次提交。

### 3.4 话题的预建与清理

- 主动链路经 `patchouli.public.prepare_agent_run` 准备话题，`NEW_TOPIC` 时预建，`enable_memory_retrieval=False` 时不检索；`cleanup_prepared_agent_run` 只清理仍为空的预建话题。
- 空闲结算对没有材料的话题正常结束生命周期（删除，不触发生成）；应用交互时目标话题不存在以 `ResourceNotFoundError` 拒绝。

### 3.5 Claude Code 连接器

- 插件只注册 `Stop`、`StopFailure`、`SessionStart`、`SessionEnd`（`integrations/claude-code/hooks/hooks.json`）；hook 入口不向标准输出写内容。
- 外部轮次标识取本轮用户消息条目的 `uuid`，外部会话标识取 `sessionId`；子代理条目（`isSidechain`）跳过（[读取器](../../integrations/claude-code/connector/claude_code/reader.py)）。
- 本插件的 `memory_search`、`memory_read` 归一化为 `SEARCH`、`READ`；导入请求的 `recent_turns` 由同步构造（`connector/core/sync.py`）。
- MCP 请求头是 `.mcp.json` 中的静态值，不携带外部会话或轮次。
- Claude Code 的 `PreToolUse` hook 可以按名称匹配插件的 MCP 工具，输入带会话标识与会话记录路径，可以经 `updatedInput` 改写工具参数；不给权限决定时，改写后的参数照常经过权限评估（[Claude Code hooks](https://code.claude.com/docs/en/hooks)，2026-10-31 核对）。

### 3.6 记忆编译

- 命名：`MemoryCompileTarget.MTP_READ`（Alice 的 MTP READ 与 MCP 的 `memory_read` 共用）、处理器 `handlers/mtp.py` 的 `compile_mtp_read`；`MemoryEnvelopeTarget.MTP_READ_RESPONSE` 与文案 `mtp_read_result_title` 没有生产调用方。
- 文案（[编译文案](../../src/hivememory/i18n/memory_compiler.py)）：检索上下文头尾使用 `⟪ READ | alias | ⟫`、`⟪ CALL … ⟫` 的指令语法，空结果提示使用 `⟪ SEARCH ⟫`；截断提示让读者“使用 READ 指令”；pending 句柄与引用解析结果提示“重新发出 WRITE/UPDATE 指令”“使用 SEARCH”“在后续的 READ/RUN/UPDATE 调用中使用正式别名”。
- 检索上下文由三处编译：任务进程为 CPU 编译预检索上下文（[CPU 分配](../../src/hivememory/workspace/process/allocation.py)，带头尾）、Alice 的 MTP SEARCH（带头尾）、MCP 的 `memory_search`（`include_header_footer=False`）。任务进程因此把 MTP 指令语法写进了交给 CPU 的材料。
- MCP 读取交付全文，注释写明是为了不出现指向 MTP READ 的截断提示；`compiler.py` 中一条错误信息与 `WriteIntentRegistry._slugify` 的 docstring 也指向 MTP。

## 5. 目标设计

### 5.1 一次写入的链路

| 步骤 | 位置 | 内容 |
|:---|:---|:---|
| 1 | 连接器 `PreToolUse` hook | 从会话记录读出当前一轮与之前几轮，把轮次信息经 `updatedInput` 补进工具参数 |
| 2 | Claude Code | 改写后的参数照常经过权限评估，用户按自己的设置确认 |
| 3 | MCP 入口 | 签发请求级 context；把轮次信息与操作参数分开 |
| 4 | Import Bus | 导入授权；在同一外部会话的串行门内为这一轮落位：已有落点直接返回，否则路由、准备话题并登记落点 |
| 5 | 操作入口 → actor API | 请求级提交写入或更新请求，派发话题为落点话题；授权、UPDATE 基础冷读、同步登记、派发、生成队列接纳 |
| 6 | MCP 入口 | 返回 PendingAtom 句柄；撤销 context |
| 7 | Import Bus（轮次结束） | 回流时取走落点，以落点话题提交，不再路由 |

同一轮的多次写入在第 4 步共用第一次的落点。没有写入的轮次只有第 7 步，与现在完全相同。

### 5.2 连接器：`PreToolUse` hook 补上轮次信息

- `hooks.json` 增加 `PreToolUse`，matcher 只匹配本插件的 `memory_write` 与 `memory_update` 调用名；hook 入口增加 `PreToolUse` 事件。
- hook 用同一读取器读出当前一轮（最后一条由人发出的用户消息开启的一轮）与之前 `RECENT_TURNS` 轮，按导入请求的同一规则构造轮次信息：`source`、`external_conversation_id`、`external_turn_id`、`user_message`、`recent_turns`（每轮的用户消息、回复正文与外部轮次标识，按同一长度上限截断）。外部轮次标识与轮次结束时导入的标识相同，服务端由此推导出同一个 `interaction_id`。
- 输出 `hookSpecificOutput.updatedInput`：原参数加上轮次信息字段，不给 `permissionDecision`。读不到当前一轮或任何失败时不输出，退出码仍为 0，工具调用照常进行，由 MCP 入口拒绝（5.3）。
- 子代理中的写入按主会话的当前一轮落位；子代理中 hook 输入的会话记录路径指向哪份记录，实施时核实，必要时由会话标识定位主会话记录。
- hook 不做网络请求，不登记会话记录、不唤醒同步。

### 5.3 MCP 入口：写入与更新工具

| 工具 | 参数 | 归一为 | 授权 |
|:---|:---|:---|:---|
| `memory_write` | `content`（必填）、`title`、`reason` | `SubmitWriteIntentRequest(focus=WriteFocus(...))` | `memory.write` |
| `memory_update` | `alias`（必填，要修改的记忆）、`instruction`（必填）、`content` | `SubmitUpdateIntentRequest(base_alias, instruction, content)` | `memory.update` |

- 轮次信息字段由连接器填写。入口把它转为 Import Bus 的在途轮次输入，操作请求只携带操作参数，不携带 topic_id（W6）。缺少轮次信息时以新的请求错误码拒绝（命名沿用 server 的 `request.*` 错误），不退化为不绑定话题。SDK 能否接收工具输入 schema 之外的参数，实施时核实：能则不在 schema 中暴露该字段，否则在 schema 中声明并写明由连接器填写。
- 同一份请求级 context 依次用于 Import Bus 的落位（导入授权）与操作入口的请求级提交，调用结束时撤销。目标 Workspace 取声明解析的结果，与导入入口相同。
- 结果：成功时返回 PendingAtom 的 pending alias，写明意图已登记并被生成队列接纳、正式记忆尚未持久化，可以用 `memory_read` 读取，生成完成后读取会重定向到正式记忆。错误沿用 `project_error` 投影：缺少操作许可、基础 alias 不存在或仍是 pending、派发被拒或结果未知、Import Bus 不可用（`import_bus.unavailable`）。
- 标注：两个工具都不是只读；`memory_write` 非破坏性；`memory_update` 改写已有记忆的当前版本，标注为破坏性。
- MCP 服务说明与工具说明写明何时写入与更新、ACK 的含义，以及更新以检索得到的 alias 为对象。
- 架构守护改为：MCP 入口可以导入 Import Bus 的在途轮次输入模型，并经门面调用 Import Bus 服务的落位方法；仍不导入 actor API、root API、任务进程与编排器内部。

### 5.4 Import Bus：在途轮次落位与回流沿用

- **输入**：在途轮次模型携带 `source`、外部会话与外部轮次、本轮用户消息与 `recent_turns`（复用 `ImportedRecentTurn`），校验规则与导入请求的同名字段一致。
- **服务**：`ImportBusService` 增加落位方法，以导入授权取得 scope 与 principal 后交给编排器，返回落点话题的真实 id。
- **编排器的落位**：推导 `interaction_id`；在同一外部会话的串行门内，已有这一轮的落点则直接返回；否则以 `PASSIVE_MEMORY` 路由（与导入相同的输入与续接规则），再经 `prepare_agent_run(enable_memory_retrieval=False)` 准备话题，新话题在此预建，然后登记落点。路由失败的可恢复异常与关闭中照导入的规则转为 `import_bus.unavailable`。
- **落点登记**：编排器的进程内状态，以 `interaction_id` 为键，保存落点话题与是否新建；不持久化，关闭时清空。按 `interaction_id` 而不是按外部会话保存，是因为下一轮的写入可能早于上一轮的回流到达，按会话只保留一轮会让上一轮丢失落点。
- **回流**：`ingest` 在串行门内查到这一轮的落点时，取走落点，以落点话题提交，不调用 Gateway，新话题不再携带标题与摘要。落点话题若已在本轮进行中结束生命周期（超过空闲时限被结算，或被 LRU 驱逐），应用以话题不存在失败，按现有路径返回 `import_bus.apply_failed`；连接器重发时已没有落点，按现行规则重新路由。写入的材料在派发时已经读取，不受影响。
- **预建话题的清理**：这一轮始终没有回流时，预建话题保持为空，由空闲结算按没有材料的话题结束生命周期，不另设清理；落点留到进程重启。
- **事件动词**：导入事件的 `verb` 增加 `WRITE`、`UPDATE`；`UPDATE` 与 `READ` 一样必须给出作用对象（被修改的 alias）。仍不接受 `produced_aliases`：pending alias 留在工具结果中。

Import Bus 只向网络输入的前提不变：落位读取候选话题不属于读取记忆，不返回记忆上下文。

### 5.5 操作入口与 actor API：请求级提交写入与更新

- `execute_request` 的可提交类型增加 `SubmitWriteIntentRequest` 与 `SubmitUpdateIntentRequest`，并多带一个派发话题参数：写入与更新必须给出，检索与读取不得给出，不符时以 `TypeError` 拒绝（接线缺陷）。
- actor API 的写入与更新接受同一个派发话题参数：给出时访问 context 必须是请求级 context，登记不带进程与线程关联；不给出时照旧从线程解析。线程路径的同步段与存活判定不变。
- `WriteIntentRegistry` 的 `process_id`、`thread_id` 改为可选。
- 派发、ACK、拒绝与结果未知的语义与线程路径相同；派发开始后调用方断开或取消不撤回写入。

### 5.6 回声：写入与更新调用的归一化

- 连接器的识别表增加 `memory_write` → `WRITE`（无作用对象）与 `memory_update` → `UPDATE`（参数 `alias` 移为作用对象），轮次信息字段从参数中去掉，不上传。`alias` 不是非空字符串时按普通工具写出，与 READ 的处理相同。
- 生成视图不渲染 `WRITE`、`UPDATE` 事件，Mode A 不会把显式写入的内容再提取一遍；交互记录与来源 Artifact 仍保存原始事件。

### 5.7 记忆编译不再按 MTP 编写

- **命名**：`MemoryCompileTarget.MTP_READ` 改为按用途命名的读取目标，处理器模块与函数随之改名；删除没有生产调用方的 `MTP_READ_RESPONSE` 与 `mtp_read_result_title`。
- **指引只写能力**（owner 决定，2026-10-31）：要改的是指引文案，不是编译方式。指引下一步操作的句子写出要用的能力（读取、检索、写入或更新、委托子代理），不写任何协议的指令语法、动词或工具名：工具名随 harness 与安装方式变化（Claude Code 看到的是带插件前缀的全名），能力是固定的。编译选项与各调用方的编译调用不变，Alice、MCP 与任务进程得到同一份文案，任务进程交给 CPU 的预检索上下文由此不含协议语法。能力与 MTP 动词的对应由 Alice 自己的协议教学给出：READ 是“获取完整内容”，SEARCH 是“发现未知记忆”，CALL 是“委托子代理执行专项任务”。
- **措辞**（中文；英文同义，实施时可调整）：

  | 句子 | 改动后 |
  |:---|:---|
  | 检索上下文尾部：摘要不足 | 若上述记忆摘要符合当前用户意图，但摘要信息不足，请先读取这条记忆的完整内容（严禁自行猜测或编造）。 |
  | 检索上下文尾部：专项任务 | 若任务需要专项能力（如数据分析、代码生成等），且上方列出了对应子代理，请优先委托给该子代理执行，不要自行承担。 |
  | 共享上下文引言 | 父代理共享了以下运行时记忆材料。如果需要再次检查它们，请重新读取。 |
  | 截断提示 | [...部分内容已截断，如需阅读完整内容，请读取这条记忆...] |
  | 句柄失败、解析失败 | 提示: 如需重试，请重新提交这次写入或更新。 |
  | 句柄过期、解析过期 | 提示: 如果需要，请检索已定型的记忆。 |
  | 解析丢弃 | 提示: 如果需要，请检索相关的已定型记忆。 |
  | 重定向 | 提示: 后续访问这条记忆时请使用 '{canonical_alias}'。 |

- **没有生产调用方的文案**：检索上下文的三条空结果提示（`retrieval_empty_context_notice`、`retrieval_memory_empty_hint`、`retrieval_agent_empty_hint`）写着 MTP 指令语法，没有生产调用方，一并删除。
- **在途写入句柄不显示来源**（owner 决定，2026-10-31）：原来的“来源: WRITE”一行删除。PendingAtom 只由写入意图登记创建，写入与更新各用一份读取模板，写入模板中的来源恒为写入，写入与更新的区别已由模板标题与别名前缀给出。
- **头尾开关**：`include_header_footer` 保留，理由改为头尾是提示词中预检索上下文的引导，不适用于工具结果；MCP 读取交付全文的注释改为工具的用途。`compiler.py` 的错误信息与 `_slugify` 的 docstring 改为直接写出规则。
- **MTP 动词映射留在 Alice**：Alice 把操作快照翻译为 MTP 动词的映射仍在 `alice/orchestration/verbs.py`，`CPUPort` 不变。

## 7. 兼容与迁移

- **连接器与后端的版本**：新连接器的导入请求可能带 `WRITE`、`UPDATE` 事件，旧后端以 422 拒绝整轮；插件与后端需同时升级。旧连接器不发出写入调用（后端旧版没有写入工具），不受影响。
- **访问登记**：仓库中的 `configs/workspace_actors.yaml` 同步增加两项许可；本地自定义的登记需要手动增加，否则写入工具返回 `workspace.operation_denied`。
- **进程内状态**：落点登记与写入意图登记都只在进程内，重启后为空，不需要迁移。
- **编译目标改名**：只影响仓库内的调用方。
- **指引文案**：Alice 与 MCP 读到的指引句由指令写法改为能力描述，编译正文的其余部分不变。
- **测试**：直接引用 `MTP_READ`、`compile_mtp_read` 与 `MTP_READ_RESPONSE` 的测试随改名改写或删除；“请求级提交只接受检索与读取”的用例随契约变更改写，不保留墓碑测试。

### 9.3 实测验收

- 记录第一次写入的 ACK 耗时（含一次路由）。

## 10. 风险与待决问题

### 10.1 风险

- **首次写入的延迟**：第一次写入要等一次 Gateway 路由，再等生成队列接纳；上一轮的回流仍持有同一外部会话的串行门时，还要等它应用完成。
- **会话记录格式**：hook 依赖 Claude Code 会话记录的结构与 `PreToolUse` 的输入格式，格式变化时轮次信息读不出，写入以结构化错误失败，不会写到错误的话题。
- **模型填写轮次信息**：轮次信息字段若暴露在 schema 中，模型可能自行填写；hook 运行时总会覆盖，hook 被禁用时模型编造的标识会让写入落到按编造内容路由的话题。
- **与查重的叠加**：显式写入经过现行查重，查重判出的 UPDATE 仍整体覆盖已有记忆（[多条提取与查重 Idea](../ideas/settlement-multi-memory-extraction-and-dedup.md)第 2.2 节）；写入变多后这种情况会更常见，直到查重计划实施。
- **落点留存**：始终没有回流的轮次的落点留在内存中直到重启；连接器对每个已结束的轮次都会补发，这种情况只在连接器长期不可用时出现。
- **Alice 的指引不再给出语法**：检索上下文尾部原有的 READ、CALL 调用示例去掉，Alice 依靠协议教学把能力对应到动词，协议规格与演示仍教授完整语法。随日常使用留意 Alice 在摘要不足时是否仍主动读取。

### 10.2 待决问题

无阻塞问题。以下候选细节在计划评审时确认：

- 工具名与参数名（第 5.3 节）、轮次信息字段的名称与暴露方式、缺少轮次信息的错误码；
- 落点登记按 `interaction_id` 保存（第 5.4 节），与外部 Actor Idea 候选设计中“每个外部会话只保留正在进行的一轮”不同，理由见该节。

### 阶段二：服务端写入链路（2026-10-31）

- **Import Bus**：
  - 在途轮次模型为 `InFlightTurn`（`source`、外部会话与外部轮次、本轮用户消息、`recent_turns`）。`ImportedTurn` 继承它并加入事件、结局与模型名，同名字段共用同一份校验，两者推导出同一个 `interaction_id`。
  - 编排器新增 `place`，服务新增 `place_turn`（导入授权）。落位与导入共用串行门与在途计数，关闭时同样等待在途的落位。
  - 落点登记直接保存 prepare 返回的 `PreparedAgentRun`，只读取话题与是否新建，不另设类型。
  - 回流时沿用落点。提交被队列接纳后才取走落点：队列拥塞时重发仍沿用落点，应用失败后的重发按现行规则重新路由。
  - 上一轮已落位、回流尚未到达时，下一轮的续接取它的落点。这一条是 code review 后补上的，第 5.4 节没有写到。
  - 落位时 Gateway 的可恢复异常转为 `import_bus.unavailable`（`gateway_unavailable`），但不记为导入推迟：推迟事件表示连接器保留这一轮稍后重发，落位失败则直接交给等待中的写入。
  - 导入事件动词增加 `WRITE`、`UPDATE`；`UPDATE` 与 `READ` 一样必须给出作用对象。
- **操作入口与 actor API**：
  - `execute_request` 增加 `dispatch_topic_id`：写入与更新必须给出，检索与读取不得给出，不符时以 `TypeError` 拒绝。
  - actor API 的写入与更新接受同一参数。给出时不解析线程，登记的进程与线程关联为空。
  - “给出时必须是请求级 context”由授权者检查，`authorize_actor_operation` 为此增加 `request_level`。能力层不解封 context，只有授权者能读出 context 的运行种类。
  - `WriteIntentRegistry` 的 `process_id`、`thread_id` 改为可选。
- **MCP 入口**：
  - 新增 `memory_write`（`content`、`title`、`reason`）与 `memory_update`（`alias`、`instruction`、`content`）。
  - 轮次信息字段名为 `turn`，类型即 `InFlightTurn`。核实结果：SDK 的工具参数模型会丢弃 schema 之外的键，只有绕过参数校验读取原始请求才能取到。因此按第 5.3 节的备选，在 schema 中声明为可选字段，并写明由插件填写、不要自行填写。缺少时在认证前以新错误码 `request.turn_required`（400）拒绝。
  - 一份 context 依次用于 `place_turn` 与 `execute_request(dispatch_topic_id=...)`。
  - 标注：写入为 `read_only_hint=False, destructive_hint=False`，更新为 `destructive_hint=True`。服务说明与工具说明写明写入与更新的时机、句柄的含义与 `memory_read` 回读。
  - 错误投影新增 `workspace.memory.intent.pending_update_not_allowed`（409）、`workspace.memory.intent.dispatch_rejected`（503）与 `workspace.memory.intent.dispatch_unknown`（500）。
  - 架构守护改为：MCP 入口在 Import Bus 中只能导入 `system.services.import_bus.models`。
- **配置**：`claude_code` 的访问登记增加 `memory.write`、`memory.update`。
