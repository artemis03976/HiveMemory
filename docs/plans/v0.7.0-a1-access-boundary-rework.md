# v0.7.0 A1 访问边界返工

**计划状态**：进行中。本计划由同名 Todo 于 2026-10-02 升级而来；第一版实现已提交（commit `37f800e`）。2026-10-03 按[身份与访问体系 Idea](../ideas/identity-and-access-model.md)的第一批改写：第一版实现暴露出访问 context 与 `IdentityScope` 的边界错误，本计划以该 Idea 的模型为准，`37f800e` 是改写后的起点（第 7 节列出保留与调整）。按改写后设计的第二版实现已提交（commit `bd9b301`）；代码审查发现 server 拿到的对象超出它的角色，同日修订 4.1–4.4 与 4.8，调整项见 7.1。同日按身份与访问体系 Idea I-10 把 guard 拆为 `WorkspaceAuthenticator` 与 `WorkspaceOperationAuthorizer`（4.2）。同日补充审查遗留、`system` 默认白名单与 mypy 门槛的调整（第 6 节、7.1、第 8 节）。2026-10-04 审查按第 6 节调整后的实现：进程表改为唯一的进程注册表，句柄按对象身份判定有效，停止与取消统一为一个方法（4.4，调整项见 7.2）。

## 1. 背景与问题

[A1](../archive/plans/v0.7.0-a1-workspace-access-boundary.md)（已归档）交付了统一认证网关、两类登记、context 签发与逐次 operation 授权，但没有接上生产入口。这部分工作原由 A2、A6 计划收口，两份计划作废后（2026-09-27，删除前最后版本见 commit `dda9d9d`）改由 Todo 承接，并在任务进程表方向完成后接入（[总 Idea](../ideas/workspace-network-task-process-architecture.md#61-已决定事项) 6.1）。

第一版实现（`37f800e`）接上了生产入口，但也暴露出 A1 留下的边界错误：访问 context 只剩 `IdentityScope` 一个字段，`identity_scope` 与 `access` 两个身份字段被随意混用。由此建立了[身份与访问体系 Idea](../ideas/identity-and-access-model.md)，本计划即该 Idea 的第一批。

以 `37f800e` 为起点，与目标之间的差距（代码核对，2026-10-03）：

1. **访问 context 只是 `IdentityScope` 的外壳**：`WorkspaceAccessContext` 唯一的字段是 `identity_scope`，各处从 context 中读取身份。
2. **认证前就组装了 `IdentityScope`**：server 先从请求头组装完整的 `IdentityScope`（`server/deps.py` 的 `resolve_request_identity_scope`），再去认证。
3. **两个身份字段混用**：54 个函数同时接收 `identity_scope` 与 `access`；能力层 `create_memory` 授权后不使用 guard 返回的 scope，而用调用方传入的 scope 构造原子。
4. **访问 context 越过了授权点**：Patchouli 经 `access_consumption` 与 `WorkspaceAccessVerifier` 端口校验 context；Gateway 处理路由与 Patchouli 阶段路由也接收 context。
5. **chat 的认证与进程创建分开**：认证由 server 完成，签发的 context 没有绑定进程；注册入口是惰性的，流开始迭代时才校验 context、创建进程。
6. **context 有三处持有者**：`ProcessRequest.access`、`TaskProcess._access`、`ProcessRecord.access`；进程记录还另存调用方传入的 `IdentityScope`。
7. **进程由 `TaskProcess` 自行登记与注销**：它持有进程表，`run()` 时登记、`close()` 时移除。
8. **W0 的 owner 规则写在身份类型里**：`IdentityScope` 的校验器 `_require_same_owner` 要求 actor 用户等于 workspace owner，guard 在准入时捕获它抛出的异常再转为拒绝。
9. **CPU 输入清单的 `IdentityScope` 取自调用方传入的 scope**（`workspace/process/allocation.py`）。

## 3. 目标与非目标

**目标**

1. 按身份与访问体系 Idea 的第一批落地身份与访问的边界：入口在认证前只持有声明；访问 context 是不透明凭据；第 2 阶段与第 3 阶段分属 `WorkspaceAuthenticator` 与 `WorkspaceOperationAuthorizer`；授权点显式接收目标 workspace 并组装 `IdentityScope`；授权点以下只接收 `IdentityScope`。
2. 与 workspace 相关的 HTTP 请求都经认证网关；chat 由注册入口认证，签发即绑定并立即创建进程，认证失败仍返回 HTTP 403。
3. operation 检查只在授权点进行：能力层、任务进程的阶段检查、注册入口与取消入口；Patchouli 与 Gateway 不接收访问 context。
4. 进程的登记与注销由注册入口负责；进程记录只持有 context 与进程元数据。
5. 保留第一版已完成的两个登记文件、用户级访问记录、默认登记、访问错误的 HTTP 映射与去掉固定有效期。
6. 附件上传的 scope 不一致缺陷按“授权点组装 scope”结构性修复。

**非目标**

- Alice 的能力层调用迁移：Alice 继续以 `IdentityScope` 直接调用 Patchouli，这些调用没有 operation 授权（与现状相同），按总 Idea 15.5 单独建计划；
- Profile 的 `allowed_mtp_verbs` / `allowed_sys_tools` 并入 operation 控制（P-2、P-10），按总 Idea 15.5 归 Alice 的能力层调用迁移方向；
- Profile 解析改经能力层：前提还缺 Profile 缓存失效（任务进程 Idea 1.2）；
- 记录与后台任务改用资源身份、修订 AGENTS.md 中 `IdentityScope` 的传播规则：身份与访问体系第二批；
- `ActorIdentity.session_id`（身份与访问体系 I-7）；
- 资源的受限穿透访问；
- System 层面的 API 与 Import Bus（`/ingest`）。`/ingest` 仍在认证前组装 `IdentityScope`，是不变量 1 的已知例外；
- 外部 Actor 的身份证明、harness 执行侧面的登记结构（v0.7.1 起）；运行时登记与配置热更新（E-1）；
- 进程级权限收窄（P-4a）：进程继承 Actor 的白名单；
- `TaskProcess` 对其余依赖（总线、CPU 端口、分配器、事件发布器、操作授权者）的持有方式，见 [TaskProcess 容器 Todo](../todo/task-process-container-ownership.md)。

## 4. 目标设计

### 4.1 各层持有的身份数据

| 层 | 持有 | 不持有 |
|:---|:---|:---|
| server（入口 adapter） | 声明：actor 声明、请求进入的 workspace，只在认证前持有、只作为认证输入；自身的 principal 与 adapter；管理操作的请求级 context 与目标 workspace；chat 的不透明进程句柄 | 认证前组装的 `IdentityScope`；认证后的身份；进程记录与其中的 context |
| 授权点：注册入口、取消入口、能力层、任务进程的阶段检查 | 访问 context、操作授权者（注册入口作为进程 context 的运行持有者，另持认证网关） | 调用方另行传入的 `IdentityScope`；`WorkspaceAuthenticator` |
| 授权点以下：Gateway、Patchouli、引擎、存储 | 由授权点组装后传入的 `IdentityScope` | 访问 context、认证网关、操作授权者 |
| 进程记录 | 访问 context 与进程元数据 | 身份字段 |

### 4.2 访问 context、认证与操作授权

**context**：`WorkspaceAccessContext` 是不透明凭据，没有公开字段，只能交给签发它的认证一侧兑现（I-1）。

**三个类的划分**（I-10）：

| 类 | 负责 | 调用方 |
|:---|:---|:---|
| `ActorAuthenticationGateway` | 唯一对外的认证入口：依次调用 `PrincipalAuthenticator`（第 1 阶段）与 `WorkspaceAuthenticator`（第 2 阶段）；转交 context 的失效与诊断查询；关闭 | 运行持有者（server、注册入口）；System |
| `WorkspaceAuthenticator` | 第 2 阶段与签发；持有授予记录；向操作授权者提供只读的兑现接口 | 只有认证网关与操作授权者 |
| `WorkspaceOperationAuthorizer` | 第 3 阶段、进程控制授权、CPU 执行身份（过渡）；无状态 | 授权点 |

模块位置（示意）：认证网关与 `WorkspaceAuthenticator` 位于 `workspace/authentication.py`，`WorkspaceOperationAuthorizer` 位于新增的 `workspace/authorization.py`；`WorkspaceAccessGuard` 拆分后删除，调用方的参数 `access_guard` 改名为 `operation_authorizer`。

**授予记录**（由 `WorkspaceAuthenticator` 持有）：

| 内容 | 说明 |
|:---|:---|
| actor | 已验证的 `ActorIdentity` |
| 驻留 workspace | 准入的 `WorkspaceIdentity` |
| principal | `CallerPrincipal`（I-2） |
| 运行绑定 | 运行类型（任务进程或请求）与运行标识（`process_id` 或 server 为本次请求生成的标识）（I-3） |

`WorkspaceAuthenticator` 以弱引用字典保存“context → 授予记录”，取代第一版的 `WeakSet`。

**`WorkspaceAuthenticator` 的接口**（示意）：

| 接口 | 作用 | 调用方 |
|:---|:---|:---|
| 准入 | 第 2 阶段：确认访问登记中有启用的准入记录，检查 actor 用户等于要进入的 workspace 的 owner（I-5），签发 context 并写入授予记录 | 只由认证网关调用 |
| 兑现（只读） | 按 context 取回授予记录；未签发、已失效或已清空时给出对应的拒绝 | 只由操作授权者调用 |
| 失效、清空 | 使单个 context 失效；System 停止时清空全部授予记录 | 经认证网关 |
| 诊断查询 | 返回授予记录的摘要，只用于日志与观测标签，不能作为兑现入口 | 经认证网关 |

**`WorkspaceOperationAuthorizer` 的接口**（示意）：

| 接口 | 作用 | 调用方 |
|:---|:---|:---|
| `authorize_operation(access, operation, target_workspace)` | 第 3 阶段：经兑现接口确认 context 有效；目标等于驻留 workspace（I-4）；actor 用户等于目标 workspace 的 owner（I-5）；访问登记的白名单包含该 operation；返回 `IdentityScope(actor, target)` | 授权点 |
| 进程控制授权 | 比对请求方 context 与进程记录中的 context：两者驻留在同一 owner 与 workspace（沿用现有规则，P-7） | 取消与状态查询入口 |
| CPU 执行身份（过渡） | 只做第 3 阶段的目标与 owner 检查、不检查 operation，返回 `IdentityScope`（I-9）；Alice 的能力层调用迁移完成后删除 | 只由任务进程在 CPU 分配时调用 |

**认证网关**：`authenticate(adapter, principal, actor, workspace, binding)`，增加运行绑定参数（I-3）。运行持有者只经认证网关接触认证一侧，不直接持有 `WorkspaceAuthenticator`。

**`IdentityScope`**：去掉 `_require_same_owner` 校验器，只表示一次操作的发起者与目标 workspace（I-5）。

**拒绝语义**：

| 情形 | 错误 |
|:---|:---|
| 接入未登记、adapter 不匹配；准入记录缺失；actor 用户不是要进入的 workspace 的 owner | `AdmissionDeniedError`（沿用现有 reason，含 `actor_not_owner`） |
| context 未签发或已失效；认证一侧已关闭 | `ScopeRequiredError`（`context_not_issued`、`authentication_gateway_closed`） |
| 目标不等于驻留 workspace | `OperationDeniedError`，reason `target_workspace_not_resident` |
| actor 用户不是目标 workspace 的 owner | `OperationDeniedError`，reason `target_owner_mismatch` |
| 白名单不含该 operation | `OperationDeniedError`（`operation_not_allowed`） |

### 4.3 HTTP 入口

server 以自身登记的 principal（`system.server_principal_id`）与 `http` adapter 调用认证网关。请求头中的用户身份不做证明，这是本地单用户部署的信任假设，在配置文档中写明。

**声明解析**：沿用现有的身份选择与冲突检测规则（用户的单一回退、只开放 `main_workspace`、Agent action 必须给出具体 `agent_id`、非 Agent action 使用保留的 `system`），但只产出 actor 声明与请求进入的 workspace，不组装 `IdentityScope`。Agent action 显式给出保留的 `system` 作为 `agent_id` 时返回 400，注册入口保留同一检查。

**声明只作为认证输入**：认证通过后，经过验证的身份只存在于 `WorkspaceAuthenticator` 的授予记录中（I-1、I-10）。server 不把声明当作已确认的身份继续使用，也不把声明交给路由处理函数。

**目标 workspace**：它是这次操作的参数，不是身份（身份与访问体系 Idea 前提第 5 条、I-4）。当前取请求进入的 workspace，受限穿透访问落地后由请求参数单独给出。server 与任务参数都以 `target_workspace` 单独命名，不复用声明中的 workspace 字段。

| 请求 | 处理 |
|:---|:---|
| `POST /chat` | server 调用注册入口的注册步骤（4.4），传入 principal、adapter、actor 声明、请求进入的 workspace、`process_id` 与请求参数；注册失败直接抛出，返回 403；注册成功后得到不透明的进程句柄，才开始流式响应。客户端断开时以句柄取消进程：`cancel_process(handle, reason="client_disconnected")`；响应结束时经 `close_process(handle)` 关闭进程，生成器从未开始迭代时由响应自身的收尾兜底（4.4） |
| 管理员操作：memories、topics、agents、workspace assets、memory-tasks | 以 (user, `system`) 声明认证，绑定本次请求，取得请求级 context；路由处理函数只取得请求级 context 与目标 workspace，调用能力层时传入这两者；请求结束时使 context 失效 |
| `POST /chat/stop` | 以 (user, `system`) 声明取得请求级 context，调用取消入口 `cancel_process(process_id, access)`；请求结束时使 context 失效 |
| System 层面的 API、`/ingest` | 不经网关（非目标） |

### 4.4 注册入口与任务进程

**注册**（立即执行，在流式响应开始之前完成）：

1. 拒绝 `system` 作为任务请求的 actor（沿用现有规则）；
2. 经认证网关完成两阶段认证，运行绑定为本进程的 `process_id`；
3. 创建进程记录，写入 context；
4. 创建任务进程（`TaskProcess`，以进程记录为控制面）并登记到进程表：进程表是唯一的进程注册表，以 `process_id` 为键登记任务进程，进程记录不单独登记；
5. 用通过认证的声明绑定运行时事件的观测标签（`workspace_id`、`agent_id`）；
6. 签发并返回不透明的进程句柄（`ProcessHandle`）：只暴露 `process_id`，不暴露进程记录、其中的 context 或 `TaskProcess`。

**进程句柄**：句柄是入口 adapter 与已注册进程之间唯一的引用（I-8 的补充）。句柄只由注册入口签发，按对象身份判定有效（I-8 的 2026-10-04 补充）：句柄私下记着它对应的进程，注册入口解析时要求进程表中登记的进程正是这一个。按 `process_id` 重新构造的对象、进程关闭后的旧句柄都不是有效句柄：运行时以 `WorkspaceDomainError`（reason `process_handle_unknown`）拒绝；取消时按不存在返回、不发布事件；关闭是幂等空操作。持有有效句柄即为该进程生命周期的所有者；运行、取消与关闭都经注册入口进行。句柄不离开进程，不提供序列化。

**运行**：`run_process(handle, stream=…)`。流式与非流式两种形态都只负责运行已注册的进程。阶段调用的目标 workspace 取自注册时通过认证的 workspace，作为任务参数 `target_workspace` 传给授权点（I-8）。

**取消**：`cancel_process` 是唯一的取消方法，取消的依据作为参数，由方法签名区分（I-8 的 2026-10-04 补充）：

| 调用形式 | 依据 | 授权 | 找不到或无权时 |
|:---|:---|:---|:---|
| `cancel_process(handle, reason=…)` | 进程的所有者，例如 chat 路由在客户端断开时 | 不经进程控制授权；不接受另传的访问 context | 返回 `not_found`，不发布事件 |
| `cancel_process(process_id, access=…, reason=…)` | 以请求级 context 发起的控制请求（`/chat/stop`） | 经进程控制授权（P-7） | 返回 `not_found`，发布带请求方观测标签的事件 |

两种形式解析出进程后，stop 记录、终态判定与运行时事件只有一份实现；只有 `process_id` 而没有 context 不能取消。客户端断开仍是一次取消，不并入关闭：chat 路由先同步取消（记录 `client_disconnected`、取消当前阶段的任务），再取消并等待正在拉取事件的任务，最后关闭进程。

**关闭**：`close_process(handle)`，由注册入口发起。`TaskProcess` 释放自身资源（工作集中的附件租借、CPU 输出流、Patchouli cleanup），注册入口随后使 context 失效并从进程表注销；关闭是幂等的。注册成功但流一直没有开始时（例如关停信号在注册期间到达，响应在开始迭代前就被取消），同样经此关闭：server 的 SSE 响应在自身收尾时兜底调用，不依赖生成器是否开始迭代。

**进程记录**（I-8）：

```python
@dataclass
class ProcessRecord:
    process_id: str
    access: WorkspaceAccessContext   # 只交给操作授权者用于授权
    phase: ProcessPhase
    outcome: ProcessOutcome
    stop_reason: str | None
```

注册请求只携带声明与请求参数，不携带 context；`TaskProcess` 经进程记录使用 context，不另存；`TaskProcess` 不再持有进程表；进程记录与 `TaskProcess` 都不离开注册入口，入口 adapter 只持有句柄。

**阶段检查**：进程在每次阶段调用前调用 `authorize_operation(record.access, operation, target_workspace)`，把得到的 `IdentityScope` 传给对应路由：

| 阶段调用 | operation |
|:---|:---|
| Gateway 分析中的话题快照与话题数据读取 | `resource.read` |
| prepare（话题与检索） | `resource.search` |
| CPU 分配：Profile 解析 | `profile.read` |
| CPU 分配：附件租借 | `asset.acquire` |
| finalize（提交交互记录） | `interaction.submit`；进入 Actor 执行前检查，避免 CPU 执行完才在结算被拒 |
| 结算后的话题池列表 | `resource.read` |
| cleanup | 不检查；只补偿本进程 prepare 的结果 |

**CPU 输入清单**：其中的 `IdentityScope` 由操作授权者的 CPU 执行身份方法组装（I-9），不取自调用方。

**控制请求的授权**：取消的控制请求形式与状态查询都调用操作授权者的进程控制授权，比对请求方 context 与进程中记录的 context；不匹配时与进程不存在一样返回 `not_found`，不泄露进程是否存在。入口取消自己注册的进程使用句柄形式，不以进程自己的 context 冒充请求方。

### 4.5 能力层

- 写入、管理与读取方法只接收 `access` 与目标 workspace（以及业务参数），不再接收 `identity_scope`；
- 方法先调用 `authorize_operation`，再用返回的 `IdentityScope` 构造领域对象并调用 Patchouli，不向下传 context；
- 附件上传同样只用操作授权者返回的 scope，调用方不再能另传 scope，P1 缺陷由此结构性消除；
- memory-tasks：列表与读取绑定 `task.observe`，取消绑定 `management.task`；
- 检索：`retrieve` 由能力层用授权返回的 scope 构造检索请求，调用方只提交检索参数，不提交含 `IdentityScope` 的请求；
- 话题列表：管理员的话题列表不再绑定 `resource.read`，暂时绑定 `management.topic`（总 Idea P-9g）；operation 目录中关于 Topic 快照读取的说明相应修改。

### 4.6 Patchouli 与 Gateway

- Patchouli 的公开方法与 `PatchouliService` 的阶段方法只接收 `IdentityScope`，删除 `access` 参数；删除 `access_consumption.py`、`core.access.WorkspaceAccessVerifier` 端口以及 guard 向 Patchouli 的注入；资源归属与资源 policy 校验保留；
- `interaction.submit` 与 `memory_intent.submit` 两个公开路由随之不再检查 operation。它们目前没有生产调用方，授权在能力层出现对应方法时进行（总 Idea 15.6 的注记）；
- Alice 的直接调用（`retrieve`、`retrieve_by_aliases`、`get_agent_profile`、`record_memory_citation`）签名不变，没有 operation 授权，属于非目标中的已知缺口；
- Gateway 的处理路由与话题读取只接收 `IdentityScope`，撤回第一版新增的 `access` 参数。

### 4.7 访问登记

沿用第一版的实现：

| 文件 | 内容 | 配置所有者 |
|:---|:---|:---|
| `configs/system_principals.yaml` | `principals`：调用来源的接入登记 | System |
| `configs/workspace_actors.yaml` | `workspace_actors`：Workspace Actor 的准入与行为白名单 | workspace |

- 两个文件都不包含 context 有效期；拒绝未知字段，缺失登记即 fail closed；principals 文件为 harness 登记的执行侧面留出位置，具体结构不在本计划定义；
- 用户级记录：省略 `agent_id` 表示覆盖该用户的所有具体 Agent，不覆盖 `system`；精确记录优先，被禁用时不回落；每个 (owner, workspace, user) 至多一条；
- 默认登记：

| 文件 | 登记 | 内容 |
|:---|:---|:---|
| principals 文件 | server 的 principal | adapter `http` |
| workspace_actors 文件 | 用户级记录（所有具体 Agent） | `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit` |
| workspace_actors 文件 | `system` | `management.memory`、`management.topic`、`management.asset`、`management.task`、`task.observe` |

`system` 不持有 `resource.read`（总 Idea 15.7）：管理员直接通道不持有任何 actor 可见的读取 operation，由白名单保证它不会走到带缓存的读取；管理员的话题列表由 `management.topic` 覆盖（4.5）。

### 4.8 context 生命周期

- 进程的 context：注册时签发并绑定进程，由进程记录持有，进程以任何结局关闭时由注册入口使其失效（P-6）；
- 请求级 context：请求开始时签发并绑定本次请求，请求结束时失效；
- System 停止时先关闭认证网关、拒绝新认证；任务进程收尾后，经认证网关清空全部授予记录。操作授权者无状态，不需要关闭，授予记录清空后兑现自然失败；
- 没有固定有效期（总 Idea 15.6），拒绝原因 `context_expired` 不再产生。

### 4.9 访问错误的 HTTP 映射

沿用第一版的实现，并覆盖 4.2 新增的 reason：

| 错误 | HTTP |
|:---|:---|
| `AdmissionDeniedError` | 403；`reason=authentication_gateway_closed` 时为 503 |
| `OperationDeniedError` | 403 |
| `ScopeRequiredError` | 生产入口经网关后不应出现，出现即为接线缺陷，按 500 返回并记录 |
| `WorkspaceMismatchError` | 409 |

响应保留稳定机器码与 `details.reason`，不暴露接入凭据。

## 5. 受影响的系统与契约

- **core**：`WorkspaceAccessContext` 改为不透明；删除 `WorkspaceAccessVerifier` 端口；`IdentityScope` 去掉 owner 校验器；新增 `OperationDeniedError` 的两个 reason。
- **workspace**：认证网关、`WorkspaceAuthenticator` 与 `WorkspaceOperationAuthorizer` 的划分与接口（4.2）；认证网关增加运行绑定；能力层签名；注册入口的注册、运行、取消与关闭，以及进程句柄与唯一的进程表；进程记录；阶段检查与 CPU 执行身份。
- **Gateway**：处理路由与话题读取撤回 `access` 参数。
- **Patchouli**：删除 `access` 参数与 `access_consumption`。
- **server**：声明解析不再组装 `IdentityScope`，声明只作为认证输入；chat 改为先注册后运行，只持有进程句柄；管理路由只取得请求级 context 与目标 workspace；取消改用请求级 context。
- **公共契约**：Patchouli 公开路由、`PatchouliService` 阶段路由与 Gateway 处理路由不再接收 `access`；能力层方法改为接收 `access` 与目标 workspace；注册入口拆为注册与运行，注册返回不透明的进程句柄，运行与关闭以句柄为参数；取消只有一个方法，依据为句柄或 `process_id` 加请求级 context；新增 4.2 的错误 reason；`context_expired` 不再产生；`OwnerMismatchError` 不再由构造 `IdentityScope` 触发。

## 6. 迁移与兼容

以 `37f800e` 为起点，按以下顺序切换，每一步都能单独验证：

1. **core 与 guard**：context 改为不透明，guard 改用授予记录；`authorize_operation` 接收目标 workspace；owner 检查移到第 2、3 阶段并删除 `IdentityScope` 的校验器；新增进程控制授权与 CPU 执行身份方法；认证网关增加运行绑定参数。

### 7.2 按第 6 节调整后的实现的审查调整（2026-10-04）

审查对象是在 `c38322c` 之上按第 6 节第 1–7 步调整后的实现。

| 部分 | 处理 |
|:---|:---|
| 注册入口同时维护 `ProcessTable`（`process_id → ProcessRecord`）与另建的 `process_id → TaskProcess` 表，以同一个键平行写入与移除，形成两个事实来源 | 调整：进程表是唯一的进程注册表，登记 `TaskProcess`；进程记录经进程取得（4.4） |

## 8. 测试与验收

**单元测试**

- 认证一侧：context 没有公开字段；认证网关依次完成两个阶段，任一失败不签发；`WorkspaceAuthenticator` 只经认证网关签发、失效与清空；
- 操作授权者：context 未签发、已失效、认证一侧已清空时分别拒绝；`authorize_operation` 对目标不等于驻留 workspace、目标 owner 不匹配、白名单不含 operation 分别给出 4.2 的错误；进程控制授权在跨 owner 或跨 workspace 时拒绝；CPU 执行身份方法不检查 operation，但检查目标与 owner；
- `IdentityScope`：可以构造 actor 用户与 workspace owner 不同的值，owner 规则只在准入与授权时生效；
- 访问登记：用户级记录匹配；精确记录优先；精确记录禁用时不回落；`system` 不被用户级记录覆盖；重复的用户级记录在装载期失败；
- 认证网关：授予记录保存 principal 与运行绑定；
- 注册入口：认证失败不创建、不登记进程；注册成功后进程已登记，context 绑定本进程；流从未开始时进程被关闭、context 失效、进程从表中注销；进程以 completed、失败、取消结束后，context 都已失效；注册返回的句柄只暴露 `process_id`；进程表是唯一的进程注册表，取消、状态查询与关闭取到的是同一个进程，关闭后都找不到它；按 `process_id` 重新构造的句柄无效：运行被拒绝（`process_handle_unknown`），取消返回 `not_found`；进程关闭后的旧句柄，取消返回 `not_found` 且不发布事件，关闭是空操作；句柄形式的取消不经进程控制授权，与控制请求形式发布相同的事件；控制请求形式缺少 context 或同时传入句柄与 context 时被拒绝；认证成功后、登记之前失败时 context 已失效；
- 任务进程：缺少各阶段 operation 时在对应阶段失败，不产生后续副作用；缺少 `interaction.submit` 时不执行 CPU；阶段路由只收到操作授权者返回的 `IdentityScope`，包括结算后的话题池读取；CPU 执行身份方法只在 CPU 分配中调用（调用点测试）；
- 能力层：每个方法缺少 operation 时拒绝且不触达 Patchouli；传给 Patchouli 的 scope 来自操作授权者；`retrieve` 只接收检索参数；
- Patchouli 与 Gateway：公开方法不再接受 `access` 参数；
- 附件：上传使用的 scope 只来自操作授权者，满足缺陷 Todo 的完成条件；
- server：声明解析不产生 `IdentityScope`；Agent action 显式使用保留的 `system` 返回 400；访问错误映射到 4.9 的状态码；客户端断开以句柄形式的 `cancel_process` 取消进程，取消先于关闭；生成器从未开始迭代时（关停信号、发送失败两种触发）响应收尾关闭进程；管理路由只取得请求级 context 与目标 workspace。

**集成测试**（真实网关；登记经 `load_access_registration()` 读取随仓库发布的两个登记文件，测试辅助构造的全量白名单不能替代这一项）

## 9. 风险与待决事项

- **Alice 的直接调用没有 operation 授权**：与现状相同，由 Alice 的能力层调用迁移解决；本计划不扩大这一缺口。
- **CPU 执行身份方法可能被滥用**：它不检查 operation，只能由任务进程在 CPU 分配时调用；以分层或调用点测试约束，并在 Alice 迁移后删除。
- **两个提交路由没有 operation 授权**：`interaction.submit` 与 `memory_intent.submit` 目前没有生产调用方；出现调用方前应先在能力层增加对应方法。
- **`/ingest` 仍在认证前组装 `IdentityScope`**：Import Bus 不在现有系统内，作为不变量 1 的已知例外。
- **第二批未完成前**：记录与后台任务仍以 `IdentityScope` 表示资源身份，AGENTS.md 的传播规则暂不修改。
- **用户级记录是 v0.7.0 的简化**：同一用户的所有 Agent 共享一份白名单，按 Agent 区分的权限随 P-2、P-10 落地。
- **请求头身份不做证明**：只适用于本地单用户部署。
- **实施时确定的事项**（2026-10-03 已确定）：
  - 请求级运行标识由 server 为每个请求生成；
  - 流从未开始时，由 server 的 SSE 响应在收尾时兜底关闭进程，测试覆盖关停信号与发送失败两种触发；
  - 诊断查询返回授予记录的只读摘要，只用于日志与观测标签（I-10 后归认证一侧，经认证网关调用）。
- **话题列表映射是暂时的**（总 Idea P-9g）：管理员的话题列表暂时由 `management.topic` 覆盖；若以后为管理视角的读取单独设立 operation，再随之调整。
- **`OwnerMismatchError` 的去留**：构造 `IdentityScope` 不再触发它，代码中已没有抛出点；收尾更新错误模型时决定删除，或保留并写明用途。
