# v0.7.0 A1 访问边界返工

**计划状态**：进行中。本计划由同名 Todo 于 2026-10-02 升级而来；第一版实现已提交（commit `37f800e`）。2026-10-03 按[身份与访问体系 Idea](../ideas/identity-and-access-model.md)的第一批改写：第一版实现暴露出访问 context 与 `IdentityScope` 的边界错误，本计划以该 Idea 的模型为准，`37f800e` 是改写后的起点（第 7 节列出保留与调整）。

## 1. 背景与问题

[A1](../archive/plans/v0.7.0-a1-workspace-access-boundary.md)（已归档）交付了统一认证网关、两类登记、context 签发与逐次 operation 授权，但没有接上生产入口。这部分工作原由 A2、A6 计划收口，两份计划作废后（2026-09-27，删除前最后版本见 commit `dda9d9d`）改由 Todo 承接，并在任务进程表方向完成后接入（[总 Idea](../ideas/workspace-network-task-process-architecture.md#61-已决定事项) 6.1）。

第一版实现（`37f800e`）接上了生产入口，但也暴露出 A1 留下的边界错误：访问 context 只剩 `IdentityScope` 一个字段，`identity_scope` 与 `access` 两个身份字段被随意混用。由此建立了[身份与访问体系 Idea](../ideas/identity-and-access-model.md)，本计划即该 Idea 的第一批。

以 `37f800e` 为起点，与目标之间的差距（代码核对，2026-10-03）：

1. **访问 context 只是 `IdentityScope` 的外壳**：`WorkspaceAccessContext` 唯一的字段是 `identity_scope`，各处从 context 中读取身份。
2. **认证前就组装了 `IdentityScope`**：server 先从请求头组装完整的 `IdentityScope`（`server/deps.py` 的 `resolve_request_identity_scope`），再去认证。
3. **两个身份字段混用**：54 个函数同时接收 `identity_scope` 与 `access`；能力层 `create_memory` 授权后不使用 guard 返回的 scope，而用调用方传入的 scope 构造原子。
4. **访问 context 越过了授权点**：Patchouli 经 `access_consumption` 与 `WorkspaceAccessVerifier` 端口校验 context；Gateway 处理路由与 Patchouli 阶段路由也接收 context。
5. **chat 的认证与进程创建分开**：认证由 server 完成，签发的 context 没有绑定进程；注册入口是惰性的，流开始迭代时才校验 context、创建进程。
6. **context 有三处持有者**：`ProcessRequest.access`、`TaskProcess._access`、`ProcessRecord.access`；进程记录还另存调用方传入的 `IdentityScope`。
7. **进程由 `TaskProcess` 自行登记与注销**：它持有进程表，`run()` 时登记、`close()` 时移除。
8. **W0 的 owner 规则写在身份类型里**：`IdentityScope` 的校验器 `_require_same_owner` 要求 actor 用户等于 workspace owner，guard 在准入时捕获它抛出的异常再转为拒绝。
9. **CPU 输入清单的 `IdentityScope` 取自调用方传入的 scope**（`workspace/process/allocation.py`）。

本计划只依据以下已作出的决定与当前代码：

| 决定 | 来源 |

## 3. 目标与非目标

**目标**

1. 按身份与访问体系 Idea 的第一批落地身份与访问的边界：入口在认证前只持有声明；访问 context 是不透明凭据；授权点显式接收目标 workspace 并组装 `IdentityScope`；授权点以下只接收 `IdentityScope`。
2. 与 workspace 相关的 HTTP 请求都经认证网关；chat 由注册入口认证，签发即绑定并立即创建进程，认证失败仍返回 HTTP 403。
3. operation 检查只在授权点进行：能力层、任务进程的阶段检查、注册入口与取消入口；Patchouli 与 Gateway 不接收访问 context。
4. 进程的登记与注销由注册入口负责；进程记录只持有 context 与进程元数据。
5. 保留第一版已完成的两个登记文件、用户级访问记录、默认登记、访问错误的 HTTP 映射与去掉固定有效期。
6. 附件上传的 scope 不一致缺陷按“授权点组装 scope”结构性修复。

**非目标**

- Alice 的能力层调用迁移：Alice 继续以 `IdentityScope` 直接调用 Patchouli，这些调用没有 operation 授权（与现状相同），按总 Idea 15.5 单独建计划；
- Profile 的 `allowed_mtp_verbs` / `allowed_sys_tools` 并入 operation 控制（P-2、P-10），按总 Idea 15.5 归 Alice 的能力层调用迁移方向；
- Profile 解析改经能力层：前提还缺 Profile 缓存失效（任务进程 Idea 1.2）；
- 记录与后台任务改用资源身份、修订 AGENTS.md 中 `IdentityScope` 的传播规则：身份与访问体系第二批；
- `ActorIdentity.session_id`（身份与访问体系 I-7）；
- 资源的受限穿透访问；
- System 层面的 API 与 Import Bus（`/ingest`）。`/ingest` 仍在认证前组装 `IdentityScope`，是不变量 1 的已知例外；
- 外部 Actor 的身份证明、harness 执行侧面的登记结构（v0.7.1 起）；运行时登记与配置热更新（E-1）；
- 进程级权限收窄（P-4a）：进程继承 Actor 的白名单；
- `TaskProcess` 对其余依赖（总线、CPU 端口、分配器、事件发布器、guard）的持有方式，见 [TaskProcess 容器 Todo](../todo/task-process-container-ownership.md)。

## 4. 目标设计

### 4.1 各层持有的身份数据

| 层 | 持有 | 不持有 |
|:---|:---|:---|
| server（入口 adapter） | 声明：actor 声明、请求进入的 workspace；自身的 principal 与 adapter；管理操作的请求级 context | 认证前组装的 `IdentityScope` |
| 授权点：注册入口、取消入口、能力层、任务进程的阶段检查 | 访问 context、guard | 调用方另行传入的 `IdentityScope` |
| 授权点以下：Gateway、Patchouli、引擎、存储 | 由授权点组装后传入的 `IdentityScope` | 访问 context、guard |
| 进程记录 | 访问 context 与进程元数据 | 身份字段 |

### 4.2 访问 context 与 guard

**context**：`WorkspaceAccessContext` 是不透明凭据，没有公开字段，只能交给签发它的 guard 兑现（I-1）。

**guard 内部的授予记录**：

| 内容 | 说明 |
|:---|:---|
| actor | 已验证的 `ActorIdentity` |
| 驻留 workspace | 准入的 `WorkspaceIdentity` |
| principal | `CallerPrincipal`（I-2） |
| 运行绑定 | 运行类型（任务进程或请求）与运行标识（`process_id` 或 server 为本次请求生成的标识）（I-3） |

guard 以弱引用字典保存“context → 授予记录”，取代第一版的 `WeakSet`。

**guard 的接口**（示意）：

| 接口 | 作用 | 调用方 |
|:---|:---|:---|
| 内部准入 | 第 2 阶段：确认访问登记中有准入记录，检查 actor 用户等于要进入的 workspace 的 owner（I-5），签发 context 并写入授予记录 | 只由认证网关调用 |
| `authorize_operation(access, operation, target_workspace)` | 第 3 阶段：确认 context 已签发且未失效；目标等于驻留 workspace（I-4）；actor 用户等于目标 workspace 的 owner（I-5）；访问登记的白名单包含该 operation；返回 `IdentityScope(actor, target)` | 授权点 |
| 进程控制授权 | 比对请求方 context 与进程记录中的 context：两者驻留在同一 owner 与 workspace（沿用现有规则，P-7） | 取消与状态查询入口 |
| CPU 执行身份（过渡） | 只做第 3 阶段的目标与 owner 检查、不检查 operation，返回 `IdentityScope`（I-9）；Alice 的能力层调用迁移完成后删除 | 只由任务进程在 CPU 分配时调用 |
| `invalidate(access)`、`close()` | 使单个或全部 context 失效 | context 的绑定所有者；组合根 |
| 诊断查询 | 返回授予记录的摘要，只用于日志与诊断，不能作为兑现入口 | 日志 |

**认证网关**：`authenticate(adapter, principal, actor, workspace, binding)`，增加运行绑定参数（I-3）。

**`IdentityScope`**：去掉 `_require_same_owner` 校验器，只表示一次操作的发起者与目标 workspace（I-5）。

**拒绝语义**：

| 情形 | 错误 |
|:---|:---|
| 接入未登记、adapter 不匹配；准入记录缺失；actor 用户不是要进入的 workspace 的 owner | `AdmissionDeniedError`（沿用现有 reason，含 `actor_not_owner`） |
| context 未签发或已失效；guard 已关闭 | `ScopeRequiredError`（`context_not_issued`、`authentication_gateway_closed`） |
| 目标不等于驻留 workspace | `OperationDeniedError`，reason `target_workspace_not_resident` |
| actor 用户不是目标 workspace 的 owner | `OperationDeniedError`，reason `target_owner_mismatch` |
| 白名单不含该 operation | `OperationDeniedError`（`operation_not_allowed`） |

### 4.3 HTTP 入口

server 以自身登记的 principal（`system.server_principal_id`）与 `http` adapter 调用认证网关。请求头中的用户身份不做证明，这是本地单用户部署的信任假设，在配置文档中写明。

**声明解析**：沿用现有的身份选择与冲突检测规则（用户的单一回退、只开放 `main_workspace`、Agent action 必须给出具体 `agent_id`、非 Agent action 使用保留的 `system`），但只产出 actor 声明与请求进入的 workspace，不组装 `IdentityScope`。

| 请求 | 处理 |
|:---|:---|
| `POST /chat` | server 调用注册入口的注册步骤（4.4），传入 principal、adapter、actor 声明、请求进入的 workspace、`process_id` 与请求参数；注册失败直接抛出，返回 403；注册成功后才开始流式响应 |
| 管理员操作：memories、topics、agents、workspace assets、memory-tasks | 以 (user, `system`) 声明认证，绑定本次请求，取得请求级 context；调用能力层时传入 context 与目标 workspace（即请求进入的 workspace）；请求结束时使 context 失效 |
| `POST /chat/stop` | 以 (user, `system`) 声明取得请求级 context，调用取消入口 `cancel_process(process_id, access)`；请求结束时使 context 失效 |
| System 层面的 API、`/ingest` | 不经网关（非目标） |

### 4.4 注册入口与任务进程

**注册**（立即执行，在流式响应开始之前完成）：

1. 拒绝 `system` 作为任务请求的 actor（沿用现有规则）；
2. 经认证网关完成两阶段认证，运行绑定为本进程的 `process_id`；
3. 创建进程记录，写入 context；
4. 登记到进程表；
5. 用通过认证的声明绑定运行时事件的观测标签（`workspace_id`、`agent_id`）；
6. 返回进程句柄。

**运行**：流式与非流式两种形态都只负责运行已注册的进程。阶段调用的目标 workspace 取自注册时通过认证的 workspace，作为任务参数传给授权点（I-8）。

**关闭**：由注册入口发起。`TaskProcess` 释放自身资源（工作集中的附件租借、CPU 输出流、Patchouli cleanup），注册入口随后使 context 失效并从进程表注销。注册成功但流一直没有开始时（例如客户端在第一次迭代前断开），注册入口同样负责关闭；server 需保证这一路径被触发。

**进程记录**（I-8）：

```python
@dataclass
class ProcessRecord:
    process_id: str
    access: WorkspaceAccessContext   # 只交给 guard 用于授权
    phase: ProcessPhase
    outcome: ProcessOutcome
    stop_reason: str | None
```

注册请求只携带声明与请求参数，不携带 context；`TaskProcess` 经进程记录使用 context，不另存；`TaskProcess` 不再持有进程表。

**阶段检查**：进程在每次阶段调用前调用 `authorize_operation(record.access, operation, target_workspace)`，把得到的 `IdentityScope` 传给对应路由：

| 阶段调用 | operation |
|:---|:---|
| Gateway 分析中的话题快照与话题数据读取 | `resource.read` |
| prepare（话题与检索） | `resource.search` |
| CPU 分配：Profile 解析 | `profile.read` |
| CPU 分配：附件租借 | `asset.acquire` |
| finalize（提交交互记录） | `interaction.submit`；进入 Actor 执行前检查，避免 CPU 执行完才在结算被拒 |
| 结算后的话题池列表 | `resource.read` |
| cleanup | 不检查；只补偿本进程 prepare 的结果 |

**CPU 输入清单**：其中的 `IdentityScope` 由 guard 的 CPU 执行身份方法组装（I-9），不取自调用方。

**取消与状态查询**：入口调用 guard 的进程控制授权，比对请求方 context 与进程记录中的 context；不匹配时返回 `not_found`，不泄露进程是否存在。

### 4.5 能力层

- 写入、管理与读取方法只接收 `access` 与目标 workspace（以及业务参数），不再接收 `identity_scope`；
- 方法先调用 `authorize_operation`，再用返回的 `IdentityScope` 构造领域对象并调用 Patchouli，不向下传 context；
- 附件上传同样只用 guard 返回的 scope，调用方不再能另传 scope，P1 缺陷由此结构性消除；
- memory-tasks：列表与读取绑定 `task.observe`，取消绑定 `management.task`。

### 4.6 Patchouli 与 Gateway

- Patchouli 的公开方法与 `PatchouliService` 的阶段方法只接收 `IdentityScope`，删除 `access` 参数；删除 `access_consumption.py`、`core.access.WorkspaceAccessVerifier` 端口以及 guard 向 Patchouli 的注入；资源归属与资源 policy 校验保留；
- `interaction.submit` 与 `memory_intent.submit` 两个公开路由随之不再检查 operation。它们目前没有生产调用方，授权在能力层出现对应方法时进行（总 Idea 15.6 的注记）；
- Alice 的直接调用（`retrieve`、`retrieve_by_aliases`、`get_agent_profile`、`record_memory_citation`）签名不变，没有 operation 授权，属于非目标中的已知缺口；
- Gateway 的处理路由与话题读取只接收 `IdentityScope`，撤回第一版新增的 `access` 参数。

### 4.7 访问登记

沿用第一版的实现：

| 文件 | 内容 | 配置所有者 |
|:---|:---|:---|
| `configs/system_principals.yaml` | `principals`：调用来源的接入登记 | System |
| `configs/workspace_actors.yaml` | `workspace_actors`：Workspace Actor 的准入与行为白名单 | workspace |

- 两个文件都不包含 context 有效期；拒绝未知字段，缺失登记即 fail closed；principals 文件为 harness 登记的执行侧面留出位置，具体结构不在本计划定义；
- 用户级记录：省略 `agent_id` 表示覆盖该用户的所有具体 Agent，不覆盖 `system`；精确记录优先，被禁用时不回落；每个 (owner, workspace, user) 至多一条；
- 默认登记：

| 文件 | 登记 | 内容 |
|:---|:---|:---|
| principals 文件 | server 的 principal | adapter `http` |
| workspace_actors 文件 | 用户级记录（所有具体 Agent） | `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit` |
| workspace_actors 文件 | `system` | `management.memory`、`management.topic`、`management.asset`、`management.task`、`resource.read`、`task.observe` |

### 4.8 context 生命周期

- 进程的 context：注册时签发并绑定进程，由进程记录持有，进程以任何结局关闭时由注册入口使其失效（P-6）；
- 请求级 context：请求开始时签发并绑定本次请求，请求结束时失效；
- System 停止时先关闭网关、拒绝新认证，任务进程收尾后再关闭 guard；
- 没有固定有效期（总 Idea 15.6），拒绝原因 `context_expired` 不再产生。

### 4.9 访问错误的 HTTP 映射

沿用第一版的实现，并覆盖 4.2 新增的 reason：

| 错误 | HTTP |
|:---|:---|
| `AdmissionDeniedError` | 403；`reason=authentication_gateway_closed` 时为 503 |
| `OperationDeniedError` | 403 |
| `ScopeRequiredError` | 生产入口经网关后不应出现，出现即为接线缺陷，按 500 返回并记录 |
| `WorkspaceMismatchError` | 409 |

响应保留稳定机器码与 `details.reason`，不暴露接入凭据。

## 5. 受影响的系统与契约

- **core**：`WorkspaceAccessContext` 改为不透明；删除 `WorkspaceAccessVerifier` 端口；`IdentityScope` 去掉 owner 校验器；新增 `OperationDeniedError` 的两个 reason。
- **workspace**：guard 的授予记录与接口（4.2）；认证网关增加运行绑定；能力层签名；注册入口的注册、运行与关闭；进程记录；阶段检查与 CPU 执行身份。
- **Gateway**：处理路由与话题读取撤回 `access` 参数。
- **Patchouli**：删除 `access` 参数与 `access_consumption`。
- **server**：声明解析不再组装 `IdentityScope`；chat 改为先注册后运行；取消改用请求级 context。
- **公共契约**：Patchouli 公开路由、`PatchouliService` 阶段路由与 Gateway 处理路由不再接收 `access`；能力层方法改为接收 `access` 与目标 workspace；注册入口拆为注册与运行；新增 4.2 的错误 reason；`context_expired` 不再产生；`OwnerMismatchError` 不再由构造 `IdentityScope` 触发。

## 6. 迁移与兼容

以 `37f800e` 为起点，按以下顺序切换，每一步都能单独验证：

1. **core 与 guard**：context 改为不透明，guard 改用授予记录；`authorize_operation` 接收目标 workspace；owner 检查移到第 2、3 阶段并删除 `IdentityScope` 的校验器；新增进程控制授权与 CPU 执行身份方法；认证网关增加运行绑定参数。
2. **Patchouli 与 Gateway**：删除 `access` 参数、`access_consumption` 与 `WorkspaceAccessVerifier` 端口。
3. **能力层**：方法改为只接收 `access` 与目标 workspace，使用 guard 返回的 scope。
4. **注册入口与任务进程**：注册步骤（认证、绑定、创建、登记）与运行分离；关闭由入口负责；进程记录按 4.4；阶段检查传目标 workspace；CPU 输入清单改用 CPU 执行身份。
5. **server**：声明解析；管理路由传 context 与目标 workspace；chat 先注册后运行，并保证流未开始时的关闭；取消改用请求级 context。
6. 测试迁移与注释清理。

**行为变化**：chat 认证失败仍返回 403；取消、状态查询与运行时事件的语义不变；Alice 的 chat 与 MTP 读取照常工作；`/ingest` 不变。

**测试迁移**：依赖旧签名的测试（同时传 `identity_scope` 与 `access`、从 context 读身份、构造跨 owner 的 `IdentityScope`）改为经真实网关取得 context、经 guard 取得 scope；第一版中 99 个失败与 17 个报错的测试在本次迁移中一并处理。

**回滚**：回退到 `37f800e`。

## 8. 测试与验收

**单元测试**

- guard：context 没有公开字段；未签发、已失效、guard 关闭时分别拒绝；`authorize_operation` 对目标不等于驻留 workspace、目标 owner 不匹配、白名单不含 operation 分别给出 4.2 的错误；进程控制授权在跨 owner 或跨 workspace 时拒绝；CPU 执行身份方法不检查 operation，但检查目标与 owner；
- `IdentityScope`：可以构造 actor 用户与 workspace owner 不同的值，owner 规则只在准入与授权时生效；
- 访问登记：用户级记录匹配；精确记录优先；精确记录禁用时不回落；`system` 不被用户级记录覆盖；重复的用户级记录在装载期失败；
- 认证网关：授予记录保存 principal 与运行绑定；
- 注册入口：认证失败不创建、不登记进程；注册成功后进程已登记，context 绑定本进程；流从未开始时进程被关闭、context 失效、进程从表中注销；进程以 completed、失败、取消结束后，context 都已失效；
- 任务进程：缺少各阶段 operation 时在对应阶段失败，不产生后续副作用；缺少 `interaction.submit` 时不执行 CPU；阶段路由只收到 `IdentityScope`；
- 能力层：每个方法缺少 operation 时拒绝且不触达 Patchouli；传给 Patchouli 的 scope 来自 guard；
- Patchouli 与 Gateway：公开方法不再接受 `access` 参数；
- 附件：上传使用的 scope 只来自 guard，满足缺陷 Todo 的完成条件；
- server：声明解析不产生 `IdentityScope`；访问错误映射到 4.9 的状态码。

**集成测试**（真实网关与默认登记）

- HTTP 管理操作、`/chat` 全链路、取消、memory-tasks 都经网关成功；
- chat 的认证失败返回 403，且不创建进程；
- 未登记的 principal、不匹配的 adapter、未登记的用户与 Agent 分别以对应 reason 拒绝；
- Alice 的 chat 与 MTP 读取照常工作；
- System 停止后新认证被拒绝，已签发的 context 失效。

**门槛**：CI 等价的 `pytest tests/unit tests/integration`、`ruff check .`、`black --check .`、`mypy src` 通过；分层测试确认 process → capability → access 的依赖方向，以及 Gateway、Patchouli 不导入 guard。

**验收出口**

- [ ] 与 workspace 相关的生产 HTTP 请求都经认证网关；chat 由注册入口认证并在注册时创建进程，认证失败返回 403；

## 9. 风险与待决事项

- **Alice 的直接调用没有 operation 授权**：与现状相同，由 Alice 的能力层调用迁移解决；本计划不扩大这一缺口。
- **CPU 执行身份方法可能被滥用**：它不检查 operation，只能由任务进程在 CPU 分配时调用；以分层或调用点测试约束，并在 Alice 迁移后删除。
- **两个提交路由没有 operation 授权**：`interaction.submit` 与 `memory_intent.submit` 目前没有生产调用方；出现调用方前应先在能力层增加对应方法。
- **`/ingest` 仍在认证前组装 `IdentityScope`**：Import Bus 不在现有系统内，作为不变量 1 的已知例外。
- **第二批未完成前**：记录与后台任务仍以 `IdentityScope` 表示资源身份，AGENTS.md 的传播规则暂不修改。
- **用户级记录是 v0.7.0 的简化**：同一用户的所有 Agent 共享一份白名单，按 Agent 区分的权限随 P-2、P-10 落地。
- **请求头身份不做证明**：只适用于本地单用户部署。
- **实施时确定**：请求级运行标识的生成方式；流从未开始时触发关闭的具体机制（必须有测试覆盖）；guard 诊断查询的形式。
