# v0.7.0 A1 访问边界返工

**计划状态**：Planned。本计划由同名 Todo 于 2026-10-02 升级而来。

## 1. 背景与问题

[A1](../archive/plans/v0.7.0-a1-workspace-access-boundary.md)（已归档）交付了统一认证网关、两类登记、context 签发与逐次 operation 授权，但没有接上生产入口：server 不调用网关，生产请求都靠 Patchouli 公开方法里的放行分支运行：缺少 access 时直接相信调用方传入的 `IdentityScope`。原本由 A2、A6 计划收口的这部分工作，在两份计划作废后（2026-09-27，删除前最后版本见 commit `dda9d9d`）改由 Todo 承接，并决定在任务进程表方向完成、入口稳定之后接入（[总 Idea](../ideas/workspace-network-task-process-architecture.md#61-已决定事项) 6.1）。任务进程表方向已于 2026-10-01 完成。

2026-10-02 按代码核对的缺口：

1. **生产入口不经认证网关。** 网关只在组合根装配（`system/assembler.py`）；`configs/config.yaml` 没有 access 段，网关按设计 fail closed。HTTP 请求的身份只来自请求头 `x-user-id` / `x-workspace-id`。
2. **operation 检查分在两处。** 读取路径在 `workspace/capability/` 检查；写入与管理路径把 access 传给 Patchouli，由 `access_consumption.verified_scope` / `required_scope` 在 Patchouli application 里检查。
3. **放行分支仍在。** [`access_consumption.py`](../../src/hivememory/patchouli/application/access_consumption.py) 冻结了一份清单，列出缺少 access 时仍放行的方法。任务进程调用 Patchouli 的阶段路由（prepare、finalize、cleanup、话题池列表、Profile）都不带 access，`PatchouliService` 的阶段方法也不接收 access；Gateway 读取话题快照与话题数据（[`gateway/context.py`](../../src/hivememory/gateway/context.py)）同样只带 `IdentityScope`。
4. **context 不能随进程失效。** 进程记录不携带访问 context；guard 只能 `close()` 全部，不能让单个 context 失效。
5. **memory-tasks 路由不带身份**，记忆任务的列表、读取与取消对任何请求开放。
6. **附件上传不校验 scope 与 context 是否一致**：P1 缺陷，见 [Todo](../todo/workspace-asset-upload-access-scope-mismatch.md)。
7. **访问错误没有 HTTP 映射**，被全局处理器当作 500 返回。
8. **代码注释过时**：`access_consumption.py` 与 `config/access.py` 仍引用已删除的 A6、协调计划和旧计划路径。

## 3. 目标与非目标

**目标**

1. 与 workspace 相关的 HTTP 请求都经认证网关取得 context。
2. operation 检查集中在 workspace：管理员操作在能力层检查，任务进程的阶段调用在进程内检查；Patchouli application 不再检查行为白名单（`interaction.submit` 与 `memory_intent.submit` 两项例外，见 4.3）。
3. 去掉 HTTP 入口、任务进程与 Gateway 所调用方法的放行分支（方法本身保留），这些方法缺少 access 时显式拒绝。
4. 两类登记各建一个单独的配置文件，并随仓库提供本地单用户可直接运行的默认登记。
5. 修复附件上传的 scope 不一致缺陷，补齐访问错误的 HTTP 映射。

**非目标**

- Alice 的能力层调用迁移，以及 Alice MTP 仍在调用的四个方法的放行分支（4.5）：按总 Idea 15.5 单独建立计划，排在本计划之后；
- Profile 的 `allowed_mtp_verbs` / `allowed_sys_tools` 并入 operation 控制（P-2、P-10）：按总 Idea 15.5 归 Alice 的能力层调用迁移方向；
- Profile 解析改经能力层：前提还缺 Profile 缓存失效（任务进程 Idea 1.2）；本计划只让进程调用 Profile 路由时带上 context；
- System 层面的 API 与 Import Bus（`/ingest`）；
- 外部 Actor 的身份证明，以及 harness 执行侧面的登记结构（v0.7.1 起）；
- 运行时登记与配置热更新（E-1）；
- 进程级权限收窄（P-4a）：进程继承 Actor 的白名单。

## 4. 目标设计

### 4.1 HTTP 入口作为 system actor 的 adapter

server 是一个登记过的调用来源：principals 文件中有它的 principal，adapter 为 `http`。server 自身的 principal 标识由配置声明，默认值与默认登记一致。

对每个与 workspace 相关的请求，server 沿用 `server/deps.py` 的身份解析与冲突检测得到 actor 与 workspace，再以自身 principal 和 `http` adapter 调用网关取得 context：

| 请求 | actor | context |
|:---|:---|:---|
| `POST /chat` | (user, 具体 agent) | 交给任务进程，绑定进程，进程关闭时失效 |
| 管理员操作：memories、topics、agents、workspace assets、memory-tasks | (user, `system`) | 一次请求一个，请求结束时失效 |
| `POST /chat/stop` | (user, `system`) | 同上；取消仍由进程服务校验 owner 与 workspace，不新增 operation |
| System 层面的 API、`/ingest` | — | 不经网关 |

任务进程的注册入口在创建进程前先校验收到的 context（`verify_context`），校验不通过不创建进程，保证“未通过两阶段认证的请求不创建任务进程”（总 Idea 前提第 3 条）由入口自身成立，不只依赖 server。

请求头中的用户身份不做证明。这是本地单用户部署的信任假设，在配置文档中写明。

### 4.2 访问登记

**登记文件**：两类登记各用一个单独的配置文件，对应各自的配置所有者（[Workspace 架构](../architecture/workspace.md)第 4 节）；`config.yaml` 不再承载 access 段。

| 文件（文件名示意） | 内容 | 配置所有者 |
|:---|:---|:---|
| `configs/system_principals.yaml` | `principals`：调用来源的接入登记 | System |
| `configs/workspace_actors.yaml` | `workspace_actors`：Workspace Actor 的准入与行为白名单 | workspace |

- 两个文件都不包含 context 有效期，原因见 4.4；
- 装载规则沿用现有约束：拒绝未知字段，缺失登记即 fail closed；
- principals 文件为 harness 登记的执行侧面（外部 Actor Idea 1.2）留出位置，具体结构不在本计划定义。

**用户级记录**：Workspace 访问记录允许省略 `agent_id`，表示覆盖该用户的所有具体 Agent。

- 不覆盖保留的 `system`；`system` 单独登记，与 [Workspace 架构](../architecture/workspace.md)第 4.1 节现有规则一致；
- 匹配时精确记录优先；精确记录禁用即拒绝，不回落到用户级记录；
- 每个 (owner, workspace, user) 至多一条用户级记录；W0 的 user 等于 owner 约束不变。

**默认登记**（随仓库提供，覆盖本地默认用户与 `main_workspace`）：

| 文件 | 登记 | 内容 |
|:---|:---|:---|
| principals 文件 | server 的 principal | adapter `http` |
| workspace_actors 文件 | 用户级记录（所有具体 Agent） | `resource.read`、`resource.search`、`profile.read`、`asset.acquire`、`interaction.submit` |
| workspace_actors 文件 | `system` | `management.memory`、`management.topic`、`management.asset`、`management.task`、`resource.read`、`task.observe` |

默认白名单只包含现有调用方实际需要的 operation；新的消费者出现时再加入。

### 4.3 operation 检查的位置

**能力层**：写入与管理方法在调用 Patchouli 之前执行 `authorize_operation`，与读取路径一致。

**任务进程**：阶段调用是任务进程自己的编排，不是 actor 的主动操作，不在前提第 4 条的范围内；它们的 operation 检查放在进程内（总 Idea 15.6）。进程持有绑定的 context，在每次阶段调用前用同一个 guard 的 `authorize_operation` 按阶段语义检查，再把 context 传给对应路由。授权规则仍是同一份访问登记的白名单，只是调用点在进程。

| 阶段调用 | operation |
|:---|:---|
| Gateway 分析中的话题快照与话题数据读取 | `resource.read` |
| prepare（话题与检索） | `resource.search` |
| CPU 分配：Profile 解析 | `profile.read` |
| CPU 分配：附件租借 | `asset.acquire` |
| finalize（提交交互记录） | `interaction.submit`；进入 Actor 执行前检查，避免 CPU 执行完才在结算被拒 |
| 结算后的话题池列表 | `resource.read` |
| cleanup | 不检查；只补偿本进程 prepare 的结果 |

Gateway 不做授权判断，只把进程交给它的 context 原样传给 Patchouli 的读取路由。

**Patchouli application**：公开方法只经 `verify_context` 校验 context（由本实例签发、尚未失效、准入仍有效）以及 DTO scope 与 context 的一致性，不再检查行为白名单；资源归属与资源 policy 校验保留。`PatchouliService` 的阶段方法改为接收 access。

例外：`interaction.submit` 与 `memory_intent.submit` 两个公开路由目前没有生产调用方（finalize 经 Patchouli 内部的提交队列提交，不走 `interaction.submit` 路由），能力层也还没有对应方法。它们的 operation 检查暂留在 Patchouli，等能力层出现对应方法时再迁（总 Idea 15.6）。

### 4.4 context 生命周期

- guard 增加使单个 context 失效的能力；
- 进程记录增加访问 context，进程以任何结局关闭时使其失效（P-6）；
- 请求级 context 在请求结束时失效；
- System 停止时先关闭网关、拒绝新认证，任务进程收尾后再关闭 guard；
- 去掉固定有效期（`context_ttl_seconds`）：context 只在上面三个时点失效，即进程关闭、请求结束、System 停止。两种 context 都有明确的失效时点，再设固定有效期没有用处；P-6 讨论时也没有采用“另设 TTL、与进程寿命取较早者”的选项。guard 的 TTL 参数、组合根的读取、配置字段与到期检查一并删除，拒绝原因 `context_expired` 不再产生。将来 plugin 模式需要长连接时，再随其设计决定是否需要有效期。

### 4.5 去掉缺少 access 时的放行分支

**放行分支**指公开方法里的一段代码：调用方没有传 `access` 时，直接相信它传入的 `IdentityScope`。例如 `access_consumption.verified_scope` 在 `access is None` 时直接返回调用方给的 scope；`access_consumption.py` 的冻结清单列出了保留这段代码的方法。

本节只去掉这段放行代码，**方法本身和对应的公开路由都保留**。去掉之后，缺少 access 的调用以 `ScopeRequiredError` 拒绝。

为了不让调用方先坏掉，每个方法都按同样的顺序改：

1. 调用方先取得 context：HTTP 路由经网关取得（4.1），任务进程使用绑定在进程上的 context（4.4）；
2. 调用方把 context 一路传下去：路由 → 能力层 → Patchouli；任务进程与 Gateway → Patchouli 路由。能力层对应方法的 `access` 参数改为必填；
3. 去掉该方法的放行分支。operation 已在能力层或任务进程检查过（4.3），这里只校验 context 是否有效、scope 是否一致。

**本计划去掉放行分支的方法**

| 方法 | 现在不带 access 的调用方 | 要做的事 |
|:---|:---|:---|
| `MemoryManagementService` 的 `create_memory`、`list_memories`、`get_memory`、`update_memory`、`delete_memory`、`record_feedback` | HTTP memories 路由 | 按上面三步改 |
| `AgentProfileManagementService` 的 `create_agent_profile`、`list_agent_profiles` | HTTP agents 路由 | 按上面三步改 |
| `TopicManagementService` 的 `list_active_topics`、`get_topic_data`、`settle_topic`、`evict_topic` | HTTP topics 路由；Gateway 读取话题快照与话题数据；任务进程结算后列出话题池 | 按上面三步改；Gateway 改为转交任务进程的 context |
| `MemoryTaskManagementService` 的 `list_memory_tasks`、`get_memory_task`、`cancel_memory_task` | HTTP memory-tasks 路由（现在不带身份） | HTTP 路由先补身份，再按三步改。冻结清单注释所说的“Patchouli 内部 finalize/wait 链路”调用方已不存在（2026-10-02 核对，`wait` 方法也已移除），清理注释即可 |
| 能力层的 `WorkspaceAssetApplicationService.upload_asset`（放行分支在该方法自身） | HTTP workspace assets 路由 | 按三步改；同时以 context 的 scope 为准，修复 scope 不一致 |
| `PatchouliService` 的 `prepare_agent_run`、`finalize_agent_run`、`cleanup_prepared_agent_run` | 任务进程 | 这三个方法现在没有 `access` 参数，等同于放行：先增加参数，由任务进程传入自己的 context，再改为必须带 access |

**暂时保留放行分支的方法**

下面四个方法仍有 Alice 的调用方不带 access。按总 Idea 15.5，它们的放行分支由 Alice 的能力层调用迁移方向去掉；在此之前保留，保证 Alice 照常工作。

| 方法 | 仍不带 access 的调用方 | 说明 |
|:---|:---|:---|
| `MemoryManagementService.retrieve` | Alice MTP；Passive 的记忆上下文 | Passive 的依赖记入冻结清单，供后续计划处理 |
| `MemoryManagementService.retrieve_by_aliases` | Alice 的 alias resolver | — |
| `AgentProfileManagementService.get_agent_profile` | Alice 的 profile resolver | 任务进程对它的调用在本计划中改为带 access |
| `PatchouliService.record_memory_citation` | Alice MTP | — |

`ModelReadinessService` 属于 System 运维入口，不在 Actor 行为目录内，不受本节影响。

改完后，冻结清单（`access_consumption.py`）只列上表四个方法，写明调用方与后续处理方向，并删除对已作废计划的引用。

### 4.6 访问错误的 HTTP 映射

| 错误 | HTTP |
|:---|:---|
| `AdmissionDeniedError`（`workspace.admission_denied`） | 403；`reason=authentication_gateway_closed` 时为 503 |
| `OperationDeniedError`（`workspace.operation_denied`） | 403 |
| `ScopeRequiredError`（`workspace.scope_required`） | 生产入口经网关后不应出现；出现即为接线缺陷，按 500 返回并记录 |
| `WorkspaceMismatchError`（`workspace.mismatch`） | 409 |

响应保留稳定机器码与 `details.reason`，不暴露接入凭据。

## 5. 受影响的系统与契约

- **server**：网关调用与请求级 context；memory-tasks 补身份；访问错误映射。
- **workspace**：registry（用户级记录）、guard（单个 context 失效、去掉固定有效期）、能力层（写入与管理的 operation 检查）、process（进程 context 与阶段检查）、assets（scope 一致）。
- **Gateway**：处理路由接收 context，并传给话题读取。
- **Patchouli**：检查方式改变；阶段方法接收 access。
- **config / system**：两个登记文件与装载；删除 `context_ttl_seconds` 配置字段；server principal 配置；停止顺序。
- **公共契约**：Patchouli 阶段路由与 Gateway 处理路由的参数增加 access；4.5 中去掉放行分支的方法缺少 access 时以 `ScopeRequiredError` 拒绝；HTTP 新增访问错误的状态码；`workspace.scope_required` 不再有 `context_expired` 这一 reason。

## 6. 迁移与兼容

按以下顺序切换，每一步都能单独验证：

1. 两个登记文件、默认登记与装载；registry 的用户级记录；guard 的单个 context 失效，并去掉固定有效期；
2. server 的管理员操作与取消接入网关；补齐 memory-tasks 身份与访问错误映射；
3. 任务进程持有 context 并做阶段检查，Gateway 与 Patchouli 阶段路由接收 context；随后 `/chat` 接入网关；
4. operation 检查从 Patchouli application 迁到能力层，去掉 4.5 中方法的放行分支；
5. 修复附件缺陷，清理过时注释。

**行为变化**：未登记的用户、Agent 或调用来源会被拒绝；此前任意请求头身份都能访问。默认登记覆盖本地默认用户；前端的身份选择默认就是这个用户，不需要改动。

**测试迁移**：依赖放行分支的测试与辅助（例如 `tests/helpers/attachment_parsing.py` 的 `make_upload_service`）改为经真实网关取得 context；验证 context 到期的测试（`tests/unit/workspace/test_access.py`、`tests/integration/workspace/test_application_access_boundary.py`、`tests/helpers/workspace.py` 中的相关部分）随固定有效期一并删除。

**回滚**：恢复放行分支即回到当前行为；不新增裸 scope 入口，不撤销已接纳的领域工作。

## 7. 测试与验收

**单元测试**

- registry：用户级记录匹配；精确记录优先；精确记录禁用时不回落；`system` 不被用户级记录覆盖；重复的用户级记录在装载期失败；
- guard：单个 context 失效后被拒绝；`close()` 后已签发的 context 与新认证都被拒绝；guard 与配置都不再接受有效期参数；
- 能力层：每个写入与管理方法缺少 operation 时拒绝，且不触达 Patchouli；
- Patchouli：4.5 中去掉放行分支的方法缺少 access 时以 `ScopeRequiredError` 拒绝；带 access 但 DTO scope 不一致时以 `WorkspaceMismatchError` 拒绝；`interaction.submit` 与 `memory_intent.submit` 在缺少 operation 时仍被拒绝；
- 任务进程：缺少各阶段 operation 时在对应阶段失败，不产生后续副作用；缺少 `interaction.submit` 时不执行 CPU；进程以 completed、失败或取消结束后，context 都已失效；
- 附件：跨 Workspace、跨 owner、替换 Actor 的 scope 冲突在副作用前拒绝，满足缺陷 Todo 的完成条件；
- server：访问错误映射到 4.6 的状态码。

## 8. 风险与待决事项

- **用户级记录是 v0.7.0 的简化**：同一用户的所有 Agent 共享一份白名单，按 Agent 区分的权限随 P-2、P-10 落地。
- **请求头身份不做证明**：只适用于本地单用户部署；多用户或远程部署前需要真实的身份证明。
- **阶段检查使 process 依赖 access**：符合总 Idea D-9 的依赖方向，需要分层测试守护。
- **实施时确定**：server principal 标识的配置位置与默认值；登记文件的最终文件名；principals 文件为执行侧面预留的写法。两者都不影响本计划的边界。
