# v0.8.1 话题的存储介质：每个话题一条只追加的日志，沉淀进度在生成完成时推进

> 状态：Planned（2026-11-25）。v0.8.1 短期记忆的第四份计划；设计依据见[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 5 节。

## 1. 背景和问题

v0.7.2 起，话题按顺序保存全部交互，折叠不丢原文，沉淀进度与本话题的写入记录也只往后加：话题已经是一条只往后增长的日志。存储却仍按缓冲时代的做法，把每个话题当作一整块 `TopicData` 快照放在内存字典里，每写一点就重建并替换整个话题。由此有三个问题：

- **没有介质**：跨重启只能在正常关闭时把整个话题池写成一份快照，进程崩溃时话题池与还没沉淀的交互全部丢失；话题越长，每次写入重建的越多。
- **写法不在存储层**：短期存储只提供整条替换（`put`、`update`），话题上发生了什么写在 core 话题模型的四个写函数里，存储层不知道。
- **工作记录无处追加**：工作记录要追加到话题上（短期记忆 Idea 第 3 节），先要有可以追加、可以落盘的介质。

话题随时落盘之后，沉淀进度不能再在生成队列接纳时推进：进程崩溃时话题以为已经沉淀，生成却随进程丢失，这段交互再也不会沉淀。

## 2. 目标与非目标

### 2.1 目标

- 每个话题是一条只追加的日志，存成一个 JSON Lines 文件。话题上发生的事各记一条，发生时即落盘，不改写已有的记录。
- 短期存储为每种记录提供一个写入方法；`TopicData` 是由日志组装出来的读取值，留在内存中供读取；运行时的写入与启动时的重放共用同一组“把一条记录套到读取值上”的函数。
- 沉淀进度在生成完成时推进：接纳时只在进程内记下在途，生成完成后日志记下进度。
- 退役记一条，退役话题的日志保留到它最后一次沉淀完成后再删除；重启时重新发起没有完成的最后一次沉淀。
- 删除关闭时的话题池快照，以及关闭时为沉淀发起的生成。

### 2.2 非目标

- **工作记录、推送与拉取、折叠摘要的结构化**：短期记忆 Idea 第 3、4、6、7 节，各自另行计划。
- **随退役执行的沉淀看到排在它前面的同话题沉淀写下的记忆**：Idea 第 5 节的候选，本计划保留现有限制（[记忆生成](../patchouli/generation.md#8-当前限制)第 8 节）。
- **交互快照的重复复制**：每次生成冻结一份来源 InteractionArtifact，属于[全链路原始资料保存](../ideas/PatchouliPageFoldingRawEvidenceDesign.md)。
- **其他运行时状态的崩溃恢复**：生成工作、任务历史、写入意图登记与会话仍只在正常关闭时写盘，崩溃时照旧丢失；本计划只让话题扛住崩溃。
- **断电耐久**：不对每条记录 fsync。
- **日志的压缩与重写**：日志只增长，话题退役后整个删除。

## 3. 当前状态（2026-11-25 核对）

- **短期存储**：`ShortTermMemoryStore` 提供 `get`、`put`、`update`、`create`、`delete`、`list_by_workspace`、`list_all` 与 `count`。端口 `ShortTermStoragePort` 的契约是按话题存取 `TopicData` 快照，唯一实现是内存字典 `InMemoryShortTermStorage`；runtime 以无参的 `ShortTermMemoryStore()` 装配，缺省创建内存实现。另外三个存储端口（Artifact、长期、中期）各自只有一个落在真实介质上的实现。
- **写函数**：core 话题模型的 `merge_interaction_into_topic`、`fold_topic`、`mark_topic_settled` 与 `record_topic_writes` 以完整构造产生新快照；前两个在函数内取当前时间。感知经 `store.update` 在最新快照上套用它们。
- **沉淀**：`_settle_topic` 在 lease 内冻结全部交互（`TopicMaterializeTask.from_topic_data`，最近一次沉淀之后没有新交互时不生成），等待 `generation.submit_settlement` 接纳；接纳后不退役的写回 `mark_topic_settled`（冻结的交互数），退役的删除话题与驻留。协调器在生成上下文为空时不建任务，进度照样推进。
- **写入记录**：控制器在 WRITE 与 SETTLE 执行时经 `topic.get` 读取记录，执行后经 `topic.record_writes` 记回；话题已经退役时不记。
- **关闭**：`shutdown_drain` 依次停止取新工作 → `flush_all_for_shutdown`（有未沉淀交互的沉淀，空话题退役）→ `save_unfinished`（排队中与还没开始写入的任务，含 SETTLE，写进 `patchouli.shutdown.pending_work_file`）→ 把话题池写成快照 `patchouli.shutdown.topic_pool_file`。
- **启动**：挂载公开路由与启动交互提交之前读回话题池快照（`restore_topics`：按 `last_update` 登记驻留，同一 Workspace 超出容量的写进 rejected 文件），之后读回任务历史、启动生成队列、读回保存的生成工作（[感知与短期话题](../patchouli/perception.md#7-维护与关闭)第 7 节）。
- **生成工作信封**：1.5，每次执行前经 codec 重建任务；SETTLE 的 `interaction_input.blocks` 是冻结时话题的全部交互。
- **删除记忆数据**：`server/__main__.py` 的 `_delete_memory_data` 删除话题池快照及其 rejected 文件。
- **测试**：多数测试以无参的 `ShortTermMemoryStore()` 构造；`tests/conftest.py` 把关闭时写盘的文件改到每个测试的临时目录。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-25）：每个话题一条只追加的日志文件；`TopicData` 是由日志组装的读取值；沉淀进度在生成完成时推进，在途只在进程内；退役话题的日志保留到最后一次沉淀完成（短期记忆 Idea 第 5 节）。依赖均已是事实：话题跨重启保存与短期记忆代码整理已经合并。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 日志与记录

- 一个话题一个文件 `<topic_dir>/<topic_id>.jsonl`，一行一条记录。话题 ID 全局唯一，Workspace 归属写在第一条记录里，目录不按 Workspace 分层：数据根的路径长度有限制，文件路径越短越好。
- 每条记录带 `kind` 与发生时间 `at`，内容沿用现有模型的 JSON 形式（`LogicalBlock`、`WorkspaceAssetRef` 等），不另设序列化：

| `kind` | 内容 | 对应现在的 |
|:---|:---|:---|
| `created` | 格式版本、Workspace 归属、标题、展示摘要 | `create` |
| `interaction` | block、这一轮的附件引用、`interaction_id`、模型名 | `merge_interaction_into_topic` |
| `fold` | 被折叠的块标识、折叠摘要 | `fold_topic` |
| `settled` | 沉淀覆盖到的交互数 | `mark_topic_settled` |
| `writes` | 写下的记忆、合并改指 | `record_topic_writes` |
| `retired` | 无 | 退役时删除话题 |

### 5.2 读取值与套用函数

- 每种记录一个套用函数，输入当前读取值（`created` 为空）与一条记录，输出新的 `TopicData`。函数是纯的：时间取记录的 `at`，不取当前时间；以完整构造产生新值，构造校验照常生效（折叠覆盖交互记录的前缀、沉淀进度不超过交互数）。
- core 的四个写函数改为这组套用函数，与记录模型一起移到短期存储（`memory_library`）。core 只保留 `TopicData`、`TopicFold` 等模型与读取侧的派生（`topic_working_blocks`、`topic_fold_summary`）。
- 运行时每次写入与启动时的重放用同一组函数，重启后读回的话题与关闭前（或崩溃前最后一条写下的记录）一致。

### 5.3 短期存储与端口

- **写入方法**，每种记录一个：`create`、`append_interaction`、`append_fold`、`append_settled`、`append_writes`、`retire`；另有删除日志的 `delete`。删除 `put` 与 `update`。读取方法不变：`get`、`list_by_workspace`、`list_all`、`count`。
- **写入顺序**：在 store 的锁内读当前值 → 用套用函数算出新值（校验失败直接抛出，什么都不写）→ 经端口追加这一行 → 替换内存中的值。先落盘再改内存，追加失败时内存不变、错误照常传播。
- **内存**：只放池中话题的读取值，读取不碰磁盘；磁盘只在写入时追加、在启动时读回。全局 ID 唯一性的检查留在 store。
- **端口**：`ShortTermStoragePort` 的契约改为日志：`append(topic_id, line)`、`read_all()`（启动时返回每个话题的全部记录）、`delete(topic_id)` 与 `check_health()`。保持同步：写一行并 flush 交给操作系统，进程崩溃不丢；不 fsync。追加失败时把文件截回追加前的长度，日志里不留半行。
- **实现**：唯一实现 `JsonlShortTermStorage`（文件）；删除 `InMemoryShortTermStorage`。Store 构造时必须传入端口，不再缺省创建内存实现。健康检查报告目录是否可写。
- **配置**：新增 `patchouli.perception.topic_dir`，默认 `.hivememory/topics`，相对路径按工作目录解析；与其他文件路径一样只有代码缺省，随附配置不列出。

### 5.4 沉淀进度在生成完成时推进

- **在途**：`TopicWorkingSet` 为驻留话题记下在途沉淀覆盖到的交互数，只在进程内。`_settle_topic` 判断有没有新交互时以“日志中的沉淀进度”与“在途”两者中较大的为准，`TopicMaterializeTask.from_topic_data` 接收这个位置。在途期间空闲扫描不会再沉淀同一段。
- **接纳之后**：建了生成任务时只记在途，不写日志；协调器没有建任务（生成上下文为空）时立即 `append_settled`。
- **完成**：控制器在 SETTLE 任务到达终态时，经新的本地路由 `topic.record_settled(topic_id, *, belong_to, interaction_count)` 交给感知；交互数取任务冻结的全部交互（`interaction_input.blocks` 的长度），工作信封不变。感知写一条 `settled`（话题在池中时同时更新读取值），清除不超过它的在途；随退役执行的沉淀完成后删除话题的日志。
- **哪些终态算完成**：成功、失败与用户取消都算，与现在一样，失败的沉淀不自动重试，取消的不重做。关闭时取消的不算：在途随进程消失，重启后日志停在上一次完成的位置，话题在重启后的空闲扫描中重新沉淀。
- **顺序**：同一话题的沉淀按话题顺序键依次执行，先接纳的先完成，日志中的进度只往前。
- **重复**：生成已经写下记忆、日志还没记下 `settled` 时崩溃，重新沉淀会复述这些记忆，交给查重。
- `topic.settled` 运行时事件照旧在接纳时发布，含义不变。

### 5.5 退役与删除

- **退役**（LRU 与手动结算）：接纳后写一条 `retired`，读取值离开存储与驻留，日志文件保留到最后一次沉淀完成。没有新交互、不提交生成的退役直接删除日志。
- **退役话题的写入记录**：话题已经不在池中，`topic.record_writes` 照旧不记；随退役执行的沉淀只用冻结时的记录（第 2.2 节）。
- **`topic.record_settled` 遇到已退役的话题**：日志还在时照常写一条 `settled`；这次是随退役执行的沉淀时，随后删除日志。
- **手动删除话题**（evict）：立即删除日志；之后到达的 `topic.record_settled` 与 `topic.record_writes` 找不到话题，不记。

### 5.6 关闭与启动

- **关闭**：生成队列停止取新工作 → 保存未执行的生成工作，不再包含 SETTLE：排队中与还没开始写入的沉淀以关闭为原因取消、不保存，已开始写入的沉淀等它写完，它的 `settled` 照常写进日志。删除 `flush_all_for_shutdown`、`TriggerReason.SHUTDOWN` 与话题池快照的保存；`shutdown_drain` 完成事件去掉 `perception` 与 `topic_pool` 两部分。空话题不再在关闭时退役，重启后由空闲扫描退役。
- **启动**：读回话题的位置不变（挂载公开路由与启动交互提交之前）。读回全部日志并重放：没有 `retired` 的话题进入存储与驻留，按最后一条记录的时间从旧到新登记，空闲计时从读回时开始；有 `retired`、最后一次沉淀没有完成的话题，在生成队列启动之后重新发起这次沉淀（材料由日志组装，`retires_topic=True`）。
- **超出容量**：全部读回。同一 Workspace 超过 `max_resident_topics`（配置在两次运行之间调小）时，下一次需要新话题时由现有的 LRU 循环逐个退役，不写 rejected 文件，不丢未沉淀的交互。
- **读不回**：中间某一行解析或校验失败、或格式版本不认识时，整个文件改名为同目录的 rejected 文件，记错误日志，这个话题不读回；最后一行不完整（没有换行，进程在写入中途退出）时丢弃并截掉这半行，其余照常读回。
- **观测**：读回仍作为一次 `patchouli.restore_topic_pool` 操作，报告读回的话题数、重新发起的最后一次沉淀数与进入 rejected 的文件数。

### 5.7 删除记忆数据

`_delete_memory_data` 删除整个话题目录（含 rejected 文件），不再删除话题池快照：日志里是还会沉淀为记忆的交互。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| core 话题模型 | 删除四个写函数；`TopicData` 的说明改为由日志组装的读取值 |
| memory_library | 记录模型与套用函数；store 的写入方法；端口契约改为日志；新增 `JsonlShortTermStorage`，删除 `InMemoryShortTermStorage` |
| Patchouli 感知 | 写入改调 store 的写入方法；在途；`topic.record_settled` 的处理；退役保留日志；启动时读回与重新发起；删除关闭时的沉淀 |
| 感知引擎 | `TopicMaterializeTask.from_topic_data` 接收沉淀位置；删除 `TriggerReason.SHUTDOWN` |
| `TopicWorkingSet` | 在途沉淀覆盖到的交互数 |
| Patchouli 本地路由 | 新增 `topic.record_settled` |
| 生成控制器 | SETTLE 终态时调用 `topic.record_settled`；关闭时不保存 SETTLE |
| Patchouli runtime 与 system | 关闭顺序；启动时读回日志；删除 `topic_pool.py` |
| 配置 | 新增 `patchouli.perception.topic_dir`；删除 `patchouli.shutdown.topic_pool_file` |
| 观测 | `shutdown_drain` 完成事件的字段；`patchouli.restore_topic_pool` 的报告字段；`topic.settled` 的 `reason` 不再有 `shutdown` |
| server | 删除记忆数据的范围 |

不涉及 Workspace 能力层、公开 route 与 HTTP 响应；话题列表与话题池界面读到的仍是 `TopicData` 与 `TopicSnapshot`。生成工作信封不变（1.5）。

## 7. 兼容与迁移

- **升级后第一次启动**：没有话题目录，话题池为空。旧版本关闭时已经沉淀了全部未沉淀的交互，生成工作保存在 `pending_work_file` 里，读回后照常执行；其中的 SETTLE 只可能来自旧版本，它们的话题不在新的话题池里，执行时只用冻结的记录，完成时 `topic.record_settled` 找不到话题、不记。记忆不丢，只是跨升级的那一次重启照旧切开话题。
- **旧的话题池快照**：`.hivememory/topic_pool.json` 不再读取，也不删除，帮助文档说明可以删除。另一种做法见第 9 节。
- **配置**：`patchouli.shutdown.topic_pool_file` 删除后，个人配置里写了这一项会因未知键启动失败；随附配置与示例从没列出它。
- **降级**：旧版本不认识话题目录，既不读取也不删除；再升级时会读回降级之前的日志，话题与沉淀进度停在降级那一刻，降级期间沉淀过的交互会再沉淀一次，重复交给查重。降级之后应删除话题目录，由帮助文档说明。
- 开发实例与日常实例各有自己的工作目录，日志互不影响。

## 8. 测试和验收标准

### 8.1 不变量与归属层

| 不变量 | 归属层 |
|:---|:---|
| 每种记录的套用函数产生与现在写函数相同的读取值；时间取自记录；构造校验照常生效 | 短期存储单元测试（`tests/unit/memory_library/test_stores.py`） |

## 9. 风险与待决问题

- **同步写盘占住事件循环**：长轮次带着工具结果，一条 `interaction` 记录可能有几 MB；每轮写一次，在 SSD 上是毫秒级。真成问题再改为在线程中写。
- **日志只增长**：话题活多久日志就有多大，与现在内存中与快照中的大小相同；退役后删除。
- **启动重放**：启动时重放全部日志，话题池有容量上限，量级与现在读回快照相同。
- **重复记忆**：崩溃时已写下记忆、没记下进度的沉淀会重做，交给查重。
- **断电**：不 fsync，最后几条记录可能丢失；最后一行不完整时丢弃。
- **界面**：话题池的“有未沉淀的交互”按日志中的进度判断，沉淀生成期间仍显示为有未沉淀的交互。
- 待评审的默认值：第 5 节的名字与目录位置；目录不按 Workspace 分层；在途记在 `TopicWorkingSet`；失败与用户取消算完成；超出容量时交给 LRU 而不是写 rejected 文件；旧快照不导入。导入的做法是升级后第一次启动时把旧快照中的每个话题转成日志，保住跨升级那一次重启的话题连续，代价是一段只运行一次的迁移代码。
