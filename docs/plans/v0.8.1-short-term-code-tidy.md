# v0.8.1 短期记忆代码整理：写回由存储层保证，折叠摘要改名，清理遗留

> 状态：Planned（2026-11-24）。v0.8.1 短期记忆的第三份计划，为话题的工作状态做准备；问题来自对短期记忆代码的评估，设计依据见[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 4、6 节的现状与差距。

## 1. 背景和问题

话题的工作状态要往话题上加一种新内容（只增的工作记录）和一个新的写者（话题停下时生成一条）。评估现在的短期记忆代码，有三处会让这件事更难做对：

- **写回的正确性靠注释守住**。`TopicData` 是不可变快照，`Store.put` 整条替换。本话题的写入记录不取 lease，所以每次写回都必须在同一段没有 await 的代码里重新读取最新快照、套用写函数、写回；折叠等待摘要、结算等待接纳之后的写回都靠这条规则才不覆盖期间记下的写入。规则现在写在三处代码旁的注释里，工作记录的生成同样是“等模型、再写回”，会是第四处。
- **折叠摘要的名字与读者都偏离了设计**。设计中折叠只为材料服务、读者是读材料的生成；代码里折叠摘要叫 `state_summary`，会与“话题的工作状态”混淆，话题池详情还把它标为“目前进展”（读者清单见短期记忆 Idea 第 6 节）。
- **遗留与重复**：从未产生的触发原因、没有调用方的方法、旧命名，以及四份几乎相同的“读回即删除、读不回改存 rejected 文件”辅助函数。

## 2. 目标与非目标

### 2.1 目标

- 短期存储提供“在最新快照上套用写函数”的原子写入，感知的全部写回改用它，删除“重新读取再写回”的注释规则与 `_leased_topic`。
- 折叠摘要在代码、HTTP 响应、前端与生成请求中统一改名为 `fold_summary`；生成队列信封升到 1.5，此前保存的工作照常读回。话题池详情的标签不再写“目前进展”。
- 删除从未产生的触发原因与没有调用方的方法，改掉两处旧命名，四份保存文件的读写辅助函数合并为一份。
- 除第 5.2 节列出的 HTTP 字段名、信封版本与话题池标签外，行为不变。

### 2.2 非目标

- **折叠调度泛化为“话题的维护工作”**：折叠现在由交互提交队列安排，工作记录的生成也许与它放在一起；但这需要第二个使用方，留给工作记录的计划决定。
- **话题记录每一轮来自哪个会话**：工作记录“会话切到别的话题”这一触发由谁判断，是工作记录计划的阻塞问题（短期记忆 Idea 第 4 节现状与差距）。
- **折叠摘要读者的去留**：Gateway 路由、候选话题渲染、查询理解与话题池以后是否改读工作记录，由工作状态的计划决定；本计划只改名，读者照旧。
- **提示词文字**：折叠提示词中的 `<old_state_summary>`、生成材料中的 `[Topic State]` 等写给模型的文字不动，属于折叠摘要结构化的计划。
- **拆分 `PerceptionFamiliar`**、Gateway 读取完整 `TopicData` 改用读模型：工作状态落地时再看。
- **`ShortTermStoragePort`**：保留（owner，2026-11-24）。
- 服务层导入 `patchouli.runtime.bus` 是 Patchouli 各服务的通行写法，不改。

## 3. 当前状态（2026-11-24 核对）

- **短期存储**：`ShortTermMemoryStore` 在 `ShortTermStoragePort` 之上提供 `get`、`put`、`create`、`delete`、`list_by_workspace`、`list_all` 与 `count`，以一把 `RLock` 保护每次 Port 读写的原子性；没有“读改写”的组合操作。
- **感知的写回**：应用交互在同一段没有 await 的代码里读取并 `put`；折叠（等待摘要之后）、沉淀进度（等待接纳之后）经 `_leased_topic` 重新读取再 `put`；`record_writes` 读取后 `put`，话题不在时跳过。另有 `_ensure_topic` 建立话题、`restore_topics` 写入读回的话题、退役与丢弃的 `delete`。
- **折叠摘要**：`TopicData.state_summary` 由 `topic_state_summary(folds)` 派生；`TopicSnapshot.state_summary`、`TopicMaterializeTask.state_summary`、生成请求的 `GenerationContext.state_summary`、HTTP `ActiveTopicResponse.state_summary` 与前端 `Topic.stateSummary` 承载同一个值。生成队列信封 1.4 以 `spec.request` 的 JSON 形式保存它，1.1～1.3 由一串读回适配器逐级升级。
- **话题池界面**：详情把折叠摘要标为“目前进展”；话题卡片与对话页的话题选择器在有折叠摘要时把它当副标题（`stateSummary || topicSummary`）。
- **遗留**：`TriggerReason.MANUAL_COMPACT` 与 `MANUAL_DELETE` 只有定义、从未产生；`BaseRelayController.create_relay_context` 没有调用方；空闲扫描叫 `scan_idle_buffers_once`，感知引擎的配置段叫 `SemanticFlowPerceptionConfig`（YAML 键是 `patchouli.perception.engine`）。
- **保存文件的辅助函数**：`saved_work.py`、`task_history.py`、`runtime/topic_pool.py` 与 `workspace/intents/registry.py` 各自实现同一套读回：文件不存在返回空；读出 JSON、校验 `format_version` 与条目列表；失败时整个文件改名为 rejected 文件；成功后删除文件。写出都是 `format_version` 加条目列表、经 `write_atomically` 写入。差别只在条目列表的键名、条目在读回时是否逐个解码，以及失败时抛出错误还是记日志返回空。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-24）：先整理再做工作状态；折叠摘要全部改名，包括 HTTP 字段与生成请求，信封升级；`ShortTermStoragePort` 保留。依赖均已是事实。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 写回由存储层保证

- `ShortTermMemoryStore.update(belong_to, topic_id, write) -> TopicData | None`：在存储的锁内读取最新快照，套用 `write(topic) -> TopicData`，写回并返回新快照；话题不存在时不调用 `write`、返回 `None`。Port 不变。
- 感知的写回全部改用它：应用交互套用 `merge_interaction_into_topic`，折叠套用 `fold_topic`，沉淀进度套用 `mark_topic_settled`，记下写入套用 `record_topic_writes`。持有 lease 的用例得到 `None` 时以 `ResourceNotFoundError` 显式失败（话题只在持有 lease 时删除，读不到说明占用被绕过），`record_writes` 得到 `None` 时不记。
- 删除 `_leased_topic` 与各处“读取与写回之间不能有 await”的注释；写函数是纯函数，正确性由“套用在最新快照上”这一结构保证。lease 的职责不变：跨 await 的交互、折叠与结算互斥。

### 5.2 折叠摘要改名

- `TopicData.state_summary` → `fold_summary`，`topic_state_summary` → `topic_fold_summary`；`TopicSnapshot`、`TopicMaterializeTask`、`GenerationContext` 与组装生成材料的参数同名改；Gateway、协调器与感知中的读取随之改。
- HTTP：`ActiveTopicResponse.state_summary` → `fold_summary`；前端 `Topic.stateSummary` → `foldSummary`。
- 生成队列信封升到 1.5；新增 1.4 的读回适配器，把 `spec.request.context.state_summary` 改名为 `fold_summary` 后按 1.5 解码，1.1～1.3 的适配器接在它之后。
- 话题池详情的标签“目前进展”改为“较早内容的摘要”：它是被折叠的那部分交互的摘要，不是话题做到哪了。卡片与话题选择器的副标题照旧。

### 5.3 遗留清理

- 删除 `TriggerReason.MANUAL_COMPACT`、`MANUAL_DELETE` 与 `BaseRelayController.create_relay_context`。
- `scan_idle_buffers_once` → `scan_idle_topics_once`；`SemanticFlowPerceptionConfig` → `PerceptionEngineConfig`，YAML 键不变。

### 5.4 保存文件的辅助函数合并

- `config/files.py` 新增一对函数：`write_json_items(path, *, format_version, key, items)` 原子写出；`take_json_items(path, *, format_version, key, decode=None)` 读回并删除，文件不存在返回 `None`，解析、版本、条目列表或 `decode` 失败时把文件改名为 rejected 文件，抛出带 `rejected_path` 的 `UnreadableFileError`。`decode` 在删除文件之前执行，任务历史与写入意图登记“任一条目读不回就整份改存”的语义因此不变。
- 四处改用它，各自保留自己的条目键、版本号、原因码与对失败的处理（生成工作与话题池抛出、由读回方报告；任务历史与写入意图记日志后以空开始）；`SavedWorkFileError` 与 `TopicPoolFileError` 由 `UnreadableFileError` 代替。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| MemoryLibrary | `ShortTermMemoryStore.update` |
| core 话题模型 | `fold_summary`、`topic_fold_summary` |
| Patchouli 感知 | 写回改用 `update`；删除 `_leased_topic`；`scan_idle_topics_once` |
| 感知引擎 | `TopicMaterializeTask.fold_summary`；删除两个触发原因与 `create_relay_context`；`PerceptionEngineConfig` |
| 生成 | `GenerationContext.fold_summary`；信封 1.5 与 1.4 读回适配器 |
| Gateway | 读取改名 |
| HTTP 与前端 | 话题列表响应的 `fold_summary`；前端类型、服务与两个组件；话题池详情标签 |
| 保存文件 | 四处读写改用 `config.files` 的一对函数；文件格式不变 |

不涉及 Workspace 能力层、公开 route 与事件。快照文件 `topic_pool.json` 不受改名影响：折叠摘要由折叠记录派生，不随话题保存。

## 7. 兼容与迁移

- 生成队列保存文件中 1.1～1.4 的工作照常读回；新保存的工作为 1.5。
- HTTP 话题列表的字段改名，前端同一改动中更新；没有其他已知消费方。
- 话题池快照、任务历史、写入意图登记与生成工作文件的格式不变。
- 降级到旧版本时，旧版本不认识 1.5 的保存工作，会把它们写进 rejected 文件。

## 9. 风险与待决问题

- **改名波及面大**：约 90 个文件（多数是测试），提示词文字有意不改，代码名与写给模型的文字之间暂时不一致，直到折叠摘要结构化。
- **`update` 在锁内调用写函数**：写函数是纯函数、不做 I/O，持锁时间与现在的 `put` 相近；写函数抛出的校验错误照常传播，话题不变。
- 待评审的默认值：第 5 节中的名字；话题池详情的新标签；四个使用方各自保留的失败处理。
