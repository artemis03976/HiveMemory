# v0.7.0 线程 context 取代执行凭据

> **文档状态**：Active（2026-10-11）。阶段一、二已完成实现、验收与 code review。按本次实施约定，阶段三的事实文档晋升、导航状态同步与计划归档暂不执行；当前事实文档继续保留上一基线。

本计划把任务进程内的访问 context 分为两类：进程 context 服务于全部四个阶段，线程 context 只服务于 CPU 执行阶段。主线程的线程 context 在进入 CPU 执行阶段时从进程 context 派生，由 CPU 持有并在提交操作请求时附上，CPU 执行结束即撤销。执行凭据、凭据表与凭据绑定随之删除，操作入口只按请求类型把请求分派到 actor API。子线程独立的 context 属于执行线程层，不在本计划内。

设计依据：

- [执行单元 Idea](../ideas/execution-unit-thread-and-environment.md#t-2-执行线程的访问-context) T-2：2026-10-11 的决定（进程 context 与线程 context 的用途与寿命；线程身份的令牌就是线程 context，不另设执行凭据；操作入口只按请求类型分派；主线程的线程 context 从进程 context 派生）；T-9（操作请求与单一操作入口；“能力方法可以直接以请求模型为参数”）及其 2026-10-11 取代说明；T-1b；
- [身份与访问体系 Idea](../ideas/identity-and-access-model.md)：I-1（访问 context 是密封凭据）、不变量 2 的 2026-10-11 补充、I-9“删除之后”的 2026-10-11 取代说明；
- [外部 Actor Idea](../ideas/external-actor-registration-and-runtime-access.md#34-操作适配器的定义与边界) 3.4（外部 harness 的操作适配器持有会话到线程 context 的映射，v0.7.1）；
- 当前事实：[Workspace 架构](../architecture/workspace.md)第 4、5.4 节，[子系统契约](../contracts/subsystem-contracts.md)第 4 节，[错误模型](../contracts/error-model.md)第 4.4 节；已归档的 [Alice 能力层调用迁移计划](../archive/plans/v0.7.0-alice-capability-migration.md)。

## 1. 背景和问题

任务进程内现在只有一份访问 context（注册时签发的进程 context），actor 操作经执行凭据间接使用它：

- **同一件事有两种令牌**：访问 context 本是密封凭据（不透明、不能复制或序列化、可撤销、读不出身份），执行凭据又以同样的性质包装了它，并另设一张凭据表负责兑现。执行线程层按 T-2 为每个线程签发 context 时，每个线程会同时有一份 context 和一份指向它的凭据。
- **寿命与用途不清**：执行凭据指向进程 context，只在进程关闭时吊销，CPU 执行结束后到进程关闭之间仍然有效；阶段调用与 actor 操作用的是同一份 context，只靠凭据把两者分开撤销。
- **入口的拆参层**：入口兑现凭据后，用 handler 把请求字段拆成关键字参数再调用 actor 方法，同一组参数写在请求、handler 与 actor 方法三处，与 T-9 的原设计（能力方法直接以请求模型为参数）不一致。

## 2. 目标与非目标

### 2.1 目标

1. **两类 context**：进程 context 服务于全部四个阶段的阶段调用，由注册入口持有并在进程关闭时最后撤销；线程 context 只服务于 CPU 执行阶段的 actor 操作，CPU 执行结束即撤销。
2. **派生**：认证一侧提供从进程 context 派生线程 context 的能力；主线程的线程 context 在进入 CPU 执行阶段时派生，不重新认证。
3. **CPU 持有线程 context**：CPU 端口与操作入口以线程 context 取代执行凭据；CPU 在提交操作请求时附上线程 context，主、子 frame 共用。
4. **入口只按请求类型分派**：actor 方法直接接收请求对象与线程 context；意图登记的进程关联取自线程 context 的运行绑定；入口只接受线程 context。
5. **删除执行凭据**：`ExecutionCredential`、`ExecutionCredentialRegistry`、`ExecutionBinding` 与入口的拆参 handler。

### 2.2 非目标

- 执行线程层：子线程各自的 context（以被调用方派生或重新认证，T-3a）、派生如何到达进程（T-1a）、子线程 context 的失效时点（T-2a）、派生授权（T-3c）。本计划中子线程沿用主线程的线程 context。
- 请求类型声明自己对应的 operation：未作决定，actor 方法仍各自确定要检查的 operation。
- 外部 harness 的 MCP 操作适配器（v0.7.1）。
- root API 与请求级 context 的用法不变。

## 3. 当前状态（2026-10-11 核对）

- **访问 context**（`core/access.py`）：`WorkspaceAccessContext` 密封 `AccessGrant`（actor、驻留 workspace、principal、`RunBinding`），撤销状态随对象本身；`_seal`、`_revoke` 只由 `WorkspaceAuthenticator` 调用，`_unseal` 只由操作授权者与诊断查询调用（架构测试守护）。`AccessRunType` 只有 `TASK_PROCESS` 与 `REQUEST`。
- **认证一侧**（`workspace/authentication.py`）：`WorkspaceAuthenticator.admit` 签发并记入已签发集合，`invalidate` 撤销单个，`revoke_all` 在 System 停止时撤销全部；`ActorAuthenticationGateway` 是唯一对外入口，关闭后拒绝新认证，不影响已签发 context。注册入口持有网关；执行器 `TaskProcessRunner` 与 CPU 分配只依赖操作授权者，不导入认证一侧（`tests/unit/architecture/test_access_boundaries.py`）。
- **执行凭据**（`workspace/credentials.py`）：`ExecutionCredentialRegistry.issue` 为进程 context、注册目标与 process_id 签发凭据，`resolve` 兑现为 `ExecutionBinding`，`revoke` 吊销。执行器在进入 Actor 阶段时签发，写入工作集；只在关闭流程中同步吊销（先于任何 await），CPU 执行结束后不吊销。
- **CPU 端口与 Alice**：`CPUPort.execute(manifest, *, credential, generation_options, stream)`；`AliceCPU` 把凭据与 `OperationEntry` 绑定为 `OperationSubmitter`，主、子 frame 共用。
- **操作入口**（`workspace/capability/operations.py`）：`execute(request, *, credential)` 先兑现凭据，再按请求类型找到 handler，handler 拆参后调用 actor 方法（`target_workspace`、`access`、需要时 `process_id`）；WRITE、UPDATE 返回后复查凭据，已吊销则同步撤回刚登记的意图并抛 `ExecutionCredentialRevokedError`；撤回意图按绑定的 process_id 执行。
- **actor API**（`workspace/capability/actor/`）：方法以关键字参数接收业务字段、`target_workspace` 与 `access`，在方法体内以写死的 operation 调用 `authorize_operation`。
- **进程 context 的撤销**：注册入口在执行器关闭流程之后撤销进程 context，cleanup 的阶段授权因此仍可执行。

## 4. 目标设计

### 4.1 两类 context

| | 进程 context | 线程 context（本计划只有主线程） |
|:---|:---|:---|
| 签发 | 注册入口认证时签发（不变） | 进入 CPU 执行阶段时从进程 context 派生 |
| 运行绑定 | 任务进程，`process_id` | 执行线程：进程的 `process_id` 加线程标识（主线程为固定标识） |
| 持有者 | 进程记录 | CPU（经提交函数）；进程工作集同时登记，用于撤销 |
| 用途 | 阶段调用（阶段授权、操作快照读取） | 该线程发起的 actor 操作（操作授权） |
| 撤销 | 进程关闭时最后撤销（不变） | CPU 执行结束即撤销；关闭流程兜底 |

两类 context 对应 2026-10-10 划分的两类操作：进程 context 用于系统操作，线程 context 用于 actor 操作。

### 4.2 派生

- `AccessRunType` 新增执行线程类型；`RunBinding` 能表达“某进程的某个执行线程”（具体字段在实施评审时确定，运行标识仍为 process_id）。
- 认证一侧新增派生：输入一份有效的进程 context，签发新的密封 context，授予内容沿用原 actor、驻留 workspace 与 principal，运行绑定换为执行线程；新 context 记入已签发集合，可单独撤销，System 停止时随 `revoke_all` 撤销。已撤销的进程 context、请求级 context 或线程 context 不能派生。
- 派生不是认证：不重新检查接入登记，也不受网关关闭影响（关闭只拒绝新认证），与现在签发执行凭据的行为一致；准入仍由每次授权即时检查。
- 执行器经一个只含“派生线程 context、撤销线程 context”两个方法的端口取得这项能力，由组合根注入网关的实现；执行器仍不导入认证一侧，调用面由架构测试限定在执行器。

### 4.3 签发与撤销时点

- 进入 CPU 执行阶段时，执行器以进程 context 派生主线程的线程 context，登记进工作集，并作为 `execute` 的独立参数交给 CPU；输入清单不携带它。
- CPU 返回终态结果、执行器关闭 CPU 输出流之后，立即同步撤销线程 context，再进入 finalize；finalize、话题池读取与 cleanup 照常以进程 context 做阶段授权。
- 关闭流程兜底：Actor 阶段因取消、失败或断流提前结束时，先于任何 await 同步撤销仍登记的线程 context，再取消本进程仍为 PENDING 的意图、释放租借（顺序与现在的凭据吊销相同）。
- 进程 context 的签发与撤销不变。

### 4.4 CPU 端口与 Alice

- `CPUPort.execute(manifest, *, access, generation_options, stream)`：`access` 是线程 context，取代 `credential`。
- `OperationEntry.execute(request, *, access)`：取代 `credential`。
- `AliceCPU` 把线程 context 与入口绑定为 `OperationSubmitter`，主、子 frame 共用；Alice 读不出 context 的内容，也不持有进程 context。

### 4.5 操作入口与 actor API

- 入口只接受线程 context：分派前经操作授权者确认它是未撤销的执行线程 context，否则拒绝且没有副作用；进程 context 与请求级 context 不能提交 actor 请求。
- 入口按请求类型直接调用 actor 方法，actor 方法以请求对象与线程 context 为参数，删除拆参 handler；目标 workspace 取 context 的驻留 workspace（第 3 阶段仍只接受驻留目标）。
- 意图登记的进程关联（process_id）取自线程 context 的运行绑定，由操作授权者提供只读查询（只对执行线程 context 有效，调用面限定在能力层）；请求不能指定 process_id。
- WRITE、UPDATE 返回入口后复查线程 context：已撤销则同步撤回刚登记的意图并拒绝返回 ACK（与现在的凭据复查相同）。
- 撤回意图仍是入口内部的补偿：按线程 context 的进程关联撤回本进程仍为 PENDING 的指定意图，不检查 operation。

### 4.6 错误

- `ExecutionCredentialRevokedError` 改为表达“线程 context 已撤销”的错误（名称在实施评审时确定），语义不变：CPU 执行结束或进程关闭后迟到的请求被明确拒绝，Alice 照旧以结构化系统错误回填。它不是 `ScopeRequiredError`：后者在错误模型中表示接线缺陷。
- 非线程 context 提交 actor 请求属于接线缺陷，沿用 `ScopeRequiredError`。

### 4.7 删除

`workspace/credentials.py`（`ExecutionCredentialRegistry`、`ExecutionBinding`）、`ExecutionCredential`、工作集的凭据槽位（改为线程 context）、入口的拆参 handler，以及组合根对凭据表的装配。

## 5. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| `core.access` | 新增执行线程运行类型与相应的运行绑定 |
| 认证一侧 | 新增派生；执行器经端口使用派生与撤销 |
| 操作授权者 | 新增线程 context 校验与进程关联查询 |
| `workspace.contracts` | `CPUPort.execute` 与 `OperationEntry.execute` 的 `credential` 改为 `access`；删除 `ExecutionCredential`，错误类型改名 |
| `workspace.capability` | 入口只按请求类型分派；actor 方法改为接收请求对象与线程 context |
| `workspace.process` | 执行器派生、登记与撤销线程 context；工作集槽位更换 |
| Alice | `AliceCPU` 绑定线程 context |
| 组合根 | 删除凭据表装配；向执行器注入派生端口 |
| 行为 | CPU 执行结束后 actor 请求即被拒绝（此前到进程关闭才拒绝，期间没有正常的 actor 请求）；其余运行行为不变 |
| 公共路由与数据 | 无 HTTP 路由或持久化数据变化 |

## 6. 兼容与迁移策略

- 进程内替换，不涉及持久化数据或 HTTP 接口。
- CPU 端口契约有破坏性变化，当前只有 `AliceCPU` 与测试用 `ScriptedCPU` 实现它，随阶段二一并修改。
- 执行线程层在此基础上为子线程派生或签发各自的线程 context，CPU 端口与入口的形态不再变化。

## 8. 测试和验收标准

按[测试设计规范](../governance/testing/test-design-standards.md)分类；认证一侧、操作授权者、任务进程与入口使用真实对象，外部 LLM 与存储使用既有替身。

1. 派生：从有效的进程 context 派生的线程 context 与原 context 是不同对象，授权组装的 `IdentityScope` 发起者与目标相同；已撤销的进程 context、请求级 context 与线程 context 不能派生。
2. 派生的 context 可单独撤销：撤销线程 context 不影响进程 context 的阶段授权；网关关闭后仍可派生；System 停止时 `revoke_all` 同时撤销两类 context。
3. 操作授权者的进程关联查询只对执行线程 context 返回 process_id，对其他 context 拒绝；调用面由架构测试限定。
4. 进入 CPU 执行阶段时 CPU 收到线程 context，输入清单中没有 context；主、子 frame 的请求以同一线程 context 授权。
5. CPU 返回终态后、finalize 之前，线程 context 已撤销；finalize、话题池读取与 cleanup 仍以进程 context 完成。
6. Actor 阶段因取消、失败或断流提前结束时，关闭流程先于任何 await 撤销线程 context。
7. 线程 context 撤销后提交的 actor 请求以新错误类型拒绝且没有副作用；撤销前已通过入口的只读请求自然完成；WRITE、UPDATE 在撤销后登记的意图被同步撤回（沿用现有测试）。
8. 进程 context 与请求级 context 经入口提交 actor 请求被拒绝，没有副作用。
9. 意图登记的 process_id 来自线程 context，请求无法指定；CALL 子帧失败时的撤回只作用于本进程仍为 PENDING 的意图（沿用现有测试）。
10. 入口只按请求类型分派：actor 方法接收请求对象，入口中没有拆参 handler（结构测试）。
11. 结构：生产代码不再引用 `ExecutionCredential`、`ExecutionCredentialRegistry` 与 `ExecutionBinding`；派生只由执行器经端口调用；执行器与 CPU 分配仍不导入认证一侧。
12. 确定性 HTTP chat E2E：WRITE 在 completed 后被认领并进入 finalize，现有 chat E2E 全部通过。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| 执行器新增对认证一侧能力的依赖 | 只经两个方法的端口，由组合根注入；执行器仍不导入认证模块，调用面由架构测试限定 |
| 派生绕过认证 | 派生只复制已认证的授予内容，不能改变 actor 或驻留 workspace；准入与白名单仍在每次授权时即时检查 |
| CPU 持有 context 与“context 只由运行持有者与授权点持有”的表述不一致 | 身份 Idea 不变量 2 的 2026-10-11 补充：线程 context 的运行即该线程在 CPU 执行阶段内的执行，持有者是 CPU；事实文档在收尾时同步 |
| CPU 执行结束即撤销导致迟到请求被拒 | Alice 关闭输出流时已取消自己的 run；迟到请求以新错误类型明确拒绝，意图提交有同步补偿 |
| 执行线程层需要子线程以被调用方身份取得 context | 不在本计划；派生只适用于与进程同一 actor 的线程，被调用方的 context 由 T-3a 决定 |
| 名称待定：运行绑定字段、派生方法与端口、进程关联查询、错误类型 | 实施评审时确定，不改变设计 |
