# v0.7.3 生成任务失败带原因码

## 1. 背景和问题

2026-11-03 排查 dsh 调研中的 4 次合并失败时，日志与事件都没有给出原因（[收敛 Idea](../ideas/generation-source-convergence.md#25-合并失败)第 2.5 节，[日志与运行时事件](../governance/observability/logs-and-events.md)第 1 节）：

- 生成队列的失败分类对一切异常给出同一个原因 `memory_generation_failed`，工作记录与 `work.failed` 只能靠异常类名区分；
- 控制器发布 `memory.task.failed` 时 `reason` 只填取消原因，失败任务为空；
- 控制器的失败日志只有任务标签与固定文本"记忆生成失败，请检查服务状态"。原始异常没有在任何一层带堆栈记录，合并中止的原因只留在 `MemoryMergeAbortedError.details` 中。

结果是前三次合并失败只能凭时序推断为版本冲突，第四次至今不知道原因；"合并遇到版本冲突时是否重做"（Idea 第 4.4 节）也因此无法判断。

owner 2026-11-03 决定：生成任务失败带原因码，经失败分类进入工作记录、事件与日志（Idea 第 3.3 节）。

## 2. 目标与非目标

### 2.1 目标

- 生成任务的失败分类按异常给出稳定原因码，进入工作记录与 `work.failed`；
- `memory.task.failed` 的 `reason` 为工作记录中的原因码，载荷带异常类名；
- 每次生成失败在后端日志中记一次：带原因码；领域错误带 `code` 与 `details`，未预期的异常带堆栈。

### 2.2 非目标

- 任务快照与任务 API 不变：`error` 仍是固定说明，不新增字段；
- 写入意图的失败结算不带原因：经 MCP 或 MTP 读取失败的 pending 句柄，看到的仍只是失败；
- 合并遇到版本冲突时不重做（Idea 第 4.4 节），等原因码落地后的真实数据再判断；
- 不改工作队列通用层、交互提交 lane，以及 Familiar 与生成引擎抛出的异常。

## 3. 当前状态（2026-11-03 核对，commit `09812c83`）

- **分类**：`MemoryGenerationHandler.classify_failure`（`patchouli/control/memory_generation/queue.py`）把原始错误文本交给句柄在进程内保存，返回 `FailureDecision(FAIL, reason="memory_generation_failed")`。通用运行时据此写入 `WorkErrorSnapshot(error_class=异常类名, message=reason)`；`work.failed` 的 `reason` 取 `message`，`data.error_class` 取异常类名。
- **超时**：生成 lane 的 `timeout_seconds` 默认 300 秒（`patchouli.generation.queue_timeout_seconds`）。超时由运行时的 `asyncio.timeout` 抛出 `TimeoutError`，同样经分类器得到 `memory_generation_failed`。提取、修订与合并的 LLM 调用没有独立超时（[生成](../patchouli/generation.md#8-当前限制)第 8 节）。
- **不经分类器的失败**：payload 解码失败直接进入 dead letter，原因为 `invalid_work_payload`；分类器自身抛错时，运行时记录带堆栈的日志，原因为 `failure_classifier_error`。
- **领域终态**：`memory_task_from_outcome` 把失败投影为固定的 `error`；控制器的 `_publish_terminal` 以 `reason=snapshot.cancel_reason` 发布终态事件，失败任务为空，`memory_task_to_payload` 的 `reason` 字段随之为空。
- **日志**：`_settle_outcome` 对失败任务记一行 `Memory generation failed: label=…, err=…`，`err` 是固定文本。Familiar 与运行时都不记录生成异常。
- **异常**：
  - `MemoryMergeAbortedError`（`workspace.memory.merge_aborted`）由 Familiar 的合并路径抛出，`details["reason"]` 为 `memory_missing`、`not_mergeable`、`version_changed` 或 `model_output_invalid`，四处抛出点都带它；
  - `ModelContextWindowExceededError` 是 `ModelProviderError` 的子类；`ModelProviderError` 不继承 `DomainError`，没有 `code`；
  - 其他领域错误继承 `DomainError`，带稳定的 `code`。

## 4. 进入条件

Idea 第 3.3 节已决定（owner，2026-11-03）；依赖都是现有事实，不依赖其他计划。

## 5. 目标设计

### 5.1 原因码

分类器按下表给出原因码，自上而下判断：

| 异常 | 原因码 |
|:---|:---|
| `MemoryMergeAbortedError` | `merge_aborted.<details 中的 reason>` |
| `ModelContextWindowExceededError` | `model_context_window_exceeded` |
| `ModelProviderError` | `model_provider_failed` |
| `TimeoutError` | `memory_generation_timed_out` |
| 其他 `DomainError` | 该错误的 `code` |
| 其他异常 | `memory_generation_failed` |

- `TimeoutError` 一行是本计划在 Idea 第 4.3 节之外新增的：生成 lane 的超时在生产中会出现，需要与程序错误分开；数据面内部抛出的其他 `TimeoutError` 也归入这一类。
- 合并中止的 `details` 缺少 `reason` 时不兜底：四处抛出点都带它；万一缺少，分类器抛错，运行时按 `failure_classifier_error` 收尾并记录堆栈。
- 原因码只用于观测与诊断，不驱动重试或业务判断；生成 lane 仍固定单次尝试。

映射写成队列模块中的一个纯函数，由分类器调用。

### 5.2 日志

分类器是做出失败判断、也持有原始异常的一层，按日志写法（治理主题第 2.2 节）在这里记一次 error 日志：

- 每次都带 `work_id`（形如 `memory_generation:<task_id>`）、原因码与异常类名；
- 领域错误另记 `code` 与 `details`，不带堆栈；
- 提供商失败与超时不带堆栈：提取器重试前已以 warning 记录第一次失败的原因，超窗不重试、原因码本身已说明；
- 其他异常带堆栈。

控制器原有的那行失败日志删除：它只有固定文本，与分类器的日志是同一次失败。

这是对 Idea 第 4.3 节候选设计的调整：Idea 设想在控制器记录，并带标签、来源与话题。控制器拿不到原始异常，要带上 `details` 与堆栈，就得让通用任务句柄保存异常对象。日志因此改在分类器记录；来源与话题由同一任务的 `memory.task.failed` 事件携带，按 `task_id` 在运行时事件记录文件中对应（`scripts/runtime_event_timeline.py task_id=<ID>`）。

### 5.3 领域终态事件

- 控制器在 `_settle_outcome` 中，从失败（FAILED 与 DEAD_LETTER）工作记录的 `last_error` 取出原因码与异常类名，交给终态事件：`memory.task.failed` 的 `reason` 为该原因码；取消任务仍为取消原因。
- `memory_task_to_payload` 新增 `error_class` 字段，失败时为异常类名，其余为空；载荷的 `reason` 字段与事件一致。
- 工作记录缺失（`outcome is None`）的现有分支不变。

### 5.4 不变的部分

- 任务快照、任务 API 与 `error` 的固定说明；
- 写入意图的失败结算；
- 工作队列通用层，以及 `work.*` 事件的结构；
- 生成 lane 的单次尝试与超时。

## 6. 受影响的系统、契约和数据

- **Patchouli 生成控制面**：失败分类、分类处的日志、控制器的终态事件；`memory.task.*` 载荷新增 `error_class`。
- **观测契约**：生成 lane 的 `work.failed.reason` 与 `memory.task.failed.reason` 的取值（[事件契约](../contracts/routes-and-events.md#44-失败与降级观测)第 4.4 节）。
- **前端**：实时面板与运行时面板显示 `reason`，失败任务从空变为原因码；前端不按它分支。
- **持久化数据**：无，工作记录只在进程内。

## 7. 兼容与迁移

没有持久化与公开 API 变化。事件消费方看到的变化：`memory.task.failed` 的 `reason` 从空变为原因码，载荷多出 `error_class`。运行时事件记录文件中，部署前后失败事件的原因码不同，复盘时按部署时间区分。

## 8. 测试和验收标准

### 8.1 不变量与归属层

| 不变量 | 归属层 |
|:---|:---|
| 每类异常得到第 5.1 节的原因码：超窗先于提供商失败判断，其他领域错误取 `code`，其余为 `memory_generation_failed` | `tests/unit/patchouli/control/test_memory_generation_queue.py`（分类器） |
| 未预期的异常在分类处记一次带堆栈的 error 日志；领域错误记 `code` 与 `details`，不带堆栈 | 同上 |
| 生成 lane 超时的工作记录原因为 `memory_generation_timed_out` | 同上，现有超时用例 |
| 失败任务的工作记录与 `memory.task.failed` 带同一个原因码，载荷带异常类名；取消任务仍带取消原因 | `tests/unit/patchouli/control/test_memory_generation_controller.py`：控制器与真实队列，数据面替身抛出合并中止 |

现有断言 `memory_generation_failed`、或只断言失败状态的用例随契约改写。去掉任一行映射，或不把原因码交给终态事件时，对应用例必须失败。

```bash
pytest tests/unit/patchouli/control -q
```

### 8.3 实测

下一次生成失败时，后端日志有一行带原因码的记录，运行时事件记录文件中的 `memory.task.failed` 带同一原因码。实测依赖自然发生的失败，不作为归档条件。

## 9. 风险与待决问题

- 原因码是观测契约的一部分：领域错误的 `code` 改名会改变原因码。`error_class` 只作诊断，不是稳定分类。
- `memory_generation_timed_out` 把数据面内部的 `TimeoutError` 与 lane 超时归为一类，需要区分时再拆。
- 日志中的 `details` 只应含诊断标识（原因、记忆 ID）；新增领域错误时，`details` 不得带正文（日志写法第 2.2 节）。
- 与 Idea 第 4.3 节候选设计的两处调整可在评审时改回：日志在分类器而不在控制器记录，日志不带话题与来源；新增超时原因码。

没有待决问题。
