# v0.6.2 W0 Workspace MVP 实施计划

**文档状态**：In Progress（P2.5 已完成，P3 返工中）

**目标版本**：`v0.6.2 W0`

**完成定义**：同一用户、同一 Agent 通过同一套共享子系统并发进入两个 Workspace 时，已经由 W0 明确归属到 Workspace 的 Topic、Memory、Artifact、WorkspaceAsset 与 TopicAssetBinding 不串台；共享 cache、registry、queue、runtime 和 EventBus 不使用 `IdentityScope` 形成新的命名分区

---

## 1. 计划定位

本计划是 Workspace MVP 设计与实施的唯一计划真相源。W0 建立资源身份、访问上下文、已裁定资源的逻辑隔离和进程内资产 working set；它不把“收到 `IdentityScope`”等同于“组件加入 Workspace 命名域”。

依赖关系固定为：

```text
v0.6.1 released baseline
  -> v0.6.2 W0 Workspace MVP
```

## 2. 当前基线与缺口

当前代码已经具备单用户条件下可运行的 Active Chat、Gateway workflow、Patchouli prepare/finalize、Alice frame、Interaction Submission 和 Memory Generation queue，但资源寻址仍隐含单 Workspace 假设：

- `ActorIdentity` 同时被用于表达执行者和资源过滤，而它只包含 user、agent、team 与兼容性 session 字段；
- `ChatRun`、`GatewayExecutionState`、`PreparedAgentRun`、`AgentRunContext`、`ExecutionFrame`、`MTPExecutionContext` 和 `InteractionSubmission` 没有统一的 Workspace 坐标；
- `SemanticBuffer`、`TopicData` 和短期存储主要按 `user_id/topic_id` 组织，裸 `topic_id` 仍可能成为事实上的访问凭证；
- `MemoryVisibility.WORKSPACE` 当前实际表示 team scope，`PUBLIC` 当前又只依赖旧 `user_id` 基线；Memory ownership、创建来源与 actor 可见性尚未拆成独立语义；
- Qdrant filter 只有 `user_id` 硬过滤，缺少 `owner_user_id + workspace_id` 硬过滤；
- Artifact filesystem adapter 允许按全局 ID 递归查找，并可从 `ArtifactRef.uri` 直接读取物理路径，尚无 Workspace-aware index；
- System 尚无可承载未资产化运行时文件的权威 working set。

P2.5 已完成 `IdentityScope` 瘦身、领域 ID 归位和异步 DTO 身份来源收敛。最初的 P3 又错误地把该身份载体用于 cache、work key 与其他共享组件的命名分区；当前返工必须保留 P2.5 的数据模型成果，同时撤销这一未经裁定的命名域扩张。RuntimeEvent 已完成可选 `workspace_id` 投影，该字段只消费字符串并且不参与路由、授权或分组，因此不回滚。

## 3. 目标与非目标

### 3.1 目标

1. 引入不可变、可序列化的 `WorkspaceIdentity`，默认 Workspace 为 `main_workspace`。
2. 引入不可变的 `IdentityScope`，只冻结 `ActorIdentity` 与 `WorkspaceIdentity` 两条正交身份轴；关联 ID 由真正需要它的领域载体持有。
3. 默认 Workspace 只在最外层入口解析一次；进入领域链后缺少 scope 必须失败。
4. 让需要访问已裁定 Workspace-owned resource 的领域边界获得不可变 `IdentityScope`；各领域 DTO 另行携带实际需要的关联 ID，但任何 W0 组件都不得把 `IdentityScope` 作为分隔 key。
5. 让 Memory、Artifact、Topic、WorkspaceAsset 和 TopicAssetBinding 使用各自明确的 Workspace resource key；共享 cache、registry、queue、runtime 和 EventBus 保持原有命名域。
6. 在不批量改写历史数据的前提下提供受控 compatibility-read/filter。
7. 由 System runtime 建立一个进程级 WorkspaceAssetStore，并实现 WorkspaceAsset/AssetRepresentation 两级状态机、READY-only 读取、删除、进程内 lease，以及 Topic shutdown settlement 完成后的统一关闭与清空。
8. 由 Patchouli SemanticBuffer/ShortTermMemoryStore 拥有幂等的 `TopicAssetBinding`。
9. 使用第二个仅供后端验证的 Workspace，为已明确 Workspace ownership 的资源建立不串台证据。
10. 将 Memory 的 Workspace ownership、actor provenance 与 Workspace 内 read policy 明确拆分，并把 `MemoryAtom` 正式升级为 schema v2。

### 3.2 非目标

本计划不实现：

- 文件上传、Composer 交互或 Workspace 切换 UI；
- 真实文本/PDF/DOCX/OCR/图像解析器、parser registry 或自动解析重试；
- Context Compiler、prompt 注入或 Artifact promotion 的生产链路；
- WorkspaceAsset、原始内容、解析结果或 `WorkspaceAssetRef` 的跨进程持久化与重启恢复；新进程必须重新上传并建立新的资产与关系；
- durable tombstone、保留期、完整 GC、分布式 lease 或对象存储；
- Workspace Registry、独立 opaque Workspace ID 生成、rename、Mount、Bridge、跨 Workspace 通信或 grant 管理；
- Memory mutation-policy/RBAC、visibility 管理 UI 或跨 Workspace sharing 的生产实现；W0 只冻结 read policy 与 ownership 边界；
- 为每个 Workspace 创建 Gateway/Patchouli/Alice/MemoryLibrary/queue/runtime 实例；
- 改变 AtomCache、ProfileCache 或其他 cache 的 ownership、生命周期与 key；
- 让通用 Work Queue、registry、runtime 或 EventBus 按 `IdentityScope`/Workspace 分区；
- 历史数据批量转换脚本的执行；脚本必须在 W0 落地并通过隔离验证后独立提供。

## 4. 冻结的身份与隔离契约

### 4.1 WorkspaceIdentity

规范模型为：

```text
WorkspaceIdentity
  owner_user_id
  workspace_key
  workspace_id
```

MVP 不变量：

```text
owner_user_id != ""
workspace_key != ""
workspace_id != ""
workspace_id == workspace_key
default workspace_key == workspace_id == "main_workspace"
```

完整资源坐标为 `(owner_user_id, workspace_id)`。`workspace_key` 只用于默认解析和 Workspace registry lookup；已裁定为 Workspace-owned 的资源在对外协议、资源键和过滤器中统一使用 `workspace_id`。共享 cache、registry、queue、runtime 与 EventBus 不因此增加 Workspace 分隔 key；领域内部禁止 `workspace_id or workspace_key` fallback。

W0 不启用独立 Workspace ID 生成器，也不建立 Workspace Registry。普通产品请求解析到当前用户的 `main_workspace`；测试和内部服务可以显式构造：

```text
WorkspaceIdentity(
  owner_user_id=current_user_id,
  workspace_key="isolation_workspace",
  workspace_id="isolation_workspace",
)
```

这只是隔离测试 seam，不代表 W0 开放了 Workspace 创建或切换产品能力。

### 4.2 IdentityScope

`IdentityScope` 是 W0 唯一的公共身份作用域。名称强调它同时承载执行者身份与资源域身份，而不是仅为 Workspace 服务：

```python
from pydantic import BaseModel, ConfigDict


class IdentityScope(BaseModel):
    actor_identity: ActorIdentity
    workspace_identity: WorkspaceIdentity

    model_config = ConfigDict(frozen=True, extra="forbid")
```

它只回答两个问题：

- `ActorIdentity`：谁在执行；
- `WorkspaceIdentity`：正在访问哪个资源归属域。

`IdentityScope` 不包含 `interaction_id`、通用 `operation_id`、`generation_id`、`agent_run_id`、`frame_id`、`request_id`、`trace_id`、授权结果、Workspace 状态或 capability/grant。这些数据的生命周期和消费者不同，将它们塞入公共身份模型只会迫使大量不需要关联 ID 的代码携带伪字段。

领域载体通过组合而不是继承来增加局部坐标：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ChatRun:
    identity_scope: IdentityScope
    interaction_id: str


@dataclass(frozen=True)
class InteractionSubmission:
    identity_scope: IdentityScope
    interaction_id: str
    payload: InteractionPayload


@dataclass(frozen=True)
class MemoryGenerationTaskSpec:
    identity_scope: IdentityScope
    request: GenerationRequest
    intent_id: str | None = None
```

规则如下：

- `interaction_id` 是 Chat/Interaction 领域的 canonical 关联 ID，只进入 `ChatRun`、`InteractionSubmission`、Perception journal 等真正消费它的对象；
- W0 不设计通用 `operation_id`。若解析、物化或其他领域确实需要局部操作标识，应使用 `parse_operation_id`、`materialization_id` 等明确名称并由该领域对象持有；
- 当前 `generation_id` 只是 Chat 控制面暴露的兼容句柄。W0 中一个 Chat Run 与一个 Interaction 保持 1:1，因此对外暂保留该字段时，其值必须由 `interaction_id` 只读派生，内部不再生成或保存第二份 generation 事实；
- Alice 的执行实例统一称为 `agent_run_id`，由 Alice 的 `RuntimeScope`/`RunSession` 持有，不进入 `IdentityScope`；
- `trace_id` 属于 observability 平面，`request_id` 属于 transport 平面，二者都不能参与 ownership、授权、资源过滤或业务幂等；
- `ActorIdentity.user_id` 表示执行者，`WorkspaceIdentity.owner_user_id` 表示资源域 owner；二者相等是 W0 的访问条件，不是可互相覆盖的别名；
- Agent/Team 是 actor policy 轴，Workspace 是 asset ownership 轴；二者正交；
- `IdentityScope` 创建后递归不可变；切换 Actor 或 Workspace 必须创建新对象，不能修改旧实例；
- 子 Frame、MTP 和后台 work 必须继承相同的 `IdentityScope`；只能缩小资源选择或重新计算授权结果，不能改写身份字段或切换 Workspace；
- `IdentityScope` 是身份坐标，不是永久 capability token，最终资源所有者仍要重验。

`IdentityScope` 的传播与组件命名域是两条独立设计轴。W0 增加以下硬约束：

- `IdentityScope` 只用于边界授权、资源 ownership/provenance 输入和领域 DTO 序列化；
- 任何 cache、registry、queue、scheduler、runtime、event bus 或 service container 都不得直接以 `IdentityScope` 为 key；
- 不得以 `scope_fingerprint`、`actor_identity + workspace_identity` tuple 或从完整 IdentityScope 派生的 hash 规避上一条约束；
- `ordering_key`、`idempotency_key`、`correlation_id`、run/task registry key 继续由各自领域 ID 决定，不从 IdentityScope 派生；
- 已明确为 Workspace-owned 的资源，可以在最终资源 owner 内从 `IdentityScope.workspace_identity` 构造规范 `WorkspaceIdentity`/resource key；这是资源寻址，不代表持有该资源的引擎、queue 或 cache 本身进入 Workspace 命名域；
- `RuntimeEvent.workspace_id` 是已实现的可选字符串投影，只用于观测；EventBus、subscription、sequence 与 event routing 不按该字段分区。

统一的 Workspace 归属硬边界为：

```text
Allowed
  = actor_can_enter_workspace
  AND resource.workspace_identity == identity_scope.workspace_identity
  AND resource_specific_actor_policy_if_defined(identity_scope.actor_identity)
```

W0 的 `actor_can_enter_workspace` 暂由 same-owner 不变量满足；未来可以替换为显式 Workspace grant，但不能改变资源 ownership。Memory v2 继续在前两项通过后执行 `PUBLIC | PRIVATE | TEAM` actor read policy；WorkspaceAsset 在 W0 不定义 visibility 或 Agent/Team policy，因此第三项恒为通过，同一 Workspace 内不同 Agent/Team 的访问结果一致。任何 `same_agent`、`same_team`、opaque ID、cache hit 或 Artifact URI 都不能绕过前两项硬边界。

### 4.3 默认解析与失败规则

默认 `main_workspace` 只允许在 HTTP、Passive ingress 或其他顶层 adapter 进入应用服务时解析。W0 的公共 Chat 产品面可以继续不暴露切换 UI；如果传输 DTO 预留 `workspace_id`，只使用这一规范名称，并在没有已知 Workspace/内部测试入口时拒绝非默认值，不从 `workspace_key` 推导。

进入会读取、写入或授权已裁定 Workspace-owned resource 的内部边界后，缺少完整 `IdentityScope` 必须返回稳定错误或抛出受控领域异常。只有具体领域接口需要关联 ID 时，才额外校验该领域字段：

- Gateway process；
- Patchouli prepare/retrieve/finalize；
- Alice run/frame/MTP；
- Topic、Memory、Artifact、WorkspaceAsset 读写；
- 对 Topic、Memory、Artifact、WorkspaceAsset 产生副作用的领域 handler attempt。

纯计算阶段、actor-only policy、cache 容器、通用 Work Queue 与 RuntimeEvent infrastructure 不因为位于同一调用链就必须接收或解释 `IdentityScope`。领域 task payload 已在 P2.5 中携带 IdentityScope 时，通用 queue 只把它视作 opaque bytes。

禁止共享 Runtime、Service、Store 或 Familiar 保存进程级 `current_workspace`。ContextVar 只可用于日志关联，不能作为授权输入。

## 5. 目标架构与所有权

```text
HiveMemorySystem
  ├─ one GatewaySystem
  ├─ one PatchouliSystem
  │    └─ one MemoryLibrary
  ├─ one AliceSystem
  ├─ one WorkspaceRuntime                  # 可选的极薄聚合
  │    └─ one WorkspaceAssetStore          # System-owned
  ├─ one Local Work Queue Runtime
  └─ one RuntimeEventBus

request/run
  └─ immutable IdentityScope
       ├─ ActorIdentity
       └─ WorkspaceIdentity

domain carriers
  ├─ ChatRun / InteractionSubmission + interaction_id
  ├─ MemoryGenerationTaskSpec + intent_id
  └─ Alice RuntimeScope + agent_run_id/frame_id/action_id
```

### 5.1 权威所有者

| 状态 | 权威所有者 | W0 责任 |
|:---|:---|:---|
| 默认 Workspace 解析 | System application boundary | 构造并验证 WorkspaceIdentity 与 IdentityScope |
| WorkspaceAsset、representation、parse state、lease | System WorkspaceAssetStore | 进程内 working set、状态和可用性真相；System shutdown 最后统一关闭并清空 |
| TopicAssetBinding | Patchouli ShortTermMemoryStore / SemanticBuffer | Topic 内幂等关联与 Topic 生命周期清理 |
| Memory 与检索 policy | Patchouli / MemoryLibrary | 持久归属、Workspace hard filter、actor read policy |
| Artifact 与 provenance | Patchouli / ArtifactStore | 持久归属、append-oriented 证据访问 |
| Run/Frame/MTP | System control / Alice | 保存不可变 IdentityScope，并由各自领域载体保存必要的执行/关联 ID；不取得资产所有权 |
| WorkRecord | Local Work Queue Runtime | 只持有机械执行状态与 bytes；不解析 IdentityScope，也不以其派生 key |
| RuntimeEvent | 事件生产域 | 可选投影 workspace_id 供观测；EventBus 不按该字段路由或分区 |
| Atom/Profile 等 cache | 现有 runtime owner | 保持既有 key、ownership 和生命周期；W0 不做 Workspace 命名域迁移 |

### 5.2 组合约束

推荐新增：

```text
src/hivememory/core/models/identity.py
  ActorIdentity
  WorkspaceIdentity
  IdentityScope

src/hivememory/core/models/workspace.py
  Workspace / WorkspaceKind / WorkspaceStatus（仅保留 MVP 必需字段）

src/hivememory/core/models/workspace_asset.py
  WorkspaceAssetRef
  WorkspaceAssetState
  AssetRepresentationState
  AssetRepresentationKind
  read-only snapshots / lease DTOs

src/hivememory/system/runtime/workspace/
  runtime.py
  store.py
  ports.py
  errors.py
```

`SystemAssembler._build_runtime()` 构造唯一 Store。实现可以选择 `_RuntimeBundle.workspace_runtime`，也可以暂时使用 `_RuntimeBundle.workspace_asset_store`；选择标准是依赖最窄、生命周期清晰。cache、registry、queue、EventBus 和 service 不进入 WorkspaceRuntime，也不以 IdentityScope 分区。

Store 的生命周期由 `HiveMemorySystem` 编排，而不是由 Patchouli、controller 或 Topic 反向持有。正常 shutdown 必须先停止资产消费者并完成 Patchouli 的 Topic shutdown settlement 与 generation drain，最后才关闭并清空 Store；不得为了接入 AssetStore 修改 memory generation controller 的 `wait_all` 语义，也不得让 Store 查询 Topic 或 binding。

HiveMemorySystem/WorkspaceRuntime 不得成为 service locator。消费者只接收 `WorkspaceAssetReader`、命名 command port 或 Topic binding cleaner 等窄接口。

## 6. 数据模型与运行时契约

### 6.1 资源身份投影与 Memory 唯一 ownership

领域内使用 `WorkspaceIdentity`；持久化或索引层可平铺：

```text
owner_user_id
workspace_key
workspace_id
```

这些字段必须从同一 `WorkspaceIdentity` 原子投影。对 `MemoryAtom` 而言，`workspace_id` 表示“该 Memory 归属于这个 Workspace”，不是“允许这个 Workspace 访问”；跨 Workspace 共享以后必须通过独立 grant/mount/ref 表达，不能把单值 `workspace_id` 改造成 ACL。

`MemoryAtom` 的领域模型只承认 `workspace_identity` 为持久化 ownership 权威。索引或存储 adapter 可以将其平铺为 `owner_user_id + workspace_key + workspace_id`，但平铺字段不能各自成为事实来源。新领域对象不得同时保留含糊的 `user_id`、独立 `owner_user_id` 和 `workspace_identity.owner_user_id`；历史 `meta.user_id` 只由 legacy decoder/filter 解释。

`source_agent_id`、`source_team_id` 只记录 provenance；`visibility` 及其 target 字段只记录 Workspace 内 actor read policy。二者均不能代替资产归属，也不能相互代替。

W0 新写入的 Memory、Artifact 和 Topic 必须具有完整 WorkspaceIdentity 投影。遇到只存在部分 Workspace 字段的记录视为歧义数据：拒绝纳入第二 Workspace，并记录可观测诊断，不能猜测补齐。领域 work payload 可以序列化 P2.5 已落地的 IdentityScope，但该投影只供 handler 恢复授权/ownership 输入，不是 queue 的资源归属或分区字段。

### 6.2 Memory schema v2 与 actor read policy

实施 P2 时必须将 `MemoryAtom.schema_version` 正式调整为 `2`。这是领域/持久化契约版本，与现有用于乐观锁或内容演化的 `meta.version` 不同；二者不得复用或互相递增。v2 冻结三套互不覆盖的语义：

```text
Memory ownership
  workspace_identity: WorkspaceIdentity

Memory provenance
  source_agent_id
  source_team_id?

Memory read policy
  visibility: PUBLIC | PRIVATE | TEAM
  target_agent_id?
  target_team_id?
```

其中 visibility 的参照系固定为 owning Workspace 内部：

```text
PUBLIC
  -> 对所有已经获准进入 owning Workspace 的 actor 可读

PRIVATE
  -> 仅 target_agent_id 匹配的 actor 可读

TEAM
  -> 仅 target_team_id 匹配的 actor 可读
```

`PUBLIC` 不是跨 Workspace 或系统全局公开；它只有在 ownership hard filter 与 Workspace entry authorization 通过后才生效。`PRIVATE` 和 `TEAM` 同样不能凭 agent/team 匹配绕过 Workspace。read policy 只授权检索、读取和进入上下文，不自动授权更新、删除、变更 visibility 或转移 ownership。

provenance 与 authorization target 必须分离。创建时可以默认令 `PRIVATE.target_agent_id = source_agent_id`、`TEAM.target_team_id = source_team_id`，但后续调整策略不得篡改创建来源。v2 应强制以下不变量：

```text
PUBLIC  -> target_agent_id is None AND target_team_id is None
PRIVATE -> target_agent_id is not None AND target_team_id is None
TEAM    -> target_agent_id is None AND target_team_id is not None
```

W0/P2 为保持现有创建行为，将未显式指定的 read policy 规范化为 `PUBLIC`；该默认值必须由 Memory builder 显式写入 v2 记录，不能依赖模型反序列化的隐式缺省。`TEAM` 在 MVP 中以 `actor_identity.team_id == target_team_id` 判定，未来如果引入多组 membership，应替换 policy evaluator，而不是改变 Memory ownership。

历史序列化映射调整为：

```text
v1 PRIVATE
  -> v2 PRIVATE(target_agent_id = v1.source_agent_id)

v1 WORKSPACE
  -> v2 TEAM(target_team_id = v1.team_id)

v1 PUBLIC
  -> v2 PUBLIC
```

所有映射都原样保留 v1 `source_agent_id`，并将 v1 `team_id` 投影为 v2 `source_team_id`。对旧 `WORKSPACE` 记录，同一个历史 `team_id` 会同时初始化不可变的 `source_team_id` 与可演化的 `target_team_id`；进入 v2 后二者不再联动。

如果 v1 `PRIVATE` 缺少 `source_agent_id`，或 v1 `WORKSPACE` 缺少有效 `team_id`，compatibility decoder 不得制造默认 target；该记录应 fail closed 并进入迁移诊断/人工处置清单。

不再引入目标 `WORKSPACE` visibility。W0/P2 在线主链路先增加 ownership hard filter，并通过命名的 v1 compatibility adapter 解释旧值，不在业务代码中散落字符串判断。新写入直接生成 schema v2；既有 v1 的批量回填仍在 W0 隔离验收后执行。在 adapter 被移除前，不能仅凭字符串 `WORKSPACE` 解释新语义。

这里的“新写入”同时包括 CREATE 与 UPDATE。更新 v1 Memory 时，repository/decoder 先将其归一化为 v2 领域对象，Mutation 保留归一化后的 Workspace ownership，再以 schema v2 写回；不得继续输出 v1 或将当前 updater 的 Workspace/actor 覆盖为新的 owner/source。

版本分派必须 fail closed：缺少 `schema_version` 的历史记录按 v1 送入 compatibility decoder；`schema_version == 2` 必须满足完整 WorkspaceIdentity 与 policy 不变量；未知版本拒绝进入领域模型并记录诊断。任何版本中的部分 Workspace 投影都不能根据 active Workspace 猜测补齐。

检索在领域层首先要求 `memory.meta.workspace_identity == identity_scope.workspace_identity`。Qdrant/storage adapter 为建立索引可以对同一值对象使用以下平铺预过滤：

```text
payload.meta.owner_user_id == identity_scope.workspace_identity.owner_user_id
AND payload.meta.workspace_id == identity_scope.workspace_identity.workspace_id
```

这些 payload 字段是 adapter projection，不是另一套领域 owner。若某种持久化格式同时保存嵌套 identity 与平铺索引字段，decoder 必须验证二者完全一致；不一致时拒绝读取。ownership hard filter 通过后才应用 v2 actor read policy，`PUBLIC` 也不能绕过该边界。

### 6.3 历史记录 compatibility-read

脚本执行前，只允许以下兼容投影：

```text
访问 user U 的 main_workspace：
  current = owner_user_id == U AND workspace_id == "main_workspace"
  legacy  = user_id == U AND owner_user_id missing AND workspace_id missing
  result  = current OR legacy

访问 user U 的任意第二 Workspace W：
  result = owner_user_id == U AND workspace_id == W
```

兼容投影只存在于 storage adapter/filter builder。领域模型、cache、work handler 和 retry 不能把缺字段记录自动解释为当前 active Workspace。legacy decoder 将 v1 `meta.user_id` 解释为历史 resource owner，并且只在对应用户的 `main_workspace` 中归一化；它不能把该字段继续解释为 actor ownership。归一化后的领域对象只暴露一份 canonical `WorkspaceIdentity`。

### 6.4 Topic 资源键

`SemanticBuffer` 与 `TopicData` 增加 WorkspaceIdentity 投影。Short-term port/store 的权威资源键从裸 `topic_id` 收紧为：

```text
(owner_user_id, workspace_id, topic_id)
```

所有 get/list/create/pop/exists/compact/evict 路径接收规范 `IdentityScope` 或已经验证的 `WorkspaceTopicKey`。只读 `TopicSnapshot` 至少保留足以在应用层重验 owner/workspace 的字段。裸 topic ID 仍可作为展示或路由标识，但不是授权凭证。

### 6.5 Artifact 资源键

`BaseArtifact`、`ArtifactRef` 的内部投影和 Artifact builder 输入补齐 Workspace 归属。ArtifactStore 的读取接口必须带规范 `IdentityScope`，或明确标记为已经由 Patchouli 内部 provenance 流程验证的窄调用；不能通过 artifact ID 或 `ArtifactRef.uri` 直接获得读取权限。

filesystem adapter 至少完成：

- 物理路径或索引按 owner/workspace 分区；
- 以 `(owner_user_id, workspace_id, artifact_id)` 查找；
- 同 ID 不覆盖另一 Workspace 的 Artifact；
- 调用方提供的 URI 不作为授权或任意文件读取入口；
- 历史无 Workspace 字段 Artifact 只在对应用户 `main_workspace` 的兼容读取中可见。

W0 不实现 DocumentArtifact promotion，但必须保证已有 Interaction/Memory Artifact 不会跨 Workspace 读取。

### 6.6 共享基础设施与异步 Task DTO

W0 不修改 AtomCache、ProfileCache 或其他 cache 的 key、ownership 和生命周期。cache 是非权威加速结构，不因缓存了 Workspace-owned resource 就自动成为 Workspace 命名域。现有 cache key 保持其当前 actor/run/alias/UUID 语义；如某次命中最终进入已裁定的 Workspace-owned resource 操作，权限与 ownership 仍由最终资源 owner 按资源自身的 `WorkspaceIdentity` 重验，不能把 cache hit 当作授权结果。

可重试的 Interaction 与 Memory Generation 任务不再建立第二套工作作用域，而是在具体领域 DTO 中保存同一种 `IdentityScope` 及该领域实际消费的关联 ID：

```text
InteractionSubmission
  identity_scope: IdentityScope
  interaction_id: str
  payload: InteractionPayload

MemoryGenerationTaskSpec
  identity_scope: IdentityScope
  request: GenerationRequest
  intent_id: str?
  ...domain payload

admission
  -> versioned codec encodes the complete domain DTO
  -> WorkItem.payload owns detached JSON bytes
  -> each attempt decodes the same IdentityScope and domain IDs
```

`IdentityScope` 是这些任务唯一的身份事实，codec 只是完整领域 DTO 在异步边界上的版本化投影，不产生新的身份语义。`InteractionSubmission` 需要 `interaction_id`，因此显式保存；`MemoryGenerationTaskSpec` 使用现有 `intent_id`、`task_id`、`work_id` 等各层局部坐标，不能为了统一外形再发明通用 `operation_id`。Memory 和 Artifact 只从 `identity_scope` 派生 ownership 与 actor provenance；`GenerationRequest` 只表达内容与生成意图，不再携带 `MemoryCreationContext` 或第二份权限字段。

P2.5 已完成上述 DTO 字段迁移，P3 不回滚。P3 返工只撤销 IdentityScope 对 queue 命名域的影响：`work_id`、ordering、idempotency、correlation 和 lane 仍使用既有领域规则，不能加入 IdentityScope、scope fingerprint 或 workspace 前缀。handler 每次 attempt 可以从 payload 解码原 DTO，并在真正访问 Workspace-owned resource 时重新授权；通用 `WorkItem`、`WorkRecord` 与 WorkExecutionContext 始终不理解 Workspace 领域模型。

## 7. WorkspaceAssetStore 契约

### 7.1 模型

```text
WorkspaceAsset
  asset_id
  workspace_identity
  kind
  display_name
  media_type
  size_bytes
  required_representation_kind
  representations[]
  state
  safe_error_code?
  safe_error_message?
  created_at

AssetRepresentation
  representation_id
  workspace_identity
  asset_id
  kind
  revision
  content_object
  content_hash
  producer
  producer_version
  parse_operation_id?
  state

WorkspaceAssetRef
  token
```

WorkspaceAsset 在 W0 不保存 `created_by_agent_id`、`created_by_team_id` 或 `visibility`，也不定义 Agent/Team read policy。同一 Workspace 内的 actor 在通过 Workspace 归属硬边界后具有相同的资产访问结果；后续附件上传功能如需要更细策略，必须在独立计划中根据产品语义重新裁定，不能从 Memory visibility 直接复制。

用户未来只持有 opaque `WorkspaceAssetRef`。`token` 是当前进程、当前 Store 存活期内随机且不可解释的句柄；文件名、asset ID、representation ID、content hash 和 token 本身都不是授权凭证。Store 解析 token 后仍要按调用方 `IdentityScope.workspace_identity` 重验资源归属，调用方不能依赖 token 的格式或把它解释为可持久化资源身份。

### 7.2 两级状态机

```text
AssetRepresentation
  PENDING -> PROCESSING -> READY
                        -> FAILED

WorkspaceAsset
  PROCESSING -> READY
             -> FAILED

  PROCESSING / READY / FAILED -> REMOVED
```

规则：

- RAW 可以在注册时 READY；
- 文档型资产的 required representation 固定为 `EXTRACTED_TEXT`；
- RAW READY 不能单独令 WorkspaceAsset READY；
- required representation 进入 READY/FAILED 与 WorkspaceAsset 聚合状态进入 READY/FAILED 必须在同一个 Store 临界区内提交；任何 reader/snapshot 都不能观察到 representation 已终态而 asset 仍停留在旧状态的中间结果；
- FAILED 不自动 retry；用户重新上传将创建新的逻辑 asset identity 和 asset ID；
- READY 冻结 content object、hash、producer/version 和 revision；
- parse result 必须带预期 revision 或 operation token；token/revision 校验、representation 更新和 asset 聚合更新必须属于同一次原子命令；
- REMOVED 是不可逆终态。进入 REMOVED 后，register/start/complete/fail 等 representation 命令均不得再改变资产或表示状态，重复 remove 只返回同一权威终态；REMOVED 记录因活跃 lease 暂未物理回收，也不能恢复 resolve/selection/lease；
- complete/fail 与 remove 并发时以同一临界区内的提交顺序线性化：结果先提交时允许随后进入 REMOVED，remove 先提交时晚到结果必须被拒绝；不得出现部分提交或从 REMOVED 复活；
- 只有 READY asset 可 resolve、selection 或 acquire lease。binding 不是 AssetStore 状态转换，它只在成功 Interaction commit 时记录已经由 lease 支撑的真实使用事实。

W0 不运行真实 parser。测试通过 Store 命名 command 构造 PENDING/PROCESSING/READY/FAILED 转换，不得直接改对象字段。

### 7.3 最小命名接口

Store/port 至少提供语义等价的命名能力：

```text
create_asset(identity_scope, metadata, client_operation_id)
register_raw_representation(...)
start_representation(...)
complete_representation(..., expected_revision_or_token)
fail_representation(..., safe_error)
resolve_asset(identity_scope, asset_ref)
list_workspace_assets(identity_scope)
acquire_ready_representation(identity_scope, asset_ref, preference)
release_representation_lease(lease_id)
remove_asset(identity_scope, asset_ref)
```

具体名称可在实现 PR 中按代码风格调整，但不能退化为暴露内部 dict 或可变模型。

这些 port 接收 IdentityScope 只为了在资源 owner 边界验证 Workspace 归属；W0 不根据 `actor_identity.agent_id` 或 `team_id` 检查 WorkspaceAsset visibility。Store 内部只使用 `WorkspaceIdentity + asset_id` 等已经冻结的 WorkspaceAsset resource key；不得把完整 IdentityScope、actor+workspace tuple 或 scope fingerprint 作为 Store 分区 key。

### 7.4 幂等、删除与 lease

进程内上传/创建幂等键预留为：

```text
owner_user_id + workspace_id + client_operation_id
```

该幂等关系属于 WorkspaceAsset command 自身，不是通用组件分区。实现时规范化为 `WorkspaceIdentity + client_operation_id`；actor 不进入分隔 key，也不进入 WorkspaceAsset metadata。同一 Workspace 内不同 actor 复用同一 operation 时，等价输入返回同一资产及权威状态，不等价输入返回 `AssetOperationConflictError`。相同 content hash 只允许内容对象去重，不能合并两个用户层面的逻辑资产。

删除顺序固定为：

1. AssetStore 原子将资产置为 REMOVED，立即拒绝新的 resolve/selection/lease；重复 remove 幂等返回同一 REMOVED 终态；
2. 删除不回调 Patchouli、不查询 Topic，也不清理 `TopicAssetBinding`；binding 继续表示资产曾被该 Topic 的成功 Interaction 真实使用过；
3. 无活跃 lease 时释放内容对象；已有 lease 保持到进行中消费者释放；
4. 最后一个 hold 释放后再物理回收 representation。

因此 asset remove 只有 AssetStore 自身的线性化点，不存在 `asset REMOVED -> binding
cleanup` 跨 Store 事务、补偿或控制器。binding 不能作为当前可用性或授权结果；任何希望
再次读取内容的消费者仍须通过 `asset_ref` acquire，并由 AssetStore 对 REMOVED ref 稳定
拒绝。历史关系仍可通过 Topic binding read model 观察，不把它称为需要清理的 dangling
relation。

W0 lease 是当前 Store 存活期内的进程内 hold，不实现 durable tombstone。显式 remove 后可以在 Store 内暂时保留 REMOVED 记录，用于拒绝晚到 callback 并等待已有 lease 释放；该记录不跨 shutdown。shutdown 是全部 WorkspaceAsset 与 ref 生命周期的终点，新进程从空 Store 开始，不继承任何 WorkspaceAsset、representation、lease、幂等记录或 ref 索引，也不定义 Store incarnation、ref expiration 或 restart recovery 契约。用户若要再次使用内容，必须重新上传并取得新的资产与 ref。

### 7.5 Shutdown 顺序与清理

WorkspaceAssetStore 不判断资产是否曾被 Topic 使用，也不触发 Topic settlement。是否使用、如何 binding、何时 materialize 属于 P5 及后续附件链路；P4 只服从 System 已完成上游 drain 的生命周期信号。

正常 `HiveMemorySystem.stop()` 的相对顺序固定为：

1. 停止 scheduler、passive ingress 等新工作来源，并完成已接纳输入的 drain；
2. 停止 Alice，确保 Agent 侧不再创建新的资产消费者；
3. 调用 `PatchouliSystem.stop()`，等待 interaction/active finalize，执行所有活跃 Topic 的 shutdown settlement，并等待由此产生的 memory generation；
4. 停止 Gateway 等剩余消费者；
5. 最后调用 Store 内部生命周期方法 `close_and_clear()`，原子拒绝后续命令并清空 asset/representation 记录、opaque ref 索引、创建幂等索引、operation token、REMOVED 记录、lease bookkeeping 和 Store 持有的 content object 引用；
6. 只有上述步骤完成后，System 才报告 `STOPPED`。

`close_and_clear()` 不属于注入给业务消费者的 Reader/Command port，并且必须幂等。不得在 Patchouli shutdown settlement 或 generation drain 之前清空 Store，否则最终结算可能失去仍需读取的 representation；也不得让 Store 自己等待 controller、调用 `wait_all` 或查询 Topic binding。逐 Topic 隔离后的 automatic admission failure 必须先被记录，再继续后续 Topic、已接纳任务 drain 与最终 Store teardown，不能让单点失败把 System 留在半停止状态；最终对外投影为 `completed_with_errors` 还是在 teardown 后抛聚合异常，由独立 shutdown TODO 冻结。其他尚未隔离、导致消费者安全停止或 drain 未完成的上游异常，不得通过提前清空 Store 伪装成有序停止成功。实际进程退出仍会自然释放全部内存。W0 不为同一个已经停止的 `HiveMemorySystem` 增加 Store reopen/restart 语义，新进程必须重新装配空 Store。

## 8. TopicAssetBinding 契约

### 8.1 所有权与模型

```text
TopicAssetBinding
  asset_id
  asset_ref
  first_bound_interaction_id
  bound_at
```

`TopicAssetBinding` 是冻结的最小关系值对象。`workspace_identity` 与 `topic_id` 由所属 `SemanticBuffer` 提供，不在 binding 内保存第二份可漂移的资源坐标；`asset_ref` 保存当前 Store 存活期内的 opaque `WorkspaceAssetRef`，`asset_id` 用于关系唯一性。`first_bound_interaction_id` 固定第一次成功完成且显式使用该资产的 Interaction；`bound_at` 记录该事实首次提交的时间。binding 不保存完整
`WorkspaceAsset`、representation 或 content object 快照，历史 READY snapshot 也不能作为后续读取或授权依据。

`TopicAssetBinding` 是 Topic 级“真实使用过”的权威事实，不是待选资产、最近上传资产或 UI selection cache。关系只能由一轮成功完成的对话产生：用户在该轮显式选择了 READY `asset_ref`，对话最终成功摄入唯一 Topic 后，系统才提交 binding。同一 Topic 后续再次使用同一资产只幂等命中既有关系，不覆盖首次 Interaction 或首次绑定时间。后续 `ContextAttachmentUse` 可以补充 representation revision、locator、token 数量和 compile 诊断，但不能成为一套与 binding 竞争“是否使用过”的第二真相源。

W0 不在 binding 上保存 `bound_by` 或 actor-policy 字段。若后续确有审计需求，应从 `first_bound_interaction_id` 关联 Interaction provenance，不能把 actor 字段用于同一 Workspace 内的访问控制。

binding 跟随 `SemanticBuffer`，由 `ShortTermMemoryStore` 的命名方法维护：

```text
apply_interaction(
  identity_scope,
  topic_id,
  interaction_id,
  block,
  asset_id_and_refs,
  model_used?,
)
list_asset_bindings(identity_scope, topic_id)
```

唯一性为 `(owner_user_id, workspace_id, topic_id, asset_id)`。同一 Topic 的写入由单写者状态
串行化；后续 Interaction 重复使用同一资产只命中既有关系。调用方不能直接修改 buffer
内列表。

`ShortTermMemoryStore` 只管理关系，不接收或保存可过期的 `WorkspaceAsset` snapshot。
本轮实际使用前，上层必须用同一次 Interaction 冻结的 `IdentityScope` 通过
`WorkspaceAssetReaderPort.acquire_ready_representation()` 建立 lease，并确认 lease 中
的 `asset_id` 与提交给 `apply_interaction()` 的关系事实一致。binding commit 不再次调用
AssetStore 做 READY 检查，避免把已经完成的真实使用重新解释成一项跨 Store 原子写入。
面向消费者的 binding list/read 同样不能把 raw binding 当作当前可用性或授权结果；若要
再次读取内容，必须通过 `asset_ref` 重新 acquire。REMOVED、未知或跨 Workspace ref 不得
因历史 binding 恢复可用性。

新建 WorkspaceAsset 以零 binding 开始，此时属于关系图中的合法 orphan：它不是失败
资产，也不因此自动回收，但尚未被任何 Topic 对话使用。W0 的 create/register 操作
不得根据“刚上传”“当前活跃 Topic”或进程级 pending list 自动建立关系；上传本身不等于
使用。W0 没有真实 `asset_refs` 请求，因此测试或内部 walking skeleton 必须先通过 Store
acquire READY representation 并持有 lease，再以一轮成功 Interaction 的显式使用输入
提交 block 与 binding；不允许为了测试绕过 acquire 或直接给空 Topic 挂关系。

### 8.2 建立时机与前置约束

从领域语义看，binding 在一轮对话成功结束后才出现；从实现原子性看，该关系必须与本轮 `LogicalBlock` 在同一个 interaction commit 中写入 SemanticBuffer，并且早于 token-overflow compact 或任何后置 settlement payload 的冻结。不得先独立提交 block，再由外围异步补写 binding。建立新关系时必须同时满足：

- 目标 Topic 在当前 Workspace 中仍然存在；
- `apply_interaction()` 携带本轮完整 `LogicalBlock`，提交后的 buffer 必须满足
  `has_blocks=True`；不要求 Topic 在本轮 commit 之前已有历史 block；
- `asset_ref` 已按上一节通过当前 `IdentityScope` acquire READY representation，并由本轮
  实际消费持有 lease；
- 当前 Interaction 携带用户显式选择且已被本轮使用的资产 ref，不允许通过“最近上传”、
  “最后活跃 Topic”或全局 pending list 猜测关系；
- `interaction_id`、本轮 block 与全部 binding 输入进入同一次原子 apply；现有
  `InteractionApplyJournal` 负责在 retry 时识别该 apply 是否已经完成：等价 retry 不再
  调用 Store 重写，不一致 retry 报冲突，不存在 block 已写而 binding 等待后置补全的状态。

Topic 不存在时不得因 binding 输入隐式创建或恢复 Topic；任何不携带本轮完整 block 的
独立 binding 命令都必须拒绝。新建的空 Topic 或只有历史 `state_summary` 的 Topic 可以在
接收新的成功 Interaction 时，由同一个 commit 同时写入新 block 与 binding。compact 已
强制至少保留一个最近 block，因此已建立 binding 的正常 Topic 在 compact 后仍继续保留
关系。

`clear_blocks` 只是 settle 内部的瞬时步骤，不是对外公开的 Topic 生命周期操作；不得新增或保留一个长期存在的“无 blocks、无 state summary、只有 binding”状态。现有 `SemanticBuffer.clear()` 不作为 P5 binding 生命周期入口，计划中也不再定义独立的 reset-content 行为。

### 8.3 SemanticBuffer 单写者保护与原子命令

P5 不把同一 Topic 的并行写入作为产品能力。当前 W0 是单进程内存实现，active Interaction
已经按 Topic ordering key 排队，正常单用户对话也不会要求两轮 Interaction 同时修改同一
buffer；因此不为极端交错实现乐观并发、版本号 CAS 或冲突重算。真正需要防止的是
Interaction、manual settle/delete/compact 与后台 IDLE/LRU 维护在异步边界交错，造成冻结
之后继续写入、旧快照清除新内容或 Topic pool/index 不一致。

`blocks`、binding、state summary、token 计数、metadata、Topic pool 索引和 last-active
索引都属于同一个 `SemanticBuffer` 聚合的可变状态。binding 不建立独立锁或控制器；
`ShortTermMemoryStore` 是唯一同步与变更边界，并采用“同一 Topic 同一时间只有一个写入者”
的状态预约：

```text
IDLE -> PROCESSING -> IDLE
IDLE -> FLUSHING -> IDLE | EVICTED
IDLE -> freeze + EVICTED
```

- Interaction 在本地 apply/compact 阶段占用 `PROCESSING`；manual compact 也必须先从
  `IDLE` 进入 `PROCESSING`。token-overflow compact 复用当前 Interaction 已持有的预约；
- `PROCESSING` 期间仍允许冻结读取，但新的 Interaction、manual settle/delete/compact
  不得修改 Topic，应返回明确的 Topic busy/conflict；Interaction queue 将其分类为可重试
  瞬态失败，手动 API 投影为冲突响应；IDLE 维护跳过该 Topic，LRU 优先
  选择其他 `IDLE` 候选，若没有可驱逐候选则让新 Topic 创建返回可重试 busy；
- manual settle 在短临界区内执行 `IDLE -> FLUSHING` 并冻结 payload，锁外等待 queue
  admission；成功或正常 skip 后 evict，失败则恢复 `IDLE`。`FLUSHING` 期间拒绝其他写入，
  重复 manual settle 也不能再次冻结一份 payload；
- automatic IDLE/LRU settle 只接受 `IDLE` Topic，并在一个短临界区内冻结
  blocks/state summary/binding refs、移除 buffer、修正 last-active/index，queue admission
  留在锁外；检测到 `PROCESSING/FLUSHING` 时跳过或改选候选；
- SHUTDOWN 不依赖“跳过 busy Topic”完成清理。既有停止顺序必须先停止新工作并 drain
  Interaction/active finalize，再进入 shutdown settlement；此时仍有 busy Topic 表示停止
  顺序或状态释放存在缺陷，应显式报告，不能由最终 Store clear 静默吞掉。

当前 `InMemoryShortTermStorage` 的 `RLock` 只保护底层复合键字典；P5 在 Store 层增加一把
`threading.RLock`，并让 buffer/index port CRUD、buffer 字段读写、状态预约与辅助索引更新
都在该锁内完成。锁顺序固定为 Store lock 在外、adapter lock 在内；不得绕过 Store 直接
调用 port。第一版使用单一 Store lock，不引入 per-topic lock registry；临界区只执行内存
检查和修改，锁内禁止 `await`、总线请求、摘要生成、AssetStore 调用或其他外部 I/O。

所有公开 read/list 方法在锁内构造冻结的 `TopicData` 或专用 snapshot；`SemanticBuffer`
不得越过 Store 边界，`create_buffer()`、`pop_buffer()` 等接口也不能向调用方返回仍可修改
的 buffer。Store 的公开写能力按有限的状态语义收敛，而不是为每个上游消费者复制一套
流程：

1. 预约或释放 `PROCESSING`；
2. 在一个临界区内 `apply_interaction()`，原子追加本轮 `LogicalBlock`、首次 bindings、
   token/model metadata 与 last-update；
3. 在已持有 `PROCESSING` 时冻结 compact 输入，并在锁外生成 summary 后回到锁内应用
   compact 结果；由于期间禁止其他写入，不需要 `content_revision`、CAS 或重算循环；
4. automatic settlement 的原子 freeze-and-evict；
5. manual settlement 的 `FLUSHING` prepare，以及 admission 后的 commit/abort。

不涉及查找、锁和辅助索引的纯字段变换可以作为 `SemanticBuffer` 内部方法；Store 负责在
锁内找到正确 buffer、验证状态、调用变换并同步索引。上层 Perception/Trigger 仍负责摘要、
总线、queue admission 与策略，不得把这些外部流程搬进 Store。

Interaction retry 继续由现有 `InMemoryInteractionApplyJournal` 承担，不在 Store 或
SemanticBuffer 内增加 `InteractionApplyReceipt`。P5 将 journal 的 `BLOCK_APPLIED` 语义
扩展为 `INTERACTION_APPLIED`，并保存 `topic_id + input_digest`：digest 覆盖可稳定重建的
canonical Interaction apply 输入，包括 payload 中形成 block 的事实、binding refs 和参与
原子 apply 的 metadata；不得纳入 retry 时重新生成的 `block_id`、`created_at`、`bound_at`
等随机值或时钟值。digest 只用于判断同一 `interaction_id` 的 retry 是否等价，不可枚举为
used refs，也不参与 settlement 或“是否使用过”的查询。
等价 retry 根据 journal 继续未完成的本地/后置义务，不再调用 Store 重写；不同输入报冲突。
Store apply 与 journal 记录之间不得插入 `await` 或外部 I/O；两者都是当前进程内状态，
进程退出后与 Topic 一同失效，不承诺崩溃恢复。Interaction Submission Queue 仍只负责
work admission 幂等，与 apply journal 的副作用恢复职责保持分离。W0 沿用 journal 现有的
进程内有界保留窗口，不把该保证扩张为无限期或跨重启幂等。

Store lock、`PROCESSING/FLUSHING` 和 apply journal 都是内部实现状态，不加入 HTTP 模型、
IdentityScope、queue partition 或公共 Workspace 命名域。只有实际观测到同一 Topic 并行
写入需求，且 `PROCESSING` busy 明显影响用户体验时，才重新评估 per-topic lock、
`content_revision` 或乐观 CAS；W0 不提前实现这些机制。

### 8.4 生命周期矩阵

manual settle/compact/delete 只从 `IDLE` 开始；token-overflow compact 在当前
Interaction 已持有的 `PROCESSING` 内完成；IDLE/LRU automatic settle 只驱逐 `IDLE`
Topic；SHUTDOWN 则依赖前置 drain 后全部 Topic 已经结束 busy 状态。下表描述成功取得对应
状态预约后的生命周期结果，不表示 busy 操作可以绕过 §8.3 的前置约束。

| 操作 | Topic 是否仍存在 | binding | WorkspaceAsset |
|:---|:---:|:---:|:---:|
| manual settle | 否 | 先冻结进 settlement payload；admission 成功或正常 skip 后随 buffer 清除 | 保留 |
| manual compact | 是 | 保留 | 保留 |
| token-overflow compact | 是 | 保留 | 保留 |
| IDLE/LRU settle/evict | 否 | 先冻结进 settlement payload，再随 buffer 清除 | 保留 |
| SHUTDOWN settle/evict | 否 | 先冻结进 settlement payload，再随 buffer 清除 | settlement/generation 完成前保留 |
| manual delete / 显式 evict/pop | 否 | 随 buffer 清除 | 保留 |
| WorkspaceAsset delete | Topic 可存在 | 保留真实使用事实；后续内容 acquire 由 AssetStore 拒绝 | REMOVED |
| System shutdown 最终 Store close | Topic/Patchouli 已停止 | 已随 Topic 生命周期清除 | 全部运行时记录与 ref 索引清空 |

binding 表示 Topic 至少有一轮成功对话真实使用过该资产。它本身不自动向后续 prompt
注入内容，也不在建立关系时创建 Artifact；Topic settlement 可以把全部 binding refs
作为已经使用过的资产事实冻结进任务，后续 Materialization 再用 ref 反查 Store、取得
READY representation 并在消费期间持有 lease。

### 8.5 Settlement 快照与 queue 责任边界

任何会结束 Topic 生命周期的 settle 都必须在清除 buffer 前，将 blocks、state summary
和当前全部 `TopicAssetBinding` 冻结进不可变 `TopicMaterializeTask`。task 至少携带
`asset_id + asset_ref`，进入 queue 后不再依赖 SemanticBuffer；后续 codec/retry 必须
原样保留 ref，不从当前 Topic 或 Workspace 最近资产重新推导。

manual settle 保留现有 `prepare -> admission -> evict` 用户可见语义：admission 抛错时
保留 Topic，允许用户重试。IDLE、LRU 与 SHUTDOWN 属于自动生命周期机制，保持
`freeze payload -> evict -> queue admission`：向 queue 提交失败不得把已预定离开的 Topic
重新插回池中，也不在 queue 外再建立一套 settlement retry/persistence 机制。queue
成功接纳后，执行重试、幂等与终态由既有任务机制负责；成功接纳前的异常必须作为
admission failure 观测，不能计入正常 generation skip。

自动 admission failure 仍不得使已经接纳的任务失去 drain：批处理或 shutdown 编排应
继续处理后续 Topic，并在结束前调用既有 controller `wait_all()`。这一要求只隔离失败
并完成清理义务，不恢复 buffer、不重放失败 payload，也不修改 controller 的通用语义。
由于 WorkspaceAsset/ref 只在当前 Store 存活期有效，本约定不产生跨进程 task 恢复承诺。

### 8.6 Asset bind/remove 跨 Store 竞态

P5 不为 AssetStore 与 ShortTermMemoryStore 增加共同锁、两阶段提交、补偿事务、cleanup
controller 或 System 协调服务。两个 Store 分别维护不同的权威事实：

| 所有者 | 权威事实 |
|:---|:---|
| WorkspaceAssetStore | asset/ref 当前是否可 resolve、selection 或 acquire，以及已有 lease 是否仍有效 |
| ShortTermMemoryStore | 成功 Interaction 是否真实使用过该 `asset_id + asset_ref` |
| RepresentationLease | remove 发生后，已经开始的消费者是否仍可完成本次内容使用 |

真实使用的线性化点是 AssetStore 的 lease acquire，而不是 binding commit：

```text
acquire READY representation
  -> 持有 lease 并把内容用于本轮 Interaction
  -> 成功 Interaction commit 原子写入 block + binding
  -> 释放本轮 lease
```

竞态结果固定为：

| 顺序 | 结果 |
|:---|:---|
| remove 先于 acquire | acquire 失败，本轮没有使用事实，也不建立 binding |
| acquire 先于 remove | 已有 lease 可完成本轮使用；Interaction 成功后建立 binding |
| acquire -> remove -> Interaction commit | binding 合法成立；它记录 remove 前已经发生的真实使用，但该 ref 后续不可再次 acquire |
| Interaction commit -> remove | binding 保留；remove 只终止后续可用性，不改写历史使用事实 |

因此 asset remove 不遍历 Topic、不删除 binding，也不存在 cleanup 部分失败。settlement task
仍可冻结历史 binding ref；若消费者开始 materialization 前资产已经 REMOVED，ref acquire
会失败。W0 不复制 representation 到 binding/task，也不为此持有 Topic 生命周期长 lease；
后续 Attachment/Artifact promotion 计划必须在“跳过该来源并记录诊断”和“令本次
materialization 失败”之间裁定。无论选择哪一种，都不能恢复 REMOVED asset，也不能把
历史 binding 当作当前读取能力。

## 9. IdentityScope 传播与分隔 key 边界

Active Chat 的规范顺序为：

```text
server adapter
  -> generate interaction_id
  -> build ActorIdentity
  -> resolve main_workspace
  -> validate owner/status
  -> freeze IdentityScope
  -> register ChatRun
  -> Gateway
  -> Patchouli prepare
  -> Alice run / child frame / MTP
  -> Patchouli finalize
  -> InteractionSubmission / Memory Generation work
```

| 当前落点 | W0 改造 |
|:---|:---|
| `server/models/chat.py`、`server/routers/chat.py` | 顶层默认解析输入；stop/status 携带并校验 owner/workspace，而非只信任 generation ID |
| `system/application/chat_service.py` | 生成唯一 `interaction_id`，冻结 `IdentityScope`，并向全链传递；旧 `generation_id` 只能作为该 ID 的兼容投影 |
| `system/runtime/control.py` | `ChatRun` 保存 `IdentityScope + interaction_id`；registry 只以 `interaction_id` 为 canonical key，不以 IdentityScope/scope fingerprint 分区 |
| `gateway/workflow/state.py`、`gateway/context.py` | state/snapshot 保存不可覆盖的 `IdentityScope`；Topic candidate/routing 使用 scoped read |
| `gateway/contracts/public_routes.py` | route payload 接收 `IdentityScope`，不重复拼装裸身份字段 |
| `patchouli/models.py`、`patchouli/service.py` | `PreparedAgentRun` 保存原始 `IdentityScope`；prepare/retrieve/finalize 复用同一对象 |
| `patchouli/contracts/public_routes.py` | 跨边界请求显式携带完整、不可变的 `IdentityScope` |
| `core/protocol/models.py` | `AgentRunContext` 保存 `IdentityScope`；`InteractionSubmission` 另带唯一 `interaction_id`，`InteractionPayload` 不再保存第二份身份事实 |
| `alice/application/agent_run_service.py` | root frame 从 AgentRunContext 继承 scope |
| `agent_runtime/models.py` | `ExecutionFrame`、`MTPExecutionContext` 保存相同 `IdentityScope`；运行坐标统一使用 `agent_run_id`、`frame_id`、`action_id` |
| child CALL/frame factory | 子 Frame 继承 hard boundary；context refs 只能缩小选择 |
| interaction/memory generation codecs | 完整序列化具体 Task DTO（含 IdentityScope 和必要领域 ID）并生成脱钩的版本化 bytes；IdentityScope 不进入 work/order/idempotency key |
| memory generation/materialization handler | 从解码后的 Task DTO 取得 `IdentityScope`，取得 Workspace ownership 与 actor provenance，重新授权后构造 schema v2；禁止以裸 ActorIdentity 推断 owner |
| RuntimeEvent producers | 已完成 metadata 的可选 workspace_id 与局部 ID 投影；只用于观测，EventBus 不按其分区 |

同一 Run 必须满足：

```text
Gateway IdentityScope
  == Patchouli prepare IdentityScope
  == Alice root/child frame IdentityScope
  == MTP IdentityScope
  == Patchouli finalize IdentityScope
  == InteractionSubmission/task IdentityScope
```

finalize 不再接收另一组可漂移的裸 `user_id/agent_id/workspace_id`。如果 prepare snapshot 与 control registry 的 scope fingerprint 不一致，Run 失败并禁止写入；fingerprint 只用于一致性诊断，不能成为 registry、cache 或 queue key。

Passive ingress 不获得例外：顶层 passive adapter 为 ActorIdentity 构造默认 `main_workspace` IdentityScope；需要关联时由 conversation key、InteractionSubmission 或 ordering key 分别携带自己的领域 ID。ordering/idempotency/correlation key 不加入 IdentityScope 或 workspace 前缀。

## 10. 分阶段实施

### W0-P0：核心模型与失败语义

实施：

- 新增 `ActorIdentity`、`WorkspaceIdentity`、`IdentityScope` 与规范序列化；
- 将现有 `Identity` 迁移为 `ActorIdentity`，修正 `team_id` 注释，不再称其为 Workspace 过滤字段；
- 定义默认 resolver 和 `main_workspace` 常量；
- 定义 scope required、owner mismatch、workspace mismatch、asset not ready/failed/removed、stale parse result 等稳定错误；
- 为第二 Workspace 提供仅供测试/内部使用的显式构造 seam。

出口：值对象不变量、序列化 round-trip、默认解析和跨 owner 拒绝均有 unit test；领域层不存在 `workspace_id=None` 或 key fallback。

### W0-P1：入口、Run 与跨子系统传播

实施：

- 依次迁移 Chat adapter -> ChatApplicationService -> ChatRun -> Gateway -> Patchouli prepare -> Alice -> finalize；
- `PreparedAgentRun` 成为 finalize 的 scope 真相源；
- root/child frame 和 MTP 继承同一 hard boundary；
- cancel/status 使用调用方 `IdentityScope` 加目标 `interaction_id`（旧 API 的 `generation_id` 仅作目标 ID 别名）进行授权；不得为控制请求伪造 control interaction；
- passive ingress 同步解析默认 Workspace。

出口：两个并发 `IdentityScope` 通过同一套单例子系统运行时不会覆盖；任一中层缺 scope 都显式失败。

### W0-P2：Topic、Memory、Artifact 与检索硬隔离

实施：

- 为 SemanticBuffer/TopicData 和 short-term port/store 增加复合资源键；
- 将 `MemoryAtom` 正式升级为 schema v2，以 `WorkspaceIdentity` 作为唯一 ownership，并拆分 provenance 与 actor read policy；
- 让 Generation/Materialization 所属 TaskSpec 携带唯一、完整的 `identity_scope: IdentityScope`，并按需携带 `interaction_id`、`intent_id` 或其他明确的领域 ID；下层只从 `IdentityScope` 派生 ownership/provenance，禁止仅凭裸 `ActorIdentity` 创建正式 Memory；
- 使 `GenerationRequest` 成为身份无关的内容/意图输入，移除 `creation_context`；`MemoryCreationContext` 仅保留为 P2 过渡别名；
- 为 Memory metadata、新写入 builder 和 retrieval filter 增加 Workspace 投影及 `PUBLIC | PRIVATE | TEAM` policy；
- 将 dedup/merge candidate 查询限制在当前 Workspace hard boundary 内；相同内容也不得跨 Workspace 演化同一 Memory；
- 实现仅 main_workspace 可见 legacy record 的 compatibility filter；
- 收口 v1 decoder/visibility adapter，将旧 `WORKSPACE` 解释为 `TEAM`、旧 `PUBLIC` 保持为 Workspace-local `PUBLIC`；
- 为 Artifact model/store/builder/filesystem adapter 增加 Workspace 归属和复合查找；
- 禁止 Artifact ID/URI 绕过 scope。

出口：相同 user、agent、alias、topic title、artifact ID 测试数据在两个 Workspace 中完全隔离；历史缺字段记录只在 main_workspace 可见；新 Memory 均为 schema v2，只有一份 canonical ownership，并且 PUBLIC/PRIVATE/TEAM 在 Workspace hard filter 之后正确执行。

### W0-P2.5：IdentityScope 字段迁移与兼容收敛

**状态：已完成。P3 返工不得回滚。** P2.5 是 P2 与 P3 之间的短迁移阶段，只处理模型形状、字段所有权和调用签名，不新增资源能力，也不重新打开 P2 的 Memory/Artifact 持久化设计。设立该阶段时，代码基线与第 4.2、17、18 节的目标模型存在以下错位：

- `WorkspaceAccessContext` 仍同时保存 actor、workspace 与 `interaction_id`，并被约 46 个源码文件引用；
- 大多数消费者只读取 actor/workspace，真正消费 `access_context.interaction_id` 的位置很少；
- `MemoryCreationContext` 与目标 `IdentityScope` 形状重复，仍通过 `GenerationRequest.creation_context`、Pending materialization 和 generation 链传播；
- `WorkScopeSnapshot` 已存在于核心模型和导出面，但尚无真实业务消费者；
- `InteractionSubmission` 已独立持有 `interaction_id`，而 `InteractionPayload` 仍嵌套旧 AccessContext；`MemoryGenerationTaskSpec` 则尚未直接持有身份边界。

因此 P2.5 将字段换形从 P3 中独立出来，并已完成以下机械迁移：

1. 在 core 中建立规范 `ActorIdentity`、`WorkspaceIdentity`、`IdentityScope`；`IdentityScope` 只包含 actor/workspace，并保持递归不可变。
2. 将 `Identity` 保留为 `ActorIdentity` 的直接兼容别名；迁移期的 `WorkspaceAccessContext`、`MemoryCreationContext` 最终都收敛为 `IdentityScope` 的直接别名，不再拥有自己的字段、validator 或 wire schema。
3. 先把 `interaction_id` 搬到实际消费者：`ChatRun`、`AgentRunContext`、`InteractionSubmission`、Prepared run 的只读投影以及 Perception journal；随后从旧 AccessContext 中删除该字段。
4. 将 `InteractionPayload.access_context` 改为单一 `identity_scope`，并让 `InteractionSubmission` 显式保存 `identity_scope + interaction_id`；payload 不再成为第二份身份事实。
5. 为 `MemoryGenerationTaskSpec` 增加唯一的 `identity_scope`；将 Pending materialization、generation service、builder 与 Artifact 输入从 `GenerationRequest.creation_context` 迁到 TaskSpec/调用载体的 IdentityScope。
6. 迁移过程可以短暂使用“旧字段读取 -> 新字段构造”的 adapter，但 adapter 必须位于明确的边界、验证新旧值相等且不得写入持久化或 work payload。完成出口前删除双字段和 fallback。
7. 删除无消费者的 `WorkScopeSnapshot` 及其导出；不以 `InteractionScope`、`OperationScope` 或通用 `operation_id` 替代它。
8. 将 `resolve_default_workspace_access(...)`、`build_internal_workspace_access(...)` 和 `require_workspace_access_context(...)` 收敛为 IdentityScope 语义；旧函数名如因兼容保留，只能直接返回/校验 IdentityScope，且不再接受或生成 `interaction_id`。
9. 对受影响的 codec 做保持行为的最小 schema 迁移，使现有 DTO 能完整 round-trip；P2.5 没有改变 retry、ordering、idempotency、cache 或观测的既有命名域，P3 只负责审计并纠正这些消费侧行为。

实施被拆为两个可独立审查的迁移单元：

```text
P2.5-A  canonical models + synchronous carriers
  -> IdentityScope / aliases
  -> ChatRun / AgentRunContext / PreparedAgentRun
  -> resource ports and default resolvers

P2.5-B  task DTO shape migration
  -> InteractionSubmission / InteractionPayload
  -> MemoryGenerationTaskSpec / Pending materialization
  -> minimal codec schema bump
  -> remove legacy fields and WorkScopeSnapshot
```

迁移兼容窗口采用单向规则：旧入口可以投影到新模型，新模型不得再反向补建带 `interaction_id` 的 AccessContext；任一内部对象同时出现旧、新字段时必须验证完全一致，不一致立即失败。不得为通过测试而生成 `memory-api-*`、`agent-api-*` 等无业务消费者的伪 interaction ID。

P2.5 出口：

- production object graph 中只有一个 `IdentityScope` 身份事实；
- `interaction_id` 只由 Chat/Interaction 领域载体持有，普通 Memory/Topic/Artifact/WorkspaceAsset 调用不再被迫传入它；
- `GenerationRequest` 不含权限或 ownership 字段，Memory creation 从 `MemoryGenerationTaskSpec.identity_scope` 取得唯一来源；
- `WorkspaceAccessContext` 与 `MemoryCreationContext` 若仍对外导出，只是 `IdentityScope` 的直接别名；
- `WorkScopeSnapshot` 不再存在；
- P2 已完成的 Memory schema v2、Artifact ownership、检索 hard filter 与 visibility 行为保持不变；
- 全量测试在不依赖 P3 cache/retry 新行为的情况下通过。

### W0-P3：共享组件命名域返工与观测投影收口

**状态：返工中。P2.5 已完成且不得回滚。** 原 P3 已经落地过一轮，但把“领域 DTO 需要传播 `IdentityScope`”错误扩大成了“承载 DTO 的 cache、queue、registry、runtime 等共享组件也应按该 scope 分区”。本阶段只纠正这一命名域扩张，不重新迁移 P2.5 字段。

保留：

- `InteractionSubmission`、`MemoryGenerationTaskSpec` 等领域 DTO 中唯一、不可变的 `IdentityScope`；
- P2.5 已升级 codec 的 canonical round-trip、schema version 校验、冲突投影拒绝和 payload 引用脱钩；
- retry 从 payload 恢复原 `IdentityScope`，并在真正访问 Workspace-owned resource 时由最终 resource owner 重新授权；
- 已完成的 `RuntimeEvent.workspace_id` 可选投影。它只消费字符串并用于观测，不参与 EventBus 路由、subscription、sequence、授权或资源分组。

撤销：

- Koakuma alias/UUID cache、AgentProfile cache 以及其他 cache 的 Workspace key 改造；其 owner、生命周期和既有 key 语义保持不变；
- Work Queue、ordering、idempotency、correlation、lane、task/run registry、scheduler 或 runtime 以 `IdentityScope`、`WorkspaceIdentity`、workspace 前缀或 scope fingerprint 建立隐式分区；
- 任何“组件只要收到或转发 `IdentityScope`，就自动进入 Workspace 命名域”的实现与文档假设。

实施：

1. 审计 W0 触及的所有 key 构造点，搜索完整 `IdentityScope`、`scope_fingerprint`、`actor_identity + workspace_identity` tuple、workspace 前缀及其派生 hash；
2. 将 cache、queue、registry、scheduler、runtime 与 EventBus 恢复为既有领域 key；相同领域 ID 不得因 payload 内的 scope 不同而被拆成两个隐式命名分区；
3. 只允许 Topic、Memory、Artifact、WorkspaceAsset、TopicAssetBinding 等已裁定 Workspace-owned resource 的最终 owner 使用 `WorkspaceIdentity + resource_id` 一类资源坐标；
4. 保持 WorkItem、WorkRecord、WorkExecutionContext 和 queue codec 的领域中立性：queue 只处理领域 ID、机械状态和 opaque bytes，不导入也不解释 Workspace 模型；
5. 保持 RuntimeEvent 的 `workspace_id` 标签，补充测试证明不同标签仍进入同一 EventBus 投递与 sequence 语义；
6. 验证 retry 每次从领域 payload 恢复原 scope 后，仅在资源边界重新授权，且不从进程状态或默认 Workspace 重建身份。

出口：

- P2.5 的 DTO、codec 与唯一身份来源保持不变；
- cache 恢复并维持既有 key、ownership 和生命周期语义；
- generic Work Queue 完全不理解 Workspace，`work_id`、ordering、idempotency、correlation 与 lane 只遵循原领域规则；
- 相同领域 ID 携带不同 scope 时不会产生两个隐式分区；payload 不一致时按既有冲突或幂等规则 fail closed；
- 不同 `workspace_id` 标签的 RuntimeEvent 仍共享同一 EventBus subscription 与 sequence 语义；
- W0 代码中不存在以 `IdentityScope`、scope fingerprint 或 actor/workspace 展开 tuple 作为组件分隔 key 的实现。

### W0-P4：System-owned WorkspaceAssetStore

实施：

- 在 `_RuntimeBundle` 构造一个进程级 Store/可选薄 WorkspaceRuntime；
- 实现按 `(owner_user_id, workspace_id, asset_id)` 分区的内存记录；
- WorkspaceAsset 不保存 created-by provenance 或 visibility；同一 Workspace 内不同 actor 不做 Agent/Team 权限区分；
- 实现仅在当前 Store 存活期有效的 opaque ref token；shutdown 结束其生命周期，不引入 incarnation 或重启恢复；
- 实现创建幂等、两级状态机、revision/token guard、READY-only resolve 和 lease；
- 实现 REMOVED、晚到 callback 拒绝和进程内回收；
- 在 System stop 中把 Store 清理放在 Alice 停止、Patchouli Topic settlement/generation drain 及其他消费者停止之后；`close_and_clear()` 幂等清空全部运行时状态，且不修改 controller `wait_all`；
- 只注入窄 Reader/Command port。

出口：两个 Workspace 的同名资产、相同 display name 和并发状态迁移不串扰；同一 Workspace 内不同 actor 获得相同访问结果；没有 parser 依赖也能完整验证状态机；正常 shutdown 在 Topic 最终结算之后关闭并清空唯一 Store。

### W0-P5：SemanticBuffer binding、单写者保护与生命周期收敛

实施：

- 将保存 `asset_id + asset_ref + first_bound_interaction_id + bound_at` 的冻结
  `TopicAssetBinding` 加入 SemanticBuffer 和 TopicData 只读投影，不保存 WorkspaceAsset
  snapshot、actor-policy 字段或第二份 Topic/Workspace 坐标；
- 将 binding 冻结为 Topic 级真实使用事实：只有一轮成功完成的 Interaction 显式选择并
  通过 lease 使用 READY ref 时，才与本轮 block 在同一个 ShortTermMemoryStore
  interaction commit 中建立；未被使用的 WorkspaceAsset 保持为合法 orphan，上传或 UI
  selection cache 不得提前建立关系；
- 由 ShortTermMemoryStore 的单一 `RLock` 保护全部 SemanticBuffer 字段、Topic pool 与
  last-active 索引；所有读取在锁内构造冻结快照，不再向调用方泄漏可变 buffer；
- 以现有 `PROCESSING/FLUSHING` 实现同一 Topic 单写者预约：Interaction 与 compact 使用
  PROCESSING，manual settle 使用 FLUSHING；冲突写入返回可重试 busy，IDLE 维护跳过 busy
  Topic，LRU 改选其他 IDLE 候选；不为 W0 增加 per-topic lock、content revision/CAS 或
  冲突重算；
- 以 `apply_interaction()` 原子提交 block、bindings、token/model metadata；现有
  `InteractionApplyJournal` 扩展 `INTERACTION_APPLIED + input_digest`，负责等价 retry
  跳过重复 Store apply、冲突输入报错以及后置义务恢复，不在 Store 内增加第二份 receipt；
- automatic settle 使用原子 freeze-and-evict；manual settle 使用 FLUSHING 保护 prepare
  与最终 evict 之间的窗口，admission 失败恢复 IDLE；所有摘要、总线和 queue I/O 保持在
  Store lock 外；
- 按 settle/compact/evict 矩阵接入清理：manual settle 与真实 evict/delete 清除
  binding，manual/token-overflow compact 保留 binding；
- 在所有 settle payload 冻结阶段复制当前 binding refs；manual settle 保持
  admission-before-evict，IDLE/LRU/SHUTDOWN 保持 freeze-then-evict，自动 admission
  failure 不恢复 Topic、不在 queue 外增加嵌套重试，但不能阻止后续 Topic 与已接纳任务
  完成 drain；
- asset remove 只在 AssetStore 内原子进入 REMOVED，不回调 Patchouli、不遍历 Topic、
  不清理 binding；通过 acquire-before-remove / remove-before-acquire 竞态测试证明已有 lease
  与历史使用事实保持稳定，后续 acquire 被拒绝；
- 验证既有 lease 不被删除中断，raw binding 也不能恢复 REMOVED asset 的读取能力；
- 新增真实 lease 贯穿 shutdown 的集成测试：消费者在 Topic settlement/generation
  drain 期间持有 READY representation lease 时 Store 必须保持可读且尚未关闭；消费者
  完成并显式 release 后，System 才能进入 P4 的最终 Store 清理，并确认
  `close_and_clear()` 没有通过强制清除活跃 lease 掩盖消费者泄漏。

出口：ShortTermMemoryStore 是 SemanticBuffer 的唯一同步与变更边界；同一 Topic 不支持
并行写入，而由 PROCESSING/FLUSHING 明确串行化；binding 只来源于成功 Interaction 的显式
真实使用，并只随真实 Topic 生命周期存在；settlement task 在 buffer 清理前取得不可变
ref 快照；asset remove 不形成跨 Store 事务，也不会改写历史使用事实或让 binding 恢复
当前读取能力。

### 11.3 E2E

扩展 `tests/e2e/pipeline/test_chat_run_e2e.py` 或增加独立 Workspace pipeline：

1. 同一 user/agent 在 main_workspace 与 isolation_workspace 启动并发 run；
2. 两侧建立同名 Topic、Memory、Artifact 和 WorkspaceAsset；
3. 交错执行 prepare、Alice frame、finalize、cancel/status 和 retry；
4. 分别读取 Topic/Memory/Artifact/asset，断言只返回当前 Workspace；
5. 删除 A 的 asset/topic，断言 B 不受影响；
6. 用 A 的 opaque ref 从 B 访问，必须稳定拒绝；
7. main_workspace 可以读取对应 user 的 legacy fixture，B 不可读取；
8. 正常 System shutdown 中，Topic settlement/materialization 使用资产期间 Store 保持可用，消费者完成后 Store 才关闭并清空；新 System 从空 Store 开始，需要重新创建资产与关系。
9. A 中的 `PUBLIC` Memory 不能被 B 召回；同 Workspace 内 PRIVATE/TEAM 只命中各自 target。

E2E 使用固定/内存 Agent 响应和真实系统编排，不依赖外部 LLM、Qdrant 或外部内容摄取。

### 11.4 Workspace 归属硬边界矩阵

| resource | user | workspace | actor/句柄条件 | 预期 |
|:---|:---|:---|:---|:---|
| Memory / Artifact / Topic / WorkspaceAsset | 相同 | 不同 | 同 Agent | 拒绝 |
| Memory / Artifact / Topic / WorkspaceAsset | 不同 | 同名 `main_workspace` | 任意 | 拒绝 |
| WorkspaceAsset | 相同 | 相同 | 不同 Agent/Team | 允许 |
| WorkspaceAsset | 相同 | 不同 | 持有另一 Workspace 的 opaque ref | `ASSET_NOT_FOUND` |
| WorkspaceAsset | 相同 | 相同 | 随机未知 token | `ASSET_NOT_FOUND` |
| WorkspaceAsset | 相同 | 相同 | 当前 Store 内已 remove 的 ref | `ASSET_REMOVED` |

Workspace 归属矩阵必须复用于 Memory、Artifact、WorkspaceAsset 和 Topic 的最终 resource owner。WorkspaceAsset 到此为止，不复用 Memory 的 actor read policy。

### 11.5 Memory actor read-policy 矩阵

| user | workspace | actor | visibility | 预期 |
|:---|:---|:---|:---|:---|
| 相同 | 相同 | 不同 Agent | `PUBLIC` | 允许 |
| 相同 | 相同 | target 不同的 Agent | `PRIVATE` | 拒绝 |
| 相同 | 相同 | target 相同的 Agent | `PRIVATE` | 允许 |
| 相同 | 相同 | target 相同的 Team | `TEAM` | 允许 |
| 相同 | 相同 | target 不同的 Team | `TEAM` | 拒绝 |

- [ ] opaque ID/ref、cache hit 和 Artifact URI 均不能绕过 Workspace；Agent/Team visibility 只在已定义该 policy 的资源上执行。
- [ ] `MemoryAtom.schema_version == 2`，领域对象只以 `workspace_identity` 表达 ownership，不存在并列的通用 `user_id` 权威。
- [ ] `workspace_id` 对 Memory 表示资源归属而非 grant；跨 Workspace 共享不复用该字段。
- [ ] Memory provenance 与 read-policy target 分离，`PUBLIC | PRIVATE | TEAM` 的 target 字段组合符合 v2 不变量。
- [ ] `PUBLIC` 只对 owning Workspace 内已授权 actor 公开，不代表全局公开，也不授予写、删或 ownership 变更权限。
- [ ] 历史缺字段记录只在对应用户 main_workspace 的受控兼容查询中可见。
- [ ] W0 新写入关键记录保存完整 WorkspaceIdentity 投影。
- [ ] W0 内所有 cache、registry、queue、scheduler、runtime、EventBus 和 service container 都不以 `IdentityScope`、scope fingerprint、actor/workspace 展开 tuple 或其派生 hash 作为分隔 key。
- [ ] generic Work Queue 的 `work_id`、ordering、idempotency、correlation 和 lane 只来自既有领域规则；相同领域 ID 不会因 payload 内 scope 不同而被拆成两个分区。
- [ ] 只有已裁定 Workspace-owned resource 的最终 owner 使用 `WorkspaceIdentity + resource_id` 一类资源键；共享基础设施不继承该命名域。
- [ ] `RuntimeEvent.workspace_id` 仅为可选观测标签；不同 workspace_id 的事件仍共享 EventBus subscription、sequence 与 routing 语义。
- [ ] work codec 序列化完整领域 DTO，但 IdentityScope 只存在于 opaque payload，不建立第二身份模型或 queue 分区。
- [ ] 每次 retry 恢复原 `IdentityScope` 与原领域 ID 后重新授权，不读取进程当前 Workspace、不重跑默认 resolver，也不修改身份坐标。
- [ ] WorkItem payload bytes 与调用方可变 TaskSpec/request 对象图脱钩。
- [ ] SystemAssembler 只构造一个进程级 WorkspaceAssetStore/WorkspaceRuntime。
- [ ] WorkspaceAsset 不保存 `created_by_agent_id`、`created_by_team_id`、`visibility` 或 actor-policy target；同一 Workspace 内不同 Agent/Team 的访问结果一致。
- [ ] `WorkspaceAssetRef` 只是当前 Store 存活期内的 opaque token，不包含可解释资源坐标；shutdown 结束全部 ref 生命周期，不存在 incarnation 或重启恢复语义。
- [ ] WorkspaceAsset/AssetRepresentation 状态机只能由 Store 命名命令推进。
- [ ] representation 终态与 WorkspaceAsset 聚合终态在同一原子命令中提交；complete/fail 与 remove 竞态只产生按提交顺序线性化的权威结果，不暴露两级状态不一致的中间快照。
- [ ] RAW READY 不足以令文档资产 READY；只有 required EXTRACTED_TEXT READY 才可使用。
- [ ] PROCESSING、FAILED、REMOVED 和跨 Workspace ref 不能 resolve 或 acquire lease；没有成功 acquire 和实际使用的 Interaction 不会建立 binding。
- [ ] REMOVED 是不可逆终态：重复 remove 幂等，后续 representation 命令与晚到解析结果不能改变任何状态；FAILED 不自动 retry。
- [ ] TopicAssetBinding 位于 SemanticBuffer，保存 `asset_id + asset_ref + first_bound_interaction_id + bound_at`，由 ShortTermMemoryStore 幂等维护；不保存 WorkspaceAsset snapshot、actor-policy 字段或第二份 Topic/Workspace 坐标。
- [ ] ShortTermMemoryStore 的单一 RLock 保护全部 SemanticBuffer 字段、Topic pool 与 last-active 索引；公开读取只返回冻结快照，锁内没有 await、总线、摘要生成、AssetStore 或 queue I/O。
- [ ] binding 是 Topic 真实使用事实，只能由一轮成功完成、显式选择并通过 lease 使用 READY ref 的 Interaction 与本轮 block 原子建立；零 binding WorkspaceAsset 是合法 orphan，上传、最近资产或 UI selection cache 不会建立关系。
- [ ] 同一 Topic 只允许一个写入者：Interaction/token-overflow compact 与 manual compact 使用 PROCESSING，manual settle 使用 FLUSHING；busy 写入明确失败，IDLE 维护跳过、LRU 改选，状态窗口结束后恢复可写；W0 不实现 content revision/CAS 或冲突重算。
- [ ] `apply_interaction()` 原子提交 block、bindings 与相关 metadata；现有 InteractionApplyJournal 以 `INTERACTION_APPLIED + input_digest` 令等价 retry 跳过重复 apply、不一致 retry 报冲突，Store 不保存第二份 receipt；同一 Topic 再次使用同一资产不会覆盖首次 Interaction 或首次绑定时间。
- [ ] automatic settle 原子 freeze-and-evict；manual settle 的 FLUSHING 窗口拒绝新 commit 并在 admission 失败后恢复 IDLE；shutdown 在 interaction/finalize drain 后仍遇到 busy Topic 时显式报告顺序缺陷，不由最终 Store clear 静默吞掉。
- [ ] manual/token-overflow compact 保留 binding；manual settle 与真实 evict/delete 随整个 buffer 清除 binding；不提供脱离 Topic 生命周期的事实删除命令。
- [ ] settle 在 buffer 清理前把全部 binding refs 冻结进不可变 task；manual settle admission 失败保留 Topic，IDLE/LRU/SHUTDOWN admission 失败不恢复 Topic或在 queue 外嵌套重试，但后续 Topic 与已接纳任务仍完成 drain。
- [ ] asset remove 不回调 Patchouli、不清理 binding；remove-before-acquire 不建立使用事实，acquire-before-remove 的已有 lease 可完成并留下 binding，后续 acquire 仍由 REMOVED 状态拒绝。
- [ ] 既有 lease 持有到消费者结束，最后一个 hold 释放后才能回收内容。
- [ ] System shutdown 先停止资产消费者并完成 Patchouli Topic settlement/generation drain，再幂等关闭并清空 AssetStore；真实 lease 测试证明消费者先显式 release，`close_and_clear()` 不以清除活跃 lease 掩盖泄漏；Store 不调用 controller `wait_all`、不查询 Topic/binding，System 只在清理完成后报告 `STOPPED`。
- [ ] Store shutdown 清空 asset/representation、ref、幂等、operation token、REMOVED 与 lease bookkeeping；新进程从空 Store 开始，用户必须重新上传并建立关系。
- [ ] 同 user/agent 的两个 Workspace 在并发 walking skeleton 中没有任何资源串扰。
- [ ] W0 不包含真实上传、parser、Context Compiler、Artifact promotion 或历史批量脚本执行。
- [ ] unit、integration、e2e 分层符合测试治理标准，完整回归通过。

## 13. 发布、回滚与风险控制

### 13.1 发布顺序

当前基线是 P0-P2.5 已落地，P2.5 的模型/DTO/codec 迁移不得作为 P3 返工的一部分回滚。剩余发布顺序为：

1. 先完成 P3 key audit，撤销 cache、work、ordering、idempotency、registry、scheduler 与 runtime 的 IdentityScope/Workspace 命名分区；
2. 保留已完成的 `RuntimeEvent.workspace_id` 可选投影，并用投递行为测试证明它不改变 EventBus 命名域；
3. 验证领域 payload/retry 仍恢复 P2.5 的唯一 IdentityScope，并只在最终 Workspace-owned resource 边界重新授权；
4. 再接入 WorkspaceAssetStore，并先验证其无 visibility/provenance 的最小模型、进程内 ref/lease 与 shutdown 最终清理顺序；
5. 接入 TopicAssetBinding，验证 Topic shutdown settlement 使用资产期间 Store 尚未关闭，binding/消费者完成后才执行 Store 最终清理；
6. 完成双 Workspace walking skeleton、完整回归与 W0 文档收口；
7. W0 稳定后另行运行历史数据转换脚本。

各阶段不得以“缺 scope 时回退 main_workspace”维持内部兼容。兼容只允许在顶层默认解析和 storage legacy projection 两处存在。

### 13.2 回滚边界

- W0 不执行历史批量转换，因此 P0-P6 失败时可以停用新入口并回滚代码，不需要反向改写全部历史记录；
- 已由 W0 写入的 Workspace 字段和 Memory schema v2 记录不能假设旧 reader 可忽略；回滚前必须确认 reader 能识别版本并安全拒绝或兼容读取；
- 历史可见性枚举的批量回填后置；P2 新写入的 `TEAM` 和 v2 policy 只能在 v2 reader 已先部署后启用；
- P2.5-B 改变进程内 Task DTO/codec 形状；部署或回滚前必须停止接纳并 drain/终止现有本地队列，不承诺在同一进程中混跑旧、新 payload schema；P2.5 不引入耐久队列数据迁移；
- P3 返工不得回滚 P2.5 的 DTO/codec 字段形状，也不回滚已完成的 `RuntimeEvent.workspace_id` 投影；只撤销共享组件以 scope/workspace 建立分隔 key 的行为；
- 如果已产生只有新版本理解的记录，禁止盲目降级，必须先使用配套兼容 reader 或转换工具读回验证；
- WorkspaceAsset、binding 和 ref 都是进程内状态；正常 shutdown 在 Topic settlement/generation drain 后统一清空，进程退出不保留任何资产或 ref 信息。新进程从空 Store 开始，用户必须重新上传并建立关系，不提供跨 shutdown 查询或恢复协议。

### 13.3 主要风险

| 风险 | 控制 |
|:---|:---|
| scope 参数改造面过大 | 用 P2.5-A/B 把模型/DTO 机械迁移从 P3 行为改造中拆出；每个出口禁止双字段与 fallback |
| P2.5 新旧 codec 混跑 | 本地队列升级前 drain/stop，schema version fail closed，不在 handler 中猜测旧字段 |
| 将 IdentityScope 传播误解为组件命名域 membership | key audit 覆盖所有共享 cache、queue、registry、runtime、scheduler 与 EventBus；只有最终 Workspace resource owner 可以构造 Workspace resource key |
| 用 scope fingerprint、actor/workspace tuple 或派生 hash 绕过禁令 | 静态搜索与行为测试并用；相同领域 ID 携带不同 scope 时仍触发既有冲突/幂等语义，不产生隐式分区 |
| RuntimeEvent workspace 标签被误作路由或授权输入 | EventBus API 不读取该标签；验证不同标签进入相同订阅与 sequence 语义 |
| P3 返工误伤已完成的 P2.5 | 将 DTO/codec 形状列为冻结基线；返工 diff 只接受 key/partition 消费侧变化 |
| Memory ownership 与 actor user 再次混合 | 领域模型只保存 canonical WorkspaceIdentity；legacy `user_id` 只在 decoder 中解释 |
| Memory 新旧 visibility 语义冲突 | 固定 Memory schema v2 与命名 v1 adapter；只迁移 `WORKSPACE -> TEAM`，`PUBLIC` 保持 Workspace-local PUBLIC；WorkspaceAsset 不引入 visibility |
| Artifact 全局路径造成越权 | 复合索引、scope-aware Store、URI 不授权、同 ID 隔离测试 |
| cache 返工破坏既有行为 | 不增加 Workspace key 结构测试；使用既有可观察 cache 回归，并在最终 Workspace resource owner 验证授权 |
| 共享 Runtime 并发覆盖 | 禁止 `current_workspace`，并发 barrier 测试两个 IdentityScope |
| SemanticBuffer 只有底层字典锁，Interaction 与生命周期操作交错后丢失新内容 | ShortTermMemoryStore 单锁保护 buffer、port 与辅助索引；冻结 read、原子 interaction apply 和 freeze-and-evict 在 Store 内线性化；PROCESSING/FLUSHING 将同一 Topic 写入串行化，锁内禁止外部 I/O |
| 为低概率并行写入提前引入 revision/CAS、重算或更多控制组件 | W0 明确采用同一 Topic 单写者；busy 操作拒绝、跳过或改选候选，不新增 content revision、Store receipt、binding controller、per-topic lock registry 或第二份 used-ref 状态；只有观测到真实并行需求后再升级 |
| AssetStore 与 binding 试图组成跨 Store 事务 | 以 lease acquire 作为真实使用线性化点；remove 只改变 AssetStore 当前可用性，不回调 Patchouli、不删除历史 binding，不引入共同锁、两阶段提交、补偿或 cleanup controller |
| 上传或 UI 选择状态被误作真实使用 | binding 只能在成功 Interaction commit 中与 block 原子建立；零 binding 资产保持合法 orphan，不从最近上传、活跃 Topic 或 pending list 推导关系 |
| 自动 settle admission 失败造成 Topic 池或 shutdown 卡住 | 自动路径先冻结 task/ref 再驱逐；失败不恢复 Topic、不在 queue 外重试，批处理继续处理后续 Topic并 drain 已接纳任务；异常独立观测且不计为 skip |
| 两级状态机分步提交或 remove 竞态产生中间态 | revision/token 校验、representation 更新、asset 聚合更新与 REMOVED 检查在同一临界区内完成；用 barrier 控制 complete/fail-remove 竞态并断言线性化终态 |
| WorkspaceAsset 提前复制 Memory 权限模型 | Asset 不保存 created-by/visibility/target；同 Workspace 不区分 Agent/Team，后续附件权限由独立计划裁定 |
| opaque ref 被误作持久身份或 capability | ref 只保存随机 token，解析后重验 Workspace；shutdown 结束 ref 生命周期并清空索引，新进程要求重新上传，不设计 incarnation 或 recovery |
| AssetStore 在 Topic 最终结算前被清空 | System 先停止 Alice 等消费者，再由 Patchouli 完成 interaction/finalize、Topic shutdown settlement 和 generation drain，最后关闭 Store；Store 不反向调用 controller 或 Topic |
| shutdown 与新 Asset 命令竞态 | Store 最终 `close_and_clear()` 与全部命名命令原子互斥，关闭后拒绝新命令，清理完成后 System 才报告 `STOPPED` |
| lease 演化成耐久事务 | W0 明确仅为当前 Store 存活期内 hold；正常 shutdown 先 drain 消费者再清空 bookkeeping，不承诺 restart recovery |
| WorkspaceRuntime 变成超级容器 | 只聚合 asset store，依赖通过窄 port 注入 |

## 15. P1 补充裁定：IdentityScope 的用户语义与渐进迁移

> **补丁日期**：2026-08-19
>
> **适用阶段**：W0-P1，并约束后续 P2/P3 的资源访问接口
>
> **裁定目的**：消除 `ActorIdentity.user_id` 与 `WorkspaceIdentity.owner_user_id` 同时存在时的读取歧义，并避免把 P1 错误实施为“用 IdentityScope 全面替换 ActorIdentity”

### 15.1 两个用户字段保留，但不存在通用 user_id

`IdentityScope` 中的两个用户字段分别回答不同问题：

| 字段 | 权威语义 | 典型用途 |
|:---|:---|:---|
| `actor_identity.user_id` | 谁正在执行本次操作 | 操作者审计、Agent/Team visibility、actor policy |
| `workspace_identity.owner_user_id` | 正在访问谁的资源命名空间 | Workspace 资源归属、Store key、检索硬过滤、Topic/Memory/Artifact owner |

W0 继续要求二者相等，但该等值关系是当前访问策略的不变量，不表示二者可以互相替代：

```text
identity_scope.actor_identity.user_id
  == identity_scope.workspace_identity.owner_user_id
```

因此 `IdentityScope` 不得新增含糊的 `user_id` 属性。若频繁读取需要改善可读性，可以提供 `actor_user_id` 与 `workspace_user_id` 两个明确命名的只读投影；不得用单一兼容属性隐藏调用方究竟需要 actor 还是 resource owner。当前存在的通用 `RetrievalRequest.user_id` 等兼容投影应逐步改名或退出资源过滤路径。

移除 `WorkspaceIdentity.owner_user_id` 不是本问题的解决方案。WorkspaceIdentity 作为可独立持久化、进入 work payload 和资源 key 的完整坐标，必须在脱离一次具体 Chat 后仍能表达资源 owner。未来若引入授权 Agent 访问其他 owner Workspace 的 grant，两个用户字段可能合法不同；届时应将 same-owner 检查从 W0 构造不变量迁入显式 Workspace authorizer，而不能依赖通用 `user_id`。

### 15.2 Scope 是安全信封，不是新版 ActorIdentity

P1 的迁移目标调整为“完整传播 IdentityScope，同时保留 `ActorIdentity` 的 actor 领域职责”。不得机械地把所有 `actor_identity: ActorIdentity` 参数替换为 `identity_scope: IdentityScope`。

| 边界或行为 | 规范输入 |
|:---|:---|
| HTTP/System application、跨子系统 Bus | `IdentityScope`；具体请求 DTO 另带必要领域 ID |
| Chat run、Gateway state、Prepared run、Interaction、可重试领域 payload | 保存完整 `IdentityScope`；仅真正需要关联的载体另存 `interaction_id`/`intent_id` 等明确字段；承载它的共享组件不按 scope 分区 |
| Topic、Memory、Artifact、WorkspaceAsset 的授权入口 | `IdentityScope`；WorkspaceAsset 在 W0 只验证 Workspace 归属，不执行 Agent/Team visibility |
| 已完成授权后的 Store 内部寻址 | `WorkspaceIdentity`、`WorkspaceTopicKey` 或其他 scoped resource key |
| 只执行 Agent/Team visibility、persona、actor 展示的叶子逻辑 | `ActorIdentity` |
| RuntimeEvent | 从 scope 显式投影所需观测字段，不作为授权输入 |

剩余 `ActorIdentity` 签名不自动视为迁移缺口。判断标准是该函数是否读取或改变 Workspace-owned resource：只做 actor policy 的纯逻辑可以继续接收 ActorIdentity；Topic、Memory、Artifact、WorkspaceAsset 等最终 resource owner 的授权入口必须获得完整 `IdentityScope`。共享 cache 不因缓存相关值而成为 resource owner，也不必为此改成 scope-aware key；cache 结果若被用于资源操作，仍由最终 owner 重验。

公共兼容入口使用“wrapper + strict scoped entry”模式：外层可以继续接受既有 `user_id/agent_id` 并一次性解析 `main_workspace`，内部入口只接受完整 `IdentityScope`。内部方法不得同时接受可选的 `ActorIdentity` 与可选的 scope，也不得根据哪个参数存在来选择身份来源。

### 15.3 载体升级、叶子兼容

P1 采用以下渐进迁移模式：

```text
request/run carrier 保存一份 IdentityScope
  -> actor-only 旧逻辑通过只读 actor_identity 投影读取 ActorIdentity
  -> resource access 通过 scope / workspace_identity 读取资源域
```

`AgentRunContext`、`ExecutionFrame`、`MTPExecutionContext` 等 carrier 可以继续提供只读 `identity` 兼容属性，但该属性固定返回 `identity_scope.actor_identity`，且不能被资源访问代码当作完整授权上下文。`InteractionPayload` 作为 `InteractionSubmission.payload` 不保存第二份 scope；兼容属性只减少 actor-only 叶子逻辑的迁移面，不得用于重新构造默认 Workspace。

同一个聚合内部只物理保存一份 `IdentityScope`。若下层对象已经权威持有它，上层通过只读属性派生，不再保存第二份字段后做等值检查。例如 `ExecutionFrame` 从 Alice `RuntimeScope` 派生 identity scope；`PreparedAgentRun` 应从 `AgentRunContext` 派生，而不是同时持有两份状态。

### 15.4 P1 实施与验收增量

W0-P1 在原出口之上增加以下要求：

- [ ] 代码中不存在 `IdentityScope.user_id` 这一通用权威入口；
- [ ] actor policy 明确读取 `ActorIdentity`，资源归属与硬过滤明确读取 `WorkspaceIdentity`；
- [ ] request/run carrier 传播完整 scope，但 actor-only 叶子逻辑不被迫改签名；
- [ ] 公共默认 Workspace wrapper 与内部 strict scoped entry 分离，内部不存在双身份来源；
- [ ] 一个聚合只物理保存一份规范 scope，其他访问均为只读派生；
- [ ] 兼容 `identity` 属性只返回 `ActorIdentity`，资源访问不能依赖它补建 Workspace；
- [ ] prepare、root/child Frame、MTP、finalize 和 work payload 仍保持同一完整 `IdentityScope`；
- [ ] P2/P3 的 Topic、Memory、Artifact 等已裁定资源继续使用 owner/workspace 复合资源键；共享 cache 保持既有 key，二者都不因 P1 保留 ActorIdentity 而降低最终资源授权强度。

测试只保护可观察的不变量与真实回归：cross-owner IdentityScope 必须拒绝、prepare scope 漂移必须失败、子 Frame 必须继承完整 hard boundary、同一 actor 的两个 Workspace 不得串扰、资源过滤必须包含 Workspace ID。简单的 `actor_user_id`/`workspace_user_id` 属性不单独增加构造后回读测试；其正确性由上述权限和传播行为覆盖。

## 16. P2 补充裁定：Memory ownership、actor policy 与 schema v2

> **补丁日期**：2026-08-19
>
> **适用阶段**：W0-P2，并约束 W0 内的 Memory、检索与 Artifact provenance
>
> **裁定目的**：消除 `MemoryAtom` 中 actor user 与 Workspace owner 的双权威，冻结 `workspace_id` 的 ownership 语义，并重定义 visibility 为 owning Workspace 内的 actor read policy

### 16.1 IdentityScope 可以有两条用户轴，Memory ownership 只能有一条

P1 中 `actor_identity.user_id` 与 `workspace_identity.owner_user_id` 可以同时存在，因为 IdentityScope 描述一次操作的硬身份坐标：前者回答“谁在执行”，后者回答“正在访问谁的资源域”。`MemoryAtom` 则是物化后的持久化资源事实，不能把这两条用户轴原样复制为并列 owner。

P2 冻结以下投影：

```text
创建时
  Memory ownership
    <- task.identity_scope.workspace_identity

  Memory provenance
    <- task.identity_scope.actor_identity.agent_id/team_id

  Memory read policy
    <- requested/default PUBLIC | PRIVATE | TEAM policy
```

因此 Memory 唯一的 ownership user 是 `workspace_identity.owner_user_id`。`actor_identity.user_id` 只参与 Workspace entry authorization、操作审计以及必要的 actor policy，不进入第二套 Memory ownership。领域对象不得提供含糊的 `meta.user_id` 作为兼容权威。

### 16.2 workspace_id 是归属，不是访问许可

对 MemoryAtom，`workspace_id` 的唯一语义是“该 Memory 归属于这个 Workspace”。它参与 Memory 自身的资源键、生命周期、检索硬过滤和管理权限判定，但不要求 alias/cache 或承载它的共享组件按 Workspace 分区。

如果将其解释为“允许这个 Workspace 访问”，它就会退化为单值 ACL：Memory 的真正 owner 仍然缺失，多个 Workspace grant 无法表达，并且与 visibility 职责重叠。任何跨 Workspace 使用都不能重解释该字段；源 Memory 始终归原 Workspace，复制或转移必须创建新的资源归属事实。

### 16.3 visibility 反转为 owning Workspace 内的 actor read policy

MemoryAtom 已由 WorkspaceIdentity 建立硬 ownership 边界后，visibility 不再表示资产范围，而只表示进入 owning Workspace 后哪些 actor 可读：

| v2 visibility | target | 读取语义 |
|:---|:---|:---|
| `PUBLIC` | 无 | owning Workspace 内所有已获准进入的 actor |
| `PRIVATE` | `target_agent_id` | owning Workspace 内指定 Agent |
| `TEAM` | `target_team_id` | owning Workspace 内指定 Agent 组 |

访问顺序必须固定为：

```text
actor_can_enter_workspace(identity_scope.actor_identity, identity_scope.workspace_identity)
AND memory.workspace_identity == identity_scope.workspace_identity
AND match_memory_read_policy(identity_scope.actor_identity, memory.access_policy)
```

`PUBLIC` 是 workspace-local public，不是 global public。任何 visibility、agent/team 匹配、alias、Memory ID 或 cache hit 都不能绕过前两项。该 policy 只授予 SEARCH/READ/Context use；更新、删除、调整 policy 与转移 ownership 必须使用独立 mutation authorization。

### 16.4 provenance 与 authorization target 分离

`source_agent_id/source_team_id` 是不可因授权调整而改写的历史来源；`target_agent_id/target_team_id` 是当前 read policy 的授权目标。默认策略可以从创建 actor 派生 target，但不能让 source 字段永久兼任 ACL。

W0/P2 未显式指定 policy 时默认写入 `PUBLIC`，以保持现有 Memory 创建行为；默认必须在 builder 中显式物化。TEAM 的 MVP evaluator 使用 `actor_identity.team_id == target_team_id`。

v2 必须校验：

```text
PUBLIC  -> no target
PRIVATE -> exactly target_agent_id
TEAM    -> exactly target_team_id
```

更新已有 Memory 时，当前 scope 只用于授权本次 mutation；原 `workspace_identity` 保持不变，更新 actor 进入版本 Artifact/event provenance，不覆盖资源 owner。若允许修改 read policy，只更新 target/policy，不修改 source provenance。

对 v1 Memory 的首次 UPDATE 是一次受控 read-normalize-write：先按 v1 adapter 得到 canonical v2，再执行 mutation，并以 schema v2 写回。该过程不能借当前 active Workspace 重新归属历史 Memory。

### 16.5 MemoryAtom schema v2 与兼容边界

P2 实施时必须正式将 `MemoryAtom.schema_version` 调整为 `2`。`schema_version` 是模型契约版本，不是 Memory 内容版本或乐观锁字段；现有 `meta.version` 保持其原职责。v2 的规范领域结构为：

```text
MemoryAtom(schema_version = 2)
  meta
    workspace_identity: WorkspaceIdentity   # sole ownership authority
    source_agent_id
    source_team_id?
    access_policy
      visibility: PUBLIC | PRIVATE | TEAM
      target_agent_id?
      target_team_id?
```

存储和 Qdrant adapter 可以从 `workspace_identity` 平铺 owner/workspace 字段用于索引，但领域模型不能同时持有多套可独立修改的 owner 字段。推荐用独立 v1 DTO/decoder 读取旧记录；如果兼容层收到 legacy `user_id` 与新 ownership 并存的数据，只有在二者一致时才能归一化，不一致时必须拒绝并记录诊断。

版本分派规则固定为：缺少 `schema_version` 视为 v1 输入；版本 2 必须完整通过 v2 ownership/policy validation；未知版本 fail closed。版本判断只能选择 decoder，不能成为缺字段时从当前 scope 猜测 ownership 的 fallback。

v1 兼容规则为：

```text
legacy meta.user_id = U and no Workspace fields
  -> only under U/main_workspace
  -> canonical workspace_identity = (U, main_workspace, main_workspace)

v1 PRIVATE
  -> v2 PRIVATE(target_agent_id = source_agent_id)

v1 WORKSPACE
  -> v2 TEAM(target_team_id = team_id)

v1 PUBLIC
  -> v2 PUBLIC
```

v1 `source_agent_id` 保留为 provenance，v1 `team_id` 转为 v2 `source_team_id`；对于 v1 WORKSPACE，它还用于初始化 `target_team_id`，但完成 v2 归一化后 source 与 target 必须独立。

v1 PRIVATE 缺少 `source_agent_id`、v1 WORKSPACE 缺少 `team_id`，或 ownership 投影彼此冲突时，decoder 和迁移脚本都必须 fail closed，不得生成默认 target。

新写入必须直接产生 v2，不再双写 legacy `meta.user_id`。历史批量转换仍遵循“W0 基本落地并通过双 Workspace 验收后再运行”的既定时机。

### 16.6 P2 实施与验收增量

P2 不得只修改 `MetaData` 字段；Memory creation 的输入链也必须获得 Workspace ownership。`MemoryGenerationTaskSpec` 只携带一份 `identity_scope: IdentityScope`，并按现有模型携带 `intent_id` 等局部领域字段，不再嵌套 `MemoryCreationContext` 或任何通用 work scope。下层 builder 从该 IdentityScope 派生 ownership/provenance 参数；`GenerationRequest` 只携带内容与生成意图，不提供权限字段。不得另建 `WorkScopeSnapshot` 作为第二身份权威；`_draft_to_memory` 一类正式创建入口也不能继续只接受裸 `ActorIdentity`。

在原 P2 出口之上增加：

- [ ] 所有新 Memory 均写入 `schema_version = 2`；
- [ ] Memory 领域对象只有一份 canonical `WorkspaceIdentity` ownership；
- [ ] legacy `user_id` 只存在于 v1 decoder/filter，不进入新领域对象；
- [ ] `workspace_id` 始终表示归属，不承担 grant 或 visibility；
- [ ] PUBLIC/PRIVATE/TEAM 均在 Workspace hard filter 后执行；
- [ ] source provenance 与 access-policy target 可以独立验证和演化；
- [ ] v1 `WORKSPACE` 仅兼容为 TEAM，v1 `PUBLIC` 兼容为 workspace-local PUBLIC；
- [ ] 更新 Memory 不覆盖原 ownership，更新者进入 version Artifact/event provenance；
- [ ] dedup/merge 只消费当前 Workspace 内已授权候选，不会跨 Workspace 合并或演化 Memory；
- [ ] PUBLIC 不授予 mutation 权限，跨 Workspace sharing 不修改源 Memory ownership。

## 17. P3 补充裁定：IdentityScope、领域关联 ID 与组件命名域

> **补丁日期**：2026-08-20
>
> **适用阶段**：W0-P2.5 至 P3
>
> **裁定目的**：说明 `IdentityScope` 的不可变职责，避免为局部关联 ID 建立公共 Scope 变体，并冻结“传播身份不等于组件按身份分区”的 P3 返工边界。

### 17.1 IdentityScope 是唯一公共身份载体

```python
from pydantic import BaseModel, ConfigDict


class IdentityScope(BaseModel):
    actor_identity: ActorIdentity
    workspace_identity: WorkspaceIdentity

    model_config = ConfigDict(frozen=True, extra="forbid")
```

`IdentityScope` 创建后递归不可变。它不含关联 ID、授权结果、Workspace 当前状态或 capability/grant。切换 Actor 或 Workspace 必须创建新实例；任何下游阶段都不能通过 `model_copy(update=...)`、替换嵌套字段或重新解析默认 Workspace 来改写既有工作的身份。

### 17.2 领域 DTO 组合局部 ID

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ChatRun:
    identity_scope: IdentityScope
    interaction_id: str


@dataclass(frozen=True)
class InteractionSubmission:
    identity_scope: IdentityScope
    interaction_id: str
    payload: InteractionPayload


@dataclass(frozen=True)
class MemoryGenerationTaskSpec:
    identity_scope: IdentityScope
    request: GenerationRequest
    intent_id: str | None = None
```

上述 DTO 的 `identity_scope` 是唯一身份来源；局部 ID 由各自领域解释。`interaction_id` 只在 Chat/Interaction、Perception journal 等实际需要它的模型出现；`intent_id`、`task_id`、`work_id` 等继续由 Memory Generation/Queue 现有模型持有。W0 不再设计通用 `operation_id`；具体状态机若需要操作 ID，应使用明确命名的领域字段。

### 17.3 Codec 边界不是可变快照

异步边界序列化只负责进程引用脱钩、版本兼容和未来重启恢复，不意味着身份在入队前可变：

```text
immutable IdentityScope + domain DTO
  -> versioned codec
  -> WorkItem-owned payload bytes
  -> decode and validate on every attempt
  -> equivalent IdentityScope + domain DTO
```

codec 必须完整编码具体 DTO，并在解码时执行与领域构造一致的不变量校验。payload 缺字段、被篡改、出现冲突投影或使用未知 schema version 时均 fail closed。不得同时保存嵌套 IdentityScope 和一组平铺 actor/workspace 字段，再依赖等值检查维持一致性。

### 17.4 不可变坐标不等于永久授权

IdentityScope 只记录任务最初绑定的身份坐标，不缓存“此 actor 永远可以执行”的结论。每次 attempt 必须：

1. 从 WorkItem payload 解码原始 `IdentityScope` 与领域 ID；
2. 由最终资源所有者按当前 Workspace 状态、grant、team membership 与资源 policy 重新授权；
3. 授权通过后执行，失败则拒绝或进入既定失败策略；
4. 无论授权结果如何，都不得刷新、替换或修改原 scope。

retry 不读取 `current_workspace`，不重新调用 `main_workspace` resolver，也不从 handler 当前进程状态补建身份。ordering key、idempotency key、correlation ID 和 lane 只能由既有领域 ID/输入派生，`IdentityScope`、`WorkspaceIdentity`、workspace 前缀与 scope fingerprint 均不得参与这些 key。审计可以把 IdentityScope 单独记录为 provenance，但不能用它合成关联或分隔 key。

### 17.5 取消/状态查询使用调用方 Scope 与目标 ID

调用方自身不属于被控制的 Chat Interaction。规范接口为：

```text
cancel/status(
  caller_scope: IdentityScope,
  target_interaction_id: str,
)
```

旧 API 的 `generation_id` 仅作为 `target_interaction_id` 的兼容字段。控制面按照调用方 IdentityScope 与目标 ChatRun 原始身份执行授权；不得生成 fake interaction，也不得以目标 ID 单独作为授权凭证。`request_id` 与 `trace_id` 仅记录控制请求，不进入身份语义。

### 17.6 已完成的 P2.5 基线与 P3 返工边界

以下结构性要求已经由 P2.5 完成，P3 返工不得回滚：

- [x] `IdentityScope` 是唯一公共身份载体，且递归不可变；
- [x] Interaction Submission 只保存一份 `IdentityScope` 和一个明确的 `interaction_id`；
- [x] MemoryGenerationTaskSpec 只保存一份 `IdentityScope`，其余字段使用现有 `intent_id/task_id/work_id` 等领域命名；
- [x] `GenerationRequest` 不携带 `creation_context` 或其他权限字段；
- [x] 生产任务链及其 codec 不使用第二套 scope 快照或平铺身份副本；

P3 在上述字段形状已经稳定的前提下增加以下行为验收：

- [ ] codec round-trip 后的 scope 与原对象完整等值，并重新执行模型不变量校验；
- [ ] payload 缺字段、冲突投影、篡改或未知 schema version 时 fail closed；
- [ ] retry 只恢复原 IdentityScope，不读取 `current_workspace`、不重新解析 `main_workspace`、不修改身份坐标；
- [ ] WorkItem、WorkRecord、WorkExecutionContext 与 generic queue 保持领域中立，不导入或解释 Workspace 模型，也不从 payload scope 派生 key；
- [ ] cache、registry、scheduler、runtime 和 EventBus 均不以 IdentityScope、scope fingerprint 或 actor/workspace tuple 分区；
- [ ] 相同领域 work/idempotency ID 不因 payload 内 scope 不同而产生两个隐式分区，冲突时遵循既有 fail-closed 语义；
- [ ] 已完成的 `RuntimeEvent.workspace_id` 投影保留为观测标签，不改变 EventBus routing、subscription 或 sequence；
- [ ] 已入队任务与调用方可变 request/容器引用脱钩。

## 18. 命名与 ID 分层补丁

> **补丁日期**：2026-08-20
>
> **适用阶段**：W0-P0 至 P3
>
> **裁定目的**：让类型名称直接表达其持有的身份维度，同时明确相似 ID 不代表需要新的公共身份模型。

### 18.1 规范名称与兼容别名

规范模型固定为：

```text
ActorIdentity
  user_id
  agent_id
  team_id

WorkspaceIdentity
  owner_user_id
  workspace_key
  workspace_id

IdentityScope
  actor_identity: ActorIdentity
  workspace_identity: WorkspaceIdentity
```

`ActorIdentity` 回答“谁在执行”，`WorkspaceIdentity` 回答“访问哪个资源归属域”，`IdentityScope` 冻结两者组成的硬身份边界。真正只属于 Workspace 资源体系的 `WorkspaceAsset`、`WorkspaceAssetStore`、`WorkspaceRuntime` 等名称保持不变。

迁移期允许以下直接别名，但不新增字段、包装层或第二份序列化结构：

```python
Identity = ActorIdentity
MemoryCreationContext = IdentityScope
WorkspaceAccessContext = IdentityScope
```

`WorkspaceAccessContext` 只能作为直接兼容别名，不能继续暗示它包含 `interaction_id`。`WorkScope`、`InteractionScope`、`OperationScope`、`BaseIdentityScope`、`WorkScopeSnapshot` 和 `WorkspaceSecurityScope` 不再作为公共设计引入；历史代码若暂时引用它们，必须在对应迁移任务中删除或收敛为上述规范模型，而不能在新 codec 或新文档中扩展。

### 18.2 ID 分层规则

| 字段 | 规范语义 | 权威持有者 | 是否进入 IdentityScope |
|:---|:---|:---|:---:|
| `interaction_id` | 一次逻辑 Chat Interaction 的稳定业务关联 | `ChatRun`、`InteractionSubmission` | 否 |
| `intent_id` | 一次生成意图 | `MemoryGenerationTaskSpec` | 否 |
| `task_id` / `work_id` | 队列任务与执行记录 | Queue/WorkRecord | 否 |
| `generation_id` | 旧 Chat 控制 API 兼容句柄 | `interaction_id` 的只读投影 | 否 |
| `agent_run_id` | Alice Agent 执行实例 | `RuntimeScope` / `RunSession` | 否 |
| `frame_id` / `action_id` | Agent 内部执行坐标 | `RuntimeScope` | 否 |
| `request_id` | 单次 HTTP/transport 请求 | adapter / middleware | 否 |
| `trace_id` | 日志、span 和事件追踪 | tracing infrastructure | 否 |
| `parse_operation_id` / `materialization_id` | 解析或物化状态机的局部操作 | 对应领域对象 | 否 |

这些 ID 不能因为都需要与身份边界共同传递，就被机械地包装成 `IdentityScope + id` 的公共类型。只有具体领域真正消费的 ID 才进入具体 DTO；没有实际消费者的字段不应预留。

### 18.3 ChatRun 与 Alice Runtime 示例

```python
@dataclass(frozen=True)
class ChatRun:
    identity_scope: IdentityScope
    interaction_id: str


class RuntimeScope(BaseModel):
    identity_scope: IdentityScope
    agent_run_id: str
    frame_id: str
    action_id: str | None = None

    model_config = ConfigDict(frozen=True, extra="forbid")
```

`ChatRun` registry、cancel、status、SSE 事件和异步 payload 的 Chat 关联使用 `interaction_id`。旧 `generation_id` 可继续出现在外部 JSON，但只能作为只读兼容投影，不得重新生成、持久化或成为第二索引事实。`RuntimeScope` 的执行坐标只用于运行隔离、事件关联和内部状态管理，不能成为资源 ownership 或授权输入。

### 18.4 命名与 ID 验收

- [ ] 新领域模型与公共契约只使用 `ActorIdentity`、`WorkspaceIdentity`、`IdentityScope`；
- [ ] `IdentityScope` 不包含 interaction、generation、agent run、frame、request、trace 或通用 operation ID；
- [ ] 一个聚合或 payload 只物理保存一份规范 IdentityScope；
- [ ] `InteractionSubmission` 与 `MemoryGenerationTaskSpec` 不保存重复身份字段；
- [ ] 内部 ChatRun 只保存一份 `interaction_id`；`generation_id` 仅为只读兼容投影；
- [ ] 不使用无命名空间的裸 `run_id`，统一使用 `agent_run_id` 或明确的领域名称；
- [ ] `request_id`/`trace_id` 不参与 ownership、授权、资源过滤、幂等或 ordering；
- [ ] WorkItem 与 RuntimeEvent 中的多个 ID 均有唯一权威来源。
- [ ] `IdentityScope` 及其 fingerprint/展开 tuple 不参与任何 W0 组件的 cache、registry、queue、scheduler、runtime、EventBus 或 service-container 分隔 key。
- [ ] `RuntimeEvent.workspace_id` 只用于观测，不改变事件路由、订阅、sequence 或授权。
