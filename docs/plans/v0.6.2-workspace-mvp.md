# v0.6.2 W0 Workspace MVP 实施计划

**文档状态**：Planned

**目标版本**：`v0.6.2 W0`

**完成定义**：同一用户、同一 Agent 通过同一套共享子系统并发进入两个 Workspace 时，Active Chat、Topic、Memory、Artifact、cache、background work 和进程内 WorkspaceAsset 均保持正确的 Workspace scope，且所有深层资源操作都不能靠 ID、默认值或 cache 命中绕过隔离

**后续计划**：`v0.6.2 W1 Chat Attachments`，必须在本计划完成后独立建立和实施

---

## 1. 计划定位

本计划将 [Workspace MVP 与 Chat Attachments 初步设计](../ideas/workspace-mvp-chat-attachments-design.md)中已经冻结的 W0 决策转录为正式实施顺序。W0 建立的是资源身份、访问上下文、逻辑隔离和进程内资产 working set；它不是附件功能的首个迭代，也不以真实上传演示作为完成条件。

依赖关系固定为：

```text
v0.6.1 released baseline
  -> v0.6.2 W0 Workspace MVP
       -> v0.6.2 W1 Chat Attachments
            -> v0.7.0 Document Ingestion & Provenance Contract
```

W1 只能消费 W0 已经稳定的 `WorkspaceIdentity`、`WorkspaceAccessContext`、WorkspaceAssetStore 和 Topic binding 契约，不得在附件代码内建立第二套 scope、临时容器或默认 Workspace fallback。

## 2. 当前基线与缺口

当前代码已经具备单用户条件下可运行的 Active Chat、Gateway workflow、Patchouli prepare/finalize、Alice frame、Interaction Submission 和 Memory Generation queue，但资源寻址仍隐含单 Workspace 假设：

- `Identity` 同时被用于表达执行者和资源过滤，而它只包含 user、agent、team 与兼容性 session 字段；
- `ChatGenerationRun`、`GatewayExecutionState`、`PreparedAgentRun`、`AgentRunContext`、`ExecutionFrame`、`MTPExecutionContext` 和 `InteractionPayload` 没有统一的 Workspace 坐标；
- `SemanticBuffer`、`TopicData` 和短期存储主要按 `user_id/topic_id` 组织，裸 `topic_id` 仍可能成为事实上的访问凭证；
- `MemoryVisibility.WORKSPACE` 当前实际表示 team scope，`PUBLIC` 当前又会在同一用户过滤后充当更宽可见性，名称与新 Workspace 轴冲突；
- Qdrant filter 只有 `user_id` 硬过滤，缺少 `owner_user_id + workspace_id` 硬过滤；
- Artifact filesystem adapter 允许按全局 ID 递归查找，并可从 `ArtifactRef.uri` 直接读取物理路径，尚无 Workspace-aware index；
- `KoakumaAtomCache` 以 alias/UUID 为核心 key，`AgentProfileResolver` 也没有 Workspace 维度；
- Interaction、Memory Generation 与其他可重试 work 的 payload、ordering key 和 idempotency key 尚未统一携带 Workspace scope；
- System 尚无可承载未资产化运行时文件的权威 working set。

因此 W0 的实施顺序必须先建立身份与传播，再迁移现存资源过滤，最后接入 WorkspaceAssetStore 和 Topic binding。反向顺序会让新资产运行在仍可漂移的权限域中。

## 3. 目标与非目标

### 3.1 目标

1. 引入不可变、可序列化的 `WorkspaceIdentity`，默认 Workspace 为 `main_workspace`。
2. 引入不可变的 `WorkspaceAccessContext`，把 actor identity、asset scope 和唯一 `interaction_id` 冻结为一次 request/run 的规范上下文。
3. 默认 Workspace 只在最外层入口解析一次；进入领域链后缺少 scope 必须失败。
4. 让 Gateway、Patchouli、Alice、MemoryLibrary、MTP、finalize、background work 和 RuntimeEvent 使用同一份 scope snapshot。
5. 让 Memory、Artifact、Topic、cache、work payload 和控制面查询按 `(owner_user_id, workspace_id)` 逻辑隔离。
6. 在不批量改写历史数据的前提下提供受控 compatibility-read/filter。
7. 由 System runtime 建立一个进程级 WorkspaceAssetStore，并实现 WorkspaceAsset/AssetRepresentation 两级状态机、READY-only 读取、删除和进程内 lease。
8. 由 Patchouli SemanticBuffer/ShortTermMemoryStore 拥有幂等的 `TopicAssetBinding`。
9. 使用第二个仅供后端验证的 Workspace 建立端到端不串台证据。
10. 为 W1 冻结窄化的资产读取接口，但不实现上传、解析或上下文编译。

### 3.2 非目标

本计划不实现：

- multipart 上传、附件 API、Composer 交互或 Workspace 切换 UI；
- 真实文本/PDF/DOCX/OCR/图像解析器、parser registry 或自动解析重试；
- `ChatRequest.asset_refs` 的真实附件接入、Context Compiler 或 prompt 注入；
- `RunAssetSelection`、`ContextAssetUse` 和 Artifact promotion 的生产链路；
- `DocumentArtifact` 的附件提升、多级 locator 或完整 provenance saga；
- WorkspaceAsset、原始内容和解析结果的跨进程持久化或重启恢复；
- durable tombstone、保留期、完整 GC、分布式 lease 或对象存储；
- Workspace Registry、独立 opaque Workspace ID 生成、rename、Mount、Bridge、跨 Workspace 通信或 grant 管理；
- 为每个 Workspace 创建 Gateway/Patchouli/Alice/MemoryLibrary/queue/runtime 实例；
- 把 AtomCache、ProfileCache 搬入 WorkspaceRuntime；W0 只修正它们的 key 与授权边界；
- 历史数据批量转换脚本的执行；脚本必须在 W0 落地并通过隔离验证后独立提供。

## 4. 冻结的身份与隔离契约

### 4.1 WorkspaceIdentity

规范模型为：

```text
WorkspaceIdentity
  owner_user_id
  workspace_key
  workspace_id
```

MVP 不变量：

```text
owner_user_id != ""
workspace_key != ""
workspace_id != ""
workspace_id == workspace_key
default workspace_key == workspace_id == "main_workspace"
```

完整资源坐标为 `(owner_user_id, workspace_id)`。`workspace_key` 只用于默认解析和未来 registry lookup；所有对外协议、资源键、过滤器、cache、event 和 work payload 使用 `workspace_id`。领域内部禁止 `workspace_id or workspace_key` fallback。

W0 不启用独立 ID 生成器，也不建立 Workspace Registry。普通产品请求解析到当前用户的 `main_workspace`；测试和内部服务可以显式构造：

```text
WorkspaceIdentity(
  owner_user_id=current_user_id,
  workspace_key="isolation_workspace",
  workspace_id="isolation_workspace",
)
```

这只是隔离测试 seam，不代表 W0 开放了 Workspace 创建或切换产品能力。

### 4.2 WorkspaceAccessContext

规范模型为：

```text
WorkspaceAccessContext
  actor_identity: Identity
  workspace_identity: WorkspaceIdentity
  interaction_id
```

规则如下：

- `interaction_id` 在 AccessContext 冻结前生成，一次 Chat run 只有一个；
- HTTP `request_id` 可以继续用于 transport/logging，但不进入 AccessContext；
- `Identity.user_id` 表示执行者，`WorkspaceIdentity.owner_user_id` 表示资源域 owner；二者相等是 W0 的访问条件，不是可互相覆盖的别名；
- Agent/Team 是 actor policy 轴，Workspace 是 asset ownership 轴；二者正交；
- 子 Frame、MTP 和后台 work 只能继承或缩小 scope，不能切换 Workspace；
- AccessContext 是请求级坐标，不是永久 capability token，最终资源所有者仍要重验。

统一授权谓词为：

```text
Allowed
  = same_owner_user
  AND same_workspace
  AND match_actor_visibility
```

任何 `same_agent`、`same_team`、opaque ID、cache hit 或 Artifact URI 都不能绕过前两项硬边界。

### 4.3 默认解析与失败规则

默认 `main_workspace` 只允许在 HTTP、Passive ingress 或其他顶层 adapter 进入应用服务时解析。W0 的公共 Chat 产品面可以继续不暴露切换 UI；如果传输 DTO 预留 `workspace_id`，只使用这一规范名称，并在没有已知 Workspace/内部测试入口时拒绝非默认值，不从 `workspace_key` 推导。

进入以下任一内部边界后，缺少完整 AccessContext 必须返回稳定错误或抛出受控领域异常：

- Gateway process；
- Patchouli prepare/retrieve/finalize；
- Alice run/frame/MTP；
- Topic、Memory、Artifact、WorkspaceAsset 读写；
- cache resolve；
- background handler attempt。

禁止共享 Runtime、Service、Store 或 Familiar 保存进程级 `current_workspace`。ContextVar 只可用于日志关联，不能作为授权输入。

## 5. 目标架构与所有权

```text
HiveMemorySystem
  ├─ one GatewaySystem
  ├─ one PatchouliSystem
  │    └─ one MemoryLibrary
  ├─ one AliceSystem
  ├─ one WorkspaceRuntime                  # 可选的极薄聚合
  │    └─ one WorkspaceAssetStore          # System-owned
  ├─ one Local Work Queue Runtime
  └─ one RuntimeEventBus

request/run
  └─ immutable WorkspaceAccessContext
       ├─ actor Identity
       ├─ WorkspaceIdentity
       └─ interaction_id
```

### 5.1 权威所有者

| 状态 | 权威所有者 | W0 责任 |
|:---|:---|:---|
| 默认 Workspace 解析 | System application boundary | 构造并验证 WorkspaceIdentity 与 AccessContext |
| WorkspaceAsset、representation、parse state、lease | System WorkspaceAssetStore | 进程内 working set、状态和可用性真相 |
| TopicAssetBinding | Patchouli ShortTermMemoryStore / SemanticBuffer | Topic 内幂等关联与 Topic 生命周期清理 |
| Memory 与检索 policy | Patchouli / MemoryLibrary | 持久归属、Workspace hard filter、actor visibility |
| Artifact 与 provenance | Patchouli / ArtifactStore | 持久归属、append-oriented 证据访问 |
| Run/Frame/MTP | System control / Alice | 保存本 Run 的冻结 scope，不取得资产所有权 |
| WorkRecord | Local Work Queue Runtime | 机械执行状态；业务 payload 自带可序列化 scope |
| RuntimeEvent | 事件生产域 | 投影 workspace_id 供观测，不参与授权 |

### 5.2 组合约束

推荐新增：

```text
src/hivememory/core/models/workspace.py
  WorkspaceIdentity
  WorkspaceAccessContext
  Workspace / WorkspaceKind / WorkspaceStatus（仅保留 MVP 必需字段）

src/hivememory/core/models/workspace_asset.py
  WorkspaceAssetRef
  WorkspaceAssetState
  AssetRepresentationState
  AssetRepresentationKind
  read-only snapshots / lease DTOs

src/hivememory/system/runtime/workspace/
  runtime.py
  store.py
  ports.py
  errors.py
```

`SystemAssembler._build_runtime()` 构造唯一 Store。实现可以选择 `_RuntimeBundle.workspace_runtime`，也可以暂时使用 `_RuntimeBundle.workspace_asset_store`；选择标准是依赖最窄、生命周期清晰，而不是提前把 cache、registry 和 service 全部塞进 WorkspaceRuntime。

HiveMemorySystem/WorkspaceRuntime 不得成为 service locator。消费者只接收 `WorkspaceAssetReader`、命名 command port 或 Topic binding cleaner 等窄接口。

## 6. 数据模型与运行时契约

### 6.1 资源身份投影

领域内使用 `WorkspaceIdentity`；持久化或索引层可平铺：

```text
owner_user_id
workspace_key
workspace_id
```

这些字段必须从同一 `WorkspaceIdentity` 原子投影。`source_agent_id`、`source_team_id` 记录 provenance，`visibility` 记录 actor policy，三者均不能代替资产归属。

W0 新写入的 Memory、Artifact、Topic 和可持久化 work payload 必须具有完整 WorkspaceIdentity 投影。遇到只存在部分 Workspace 字段的记录视为歧义数据：拒绝纳入第二 Workspace，并记录可观测诊断，不能猜测补齐。

### 6.2 Memory 与 visibility 过渡

目标可见性语义为：

```text
PRIVATE    -> 仅创建 Agent
TEAM       -> team_id 匹配
WORKSPACE  -> 当前 Workspace 内任意合法 Agent
```

当前持久化值仍为：

```text
旧 PRIVATE    -> 目标 PRIVATE
旧 WORKSPACE  -> 目标 TEAM
旧 PUBLIC     -> 目标 WORKSPACE
```

W0 的在线主链路先增加 Workspace hard filter，并通过一个命名的 legacy visibility adapter 解释旧值，不在业务代码中散落字符串判断。W0 不执行批量枚举改写；目标 `TEAM/WORKSPACE` 序列化切换、schema/version 标记与历史回填由 W0 验收后的独立脚本完成。在该脚本完成前，不能仅凭字符串 `WORKSPACE` 判断它是新 Workspace-visible 还是旧 team-visible。

检索谓词必须先应用：

```text
meta.owner_user_id == access.workspace_identity.owner_user_id
AND meta.workspace_id == access.workspace_identity.workspace_id
```

然后才应用 actor visibility。`PUBLIC` 的历史兼容语义也不能绕过 user/workspace hard filter。

### 6.3 历史记录 compatibility-read

脚本执行前，只允许以下兼容投影：

```text
访问 user U 的 main_workspace：
  current = owner_user_id == U AND workspace_id == "main_workspace"
  legacy  = user_id == U AND owner_user_id missing AND workspace_id missing
  result  = current OR legacy

访问 user U 的任意第二 Workspace W：
  result = owner_user_id == U AND workspace_id == W
```

兼容投影只存在于 storage adapter/filter builder。领域模型、cache、work handler 和 retry 不能把缺字段记录自动解释为当前 active Workspace。

### 6.4 Topic 资源键

`SemanticBuffer` 与 `TopicData` 增加 WorkspaceIdentity 投影。Short-term port/store 的权威资源键从裸 `topic_id` 收紧为：

```text
(owner_user_id, workspace_id, topic_id)
```

所有 get/list/create/pop/exists/compact/evict 路径接收 AccessContext 或已经验证的 `WorkspaceTopicKey`。只读 `TopicSnapshot` 至少保留足以在应用层重验 owner/workspace 的字段。裸 topic ID 仍可作为展示或路由标识，但不是授权凭证。

### 6.5 Artifact 资源键

`BaseArtifact`、`ArtifactRef` 的内部投影和 Artifact builder 输入补齐 Workspace 归属。ArtifactStore 的读取接口必须带 AccessContext 或明确标记为已经由 Patchouli 内部 provenance 流程验证的窄调用；不能通过 artifact ID 或 `ArtifactRef.uri` 直接获得读取权限。

filesystem adapter 至少完成：

- 物理路径或索引按 owner/workspace 分区；
- 以 `(owner_user_id, workspace_id, artifact_id)` 查找；
- 同 ID 不覆盖另一 Workspace 的 Artifact；
- 调用方提供的 URI 不作为授权或任意文件读取入口；
- 历史无 Workspace 字段 Artifact 只在对应用户 `main_workspace` 的兼容读取中可见。

W0 不实现 DocumentArtifact promotion，但必须保证已有 Interaction/Memory Artifact 不会跨 Workspace 读取。

### 6.6 Cache 与 work scope

W0 不迁移 cache 所有权，只修正逻辑分区：

```text
Memory object cache key
  = owner_user_id + workspace_id + memory_id

Alias resolution cache key
  = owner_user_id + workspace_id + alias

Profile cache key
  = owner_user_id + workspace_id + agent_id + team_id + alias
```

如果命中结果受 PRIVATE/TEAM policy 影响，key 还需包含相应 actor scope，或在命中后交回资源所有者重验。cache miss 可以降级，cache hit 不能扩大权限。

可重试业务 payload 使用：

```text
WorkScopeSnapshot
  actor_identity
  workspace_identity
  interaction_id or operation_id
```

Interaction Submission、Memory Generation 和纳入 W0 的 lifecycle payload/codec 均序列化该快照；ordering/idempotency key 加入 owner/workspace，handler 每次 attempt 重新授权。通用 `WorkItem` 不必理解 Workspace 领域模型。

## 7. WorkspaceAssetStore 契约

### 7.1 模型

```text
WorkspaceAsset
  asset_id
  workspace_identity
  created_by_agent_id
  created_by_team_id?
  visibility
  kind
  display_name
  media_type
  size_bytes
  required_representation_kind
  representations[]
  state
  safe_error_code?
  safe_error_message?
  created_at

AssetRepresentation
  representation_id
  workspace_identity
  asset_id
  kind
  revision
  content_object
  content_hash
  producer
  producer_version
  parse_operation_id?
  state
```

用户未来只持有 opaque `WorkspaceAssetRef`。文件名、asset ID、representation ID 和 content hash 都不是授权凭证。

### 7.2 两级状态机

```text
AssetRepresentation
  PENDING -> PROCESSING -> READY
                        -> FAILED

WorkspaceAsset
  PROCESSING -> READY
             -> FAILED

  PROCESSING / READY / FAILED -> REMOVED
```

规则：

- RAW 可以在注册时 READY；
- 文档型资产的 required representation 固定为 `EXTRACTED_TEXT`；
- RAW READY 不能单独令 WorkspaceAsset READY；
- required representation READY 时 Store 原子推动 asset READY；
- required representation FAILED 时 Store 推动 asset FAILED；
- FAILED 不自动 retry；用户重新上传将使用新的 operation identity 和 asset ID；
- READY 冻结 content object、hash、producer/version 和 revision；
- parse result 必须带预期 revision 或 operation token；REMOVED 后的晚到结果只能拒绝或丢弃；
- 只有 READY asset 可 resolve、bind、selection 或 acquire lease。

W0 不运行真实 parser。测试通过 Store 命名 command 构造 PENDING/PROCESSING/READY/FAILED 转换，不得直接改对象字段。

### 7.3 最小命名接口

Store/port 至少提供语义等价的命名能力：

```text
create_asset(access_context, metadata, client_operation_id)
register_raw_representation(...)
start_representation(...)
complete_representation(..., expected_revision_or_token)
fail_representation(..., safe_error)
resolve_asset(access_context, asset_ref)
list_workspace_assets(access_context)
acquire_ready_representation(access_context, asset_id, preference)
release_representation_lease(lease_id)
remove_asset(access_context, asset_id)
```

具体名称可在实现 PR 中按代码风格调整，但不能退化为暴露内部 dict 或可变模型。

### 7.4 幂等、删除与 lease

进程内上传/创建幂等键预留为：

```text
owner_user_id + workspace_id + actor + client_operation_id
```

相同 operation replay 返回同一资产及权威状态；相同 content hash 只允许内容对象去重，不能合并两个用户层面的逻辑资产。

删除顺序固定为：

1. AssetStore 原子将资产置为 REMOVED，立即拒绝新 resolve/bind/lease；
2. System 应用服务通过 Patchouli 的窄化 binding-cleanup contract 幂等清理 Topic binding；
3. dangling binding 在读取 Topic assets 时必须被过滤，不能恢复授权；
4. 无活跃 lease 时释放内容对象；已有 lease 保持到进行中消费者释放；
5. 最后一个 hold 释放后再物理回收 representation。

W0 lease 是进程内 hold，不承诺跨重启恢复，也不实现 durable tombstone。进程重启后旧 ref 返回明确的 `ASSET_NOT_FOUND` 或 `ASSET_EXPIRED`，绝不能解析到同名或复用 ID 的其他资产。

## 8. TopicAssetBinding 契约

### 8.1 所有权与模型

```text
TopicAssetBinding
  workspace_identity
  topic_id
  asset_id
  bound_by
  bound_at
  first_bound_interaction_id
```

binding 跟随 `SemanticBuffer`，由 `ShortTermMemoryStore` 的命名方法维护：

```text
ensure_asset_binding(access_context, topic_id, asset_snapshot)
detach_asset_binding(access_context, topic_id, asset_id)
list_asset_bindings(access_context, topic_id)
detach_asset_from_workspace_topics(access_context, asset_id)
```

唯一性为 `(owner_user_id, workspace_id, topic_id, asset_id)`。并发首次绑定同一资产只产生一条关系。调用方不能直接修改 buffer 内列表。

新建 WorkspaceAsset 以零 binding 开始，这是合法状态，不是 orphan 或失败。W0 的 create/register 操作不得根据“最近上传”“当前活跃 Topic”或进程级 pending list 自动建立关系；未来 W1 只能在 Chat 完成路由、READY ref 通过当前 AccessContext 校验并被该请求接纳后建立 binding。

W0 没有真实 `asset_refs` 请求，因此测试或内部 walking skeleton 必须先通过 Store 获得 READY asset snapshot，再调用 binding 命令；不允许为了测试绕过 READY 校验。

### 8.2 生命周期矩阵

| 操作 | Topic 是否仍存在 | binding | WorkspaceAsset |
|:---|:---:|:---:|:---:|
| manual settle / compact | 是 | 保留 | 保留 |
| token-overflow compact | 是 | 保留 | 保留 |
| clear blocks/reset content | 是 | 默认保留 | 保留 |
| Topic detach | 是 | 仅删指定关系 | 保留 |
| IDLE/LRU/SHUTDOWN evict | 否 | 随 buffer 清除 | 保留 |
| 显式 Topic delete/pop | 否 | 随 buffer 清除 | 保留 |
| WorkspaceAsset delete | Topic 可存在 | 幂等清理；残留读取过滤 | REMOVED |

binding 只表示 Topic working set 中可再次选择，不承担 provenance，不表示自动注入，也不创建 Artifact。

## 9. Scope 端到端传播

Active Chat 的规范顺序为：

```text
server adapter
  -> generate interaction_id
  -> build actor Identity
  -> resolve main_workspace
  -> validate owner/status
  -> freeze WorkspaceAccessContext
  -> register ChatGenerationRun
  -> Gateway
  -> Patchouli prepare
  -> Alice run / child frame / MTP
  -> Patchouli finalize
  -> InteractionSubmission / Memory Generation work
```

| 当前落点 | W0 改造 |
|:---|:---|
| `server/models/chat.py`、`server/routers/chat.py` | 顶层默认解析输入；stop/status 携带并校验 owner/workspace，而非只信任 generation ID |
| `system/application/chat_service.py` | 生成唯一 interaction_id，冻结 AccessContext，并向全链传递 |
| `system/runtime/control.py` | `ChatGenerationRun` 保存 interaction_id、AccessContext/scope fingerprint；registry 查询和 cancel 重验 scope |
| `gateway/workflow/state.py`、`gateway/context.py` | state/snapshot 保存不可覆盖的 AccessContext；Topic candidate/routing 使用 scoped read |
| `gateway/contracts/public_routes.py` | route payload 接收 AccessContext，不重复拼装裸身份字段 |
| `patchouli/models.py`、`patchouli/service.py` | `PreparedAgentRun` 保存原始 AccessContext；prepare/retrieve/finalize 复用同一对象 |
| `patchouli/contracts/public_routes.py` | 跨边界请求显式携带 scope snapshot |
| `core/protocol/models.py` | `AgentRunContext`、`InteractionPayload` 保存 AccessContext |
| `alice/application/agent_run_service.py` | root frame 从 AgentRunContext 继承 scope |
| `agent_runtime/models.py` | `ExecutionFrame`、`MTPExecutionContext` 保存相同 AccessContext |
| child CALL/frame factory | 子 Frame 继承 hard boundary；context refs 只能缩小选择 |
| interaction/memory generation codecs | 序列化 WorkScopeSnapshot；retry 不依赖进程当前值 |
| RuntimeEvent producers | metadata 投影 workspace_id/interaction_id，仅用于观测 |

同一 Run 必须满足：

```text
Gateway scope
  == Patchouli prepare scope
  == Alice root/child frame scope
  == MTP scope
  == Patchouli finalize scope
  == InteractionPayload/work scope
```

finalize 不再接收另一组可漂移的裸 `user_id/agent_id/workspace_id`。如果 prepare snapshot 与 control registry 的 scope fingerprint 不一致，Run 失败并禁止写入。

Passive ingress 不获得例外：顶层 passive adapter 为 actor 构造默认 `main_workspace` AccessContext，conversation key、InteractionPayload、ordering key 和 retry payload 均带 scope。W0 不为 passive connector 开放 Workspace 选择。

## 11. 测试计划

所有测试遵循 [测试设计标准](../governance/testing/test-design-standards.md)。每个测试只属于 unit、integration 或 e2e 一层；权限、过滤、状态迁移、幂等和并发通过可观察行为断言，不使用 mock 镜像、恒真断言、宽松断言或固定 sleep。

### 11.1 Unit

|:---|:---|:---|
| `tests/unit/core/models/` | WorkspaceIdentity 非空/等值、AccessContext 冻结与 round-trip | `None`、key fallback、字段漂移 |
| `tests/unit/system/runtime/workspace/` | representation/asset 状态机、READY-only、幂等 create、late callback、delete/lease | RAW 误判 READY、FAILED 自动复活、REMOVED 被回调复活、hold 提前释放 |

| `tests/unit/engines/retrieval/` | current/legacy filter、visibility 顺序、partial field reject | 第二 Workspace 召回 legacy、team/agent 绕过 Workspace |
| `tests/unit/engines/artifacts/` | composite lookup、URI/ID 不授权、同 ID 隔离 | 全局 rglob 或 URI 导致越权读取 |
| `tests/unit/agent_runtime/aliases/` | owner/workspace cache key、命中重验 | A 的 alias/UUID 命中污染 B |

并发用例使用 event/barrier 或有界轮询，不用固定 `sleep` 证明时序。

### 11.3 E2E

扩展 `tests/e2e/pipeline/test_chat_run_e2e.py` 或增加独立 Workspace pipeline：

1. 同一 user/agent 在 main_workspace 与 isolation_workspace 启动并发 run；
2. 两侧建立同名 Topic、Memory、Artifact 和 WorkspaceAsset；
3. 交错执行 prepare、Alice frame、finalize、cancel/status 和 retry；
4. 分别读取 Topic/Memory/Artifact/asset，断言只返回当前 Workspace；
5. 删除 A 的 asset/topic，断言 B 不受影响；
6. 用 A 的 opaque ID 从 B 访问，必须稳定拒绝；
7. main_workspace 可以读取对应 user 的 legacy fixture，B 不可读取；
8. 进程内 Store 重建后旧 asset ref 明确失效，不解析到新资产。

E2E 使用固定/内存 Agent 响应和真实系统编排，不依赖外部 LLM、Qdrant 或真实附件。

## 13. 发布、回滚与风险控制

### 13.1 发布顺序

1. 先落核心模型和 dual-read compatibility，不改变历史数据；
2. 再让入口和内部链路显式传播 scope；
3. 再启用 Memory/Artifact/Topic hard filter 与新写入 Workspace 投影；
4. 再修正 cache/work key；
5. 最后接入 WorkspaceAssetStore 和 binding；
6. 双 Workspace 验收通过前，不建立 W1 上传入口；
7. W0 稳定后另行运行历史数据转换脚本。

各阶段不得以“缺 scope 时回退 main_workspace”维持内部兼容。兼容只允许在顶层默认解析和 storage legacy projection 两处存在。

### 13.2 回滚边界

- W0 不执行历史批量转换，因此 P0-P6 失败时可以停用新入口并回滚代码，不需要反向改写全部历史记录；
- 已由 W0 写入的 Workspace 字段是扩展字段，回滚前必须确认旧 reader 对扩展字段安全忽略；
- 可见性新枚举值的批量写入后置，避免在 W0 验证期制造旧版本无法解析的 `TEAM` 数据；
- 如果已产生只有新版本理解的记录，禁止盲目降级，必须先使用配套兼容 reader 或转换工具读回验证；
- WorkspaceAsset 和 binding 是进程内状态，进程重启可清空，但必须向旧 ref 返回明确失效，不承诺恢复。

### 13.3 主要风险

| 风险 | 控制 |
|:---|:---|
| scope 参数改造面过大 | 先冻结单一 AccessContext，按传播链逐段迁移，禁止重复裸字段 |
| 新旧 visibility 语义冲突 | 命名 legacy adapter，批量枚举转换后置，转换时引入明确 schema/version |
| Artifact 全局路径造成越权 | 复合索引、scope-aware Store、URI 不授权、同 ID 隔离测试 |
| cache 修正遗漏 | 用同 alias/UUID 的 A->B 命中用例覆盖每个 cache consumer |
| 共享 Runtime 并发覆盖 | 禁止 `current_workspace`，并发 barrier 测试两个 AccessContext |
| AssetStore 与 binding 跨 owner 不一致 | Store 先 REMOVED、binding 后幂等清理、读取过滤 dangling relation |
| lease 演化成耐久事务 | W0 明确仅进程内 hold，不承诺 restart recovery |
| WorkspaceRuntime 变成超级容器 | 只聚合 asset store，依赖通过窄 port 注入 |
| W1 偷跑导致契约分叉 | W1 Plan 以 W0 验收为硬前置，不允许私有 scope/ref 模型 |

## 15. P1 补充裁定：AccessContext 的用户语义与渐进迁移

> **补丁日期**：2026-08-19
>
> **适用阶段**：W0-P1，并约束后续 P2/P3 的资源访问接口
>
> **裁定目的**：消除 `Identity.user_id` 与 `WorkspaceIdentity.owner_user_id` 同时存在时的读取歧义，并避免把 P1 错误实施为“用 WorkspaceAccessContext 全面替换 Identity”

### 15.1 两个用户字段保留，但不存在通用 user_id

`WorkspaceAccessContext` 中的两个用户字段分别回答不同问题：

| 字段 | 权威语义 | 典型用途 |
|:---|:---|:---|
| `actor_identity.user_id` | 谁正在执行本次操作 | 操作者审计、Agent/Team visibility、actor policy |
| `workspace_identity.owner_user_id` | 正在访问谁的资源命名空间 | Workspace 资源归属、Store key、检索硬过滤、Topic/Memory/Artifact owner |

W0 继续要求二者相等，但该等值关系是当前访问策略的不变量，不表示二者可以互相替代：

```text
access.actor_identity.user_id
  == access.workspace_identity.owner_user_id
```

因此 `WorkspaceAccessContext` 不得新增含糊的 `user_id` 属性。若频繁读取需要改善可读性，可以提供 `actor_user_id` 与 `workspace_user_id` 两个明确命名的只读投影；不得用单一兼容属性隐藏调用方究竟需要 actor 还是 resource owner。当前存在的通用 `RetrievalRequest.user_id` 等兼容投影应逐步改名或退出资源过滤路径。

移除 `WorkspaceIdentity.owner_user_id` 不是本问题的解决方案。WorkspaceIdentity 作为可独立持久化、进入 work payload 和资源 key 的完整坐标，必须在脱离 AccessContext 后仍能表达资源 owner。未来若引入授权 Agent 访问其他 owner Workspace 的 grant，两个用户字段可能合法不同；届时应将 same-owner 检查从 W0 构造不变量迁入显式 Workspace authorizer，而不能依赖通用 `user_id`。

### 15.2 AccessContext 是安全信封，不是新版 Identity

P1 的迁移目标调整为“完整传播 AccessContext，同时保留 Identity 的 actor 领域职责”。不得机械地把所有 `identity: Identity` 参数替换为 `access_context: WorkspaceAccessContext`。

| 边界或行为 | 规范输入 |
|:---|:---|
| HTTP/System application、跨子系统 Bus | `WorkspaceAccessContext` |
| Chat run、Gateway state、Prepared run、Interaction、可重试 work | 保存完整 `WorkspaceAccessContext` / `WorkScopeSnapshot` |
| Topic、Memory、Artifact、WorkspaceAsset 的授权入口 | `WorkspaceAccessContext` |
| 已完成授权后的 Store 内部寻址 | `WorkspaceIdentity`、`WorkspaceTopicKey` 或其他 scoped resource key |
| 只执行 Agent/Team visibility、persona、actor 展示的叶子逻辑 | `Identity` |
| RuntimeEvent | 从 AccessContext 显式投影所需观测字段，不作为授权输入 |

剩余 `Identity` 签名不自动视为迁移缺口。判断标准是该函数是否读取或改变 Workspace-owned resource：只做 actor policy 的纯逻辑可以继续接收 Identity；接触 Topic、Memory、Artifact、WorkspaceAsset 或 Workspace-sensitive cache 的边界必须获得完整 AccessContext 或已验证的 resource scope。

公共兼容入口使用“wrapper + strict scoped entry”模式：外层可以继续接受既有 `user_id/agent_id` 并一次性解析 `main_workspace`，内部入口只接受完整 AccessContext。内部方法不得同时接受可选的 `identity` 与可选的 `access_context`，也不得根据哪个参数存在来选择身份来源。

### 15.3 载体升级、叶子兼容

P1 采用以下渐进迁移模式：

```text
request/run carrier 保存一份 WorkspaceAccessContext
  -> actor-only 旧逻辑通过只读 identity 投影读取 actor_identity
  -> resource access 通过 access_context / workspace_identity 读取资源域
```

`AgentRunContext`、`InteractionPayload`、`ExecutionFrame`、`MTPExecutionContext` 等载体可以继续提供只读 `identity` 兼容属性，但该属性固定返回 `access_context.actor_identity`，且不能被资源访问代码当作完整授权上下文。兼容属性只减少 actor-only 叶子逻辑的迁移面，不得用于重新构造默认 Workspace。

同一个聚合内部只物理保存一份 AccessContext。若下层对象已经权威持有 AccessContext，上层通过只读属性派生，不再保存第二份字段后做等值检查。例如 `ExecutionFrame` 从 `RuntimeScope` 派生 AccessContext；`PreparedAgentRun` 应从 `AgentRunContext` 派生 AccessContext，而不是同时持有 `prepared_run.access_context` 与 `agent_run_context.access_context` 两份状态。

### 15.4 P1 实施与验收增量

W0-P1 在原出口之上增加以下要求：

- [ ] 代码中不存在 `WorkspaceAccessContext.user_id` 这一通用权威入口；
- [ ] actor policy 明确读取 actor Identity，资源归属与硬过滤明确读取 WorkspaceIdentity；
- [ ] request/run carrier 传播完整 AccessContext，但 actor-only 叶子逻辑不被迫改签名；
- [ ] 公共默认 Workspace wrapper 与内部 strict scoped entry 分离，内部不存在双身份来源；
- [ ] 一个聚合只物理保存一份 AccessContext，其他访问均为只读派生；
- [ ] 兼容 `identity` 属性只返回 actor identity，资源访问不能依赖它补建 Workspace；
- [ ] prepare、root/child Frame、MTP、finalize 和 work payload 仍保持同一完整 AccessContext；
- [ ] P2/P3 的 Topic、Memory、Artifact、cache 迁移继续使用 owner/workspace 复合资源键，不因 P1 保留 Identity 而降级。

测试只保护可观察的不变量与真实回归：cross-owner AccessContext 必须拒绝、prepare scope 漂移必须失败、子 Frame 必须继承完整 hard boundary、同一 actor 的两个 Workspace 不得串扰、资源过滤必须包含 Workspace ID。简单的 `actor_user_id`/`workspace_user_id` 属性不单独增加构造后回读测试；其正确性由上述权限和传播行为覆盖。
