# v0.8.1 结算拆成沉淀与退役：空闲时只沉淀，话题留在话题池

> 状态：Planned（2026-11-24）。v0.8.1 短期记忆的第一份计划；设计依据见[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 5 节。

## 1. 背景和问题

现在话题空闲 3600 秒就结算：结算被生成队列接纳后，话题立即从短期存储删除。用户断断续续地回到同一件事时，后台已经把话题关了，下一轮只能开新话题，后台的话题反而比前台的会话更不连贯：

- 日常实例 11 天 89 次结算中，空闲 77 次、关闭 11 次、LRU 1 次；
- 77 个空闲结算的话题中，32 个在 2 小时内被同一会话续上；续上的 65 次里，48 次开了新话题，例如“MemOS 仓库深度调研”在 97 分钟后被切成“通俗解读 MemOS 离线实测结果的含义”。

结算同时做了两件事：把话题整理进中期（沉淀），以及让话题离开话题池（退役）。用户断断续续地回来，反对的是空闲时退役；别的话题要尽早引用它的内容，要的是尽早沉淀。拆开之后两者都满足，话题的工作状态（短期记忆 Idea 第 3 节）也才有意义：话题熬得过停顿，回来的人才读得到它。

## 2. 目标与非目标

### 2.1 目标

- 空闲只触发沉淀：话题自上次沉淀之后有新的交互、且空闲超时，就把它交给生成；话题留在话题池，可以接着写、仍是 Gateway 的候选话题。
- 退役只由容量（池满时 LRU）、明确的结束（手动结算）与进程关闭触发：退役前对上次沉淀之后的新交互做最后一次沉淀，没有新交互则不生成。
- 同一话题多次沉淀时，本话题经任何途径写下的记忆进入同一份“本话题的写入”记录：主动写入结算到的记忆，与本话题之前几次沉淀产出的记忆，不分途径（[记忆生成](../patchouli/generation.md#42-本话题的主动写入)）。馆长经 `list_topic_writes` 看到它们；现有的一次性生成与 WRITE 规则对记录里的记忆一视同仁。每次沉淀仍读话题的全部材料。
- 话题池界面与设置说明按新语义改写。

### 2.2 非目标

- **话题跨重启保存**：在 v0.8.1 内另行计划；本计划中进程关闭时话题照旧沉淀并退役。
- **工作记录、推送与拉取、折叠摘要的结构化**：短期记忆 Idea 第 3、4、6、7 节，各自另行计划。
- **只沉淀新增部分的生成材料**：每次沉淀仍冻结全部交互记录与折叠记录，生成材料不变。
- **跨话题的查重与合并语义、Mode B 与 Mode C**：不变。

## 3. 当前状态（2026-11-24 核对）

- **结算时序**：`PerceptionService._settle_topic` 是所有来源（手动、空闲、LRU、关闭）共用的时序：取得 lease → 冻结全部交互与折叠记录为 `TopicMaterializeTask` → 锁外请求生成队列接纳 → 删除话题并移除驻留 → 发 `topic.settled`。没有材料时直接结束生命周期、不生成（[感知与短期话题](../patchouli/perception.md)）。
- **空闲与 LRU**：`TopicWorkingSet.list_idle_candidates` 按访问时间返回空闲超时且未被占用的驻留话题；`scan_idle_buffers_once` 逐个结算。建新话题且池满（`max_resident_topics`，随附配置 5）时按 LRU 结算一个话题。关闭时 `flush_all_for_shutdown` 结算全部驻留话题。
- **触发原因只作来源标签**：`TriggerReason` 的取值只写进 `TopicMaterializeTask` 的 provenance，不驱动分支。
- **本话题的写入记录**：生成控制器在进程内按话题记录主动写入结算到的正式记忆（`_topic_write_memory_ids`），WRITE 与 SETTLE 执行时放进 `GenerationRequest.topic_write_memory_ids`；SETTLE 执行成功后清除这个话题的记录；只记带 settlement 的结果（主动写入，以及吸收了写入新建记忆的合并所保留的那条）。被动沉淀新建的记忆不进记录。
- **生成结果**：`MemoryGenerationResult` 只有 canonical 身份、settlement、合并提名与被吸收的身份，不带新建、更新或触碰的动作；动作只在数据面的 `GenerationOutcome.action` 中。
- **生成队列信封**：1.3；关闭时未执行的工作保存到磁盘，下次启动继续。
- **事件**：`topic.settled` 的 `data` 带 `reason` 与 `generation_submitted`（[事件契约](../contracts/routes-and-events.md)）。
- **界面**：话题池按最后更新时间与空闲时长显示“约 N 分钟后自动结算”；设置页把 `idle_timeout_seconds` 写作“对话停多久后结算话题”，把 `max_resident_topics` 写作“超过时最久没用的话题被结算”（[管理视图](../frontend/management-views.md)第 1.2 节）。话题列表响应不含任何与结算进度有关的字段。

## 4. 进入条件

阻塞问题已决定（owner，2026-11-24）：结算拆成沉淀与退役；同一话题多次沉淀时，之前沉淀出的记忆记作本话题的写入（短期记忆 Idea 第 5 节）；本计划不做话题跨重启保存，进程关闭时照旧沉淀并退役。依赖均已是事实。

## 5. 目标设计

以下名字与数值是起草时的默认值，计划评审时可以调整。

### 5.1 话题记下已经沉淀到哪里

`TopicData` 新增 `settled_interaction_count`：最近一次被生成队列接纳的沉淀所覆盖的交互数，初值 0。沉淀在 lease 内冻结全部交互，被接纳后把它写回为冻结时的交互数；接纳失败不写回，下次重试。话题“有未沉淀的交互”即交互数大于它。字段只在进程内，随话题快照存储。

### 5.2 沉淀与退役的触发

- **空闲 → 沉淀**：空闲扫描只处理有未沉淀交互的候选；沉淀被接纳后话题留在存储与驻留集合中，访问时间不变。没有未沉淀交互的空闲话题不处理，所以同一段空闲不会反复沉淀。
- **LRU、手动结算、关闭 → 退役**：先在 lease 内判断是否有未沉淀的交互，有则做最后一次沉淀（接纳失败时与现在一样保留话题、可重试），然后删除话题并移除驻留；没有则不生成、直接退役。
- **手动删除不变**：`evict_topic` 直接退役、不生成。
- 两个用例共用现在的结算时序，只在“接纳之后是否删除话题”上分开。`TriggerReason` 的取值不变、仍只作来源标签；是否退役由用例决定，不读原因分支。

### 5.3 本话题的写入记录包含之前沉淀出的记忆

- `TopicMaterializeTask` 与 SETTLE 的任务规格新增 `retires_topic`：退役时的最后一次沉淀为真，空闲沉淀为假。
- `MemoryGenerationResult` 新增 `action`（新建、更新或触碰），由数据面从 `GenerationOutcome.action` 带出。
- 控制器在 SETTLE 执行之后：`retires_topic` 为假时不清除记录，把这次沉淀新建的记忆加入记录；为真时与现在一样清除。触碰与更新的记忆不加入。
- 合并吸收了记录中的记忆时，记录改为保留的那条，与主动写入一致。
- 没有生成任务的退役不另行清除记录：话题标识不会复用，残留只占少量内存，进程重启时清空。
- 馆长提示词中 `list_topic_writes` 的说明改为“本话题写入过的记忆：agent 主动写入的，以及本话题此前沉淀出的”。一次性生成与 WRITE 的现有规则不变，对记录里的记忆不分途径一视同仁，作用范围随记录扩大。

### 5.4 关闭

`flush_all_for_shutdown` 对全部驻留话题执行退役。关闭时保存的 SETTLE 照旧带上本话题的写入记录。

### 5.5 事件

每次沉淀都发 `topic.settled`，`data` 增加 `retired`（这次是否随之退役）；没有未沉淀交互的退役同样发 `topic.settled`，`generation_submitted` 为假、`retired` 为真。`topic.deleted` 不变。

### 5.6 话题池与设置

- 话题列表响应（`ActiveTopicResponse`）增加 `has_unsettled_interactions`。
- 话题池只对有未沉淀交互的话题显示倒计时，文字改为“约 N 分钟后沉淀”；工具栏的规则说明改为“话题空闲 N 分钟时，新内容会沉淀为长期记忆，话题仍留在池中；池满需要腾出位置时，最久没用的话题先沉淀再退出”。
- 设置页：`idle_timeout_seconds` 写作“对话停多久后沉淀话题”，`max_resident_topics` 写作“超过时最久没用的话题先沉淀再退出话题池”；手动结算按钮的语义不变（沉淀并退出）。
- `configs/config.yaml` 中两项的注释同步。`max_resident_topics` 默认仍为 5。

## 6. 受影响的系统、契约和数据

| 范围 | 改动 |
|:---|:---|
| Patchouli 感知 | 结算时序拆成沉淀与退役；空闲扫描只处理有未沉淀交互的话题；`TopicData.settled_interaction_count` |
| Patchouli 生成控制与数据面 | SETTLE 规格带 `retires_topic`；结果带 `action`；本话题的写入记录在沉淀后保留并加入沉淀新建的记忆，合并时改指 |
| 生成队列 | 信封升到 1.4，带 `retires_topic`；1.3 的保存项读回时按退役处理（旧语义下每次结算都退役） |
| 馆长提示词 | `list_topic_writes` 的说明（中英文） |
| 事件契约 | `topic.settled` 的 `data.retired` |
| HTTP 与前端 | 话题列表响应的 `has_unsettled_interactions`；话题池的倒计时与规则说明；设置页两项说明 |
| 配置 | 两项注释；键与默认值不变 |

不涉及 Workspace 能力层的授权与公开 route：手动结算仍经 root API 的 `settle_topic`，含义仍是结束话题的生命周期。

## 7. 兼容与迁移

- 话题只在进程内，没有存量需要迁移；升级后的第一次启动没有驻留话题。
- 生成队列保存文件中 1.3 的 SETTLE 项按 `retires_topic=true` 读回。
- 配置键不变，`idle_timeout_seconds` 的含义从“结算”变为“沉淀”，由设置页与文档说明。
- 话题会在池中待得更久，进程内的话题数量受 `max_resident_topics` 约束。

## 9. 风险与待决问题

- **重复仍可能出现**：一次性生成只丢弃查重为相同或相似、且命中记录中的记忆的草稿，换了说法的复述仍会新建；馆长是否避开靠提示词。8.3 的抽查用来判断要不要进一步处理。
- **成本与存储**：每次沉淀读全部材料、生成一份来源 InteractionArtifact，多次沉淀的话题成本与存储随次数增加；日常话题的交互中位 5 轮。
- **进程内占用**：话题在池中待得更久，单个话题的交互记录与结算载荷随轮次增长，没有容量上限以外的背压。
- **重启**：关闭时照旧沉淀并退役，重启仍会切开正在进行的工作，直到话题跨重启保存落地。
- 待评审的默认值：第 5 节中的名字；触碰与更新的记忆不加入记录；`max_resident_topics` 保持 5；话题列表新增的字段。

## 11. 实施记录

2026-11-24，分支 `feat/v0.8.1-settle-and-retire`。第 5 节的名字与数值都按起草的默认值实现，以下是计划没有写明、实现时补上或确认的部分。

### 11.1 计划之外补上的实现细节

- **沉淀进度的写函数**：`TopicData` 只经 core 话题模型的写函数写入，新增第三个写函数 `mark_topic_settled`，只改 `settled_interaction_count`，不改内容与 `last_update`（展示的最后写入时间与空闲计时都不因沉淀变化）。构造时校验计数不超过交互数。
- **快照带上进度**：话题列表经 `TopicSnapshot` 投影为 `ActiveTopicResponse`，`has_unsettled_interactions` 因此也加在 `TopicSnapshot` 上（缺省为假，由 `TopicData.to_topic_snapshot` 填写）。Gateway 渲染候选话题时逐字段取值，不受影响。
- **任务规格的 `retires_topic`** 缺省为假，非 SETTLE 的任务带真时构造即拒绝。1.3 保存项中只有 SETTLE 读回为退役，其余来源读回为不退役。
- **`MemoryGenerationResult.action` 是必填字段**；合并任务的结果记为 UPDATE（写回保留记忆的新版本）。
- **合并改指对两种来源一视同仁**：合并吸收的记忆在记录中时，记录删去被吸收的、加入保留的；主动写入被合并时，记录不再同时留着已删除的被吸收记忆。被吸收的记忆不在记录中、但结果带句柄结算时，照旧把保留的那条加入记录。
- **同一话题的结算依次执行**（code review 发现）：生成 lane 原本不按话题排序，同一话题的两次结算可能同时执行（空闲沉淀还在执行时用户手动结算，或重启后读回的同一话题的沉淀与退役同时开始），后一次读不到前一次新建的记忆，复述它们的草稿照常新建。现在生成 lane 开启按键排序，只有 SETTLE 任务带顺序键（话题 ID），写入、修订与合并的顺序键为空，照常并行；读回的保存工作按保存顺序执行。按键排序由队列强制开启，不是配置项。
- **前端**：除计划列出的倒计时、工具栏与设置页外，话题池的空状态说明与手动结算的提示也按新语义改写（手动结算在没有新内容时不建立生成任务，提示不再保证有生成进度可看）。

### 11.2 计划没有写明的后果，收尾时需要同步

- **没有接收过交互的空话题不再随空闲结束**：它没有未沉淀的交互，空闲扫描不处理，只在 LRU、手动结算或关闭时退役。`AGENTS.md` 第 4 节“建立后没有接收交互的话题由空闲结算或 LRU 回收”与[感知与短期话题](../patchouli/perception.md)第 3 节的同一说法，收尾时改为只由 LRU 回收（关闭时照旧退役）。
- **主动写入同样看到扩大的记录**：WRITE 执行时带上的是同一份记录，相似命中本话题此前沉淀新建的记忆时照常新建、不提名合并（与命中主动写入时相同）。这是记录不分途径、现有规则一视同仁的直接结果，owner 评审时确认保持（2026-11-24）：一次性生成与 WRITE 的这两条规则是现在的保障与兼容，在一次性生成重做之前不删除；在此之前，同一话题里可能留下相似的两条。[记忆生成](../patchouli/generation.md)第 4.2 节收尾时按“本话题的写入不分途径”改写。
- **生成 lane 的排序**：[记忆生成](../patchouli/generation.md)第 8 节“生成 lane 不按话题排序”一条收尾时改为只有同一话题的结算依次执行；排队等待前一次结算的结算不占执行位，但同一话题积压的结算会依次等待前一次的模型调用。

### 11.3 有意没有改的部分

- 对话页运行视图中 `topic.settled` 的标签仍写“话题结算”，`generation_submitted` 为假时显示“没有可保存的材料”，没有区分沉淀与退役；`data.retired` 已在事件中，界面是否展示留给后续。
- 馆长系统提示词开头“一段话题刚刚结束”没有改：计划只要求改 `list_topic_writes` 的说明，空闲沉淀时话题并未结束，这句是否调整留给评审。
