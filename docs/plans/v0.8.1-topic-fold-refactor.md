# v0.8.1 话题折叠的重构：折叠作为系统内部的材料压缩，写进展记录共用工作视图

> 状态：Planned（2026-11-27）。v0.8.1 短期记忆的第九份计划。设计依据是[短期记忆 Idea](../ideas/short-term-memory-and-context-compaction.md)第 6 节与第 1.5 节：话题折叠的重构完成之后，短期记忆 V1 才算初步成立。

## 1. 背景和问题

话题的交互记录只增长。系统内部有几个模型要读这份材料：记忆生成（馆长、一次性生成与主动写入）、写进展记录的写作者，以及写折叠摘要的写作者自己。材料太长时，这些模型的上下文会被撑爆。

owner 对折叠的定位是：折叠只是处理过长材料的一种手段，与前台 agent 的会话压缩作用相同，区别只在它是系统内部的处理。按这个定位，现在有四处不对：

- **写进展记录不经过折叠**：它读第 `recorded_until` 轮之后的全部原文，没有任何预算。超出模型窗口或超时（60 秒）就失败，同一位置之后不再重试；话题有了新交互，要整理的原文更长，下一次多半仍然失败。日常实例 2026-11-27 01:02 出现过一次 `progress_record_failed`（`TimeoutError`）。
- **折叠摘要被前台与 Gateway 读**：话题路由在话题没有 `topic_summary` 时用它，查询理解把它拼进话题背景，话题池的话题卡片与对话页的话题选择器把它当副标题，话题详情把它标为“较早内容的摘要”。界面上它与进展记录并排出现，读者分不清两者，owner 认为这两个概念对读者贴得太近。
- **提示词还停在旧定位**：折叠摘要的提示词按“核心目标、系统状态与已完成、约束与避坑、当前焦点”四段写，写明“供 Worker Agent 使用”，是话题当初承担 agent 上下文控制时留下的，写出来的东西本身就像一份给前台的进度总结。
- **递推重写丢细节**：每次折叠由模型把旧摘要与新折叠的轮次合成一份新摘要。日常 17 份折叠摘要中 16 份按四段写，文件路径多只保住 5% 以下；模型失败时回退的规则摘要只有请求数、工具名与 token 数，一份把约 79 万字符压成了 120 字符。话题保存的是折叠记录的列表，但每条存的是累积的整份摘要，只有最后一条被读，列表里重复保存着越来越长的副本。

## 2. 目标与非目标

### 2.1 目标

1. 折叠服务所有读材料的内部模型：记忆生成与写进展记录都读工作视图（已折叠部分的折叠摘要，加折叠之后的原文），控制材料长度只有折叠这一处。
2. 写进展记录共用工作视图：还没整理的轮次如果已经有一部分被折叠，这部分只给覆盖它们的折叠记录的摘要，其后给原文。
3. 其他读者不再读折叠摘要：话题路由与查询理解改读 `topic_summary` 与进展记录最近的一条，话题池与话题选择器改读进展记录；进展记录成为唯一面向前台的总结。
4. 折叠摘要结构化、只往后追加：每条折叠记录只存这一次折叠的摘要，工作视图的折叠摘要由折叠记录的列表按顺序拼接；模型只为这一次折叠的轮次写判断类的栏，不改写此前的摘要；规则抽取的部分由代码从被折叠的原文取出，模型失败时也照样写出。

### 2.2 非目标

- **单轮超过阈值**：在段的边界上折叠，以及一轮很大时每来一轮就折一次，属于短期记忆 V2。
- **controller 模式的注入**：话题的进展注入 Alice 的上下文，属于 V1 与 V2 之间（候选）。
- **有人读时补**：还没有归到哪一步。
- **折叠摘要自身的再压缩**：话题多次折叠时摘要只增长；日常多数话题直到沉淀都没有折叠，增长先作为风险记下（第 9 节）。
- **折叠的阈值与保留块数**：缺省值与随附配置都不改，不改为按 token 保留后缀。
- **改名**：`fold`、`fold_summary`、`TopicFold` 等代码名字不改；读者分不清的问题由撤掉接触点与改写讲法解决。

## 3. 当前状态（2026-11-27 核对）

- **折叠**（`PerceptionFamiliar._fold_if_needed`）：工作视图的 token 超过 `fold_token_threshold`（代码缺省 32768，随附配置 131072），把保留的最近 `fold_retain_recent_blocks`（2）块之前的旧块交给写作者，`append_fold` 追加一条 `TopicFold`（被折叠的块标识、摘要与时间）。`TopicFold.summary` 是累积的：已经并入此前各次折叠，工作视图的 `fold_summary` 取最后一次折叠的摘要（`topic_fold_summary`）；日志里每条 `fold` 记录同样存累积的摘要。
- **写作者**（`engines/perception/fold_summary.py`）：`LLMFoldSummaryWriter` 把旧摘要与被折叠的块交给模型，模型输出整份新摘要；没有可用模型、提供商失败或超过 `summary_timeout_seconds` 时，回退为 `RuleFoldSummaryWriter`，把规则摘要以 `---` 接在旧摘要之后。模型的输出不做任何校验。
- **写进展记录**（`PerceptionFamiliar.write_progress_entry` 与 `ProgressRecordWriter`）：材料是 `topic.interactions[recorded_until:]`，按 `[Turn N]` 逐轮渲染，加旧进展记录；不看折叠。
- **模型**：折叠摘要、进展记录、一次性生成与馆长都用 `patchouli.llm` 的同一个模型与请求参数（`PatchouliRuntime` 的 `_llm_params`）。模型定义可以带 `context_window`（`configs/models.example.yaml`），Patchouli 不读它。
- **折叠摘要的读者**：
  - 记忆生成：`GenerationContext.fold_summary`，生成材料中以 `[Topic State]` 为标题（`prompts/transcript/generation.py`）；主动写入取 `fold_summary` 与最近若干块；
  - 话题路由：`TopicRouter._render_topics` 渲染 `topic_summary or fold_summary`；
  - 查询理解：`QueryUnderstanding._render_topic_context` 在标题与 `topic_summary` 之后加 `fold_summary`；
  - `render_topic_snapshots`（`gateway/topic_context.py`）把它渲染为“状态”，结果存进 `CandidateTopics.active_topics_menu`，这个字段在生产代码中没有读取方；
  - HTTP：话题列表响应（`server/models/topic.py`）带 `fold_summary`；前端 `TopicPool` 的卡片与 `TopicPicker` 以 `foldSummary || topicSummary` 作副标题，`TopicPool` 详情另有“较早内容的摘要”一节。
- **话题的日志**：`fold` 记录保存 `TopicFold` 的 JSON，日志 `format_version` 为 1。
- **参照：Claude Code 的压缩记录**：本机会话记录中有 49 份（5 个项目），全部按同一个九节模板写，中位约 1.6 万字符。各节的中位占比：请求与意图 10%、技术要点 15%、文件与代码 34%、错误与修正 8%、问题解决 5%、用户消息原文 7%、待办 4%、当前工作 6%、下一步 9%。每份中位提到 30 个文件路径；用户消息逐条引用原文；26 份在错误与修正中记了用户的纠正；决定没有单独一节，散在技术要点、问题解决与错误中；多次压缩时整份重写，较早的用户消息被概括。

## 5. 目标设计

### 5.1 折叠的读者

折叠摘要只进入读材料的内部模型：记忆生成与写进展记录，以及下一次折叠本身。它不出现在前台，也不进入 Gateway。

### 5.2 写进展记录共用工作视图

写一条进展记录时，按 `recorded_until` 与 `folded_until` 的关系取材料：

- `recorded_until >= folded_until`：还没整理的交互都在工作视图里，照旧给第 `recorded_until` 轮之后的原文。
- `recorded_until < folded_until`：第 `recorded_until` 轮到第 `folded_until` 轮已经被折叠。给覆盖第 `recorded_until` 轮之后的那几条折叠记录的摘要（一条折叠记录跨过第 `recorded_until` 轮时整条给出），再给第 `folded_until` 轮之后的原文。更早的折叠记录已经写进旧进展记录，不再给；每条摘要的标题写明它覆盖第几轮到第几轮。

条目覆盖的位置与指回的原文区间不变：仍然是第 `recorded_until + 1` 轮到第 `interaction_count` 轮的原文。只是写它的材料里，被折叠的那几轮只有摘要。这样两类读者的输入都受同一个折叠阈值约束。

### 5.3 折叠摘要：每条折叠记录只存这一次的摘要

每次折叠追加一条折叠记录，`TopicFold.summary` 只存这一次折叠的摘要；工作视图的折叠摘要（`TopicData.fold_summary`）由全部折叠记录的摘要按顺序拼接。此前的摘要不交给模型改写：与进展记录相同，“已整理的内容只往后追加，不被递推重写”（Idea 第 1.3 节）。日志里也不再重复保存越来越长的副本。

这一次的摘要有三部分：

1. **标题**：覆盖第几轮到第几轮。
2. **判断类的栏**，由模型写，只写这一次被折叠的轮次：
   - 已定的决定及理由；
   - 被否掉的方案、失败的尝试与纠正；
   - 确认的事实与结论；
   - 用户的偏好与要求；
   - 涉及的文件及其作用：改动或用到的关键文件，各一句说明为什么涉及它（路径的完整清单在规则抽取的部分）。

   空的栏不写。
3. **规则抽取的部分**，由代码从被折叠的原文取出，不经过模型：
   - 用户消息：每一轮的用户消息原文，标上轮次，每条截到 200 字符；
   - 文件与标识符：外部工具调用参数中的路径，HiveMemory 能力调用的作用对象与产出的 alias；
   - 失败的工具调用：状态为 error 的调用，工具名加结果的第一行；
   - 用到的工具。

**为什么这样分**（参照第 3 节的 Claude Code 压缩记录）：

- 它的请求、待办、当前工作与下一步四节（合计约三成）回答的是“做到哪了、接下来做什么”，是给接着工作的 agent 看的进展。话题里这是进展记录的职责，折叠摘要不写。
- 用户的原话最能保住偏好、要求与纠正，又不需要判断，所以由代码逐轮抽取，模型失败时也不丢；判断类的栏再写其中哪些是长期的偏好与要求。
- 文件与代码一节占比最大，因为每个文件都写了改了什么、为什么。路径由代码列全，模型只为关键文件写一句作用。
- 它的决定散在几节里；决定是记忆生成最看重的内容之一，这里单列一栏。
- 它多次压缩时整份重写；这里每条折叠记录只存这一次的摘要，此前的不被改写。

模型能看到此前的折叠摘要（拼接后的整份），作为上下文，不重复其中已有的内容。读者是读材料的内部模型，不是前台 agent：提示词不再写“状态快照”“当前焦点”。

### 5.4 写折叠摘要：输出与失败

- 模型以 JSON 输出五个栏（各为字符串列表），代码校验形状后渲染成这一次的摘要。
- 没有可用模型、提供商失败、超时，或输出不合格（不是 JSON、形状不对）时，这一次的摘要只写标题与规则抽取的部分，并注明没有模型写的部分。折叠照常提交：否则工作视图会一直涨，把读材料的模型撑爆。
- 此前的摘要在任何情况下都不会丢：折叠记录只追加，不被改写。现在模型成功时，旧摘要是被整份改写的。
- `RuleFoldSummaryWriter`（`summary_writer.type: simple`）只写标题与规则抽取的部分。
- **与 Idea 的出入**：Idea 第 6 节的候选是“再加一道覆盖校验，保不住就不提交这次折叠”，这里改为照常提交。理由有三：标识符改由代码抽取之后，覆盖校验要防的主要丢失已经由结构保证；判断类的内容无法机械地核对是否保住；不提交会让工作视图一直涨。是否改回待评审（第 9 节）。

### 5.5 其他读者改读别的

- **话题路由**：候选话题一行写标题、`topic_summary`，有进展记录时再加最近一条的节选（`topic_excerpt`，200 字符）。
- **查询理解**：话题背景在标题与 `topic_summary` 之后加最近一条进展记录，按 `context_text_limit` 截断，不再加折叠摘要。
- **删除没有读取方的渲染**：`render_topic_snapshots` 与 `CandidateTopics.active_topics_menu`。
- **HTTP 与前端**：话题列表响应去掉 `fold_summary`，`TopicSnapshot` 去掉 `fold_summary`。话题卡片与话题选择器的副标题改为最近一条进展记录的节选，没有时用 `topic_summary`；话题详情去掉“较早内容的摘要”一节。
- **生成材料**：标题 `[Topic State]` 是“状态快照”的旧说法，改为表明它是被折叠的较早轮次的摘要（候选：`[Folded Earlier Turns]`）。

### 5.6 阈值与模型窗口

折叠的阈值要小于读材料的模型的窗口。所有读者都用 `patchouli.llm` 的同一个模型，所以只有一个窗口要比。这一条写进配置说明与随附配置的注释，不做启动校验（候选，第 9 节）。

## 6. 受影响的系统、契约和数据

| 范围 | 变化 |
|:---|:---|
| Patchouli 感知 | 写进展记录按 5.2 取材料；折叠写作者按 5.3、5.4 只写这一次的摘要 |
| 提示词（i18n 与生成材料） | 折叠摘要提示词改写，输出 JSON；进展记录提示词增加“已折叠部分的摘要”一节；生成材料中折叠摘要的标题 |
| Gateway | 话题路由与查询理解改读 `topic_summary` 与进展记录；删除 `render_topic_snapshots` 与 `CandidateTopics.active_topics_menu` |
| 核心模型 | `TopicFold.summary` 改为只存这一次的摘要，`topic_fold_summary` 改为按顺序拼接；`TopicSnapshot` 去掉 `fold_summary` |
| HTTP | 话题列表响应去掉 `fold_summary`（前端是唯一消费者） |
| 前端 | 话题卡片、话题选择器与话题详情改读进展记录 |
| 话题的日志 | `fold` 记录加一个标记，区分旧的累积摘要与只存这一次的摘要（第 7 节） |
| 配置 | 键与缺省值不变，只改说明 |

## 7. 兼容与迁移

- **已有的累积摘要**：旧日志里每条 `fold` 记录存的是累积的整份摘要。新写的 `fold` 记录带一个标记，表明它只存这一次的摘要；没有标记的是旧记录。读回时，套用一条旧记录会清空它之前各条折叠记录的摘要，因为它们的内容已经包含在这一条里；拼接的结果因此与旧的工作视图相同，之后的新折叠追加在后面。不迁移、不改写日志。候选：标记是 `fold` 记录的字段 `covers_earlier_folds`，缺省为真（旧记录），新写的记录为假。
- **来源 InteractionArtifact**：沉淀时随全部记录冻结的折叠记录也改为每条只有这一次的摘要；读它的是审计与调试，不参与生成。
- **降级**：旧版本读到带新字段的 `fold` 记录时整个日志读不回，进入 rejected。
- **HTTP**：去掉 `fold_summary` 是响应字段的删除，前端与后端同一个版本发布，没有其他消费者。
- **没有写过进展记录的话题**：前台只看到 `topic_summary` 与还没整理的轮次的节选，不再看到折叠摘要。

## 9. 风险与待决问题

- **进展记录依据摘要来写**：话题长时间连续工作、中间没有停下时，已经被折叠的那几轮在进展记录里只能依据摘要来写。
- **摘要只增长**：每次折叠追加一条折叠记录，拼接出的折叠摘要不再压缩。多次折叠的长话题，摘要本身会变长；多数话题直到沉淀都没有折叠，等真实出现再处理。
- **单轮超过阈值**：保留的最近几块本身超过阈值时，每来一轮就折一次，模型输入也可能超窗而只剩规则抽取的部分；属于 V2。
- **待评审的默认值**：
  - 判断类的五个栏的划分与名称；
  - 用户消息每条截到 200 字符；
  - 规则抽取取哪些参数作为路径，失败结果取第一行；
  - 话题路由加最近一条进展记录的节选，查询理解加最近一条；
  - 副标题改用最近一条进展记录的节选；
  - 生成材料的标题改为 `[Folded Earlier Turns]`；
  - 不做阈值与模型窗口的启动校验。备选是窗口已知、阈值不小于它时启动失败；
  - 区分旧累积记录的标记：字段 `covers_earlier_folds`，缺省为真；
  - 模型失败时照常提交、只写规则抽取的部分，而不是 Idea 候选的“保不住就不提交”（5.4）。

### 11.1 计划没有写明的细节与所选做法

- **写作者的接口**：`FoldSummaryWriter.generate_summary(blocks_to_fold, *, first_turn_number, earlier_summary)`。`PerceptionFamiliar._fold_if_needed` 传 `folded_until + 1` 与拼接后的 `fold_summary`；写作者只把后者当作模型的上下文，返回值只是这一次的摘要。
- **这一次的摘要的形式**：标题一行 `## 第 a–b 轮`（只折叠一轮时 `## 第 a 轮`），其后每一栏、每一节以 `### 栏名` 开头，要点以 `- ` 开头，“用到的工具”是一行逗号分隔的名字。顺序是标题、五栏（或缺失说明）、规则抽取的部分；空的栏与空的一节不写。全部标题、栏名、节名、缺失说明与逐条的格式都放在 `i18n/prompts.py` 的折叠摘要文案里，中英文各一份，随语言设置；新增的键是 `earlier_summary_empty`、`title_one_turn`、`title_turns`、`column_*`（五个）、`model_part_missing`、`rule_user_messages`、`rule_user_message`、`rule_identifiers`、`rule_failed_calls`、`rule_failed_call`、`rule_tools`，`previous_summary_empty` 删去。
- **模型输出的 JSON**：字段名 `decisions`、`rejected`、`facts`、`preferences`、`files`，各为字符串列表。缺少的字段按空栏处理；多出的字段、字段不是列表或列表里不是字符串，都算输出不合格。要点去掉首尾空白，空白的要点丢掉。五栏都为空时模型算写成了，摘要只有标题与规则抽取的部分，不加缺失说明。请求参数与写进展记录一样加 `json_output`；仍然直接调 `complete`，不加提供商重试（与原先相同）。
- **模型的输入**：被折叠的轮次改为逐轮标上轮次号、结局不是 completed 时在轮首注明，与写进展记录同一种写法。这段渲染原来是 `ProgressRecordWriter` 的私有方法，现在移到 `engines/perception/material.py` 的 `render_numbered_turn`，两个写作者共用。第一次折叠时 `<earlier_summary>` 写“无。这是这个话题的第一次折叠。”。
- **规则抽取**：
  - 用户消息：先把连续空白压成一个空格（一条一行），再用话题池节选的 `topic_excerpt` 截到 200 字符加省略号；用户消息为空的轮次跳过。
  - 路径：取工具调用参数中名为 `path`、`paths`、`file_path`、`notebook_path`、`file`、`filename` 的值（字符串或字符串列表）。对外部工具与能力调用一样取：Alice 的 RUN 文件工具也用 `path`。能力调用另取 `targets` 与 `produced_aliases`。全部按首次出现的顺序去重。
  - 失败的调用：`status == "error"` 的外部工具与能力调用，名字是工具名或动词；结果取第一行，同样截到 200 字符；行首加轮次号（`- 第 4 轮 apply_patch：…`）。
  - 用到的工具：工具名或动词（动词保持大写，与材料中的写法一致），按首次出现的顺序；无法解析的 MTP 指令（两者都为空）不计入，也不取它的标识符。
  - 不设总量上限。
- **拼接**：`topic_fold_summary` 用空行（`\n\n`）连接各条，空串跳过。
- **兼容的套用**：`apply_fold` 遇到 `covers_earlier_folds` 为真的记录时，把此前各条 `TopicFold` 重建为摘要为空串的同一条；`TopicFold` 本身没有加字段。
- **写进展记录的材料**：原文从 `max(recorded_until, folded_until) + 1` 轮起编号；摘要取“覆盖到的位置大于 `recorded_until`、摘要不为空”的折叠记录（`PerceptionFamiliar._fold_summaries_after`，静态方法）。提示词仍只有一份，在旧进展记录与原文之间加 `[已折叠轮次的摘要]` / `[Summaries of folded turns]` 一节，没有时写“无” / “None”（新键 `folded_summaries_empty`）；系统提示词说明摘要标题写明覆盖的轮次、可能覆盖旧进展记录已写过的轮次。`write_entry` 加关键字参数 `folded_summaries`，缺省为空。
- **话题路由**：一行是 `- id: 标题 | topic_summary | 最近一条进展记录的节选`，没有进展记录时没有第三项。提示词“活跃话题”一节加了一句说明每行的各项（中英文）。
- **查询理解**：在标题、`topic_summary` 之后加一行 `latest progress: <最近一条，截到 context_text_limit>`，其后是工作视图最近几轮；标签沿用 `user:`、`assistant:` 的英文小写写法。
- **生成材料**：`[Topic State]` 改为 `[Folded Earlier Turns]`；生成提示词中引用这个标题的四处（段标签与引用的规则，中英文各两处）一并改为“来自较早轮次的折叠摘要 [Folded Earlier Turns] 的内容没有段，不引用”。
- **前端**：`utils/topicPool.ts` 加 `topicSubtitle`，话题卡片与话题选择器共用。“节选”沿用现有的按行截断（卡片 2 行、选择器 1 行），不在前端按字符截断。
- **日志**：写作者没有模型时 `warning`，`reason=fold_summary_no_model`；模型部分没写成时 `warning`，`reason=fold_summary_model_failed, error_class=…`。写作者不知道 `topic_id`，靠感知服务折叠前的 `info` 日志对应。
- **配置注释**：`fold_token_threshold` 上方加注释；`progress_record_after_seconds` 的注释同步改为“已经折叠的部分只给摘要”。
- **测试**：
  - `test_fold_summary.py` 重写；`test_fold_summary_prompt.py` 改为守护中英文键与占位符一致、英文文案没有中文、按语言取用（原来断言旧提示词的措辞）；
  - `test_progress_record.py` 更新提示词期望并新增折叠摘要一节的用例；`test_perception.py` 的折叠替身改为新接口，新增“跨过折叠边界写进展记录”的用例；
  - `test_topic.py`、`test_topic_log.py` 改为拼接语义，新增旧累积记录读回的用例（以缺少字段的 JSON 行解码模拟旧日志）；
  - 话题路由与查询理解各新增一个渲染用例；`test_topics.py` 把原来的 `workspace_identity not in` 改为断言响应字段的完整集合；
  - 删去 `test_context_provider.py`、`test_contracts.py`、`test_workflow.py` 中只守护 `active_topics_menu` 的部分；其余测试里的写作者替身改为新签名，`test_session_context.py` 的快照把 `fold_summary` 改为 `topic_summary`（快照多余的字段会被静默忽略）；
