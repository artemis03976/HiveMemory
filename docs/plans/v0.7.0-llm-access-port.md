# v0.7.0 LLM 访问收敛到 infrastructure 服务接口

> **文档状态**：In progress（2026-10-18）。同日修订了接口位置与调用形态，阶段由三个改为两个（第 11 节）；修订后的阶段一已完成并经 code review，阶段二尚未实施。目标接口、类型名与模块位置不能作为当前事实使用。

项目里有两套 litellm 包装：infrastructure 的 `LiteLLMService` 供 Gateway 与 Patchouli 使用，`agent_runtime` 的 `LLMClient` 供 Alice 使用。前者绑定单一配置、不支持流式，返回值与异常都是 litellm 的形状，Alice 用不上；后者因此绕过 infra 直接调用 SDK。结果是 SDK 的类型同时出现在 L2 的分析引擎与 L3 的执行内核里，提供商异常由各使用方分别识别，Alice 的生成接口绑定在 litellm 上。

本计划把 infrastructure 现有的 LLM 服务基类 `BaseLLMService` 改写为中立的异步接口，以 `stream` 参数在唯一入口内选择完整调用或流式调用，由唯一的 litellm 实现；Gateway、Patchouli 与 Alice 都只依赖这一基类，SDK 只在实现中出现，提供商失败在 SDK 边界转换为 core 的中立错误。Alice 保留自己的 MTP 生成语义，建立在该接口之上。

设计依据：

- 当前事实：[错误模型](../contracts/error-model.md)（中立错误由依赖适配器在边界产生、调用方按类型处理）、[Agent Runtime](../alice/agent-runtime.md)第 4、5 节（模型解析、LLM 调用与 MTP 停止符）、[System 组合根](../system/composition.md)与 [System 配置](../system/configuration.md)（组件 LLM 配置经模型注册表解析）、[Gateway 分析](../gateway/analysis.md)与 [Patchouli 生成](../patchouli/generation.md)；
- 代码：2026-10-18 `master` 的合并提交 `f0e52f45`（含异常收敛与单例缺陷修复）；infrastructure 对外部技术的既有抽象方式（`infrastructure/embedding/base.py`、`infrastructure/rerank/base.py` 的抽象基类，`infrastructure/storage/_errors.py` 在 SDK 边界转换为中立错误）；`ProcessService.run_process` 与 `CPUPort.execute` 以 `stream` 参数在同一入口选择形态；
- 已归档：[异常收敛](../archive/plans/v0.7.0-error-model-convergence.md)（把 SDK 异常元组下沉到 `infrastructure/llm/errors.py` 供引擎与 `LLMClient` 共用，并把“不改造 LLM 客户端”列为非目标；本计划承接这一遗留）、[Alice 与 agent_runtime 结构重构](../archive/plans/v0.7.0-alice-agent-runtime-restructure.md)（`LLMClient` 与 `ModelProviderError` 的来历）。

## 1. 背景和问题

1. **两套包装，各缺一半**：`LiteLLMService`（`infrastructure/llm/`）每个实例按一份 `LLMConfig` 固定模型、凭证与采样参数，提供同步与异步补全、JSON 模式与工具调用，但没有流式；`complete_with_tools` 原样返回 litellm 响应对象，调用方解析 `choices[0].message.tool_calls`。`LLMClient`（`agent_runtime/model/client.py`）按调用接收参数，支持流式、MTP 停止符与定界符补齐，并把 SDK 异常转换为中立错误，但直接导入 litellm。
2. **异常在使用方识别**：Gateway 的查询理解与话题路由、`LLMClient` 都捕获 `infrastructure/llm/errors.py` 中的 SDK 异常元组再自行转换；`LiteLLMService` 本身不转换。`ModelProviderError` 定义在 `agent_runtime`（L3），infrastructure（L2）与引擎（L2）无法抛出或捕获它，只能认识 SDK 类型。
3. **异步路径中的同步调用**：Patchouli 的 `MemoryGenerationEngine.process` 是协程，却同步调用 `LLMExtractor.extract`，后者经 `complete_with_retry` 调用同步的 `litellm.completion`，在网络请求期间阻塞事件循环；Page Folding 摘要（`LLMRelayController.generate_summary`）同样同步调用 `complete`。
4. **宽泛捕获吞掉错误**：`complete_with_retry` 与 `acomplete_with_retry` 捕获所有 `Exception`，耗尽后返回 `None`；抽取器把 `None` 当作“LLM 返回空响应”，程序错误与提供商失败都被记录为没有产出。Page Folding 摘要捕获所有异常后回退为简单摘要，程序错误同样被降级掩盖。
5. **参数以无类型字典传递**：`LLMClient` 从 `**kwargs` 中弹出 model、api_key、api_base 与采样参数；组件侧则在实例上固定。两条路径各自决定传给 SDK 的参数，没有共同的请求模型。
6. **调用形态分散**：`LiteLLMService` 按同步与异步、JSON、工具与重试拆成七个补全方法，`LLMClient` 把完整与流式拆成 `generate_async` 与 `generate_stream`，帧循环按输出端是否流式二选一；项目其余入口（`ProcessService.run_process`、`CPUPort.execute`）都以 `stream` 参数在同一入口内选择形态。
7. **单例缺陷（已在本计划前修复）**：`SingletonLLMService` 曾使 Gateway 与 Librarian 共用先构造的实例，`shared.llm.librarian` 被静默忽略。修复已改为每份配置一个实例并有回归测试，本计划在此基础上进行。

## 2. 目标与非目标

### 2.1 目标

1. litellm 只在 `infrastructure/llm/` 中导入，由架构守卫固定。
2. infrastructure 的 `BaseLLMService` 改写为中立的异步接口：唯一入口以 `stream` 参数选择完整调用或流式调用，请求逐次携带模型参数、停止符与 JSON 模式，返回中立的结果与分块；流必须可关闭。接口与模型不依赖 SDK。
3. `ModelProviderError` 与 `ModelContextWindowExceededError` 迁入 `core/errors/model.py`，由 litellm 实现在 SDK 边界产生；调用方只捕获中立类型。
4. 唯一的 litellm 实现继承该基类，无状态，不绑定配置，不使用单例。
5. Gateway 的两个分析引擎、Patchouli 的抽取器与 Page Folding 摘要、Alice 的帧生成与会话摘要器都只依赖该基类；Patchouli 的 LLM 调用改为异步，不再阻塞事件循环。
6. 提供商失败与“没有产出”可以区分：重试只针对 `ModelProviderError`，耗尽后以中立错误结束，程序错误与取消照常传播。
7. 组合根创建一个 litellm 实现的实例并注入全部使用方；`build_agent_runtime` 与 `AliceSystem` 不再自行构造 LLM 客户端。
8. 发给提供商的参数、Alice 的流式与 MTP 语义、Gateway 与 Passive 的降级语义保持现状（第 4.6 节）。

### 2.2 非目标

- 改名 `ModelDefinition.litellm_model` 与 `models.yaml` 的配置键：属于配置契约变更，如需处理另行登记。
- 接入 litellm 之外的提供商 SDK，或新增熔断、全局重试与限流策略。
- 修改模型注册表的解析规则、组件 LLM 配置段的结构或默认值。
- 修改提示词内容、MTP 协议、会话压缩算法。
- 用量计费或新的观测事件：只保留现有日志信息。

## 3. 当前状态（2026-10-18 核对）

| 使用方 | 现在的入口 | 调用方式 | 异常处理 |
|:---|:---|:---|:---|
| Gateway 查询理解、话题路由 | `BaseLLMService.acomplete_json` | 异步，实例固定配置 | 捕获 SDK 异常元组后降级 |
| Patchouli 记忆抽取 | `complete_with_retry` | 同步，在协程内调用 | 重试吞掉全部异常，返回 `None` |
| Page Folding 摘要 | `complete` | 同步 | 捕获全部异常后回退为简单摘要 |
| Alice 帧生成 | `LLMClient.generate_async` / `generate_stream` | 异步，逐次参数 | 转换为 `ModelProviderError` / 超窗错误 |
| Alice 会话摘要器 | `LLMClient.generate_async` | 异步，逐次参数 | 只捕获中立错误 |

- 组件 LLM 配置（`shared.llm.gateway`、`shared.llm.librarian`）由组合根经 `ModelRegistry.resolve_for_llm_config` 解析后，分别交给 `get_gateway_llm_service` 与 `get_librarian_llm_service`。
- Alice 的模型参数由 `ModelResolver`（System 的模型注册表实现）按 Profile 与生成参数逐帧解析为 `ResolvedFrameModel`，再以字典交给 `LLMClient`。
- `LLMClient` 由 `build_agent_runtime` 内部构造；`AliceSystem` 另构造一个给 `RelaySummarizer`。
- 工具调用接口（`complete_with_tools`、`acomplete_with_tools`）与 `acomplete_with_retry` 目前没有生产调用方。
- infrastructure 对 embedding 与 rerank 采用 `base.py` 抽象基类加实现的方式，调用方依赖基类（如 `engines/retrieval/reranker.py` 依赖 `BaseRerankService`）；存储适配器在 SDK 边界把异常转换为 `core.errors` 的中立错误（`infrastructure/storage/_errors.py`）。

## 4. 目标设计

### 4.1 分层

```text
core（L0）
  errors/model.py         ModelNotFoundError（已有）、ModelProviderError、ModelContextWindowExceededError
infrastructure（L2）
  llm/base.py             BaseLLMService 接口与请求参数、结果、分块模型；不依赖 SDK
  llm/litellm_service.py  LiteLLMService：SDK 调用、响应解析、流的迭代与关闭、异常转换、JSON 模式回退
engines / gateway / patchouli（L2/L3）  依赖 BaseLLMService；组件的固定配置在构造时转换为请求参数
agent_runtime（L3）       MTP 生成器：建立在 BaseLLMService 之上，负责停止符、定界符检测与补齐、分块语义
system（L4）              创建唯一的 LiteLLMService 实例并注入 Gateway、Patchouli 与 build_agent_runtime
```

接口留在 infrastructure，不在 core 另设端口：全部调用方位于 L2 及以上，分层规则允许它们直接依赖 infrastructure；`core/ports` 用于由资源所有者实现、供彼此不能导入的子系统消费的协议，外部技术适配器不属于这一类。embedding 与 rerank 已采用 `base.py` 抽象基类加实现的方式，LLM 与之一致，只保留一套抽象；“调用方不接触 SDK”由只允许导入基类模块的架构守卫保证（第 4.5 节）。中立错误放在 `core/errors`，与 `ModelNotFoundError` 和存储错误的位置一致，错误模型的中立类型只有这一处来源。

### 4.2 接口与请求模型

- **请求参数**：一个冻结的中立模型，包含 model、api_key、api_base、temperature、top_p、max_tokens、stop，以及是否要求 JSON 输出。组件的 `LLMConfig` 与 Alice 的 `ResolvedFrameModel` 各自转换为它，转换函数位于各自的所有者一侧。
- **唯一入口**：`complete(messages, params, *, stream=False)`，与 `ProcessService.run_process` 相同，以重载标注两种返回：`stream=False` 返回可 await 的完整结果，`stream=True` 返回可关闭的异步生成器。默认不流式，与 SDK 一致；六个调用点中只有 Alice 的帧生成会流式调用。基类负责按 `stream` 分派，实现只提供完整调用与流式调用两个受保护的抽象钩子，调用方与测试替身都只面对同一入口。不采用 `CPUPort` 那样两种模式都返回同一句柄的形式：CPU 在两种模式下都需要结果槽与事件流，LLM 的完整调用没有中间项，统一为迭代器会迫使不流式的调用方先排空迭代器。
- **完整结果**：返回文本、finish_reason 与用量（可缺省）；provider 没有返回文本时显式失败，沿用现有 `_response_text` 的语义。
- **流**：首次拉取时才发出请求，逐项产出文本增量，最后一项带 finish_reason；调用方关闭或取消时实现关闭底层响应，关闭失败只记录日志、不替换正在传播的取消。
- **异常**：上下文超窗转换为 `ModelContextWindowExceededError`，已知的提供商失败转换为 `ModelProviderError`，原始异常保留在原因链；其他异常与取消原样传播。完整调用、流式启动与流式拉取三个边界采用同一转换，与现有 `LLMClient` 一致。
- **JSON 模式**：只在 SDK 明确报告不支持该参数时回退为普通补全，与异常收敛后的现状一致。

### 4.3 litellm 实现

- `LiteLLMService` 是 `BaseLLMService` 的唯一实现，无状态，可被全部使用方共享；不读取配置、不持有默认模型。
- `ConfiguredLLMService`、`get_gateway_llm_service` 与 `get_librarian_llm_service`、旧接口的同步、重试与工具方法随使用方迁移删除；`infrastructure/llm/errors.py` 中的 SDK 元组在 `LLMClient` 迁移后只作为实现的私有细节保留。
- 工具调用没有生产调用方，接口不提供工具定义与工具调用结果；需要时依据届时的调用方加入，不为不存在的使用方保留兼容层。

### 4.4 使用方的迁移

- **Gateway**：查询理解与话题路由以 JSON 输出的请求参数调用 `complete`，构造时取得由 `shared.llm.gateway` 转换的请求参数；降级只针对 `ModelProviderError` 与模型解析失败，与现状相同。
- **Patchouli**：抽取器与 Page Folding 摘要改为异步并经基类调用，由 `shared.llm.librarian` 转换请求参数。抽取的重试只针对 `ModelProviderError`，耗尽后抛出中立错误，由生成任务按失败收尾，不再记录为“没有产出”；程序错误与取消照常传播。重试次数沿用现有默认值。Page Folding 摘要只在 `ModelProviderError` 时回退为简单摘要。
- **Alice**：`LLMClient` 改为建立在 `BaseLLMService` 之上的 MTP 生成器，入口同样合并为一个、以 `stream` 参数选择形态（取代 `generate_async` 与 `generate_stream`），帧循环按输出端是否流式传入该参数；保留 MTP 停止符、定界符检测与补齐、`GenerationResult` / `StreamChunk` 语义。会话摘要器经同一生成器或直接经基类调用，只捕获中立错误。`build_agent_runtime` 接收基类实例，`AliceSystem` 不再构造客户端。
- **组合根**：创建一个 `LiteLLMService` 实例，分别交给 Gateway、Patchouli 与 Alice；组件的固定参数在组合根或组件构造时转换，实现本身不感知是谁在调用。

### 4.5 架构守卫

扩展既有的分层守卫：litellm 只能在 `infrastructure/llm/` 中导入；`infrastructure/llm/base.py` 不依赖任何 SDK；除组合根外，引擎与子系统从 LLM 包只导入 `infrastructure.llm.base`，不导入实现模块，也不经包根导入。

### 4.6 必须保持的行为

- 每个使用方发给提供商的参数与现状一致：组件侧的 model、凭证、temperature、max_tokens（现有实现不传 top_p 与 stop），Alice 侧的 model、凭证、temperature、top_p、max_tokens 与 MTP 停止符。迁移时逐个使用方比较迁移前后的 SDK 调用参数。
- Alice 的流式分块、定界符补齐、取消时关闭响应的语义不变；`ModelProviderError` 与超窗错误的分类、CPU 失败原因与摘要器的降级不变。
- Gateway 与 Passive 的降级条件不变。有意的行为变化只有两处（第 1 节第 4 点）：Patchouli 抽取在提供商失败时由“没有产出”改为显式失败；Page Folding 摘要的回退收窄到提供商失败，程序错误不再被简单摘要掩盖。

## 5. 受影响的系统、契约和数据

- **core**：`ModelProviderError`、`ModelContextWindowExceededError` 迁入 `core/errors/model.py`，`agent_runtime` 包根继续导出它们。
- **infrastructure**：`BaseLLMService` 改写为中立接口，`LiteLLMService` 改为无状态的唯一实现。
- **Gateway / Patchouli / engines**：LLM 依赖改为注入的基类实例；Patchouli 抽取与 Page Folding 摘要变为异步。
- **Alice / agent_runtime**：生成器建立在基类上并合并为单一入口，内核工厂接收基类实例。
- **System**：组合根创建并注入实例。
- **不变**：公开 HTTP 与 SSE 契约、配置键、模型注册表、持久化数据、MTP 协议。

## 6. 兼容与迁移

- `BaseLLMService` 原地改写。Gateway 与 Patchouli 是旧接口仅有的调用方，与改写在同一阶段迁移，不设新旧两套抽象并存的过渡期；Alice 的 `LLMClient` 不依赖旧接口，阶段二迁移前继续直接调用 SDK，这是唯一保留到下一阶段的并行 SDK 路径。每个阶段结束时后端全量测试通过。
- 删除的符号不保留别名：`ConfiguredLLMService`、两个工厂函数与旧接口方法只有组合根、Gateway 与 Patchouli 使用，随同修改。
- 测试中直接替换 `litellm.acompletion` 或 `LLMClient.generate_async` 的用例，改为注入继承 `BaseLLMService` 的手写替身；只有实现自身的测试替换 SDK。
- Patchouli 抽取失败语义的变化在[Patchouli 生成](../patchouli/generation.md)与错误模型中记录，并用归属层测试覆盖。

## 7. 实施阶段

**阶段一：接口、实现与 Gateway、Patchouli 迁移**

1. `BaseLLMService` 改写为中立接口（唯一入口与两个抽象钩子），请求、结果与分块模型同在 `infrastructure/llm/base.py`；两类模型错误迁入 `core/errors/model.py`（已完成）；
2. `LiteLLMService` 改为无状态实现：SDK 参数构造、完整与流式调用、JSON 模式回退、异常转换与流关闭；
3. Gateway 两个分析引擎、Patchouli 抽取器与 Page Folding 摘要经基类调用，后两者改为异步，重试与失败语义按第 4.4 节；
4. 组合根创建实例并注入 Gateway 与 Patchouli，组件配置转换为请求参数；删除 `ConfiguredLLMService`、工厂函数与旧接口方法。

验收：第 8 节第 1–5 项。

**阶段二：Alice 迁移与收尾**

1. MTP 生成器建立在基类上并合并为单一入口，`build_agent_runtime` 与 `AliceSystem` 改为接收注入；SDK 异常元组成为实现的私有细节；
2. 架构守卫；
3. 晋升事实文档（第 10 节），同步 Plans 导航与 ROADMAP，归档本计划。

验收：第 8 节全部。

## 8. 测试和验收标准

按[测试设计规范](../governance/testing/test-design-standards.md)分类；每条不变量只在作出判断的归属层写权威测试，上层与 E2E 只保留代表性链路，验收测试写入归属层的现有文件。

1. **实现参数与形态**：请求参数逐项传给 SDK，不补入请求未携带的参数；同一入口按 `stream` 返回完整结果或流；JSON 模式只在 SDK 明确不支持时回退（改写现有 `tests/unit/infrastructure/test_litellm_service.py`）。
2. **实现的异常与关闭**：完整调用、流式启动与流式拉取的超窗与提供商失败分别转换，原因链保留，其他异常与取消原样传播；流在耗尽、关闭与取消时都关闭底层响应（同上）。
3. **Gateway 降级**：提供商失败与模型解析失败降级，程序错误传播（现有 `tests/unit/engines/gateway/` 测试改为注入基类替身）。
4. **Patchouli 抽取与摘要**：抽取的重试只针对提供商失败，耗尽后显式失败而不是没有产出；Page Folding 摘要只在提供商失败时回退；等待 LLM 时事件循环可以推进其他任务（`tests/unit/engines/generation/`、`tests/unit/engines/perception/` 与生成服务的归属层测试）。
5. **组件参数各自独立**：Gateway 与 Librarian 经组合根得到各自配置转换的请求参数（组合根测试；单例修复的回归测试随迁移改写到这一层）。
6. **Alice 生成语义**：生成器以同一入口按 `stream` 选择两种形态；停止符、定界符补齐、分块序列、取消关闭与中立错误分类不变（现有 `tests/unit/agent_runtime/model/test_client.py` 改为基类替身）；摘要器的降级不变。
7. **依赖方向**：litellm 只在 `infrastructure/llm/` 中导入，`base.py` 不依赖 SDK，引擎与子系统不导入实现模块或包根（扩展 `tests/unit/architecture/test_package_layers.py`）。
8. **链路不变**：Alice、Gateway、Patchouli 生成的现有集成测试与离线 E2E 通过。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| 迁移中发给提供商的参数漂移（例如组件侧意外多传 top_p） | 第 4.6 节逐使用方比较 SDK 调用参数，结果记入第 11 节 |
| 阶段一同时改写接口并迁移两个子系统，改动面较大 | 按使用方逐个迁移，每完成一个运行其归属层测试；阶段结束前不提交半迁移状态 |
| 抽取改为异步后与 chat 并发，提供商限流更容易触发 | 不改变重试次数；限流表现为 `ModelProviderError` 按失败收尾，记入文档；需要并发控制时另行评估 |
| 抽取失败从“没有产出”变为显式失败、摘要回退收窄，影响生成任务的终态统计与 Topic 折叠 | 作为两处有意的行为变化，在生成文档与错误模型中记录并测试 |
| 测试大量替换 SDK 或 `LLMClient` 方法，迁移成本高 | 提供一个共享的基类替身 helper，逐个文件迁移；只有实现自身的测试替换 SDK |
| 流式关闭与取消语义在实现与生成器之间分工不清 | 关闭底层响应只在实现中做，生成器只负责关闭实现返回的流；沿用现有取消回归 |

  - `ModelProviderError` 与 `ModelContextWindowExceededError` 迁入 `core/errors/model.py`，`agent_runtime` 包根继续导出；超窗是提供商失败的子类，与 SDK 中超窗属于请求错误一致，按提供商失败处理的调用方（Gateway 降级、Page Folding 回退）无需单独捕获，需要区分超窗的调用方先判断子类。
  - 工具调用没有生产调用方，接口不提供工具定义与工具调用结果（第 4.3 节）。
  - 为 `None` 或为空的可选参数（含凭证）不传给 SDK；litellm 对缺省与显式 `None` 的凭证处理相同，第 4.6 节的参数比较据此进行。
  - 完整调用没有返回文本（没有候选，或内容不是字符串）时抛出无原因链的 `ModelProviderError`，空字符串仍是合法文本；`finish_reason` 原样上报，提供商未报告时为 `None`，由调用方解释。现有 `LLMClient` 把缺失内容当作空文本，阶段二迁移 Alice 非流式生成时需按此确认行为。
- 2026-10-18：修订计划。审查原阶段一时发现两处设计问题：
  - 在 core 另设端口与 infrastructure 既有的 `BaseLLMService` 形成两套抽象；全部调用方本可直接依赖 infrastructure，`core/ports` 也不用于外部技术适配器，与 embedding、rerank 的基类方式不一致。修订为把 `BaseLLMService` 原地改写为中立接口，实现沿用 `LiteLLMService` 之名（第 4.1、4.3 节）。
  - 完整调用与流式调用分为两个方法，与项目以 `stream` 参数在同一入口选择形态的方式不符。修订为唯一入口 `complete(..., stream=False)` 加两个受保护钩子，Alice 的生成器同样合并入口（第 4.2、4.4 节）。

  原阶段一的成果按修订处理：模型错误迁入 core 保留；`core/ports/llm.py` 删除，请求、结果与分块模型连同类型名移入 `infrastructure/llm/base.py`；`LiteLLMAdapter` 的 SDK 参数构造、异常转换、JSON 回退与流关闭并入 `LiteLLMService`，测试随调用方式改写。基类原地改写后旧调用方立即失效，因此原阶段一、二合并为新的阶段一，原阶段三为阶段二（第 6、7 节）。

  - 实施命名：`infrastructure/llm/base.py` 的 `BaseLLMService.complete(messages, params, *, stream=False)` 以重载标注两种返回，实现钩子为 `_complete` 与 `_stream`；`LiteLLMService`（`infrastructure/llm/litellm_service.py`）无状态；原 `core/ports/llm.py` 与 `litellm_adapter.py` 已删除。测试替身为 `tests/helpers/llm.py` 的 `ScriptedLLMService`。

  - Patchouli：抽取器只对 `ModelProviderError` 重试（共两次请求，与原默认值相同），超窗与程序错误不重试；模型输出为空或 `JSONParseError` 仍是没有产出。Mode A 的提供商失败向上传播，生成任务以 `memory_generation_failed` 失败收尾；Mode B 与 Mode C 对提供商失败仍走既有 fallback，以保留[Patchouli 生成](../patchouli/generation.md)记录的“明确保存意图不因 Librarian LLM 暂时失败而丢失”，程序错误不再被 fallback 掩盖。Page Folding 摘要只在提供商失败时回退。
  - 第 4.6 节参数比较（以 `HEAD` 的旧实现为基准，替换 SDK 记录参数）：Gateway（含 `model_override`）与 Librarian（抽取、Page Folding）迁移前后的 SDK 参数一致；唯一差异是值为 `None` 的凭证不再显式传入，litellm 对缺省与 `None` 的处理相同；Librarian 的调用由同步 `completion` 变为异步 `acompletion`。

  - code review 中未采纳的意见：Page Folding 与抽取的 LLM 调用没有超时（旧实现同样没有，且同步阻塞事件循环；新增超时属于配置变更，不在本计划）；重试没有退避（第 2.2 节不新增重试策略）。
