# v0.7.0 LLM 访问收敛到 infrastructure 端口

> **文档状态**：Planned（2026-10-18）。尚未实施；目标接口、类型名与模块位置不能作为当前事实使用。

项目里有两套 litellm 包装：infrastructure 的 `LiteLLMService` 供 Gateway 与 Patchouli 使用，`agent_runtime` 的 `LLMClient` 供 Alice 使用。前者绑定单一配置、不支持流式，返回值与异常都是 litellm 的形状，Alice 用不上；后者因此绕过 infra 直接调用 SDK。结果是 SDK 的类型同时出现在 L2 的分析引擎与 L3 的执行内核里，提供商异常由各使用方分别识别，Alice 的生成接口绑定在 litellm 上。

本计划在 core 定义一个中立的异步 LLM 端口，由 infrastructure 中唯一的 litellm 适配器实现；Gateway、Patchouli 与 Alice 都只依赖端口，SDK 只在适配器中出现。Alice 保留自己的 MTP 生成语义，建立在端口之上。

设计依据：

- 当前事实：[错误模型](../contracts/error-model.md)（中立错误由依赖适配器在边界产生、调用方按类型处理）、[Agent Runtime](../alice/agent-runtime.md)第 4、5 节（模型解析、LLM 调用与 MTP 停止符）、[System 组合根](../system/composition.md)与 [System 配置](../system/configuration.md)（组件 LLM 配置经模型注册表解析）、[Gateway 分析](../gateway/analysis.md)与 [Patchouli 生成](../patchouli/generation.md)；
- 代码：2026-10-18 分支 `refactor/error-model` 提交 `0d2b7ce6` 及其后的单例缺陷修复；
- 已归档：[异常收敛](../archive/plans/v0.7.0-error-model-convergence.md)（把 SDK 异常元组下沉到 `infrastructure/llm/errors.py` 供引擎与 `LLMClient` 共用，并把“不改造 LLM 客户端”列为非目标；本计划承接这一遗留）、[Alice 与 agent_runtime 结构重构](../archive/plans/v0.7.0-alice-agent-runtime-restructure.md)（`LLMClient` 与 `ModelProviderError` 的来历）。

## 1. 背景和问题

1. **两套包装，各缺一半**：`LiteLLMService`（`infrastructure/llm/`）每个实例按一份 `LLMConfig` 固定模型、凭证与采样参数，提供同步与异步补全、JSON 模式与工具调用，但没有流式；`complete_with_tools` 原样返回 litellm 响应对象，调用方解析 `choices[0].message.tool_calls`。`LLMClient`（`agent_runtime/model/client.py`）按调用接收参数，支持流式、MTP 停止符与定界符补齐，并把 SDK 异常转换为中立错误，但直接导入 litellm。
2. **异常在使用方识别**：Gateway 的查询理解与话题路由、`LLMClient` 都捕获 `infrastructure/llm/errors.py` 中的 SDK 异常元组再自行转换；`LiteLLMService` 本身不转换。`ModelProviderError` 定义在 `agent_runtime`（L3），infrastructure（L2）与引擎（L2）无法抛出或捕获它，只能认识 SDK 类型。
3. **异步路径中的同步调用**：Patchouli 的 `MemoryGenerationEngine.process` 是协程，却同步调用 `LLMExtractor.extract`，后者经 `complete_with_retry` 调用同步的 `litellm.completion`，在网络请求期间阻塞事件循环；Page Folding 摘要（`LLMRelayController.generate_summary`）同样同步调用 `complete`。
4. **宽泛捕获吞掉错误**：`complete_with_retry` 与 `acomplete_with_retry` 捕获所有 `Exception`，耗尽后返回 `None`；抽取器把 `None` 当作“LLM 返回空响应”，程序错误与提供商失败都被记录为没有产出。Page Folding 摘要捕获所有异常后回退为简单摘要，程序错误同样被降级掩盖。
5. **参数以无类型字典传递**：`LLMClient` 从 `**kwargs` 中弹出 model、api_key、api_base 与采样参数；组件侧则在实例上固定。两条路径各自决定传给 SDK 的参数，没有共同的请求模型。
6. **单例缺陷（已在本计划前修复）**：`SingletonLLMService` 曾使 Gateway 与 Librarian 共用先构造的实例，`shared.llm.librarian` 被静默忽略。修复已改为每份配置一个实例并有回归测试，本计划在此基础上进行。

## 2. 目标与非目标

### 2.1 目标

1. litellm 只在 `infrastructure/llm/` 中导入，由架构守卫固定。
2. core 定义中立的异步 LLM 端口：完整调用与流式调用两种操作，请求逐次携带模型参数、停止符、JSON 模式或工具定义，返回中立的结果与分块；流必须可关闭。
3. `ModelProviderError` 与 `ModelContextWindowExceededError` 迁入 `core/errors/model.py`，由适配器在 SDK 边界产生；调用方只捕获中立类型。
4. infrastructure 中唯一的 litellm 适配器实现端口，无状态，不绑定配置，不使用单例。
5. Gateway 的两个分析引擎、Patchouli 的抽取器与 Page Folding 摘要、Alice 的帧生成与会话摘要器都只依赖端口；Patchouli 的 LLM 调用改为异步，不再阻塞事件循环。
6. 提供商失败与“没有产出”可以区分：重试只针对 `ModelProviderError`，耗尽后以中立错误结束，程序错误与取消照常传播。
7. 组合根创建一个适配器并注入全部使用方；`build_agent_runtime` 与 `AliceSystem` 不再自行构造 LLM 客户端。
8. 发给提供商的参数、Alice 的流式与 MTP 语义、Gateway 与 Passive 的降级语义保持现状（第 4.6 节）。

### 2.2 非目标

- 改名 `ModelDefinition.litellm_model` 与 `models.yaml` 的配置键：属于配置契约变更，如需处理另行登记。
- 接入 litellm 之外的提供商 SDK，或新增熔断、全局重试与限流策略。
- 修改模型注册表的解析规则、组件 LLM 配置段的结构或默认值。
- 修改提示词内容、MTP 协议、会话压缩算法。
- 用量计费或新的观测事件：只保留现有日志信息。

## 3. 当前状态（2026-10-18 核对）

| 使用方 | 现在的入口 | 调用方式 | 异常处理 |
|:---|:---|:---|:---|
| Gateway 查询理解、话题路由 | `BaseLLMService.acomplete_json` | 异步，实例固定配置 | 捕获 SDK 异常元组后降级 |
| Patchouli 记忆抽取 | `complete_with_retry` | 同步，在协程内调用 | 重试吞掉全部异常，返回 `None` |
| Page Folding 摘要 | `complete` | 同步 | 捕获全部异常后回退为简单摘要 |
| Alice 帧生成 | `LLMClient.generate_async` / `generate_stream` | 异步，逐次参数 | 转换为 `ModelProviderError` / 超窗错误 |
| Alice 会话摘要器 | `LLMClient.generate_async` | 异步，逐次参数 | 只捕获中立错误 |

- 组件 LLM 配置（`shared.llm.gateway`、`shared.llm.librarian`）由组合根经 `ModelRegistry.resolve_for_llm_config` 解析后，分别交给 `get_gateway_llm_service` 与 `get_librarian_llm_service`。
- Alice 的模型参数由 `ModelResolver`（System 的模型注册表实现）按 Profile 与生成参数逐帧解析为 `ResolvedFrameModel`，再以字典交给 `LLMClient`。
- `LLMClient` 由 `build_agent_runtime` 内部构造；`AliceSystem` 另构造一个给 `RelaySummarizer`。
- 工具调用接口（`complete_with_tools`、`acomplete_with_tools`）与 `acomplete_with_retry` 目前没有生产调用方。

## 4. 目标设计

### 4.1 分层

```text
core（L0）
  ports/llm.py        LLM 端口协议、请求参数、结果与分块模型
  errors/model.py     ModelNotFoundError（已有）、ModelProviderError、ModelContextWindowExceededError
infrastructure（L2）
  llm/                litellm 适配器：SDK 调用、响应解析、流的迭代与关闭、异常转换、JSON 模式回退
engines / patchouli（L2/L3）  经端口调用；组件的固定配置在构造时转换为请求参数
agent_runtime（L3）   MTP 生成器：建立在端口之上，负责停止符、定界符检测与补齐、分块语义
system（L4）          创建唯一适配器并注入 Gateway、Patchouli 与 build_agent_runtime
```

模块名与类型名是实施时的候选，实施评审确定后记入第 11 节；分层、依赖方向与“SDK 只在适配器中”是本计划的约束。

### 4.2 端口与请求模型

- **请求参数**：一个冻结的中立模型，包含 model、api_key、api_base、temperature、top_p、max_tokens、stop，以及可选的 JSON 输出要求与工具定义。组件的 `LLMConfig` 与 Alice 的 `ResolvedFrameModel` 各自转换为它，转换函数位于各自的所有者一侧。
- **完整调用**：返回文本、finish_reason、用量（可缺省）与已解析的工具调用；provider 没有返回文本时显式失败，沿用现有 `_response_text` 的语义。
- **流式调用**：返回可关闭的异步迭代器，逐项产出文本增量，最后一项带 finish_reason；调用方关闭或取消时适配器关闭底层响应，关闭失败只记录日志、不替换正在传播的取消。
- **异常**：上下文超窗转换为 `ModelContextWindowExceededError`，已知的提供商失败转换为 `ModelProviderError`，原始异常保留在原因链；其他异常与取消原样传播。完整调用、流式启动与流式拉取三个边界采用同一转换，与现有 `LLMClient` 一致。
- **JSON 模式**：只在 SDK 明确报告不支持该参数时回退为普通补全，与异常收敛后的现状一致。

### 4.3 infrastructure 适配器

- 单个无状态适配器实现端口，可被全部使用方共享；不读取配置、不持有默认模型。
- `BaseLLMService`、`ConfiguredLLMService`、`LiteLLMService`、两个工厂函数与 `infrastructure/llm/errors.py` 中的 SDK 元组随使用方迁移删除；SDK 元组只作为适配器的私有实现保留。
- 没有生产调用方的工具调用接口按端口的工具定义重新提供或不提供，实施时依据届时的调用方确定，不为不存在的使用方保留兼容层。

### 4.4 使用方的迁移

- **Gateway**：查询理解与话题路由经端口的 JSON 输出调用，构造时取得由 `shared.llm.gateway` 转换的请求参数；降级只针对 `ModelProviderError` 与模型解析失败，与现状相同。
- **Patchouli**：抽取器与 Page Folding 摘要改为异步并经端口调用，由 `shared.llm.librarian` 转换请求参数。抽取的重试只针对 `ModelProviderError`，耗尽后抛出中立错误，由生成任务按失败收尾，不再记录为“没有产出”；程序错误与取消照常传播。重试次数沿用现有默认值。Page Folding 摘要只在 `ModelProviderError` 时回退为简单摘要。
- **Alice**：`LLMClient` 改为建立在端口之上的 MTP 生成器，保留 MTP 停止符、定界符检测与补齐、`GenerationResult` / `StreamChunk` 语义；会话摘要器经同一生成器或直接经端口调用，只捕获中立错误。`build_agent_runtime` 接收端口，`AliceSystem` 不再构造客户端。
- **组合根**：创建一个适配器，分别交给 Gateway、Patchouli 与 Alice；组件的固定参数在组合根或组件构造时转换，适配器本身不感知是谁在调用。

### 4.5 架构守卫

扩展既有的分层守卫：litellm 只能在 `infrastructure/llm/` 中导入；`core/ports/llm.py` 不依赖任何 SDK；L2 引擎与 L3 子系统不导入 infrastructure 的 LLM 实现模块，只依赖端口（组合根除外）。

### 4.6 必须保持的行为

- 每个使用方发给提供商的参数与现状一致：组件侧的 model、凭证、temperature、max_tokens（现有实现不传 top_p 与 stop），Alice 侧的 model、凭证、temperature、top_p、max_tokens 与 MTP 停止符。迁移时逐个使用方比较迁移前后的 SDK 调用参数。
- Alice 的流式分块、定界符补齐、取消时关闭响应的语义不变；`ModelProviderError` 与超窗错误的分类、CPU 失败原因与摘要器的降级不变。
- Gateway 与 Passive 的降级条件不变。有意的行为变化只有两处（第 1 节第 4 点）：Patchouli 抽取在提供商失败时由“没有产出”改为显式失败；Page Folding 摘要的回退收窄到提供商失败，程序错误不再被简单摘要掩盖。

## 5. 受影响的系统、契约和数据

- **core**：新增 LLM 端口与模型；`ModelProviderError`、`ModelContextWindowExceededError` 迁入 `core/errors/model.py`，`agent_runtime` 包根继续导出它们。
- **infrastructure**：LLM 包改为单一适配器。
- **Gateway / Patchouli / engines**：LLM 依赖改为端口；Patchouli 抽取与 Page Folding 摘要变为异步。
- **Alice / agent_runtime**：生成器建立在端口上，内核工厂接收端口。
- **System**：组合根创建并注入适配器。
- **不变**：公开 HTTP 与 SSE 契约、配置键、模型注册表、持久化数据、MTP 协议。

## 6. 兼容与迁移

- 端口与适配器先落地并通过适配器自身的测试，再逐个迁移使用方；每个阶段结束时后端全量测试通过，不保留新旧两条并行的 SDK 调用路径超过一个阶段。
- 删除的符号不保留别名：`LiteLLMService` 与工厂函数只有组合根、Gateway 与 Patchouli 使用，随同修改。
- 测试中直接替换 `litellm.acompletion` 或 `LLMClient.generate_async` 的用例，改为向端口注入手写替身；只有适配器自身的测试替换 SDK。
- Patchouli 抽取失败语义的变化在[Patchouli 生成](../patchouli/generation.md)与错误模型中记录，并用归属层测试覆盖。

## 7. 实施阶段

**阶段一：端口、错误与适配器**

1. core 端口与请求、结果、分块模型；两类模型错误迁入 `core/errors/model.py`；
2. litellm 适配器实现完整调用、流式调用、JSON 模式与异常转换；
3. 适配器的归属层测试。

验收：第 8 节第 1、2 项。

**阶段二：Gateway 与 Patchouli 迁移**

1. 两个分析引擎经端口调用；
2. 抽取器与 Page Folding 摘要改为异步并经端口调用，重试与失败语义按第 4.4 节；
3. 组合根注入适配器，删除 `LiteLLMService`、配置绑定基类、工厂函数与对外的 SDK 元组。

验收：第 8 节第 3–5 项。

**阶段三：Alice 迁移与收尾**

1. MTP 生成器建立在端口上，`build_agent_runtime` 与 `AliceSystem` 改为接收注入；
2. 架构守卫；
3. 晋升事实文档（第 10 节），同步 Plans 导航与 ROADMAP，归档本计划。

验收：第 8 节全部。

## 8. 测试和验收标准

按[测试设计规范](../governance/testing/test-design-standards.md)分类；每条不变量只在作出判断的归属层写权威测试，上层与 E2E 只保留代表性链路，验收测试写入归属层的现有文件。

1. **适配器参数**：请求参数逐项传给 SDK，不补入请求未携带的参数；JSON 模式只在 SDK 明确不支持时回退（改写现有 `tests/unit/infrastructure/test_litellm_service.py`）。
2. **适配器异常与关闭**：完整调用、流式启动与流式拉取的超窗与提供商失败分别转换，原因链保留，其他异常与取消原样传播；流在耗尽、关闭与取消时都关闭底层响应（同上）。
3. **Gateway 降级**：提供商失败与模型解析失败降级，程序错误传播（现有 `tests/unit/engines/gateway/` 测试改为注入端口替身）。
4. **Patchouli 抽取与摘要**：抽取的重试只针对提供商失败，耗尽后显式失败而不是没有产出；Page Folding 摘要只在提供商失败时回退；等待 LLM 时事件循环可以推进其他任务（`tests/unit/engines/generation/`、`tests/unit/engines/perception/` 与生成服务的归属层测试）。
5. **组件参数各自独立**：Gateway 与 Librarian 经组合根得到各自配置转换的请求参数（组合根测试；单例修复的回归测试随适配器迁移改写到这一层）。
6. **Alice 生成语义**：停止符、定界符补齐、分块序列、取消关闭与中立错误分类不变（现有 `tests/unit/agent_runtime/model/test_client.py` 改为端口替身）；摘要器的降级不变。
7. **依赖方向**：litellm 只在 `infrastructure/llm/` 中导入，端口不依赖 SDK（扩展 `tests/unit/architecture/test_package_layers.py`）。
8. **链路不变**：Alice、Gateway、Patchouli 生成的现有集成测试与离线 E2E 通过。

## 9. 风险与待决问题

| 风险或问题 | 处理 |
|:---|:---|
| 迁移中发给提供商的参数漂移（例如组件侧意外多传 top_p） | 第 4.6 节逐使用方比较 SDK 调用参数，结果记入第 11 节 |
| 抽取改为异步后与 chat 并发，提供商限流更容易触发 | 不改变重试次数；限流表现为 `ModelProviderError` 按失败收尾，记入文档；需要并发控制时另行评估 |
| 抽取失败从“没有产出”变为显式失败、摘要回退收窄，影响生成任务的终态统计与 Topic 折叠 | 作为两处有意的行为变化，在生成文档与错误模型中记录并测试 |
| 测试大量替换 SDK 或 `LLMClient` 方法，迁移成本高 | 提供一个共享的端口替身 helper，逐个文件迁移；只有适配器测试替换 SDK |
| 流式关闭与取消语义在适配器与生成器之间分工不清 | 关闭底层响应只在适配器中做，生成器只负责关闭适配器的流；沿用现有取消回归 |
| 实施命名（端口、请求模型、适配器、MTP 生成器的名字与模块） | 实施评审时确定并记入第 11 节 |
