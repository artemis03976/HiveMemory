# v0.7.0 代码结构成因调查基线

本文冻结 `source_commit` 上对 v0.7.0 代码结构的成因调查。该提交位于分支 `refactor/v0.7.0-convergence-p2`，是收敛清单第 2.15 条前三项完成后的状态。

调查的起因是 owner 的判断：v0.7.0 至今的实现较乱，各种边界叠加之后，整体流程并没有更有序；零散的数据模型、函数与文件增多，任务进程与 CPU 体系也不够扎实。这不只是[代码收敛清单](../../todo/v0.7.0-code-convergence.md)覆盖的那些问题。

本轮只调查并整理文档，没有修改代码；最新行为仍以代码、测试与当前设计为准。第 3.1 节的成因已经形成[任务进程拥有执行流计划](../../archive/plans/v0.7.0-task-process-owned-execution.md)（2026-10-19 完成并归档），其余成因只在本文记录，尚未排期（第 6 节）。

## 1. 范围与方法

- **比较区间**：`v0.6.2` 标签到 `source_commit`，共 40 个提交。
- **规模统计**：
  - 用 `git log --numstat` 按 `src/`、`tests/`、`docs/` 汇总增删行数；
  - 用 `git ls-tree` 统计两个版本的源码文件数与行数；
  - 用 AST 按种类统计类定义，分为 pydantic、dataclass、Enum、Protocol、异常类与其他。
- **代码结构**：
  - 通读任务进程（`workspace/process/`）、CPU 契约（`workspace/contracts/`）、actor API 与操作入口、认证与授权、Alice 的 CPU 适配与运行服务、`agent_runtime` 的帧与输出端口，以及 chat 路由；
  - 用 `git log --follow` 追溯进程记录与执行器的来历。
- **设计文档**：第五代架构、任务进程、执行单元、AE2、Chat Run 生命周期等 Idea，System 应用服务，以及 v0.7.0 已归档和已删除的计划。
- **判断边界**：本文只回答“为什么整体显得乱”，不逐条评价单个模块。单个模块的缺陷由收敛清单跟踪。

## 3. 成因

### 3.1 执行骨架沿用旧的 chat run，任务进程不拥有执行流

**来历**：

- `ProcessRecord` 与 `ProcessTable` 的前身是 v0.4.0 取消加固时写的 `system/runtime/control.py`。#103 把它原样搬到 `alice/application/chat_control.py`，#105 再改名迁入 `workspace/process/table.py`。
- v0.6.2 的 `ChatApplicationService` 已经有 `_run_interruptible`、`ChatGenerationRun`、run registry 和生成器式的流式输出。
- [任务进程表计划](../../archive/plans/v0.7.0-task-process-table.md)（历史）阶段 A 的目标是“改用进程的词汇；行为不变”。之后的计划在这个骨架上逐步叠加了访问 context、线程、会话认领、检查点、封口与 CPU 分配，执行模型本身始终没有重新设计。
- [Chat Run 生命周期 Idea](../../ideas/chat-run-lifecycle-follow-ups.md) 的候选 A（独立 Job 与 SSE 解耦）当时被延后，理由是它“只增加 registry、task、队列和关闭协议”。此后，进程表与句柄、关闭协议（`close_process`、`closed` 事件、shutdown 等待、响应收尾时的兜底关闭）都已实现；task 与队列也已存在，只是放在 Alice 内部。

**证据**：进程由交付方逐项拉取的一串异步生成器推进，链路依次是 chat 路由的 pull task → `_deliver_stream` → `TaskProcessRunner.run` → `AliceCPU._execute` → `AgentRunStream._events`，最底层是 Alice 的 runner task 与有界队列。这种结构带来了以下现象：

- `TaskProcess.owner_task` 不固定。System 关闭时只能先发出停止，再等交付方自己收口，超时后才兜底关闭。
- chat 路由每个事件都新建一个 pull task 并检查一次断连；执行器每次拉取，又经 `_run_interruptible` 再新建一个子 task。
- 停止如果落在两次拉取之间，只会记录一个标志，要等下一次拉取才生效。
- 生成器被关闭时不能返回值，部分输出只能经 `CPUResultSlot` 从旁路回填。
- 正常结束、拉取中停止、两次拉取之间停止、断连和异常各是一个出口，需要分别收尾。因此在 `runner.py` 的 Actor 阶段与关闭流程中，`revoke_threads` 被调用 4 处，`_accept_checkpoint` 被调用 3 处，另外还有一个 `(CancelledError, GeneratorExit)` 分支。
- 执行器收尾、交付收尾、路由收尾和 shutdown 都会走到 `close()`，幂等只能靠工作集里的资源“只取出一次”来保证。
- 正确性依赖时序不变量，例如“封口、会话追加、进入 finalize 与登记提交任务之间没有 await/yield”。
- Alice 内部是推模型，进程层是拉模型，停止信号和执行结果都要在两种模型之间来回转换。

**影响**：名为“进程”的对象其实只是被动的状态容器，执行流属于 HTTP 连接。操作系统、AE2 与任务进程 Idea 对进程有三点共同要求：独立于读取方推进，任务寿命独立于终端，只有一条退出路径。现状与这三点都不一致，这是“任务进程与 CPU 体系没有夯实”的直接来源。

### 3.2 抽象按未来的多个实现设计，当前只有一个，无法校验

**证据**：

- **设计目标**：第五代理念面向任何执行者接入，包括外部 harness 的 controller 与 plugin 模式、被动请求和跨 Workspace。
- **现状**：
  - `CPUPort` 只有 `AliceCPU` 一个实现；
  - 接入登记只有 HTTP server 与 Profile 注入器两个内部 principal；
  - `WorkspaceIdentity` 要求 key 与 id 相同；
  - 被动请求按 Q-6 暂不考虑；命令只解析、不执行；
  - 进程表是否收录后台任务（Q-7）、外部执行单元的进程怎么处理（Q-8）仍未决定。

  实际只存在主动 chat 这一种进程。
- **“中立”只在类型上成立**：
  - `CPUOutput` 里的交互事件是 `dict[str, Any]`，内容用的是 Alice 的词汇（token、mtp_start、sub_agent_start），原样穿过进程送到前端。执行单元 Idea 也把“CPU 输出使用谁的词汇”列为未决问题。
  - `CPUInputManifest` 的 `agent_profile`、`language`、`allowed_operations`（由 Alice 翻译为 MTP 动词）与 `compaction_checkpoint`（由 CPU 判断格式）都是按 Alice 的形状确定的。

**影响**：每条中立边界都要配一个 Protocol、一个中立 DTO、一个适配器和一处映射，零散的模型类与文件大多出在这里。只有一个实现时，无法验证这些边界是否切对了。

### 3.3 边界按所有权原则划分，与数据流不一致，回流通道多

**证据**：

- **能力层在运行时依赖进程**：理念要求能力层不依赖进程，但实际上：
  - WRITE/UPDATE 经 `IntentDispatchTopicReader` 从进程取派发话题，路径是 `ActorMemoryService._dispatch_coordinates` → `ProcessThreads.get_dispatch_topic`；
  - CALL 经 `ChildThreadSpawner` 回到 `ProcessThreads` 派生子线程。

  这两处都靠 `workspace/thread_ports.py` 里的 Protocol 通过导入守卫。
- **CPU 到进程的回流**：检查点经结果槽回来，交互事件以原始字典回来，CALL 经 actor 操作回到进程。
- **提示词编译被切成两半**：进程编译记忆、附件与人格，CPU 负责布局、MTP 教学与历史。
- **阶段顺序被扭曲**：Profile 被提前到 prepare 之前解析，只是因为 prepare 有不可逆的副作用（任务进程 Idea 2.2）。

**影响**：后来加入的会话（#122）、意图在途派发（#120）和会话压缩（#126）都必须穿过这条边界。结果槽和多处检查点接受，就是会话压缩为了穿过它而开的路径。

### 3.4 纵切迁移逐片叠加概念，切片之间没有整体合并

**证据**：

- **计划与决定的频度**：
  - v0.7.0 已归档 24 份计划，另有约 8 份中途作废删除（A 系列、计划 A 宪章、WRX-0 冻结清单等）；
  - #104 删除了 2658 行文档；
  - 文档中带日期的 owner 决定标注共 56 处，其中 9 月 19 处、10 月 37 处。
- **概念逐片叠加**：访问 context（#106）→ 身份第二批（#107）→ 操作适配器（#108）→ 能力面拆分（#113）→ 白名单（#114）→ 线程 context（#115）→ 执行线程（#116）。“线程”是后来补到访问 context 上的，于是分散在 `RunBinding.thread_id`、`AccessRunType.EXECUTION_THREAD`、`ThreadContextLifecycle`、`ProcessThreads`、`ExecutionThread`、`ThreadOperationSubmitter`、`ChildThreadSpawner` 和 `IntentDispatchTopicReader` 中。
- **重复校验**：一次 WRITE 会把同一个线程 context 校验 4 次，分别在操作入口、操作授权、读取进程关联和读取派发话题时。
- **签名反复变动**：`CPUPort.execute` 的签名在各份归档计划中依次是 `(manifest, *, generation_options, stream)`、带 `operations`、带 `credential`、带 `access`；收敛清单第 2.7 条又去掉了 `stream`。
- **同一位置反复修改**：`runner.py` 被 40 个提交中的 16 个修改过；进程记录在 v0.7.0 内从 `system` 迁到 `alice`，再迁到 `workspace`。

**影响**：纵切的初衷是避免脱离实际做理想设计（见第五代架构 Idea 第 1 节）。但每一片都默认前面的结构已经稳定，中间没有整体合并的环节。收敛清单是逐条清理，同样合并不了骨架。

### 3.5 约束靠规则、守卫与运行时防御维持，结构被提前冻结

**证据**：

- 35 个架构测试按函数粒度规定调用方，例如“阶段授权只能由任务进程调用”“线程生命周期只能被 `ProcessThreads` 消费”。运行时需要的依赖一旦被守卫禁止，就新增一个 Protocol，例如 `thread_ports.py`、`ThreadContextLifecycle`、`_AgentProfileReader`。
- 正确性依赖时序注释，例如 `runner.py` 的封口与关闭、`ActorMemoryService._dispatch_coordinates`、`ProcessRecord.is_terminal`。
- `table.py`、`task_process.py`、`working_set.py`、`service.py` 的 docstring 大段在说明“这件事由哪个邻居负责”。
- 密封的访问 context 拒绝复制与序列化，而它的 docstring 同时说明，这只是在维护可信进程内的调用纪律。
- 规划侧也有同样的现象：2026-10-06 时，六份 current Idea 共约 2950 行，主 Idea 里约有 90 个问题编号。

**影响**：任何重新分解都要同步修改守卫、文档、AGENTS.md 与状态图，结构在被验证之前就已经难以改动。

## 4. 成因之间的关系

- 3.2 与 3.3 产生了大量中立 DTO、端口与回流通道；
- 3.1 带来了取消、关闭与资源释放的复杂度；
- 3.4 解释了骨架为什么一直没有被重新设计；
- 3.5 让现状难以调整。

## 5. 不属于成因的部分

单个模块的质量并不差：包分层清楚，并由守卫维持；当时 CI 等价门槛的结果是 2951 passed、2 skipped，覆盖率 93.94%；取消语义也有测试守护。

任务进程中站得住的部分如下，它们在进程拥有执行流之后可以原样保留：

- 执行器与进程容器分离，分别对应所有进程共享的代码和每个进程自己的数据；
- 进程记录里的阶段与结局；
- 停止规则：只有 Gateway 与 Actor 两个阶段可以中断，prepare 与分配期间收到的停止在进入 Actor 前统一生效，FINALIZE 阶段拒绝停止；
- 工作集登记资源，并在关闭时释放。
