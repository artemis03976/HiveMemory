# 记忆核心：写入链路

## 0. 文档性质

本文是 v0.8 设计讨论的子文档，2026-11-16 从[总纲](./memory-flow-short-to-mid-term.md)中按主题拆出，内容未删减。总纲有 owner 的出发点与总体说明、全部决定的一览（第 1.3 节）、与讨论有关的代码现状（第 2 节）、外部调研的启发与评判方式；外部项目与文章的事实见[外部参考](../research/memory-core-external-references.md)。本文不描述当前行为，也不代表排期；除注明为 owner 决定的内容外，都是讨论中的分析或候选设计。

结构：第 1 节是 owner 关于写入链路与 Patchouli 角色的说明；第 2 节是写入链路（对照已有记忆复核、主动写入的背景与短期记忆、时间线、什么值得写）；第 3 节是 Patchouli 的角色（馆长、保存来源与能力分级、知识与工具）；第 4 节是整理写入与生命周期维护的边界；第 5 节是两条写入路径在哪里汇合（被动一侧已决定）。

## 1. 讨论中的说明（owner）

**写入链路**

- 按时间线消费交互的来源（2026-11-14）。[统一的交互记忆](./unified-interaction-memory.md)中按时间线消费交互的设想（owner 称之为绝对交互时间线），多少来自 VCPToolBox 的 OneRing：它宣称是"终极分布式上下文统一方案"，能为 Agent 维护唯一化的上下文。真实机制与两者的联系见本文第 2.3 节、[外部参考](../research/memory-core-external-references.md)第 3 节。
- 被动结算的定位（2026-11-15）。被动话题的结算问题已经比较清楚：作为话题的终态收尾者，完全可以让它知道这个话题以来发生过哪些记忆事件、又需要补充哪些关键记忆，以全局视角重新审视这次话题的信息含量；让生成事件带有轮次事件的信息，至少保证了溯源的清晰度。所以有一部分候选设计已经成立（第 5 节）。主动写入写下之后即生效，在任何修订到来之前，其内容本身仍然有效且合理，不能因为话题还没有结算就假设它已经是"旧结论"。
- 主动写入缺少背景（2026-11-15）。被动结算相对前台的主动写入是一个很晚的时间点，看得全但是很慢。八个调研项目中有五六个是"一句话直出"：agent 按 skill 调研，完成调研报告并写入记忆库；此时前面没有话题轮次，只有 agent 的指令能用作生成材料。在最初的几个调研工作流验证中，agent 喜欢略去背景、直接写结论，生成侧又没有东西可补，写出来的记忆是"空中楼阁"，owner 因此在 skill 中补充要求：主动写入要完整说明问题背景与解决方案（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节、本文第 2.2 节）。
- 背景是短期记忆的缺陷（2026-11-15）。"背景"问题仍是短期记忆的缺陷，也是 owner 提出流式接收交互事件的原因之一。这个方案的诡异之处在于相当于照抄一遍 agent 的上下文：大部分已有工作把短期记忆描述为"上下文"或"working memory"，即当前正在做什么，这是第一方视角，好比 Alice 能直接控制上下文的注入；HiveMemory 一手拿不到上下文，就算拿到也不能直接介入管理，于是只能复写一份副本，而且对复制的时机有要求。本质上，背景的缺失仍是时序问题，也因为拥有完整背景的前台 agent 并不是第一写入人。已有调研基本没人关注这一点，最接近的主题反而是直接影响上下文的"对话压缩"。由此要问：作为一个"外人"，系统对 agent 短期记忆的支持应当是什么样的，即 agent 短期记忆的定义（第 2.2 节）。
- 时间线仍然存在，但不必流式（2026-11-15）。绝对时间线这件事仍然存在，毕竟所有事件在交互中都有到来的先后；只是没有必要再非要做成"流式"。VCPToolBox 的 OneRing 对此有什么启发（第 2.3 节）。
- 消费水位退场（2026-11-15）。时间线上"每个事件只消费一次"的水位语义确实该退场了（第 2.3 节）。
- 完整性的上限在 harness（2026-11-15）。Obelisk 声称"统一格式有损"，但这本身是 harness 的问题，不是提炼记忆带来的：作为第三方拿不到真正完整的会话记录，这一点已在项目中被证实。所以即便保存了原始会话记录，这条路从根源上就是断的，做不做提炼都不会改变；owner 因此一直在尝试自己开发 harness，让会话记录彻底透明、可见、可操控（第 2.2 节）。

**Patchouli 的角色**

- Patchouli 作为馆长（2026-11-15）。owner 构想过让 Patchouli 晋升为面向 MemoryLibrary 的自主 Agent，打破现在只有一次 LLM 调用的一次性流程：短期、中期、长期库她都能自由探索，这是"图书馆馆长"天然的权力。外部 agent 主动写入但不感知记忆库的本质，Patchouli 拥有最高权限，根据手上的材料决定怎样放进记忆库。本质上是一个专职 agent，但同时拿到了 agent 的长处与对外的隔离，与第 2.1 节的复核思路不冲突（第 3.1 节）。
- agent 循环的现状（2026-11-15）。`agent_runtime` 一直"独属于 Alice"：工具调用只能用 MTP，不能并发调用工具，仍按 stop sequence 以 ReAct 方式停止生成，工具执行环境 KoakumaRuntime 也还是原型。owner 很早就考虑过 Patchouli 是否也需要共用它，一直想把它做得通用；要让 Patchouli 以它为底层，需要先好好优化。
- Patchouli 的能力范围与外部来源（2026-11-15）。如果只是浏览记忆库并有限地写入，MTP 也够用；owner 也设想过赋予她更高级别的"查证"能力，例如访问网络追查资料、执行一定量的沙盒工具。原因之一是记忆原子"保存外部文档来源"的功能一直因为没有来源而无法启动：用户上传的文件、agent 在对话中拉取的网页都是易逝的，记忆应当保留对来源的引用；现在的路径里没有谁能整理出这一点，作为终端的 Patchouli 是否应当补上（[总纲](./memory-flow-short-to-mid-term.md)第 2.5 节、本文第 3.2 节）。

## 2. 写入链路

### 2.1 对照已有记忆复核（另一位 agent 的思路与评估，2026-11-15）

**思路**：
- 保留两个写入时机，对同一份中期记忆承担不同的责任：主动写入负责兑现明确的保存意图；被动提取负责在一段经历结束后，检查已有记忆还有哪些遗漏或错误。两者都由 Patchouli 整理并写入。
- 与断言设想的区别在于先做什么判断：断言先问"这段材料里有哪些值得记的主张"，再逐条判断与库的关系；这里让被动路径先看到相关的已有记忆，再问"经历了这一段之后，哪一条需要怎样改？还有什么值得记的，在这些记忆里完全找不到？"。
- 主动写入的优先权落在"值得保存"上：WRITE 提供了被动路径还原不了的信号，即当事人在那一刻认为这件事值得让未来的 agent 找回来。Patchouli 可以发现已有记忆已经完整表达、可以整理措辞，但应保住它的用意，并允许它沿现有路径及时生效。边界：WRITE 只证明当时作出了这个判断，之后复验失败仍应纠正；没写某件事只说明没有提出保存请求，沉默推不出审阅过并决定舍弃。
- 被动结算的材料：本次话题轨迹；这段交互中明确写入或更新过的内容及其可定位的目标（主动写入提供了确定的线索）；少量可能受影响的既有记忆（跨话题的靠检索补充）。三种判断：已有记忆足以支持下次使用，保持原文（同一结果被工具输出、agent 总结与 WRITE 转述三遍，仍只算一份依据）；新材料改变了某条记忆的结论、适用条件或当前状态，定位到那条，只修改发生变化的部分并指明依据；有值得未来独立找回的内容、已有记忆承载不了，新建，一次可以新增多条，也可以一条都不新增。
- "这是新信息"只回答了以前有没有出现，没有回答值不值得改变记忆，后一问放在生成的中心。
- 按结论协调，不按轨迹区间消费：不让一次 WRITE 消费掉之前的整段轨迹，同一段可能还支持另一件事（例如用户中途纠正的工作习惯）。允许被动结算再次阅读证据；要抑制的是同一份证据反复制造新记忆，或被误当成多次独立验证。纯聊天时被动路径照常发现变化；主动写得充分时，读完整段得到零修改也是成功结果。
- 最薄弱处是能否找出真正相关的旧记忆，因此保守取舍：有明确对象和明确变化时才自动改写，两条内容仅仅相关时保留各自原意。
- v0.8 最先能独立验证的机制：被动结算针对已有记忆提出有依据的修改，并能判断"这一轮什么都不用改"；直接利用已有的 Topic、写入意图、正式记忆与来源 Artifact。断言是否持久化为独立对象，等确实出现跨多次整理复用的场景再决定。

**评估（我的看法）**：
- 这是到目前为止最具体、也最贴合[总纲](./memory-flow-short-to-mid-term.md)第 1.1 节诊断的一版：被动提取从"提取"变成"对照已有记忆复核"，新建成了例外，"改哪条、怎么改、要不要新建"在看到已有记忆之后判断，而不是事后靠相似度对账。它与第 2.1 节的最简版本方向一致，并把顺序讲清楚了；也给统一交互记忆 Idea 第 5 节的两问提供了合理的默认（没写不等于取舍；主动写入照现有路径立即生效），仍由 owner 决定。
- 认同的几点："新信息"不等于"值得改变记忆"，与第 2.4 节的判据是同一标准；按结论协调对消费水位的批评成立；保守取舍；"进行中"的终态成为对旧记忆的修订，在结构上解决而不是打补丁；两种交互形式落在同一套机制里。
- 质疑：
  1. 最弱的一环恰好是[库的形状](./memory-library-shape-and-index.md)第 4.1 节。平铺库中"相关的已有记忆"只能取全库相似度的前几条，同项目的记忆在索引层天然相近；如果库有分组，可能受影响的记忆可以是所在分组的内容，像主动写入一样确定。所以这个方案让库的形状更关键。
  2. "只修改发生变化的部分并指明依据"，现有的修订做不到（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。整篇重写在多次修订中会让细节漂移，mem0 放弃写入时由 LLM 增删改的理由正是覆盖会丢细节。可以借 Hindsight 的做法：模型只给结构化判定（保持；修订某一部分并给出依据；新建），由唯一写入者按判定落地，修订以局部修改的形式记入版本，自动修改因此可以审计。
  3. "同一份证据只算一次"需要证据有可定位的身份，现在的引用只到整个 Artifact；主动写入一侧知道自己在哪一轮（MCP 写入带 `turn`），被动一侧还没有。
  4. 结算时机仍然重要，但不再那么敏感：现在的结算与经历是否结束无关，修订机制让提前结算的代价变小，前提仍是下一次结算找得到那条记忆。
  5. 正式记忆被 LLM 改写的频率会明显上升：一条记忆的当前版本可能是多次自动修订的叠加，版本 Artifact 保留了快照，但没有记录每次修订依据的是哪段证据。

**更早的提议：素材来源与生成之间的中间表示（2026-11-13，owner 未决定）**

- 按整理的程度排列：会话轨迹（只追加的时间线，短期是其中尚未整理的尾部）→ 断言（小、带归属与证据、带发生时间的条目；主动写入是第一当事人的断言，被动提取只产出推断的断言）→ 正式记忆（只由整理写入）。三者都在中期库之前，术语沿用[统一的交互记忆](./unified-interaction-memory.md)。
- 最简版本：中间表示只存在于进入生成队列的路上，不单独存储；生成时把每一条与已有的中期记忆比对，参照 Hindsight 的逐条判定，判为重复、改变、终止、新增或不值得保存，取代相似度查重。更完整的做法是把断言作为单独存储的一层。
- 现在两条路径在生成之后由查重协调（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）；引入中间表示，意味着两条路径在生成之前汇合。

### 2.2 主动写入的背景与外部者视角下的短期记忆（候选定义，不是 owner 决定）

已有的框架见[短期记忆与上下文压缩](./short-term-memory-and-context-compaction.md)第 1 节：短期记忆分为 agent 的执行工作记忆（前台上下文）与 Patchouli 的记忆形成工作集（话题）；owner 于 2026-09-28 决定话题不承担前台会话上下文的控制。

**"复制上下文"的诡异感来自时序，而不是复制本身**。流式接收复制的不是 agent 的上下文，而是交互事实。上下文是前台 harness 对这些事实的视图（经过压缩、注入与截断），属于第一方，HiveMemory 拿不到，也不该管；话题与交互记录是同一份事实的另一种视图，属于写入者。短期 Idea 第 4 节早已如此表述：两份摘要根据共同的交互事实分别生成。外部者总是滞后的，各类使用者对滞后的容忍度不同：话题结算可以等到轮次结束（现在的 Import Bus 正是如此）；主动写入的生成需要截至写入那一刻的事实，缺背景正是因为这一刻写入者还没追上（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。owner 所说"拥有完整背景的前台 agent 并不是第一写入人"就是这个错位：有背景的不负责写，负责写的在写入那一刻没有背景。

**定义**：HiveMemory 的短期记忆，是时间轴上最新、尚未被整理的那一段交互记录。它按会话的时间线存放，按话题（经历节点，[库的形状](./memory-library-shape-and-index.md)第 2.2 节）归组；保存原文，每个事件都有轮次与事件的身份。它是写入者的工作记忆，不是 agent 的上下文。三类使用者：
1. Patchouli（写入者）：生成与复核的材料，主动写入需要的背景应当从这里来。
2. 其他上下文中的 agent：跨会话的 agent、压缩之后的同一个 agent、另一个 agent，用它了解"最近发生了什么"。这是外部者能为 agent 的短期需求做、而前台自己做不到的事：上下文压缩后会丢细节，另开会话就看不到之前的内容，而这份记录还在。但交互原文现在没有任何检索入口（[外部参考](../research/memory-core-external-references.md)第 4 节第 6 点）。
3. 维护：结算与复核的范围就是这一段尚未整理的记录。

这个定义落在时空框架上：短期就是时间轴新鲜的那一端。结算不是把短期"搬"成中期，而是这一段被整理之后，记录本身作为证据留下，它的经历节点留在时间轴上，整理出的记忆挂到主题与经历节点上。它与 2026-09-28 的决定一致：HiveMemory 不复制、不管理前台上下文，对 agent 短期需求的支持只走两条间接的路：把中期记忆送进上下文（检索与常驻的小索引），以及把最近的交互记录开放给需要它的上下文。

**写入就是同步点**。既然只有写入者需要"追平到当下"，就不需要持续镜像上下文，只需在写入发生时把轨迹追平到写入那一刻。写入前的 hook 已经在读本地会话记录，那一刻正是追平的时机；对长时间运行、一轮内多次写入的 agent，每一次写入都是一个同步点；持续的流式接收作为更通用的版本，留给[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)。两种落法：
- 作为生成材料随写入一起提交：不触碰交互的封口语义，但要截断或挑选（工具结果可能有 MB 级）。
- 作为未封口的部分轮次先导入话题：写入者的工作记忆真正追平，但要先回答长 Turn Idea 中开放交互、封口与迟到事件的问题。

**分工**：agent 提供意图（写什么、为什么写），skill 的要求只需保证这一点；事实背景来自记录，由写入者从短期记忆中取，而不是靠 agent 复述。agent 复述背景必然压缩，这正是"空中楼阁"的来源。

**"空中楼阁"其实是两件事**：一是记忆正文缺背景，读者看不出结论在什么情况下、为了解决什么问题得出；二是证据够不到，即使正文简短，能顺着链接找到背景就不是空中楼阁，只是"地基在别处"。调研类工作流中，背景其实就在 agent 刚写完的调研报告里：与其要求 agent 在记忆中再写一遍背景，不如让记忆写一段简短的背景，加上指向报告具体章节的来源链接（DocumentArtifact 与定位符，第 3.2 节第 2 级），后一件事由此解决，不依赖 agent 是否遵守 skill；前一件事靠写入即同步点。三者互补：skill 的要求作为下限，写入时有轨迹则由 Patchouli 补背景，结算时终态收尾者再以完整轨迹复核。

**与调研的关系**：几乎没有人关注外部者的短期记忆。dsh-agent-soul、gliding_horse 与上下文压缩调研中的五个 harness 都掌握前台；唯一接近的是 EverOS，它的"短期"是会话缓冲中尚未切出的尾段，单位是会话时间线，与这个定义一致。它没有解决的正是写入时机：EverOS 没有第一当事人的主动写入，从不需要在写入那一刻追平。

**外部者与第一方两种处境（分析，2026-11-15）**：Obelisk 读原生日志，只避开了"转换成统一格式"这一层损失，原生日志本身的不完整它同样无能为力（它自己的说明承认：Claude Code 的日志不标记回退与当前所在的分支，Codex 的日志没有分支的概念）。所以"证据层的完整性上限由 harness 决定"对第三方是结构性的（第 1 节）。由此，HiveMemory 面对两种处境：
- 插件模式下是外部者：拿不到上下文，记录的完整性受制于 harness；本节的定义与"写入即同步点"是为这种处境写的。
- 在自己的 harness 中（Alice，或 owner 正在开发的 harness）是第一方：上下文透明、可以操控，事件可以按发生顺序直接交给 Patchouli，时间线与流式接收都变得自然，短期记忆甚至可以与上下文统一管理。

同一套设计需要写明哪些机制两种处境共用、哪些只在第一方的处境中成立，避免把自研 harness 才有的条件当成所有入口的前提。

### 2.3 时间线：顺序与身份，不是流式（分析；水位语义退场为 owner 决定，2026-11-15）

时间线关乎顺序与身份，流式关乎多早送到，是两件事：时间线一直需要，流式只在某些使用者等不起时才需要。

**时间线需要的三样**：
1. **每个事件都有稳定的位置**：会话内由"会话、轮次、事件序号"确定（轮次有外部标识，Import Bus 由它推导交互标识；轮内事件本来就按序号排列）；跨会话之间只有发生的时间。统一交互记忆 Idea 第 3.3 节已经写明：时间线按会话划分，并发的不同会话之间只有时间戳，没有可消费的先后。所以"绝对时间线"的准确含义是会话内全序、跨会话按时间戳排列的偏序。
2. **按发生的位置排，不按到达的先后排**：批量导入时，事件到达的顺序可能与发生的顺序不同（导入延迟、重试、多会话并发）；只要事件自带位置，晚到的也能插回原处。反过来，按到达顺序拼时间线，流式也救不了。
3. **重复导入不产生重复，晚到的事件有处理规则**：Import Bus 已按外部会话串行导入、按交互标识去重；还缺事件级的身份（第 5 节已决定生成事件带上轮次与事件的信息），以及"已经切过的段又来了迟到事件"的规则（长 Turn Idea）。

这三样在轮次结束时批量导入就能做到。

**流式（更早送到）只在这几种情况下需要**：写入时的同步点，按需追平到写入那一刻（第 2.2 节）；轮次结束遥遥无期的长 turn，又有使用者需要更早看到事实（长 Turn Idea）；以后出现的其他延迟敏感的使用者。崩溃安全不需要流式：harness 的会话记录在本地磁盘上，连接器下次同步时仍能导入。

**时间线的角色变了**：最初的设想中，时间线还承担"消费水位"，每个事件只被消费一次，以免重复提取。按第 5 节的决定，被动结算是话题的终态收尾者，以全局视角复核，按结论协调而不按区间消费，这层消费语义不再需要：owner 于 2026-11-15 确认，统一交互记忆 Idea 第 3.3 节的消费水位语义就此退场。时间线留下两个角色：顺序与身份的骨架（时空图索引中时间轴的底座，经历节点建在其上）；证据的坐标（记忆引用"第几轮、第几个事件"，指向时间线上的位置）。即：时间线保留，"每个事件只消费一次"的水位语义退场，流式降级为按需追平。

**OneRing 的启发：它是一份"流式"的账本，却不是一条可靠的时间线**（本文第 2.3 节、[外部参考](../research/memory-core-external-references.md)第 3 节）：
1. **有流式而没有身份，就成不了时间线**：OneRing 在每个请求经过时记账，但消息没有 ID、没有会话字段，按写库时刻排序，于是只能靠 hash 猜"是否已存在"（重复的短句被当成已有）、晚于最后一块的消息被丢弃、编辑原地覆写不留历史、重试时相似度 ≥0.92 的两条用户消息被合并。时间线成立的条件是身份与位置，不是送达方式。
2. **过早接收、没有封口语义，就会留下孤儿**：OneRing 在预处理阶段就写入用户消息，AI 回复要等整轮成功才写，一轮失败或断连后账本里留下没有回复的孤立用户消息；这正是长 Turn Idea 中开放交互、封口与迟到事件要回答的问题，也是第 2.2 节倾向"按需追平"而不是"持续流式"的理由。结构上，VCP 是坐在前端与模型之间的代理，每个请求都经过它，所以能在请求那一刻记账；HiveMemory 在插件模式下不在请求路径上，能介入的只有会话开始、写入之前与轮次结束这几个 hook，"写入即同步点"是其中最接近 OneRing 记账那一刻的地方。
3. **读回其他上下文要慎推、多拉**：OneRing 是调研中唯一把外部记录读回别的上下文的例子（第 2.2 节第二类使用者），为此加了很多限制：只在上下文少于 10 块时补、只插进时间戳可信的缝隙、每条加来源尾标、"宁可不补也不补错"，可见把原始消息推进运行中的上下文风险很高；它的另一半做法 OneRingMemo（把近 3 天压缩成常驻的客观时间线摘要）反而更稳。所以给其他上下文提供最近的经历，以常驻的近期摘要为入口，细节按需去拉（检索交互记录、读经历节点），与时空图索引的时间轴新鲜一端加常驻小索引中"最近几段经历"是同一回事。
4. **"同一个它"作为视图保留，不作为存储单位**：OneRing 以 Agent 为单位存账本，代价是不同话题互相渗入；但"这个 agent 最近在各处做了什么"的需求成立。在 HiveMemory 中它可以是时间线上的一个视图：时间线按会话存放，每个事件带着参与者（轮次上已有 actor 身份）与来源（harness 名），按 agent 过滤出的那条线就是"同一个它"，按话题、按时间过滤是另几个视图。存储只有一份、视图可以有很多个，与[库的形状](./memory-library-shape-and-index.md)第 4.1 节"存储平铺、分层由派生索引承担"同一个思路，只是放在时间轴上。

一句话：OneRing 想要的（Agent 级的连续性、每条消息带来源、整轮完成才落账、一份常驻的近期摘要）都对；它没做好的（没有身份、按到达排序、在请求路径上过早写入、直接把原文推进上下文）恰好说明 HiveMemory 的时间线该怎么做：位置与身份先行，流式按需，读回时以摘要为入口、细节按需去拉。

**OneRing 与按时间线消费交互**

OneRing 留下的理念是：连续性的单位是 Agent，而不是某个前端临时传来的消息数组。两个具体做法与 HiveMemory 一致：AI 回复只在整轮完成后才落账，与"有输出时才封口提交"是同一个原则；每条消息标明是谁、何时、从哪里来。它的实现则说明了几件事（[外部参考](../research/memory-core-external-references.md)第 3 节）：

1. **以 Agent 为单位，代价是不同话题互相渗入**，同一前端的多个窗口也分不出来。统一交互记忆 Idea 第 3.3 节把时间线按会话划分，再由话题按内容跨会话归并，正好绕开了这一点。所以"绝对时间线"可以作为存放的顺序，但被消费时需要切分（按会话或按话题），不能整条交给模型。
2. **用途不同。** OneRing 服务于上下文补齐，只有 100 条，读完不做任何结算；按时间线消费服务于记忆生成，每次触发时消费到当前为止的事件，每个事件只被消费一次。OneRing 里没有这层语义，它是 owner 的设想自己加上的。按第 5 节的决定，这层消费语义已经退场（owner，2026-11-15），时间线保留为顺序与身份的骨架（第 2.3 节）。
3. **事件需要稳定的身份。** OneRing 做不到"编辑作为新事件追加"，根本原因是消息没有 ID，只能靠 hash 判断"是否已存在"，于是重复的短句被当成已有，晚到的消息被丢弃。HiveMemory 的 Import Bus 用 harness 给出的外部轮次标识推导交互标识，不需要模糊比对。
4. **保存更彻底。** HiveMemory 的 InteractionArtifact 保存全部交互原文，比 OneRing 本身更接近它宣称的"旧消息不会无意义丢失"。
5. **OneRingMemo 是一个常驻的近期动态摘要。** 一份跨前端、跨会话的近期时间线摘要，可能是值得常驻的少数内容之一（第 2.4 节），也与短期记忆的定义有关。

### 2.4 什么值得写：内化与价值标准

1. **内化一半落在交付上。** 模型的权重不变，一段知识"属于 agent"只能表现为：需要的时候，它以能直接用上的形式出现在上下文里。HiveMemory 为此选择了动态检索，并保留了从索引到正文的渐进式披露（第 1 节）；四百多条记忆照旧动态检索，这一点不变。在此之上仍有两点值得考虑：
   - **由谁判断该加载什么。** skill 机制让模型看到常驻的菜单，由模型决定读哪一篇；检索由系统按相似度决定，模型只看到命中的结果。两者失败的方式不同：检索漏掉的，agent 察觉不到，它不知道自己不知道什么。所以只有少数漏掉代价很高的部分（用户偏好、可用子代理的清单，[库的形状](./memory-library-shape-and-index.md)第 2.1 节）不该依赖检索命中。
   - **日常路径上没有预检索**（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节）。外部 harness 上，记忆能否进入上下文完全取决于 agent 自己决定检索：它知道 HiveMemory 可用，却不知道库里有什么，比 skill 还多一层盲区（skill 至少把菜单放在了上下文里）。平铺的库中找不到比全部记忆更小、又能常驻的东西；分层时可以多级披露：常驻少量分组的描述，需要时读分组的索引，再读正文，agent 不必看到每一条记忆，也能知道哪些方向值得检索。这与[库的形状](./memory-library-shape-and-index.md)第 4.1 节是同一个问题。
2. **"一切都是记忆"与"一条生成链路"之间有张力。** VISION 写明"统一并不等于同质化"：skill 是必须整体正确的程序性文档；犯错的反思是一次经历得到的教训；知识库条目的真相在外部文档里，记忆更应该记从中学到了什么、何时、用于什么决定，而不是复制它。现在的被动提取按单次结算进行，只能产出事实一级的东西；人从经历得到先验知识，靠的是在多次经历上归纳，而 HiveMemory 现在跨经历的机制只有按相似度两两合并。调研中真正做"经历变成知识"的都是在多条经历之上整理：EverOS 把聚类的 agent case 生成 `SKILL.md`，Hindsight 从事实沉淀出 observation、再到 mental model。只改进单次提取到不了内化，缺的是一个跨经历归纳的环节，它可能比提取本身更关键。
3. **判断"是不是知识"需要一个标准。** dsh-agent-soul 给 `SELF.md` 的入选判据是"这一行不在了，我会不会做出不同的决定"。流水账不满足它，owner 删掉的 PR 记录大概也不满足。现在被动提取的价值标准是"包含具体的讨论内容"，衡量的是记录完整，不是能否改变决定。这个判据可以作为重新设计时"什么值得成为记忆"的原则，而不是一处提示词修补。Anthropic 的文章给出了一个更具体的判据：环境能重新告诉你的不记，只有自己推出来、不写就会消失的才记（[外部参考](../research/memory-core-external-references.md)第 4 节）。
4. **全自主维护缺少结果信号。** 系统只知道一条记忆被检索到、被读过，不知道它有没有让 agent 做对或做错；验证状态没有写入方、负反馈没有发出方（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节）正是这个缺口。人的遗忘与强化按"用上了、有效"选择；没有结果信号，自主维护只能依据访问这类替代信号。这可能是自主维护目标中最难、也最需要提前设计的一环。两个可能的信号来源（[外部参考](../research/memory-core-external-references.md)第 3 节）：一是记录使用方实际采纳了哪些检索结果，"被采纳"比"被检索到""被读取"强得多；二是检索本身暴露的知识缺口，命中稀疏、覆盖不足，说明库在这方面缺少内容，能告诉自主维护"该补什么"，而不只是"该删什么"。

## 3. Patchouli 的角色

### 3.1 Patchouli 作为馆长

- **价值判定的位置**：停用外部价值标记的根本理由，是判断"值不值得记"需要知道库里已经有什么；外部评判者看不到库，只能判断"像不像有价值"。现在缺的不是信息，而是没有把信息放到做判断的地方（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。
- **馆长 agent 是第 2.1 节的执行形式，不是另一个方向**。两个实际的好处：
  1. 它补的正是第 2.1 节最弱的一环：找出相关的旧记忆本质上是探索问题，一次性调用只能拿到相似度的前几条，agent 可以换说法反复检索，顺着版本与来源 Artifact 往回查，也能去冷藏库里看。
  2. 隔离让[库的形状](./memory-library-shape-and-index.md)第 4.1 节可以单独决定：外部 agent 只表达"我想保存这个"，不需要知道库是平铺还是分层，外部 harness 的四个工具可以不变，库的形状成为馆长一个人的事。

  跨经历的归纳、补知识缺口、决定归档什么，以后也都适合交给它。调研中最接近的先例是 VCPToolBox 的"记忆大师"：普通 agent 用专门的提示词列日记、读候选、自己写合并稿，但没有唯一写入者，没有审计，只能手动触发。
- **边界：自由放在读的一侧，写的一侧保持收紧**：
  1. 写入仍是结构化判定（保持；修订某一部分并给出依据；新建；提议归档），由 MemoryGenerationFamiliar 落地，修订连同依据记入版本；不给自由重写或删除的能力。
  2. 提示词注入的风险放大：材料中有不可信内容，而馆长拥有全库最高权限。只允许修改本次运行读过并能给出依据的记忆，不提供删除，所有修改都能经版本回退。
  3. 读的权限最高，写要守可见范围：不能把 PRIVATE 的内容带进 PUBLIC 记忆，延续"策略不同的记忆不合并"。
  4. 成本与并发：每次结算一个 agent 运行，开销是一次性调用的数倍，运行越长同改一条记忆的冲突越多；最简单的是每个 Workspace 同一时间只跑一个馆长，并设步数与 token 预算。
  5. 所有权边界：`agent_runtime` 属于 Alice 子系统，工具又是 MTP，而记忆操作的能力在 actor API，馆长的工具应是 Patchouli 内部的操作。可选：Patchouli 自带一个小的工具循环（多一个循环概念）；把通用循环内核下沉一层共用；让馆长作为 Alice 的 frame 运行（等于让 Alice 持有记忆库的写入者，与 Patchouli 是权威冲突）。这是架构层面的决定，大概需要一份 ADR。
- **推进顺序**：第一步用固定流程实现复核（取本轮动过的记忆与相关记忆，一次判断，输出结构化判定），相当于探索步骤写死的馆长；第二步只放开读的一侧，让馆长自己决定还要查什么（检索中期库与冷藏库、读版本与 Artifact，有步数上限），写的一侧沿用第一步的判定格式与审计。第一步因此也是评估第二步的基线：多探索几步是否把相关记忆找得更准。
- **先做第一步**（owner，2026-11-18）：固定流程的复核本来就是新的主被动复核需要实现的，被动结算要结合主动写入动过的记忆来生成；它不等于 agent 化。agent 化（第二步的循环放在哪里、agent_runtime 与 MTP 解耦）排在它之后。第一步之前，先让生成出来的记忆指向具体的交互轮次（第 5 节，owner，2026-11-18）。

**第一步建立计划前要决定的三项**（待 owner 决定）：

1. **判定的格式**：动作集合已有候选（保持；修订某一部分并给出依据；新建；提议归档；不删除），还要定每条判定带什么。依据的选项：只写一句理由；指向材料中的轮次与事件（与“生成事件带上轮次与事件的信息”一致，材料要保留事件坐标）；引用原文片段（最直观，但材料很长时判定也随之变长）。修订的说明写进版本记录现有的 changelog。影响：依据越细，事后核对与回放验收越容易，模型的输出也越长、越容易出格式错误。
2. **复核的输入**：两部分。一是本话题的写入与更新怎样交给结算：现在生成材料不渲染 WRITE 与 UPDATE，控制面只在进程内记下写入结算到的记忆 id、交给查重丢弃。选项：结算时取这些记忆的全文；在材料中按发生位置渲染写入与更新；两者都要。二是相关旧记忆按什么找：现在查重以每条草稿为查询取 dense top-1。选项：以每条草稿为查询取 top-k；以整段材料为查询取 top-k；两者合并去重。影响：找不到的旧记忆就复核不到，这是第 2.1 节说的最弱一环；候选越多，判定的输入越长。
3. **修订的粒度**：第一步整篇修订，依据写进版本说明；或者只改受影响的段落，这要求正文按段可寻址，取决于[库的形状](./memory-library-shape-and-index.md)第 4.2 节仍开放的保存形态。影响：整篇修订现在就能做，但第 2.1 节质疑过多次修订后会走样；局部修订要先定保存形态。

### 3.2 保存来源与 Patchouli 的能力分级

- **保存来源必须针对当时看到的那一份**：附件存储重启即清空，网页之后会变，事后联网抓取得到的已不是 agent 当时看到的内容。结算时这些内容通常还在：附件还在附件存储里，网页内容已在交互 Artifact 里。缺的是判断：这一轮的哪些记忆依赖了哪些来源、值不值得单独保存、具体哪一部分支撑了结论（以引文或行号定位）。这正是馆长的工作，只需要读与结构化写，不需要联网。
- 它顺带补上几个缺口：外部来源的 DocumentArtifact 加定位符，是"同一份证据只算一次"所需证据身份的一部分；[库的形状](./memory-library-shape-and-index.md)第 3.1 节"不会漂移的证据"对文档现在并不成立，因为没有快照；验证状态没有写入方，馆长可以先根据轨迹中的证据写它（例如后来的工具结果表明修复没有生效）。
- 有的 harness 的网页工具返回的是按提问处理过的内容，不是原页面，所以能从轨迹中保存的是"agent 看到的那一份"。这对记忆恰恰是对的：记忆依据的就是 agent 当时看到的东西。
- **查证是另一种能力**：联网追查、运行沙盒工具，服务于检查一条记忆现在是否仍成立或寻找规范出处。风险大得多：后台 agent 会根据私人记忆自己拟查询发往外部服务（隐私）；网页内容进入一个能改全库的写入者（注入）；馆长运行沙盒工具就成了工具宿主（第 3.3 节）。
- **分三级分别决定**：

  | 级别 | 能力 | 依赖 |
  |:---|:---|:---|
  | 1 | 读全部三层库、读轨迹与 Artifact，结构化写（复核、修订、新建） | 第一步的固定流程甚至不需要循环 |
  | 2 | 保存来源：把轨迹中已有的内容存成带快照的 DocumentArtifact，以定位符挂到记忆上 | 同上，没有外部访问 |
  | 3 | 查证：联网、沙盒 | 成熟的 agent 循环，以及隐私与注入的策略 |

- **agent_runtime 的改造不必挡在 v0.8 前面**：前两级用不到并发工具调用、原生工具调用协议与沙盒，馆长的工具是内部读取操作、输出是结构化判定，很简单的循环就够；只有第 3 级需要成熟的通用循环。改造的方向正是把循环与 MTP 解耦，之后下沉一层供 Alice 与 Patchouli 共用，可以作为并行的主线。

### 3.3 知识与工具：按由谁消费来划界

- **知识由模型的推理消费**，改变的是 agent 怎样决定；**工具由环境执行**，改变外部世界或带回观察。修自行车的 skill 文档是知识，配套的脚本才是扳手。
- 记忆库中像工具的成员，恰好是需要特殊路径或例外的那几个；日常使用的主路径（外部 harness 经 MCP）只开放四个记忆操作（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节）。
- "记忆作为工具"有三种解读，目标各不相同：
  1. 记忆操作本身是 agent 的工具：检索、读取、写入、修正。这是 VISION 第 5.2 节的原意，现在已经成立。
  2. 关于工具的知识：哪个版本可用、怎样失败过、根因是什么，扳手留在插件里，记忆保存对它的引用与使用经验。被动提取把出错的工具结果当作修复经验的依据，是这个方向的雏形。
  3. 记忆本身被执行（RUN）：HiveMemory 成为工具的宿主，要与 harness 和插件在沙箱与环境上竞争，而它在这些方面没有优势。MaaT Idea 第 5 节列的可信、可复现、溯源、复用四个轴，在知识不等于工具的视角下更像工具宿主应有的性质，未必是记忆系统的。
- 同一个视角也许能解开 agent profile 的问题：把它拆成定义（模型、配置、提示词，是工具性的配置，不进入记忆的维护）与关于这个 agent 的知识（擅长什么、哪些任务做得好或做砸了）。后者是真正的记忆，可以被生成、合并与维护，也能帮助选择委托给谁。这只是让 profile 享受维护好处的一种实现方式。
- owner 于 2026-11-15 明确：AGENT_PROFILE 的"可运行"只是能被 CALL 调用，与 RUN 执行记忆性质不同，可运行的轴不延伸到它（[类型体系](./memory-type-system.md)第 6.2 节）。按 MTP 契约，CALL 是委派：被调用方须在本 Workspace 有准入，子 frame 以被调用方的身份和操作集合运行，Profile 只提供 persona、模型与语言；两者相同的只有"按 alias 精确解析"，那是寻址方式。上面的拆分仍是候选，理由是定义要稳定、精确，而关于 agent 的知识会演化，与可运行无关。
- owner 随后决定把定义一半（图纸）移出中期记忆库，单独成一个 store（[类型体系](./memory-type-system.md)第 6.3 节）；关于 agent 的知识一半仍是候选。

## 4. 整理写入与生命周期维护的边界

按 owner 的划分（第 1 节），用三个问题区分：

| | 整理与写入 | 生命周期维护 |
|:---|:---|:---|
| 由什么触发 | 新材料：一次结算或一次主动写入 | 时间、使用情况与库的状态，与有没有新材料无关 |
| 看哪些记忆 | 这份材料直接牵涉到的记忆：本轮动过的，以及与它相关的 | 整个库，包括从未在同一份材料里出现过的记忆 |
| 回答什么 | 这段新经历是否改变了库 | 库本身是否仍然一致、好用 |
| 典型动作 | 复核、修订、新建，或什么都不改 | 冲突检测，记忆的分裂与合并，对照轨迹纠错，过时检查，维护分组、索引等组织方式，归档 |

第 2.1 节的保守规则正好是分界线：对象明确、变化明确的改动留在写入时；两条内容仅仅相关的情况交给维护。由此推出三点：

1. **重叠是暂时的，并且印证了"写入决定维护的难度"。** 现在看起来重叠，是因为写入时缺少复核，质量的负担全压在落库之后：先新建，再由查重提名合并。写入时的复核做好之后，"改哪条还是新建"在落库前就已决定，写入时的查重与合并基本退场；剩下的合并是旧记忆之间随时间变得相近，属于纯粹的维护。
2. **分属的是由谁决定，写入者仍只有一个。** 维护作出的分裂、合并与纠错，都经 MemoryGenerationFamiliar 提交，才有版本与来源；拆开的是决策方与触发方式，不是写入通道，否则就多了一个并行的写入者。馆长（第 3.1 节）可以同时承担两种角色，只是被不同的事件唤醒。
3. **写入时要为维护留好接口**：证据可以定位到轮次或事件（第 2.1 节质疑 3）；修订是局部修改而不是整篇重写（质疑 2）；验证状态有写入方（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节）。维护对照轨迹纠错、检测冲突，都依赖这三点。

## 5. 两条写入路径在哪里汇合（被动一侧已决定，owner，2026-11-15）

**决定**：两条路径在中期记忆上汇合（第 2.1 节）。
- 主动写入写下即生效；在任何修订到来之前，它的内容是 agent 当时的第一当事人判断，有效且合理，不因为话题还没有结算就被视为"旧结论"，也不加"待复核"之类的标记。修订是改进，不是纠错。
- 被动结算是话题的终态收尾者：它知道这个话题以来发生过哪些记忆事件（写入、更新），以全局视角重新审视这个话题的信息含量，对已有记忆作出修订、补上缺少的关键记忆，或者什么都不改。
- 生成事件带上轮次与事件的信息，保证溯源清晰（第 2.1 节质疑 3）。

**先做：让生成出来的记忆指向具体的交互轮次**（owner，2026-11-18）。它排在馆长的第一步（第 3.1 节）之前：被动结算下的复核与复核要用的判定格式都依赖它，判定要能指回材料中的轮次，复核要能看到写入与更新发生在哪一轮。坐标在哪一步丢失见[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节：原始记录有轮次与事件的身份，生成材料、模型输出与记忆的引用都没有。具体的轮次只能由模型在草稿中引用；代码自己只能挂上全部轮次，也就是现在指向整个话题快照的引用。

**建立计划前要决定的两项**（待 owner 决定）：

1. **粒度**：只到轮次，或者到轮次与事件。只到轮次时，材料沿用现有的轮次编号，模型的输出最短、引错的机会最少；到事件时，材料要为每个事件编号，材料变长，引用也更容易出错。影响：复核的判定能指到多细（第 3.1 节第 1 项）。
2. **由谁读取**：新字段要有生产使用方，而现在记忆中的引用只被写入、在合并时带上，没有读取方。选项：管理页的记忆详情显示来源轮次及其原文，对 owner 核对生成质量最有用，要新增读取交互快照的接口，界面先出 mockup；或者作为复核方向的第一份计划，由下一份计划的复核读取，落地时暂时没有读取方，需要 owner 同意这个例外。影响：计划的范围，以及它单独成为一个方向还是复核方向的第一份计划。

候选默认（Claude 整理，不是 owner 决定，可在计划评审时调整）：

- 模型引用了不存在的轮次或没有引用：丢弃这个引用，保留指向整个快照的引用，记忆照常生成，与现在一致；
- 已折叠的轮次在被动材料中只以话题状态摘要出现：来自摘要的内容指向那次折叠的块，或者不指向轮次；
- 主动写入：本轮的 `turn_id` 在感知应用这一轮时才生成（`TurnRecord` 默认的随机标识），WRITE 执行时还不存在，`TurnRecord` 也不记录交互标识；主动写入先只指向材料中已完成的轮次，指回 WRITE 所在的这一轮与下面"仍开放"的主动写入材料一起解决；
- 合并取两条记忆来源轮次的并集；已有记忆不回填，仍指向整个快照。

**原来其他选项的去向**（作为背景保留）：生成之后由查重按相似度协调（v0.7.3 的"话题内主动写入优先"）不再作为方向，它会把修正当作复述丢弃；生成之前经同一种中间表示汇合（第 2.1 节、统一交互记忆 Idea 的断言层），中间表示暂不持久化，等确实需要跨多次整理复用时再决定（第 2.1 节）；读取时汇合（dsh-agent-soul 的做法）不采用。

**仍开放**：主动写入生成时能拿到什么材料。写入的那一刻，生成侧只有话题已完成的轮次与 agent 在 WRITE 中写下的内容，当前这一轮还没有导入（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。owner 把它归为短期记忆的缺陷；候选是"写入即同步点"，在写入发生时把轨迹追平到写入那一刻，以及以来源链接补上够不到的背景（第 2.2 节）。

材料上的约束（2026-11-16 由已归档的[写入意图 Idea](../archive/ideas/pending-intent-migration.md)第 8 节移入，作为背景，不是 owner 决定）：

- 先取得材料契约所选时点的全部可用材料，再按生成预算编译，不让 adapter 截取最近几条代替领域读取；已折叠且未保存的原文无法恢复；
- Topic 缺失、越权、为空与读取失败分别表达，缺失不等于空材料；
- 生成侧只提供材料约束，不决定是否创建空 Topic；
- 意图接纳后物化失败，不回滚已应用的交互；Topic 清理不影响已接纳任务依赖的资料。

原第 8 节还记有 owner 2026-10-13 的方向：对话流式同步到 Patchouli 之后，材料是此前全部的交互记录加上当前一轮已接收的消息（见[Turn 内上下文折叠](./long-running-agent-intra-turn-context-folding.md)开头）；2026-11-15 owner 认为时间线仍然存在，但不必流式（第 1 节）。
