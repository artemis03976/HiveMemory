# 记忆核心：写入链路

## 0. 文档性质

本文是 v0.8 记忆核心的子文档，写入链路的设计：对照已有记忆的判断与修订、主动写入的背景与短期记忆、时间线、什么值得写、结算时 Patchouli 做什么、来源，写入与维护的边界，以及两条写入路径在哪里汇合。v0.8 的目标与各子文档见[总纲](./memory-flow-short-to-mid-term.md)，库的形状见[库的形状、图索引与保存形态](./memory-library-shape-and-index.md)，类型见[类型体系](./memory-type-system.md)，外部项目与文章的事实见[外部参考](../research/memory-core-external-references.md)。

正文是已定的设计，候选设计标“候选”；已经实现的部分以当前事实文档为准，本文只链接。

## 1. 目标与原则

写入链路把任何形式的交互整理成以后的 agent 能用上的记忆资产。以下原则约束全部设计：

- **两条写入路径都保留**：被动结算从交互材料中整理记忆，agent 的主动写入兑现它当时明确的保存意图。人本来就有“潜意识记忆”与“主动记忆”两种行为；chatbot 式交互中写记忆的主要是被动结算，agent 工作式交互中主动写入很密，两侧的信息同样重要。
- **两条路径在中期记忆上汇合**：主动写入写下即生效，被动结算是话题的终态收尾者（第 5 节）。
- **价值由写入者判定**：判断“值不值得记”需要知道库里已经有什么，外部评判者看不到库，只能判断“像不像有价值”，所以入口不给价值标记（`worth_saving` 已移除）。只有终端的 Patchouli 有资格决定“看到了什么但不写成记忆”；为此她要知道这个话题以来发生过什么、写过什么、改过什么，作为库唯一的管理者，她有权看到全部历史记忆记录。
- **唯一写入者**：所有写入，包括以后维护作出的修改，都经 MemoryGenerationFamiliar 提交，才有版本与来源。
- **记忆即知识**：持久化、可寻址、可追溯、可演化的记忆资产是 agent 所有知识的外部积累；skill 文档、犯错的反思、知识库，对无状态的 LLM 都是记忆。写入链路要把这些材料统一内化，成为真正属于 agent 的知识（第 2.4 节）。
- **写入决定维护的难度**：目标是全自主地维护记忆库，维护的难度从写入时就决定了；整理写入与生命周期维护仍是两件事（第 4 节）。
- **重新设计机制，不为机制打补丁**：为一个机制找补缺陷，相当于无限制地允许它复杂化；一项改进的评估要绕很多层才能说明效果，说明机制本身不对。设计时把可评估作为条件（第 3.1 节）。

数据流（当前实现见[记忆生成](../patchouli/generation.md)、[短期记忆](../architecture/short-term-memory.md)）：

```text
交互 ──导入或提交──> 交互记录（时间线；事件带轮次、序号与响应序号）──> 话题（短期工作台）
                                                                      │
                                                                     结算
                                                                      v
                                                          一次性生成，或馆长 ─────┐
主动写入（WRITE / UPDATE）──意图登记──> Mode B / Mode C 生成 ─────────────────────┤
                                                                                v
                                                     MemoryGenerationFamiliar ──> 中期库
```

## 2. 写入链路

### 2.1 对照已有记忆：判断与修订的形态

被动结算作为终态收尾者（第 5 节），先看到相关的已有记忆，再问：经历了这一段之后，哪一条需要怎样改？还有什么值得记的，在这些记忆里完全找不到？这类判断与修订由馆长执行（第 3.1 节）。

**设计**：

- **三种判断**：已有记忆足以支持下次使用，保持原文；新材料改变了某条记忆的结论、适用条件或当前状态，定位到那一条，只修改变化的部分并指明依据；有值得以后独立找回、已有记忆承载不了的内容，才新建，一次可以新增多条，也可以一条都不新增。“这是新信息”只回答了以前有没有出现，没有回答值不值得改变记忆，后一问放在判断的中心。
- **结构化判定，以编辑集落地**：模型只给判定（保持；修订某一条并给出依据；新建），由唯一写入者 MemoryGenerationFamiliar 落地，修订连同依据的段记入版本，每次修订依据的是哪段证据都能审计。修订是一个编辑集：若干处“原文 → 新文”的片段替换，原文必须在当前版本中逐字出现且只出现一次；只有确实需要大段改写时，才替换整段或整篇。理由：整篇重写在多次修订中会让细节漂移，mem0 放弃写入时由 LLM 增删改，理由正是覆盖会丢细节（[外部参考](../research/memory-core-external-references.md)）；输出格式只有“给出新的全文”时，模型没有“有限度地改”这个选项，片段替换从结构上给出这个选项，编码 agent 能只改几行代码也是因为编辑工具要求先写出原文。
- **索引层随修订更新，只允许有限的修改**：检索与查重的向量只由标题、类型、标签与摘要编译，不含正文，只改正文的修订在检索中等于没有修订。标题与摘要只做片段替换；标签逐个增删，不整组重新生成；类型不变；编译文本变化时重算向量。修改的幅度由编辑集的结构限制，不另外比较修改前后的向量：修改前后稠密向量的余弦相似度分不开“状态真的变了的修订”与“同一主题的整条重写”（第一次 HaluMem 评测中整条重写的合并中位数 0.930、最低 0.800，试跑中正确的修订最低 0.876），而在编辑集的格式下，合并改了标题的从 16 次中 16 次降到 3 次。
- **三条更新路径一起改用编辑集**：被动结算的修订、主动 UPDATE 与查重提名的合并共用同一种编辑集与应用它的同一个函数，在同一次改动中完成；分开实施容易漏掉条件之间的联系，让所有的更新链路都留下问题。
- **写入时的合并是以保留记忆为底的修订**：查重提名的合并不再把两条对等的记忆融成一条，而是以保留的那条为底，把被吸收那条独有的内容写成对它的编辑集（补入新的事实、改掉被推翻的说法、逐个增加标签），落地后删除被吸收的那条。保留记忆是底，原有的细节不会被较新的那条覆盖。编辑集带着错误重试一次后仍不能应用时合并中止，两条都保留。哪两条记忆提名合并由查重决定；讲的不是同一件事的两条是否融合，是维护的决策（第 4 节）。
- **结局不取决于执行顺序与时机**：同一条链路上的更新，结局只由内容决定。几次合并提名串成一串、同一次结算的几条草稿命中同一条记忆，或者修订与合并同时落在一条记忆上，无论哪个先执行，结局都应是内容依次进入同一条记忆，或者明确地保留为两条；不能因为另一项写入恰好先执行就中止。
- **原文即前提条件，三条路径同一规则**：提交前重读基础记忆；版本没变就落地；变了就把编辑集重放到当前版本上，原文都还在且唯一就以当前版本为底落地，否则按各自路径的方式失败（馆长丢弃这一条修订，Mode C 以基础已变失败，合并中止）。不再要求基础的内容版本不变。合并的被吸收记忆在期间变了时不重放：要吸收的内容已经不同，合并中止。
- **合并依次执行并沿吸收关系改指**：同一 Workspace 的合并依次执行，两个合并不再同时写同一条记忆，也不会在模型调用期间删掉对方的目标；合并的目标已被吸收进另一条记忆时，改指仍然存在的那条，把内容补到那里。吸收关系只记在进程内，重启后改指不到时按目标缺失中止。
- **外部契约**：外部的 UPDATE 契约（MTP UPDATE 与 MCP `memory_update` 只传指令与内容）不变，编辑集在 Patchouli 内部产生。

候选设计：

- **主动写入的用意要保住**：WRITE 提供了被动路径还原不了的信号，当事人在那一刻认为这件事值得让以后的 agent 找回来。可以整理措辞，但保住用意；WRITE 只证明当时作出了这个判断，之后复验失败仍应纠正。反过来，没写某件事只说明没有提出保存请求，推不出当事人审阅过并决定舍弃（这一问搁置，第 6 节）。
- **按结论协调，不按轨迹区间消费**：一次写入不消费掉之前的整段轨迹，同一段可能还支持另一件事（例如用户中途纠正的工作习惯）。允许再次阅读证据，要抑制的是同一份证据反复制造新记忆，或被误当成多次独立验证：同一结果被工具输出、agent 总结与 WRITE 转述三遍，仍只算一份依据。主动写得充分时，读完整段得到零修改也是成功的结果。
- **保守取舍**：有明确对象和明确变化时才自动改写；两条内容仅仅相关时保留各自原意，交给维护（第 4 节）。
- **“进行中”在结构上解决**：一段工作的终态成为对旧记忆的修订，而不是靠提示词禁止进度措辞。

**现状与差距**：

- 上面的设计已经实现（[记忆生成](../patchouli/generation.md#34-编辑集修订已有记忆的共同形式)第 3.4 节）：馆长以 `revise_memory` 修订本次读过的记忆，Mode C 与合并输出编辑集，不合格时带着错误重试一次；三条路径提交前按同一条基础变化规则重读、重放或按路径失败；合并按 Workspace 依次执行，沿进程内的吸收关系改指。
- 改为编辑集之前，第一次 HaluMem 评测中一次性生成的 628 次合并有 98% 改了标题、全部改了摘要，前后文本相似度的中位数分别为 0.69 与 0.53，正文每合并一次中位数变为原来的 1.47 倍；同一条记忆合并 15 次之后，标题成了逐次累加的关键词清单。改为编辑集之后只在试跑中看过（16 次合并中改了标题的 3 次），没有在完整评测上复量。
- 依次执行与改指针对的是同一次评测中的合并中止：1,385 个生成任务有 82 个因合并中止失败，58 个是合并目标正等着被吸收，20 个是两个合并同时写同一条保留记忆，4 个是合并模型的输出无法解析，留下 82 对没有整合的相似记忆。改动之后同样没有在完整评测上复量。
- 吸收关系只在进程内，重启后改指不到的合并按目标缺失中止；在门外等待的合并占着生成 lane 的执行位，试跑规模下没有观察到影响。
- workspace 登记 UPDATE 时记下的基础版本（`UpdateFocus.base_version`）不再参与写回判断，只作记录，仍在 MTP 与 MCP 的意图契约中。

### 2.2 主动写入的背景与短期记忆

**问题**：被动结算看得全，但很晚。主动写入的那一刻，生成侧只有话题中已完成的轮次与 agent 在 WRITE 中写下的内容，外部 harness 的当前一轮要等轮次结束才导入。“一句话直出”的工作流中（agent 按 skill 调研、写完报告就写入记忆），话题是新的、空的，agent 又喜欢略去背景、直接写结论，写出的记忆是“空中楼阁”。背景的缺失本质上是时序问题：拥有完整背景的前台 agent 不负责写，负责写的 Patchouli 在写入那一刻还没有背景。插件模式下 HiveMemory 是外部者，拿不到上下文，拿到也不能介入管理；第三方拿不到完整的会话记录，这一点已在项目中被证实，证据层的完整性上限在 harness。

**设计**：plugin 模式下 HiveMemory 不复制、不管理前台上下文，话题不承担前台会话上下文的控制；controller 模式下记忆系统本身就是对 agent 的上下文管理，两种模式的分工见[短期记忆](./short-term-memory-and-context-compaction.md)第 1.4 节。短期记忆以话题为载体，话题的进展回答“进行到哪一步”，设计见[短期记忆](./short-term-memory-and-context-compaction.md)；本节只讨论主动写入那一刻能拿到什么背景。

候选设计：

- **写入就是同步点**：只有写入者需要追平到当下，所以不持续镜像上下文，只在写入发生时把轨迹追平到写入那一刻。写入前的 hook 已经在读本地会话记录，那一刻正是时机；一轮内多次写入时，每一次写入都是一个同步点。持续的流式接收作为更通用的版本，留给[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)，属于短期记忆 V2。
- **分工**：agent 提供意图（写什么、为什么写），skill 的要求只需保证这一点；事实背景由写入者从交互记录中取，不靠 agent 复述，复述必然压缩。
- **“空中楼阁”是两件事**：一是正文缺背景，读者看不出结论在什么情况下、为了解决什么问题得出；二是证据够不到，即使正文简短，能顺着链接找到背景就只是“地基在别处”。调研类工作流中，背景就在 agent 刚写完的报告里：记忆写一段简短背景，加上指向报告具体章节的来源链接（第 3.2 节第 2 级）。skill 的要求是下限，写入时有轨迹则由 Patchouli 补背景，结算时终态收尾者再以完整轨迹复核。
- **两种处境**：插件模式下是外部者，记录的完整性受制于 harness，写入即同步点是为这种处境写的；在自己的 harness 中（Alice，或 owner 正在开发的 harness）是第一方，上下文透明、可以操控，事件可以按发生顺序直接交给 Patchouli，短期记忆甚至可以与上下文统一管理。设计要写明哪些机制两种处境共用，哪些只在第一方成立，不把自研 harness 才有的条件当成所有入口的前提；短期记忆的划分见[短期记忆](./short-term-memory-and-context-compaction.md)第 1.4 节，两种模式的统一是 V1 与 V2 之间的候选一步（同文第 1.5 节）。

材料的约束（候选）：先取得材料契约所选时点的全部可用材料，再按生成预算编译，不让 adapter 截取最近几条代替领域读取，已折叠且未保存的原文无法恢复；话题缺失、越权、为空与读取失败分别表达，缺失不等于空材料；生成侧只提供材料约束，不决定是否创建空话题；意图接纳后物化失败，不回滚已应用的交互，话题清理不影响已接纳任务依赖的资料。

**现状**：主动写入生成时的材料是话题的折叠摘要与最近若干个已完成的轮次，话题不存在时按空材料生成；写入前的 hook 只为工具参数补上当前一轮的用户消息与之前几轮的文本，用于确定话题，不带本轮的工具事件（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。

**开放问题：主动写入生成时能拿到什么材料**。

- 选项甲：写入即同步点，追平的轨迹作为生成材料随写入一起提交。不触碰交互的封口语义，但要截断或挑选，工具结果可能有 MB 级。
- 选项乙：写入即同步点，未封口的部分轮次先导入话题。写入者的工作记忆真正追平，但要先回答长 Turn Idea 中开放交互、封口与迟到事件的问题。
- 选项丙：材料保持现状，只以来源链接补够不到的背景。改动最小，不解决正文缺背景。
- 影响：主动写入的质量、Import Bus 与 MCP 写入的契约、长 turn 的封口语义。按 v0.8 的顺序，主动写入排在被动生成之后（[总纲](./memory-flow-short-to-mid-term.md)）。

### 2.3 时间线

**设计**：时间线保留为顺序与身份的骨架，“每个事件只消费一次”的消费水位语义退场，流式降级为按需追平。时间线关乎顺序与身份，流式关乎多早送到，是两件事。被动结算按结论协调、不按区间消费（第 2.1 节），所以不再需要消费语义；时间线留下两个角色：顺序与身份的骨架，即时空图索引中时间轴的底座，经历节点建在其上；证据的坐标，记忆引用“第几轮、第几个事件”。

时间线需要三样，轮次结束时批量导入就能做到：

1. **每个事件都有稳定的位置**：会话内由“会话、轮次、事件序号”确定，跨会话之间只有发生的时间。“绝对时间线”的准确含义因此是会话内全序、跨会话按时间戳排列的偏序。
2. **按发生的位置排，不按到达的先后排**：批量导入时到达顺序可能与发生顺序不同（导入延迟、重试、多会话并发）；事件自带位置，晚到的也能插回原处。按到达顺序拼时间线，流式也救不了。
3. **重复导入不产生重复，晚到的事件有处理规则**。

流式（更早送到）只在这几种情况下需要：写入时的同步点（第 2.2 节）；轮次结束遥遥无期的长 turn，又有使用者需要更早看到事实；以后出现的其他延迟敏感的使用者。崩溃安全不需要流式：harness 的会话记录在本地磁盘上，连接器下次同步时仍能导入。

按时间线消费交互的设想多少来自 VCPToolBox 的 OneRing；它的实现说明了时间线该怎么做（事实见[外部参考](../research/memory-core-external-references.md)第 3 节）：

- **位置与身份先行**：OneRing 在每个请求经过时记账，但消息没有 ID、没有会话字段，只能靠 hash 猜“是否已存在”，于是重复的短句被当成已有、晚于最后一块的消息被丢弃、编辑原地覆写不留历史。有流式而没有身份，成不了时间线。HiveMemory 的 Import Bus 用 harness 给出的外部轮次标识推导交互标识，不需要模糊比对。
- **不过早接收**：OneRing 在预处理阶段就写入用户消息，AI 回复要等整轮成功才写，一轮失败或断连后留下没有回复的孤立消息，所以倾向按需追平而不是持续流式。“AI 回复只在整轮完成后落账”与“有输出时才封口提交”是同一个原则。插件模式下 HiveMemory 不在请求路径上，能介入的只有会话开始、写入之前与轮次结束这几个 hook，写入即同步点是其中最接近 OneRing 记账那一刻的地方。
- **读回其他上下文时慎推、多拉**：把原始消息推进运行中的上下文风险很高，OneRing 为此加了很多限制；它的另一半做法 OneRingMemo（把近几天压缩成常驻的客观时间线摘要）更稳。给其他上下文提供最近的经历，以常驻的近期摘要为入口，细节按需去拉（检索交互记录、读经历节点）。
- **“同一个它”是视图，不是存储单位**：以 Agent 为单位存账本，不同话题互相渗入，同一前端的多个窗口也分不出来；但“这个 agent 最近在各处做了什么”的需求成立。交互按话题存放，每个事件带参与者与来源，按 agent 或时间过滤出的都是视图。存储只有一份，视图可以有很多个，与[库的形状](./memory-library-shape-and-index.md)第 4.1 节“存储平铺、分层由派生索引承担”是同一个思路。

**现状**：Import Bus 按外部会话串行导入、按交互标识去重；`TurnEvent` 有序号，并记下来自本轮第几次模型响应（[数据模型](../architecture/data-model.md#49-交互记录turnevent-与-interactionpayload)）；InteractionArtifact 保存全部交互原文。**差距**：“已经切过的段又来了迟到事件”的规则还没有，由[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)跟踪。

### 2.4 什么值得写

**设计**：动态检索加载记忆是有意的选择，保留从索引到正文的渐进式披露。内化有一半落在交付上：模型的权重不变，一段知识“属于 agent”只能表现为需要的时候，它以能直接用上的形式出现在上下文里。

**开放问题：什么值得写成记忆**，在孵化中。它决定馆长的提示词与被动结算的产出量，也关系到记忆价值体系的重新设计（[ROADMAP](../ROADMAP.md) 第 4.7 节）。

## 3. Patchouli 的角色

### 3.1 馆长：执行结算的 agent

**设计**：

- Patchouli 是面向 MemoryLibrary 的馆长：短期、中期、长期库她都能探索，外部 agent 主动写入但不感知记忆库，由拥有最高权限的 Patchouli 根据手上的材料决定怎样放进库里。这带来隔离：外部 agent 只表达“我想保存这个”，不需要知道库是平铺还是分层，外部 harness 的工具可以不变，库的形状成为馆长一个人的事。
- 结算时 Patchouli 要完成三件事：尽量不与本话题生成的记忆重叠；尽量不与库中相关的记忆重叠；在这两个前提下写记忆。前两步是两个阶段的探索：先看本话题生成的记忆，再看库里有什么相关的。最后仍有的重叠接受，不再为它加复核、去重或兜底的逻辑，兜底消除不了它。
- 这两个阶段由馆长 agent 完成，以 agent 的主动探索代替规则拦截与生成。一次性生成看不到本话题生成的记忆，也看不到库，只能先尽量多地提取，再由查重、触碰、合并提名与命中本话题生成的记忆即丢弃这一串规则补救，每一层都在补前一层的漏洞。找出相关的旧记忆本质上是探索问题：平铺的库中，一次性调用只能拿到相似度的前几条，agent 可以换说法反复检索，顺着版本与来源往回查；库有分组之后，可能受影响的记忆可以是所在分组的内容（[库的形状](./memory-library-shape-and-index.md)第 4.1 节）。
- Patchouli 内部自己定义工具与 agent 循环，不复用 Alice 的执行循环与 MTP，也不作为 Alice 的 frame 运行。`agent_runtime` 属于 Alice，工具调用只能用 MTP；记忆操作是 Patchouli 的内部操作，不是 MTP。让馆长作为 Alice 的 frame 运行，等于让 Alice 持有记忆库的写入者，与 Patchouli 的权威冲突。
- 一次性生成与馆长并存，作为用户选项，因为馆长更慢、开销更大。一次性生成的提取按现状冻结，不再为它的重复问题修补，有更好的解决办法时再优化；它的合并是三条更新路径之一，随之改用编辑集（第 2.1 节）。
- **馆长修订已有记忆**：按第 2.1 节的结构化判定与编辑集，修订本话题生成的记忆与库中已有的记忆，经 MemoryGenerationFamiliar 落地。修订工具对正文、标题与摘要做片段替换，对标签逐个增删；原文对不上时作为工具错误交回馆长，由它在剩余的步数内改正。

候选设计：

- **自由放在读的一侧，写的一侧收紧**：写入是结构化判定（第 2.1 节），由 MemoryGenerationFamiliar 落地，修订连同依据记入版本，不给自由重写或删除的能力。材料中有不可信内容，而馆长拥有全库最高权限，所以只允许修改本次运行读过、能给出依据的记忆，所有修改都能经版本回退。读的权限最高，写守可见范围：不把 PRIVATE 的内容带进 PUBLIC 记忆，延续“策略不同的记忆不合并”。每个 Workspace 同一时间只跑一个馆长，并设步数与 token 预算：运行越长，同改一条记忆的冲突越多。
- **可评估**：模型在输出中写明它的判断，例如每条已写入的记忆覆盖了什么、还缺什么、为什么新建，结果可以直接核对，不必事后再用另一个模型推断。
- **以后的角色**：跨经历的归纳、补知识缺口、决定归档什么，都适合交给馆长，由不同的事件唤醒（第 4 节）。馆长也可以在前台当参考咨询台：外部 agent 问“关于 X 我们知道什么”，馆长返回一段带引用的综合，同时保护调用方的上下文窗口（Perplexity 的检索子 agent，[外部参考](../research/memory-core-external-references.md)第 5 节）。

**现状**：已实现。话题结算的生成方式是用户选项 `patchouli.generation.settle_mode`（`one_shot` 默认，或 `librarian`）；循环、JSON 动作协议、六个工具（含只改本次读过的记忆的 `revise_memory`）、预算与失败语义见[记忆生成](../patchouli/generation.md#31-mode-a被动观察--archive)第 3.1 节，修订的编辑集与基础变化规则见第 3.4 节。

**差距**（[记忆生成](../patchouli/generation.md#8-当前限制)第 8 节）：

- 不提名合并：一次性生成留下的相近记忆不会被它合并，两种方式的产出在库中混合。
- 修订与“助手正文中的事实”的提示词只在 HaluMem 的试跑上看过，没有在日常结算材料上检查。
- 只读中期库中的记忆本身，不读其他话题的原始轨迹、冷藏库与版本记录。
- 同一 Workspace 的两次馆长结算可以同时运行，彼此看不到对方暂存的记忆。
- 动作是文本中的 JSON，模型不按协议输出时只能交回错误、消耗步数。
- 写什么由馆长的提示词决定，判据仍开放（第 2.4 节）。

### 3.2 保存来源与能力分级（候选）

- **保存来源必须针对当时看到的那一份**：附件存储重启即清空，网页之后会变，事后联网抓取得到的已不是 agent 当时看到的内容。结算时这些内容通常还在：附件在附件存储里，网页内容在交互 Artifact 里。缺的是判断：这一轮的哪些记忆依赖了哪些来源、值不值得单独保存、具体哪一部分支撑了结论（以引文或行号定位）。这正是馆长的工作，只需要读与结构化写，不需要联网。有的 harness 的网页工具返回按提问处理过的内容而不是原页面，能保存的就是 agent 看到的那一份，这对记忆恰恰是对的：记忆依据的就是 agent 当时看到的东西。
- **顺带补上的缺口**：外部来源的 DocumentArtifact 加上定位符，是“同一份证据只算一次”所需证据身份的一部分；文档有了快照，“不会漂移的证据”（[库的形状](./memory-library-shape-and-index.md)第 3.1 节）才对文档成立；验证状态可以先根据轨迹中的证据写，例如后来的工具结果表明修复没有生效。
- **查证是另一种能力**：联网追查、运行沙盒工具，用来检查一条记忆现在是否仍成立或寻找规范出处。风险大得多：后台 agent 会根据私人记忆自拟查询发往外部服务（隐私）；网页内容进入一个能改全库的写入者（注入）；馆长运行沙盒工具就成了工具宿主（第 3.3 节）。
- **分三级分别决定**：

  | 级别 | 能力 | 依赖 |
  |:---|:---|:---|
  | 1 | 读全部三层库、读轨迹与 Artifact，结构化写（复核、修订、新建） | 简单的工具循环 |
  | 2 | 保存来源：把轨迹中已有的内容存成带快照的 DocumentArtifact，以定位符挂到记忆上 | 同上，没有外部访问 |
  | 3 | 查证：联网、沙盒 | 成熟的通用 agent 循环，以及隐私与注入的策略 |

  前两级用不到并发工具调用、原生工具调用协议与沙盒。

**现状**：Alice 对话中的附件在结算产出新建或更新时被提升为 DocumentArtifact，但只写元数据：`source_uri` 指向不跨重启保留的附件存储，没有内容快照，也没有挂到记忆上。外部 harness 的网页、文件等工具结果作为轮次事件完整保存在交互 Artifact 中，记忆的版本记录可以引用其中的段，但这些结果没有被识别为来源。DocumentArtifact 的模型是齐的（来源 URI、取回时间、快照地址与定位符），没有接入主流程（[总纲](./memory-flow-short-to-mid-term.md)第 2.5 节、[Artifacts 与来源追踪](../patchouli/artifacts.md)）。

### 3.3 知识与工具

**设计**：知识不等于工具。知识由模型的推理消费，改变的是 agent 怎样决定；工具由环境执行，改变外部世界或带回观察：修自行车的 skill 文档是知识，配套的脚本才是扳手。“记忆作为工具”的对象与目标因此要从头考虑，不阻塞 v0.8，在孵化中；已经作出的边界决定见 [ADR-0003](../architecture/decisions/0003-memory-as-a-tool-and-mtp-run-boundary.md)。

**现状**：记忆库中像工具的成员，恰好是需要特殊路径或例外的那几个；日常使用的主路径（外部 harness 经 MCP）只开放四个记忆操作。AGENT_PROFILE 的定义已移出中期库，它的可运行只是能被 CALL 调用，与 RUN 执行记忆的内容性质不同（[类型体系](./memory-type-system.md)第 6.2、6.3 节）；关于一个 agent 的知识（擅长什么、哪些任务做得好或做砸了）仍是候选，可以作为记忆被生成、合并与维护，帮助选择委托给谁。

## 4. 整理写入与生命周期维护的边界

**设计**：整理写入与生命周期维护是两件事。Anthropic 文章中的 dreaming 属于维护；记忆的分裂与合并、冲突检测属于落库之后怎样保证演化质量，记在[生命力分数长期演进](./VitalityScoringLongTermEvolutionIdeas.md)方向 6。两者用三个问题区分：

| | 整理与写入 | 生命周期维护 |
|:---|:---|:---|
| 由什么触发 | 新材料：一次结算或一次主动写入 | 时间、使用情况与库的状态，与有没有新材料无关 |
| 看哪些记忆 | 这份材料直接牵涉到的记忆：本轮动过的，以及与它相关的 | 整个库，包括从未在同一份材料里出现过的记忆 |
| 回答什么 | 这段新经历是否改变了库 | 库本身是否仍然一致、好用 |
| 典型动作 | 复核、修订、新建，或什么都不改 | 冲突检测，记忆的分裂与合并，对照轨迹纠错，过时检查，维护分组、索引等组织方式，归档 |

第 2.1 节的保守规则正好是分界线：对象明确、变化明确的改动留在写入时；两条内容仅仅相关的情况交给维护。由此：

1. **现在的重叠是暂时的**，也印证了“写入决定维护的难度”：现在看起来重叠，是因为写入时缺少对照，质量的负担全压在落库之后，先新建，再由查重提名合并。写入时的对照做好之后，“改哪条还是新建”在落库前就已决定，写入时的查重与合并基本退场；剩下的合并是旧记忆之间随时间变得相近，属于纯粹的维护。
2. **分属的是由谁决定，写入者仍只有一个**：维护作出的分裂、合并与纠错都经 MemoryGenerationFamiliar 提交，才有版本与来源；拆开的是决策方与触发方式，不是写入通道，否则就多了一个并行的写入者。馆长可以同时承担两种角色，只是被不同的事件唤醒。
3. **写入时要为维护留好接口**：证据可以定位到轮次或事件（第 5 节）；修订是局部修改而不是整篇重写（第 2.1 节）；验证状态有写入方（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节）。维护对照轨迹纠错、检测冲突，都依赖这三点。

## 5. 两条写入路径在哪里汇合

**设计**：

- 两条路径在中期记忆上汇合。
- 主动写入写下即生效。在任何修订到来之前，它的内容是 agent 当时的第一当事人判断，有效且合理，不因为话题还没有结算就被视为“旧结论”，也不加“待复核”之类的标记；修订是改进，不是纠错。
- 被动结算是话题的终态收尾者：它知道这个话题以来发生过哪些记忆事件（写入、更新），以全局视角重新审视这个话题的信息含量，对已有记忆作出修订、补上缺少的关键记忆，或者什么都不改。
- 结算拆成沉淀与退役之后，同一话题会被沉淀多次：空闲只触发沉淀，退役前的最后一次沉淀是终态收尾。本话题之前沉淀出的记忆记作本话题生成的记忆，下一次沉淀看得到它们（[短期记忆](./short-term-memory-and-context-compaction.md)第 5 节）。
- 生成的记忆指向具体的交互轮次，保证溯源清晰：原始记录中的事件记下来自本轮第几次模型响应，一次响应与供引用的段都由事件派生、不保存；切段与引用以原始交互记录为准，生成材料只是视图。这继承了最初 Thought-Tool-Observation 三元组的思想，区别是分组依据来源记下的响应边界，而不是把思考猜着归给某个调用；`TurnEvent` 仍是唯一的原子事件。

不采用的汇合方式：

- 生成之后由查重按相似度协调（v0.7.3 的“话题内主动写入优先”，现在只留在一次性生成中）：它会把修正当作复述丢弃。
- 生成之前经同一种中间表示汇合（已归档的[统一的交互记忆](../archive/ideas/unified-interaction-memory.md)中的断言层）：中间表示暂不持久化，等确实出现跨多次整理复用的场景再决定。
- 读取时汇合（dsh-agent-soul 的做法）。

**现状**：已实现轮次指向。被动提取、主动写入、修订与馆长的模型引用段，代码换算为轮次标识加事件序号区间，保存在这一版记忆的版本记录中（[数据模型](../architecture/data-model.md#49-交互记录turnevent-与-interactionpayload)、[感知](../patchouli/perception.md#2-结构化摄入)、[记忆生成](../patchouli/generation.md#22-段标签与记忆引用)、[Artifacts](../patchouli/artifacts.md#24-memoryversionartifact)）。

**差距与候选**：

- 引用现在没有读取方，由馆长对已有记忆的修订读取（第 2.1、3.1 节）。
- 主动写入的锚点（候选）：WRITE、UPDATE 事件自身的位置，与证据分开。Alice 一侧在这一轮应用到话题之后，按事件的 `produced_aliases`（pending alias，结算后指向正式记忆）推出锚点；外部 harness 经 MCP 写入时，Import Bus 不接受 `produced_aliases`，alias 只在工具结果的原文中，要么由连接器取出写进事件、导入接受它（公开契约的变更），要么只记证据、不记锚点。
- 段的粒度（候选）：带思考正文的响应也开启新段。回放中 Claude Code 上思考使段数多约 30%（每轮段数中位 3、P90 13），dsh 的响应 87% 带思考正文，几乎每次响应自成一段。读取引用时若段太碎，可以改为只按正文切；已保存的引用是事件区间，不受规则调整影响。
- 引用的准确性：回放中引用全部合格，各次运行引用的段集合两两 Jaccard 均值 0.90；少数引用偏向这一轮开头的段，而不是更精确的后一段，以引用为依据时要容忍这种偏差。
- 已有数据：已有轮次没有响应序号，整轮一段；已有记忆不回填，仍只指向整份快照；合并的版本记录不带引用，来源经被吸收记忆的 Artifact 引用追溯，是否改为取两条记忆引用的并集，留给修订决定。

## 6. 非目标与搁置

- **非目标**：用强化学习让 agent 自发使用记忆工具（对闭源模型不可行）；plugin 模式下 HiveMemory 复制或管理前台上下文；写入链路承担生命周期维护（第 4 节）；修补一次性生成的重复问题。
- **搁置：第一当事人“没写”算不算判断**。被动结算会补回 agent 有意精简的内容；如果第一当事人对“写什么”也有权威，推断出的新细节是否要尊重它的不写。可能的处置有三种：丢弃；作为推断另立一条，与第一当事人的写入关联但不并入；挂为佐证。现在也没有办法表达“看过、决定不记”。
