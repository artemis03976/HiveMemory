# 记忆核心：类型体系

## 0. 文档性质

本文是 v0.8 设计讨论的子文档，2026-11-16 从[总纲](./memory-flow-short-to-mid-term.md)中按主题拆出，内容未删减。总纲有 owner 的出发点与总体说明、全部决定的一览（第 1.3 节）、与讨论有关的代码现状（第 2 节）、外部调研的启发与评判方式；外部项目与文章的事实见[外部参考](../research/memory-core-external-references.md)。本文不描述当前行为，也不代表排期；除注明为 owner 决定的内容外，都是讨论中的分析或候选设计。

结构：第 1 节是 owner 关于类型体系的说明；第 2 节是项目最初设计（2026-02-05）的回顾；第 3 至 10 节由原总纲第 9.6 节的各部分改为独立的节：出发点与现状；类型是做什么的（已决定）；怎样判断一个区分该不该成为类型（候选）；已从类型中移出的三处（已决定）；剩下的类型（资源记忆、FACT 的拆分、用户一侧、经历与只存在于记忆中的代码已决定，最后是类型全貌）；写法与修订上的候选；LLM 能否把握与回放检验（候选）；待讨论。

## 1. 讨论中的说明（owner）

**类型体系**

- WORK_IN_PROGRESS 的去留（2026-11-15）。重新审视类型体系，第一个要决定的是还要不要保留 WIP。它确实能表示哪项工作没有做完，但从 owner 的删除记录看，它一直得不到更新；即便更新了，现在的机制也不允许它变成其他类型，于是成了名义上一直在进行的工作记忆。owner 记得最初的设计中也没有这个类型；核对后，2025-12-23 的第一版设计中有它，后来从文档中删去（第 2 节）。owner 据此选择去掉这个类型，并且中期库不再收"当前进度"（第 6.1 节）。
- CODE_SNIPPET 与可运行（2026-11-15）。这个类型一开始是为代码复用而存在的，后来的 MTP RUN 又把它推向 MaaT 的一个实现点，允许它作为工具执行。owner 最初的想法其实是给记忆加一个 runnable 修饰符，声明它可以运行，而不是单独列一个类型；这已经在一定程度上说明了问题：类型本身是在声明记忆的使用形态或使用方法。在 MaaT 需要重新审视的当下，这个类型就比较尴尬：不是要删除它，而是它的地位不再明确。按不同轴的思路，runnable 本身就是一条轴，不应该绑在一个类型上，例如"这段 SQL 能在某个数据库里运行"与"当前 Alice 可以对这条记忆发 RUN"是两件事。但这不延伸到 AGENT_PROFILE，两者性质不同：runnable 的理念几乎只服务于"可运行的记忆"，成熟的形态应当是对这条记忆做某种 AOT 或 JIT 编译，形成像可执行代码一样的东西在沙箱中运行；AGENT_PROFILE 的目的不是这样，它的"可运行"只体现在能被 CALL 调用，与此有很大区别（第 6.2 节）。
- AGENT_PROFILE 的取舍（2026-11-15）。USER_PROFILE 与 AGENT_PROFILE 都描述主体，一般的 agent 系统也只有这两种主体；微妙之处在于前者存的是用户偏好画像，后者存的是职责事实，实际的读取者与修订条件差别很大，用词接近，却很难定义它们的类型体系。讨论从 AGENT_PROFILE 开始：最初把它放进记忆库，是想得到两点好处，一是 agent 能被检索发现，二是 agent 的提示词能在演化中得到修正。后者在没有明确反馈途径的情况下，执行者不会主动去修改，只剩检索发现一点；而把 agent profile 的列表固定在提示词中，与 agent 主动去找一个 profile，实际差得并不多，以前的方案确实太过理想。用户制定的 agent profile 一般不会很多，载进提示词不会有大问题。另外，在现在的插件模式下，HiveMemory 这一侧定义的 agent 穿透不到 harness 中使用，所以把 agent profile 移出中期记忆库、单独列一个 store，分得更清楚（第 6.3 节）。
- 类型体系要提供什么（2026-11-16）。解决了 WIP、可运行与 AGENT_PROFILE 之后，记忆类型实际上回到了最初的设想，此时重新考虑类型体系会更清楚。按几条预定的性质轴为记忆原子打标签，相当于多个正交维度的性质叠加，有一点像 VCPToolBox 用 Tag 来构建"按什么分"；但要设计记忆类型，仍然必须先决定希望从类型体系里得到什么。owner 选择以维护契约为主（第 4 节）。随后补充：以维护契约为主，不等于类型只服务于记忆维护，也不是只要满足一个消费方就行。检索与送达可以合并，两者都相当于决定记忆出现的位置，于是消费方是四个。一条记忆之所以值得赋予一个类型标签，是因为下一位使用者对它有一种可以预期的用法。同日看过另一位 agent 的分析（同一决定之下三个命中相同关键词、却该导向不同行动的问题）之后，owner 改写了决定：类型首先告诉读者能拿它做什么，其次告诉馆长怎样才算写完整，修订时只作提示（第 4 节）。
- 资源记忆是导览（2026-11-16）。比较清晰的一点是 CODE_SNIPPET 与 URL_RESOURCE 的同质性：两者都试图表达对一个外部资源的记忆，对应 owner 最初痛点中的"外源信息的高成本与易逝性"，原文是："通过 Web Search 或 Deep Research 获取的高价值信息（如第三方库文档、法律条款、API 规范）仅存在于当前的 Context 中。一旦会话结束，这些高保真信息即丢失。下次任务需再次联网搜索，既增加了时间成本（Latency），又引入了因搜索结果变动而导致的不一致风险。"这其实并不太准确：存下的资源内容本身就是快照，会随着时间过时；怎样定义"外源信息"也是问题，存在当前电脑环境中的一份文档算不算，一个网址算不算；如果存了一份文档的内容副本，为什么不直接去读这份文档，现代的 agent harness 完全有能力随时随地读取，而且能保证最新。所以"资源记忆"（如果这样分的话）实际上也是一个导览：对于代码，存的可能不是精准的代码片段，而是指向它的一份导读，说明这段代码做什么、设计意图是什么。比起完全不了解再去探索，有一个模糊的引导方向显然更快，它可以引导读者精确找到原本需要大量 grep 才能找到的那个点（第 7.1 节）。
- FACT 的混杂（2026-11-16）。调研的八个项目里几乎都有关于事实的记忆类型，而这个概念本身就比较模糊，不可能直接定义什么叫事实：前面的资源记忆其实也是一种事实，一条世界知识也是事实，agent 学来的东西也能叫事实，这也是 FACT 类型会混杂的原因。owner 据此选择按真相所在拆开 FACT（第 7.2 节）。
- 用户一侧的三类（2026-11-16）。拆出的"决定与约定"不够稳定：agent 的决定与用户的决定都会重叠进去，如果它一开始就为"owner、用户、团队的决定与约定"而建，又与现在的 USER_PROFILE 太过接近。早在 agent、skill 流行之前，IDE 中的 LLM 辅助开发就流行一份 rule.md，写着用户为 LLM 设定的项目与全局规范（"项目用 Python 开发""为函数添加 docstring"），今天看来就是记录用户要求与偏好的文件，现在很多项目也仍单独保留一个为用户而存在的文件；"让 agent 记住你，成为你的个性化助手"基本上是很多记忆系统第一个要解决的需求。以三餐推荐 agent 为例，用户说"我不喜欢吃辣"是明确的；agent 一直不推荐辣菜，并不会因此主动总结出"用户不喜欢吃辣"，所以现在的 user profile 仍如当年一样，只有用户亲手定下的才成为真正的记忆。合并成一类又会让它们都进入提示词，而这类用户决定的性质并不一样；决定与规则本身都有对象：始终生效的是用户给 agent 定下的规则，项目上的决定跟着工作方式走，代码项目里有许多工程约定，"全天候 AI 助手"却没有工程项目的概念。讨论在几轮中反复推翻与重建，owner 重新审视问题所在：用户画像与用户定下的规则本身就是两件事，但都是说给工作的人听的，于是都变成了某种约束；事实上它们描述的东西不同，用户画像描述用户自己，用户的决定是对外界的。同样有细微区别的是"我说过一次，你就一直记得"与"相处久了，你逐渐了解我"：前者是用户明确说过的内容，后者是在一次次反馈中归纳得到的记忆。新的类型不能再冠以 USER 的名号，Preference 或者别的词会更贴切。owner 据此定下 USER_PROFILE、Preference 与 Decision 三类（第 7.3 节）。
- 经历（2026-11-16）。REFLECTION 本质上是从工作轨迹中总结出的经验；有意思的是，现在库里标为 REFLECTION 的经验与 FACT 重叠得相当厉害，先前调研中那些"可复用的经验模式"也经常落到 REFLECTION 上。这就是 Hindsight 的 experience 部分，也是很多工作所说的情景记忆，是距离原始交互最近的类型。owner 认为另一位 agent 的分析（按出处识别一次经历、读别人项目得到的模式不算自己的经历）是合理的，并追问它是否只覆盖工作流式的场景。"经历"与"经验"有细微的区别：经验只覆盖"下次遇到类似情况，有什么可借鉴"；更广的情景记忆，即经历，还要覆盖"你记不记得那一次"，本质上重在发生了什么，从中总结出的经验教训是可选的，这也符合 owner 一直以来对记忆的背景要求（第 7.4 节）。
- 全局部分的送达（2026-11-16）。USER_PROFILE 与 Preference 的全局部分怎样送达外部 harness，有一个尴尬的冲突：harness 也可能有自己的记忆；强硬一点就走强制注入，但这依赖插件能接受多大程度的提示词干预。这一块与类型体系关系不大，是 harness 插件的问题；实在不能注入，就引导 agent 在对话开始时获取 USER_PROFILE 与 Preference，用主动阅读绕开注入的麻烦。owner 据此把它归入外部 actor 接入 Idea 的 E-7，先走主动读取（第 7.3 节）。
- 只存在于记忆中的代码（2026-11-16）。资源记忆的第 3 种例外，即记忆本身就是唯一副本的代码，owner 选择不另设类型，按角色并入经历或知识（第 7.5 节）。
- LLM 能否把握类型的边界（2026-11-16）。owner 对边界混淆有很大的担忧，这正是旧的记忆类型体系经常遇到的问题：一个面向 agent 与 LLM 的系统，设计得越复杂越糟，因为 LLM 可能根本不能理解设计意图，总处在漂移的状态，到头来还不如最简单的设计，这也是 Obelisk 提到的一点（[外部参考](../research/memory-core-external-references.md)第 6 节）。这件事多半要让新的类型体系在已有的对话数据上回放一遍看效果。另外，现在的类型有一半是从用户那边分出来的，这部分规则就已经足够复杂，很难保证有效性（第 9 节）。

## 2. 项目最初的设计回顾（2026-02-05）

为重新审视类型体系，owner 要求追溯项目刚起步时的规划文档：提交 `18cca7c`（2026-02-05，"Modify Demo Chatbot UI"）下的 `docs/PROJECT.md`（可用 `git show 18cca7c:docs/PROJECT.md` 查看）。项目文档体系此后经历过大改与多次更迭，其中的信息可能已漂移或丢失。下面是与记忆原子和类型体系相关的部分（2026-11-15 阅读）。

**类型体系：按"agent 应该如何使用"划分，与标签正交**

| 类型 | 当时的说明 | 当时设想的用法 |
|:---|:---|:---|
| CODE_SNIPPET | 代码片段、函数实现、配置文件 | 注入代码解释器，直接复用 |
| FACT | 明确的事实、业务规则、参数定义 | 注入系统提示词，约束 agent 的行为 |
| URL_RESOURCE | 外部文档快照、API 文档 | 带 URL 与清洗后的正文，替代再次联网搜索 |
| REFLECTION | 经验总结、错误反思、任务规划 | 帮 agent 避坑 |
| USER_PROFILE | 用户偏好、习惯、指令别名 | 个性化设置，长期生效 |

类型表中没有 WORK_IN_PROGRESS 与 AGENT_PROFILE。AGENT_PROFILE 是后来加入的；WORK_IN_PROGRESS 则出现在更早的第一版设计中：2025-12-23 首次提交的 `docs/PROJECT.md` 在"闲置超时触发"一节写道，任务未完成时生成一条 `WORK_IN_PROGRESS` 或 `TODO` 记忆，记下停在哪里、还差什么，用户几天后回来时由 Patchouli 主动提示要不要继续。2026-01-01（`543e02ac`）重写这一节时删去了这段，类型表一直只列五种；代码中的枚举值则从首次提交起一直保留。

**记忆原子与演化**：
- 粒度是"语义事务"：一个独立、自包含的知识点（一个完整的函数、一条条款、一段完整的推理链），由 Librarian 剥去闲聊、尝试过程与错误分支，只留下有效结论。
- 冰山三层：索引层只对 Title、Summary、Tags、Type 向量化（至今未变）；负载层是清洗后的 Markdown；原始层有 `context_ref`，按 `session_id` 与 `msg_id` 精确指回原始对话中的具体消息。
- 记忆是随时间演进的实体：索引指向最新，存储保留历史；变更时生成补丁而不是覆盖；负载层附一段注入上下文的历史摘要（例如"项目初始化用 Python 3.8；后来升级到 3.10"），让 agent 知道它怎样变过来；注入时附上"最后更新于几天前、此前有几个旧版本"。
- 按来源分级的信任：用户显式输入 1.0、不可被 agent 覆盖；运行验证成功 0.9、标为 VERIFIED；外部权威资源 0.8；LLM 纯推理 0.6、标为 UNVERIFIED。另有动态验证循环：正反馈提分，负反馈降权、标为 DEPRECATED 或 HALLUCINATION，或生成更正版本。

**生成**：原则是"写前查重"，宁可多花推理 token 也要保证库的纯净。四种决策：新建；TOUCH（只强化）；EVOLVE（同一实体的状态变更，走类似 git 的版本流程）；DISCARD（防污染：草稿置信度低而旧记忆置信度高时丢弃草稿）。外部资料单独处理：存来源 URL、抓取时间与清洗后的正文，标为不可变。

**作用域与生命周期**：私有、领域、全局三级同心圆作用域，私有记忆被验证、被多次引用后自动晋升为全局（个人经验经验证后成为团队的标准作业程序）；三级流水线中短期即 agent 的上下文窗口，中期是向量库，长期是冷存储；生命力按类型赋予固有价值（代码 1.2 > 事实 1.0 > 闲聊 0.1），被动命中、主动引用与用户反馈分别加分；按 `relations` 连带召回强依赖的记忆。

**目标与指标**：核心成功标准之一是"自主的记忆管理"；评估指标中列有"人工干预频率"，即用户手动修正标签或删除错误记忆的频率，越低越好。

**与现在的对照**：

| 当初的设计 | 现在 | 与 v0.8 讨论的关系 |
|:---|:---|:---|
| 类型按"怎样使用"划分，各有不同的送达方式 | 类型只是标签，生成、查重、衰减几乎一视同仁，只有 Profile 靠例外区别（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节） | 语义丢失；重新审视类型体系的起点（第 3 节） |
| 原始层按会话与消息指回原文 | `ArtifactRef` 只指向整个 Artifact（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节） | 丢失；"生成事件带上轮次与事件的信息"的决定（[写入链路](./memory-flow-write-path.md)第 5 节）等于把它找回来 |
| 生成补丁、不覆盖；历史摘要对 agent 可见 | 版本快照保留了，但 Mode C 整篇重写，agent 看不到变迁 | 漂移；对应局部修改、"错了与变了"、沿时间轴回读（[写入链路](./memory-flow-write-path.md)第 2.1 节、[库的形状](./memory-library-shape-and-index.md)第 2.2 节） |
| 来源分级与动态验证循环 | 置信度生成后基本固定，验证状态没有写入方，负反馈没有发出方（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节） | 设计了没有实现；对应"缺少结果信号"（[写入链路](./memory-flow-write-path.md)第 2.4 节） |
| EVOLVE：同一实体的状态变更就地演化 | 2026-10-31 之前相似时用草稿整体覆盖，之后改为先新建再合并 | 漂移；复核（[写入链路](./memory-flow-write-path.md)第 2.1 节）重新走向"先判断关系再决定" |
| DISCARD：低置信的草稿不得覆盖高置信的旧记忆 | 没有 | 丢失；与主动写入的优先权、防止推断冒充事实同类 |
| 私有记忆经验证后晋升为全局 | 只有 PUBLIC 与 PRIVATE，没有晋升 | 未实现 |
| 闲置时生成 WIP 快照，用户回来时主动提示续接（第一版设计） | 只剩类型标签：没有续接，也没有关闭 | 已决定去掉这个类型（第 6.1 节） |
| 短期即上下文窗口（第一方视角） | 短期是话题工作台 | owner 后来的反思（外部者拿不到上下文，[写入链路](./memory-flow-write-path.md)第 2.2 节）解释了偏离 |
| 评估指标包含人工干预频率 | — | 一脉相承：长程标准（[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节）与最初的设想一致 |
| System 2 是在对话间隙阅读、打标、去重、入库的图书管理员 | Patchouli 是一次性调用 | 馆长 agent（[写入链路](./memory-flow-write-path.md)第 3.1 节）是最初设想的回归 |

当初就存在一处内在张力：粒度定义要求剥去尝试过程与错误分支，REFLECTION 却专门记"错误反思"；Obelisk 的作者也批评摘要会先删掉失败路径，而在编程中失败路径正是不再重蹈覆辙的凭据（[外部参考](../research/memory-core-external-references.md)第 6 节）。重新设计类型体系时需要正面回答。已于 2026-11-16 回答：失败路径属于"经历"，写入时必须保住（第 7.4 节）。

## 3. 出发点与现状

owner 于 2026-11-15 确认，类型体系是下一步要重新审视的。项目最初的设计按"agent 应该如何使用"划分类型（第 2 节），这层语义后来丢失，七种类型只剩标签。本文按逻辑顺序排列：现状；类型是做什么的（已决定）；怎样判断一个区分该不该成为类型（候选）；已从类型中移出的三处（已决定）；剩下的类型（资源记忆、FACT 的拆分、用户一侧、经历与只存在于记忆中的代码已决定，最后是类型全貌）；写法与修订上的候选；LLM 能否把握与回放检验（候选）；待讨论。

**现状：类型现在被谁读（以代码为准）**

生成时模型从列表中选一个标签，写法不随类型变化，类型只决定 alias 前缀；类型写进稠密向量的输入文本（`Type: X` 一行，[embedding handler](../../src/hivememory/engines/memory_compiler/handlers/embedding.py)），轻微影响相似度与查重；SEARCH 可以按类型过滤；注入时显示给 agent；生命力按类型给固有价值权重，USER_PROFILE 不归档。也就是说，类型主要是展示与过滤用的标签，外加一个衰减倍数，没有任何地方按类型决定怎样写、怎样修订、怎样维护。

## 4. 类型是做什么的（已决定，owner，2026-11-16）

一条记忆之所以值得赋予一个类型，是因为下一位使用者对它有一种可以预期的用法（owner）。检索与送达合并为"出现位置"后，使用者有四个：读者、出现位置、写入者与维护。

另一位 agent 的例子（2026-11-16）：围绕 AGENT_PROFILE 的决定（第 6.3 节），之后的 agent 可能问三个问题，它们命中几乎相同的关键词，读到答案后却该采取不同的行动：

| 下一位 agent 想知道什么 | 记忆必须保住什么 | 后来发生什么才应该改它 |
|:---|:---|:---|
| 做 v0.8 迁移：Profile 应该放在哪里 | owner 已决定移到独立的 store，以及这个决定的适用范围 | owner 改了设计或收窄了范围；迁移完成本身不推翻决定 |
| 排查当前版本：Profile 实际从哪里读出来 | 哪个版本、哪条真实的读取路径支持这个回答 | 迁移落地、读取路径改变；拍板当天运行事实并没有变 |
| 下次遇到类似对象：它适不适合放进记忆库 | 这次判断的理由，例如由管理入口维护、调用方需要可靠地列举它 | 新案例表明某个条件不足以得出结论，需要给经验加上限定 |

迁移完成的那一天，同一个新事件只该让馆长更新第二个答案：第一个仍然成立，第三个也没有因此得到验证。只靠文本相似度，三段材料都高度相关；知道每段在回答什么问题，馆长才能判断该动哪一处。这个例子不需要预设三条原子或三个枚举值，决定与理由可以写在一起，直到那条经验真的值得拿去解释其他案例。

**决定**（2026-11-16 改写，取代同日较早的"以维护契约为主"）：一条记忆值得赋予类型，是因为下一位使用者对它有可以预期的用法。

1. 类型首先告诉读者能拿它做什么。"按这个决定实施""当作某个版本的事实""借鉴这个案例"会导向不同的行动；即使系统只给出检索摘要，类型也要帮读者判断该点开哪一条，以及读完能据此做多强的判断。这对跨 harness 的 HiveMemory 尤其有价值。
2. 其次告诉馆长怎样才算写完整。要留的是排错经验，删去触发条件与失败尝试，结论即使正确也很难复用；要留的是一段已验证的实现，背景可以压缩，决定行为的关键条件必须原样保住。类型为主动写入与被动提取提供共同的取舍依据，这也是对"一句话直出"最直接的帮助（第 1 节）。
3. 修订时类型只提示该去找哪种依据："当初记错了""后来情况变了""又出现了一个适用条件"。该不该改，由那一段的内容、出处与新证据决定。

理由（分析）：这个定义找回了项目最初"按 agent 应该如何使用"划分类型的本意（第 2 节）。同日较早以维护为主，是把维护压在了类型上：维护的触发点在一条记忆内部的某一段，整条记忆级别的类型给不出"该改哪一段"。维护仍是系统的首要目标（[总纲](./memory-flow-short-to-mid-term.md)第 1.3 节），它的载体是记忆内部每一段回答什么问题、每一段的来源与时间锚，而不是类型。

## 5. 怎样判断一个区分该不该成为类型（候选，不是 owner 决定）

- **判据**（另一半见第 9 节：LLM 能否稳定作出这个区分）：遮住类型名之后，读者最容易用错什么，馆长最容易删错、改错什么？能指出具体错误，这个区分就值得保留；只能说"这样比较好找"，标签或时空图索引可能就够了。
- **轴与 tag 的区别**：VCPToolBox 的 Tag 是自由标注，用来找；它真正"按什么分"靠目录命名，目录名决定进不进索引、怎样送达。作为类型体系的轴应当数量少、取值封闭，每个取值都对应系统中一处不同的处理；某个取值没有任何地方据此做不同的事，它就只是 tag。第 6 节的三项决定用的都是这条标准：WIP 没有消费方，可运行的消费方是执行而不是记忆，AGENT_PROFILE 的消费方是运行时配置。
- **形式**：类型仍是一个枚举，每条记忆取一个值，只承载"用法"这一条轴；其他有消费方的性质作为单独的字段，没有消费方的区分只作标签。旧的七种类型横跨了几条轴，它们的去处：

  | 性质 | 旧类型中的代表 | 去处 |
  |:---|:---|:---|
  | 用法 | FACT、REFLECTION 等 | 类型（第 4 节） |
  | 可运行 | CODE_SNIPPET 作为 RUN 的门槛 | 独立的轴（第 6.2 节，已决定） |
  | 时间上的进度 | WORK_IN_PROGRESS | 不进中期库（第 6.1 节，已决定） |
  | 关于谁 | USER_PROFILE、AGENT_PROFILE | AGENT_PROFILE 已移出（第 6.3 节）；用户一侧按描述的对象分为 USER_PROFILE、Preference 与 Decision（第 7.3 节） |
  | 真相来源与验证 | URL_RESOURCE 隐含的"外部资料" | 真相在哪里、该听谁的决定读者的用法，进入类型（第 7.2 节）；信多少（置信度与验证状态）仍逐条、逐段给出（第 8 节） |
  | 怎样被找到 | — | 标签与锚点；触发它出现的线索种类随类型 |

- **检验问题**：下面五个维度是讨论的出发点，现在用来检验候选类型；每项是否值得成为原子上的固定字段，分别判断。可运行单独拿出来，正说明一种性质可以很重要，同时横跨多种用法。
  1. **怎样送达**：常驻、按需检索、注入执行环境、替代外部查询（最初设计的维度；[库的形状](./memory-library-shape-and-index.md)第 2.1 节的常驻与可列举）。
  2. **在一个月里会发生什么、怎样维护**：会过时、会被推翻、会到期、缓慢变化，还是越用越好（[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节的长程视角；"错了与变了"）。
  3. **真相来自哪里、怎样验证**：用户说的、运行验证过的、外部资料还是推断（最初的来源分级；统一交互记忆 Idea 中"谁断言的"）。
  4. **挂在哪条轴上**：空间（主题）还是时间（经历）；例如 WORK_IN_PROGRESS 更像经历节点上的状态，而不是一条独立的知识（[库的形状](./memory-library-shape-and-index.md)第 2.2 节）。
  5. **靠什么被找到**：锚点（文件路径、报错原文、方案名）还是语义（[外部参考](../research/memory-core-external-references.md)第 6 节中执行记忆与社交情节记忆的区别）。

  用这些问题检验，可以看出哪些是同一种东西的不同标签、哪些需要不同的处理流程，以及缺了哪一类，例如 Nowledge 单独列出的"决定"（[外部参考](../research/memory-core-external-references.md)第 6 节）在 HiveMemory 中没有对应的类型；失败路径与错误反思的去留（第 2 节末尾）也要在这里回答（已由第 7.4 节回答）。

## 6. 已从类型中移出的（已决定，owner，2026-11-15）

### 6.1 WORK_IN_PROGRESS 的去留

现状（以代码为准）：

- 类型只在产生时决定一次：修订与手动编辑都改不了类型，只有合并会由模型重选（[总纲](./memory-flow-short-to-mid-term.md)第 2.1 节）。一条 WIP 即使被修订为"已完成"，标题、摘要与类型仍是进行中的样子。
- 没有关闭：没有到期，也没有"完成"状态；它的固有价值最低（0.5，衰减快 1.5 倍），只会更快淡出检索。
- 没有专门的读取方：只有 SEARCH 能按类型过滤，guide skill 提醒 agent 对 WIP 尤其要核实。第一版设计中与它配套的主动续接从未实现（第 2 节）。
- 已有的记录：2026-10-29 核对对话回流时，生成的 5 条记忆中有 2 条标为 WIP，所述工作在生成之前已经合并（[外部 actor 接入 Idea](./external-actor-registration-and-runtime-access.md)）；一次调研记忆的清理中删去过一条 WIP，理由是这个类型会误导（[生成来源收敛](../archive/ideas/generation-source-convergence.md)）。

只删标签不够：被动提取的拆分规则把"一项工作的当前状态"列为单独成条的一件事，guide skill 也让 agent 在工作中断时写下未完成工作的状态。只删标签，进度快照会改标成 FACT 一类，看起来反而更持久。调研的八个项目都不把进度当作长期知识：要么放在时间轴上（任务期间的状态、账本），要么像 Hindsight 一样把"此刻在做什么"排除在外；dsh 的账本有"未结"、没有"关闭"，未结事项只增不减，与 WIP 是同一个问题。

**决定**：去掉 WORK_IN_PROGRESS 类型，中期库也不再收"当前进度"；"做到哪了"留在交互记录上，即时间轴上，以后由短期记忆（[写入链路](./memory-flow-write-path.md)第 2.2 节）或经历节点上的状态（[库的形状](./memory-library-shape-and-index.md)第 2.2 节）承担。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 被动提取的拆分规则去掉"一项工作的当前状态"；guide skill 改为写下得出的结论、决定与尚未解决的问题本身，不写"做到哪了"。
- 记忆数据只按 schema 2.1 严格解码，删除枚举值之前要先处理库中已有的 WIP 记忆；默认列出来交给 owner 逐条决定改类型还是删除。
- 随之移除：生成、写入与合并提示词中的类型与 alias 示例，MTP 的类型别名与 SEARCH 过滤说明，生命力权重与配置项 `work_in_progress_weight`，alias 前缀，前端的类型列表与创建表单，guide skill 的中英文版本，相关测试；[MealAssistant 产品规格](../applications/MealAssistantProductSpec.md)把这个类型用作近期饮食记录，也要改写。
- 暂不处理：外部 harness 现在只能检索记忆、搜不到交互记录；时间线的读取做出来之前，"上次停在哪"只能靠当时写下的结论与决定间接保留。

### 6.2 CODE_SNIPPET 与可运行

现状：CODE_SNIPPET 同时承担三件事：生成提示词中"代码片段、函数实现、配置文件"这类知识；RUN 唯一接受的类型；最高的固有价值。类型充当了 RUN 的门槛，但生成链写出的 CODE_SNIPPET 基本运行不了（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节）；能否运行实际上是某一份内容的性质，不是类型的。

可运行这条轴里有两层：

| | 环境声明 | 宿主执行 |
|:---|:---|:---|
| 例子 | "这段 SQL 能在某个数据库里运行" | "Alice 可以对这条记忆发 RUN" |
| 是什么 | 内容相对某个环境的性质：语言、运行时、目标系统、入口与参数 | 系统的执行能力：有没有这个环境，能不能把记忆变成可执行物，谁被允许执行 |
| 谁消费 | 任何读者，例如外部 harness 的 agent 在自己的环境里运行 | 只在经 HiveMemory 执行时 |
| 归属 | 知识，是记忆的一部分 | MaaT，即工具宿主 |
| 现状 | 没有表达，只能写在正文里 | 用类型当门槛，把整段正文当 Python 执行，省掉了编译 |

**决定**：

1. 可运行是一条独立的轴，不绑在类型上；只适用于有可执行主体的记忆，不延伸到 AGENT_PROFILE（AGENT_PROFILE 的问题见[写入链路](./memory-flow-write-path.md)第 3.3 节与第 6.3 节）。
2. 这条轴分两层：环境声明属于知识，宿主执行属于 MaaT。
3. 可执行物是从记忆编译出的派生物，与索引同一原则（[库的形状](./memory-library-shape-and-index.md)第 3.2 节）：可以重建，挂在记忆的版本上，版本变了即失效；生成链只写知识，不产出可执行物。
4. v0.8 不新增机制，RUN 的类型检查暂时保留；环境声明要不要在 v0.8 落地，看类型体系中"形态"这条轴怎么定。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 编译已有预留的位置：MemoryCompiler 的编译目标 `RUNNABLE_TOOL`，与提示词注入、向量文本等目标并列。
- AOT 在写入或结算之后编译并试运行，结果可以作为验证状态的写入方，接回第一版设计中"运行验证成功"的回路（本文第 2 节、[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节）；JIT 在 RUN 时编译，简单但没有验证信号。两者的取舍与 HiveMemory 宿主哪些环境，留给 MaaT（[MaaT Idea](./memory-as-tool-skill-plugin-boundary.md)）。
- CODE_SNIPPET 是否作为"代码形态的知识"保留为类型，已由第 7.1 节回答：源头在别处的代码写成导览，只存在于记忆中的代码是资产本身，并入经历或知识（第 7.5 节）；它的其他特点（依附外部真相、靠锚点被找到）并不是代码独有的。

### 6.3 AGENT_PROFILE 移出中期库

现状（以代码为准）：AGENT_PROFILE 是 Alice 的"人偶图纸"：正文是 agent 自己的人设提示词，标题与摘要组成调用方看到的子代理菜单项，`agent_config` 存模型、温度、top_p 与是否启用（[Agent 模型](../../src/hivememory/core/models/agent.py)）。它只能经管理入口创建与编辑，生成、查重、合并、归档、管理页列表都以类型判断绕开它（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节）；运行时发现子代理只能靠检索恰好命中。只有 Alice 的 chat 需要它，外部 harness 的 agent 没有 Profile，CALL 也只在 Alice 的 MTP 中存在。

最初放进记忆库的两点理由，一点没有实现：提示词在演化中修正需要反馈途径，现在没有，执行者也不会主动修改；另一点"能被检索发现"，用固定列表即可替代（第 1 节）。

**决定**：AGENT_PROFILE 移出中期记忆库，单独成一个 store；可用 agent 的列表固定载入提示词，不再靠检索发现。

**新 store 的位置**（owner 标注）：新的 AgentProfileStore 与 ArtifactStore 一样，属于 MemoryLibrary，但不在三层记忆存储（短期、中期、长期）之中，不参与冷热迁移（[MemoryLibrary 与存储层](../patchouli/memory-library.md#1-四种存储角色)第 1 节）。所有权因此不变：Profile 本来就列在 Patchouli 的职责中，MemoryLibrary 也只由 Patchouli runtime 构造并持有。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 列表的内容：在本 Workspace 有准入、Profile 已启用、对调用方可见的 agent，每项是 alias 与职责摘要，沿用现有的子代理菜单编译目标；列表为空时不出现委托的一节。
- 随之删除：MemoryType 中的 AGENT_PROFILE，以及散落在生成、查重、合并、归档、检索、管理页列表与生命力中的类型判断；生命力对它照常计算却不据此做任何处理，一并去掉。
- 保留：可见性（执行者自己的进程按管理语义加载自己的图纸，CALL 按调用方的可见性解析被调用方的图纸）、`enabled`、手动编辑的版本记录。
- 迁移：记忆数据只按 schema 2.1 严格解码，删除枚举值之前，要把库中已有的 Profile 原子迁到新的 store。
- 关于 agent 的知识（擅长什么、做砸过什么）是否作为普通记忆生成，仍是[写入链路](./memory-flow-write-path.md)第 3.3 节的候选，不随这次决定。

## 7. 剩下的类型

### 7.1 资源记忆：导览（已决定，owner，2026-11-16）

CODE_SNIPPET 与 URL_RESOURCE 是同质的：两者都想表达对一个外部资源的记忆，对应最初痛点中的"外源信息的高成本与易逝性"（第 1 节）。但存下的内容本身就是快照，会随时间过时；"外源"也难以定义；存了一份文档的副本，不如直接去读那份文档，现代 harness 可以随时读取，并且保证是最新的。所以资源记忆实际上是一份导览。

**决定**：CODE_SNIPPET 与 URL_RESOURCE 同质，都是对外部资源的记忆；资源记忆的主体是导览：说明它是什么、为什么这样设计、在哪里，把读者引向原本要大量检索才能找到的那个点；真相留在源头。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 导览的形态对应单条原子的冰山三层：索引层用来被找到；正文就是导览，"在哪里"写到路径、符号名、条款号一级，并带版本锚；Artifact 层是指向源头的链接，需要时还有当时的快照。
- "必须原样保住"收窄为锚点与起决定作用的细节（函数名、报错原文、关键的条件），它们既是检索的锚点，也不能被转述；其余部分可以概括。
- "直接去读源头"不成立的三种情况：
  1. 源头会变或会消失，而需要的是当时那一份（网页搜索结果、不跨重启的附件、一次性的命令输出与 API 返回、harness 网页工具按提问处理过的内容）：导览照写，当时那一份作为证据存成带定位符的 Artifact 快照（[写入链路](./memory-flow-write-path.md)第 3.2 节），快照是证据，不是正文。
  2. 读者够不到源头（跨机器共享、chat 形态的 agent 没有文件工具、需要认证的来源）：导览带上足以判断的信息，例如来源在哪台机器、哪个仓库、哪个版本。
  3. 记忆本身就是唯一的副本（对话中写出的一次性脚本、在数据库控制台运行过的查询）：它不是资源记忆，而是资产本身，要原样保住，可运行的轴也落在这里；按它在记忆中的角色并入经历或知识（第 7.5 节）。
- 用判据检验：读者最容易把导览中的转述当作源头本身来引用或执行，类型要提示行动之前先顺着指引去读源头；馆长最容易在合并时丢掉锚点，或者照对话内容而不是照源头去更新导览。
- 维护：导览是否失效可以机械地检查（路径与符号还在不在、网址还能不能打开、版本锚之后源头有没有变），比逐字比对快照便宜得多，可以作为验证状态的写入方；快照只会变旧，它记的本来就是当时那一份。
- 时空图索引是对库内记忆的导览，资源记忆是对库外事物的导览，理念一致、对象不同，不合并。

### 7.2 FACT 按真相所在拆开（已决定，owner，2026-11-16）

调研的八个项目几乎都有"事实"这一类，但这个概念本身就模糊，不可能直接定义什么叫事实：资源记忆也是一种事实，一条世界知识是事实，agent 学来的东西也能叫事实，所以 FACT 会混杂（第 1 节）。

现状与调研（以代码与报告为准）：

- 代码中 FACT 是兜底类型：生成模型给出未知的类型时一律落成 FACT（[生成引擎](../../src/hivememory/engines/generation/engine.py)），WRITE 的生成失败时，兜底草稿也写成 FACT。生成提示词对它的说明是"明确事实、业务规则、参数定义"。
- 八个项目中的"事实"多是粒度或加工层的名字，不是用法：mem0 的自含事实句，EverOS 比 episode 更细的 atomic_fact，Hindsight 的事实层（与信念层、预合成文档相对），SME 由用户原话拆成的事实。最接近拆分的是 Hindsight 按来源分出的 world 与 experience；没有一个项目用"事实"告诉读者该怎样用它。
- "事实"说的是"它是真的"，而库中每一条记忆都声称自己是真的，所以它给不出下一位使用者可以预期的用法；把业务规则、运行事实与参数定义都叫作事实之后，读者得不到共同的用法，修订的触发也最不相同（"Qdrant 现在是 1.19.2"会变，"查重只看索引层"只会被证明错）。

真相所在决定读者该做什么：

| 真相在哪里 | 读者怎样用 | 什么事件会改它 | 例子 |
|:---|:---|:---|:---|
| 一个可以查看的源头：代码、文档、正在运行的系统 | 顺着指引去核对，再行动 | 源头变了 | "Qdrant 现在是 1.19.2""数据根在哪里""查重只看索引层（见 embedding handler）" |
| 有权决定的人：owner、用户、团队的决定与约定 | 照做；有疑问去问有权的人 | 有权的人改了主意 | "Profile 移出中期库""提交说明用中文" |
| 做过的事 | 动手前对照 | 新的经历加强或限定 | 排错经验、教训 |
| 推理与多方证据，没有单一源头 | 当作前提，连同依据一起用 | 被证明是错的 | 调研结论、领域原理、世界知识 |

**决定**：FACT 不作为类型保留，按真相所在拆开：真相在可以查看的源头的并入资源记忆（第 7.1 节，导览带版本锚）；由有权的人决定的成为"决定与约定"；从推理与多方证据得出的留作"知识"；从做过的事中得出的是经验，即原来的 REFLECTION。

候选细节（不是 owner 决定，可在计划评审时调整）：

- "知识"是讨论中的称呼，正式的名字在计划中确定。"决定与约定"随后由第 7.3 节细分为 Preference 与 Decision；"经验"随后改为"经历"（第 7.4 节）。
- 决定要带上适用范围与理由，只有用户能改；迁移完成这类运行事实的变化不影响它（第 4 节的例子）。
- 同一条轴也能解释前面的几项决定（分析）：资源记忆的真相在源头；WIP 的真相在时间线上，所以不进中期库；AGENT_PROFILE 的定义由 owner 决定，所以作为配置移出。真相在用户的那一块，按描述的对象再分为三类，来源作为逐条的标记（第 7.3 节）。
- 信多少与该去哪里核实是两件事：置信度与验证状态仍逐条（逐段）给出；类型回答的是该去哪里核实、该听谁的。
- 一条记忆同时含有决定、运行事实与理由时，类型取它主要回答的问题，其余各段按第 8 节的候选各自带上来源。
- 写入者拿不准时不能再落到 FACT，需要另定默认类型，随具体划分一起决定。

### 7.3 用户一侧：USER_PROFILE、Preference 与 Decision（已决定，owner，2026-11-16）

FACT 拆分后的"决定与约定"不稳定：agent 的决定与用户的决定都会落进去，而如果这一类是为"owner、用户、团队的决定与约定"而建，它又与 USER_PROFILE 太过接近。讨论在几轮中反复合并与拆分，owner 指出问题所在（第 1 节）：用户画像与用户定下的规则本来就是两件事，只是都说给工作的人听，于是都变成了某种约束；它们描述的东西确实不同，画像描述用户自己，用户的决定是对外界的。同样有细微区别的是"我说过一次，你就一直记得"与"相处久了，你逐渐了解我"：前者是用户明确说过的，后者是在一次次反馈中归纳得到的。

反复的原因（分析）：每一轮只沿当时讨论的一条轴提出合并或拆分，并且主要按读者的用法判断；凡是说给工作者听的东西最后都会变成约束，只看读者的用法，差别就被抹平了。区分它们的是另外两个消费方：写入时要保住什么（引述原话还是积累依据），以及什么事件会改它（用户的情况变了、用户改了主意，还是有了新的反馈）。

两组区分：

| | 说过一次，就一直记得 | 相处久了，逐渐了解 |
|:---|:---|:---|
| 描述用户本人 | "我在东八区""我是素食者" | "他习惯晚上工作""他先看结论再看过程" |
| 用户希望事情怎样做：对外界的要求与立场 | "提交说明用中文""不经要求不开 PR" | "他倾向选更简单的方案""他不喜欢流水账式的记录" |
| 对某件事的决定 | "Profile 移出中期库""这次旅行定在京都" | 基本没有：决定本来就要用户说出或认可 |

**决定**：用户一侧按描述的对象分为三类；"说过一次"与"逐渐了解"作为每条记忆的来源标记，不另立类型。

| 类型 | 描述什么 | 出现位置 | 什么时候改 |
|:---|:---|:---|:---|
| USER_PROFILE | 用户本人，即这个概念最初想要的"描述用户的记忆" | 全局 | 用户自己的情况变了 |
| Preference | 用户希望事情怎样做：对外界的要求与立场；不再冠以 USER 的名号 | 全局；拼进每个 agent 的系统提示词 | 用户改了主意 |
| Decision | 对某件事的决定，包括那件事上的约定 | 只在那件事上出现 | 被后来的决定取代；落地写进文档后转为导览，保留历史 |

候选细节（不是 owner 决定，可在计划评审时调整）：

- 来源标记的规则：说过的引述原话，是硬约束，只有用户能改；归纳的列出依据，是软的默认，新的反馈可以修正它，但不能覆盖说过的；用户确认之后转为说过的。来源回答的是"该多信、该多硬"，与第 5 节"信多少逐条给出"一致；它对三类都同样适用，做成类型会让类型数量翻倍。
- 归纳必须依据用户自己的信号（例如几次拒绝了某类推荐），不能依据 agent 自己的行为：agent 从没推荐过辣菜，并不说明用户不吃辣，把自己做过的事记成用户的偏好正是 SME 丢弃 assistant 消息所要切断的自我强化。owner 的判断是，agent 一般没有主动归纳的意愿，真正成为记忆的多半是用户亲手定下的；归纳的一格因此可能很少。
- Decision 原则上只有说过的；agent 自己作出、用户没有确认的选择不进这三类：关于代码的进资源记忆导览中的"设计意图"，其余进"知识"并带上理由；用户认可后转为 Decision。
- Decision 的对象是"正在做的那件事"：在代码仓库里是项目或组件，工程约定就是对象为代码仓库的决定；对全天候助手是一次旅行、家里的三餐安排或一件进行中的事务。这个对象就是时空图索引中空间轴上的主题节点（[库的形状](./memory-library-shape-and-index.md)第 2.2 节），所以不依赖"工程项目"的概念。
- Preference 的全局部分对所有 agent 生效，是要拼进每个 agent 系统提示词的那一段，与单个 agent 自己的身份与职责（AGENT_PROFILE，第 6.3 节）分开：外部 harness 的 agent 在 HiveMemory 这一侧没有 Profile，规则又多半由对话中的纠正与认可产生，要经生成链写入，而 AGENT_PROFILE 是生成链之外的配置。
- 参照：早期 IDE 中的 rule.md 是用户为 LLM 设定的项目与全局规范；Claude Code 自己的记忆分 user（用户是谁）、feedback（怎样工作，包括纠正与确认过的做法，要求写明理由与应用方式）、project（代码与 git 历史推不出的进行中的工作、目标与约束）、reference（指向外部资源）四类，与这里的 USER_PROFILE、Preference、Decision 以及资源记忆大致对应；ChatGPT 的自定义指令曾分"希望了解你什么"与"希望怎样回应"两栏。
- 送达：Claude Code 的记忆是索引常驻（每条一行）、正文按需，常驻与否不按类型决定，与已决定的渐进式披露一致（[总纲](./memory-flow-short-to-mid-term.md)第 1.3 节）。类型体系只标出哪些是全局的；USER_PROFILE 与 Preference 的全局部分怎样到达外部 harness 是插件的问题，owner 于 2026-11-16 决定归入[外部 actor 接入 Idea](./external-actor-registration-and-runtime-access.md) 的 E-7，先走主动读取，仍在 plugin 模式只经 MCP 工具的选项 A 之内。

### 7.4 REFLECTION 改为"经历"（已决定，owner，2026-11-16）

REFLECTION 本质上是从工作轨迹中总结出的经验，是离原始交互最近的类型，对应 Hindsight 的 experience，也就是很多工作所说的情景记忆。库中标为 REFLECTION 的记忆与 FACT 重叠得很厉害，调研中的"可复用模式"也常常落到这个类型上（第 1 节）。

现状（以代码与记录为准）：

- 被动提取的提示词把失败路径删掉了："去噪：忽略寒暄、简单确认、错误尝试过程"，"无价值"一栏写着"报错后的失败尝试（仅保留最终成功版本）"；同一份提示词又说出错的工具结果"可用于提炼错误原因与修复经验"（[生成提示词](../../src/hivememory/i18n/prompts.py)）。失败路径一删，经历只剩一句结论，读起来与 FACT 无异；话题的状态摘要反而要求保留失败尝试。这正是第 2 节末尾那处张力在现在提示词里的样子。
- 调研得来的模式被归进了 REFLECTION，例如归档中的 `ref_lazy_decay_pattern`（`ref_` 是 REFLECTION 的 alias 前缀）：它是读 SME 的源码学到的，亲历的是阅读与核对源码，保存的却是外部系统的设计。

"经历"与"经验"有区别：经验只覆盖"下次遇到类似情况，有什么可借鉴"；更广的情景记忆，即经历，还要覆盖"你记不记得那一次"，重在发生了什么，从中总结出的经验教训是可选的。这也符合 owner 一直以来对记忆的背景要求：对别的类型，背景是必须附带的；对经历，背景就是它的主体。

**决定**：REFLECTION 改为"经历"（情景记忆）。

1. **判据**：下一位 agent 需要回到这一次具体经历，才能判断它对眼前的问题有没有用。
2. **写入时要保住**：情境；发生了什么（做了什么、推荐了什么、说了什么，包括失败的尝试）；结果，包括用户的反应；出处，即轮次与事件锚点；教训可选。
3. **身份按出处**：一条经历对应一次发生。同一段轨迹不论被主动写入与被动结算读到几次，都只算一次经历；两次独立的经历即使文字相似，也各自保留出处。这给主动写入与被动结算的汇合提供了比"摘要是否相似"更可靠的依据，也是[写入链路](./memory-flow-write-path.md)第 5 节"生成事件带上轮次与事件的信息"最直接的用处。
4. **不算经历的**：

   | 内容 | 去处 |
   |:---|:---|
   | 读别人的项目得到的模式 | 指回那个项目的导览，或者作为知识；"这个设计也适合 HiveMemory"是有依据的判断，也归知识；真正用过并看到它解决了什么、在哪里失效，才有自己的经历 |
   | 例行记录（每一餐吃了什么） | 留在时间轴上，即交互记录；值得回头看的那几次才写成经历 |
   | 面向未来的事项（"下周三面试"） | 留在时间轴上，由短期记忆或经历节点上的状态承担（第 6.1 节） |
   | 用户稳定的特征（"做过膝盖手术"） | USER_PROFILE；与之相关的那段经过仍是经历 |

5. **修订**：经历本身只有记错了才更正；当时还不知道、后来才明确的结果可以补上（例如"后来证明那次修复没有生效"）；教训部分可以随新的理解修改。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 归组：相似的经历不并成一条，交给图索引：经历是时间轴上的节点，再由空间轴上的主题节点连起来（[库的形状](./memory-library-shape-and-index.md)第 2.2 节），与已决定的"存储平铺、分层由派生的图索引承担"一致。
- 演化：跨多次经历的教训作为知识演化，并链接回那些经历作为依据，这一步属于维护，不属于写入（[写入链路](./memory-flow-write-path.md)第 4 节）；Preference 中"逐渐了解"的部分，依据就是经历（第 7.3 节），例如连续三次拒绝辣菜推荐是三次经历。
- 用途：工作流中，动手之前对照相似的经历；助手场景中，推荐与反馈的案例（三餐助手规格已把"用户对某次推荐的反馈"映射为 REFLECTION，见 [MealAssistant 产品规格](../applications/MealAssistantProductSpec.md)）、共同经历与对话的连续性、Preference 归纳的依据。
- 时间轴的设计要把助手场景中未结的话头考虑进去，个人助手比工作流更需要"下次见面问一句面试怎么样了"。
- 随之要改：被动提取提示词中删去失败路径的两条规则；名字从 REFLECTION 改掉，正式名字在计划中确定；被错标成 REFLECTION 的调研模式，迁移时改归知识或导览。
- 可能的副作用（分析）：背景与经过留在一条经历里，只把用户说出的 Preference、Decision 与真正独立的知识拆出去，被动结算产出的碎片可能减少（[总纲](./memory-flow-short-to-mid-term.md)第 1.1 节的根因），属于生成链的重新设计，未展开。
- 讨论中被取代的说法：以"真相在做过的事里"作为判据（太宽，读源码、做调研也算做过的事）；"一条经验等于教训加它的案例，相似的案例累积进同一条"（改为一次发生一条，归组交给图索引）；"新证据只加强或限定，不覆盖"（补上记错了更正、结果可以后补）；"教训是必需的"（改为可选）。另一位 agent 的分析补上了收紧的判据、更正旧案例与按出处识别三点。

### 7.5 只存在于记忆中的代码与类型全貌

**只存在于记忆中的代码（已决定，owner，2026-11-16）**：资源记忆的前提是真相在别处，而有一类代码别处没有，记忆中存的就是唯一的一份：对话中写给用户、运行一次后没有提交的脚本，在数据库控制台执行过的查询，修好某个环境问题的一行命令，粘贴进软件设置界面的配置片段，调好的正则。它写不成导览，是资产本身（第 7.1 节的第 3 种情况）。

**决定**：不另设类型，按代码在记忆中的角色并入已有类型：属于某一次经过的（"那次用这条 SQL 修好了数据"），是那条经历里的细节；可以反复使用的做法（"查某类数据用这条 SQL"），归知识。代码部分原样保住，写入与合并时不能改写或转述，只能整段替换；能运行时附上环境声明（第 6.2 节）。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 理由（分析）：按第 5 节的判据，遮住类型名之后最容易出的错是代码被改写或转述，这是写入与合并时的约束，用逐条的"原样保住"标记就能防住；这与资源记忆中"原样保住"收窄为写入约束的做法一致。编程工作中的代码绝大多数在仓库中，写成导览即可，只存在于记忆中的代码相对少。
- "原样保住"标记的形式（例如对正文中的代码块整体标注）在计划中确定。

候选的类型全貌（分析）：真相在用户的 USER_PROFILE、Preference、Decision；真相在可以查看的源头的资源记忆（导览）；真相在推理与多方证据中的知识；在发生过的事中、重在"那一次"的经历（原来的 REFLECTION）。正式的名字在计划中确定。

## 8. 写法与修订上的候选（不是 owner 决定）

- 一份材料含有几种回答时，不拆成几条原子（撤回此前"选不出唯一类型就拆开"的建议，它会加重碎片），而是让每一段可以被单独定位与修订，与[写入链路](./memory-flow-write-path.md)第 2.1 节"修订其中一部分"的复核一致。
- 第 4 节例子中三个答案的修订触发，正好对应三种来源：owner 的决定（规定）、对照代码核实（描述）、新案例累积（证据）。来源这条轴落在段落上，不在整条记忆上。
- 描述运行事实的一段，写入时带上版本锚（截至哪个版本、经哪条路径）：它只会变旧、不会变错，读者据锚点去核对代码，馆长不必追着改。与 WIP 同理：真相在代码仓库中、变化又快的东西，不让馆长追着改。
- 类型是否还写进稠密向量的输入文本，随具体划分一起决定。

## 9. LLM 能否把握与回放检验（候选，不是 owner 决定；回放本身是 owner 的方向）

写入者（Patchouli）与读者（外部 agent）都是 LLM，一个区分如果两边都把握不住，就只剩成本；这也是 Obelisk 一派"加工越多、记忆税越重"的论点（[外部参考](../research/memory-core-external-references.md)第 6 节）。owner 担心规则过于复杂，尤其用户一侧占了六类中的三类（第 1 节）。

- **判据的另一半**：第 5 节的判据问"遮住类型名之后会用错什么"；还要问 LLM 能否稳定地作出这个区分。一个区分要么能由系统机械完成，要么能由写入者回答一个简单的事实问题；做不到的，就要保证判错的代价低。
- **现在设计中的每一处判断**：

  | 判断 | 能否不靠 LLM 的语义判断 |
  |:---|:---|
  | 出处锚点 | 能：系统知道是哪一轮、哪个事件 |
  | 说过的或归纳的 | 大部分能：写入者给出原话，系统核对它是否出现在用户的轮次中 |
  | 原样保住 | 能：规定正文中的代码块一律原样保住 |
  | 版本锚 | 大部分能：harness 的 hook 可以提供当前提交号，写入者只写路径与符号 |
  | 是否经历 | 简单的事实问题：这是某一次发生的事吗 |
  | 是否资源记忆 | 简单，并且能机械核对：主体是否指向一个打得开的源头（路径、网址、符号） |
  | USER_PROFILE、Preference 与 Decision | 不能：要判断说的是用户本人、做事的方式还是某件具体的事 |
  | 知识 | 不能：它是兜底，定义最宽 |

  风险集中在用户一侧的三分与知识。用户一侧中，USER_PROFILE 与 Preference 判错的代价低（来源相同、都是全局的、修订的权限相同）；Preference 与 Decision 判错的代价才要紧（项目决定被当作全局规则常驻，或全局要求被藏进某个项目），而这可以改为一个事实问题："它是否针对某件具体的事"。
- **由系统计算类型**：写入者不从类型名中挑选，而是回答几个事实问题（是某一次发生的事吗；主体是否指向打得开的源头；是用户说过或认可的吗，给出原话；是否针对某件具体的事），由系统算出类型。LLM 只需理解这几句问话，不需要理解整套设计意图。
- **变体 B：用户一侧简化为一类**，与已决定的三类（变体 A）一起回放比较：
  - 用户一侧只留一类"用户说过的"：判据是"用户说过或认可过吗"，写入时必须给出原话，系统核对原话出现在用户的轮次中，只有用户能改；
  - 加一个适用范围字段，取值"全局"或"某件具体的事"：全局的适合常驻，具体的按需出现；Decision 由此成为适用范围的一个取值，USER_PROFILE 与 Preference 不再区分；
  - "逐渐了解"的部分不单独存：用户确认之前，它以经历的形式存在（例如三次拒绝辣菜推荐是三次经历），确认之后写成"用户说过的"；owner 判断 agent 一般不会主动归纳，来源标记因此也可以去掉；
  - 变体 B 共四类：经历、资源记忆、用户说过的、知识，每一类都能靠一个事实问题判断，外加适用范围一个字段。调研中，多数系统的用户一侧只有一类，Claude Code 与 ChatGPT 的自定义指令是两类，现在的三类加来源标记与适用范围是整套规则中最重的部分。
- **回放**（[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节）：用已有的结算材料，按变体 A 与 B 分别重新生成并比较；默认选更简单的 B，只有 A 多出来的区分被稳定地判对、并且确实改变了出现位置或修订方式时，才保留 A。回放检验的是 LLM 能否把握设计，不是用样本推出设计，与"样本统计不作为设计依据"不冲突。
- 知识仍是最大的风险：它可以作为兜底，但不能当默认类型，否则会重演 FACT 作为兜底类型的老路；其中的做法（照着做，环境变了就要改）与原理（用来推理，只会被证明错）要不要分开，也用回放检验。
