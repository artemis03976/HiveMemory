# 记忆核心：类型体系

## 0. 文档性质

本文是 v0.8 记忆核心的子文档，记忆类型的设计：类型是做什么的、怎样判断一个区分该不该成为类型、已从类型中移出的三处，以及剩下的类型怎样划分。v0.8 的目标与各子文档见[总纲](./memory-flow-short-to-mid-term.md)，外部项目与文章的事实见[外部参考](../research/memory-core-external-references.md)。

正文是已定的设计，候选设计标“候选”；已经实现的部分以当前事实文档为准，本文只链接。

现在的状态：已从类型中移出的三处（第 6 节）与资源记忆的合并（第 7.1 节）已经实现；FACT 的拆分、用户一侧、经历与只存在于记忆中的代码（第 7.2 至 7.5 节）方向已定，暂不实施（第 7 节开头）。

## 1. 原则

- **类型声明的是用法**：一条记忆值得赋予类型，是因为下一位使用者对它有可以预期的用法（第 4 节）。这找回了项目最初“按 agent 应该如何使用”划分类型的本意（第 2 节）。
- **只有用法这一条轴是类型**：其他有消费方的性质（可运行、来源、版本锚）作为单独的轴或字段，没有消费方的区分只作标签（第 5 节）。
- **类型不能假定一条记忆什么时候被用到**：每段对话都有它会用到的用户画像，“我喜欢吃番茄”与一场算法讨论无关，“始终用中文回答”却一直生效；类型能假定一条记忆怎么用，不能假定它何时用。“全局与具体”因此不是类型能回答的问题。
- **面向 LLM 的设计越复杂越容易漂移**：写入者与读者都是 LLM，它们可能根本理解不了设计意图，一直处在漂移的状态，到头来还不如最简单的设计（Obelisk 的论点，[外部参考](../research/memory-core-external-references.md)第 6 节）。一个区分要能被 LLM 稳定把握，否则判错的代价必须低（第 9 节）。
- **新的划分先回放检验，再进计划**：回放检验的是 LLM 能否把握设计，不是用样本推出设计，与“样本统计不作为设计依据”不冲突（第 9 节）。

## 2. 项目最初的设计（参照）

项目刚起步时的规划文档是提交 `18cca7c` 下的 `docs/PROJECT.md`（`git show 18cca7c:docs/PROJECT.md`）；此后文档体系经历过大改，其中的信息有的漂移、有的丢失。与记忆原子和类型相关的部分：

- **类型按“agent 应该如何使用”划分，与标签正交**，每种类型有不同的送达方式：

  | 类型 | 当时的说明 | 当时设想的用法 |
  |:---|:---|:---|
  | CODE_SNIPPET | 代码片段、函数实现、配置文件 | 注入代码解释器，直接复用 |
  | FACT | 明确的事实、业务规则、参数定义 | 注入系统提示词，约束 agent 的行为 |
  | URL_RESOURCE | 外部文档快照、API 文档 | 带 URL 与清洗后的正文，替代再次联网搜索 |
  | REFLECTION | 经验总结、错误反思、任务规划 | 帮 agent 避坑 |
  | USER_PROFILE | 用户偏好、习惯、指令别名 | 个性化设置，长期生效 |

  AGENT_PROFILE 是后来加入的。WORK_IN_PROGRESS 出现在更早的第一版设计中（仓库首次提交的 `docs/PROJECT.md`，“闲置超时触发”一节）：任务未完成时生成一条记忆，记下停在哪里、还差什么，用户回来时由 Patchouli 主动提示要不要继续；这段在 `543e02ac` 重写时删去，枚举值一直保留。
- **记忆原子**：粒度是“语义事务”，一个独立、自包含的知识点；冰山三层中索引层只对标题、摘要、标签与类型向量化（至今未变），负载层是清洗后的 Markdown，原始层按 `session_id` 与 `msg_id` 精确指回原始对话中的消息。
- **演化**：索引指向最新、存储保留历史；变更时生成补丁而不是覆盖，负载层附一段注入上下文的历史摘要，让 agent 知道它怎样变过来。
- **信任**：按来源分级（用户显式输入 1.0、不可被 agent 覆盖；运行验证成功 0.9；外部权威资源 0.8；LLM 纯推理 0.6），并有动态验证循环。
- **生成**：写前查重，四种决策：新建；TOUCH；EVOLVE（同一实体的状态变更，走类似 git 的版本流程）；DISCARD（低置信的草稿不得覆盖高置信的旧记忆）。
- **作用域**：私有、领域、全局三级，私有记忆被验证、被多次引用后晋升为全局。
- **目标与指标**：核心成功标准之一是自主的记忆管理，评估指标中有“人工干预频率”。

与现在的对照：

| 当初的设计 | 现在 | 与 v0.8 的关系 |
|:---|:---|:---|
| 类型按“怎样使用”划分，各有不同的送达方式 | 类型只是标签（第 3 节） | 语义丢失；本文的起点 |
| 原始层按会话与消息指回原文 | 记忆的版本记录引用到段（[记忆生成](../patchouli/generation.md#22-段标签与记忆引用)） | 已经找回 |
| 生成补丁、不覆盖；历史摘要对 agent 可见 | 修订以编辑集只改变化的部分（[记忆生成](../patchouli/generation.md#34-编辑集修订已有记忆的共同形式)），版本快照保留了，agent 看不到变迁 | 补丁已经找回；变迁对 agent 可见对应沿时间轴回读（[库的形状](./memory-library-shape-and-index.md)第 2.2 节） |
| 来源分级与动态验证循环 | 置信度生成后基本固定，验证状态没有写入方，负反馈没有发出方 | 设计了没有实现；对应“缺少结果信号”（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节） |
| EVOLVE：同一实体的状态变更就地演化 | 馆长修订读过的记忆；一次性生成先新建，再由合并补进命中的记忆 | 馆长一侧已经找回，一次性生成仍先新建（[写入链路](./memory-flow-write-path.md)第 2.1 节） |
| DISCARD：低置信的草稿不得覆盖高置信的旧记忆 | 没有 | 丢失；与主动写入的优先权、防止推断冒充事实同类 |
| 私有记忆经验证后晋升为全局 | 只有 PUBLIC 与 PRIVATE，没有晋升 | 未实现 |
| 闲置时生成 WIP 快照，用户回来时主动提示续接 | 类型已去掉（第 6.1 节） | “做到哪了”留在时间轴上 |
| 短期即上下文窗口（第一方视角） | 短期是话题工作台 | 外部者拿不到上下文，解释了偏离（[写入链路](./memory-flow-write-path.md)第 2.2 节） |
| 评估指标包含人工干预频率 | — | 与长程标准一致（[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节） |
| System 2 是在对话间隙阅读、打标、去重、入库的图书管理员 | 馆长 agent（[写入链路](./memory-flow-write-path.md)第 3.1 节） | 最初设想的回归 |

当初就有一处内在张力：粒度定义要求剥去尝试过程与错误分支，REFLECTION 却专门记“错误反思”；在编程中失败路径正是不再重蹈覆辙的凭据（[外部参考](../research/memory-core-external-references.md)第 6 节）。这处张力由“经历”回答：失败路径写入时必须保住（第 7.4 节）。

## 3. 现状：类型现在被谁读

以代码为准（[记忆模型](../../src/hivememory/core/models/memory.py)）：生成时模型从 FACT、REFLECTION、USER_PROFILE 与 RESOURCE 中选一个标签，模型给出的类型名不在其中时落为 FACT；WORK_IN_PROGRESS、CODE_SNIPPET、URL_RESOURCE 与 AGENT_PROFILE 只作为历史取值留在枚举中，版本快照仍要按 schema 严格解码。写法不随类型变化，类型只决定 alias 前缀；类型写进稠密向量的输入文本（`Type: X` 一行），轻微影响相似度与查重；检索可以按类型过滤；注入时显示给 agent；生命力按类型给固有价值权重（`configs/config.yaml`：FACT 0.9、RESOURCE 0.8、REFLECTION 0.7、USER_PROFILE 0.6），USER_PROFILE 不归档（[垃圾回收器](../../src/hivememory/engines/lifecycle/garbage_collector.py)）。

也就是说，类型主要是展示与过滤用的标签，外加一个衰减倍数，没有任何地方按类型决定怎样写、怎样修订、怎样维护。

## 4. 类型是做什么的

一条记忆值得赋予类型，是因为下一位使用者对它有可以预期的用法。使用者有四个：读者、出现位置（检索与送达合并为一项）、写入者与维护。

1. **类型首先告诉读者能拿它做什么**。“按这个决定实施”“当作某个版本的事实”“借鉴这个案例”会导向不同的行动；即使系统只给出检索摘要，类型也要帮读者判断该点开哪一条，以及读完能据此做多强的判断。这对跨 harness 的 HiveMemory 尤其有价值。
2. **其次告诉馆长怎样才算写完整**。要留的是排错经验，删去触发条件与失败尝试，结论即使正确也很难复用；要留的是一段已验证的实现，背景可以压缩，决定行为的关键条件必须原样保住。类型为主动写入与被动结算提供共同的取舍依据，这也是对“一句话直出”最直接的帮助。
3. **修订时类型只提示该去找哪种依据**：“当初记错了”“后来情况变了”“又出现了一个适用条件”。该不该改，由那一段的内容、出处与新证据决定。

例子：围绕 AGENT_PROFILE 移出中期库的决定（第 6.3 节），之后的 agent 可能问三个问题，它们命中几乎相同的关键词，读到答案后却该采取不同的行动：

| 下一位 agent 想知道什么 | 记忆必须保住什么 | 后来发生什么才应该改它 |
|:---|:---|:---|
| 做 v0.8 迁移：Profile 应该放在哪里 | owner 已决定移到独立的 store，以及这个决定的适用范围 | owner 改了设计或收窄了范围；迁移完成本身不推翻决定 |
| 排查当前版本：Profile 实际从哪里读出来 | 哪个版本、哪条真实的读取路径支持这个回答 | 迁移落地、读取路径改变；拍板当天运行事实并没有变 |
| 下次遇到类似对象：它适不适合放进记忆库 | 这次判断的理由，例如由管理入口维护、调用方需要可靠地列举它 | 新案例表明某个条件不足以得出结论，需要给经验加上限定 |

迁移完成的那一天，同一个新事件只该让馆长更新第二个答案：第一个仍然成立，第三个也没有因此得到验证。只靠文本相似度，三段材料都高度相关；知道每段在回答什么问题，馆长才能判断该动哪一处。这个例子不需要预设三条原子或三个枚举值，决定与理由可以写在一起，直到那条经验真的值得拿去解释其他案例。

理由：维护仍是系统的首要目标，但维护的触发点在一条记忆内部的某一段，整条记忆级别的类型给不出“该改哪一段”；维护的载体是每一段回答什么问题、每一段的来源与时间锚（第 8 节），而不是类型。

## 5. 怎样判断一个区分该不该成为类型（候选）

- **判据**：遮住类型名之后，读者最容易用错什么，馆长最容易删错、改错什么？能指出具体错误，这个区分就值得保留；只能说“这样比较好找”，标签或时空图索引可能就够了。判据的另一半是 LLM 能否稳定作出这个区分（第 9 节）。
- **轴与标签的区别**：VCPToolBox 的 Tag 是自由标注，用来找；它真正“按什么分”靠目录命名，目录名决定进不进索引、怎样送达。作为类型体系的轴应当数量少、取值封闭，每个取值都对应系统中一处不同的处理；某个取值没有任何地方据此做不同的事，它就只是标签。第 6 节的三项用的都是这条标准：WIP 没有消费方，可运行的消费方是执行而不是记忆，AGENT_PROFILE 的消费方是运行时配置。
- **形式**：类型仍是一个枚举，每条记忆取一个值，只承载用法这一条轴。旧的七种类型横跨了几条轴，它们的去处：

  | 性质 | 旧类型中的代表 | 去处 |
  |:---|:---|:---|
  | 用法 | FACT、REFLECTION 等 | 类型（第 4 节） |
  | 可运行 | CODE_SNIPPET 作为 RUN 的门槛 | 独立的轴（第 6.2 节） |
  | 时间上的进度 | WORK_IN_PROGRESS | 不进中期库（第 6.1 节） |
  | 关于谁 | USER_PROFILE、AGENT_PROFILE | AGENT_PROFILE 已移出（第 6.3 节）；用户一侧按描述的对象分为三类（第 7.3 节） |
  | 真相来源与验证 | URL_RESOURCE 隐含的“外部资料” | 真相在哪里、该听谁的进入类型（第 7.2 节）；信多少（置信度与验证状态）仍逐条、逐段给出（第 8 节） |
  | 怎样被找到 | — | 标签与锚点 |

- **检验问题**：用下面五个维度检验候选类型，看出哪些是同一种东西的不同标签、哪些需要不同的处理流程、缺了哪一类；每项是否值得成为原子上的固定字段，分别判断。
  1. 怎样送达：常驻、按需检索、注入执行环境、替代外部查询（[库的形状](./memory-library-shape-and-index.md)第 2.1 节）。
  2. 在一个月里会发生什么、怎样维护：会过时、会被推翻、会到期、缓慢变化，还是越用越好（[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节）。
  3. 真相来自哪里、怎样验证：用户说的、运行验证过的、外部资料还是推断。
  4. 挂在哪条轴上：空间（主题）还是时间（经历）（[库的形状](./memory-library-shape-and-index.md)第 2.2 节）。
  5. 靠什么被找到：锚点（文件路径、报错原文、方案名）还是语义（执行记忆与社交情节记忆的区别，[外部参考](../research/memory-core-external-references.md)第 6 节）。

## 6. 已从类型中移出的

### 6.1 WORK_IN_PROGRESS

**设计**：去掉 WORK_IN_PROGRESS 类型，中期库也不再收“当前进度”；“做到哪了”留在交互记录上，即时间轴上，以后由短期记忆（[写入链路](./memory-flow-write-path.md)第 2.2 节）或经历节点上的状态（[库的形状](./memory-library-shape-and-index.md)第 2.2 节）承担。

理由：

- 类型只在产生时决定一次，修订、合并与手动编辑都改不了类型；一条 WIP 即使被修订为“已完成”，标题、摘要与类型仍是进行中的样子。
- 没有关闭：没有到期，也没有“完成”状态，成了名义上一直在进行的工作记忆；也没有专门的读取方，第一版设计中与它配套的主动续接从未实现。
- 只删标签不够：拆分规则与 guide skill 都要求写下工作的当前状态，只删标签，进度快照会改标成 FACT 一类，看起来反而更持久。调研的八个项目都不把进度当作长期知识，要么放在时间轴上（任务期间的状态、账本），要么把“此刻在做什么”排除在外；dsh 的账本有“未结”、没有“关闭”，未结事项只增不减，是同一个问题。

**现状**：已实现，WORK_IN_PROGRESS 只作历史取值；被动提取的拆分规则改为“做到哪了”不写成记忆，结论、决定与尚未解决的问题照常成条（[记忆生成](../patchouli/generation.md#3-三种生成模式)第 3 节）。

**差距**：回放中仍有十余条进度快照改写成 FACT 出现，与“只删标签不够”的判断一致；外部 harness 只能检索记忆、搜不到交互记录，时间线的读取做出来之前，“上次停在哪”只能靠当时写下的结论与决定间接保留。

### 6.2 可运行

**设计**：

1. 可运行是一条独立的轴，不绑在类型上；只适用于有可执行主体的记忆，不延伸到 AGENT_PROFILE。AGENT_PROFILE 的“可运行”只是能被 CALL 调用：CALL 是委派给有准入的 agent，RUN 是执行记忆的内容，两者性质不同（[写入链路](./memory-flow-write-path.md)第 3.3 节）。
2. 这条轴分两层：环境声明属于知识，宿主执行属于 MaaT。

   | | 环境声明 | 宿主执行 |
   |:---|:---|:---|
   | 例子 | “这段 SQL 能在某个数据库里运行” | “Alice 可以对这条记忆发 RUN” |
   | 是什么 | 内容相对某个环境的性质：语言、运行时、目标系统、入口与参数 | 系统的执行能力：有没有这个环境，能不能把记忆变成可执行物，谁被允许执行 |
   | 谁消费 | 任何读者，例如外部 harness 的 agent 在自己的环境里运行 | 只在经 HiveMemory 执行时 |
   | 归属 | 知识，是记忆的一部分 | MaaT，即工具宿主 |

3. 可执行物是从记忆编译出的派生物，与索引同一原则（[库的形状](./memory-library-shape-and-index.md)第 3.2 节）：可以重建，挂在记忆的版本上，版本变了即失效；生成链只写知识，不产出可执行物。
4. v0.8 不新增机制，并关闭 RUN 的用户工具路径（解析记忆、把正文放进沙箱执行的那一条）；`sys_*` 系统工具走另一条路径，不受影响；可运行的轴或 MaaT 落地之后再打开。

理由：类型本身是在声明记忆的使用形态。最初的想法其实是给记忆加一个 runnable 修饰符，而不是单列一个类型；CODE_SNIPPET 同时承担了代码知识、RUN 的门槛与最高的固有价值三件事，而生成链写出的 CODE_SNIPPET 是带说明文字的 Markdown，基本运行不了：能否运行是某一份内容的性质，不是类型的。

**现状**：RUN 的用户工具路径已关闭，解析到的记忆一律以不可运行拒绝（[MTP 契约](../contracts/mtp.md#33-run)第 3.3 节）。

候选设计：

- 编译的位置：MemoryCompiler 的编译目标 `RUNNABLE_TOOL`，与提示词注入、向量文本等目标并列。
- AOT 在写入或结算之后编译并试运行，结果可以作为验证状态的写入方，接回第一版设计中“运行验证成功”的回路；JIT 在 RUN 时编译，简单但没有验证信号。两者的取舍与 HiveMemory 宿主哪些环境，留给“记忆作为工具”的重新定型（在孵化中；此前的草案见已归档的 [MaaT Idea](../archive/ideas/memory-as-tool-skill-plugin-boundary.md)）。
- 环境声明要不要在 v0.8 落地，随内容类别的划分一起决定。

### 6.3 AGENT_PROFILE 移出中期库

**设计**：

- AGENT_PROFILE 移出中期记忆库，单独成一个 store（AgentProfileStore）：与 ArtifactStore 一样属于 MemoryLibrary，但不在三层记忆存储之中，不参与冷热迁移；所有权因此不变，仍属于 Patchouli。
- 可用 agent 的列表固定载入提示词，不再靠检索发现。
- Agent Profile 不再作为记忆原子看待，也不再遵循记忆原子的结构（索引层、负载层、版本与生命力都不适用）。用文件存储，一个 Agent Profile 一个文件；手动编辑的历史不保留；直接修改本地文件与经 Agent 页修改等同，运行中的后端热重载。
- Agent 的定义是全局的，它作为工作者进入 Workspace；删除记忆数据不删除 Profile 文件。`agent_id` 保持不变，既是名字也是不可改的标识；换成不透明的 id 涉及整个身份模型，归[身份与访问体系 Idea](./identity-and-access-model.md)。

理由：最初把它放进记忆库是想得到两点好处，一是 agent 能被检索发现，二是 agent 的提示词能在演化中得到修正。后者没有反馈途径，执行者也不会主动修改；前者用固定列表即可替代，主动去找一个 Profile 与列表常驻提示词实际差得不多，用户制定的 Profile 一般也不多。插件模式下，HiveMemory 一侧定义的 agent 穿透不到 harness 中使用。USER_PROFILE 与 AGENT_PROFILE 用词接近，都描述主体，但一个存用户画像、一个存职责与配置，读取者与修订条件差别很大。

**现状**：已实现，见 [MemoryLibrary 与存储层](../patchouli/memory-library.md#15-agent-profile人偶图纸)第 1.5 节与[任务进程](../workspace/task-process.md#6-cpu-分配)第 6 节。

候选设计：关于一个 agent 的知识（擅长什么、做砸过什么）是否作为普通记忆生成，见[写入链路](./memory-flow-write-path.md)第 3.3 节。

## 7. 剩下的类型

**范围**：第 6 节的三处与资源记忆的合并（第 7.1 节）已经实现。第 7.2 至 7.5 节对 FACT、用户一侧、REFLECTION 与只存在于记忆中的代码的重新划分，方向已定，暂不实施：回放与对照组之后（第 9 节），新旧类别在稳定性上没有区别，类别依旧不平衡，类别能否引导记忆按预期用法被使用，两边都测不了，新类型对生命周期信号意味着什么也没有决定。FACT、REFLECTION 与 USER_PROFILE 维持现状；只存在于记忆中的代码暂时落在 FACT。

**现状**：已有的 WIP、CODE_SNIPPET 与 URL_RESOURCE 记忆由 owner 逐条决定改类型还是删除，已经迁移；资源记忆的固有价值权重取 0.8：真相在源头、会过时，不该是最抗衰减的一类。

### 7.1 资源记忆

**设计**：CODE_SNIPPET 与 URL_RESOURCE 同质，都是对外部资源的记忆，合并为资源记忆。它的正文说明是什么、为什么这样设计、在哪里，把读者引向原本要大量检索才能找到的那个点；真相留在源头。资源记忆的主体是指出某样东西在哪里、是什么、为什么值得去看；陈述“怎样运作”的内容即使引用路径也不是资源记忆。资源记忆不叫导览：导览是一种性质，所有记忆最终都可以成为一份导览图，这符合渐进式披露的设计。

理由：两者对应项目最初的痛点“外源信息的高成本与易逝性”，即联网获取的高价值信息只存在于当前上下文，会话结束即丢失。但存下的内容本身就是快照，会随时间过时；“外源”也难以定义，本机的一份文档、一个网址算不算；存了一份文档的副本，不如直接去读那份文档，现代 harness 可以随时读取并保证最新。比起完全不了解再去探索，有一个引导方向显然更快。

**现状**：已实现为 `RESOURCE`（alias 前缀 `res`）（[记忆生成](../patchouli/generation.md#3-三种生成模式)第 3 节）。

候选设计：

- 资源记忆的形态对应单条原子的冰山三层：索引层用来被找到；正文是引向源头的说明，“在哪里”写到路径、符号名、条款号一级，并带版本锚；Artifact 层是指向源头的链接，需要时还有当时的快照。
- “必须原样保住”收窄为锚点与起决定作用的细节（函数名、报错原文、关键的条件），它们既是检索的锚点，也不能被转述；其余部分可以概括。
- “直接去读源头”不成立的三种情况：
  1. 源头会变或会消失，而需要的是当时那一份（网页搜索结果、不跨重启的附件、一次性的命令输出与 API 返回、harness 网页工具按提问处理过的内容）：资源记忆照写，当时那一份作为证据存成带定位符的 Artifact 快照（[写入链路](./memory-flow-write-path.md)第 3.2 节），快照是证据，不是正文。
  2. 读者够不到源头（跨机器共享、chat 形态的 agent 没有文件工具、需要认证的来源）：正文带上足以判断的信息，例如来源在哪台机器、哪个仓库、哪个版本。
  3. 记忆本身就是唯一的副本：它不是资源记忆，而是资产本身（第 7.5 节）。
- 用判据检验：读者最容易把资源记忆中的转述当作源头本身来引用或执行，类型要提示行动之前先顺着指引去读源头；馆长最容易在合并时丢掉锚点，或者照对话内容而不是照源头去更新资源记忆。
- 维护：资源记忆是否失效可以机械地检查（路径与符号还在不在、网址还能不能打开、版本锚之后源头有没有变），比逐字比对快照便宜得多，可以作为验证状态的写入方。
- 时空图索引是对库内记忆的导览，资源记忆是对库外事物的导览，理念一致、对象不同，不合并。

### 7.2 FACT 按真相所在拆开

**设计**：FACT 不作为类型保留，按真相所在拆开：真相在可以查看的源头的并入资源记忆（带版本锚）；由有权的人决定的成为决定与约定，再细分为 Preference 与 Decision（第 7.3 节）；从推理与多方证据得出的留作“知识”；从做过的事中得出的是经历（第 7.4 节）。

真相所在决定读者该做什么：

| 真相在哪里 | 读者怎样用 | 什么事件会改它 | 例子 |
|:---|:---|:---|:---|
| 一个可以查看的源头：代码、文档、正在运行的系统 | 顺着指引去核对，再行动 | 源头变了 | “Qdrant 现在是 1.19.2”“数据根在哪里” |
| 有权决定的人：owner、用户、团队 | 照做；有疑问去问有权的人 | 有权的人改了主意 | “Profile 移出中期库”“提交说明用中文” |
| 做过的事 | 动手前对照 | 新的经历加强或限定 | 排错经验、教训 |
| 推理与多方证据，没有单一源头 | 当作前提，连同依据一起用 | 被证明是错的 | 调研结论、领域原理、世界知识 |

理由：“事实”这个概念本身就模糊，资源记忆也是事实，一条世界知识是事实，agent 学来的东西也能叫事实，所以 FACT 会混杂。它说的是“它是真的”，而库中每一条记忆都声称自己是真的，所以给不出下一位使用者可以预期的用法；把业务规则、运行事实与参数定义都叫作事实之后，修订的触发也最不相同（“Qdrant 现在是 1.19.2”会变，“查重只看索引层”只会被证明错）。调研的八个项目中，“事实”多是粒度或加工层的名字（mem0 的自含事实句、EverOS 的 atomic_fact、Hindsight 的事实层、SME 由用户原话拆成的事实），没有一个项目用“事实”告诉读者该怎样用它。

**现状**：FACT 是兜底类型：模型给出未知的类型时一律落成 FACT，WRITE 的生成失败时兜底草稿也写成 FACT（[生成引擎](../../src/hivememory/engines/generation/engine.py)）。

候选设计：

- “知识”是讨论中的称呼，正式的名字在计划中确定。
- 决定要带上适用范围与理由，只有有权的人能改；迁移完成这类运行事实的变化不影响它（第 4 节的例子）。
- 同一条轴也能解释第 6 节的几项：资源记忆的真相在源头；WIP 的真相在时间线上，所以不进中期库；AGENT_PROFILE 的定义由 owner 决定，所以作为配置移出。
- 信多少与该去哪里核实是两件事：置信度与验证状态仍逐条（逐段）给出；类型回答的是该去哪里核实、该听谁的。
- 一条记忆同时含有决定、运行事实与理由时，类型取它主要回答的问题，其余各段按第 8 节各自带上来源。
- 写入者拿不准时不能再落到 FACT，需要另定默认类型（第 10 节）。

### 7.3 用户一侧：USER_PROFILE、Preference 与 Decision

**设计**：用户一侧按描述的对象分为三类；“说过一次，就一直记得”与“相处久了，逐渐了解”作为每条记忆的来源标记，不另立类型。

| 类型 | 描述什么 | 出现位置 | 什么时候改 |
|:---|:---|:---|:---|
| USER_PROFILE | 用户本人 | 全局 | 用户自己的情况变了 |
| Preference | 用户希望事情怎样做：对外界的要求与立场；不再冠以 USER 的名号 | 全局；拼进每个 agent 的系统提示词 | 用户改了主意 |
| Decision | 对某件事的决定，包括那件事上的约定 | 只在那件事上出现 | 被后来的决定取代；落地写进文档后转为资源记忆，保留历史 |

两组区分的例子：

| | 说过一次，就一直记得 | 相处久了，逐渐了解 |
|:---|:---|:---|
| 描述用户本人 | “我在东八区”“我是素食者” | “他习惯晚上工作”“他先看结论再看过程” |
| 用户希望事情怎样做 | “提交说明用中文”“不经要求不开 PR” | “他倾向选更简单的方案”“他不喜欢流水账式的记录” |
| 对某件事的决定 | “Profile 移出中期库”“这次旅行定在京都” | 基本没有：决定本来就要用户说出或认可 |

理由：用户画像与用户定下的规则本来就是两件事，只是都说给工作的人听，于是都变成了某种约束；画像描述用户自己，用户的决定是对外界的。只按读者的用法判断，凡是说给工作者听的东西最后都会变成约束，差别就被抹平；区分它们的是另外两个消费方：写入时要保住什么（引述原话还是积累依据），以及什么事件会改它。让 agent 记住用户、成为个性化助手，基本上是很多记忆系统第一个要解决的需求，早期 IDE 中的 `rule.md` 就是用户为 LLM 设定的项目与全局规范。

候选设计：

- 来源标记的规则：说过的引述原话，是硬约束，只有用户能改；归纳的列出依据，是软的默认，新的反馈可以修正它，但不能覆盖说过的；用户确认之后转为说过的。它对三类都同样适用，做成类型会让类型数量翻倍。
- 归纳必须依据用户自己的信号（例如几次拒绝了某类推荐），不能依据 agent 自己的行为：agent 从没推荐过辣菜，并不说明用户不吃辣，把自己做过的事记成用户的偏好正是 SME 丢弃 assistant 消息所要切断的自我强化。agent 一般没有主动归纳的意愿，真正成为记忆的多半是用户亲手定下的，归纳的一格因此可能很少。
- Decision 原则上只有说过的；agent 自己作出、用户没有确认的选择不进这三类：关于代码的进资源记忆中的设计意图，其余进知识并带上理由；用户认可后转为 Decision。
- Decision 的对象是“正在做的那件事”：在代码仓库里是项目或组件，工程约定就是对象为代码仓库的决定；对全天候助手是一次旅行、家里的三餐安排或一件进行中的事务。这个对象就是时空图索引中空间轴上的主题节点（[库的形状](./memory-library-shape-and-index.md)第 2.2 节），所以不依赖“工程项目”的概念。
- Preference 的全局部分与单个 agent 自己的身份与职责（第 6.3 节）分开：外部 harness 的 agent 在 HiveMemory 一侧没有 Profile，规则又多半由对话中的纠正与认可产生，要经生成链写入，而 Agent Profile 是生成链之外的配置。
- 参照：Claude Code 自己的记忆分 user、feedback、project、reference 四类，与 USER_PROFILE、Preference、Decision 以及资源记忆大致对应；ChatGPT 的自定义指令分“希望了解你什么”与“希望怎样回应”两栏。

送达：USER_PROFILE 与 Preference 的全局部分怎样到达外部 harness，是插件的问题，不是类型体系的问题，归入[外部 actor 接入 Idea](./external-actor-registration-and-runtime-access.md) 的 E-7：先走主动读取，引导 agent 在对话开始时获取，仍在 plugin 模式只经 MCP 工具的选项之内。类型体系只标出哪些是全局的。

### 7.4 经历

**设计**：REFLECTION 改为“经历”（情景记忆）。

1. **判据**：下一位 agent 需要回到这一次具体经历，才能判断它对眼前的问题有没有用。
2. **写入时要保住**：情境；发生了什么（做了什么、推荐了什么、说了什么，包括失败的尝试）；结果，包括用户的反应；出处，即轮次与事件锚点；教训可选。
3. **身份按出处**：一条经历对应一次发生。同一段轨迹不论被主动写入与被动结算读到几次，都只算一次经历；两次独立的经历即使文字相似，也各自保留出处。这给两条写入路径的汇合提供了比“摘要是否相似”更可靠的依据，也是“生成的记忆指向交互轮次”（[写入链路](./memory-flow-write-path.md)第 5 节）最直接的用处。
4. **不算经历的**：

   | 内容 | 去处 |
   |:---|:---|
   | 读别人的项目得到的模式 | 指回那个项目的资源记忆，或者作为知识；真正用过并看到它解决了什么、在哪里失效，才有自己的经历 |
   | 例行记录（每一餐吃了什么） | 留在时间轴上，即交互记录；值得回头看的那几次才写成经历 |
   | 面向未来的事项（“下周三面试”） | 留在时间轴上，由短期记忆或经历节点上的状态承担（第 6.1 节） |
   | 用户稳定的特征（“做过膝盖手术”） | USER_PROFILE；与之相关的那段经过仍是经历 |

5. **修订**：经历本身只有记错了才更正；当时还不知道、后来才明确的结果可以补上（例如“后来证明那次修复没有生效”）；教训部分可以随新的理解修改。

理由：“经历”与“经验”有区别：经验只覆盖“下次遇到类似情况，有什么可借鉴”；经历还要覆盖“你记不记得那一次”，重在发生了什么，教训是可选的。这符合项目一贯的背景要求：对别的类型，背景是必须附带的；对经历，背景就是它的主体。

**现状**：被动提取的提示词把失败路径删掉了（“去噪：忽略……错误尝试过程”，“报错后的失败尝试（仅保留最终成功版本）”），同一份提示词又说出错的工具结果可以用于提炼错误原因与修复经验（[生成提示词](../../src/hivememory/i18n/prompts.py)）；失败路径一删，经历只剩一句结论，读起来与 FACT 无异。调研得来的模式被归进了 REFLECTION，例如归档中的 `ref_lazy_decay_pattern`：它是读 SME 的源码学到的，保存的却是外部系统的设计。

候选设计：

- 归组：相似的经历不并成一条，交给图索引：经历是时间轴上的节点，再由空间轴上的主题节点连起来（[库的形状](./memory-library-shape-and-index.md)第 2.2 节）。
- 演化：跨多次经历的教训作为知识演化，并链接回那些经历作为依据，这一步属于维护（[写入链路](./memory-flow-write-path.md)第 4 节）；Preference 中“逐渐了解”的部分，依据就是经历，例如连续三次拒绝辣菜推荐是三次经历。
- 用途：工作流中，动手之前对照相似的经历；助手场景中，推荐与反馈的案例（[MealAssistant 产品规格](../applications/MealAssistantProductSpec.md)已把“用户对某次推荐的反馈”映射为 REFLECTION）、共同经历与对话的连续性、Preference 归纳的依据。时间轴的设计要把助手场景中未结的话头考虑进去，个人助手比工作流更需要“下次见面问一句面试怎么样了”。
- 背景与经过留在一条经历里，只把用户说出的 Preference、Decision 与真正独立的知识拆出去，被动结算产出的碎片可能减少。

### 7.5 只存在于记忆中的代码与类型全貌

**设计**：只存在于记忆中的代码不另设类型，按它在记忆中的角色并入已有类型：属于某一次经过的（“那次用这条 SQL 修好了数据”），是那条经历里的细节；可以反复使用的做法（“查某类数据用这条 SQL”），归知识。代码部分原样保住，写入与合并时不能改写或转述，只能整段替换；能运行时附上环境声明（第 6.2 节）。

这类代码别处没有，记忆中存的就是唯一的一份：对话中写给用户、运行一次后没有提交的脚本，在数据库控制台执行过的查询，修好某个环境问题的一行命令，粘贴进软件设置界面的配置片段，调好的正则。它写不成资源记忆，是资产本身。

理由：按第 5 节的判据，遮住类型名之后最容易出的错是代码被改写或转述，这是写入与合并时的约束，用逐条的“原样保住”标记就能防住。编程工作中的代码绝大多数在仓库中，写成资源记忆即可，只存在于记忆中的代码相对少。

候选设计：“原样保住”标记的形式（例如对正文中的代码块整体标注）在计划中确定。

**类型全貌**（候选）：真相在用户的 USER_PROFILE、Preference、Decision；真相在可以查看的源头的资源记忆；真相在推理与多方证据中的知识；在发生过的事中、重在“那一次”的经历。正式的名字在计划中确定。

## 8. 写法与修订（候选）

- 一份材料含有几种回答时，不拆成几条原子（“选不出唯一类型就拆开”会加重碎片），而是让每一段可以被单独定位与修订，与[写入链路](./memory-flow-write-path.md)第 2.1 节“只修改变化的部分”一致。
- 第 4 节例子中三个答案的修订触发，正好对应三种来源：owner 的决定（规定）、对照代码核实（描述）、新案例累积（证据）。来源这条轴落在段落上，不在整条记忆上。
- 描述运行事实的一段，写入时带上版本锚（截至哪个版本、经哪条路径）：它只会变旧、不会变错，读者据锚点去核对代码，馆长不必追着改。与 WIP 同理：真相在代码仓库中、变化又快的东西，不让馆长追着改。
- 类型是否还写进稠密向量的输入文本，随具体划分一起决定。

## 9. LLM 能否把握：判断的代价与回放

写入者与读者都是 LLM，一个区分如果两边都把握不住，就只剩成本，这也是“加工越多、记忆税越重”的论点（[外部参考](../research/memory-core-external-references.md)第 6 节）。用户一侧占了候选全貌六类中的三类，这部分规则最重，最难保证有效。

- **判据的另一半**（候选）：一个区分要么能由系统机械完成，要么能由写入者回答一个简单的事实问题；做不到的，就要保证判错的代价低。

  | 判断 | 能否不靠 LLM 的语义判断 |
  |:---|:---|
  | 出处锚点 | 能：系统知道是哪一轮、哪个事件 |
  | 说过的或归纳的 | 大部分能：写入者给出原话，系统核对它是否出现在用户的轮次中 |
  | 原样保住 | 能：规定正文中的代码块一律原样保住 |
  | 版本锚 | 大部分能：harness 的 hook 可以提供当前提交号，写入者只写路径与符号 |
  | 是否经历 | 简单的事实问题：这是某一次发生的事吗 |
  | 是否资源记忆 | 简单，并且能机械核对：主体是否指向一个打得开的源头 |
  | USER_PROFILE、Preference 与 Decision | 不能：要判断说的是用户本人、做事的方式还是某件具体的事 |
  | 知识 | 不能：它是兜底，定义最宽 |

  风险集中在用户一侧的三分与知识。USER_PROFILE 与 Preference 判错的代价低（来源相同、都是全局的、修订的权限相同）；Preference 与 Decision 判错的代价才要紧：项目决定被当作全局规则常驻，或全局要求被藏进某个项目。
- **变体 B**（候选，与已定的三类即变体 A 对照）：用户一侧只留一类“用户说过的”，写入时必须给出原话，系统核对原话出现在用户的轮次中，只有用户能改；另加一个适用范围字段（全局或某件具体的事），Decision 成为它的一个取值；“逐渐了解”的部分在用户确认之前以经历的形式存在。变体 B 共四类：经历、资源记忆、用户说过的、知识。取舍规则：默认选更简单的变体，只有多出来的区分被稳定地判对、并且确实改变了出现位置或修订方式时，才保留复杂的变体。
- 知识仍是最大的风险：它可以作为兜底，但不能当默认类型，否则会重演 FACT 作为兜底类型的老路；其中的做法（照着做，环境变了就要改）与原理（用来推理，只会被证明错）要不要分开，用回放检验。
- 重新回放时按描述直接选类型，与现在的记忆生成相同（第 9.2 节）。

### 9.1 第一轮回放：由事实问题算出类型

数据是日常实例的 149 次结算、735 条被动记忆（几乎都来自 agent 工作式的会话），以及 12 段 chatbot 式对话（40 条预期标签，由 Claude 起草）；模型 deepseek-chat，温度 0.3。写入者回答几个事实问题（是某一次发生的事吗；主体是否指向打得开的源头；是用户说过或认可的吗；是否针对某件具体的事），由系统算出类型。

| 指标 | 结果 |
|:---|:---|
| 三次分类完全一致 | 变体 A 79%，变体 B 81%，旧的七类 93% |
| 最不稳定的事实问题 | “是否只针对某件具体的事” 79% |
| 摇摆最多的边界 | 资源记忆与不存；知识与资源记忆；知识与经历；变体 A 中 Decision 与 Preference |
| chatbot 对话与预期标签吻合 | 变体 A 89/120，变体 B 94/120 |
| 每次结算的条数 | 新的抽取 4.79，现在的提示词 5.90，当时查重后实际建成 4.14 |

结论：

- 按取舍规则应取变体 B，但 B 的稳定性优势主要来自把 Decision 与 Preference 的翻转挪进了适用范围，而范围决定常驻还是按需出现，不稳定没有消失，只是换了位置。
- “资源记忆与不存”“知识与资源记忆”的摇摆，是两条原则在代码相关的事实上相撞：“环境能重新告诉你的不记”（[外部参考](../research/memory-core-external-references.md)第 4 节）与“真相在可以查看的源头的归资源记忆”（第 7.1、7.2 节）。
- 只换类型，碎片只少了约两成；碎片的成因在结构上，不在类型（[总纲](./memory-flow-short-to-mid-term.md)第 1.1 节）。
- 局限：“已不在库中”几乎没有信号意义，owner 只顺手删过一部分记忆，没有筛过全库；chatbot 样本与预期标签由 Claude 起草，不是标准答案。

### 9.2 对照组：按描述直接选类型

沿用第一轮抽好的正文，类型按每一类“是什么、怎么用”的描述直接选，与现在的记忆生成相同。

| 指标 | 事实问题组 | 直接选 A | 直接选 B | 旧的七类 |
|:---|:---|:---|:---|:---|
| 存不存三次一致 | 92% | 98% | 98% | — |
| 类型三次一致 | A 84%，B 86% | 91% | 92% | 93% |
| 最大的一类 | — | 知识 50% | 知识 56% | FACT 47% |
| chatbot 对话与预期标签吻合 | A 89/120，B 94/120 | 93/120 | 99/120 | — |

结论：

- 第一轮的不稳定主要来自问法：几个事实问题可以同时成立，由优先级定出类型，任何一问翻转，结果就跟着翻转；直接选是一次综合判断。“由系统计算类型”在这批数据上没有优势，不采用。
- 稳定不等于分得对。两种方法的分歧正落在第 10 节第 2、3 项的边界上；直接选只是稳定地把它们归进知识，知识因此装下一半的库，位置与旧的 FACT 相同。
- 类别能否引导记忆按预期用法被使用，两种方法都测不了。这是第 7 节开头“方向已定、暂不实施”的依据。

数据集、提示词与每次运行的结果在开发实例的 `.hivememory/replay/`，含 owner 的对话，不进版本控制；可以复用的导出、提取、分类与一致性统计在[回放脚本](../../scripts/memory_replay.py)。

## 10. 搁置的问题

内容类别的重新划分暂不实施（第 7 节开头），下面几项随之搁置，不阻塞计划：

1. 用户一侧是否取变体 B，以及适用范围怎样判；“全局与具体”不是类型能回答的问题（第 1 节）。
2. 代码相关的事实存不存、怎样存；候选：只存仓库本身给不出的部分（意图、理由、历史与决定），“代码现在是什么样”需要时读源头。
3. 知识与经历的边界：收紧问法（含“这一次”的经过就是经历，脱离具体某次的结论才是知识），或者接受两者之间的摇摆（判错的代价较低）。
4. 写入者拿不准时的默认类型：现在的类型体系空不出一个默认的来。
5. 新类型对生命周期信号意味着什么。
