# 记忆核心：短期到中期的流转

## 0. 文档性质与阅读路径

本文是 v0.8 的设计讨论，为该版本的计划供料，不描述当前行为，也不代表排期。三层存储的当前设计见 [MemoryLibrary 与存储层](../patchouli/memory-library.md)，生成、查重与合并见 [Patchouli 生成](../patchouli/generation.md)，话题与结算见[感知与短期话题](../patchouli/perception.md)。

[统一的交互记忆](./unified-interaction-memory.md)是 owner 认为可能的出发点，但 owner 还没有逐项过，认为它仍有缺陷；其中的轨迹、断言、整理与消费水位设想不在本文复述，它第 5 节的两项与本文第 9 节一并考虑。

结构：第 1 节是 owner 的出发点、说明与已作出的决定，第 1.3 节是决定一览，第 1.4 节是项目最初设计（2026-02-05）的回顾；第 2 节是与讨论有关的现状，以代码为准；第 3 至 7 节按主题展开讨论中的分析与候选设计：写入链路、库的形状与访问、存储与保存形态、Patchouli 的角色、整理写入与生命周期维护的边界；第 8 节是外部调研的参考；第 9 节是问题与决定，并列出 v0.8 的主线、辅线、仍未定论的事项、候选的评判方式与类型体系的出发点；第 10 至 12 节是搁置项、与其他文档的关系和升级为计划的条件。第 3 至 8 节中，除注明为 owner 决定的内容外，都是讨论中的分析或候选设计。2026-11-15 按主题重新整理了章节，内容未删减。

## 1. 出发点、说明与决定（owner）

### 1.1 进入 v0.8（2026-11-13）

- v0.8 重新设计记忆的核心机制：重新定义并设计短期到中期的流转，而不是为现有的症状打补丁。
- 根因在上游，是被动生成的质量：一次结算可以产出多条记忆（[多记忆提取](../archive/ideas/settlement-multi-memory-extraction-and-dedup.md)，v0.7.2）之后，模型倾向于保留每个细节，较长的对话产出三四条甚至更多；碎片多了，系统就依赖查重大量合并，数量一大，查重的失衡就暴露出来。查重的判定信号（[查重 Todo](../todo/generation-dedup-decision-signal.md)）重要，但只是下游策略。
- 原型证明了能保留重要证据并反哺 agent，但质量与自主程度离目标还很远。目标是全自主地维护记忆库；维护固然重要，但写入从一开始就决定了维护的难度（2026-11-14）。
- 三层的含义不变：短期是话题工作台，中期是 Qdrant 中可检索的记忆，长期是归档记忆的冷藏库。长期层在项目开始时就已定下，计划改用 sqlite 一类数据库存储，有自己的维护规则，不在这次重新设计的范围内。
- owner 对讨论中第一份提议的转述：记忆素材的来源与最终的生成队列之间，缺少一个归一化的中间表示（第 3.1 节）。

### 1.2 讨论中的说明与纠正（2026-11-13～15，按主题）

**方法与诊断的补充**

- 查重的相似度只看索引层，正文不参与，正文的长短影响不了相似度（第 2.2 节）。
- 被删除的被动记忆，大多出于 owner 的偏好：记忆不该像流水账，不为 PR 单独写工作记录。这与两种交互形式有关：chatbot 式的交互天然像流水账，倾向于记住"用户说的"；agent 工作式的交互要记的是工作要点。真实情况比这复杂得多，不能只凭这几点概括设计。
- 样本分析对重新设计基本没有作用，设计要从底层重新开始。样本以 owner 自己的 HiveMemory 开发会话为主，从中得到的特征（例如 agent 工作式的会话里用户消息多是短指令）只对 owner 现在的使用成立，不能推广。

**记忆观**

- 两条写入路径都保留。被动提取与 agent 的主动写入是大多数 agent 记忆项目会采用的两种做法（第 8 节）；把 chatbot 式与 agent 工作式同时纳入考虑时，两侧的信息同样重要。从人的角度看，本来就有"潜意识记忆"与"主动记忆"两种行为，因此这个方向是合理的，也是必须解决的。
- 调研过的项目都没有覆盖一点：通过强化学习让 agent 学会使用记忆工具。如果 agent 从根本行为上就愿意一直使用记忆工具，而不是依赖外部的 skill，留给被动提取的信息就不多了；但对闭源模型，这条路不可行（第 10 节）。
- 记忆即知识（2026-11-14）。项目一贯的理念是：持久化、可寻址、可追溯、可演化的记忆资产，不只是一段可读文本的"回忆"，而是 agent 所有知识的外部积累。流行的 skill 文档、犯错经验的反思、知识库，对无状态、无感知的 LLM 来说都是记忆，正如人从出生起的所有经历既是记忆，也是先验知识。关键在于把这些材料统一内化，成为真正属于 agent 的知识，这是记忆生成链路要做到的事（第 3.4 节）。
- 价值由写入者判定（2026-11-15）。记忆价值体系原本通过分析用户输入来标记对话价值，后来被 owner 停用：不只是误判率太高，更因为只有终端的 Patchouli 才有资格决定"看到了什么但不写成记忆"。如果 Patchouli 完全明白什么该写、什么不用写，记忆价值在这一刻就已经判定，不再需要外部评判来决定材料的去向。关键在于她需要知道发生过什么、写过什么、更新过什么；作为记忆库唯一的管理者，她有权知道全部历史记忆记录，尽管现在所有写入路径都已经经过她（第 2.1、6.1 节）。
- 写入与维护分属（2026-11-15）。Anthropic 文章中的 dreaming 更偏向记忆的生命周期维护，原则上与记忆的整理和写入分属两件事；只是在强调查重与复核的当下，两者确实有重叠。未来的"记忆的分裂与合并""记忆冲突检测"等，都属于落库之后怎样保证记忆的演化质量（第 7 节；维护一侧的内容记在[生命力分数长期演进](./VitalityScoringLongTermEvolutionIdeas.md)方向 6）。
- 知识不等于工具（2026-11-14）。如果记忆即知识，那么插件就是工具，是 agent 与外界交互必不可少的一环：正如人空有理论知识也不能行动，知道自行车哪里坏了、怎么修，也得有一把扳手来修。所以 [MaaT Idea](./memory-as-tool-skill-plugin-boundary.md) 的对象需要重新考虑，核心命题是知识与工具不能划等号；"记忆作为工具"要如何体现、目标是什么，或许要从头考虑（第 2.4 节、第 6.3 节）。
- 记忆的价值在长时间段内（2026-11-15）。agent memory 的重点一直在可演化与动态维护，即一部分人所说的 runtime adaptation。如果只是一轮召回，那就是 RAG，与老技术没有区别；agent memory 应当是一个极长时间段内的行为设计：让一个系统连续跑一周、甚至一个月，它积累的内容能否有效地用在未来的运行中，以及需要多少人类的介入，才是这个领域真正的价值（第 9.5 节）。

**库的形状、访问与保存**

- 把原始轮次按内容归入容器，在论文中很常见（如 Nemori）。话题跨会话按内容归并是最初就有意的设计，已经实现了"相似的对话无论出自哪个会话都合在一起"；剩下的问题是归并由 LLM 判定，不能保证每次合理（[跨会话话题 Todo](../todo/cross-conversation-topic-placement.md)）。所以"话题能否跨外部会话"不是开放问题。
- 成熟的记忆系统都会分层，比如用文件夹组织目录结构；HiveMemory 的记忆一旦进入中期库就平铺了，完全由检索系统"扫盘"。owner 在反思：是否中期库的形状限制了写入链路，间接限制了生成的材料与形式（第 4.1 节、第 9.1 节）。
- 不分层的问题不只体现在写入上。user profile 一般保存长期的用户偏好，但任何检索都可能遗漏某一条重要的信息；大部分记忆框架因此把用户偏好单独存为一层，常驻在系统提示词里，避免要用的时候找不到。agent profile 的问题没有那么严重：它本来就是想借助记忆库的检索能力，让 agent 在运行时检索到它、作为子代理的材料，并且作为记忆原子享受维护的好处；但现在的系统行为对此并不友好，没有发挥出 agent profile 应有的独立性质（第 2.4 节、第 4.1 节）。
- 记忆的保存形态（2026-11-14）。包括调研的八个项目在内，很少有项目像 HiveMemory 这样用自定义的数据格式保存记忆，主流做法已经接受 md 文档作为记忆的文本载体（例如 Claude Code 的原生记忆，第 8.1 节）。大部分人称之为 LLM wiki，但它与以前的知识库没有太大差别：技术仍是 RAG 与索引那一套，"数据库"与渐进式披露的核心理念没有变。它的好处是对人和 agent 都友好：不需要定义新的编辑方法，普通的文件编辑就够了，能充分利用已有的通用文档格式。反观记忆原子：索引层类似 frontmatter，正文就是 md 的正文，修改起来却不像编辑文档那么简单；唯一的优势是 Artifact 层，即与外部的联系，但这在 md 中用链接也能简单实现。原子格式还把生成链路完全锁死，只能通过特定方法修改，这不是坏事，但确实是局限。只要仍在文本的范围内，新定义一个数据格式不可能比成熟的文档更有竞争力；要让记忆原子超越普通的 md 文本记忆，就必须让它做到文本载体做不到的事（第 2.3 节、第 5.1 节、第 9.3 节）。
- 动态检索是有意的选择（2026-11-14）。"决定每条知识以哪一档进入上下文"实际上就是现在的预检索，也是 RAG 检索技术的本源。owner 一年前了解 skill 体系时就想到了这个问题：skill 的描述常驻上下文，但 skill 是有限的、从外部安装进来的，而 owner 构想的记忆是动态的；四百多条记忆如果都固定载入，上下文会爆，也不符合相关性。所以选择了动态检索加载记忆，并且仍保持与 skill 相同的、从索引到正文的渐进式披露（第 3.4 节）。
- 高层索引（2026-11-15）。记忆库的分层一定会决定记忆的工作形态，写入侧与维护侧都是，Perplexity 的工程实践已经证明了这一点。分层的最终目的，是引导任何访问记忆库的人或 agent 经过渐进的了解，从一个模糊的想法逐步追溯到并回忆起特定的信息。单条记忆原子已经做成类似的"冰山模型"：Index 层是笼统信息，Payload 层是核心内容，Artifact 层链接到真正的资料源，形成逐级递进的获取流程。但这只对单个原子成立：从 agent 主动或根据用户的问题出发找到对应的原子，中间的渐进引导是断的，完全依赖检索系统的能力，原因就是记忆库是平铺的。即便关系型数据库，数据也不会平铺摆放，而是可以从某些表的字段派生关联表，形成嵌套，也就是渐进的获取过程；记忆库与现代数据库同源，数据库的设计哲学同样适用。因此中期记忆、甚至长期记忆都需要一层 memory index，即按主题综合、带引用的高层索引层：可以是人工制定或非人工层次聚类的树形索引，更理想的是图索引，因为记忆之间的边界不一定清晰，一条记忆不必只归属于一棵子树。这与 owner 构想过的图数据库方向、以及一直没有启用的关系层相连：有了图的关系结构，就能用经典的图搜索算法从某一节点出发，以启发式的方法完成引导。这里的图不再是直接把记忆原子连成图，而是更高层次的东西（第 4.2 节）。
- 图是指导检索的索引表（2026-11-15）。owner 想要的已经不是图数据库：图会变成一份索引表，指导检索如何进行，即在模糊的先验想法下，根据图的指引一步步认识问题，有一点贝叶斯网络的意思。更激进的设想是"嵌套图"：高层索引的一个节点对应一张展开的子图，agent 在"搜索、展开"的循环中逐步深入，达成渐进式访问；但这是极度复杂的组织，至少 v0.8 没有必要实现。高层节点分为主题与经历两类，可以用经典的"时间与空间"来解释：主题轴是记忆的空间内容，经历轴是记忆的时间序列，为图索引同时赋予时空两个角度，涵盖了不同的性质（第 4.2 节）。
- 图索引是补偿性引导，存储仍然平铺（2026-11-15）。时空图索引实际上是一种对读者的补偿引导机制，中期记忆库的底层结构并没有变化，仍然平铺，第 9.1 节"中期库的形状"与这个问题已经对不上；按馆长 Agent 的构想，一个完全派生、可以重建的索引也可以直接参与写入判断。owner 的理解是：这相当于用自己设计的索引机制替换掉了 Qdrant 原生的向量索引，从而让记忆库的形状不再影响写入与访问方式；由此要问 Qdrant 作为向量数据库还剩什么意义，以及时空索引图在当前设计中的定位；这只解决了 v0.8 的一部分问题，写入链路的材料以及被动提取与主动写入之间的冲突还没有完全的定论。owner 据此决定关闭第 9.1 节（第 4.3 节）。
- 关系层的去向（2026-11-15）。记忆原子上的关系层是原本规划中图数据库的一部分预设；在时空高层图索引的规划下，需要重新看待这个挂在原子上的关系层（第 2.2、4.4 节）。
- 维护的关系索引比原始文本更有意义（2026-11-15）。原始文本的噪声问题摆在那里：Obelisk 的作者自己也承认，单靠全文检索命中范围有限、单次检索结果无法跨会话复用、第一轮命中会带偏后续检索。把一堆会话记录当作知识库、用常规的 RAG 手段去检索，极其 token 低效，它们也不是高度精炼的知识。一个精心维护的关系索引远比一段段原始文本有意义；该作者后来也要在检索层之上建 view，正好对应时空图索引（第 4.3、8.6 节）。

**写入链路**

- 按时间线消费交互的来源（2026-11-14）。[统一的交互记忆](./unified-interaction-memory.md)中按时间线消费交互的设想（owner 称之为绝对交互时间线），多少来自 VCPToolBox 的 OneRing：它宣称是"终极分布式上下文统一方案"，能为 Agent 维护唯一化的上下文。真实机制与两者的联系见第 3.3、8.3 节。
- 被动结算的定位（2026-11-15）。被动话题的结算问题已经比较清楚：作为话题的终态收尾者，完全可以让它知道这个话题以来发生过哪些记忆事件、又需要补充哪些关键记忆，以全局视角重新审视这次话题的信息含量；让生成事件带有轮次事件的信息，至少保证了溯源的清晰度。所以有一部分候选设计已经成立（第 9.2 节）。主动写入写下之后即生效，在任何修订到来之前，其内容本身仍然有效且合理，不能因为话题还没有结算就假设它已经是"旧结论"。
- 主动写入缺少背景（2026-11-15）。被动结算相对前台的主动写入是一个很晚的时间点，看得全但是很慢。八个调研项目中有五六个是"一句话直出"：agent 按 skill 调研，完成调研报告并写入记忆库；此时前面没有话题轮次，只有 agent 的指令能用作生成材料。在最初的几个调研工作流验证中，agent 喜欢略去背景、直接写结论，生成侧又没有东西可补，写出来的记忆是"空中楼阁"，owner 因此在 skill 中补充要求：主动写入要完整说明问题背景与解决方案（第 2.1、3.2 节）。
- 背景是短期记忆的缺陷（2026-11-15）。"背景"问题仍是短期记忆的缺陷，也是 owner 提出流式接收交互事件的原因之一。这个方案的诡异之处在于相当于照抄一遍 agent 的上下文：大部分已有工作把短期记忆描述为"上下文"或"working memory"，即当前正在做什么，这是第一方视角，好比 Alice 能直接控制上下文的注入；HiveMemory 一手拿不到上下文，就算拿到也不能直接介入管理，于是只能复写一份副本，而且对复制的时机有要求。本质上，背景的缺失仍是时序问题，也因为拥有完整背景的前台 agent 并不是第一写入人。已有调研基本没人关注这一点，最接近的主题反而是直接影响上下文的"对话压缩"。由此要问：作为一个"外人"，系统对 agent 短期记忆的支持应当是什么样的，即 agent 短期记忆的定义（第 3.2 节）。
- 时间线仍然存在，但不必流式（2026-11-15）。绝对时间线这件事仍然存在，毕竟所有事件在交互中都有到来的先后；只是没有必要再非要做成"流式"。VCPToolBox 的 OneRing 对此有什么启发（第 3.3 节）。
- 消费水位退场（2026-11-15）。时间线上"每个事件只消费一次"的水位语义确实该退场了（第 3.3 节）。
- 完整性的上限在 harness（2026-11-15）。Obelisk 声称"统一格式有损"，但这本身是 harness 的问题，不是提炼记忆带来的：作为第三方拿不到真正完整的会话记录，这一点已在项目中被证实。所以即便保存了原始会话记录，这条路从根源上就是断的，做不做提炼都不会改变；owner 因此一直在尝试自己开发 harness，让会话记录彻底透明、可见、可操控（第 3.2 节）。

**Patchouli 的角色**

- Patchouli 作为馆长（2026-11-15）。owner 构想过让 Patchouli 晋升为面向 MemoryLibrary 的自主 Agent，打破现在只有一次 LLM 调用的一次性流程：短期、中期、长期库她都能自由探索，这是"图书馆馆长"天然的权力。外部 agent 主动写入但不感知记忆库的本质，Patchouli 拥有最高权限，根据手上的材料决定怎样放进记忆库。本质上是一个专职 agent，但同时拿到了 agent 的长处与对外的隔离，与第 3.1 节的复核思路不冲突（第 6.1 节）。
- agent 循环的现状（2026-11-15）。`agent_runtime` 一直"独属于 Alice"：工具调用只能用 MTP，不能并发调用工具，仍按 stop sequence 以 ReAct 方式停止生成，工具执行环境 KoakumaRuntime 也还是原型。owner 很早就考虑过 Patchouli 是否也需要共用它，一直想把它做得通用；要让 Patchouli 以它为底层，需要先好好优化。
- Patchouli 的能力范围与外部来源（2026-11-15）。如果只是浏览记忆库并有限地写入，MTP 也够用；owner 也设想过赋予她更高级别的"查证"能力，例如访问网络追查资料、执行一定量的沙盒工具。原因之一是记忆原子"保存外部文档来源"的功能一直因为没有来源而无法启动：用户上传的文件、agent 在对话中拉取的网页都是易逝的，记忆应当保留对来源的引用；现在的路径里没有谁能整理出这一点，作为终端的 Patchouli 是否应当补上（第 2.5、6.2 节）。

**类型体系**

- WORK_IN_PROGRESS 的去留（2026-11-15）。重新审视类型体系，第一个要决定的是还要不要保留 WIP。它确实能表示哪项工作没有做完，但从 owner 的删除记录看，它一直得不到更新；即便更新了，现在的机制也不允许它变成其他类型，于是成了名义上一直在进行的工作记忆。owner 记得最初的设计中也没有这个类型；核对后，2025-12-23 的第一版设计中有它，后来从文档中删去（第 1.4 节）。owner 据此选择去掉这个类型，并且中期库不再收"当前进度"（第 9.6 节）。
- CODE_SNIPPET 与可运行（2026-11-15）。这个类型一开始是为代码复用而存在的，后来的 MTP RUN 又把它推向 MaaT 的一个实现点，允许它作为工具执行。owner 最初的想法其实是给记忆加一个 runnable 修饰符，声明它可以运行，而不是单独列一个类型；这已经在一定程度上说明了问题：类型本身是在声明记忆的使用形态或使用方法。在 MaaT 需要重新审视的当下，这个类型就比较尴尬：不是要删除它，而是它的地位不再明确。按不同轴的思路，runnable 本身就是一条轴，不应该绑在一个类型上，例如"这段 SQL 能在某个数据库里运行"与"当前 Alice 可以对这条记忆发 RUN"是两件事。但这不延伸到 AGENT_PROFILE，两者性质不同：runnable 的理念几乎只服务于"可运行的记忆"，成熟的形态应当是对这条记忆做某种 AOT 或 JIT 编译，形成像可执行代码一样的东西在沙箱中运行；AGENT_PROFILE 的目的不是这样，它的"可运行"只体现在能被 CALL 调用，与此有很大区别（第 9.6 节）。
- AGENT_PROFILE 的取舍（2026-11-15）。USER_PROFILE 与 AGENT_PROFILE 都描述主体，一般的 agent 系统也只有这两种主体；微妙之处在于前者存的是用户偏好画像，后者存的是职责事实，实际的读取者与修订条件差别很大，用词接近，却很难定义它们的类型体系。讨论从 AGENT_PROFILE 开始：最初把它放进记忆库，是想得到两点好处，一是 agent 能被检索发现，二是 agent 的提示词能在演化中得到修正。后者在没有明确反馈途径的情况下，执行者不会主动去修改，只剩检索发现一点；而把 agent profile 的列表固定在提示词中，与 agent 主动去找一个 profile，实际差得并不多，以前的方案确实太过理想。用户制定的 agent profile 一般不会很多，载进提示词不会有大问题。另外，在现在的插件模式下，HiveMemory 这一侧定义的 agent 穿透不到 harness 中使用，所以把 agent profile 移出中期记忆库、单独列一个 store，分得更清楚（第 9.6 节）。
- 类型体系要提供什么（2026-11-16）。解决了 WIP、可运行与 AGENT_PROFILE 之后，记忆类型实际上回到了最初的设想，此时重新考虑类型体系会更清楚。按几条预定的性质轴为记忆原子打标签，相当于多个正交维度的性质叠加，有一点像 VCPToolBox 用 Tag 来构建"按什么分"；但要设计记忆类型，仍然必须先决定希望从类型体系里得到什么。owner 选择以维护契约为主（第 9.6 节）。随后补充：以维护契约为主，不等于类型只服务于记忆维护，也不是只要满足一个消费方就行。检索与送达可以合并，两者都相当于决定记忆出现的位置，于是消费方是四个。一条记忆之所以值得赋予一个类型标签，是因为下一位使用者对它有一种可以预期的用法。同日看过另一位 agent 的分析（同一决定之下三个命中相同关键词、却该导向不同行动的问题）之后，owner 改写了决定：类型首先告诉读者能拿它做什么，其次告诉馆长怎样才算写完整，修订时只作提示（第 9.6 节）。
- 资源记忆是导览（2026-11-16）。比较清晰的一点是 CODE_SNIPPET 与 URL_RESOURCE 的同质性：两者都试图表达对一个外部资源的记忆，对应 owner 最初痛点中的"外源信息的高成本与易逝性"，原文是："通过 Web Search 或 Deep Research 获取的高价值信息（如第三方库文档、法律条款、API 规范）仅存在于当前的 Context 中。一旦会话结束，这些高保真信息即丢失。下次任务需再次联网搜索，既增加了时间成本（Latency），又引入了因搜索结果变动而导致的不一致风险。"这其实并不太准确：存下的资源内容本身就是快照，会随着时间过时；怎样定义"外源信息"也是问题，存在当前电脑环境中的一份文档算不算，一个网址算不算；如果存了一份文档的内容副本，为什么不直接去读这份文档，现代的 agent harness 完全有能力随时随地读取，而且能保证最新。所以"资源记忆"（如果这样分的话）实际上也是一个导览：对于代码，存的可能不是精准的代码片段，而是指向它的一份导读，说明这段代码做什么、设计意图是什么。比起完全不了解再去探索，有一个模糊的引导方向显然更快，它可以引导读者精确找到原本需要大量 grep 才能找到的那个点（第 9.6 节）。
- FACT 的混杂（2026-11-16）。调研的八个项目里几乎都有关于事实的记忆类型，而这个概念本身就比较模糊，不可能直接定义什么叫事实：前面的资源记忆其实也是一种事实，一条世界知识也是事实，agent 学来的东西也能叫事实，这也是 FACT 类型会混杂的原因。owner 据此选择按真相所在拆开 FACT（第 9.6 节）。
- 用户一侧的三类（2026-11-16）。拆出的"决定与约定"不够稳定：agent 的决定与用户的决定都会重叠进去，如果它一开始就为"owner、用户、团队的决定与约定"而建，又与现在的 USER_PROFILE 太过接近。早在 agent、skill 流行之前，IDE 中的 LLM 辅助开发就流行一份 rule.md，写着用户为 LLM 设定的项目与全局规范（"项目用 Python 开发""为函数添加 docstring"），今天看来就是记录用户要求与偏好的文件，现在很多项目也仍单独保留一个为用户而存在的文件；"让 agent 记住你，成为你的个性化助手"基本上是很多记忆系统第一个要解决的需求。以三餐推荐 agent 为例，用户说"我不喜欢吃辣"是明确的；agent 一直不推荐辣菜，并不会因此主动总结出"用户不喜欢吃辣"，所以现在的 user profile 仍如当年一样，只有用户亲手定下的才成为真正的记忆。合并成一类又会让它们都进入提示词，而这类用户决定的性质并不一样；决定与规则本身都有对象：始终生效的是用户给 agent 定下的规则，项目上的决定跟着工作方式走，代码项目里有许多工程约定，"全天候 AI 助手"却没有工程项目的概念。讨论在几轮中反复推翻与重建，owner 重新审视问题所在：用户画像与用户定下的规则本身就是两件事，但都是说给工作的人听的，于是都变成了某种约束；事实上它们描述的东西不同，用户画像描述用户自己，用户的决定是对外界的。同样有细微区别的是"我说过一次，你就一直记得"与"相处久了，你逐渐了解我"：前者是用户明确说过的内容，后者是在一次次反馈中归纳得到的记忆。新的类型不能再冠以 USER 的名号，Preference 或者别的词会更贴切。owner 据此定下 USER_PROFILE、Preference 与 Decision 三类（第 9.6 节）。
- 经历（2026-11-16）。REFLECTION 本质上是从工作轨迹中总结出的经验；有意思的是，现在库里标为 REFLECTION 的经验与 FACT 重叠得相当厉害，先前调研中那些"可复用的经验模式"也经常落到 REFLECTION 上。这就是 Hindsight 的 experience 部分，也是很多工作所说的情景记忆，是距离原始交互最近的类型。owner 认为另一位 agent 的分析（按出处识别一次经历、读别人项目得到的模式不算自己的经历）是合理的，并追问它是否只覆盖工作流式的场景。"经历"与"经验"有细微的区别：经验只覆盖"下次遇到类似情况，有什么可借鉴"；更广的情景记忆，即经历，还要覆盖"你记不记得那一次"，本质上重在发生了什么，从中总结出的经验教训是可选的，这也符合 owner 一直以来对记忆的背景要求（第 9.6 节）。

### 1.4 项目最初的设计回顾（2026-02-05）

为重新审视类型体系，owner 要求追溯项目刚起步时的规划文档：提交 `18cca7c`（2026-02-05，"Modify Demo Chatbot UI"）下的 `docs/PROJECT.md`（可用 `git show 18cca7c:docs/PROJECT.md` 查看）。项目文档体系此后经历过大改与多次更迭，其中的信息可能已漂移或丢失。下面是与记忆原子和类型体系相关的部分（2026-11-15 阅读）。

**类型体系：按"agent 应该如何使用"划分，与标签正交**

| 类型 | 当时的说明 | 当时设想的用法 |
|:---|:---|:---|
| CODE_SNIPPET | 代码片段、函数实现、配置文件 | 注入代码解释器，直接复用 |
| FACT | 明确的事实、业务规则、参数定义 | 注入系统提示词，约束 agent 的行为 |
| URL_RESOURCE | 外部文档快照、API 文档 | 带 URL 与清洗后的正文，替代再次联网搜索 |
| REFLECTION | 经验总结、错误反思、任务规划 | 帮 agent 避坑 |
| USER_PROFILE | 用户偏好、习惯、指令别名 | 个性化设置，长期生效 |

类型表中没有 WORK_IN_PROGRESS 与 AGENT_PROFILE。AGENT_PROFILE 是后来加入的；WORK_IN_PROGRESS 则出现在更早的第一版设计中：2025-12-23 首次提交的 `docs/PROJECT.md` 在"闲置超时触发"一节写道，任务未完成时生成一条 `WORK_IN_PROGRESS` 或 `TODO` 记忆，记下停在哪里、还差什么，用户几天后回来时由 Patchouli 主动提示要不要继续。2026-01-01（`543e02ac`）重写这一节时删去了这段，类型表一直只列五种；代码中的枚举值则从首次提交起一直保留。

**记忆原子与演化**：
- 粒度是"语义事务"：一个独立、自包含的知识点（一个完整的函数、一条条款、一段完整的推理链），由 Librarian 剥去闲聊、尝试过程与错误分支，只留下有效结论。
- 冰山三层：索引层只对 Title、Summary、Tags、Type 向量化（至今未变）；负载层是清洗后的 Markdown；原始层有 `context_ref`，按 `session_id` 与 `msg_id` 精确指回原始对话中的具体消息。
- 记忆是随时间演进的实体：索引指向最新，存储保留历史；变更时生成补丁而不是覆盖；负载层附一段注入上下文的历史摘要（例如"项目初始化用 Python 3.8；后来升级到 3.10"），让 agent 知道它怎样变过来；注入时附上"最后更新于几天前、此前有几个旧版本"。
- 按来源分级的信任：用户显式输入 1.0、不可被 agent 覆盖；运行验证成功 0.9、标为 VERIFIED；外部权威资源 0.8；LLM 纯推理 0.6、标为 UNVERIFIED。另有动态验证循环：正反馈提分，负反馈降权、标为 DEPRECATED 或 HALLUCINATION，或生成更正版本。

**生成**：原则是"写前查重"，宁可多花推理 token 也要保证库的纯净。四种决策：新建；TOUCH（只强化）；EVOLVE（同一实体的状态变更，走类似 git 的版本流程）；DISCARD（防污染：草稿置信度低而旧记忆置信度高时丢弃草稿）。外部资料单独处理：存来源 URL、抓取时间与清洗后的正文，标为不可变。

**作用域与生命周期**：私有、领域、全局三级同心圆作用域，私有记忆被验证、被多次引用后自动晋升为全局（个人经验经验证后成为团队的标准作业程序）；三级流水线中短期即 agent 的上下文窗口，中期是向量库，长期是冷存储；生命力按类型赋予固有价值（代码 1.2 > 事实 1.0 > 闲聊 0.1），被动命中、主动引用与用户反馈分别加分；按 `relations` 连带召回强依赖的记忆。

**目标与指标**：核心成功标准之一是"自主的记忆管理"；评估指标中列有"人工干预频率"，即用户手动修正标签或删除错误记忆的频率，越低越好。

**与现在的对照**：

| 当初的设计 | 现在 | 与本文讨论的关系 |
|:---|:---|:---|
| 类型按"怎样使用"划分，各有不同的送达方式 | 类型只是标签，生成、查重、衰减几乎一视同仁，只有 Profile 靠例外区别（第 2.4 节） | 语义丢失；重新审视类型体系的起点（第 9.6 节） |
| 原始层按会话与消息指回原文 | `ArtifactRef` 只指向整个 Artifact（第 2.1 节） | 丢失；"生成事件带上轮次与事件的信息"的决定（第 9.2 节）等于把它找回来 |
| 生成补丁、不覆盖；历史摘要对 agent 可见 | 版本快照保留了，但 Mode C 整篇重写，agent 看不到变迁 | 漂移；对应局部修改、"错了与变了"、沿时间轴回读（第 3.1、4.2 节） |
| 来源分级与动态验证循环 | 置信度生成后基本固定，验证状态没有写入方，负反馈没有发出方（第 2.3 节） | 设计了没有实现；对应"缺少结果信号"（第 3.4 节） |
| EVOLVE：同一实体的状态变更就地演化 | 2026-10-31 之前相似时用草稿整体覆盖，之后改为先新建再合并 | 漂移；复核（第 3.1 节）重新走向"先判断关系再决定" |
| DISCARD：低置信的草稿不得覆盖高置信的旧记忆 | 没有 | 丢失；与主动写入的优先权、防止推断冒充事实同类 |
| 私有记忆经验证后晋升为全局 | 只有 PUBLIC 与 PRIVATE，没有晋升 | 未实现 |
| 闲置时生成 WIP 快照，用户回来时主动提示续接（第一版设计） | 只剩类型标签：没有续接，也没有关闭 | 已决定去掉这个类型（第 9.6 节） |
| 短期即上下文窗口（第一方视角） | 短期是话题工作台 | owner 后来的反思（外部者拿不到上下文，第 3.2 节）解释了偏离 |
| 评估指标包含人工干预频率 | — | 一脉相承：长程标准（第 9.5 节）与最初的设想一致 |
| System 2 是在对话间隙阅读、打标、去重、入库的图书管理员 | Patchouli 是一次性调用 | 馆长 agent（第 6.1 节）是最初设想的回归 |

当初就存在一处内在张力：粒度定义要求剥去尝试过程与错误分支，REFLECTION 却专门记"错误反思"；Obelisk 的作者也批评摘要会先删掉失败路径，而在编程中失败路径正是不再重蹈覆辙的凭据（第 8.6 节）。重新设计类型体系时需要正面回答。已于 2026-11-16 回答：失败路径属于"经历"，写入时必须保住（第 9.6 节第 4.4 部分）。

## 2. 现状（以代码为准）

### 2.1 写入链路：两条路径、生成材料、判断与修订

**两条写入路径互相看不到**

- 被动提取的输入只有话题材料。交互材料有意不渲染 WRITE、UPDATE 与 CALL（[交互材料](../../src/hivememory/engines/perception/material.py)），提取时也不带中期库中的任何记忆。
- 两条路径只在查重时碰面：控制面记下本话题的主动写入已经结算到的正式记忆（`GenerationRequest.topic_write_memory_ids`）；被动提取的草稿查重命中其中一条时丢弃，主动写入的草稿相似命中时照常新建、不提名合并（[生成引擎](../../src/hivememory/engines/generation/engine.py)）。也就是说，两边的关系在各自生成之后才按相似度判断。
- 生成提示词按模式分开（被动、写入、更新、合并）。被动提取用同一份提示词处理所有来源（Alice 的对话与外部 harness 导入的会话），其中已经有针对 agent 工作过程的规则：思考不作为事实依据，工具调用与结果可以作为事实依据，子 Agent 交回的消息按结论对待（[生成提示词](../../src/hivememory/i18n/prompts.py)）。

**主动写入生成时的材料**

- 主动写入生成时的材料是话题的状态摘要与最近若干个已完成的轮次；话题不存在时按空材料生成（[生成协调](../../src/hivememory/patchouli/control/memory_generation/coordinator.py)）。
- 外部 harness 的交互在轮次结束后才经 Import Bus 导入，所以写入的那一刻，当前这一轮还不在话题中；"一句话直出"时话题是新的、空的，生成侧只有 agent 在 WRITE 中写下的内容、标题与理由。
- 写入前的 hook 会读取本地的会话记录，但只为工具参数补上当前一轮的用户消息与之前几轮的文本，用于确定话题，不带本轮的工具事件（[Claude Code hooks](../../integrations/hivememory/connector/claude_code/hooks.py)）。

**判断的位置、修订的形态与证据引用**

- **外部的价值标记已经移除**：代码中已没有 `worth_saving`。
- **信息在系统里，但不在做判断的地方**：控制面知道本话题的主动写入落到了哪些记忆（第 2.1 节），但这份信息只用于查重；真正做判断的那次 LLM 调用既看不到这些写入，也看不到库。
- **修订是整篇重写**：Mode C 的输出是整篇新正文加一句变更说明（`RevisionResult`），合并也是整体重写。
- **修订不改索引层**：Mode C 只覆盖正文，标题、摘要、标签与类型保持不变，检索与查重用的向量也随之不变；一条记忆被修订后，检索结果显示的仍是修订前的标题与摘要（[生成引擎](../../src/hivememory/engines/generation/engine.py)）。管理页的手动编辑可以改标题、摘要、标签与正文，不能改类型（[记忆生成服务](../../src/hivememory/patchouli/services/memory_generation.py)）。能改类型的只有合并：类型由模型重选。
- **证据引用只到整个 Artifact**：记忆中的 `ArtifactRef` 指向整个 Artifact（话题快照），没有轮次或事件的位置。

### 2.2 中期库：平铺、查重与生成形式

**查重只看索引层**

草稿按 `Title / Type / Tags / Summary` 四行编译成稠密向量的输入（[embedding handler](../../src/hivememory/engines/memory_compiler/handlers/embedding.py)），在整个 Workspace 中取最近的一条，按阈值判为相同、相似（先新建，再由合并任务融合）或不同（[Patchouli 生成](../patchouli/generation.md#4-查重与合并)第 4 节）。正文不参与。

**中期库是平铺的**

- `MemoryAtom` 只有 Workspace 归属、来源、读取策略与生命周期，索引层（标题、摘要、标签、类型、alias），正文与 Artifact 引用。关系层的 `relates_to`、`supersedes`、`depends_on` 是预留字段，生产代码不写入（[记忆模型](../../src/hivememory/core/models/memory.py)）。
- 检索的业务过滤只有类型、来源 agent、时间范围、标签与最低置信度（`QueryFilters`），没有"属于哪一组"。
- 话题是系统中唯一按内容归组的结构，但只存在于短期：结算时材料一经生成队列接纳，话题就被删除（`PerceptionFamiliar._settle_topic`）。之后，一条记忆与它的话题只剩间接的联系：它引用的来源 InteractionArtifact 记着 `topic_id`。

**生成的形式为平铺检索而定**

生成提示词（[生成提示词](../../src/hivememory/i18n/prompts.py)）把这一点写得很明确：

- 被动提取要求"将内容拆解为独立、自包含的知识点"，每件事写成一条记忆，"标题与摘要要让人能单独检索到它"；
- 主动写入沿用 agent 拟定的标题，但标题缺少"让人检索到它的关键名词（项目、组件、工具名）"时要修改；
- 合并要求标题与摘要覆盖合并后的全部要点，因为"检索只使用标题、类型、标签与摘要，不读取正文"。

**关系层**

- `RelationLayer` 有 `relates_to`、`supersedes`、`depends_on` 三个记忆 ID 列表，标注为预留（[记忆模型](../../src/hivememory/core/models/memory.py)）。
- 后端与前端都没有任何读取方或写入方。
- 它被序列化进每一个 Qdrant point；记忆版本快照也把 `relations` 列为必备字段。
- `patch_payload` 的白名单只有生命周期字段与读取策略，不含关系层；改一次关系就要整条记忆重新提交，并生成新的版本记录。
- 合并已经以另一种形式记录了"取代"：被吸收的记忆被删除，旧 alias 改指到保留的记忆，版本记录以 MERGE 来源记下这次合并。

### 2.3 存储：真相、一致性与记忆原子中的非文本部分

**存储层的真相与跨存储的一致性**

- 中期层的真相就是 Qdrant：向量、索引层与正文在同一个 point 上，它是 Retrieval、Generation 与 Lifecycle 共同依赖的当前记忆事实库（[MemoryLibrary 与存储层](../patchouli/memory-library.md#12-中期当前可检索书库)第 1.2 节）。
- 跨存储的写入都不在一个事务里（[耐久性与故障恢复](../governance/reliability/durability-and-recovery.md#1-当前状态与问题证据)第 1 节）：MemoryAtom 与 Artifact 的写入失败时可能留下未被引用的 Artifact；archive 与 revive 在中期库与冷藏库之间搬运，失败时可能留下重复副本或中间态。治理文档写的处理方向是对账与可重试的 saga。
- 读取视图的失效经进程内的变更事件，尽力而为、不重放；读取视图本身不跨重启，所以这样成立。
- 启动时，记忆 payload 只接受 schema 2.1，其他版本拒绝解码；已有的 Qdrant 集合则不核对向量配置，存在即直接使用（[向量存储](../../src/hivememory/infrastructure/storage/vector_store.py)）。

**记忆原子中哪些部分与文本等价**

- **与文本等价**：索引层（标题、摘要、标签、类型、alias）相当于 frontmatter；`payload.content` 本身就是 Markdown 正文；Artifact 引用可以用链接表达。
- **不是文本，并且有生产使用方**：
  - 使用状态：检索命中时只刷新最近访问时间；actor 经 READ 或 RUN 读取时记录一次引用，访问次数、生命力与衰减基准随之变化（[actor 记忆操作](../../src/hivememory/workspace/capability/actor/memory.py)、[强化](../../src/hivememory/engines/lifecycle/reinforcement.py)）。生命力参与检索排序（[融合排序](../../src/hivememory/engines/retrieval/fusion.py)）与归档。
  - 置信度：生成时给出，注入时显示，也参与检索排序。
  - 读取策略：读取时按 agent 执行（[MemoryLibrary 与存储层](../patchouli/memory-library.md#12-中期当前可检索书库)第 1.2 节）。
  - 版本：每次内容提交都必须带版本记录，变更事件让 workspace 的读取视图失效（同上）。
  - 可运行的定义：AGENT_PROFILE 的 `agent_config` 可以被 CALL，CODE_SNIPPET 可以被 RUN。
- **字段存在，但没有任何写入方**：
  - `verification_status` 永远是 UNVERIFIED。注入时会按它显示"已验证""已过时""幻觉"，但生产代码中没有任何地方设置这三种状态（[注入渲染](../../src/hivememory/engines/memory_compiler/handlers/prompt.py)）。
  - 关系层从未被写入（第 2.2 节）。
  - 负反馈在强化中有处理逻辑，但没有任何地方发出这个事件。

### 2.4 读取与交付

**两类 Profile**

- **USER_PROFILE** 是普通类型：由被动提取与写入产出，只能经相同的相似度检索找到，系统中没有任何常驻注入。它不按生命力归档，理由是"长时间未被检索不代表已经过时"（[垃圾回收器](../../src/hivememory/engines/lifecycle/garbage_collector.py)）。合并不排除它，合并结果的类型由模型给出，一条偏好可能被并进其他类型的记忆。
- **AGENT_PROFILE** 按 alias 精确解析：执行者自己的 Profile 与 CALL 的被调用方都不经检索（`RetrievalFamiliar.get_agent_profile`）。但运行时发现子代理只能靠检索命中：检索上下文中的"可用子代理"一节，只由这一轮检索结果中恰好出现的 Profile 组成（`MemoryCompiler` 的检索上下文分节）；MTP 提示词也只让 agent 在"记忆上下文中列出了可用子代理"时委托。运行时没有列出全部可用 agent 的途径，完整列表只供 HTTP 管理入口使用。
- AGENT_PROFILE 还以一组分散的类型判断，被排除在记忆原子的大部分行为之外：只能经 Profile 创建入口创建；查重不提名它合并，合并任务拒绝它，合并结果也不能变成它；不按生命力归档；不出现在管理页的记忆列表中；不在生成提示词的类型之内，所以交互经验永远不会产出或修订一个 Profile，它只能手动编辑。生命力照常计算和展示，但不据此做任何处理。

**记忆库中像工具的成员与外部入口**

- 外部 harness 经 MCP 只有检索、读取、写入、更新四个工具（[MCP 入口](../../src/hivememory/mcp_server/server.py)）；RUN 与 CALL 只在 Alice 的 MTP 中存在。
- 记忆库中像工具的成员都走特殊路径：AGENT_PROFILE 被 CALL 解析，并被一组类型判断排除在记忆原子的大部分行为之外（第 2.4 节）；CODE_SNIPPET 被 RUN，由本地执行器运行，面向执行的编译目标 `RUNNABLE_TOOL` 仍是保留项，编译时直接报错（[编译目标](../../src/hivememory/engines/memory_compiler/handlers/targets.py)）。
- RUN 把整段正文当作 Python，在子进程中执行：内置函数走白名单，禁用 import、open、exec、eval，参数经 `params` 字典传入（[用户工具](../../src/hivememory/agent_runtime/tools/user.py)、[沙箱执行](../../src/hivememory/agent_runtime/tools/repl.py)）。生成链写出的正文是 Markdown（带说明文字与代码围栏，代码可能不是 Python，也可能是配置文件），写入提示词还要求补全 import 语句，所以被动提取与 WRITE 产出的 CODE_SNIPPET 基本运行不了；能运行的只有专门写成"纯 Python、不用 import、读取 `params`"的记忆。运行结果不回流到验证状态。
- 被动提取把出错的工具结果当作提炼错误原因与修复经验的依据（[生成提示词](../../src/hivememory/i18n/prompts.py)的过程条目规则）。

**预检索只在 Alice 中存在**

- Alice 的任务进程在 PREPARE 阶段以主线程做预检索（[任务进程](../workspace/task-process.md)）。
- 外部 harness 上没有预检索。Claude Code 与 Codex 插件的 hook 只在会话开始、结束与每轮结束时登记会话记录，并在写入与更新前为工具参数补上当前一轮的信息（[hooks 配置](../../integrations/hivememory/hooks/hooks.json)）；dsh 与 pi 插件向系统提示词注入的是 MCP 的使用说明，不是记忆。记忆能否进入上下文，取决于 agent 依照这份说明与 skill 自己调用检索。

### 2.5 外部来源与 agent 循环

- **agent 循环属于 Alice**：`agent_runtime` 是走 MTP 的单帧执行内核，分层测试把它与 Alice 视为同一个子系统，Patchouli 不能导入它。
- **附件只留下了元数据**：Alice 对话中的附件在结算产出新建或更新时被提升为 DocumentArtifact（`MemoryGenerationFamiliar._promote_attachment_bindings`），但只写元数据：`source_uri` 指向不跨重启保留的附件存储，没有内容快照，返回的引用被丢弃，没有挂到任何记忆上。
- **外部 harness 的工具结果完整保存，但没有被识别为来源**：网页、文件等工具结果作为轮次事件完整保存在交互 Artifact 中，记忆只能引用整个交互 Artifact。
- **DocumentArtifact 模型是齐的**：来源 URI、取回时间、内容快照地址，以及页码、标题路径、行号、引文等定位符都有，只是没有接入主流程（[Artifacts 与来源追踪](../patchouli/artifacts.md)第 2.2、7 节）。

## 3. 写入链路

### 3.1 对照已有记忆复核（另一位 agent 的思路与评估，2026-11-15）

**思路**：
- 保留两个写入时机，对同一份中期记忆承担不同的责任：主动写入负责兑现明确的保存意图；被动提取负责在一段经历结束后，检查已有记忆还有哪些遗漏或错误。两者都由 Patchouli 整理并写入。
- 与断言设想的区别在于先做什么判断：断言先问"这段材料里有哪些值得记的主张"，再逐条判断与库的关系；这里让被动路径先看到相关的已有记忆，再问"经历了这一段之后，哪一条需要怎样改？还有什么值得记的，在这些记忆里完全找不到？"。
- 主动写入的优先权落在"值得保存"上：WRITE 提供了被动路径还原不了的信号，即当事人在那一刻认为这件事值得让未来的 agent 找回来。Patchouli 可以发现已有记忆已经完整表达、可以整理措辞，但应保住它的用意，并允许它沿现有路径及时生效。边界：WRITE 只证明当时作出了这个判断，之后复验失败仍应纠正；没写某件事只说明没有提出保存请求，沉默推不出审阅过并决定舍弃。
- 被动结算的材料：本次话题轨迹；这段交互中明确写入或更新过的内容及其可定位的目标（主动写入提供了确定的线索）；少量可能受影响的既有记忆（跨话题的靠检索补充）。三种判断：已有记忆足以支持下次使用，保持原文（同一结果被工具输出、agent 总结与 WRITE 转述三遍，仍只算一份依据）；新材料改变了某条记忆的结论、适用条件或当前状态，定位到那条，只修改发生变化的部分并指明依据；有值得未来独立找回的内容、已有记忆承载不了，新建，一次可以新增多条，也可以一条都不新增。
- "这是新信息"只回答了以前有没有出现，没有回答值不值得改变记忆，后一问放在生成的中心。
- 按结论协调，不按轨迹区间消费：不让一次 WRITE 消费掉之前的整段轨迹，同一段可能还支持另一件事（例如用户中途纠正的工作习惯）。允许被动结算再次阅读证据；要抑制的是同一份证据反复制造新记忆，或被误当成多次独立验证。纯聊天时被动路径照常发现变化；主动写得充分时，读完整段得到零修改也是成功结果。
- 最薄弱处是能否找出真正相关的旧记忆，因此保守取舍：有明确对象和明确变化时才自动改写，两条内容仅仅相关时保留各自原意。
- v0.8 最先能独立验证的机制：被动结算针对已有记忆提出有依据的修改，并能判断"这一轮什么都不用改"；直接利用已有的 Topic、写入意图、正式记忆与来源 Artifact。断言是否持久化为独立对象，等确实出现跨多次整理复用的场景再决定。

**评估（我的看法）**：
- 这是到目前为止最具体、也最贴合第 1.1 节诊断的一版：被动提取从"提取"变成"对照已有记忆复核"，新建成了例外，"改哪条、怎么改、要不要新建"在看到已有记忆之后判断，而不是事后靠相似度对账。它与第 3.1 节的最简版本方向一致，并把顺序讲清楚了；也给统一交互记忆 Idea 第 5 节的两问提供了合理的默认（没写不等于取舍；主动写入照现有路径立即生效），仍由 owner 决定。
- 认同的几点："新信息"不等于"值得改变记忆"，与第 3.4 节的判据是同一标准；按结论协调对消费水位的批评成立；保守取舍；"进行中"的终态成为对旧记忆的修订，在结构上解决而不是打补丁；两种交互形式落在同一套机制里。
- 质疑：
  1. 最弱的一环恰好是第 9.1 节。平铺库中"相关的已有记忆"只能取全库相似度的前几条，同项目的记忆在索引层天然相近；如果库有分组，可能受影响的记忆可以是所在分组的内容，像主动写入一样确定。所以这个方案让库的形状更关键。
  2. "只修改发生变化的部分并指明依据"，现有的修订做不到（第 2.1 节）。整篇重写在多次修订中会让细节漂移，mem0 放弃写入时由 LLM 增删改的理由正是覆盖会丢细节。可以借 Hindsight 的做法：模型只给结构化判定（保持；修订某一部分并给出依据；新建），由唯一写入者按判定落地，修订以局部修改的形式记入版本，自动修改因此可以审计。
  3. "同一份证据只算一次"需要证据有可定位的身份，现在的引用只到整个 Artifact；主动写入一侧知道自己在哪一轮（MCP 写入带 `turn`），被动一侧还没有。
  4. 结算时机仍然重要，但不再那么敏感：现在的结算与经历是否结束无关，修订机制让提前结算的代价变小，前提仍是下一次结算找得到那条记忆。
  5. 正式记忆被 LLM 改写的频率会明显上升：一条记忆的当前版本可能是多次自动修订的叠加，版本 Artifact 保留了快照，但没有记录每次修订依据的是哪段证据。

**更早的提议：素材来源与生成之间的中间表示（2026-11-13，owner 未决定）**

- 按整理的程度排列：会话轨迹（只追加的时间线，短期是其中尚未整理的尾部）→ 断言（小、带归属与证据、带发生时间的条目；主动写入是第一当事人的断言，被动提取只产出推断的断言）→ 正式记忆（只由整理写入）。三者都在中期库之前，术语沿用[统一的交互记忆](./unified-interaction-memory.md)。
- 最简版本：中间表示只存在于进入生成队列的路上，不单独存储；生成时把每一条与已有的中期记忆比对，参照 Hindsight 的逐条判定，判为重复、改变、终止、新增或不值得保存，取代相似度查重。更完整的做法是把断言作为单独存储的一层。
- 现在两条路径在生成之后由查重协调（第 2.1 节）；引入中间表示，意味着两条路径在生成之前汇合。

### 3.2 主动写入的背景与外部者视角下的短期记忆（候选定义，不是 owner 决定）

已有的框架见[短期记忆与上下文压缩](./short-term-memory-and-context-compaction.md)第 1 节：短期记忆分为 agent 的执行工作记忆（前台上下文）与 Patchouli 的记忆形成工作集（话题）；owner 于 2026-09-28 决定话题不承担前台会话上下文的控制。

**"复制上下文"的诡异感来自时序，而不是复制本身**。流式接收复制的不是 agent 的上下文，而是交互事实。上下文是前台 harness 对这些事实的视图（经过压缩、注入与截断），属于第一方，HiveMemory 拿不到，也不该管；话题与交互记录是同一份事实的另一种视图，属于写入者。短期 Idea 第 4 节早已如此表述：两份摘要根据共同的交互事实分别生成。外部者总是滞后的，各类使用者对滞后的容忍度不同：话题结算可以等到轮次结束（现在的 Import Bus 正是如此）；主动写入的生成需要截至写入那一刻的事实，缺背景正是因为这一刻写入者还没追上（第 2.1 节）。owner 所说"拥有完整背景的前台 agent 并不是第一写入人"就是这个错位：有背景的不负责写，负责写的在写入那一刻没有背景。

**定义**：HiveMemory 的短期记忆，是时间轴上最新、尚未被整理的那一段交互记录。它按会话的时间线存放，按话题（经历节点，第 4.2 节）归组；保存原文，每个事件都有轮次与事件的身份。它是写入者的工作记忆，不是 agent 的上下文。三类使用者：
1. Patchouli（写入者）：生成与复核的材料，主动写入需要的背景应当从这里来。
2. 其他上下文中的 agent：跨会话的 agent、压缩之后的同一个 agent、另一个 agent，用它了解"最近发生了什么"。这是外部者能为 agent 的短期需求做、而前台自己做不到的事：上下文压缩后会丢细节，另开会话就看不到之前的内容，而这份记录还在。但交互原文现在没有任何检索入口（第 8.4 节第 6 点）。
3. 维护：结算与复核的范围就是这一段尚未整理的记录。

这个定义落在时空框架上：短期就是时间轴新鲜的那一端。结算不是把短期"搬"成中期，而是这一段被整理之后，记录本身作为证据留下，它的经历节点留在时间轴上，整理出的记忆挂到主题与经历节点上。它与 2026-09-28 的决定一致：HiveMemory 不复制、不管理前台上下文，对 agent 短期需求的支持只走两条间接的路：把中期记忆送进上下文（检索与常驻的小索引），以及把最近的交互记录开放给需要它的上下文。

**写入就是同步点**。既然只有写入者需要"追平到当下"，就不需要持续镜像上下文，只需在写入发生时把轨迹追平到写入那一刻。写入前的 hook 已经在读本地会话记录，那一刻正是追平的时机；对长时间运行、一轮内多次写入的 agent，每一次写入都是一个同步点；持续的流式接收作为更通用的版本，留给[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)。两种落法：
- 作为生成材料随写入一起提交：不触碰交互的封口语义，但要截断或挑选（工具结果可能有 MB 级）。
- 作为未封口的部分轮次先导入话题：写入者的工作记忆真正追平，但要先回答长 Turn Idea 中开放交互、封口与迟到事件的问题。

**分工**：agent 提供意图（写什么、为什么写），skill 的要求只需保证这一点；事实背景来自记录，由写入者从短期记忆中取，而不是靠 agent 复述。agent 复述背景必然压缩，这正是"空中楼阁"的来源。

**"空中楼阁"其实是两件事**：一是记忆正文缺背景，读者看不出结论在什么情况下、为了解决什么问题得出；二是证据够不到，即使正文简短，能顺着链接找到背景就不是空中楼阁，只是"地基在别处"。调研类工作流中，背景其实就在 agent 刚写完的调研报告里：与其要求 agent 在记忆中再写一遍背景，不如让记忆写一段简短的背景，加上指向报告具体章节的来源链接（DocumentArtifact 与定位符，第 6.2 节第 2 级），后一件事由此解决，不依赖 agent 是否遵守 skill；前一件事靠写入即同步点。三者互补：skill 的要求作为下限，写入时有轨迹则由 Patchouli 补背景，结算时终态收尾者再以完整轨迹复核。

**与调研的关系**：几乎没有人关注外部者的短期记忆。dsh-agent-soul、gliding_horse 与上下文压缩调研中的五个 harness 都掌握前台；唯一接近的是 EverOS，它的"短期"是会话缓冲中尚未切出的尾段，单位是会话时间线，与这个定义一致。它没有解决的正是写入时机：EverOS 没有第一当事人的主动写入，从不需要在写入那一刻追平。

**外部者与第一方两种处境（分析，2026-11-15）**：Obelisk 读原生日志，只避开了"转换成统一格式"这一层损失，原生日志本身的不完整它同样无能为力（它自己的说明承认：Claude Code 的日志不标记回退与当前所在的分支，Codex 的日志没有分支的概念）。所以"证据层的完整性上限由 harness 决定"对第三方是结构性的（第 1.2 节）。由此，HiveMemory 面对两种处境：
- 插件模式下是外部者：拿不到上下文，记录的完整性受制于 harness；本节的定义与"写入即同步点"是为这种处境写的。
- 在自己的 harness 中（Alice，或 owner 正在开发的 harness）是第一方：上下文透明、可以操控，事件可以按发生顺序直接交给 Patchouli，时间线与流式接收都变得自然，短期记忆甚至可以与上下文统一管理。

同一套设计需要写明哪些机制两种处境共用、哪些只在第一方的处境中成立，避免把自研 harness 才有的条件当成所有入口的前提。

### 3.3 时间线：顺序与身份，不是流式（分析；水位语义退场为 owner 决定，2026-11-15）

时间线关乎顺序与身份，流式关乎多早送到，是两件事：时间线一直需要，流式只在某些使用者等不起时才需要。

**时间线需要的三样**：
1. **每个事件都有稳定的位置**：会话内由"会话、轮次、事件序号"确定（轮次有外部标识，Import Bus 由它推导交互标识；轮内事件本来就按序号排列）；跨会话之间只有发生的时间。统一交互记忆 Idea 第 3.3 节已经写明：时间线按会话划分，并发的不同会话之间只有时间戳，没有可消费的先后。所以"绝对时间线"的准确含义是会话内全序、跨会话按时间戳排列的偏序。
2. **按发生的位置排，不按到达的先后排**：批量导入时，事件到达的顺序可能与发生的顺序不同（导入延迟、重试、多会话并发）；只要事件自带位置，晚到的也能插回原处。反过来，按到达顺序拼时间线，流式也救不了。
3. **重复导入不产生重复，晚到的事件有处理规则**：Import Bus 已按外部会话串行导入、按交互标识去重；还缺事件级的身份（第 9.2 节已决定生成事件带上轮次与事件的信息），以及"已经切过的段又来了迟到事件"的规则（长 Turn Idea）。

这三样在轮次结束时批量导入就能做到。

**流式（更早送到）只在这几种情况下需要**：写入时的同步点，按需追平到写入那一刻（第 3.2 节）；轮次结束遥遥无期的长 turn，又有使用者需要更早看到事实（长 Turn Idea）；以后出现的其他延迟敏感的使用者。崩溃安全不需要流式：harness 的会话记录在本地磁盘上，连接器下次同步时仍能导入。

**时间线的角色变了**：最初的设想中，时间线还承担"消费水位"，每个事件只被消费一次，以免重复提取。按第 9.2 节的决定，被动结算是话题的终态收尾者，以全局视角复核，按结论协调而不按区间消费，这层消费语义不再需要：owner 于 2026-11-15 确认，统一交互记忆 Idea 第 3.3 节的消费水位语义就此退场。时间线留下两个角色：顺序与身份的骨架（时空图索引中时间轴的底座，经历节点建在其上）；证据的坐标（记忆引用"第几轮、第几个事件"，指向时间线上的位置）。即：时间线保留，"每个事件只消费一次"的水位语义退场，流式降级为按需追平。

**OneRing 的启发：它是一份"流式"的账本，却不是一条可靠的时间线**（第 3.3、8.3 节）：
1. **有流式而没有身份，就成不了时间线**：OneRing 在每个请求经过时记账，但消息没有 ID、没有会话字段，按写库时刻排序，于是只能靠 hash 猜"是否已存在"（重复的短句被当成已有）、晚于最后一块的消息被丢弃、编辑原地覆写不留历史、重试时相似度 ≥0.92 的两条用户消息被合并。时间线成立的条件是身份与位置，不是送达方式。
2. **过早接收、没有封口语义，就会留下孤儿**：OneRing 在预处理阶段就写入用户消息，AI 回复要等整轮成功才写，一轮失败或断连后账本里留下没有回复的孤立用户消息；这正是长 Turn Idea 中开放交互、封口与迟到事件要回答的问题，也是第 3.2 节倾向"按需追平"而不是"持续流式"的理由。结构上，VCP 是坐在前端与模型之间的代理，每个请求都经过它，所以能在请求那一刻记账；HiveMemory 在插件模式下不在请求路径上，能介入的只有会话开始、写入之前与轮次结束这几个 hook，"写入即同步点"是其中最接近 OneRing 记账那一刻的地方。
3. **读回其他上下文要慎推、多拉**：OneRing 是调研中唯一把外部记录读回别的上下文的例子（第 3.2 节第二类使用者），为此加了很多限制：只在上下文少于 10 块时补、只插进时间戳可信的缝隙、每条加来源尾标、"宁可不补也不补错"，可见把原始消息推进运行中的上下文风险很高；它的另一半做法 OneRingMemo（把近 3 天压缩成常驻的客观时间线摘要）反而更稳。所以给其他上下文提供最近的经历，以常驻的近期摘要为入口，细节按需去拉（检索交互记录、读经历节点），与时空图索引的时间轴新鲜一端加常驻小索引中"最近几段经历"是同一回事。
4. **"同一个它"作为视图保留，不作为存储单位**：OneRing 以 Agent 为单位存账本，代价是不同话题互相渗入；但"这个 agent 最近在各处做了什么"的需求成立。在 HiveMemory 中它可以是时间线上的一个视图：时间线按会话存放，每个事件带着参与者（轮次上已有 actor 身份）与来源（harness 名），按 agent 过滤出的那条线就是"同一个它"，按话题、按时间过滤是另几个视图。存储只有一份、视图可以有很多个，与第 9.1 节"存储平铺、分层由派生索引承担"同一个思路，只是放在时间轴上。

一句话：OneRing 想要的（Agent 级的连续性、每条消息带来源、整轮完成才落账、一份常驻的近期摘要）都对；它没做好的（没有身份、按到达排序、在请求路径上过早写入、直接把原文推进上下文）恰好说明 HiveMemory 的时间线该怎么做：位置与身份先行，流式按需，读回时以摘要为入口、细节按需去拉。

**OneRing 与按时间线消费交互**

OneRing 留下的理念是：连续性的单位是 Agent，而不是某个前端临时传来的消息数组。两个具体做法与 HiveMemory 一致：AI 回复只在整轮完成后才落账，与"有输出时才封口提交"是同一个原则；每条消息标明是谁、何时、从哪里来。它的实现则说明了几件事（第 8.3 节）：

1. **以 Agent 为单位，代价是不同话题互相渗入**，同一前端的多个窗口也分不出来。统一交互记忆 Idea 第 3.3 节把时间线按会话划分，再由话题按内容跨会话归并，正好绕开了这一点。所以"绝对时间线"可以作为存放的顺序，但被消费时需要切分（按会话或按话题），不能整条交给模型。
2. **用途不同。** OneRing 服务于上下文补齐，只有 100 条，读完不做任何结算；按时间线消费服务于记忆生成，每次触发时消费到当前为止的事件，每个事件只被消费一次。OneRing 里没有这层语义，它是 owner 的设想自己加上的。按第 9.2 节的决定，这层消费语义已经退场（owner，2026-11-15），时间线保留为顺序与身份的骨架（第 3.3 节）。
3. **事件需要稳定的身份。** OneRing 做不到"编辑作为新事件追加"，根本原因是消息没有 ID，只能靠 hash 判断"是否已存在"，于是重复的短句被当成已有，晚到的消息被丢弃。HiveMemory 的 Import Bus 用 harness 给出的外部轮次标识推导交互标识，不需要模糊比对。
4. **保存更彻底。** HiveMemory 的 InteractionArtifact 保存全部交互原文，比 OneRing 本身更接近它宣称的"旧消息不会无意义丢失"。
5. **OneRingMemo 是一个常驻的近期动态摘要。** 一份跨前端、跨会话的近期时间线摘要，可能是值得常驻的少数内容之一（第 3.4 节），也与短期记忆的定义有关。

### 3.4 什么值得写：内化与价值标准

1. **内化一半落在交付上。** 模型的权重不变，一段知识"属于 agent"只能表现为：需要的时候，它以能直接用上的形式出现在上下文里。HiveMemory 为此选择了动态检索，并保留了从索引到正文的渐进式披露（第 1.2 节）；四百多条记忆照旧动态检索，这一点不变。在此之上仍有两点值得考虑：
   - **由谁判断该加载什么。** skill 机制让模型看到常驻的菜单，由模型决定读哪一篇；检索由系统按相似度决定，模型只看到命中的结果。两者失败的方式不同：检索漏掉的，agent 察觉不到，它不知道自己不知道什么。所以只有少数漏掉代价很高的部分（用户偏好、可用子代理的清单，第 4.1 节）不该依赖检索命中。
   - **日常路径上没有预检索**（第 2.4 节）。外部 harness 上，记忆能否进入上下文完全取决于 agent 自己决定检索：它知道 HiveMemory 可用，却不知道库里有什么，比 skill 还多一层盲区（skill 至少把菜单放在了上下文里）。平铺的库中找不到比全部记忆更小、又能常驻的东西；分层时可以多级披露：常驻少量分组的描述，需要时读分组的索引，再读正文，agent 不必看到每一条记忆，也能知道哪些方向值得检索。这与第 9.1 节是同一个问题。
2. **"一切都是记忆"与"一条生成链路"之间有张力。** VISION 写明"统一并不等于同质化"：skill 是必须整体正确的程序性文档；犯错的反思是一次经历得到的教训；知识库条目的真相在外部文档里，记忆更应该记从中学到了什么、何时、用于什么决定，而不是复制它。现在的被动提取按单次结算进行，只能产出事实一级的东西；人从经历得到先验知识，靠的是在多次经历上归纳，而 HiveMemory 现在跨经历的机制只有按相似度两两合并。调研中真正做"经历变成知识"的都是在多条经历之上整理：EverOS 把聚类的 agent case 生成 `SKILL.md`，Hindsight 从事实沉淀出 observation、再到 mental model。只改进单次提取到不了内化，缺的是一个跨经历归纳的环节，它可能比提取本身更关键。
3. **判断"是不是知识"需要一个标准。** dsh-agent-soul 给 `SELF.md` 的入选判据是"这一行不在了，我会不会做出不同的决定"。流水账不满足它，owner 删掉的 PR 记录大概也不满足。现在被动提取的价值标准是"包含具体的讨论内容"，衡量的是记录完整，不是能否改变决定。这个判据可以作为重新设计时"什么值得成为记忆"的原则，而不是一处提示词修补。Anthropic 的文章给出了一个更具体的判据：环境能重新告诉你的不记，只有自己推出来、不写就会消失的才记（第 8.4 节）。
4. **全自主维护缺少结果信号。** 系统只知道一条记忆被检索到、被读过，不知道它有没有让 agent 做对或做错；验证状态没有写入方、负反馈没有发出方（第 2.3 节）正是这个缺口。人的遗忘与强化按"用上了、有效"选择；没有结果信号，自主维护只能依据访问这类替代信号。这可能是自主维护目标中最难、也最需要提前设计的一环。两个可能的信号来源（第 8.3 节）：一是记录使用方实际采纳了哪些检索结果，"被采纳"比"被检索到""被读取"强得多；二是检索本身暴露的知识缺口，命中稀疏、覆盖不足，说明库在这方面缺少内容，能告诉自主维护"该补什么"，而不只是"该删什么"。

## 4. 库的形状与访问

### 4.1 平铺的库怎样限制写入与读取

**中期库的形状限制了写入链路**

1. 库是平铺的，读取只有一种方式：按索引层的相似度检索（第 2.2 节）。
2. 所以每条记忆都必须能被单独检索到，要把自己所处的上下文（项目、组件）写进索引层（第 2.2 节）。
3. 同一项目的记忆因此在索引层上天然相近，查重分不清"同一件事"与"同一项目里的另一件事"：分数落在 0.75 阈值两侧（[查重 Todo](../todo/generation-dedup-decision-signal.md)）。分层时，这些上下文由所在的组承担，不必每条重复。
4. "这件事该放在哪、库里已经知道什么"只能由全库相似度回答。查重取全库最近的一条；被动提取看不到库，平铺的库最多也只能像 mem0 那样给它几条相似的旧记忆，无法让它"更新关于 X 的那一部分"，只能先产出新的记忆，再由相似度决定它与已有记忆的关系。
5. 会随时间变化的状态没有固定的位置。后来的终态只能成为又一条记忆，相似度超过阈值时才会被合并进旧记忆；分层时，"某项工作的当前状态"可以是组内一个固定的位置，新状态直接覆盖。

一份外部讨论稿（第 8.3 节）中也有同样的观察：把记忆按领域分区，每个使用方只在自己的分区里检索，共现关系、去重阈值这些信号会更可靠，原因不是算法变好了，而是无关的内容不再参与比较。

这同时作用于两条写入路径：主动写入与被动提取的草稿走同一个查重。即使将来主动写入的比例变高，形状带来的限制仍然存在。在第 9.1 节的决定下（存储平铺、分层由派生索引承担），这些限制大多由索引参与写入解除，见第 4.3 节。

**Profile 需要另外两种读取方式**

- 用户偏好需要常驻：不论当前在问什么，它都应该在场。
- agent profile 需要可列举、可寻址：先知道有哪些 agent，再从中选择；检索可以帮助挑选，但不应是唯一的入口。

平铺的库把这两种需求都压进相似度检索，特殊需求就只能成为例外：USER_PROFILE 的归档豁免与 AGENT_PROFILE 的合并排除都是这样来的。AGENT_PROFILE 存放在同一个库里，却靠十来处例外表达它的独立性，结果既没有得到作为记忆原子的好处（维护，从交互中学习），也没有得到单独成层的好处（运行时可以列全）。

**分层的代价与现成的出发点**

- 分层把"这件事属于哪里"从检索时挪到了写入时。现在这个判断由检索按相似度临时做出，每次都可能不同，但写入时不用承担；分层后，写入时要决定归入哪一组，而组由谁建立、怎样命名，又是一个与话题路由同类、由模型判定、不能保证合理的判断。
- 一旦某一层常驻，它的写入方式也随之改变：不再追加原子，而是维护一份有预算上限的文档。调研中已经出现了代价：EverOS 每次整体重写用户的 `user.md`，用户手改的内容会丢失；dsh-agent-soul 的 `USER.md` 超出预算的部分会被省略。
- 一个现成的出发点：系统已经有按内容归组的结构，就是话题，只是它在进入中期库时被删除了（第 2.2 节）。

### 4.2 高层图索引：库一级的冰山模型

**把单条记忆的冰山推到整个库**：常驻的小索引 → 按主题综合、带引用的页面 → 记忆原子（Index 与 Payload）→ Artifact 中的原始证据。现在从问题走到原子只有一次相似度检索，这就是 owner 所说"渐进引导断了"的地方。

**高层节点的候选**：

| 候选 | 例子 | 长处 | 问题 |
|:---|:---|:---|:---|
| 主题：项目、组件、工具、人、概念 | Perplexity 的 `knowledge/`、Hindsight 按单主体组织的 observation、BaiShou-Next 的实体图 | 有名字，回答"关于 X 我们知道什么" | 需要有人建立与维护，由 LLM 判断 |
| 经历：一段交互或一个话题 | EverOS 的 episode；HiveMemory 的话题（结算时被删除） | 回答"上次那件事"，有时间顺序 | 按交互划分，不是按知识划分 |
| Tag | VCPToolBox 的 Tag 共现图；HiveMemory 索引层已有的 tags | 数据现成，代价最低 | 噪声大、没有名字层级；VCP 一年下来只让它在候选内加不到 0.21 的分 |
| 身份主体：用户、各个 agent | 用户偏好、agent profile | 天然的枢纽，也解开第 4.1 节的 profile 问题 | 数量少，只能当几个入口 |

**两类节点，对应时间与空间**（owner 的说法，第 1.2 节）：主题节点是记忆的空间内容，回答"是什么"；经历节点是记忆的时间序列，回答"在哪里学到的、什么时候"。记忆原子挂在两者之间，证据在它下面；用户与各个 agent 作为主题一侧的几个特殊节点。理由：人的回忆本来就有"关于 X"与"上次那件事"两种入口，Perplexity 的 wiki 提升最大的几类中就有时间推理；话题本来就是按内容跨会话归并的经历容器，保留下来作为经历节点是最小的改动，按时间线消费的设想也可以成为这条轴的骨架；主题一侧的归属是多对多的，一条记忆可以同时挂在几个主题下，不要求边界清晰。时间还有更细的一层：单条记忆与主题页本身也随时间变化（版本、取代、"之前怎么定、现在怎么定"），记忆的这条时间线由 MemoryVersionArtifact 记录；"X 是怎么变成现在这样的"可以先在空间上定位到 X，再沿时间轴往回读，这也对应第 4.1 节第 5 点"状态类信息需要固定的位置"。

**边分三类**：主题之间的上下文边（属于、依赖、相关），用于导航，即 `relates_to` 本来想表达的东西；主题、经历到原子的归属与引用边，多对多，用于从综合页下钻到具体记忆；原子之间的取代与冲突边（例如 `supersedes`），主要供维护检测冲突、在检索时给被取代的记忆降权，按第 7 节属于维护一侧。所以关系层不必是"原子之间互相连边"，导航用的边主要建在高层节点上；关系层本身的去向见第 4.4 节。

**设计约束（分析，不是 owner 决定）**：
- **图索引是路由结构，不是真相**：它与 VCP 中"只给出候选的 ANN 路由缓存"同类，真相仍是记忆原子与 Artifact。它由馆长从原子派生，可以重建，第 5.2 节"同一事务标脏、查询时修复"可以直接套用；路由出错只多花几步或漏掉一些，不会返回错误内容，漏掉的仍可由检索补回。这也是"叠加在检索之上、不替代检索"在工程上的含义。
- **每个节点要带一份足以决定"要不要往下走"的摘要**：逐步认识的过程中，先验来自常驻索引与当前上下文，每展开一个节点、看到其子节点的摘要相当于一次观测，据此判断答案更可能在哪个分支。摘要笼统时 agent 只能逐个打开，渐进就退化成遍历，所以维护这张图最要紧的产出是节点摘要的质量，与原子 Index 层的作用相同，只是在更高的层级。
- **节点由谁建立**：层次聚类得到的簇没有名字，重新聚类后身份会变，无法被稳定地引用与链接；聚类只用来提出候选，由馆长（第 6.1 节）命名、建立、合并与拆分节点，人工制定的节点作为不被自动改动的锚点。
- **节点身份要稳定**：主题被合并或拆分后，指向它的链接不能断；现有记忆合并后旧 alias 会改指到新记忆（读取时的 redirect），主题节点可以沿用同样的思路。
- **图搜索由谁来走**：导航时让 agent 或馆长自己顺着边走（Perplexity 与 Anthropic 都是如此，agent 拿着入口索引自己决定下一步）；扩散激活或个性化 PageRank 这类算法只在检索出的候选内重排，不决定召回（第 5.2 节）。两者可以并存。
- **不需要图数据库**：个人规模下，图是一种数据模型，可以用 sqlite 的节点表与边表存放、用递归查询遍历，并与第 5.2 节的记录系统同库、按事务一起提交；单独的图数据库引擎会多出一个需要保持一致的真相源。这是"数据库的设计哲学适用于记忆库"的直接应用。
- **入口是一份常驻的小索引**：列出顶层主题与最近的几段经历，在会话开始时注入，补上日常路径"什么都不注入"的缺口（第 2.4 节）。
- **嵌套图 v0.8 不做，但不堵死**：两层结构（常驻索引 → 主题页或经历节点 → 原子）就是只展开一层的嵌套图。只要节点能引用节点、节点的摘要与子集合分开存放，以后往下嵌套就只是在节点下多挂一层，不需要改数据形态；按 AGENTS.md 第 1.1 节，v0.8 不为嵌套预留任何多余的类型或配置。
- **一个提醒**：VISION 把"以复杂知识图谱或新算法替代尚未跑通的基本检索闭环"列为要避免的事；两篇文章的数据也表明 wiki 加搜索最好，单独 wiki 不如单独搜索（第 8.4、8.5 节）。所以高层图是另一条入口：检索负责"我知道要找什么"，图负责"我只有一个模糊的想法"。

**推进顺序（分析）**：接在 v0.8 第一份切片（复核，第 3.1 节）之后，先把话题保留为经历节点并挂上记忆，再由馆长建立主题节点，最后加入常驻索引，每一步都可以单独验收。

### 4.3 时空图索引在设计中的定位（候选设计，不是 owner 决定）

第 9.1 节的决定（存储平铺，分层由派生索引承担）之下的展开。

**它替换的不是向量索引，而是"相似度检索是唯一入口"**。现在的 Qdrant 同时是真相、唯一的访问路径与写入时查重的依据；图索引与记录系统（第 5.2 节）到位之后，Qdrant 收缩为一个从真相派生、可以重建的相似度引擎，仍不可缺少：

1. "我知道要找什么"的直接检索：两篇文章的数据都表明单用 wiki 不如单用搜索、wiki 加搜索最好（第 8.4、8.5 节），检索仍是另一个入口，也是索引漏掉时的兜底。
2. 从模糊的想法落到图上的第一步：节点摘要本身也向量化后，一个模糊的问题先经向量检索落到几个起始节点，再顺着图往下走；相似度检索成为进入图的入口，而不是整条访问路径。
3. 建图与写入判断时的候选生成：新记忆该挂到哪个主题、哪些记忆语义相近却没有被链接，都靠相似度先给候选，补上索引的盲区，也为"聚类只提出候选"（第 4.2 节）提供原料。
4. 按名字与关键词精确匹配：项目名、组件名这类专有名词由稀疏向量负责，光靠图导航找不准。

在个人规模下还要不要为它单独运行一个服务，是[轻量化 Idea](./lightweight-footprint.md)中"更轻的嵌入方案与嵌入式存储"的问题，属于资源层面的独立决定。

**分层的位置**：

| 层 | 内容 | 谁写 |
|:---|:---|:---|
| 真相 | 记忆原子、Artifact 中的证据、断定边（取代、矛盾，第 4.4 节） | 唯一写入者 |
| 派生索引 | 相似度索引（Qdrant）；时空图索引（节点、归属边、节点摘要） | 由真相派生，可以重建；馆长维护 |
| 交付 | 常驻的小索引、检索结果、导航路径 | 按需组合 |

**原始证据的角色：用来对质，不是用来检索的知识库（分析，2026-11-15）**：把会话记录当知识库、用常规的 RAG 检索，噪声大、token 低效（第 1.2 节）；承担"用"的是维护过的关系索引与提炼过的记忆。原始层的角色因此是事实的底座：核实一条结论、按轨迹纠错（Anthropic 的 dreaming）、在结论冲突时作为裁决依据，以及审计。"锁定设计"的案例（第 8.6 节）正是靠回到原始记录才发现的。图索引负责导航、记忆原子承载知识、原始证据负责对质，三者各司其职，不互相替代。

时空图索引是一种访问结构，不是存储、不是真相，也不是写入者。它服务三类使用者：读者（从模糊的想法逐步走到具体的记忆）；写入时的判断（复核或馆长用它找到相关的记忆，决定新内容挂在哪里）；维护（节点就是一致性检查的作用域，按节点标脏，在节点内外检测冲突）。正因为它只是派生的访问结构，它可以参与写入判断，而不会让存储的形状重新绑住写入。

**索引参与写入后，第 4.1 节的限制怎样变化**：

| 第 4.1 节的限制 | 现在 |
|:---|:---|
| 第 4 点："该放在哪、库里已经知道什么"只能由全库相似度回答 | 解除：馆长顺着索引找到相关的主题与记忆，第 3.1 节复核最弱的一环由此补强 |
| 第 5 点：状态类信息没有固定的位置 | 基本解除：主题节点就是固定位置，它的摘要指向"当前状态"那条记忆，记忆被修订时节点随之更新 |
| 第 2、3 点：每条记忆自带项目上下文，同项目的记忆在索引层相近，查重分不清 | 减弱但没有消失：检索仍单条返回记忆，记忆的索引层仍要能被单独找到；但读取时索引可以补上"属于哪个主题"的路径，写入判断依据索引与复核而不是相似度阈值，"同项目相近"不再直接导致误合并 |

**索引参与写入时的三点注意**：
1. 只用它找候选，不作为判断依据：派生的东西可能过时或出错；馆长用它找候选，下判断时读记忆原子与证据；检索保留为第二个入口，补上索引漏掉的部分。这与第 5.2 节"额外的信号只在候选内重排"是同一条规则。
2. 先确认节点是新鲜的：写入判断用到某个节点之前检查它的水位（VCP 的"按作用域标脏、查询时修复"），过时就当场修复或退回检索。
3. 防止索引的错误自我强化：写入更新索引，索引又引导写入，一条记忆挂到错误的主题下，后来相关的记忆就可能被继续引到错的地方。缓解：人工制定的节点作为不被自动改动的锚点；维护一侧定期把索引与"从原子完整重建的结果"对比，检查漂移（Perplexity 在上一版上增量更新，VCP 的快照是数据的纯函数可以重建对照，两者各取一半）。

### 4.4 关系层：关系保留，但存成关联表，不挂在原子上

**三种关系的去向**：

| 现在的字段 | 原本想表达的 | 在时空图索引下 |
|:---|:---|:---|
| `relates_to` | 两条记忆相关 | 上移到图索引：两条记忆挂在同一个主题节点下就表达了"相关"，主题之间的横向边负责导航；它是派生的，不该存在原子上 |
| `depends_on` | 一条依赖另一条 | 大多也上移，例如"某个项目依赖某个组件"是主题之间的边；原子之间的依赖（某个操作流程依赖某条配置事实）较少见，遇到再加 |
| `supersedes` | 新的取代旧的 | 留在原子一级，并会是关系的第一个真正用途：维护时检测冲突，检索时给被取代的记忆降权，读取时提示"已被 Y 取代"；以后的"互相矛盾"也属于这一类 |

原子之间真正需要的边只剩"取代"与"矛盾"这类与记忆演化有关的关系，导航用的边都在高层（第 4.2 节）。合并已经以另一种形式记录了取代（第 2.2 节）；真正没有落脚处的是"不合并，但旧状态已经过时"的取代，两条记忆都保留，其中一条已不再成立，这正是 `supersedes` 边第一次有用武之地的地方。

**为什么不挂在原子上**：
1. 方向单一：数组只能从新记忆查到旧记忆，"X 有没有被取代"要反向扫描整个库；关联表可以在两个方向上建索引。
2. 改关系就要改内容：关系层不在可局部更新的字段中，改一次关系就是整条记忆的内容提交并生成版本；而关系的变化大多来自维护或索引重建，不该让原子的内容版本跟着变。
3. 边需要自己的属性：一条取代边要记下谁断定的（agent、馆长还是用户）、依据哪段证据、什么时候、现在是否有效，这与记忆本身"可追溯"是同一个原则；只放 ID 的数组装不下。

这正是 owner 所说"关系型数据库的设计哲学适用于记忆库"（第 1.2 节）：用关联表，而不是数组字段。

**边分成两种真相等级**：
- **索引边**：派生的，可以重建。主题与经历到原子的归属与引用边、主题之间的上下文边都属于图索引，坏了或过时了由馆长重建，适用第 5.2 节"派生物可丢弃"。
- **断定边**：属于真相，不能重建。取代与矛盾是馆长、agent 或用户作出的判断，与记忆一样需要来源与审计，不能清空后重算；当它与某次修订或合并出自同一个决定时，与相关的原子写入在同一个事务中提交（第 5.2 节的记录系统）。

这也让第 7 节的边界更清楚：索引边主要由整理时的复核与馆长维护，断定边主要是生命周期维护的产物。

**现在怎么处理这个字段**：按 AGENTS.md 第 1.1 节，没有生产使用方的字段本不该存在，它是删除的候选；但删除会牵动 Qdrant 中的 payload 与版本快照的必备字段，属于契约变更。比较合理的是：关联表引入之前不在这个字段上构建任何东西；记录系统与关联表落地时，在同一次改动里删掉它。[Memory-Centric TDA Idea](./TDA_Memory_Centric_Agent_Ideas.md) 设想的原子级记忆图不因此失去基础：有了关联表与图索引，原子级的图随时可以派生出来用于分析，不必存在原子身上。

## 5. 存储与保存形态

### 5.1 保存形态：差别在系统维护的部分，不在内容格式

- 第 2.3 节中有使用方的非文本部分，都可以放在 md 旁边：EverOS 就是 md 作为真相、系统状态另存于 SQLite。所以 md 与记忆原子之间真正的取舍，在于谁能修改内容、系统怎样知道内容被改了，以及谁维护内容之外的状态。
- 这正是"锁死生成链路"的两面。锁住的好处是每次改动都有版本、来源与理由，合并与缓存失效的正确性有保证；md 的好处是任何工具都能直接修改。两者冲突：只要允许直接修改文件，就多了一个绕过唯一写入者的写入方，系统要么事后发现并补齐这些改动（EverOS 按内容哈希重建索引），要么放弃对每次改动的保证。也可以只换载体、写入仍经唯一写入者，但那样拿不到"普通文件编辑就够了"的好处。
- 文本做不到的，是必须由系统维护和保证、不能靠编辑者手写的东西：
  - 由使用产生的状态：写进文本，每次读取都成了一次编辑。现在已经实现。
  - 带类型、由系统在任一端变化时维护的关系：例如一条记忆被取代后，旧的一条自动降权。文本中的链接没有类型，内容一改就悄悄失效。对应 Hindsight 的"重复、改变、终止"判定与 SME 的取代链。现在只是预留字段。
  - 验证状态：确认过、已过时，还是被证明是幻觉。现在有字段、有显示，但没有写入方。
  - 不会漂移的证据：链接只是指向一个文件，Artifact 是冻结的快照。这一点的差别在于保证，不在格式本身。

  最可能让记忆原子超越文本的几项，恰好都是现在没有写入方的那几项。
- 保存形态与第 9.1 节、第 4.1 节绑在一起：选择文件作为载体，几乎就带来了目录（即分层）与常驻的索引文件（`MEMORY.md`、`USER.md` 正是用户偏好常驻的做法）。

### 5.2 索引不是真相（受 VCP 存储层启发）

- **第 9.3 节有了一个真实样本。** VCPToolBox 完整实现了"文件为真相、允许直接编辑"（第 8.2 节），它为此付出的代价就是这个选项的真实代价：每个路径的代际号、等文件稳定后再读、提交前复核、按文件版本 CAS、为重命名准备的向量回收站、墓碑与全量对账，做完这些也只换来最终一致，并且只能单进程。它的文件主要由日记插件写入，人直接改文件是被容忍的，不是主路径。
- **"索引不是真相"可能比"md 还是记忆原子"更根本。** 如果 v0.8 重新安排存储，可以让一个有事务的记录系统（sqlite 一类）保存内容与全部系统状态（生命周期、关系、验证状态、版本），Qdrant 降级为可以从它重建的索引：
  - 换嵌入模型、Qdrant 损坏或升级，都只需要重建索引；
  - 中期到长期的归档可以变成"移出检索索引"，而不是跨存储搬运，第 2.3 节中 archive 与 revive 不是事务的问题随之消失；MemoryLibrary 文档对长期层的定位本来就是"让低活跃记忆可以退出高成本索引"；
  - 记忆原子与 Artifact 的提交可以进同一个事务，或者用 outbox 衔接。

  这不改变长期层的概念与它自己的维护规则（第 1.1 节），只是物理存放的选择；owner 计划用 sqlite 存放长期层，它正好可以是同一个记录系统。
- **v0.8 可能新增的派生层，都可以套用"同一事务标脏、查询时修复"。** 常驻的分组描述（第 3.4 节）、用户偏好文档（第 4.1 节）、跨经历归纳出的知识（第 3.4 节），都是从记忆派生、可以重建的东西。它们落后于事实时，用 VCP 的新鲜度水位就能保证不读到过期内容，不需要可靠的事件投递。LLM 生成的派生物做不到逐位相同，但"输入签名不变就不重建"仍然适用。
- **复杂度上的教训。** VCP 的维护者拒绝了 MVCC 加不可变 segment 的分代索引方案，理由是 ANN 本来就不是真相，那套机制都是多余的。先让派生物可以丢弃，一致性机制就可以很简单。
- **额外的信号只在候选内重排，不改变召回。** VCP 的 Tag 图信号在一年里权限一再收紧：早期用图改写查询向量、直接决定召回谁，现在召回只用原始查询，图只能在 ANN 选出的候选内加一个上限约 0.21 的分。每次收紧都有记录在案的理由，例如弱的图证据把第 30 名推到第 1 名、大量真实查询整体退回 KNN。HiveMemory 今后加入关系、分组或使用状态等新信号时，可以守这一条。

## 6. Patchouli 的角色

### 6.1 Patchouli 作为馆长

- **价值判定的位置**：停用外部价值标记的根本理由，是判断"值不值得记"需要知道库里已经有什么；外部评判者看不到库，只能判断"像不像有价值"。现在缺的不是信息，而是没有把信息放到做判断的地方（第 2.1 节）。
- **馆长 agent 是第 3.1 节的执行形式，不是另一个方向**。两个实际的好处：
  1. 它补的正是第 3.1 节最弱的一环：找出相关的旧记忆本质上是探索问题，一次性调用只能拿到相似度的前几条，agent 可以换说法反复检索，顺着版本与来源 Artifact 往回查，也能去冷藏库里看。
  2. 隔离让第 9.1 节可以单独决定：外部 agent 只表达"我想保存这个"，不需要知道库是平铺还是分层，外部 harness 的四个工具可以不变，库的形状成为馆长一个人的事。

  跨经历的归纳、补知识缺口、决定归档什么，以后也都适合交给它。调研中最接近的先例是 VCPToolBox 的"记忆大师"：普通 agent 用专门的提示词列日记、读候选、自己写合并稿，但没有唯一写入者，没有审计，只能手动触发。
- **边界：自由放在读的一侧，写的一侧保持收紧**：
  1. 写入仍是结构化判定（保持；修订某一部分并给出依据；新建；提议归档），由 MemoryGenerationFamiliar 落地，修订连同依据记入版本；不给自由重写或删除的能力。
  2. 提示词注入的风险放大：材料中有不可信内容，而馆长拥有全库最高权限。只允许修改本次运行读过并能给出依据的记忆，不提供删除，所有修改都能经版本回退。
  3. 读的权限最高，写要守可见范围：不能把 PRIVATE 的内容带进 PUBLIC 记忆，延续"策略不同的记忆不合并"。
  4. 成本与并发：每次结算一个 agent 运行，开销是一次性调用的数倍，运行越长同改一条记忆的冲突越多；最简单的是每个 Workspace 同一时间只跑一个馆长，并设步数与 token 预算。
  5. 所有权边界：`agent_runtime` 属于 Alice 子系统，工具又是 MTP，而记忆操作的能力在 actor API，馆长的工具应是 Patchouli 内部的操作。可选：Patchouli 自带一个小的工具循环（多一个循环概念）；把通用循环内核下沉一层共用；让馆长作为 Alice 的 frame 运行（等于让 Alice 持有记忆库的写入者，与 Patchouli 是权威冲突）。这是架构层面的决定，大概需要一份 ADR。
- **推进顺序**：第一步用固定流程实现复核（取本轮动过的记忆与相关记忆，一次判断，输出结构化判定），相当于探索步骤写死的馆长；第二步只放开读的一侧，让馆长自己决定还要查什么（检索中期库与冷藏库、读版本与 Artifact，有步数上限），写的一侧沿用第一步的判定格式与审计。第一步因此也是评估第二步的基线：多探索几步是否把相关记忆找得更准。

### 6.2 保存来源与 Patchouli 的能力分级

- **保存来源必须针对当时看到的那一份**：附件存储重启即清空，网页之后会变，事后联网抓取得到的已不是 agent 当时看到的内容。结算时这些内容通常还在：附件还在附件存储里，网页内容已在交互 Artifact 里。缺的是判断：这一轮的哪些记忆依赖了哪些来源、值不值得单独保存、具体哪一部分支撑了结论（以引文或行号定位）。这正是馆长的工作，只需要读与结构化写，不需要联网。
- 它顺带补上几个缺口：外部来源的 DocumentArtifact 加定位符，是"同一份证据只算一次"所需证据身份的一部分；第 5.1 节"不会漂移的证据"对文档现在并不成立，因为没有快照；验证状态没有写入方，馆长可以先根据轨迹中的证据写它（例如后来的工具结果表明修复没有生效）。
- 有的 harness 的网页工具返回的是按提问处理过的内容，不是原页面，所以能从轨迹中保存的是"agent 看到的那一份"。这对记忆恰恰是对的：记忆依据的就是 agent 当时看到的东西。
- **查证是另一种能力**：联网追查、运行沙盒工具，服务于检查一条记忆现在是否仍成立或寻找规范出处。风险大得多：后台 agent 会根据私人记忆自己拟查询发往外部服务（隐私）；网页内容进入一个能改全库的写入者（注入）；馆长运行沙盒工具就成了工具宿主（第 6.3 节）。
- **分三级分别决定**：

  | 级别 | 能力 | 依赖 |
  |:---|:---|:---|
  | 1 | 读全部三层库、读轨迹与 Artifact，结构化写（复核、修订、新建） | 第一步的固定流程甚至不需要循环 |
  | 2 | 保存来源：把轨迹中已有的内容存成带快照的 DocumentArtifact，以定位符挂到记忆上 | 同上，没有外部访问 |
  | 3 | 查证：联网、沙盒 | 成熟的 agent 循环，以及隐私与注入的策略 |

- **agent_runtime 的改造不必挡在 v0.8 前面**：前两级用不到并发工具调用、原生工具调用协议与沙盒，馆长的工具是内部读取操作、输出是结构化判定，很简单的循环就够；只有第 3 级需要成熟的通用循环。改造的方向正是把循环与 MTP 解耦，之后下沉一层供 Alice 与 Patchouli 共用，可以作为并行的主线。

### 6.3 知识与工具：按由谁消费来划界

- **知识由模型的推理消费**，改变的是 agent 怎样决定；**工具由环境执行**，改变外部世界或带回观察。修自行车的 skill 文档是知识，配套的脚本才是扳手。
- 记忆库中像工具的成员，恰好是需要特殊路径或例外的那几个；日常使用的主路径（外部 harness 经 MCP）只开放四个记忆操作（第 2.4 节）。
- "记忆作为工具"有三种解读，目标各不相同：
  1. 记忆操作本身是 agent 的工具：检索、读取、写入、修正。这是 VISION 第 5.2 节的原意，现在已经成立。
  2. 关于工具的知识：哪个版本可用、怎样失败过、根因是什么，扳手留在插件里，记忆保存对它的引用与使用经验。被动提取把出错的工具结果当作修复经验的依据，是这个方向的雏形。
  3. 记忆本身被执行（RUN）：HiveMemory 成为工具的宿主，要与 harness 和插件在沙箱与环境上竞争，而它在这些方面没有优势。MaaT Idea 第 5 节列的可信、可复现、溯源、复用四个轴，在知识不等于工具的视角下更像工具宿主应有的性质，未必是记忆系统的。
- 同一个视角也许能解开 agent profile 的问题：把它拆成定义（模型、配置、提示词，是工具性的配置，不进入记忆的维护）与关于这个 agent 的知识（擅长什么、哪些任务做得好或做砸了）。后者是真正的记忆，可以被生成、合并与维护，也能帮助选择委托给谁。这只是让 profile 享受维护好处的一种实现方式。
- owner 于 2026-11-15 明确：AGENT_PROFILE 的"可运行"只是能被 CALL 调用，与 RUN 执行记忆性质不同，可运行的轴不延伸到它（第 9.6 节）。按 MTP 契约，CALL 是委派：被调用方须在本 Workspace 有准入，子 frame 以被调用方的身份和操作集合运行，Profile 只提供 persona、模型与语言；两者相同的只有"按 alias 精确解析"，那是寻址方式。上面的拆分仍是候选，理由是定义要稳定、精确，而关于 agent 的知识会演化，与可运行无关。
- owner 随后决定把定义一半（图纸）移出中期记忆库，单独成一个 store（第 9.6 节）；关于 agent 的知识一半仍是候选。

## 7. 整理写入与生命周期维护的边界

按 owner 的划分（第 1.2 节），用三个问题区分：

| | 整理与写入 | 生命周期维护 |
|:---|:---|:---|
| 由什么触发 | 新材料：一次结算或一次主动写入 | 时间、使用情况与库的状态，与有没有新材料无关 |
| 看哪些记忆 | 这份材料直接牵涉到的记忆：本轮动过的，以及与它相关的 | 整个库，包括从未在同一份材料里出现过的记忆 |
| 回答什么 | 这段新经历是否改变了库 | 库本身是否仍然一致、好用 |
| 典型动作 | 复核、修订、新建，或什么都不改 | 冲突检测，记忆的分裂与合并，对照轨迹纠错，过时检查，维护分组、索引等组织方式，归档 |

第 3.1 节的保守规则正好是分界线：对象明确、变化明确的改动留在写入时；两条内容仅仅相关的情况交给维护。由此推出三点：

1. **重叠是暂时的，并且印证了"写入决定维护的难度"。** 现在看起来重叠，是因为写入时缺少复核，质量的负担全压在落库之后：先新建，再由查重提名合并。写入时的复核做好之后，"改哪条还是新建"在落库前就已决定，写入时的查重与合并基本退场；剩下的合并是旧记忆之间随时间变得相近，属于纯粹的维护。
2. **分属的是由谁决定，写入者仍只有一个。** 维护作出的分裂、合并与纠错，都经 MemoryGenerationFamiliar 提交，才有版本与来源；拆开的是决策方与触发方式，不是写入通道，否则就多了一个并行的写入者。馆长（第 6.1 节）可以同时承担两种角色，只是被不同的事件唤醒。
3. **写入时要为维护留好接口**：证据可以定位到轮次或事件（第 3.1 节质疑 3）；修订是局部修改而不是整篇重写（质疑 2）；验证状态有写入方（第 2.3 节）。维护对照轨迹纠错、检测冲突，都依赖这三点。

## 8. 外部调研的参考

### 8.1 八个项目的两类写入路径与保存形态

依据是 DeeperResearch 工作区（不在本仓库）中八个项目的调研报告：mem0、Hindsight、EverOS、spatial-memory-engine（SME）、BaiShou-Next、VCPToolBox、dsh-agent-soul、gliding_horse。2026-11-14 按"谁决定记什么内容"重新整理。结论来自报告，不是各项目的源码；mem0 的命令行与集成、EverOS 的 MCP 适配器、Hindsight 的集成不在报告范围内，下表中的"没有"只表示报告里没有看到。

**归类**

分类的界线是谁决定内容，不是谁发起调用：Hindsight 的 `retain` 可以由 agent 经 MCP 或 hook 调用，但记什么由服务端的提取决定，仍归为被动。

| 项目 | 被动提取 | 主动写入 |
|:---|:---|:---|
| mem0 | `add()`：LLM 从对话中抽出事实句 | 没有 |
| Hindsight | `retain`：服务端 LLM 分块抽取事实 | 没有单独的通道 |
| EverOS | `/add`：LLM 判断边界切出 memcell，再产出 episode 与 agent case | 没有 |
| SME | 模块 01（默认关闭）：逐条消息抽取原子事实 | 没有 |
| BaiShou-Next | 没有 | 日记技能、`memory_store`、`graph_upsert` |
| VCPToolBox | 只记录原始发言，不产生可检索的记忆 | DailyNote 写日记、整理日记 |
| dsh-agent-soul | 压缩上下文时产出指回原文的摘要 | 账本 |
| gliding_horse | 每轮机械归档，不做取舍 | `create_skill`，没有接通 |

gliding_horse 与 dsh-agent-soul 的被动路径不判断值不值得记，下面的被动类只指前四个项目。

**被动提取类（mem0、Hindsight、EverOS、SME）**

- **共同点**：
  - 产出单位都很小：mem0 是 15～80 词的自包含事实句；Hindsight 是一句"什么 | 何时 | 何地 | 涉及谁 | 为什么"；SME 与 EverOS 是原子事实。
  - 都标出记忆来自哪一方：mem0 的 `attributed_to`，Hindsight 的 world 与 experience，EverOS 的用户轨与 agent 轨，SME 的 `source`。
  - 提取时只追加，基本不处理与已有记忆的关系：mem0 只按 md5 精确去重（它曾在写入时让 LLM 裁决增删改，后来改为只新增）；Hindsight 与 EverOS 写入时不查重；SME 只有余弦相似度 ≥0.92 就丢弃的规则。与已有记忆的协调推迟到后台（Hindsight 的 consolidation、EverOS 的 reflection、SME 的 consolidate），或者不做（mem0 开源版）。
- **差异**：
  - 提取哪一方：SME 只记用户的话，避免把模型自己说的再记回来；mem0 两方都抽，产出同一种事实；Hindsight 两方都收但分成两种事实（用户的偏好、规则与纠正是 world，agent 的动作与决定是 experience）；EverOS 两方分成两种产物（每个用户各一条 episode；agent case 从助手消息与工具调用中产出，先经过筛选）。
  - 怎样切分材料：SME 逐条消息；mem0 每次调用；Hindsight 每次调用再按约 3000 字符分块；EverOS 让模型判断最后一段是否讲完，没讲完就留在缓冲里，并且明确不按 token 数或时间收尾。
  - 提取时看不看已有记忆：mem0 看向量最相似的 10 条；Hindsight 不看，到 consolidation 才看相近的 observation。
  - 取舍标准：Hindsight 问两次，时间尺度不同（提取时"六个月后还值得回忆吗"，沉淀时"一个月后还值得知道吗"）；mem0 拿不准就抽；SME 用规则丢掉情绪、短句与闲聊；EverOS 的 episode 不设门槛。
  - 原文证据：Hindsight 与 EverOS 保留原文并挂指针；mem0 的记忆没有证据链接。

**主动写入类（VCPToolBox、BaiShou-Next、dsh-agent-soul）**

- **共同点**：
  - 取舍规则写在给 agent 的说明或技能里，不在处理流程里：VCPToolBox 的日记说明书要求"一事一记"；BaiShou-Next 的日记技能只追加日记里还没有的事实，并用"半年后还重要吗"决定详略；dsh-agent-soul 的账本规定了八种类型。
  - 写入只追加，写入时基本不检查。例外是 BaiShou-Next 的 `memory_store`：相似度大于 0.92 直接跳过，在 0.70～0.92 之间由对话模型判断跳过、合并还是新建，合并时给旧条目留墓碑、另写一条新的。
  - 避免重复主要靠写的人自己看得到相关的已有记忆：VCPToolBox 每轮把已有日记注入上下文；BaiShou-Next 写日记前先读当天的日记。
  - 作者署名由写的人自己填，没有验证。
  - 之后的整理也交给 agent 或人；系统自动的加工只有 BaiShou-Next 从日记抽取关系图，输入是日记而不是对话。
- **差异**：
  - 谁决定什么时候写：VCPToolBox 由 agent 自己决定，没人看着的定时请求里也会写；BaiShou-Next 由用户要求，应用内的写入需要用户确认，对外的 MCP 则自动放行。
  - 产出单位：VCPToolBox 是一篇日记一个文件；BaiShou-Next 是按发生时间插进日记的段落，或单行记忆、图谱的边；dsh-agent-soul 是一行带类型的账本条目。
  - 类型：dsh-agent-soul 有八种，其中"搁置""承诺""线索"表示工作状态；VCPToolBox 只有 Tag。
  - 状态怎样改变：VCPToolBox 可以替换文中的一段；BaiShou-Next 从不改旧文；dsh-agent-soul 没有"关闭"类型，未完成的条目只增不减，它的文档自己承认这是缺陷。
  - 内容取向：BaiShou-Next 的技能偏生活与关系，原话、态度与情绪写详细，代码改动只写一两句结论；dsh-agent-soul 的账本类型偏工作。

**两类之间**

- "用户说的"与"agent 做的"是在每条路径内部区分的，不是两条路径各管一方：被动类里 Hindsight 与 EverOS 从同一次提取中分出两方的产物；主动类里 BaiShou-Next 的伙伴写日记，记下的主要是用户的原话与态度。
- 只有 dsh-agent-soul 同时有两类路径：压缩摘要进入索引，账本单独存放，两者写入时互不可见，只在读取时合并、标注来源，冲突时以原文为准。没有一个项目在写入时协调两类路径。
- 结构多出现在派生层：Hindsight 的 observation 按"单主体、单侧面"组织，另有 mental model 文档；EverOS 给每个用户合成一份 `user.md`，技能写成 `SKILL.md`。用户偏好单独成层的有 EverOS（`user.md`）、dsh-agent-soul（`USER.md` 与 `SELF.md`）与 BaiShou-Next（手写的身份卡）；mem0 开源版是反例，偏好与其他事实一样平铺。

**保存形态**

- **以文本文件为真相**：EverOS（Markdown 是唯一真相，系统状态存于 SQLite，检索索引可以整份重建，用户手改文件后按内容哈希重建索引）；BaiShou-Next（主记忆是日记 md）；VCPToolBox（一篇日记一个 txt 文件）；dsh-agent-soul（`SELF.md`、`USER.md`、账本与会话日志）。主动写入类都在这一组。
- **以数据库记录保存**：mem0、Hindsight、SME、gliding_horse，但单位只是一句文本加元数据，并不比文本更丰富。
- 八个项目中没有一个定义了比文本更丰富的内容格式。
- Claude Code 的原生记忆（不来自调研报告，来自它自身的记忆机制）：每条记忆一个 md 文件，frontmatter 有名称、一句描述与 user、feedback、project、reference 四种类型之一，正文之间用 `[[名称]]` 链接；`MEMORY.md` 是索引，一行一条指针，每次会话载入它的开头部分（前 200 行或 25 KB 以内，见第 8.4 节），具体文件用到时才读。写入用普通的写文件工具，写之前由 agent 自己检查有没有已经覆盖它的文件，另有整理技能合并重复、修正过时的内容；系统不记录使用状态。

### 8.2 VCPToolBox 的 Rust 记忆运行时

VCPToolBox 是 owner 一年前开始做 HiveMemory 的启蒙，它的 Rust 记忆运行时（`rust-vexus-lite`）是该项目最扎实的部分（owner，2026-11-14）。依据是 DeeperResearch 工作区中的 VCPToolBox 第 2 轮调研（基线 `73fd165`，调研者在本机跑通了全部单元测试），不是源码通读。

- **三层真相**：日记文本文件是内容的真相，人可以直接编辑；SQLite 是向量与全部派生资产的记录系统，损坏时隔离旧库、从文件重新灌入；ANN 图、磁盘快照与 Memo 产物都是可以丢弃的缓存，随时从 SQLite 重建。ANN 在恢复后主动释放原始向量，精排一律回 SQLite 读原值，所以索引陈旧只损失一点召回，不会返回错误内容。
- **五个机制**：
  1. 单写者：进程里只有一个 SQLite 写线程，一条命令一个事务，所有事实提交持有全局排他闸门；起因是早先多连接写入导致库损坏。
  2. 文件到 SQLite 只求最终一致：不追求跨介质原子性，用代际号、稳定采样、提交前复核与按文件版本 CAS 挡住常见竞态，再用全量对账兜底；embedding 的网络调用放在事务之外。
  3. 新鲜度水位：把"派生索引落后于事实"与事实写在同一个事务里（标为 invalid，记下已提交水位），事务后应用增量、成功后用 CAS 置为 ready；查询时发现没有 ready，就当场从 SQLite 重建。即物化视图的已提交水位与已应用水位，加查询时修复。
  4. 快照的提交点在数据库事务里：写全新的不可变文件，rename 进非活动槽，再在带版本 CAS 的 SQL 事务里写背书，这一刻才算提交；恢复只认背书过的槽，再按 SQLite 补齐差量；删除文件之类的磁盘副作用记在事务性 outbox 中，重启后幂等重试。
  5. 近似只找候选，精度留给裁决：每维 2 位的量化图只产出约 128 个候选，精确余弦、近重复去重与重排都读原始向量，并在同一个冻结的读事务里完成。
- **两个小设计**：加载原生模块时做能力握手，能力字符串、ABI 版本或向量维度不匹配就拒绝启动；schema 迁移只做加法，遇到比自己新的 schema 就拒绝启动。
- **代价**：只能单进程；入库提交期间所有查询都要等；写线程 panic 之后再也写不进去，只能重启；查询不能取消；文档与实现漂移严重。

### 8.3 VCPToolBox 的 OneRing 与一份社区讨论稿

依据是 2026-11-14 对 VCPToolBox 源码（基线 `73fd165`，之后主分支对 OneRing 没有改动）的只读核实，关键处已经抽查。

- **是什么**：主服务进程中的一个消息预处理器。每个 Agent 一个本地 SQLite 账本（`data/{Agent}.db`），消息表只有角色、发送者、前端名、正文与时间，没有会话 ID，也没有消息 ID；每次插入后只保留最近 100 条，其余直接删除。
- **默认只记录、不补齐**：`ONERING_RECORD_ONLY` 默认为 true，要在配置中关掉才会补齐。
- **写入**：每次请求只把最后一条真实的用户消息入库；AI 回复要等整轮成功、HTTP 发送完毕才写入，只写可见正文，推理与工具结果不写；写入失败不重试，也没有锁。
- **补齐**：只在客户端带来的对话块少于 10 块时触发；从这个 Agent 最近 30 条中，按 hash 挑出本次请求里没有的，补到 10 块；只插进时间戳可信的缝隙，晚于最后一块的丢弃；每条加 `[OneRing通知:X于T发送于F]` 标明来源。上下文的主体仍是客户端自带的历史。
- **"分布式"** 指的是多个前端连同一台服务器，没有任何网络同步代码。
- **OneRingMemo**：用 LLM 把账本里近 3 天的消息压缩成一段客观时间线，注入系统提示词；手动触发，自动生成默认关闭；每次全量重算并覆盖旧结果。
- **与记忆系统的关系**：账本不进入日记，也不进入检索；VCP 自己的文档称它是"短期连续性，不替代永久记忆"。
- **宣称与实现之差**：VCP.md 宣称标注消息来自哪个会话、编辑作为新事件追加进统一时间线、旧消息"像推币机一样"不会无意义丢失、按 fuzzy diff 比对；实际上没有会话字段，编辑是原地覆写、时间不变、不留历史，超过 100 条就删除，fuzzy diff 的函数没有调用方。

**一份 VCP 社区讨论稿**

一份 2026-07-03 的社区讨论稿设想把一个"个体"拆成多个子 Agent：每个子 Agent 只负责一个领域，有自己的记忆分区与小上下文，由一个汇总者整合它们上报的结论。其中的术语多是 VCP 检索机制的比喻（第 3 轮调研：Tag 图实际是余弦召回加 Agent 自写 Tag 的共现图，图信号只做有上限的加分），引用的代码位置也早于 VCP 的 Rust 化，因此不作为依据。与本文直接相关的内核已经并入第 3.4、4.1、5.2 节：按领域分区让检索信号更可靠；记录使用方实际采纳了哪些检索结果；从检索命中的稀疏程度发现知识缺口；额外的信号只在候选内重排。

### 8.4 Anthropic：The components of agent memory（2026-11-06）

Anthropic 工程团队的文章（[原文](https://www.anthropic.com/research/components-of-agent-memory)），2026-11-15 阅读。它把 agent 记忆定义为从经历中得到、跨会话保留、以可读上下文保存的知识，不含权重变化、单次对话内的学习与上下文压缩；主线是两种时机的分工：会话中由 agent 判断重要性并写笔记，离线时（文中称 dreaming，思路来自 Letta 与 UC Berkeley 的 sleep-time compute）回看日志与轨迹，修正、补充、重组与提升已有笔记。按第 7 节的划分，这里只记写入一侧的要点；离线维护的要点记在[生命力分数长期演进](./VitalityScoringLongTermEvolutionIdeas.md)方向 6。

- **记忆是一种预测**：写下规则，是预测这个模式还会用到；写下验证过的事实，是预测以后的 agent 可以直接依赖、不必再查。在 CL-Bench 的数据库题上，几代模型的差别在于能否闭合学习回路：较早的模型只留下零散、未验证的猜测；之后的模型开始标出已确认与未确认、答错时写更正；Opus 5 起，每条笔记写明规则本身、怎么知道它成立，以及踩过的坑。
- **判断什么值得记**：在 Pokémon 实验中，Sonnet 3.7 什么都记（约一万步时 413 个文件、225 个文件夹，1 枚徽章），记录随游戏状态持续过时，翻找记忆还挤占了行动；Fable 5 只写 9 个文件加一个当仪表盘用的 `global.md`（当前目标、计划、自己的记忆规则），拿到 4 枚徽章。分界是：环境每一轮都会重新告诉你的（金钱、位置）不记；只有自己推出来、不写就会消失的（策略、计划、验证过的规则）才记。
- **只说明记忆的用途，不规定写法**：给强模型加上"只记失败"这类固定规则，记忆带来的收益大幅下降；引导对旧模型帮助最大（提示 Sonnet 4.6 先读记忆、再验证猜测，分数几乎翻倍）。对前沿模型，他们只给简单的指引：用户要求时，或者明显值得记时再写。
- **常驻的顶层要小**：顶层在每次会话开始时预先加载，占用 token，错误的笔记会带进每一次会话，指令越长越不容易被遵守；所以细节下沉、顶层只留链接。Claude Code 的自动记忆只加载 `MEMORY.md` 的前 200 行或 25 KB，作为索引。
- **多个写入者互相覆盖会丢事实，原文照引能保住事实**：多个 agent 同时写一张共享的合同条款表，57 条关键事实只留下 41 条；改为每份合同一页、由单个 agent 撰写、条款原文照引后，57 条全部保留。
- **轨迹搜索作为基础**：文章把轨迹搜索列为记忆的一种可能基础，再加 wiki 一类组织方式；后者的效果见方向 6。

对 HiveMemory 的启发（我的看法）：

1. "环境能重新告诉你的，不记"给"记忆不该像流水账"一个更清楚的判据（第 3.4 节第 3 点）。对编码 agent，环境就是仓库、git 与 GitHub：PR 状态、代码结构都能重新读到，不该成为记忆，这也解释了 owner 删掉的那批 PR 记录。
2. "怎么知道它成立"应与记忆放在一起：验证状态现在没有写入方（第 2.3 节），而这一项正是让后来者不必再查的关键。
3. 复核或馆长拿到的应是"未来的 agent 需要什么"，而不是一张固定规则清单；被动提示词中的拆分粒度清单就是这类固定规则。
4. 小而常驻的顶层正是日常路径缺少的（第 2.4 节）：HiveMemory 插件已有 SessionStart hook，现在只登记会话，技术上可以注入一份小顶层；放什么、由谁维护，是第 3.4、4.1 节的问题。
5. 共享表互相覆盖的教训支持唯一写入者，也提醒馆长不能并发写同一页（第 6.1 节边界 4）；"关键条款原文照引"对应第 6.2 节以引文定位来源。
6. HiveMemory 保存了轨迹却无法检索：MCP 的四个工具都只针对记忆，交互原文没有检索入口。
7. 差异：文章的场景是单 agent、文件夹存储，写笔记与做整理的是同一个模型，没有被动提取，前提是强模型自己会判断什么该记；HiveMemory 还要兜住不主动写的 agent 与纯聊天，所以被动路径不能取消，但它的角色应从"提取"转向复核与维护。文中数字来自他们自己的基准（数据库问答、Pokémon、法律文书与公司语料），只作方向参考。

### 8.5 Perplexity：Brain: Agentic memory as a knowledge wiki（2026-08-19）

Perplexity 工程团队的文章（[原文](https://www.perplexity.ai/hub/blog/brain-agentic-memory-as-a-knowledge-wiki)），讲其 Computer 产品的记忆系统，2026-11-15 阅读。

- **要解决的问题**：把静态记忆文件直接放进上下文，多了挤占窗口、少了缺上下文；让 agent 按需查外部库，又把导航的负担转给了 agent，向量库存的是互不相连的碎片，图数据库要求 agent 会写查询。
- **存储：`memory/` 下三个抽象层级**，有意冗余：`sessions/` 是原始历史（索引、摘要与完整轨迹）；`notes/` 是按主题分文件夹的提炼片段；`knowledge/` 即 Brain，一个综合 wiki，涵盖实体、概念、进行中的项目与学到的经验。单跳问题在 notes 里检索关键词就够；需要把几周、几个月的证据串起来的问题才用 knowledge。
- **wiki 的形态**：每页是对一个主题持续维护的视图，单独读也有用，又方便顺着链接探索。链接分两种：`[[wikilink]]` 是横向的上下文边（"还需要知道什么"）；`[cite:N]` 是向下的证据边，指向原始会话（精确到会话中的片段）或连接器来源（"怎么知道这是真的"）。整个 wiki 用 Git 管理，有版本、变更记录与 diff，也方便多个 agent 协同。
- **使用**：初始消息里放一份紧凑的 wiki 索引；agent 用 cat、grep、跟链接、查引用、比对 git 版本、下钻原始会话，自己决定查到什么程度，而不是走固定流水线；无关紧要的偏好直接采用，重要决定或来源冲突时才顺着引用读原始记录。全量记忆不复制进沙盒，只预载一份初始工作集；缺上下文时调用一个做语义检索的子 agent，它返回一段综合，并把支撑材料落成文件，工作集逐步扩大（远程挂载的路径上 grep 比本地慢四五百倍）。
- **后台维护（Dream）**：在沙盒中只读运行，每次从上一版 Brain 出发而不是从零重建；拿到的是可以自己探索的环境，而不是压平成一段提示词的输入；可以用只读连接器核实知识、把局部工作委派给子 agent；职责范围写成一份 Skill。四个阶段：定向（权威范围、长期指令、删除记录、额外输入与停止条件）；为新会话或有新轮次的会话写摘要；把每条值得记的观察挂到它该在的主题页上；更新 wiki（新建页面、修订综合、补链接与引用，或者什么都不改）。护栏：改动先写进一棵暂存的输出树，全部完成后才生效，从而把整张图当作整体更新；改动须通过确定性校验（格式、必备字段、引用格式）与语义核验（有证据支撑、与图的其余部分一致）；再由受控的同步步骤把差异应用到仓库，事后可在 git 历史中查看。
- **评估**：离线用 44 个合成用户、640 道题，答案与具体证据绑定；只去掉 wiki、其余记忆照常保留，正确率 0.600 升到 0.661，证据召回 0.573 升到 0.625，提升最大的是偏好类（+10.2 个百分点）、时间推理（+8.6）与过往活动细节（+6.9）。公开基准上，去掉 wiki 使 LoCoMo 降 4.6 个百分点，LongMemEval-S 无显著变化（单次会话的事实，原始轨迹本身就能答）。线上每天做配对评估，正确率 +9.3、时效性 +8.0、召回 +8.9，token 少约 15%、成本低 10%、速度快 10%。把索引直接放进初始上下文的随机对照实验中，wiki 的使用增加，与记忆相关的不满下降 6.9%。评估同时被当作自动改进的管线：agent 修改记忆子 agent、检索 skill 与提示词，只保留让指标变好的改动。

对 HiveMemory 的启发（我的看法）：

1. **三层冗余是第 9.1 节的一种形态：保留原子，在上面加一层综合。** sessions 约等于 InteractionArtifact，notes 约等于现在的记忆原子，knowledge 是 HiveMemory 缺的那一层（按主题综合、带引用的页面）。两篇文章的证据一致：综合层帮的是跨会话、跨文档的问题，单次会话的事实没有提升（第 8.4 节）。所以它是叠加在原子之上的派生层，不是替换，也符合第 5.2 节"派生物可以重建"。
2. **证据边精确到会话片段**，正是第 3.1 节质疑 3 所需的证据身份；"同一份证据只算一次"与"对照轨迹纠错"都要靠它。HiveMemory 现在的引用只能指向整个 Artifact。
3. **上下文边就是没有写入方的关系层**：wikilink 正是 `relates_to` 想表达的东西，区别是 Brain 中由后台 agent 维护，并写在正文里。
4. **索引预载有了第二份证据**，而且是随机对照实验。两篇文章都表明开局的小索引很关键；HiveMemory 的日常路径恰好什么都不注入（第 2.4 节），插件已有的 SessionStart hook 是现成的接入点。
5. **Dream 的护栏是第 6.1 节"写的一侧收紧"的一个完整实现**：从上一版出发、整体暂存、确定性校验加语义核验、受控同步、版本历史。HiveMemory 已有唯一写入者与版本记录，缺的是"一次运行的改动整体暂存、校验通过后统一提交"，与第 5.2 节"有事务的记录系统"是同一件事。
6. **删除记录与长期指令对应 owner 的使用方式**：owner 删掉的流水账与 PR 记录，应作为决定被复核或馆长尊重，不能下次又提取回来；"不为 PR 单独写工作记录"这类偏好可以作为长期指令交给馆长，而不是写死在生成提示词里，这也呼应第 8.4 节"只说明记忆的用途，不规定写法"。
7. **检索子 agent 提示了馆长的第二个角色**：除了后台整理，馆长也可以在前台当参考咨询台，外部 agent 问"关于 X 我们知道什么"，馆长返回一段带引用的综合，同时保护调用方的上下文窗口。这是对第 6.1 节的延伸设想。
8. **第 12 节的评判方式有了可借鉴的做法**：组件级对比（只开或只关某一个机制，例如复核，其余不变）、题目与具体证据绑定、固定题目反复回放。它用来验收已建成的机制，不是推出设计，与"样本统计不作为设计依据"（第 1.2 节）不冲突。
9. **差异与保留**：按第 7 节的划分，Dream 把写入（由新会话触发的第 2 至 4 阶段）与维护（移除过时内容）混在一起，可以借鉴做法，边界仍按 owner 的划分；Perplexity 有被动提取（评估中写明账户经过"记忆提取、会话摘要、Dream 编译"），没有提到 agent 的主动写入，属于被动一类加一个后台编译器；Brain 是单用户、产品内置、在沙盒中运行，HiveMemory 是多个 harness、多个 agent 共用一个库，并有可见范围的约束；数字来自他们自己的评估，离线提升为中等幅度，只作方向参考。

### 8.6 原始历史优先的一派：Obelisk 与 Nowledge Mem（2026-11-15 阅读）

来源是一条推特帖子（作者 Yuu，2026-11-15）、[Obelisk 仓库](https://github.com/tommy0103/obelisk)的说明与设计文档、[演讲材料](https://github.com/tommy0103/talks/tree/main/2026-11-15-coscon26-magic)（提纲与此前一场演讲的文字稿）、[Nowledge Mem 网站](https://mem.nowledge.co)，以及帖子引用的三篇论文的摘要（只读了摘要，没有读正文）。

**帖子的三个论点与论文摘要的对照**：
- 原始历史上的朴素检索在 7 组设置中 6 组第一：与 *Is Complex Agentic Memory Always Needed?*（arXiv 2610.30755）的摘要一致，领先最强的复杂记忆系统 0.13 到 5.53 分；但测的是 LoCoMo、LongMemEval 等对话问答任务。摘要也指出，即使能完整访问加工过的记忆，准确率仍不如原文。
- 许多记忆系统的净收益为负：与 *Memory Tax*（arXiv 2610.34073）一致，论文把记忆的净值拆成相对直接检索的"收益"与"税"，税来自加工过程删去或遮蔽了证据。
- 只用 BM25 与 grep 的 harness 已基本解决准确率：与 *Context as Infrastructure*（arXiv 2610.41172）一致，但测的是 BrowseComp-Plus 与 FRAMES 这类文档检索问答。论文的结论是编译出的结构不是更好的检索器，而是供给层：以"结论加证据"为叶子的导航树平均少读 38% 的 token；图、wiki、时间线、记忆等产物在准确率基准看不到的地方（治理、连续性、时间定向）才有回报。帖子没有提这一点。

**Obelisk（第一阶段：让历史可查）**：把 11 个 harness 的原生会话日志只读地索引进一个 SQLite 文件（FTS5 全文检索），日志原样不动、索引随时可以重建；agent 通过 skill 现场写 JS 查询脚本（CodeAct），而不是调用固定的检索 API；"记忆层"只是人批准的结论加指回源会话的指针，是结论的缓存，不替代原始记录；人与 agent 读同一份索引，每条结论都能回到原文。演讲中的四个取舍：原生日志是事实来源（认为跨 harness 的统一格式有损）；全文检索是主路径、向量是补充（编码会话是有文件路径、报错原文、方案名等锚点的"执行记忆"，发散的社交情节记忆才是向量的主场）；查询是一等公民，注入不是；人要有观测面。一个实例：agent 在换窗交接中把一个早期未验证的判断一代代继承加固，最后写成"锁定设计"，只有站在完整历史上纵向回看才发现；修复是交接时把事实、推断、冲突、未验证项分栏，推断不能因为反复出现就升级为事实。

**Nowledge Mem（第二阶段：检索层之上的 view）**：分层为轨迹 → 单元 → 实体 → 演化 → 社群 → 结晶，原始轨迹是这张图的最底层；它赢在读得少、让 agent 先看到全貌并知道分母，而不是召回更准。维护（作者称 live-update）：按变化快慢分层更新；新结论进来先判断与旧结论的关系（取代、补充、印证或质疑），被取代的旧结论仍留在图上；有争议的取代降级为"质疑"；先有准入判断，再由定期回补接住漏掉的；更新是局部的，加一条边、改一个标志，而不是重写一整页。产品上有版本历史、批量的"记忆健康"复核（没有用户批准不改动），以及从几次重复的工作中起草 skill、只有在没见过的检查上胜过现有版本才上线。记忆类型是 DECISION、LEARNING、FACT 三种，另有实体、结晶、wiki 与 Artifact。

**对 HiveMemory 的启发（我的看法）**：
1. **印证**：图索引是路由结构而不是真相、赢在读得少（第 4.3、5.2 节），至此 Anthropic、Perplexity 与这一派的证据指向同一点：视图加原文最好，视图不能替代原文。"复述不是验证"（第 3.1 节）在"锁定设计"的案例中有了现实的反例；局部修改而不是整篇重写（第 3.1 节对 Mode C 的质疑）与 live-update 的做法和它对 wiki 页面"膨胀、互相覆盖、断链"的批评一致；新旧结论之间有明确关系、被取代的保留在图上，对应第 4.4 节的断定边。
2. **挑战**：HiveMemory 保存了原始交互却不能检索，MCP 的四个工具都只针对记忆（第 2.4 节）；记忆原子作为主要产物有交"记忆税"的风险，所以它只能是补充，不能是唯一的入口（应对方向已在第 3.1、4.3 节：原文保留、证据可定位、索引只做导航）。关于"统一格式有损"，owner 指出完整性的上限其实在 harness（第 1.2 节，见第 3.2 节的两种处境）。
3. **评判的基准**：以"直接检索原始历史"为对照，衡量新流转的净收益（第 9.5 节）。
4. **对类型体系的输入**：执行记忆与社交情节记忆的区分对应 agent 工作式与 chatbot 式，两者靠不同的方式被找到（锚点与语义）；Nowledge 的六层可以对照 HiveMemory：轨迹即交互记录，单元即记忆原子，实体即主题节点，演化即时间轴与版本链，社群即主题聚类，结晶即跨多次经历归纳出的知识或 skill（第 3.4 节）；它把"决定"单独列为一类，HiveMemory 现在没有这一类。
5. **保留**：三篇论文测的都是问答准确率，没有测跨 agent 的知识传递、偏好的遵守、自主维护的成本或"下一位 agent 该怎么做"，而这些正是 HiveMemory 的目标；帖子把结论说得比论文宽。帖子与演讲提纲中的一些数字（例如"抽成原子事实掉 19.62 分"）没能在摘要中核实。Obelisk 的记忆层要人批准，Nowledge 的维护也要用户批准；owner 的目标是全自主维护，所以审计能力（版本加证据）对 HiveMemory 更重要，它是"人批准"的替代。

## 9. 问题与决定（未决定的只列选项与影响）

### 9.1 中期库的形状（已决定，owner，2026-11-15）

**决定**：中期库的存储保持平铺，以记忆原子为单位；分层由一张派生、可以重建的时空图索引承担（第 4.2 节），读写两侧都可以使用。图索引是给读者的补偿性引导，归属关系只存在于索引中，记忆原子不搬进容器。

**为什么原来的问法对不上**：原先的三个选项把"存储怎么组织"（要不要把原子搬进容器）与"怎么访问"（从模糊的想法怎样走到具体的记忆）混在一起。决定回答的是前者：存储不变；后者由派生索引承担。

**原来三个选项的去向**（作为背景保留）：
- 保持平铺、结构在派生层形成：与决定最接近，派生层就是时空图索引；Perplexity 的 Brain 是这一形态的实例（第 8.5 节）。
- 整体分层（记忆归入组，组成为写入、合并与维护的单位）：不采用；它想要的"组"由索引中的主题节点承担，组内查重、状态的固定位置等好处由索引参与写入获得（第 4.3 节）。
- 只把读取方式不同的部分单独成层：并入索引，用户与各个 agent 是索引中的身份节点，常驻索引可以带上用户偏好的摘要，agent 节点可以被列全（第 4.1 节的问题由此解决）。

后续细节（索引参与写入时的注意事项、Qdrant 的角色、图索引在 v0.8 中的定位）是候选设计，见第 4.3 节。

### 9.2 两条写入路径在哪里汇合（被动一侧已决定，owner，2026-11-15）

**决定**：两条路径在中期记忆上汇合（第 3.1 节）。
- 主动写入写下即生效；在任何修订到来之前，它的内容是 agent 当时的第一当事人判断，有效且合理，不因为话题还没有结算就被视为"旧结论"，也不加"待复核"之类的标记。修订是改进，不是纠错。
- 被动结算是话题的终态收尾者：它知道这个话题以来发生过哪些记忆事件（写入、更新），以全局视角重新审视这个话题的信息含量，对已有记忆作出修订、补上缺少的关键记忆，或者什么都不改。
- 生成事件带上轮次与事件的信息，保证溯源清晰（第 3.1 节质疑 3）。

**原来其他选项的去向**（作为背景保留）：生成之后由查重按相似度协调（v0.7.3 的"话题内主动写入优先"）不再作为方向，它会把修正当作复述丢弃；生成之前经同一种中间表示汇合（第 3.1 节、统一交互记忆 Idea 的断言层），中间表示暂不持久化，等确实需要跨多次整理复用时再决定（第 3.1 节）；读取时汇合（dsh-agent-soul 的做法）不采用。

**仍开放**：主动写入生成时能拿到什么材料。写入的那一刻，生成侧只有话题已完成的轮次与 agent 在 WRITE 中写下的内容，当前这一轮还没有导入（第 2.1 节）。owner 把它归为短期记忆的缺陷；候选是"写入即同步点"，在写入发生时把轨迹追平到写入那一刻，以及以来源链接补上够不到的背景（第 3.2 节）。

### 9.3 记忆的保存形态

- **保留记忆原子，补上文本做不到的部分**：生成链路仍然锁定，由系统维护带类型的关系、验证状态等（第 5.1 节）。人与 agent 仍只能经特定方法修改。
- **md 作为内容载体、系统状态另存，写入仍经唯一写入者**：内容可读、可审、可移植，每次改动的保证不变；但不能直接编辑文件，拿不到"普通文件编辑就够了"的好处。
- **md 作为真相、允许直接编辑**：系统事后发现改动并补齐索引与状态（EverOS 的做法）。人与 agent 都能直接修改；代价是多了一个绕过唯一写入者的写入方，每次改动的版本、来源与理由不再有保证。

影响：与第 9.1 节的决定相关：存储保持平铺，分层由派生索引承担，所以选文件载体时，目录只作存放，不承担分层的语义（分析）；也决定第 9.2 节汇合之后写出的是什么，以及维护要怎样识别内容被谁改过。第三项的真实代价见第 5.2 节的 VCP 样本。不论选哪一项，都可以同时考虑让 Qdrant 不再是真相，只作为可以从记录系统重建的索引（第 5.2 节）。如果把记忆直接作为文件暴露给外部 agent、让它们用普通的文件工具读取，PRIVATE 这类可见范围就无法执行（第 8.5 节第 9 点）。

### 9.5 评判方式（候选，不是 owner 决定）

按 owner 的判断（第 1.2、1.3 节），记忆的价值在长时间段内衡量。评判分两层：

1. **单轮的底线：不交记忆税**。在同一组题目上，新流转不比"直接检索原始历史"更差（第 8.6 节）；可以与 Perplexity 的组件级对比合用：只开或只关某一个机制，题目与具体证据绑定，固定题目反复回放（第 8.5 节第 8 点）。这是必要条件，远不够。
2. **长程的标准：演化质量与人工介入**，这是 HiveMemory 真正要证明的。可衡量的有：
   - 人工介入量：owner 每周手动删改的记忆数量，即"全自主维护"最直接的度量；
   - 使用效果：记忆被用上的比例，以及用上之后是否有效（第 3.4 节第 4 点的结果信号）；
   - 库的健康走势：重复、过时与互相矛盾的记忆随时间是收敛还是累积；
   - 维护成本：每周花在复核与维护上的 token。

owner 每天实际使用 HiveMemory，这本身就是现成的长程试验场；这里的数据用于验收已建成的机制，不用于推出设计，与"样本统计不作为设计依据"不冲突。

**统一的检验题**：让一个候选机制连续跑一个月，库会收敛还是退化？前面讨论中好几个问题都属于这一类：按相似度合并使细节漂移、整篇重写在多次修订后走样、过时的状态一直累积、索引的错误自我强化（第 4.3 节）。好的机制应有这些长程性质：重复执行稳定（同一份证据再复核一遍，结果不变）、增长有界、错误能被纠正、人工介入作为一项成本记账。

这也连到类型体系：事实会过时、决定会被推翻、状态会到期、偏好缓慢变化、做法越用越好；按行为划分类型时，最核心的维度可能就是"这种记忆在一个月里会发生什么、该怎样维护"。

### 9.6 类型体系（类型的用途、三处移出、资源记忆、FACT 的拆分、用户一侧与经历已决定；其余待讨论）

owner 于 2026-11-15 确认，类型体系是下一步要重新审视的。项目最初的设计按"agent 应该如何使用"划分类型（第 1.4 节），这层语义后来丢失，七种类型只剩标签。本节按逻辑顺序排列：现状；类型是做什么的（已决定）；怎样判断一个区分该不该成为类型（候选）；已从类型中移出的三处（已决定）；剩下的类型（资源记忆、FACT 的拆分、用户一侧与经历已决定，最后是尚未回答的与类型全貌）；写法与修订上的候选；待讨论。

**现状：类型现在被谁读（以代码为准）**

生成时模型从列表中选一个标签，写法不随类型变化，类型只决定 alias 前缀；类型写进稠密向量的输入文本（`Type: X` 一行，[embedding handler](../../src/hivememory/engines/memory_compiler/handlers/embedding.py)），轻微影响相似度与查重；SEARCH 可以按类型过滤；注入时显示给 agent；生命力按类型给固有价值权重，USER_PROFILE 不归档。也就是说，类型主要是展示与过滤用的标签，外加一个衰减倍数，没有任何地方按类型决定怎样写、怎样修订、怎样维护。

**1. 类型是做什么的（已决定，owner，2026-11-16）**

一条记忆之所以值得赋予一个类型，是因为下一位使用者对它有一种可以预期的用法（owner）。检索与送达合并为"出现位置"后，使用者有四个：读者、出现位置、写入者与维护。

另一位 agent 的例子（2026-11-16）：围绕 AGENT_PROFILE 的决定（第 3.3 部分），之后的 agent 可能问三个问题，它们命中几乎相同的关键词，读到答案后却该采取不同的行动：

| 下一位 agent 想知道什么 | 记忆必须保住什么 | 后来发生什么才应该改它 |
|:---|:---|:---|
| 做 v0.8 迁移：Profile 应该放在哪里 | owner 已决定移到独立的 store，以及这个决定的适用范围 | owner 改了设计或收窄了范围；迁移完成本身不推翻决定 |
| 排查当前版本：Profile 实际从哪里读出来 | 哪个版本、哪条真实的读取路径支持这个回答 | 迁移落地、读取路径改变；拍板当天运行事实并没有变 |
| 下次遇到类似对象：它适不适合放进记忆库 | 这次判断的理由，例如由管理入口维护、调用方需要可靠地列举它 | 新案例表明某个条件不足以得出结论，需要给经验加上限定 |

迁移完成的那一天，同一个新事件只该让馆长更新第二个答案：第一个仍然成立，第三个也没有因此得到验证。只靠文本相似度，三段材料都高度相关；知道每段在回答什么问题，馆长才能判断该动哪一处。这个例子不需要预设三条原子或三个枚举值，决定与理由可以写在一起，直到那条经验真的值得拿去解释其他案例。

**决定**（2026-11-16 改写，取代同日较早的"以维护契约为主"）：一条记忆值得赋予类型，是因为下一位使用者对它有可以预期的用法。

1. 类型首先告诉读者能拿它做什么。"按这个决定实施""当作某个版本的事实""借鉴这个案例"会导向不同的行动；即使系统只给出检索摘要，类型也要帮读者判断该点开哪一条，以及读完能据此做多强的判断。这对跨 harness 的 HiveMemory 尤其有价值。
2. 其次告诉馆长怎样才算写完整。要留的是排错经验，删去触发条件与失败尝试，结论即使正确也很难复用；要留的是一段已验证的实现，背景可以压缩，决定行为的关键条件必须原样保住。类型为主动写入与被动提取提供共同的取舍依据，这也是对"一句话直出"最直接的帮助（第 1.2 节）。
3. 修订时类型只提示该去找哪种依据："当初记错了""后来情况变了""又出现了一个适用条件"。该不该改，由那一段的内容、出处与新证据决定。

理由（分析）：这个定义找回了项目最初"按 agent 应该如何使用"划分类型的本意（第 1.4 节）。同日较早以维护为主，是把维护压在了类型上：维护的触发点在一条记忆内部的某一段，整条记忆级别的类型给不出"该改哪一段"。维护仍是系统的首要目标（第 1.3 节），它的载体是记忆内部每一段回答什么问题、每一段的来源与时间锚，而不是类型。

**2. 怎样判断一个区分该不该成为类型（候选，不是 owner 决定）**

- **判据**：遮住类型名之后，读者最容易用错什么，馆长最容易删错、改错什么？能指出具体错误，这个区分就值得保留；只能说"这样比较好找"，标签或时空图索引可能就够了。
- **轴与 tag 的区别**：VCPToolBox 的 Tag 是自由标注，用来找；它真正"按什么分"靠目录命名，目录名决定进不进索引、怎样送达。作为类型体系的轴应当数量少、取值封闭，每个取值都对应系统中一处不同的处理；某个取值没有任何地方据此做不同的事，它就只是 tag。第 3 部分的三项决定用的都是这条标准：WIP 没有消费方，可运行的消费方是执行而不是记忆，AGENT_PROFILE 的消费方是运行时配置。
- **形式**：类型仍是一个枚举，每条记忆取一个值，只承载"用法"这一条轴；其他有消费方的性质作为单独的字段，没有消费方的区分只作标签。旧的七种类型横跨了几条轴，它们的去处：

  | 性质 | 旧类型中的代表 | 去处 |
  |:---|:---|:---|
  | 用法 | FACT、REFLECTION 等 | 类型（第 1 部分） |
  | 可运行 | CODE_SNIPPET 作为 RUN 的门槛 | 独立的轴（第 3.2 部分，已决定） |
  | 时间上的进度 | WORK_IN_PROGRESS | 不进中期库（第 3.1 部分，已决定） |
  | 关于谁 | USER_PROFILE、AGENT_PROFILE | AGENT_PROFILE 已移出（第 3.3 部分）；用户一侧按描述的对象分为 USER_PROFILE、Preference 与 Decision（第 4.3 部分） |
  | 真相来源与验证 | URL_RESOURCE 隐含的"外部资料" | 真相在哪里、该听谁的决定读者的用法，进入类型（第 4.2 部分）；信多少（置信度与验证状态）仍逐条、逐段给出（第 5 部分） |
  | 怎样被找到 | — | 标签与锚点；触发它出现的线索种类随类型 |

- **检验问题**：下面五个维度是讨论的出发点，现在用来检验候选类型；每项是否值得成为原子上的固定字段，分别判断。可运行单独拿出来，正说明一种性质可以很重要，同时横跨多种用法。
  1. **怎样送达**：常驻、按需检索、注入执行环境、替代外部查询（最初设计的维度；第 4.1 节的常驻与可列举）。
  2. **在一个月里会发生什么、怎样维护**：会过时、会被推翻、会到期、缓慢变化，还是越用越好（第 9.5 节的长程视角；"错了与变了"）。
  3. **真相来自哪里、怎样验证**：用户说的、运行验证过的、外部资料还是推断（最初的来源分级；统一交互记忆 Idea 中"谁断言的"）。
  4. **挂在哪条轴上**：空间（主题）还是时间（经历）；例如 WORK_IN_PROGRESS 更像经历节点上的状态，而不是一条独立的知识（第 4.2 节）。
  5. **靠什么被找到**：锚点（文件路径、报错原文、方案名）还是语义（第 8.6 节中执行记忆与社交情节记忆的区别）。

  用这些问题检验，可以看出哪些是同一种东西的不同标签、哪些需要不同的处理流程，以及缺了哪一类，例如 Nowledge 单独列出的"决定"（第 8.6 节）在 HiveMemory 中没有对应的类型；失败路径与错误反思的去留（第 1.4 节末尾）也要在这里回答（已由第 4.4 部分回答）。

**3. 已从类型中移出的（已决定，owner，2026-11-15）**

**3.1 WORK_IN_PROGRESS 的去留**

现状（以代码为准）：

- 类型只在产生时决定一次：修订与手动编辑都改不了类型，只有合并会由模型重选（第 2.1 节）。一条 WIP 即使被修订为"已完成"，标题、摘要与类型仍是进行中的样子。
- 没有关闭：没有到期，也没有"完成"状态；它的固有价值最低（0.5，衰减快 1.5 倍），只会更快淡出检索。
- 没有专门的读取方：只有 SEARCH 能按类型过滤，guide skill 提醒 agent 对 WIP 尤其要核实。第一版设计中与它配套的主动续接从未实现（第 1.4 节）。
- 已有的记录：2026-10-29 核对对话回流时，生成的 5 条记忆中有 2 条标为 WIP，所述工作在生成之前已经合并（[外部 actor 接入 Idea](./external-actor-registration-and-runtime-access.md)）；一次调研记忆的清理中删去过一条 WIP，理由是这个类型会误导（[生成来源收敛](../archive/ideas/generation-source-convergence.md)）。

只删标签不够：被动提取的拆分规则把"一项工作的当前状态"列为单独成条的一件事，guide skill 也让 agent 在工作中断时写下未完成工作的状态。只删标签，进度快照会改标成 FACT 一类，看起来反而更持久。调研的八个项目都不把进度当作长期知识：要么放在时间轴上（任务期间的状态、账本），要么像 Hindsight 一样把"此刻在做什么"排除在外；dsh 的账本有"未结"、没有"关闭"，未结事项只增不减，与 WIP 是同一个问题。

**决定**：去掉 WORK_IN_PROGRESS 类型，中期库也不再收"当前进度"；"做到哪了"留在交互记录上，即时间轴上，以后由短期记忆（第 3.2 节）或经历节点上的状态（第 4.2 节）承担。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 被动提取的拆分规则去掉"一项工作的当前状态"；guide skill 改为写下得出的结论、决定与尚未解决的问题本身，不写"做到哪了"。
- 记忆数据只按 schema 2.1 严格解码，删除枚举值之前要先处理库中已有的 WIP 记忆；默认列出来交给 owner 逐条决定改类型还是删除。
- 随之移除：生成、写入与合并提示词中的类型与 alias 示例，MTP 的类型别名与 SEARCH 过滤说明，生命力权重与配置项 `work_in_progress_weight`，alias 前缀，前端的类型列表与创建表单，guide skill 的中英文版本，相关测试；[MealAssistant 产品规格](../applications/MealAssistantProductSpec.md)把这个类型用作近期饮食记录，也要改写。
- 暂不处理：外部 harness 现在只能检索记忆、搜不到交互记录；时间线的读取做出来之前，"上次停在哪"只能靠当时写下的结论与决定间接保留。

**3.2 CODE_SNIPPET 与可运行**

现状：CODE_SNIPPET 同时承担三件事：生成提示词中"代码片段、函数实现、配置文件"这类知识；RUN 唯一接受的类型；最高的固有价值。类型充当了 RUN 的门槛，但生成链写出的 CODE_SNIPPET 基本运行不了（第 2.4 节）；能否运行实际上是某一份内容的性质，不是类型的。

可运行这条轴里有两层：

| | 环境声明 | 宿主执行 |
|:---|:---|:---|
| 例子 | "这段 SQL 能在某个数据库里运行" | "Alice 可以对这条记忆发 RUN" |
| 是什么 | 内容相对某个环境的性质：语言、运行时、目标系统、入口与参数 | 系统的执行能力：有没有这个环境，能不能把记忆变成可执行物，谁被允许执行 |
| 谁消费 | 任何读者，例如外部 harness 的 agent 在自己的环境里运行 | 只在经 HiveMemory 执行时 |
| 归属 | 知识，是记忆的一部分 | MaaT，即工具宿主 |
| 现状 | 没有表达，只能写在正文里 | 用类型当门槛，把整段正文当 Python 执行，省掉了编译 |

**决定**：

1. 可运行是一条独立的轴，不绑在类型上；只适用于有可执行主体的记忆，不延伸到 AGENT_PROFILE（AGENT_PROFILE 的问题见第 6.3 节与第 3.3 部分）。
2. 这条轴分两层：环境声明属于知识，宿主执行属于 MaaT。
3. 可执行物是从记忆编译出的派生物，与索引同一原则（第 5.2 节）：可以重建，挂在记忆的版本上，版本变了即失效；生成链只写知识，不产出可执行物。
4. v0.8 不新增机制，RUN 的类型检查暂时保留；环境声明要不要在 v0.8 落地，看类型体系中"形态"这条轴怎么定。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 编译已有预留的位置：MemoryCompiler 的编译目标 `RUNNABLE_TOOL`，与提示词注入、向量文本等目标并列。
- AOT 在写入或结算之后编译并试运行，结果可以作为验证状态的写入方，接回第一版设计中"运行验证成功"的回路（第 1.4、2.3 节）；JIT 在 RUN 时编译，简单但没有验证信号。两者的取舍与 HiveMemory 宿主哪些环境，留给 MaaT（[MaaT Idea](./memory-as-tool-skill-plugin-boundary.md)）。
- CODE_SNIPPET 是否作为"代码形态的知识"保留为类型，已由第 4.1 部分回答：源头在别处的代码写成导览，只存在于记忆中的代码是资产本身；它的其他特点（依附外部真相、靠锚点被找到）并不是代码独有的。

**3.3 AGENT_PROFILE 移出中期库**

现状（以代码为准）：AGENT_PROFILE 是 Alice 的"人偶图纸"：正文是 agent 自己的人设提示词，标题与摘要组成调用方看到的子代理菜单项，`agent_config` 存模型、温度、top_p 与是否启用（[Agent 模型](../../src/hivememory/core/models/agent.py)）。它只能经管理入口创建与编辑，生成、查重、合并、归档、管理页列表都以类型判断绕开它（第 2.4 节）；运行时发现子代理只能靠检索恰好命中。只有 Alice 的 chat 需要它，外部 harness 的 agent 没有 Profile，CALL 也只在 Alice 的 MTP 中存在。

最初放进记忆库的两点理由，一点没有实现：提示词在演化中修正需要反馈途径，现在没有，执行者也不会主动修改；另一点"能被检索发现"，用固定列表即可替代（第 1.2 节）。

**决定**：AGENT_PROFILE 移出中期记忆库，单独成一个 store；可用 agent 的列表固定载入提示词，不再靠检索发现。

**新 store 的位置**（owner 标注）：新的 AgentProfileStore 与 ArtifactStore 一样，属于 MemoryLibrary，但不在三层记忆存储（短期、中期、长期）之中，不参与冷热迁移（[MemoryLibrary 与存储层](../patchouli/memory-library.md#1-四种存储角色)第 1 节）。所有权因此不变：Profile 本来就列在 Patchouli 的职责中，MemoryLibrary 也只由 Patchouli runtime 构造并持有。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 列表的内容：在本 Workspace 有准入、Profile 已启用、对调用方可见的 agent，每项是 alias 与职责摘要，沿用现有的子代理菜单编译目标；列表为空时不出现委托的一节。
- 随之删除：MemoryType 中的 AGENT_PROFILE，以及散落在生成、查重、合并、归档、检索、管理页列表与生命力中的类型判断；生命力对它照常计算却不据此做任何处理，一并去掉。
- 保留：可见性（执行者自己的进程按管理语义加载自己的图纸，CALL 按调用方的可见性解析被调用方的图纸）、`enabled`、手动编辑的版本记录。
- 迁移：记忆数据只按 schema 2.1 严格解码，删除枚举值之前，要把库中已有的 Profile 原子迁到新的 store。
- 关于 agent 的知识（擅长什么、做砸过什么）是否作为普通记忆生成，仍是第 6.3 节的候选，不随这次决定。

**4. 剩下的类型**

**4.1 资源记忆：导览（已决定，owner，2026-11-16）**

CODE_SNIPPET 与 URL_RESOURCE 是同质的：两者都想表达对一个外部资源的记忆，对应最初痛点中的"外源信息的高成本与易逝性"（第 1.2 节）。但存下的内容本身就是快照，会随时间过时；"外源"也难以定义；存了一份文档的副本，不如直接去读那份文档，现代 harness 可以随时读取，并且保证是最新的。所以资源记忆实际上是一份导览。

**决定**：CODE_SNIPPET 与 URL_RESOURCE 同质，都是对外部资源的记忆；资源记忆的主体是导览：说明它是什么、为什么这样设计、在哪里，把读者引向原本要大量检索才能找到的那个点；真相留在源头。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 导览的形态对应单条原子的冰山三层：索引层用来被找到；正文就是导览，"在哪里"写到路径、符号名、条款号一级，并带版本锚；Artifact 层是指向源头的链接，需要时还有当时的快照。
- "必须原样保住"收窄为锚点与起决定作用的细节（函数名、报错原文、关键的条件），它们既是检索的锚点，也不能被转述；其余部分可以概括。
- "直接去读源头"不成立的三种情况：
  1. 源头会变或会消失，而需要的是当时那一份（网页搜索结果、不跨重启的附件、一次性的命令输出与 API 返回、harness 网页工具按提问处理过的内容）：导览照写，当时那一份作为证据存成带定位符的 Artifact 快照（第 6.2 节），快照是证据，不是正文。
  2. 读者够不到源头（跨机器共享、chat 形态的 agent 没有文件工具、需要认证的来源）：导览带上足以判断的信息，例如来源在哪台机器、哪个仓库、哪个版本。
  3. 记忆本身就是唯一的副本（对话中写出的一次性脚本、在数据库控制台运行过的查询）：它不是资源记忆，而是资产本身，要原样保住，可运行的轴也落在这里；它归哪一类，随剩下类型的划分一起回答。
- 用判据检验：读者最容易把导览中的转述当作源头本身来引用或执行，类型要提示行动之前先顺着指引去读源头；馆长最容易在合并时丢掉锚点，或者照对话内容而不是照源头去更新导览。
- 维护：导览是否失效可以机械地检查（路径与符号还在不在、网址还能不能打开、版本锚之后源头有没有变），比逐字比对快照便宜得多，可以作为验证状态的写入方；快照只会变旧，它记的本来就是当时那一份。
- 时空图索引是对库内记忆的导览，资源记忆是对库外事物的导览，理念一致、对象不同，不合并。

**4.2 FACT 按真相所在拆开（已决定，owner，2026-11-16）**

调研的八个项目几乎都有"事实"这一类，但这个概念本身就模糊，不可能直接定义什么叫事实：资源记忆也是一种事实，一条世界知识是事实，agent 学来的东西也能叫事实，所以 FACT 会混杂（第 1.2 节）。

现状与调研（以代码与报告为准）：

- 代码中 FACT 是兜底类型：生成模型给出未知的类型时一律落成 FACT（[生成引擎](../../src/hivememory/engines/generation/engine.py)），WRITE 的生成失败时，兜底草稿也写成 FACT。生成提示词对它的说明是"明确事实、业务规则、参数定义"。
- 八个项目中的"事实"多是粒度或加工层的名字，不是用法：mem0 的自含事实句，EverOS 比 episode 更细的 atomic_fact，Hindsight 的事实层（与信念层、预合成文档相对），SME 由用户原话拆成的事实。最接近拆分的是 Hindsight 按来源分出的 world 与 experience；没有一个项目用"事实"告诉读者该怎样用它。
- "事实"说的是"它是真的"，而库中每一条记忆都声称自己是真的，所以它给不出下一位使用者可以预期的用法；把业务规则、运行事实与参数定义都叫作事实之后，读者得不到共同的用法，修订的触发也最不相同（"Qdrant 现在是 1.19.2"会变，"查重只看索引层"只会被证明错）。

真相所在决定读者该做什么：

| 真相在哪里 | 读者怎样用 | 什么事件会改它 | 例子 |
|:---|:---|:---|:---|
| 一个可以查看的源头：代码、文档、正在运行的系统 | 顺着指引去核对，再行动 | 源头变了 | "Qdrant 现在是 1.19.2""数据根在哪里""查重只看索引层（见 embedding handler）" |
| 有权决定的人：owner、用户、团队的决定与约定 | 照做；有疑问去问有权的人 | 有权的人改了主意 | "Profile 移出中期库""提交说明用中文" |
| 做过的事 | 动手前对照 | 新的经历加强或限定 | 排错经验、教训 |
| 推理与多方证据，没有单一源头 | 当作前提，连同依据一起用 | 被证明是错的 | 调研结论、领域原理、世界知识 |

**决定**：FACT 不作为类型保留，按真相所在拆开：真相在可以查看的源头的并入资源记忆（第 4.1 部分，导览带版本锚）；由有权的人决定的成为"决定与约定"；从推理与多方证据得出的留作"知识"；从做过的事中得出的是经验，即原来的 REFLECTION。

候选细节（不是 owner 决定，可在计划评审时调整）：

- "知识"是讨论中的称呼，正式的名字在计划中确定。"决定与约定"随后由第 4.3 部分细分为 Preference 与 Decision；"经验"随后改为"经历"（第 4.4 部分）。
- 决定要带上适用范围与理由，只有用户能改；迁移完成这类运行事实的变化不影响它（第 1 部分的例子）。
- 同一条轴也能解释前面的几项决定（分析）：资源记忆的真相在源头；WIP 的真相在时间线上，所以不进中期库；AGENT_PROFILE 的定义由 owner 决定，所以作为配置移出。真相在用户的那一块，按描述的对象再分为三类，来源作为逐条的标记（第 4.3 部分）。
- 信多少与该去哪里核实是两件事：置信度与验证状态仍逐条（逐段）给出；类型回答的是该去哪里核实、该听谁的。
- 一条记忆同时含有决定、运行事实与理由时，类型取它主要回答的问题，其余各段按第 5 部分的候选各自带上来源。
- 写入者拿不准时不能再落到 FACT，需要另定默认类型，随具体划分一起决定。

**4.3 用户一侧：USER_PROFILE、Preference 与 Decision（已决定，owner，2026-11-16）**

FACT 拆分后的"决定与约定"不稳定：agent 的决定与用户的决定都会落进去，而如果这一类是为"owner、用户、团队的决定与约定"而建，它又与 USER_PROFILE 太过接近。讨论在几轮中反复合并与拆分，owner 指出问题所在（第 1.2 节）：用户画像与用户定下的规则本来就是两件事，只是都说给工作的人听，于是都变成了某种约束；它们描述的东西确实不同，画像描述用户自己，用户的决定是对外界的。同样有细微区别的是"我说过一次，你就一直记得"与"相处久了，你逐渐了解我"：前者是用户明确说过的，后者是在一次次反馈中归纳得到的。

反复的原因（分析）：每一轮只沿当时讨论的一条轴提出合并或拆分，并且主要按读者的用法判断；凡是说给工作者听的东西最后都会变成约束，只看读者的用法，差别就被抹平了。区分它们的是另外两个消费方：写入时要保住什么（引述原话还是积累依据），以及什么事件会改它（用户的情况变了、用户改了主意，还是有了新的反馈）。

两组区分：

| | 说过一次，就一直记得 | 相处久了，逐渐了解 |
|:---|:---|:---|
| 描述用户本人 | "我在东八区""我是素食者" | "他习惯晚上工作""他先看结论再看过程" |
| 用户希望事情怎样做：对外界的要求与立场 | "提交说明用中文""不经要求不开 PR" | "他倾向选更简单的方案""他不喜欢流水账式的记录" |
| 对某件事的决定 | "Profile 移出中期库""这次旅行定在京都" | 基本没有：决定本来就要用户说出或认可 |

**决定**：用户一侧按描述的对象分为三类；"说过一次"与"逐渐了解"作为每条记忆的来源标记，不另立类型。

| 类型 | 描述什么 | 出现位置 | 什么时候改 |
|:---|:---|:---|:---|
| USER_PROFILE | 用户本人，即这个概念最初想要的"描述用户的记忆" | 全局 | 用户自己的情况变了 |
| Preference | 用户希望事情怎样做：对外界的要求与立场；不再冠以 USER 的名号 | 全局；拼进每个 agent 的系统提示词 | 用户改了主意 |
| Decision | 对某件事的决定，包括那件事上的约定 | 只在那件事上出现 | 被后来的决定取代；落地写进文档后转为导览，保留历史 |

候选细节（不是 owner 决定，可在计划评审时调整）：

- 来源标记的规则：说过的引述原话，是硬约束，只有用户能改；归纳的列出依据，是软的默认，新的反馈可以修正它，但不能覆盖说过的；用户确认之后转为说过的。来源回答的是"该多信、该多硬"，与第 2 部分"信多少逐条给出"一致；它对三类都同样适用，做成类型会让类型数量翻倍。
- 归纳必须依据用户自己的信号（例如几次拒绝了某类推荐），不能依据 agent 自己的行为：agent 从没推荐过辣菜，并不说明用户不吃辣，把自己做过的事记成用户的偏好正是 SME 丢弃 assistant 消息所要切断的自我强化。owner 的判断是，agent 一般没有主动归纳的意愿，真正成为记忆的多半是用户亲手定下的；归纳的一格因此可能很少。
- Decision 原则上只有说过的；agent 自己作出、用户没有确认的选择不进这三类：关于代码的进资源记忆导览中的"设计意图"，其余进"知识"并带上理由；用户认可后转为 Decision。
- Decision 的对象是"正在做的那件事"：在代码仓库里是项目或组件，工程约定就是对象为代码仓库的决定；对全天候助手是一次旅行、家里的三餐安排或一件进行中的事务。这个对象就是时空图索引中空间轴上的主题节点（第 4.2 节），所以不依赖"工程项目"的概念。
- Preference 的全局部分对所有 agent 生效，是要拼进每个 agent 系统提示词的那一段，与单个 agent 自己的身份与职责（AGENT_PROFILE，第 3.3 部分）分开：外部 harness 的 agent 在 HiveMemory 这一侧没有 Profile，规则又多半由对话中的纠正与认可产生，要经生成链写入，而 AGENT_PROFILE 是生成链之外的配置。
- 参照：早期 IDE 中的 rule.md 是用户为 LLM 设定的项目与全局规范；Claude Code 自己的记忆分 user（用户是谁）、feedback（怎样工作，包括纠正与确认过的做法，要求写明理由与应用方式）、project（代码与 git 历史推不出的进行中的工作、目标与约束）、reference（指向外部资源）四类，与这里的 USER_PROFILE、Preference、Decision 以及资源记忆大致对应；ChatGPT 的自定义指令曾分"希望了解你什么"与"希望怎样回应"两栏。
- 送达：Claude Code 的记忆是索引常驻（每条一行）、正文按需，常驻与否不按类型决定，与已决定的渐进式披露一致（第 1.3 节）。USER_PROFILE 与 Preference 的全局部分适合常驻，但外部 harness 现在没有注入通道，只注入 MCP 的使用说明，送达方式还没有定论。

**4.4 REFLECTION 改为"经历"（已决定，owner，2026-11-16）**

REFLECTION 本质上是从工作轨迹中总结出的经验，是离原始交互最近的类型，对应 Hindsight 的 experience，也就是很多工作所说的情景记忆。库中标为 REFLECTION 的记忆与 FACT 重叠得很厉害，调研中的"可复用模式"也常常落到这个类型上（第 1.2 节）。

现状（以代码与记录为准）：

- 被动提取的提示词把失败路径删掉了："去噪：忽略寒暄、简单确认、错误尝试过程"，"无价值"一栏写着"报错后的失败尝试（仅保留最终成功版本）"；同一份提示词又说出错的工具结果"可用于提炼错误原因与修复经验"（[生成提示词](../../src/hivememory/i18n/prompts.py)）。失败路径一删，经历只剩一句结论，读起来与 FACT 无异；话题的状态摘要反而要求保留失败尝试。这正是第 1.4 节末尾那处张力在现在提示词里的样子。
- 调研得来的模式被归进了 REFLECTION，例如归档中的 `ref_lazy_decay_pattern`（`ref_` 是 REFLECTION 的 alias 前缀）：它是读 SME 的源码学到的，亲历的是阅读与核对源码，保存的却是外部系统的设计。

"经历"与"经验"有区别：经验只覆盖"下次遇到类似情况，有什么可借鉴"；更广的情景记忆，即经历，还要覆盖"你记不记得那一次"，重在发生了什么，从中总结出的经验教训是可选的。这也符合 owner 一直以来对记忆的背景要求：对别的类型，背景是必须附带的；对经历，背景就是它的主体。

**决定**：REFLECTION 改为"经历"（情景记忆）。

1. **判据**：下一位 agent 需要回到这一次具体经历，才能判断它对眼前的问题有没有用。
2. **写入时要保住**：情境；发生了什么（做了什么、推荐了什么、说了什么，包括失败的尝试）；结果，包括用户的反应；出处，即轮次与事件锚点；教训可选。
3. **身份按出处**：一条经历对应一次发生。同一段轨迹不论被主动写入与被动结算读到几次，都只算一次经历；两次独立的经历即使文字相似，也各自保留出处。这给主动写入与被动结算的汇合提供了比"摘要是否相似"更可靠的依据，也是第 9.2 节"生成事件带上轮次与事件的信息"最直接的用处。
4. **不算经历的**：

   | 内容 | 去处 |
   |:---|:---|
   | 读别人的项目得到的模式 | 指回那个项目的导览，或者作为知识；"这个设计也适合 HiveMemory"是有依据的判断，也归知识；真正用过并看到它解决了什么、在哪里失效，才有自己的经历 |
   | 例行记录（每一餐吃了什么） | 留在时间轴上，即交互记录；值得回头看的那几次才写成经历 |
   | 面向未来的事项（"下周三面试"） | 留在时间轴上，由短期记忆或经历节点上的状态承担（第 3.1 部分） |
   | 用户稳定的特征（"做过膝盖手术"） | USER_PROFILE；与之相关的那段经过仍是经历 |

5. **修订**：经历本身只有记错了才更正；当时还不知道、后来才明确的结果可以补上（例如"后来证明那次修复没有生效"）；教训部分可以随新的理解修改。

候选细节（不是 owner 决定，可在计划评审时调整）：

- 归组：相似的经历不并成一条，交给图索引：经历是时间轴上的节点，再由空间轴上的主题节点连起来（第 4.2 节），与已决定的"存储平铺、分层由派生的图索引承担"一致。
- 演化：跨多次经历的教训作为知识演化，并链接回那些经历作为依据，这一步属于维护，不属于写入（第 7 节）；Preference 中"逐渐了解"的部分，依据就是经历（第 4.3 部分），例如连续三次拒绝辣菜推荐是三次经历。
- 用途：工作流中，动手之前对照相似的经历；助手场景中，推荐与反馈的案例（三餐助手规格已把"用户对某次推荐的反馈"映射为 REFLECTION，见 [MealAssistant 产品规格](../applications/MealAssistantProductSpec.md)）、共同经历与对话的连续性、Preference 归纳的依据。
- 时间轴的设计要把助手场景中未结的话头考虑进去，个人助手比工作流更需要"下次见面问一句面试怎么样了"。
- 随之要改：被动提取提示词中删去失败路径的两条规则；名字从 REFLECTION 改掉，正式名字在计划中确定；被错标成 REFLECTION 的调研模式，迁移时改归知识或导览。
- 可能的副作用（分析）：背景与经过留在一条经历里，只把用户说出的 Preference、Decision 与真正独立的知识拆出去，被动结算产出的碎片可能减少（第 1.1 节的根因），属于生成链的重新设计，未展开。
- 讨论中被取代的说法：以"真相在做过的事里"作为判据（太宽，读源码、做调研也算做过的事）；"一条经验等于教训加它的案例，相似的案例累积进同一条"（改为一次发生一条，归组交给图索引）；"新证据只加强或限定，不覆盖"（补上记错了更正、结果可以后补）；"教训是必需的"（改为可选）。另一位 agent 的分析补上了收紧的判据、更正旧案例与按出处识别三点。

**4.5 尚未回答的与类型全貌**

- 只存在于记忆中的代码（第 4.1 部分的第 3 种情况）归哪一类，尚未回答。

候选的类型全貌（分析）：真相在用户的 USER_PROFILE、Preference、Decision；真相在可以查看的源头的资源记忆（导览）；真相在推理与多方证据中的知识；在发生过的事中、重在"那一次"的经历（原来的 REFLECTION）。正式的名字在计划中确定。

**5. 写法与修订上的候选（不是 owner 决定）**

- 一份材料含有几种回答时，不拆成几条原子（撤回此前"选不出唯一类型就拆开"的建议，它会加重碎片），而是让每一段可以被单独定位与修订，与第 3.1 节"修订其中一部分"的复核一致。
- 第 1 部分例子中三个答案的修订触发，正好对应三种来源：owner 的决定（规定）、对照代码核实（描述）、新案例累积（证据）。来源这条轴落在段落上，不在整条记忆上。
- 描述运行事实的一段，写入时带上版本锚（截至哪个版本、经哪条路径）：它只会变旧、不会变错，读者据锚点去核对代码，馆长不必追着改。与 WIP 同理：真相在代码仓库中、变化又快的东西，不让馆长追着改。
- 类型是否还写进稠密向量的输入文本，随具体划分一起决定。

**6. 待讨论**

剩下要回答的：只存在于记忆中的代码归哪一类；写入者拿不准时的默认类型；USER_PROFILE 与 Preference 的全局部分怎样送达外部 harness。
