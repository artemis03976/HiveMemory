# 轻量化：模型依赖、运行内存与包体

## 0. 文档性质

owner（2026-11-12）：轻量化是项目的目标之一，包括减轻对 embedding 与 reranker 模型的依赖，降低运行内存与包体大小。先建立本 Idea；第 4.1 节中不需要研究的改进先做，其余方向在评测数据的指引下研究。第 4.1 节已于 2026-11-12 实施（PR #223），当前事实见[桌面客户端](../frontend/desktop-client.md)第 8 节与 [MemoryLibrary](../patchouli/memory-library.md#12-中期当前可检索书库)。

除注明 owner 决定的内容外，本文是候选方向与开放问题，不描述当前行为，也不代表排期。当前事实见[桌面客户端](../frontend/desktop-client.md)、[检索](../patchouli/retrieval.md)与[记忆生成](../patchouli/generation.md)。

## 1. 问题

HiveMemory 是在用户自己电脑上常驻运行的个人软件。资源占用直接决定它能不能一直开着：后端带两个本地模型时占用约 2.4 GB 内存，首次启动要下载 1.67 GB 模型，覆盖安装需要一到两分钟且时间不固定。这些代价大多不来自记忆本身：475 条记忆的向量只有约 2 MB。

## 2. 基线（2026-11-12 在 owner 的电脑上实测）

| 项目 | 实测 | 主要来源 |
|:---|:---|:---|
| 安装包 / 安装后 | 254 MB / 848 MB，16,111 个文件 | Electron 主程序 247 MB；随包 Python 391 MB、15,510 个文件（litellm 3,313 个、boto 系 2,000 多个、openai 1,503 个、pip 841 个、各包测试目录 637 个） |
| 运行后的安装目录 | 19,534 个文件 | 后端运行时写入的 3,993 个 `.pyc` |
| 覆盖安装的文件操作 | 约 1.5～2 分钟 | 旧版卸载删除约 1.95 万个文件（13～26 s）、解压到临时目录（约 26 s）、复制到安装目录（20～34 s）、删除临时目录（13～26 s）；同一次复制前后两次 34 s 与 20 s，波动来自实时防护（火绒）与磁盘缓存 |
| 首次启动下载的模型 | 1.67 GB | bge-reranker-base 为 fp32 ONNX，1.1 GB；bge-m3 已是 int8，568 MB |
| 后端内存：导入 | 299 MB，导入 4.3 s | 其中 `import litellm` 单独 214 MB、5.1 s |
| 后端内存：加载嵌入模型 | +813 MB，约 1.1 GB | bge-m3（int8） |
| 后端内存：再加载重排模型 | +1.3 GB，约 2.4 GB，峰值工作集 2.9 GB | bge-reranker-base（fp32） |
| Qdrant | 475 条记忆占 865 MB 磁盘，内存约 50 MB | 8 个 segment，每个对稠密向量、稀疏向量与 payload 各预分配 32 MB，合计约 770 MB |
| Electron 各进程 | 合计约 80 MB 工作集 | 不是瓶颈 |

测量方式：内存在开发环境中逐步导入、加载模型并以 psutil 读取驻留内存；安装耗时以单线程复制、解压与删除模拟安装程序的文件操作，没有在 owner 的安装上完整运行安装程序。

## 3. 指标与评测

换模型与换存储都会改变检索与查重的质量，没有评测时“减轻依赖”只能凭感觉判断。候选做法：

- **资源指标**：安装包大小、安装后文件数、覆盖安装耗时、首次下载、导入后内存、加载各模型后的内存与峰值、冷启动耗时；按第 2 节的方式在每个版本复测。
- **检索评测集**：从真实记忆整理“查询 → 应该找到的记忆”，记录 recall@5 与 MRR，比较只用 dense、只用 BM25、混合、加不加重排，以及候选模型。
- **查重标定**：生成时的查重以 dense 余弦与固定阈值判断，阈值按 bge-m3 的分布标定；换嵌入模型时阈值要重新标定，评测需要覆盖查重。

## 4. 候选方向

### 4.1 不需要研究的减量（owner 2026-11-12 决定先做；已实施）

2026-11-12 实施（PR #223），实测：安装后 16,111 个文件、848 MB → 14,570 个、779 MB；安装包 254 MB → 304 MB（zip 压缩率低于 7z）；直接解压到安装目录约 25 s，省去复制到安装目录（20～34 s）与删除临时目录（13～26 s）两步；以启动代码处理 475 个点的已有集合，8 个 segment、865 MB → 1 个、164 MB，点数不变。安装程序的完整运行（含先请程序正常退出）由 owner 在安装版上验收；从不认识 `--quit` 的旧版升级时，安装程序等满 60 秒后照旧强制结束，需要先从托盘退出。

- **打包精简**：随包 Python 不带 pip 与各包的测试目录；Electron 只保留中文与英文语言包。
- **安装程序直接解压到安装目录**：electron-builder 的 7z 安装包先解压到临时目录再复制，改为 zip 载荷直接解压到安装目录（`useZip`；不做自动升级，用不上差分包），省掉复制与删除临时目录两遍。代价是安装包变大，安装中途失败时不再整体回退。
- **字节码缓存不写进安装目录**：后端的 `.pyc` 写到数据根，升级时少删约 4,000 个文件，安装目录与安装包一致。
- **Qdrant 少分 segment**：集合按 1～2 个 segment 优化，已有集合随之合并，预计磁盘占用降到一两百 MB。
- **覆盖安装前请程序正常退出**：安装程序在程序运行时直接结束安装目录下的全部进程，包括后端与 Qdrant，跳过了正常关闭，关闭时本该写盘的生成工作、写入句柄与任务历史随之丢失。改为先请程序正常退出并等待，超时再强制结束。

### 4.2 重排模型

- 改用 int8 的 ONNX 版本：磁盘约 1.1 GB → 约 0.3 GB，内存约 1.3 GB → 0.3～0.4 GB，首次下载随之降到约 0.85 GB。需要核实可用的转换版本，并用评测集确认排序与 fp32 一致。
- 默认关闭：重排只从 20 个候选中选出前 5 条，且未加载时本来就按召回顺序返回；收益由评测集决定。

### 4.3 替换 litellm

用精简的 OpenAI 兼容客户端替换 litellm，可去掉 litellm、openai 与 boto 系约 6,800 个文件、超过 120 MB 包体，以及 214 MB 内存与 5 秒导入。需要自行实现：按服务商路由、失败分类（提供商失败与超出上下文窗口要区分，生成的失败原因码依赖它）、token 计数；使用 Anthropic 原生接口时另需适配器。

### 4.4 嵌入模型

从轻到重：

- **静态嵌入**（例如从 bge-m3 蒸馏的 Model2Vec 类模型）：几十 MB，几乎不占内存与 CPU，质量较低；
- **小型多语言模型**（384 维 int8，约 100 MB）：维度改变，需要一次重新嵌入全部记忆的迁移；
- **服务商的嵌入 API**：本地零占用，但有费用、隐私与离线可用的问题，适合作为配置选项而非默认；
- **更多交给 BM25 与现有的 LLM**：Gateway 已经在分析查询，可以让它产出关键词走 BM25；个人规模的记忆量下可能已经足够。

嵌入模型同时服务 dense 召回、写入时的查重与存储，任何替换都要同时看检索评测与查重标定（第 3 节）。

### 4.5 存储

个人规模（几千到上万条记忆）下，暴力余弦计算也只要毫秒级。嵌入式存储（SQLite，加 FTS5 做 BM25，再加向量矩阵或 sqlite-vec）可以去掉 Qdrant 这个独立进程、83 MB 的程序、端口管理与长路径限制。它牵涉记忆库的存储端口、过滤与权限查询，改动最大，适合在嵌入方向确定之后评估，以 ADR 记录。

### 4.6 Electron 外壳

Electron 主程序是最大的单个文件，但运行时不是瓶颈；换成 Tauri 等基于 WebView2 的外壳等于重写桌面端，现阶段投入产出比不高。

## 5. 主要未知项

- 重排在个人规模的记忆量下对前 5 条结果的实际提升有多大；
- 静态嵌入或小模型在中文、代码与专有名词混排的记忆上的召回损失，以及 BM25 能补回多少；
- 替换嵌入模型时，查重阈值能否重新标定到与现在相当的误判率；
- 嵌入式存储能否保持现有的 Workspace 归属过滤与可见性查询语义。

## 6. 升级为计划的条件

- 第 4.1 节的改进不需要研究，直接实施；
- 第 4.2～4.5 节的任一方向进入计划之前，先有第 3 节的检索评测集与资源基线，并以评测结果说明质量损失可以接受；
- 存储方向另需 ADR，写明归属过滤与可见性查询怎样在新存储上成立。
