# 记忆核心：库的形状、图索引与保存形态

## 0. 文档性质

本文是 v0.8 设计讨论的子文档，2026-11-16 从[总纲](./memory-flow-short-to-mid-term.md)中按主题拆出，内容未删减。总纲有 owner 的出发点与总体说明、全部决定的一览（第 1.3 节）、与讨论有关的代码现状（第 2 节）、外部调研的启发与评判方式；外部项目与文章的事实见[外部参考](../research/memory-core-external-references.md)。本文不描述当前行为，也不代表排期；除注明为 owner 决定的内容外，都是讨论中的分析或候选设计。

结构：第 1 节是 owner 关于库的形状、访问与保存的说明；第 2 节是库的形状与访问（平铺的限制、高层图索引、时空图索引的定位、关系层）；第 3 节是存储与保存形态（差别在系统维护的部分、索引不是真相）；第 4 节是问题与决定（中期库的形状已决定，保存形态仍开放）。

## 1. 讨论中的说明（owner）

**库的形状、访问与保存**

- 把原始轮次按内容归入容器，在论文中很常见（如 Nemori）。话题跨会话按内容归并是最初就有意的设计，已经实现了"相似的对话无论出自哪个会话都合在一起"；剩下的问题是归并由 LLM 判定，不能保证每次合理（[跨会话话题 Todo](../todo/cross-conversation-topic-placement.md)）。所以"话题能否跨外部会话"不是开放问题。
- 成熟的记忆系统都会分层，比如用文件夹组织目录结构；HiveMemory 的记忆一旦进入中期库就平铺了，完全由检索系统"扫盘"。owner 在反思：是否中期库的形状限制了写入链路，间接限制了生成的材料与形式（第 2.1 节、第 4.1 节）。
- 不分层的问题不只体现在写入上。user profile 一般保存长期的用户偏好，但任何检索都可能遗漏某一条重要的信息；大部分记忆框架因此把用户偏好单独存为一层，常驻在系统提示词里，避免要用的时候找不到。agent profile 的问题没有那么严重：它本来就是想借助记忆库的检索能力，让 agent 在运行时检索到它、作为子代理的材料，并且作为记忆原子享受维护的好处；但现在的系统行为对此并不友好，没有发挥出 agent profile 应有的独立性质（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节、第 2.1 节）。
- 记忆的保存形态（2026-11-14）。包括调研的八个项目在内，很少有项目像 HiveMemory 这样用自定义的数据格式保存记忆，主流做法已经接受 md 文档作为记忆的文本载体（例如 Claude Code 的原生记忆，[外部参考](../research/memory-core-external-references.md)第 1 节）。大部分人称之为 LLM wiki，但它与以前的知识库没有太大差别：技术仍是 RAG 与索引那一套，"数据库"与渐进式披露的核心理念没有变。它的好处是对人和 agent 都友好：不需要定义新的编辑方法，普通的文件编辑就够了，能充分利用已有的通用文档格式。反观记忆原子：索引层类似 frontmatter，正文就是 md 的正文，修改起来却不像编辑文档那么简单；唯一的优势是 Artifact 层，即与外部的联系，但这在 md 中用链接也能简单实现。原子格式还把生成链路完全锁死，只能通过特定方法修改，这不是坏事，但确实是局限。只要仍在文本的范围内，新定义一个数据格式不可能比成熟的文档更有竞争力；要让记忆原子超越普通的 md 文本记忆，就必须让它做到文本载体做不到的事（[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节、第 3.1 节、第 4.2 节）。
- 动态检索是有意的选择（2026-11-14）。"决定每条知识以哪一档进入上下文"实际上就是现在的预检索，也是 RAG 检索技术的本源。owner 一年前了解 skill 体系时就想到了这个问题：skill 的描述常驻上下文，但 skill 是有限的、从外部安装进来的，而 owner 构想的记忆是动态的；四百多条记忆如果都固定载入，上下文会爆，也不符合相关性。所以选择了动态检索加载记忆，并且仍保持与 skill 相同的、从索引到正文的渐进式披露（[写入链路](./memory-flow-write-path.md)第 2.4 节）。
- 高层索引（2026-11-15）。记忆库的分层一定会决定记忆的工作形态，写入侧与维护侧都是，Perplexity 的工程实践已经证明了这一点。分层的最终目的，是引导任何访问记忆库的人或 agent 经过渐进的了解，从一个模糊的想法逐步追溯到并回忆起特定的信息。单条记忆原子已经做成类似的"冰山模型"：Index 层是笼统信息，Payload 层是核心内容，Artifact 层链接到真正的资料源，形成逐级递进的获取流程。但这只对单个原子成立：从 agent 主动或根据用户的问题出发找到对应的原子，中间的渐进引导是断的，完全依赖检索系统的能力，原因就是记忆库是平铺的。即便关系型数据库，数据也不会平铺摆放，而是可以从某些表的字段派生关联表，形成嵌套，也就是渐进的获取过程；记忆库与现代数据库同源，数据库的设计哲学同样适用。因此中期记忆、甚至长期记忆都需要一层 memory index，即按主题综合、带引用的高层索引层：可以是人工制定或非人工层次聚类的树形索引，更理想的是图索引，因为记忆之间的边界不一定清晰，一条记忆不必只归属于一棵子树。这与 owner 构想过的图数据库方向、以及一直没有启用的关系层相连：有了图的关系结构，就能用经典的图搜索算法从某一节点出发，以启发式的方法完成引导。这里的图不再是直接把记忆原子连成图，而是更高层次的东西（第 2.2 节）。
- 图是指导检索的索引表（2026-11-15）。owner 想要的已经不是图数据库：图会变成一份索引表，指导检索如何进行，即在模糊的先验想法下，根据图的指引一步步认识问题，有一点贝叶斯网络的意思。更激进的设想是"嵌套图"：高层索引的一个节点对应一张展开的子图，agent 在"搜索、展开"的循环中逐步深入，达成渐进式访问；但这是极度复杂的组织，至少 v0.8 没有必要实现。高层节点分为主题与经历两类，可以用经典的"时间与空间"来解释：主题轴是记忆的空间内容，经历轴是记忆的时间序列，为图索引同时赋予时空两个角度，涵盖了不同的性质（第 2.2 节）。
- 图索引是补偿性引导，存储仍然平铺（2026-11-15）。时空图索引实际上是一种对读者的补偿引导机制，中期记忆库的底层结构并没有变化，仍然平铺，第 4.1 节"中期库的形状"与这个问题已经对不上；按馆长 Agent 的构想，一个完全派生、可以重建的索引也可以直接参与写入判断。owner 的理解是：这相当于用自己设计的索引机制替换掉了 Qdrant 原生的向量索引，从而让记忆库的形状不再影响写入与访问方式；由此要问 Qdrant 作为向量数据库还剩什么意义，以及时空索引图在当前设计中的定位；这只解决了 v0.8 的一部分问题，写入链路的材料以及被动提取与主动写入之间的冲突还没有完全的定论。owner 据此决定关闭第 4.1 节（第 2.3 节）。
- 关系层的去向（2026-11-15）。记忆原子上的关系层是原本规划中图数据库的一部分预设；在时空高层图索引的规划下，需要重新看待这个挂在原子上的关系层（[总纲](./memory-flow-short-to-mid-term.md)第 2.2 节、本文第 2.4 节）。
- 维护的关系索引比原始文本更有意义（2026-11-15）。原始文本的噪声问题摆在那里：Obelisk 的作者自己也承认，单靠全文检索命中范围有限、单次检索结果无法跨会话复用、第一轮命中会带偏后续检索。把一堆会话记录当作知识库、用常规的 RAG 手段去检索，极其 token 低效，它们也不是高度精炼的知识。一个精心维护的关系索引远比一段段原始文本有意义；该作者后来也要在检索层之上建 view，正好对应时空图索引（本文第 2.3 节、[外部参考](../research/memory-core-external-references.md)第 6 节）。

## 2. 库的形状与访问

### 2.1 平铺的库怎样限制写入与读取

**中期库的形状限制了写入链路**

1. 库是平铺的，读取只有一种方式：按索引层的相似度检索（[总纲](./memory-flow-short-to-mid-term.md)第 2.2 节）。
2. 所以每条记忆都必须能被单独检索到，要把自己所处的上下文（项目、组件）写进索引层（[总纲](./memory-flow-short-to-mid-term.md)第 2.2 节）。
3. 同一项目的记忆因此在索引层上天然相近，查重分不清"同一件事"与"同一项目里的另一件事"：分数落在 0.75 阈值两侧（[查重 Todo](../todo/generation-dedup-decision-signal.md)）。分层时，这些上下文由所在的组承担，不必每条重复。
4. "这件事该放在哪、库里已经知道什么"只能由全库相似度回答。查重取全库最近的一条；被动提取看不到库，平铺的库最多也只能像 mem0 那样给它几条相似的旧记忆，无法让它"更新关于 X 的那一部分"，只能先产出新的记忆，再由相似度决定它与已有记忆的关系。
5. 会随时间变化的状态没有固定的位置。后来的终态只能成为又一条记忆，相似度超过阈值时才会被合并进旧记忆；分层时，"某项工作的当前状态"可以是组内一个固定的位置，新状态直接覆盖。

一份外部讨论稿（[外部参考](../research/memory-core-external-references.md)第 3 节）中也有同样的观察：把记忆按领域分区，每个使用方只在自己的分区里检索，共现关系、去重阈值这些信号会更可靠，原因不是算法变好了，而是无关的内容不再参与比较。

这同时作用于两条写入路径：主动写入与被动提取的草稿走同一个查重。即使将来主动写入的比例变高，形状带来的限制仍然存在。在第 4.1 节的决定下（存储平铺、分层由派生索引承担），这些限制大多由索引参与写入解除，见第 2.3 节。

**Profile 需要另外两种读取方式**

- 用户偏好需要常驻：不论当前在问什么，它都应该在场。
- agent profile 需要可列举、可寻址：先知道有哪些 agent，再从中选择；检索可以帮助挑选，但不应是唯一的入口。

平铺的库把这两种需求都压进相似度检索，特殊需求就只能成为例外：USER_PROFILE 的归档豁免与 AGENT_PROFILE 的合并排除都是这样来的。AGENT_PROFILE 存放在同一个库里，却靠十来处例外表达它的独立性，结果既没有得到作为记忆原子的好处（维护，从交互中学习），也没有得到单独成层的好处（运行时可以列全）。

**分层的代价与现成的出发点**

- 分层把"这件事属于哪里"从检索时挪到了写入时。现在这个判断由检索按相似度临时做出，每次都可能不同，但写入时不用承担；分层后，写入时要决定归入哪一组，而组由谁建立、怎样命名，又是一个与话题路由同类、由模型判定、不能保证合理的判断。
- 一旦某一层常驻，它的写入方式也随之改变：不再追加原子，而是维护一份有预算上限的文档。调研中已经出现了代价：EverOS 每次整体重写用户的 `user.md`，用户手改的内容会丢失；dsh-agent-soul 的 `USER.md` 超出预算的部分会被省略。
- 一个现成的出发点：系统已经有按内容归组的结构，就是话题，只是它在进入中期库时被删除了（[总纲](./memory-flow-short-to-mid-term.md)第 2.2 节）。

### 2.2 高层图索引：库一级的冰山模型

**把单条记忆的冰山推到整个库**：常驻的小索引 → 按主题综合、带引用的页面 → 记忆原子（Index 与 Payload）→ Artifact 中的原始证据。现在从问题走到原子只有一次相似度检索，这就是 owner 所说"渐进引导断了"的地方。

**高层节点的候选**：

| 候选 | 例子 | 长处 | 问题 |
|:---|:---|:---|:---|
| 主题：项目、组件、工具、人、概念 | Perplexity 的 `knowledge/`、Hindsight 按单主体组织的 observation、BaiShou-Next 的实体图 | 有名字，回答"关于 X 我们知道什么" | 需要有人建立与维护，由 LLM 判断 |
| 经历：一段交互或一个话题 | EverOS 的 episode；HiveMemory 的话题（结算时被删除） | 回答"上次那件事"，有时间顺序 | 按交互划分，不是按知识划分 |
| Tag | VCPToolBox 的 Tag 共现图；HiveMemory 索引层已有的 tags | 数据现成，代价最低 | 噪声大、没有名字层级；VCP 一年下来只让它在候选内加不到 0.21 的分 |
| 身份主体：用户、各个 agent | 用户偏好、agent profile | 天然的枢纽，也解开第 2.1 节的 profile 问题 | 数量少，只能当几个入口 |

**两类节点，对应时间与空间**（owner 的说法，第 1 节）：主题节点是记忆的空间内容，回答"是什么"；经历节点是记忆的时间序列，回答"在哪里学到的、什么时候"。记忆原子挂在两者之间，证据在它下面；用户与各个 agent 作为主题一侧的几个特殊节点。理由：人的回忆本来就有"关于 X"与"上次那件事"两种入口，Perplexity 的 wiki 提升最大的几类中就有时间推理；话题本来就是按内容跨会话归并的经历容器，保留下来作为经历节点是最小的改动，按时间线消费的设想也可以成为这条轴的骨架；主题一侧的归属是多对多的，一条记忆可以同时挂在几个主题下，不要求边界清晰。时间还有更细的一层：单条记忆与主题页本身也随时间变化（版本、取代、"之前怎么定、现在怎么定"），记忆的这条时间线由 MemoryVersionArtifact 记录；"X 是怎么变成现在这样的"可以先在空间上定位到 X，再沿时间轴往回读，这也对应第 2.1 节第 5 点"状态类信息需要固定的位置"。

**边分三类**：主题之间的上下文边（属于、依赖、相关），用于导航，即 `relates_to` 本来想表达的东西；主题、经历到原子的归属与引用边，多对多，用于从综合页下钻到具体记忆；原子之间的取代与冲突边（例如 `supersedes`），主要供维护检测冲突、在检索时给被取代的记忆降权，按[写入链路](./memory-flow-write-path.md)第 4 节属于维护一侧。所以关系层不必是"原子之间互相连边"，导航用的边主要建在高层节点上；关系层本身的去向见第 2.4 节。

**设计约束（分析，不是 owner 决定）**：
- **图索引是路由结构，不是真相**：它与 VCP 中"只给出候选的 ANN 路由缓存"同类，真相仍是记忆原子与 Artifact。它由馆长从原子派生，可以重建，第 3.2 节"同一事务标脏、查询时修复"可以直接套用；路由出错只多花几步或漏掉一些，不会返回错误内容，漏掉的仍可由检索补回。这也是"叠加在检索之上、不替代检索"在工程上的含义。
- **每个节点要带一份足以决定"要不要往下走"的摘要**：逐步认识的过程中，先验来自常驻索引与当前上下文，每展开一个节点、看到其子节点的摘要相当于一次观测，据此判断答案更可能在哪个分支。摘要笼统时 agent 只能逐个打开，渐进就退化成遍历，所以维护这张图最要紧的产出是节点摘要的质量，与原子 Index 层的作用相同，只是在更高的层级。
- **节点由谁建立**：层次聚类得到的簇没有名字，重新聚类后身份会变，无法被稳定地引用与链接；聚类只用来提出候选，由馆长（[写入链路](./memory-flow-write-path.md)第 3.1 节）命名、建立、合并与拆分节点，人工制定的节点作为不被自动改动的锚点。
- **节点身份要稳定**：主题被合并或拆分后，指向它的链接不能断；现有记忆合并后旧 alias 会改指到新记忆（读取时的 redirect），主题节点可以沿用同样的思路。
- **图搜索由谁来走**：导航时让 agent 或馆长自己顺着边走（Perplexity 与 Anthropic 都是如此，agent 拿着入口索引自己决定下一步）；扩散激活或个性化 PageRank 这类算法只在检索出的候选内重排，不决定召回（第 3.2 节）。两者可以并存。
- **不需要图数据库**：个人规模下，图是一种数据模型，可以用 sqlite 的节点表与边表存放、用递归查询遍历，并与第 3.2 节的记录系统同库、按事务一起提交；单独的图数据库引擎会多出一个需要保持一致的真相源。这是"数据库的设计哲学适用于记忆库"的直接应用。
- **入口是一份常驻的小索引**：列出顶层主题与最近的几段经历，在会话开始时注入，补上日常路径"什么都不注入"的缺口（[总纲](./memory-flow-short-to-mid-term.md)第 2.4 节）。
- **嵌套图 v0.8 不做，但不堵死**：两层结构（常驻索引 → 主题页或经历节点 → 原子）就是只展开一层的嵌套图。只要节点能引用节点、节点的摘要与子集合分开存放，以后往下嵌套就只是在节点下多挂一层，不需要改数据形态；按 AGENTS.md [总纲](./memory-flow-short-to-mid-term.md)第 1.1 节，v0.8 不为嵌套预留任何多余的类型或配置。
- **一个提醒**：VISION 把"以复杂知识图谱或新算法替代尚未跑通的基本检索闭环"列为要避免的事；两篇文章的数据也表明 wiki 加搜索最好，单独 wiki 不如单独搜索（[外部参考](../research/memory-core-external-references.md)第 4、5 节）。所以高层图是另一条入口：检索负责"我知道要找什么"，图负责"我只有一个模糊的想法"。

**推进顺序（分析）**：接在 v0.8 第一份切片（复核，[写入链路](./memory-flow-write-path.md)第 2.1 节）之后，先把话题保留为经历节点并挂上记忆，再由馆长建立主题节点，最后加入常驻索引，每一步都可以单独验收。

### 2.3 时空图索引在设计中的定位（候选设计，不是 owner 决定）

第 4.1 节的决定（存储平铺，分层由派生索引承担）之下的展开。

**它替换的不是向量索引，而是"相似度检索是唯一入口"**。现在的 Qdrant 同时是真相、唯一的访问路径与写入时查重的依据；图索引与记录系统（第 3.2 节）到位之后，Qdrant 收缩为一个从真相派生、可以重建的相似度引擎，仍不可缺少：

1. "我知道要找什么"的直接检索：两篇文章的数据都表明单用 wiki 不如单用搜索、wiki 加搜索最好（[外部参考](../research/memory-core-external-references.md)第 4、5 节），检索仍是另一个入口，也是索引漏掉时的兜底。
2. 从模糊的想法落到图上的第一步：节点摘要本身也向量化后，一个模糊的问题先经向量检索落到几个起始节点，再顺着图往下走；相似度检索成为进入图的入口，而不是整条访问路径。
3. 建图与写入判断时的候选生成：新记忆该挂到哪个主题、哪些记忆语义相近却没有被链接，都靠相似度先给候选，补上索引的盲区，也为"聚类只提出候选"（第 2.2 节）提供原料。
4. 按名字与关键词精确匹配：项目名、组件名这类专有名词由稀疏向量负责，光靠图导航找不准。

在个人规模下还要不要为它单独运行一个服务，是[轻量化 Idea](./lightweight-footprint.md)中"更轻的嵌入方案与嵌入式存储"的问题，属于资源层面的独立决定。

**分层的位置**：

| 层 | 内容 | 谁写 |
|:---|:---|:---|
| 真相 | 记忆原子、Artifact 中的证据、断定边（取代、矛盾，第 2.4 节） | 唯一写入者 |
| 派生索引 | 相似度索引（Qdrant）；时空图索引（节点、归属边、节点摘要） | 由真相派生，可以重建；馆长维护 |
| 交付 | 常驻的小索引、检索结果、导航路径 | 按需组合 |

**原始证据的角色：用来对质，不是用来检索的知识库（分析，2026-11-15）**：把会话记录当知识库、用常规的 RAG 检索，噪声大、token 低效（第 1 节）；承担"用"的是维护过的关系索引与提炼过的记忆。原始层的角色因此是事实的底座：核实一条结论、按轨迹纠错（Anthropic 的 dreaming）、在结论冲突时作为裁决依据，以及审计。"锁定设计"的案例（[外部参考](../research/memory-core-external-references.md)第 6 节）正是靠回到原始记录才发现的。图索引负责导航、记忆原子承载知识、原始证据负责对质，三者各司其职，不互相替代。

时空图索引是一种访问结构，不是存储、不是真相，也不是写入者。它服务三类使用者：读者（从模糊的想法逐步走到具体的记忆）；写入时的判断（复核或馆长用它找到相关的记忆，决定新内容挂在哪里）；维护（节点就是一致性检查的作用域，按节点标脏，在节点内外检测冲突）。正因为它只是派生的访问结构，它可以参与写入判断，而不会让存储的形状重新绑住写入。

**索引参与写入后，第 2.1 节的限制怎样变化**：

| 第 2.1 节的限制 | 现在 |
|:---|:---|
| 第 4 点："该放在哪、库里已经知道什么"只能由全库相似度回答 | 解除：馆长顺着索引找到相关的主题与记忆，[写入链路](./memory-flow-write-path.md)第 2.1 节复核最弱的一环由此补强 |
| 第 5 点：状态类信息没有固定的位置 | 基本解除：主题节点就是固定位置，它的摘要指向"当前状态"那条记忆，记忆被修订时节点随之更新 |
| 第 2、3 点：每条记忆自带项目上下文，同项目的记忆在索引层相近，查重分不清 | 减弱但没有消失：检索仍单条返回记忆，记忆的索引层仍要能被单独找到；但读取时索引可以补上"属于哪个主题"的路径，写入判断依据索引与复核而不是相似度阈值，"同项目相近"不再直接导致误合并 |

**索引参与写入时的三点注意**：
1. 只用它找候选，不作为判断依据：派生的东西可能过时或出错；馆长用它找候选，下判断时读记忆原子与证据；检索保留为第二个入口，补上索引漏掉的部分。这与第 3.2 节"额外的信号只在候选内重排"是同一条规则。
2. 先确认节点是新鲜的：写入判断用到某个节点之前检查它的水位（VCP 的"按作用域标脏、查询时修复"），过时就当场修复或退回检索。
3. 防止索引的错误自我强化：写入更新索引，索引又引导写入，一条记忆挂到错误的主题下，后来相关的记忆就可能被继续引到错的地方。缓解：人工制定的节点作为不被自动改动的锚点；维护一侧定期把索引与"从原子完整重建的结果"对比，检查漂移（Perplexity 在上一版上增量更新，VCP 的快照是数据的纯函数可以重建对照，两者各取一半）。

### 2.4 关系层：关系保留，但存成关联表，不挂在原子上

**三种关系的去向**：

| 现在的字段 | 原本想表达的 | 在时空图索引下 |
|:---|:---|:---|
| `relates_to` | 两条记忆相关 | 上移到图索引：两条记忆挂在同一个主题节点下就表达了"相关"，主题之间的横向边负责导航；它是派生的，不该存在原子上 |
| `depends_on` | 一条依赖另一条 | 大多也上移，例如"某个项目依赖某个组件"是主题之间的边；原子之间的依赖（某个操作流程依赖某条配置事实）较少见，遇到再加 |
| `supersedes` | 新的取代旧的 | 留在原子一级，并会是关系的第一个真正用途：维护时检测冲突，检索时给被取代的记忆降权，读取时提示"已被 Y 取代"；以后的"互相矛盾"也属于这一类 |

原子之间真正需要的边只剩"取代"与"矛盾"这类与记忆演化有关的关系，导航用的边都在高层（第 2.2 节）。合并已经以另一种形式记录了取代（[总纲](./memory-flow-short-to-mid-term.md)第 2.2 节）；真正没有落脚处的是"不合并，但旧状态已经过时"的取代，两条记忆都保留，其中一条已不再成立，这正是 `supersedes` 边第一次有用武之地的地方。

**为什么不挂在原子上**：
1. 方向单一：数组只能从新记忆查到旧记忆，"X 有没有被取代"要反向扫描整个库；关联表可以在两个方向上建索引。
2. 改关系就要改内容：关系层不在可局部更新的字段中，改一次关系就是整条记忆的内容提交并生成版本；而关系的变化大多来自维护或索引重建，不该让原子的内容版本跟着变。
3. 边需要自己的属性：一条取代边要记下谁断定的（agent、馆长还是用户）、依据哪段证据、什么时候、现在是否有效，这与记忆本身"可追溯"是同一个原则；只放 ID 的数组装不下。

这正是 owner 所说"关系型数据库的设计哲学适用于记忆库"（第 1 节）：用关联表，而不是数组字段。

**边分成两种真相等级**：
- **索引边**：派生的，可以重建。主题与经历到原子的归属与引用边、主题之间的上下文边都属于图索引，坏了或过时了由馆长重建，适用第 3.2 节"派生物可丢弃"。
- **断定边**：属于真相，不能重建。取代与矛盾是馆长、agent 或用户作出的判断，与记忆一样需要来源与审计，不能清空后重算；当它与某次修订或合并出自同一个决定时，与相关的原子写入在同一个事务中提交（第 3.2 节的记录系统）。

这也让[写入链路](./memory-flow-write-path.md)第 4 节的边界更清楚：索引边主要由整理时的复核与馆长维护，断定边主要是生命周期维护的产物。

**现在怎么处理这个字段**：按 AGENTS.md [总纲](./memory-flow-short-to-mid-term.md)第 1.1 节，没有生产使用方的字段本不该存在，它是删除的候选；但删除会牵动 Qdrant 中的 payload 与版本快照的必备字段，属于契约变更。比较合理的是：关联表引入之前不在这个字段上构建任何东西；记录系统与关联表落地时，在同一次改动里删掉它。[Memory-Centric TDA Idea](./TDA_Memory_Centric_Agent_Ideas.md) 设想的原子级记忆图不因此失去基础：有了关联表与图索引，原子级的图随时可以派生出来用于分析，不必存在原子身上。

## 3. 存储与保存形态

### 3.1 保存形态：差别在系统维护的部分，不在内容格式

- [总纲](./memory-flow-short-to-mid-term.md)第 2.3 节中有使用方的非文本部分，都可以放在 md 旁边：EverOS 就是 md 作为真相、系统状态另存于 SQLite。所以 md 与记忆原子之间真正的取舍，在于谁能修改内容、系统怎样知道内容被改了，以及谁维护内容之外的状态。
- 这正是"锁死生成链路"的两面。锁住的好处是每次改动都有版本、来源与理由，合并与缓存失效的正确性有保证；md 的好处是任何工具都能直接修改。两者冲突：只要允许直接修改文件，就多了一个绕过唯一写入者的写入方，系统要么事后发现并补齐这些改动（EverOS 按内容哈希重建索引），要么放弃对每次改动的保证。也可以只换载体、写入仍经唯一写入者，但那样拿不到"普通文件编辑就够了"的好处。
- 文本做不到的，是必须由系统维护和保证、不能靠编辑者手写的东西：
  - 由使用产生的状态：写进文本，每次读取都成了一次编辑。现在已经实现。
  - 带类型、由系统在任一端变化时维护的关系：例如一条记忆被取代后，旧的一条自动降权。文本中的链接没有类型，内容一改就悄悄失效。对应 Hindsight 的"重复、改变、终止"判定与 SME 的取代链。现在只是预留字段。
  - 验证状态：确认过、已过时，还是被证明是幻觉。现在有字段、有显示，但没有写入方。
  - 不会漂移的证据：链接只是指向一个文件，Artifact 是冻结的快照。这一点的差别在于保证，不在格式本身。

  最可能让记忆原子超越文本的几项，恰好都是现在没有写入方的那几项。
- 保存形态与第 4.1 节、第 2.1 节绑在一起：选择文件作为载体，几乎就带来了目录（即分层）与常驻的索引文件（`MEMORY.md`、`USER.md` 正是用户偏好常驻的做法）。

### 3.2 索引不是真相（受 VCP 存储层启发）

- **第 4.2 节有了一个真实样本。** VCPToolBox 完整实现了"文件为真相、允许直接编辑"（[外部参考](../research/memory-core-external-references.md)第 2 节），它为此付出的代价就是这个选项的真实代价：每个路径的代际号、等文件稳定后再读、提交前复核、按文件版本 CAS、为重命名准备的向量回收站、墓碑与全量对账，做完这些也只换来最终一致，并且只能单进程。它的文件主要由日记插件写入，人直接改文件是被容忍的，不是主路径。
- **"索引不是真相"可能比"md 还是记忆原子"更根本。** 如果 v0.8 重新安排存储，可以让一个有事务的记录系统（sqlite 一类）保存内容与全部系统状态（生命周期、关系、验证状态、版本），Qdrant 降级为可以从它重建的索引：
  - 换嵌入模型、Qdrant 损坏或升级，都只需要重建索引；
  - 中期到长期的归档可以变成"移出检索索引"，而不是跨存储搬运，[总纲](./memory-flow-short-to-mid-term.md)第 2.3 节中 archive 与 revive 不是事务的问题随之消失；MemoryLibrary 文档对长期层的定位本来就是"让低活跃记忆可以退出高成本索引"；
  - 记忆原子与 Artifact 的提交可以进同一个事务，或者用 outbox 衔接。

  这不改变长期层的概念与它自己的维护规则（[总纲](./memory-flow-short-to-mid-term.md)第 1.1 节），只是物理存放的选择；owner 计划用 sqlite 存放长期层，它正好可以是同一个记录系统。
- **v0.8 可能新增的派生层，都可以套用"同一事务标脏、查询时修复"。** 常驻的分组描述（[写入链路](./memory-flow-write-path.md)第 2.4 节）、用户偏好文档（第 2.1 节）、跨经历归纳出的知识（[写入链路](./memory-flow-write-path.md)第 2.4 节），都是从记忆派生、可以重建的东西。它们落后于事实时，用 VCP 的新鲜度水位就能保证不读到过期内容，不需要可靠的事件投递。LLM 生成的派生物做不到逐位相同，但"输入签名不变就不重建"仍然适用。
- **复杂度上的教训。** VCP 的维护者拒绝了 MVCC 加不可变 segment 的分代索引方案，理由是 ANN 本来就不是真相，那套机制都是多余的。先让派生物可以丢弃，一致性机制就可以很简单。
- **额外的信号只在候选内重排，不改变召回。** VCP 的 Tag 图信号在一年里权限一再收紧：早期用图改写查询向量、直接决定召回谁，现在召回只用原始查询，图只能在 ANN 选出的候选内加一个上限约 0.21 的分。每次收紧都有记录在案的理由，例如弱的图证据把第 30 名推到第 1 名、大量真实查询整体退回 KNN。HiveMemory 今后加入关系、分组或使用状态等新信号时，可以守这一条。

## 4. 问题与决定（未决定的只列选项与影响）

### 4.1 中期库的形状（已决定，owner，2026-11-15）

**决定**：中期库的存储保持平铺，以记忆原子为单位；分层由一张派生、可以重建的时空图索引承担（第 2.2 节），读写两侧都可以使用。图索引是给读者的补偿性引导，归属关系只存在于索引中，记忆原子不搬进容器。

**为什么原来的问法对不上**：原先的三个选项把"存储怎么组织"（要不要把原子搬进容器）与"怎么访问"（从模糊的想法怎样走到具体的记忆）混在一起。决定回答的是前者：存储不变；后者由派生索引承担。

**原来三个选项的去向**（作为背景保留）：
- 保持平铺、结构在派生层形成：与决定最接近，派生层就是时空图索引；Perplexity 的 Brain 是这一形态的实例（[外部参考](../research/memory-core-external-references.md)第 5 节）。
- 整体分层（记忆归入组，组成为写入、合并与维护的单位）：不采用；它想要的"组"由索引中的主题节点承担，组内查重、状态的固定位置等好处由索引参与写入获得（第 2.3 节）。
- 只把读取方式不同的部分单独成层：并入索引，用户与各个 agent 是索引中的身份节点，常驻索引可以带上用户偏好的摘要，agent 节点可以被列全（第 2.1 节的问题由此解决）。

后续细节（索引参与写入时的注意事项、Qdrant 的角色、图索引在 v0.8 中的定位）是候选设计，见第 2.3 节。

### 4.2 记忆的保存形态

- **保留记忆原子，补上文本做不到的部分**：生成链路仍然锁定，由系统维护带类型的关系、验证状态等（第 3.1 节）。人与 agent 仍只能经特定方法修改。
- **md 作为内容载体、系统状态另存，写入仍经唯一写入者**：内容可读、可审、可移植，每次改动的保证不变；但不能直接编辑文件，拿不到"普通文件编辑就够了"的好处。
- **md 作为真相、允许直接编辑**：系统事后发现改动并补齐索引与状态（EverOS 的做法）。人与 agent 都能直接修改；代价是多了一个绕过唯一写入者的写入方，每次改动的版本、来源与理由不再有保证。

影响：与第 4.1 节的决定相关：存储保持平铺，分层由派生索引承担，所以选文件载体时，目录只作存放，不承担分层的语义（分析）；也决定[写入链路](./memory-flow-write-path.md)第 5 节汇合之后写出的是什么，以及维护要怎样识别内容被谁改过。第三项的真实代价见第 3.2 节的 VCP 样本。不论选哪一项，都可以同时考虑让 Qdrant 不再是真相，只作为可以从记录系统重建的索引（第 3.2 节）。如果把记忆直接作为文件暴露给外部 agent、让它们用普通的文件工具读取，PRIVATE 这类可见范围就无法执行（[外部参考](../research/memory-core-external-references.md)第 5 节第 9 点）。
