# 孵化场、试验场与垃圾回收场：低成本地定型、验证与搁置想法

## 0. 文档性质

本文是三个场的设计，回答怎样让"和现在的项目接不上轨"的想法也能被低成本地定型、检验或搁置：孵化场定型还说不清的想法，试验场在冻结的真实数据上证明机制有效或无效，垃圾回收场冷藏说不清的想法与失败的方案（第 4 节开头）。文件名沿用最初的 `experiment-field.md`。

三个场是项目的开发规范，不绑定版本。体系成型之后由事实文档记录三场体系，本文随之归档。

- 孵化场与垃圾回收场已经在用，设计见第 4 节开头与第 4.8、4.9 节；试验场尚未建立，它是 v0.8 评测的承载（第 6 节），第 4.1～4.7 节的细节是候选设计。
- 第 1 节是 owner 的出发点；第 2、3 节是现状与问题。
- 与 v0.8 评测的关系：[评测集](./memory-evaluation-benchmarks.md)回答"用什么题目检验记忆核心"，本文回答"在哪里、用什么数据、怎样隔离地跑起来"。评测与试验共用同一套快照、评分器、对照与试验实例（第 6 节）。

## 1. 出发点（owner）

- owner 有一部分天马行空的想法，几乎完全跟现在的项目接不上轨。它们要么写在 Idea 里，要么只在脑子里有一个模糊的概念。
- 试验场是与 v0.8 方向并行的另一个要点，参考 VCP（VCPToolBox）的开发方式（第 3 节的外部观察）：利用 agent 的主观能动性，快速做出一个想法的原型，再据此判断它之后是否值得工程化到项目中。
- 现在有两套数据：开发版本的数据库，以及日常插件接入使用的数据库。如果试验场需要隔离出第三套，直接写进本文。第 4.4 节给出的判断是：需要第三类，但不是一个长期存在的库，而是按需建立、用完即删的试验实例。
- 记忆核心 Patchouli 有四个大命题：记忆写入（生成）、记忆读取（检索）、记忆使用（编译器、MaaT 与最终 agent 的表现）与记忆维护；它们共同的底座是记忆系统的架构，包括短期、中期与长期记忆的形态定义，以及三个库的形状。记忆系统之外是“系统生态”，以及 Alice 的多智能体系统（例如任务进程）。
- owner 的想法往往还不成熟：很多时候只有一个模糊的想法，或者是从别的工作、论文里看到的做法，想尝试一下，却并不明白自己真正想要的是什么。交给 agent 的任务因此不准确、不全面，agent 一实施就开始漂移；owner 反复参与修改方案，在这个过程中才逐渐认识到想达成什么，也可能开始膨胀，什么都会发生。例如手机备忘录里的一条：“记忆的渐进式披露理念与前缀树算法的某种联系，以及可能的启发？”（来自某个视频的评论区）。这是纯粹的抽象，没有验收目标；agent 给出的方案会进一步触发思考，于是被带着跑；如果就此停下，之后再想这个想法，思路和理解可能就断了。
- owner 跟着直觉走：觉得哪个看起来是对的就推进，不太对就退回去重新考虑，始终处在核心的决策位置，没法放开。原因之一是不完全信任 agent，之二是希望始终保持透彻的理解，因为 owner 才是维护者。owner 同时是产品经理与 tech lead，既管全局又管实现细节，对代码结构要求很高，时常重构以控制复杂度。这些因素叠加，使 owner 成为效率最大的瓶颈，也是最费精力的位置。
- 三个场的比喻：先有一个"孵化场"，用来定型那些完全模糊的想法；再是"试验场"，集中通过实验证明机制的有效性或无效性；再有一个"垃圾回收场"，记录那些未能成功明确的想法和失败的试验方案。这样可以让现有的 Idea 文档真正起到指导设计与计划的作用，而不是平铺。

## 2. 现状（以代码为准）

- **回放脚本**：[`memory_replay.py`](../../scripts/memory_replay.py) 只读已有数据，结果写到调用方给出的位置，不启动后端，也不写记忆。
  - `export` 从一个 Workspace 的 Artifact 目录导出被动结算的生成材料，以及每条记忆建成时的类型与正文；
  - `extract` 与 `classify` 用当前的提取器，或一份自定义提示词，把同一批材料重复跑几次；
  - `agreement` 统计多次运行是否一致。

  它没有标准答案，也不经过话题、查重与检索（[评测集](./memory-evaluation-benchmarks.md)第 2 节）。
- **两套实例**（[桌面客户端](../frontend/desktop-client.md)第 1、5 节）：

  | | 安装版（日常，插件接入） | 用 checkout 运行（开发） |
  |:---|:---|:---|
  | 数据根 | 用户选择，默认 `%LOCALAPPDATA%\HiveMemory` | 仓库根 |
  | Qdrant 存储 | `<数据根>\.hivememory\qdrant` | `.hivememory\dev.env` 中的存储路径 |
  | 端口 | 固定 8769、6333、6334 | `.hivememory\dev.env` 中的三个端口，缺省与安装版相同 |

  插件都写死了 8769。因此谁占着 8769，日常 harness 的检索、写入与回流就进到谁那里。

  数据根由 `HIVEMEMORY_DATA_ROOT` 指定（[`config/files.py`](../../src/hivememory/config/files.py)），路径不能超过 100 个字符（`qdrant.exe` 的路径限制）。Qdrant 的地址、端口与集合名都是 `patchouli.storage` 的配置项（[`config/patchouli.py`](../../src/hivememory/config/patchouli.py)），配置里没有进程内的本地模式；集成测试用的 `:memory:` 是在测试里替换客户端得到的。
- **可以当作标签的使用信号**：
  - 经 MCP 的检索、读取、写入与更新，都会作为普通工具调用留在会话记录里，回流时带回声标记再次导入（[MCP 记忆访问](../contracts/mcp.md)第 6 节）；
  - 工具调用与结果的原文随 InteractionArtifact 的 `turn_events` 快照保存（[Artifacts](../patchouli/artifacts.md)）。
  - 推断：从中可以还原"检索了什么、随后读了哪几条"，需要核对。
  - 删除不留单独的记录。被动提取的留存统计，是用 memory_creation Artifact 与库的现状对比得出的（[被动提取的膨胀与留存](../todo/passive-extraction-volume-and-retention.md)）；owner 只顺手删过一部分，删除信号偏弱（[评测集](./memory-evaluation-benchmarks.md)第 1 节）。
- **试验实例与第一个插座**：[`trial_instance.py`](../../scripts/trial_instance.py) 在一次运行目录下建立独立的数据根，有自己的配置覆盖、访问登记、Qdrant 存储与端口，每个用户一个 Workspace，每次从空库开始；端口被占用或属于安装版时拒绝启动。[`halumem_eval.py`](../../scripts/halumem_eval.py) 是“写”插座的驱动、评分器与报告：把 HaluMem 的对话逐次会话导入试验实例，按官方协议判抽取与更新，报告可以并排几次运行并向账本追加一条。用法见[在 HaluMem 上评测记忆生成](../help/halumem-evaluation.md)。
- **代码检查的范围**：
  - 注释自包含的架构测试扫描 `src`、`tests`、`scripts`、`integrations`（[`test_self_contained_comments.py`](../../tests/unit/architecture/test_self_contained_comments.py)）；
  - `ruff check .` 与 `black --check .` 覆盖整个仓库；
  - 覆盖率只统计 `hivememory` 包。
- **与 v0.8 评判方式的关系**：[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节把评判分为"单轮的底线"与"长程的演化质量与人工介入"。owner 的日常使用是现成的长程试验场，只用于验收已建成的机制；"样本统计不作为设计依据"是 v0.8 的原则（总纲第 1.2 节）。

## 3. 问题：为什么这些想法接不上轨

现在检验一个想法，唯一的办法是接到生产架构上：先想清楚它落在 Patchouli、Workspace 还是生成队列的哪一处，按分层与所有权写进 `src`，过架构测试与文档门禁，再靠日常使用慢慢暴露问题。

对于从当前代码延伸出来的想法，这条路可以走通。对于天马行空的想法，第一步就会卡住：还不知道它值不值得做，就得先为它设计接轨方案。于是这些想法只能留在 Idea 或脑子里，既没有被证实，也没有被否定。

需要分开的是两件事：

- **接轨**：怎样嵌进生产架构；
- **验证**：它到底有没有用。

插座放在代码层时，验证必须等接轨完成。插座放在数据层（第 4.2 节）时，可以先验证，再决定值不值得接轨。大多数想法过不了验证这一关，为它们设计接轨方案的成本也就省下了。

外部观察（2026-11-18，对 VCPToolBox 的只读调研，不在本仓库）：该项目在冻结的库副本上为一套新几何单独建了索引，只比较输出，一夜跑完十余轮预注册实验，迭代很快。它同时留下了两个反面教训：

- 指标是自指的（返回的候选重构查询向量的程度、近似索引逼近自身精确几何的程度），没有相关性判断；
- 终验失败后仍然切换了生产默认，并删除了实验记录。

第 4.5 节的规则针对这两点。

## 4. 设计

**三个场**（按 owner 的比喻组织，第 1 节）：

| 场 | 进来的是什么 | 出去的是什么 | agent 做什么 | owner 的位置 | 本文 |
|:---|:---|:---|:---|:---|:---|
| 孵化场 | 完全模糊的想法、从别的工作或论文看来的做法 | 写进 Idea 的设计，或写得出五行卡片的想法 | 发散：给出互相不同的解读 | 必须在场，凭直觉挑选 | 第 4.8 节 |
| 试验场 | 带指标的五行卡片 | 淘汰、继续迭代或毕业的结论 | 收敛：实现原型、跑对照 | 看结果、做裁决 | 第 4.1～4.7 节 |
| 垃圾回收场 | 孵化不出来的想法、试验失败的方案 | 偶尔有一条复活，回到孵化场 | 提出新解读之前先查这里 | 几乎不花精力 | 第 4.9 节 |

流向：

- 孵化场 → Idea：定型为设计，写成设计陈述；
- 孵化场 → 试验场：写得出五行卡片的第三行（第 4.3 节）；试验场建立之前，先冻结进垃圾回收场；
- 孵化场 → 垃圾回收场：时间盒用完仍然说不清；
- 试验场 → 垃圾回收场：被淘汰；
- 试验场 → 毕业：写进对应的 Idea，按治理规范建立 Plan；
- 垃圾回收场 → 孵化场：复活条件满足。

孵化不是必经之路：问题能说清楚的，直接作为 Idea 的开放问题由 owner 决定；只有 owner 自己还说不清想要什么时，才进孵化场。计划只从 Idea 派生，三个场都不派生计划。

**笔记的位置与边界**：孵化场与垃圾回收场是工作笔记，放在仓库的 `.hivememory/fields/`，不提交，也不受文档治理（没有状态值、索引与入链规则）：

```text
.hivememory/fields/
  incubator/<题目>.md   孵化场：一个题目一份
  graveyard.md          垃圾回收场
  experiment.md         试验场的占位
```

它们与 Idea 的读者不同：Idea 的读者是写计划、判断设计是否成立的人，内容是设计；孵化备忘的读者是下一轮孵化，内容是过程；垃圾回收场的读者是提出新想法之前的 agent。所以讨论过程与搁置的想法不写进 Idea，其他 Idea 与当前文档也不链接这些笔记，引用方向只有笔记指向 Idea。

### 4.1 定位与边界

- 试验场检验已有的想法，决定淘汰、继续迭代还是毕业；**不从数据里推导设计**，与"样本统计不作为设计依据"一致。
- 试验场**从不写日常数据**。它对日常实例的唯一一次接触，是建立快照（第 4.4 节）。
- 原型代码不进 `src`，`src` 也不导入试验场的任何东西。想法毕业时按正式设计重写，不搬运原型。
- 试验场不是第三套生产数据，不承载 owner 的日常使用。

### 4.2 三层：快照、插座、对照

**快照（冻结，只读）**

每份快照有一个快照 id，以后不再改动。内容分两部分：

1. **冷拷贝**：日常数据根中的 Qdrant 存储与 Artifact 目录。快照**不包含** `configs` 下的密钥与访问登记文件，凭证与回放脚本一样取自环境变量和 `.env`。
2. **派生视图**：从冷拷贝导出的 JSONL，供不依赖 HiveMemory 的原型读取：
   - 生成材料与建成时的记忆（沿用 `export`）；
   - 当前正式记忆的 index 与 payload；
   - 从 `turn_events` 还原的检索与读取记录；
   - 由 creation Artifact 与库现状的差集推出的删除，以及由版本 Artifact 推出的合并。

快照放在仓库外由调用方给出的试验根目录，含私有内容，不提交。

**插座（固定的任务与评分器）**

不论想法多天马行空，只要它属于记忆系统，就会落到下面某一个插座上。四个插座与第 1 节 owner 列出的四个命题一一对应（写入对应写、读取对应找、使用对应用、维护对应整理）；记忆系统的架构、系统生态与多智能体系统不在插座之内，按第 4.3 节第三档进场：

| 插座 | 输入 → 输出 | 外部判断从哪来 | 可衔接的公开评测（[评测集](./memory-evaluation-benchmarks.md)） |
|:---|:---|:---|:---|
| 写 | 交互材料 → 记忆条目 | owner 保留与删除的记录；人工抽检 | HaluMem 的抽取与更新 |
| 整理 | 记忆集合 → 合并、遗忘与关系 | owner 的合并与删除；人工标注的成对关系 | MemoryAgentBench 的冲突消解 |
| 找 | 查询 → 排好序的记忆 | 检索之后随即读取的隐式正例，再人工抽检 | LongMemEval S 版分层抽样 |
| 用 | 记忆 + 任务 → 行动结果 | 任务成败 | MemoryArena、DreamBench-SWE |

另有一种跨插座的运行方式，称为**快进回放**：

- 做法：在试验实例上，把快照中的历史交互按原来的顺序，交给一个候选机制重新走一遍"写"与"整理"；
- 观察：库的健康走势，即重复、过时与互相矛盾的数量随时间收敛还是累积，以及一个裁判模型会删掉多少条（近似人工介入量）；
- 意义：这是[总纲](./memory-flow-short-to-mid-term.md)第 4.2 节"统一的检验题"（候选机制连续跑一个月，库会收敛还是退化）的压缩版，几小时代替一个月；
- 局限：它只能近似，不替代 owner 的日常使用。

**对照**

同一份快照上同时跑三类对照：

- 当前 HiveMemory 的行为；
- 朴素基线：BM25、只用 dense，以及"把全部历史直接交给模型"；
- 上一次毕业的方案。

没有对照的数字不进入判断。

### 4.3 想法按成熟度分三档进场

| 档位 | 例子 | 进场方式 |
|:---|:---|:---|
| 只在脑子里的模糊概念 | 一个直觉或比喻 | 先写一张五行卡片：一句话说清想法；它落在哪个插座；如果成立，哪个数字会变、往哪个方向变；最便宜的验证用多少数据、多长时间；什么结果算失败。第三行写不出来，就说明还不能实验，先进入孵化场（第 4.8 节） |
| Idea 中的长期想法 | [Memory-Centric Agent TDA](./TDA_Memory_Centric_Agent_Ideas.md)、[库的形状与图索引](./memory-library-shape-and-index.md) | 从文档里抽出一条可以检验的主张。TDA 那份文档第 0 节列出的前提（离线只读、先建扁平检索与普通图指标的基线、在真实记忆空间里验证 component 与 cycle 是否有稳定且可行动的语义）可以直接作为入场条件。例如：H0 连通分量能否找出 owner 合并或删除过的重复簇，属于"整理"；拓扑感知检索在隐式正例上能否胜过扁平检索，属于"找" |
| 系统形态与愿景级的想法 | [AE2 同构](./ae2-hivememory-architecture-analogy.md)（子网、Pattern、Crafting CPU）、全局共享、全自主维护 | 四个插座量不出这类想法，换两种实验：**spike**，做最小的端到端原型（如两个试验实例作为子网互相调用，或把一组可应用的记忆当作 Pattern 交给 agent 完成一类重复任务），证据是第一处摩擦出现在哪里，而不是分数；**仿真**，几个 agent 在同一个试验实例上协作跑任务，统计重复、冲突与陈旧，用裁判会删掉多少条近似维护成本 |

### 4.4 实例隔离：第三类数据

| | 日常实例 | 开发实例 | 试验实例（新增） |
|:---|:---|:---|:---|
| 用途 | owner 的日常使用、插件接入 | 开发与调试 | 跑实验 |
| 数据从哪来 | 真实使用 | 开发过程中随意写入 | 从快照复制而来 |
| 状态 | 持续演化 | 随开发漂移，不可复现 | 每次运行开始时都等于某个快照，可以复现 |
| 生命周期 | 长期 | 长期 | 一次运行一个，跑完删除，只保留结果 |
| 端口 | 8769、6333、6334 | 缺省与日常相同 | 必须避开这三个端口，候选默认 18769、16333、16334 |
| 试验场能否写 | 不能 | 不能 | 只写自己 |

为什么需要第三类，而不是直接用开发实例：

1. **可复现**：开发实例的内容随开发与调试漂移，同一个实验隔几天重跑，输入已经不同；实验的写入也会反过来污染开发调试。
2. **端口与插件**：开发实例的端口缺省与日常实例相同，插件又写死了 8769。试验实例只要占了 8769，日常 harness 的真实流量就会写进实验数据。所以试验实例必须用另一组端口，并且关闭插件代为安装（只有安装版会打开这一项）。
3. **并行与重置**：公开评测要求每份历史一个独立的库（[评测集](./memory-evaluation-benchmarks.md)第 4 节），一个想法的几个变体也要同时跑。这些需要按需复制、用完即删的多份实例，长期存在的单个库做不到。

候选做法：

- **建立快照（默认冷拷贝）**：日常实例正常退出后，复制数据根中的 Qdrant 存储与 Artifact 目录，再启动日常实例。日常数据只在这几分钟里被读一次。备选是 Qdrant 的快照接口：不用停机，但会在日常实例一侧写出快照文件，再恢复到试验实例。
- **建立试验实例**：在试验根目录下为一次运行建一个数据根，从快照复制 Qdrant 存储与 Artifact，用 `HIVEMEMORY_DATA_ROOT` 与 `patchouli.storage` 的端口配置指向它，起一个独立的 Qdrant 进程。整个过程只用现有配置项，不新增生产配置。注意：数据根路径必须在 100 个字符以内。
- **不需要实例的实验**：只读派生视图、在进程内算基线的原型（多数"写"与"整理"的实验）根本不必起实例。

### 4.5 运转方式与规则

流程如下：

1. 写一张卡片（第 4.3 节）；
2. 以本文与试验根中的数据说明作为施工依据，交给 coding agent；
3. agent 在试验根下实现原型，跑完对照；
4. agent 按固定模板交报告：预注册的内容、每个对照的数字、失败样本、成本；
5. owner 决定淘汰、继续迭代还是毕业。

规则：

- **跑之前先预注册**：写下三行，即假设、指标、门槛；跑完之后不改门槛。
- **指标必须依赖外部判断**：owner 的行为（保留、删除、合并、读取）、人工抽检、公开评测的标准答案或任务成败。只衡量系统与它自身一致性的量（重构了自己、逼近了自己、与旧结果重合多少）可以用来检查实现，不能用来证明"更好"。
- **钉住输入**：每次运行记录快照 id、代码版本、提示词与配置的哈希、模型。
- **结果账本只追加、不删除**：失败的实验同样入账，写明为什么失败。这样已经否定过的想法不会反复回来，也能看出哪个方向失败了很多次。淘汰的方案同时登记进垃圾回收场（第 4.9 节）。
- **毕业条件**：在留出的切片上胜过对照；在生产架构里找到了它接入的位置；成本可以接受。三条都满足之后，结论与数字写进对应的 Idea（满足 [Ideas 升级规则](./README.md)第 1、3 条的证据要求），再按治理规范建立 Plan，按正式设计重写进 `src`。

### 4.6 代码与数据放在哪（候选）

- **仓库内只放试验台**：快照导出、派生视图、插座的评分器与对照跑分，写成 `scripts/` 下的脚本，沿用 `memory_replay.py` 的写法（只读输入、结果写到调用方给出的目录、不启动日常后端）。这样它们自动受 ruff、black 与注释自包含测试约束，不需要新目录，也不需要新的配置项；用法说明写在 `docs/` 中，`scripts/` 下不放 README。
- **仓库外的试验根**：快照、试验实例、原型与结果账本放在调用方给出的目录，不提交。原型可以用任何语言或库实现，不受仓库的分层、类型与覆盖率要求约束。

备选：在仓库顶层新建一个提交原型代码的目录。好处是原型有版本记录、可以评审；代价是多出一个不受分层规则管理、却与源码同仓的区域。本文默认不这样做。

**现状**：第一版按默认做法：试验台是 `scripts/` 下的两个脚本，试验根是开发 checkout 中被 git 忽略的 `.hivememory/lab/`（数据集、官方评判提示词、运行目录与结果账本）。

### 4.7 最小的第一版

第一版只做三件事：

1. **试验实例**：独立的数据根与端口，每次运行从空库开始；公开评测集的历史导入试验实例。日常数据的快照导出（正式记忆、检索与读取记录、删除与合并，以及冷拷贝的步骤）留给第一个用日常数据的插座。
2. **一个带外部判断的插座**：“写”，外部判断来自 HaluMem 的标注（要点、更新与干扰），对照是一次性生成与馆长两种结算方式。v0.8 改的是写入一侧，所以第一个插座先测写；“找”的隐式正例（检索之后随即读取）留给之后。
3. **对照跑分器、报告模板与结果账本。**

第一版不处理：

- "找"与"用"插座；
- 日常数据的快照；
- 快进回放；
- 多个变体并行的实例编排；
- 任何界面。

第一版的首个公开插座是 HaluMem 的抽取与更新（[评测集](./memory-evaluation-benchmarks.md)第 6 节）。之后再用一个便宜的想法试运行“找”插座的整条流程，例如"检索前对向量做部分去均值"；再用一条 TDA 主张作为第一个真正"接不上轨"的用例。

**现状**：第一版的三件事已经建成（第 2 节），并在 HaluMem Medium 的 5 个用户上对照了一次性生成与馆长，结果见[评测集](./memory-evaluation-benchmarks.md)第 6 节。跑之前在账本写下预注册（假设与门槛），跑完逐条核对，没有改门槛。实际运转中补上的做法：

- 先用 1 个用户的前 10 次会话试跑，核对“取出的记忆完整”（按会话重放取出的记忆，与实例最终的库逐条比对）与评判的解析失败率，再跑全量；
- 评判模型与生成模型必须不同，并随机抽 10% 的调用复判，一致率作为评判本身波动的底线，几个百分点以内的差距按逐用户的方向来读；
- 两种方式各用一个试验实例、一组端口，同时运行。

差距：账本只记次数与馆长的 token，路由与一次性生成的 token 没有记录，花费以提供商账单为准；一个变体只跑了一次，没有重复运行的方差。

### 4.8 孵化场：定型还说不清的想法

第 1 节描述的漂移，原因不全在 agent，也不全在 owner：想法还没成形时，就被放进了执行模式。agent 拿到一个模糊的想法，默认会交出一份完整方案；方案一出来，空白就被它的假设填满了。owner 对着方案作反应——这里对、那里不对、这个点有意思——于是被带着跑，范围也随之膨胀。第 4.3 节的五行卡片要求写出“如果成立，哪个数字会变”，已经假设想法相当成熟；大多数想法还停在它之前的一个阶段。

在试验场之前加一个孵化场，规则与试验不同：

| | 孵化场 | 试验场（第 4.3、4.5 节） |
|:---|:---|:---|
| owner 知道要什么吗 | 不知道 | 知道，写得出会变的数字 |
| agent 做什么 | **发散**：给出三四种互相不同的解读，不给方案 | **收敛**：实现原型、跑对照 |
| owner 做什么 | 凭直觉挑一个、否掉几个，说出否掉的原因 | 看结果、做裁决 |
| 产出 | 一个更尖锐的问题 | 淘汰、继续迭代或毕业的结论 |
| 什么时候结束 | 写得出五行卡片的第三行，转入试验场 | 结论出来，或者时间盒用完 |

**每种解读写三件事**：一句话说清“如果是这个意思，会改变什么”；它落在哪个命题上（四个插座之一，还是记忆系统的架构、系统生态或多智能体系统）；最便宜的验证是什么。owner 本来就按“哪个看起来对就跟哪个”工作，这样用的正是直觉，又不会被一份完整方案牵着走。

**每轮孵化结束时写五行记录**，写在备忘这一轮的末尾，下次从这里接着想：

1. 当前的理解；
2. 否掉了什么、为什么；
3. 是什么触发了新的想法；
4. 下一个问题；
5. 下次从哪里接着想。

这五行也正是记忆系统以后应当自动沉淀的那种“经历”。在它能做到之前，用备忘代替，同时也是拿自己的使用场景检验记忆系统。

**备忘的写法**：一个题目一份 `incubator/<题目>.md`。开头三行写所服务的 Idea（没有时写“无”）、所落的命题（四个插座之一，或记忆系统的架构、系统生态、多智能体系统）与状态（孵化中、冻结或已定型）。之后按轮只追加，每一轮写 Claude 给出的解读、owner 的选择与否掉的原因（原话）、五行记录；最后一轮的五行记录就是这个题目当前的状态，不另设卡片或账本。提出解读之前先查垃圾回收场（第 4.9 节）。

**出口**：

- **定型为设计**：owner 的回答写进所服务的 Idea，写成设计陈述，不带讨论过程；被否掉、仍值得留的解读转进垃圾回收场。备忘标为已定型，注明结论落在 Idea 的哪一节；笔记不提交，所以定型的备忘保留。
- **需要试验**：写得出五行卡片的第三行（第 4.3 节）。试验场建立之前，冻结进垃圾回收场，复活条件写“试验场建立”。
- **时间盒用完**：几轮之后仍然挑不出一个解读，就冻结进垃圾回收场，备忘保留，不要拖着；搁置的想法有记录可接，不会从头再来。候选：连续三轮没有选中任何解读时，Claude 提议冻结，由 owner 决定。

**示例**：第 1 节那条备忘录，展开成三种解读——

- **检索结果按层展开**：`memory_search` 只给标题与摘要、`memory_read` 才给全文，已经是两层；推广为“经历节点 → 记忆 → 段 → 原始事件”的 N 层，后两层由[写入链路](./memory-flow-write-path.md)第 5 节的轮次指向提供。若成立，改变的是读的一侧：agent 先拿到很短的前缀，按需往下钻。
- **常驻上下文的稳定前缀**：模型的前缀缓存要求提示词开头稳定；常驻索引按“越稳定越靠前”排列，披露只在尾部增长。若成立，改变的是常驻小索引的组织方式与 token 成本。
- **别名的命名空间**：别名已经带类型前缀（`fact_`、`res_`）；按层级命名之后，按前缀浏览本身就是一种渐进式披露。若成立，改变的是寻址方式，而不是检索。

owner 可能一眼否掉两种，或者发现自己想的是第四种；这一步产出的是“原来想的是这个”这样一句话。

**owner 的位置**：不需要放手决策，减少的是每个决策的准备与检查成本。

- 决策权留在 owner，agent 交来的是可以挑选的解读与选项，而不是需要逐行审阅的方案；
- 每次为控制复杂度而重构，问一句它的理由能不能写成一条规则或一个架构测试；分层与注释的规则已经这样做，owner 在结构上放得了手，是因为测试替 owner 守着；
- 孵化需要 owner 在场，试验与执行不需要：分开安排，试验与执行交给独立的会话。

### 4.9 垃圾回收场：冷藏说不清的想法与失败的方案

名字对应 HiveMemory 生命周期里的垃圾回收：那里的回收不删除记忆，低生命力的记忆被归档进冷存储（长期层），需要时经 `MemoryLibrary.revive` 复活回中期库（[垃圾回收器](../../src/hivememory/engines/lifecycle/garbage_collector.py)、[MemoryLibrary](../../src/hivememory/memory_library/library.py)）。垃圾回收场按同样的方式对待想法：

- **不删除，只冷藏**：`graveyard.md` 一行一条，来源有三种：孵化场时间盒用完的题目、定型时被否掉但还值得留的解读、试验场淘汰的方案。每条写名称、来自哪个场、停下的原因、复活条件，以及记录所在的位置（备忘的路径，或实验报告）。
- **带复活条件**：写明什么变化会让它值得再试，例如有了新的数据（带响应序号的交互记录）、某个机制已经落地、模型的能力或成本到了某个程度。复活条件满足时，这一条回到孵化场，从它留下的五行记录接着想，并从 `graveyard.md` 删掉这一行。
- **先查再提**：agent 在孵化场给出解读之前，先在这里查有没有同一个想法或相近的解读；有的话说明它当时为什么停下、复活条件是否已经满足。已经否定过的想法不会换个说法再提一遍。
- **放弃变得便宜**：停下只是冷藏，有记录可接；时间盒用完时，更容易真的停手。

## 5. 主要未知项与验证方式

| 未知项 | 怎样验证 |
|:---|:---|
| 从 `turn_events` 能否完整还原"检索 → 读取"的序列，以及 Alice 原生对话与插件会话的记录是否同样可用 | 在一份快照上导出，抽样与会话原文对照 |
| 隐式正例的偏差：只有被展示的结果才可能被读取，排在前面的更容易被读 | 人工抽检一批未被读取的检索结果，估计漏标的比例 |
| 冷拷贝的大小与耗时（Artifact 与 Qdrant 存储合计可能达到数百 MB） | 第一次建立快照时记录 |
| 试验实例与日常实例的检索行为是否一致（同一份数据、同样的配置） | 在快照上用同一组查询对照两边的结果 |
| 裁判模型近似"owner 会删掉哪些"有多准 | 用 owner 已经删除过的记忆做一次校准 |

## 6. v0.8 评测的承载

**设计**：试验场是 v0.8 评测的承载。评测壳就是试验台加试验实例：公开评测集的历史导入独立的试验实例（第 4.4 节），由试验台的评分器与对照跑分；[评测集](./memory-evaluation-benchmarks.md)选定的首个切片成为第一个公开插座（第 4.2 节的插座表）。
