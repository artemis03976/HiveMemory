# 短期记忆：话题的进展及其维护

## 0. 文档性质

本文是短期记忆的设计：短期记忆以话题为载体，话题的进展回答“进行到哪一步”；包括它由什么组成、什么时候写、话题的生命周期与存储、折叠，以及前台在什么时候用到它。V1 在 v0.8.1 中实现并初步成立，之后的演进见第 1.5 节。正文是已定的设计，候选设计标“候选”；已经实现的部分以当前事实文档为准，本文只链接。

相邻的设计各在一处维护：一轮进行中的事件接收、封口与恢复见[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)；原始资料的保存见[全链路原始资料保存](./PatchouliPageFoldingRawEvidenceDesign.md)；沉淀时写什么、主动写入能拿到什么材料，属于短期到中期的过渡，见[写入链路](./memory-flow-write-path.md)与 [v0.8 总纲](./memory-flow-short-to-mid-term.md)；会话与话题的交接与路由见[外部会话 Idea](./external-session-and-topic-projection.md)。

## 1. 目标与原则

### 1.1 要解决的问题

- 长上下文的遗忘与注意力衰减是短期记忆的问题。各 harness 用会话压缩应对，但压缩会丢细节、让注意力漂移。
- 记忆要对 agent 起作用，最好的干预方式是直接把信息注入它的上下文，短期、中期与长期记忆都是如此。controller 模式下 agent 由 HiveMemory 运行，记忆系统本身就是对 agent 的上下文管理工程；plugin 模式下前台上下文属于 harness，HiveMemory 处于被动地位，只能提供信息。两种模式共有的是话题这一环，所以从话题入手。
- 话题若只被 Patchouli 用来生成记忆，对前台就没有直接用处：交互从会话流进话题，前台还要能把话题的进展读回来（第 7 节）。
- 话题停下一段时间就离开话题池，会把一段连续的对话切成几个话题，后台的话题反而比前台的会话更不连贯：结算拆开之前的日常实例 11 天中，77 个因停下超时而结算的话题有 32 个在 2 小时内被同一会话续上，续上的 65 次里有 48 次开了新话题。所以停下够久只沉淀、不退役（第 5 节）。

### 1.2 定位

- 短期记忆是基于话题机制的一套上下文控制工程，由话题路由、进展记录、折叠、沉淀与退役以及读回组合而成。controller 模式下它是对 agent 上下文管理的一部分；plugin 模式下它管理 HiveMemory 保管的这一份上下文，只向前台提供信息。前台的会话压缩属于 harness 与 Alice（第 8 节）。已经成立的跨层不变量见[短期记忆](../architecture/short-term-memory.md)。
- 短期记忆的单位是话题：交互按内容跨会话归并进话题，每个话题一条只追加的日志。按时间线切段由交互记录的推进进度承担：交互只按顺序追加，折叠、进展记录与沉淀各自记下推进到第几轮，不另按会话切段。
- 与中期同构：中期由整理过的记忆和作为证据的原始交互组成；短期由话题的进展（整理过、随交互推进而增长）和话题的交互记录（次级的完整记录）组成。
- 话题的进展回答“进行到哪一步”。前台的上下文按会话组织、会被压缩；话题按内容组织、原文完整。所以“先讨论 A、做了十几轮 B、再回到 A”时，前台丢掉或混在一起的东西，可以从 A 的话题里拿回来。
- 进展记录是索引：每一条指回原文，agent 可以照着它回查之前的交互。
- plugin 模式下话题提供信息，不控制前台上下文，与被动地位相容，话题向前台的流动只是读出；controller 模式下话题的进展最好直接注入 agent 的上下文，两种模式的分工见第 1.4 节。会话与话题不共享状态、互不控制，这已是跨层不变量，见[短期记忆](../architecture/short-term-memory.md#8-必须守住的规则)第 8 节。
- 话题的短期记忆不局限在轮次上：长 turn 下的短期记忆管理由本设计一并承担，写一条与折叠的切点都可以落在一轮之内；这是 V2 的内容，V1 以整轮为单位（第 1.5 节）。

### 1.3 原则

- 资料退出某个模型视图、原文是否继续保存、是否生成正式 Memory，是三个独立判断。话题也不等于“尚未写入 Memory 的队列”：主动 WRITE 可能已物化，相关交互仍留在话题中。
- 已整理的内容只往后追加，不被递推重写：多次整段重写会让细节漂移。
- 触发先用简单规则，规则定义在事件序列上，与事件什么时候到达无关。
- 话题可以是 agent 的一项工作，也可以是一段讨论或闲聊；进展的结构、触发与写法对 agent 工作流与对话流都成立，措辞不假设话题是工作：前者回答做到哪了，后者回答聊到哪了。

### 1.4 两种接入模式的分工

短期记忆分成内容与送达两侧。内容是记住什么、怎样整理；送达是怎样把话题的进展交到 agent 手里。

| 侧 | 包括 | plugin 模式 | controller 模式 |
|:---|:---|:---|:---|
| 内容 | 话题的单位与交互记录、推进进度、进展记录、折叠、沉淀与退役、日志与重启读回、句柄与渲染 | 共用 | 共用 |
| 送达 | 话题的进展怎样进入 agent 的上下文 | 拉取为基线，会话压缩之后只推指针（第 7 节） | 直接注入 agent 的上下文，还没有设计（第 9 节搁置项） |

- **内容一侧两种模式共用**：它与 HiveMemory 对上下文有多少控制权无关。
- **送达一侧随控制权而定**：plugin 模式下 HiveMemory 处于被动地位，各 harness 能捕捉的时点与能做的干预不一样，所以拉取为基线、只推指针、不在轮首推送，agent 不知道话题 id 时读 `topic:current`。controller 模式下这些约束都不存在：Gateway 在入口就为这一轮判断了话题，上下文由 HiveMemory 构建，会话压缩由 Alice 自己做，所以送达是直接注入。
- **使用点两种模式相同**：被路由回已有话题时，与会话压缩之后。controller 模式下系统自己就能识别这两个时刻：PREPARE 时 Gateway 指向的话题与这个会话上一轮所在的话题不同；Alice 完成了一次会话压缩。
- 推论：注入的是进展记录，不是折叠摘要。折叠摘要的读者是读材料的内部模型（第 6 节），面向前台的是进展记录。
- **与中期记忆对照**：中期记忆在 controller 模式下由预检索注入，在 plugin 模式下由 agent 自己检索；短期记忆目前只有 plugin 一侧，Alice 的上下文不含话题（第 7 节现状）。
- **只在 plugin 模式下成立的约束**：话题向前台只是读出；会话压缩与折叠、写进展记录之间没有机制联系（第 8.2 节）。controller 模式下会话压缩与话题都归 HiveMemory，二者要不要建立联系还没有设计：例如压缩之后注入进展记录，Alice 的接力摘要可以少写，或者一部分由进展记录承担。

### 1.5 演进：V1、两种模式的统一与 V2

- **V1（v0.8.1，已初步成立）**：以整轮为单位。内容一侧：话题的单位与日志、沉淀与退役、进展记录（话题停下时写一条，每一条覆盖相邻的整轮）、折叠作为系统内部的材料压缩（第 6 节）；送达一侧只有 plugin 模式：拉取、`topic:current` 与 Claude Code 压缩之后的指针。当前事实见[短期记忆](../architecture/short-term-memory.md)。
- **V1 与 V2 之间（候选）**：两种模式下短期记忆的统一，包括与外部会话的接驳。统一补的是 controller 模式的送达：话题的进展注入 Alice 的上下文，以及 Alice 的会话压缩与话题要不要建立联系（第 1.4 节）；接驳是外部会话的输入、交接与话题投影（[外部会话 Idea](./external-session-and-topic-projection.md)）。
- **V2**：兼容长 turn 下的短期记忆工作方式：一轮进行中接收已完成的事件，一轮之内写一条进展记录、条目的区间落在一轮之内，单轮超过上限时在段的边界上折叠，一轮中间压缩之后读到的进展覆盖这一轮前面的部分。事件的接收、分段、封口与恢复见[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)。

第 4 节的“有人读时补”不在 V1 中，归到哪一步还没有定。

## 2. 组成与数据流

```text
会话（前台上下文；harness 或 Alice 压缩，第 8 节）
  │ 交互（plugin 模式在一轮结束后导入；一轮之内的接收见长 Turn Idea）
  ▼
话题
  ├─ 交互记录：完整原文，次级的完整记录；材料变长时折叠（第 6 节）
  └─ 进展记录：只增的条目，每一条指回原文；话题停下时写一条（第 3、4 节）
  │
  ├─ 推送（plugin 模式）：会话压缩之后 → 话题句柄的指针（第 7 节）
  ├─ 拉取：按句柄读话题与原文；被路由回已有话题时读当前话题（第 7 节）
  ├─ 生命周期：停下够久 → 沉淀；容量满或明确结束 → 退役（第 5 节）
  └─ 存储：每个话题一条只追加的日志（第 5 节）
```

话题里的东西分两层：**材料层**是交互记录与折叠，供系统内部的模型读（记忆生成与进展记录的写作者）；**输出层**是进展记录与沉淀出的记忆，分别交给前台与中期。折叠是材料层的压缩，与前台的会话压缩是同一类事，只是在系统内部进行；进展记录是读材料得到的一种输出。

| 部分 | 所有者 | 本文位置 |
|:---|:---|:---|
| 交互记录、进展记录、折叠、话题的生命周期与存储 | Patchouli | 第 3～6 节 |
| 前台读取（拉取）的授权与入口 | Workspace 能力层 | 第 7 节 |
| plugin 模式下推送的时机与注入 | 连接器 | 第 7 节 |
| 会话压缩与检查点 | harness、Alice 与会话资源 | 第 8 节 |

## 3. 话题的进展

**设计**：

话题的进展 = 已整理的部分 + 未整理的原始交互记录，读话题的 agent 看到的就是这两部分：

- **已整理的部分**：进展记录，按时间排列的条目，每一条写自上一条以来话题有了什么进展（像过去 WIP 记忆那样的总结性语句），可以跨几轮，V2 起也可以只是一轮之中的一部分。只往后追加，旧条目不改写；不整段重写。
- **指回原文**：每一条用“轮次标识 + 事件序号区间”指回原文，与记忆引用是同一套坐标（[记忆生成](../patchouli/generation.md#22-段标签与记忆引用)）；V2 起区间可以落在一轮之内。
- **未整理的原始交互记录**：进展记录还没有覆盖到的交互原文。

合起来就是完整可用的短期记忆。还没写过一条的话题，进展就是它的原文，所以从未折叠的话题也能回答“进行到哪一步”。

进展记录的数据、写一条的输入（旧进展记录加新交互记录原文，输出一段总结）与它的理由已经实现，见[短期记忆](../architecture/short-term-memory.md#3-基本概念)第 3 节与[第 4.3 节](../architecture/short-term-memory.md#43-写进展记录)。

todo 与 plan 的渲染设计待定，取决于各家harness的实现细节与完成逻辑。

**现状与差距**：

- `topic_summary` 在建话题时由 Gateway 写一次，之后不更新；话题路由与话题池读它与进展记录最近的一条，不读折叠摘要（[短期记忆](../architecture/short-term-memory.md#44-折叠)第 4.4 节）。日常约 97% 的话题直到结算都没有折叠。
- 进展记录已实现（[短期记忆](../architecture/short-term-memory.md#3-基本概念)第 3 节）：每一条覆盖相邻的若干整轮，区间落在一轮之内的条目属于 V2；进展记录经话题列表的 HTTP 响应交给话题池，经话题句柄交给 agent（第 7 节）。
- 写一条进展记录读工作视图：还没整理的轮次已经被折叠的部分只给覆盖它们的折叠摘要，其余给原文，输入长度由折叠控制（第 6 节）。
- 段与引用坐标已经实现：段由一轮的事件按模型响应推出，工具结果挂在调用事件上，一段不会拆开调用与结果；记忆的版本记录保存“轮次标识 + 事件序号区间”（[记忆生成](../patchouli/generation.md#22-段标签与记忆引用)）。这些引用现在只有写入方。
- 规模：只按轮与轮之间的停下计，日常话题的进展记录中位 1 条，90% 不超过 3 条，最长 14 条（85 轮的话题）。

## 4. 什么时候写一条

**设计**：

- **时间与空间两个维度**：话题的进度从两个维度判断，任一满足就生成，进展记录与沉淀都是如此：
  - 时间：话题停下一段时间，说明进度暂缓，是天然的生成点。话题停下 `progress_record_after_seconds` 之后写一条、停下 `settle_after_seconds` 之后沉淀，已经实现（[短期记忆](../architecture/short-term-memory.md#43-写进展记录)第 4.3 节）；
  - 空间：自上一次以来积累的材料超过一个量。连续进行、从不停下的话题只能靠这一维：记忆驱动的主动化要求假定一个话题会连续驱动并产生交互流，这时时间维度永远不会触发。
- **按量是补齐空间维度的最简单策略**：进展记录看还没整理的交互（`recorded_until` 之后）的材料量，沉淀看还没沉淀的交互（已完成与在途沉淀之后）的材料量，各自超过阈值就生成；计量沿用折叠的 token 估算。阈值满足“进展 < 沉淀 ≤ 折叠”：阈值越小于折叠阈值，两次折叠之间按量触发的次数越多，每次折叠时还没整理或还没沉淀、因而只剩摘要的部分就越少；它只减少这部分，不能保证没有。两个维度推进的是同一个位置，看的都是“位置之后还有多少”，所以不会因为另一维刚触发过而重复生成。
- 更好的进度判定是开放问题（第 9 节）；按量只是其中最简单的一种。
- **会话切走**：会话切到别的话题也是一种进度暂缓，判断逻辑还没有设计（第 9 节搁置项）。
- **一轮之内**：长 turn 可能一直不停，是空间维度的极端情形；段用来指回原文，但不必每段都写一条。按量推到一轮之内、在段的边界上切，属于 V2（第 1.5 节）。
- 候选，有人读时补：新对话不多时，直接给“已整理的部分 + 未整理的原始交互记录”，不需要生成；新对话已经很长，才在读之前先写出新的一条。

**现状与差距**：

- 时间维度已实现（随附配置的 `progress_record_after_seconds` 为 1800 秒、`settle_after_seconds` 为 3600 秒）；空间维度还没有实现：连续进行的话题既不写进展记录，也不沉淀，只在池满或手动退役之前沉淀一次。会话切到别的话题、一轮之内都没有触发。plugin 模式在一轮结束后才导入：Claude Code 在 `Stop` 钩子同步，连接器按最后一条助手条目的 `stop_reason` 判断这一轮是否写完（[Import Bus](../system/import-bus.md)）。
- 单个事件没有时间戳（[数据模型](../architecture/data-model.md#49-交互记录turnevent-与-interactionpayload)），“步与步之间长时间等待”无法从已存的事件算出。
- “会话切到了别的话题”由 Gateway 的话题路由判断：任务进程与 Import Bus 都把上一轮实际所在的话题交给 Gateway（`GatewaySessionTurn.topic_id`），这一轮的目标话题与它不同即是切走。差距在于这个结果不随提交交给 Patchouli：交互提交只带目标话题，Patchouli 只看到一轮应用到了哪个话题，看不到这个会话离开了哪个话题。候选：root API 提交交互时拿到的话题来源中已有上一轮的话题，随提交一并交出。
- 日常 121 个长轮次（每轮至少 72 个事件）中，83 个没有一次计划步骤完成；Claude 桌面端每轮都列自己的操作步骤，计划步骤完成在普通轮次里也频繁出现，不代表话题的工作单位。
- 成本：日常 11 天导入 881 轮，同一会话切到别的话题 132 次、话题内停下超过 30 分钟 41 次，轮与轮之间停下时写的次数约为每轮都写的四分之一。

## 5. 生命周期与存储：沉淀、退役与话题的日志

**设计**：

- 结算拆成沉淀与退役，话题的存储是每个话题一条只追加的日志：均已实现，设计与理由见[短期记忆](../architecture/short-term-memory.md#4-话题的一生)第 4.5、4.6 节（沉淀与退役、沉淀进度在生成完成时推进、退役话题的日志保留到最后一次沉淀完成）与[第 7 节](../architecture/short-term-memory.md#7-保存与重启)（日志、短期存储与 Port 契约、关闭与启动时读回）。
- 话题跨重启保存整个话题，本话题生成的记忆是话题的一部分。只保存进展记录的话，恢复后不能续写原文，重启照样切开正在进行的话题。
- 进展记录的一条同样是话题日志中的一种记录（`progress_entry`），在短期存储里有对应的写入方法，发生时即落盘：已实现，见[短期记忆](../architecture/short-term-memory.md#7-保存与重启)第 7 节。
- 随退役执行的沉淀在执行时读本话题生成的记忆，看得到排在它前面的同话题沉淀生成的记忆：已实现，见[记忆生成](../patchouli/generation.md#42-本话题生成的记忆)第 4.2 节。

**现状与差距**：

- 沉淀与退役、话题的日志、跨重启与崩溃后读回均已实现（链接见上）；同一话题多次沉淀时，本话题经任何途径生成的记忆进入同一份“本话题生成的记忆”记录，记在话题的日志上，见[记忆生成](../patchouli/generation.md#42-本话题生成的记忆)第 4.2 节。
- 拆开之前的日常数据（11 天 89 次结算）：话题停下超过时限 77、关闭 11、LRU 1。

## 6. 折叠：只为材料服务

**设计**：

- 折叠是系统内部的材料压缩，与前台的会话压缩是同一类事：会话压缩让前台 agent 的上下文装得下，折叠让系统内部读材料的模型装得下。读者是记忆生成与写进展记录，两者都读工作视图；每条折叠记录只存这一次的摘要，工作视图按顺序拼接；这一次的摘要是标题、模型写的判断类五栏与代码从原文取出的部分，模型写不成时只写后者、折叠照常提交；折叠摘要不给前台与 Gateway。均已实现，见[短期记忆](../architecture/short-term-memory.md#44-折叠)第 4.4 节。
- 一旦折叠，就接受可能的细节丢失。一次折叠不隐式沉淀，不证明已经生成 Memory。
- 候选（V2）：单轮超过上限时，在段的边界上折叠，不拆开调用与结果。

| 议题 | 候选 |
|:---|:---|
| 预算 | 同时约束已有折叠摘要、保留后缀与渲染开销；计数与块数联合使用，按实际的读取请求分别校验，不能把话题的软水位当作最终请求上限 |
| 工具证据 | 从实际工具结果选取关键返回值与验证结论，保留原文定位，不要求把所有日志重新内联 |
| 跨入口 | 按实际来源与能力处理材料；主动、被动或连接器名称不直接决定是否折叠 |
| 观测 | 记录资料规模、内联规模、摘要规模、耗时与失败原因；观测不替代领域结果 |

**现状与差距**：

- 已实现的部分见上。折叠摘要的结构参照了本机 49 份 Claude Code 压缩记录：其中约三成是请求、待办、当前工作与下一步，属于进展，折叠摘要不写；用户原话与文件路径改由代码取出。
- 折叠摘要只增长：每次折叠追加一份，不再压缩，代码取出的部分也没有总量上限；单轮超大时工作视图一直超过阈值，每来一轮就折一次（V2）。
- 话题长时间连续工作、中间没有停下时，已经被折叠的那几轮在进展记录里只能依据摘要来写。

## 7. 什么时候用：推送与拉取

**设计**：

- 短期记忆的目的是让回到话题的 agent 知道话题进行到哪一步：一项工作做到哪了，或一段对话聊到哪了。plugin 模式下使用点、拉取与推送的分工已经实现（两种模式的分工见第 1.4 节）：
  - 两个使用点（被路由回已有话题时、会话压缩之后的失忆窗口），拉取是基线、推送只在会话压缩之后且只推送一个指针、不推送话题或中期记忆的内容，以及为什么不在轮首推送：见[短期记忆](../architecture/short-term-memory.md#6-把话题读回前台)第 6 节；
  - 话题的归属按需确定、每轮至多一次，写入或更新之前、读当前话题之前与轮次结束导入时共用同一个为一轮确定话题：见 [Import Bus](../system/import-bus.md#47-写入与读当前话题时确定话题)第 4.7 节；
  - 拉取：agent 经 actor API 的 READ 按话题句柄读话题，不知道话题 id 时读 `topic:current`；句柄的形态、`topic:current` 的确定与替换、与 alias 的互斥、可见性与结局见[短期记忆](../architecture/short-term-memory.md#61-拉取按句柄读话题)第 6.1 节，alias 的保留前缀见 [MemoryLibrary](../patchouli/memory-library.md#12-中期当前可检索书库)第 1.2 节，索引与一条原文的渲染见[短期记忆](../architecture/short-term-memory.md#62-读到什么)第 6.2 节，MCP 一侧的轮次信息与未解析时的说明见 [MCP 记忆访问](../contracts/mcp.md#31-读话题句柄)第 3.1 节；
  - 压缩之后的指针：Claude Code 压缩会话之后，插件的钩子以连接器记下的话题写出句柄与一句读法，不发网络请求，见[短期记忆](../architecture/short-term-memory.md#63-推送会话压缩之后的指针)第 6.3 节；
  - 话题向会话只是单向读出，见[短期记忆](../architecture/short-term-memory.md#8-必须守住的规则)第 8 节的跨层不变量。
- 候选：话题池也签发句柄，在话题池界面显示，需要先出样稿。
- 长 turn 中压缩常发生在一轮中间，读到的索引能否覆盖这一轮前面的部分，取决于一轮之内写一条与一轮进行中接收已完成的事件，属于 V2（第 1.5 节）。

**现状与差距**：

- 拉取、`topic:current` 与压缩之后的指针已实现（链接见上）；agent 是否按 skill 去读 `topic:current`、是否读指针中的句柄，要在日常使用里看。
- 一个外部会话在哪个话题上，只记得最近一轮所在的那一个：连接器为每个会话记下导入结果带回的话题，随状态文件跨过后端重启（[Import Bus](../system/import-bus.md#84-结束判定与游标)第 8.4 节）；后端不保存外部会话。
- controller 模式下 Alice 的上下文不含话题（[Agent Runtime](../alice/agent-runtime.md#3-输入上下文与-prompt-组装)）；Alice 的 MTP READ 能读话题句柄，但没有地方发给它句柄，`topic:current` 在 MTP 中按未命中处理。
- `determine_topic` 已供任务进程的线程表与 Import Bus 编排器使用，MCP 写入与读当前话题时以它在一轮结束前确定话题（[能力层](../workspace/capability.md)）。日常一次话题路由约 3 秒。
- Claude Code：`UserPromptSubmit` 与 `SessionStart` 都能返回 `additionalContext`；注入只保证交到模型手里，不保证模型会读；`PostCompact` 不能注入。Codex 的钩子是 `SessionStart`、`Stop`、`Interrupt` 与 `SessionEnd`；Codex、pi 与 DeepSeek Harness 的连接器不注入，它们能否注入内容没有核对。

## 8. 会话压缩（前台一侧）

### 8.1 已完成的范围

- 会话提供完整、原样积累的对话历史；CPU 自行压缩派生上下文，会话记录保持原样。Alice 的自动压缩、工具结果减重、增量接力摘要与逐帧输入守卫已经实现，算法见 [Agent Runtime](../alice/agent-runtime.md#31-会话上下文视图)。
- 压缩检查点属于会话资源，不属于 Agent 或 CPU 的进程内状态（[会话资源](../workspace/sessions.md)）。
- 用户的 `/compact` 对外部 Actor 触发其 harness 的压缩，对 Alice 使用 Alice 自己的实现；手动 `/compact` 要等命令系统接回（[命令 Todo](../todo/conversation-compact-command.md)）。
- 保留新建、恢复与会话内 compact，不设“新会话接续旧会话”的交接摘要：把旧会话完整历史带入新会话等同恢复。话题的进展按话题读出（第 7 节），不是会话的交接摘要。
- 真实 LLM 下接力摘要的事实保留、继续执行的质量与成本还没有评估。

### 8.2 两边的关系与不变量

- 两边的关系已是跨层不变量：会话压缩、折叠与进展记录各回答一个问题、各自触发，Alice 的接力摘要不进入话题，plugin 模式下话题向前台只是读出，见[短期记忆](../architecture/short-term-memory.md#8-必须守住的规则)第 8 节。controller 模式下会话压缩与话题都归 HiveMemory，二者要不要建立联系见第 1.4 节。
- 外部 harness 的 summary/checkpoint 若交给 HiveMemory，应保留产生者、来源与覆盖信息，未知覆盖范围不能驱动裁剪，也不能直接充当话题的折叠摘要或进展记录。
- 摘要范围与保留的原文后缀不重复覆盖；覆盖只能相对同一来源与顺序向前推进。
- 压缩、折叠与写进展记录都不改变授权、写入接纳或持久化事实；RuntimeEvent 只观测，不决定提交成功。

### 8.3 可共享的技术

可以共享 token 估算、完整交互边界、有界摘要更新、完成状态校验、覆盖范围校验与有限重试；先复用已有低层工具与端口，不预设统一的压缩子系统，跨 L3 子系统只消费公共 contracts。摘要策略、模型选择、预算、数据所有者、覆盖游标、接受条件与清理生命周期分别维护；使用同一算法不使两边成为同一状态。技术调研见 [Agent Harness 会话压缩技术调研](../research/agent-context-compaction-research.md)。

## 9. 开放问题

**话题进度的判定**（不阻塞按量补齐空间维度的计划）

- **背景**：时间与空间各有一个最简单的判断：停下多久、积了多少。两者都只是进度的近似；要找的是跟着话题的进度生成短期记忆的方式。长 turn 要解决的是同一个问题，区别只在单位更小，方法要能从整轮推到段与事件区间。
- **是否假定话题永不停止且永不结束**：假定时，停下、结束与读取只是让生成更早发生的加速条件，不是生成的前提；退役也不再是回收的唯一途径：三个位置（折叠、进展、沉淀）都推过的前缀可以离开话题的活跃部分、只留在来源记录里，话题才有上界。
- **候选的进度信号**：
  - 量：自上一次以来新增的材料超过一个量，与折叠同构，当前选用；
  - 消耗：某一段已经用完，后面的工作不再依赖它；dsh-live-compact 以此每轮切掉一小段已经用完的工具轮，切点只向右推进；
  - 结构边界：用户请求结束、计划完成一步、会话切走；日常数据中计划步骤完成频繁出现在普通轮次里，不代表话题的工作单位；
  - 需求：有人要读、前台压缩，属于补救，不是生成点本身。
- **影响**：进展记录与沉淀的频率与成本（日常数据里每轮都写约是停下才写的四倍）；同一话题沉淀次数增多后馆长每次重看的材料；为时间扫描引入的进程内位置（如写进展记录失败的位置）是否还需要。

搁置：

- 会话切走这一触发：多个会话并发进行时，一个会话离开话题不等于话题停下，判断逻辑还没有设计；在此之前按时间与空间两个维度触发。
- 长话题的旧条目怎样处理（合并成阶段，或只给最近若干条）。
- 每次记忆生成前都把话题的全部交互冻结成一份交互快照，各份互相重叠；属于[全链路原始资料保存](./PatchouliPageFoldingRawEvidenceDesign.md)。
- Codex、pi 与 DeepSeek Harness 能否注入内容。
- controller 模式下话题的进展怎样注入 Alice 的上下文（第 1.4 节，V1 与 V2 之间）：注入位置（`turn_context` 排在全部历史之前，内容一变其后的前缀缓存全部失效）、预算（索引约 4,000 字符，与预检索的记忆、附件共用）、被路由回来时还没整理的最近几轮（与第 4 节“有人读时补”相关），以及与 Alice 的会话压缩、预检索怎样共处。
- 一轮进行中接收已完成的事件（V2），由[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)维护。
- 一轮之内写一条的触发（V2）：把轮与轮之间的按量推到一轮之内（在段的边界上切），以及计划完成一步，都暂缓设计；“步与步之间长时间等待”等事件有时间来源再看。
- Alice 的 `turn_context`（每轮重新编译的检索记忆与附件）排在全部历史之前，检索结果一变，其后的历史都失去前缀缓存；实际命中率没有测过。
- 代码中已实现的段类名 `TurnSegment`，与长 Turn Idea 第 2.3 节候选的 `TurnSegment`（容量单位）同名。

## 10. 非目标

- plugin 模式下 HiveMemory 不控制、不替代前台上下文与 harness 的压缩；任何模式下都不改写会话原文。
- 会话与话题不共享状态；plugin 模式下会话压缩与折叠、写进展记录之间没有机制联系。
- 不为每段写一条进展记录，不整段重写进展记录。
- 不在本文设计沉淀时写什么与主动写入的材料（过渡）。
- 为轻量 bot 管理 prompt 的托管上下文，属于[长 Turn Idea](./long-running-agent-intra-turn-context-folding.md)第 8.3 节。
