# 三餐推荐助手 产品规格文档 (Meal Assistant Product Spec)

# 1 定位与目标 (Positioning & Goals)

## 1.1 产品定位

三餐推荐助手是 HiveMemory 的**第一个真实应用场景**，用于验证以 Agent Memory 为核心的系统能够跑通端到端闭环。它不是一个通用的菜谱推荐引擎，而是一个**具备跨会话记忆能力的个人饮食助手**——它能记住用户是谁、喜欢什么、最近吃了什么，并在此基础上给出个性化推荐。

## 1.2 为什么选这个场景

本场景看似简单，实则天然覆盖了 HiveMemory 记忆系统的核心能力闭环：

- **跨会话记忆**：记住用户的长期偏好与短期饮食历史
- **主动写入**：Agent 通过 MTP 的 `WRITE` 指令主动沉淀高价值信息
- **主动检索**：推荐时综合多源记忆（偏好、历史、库存）进行决策
- **动态更新**：偏好变化、新菜谱学习通过 `UPDATE` 修正
- **时间敏感推理**：避免推荐"昨天刚吃过"的菜

这是验证 `everything is memory` 与 `memory as a tool` 理念的最小完整闭环。

## 1.3 核心成功标准

- **朋友（真实用户）能连续使用一周**，并主观感受到"它记得我"
- **至少 3 个跨会话记忆场景**被验证有效：偏好记忆、饮食历史、新菜谱学习
- **HiveMemory 现有子系统（Patchouli + Alice + MTP）跑通完整链路**，不依赖未完成的重构（如 Gateway v0.6.0）

## 1.4 非目标 (Non-Goals)

明确不做以下事情，以避免再次陷入过度设计：

- **不做多智能体编排**：单 Agent 即可，不使用 Alice 的子帧派生能力
- **不做复杂 UI**：能对话即可，优先复用现有前端或直接用 API
- **不做营养分析/健康建议**：仅做推荐，不做营养学推理
- **不做图片识别**：用户手动描述菜品，不接入多模态
- **不做个性化推荐算法优化**：第一版依赖 LLM 的推理能力 + 记忆检索，不引入协同过滤等 ML 推荐
- **不等待 Gateway 重构完成**：使用现有的检索与路由逻辑

# 2 用户与场景 (Users & Scenarios)

## 2.1 目标用户

**单一真实用户**：项目作者的朋友。需求边界由用户自然提出，不由开发者预设。

## 2.2 核心用户场景

### 场景 A：建立偏好档案

> 用户："我喜欢吃辣，不喜欢甜食，对海鲜过敏。"
> 助手：（记下偏好，下次对话默认遵循）

**验证能力**：`WRITE` 写入 USER_PROFILE 类型记忆，跨会话保留。

### 场景 B：记录饮食历史

> 用户："我今天中午做了番茄炒蛋。"
> 助手：（记下日期与菜品）
> （次日）用户："今晚吃什么？"
> 助手："你昨天吃了番茄炒蛋，今天换个口味？要不要试试……"

**验证能力**：时间敏感的记忆写入与检索，避免短期重复推荐。

### 场景 C：库存驱动的推荐

> 用户："我冰箱里有鸡蛋、西红柿、青椒。"
> 助手：（记下库存）"基于你的库存和偏好，推荐青椒炒蛋或西红柿鸡蛋汤？"

**验证能力**：多源记忆融合（库存 FACT + 偏好 USER_PROFILE + 历史 WORK_IN_PROGRESS）。

### 场景 D：学习新菜谱

> 用户："我刚学了一道菜叫‘酸汤肥牛’，做法是……"
> 助手：（记下菜谱）"记下了。下次推荐时我会考虑这道菜。"
> （若干天后）用户："推荐点新菜？"
> 助手："要不要试试你之前学的酸汤肥牛？"

**验证能力**：FACT 类型记忆的长期保留与检索召回。

### 场景 E：偏好修正

> 用户："其实我最近开始接受一点甜食了，不用完全避开。"
> 助手：（更新偏好记忆）"好的，我会适度推荐带甜味的菜。"

**验证能力**：`UPDATE` 对已有记忆的精准修正，而非追加新记忆导致冲突。

# 3 记忆类型映射 (Memory Type Mapping)

本场景下 HiveMemory 的七种记忆类型使用情况：

| 记忆类型 | 本场景用途 | 使用频率 | MTP 指令 |
|:---|:---|:---|:---|
| `USER_PROFILE` | 用户口味偏好、过敏信息、饮食限制 | 高 | `WRITE` / `UPDATE` / `SEARCH` |
| `FACT` | 菜谱内容、用户会做的菜、库存食材 | 高 | `WRITE` / `SEARCH` |
| `WORK_IN_PROGRESS` | 近期饮食记录（带时间戳） | 高 | `WRITE` / `SEARCH` |
| `REFLECTION` | 用户对某次推荐的反馈（如"这个菜太咸了"） | 中 | `WRITE` / `SEARCH` |
| `CODE_SNIPPET` | （可选）存储菜谱生成逻辑作为可执行工具 | 低/可选 | `RUN` |
| `URL_RESOURCE` | （可选）外部菜谱链接快照 | 低/可选 | `WRITE` |
| `AGENT_PROFILE` | 本助手的 Agent 配置 | 一次性 | 由系统初始化 |

**核心记忆类型为前四种**，后三种为可选扩展，第一版不强制实现。

# 4 核心交互流程 (Core Interaction Flows)

## 4.1 最小可用闭环（MVP）

第一版必须跑通的完整流程：

```
用户输入
  ↓
Alice Runtime 接收消息
  ↓
Patchouli 检索（基于现有检索逻辑）
  ├─ SEARCH user_profile  → 用户偏好
  ├─ SEARCH recent_meals  → 近期饮食（时间过滤）
  └─ SEARCH recipes       → 会做的菜/库存
  ↓
Agent Loop 推理（LLM）
  ├─ 生成推荐 / 回答
  └─ 判断是否值得记忆
       ├─ WRITE 新信息（新偏好/新菜谱/新饮食记录）
       ├─ UPDATE 已有信息（偏好修正）
       └─ 无操作（闲聊不值得记）
  ↓
MTP 响应执行
  ↓
回复用户
```

## 4.2 MTP 指令使用清单

第一版需支持的 MTP 指令子集：

| 指令 | 用途 | 示例 |
|:---|:---|:---|
| `SEARCH` | 检索记忆 | 检索偏好、历史饮食、菜谱 |
| `WRITE` | 写入新记忆 | 记录新偏好、新菜谱、今日饮食 |
| `UPDATE` | 修正已有记忆 | 偏好变化、修正错误记录 |
| `READ` | 读取单条记忆 | 读取特定菜谱详情 |

**不使用**的指令（第一版）：`RUN`（MaaT 暂不启用）、`DELETE`（由生命周期管理自动处理）、`CALL`（单 Agent 无子帧派生）。

# 5 功能需求 (Functional Requirements)

## 5.1 P0 - 必须有（MVP）

- **F1 跨会话偏好记忆**：用户声明偏好后，新会话中 Agent 能自动遵循
- **F2 饮食历史记录**：用户报告"今天吃了X"时自动记录日期与菜品
- **F3 个性化推荐**：推荐时综合考虑偏好、历史、库存三源记忆
- **F4 时间敏感去重**：推荐时避免推荐"最近几天刚吃过"的菜
- **F5 新菜谱学习**：用户分享菜谱时能完整记录并在后续推荐中纳入
- **F6 偏好修正**：用户修正偏好时更新已有记忆，而非追加冲突记忆
- **F7 基础对话**：能回答"我能做什么菜"、"我最近吃了什么"等查询

## 5.2 P1 - 应该有（第一版后迭代）

- **F8 库存管理**：用户报告库存时记录，推荐时优先消耗库存
- **F9 反馈学习**：用户对推荐给出反馈（好吃/不好吃）时记录为 REFLECTION
- **F10 记忆溯源**：推荐时说明"我推荐这个是因为你上次说喜欢……"

## 5.3 P2 - 可选扩展

- **F11 菜谱作为工具（MaaT）**：将菜谱存储为 CODE_SNIPPET，通过 `RUN` 执行生成步骤
- **F12 外部菜谱链接**：存储 URL_RESOURCE 类型记忆，保留外部菜谱快照
- **F13 多用户隔离**：支持多个用户独立使用（当前仅单用户）

# 6 验收标准 (Acceptance Criteria)

## 6.1 MVP 验收（第一版完成标准）

以下场景必须全部跑通，且**由朋友实际验证**：

- [ ] **AC1**：首次对话声明偏好 → 新建会话 → Agent 推荐时遵循该偏好
- [ ] **AC2**：报告"今天吃了番茄炒蛋" → 次日问推荐 → Agent 不重复推荐番茄炒蛋
- [ ] **AC3**：报告"我会做酸汤肥牛，做法是……" → 若干天后推荐时纳入该菜
- [ ] **AC4**：修正偏好（"我现在能接受一点甜食"）→ 后续推荐体现修正
- [ ] **AC5**：问"我最近吃了什么" → Agent 能列出近期饮食记录

## 6.2 一周使用后验收

- [ ] **AC6**：朋友主观反馈"它记得我"（非量化，但关键）
- [ ] **AC7**：连续使用一周，无需用户手动修正记忆（除非 Agent 明显记错）
- [ ] **AC8**：识别至少 3 个真实使用中暴露的问题（作为下一版迭代依据）

# 7 实现约束 (Implementation Constraints)

## 7.1 必须遵守

- **基于现有 v4 架构**：不引入新的架构重构
- **使用现有 Patchouli 检索逻辑**：不等待 Gateway v0.6.0
- **单 Agent**：不启用 Alice 的子帧派生
- **MTP 指令子集**：仅 SEARCH / WRITE / UPDATE / READ
- **第一版不超过 3 天开发时间**：超时则砍功能而非延期

## 7.2 明确允许

- 允许代码粗糙、UI 丑陋
- 允许记忆价值判断不准确（先能记，再判断准）
- 允许推荐质量一般（先能推荐，再优化质量）
- 允许使用现有 LLM 的通用能力补足推理（不引入专门推荐算法）

## 7.3 明确禁止

- 禁止为了本应用重构 Patchouli 或 Alice 子系统
- 禁止引入新的存储引擎或检索算法
- 禁止优化未在本规格中提及的模块
- 禁止在设计上投入超过 1 天（剩余时间全部用于实现）

# 8 验证与反馈 (Validation & Feedback)

## 8.1 第一版交付后

1. **立即交给朋友使用**，不等待"打磨好"
2. **观察一周**，记录以下信息：
   - 朋友主动提出的抱怨或建议
   - 朋友未抱怨但明显不合理的推荐（开发者观察）
   - 朋友重复说过但 Agent 没记住的信息
   - 朋友没说过但 Agent "幻觉"出的偏好
3. **形成问题清单**，作为下一版迭代的唯一依据

## 8.2 下一版迭代依据

下一版做什么，**由一周使用后的问题清单决定**，不由开发者预设。可能的迭代方向（仅供参考，不作为承诺）：

- 检索质量优化（如果推荐总不相关）
- 记忆价值判断优化（如果记了太多无用信息）
- 时间推理增强（如果"最近"判断不准）
- UI 改进（如果朋友抱怨交互方式）

# 9 项目意义 (Project Significance)

## 9.1 对 HiveMemory 的价值

本应用是 HiveMemory 从"理论先进"走向"被验证先进"的第一步。它不证明系统的强大，只证明**系统能用**。

## 9.2 不证明什么

- 不证明多智能体能力
- 不证明 AIOS 架构优势
- 不证明 MaaT 的价值
- 不证明性能优于其他框架

## 9.3 只证明一件事

**以 Agent Memory 为核心的架构，能跑通一个真实的、有人用的、跨会话记忆有效的应用闭环。**

这一件事，是 HiveMemory 当前最需要的证据。

# 10 附录：与论文发现的对照

本场景的设计已参考论文《Are We Ready For An Agent-Native Memory System?》(arXiv:2606.24775) 的关键发现：

- **Finding 6（保留原始内容）**：菜谱以原始文本存储，不压缩为摘要
- **Finding 7（保守提取）**：用户偏好原话保留，不激进改写
- **Finding 8（适度结构）**：检索不堆叠过多 Reflect 步骤
- **Finding 9（保守整合）**：偏好修正用 UPDATE 而非追加冲突记忆
- **Finding 4（时间敏感）**：饮食历史保留时间戳，检索时支持时间过滤
