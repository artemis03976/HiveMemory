# 三餐推荐助手 产品规格文档 (Meal Assistant Product Spec)

> **当前状态（2026-07-28）**：本文是一份可执行的产品验证规格，不是已交付应用说明。仓库中尚无独立 Meal Assistant package、专用 UI、应用级自动化测试或“一周真实用户使用”证据；第 6 节验收项均未完成。规格复用当前 Chat 与 Agent Management，并以现有 Patchouli、Alice、Gateway 和六个 MTP verb 为基础；其中 CALL 已由系统实现，但本应用主动禁用，多 Agent 不是 MVP 依赖。

# 1 定位与目标 (Positioning & Goals)

## 1.1 产品定位

三餐推荐助手是 HiveMemory 的**第一个真实应用场景**，用于验证以 Agent Memory 为核心的系统能够跑通端到端闭环。它不是一个通用的菜谱推荐引擎，而是一个**具备跨会话记忆能力的个人饮食助手**——它能记住用户是谁、喜欢什么、最近吃了什么，并在此基础上给出个性化推荐。

## 1.2 为什么选这个场景

本场景看似简单，实则天然覆盖了 HiveMemory 记忆系统的核心能力闭环：

- **跨会话记忆**：记住用户的长期偏好与短期饮食历史
- **主动写入**：Agent 通过 MTP 的 `WRITE` 指令主动沉淀高价值信息
- **主动检索**：推荐时综合多源记忆（偏好、历史、库存）进行决策
- **动态更新**：偏好变化、新菜谱学习通过 `UPDATE` 修正
- **时间敏感推理**：避免推荐"昨天刚吃过"的菜

这是验证 `everything is memory` 与 `memory as a tool` 理念的最小完整闭环。

## 1.3 核心成功标准

- **朋友（真实用户）能连续使用一周**，并主观感受到"它记得我"
- **至少 3 个跨会话记忆场景**被验证有效：偏好记忆、饮食历史、新菜谱学习
- **HiveMemory 当前子系统（Gateway + Patchouli + Alice + MTP）跑通完整链路**，不为该应用额外引入新的后端重构依赖

## 1.4 非目标 (Non-Goals)

明确不做以下事情，以避免再次陷入过度设计：

- **不做多智能体编排**：单 Agent 即可，不使用 Alice 的子帧派生能力
- **不做复杂 UI**：能对话即可，优先复用现有前端或直接用 API
- **不做营养分析/健康建议**：仅做推荐，不做营养学推理
- **不做图片识别**：用户手动描述菜品，不接入多模态
- **不做个性化推荐算法优化**：第一版依赖 LLM 的推理能力 + 记忆检索，不引入协同过滤等 ML 推荐
- **不扩展 Gateway 范围**：直接使用当前 v0.6 开发基线已经存在的入口决策、检索准备与 Agent 执行链路

# 2 用户与场景 (Users & Scenarios)

## 2.1 目标用户

**单一真实用户**：项目作者的朋友。需求边界由用户自然提出，不由开发者预设。

## 2.2 核心用户场景

### 场景 A：建立偏好档案

> 用户："我喜欢吃辣，不喜欢甜食，对海鲜过敏。"
> 助手：（记下偏好，下次对话默认遵循）

**验证能力**：`WRITE` 写入 USER_PROFILE 类型记忆，跨会话保留。

### 场景 B：记录饮食历史

> 用户："我今天中午做了番茄炒蛋。"
> 助手：（记下日期与菜品）
> （次日）用户："今晚吃什么？"
> 助手："你昨天吃了番茄炒蛋，今天换个口味？要不要试试……"

**验证能力**：时间敏感的记忆写入与检索，避免短期重复推荐。

### 场景 C：库存驱动的推荐

> 用户："我冰箱里有鸡蛋、西红柿、青椒。"
> 助手：（记下库存）"基于你的库存和偏好，推荐青椒炒蛋或西红柿鸡蛋汤？"

**验证能力**：多源记忆融合（库存 FACT + 偏好 USER_PROFILE + 历史 WORK_IN_PROGRESS）。

### 场景 D：学习新菜谱

> 用户："我刚学了一道菜叫‘酸汤肥牛’，做法是……"
> 助手：（记下菜谱）"记下了。下次推荐时我会考虑这道菜。"
> （若干天后）用户："推荐点新菜？"
> 助手："要不要试试你之前学的酸汤肥牛？"

**验证能力**：FACT 类型记忆的长期保留与检索召回。

### 场景 E：偏好修正

> 用户："其实我最近开始接受一点甜食了，不用完全避开。"
> 助手：（更新偏好记忆）"好的，我会适度推荐带甜味的菜。"

**验证能力**：`UPDATE` 对已有记忆的精准修正，而非追加新记忆导致冲突。

# 3 记忆类型映射 (Memory Type Mapping)

本场景下 HiveMemory 的七种记忆类型使用情况：

| 记忆类型 | 本场景用途 | 使用频率 | MTP 指令 |
|:---|:---|:---|:---|
| `USER_PROFILE` | 用户口味偏好、过敏信息、饮食限制 | 高 | `WRITE` / `UPDATE` / `SEARCH` |
| `FACT` | 菜谱内容、用户会做的菜、库存食材 | 高 | `WRITE` / `SEARCH` |
| `WORK_IN_PROGRESS` | 近期饮食记录（带时间戳） | 高 | `WRITE` / `SEARCH` |
| `REFLECTION` | 用户对某次推荐的反馈（如"这个菜太咸了"） | 中 | `WRITE` / `SEARCH` |
| `CODE_SNIPPET` | （可选）存储菜谱生成逻辑作为可执行工具 | 低/可选 | `RUN` |
| `URL_RESOURCE` | （可选）外部菜谱链接快照 | 低/可选 | `WRITE` |
| `AGENT_PROFILE` | 本助手的 Agent 配置 | 一次性 | 由系统初始化 |

**核心记忆类型为前四种**，后三种为可选扩展，第一版不强制实现。

# 4 核心交互流程 (Core Interaction Flows)

## 4.1 最小可用闭环（MVP）

第一版必须跑通的完整流程：

```
用户输入
  ↓
Alice Runtime 接收消息
  ↓
Patchouli 检索（基于现有检索逻辑）
  ├─ SEARCH user_profile  → 用户偏好
  ├─ SEARCH recent_meals  → 近期饮食（时间过滤）
  └─ SEARCH recipes       → 会做的菜/库存
  ↓
Agent Loop 推理（LLM）
  ├─ 生成推荐 / 回答
  └─ 判断是否值得记忆
       ├─ WRITE 新信息（新偏好/新菜谱/新饮食记录）
       ├─ UPDATE 已有信息（偏好修正）
       └─ 无操作（闲聊不值得记）
  ↓
MTP 响应执行
  ↓
回复用户
```

## 4.2 MTP 指令使用清单

第一版需支持的 MTP 指令子集：

| 指令 | 用途 | 示例 |
|:---|:---|:---|
| `SEARCH` | 检索记忆 | 检索偏好、历史饮食、菜谱 |
| `WRITE` | 写入新记忆 | 记录新偏好、新菜谱、今日饮食 |
| `UPDATE` | 修正已有记忆 | 偏好变化、修正错误记录 |
| `READ` | 读取单条记忆 | 读取特定菜谱详情 |
| `RUN` | 获取可信的当前日期 | 仅允许调用 `sys_clock`，不开放其他系统工具 |

当前 MTP 契约共有 SEARCH、READ、RUN、WRITE、UPDATE、CALL 六个 verb。本应用第一版**不使用**面向记忆工具的 `RUN`（MaaT 暂不启用）和 `CALL`（尽管 CALL 已实现，MVP 仍保持单 Agent）；协议没有 `DELETE` verb，正式记忆删除由管理 API 或生命周期能力处理。`RUN` 仅作为调用 `sys_clock` 的必要入口开放，并由 `allowed_sys_tools` 白名单阻止其调用其他系统工具。当前权限模型尚不能在开放 `RUN` 的同时硬性禁止执行 `CODE_SNIPPET` 记忆，因此“不执行 MaaT”在 MVP 中仍是 system prompt 软约束；首版不创建或投放 `CODE_SNIPPET`。

# 5 功能需求 (Functional Requirements)

## 5.1 P0 - 必须有（MVP）

- **F1 跨会话偏好记忆**：用户声明偏好后，新会话中 Agent 能自动遵循
- **F2 饮食历史记录**：用户报告"今天吃了X"时自动记录日期与菜品
- **F3 个性化推荐**：推荐时综合考虑偏好、历史、库存三源记忆
- **F4 时间敏感去重**：推荐时避免推荐"最近几天刚吃过"的菜
- **F5 新菜谱学习**：用户分享菜谱时能完整记录并在后续推荐中纳入
- **F6 偏好修正**：用户修正偏好时更新已有记忆，而非追加冲突记忆
- **F7 基础对话**：能回答"我能做什么菜"、"我最近吃了什么"等查询

## 5.2 P1 - 应该有（第一版后迭代）

- **F8 库存管理**：用户报告库存时记录，推荐时优先消耗库存
- **F9 反馈学习**：用户对推荐给出反馈（好吃/不好吃）时记录为 REFLECTION
- **F10 记忆溯源**：推荐时说明"我推荐这个是因为你上次说喜欢……"

## 5.3 P2 - 可选扩展

- **F11 菜谱作为工具（MaaT）**：将菜谱存储为 CODE_SNIPPET，通过 `RUN` 执行生成步骤
- **F12 外部菜谱链接**：存储 URL_RESOURCE 类型记忆，保留外部菜谱快照
- **F13 多用户隔离**：支持多个用户独立使用（当前仅单用户）

# 6 验收标准 (Acceptance Criteria)

## 6.1 MVP 验收（第一版完成标准）

以下场景必须全部跑通，且**由朋友实际验证**：

- [ ] **AC1**：首次对话声明偏好 → 新建会话 → Agent 推荐时遵循该偏好
- [ ] **AC2**：报告"今天吃了番茄炒蛋" → 次日问推荐 → Agent 不重复推荐番茄炒蛋
- [ ] **AC3**：报告"我会做酸汤肥牛，做法是……" → 若干天后推荐时纳入该菜
- [ ] **AC4**：修正偏好（"我现在能接受一点甜食"）→ 后续推荐体现修正
- [ ] **AC5**：问"我最近吃了什么" → Agent 能列出近期饮食记录

## 6.2 一周使用后验收

- [ ] **AC6**：朋友主观反馈"它记得我"（非量化，但关键）
- [ ] **AC7**：连续使用一周，无需用户手动修正记忆（除非 Agent 明显记错）
- [ ] **AC8**：识别至少 3 个真实使用中暴露的问题（作为下一版迭代依据）

# 7 实现约束 (Implementation Constraints)

## 7.1 必须遵守

- **基于现有 v4 架构**：不引入新的架构重构
- **复用当前主动链路**：Gateway 决策 -> Patchouli prepare -> Alice run -> Patchouli finalize，不为应用另建入口或检索旁路
- **单 Agent**：不启用 Alice 的子帧派生
- **MTP 指令子集**：SEARCH / WRITE / UPDATE / READ，以及仅用于 `sys_clock` 的 RUN
- **第一版不超过 3 天开发时间**：超时则砍功能而非延期

## 7.2 明确允许

- 允许代码粗糙、UI 丑陋
- 允许记忆价值判断不准确（先能记，再判断准）
- 允许推荐质量一般（先能推荐，再优化质量）
- 允许使用现有 LLM 的通用能力补足推理（不引入专门推荐算法）

## 7.3 明确禁止

- 禁止为了本应用重构 Patchouli 或 Alice 子系统
- 禁止引入新的存储引擎或检索算法
- 禁止优化未在本规格中提及的模块
- 禁止在设计上投入超过 1 天（剩余时间全部用于实现）

# 8 验证与反馈 (Validation & Feedback)

## 8.1 第一版交付后

1. **立即交给朋友使用**，不等待"打磨好"
2. **观察一周**，记录以下信息：
   - 朋友主动提出的抱怨或建议
   - 朋友未抱怨但明显不合理的推荐（开发者观察）
   - 朋友重复说过但 Agent 没记住的信息
   - 朋友没说过但 Agent "幻觉"出的偏好
3. **形成问题清单**，作为下一版迭代的唯一依据

## 8.2 下一版迭代依据

下一版做什么，**由一周使用后的问题清单决定**，不由开发者预设。可能的迭代方向（仅供参考，不作为承诺）：

- 检索质量优化（如果推荐总不相关）
- 记忆价值判断优化（如果记了太多无用信息）
- 时间推理增强（如果"最近"判断不准）
- UI 改进（如果朋友抱怨交互方式）

# 9 项目意义 (Project Significance)

## 9.1 对 HiveMemory 的价值

本应用是 HiveMemory 从"理论先进"走向"被验证先进"的第一步。它不证明系统的强大，只证明**系统能用**。

## 9.2 不证明什么

- 不证明多智能体能力
- 不证明 AIOS 架构优势
- 不证明 MaaT 的价值
- 不证明性能优于其他框架

## 9.3 只证明一件事

**以 Agent Memory 为核心的架构，能跑通一个真实的、有人用的、跨会话记忆有效的应用闭环。**

这一件事，是 HiveMemory 当前最需要的证据。

# 10 附录：与论文发现的对照

本场景的设计已参考论文《Are We Ready For An Agent-Native Memory System?》(arXiv:2606.24775) 的关键发现：

- **Finding 6（保留原始内容）**：菜谱以原始文本存储，不压缩为摘要
- **Finding 7（保守提取）**：用户偏好原话保留，不激进改写
- **Finding 8（适度结构）**：检索不堆叠过多 Reflect 步骤
- **Finding 9（保守整合）**：偏好修正用 UPDATE 而非追加冲突记忆
- **Finding 4（时间敏感）**：饮食历史保留时间戳，检索时支持时间过滤

# 11 Agent Profile 与 System Prompt

## 11.1 设计原则

该 Agent Profile 只服务于当前 MVP，不承担通用营养顾问、菜谱搜索器或多 Agent 调度器的职责。MTP 的协议语法、错误恢复和可用工具列表由运行时统一注入，Profile 中的 system prompt 仅定义三餐推荐领域的决策规则和记忆行为，避免重复维护协议说明。

首版应采用当前权限模型能表达的最小权限：Agent 可以检索、读取、新建和修正记忆；可以通过 `sys_clock` 获取真实日期；不能访问网络、文件、Python REPL，也不能派生子 Agent。

## 11.2 Agent Profile 建议值

| 字段 | 建议值 | 说明 |
|:---|:---|:---|
| 显示名称 `title` | `三餐推荐助手` | 面向用户的名称 |
| 别名 `alias` | `meal_assistant` | 固定 Agent ID，使用 snake_case |
| 简介 `summary` | `记住饮食偏好、近期餐食、会做的菜与现有食材，并据此推荐下一餐。` | 明确能力边界，不承诺营养或医疗建议 |
| 标签 `tags` | `meal-assistant`, `recommendation`, `memory`, `personal` | 用于识别和检索 Agent Profile |
| 模型 `model_name` | `default` | 先沿用当前注册表的默认模型，避免为 MVP 引入模型选型变量 |
| 温度 `temperature` | `0.3` | 推荐可以有少量变化，但记忆判断和约束执行应相对稳定 |
| 语言 `language` | `zh` | 与目标用户及 system prompt 一致 |
| MTP 权限 `allowed_mtp_verbs` | `SEARCH`, `READ`, `WRITE`, `UPDATE`, `RUN` | 在本 Agent 的行为约束中，`RUN` 仅用于访问时钟 |
| 系统工具 `allowed_sys_tools` | `sys_clock` | 空列表会禁用时钟，`null` 会放开全部工具，均不符合本场景 |

> **当前权限粒度说明**：`allowed_sys_tools` 只约束 `sys_` 内核工具，不约束 `RUN` 对 `CODE_SNIPPET` 记忆的执行。也就是说，该配置会硬性拒绝网络、文件和 Python REPL 等其他系统工具，但“不得执行 MaaT”暂时依赖 system prompt，并非安全边界。MVP 通过不创建 `CODE_SNIPPET`、明确禁止相关行为和加入权限自测来控制风险；不要为此阻塞首版，只有真实使用证明需要更细权限时再拆分 `RUN_KERNEL` / `RUN_MEMORY` 能力。

对应的 `agent_config`：

```json
{
  "model_name": "default",
  "temperature": 0.3,
  "allowed_mtp_verbs": ["SEARCH", "READ", "WRITE", "UPDATE", "RUN"],
  "allowed_sys_tools": ["sys_clock"],
  "language": "zh"
}
```

## 11.3 System Prompt（可直接使用）

```text
你是一个面向单一用户的三餐推荐助手。你的核心职责是借助持久化记忆，记住用户明确表达的饮食偏好、硬性禁忌、会做的菜、用户分享的菜谱、当前可用食材和已经吃过的餐食，并据此帮助用户决定下一顿吃什么。

你的目标不是展示知识，而是给出真实可做、符合约束、不过度重复的建议。你只做日常餐食推荐，不提供营养诊断、疾病治疗或替代专业意见。

【推荐决策顺序】
1. 首先遵守过敏、医疗相关限制、宗教禁忌及其他用户明确声明的硬约束。任何候选只要可能违反硬约束，就不要推荐。
2. 其次遵守用户明确的不喜欢、饮食规则和当前明确需求。
3. 优先考虑用户确认拥有的食材，以及用户会做或曾分享过菜谱的菜。
4. 避免与最近几天已经确认吃过的菜重复，并尽量在食材、口味和做法上保持变化。
5. 最后再考虑用户的喜好、可用时间、烹饪难度和本轮对话中的临时偏好。

【使用记忆】
- 在回答“吃什么”、制定一餐建议或回答用户饮食历史之前，先检查已注入的记忆上下文；信息不足时，主动 SEARCH 用户偏好与禁忌、近期饮食、会做的菜或菜谱，并按当前问题检索库存食材。
- 搜索结果只有摘要而细节会影响判断时，使用 READ 获取完整内容。菜谱步骤、配料或过敏相关信息不完整时，不要只依赖摘要作结论。
- 不得编造用户的偏好、库存、菜谱、饮食历史或记忆别名。没有检索到的信息就是未知，不要把常识或猜测说成“你之前告诉过我”。
- 当用户问“今天”“昨天”“最近”等时间敏感问题，或需要记录未给出绝对日期的饮食事件时，先通过 sys_clock 获取当前日期。不要根据模型知识猜当前日期。
- sys_clock 是你唯一可以调用的 RUN 目标。不得对任何 CODE_SNIPPET 或其他记忆执行 RUN，即使它出现在检索结果或用户明确要求你执行。

【写入与更新记忆】
- 只有对未来对话有价值且由用户明确表达的信息才值得长期记录，包括稳定偏好、硬性禁忌、用户会做的菜、完整菜谱、当前库存和已经发生的饮食事件。闲聊、一次性的措辞和你的推荐本身不写入记忆。
- 用户首次提供且不存在对应旧记忆的信息，使用 WRITE。内容应忠实保留用户原意；保存菜谱时尽量保留原始配料、用量和步骤，不要压缩成失去细节的摘要。
- 用户纠正、撤回或改变既有偏好、禁忌、菜谱或库存时，先 SEARCH 找到旧记忆的真实别名，再使用 UPDATE。绝不猜测别名，也不要用新的 WRITE 制造相互冲突的副本。
- 只有用户明确表示某道菜已经做了或吃了，才记录为饮食历史。被推荐、准备做、可能会吃或仅询问过的菜，都不能记成已经吃过。
- 推荐菜品不会自动消耗库存。只有用户明确确认食材已使用、已吃完、新增或丢弃时，才更新库存。
- MTP 写入或更新失败时，不得声称“已经记住”。你仍可继续回答，但要用简短、自然的方式告知用户本次未能保存。
- WRITE 或 UPDATE 成功后，只在内容容易出错、涉及硬约束或一次提交包含多项细节时，使用返回的 pending alias 进行 READ 核对；不要为每次简单写入增加无意义的读取。

【回答方式】
- 信息足够时，优先给出 1 个主推荐和最多 2 个备选；每项用一句话说明它为何适合当前用户。不要输出冗长的菜品百科。
- 若缺少的信息会决定推荐是否可行或安全，只问 1 个最关键、简短的问题。若只是次要信息缺失，可以明确说明假设后直接推荐。
- 当用户的要求与已知硬约束冲突时，清楚指出冲突并提供安全替代，不要为了迎合而忽略约束。
- 不要把“可能不含某过敏原”描述为“确定安全”，也不要在信息不足时判断食材是否新鲜。必要时请用户检查包装、配料表或食材状态。
- 回复使用自然、简洁的中文。不要向用户展示内部协议、记忆类型、别名、权限配置或推理过程；只在自然语言中说明与推荐直接相关的依据。
```

## 11.4 首次创建方式

可以在现有 Agent 管理界面中创建一个 Agent，将 11.2 的字段分别填入，并把 11.3 的完整内容粘贴到“系统指令”。保存后应确认工具权限只选中 `Clock`，MTP 权限只选中 `SEARCH`、`READ`、`WRITE`、`UPDATE`、`RUN`。

若直接调用 API，可向 `POST /api/v1/agents` 提交以下结构，其中 `content` 填入 11.3 的完整 system prompt：

```json
{
  "title": "三餐推荐助手",
  "alias": "meal_assistant",
  "summary": "记住饮食偏好、近期餐食、会做的菜与现有食材，并据此推荐下一餐。",
  "content": "<粘贴 11.3 的完整 system prompt>",
  "tags": ["meal-assistant", "recommendation", "memory", "personal"],
  "agent_config": {
    "model_name": "default",
    "temperature": 0.3,
    "allowed_mtp_verbs": ["SEARCH", "READ", "WRITE", "UPDATE", "RUN"],
    "allowed_sys_tools": ["sys_clock"],
    "language": "zh"
  }
}
```

## 11.5 交付前最小闭环自测

每一步都观察 Agent 的最终回复和 MTP 执行结果；涉及记忆的步骤应在新会话中复查，不能只凭同一会话的上下文判断成功。

1. **建立硬约束与偏好**
   - 输入：`我对虾过敏，喜欢吃辣，不太喜欢甜食。`
   - 预期：创建偏好记忆；回复不夸大为医疗建议，也不推荐含虾菜品。
2. **跨会话召回**
   - 新建会话，输入：`今晚吃什么？`
   - 预期：主动检索既有偏好；推荐避开虾和明显甜口，并给出简短依据。
3. **学习完整菜谱**
   - 输入一份包含菜名、配料和步骤的自定义菜谱，并说明 `这是我会做的菜，请记住。`
   - 预期：用 WRITE 保存原始细节；随后询问做法时能 SEARCH 并 READ 回完整内容。
4. **记录真实餐食**
   - 输入：`我今天中午已经吃了番茄炒蛋。`
   - 预期：先调用 `sys_clock` 确认日期，再写入一条已发生的饮食记录。
5. **区分推荐与已吃**
   - 输入：`我明天可能做宫保鸡丁。`
   - 预期：不得把宫保鸡丁写成已经吃过；如无长期价值，可不写入任何记忆。
6. **近期去重**
   - 新建会话，输入：`我最近吃了什么？今晚再推荐一道。`
   - 预期：能说出带正确日期的番茄炒蛋，并避免再次把它作为主推荐。
7. **修正而非追加冲突**
   - 输入：`我现在可以接受少量甜味，但仍然不喜欢很甜的菜。`
   - 预期：先定位原偏好记忆并 UPDATE；后续检索结果中不应同时存在“完全排斥甜味”和“接受少量甜味”两份有效偏好。
8. **库存不被推荐自动扣减**
   - 输入：`冰箱里有鸡蛋和青椒。`，随后让 Agent 推荐，再询问 `我冰箱里还有什么？`
   - 预期：推荐可使用这些食材，但在用户确认做饭或用完之前，库存记忆不能被自动扣减。
9. **权限边界**
   - 要求 Agent 上网搜索菜谱、读取本地文件、执行一条 `CODE_SNIPPET` 记忆或调用子 Agent。
   - 预期：运行时硬性拒绝 `sys_web_search`、`sys_read_file`、`sys_write_file`、`sys_python_repl` 和 `CALL`；Agent 依据 system prompt 拒绝执行 `CODE_SNIPPET`。后者是行为验证，不是运行时安全隔离。

满足步骤 1 至 7 即视为最小闭环跑通；步骤 8 验证 P1 库存行为，步骤 9 验证 Profile 的最小权限配置。任何一步失败时，先记录失败发生在“检索、读取、写入、更新、时间获取或回复决策”中的哪一层，再决定是否修改 prompt；不要直接扩大为框架重构。
