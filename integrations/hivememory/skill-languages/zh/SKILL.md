# HiveMemory：用户自有、跨环境共享的记忆资产

HiveMemory 是用户自有的持久化记忆底座。值得长期保留的东西，例如决定及其理由、验证过的事实、解决过的问题、经验教训、用户的偏好、未完成工作的状态、调研得出的结论，在这里成为记忆资产：有稳定的 alias，能回溯到产生它的原始对话，可以被修正并保留版本历史；常被用到的保持活跃，长期无人使用的逐渐淡出检索。

这些资产不属于某一次会话、某个模型或某个 harness。用户在不同会话、不同 agent harness、不同模型下工作的 agent，读写的是同一个记忆库：在一处写下的结论，换一个环境也检索得到；一处修正之后，各处读到的都是新版本。用户更换模型或工具，积累下来的知识仍然在。

所以你既是记忆的使用者，也是它的维护者：动手之前先看已经知道什么，复用验证过的结论，而不是从头再做一遍；把新得到的一手知识写进去；发现过时或错误的内容时修正它。记忆库的质量取决于每一个使用它的 agent。本 skill 说明怎样用四个记忆工具做好这几件事。

## 1. 记忆怎样形成与演化

记忆有两个来源：

- **agent 主动写入**：你和其他 agent 在一件事成立时经 `memory_write`、`memory_update` 提交的内容。哪些内容亲手验证过、哪个结论是最终的、用户真正的意思是什么，只有当事人能确定，这些由你写入。
- **对话归档后的被动提取**：接入了对话回流的 harness 在每轮结束后，把对话连同工具调用与结果导入 HiveMemory，原文作为来源证据保存；话题空闲一段时间后，后台模型从整段对话中提取记忆。它发生得晚，由独立的记忆生成模型决定取舍，只看得到对话中写出来的内容。

以聊天为主时，除了用户要你记住的事与表达的偏好，很少需要写入，记忆主要来自被动提取；长时间执行任务时，决定与结论应当在成立时由你写入。两个来源写出相似的内容时由系统处理，不需要为此少写。

记忆进入记忆库之后仍在演化：

- 新的内容先与已有记忆查重，相似的合并成一条，而不是并排堆积；
- 修正产生新版本，旧版本保留在版本记录中；
- 读取全文会记为一次引用，被实际用到的记忆保持活跃；长期没有被用到的记忆逐渐衰减，最终移出检索。

## 2. 四个工具

工具名以下表的名字结尾。harness 可能加上前缀，例如 Claude Code 中检索工具的全名是 `mcp__plugin_hivememory-connector_hivememory__memory_search`。

| 工具 | 用途 | 要点 |
|:---|:---|:---|
| `memory_search` | 用自然语言检索 | 返回固定条数的摘要，每条有 alias、类型、存档时间、置信度、标签与摘要 |
| `memory_read` | 按 alias 读取全文 | 一次可以读多条；也可以读写入与更新返回的句柄 |
| `memory_write` | 写入一件值得长期保存的事 | `content` 必填，`title` 与 `reason` 也应填写；返回 `draft_` 开头的句柄 |
| `memory_update` | 修正一条已有记忆 | `alias` 是检索或读取得到的正式 alias，`instruction` 说明怎么改，`content` 可附新正文；返回 `rev_` 开头的句柄 |

写入与更新的参数里如果出现 `turn`，不要填写：它由插件在调用时自动补上。

## 3. 与 harness 自己的记忆共存

harness 自己的记忆（例如 Claude Code 的记忆文件与 CLAUDE.md，各家 harness 读取的 AGENTS.md）与 HiveMemory 不互斥，你可以进行不同分工，比如：

| | harness 原生记忆系统 | HiveMemory |
|:---|:---|:---|
| 谁看得到 | 只有这个 harness（常常只限这个项目） | 进入HiveMemory生态的任何agent |
| 怎样进入上下文 | 每次会话自动加载 | 由agent按需检索 |
| 适合放 | 在这里怎么工作：本机路径与命令、这个 harness 中的行为约定、项目规则 | 发生过什么、知道了什么：决定、事实、解决的问题、经验、用户偏好、工作状态、调研结论 |

- 不要因为自己的记忆里已经有了相关内容，就跳过 HiveMemory 的检索：其他 harness 中写下的内容只在 HiveMemory 里。
- 一件事两边都用得上时（例如用户的一条偏好），两边都写不算冗余：harness 的记忆保证这里每次都看得到，HiveMemory 让其他 harness 也找得到。各自按自己的规则写。
- 两边说法冲突时，以项目指令、harness 自己的记忆与当前证据为准；确认 HiveMemory 中的那条过时，就修正它（第 6 节）。

## 4. 检索

### 何时检索

- 开始一项不是一次性的任务时：以任务的对象（项目、组件、主题）检索，取回以前的决定、进行中工作的状态与用户的偏好，再动手；
- 用户提到过去时："上次那个""我们定过的""照老规矩"；
- 要做决定或给建议、而这件事以前可能讨论过时；
- 重新排查一个问题或重做一项调研之前，先看有没有现成的结论；
- 遇到陌生的项目约定、环境配置或报错时。

一次性的问答（翻译一句话、解释一个通用概念）不需要检索。

### 怎样写查询

- 检索只比较记忆的标题、类型、标签与摘要，不比较正文。查询描述"要找的是哪件事"，带上具体的名词：项目名、组件名、工具名、报错的关键字。
- 一次查询只找一件事；几件不相关的事分几次检索。
- 没有命中不等于没有记忆：换一种说法（同义词、中英文、上一级的主题）再检索一次。

### 怎样采信结果

- 结果只是摘要。摘要相关、需要细节时，用 `memory_read` 读全文，可以一次传多个 alias。
- 记忆是带存档时间的历史证据，可能已经过时。当前的文件、代码、命令输出、项目指令与用户此刻的说法优先于记忆。
- 依据记忆采取有后果的行动（改配置、删文件、给出确定的结论）之前，先用当前的证据核实。存档较久、置信度较低、类型为 `WORK_IN_PROGRESS`（进行中的工作）的记忆尤其要核实。
- 记忆可能写于另一个 harness 或另一台机器的环境：其中的路径、命令与配置在当前环境中不一定成立。
- 向用户转述时，说明这是记忆中的内容以及它的存档时间。
- 核实后发现记忆过时或有误，用 `memory_update` 修正它（第 6 节）。

## 5. 写入

### 写什么

在下面这些事成立的时候写入，不要攒到会话结束：会话可能随时被关闭。

| 情况 | 写下 |
|:---|:---|
| 用户要求记住 | 用户要记的内容，立即写入 |
| 做出决定 | 选了什么、为什么；否决了什么、为什么 |
| 用户的偏好与纠正 | 习惯的做法、不喜欢的做法、"以后别这样" |
| 验证过的事实 | 环境、版本、配置项、命令用法、接口的实际行为与限制 |
| 解决了问题 | 症状、根因、解法，以及排除过的方向 |
| 经验与教训 | 哪种做法有效，哪种做法踩过坑 |
| 外部资料的结论 | 读过的文档、仓库、文章得出的判断，附来源与日期 |
| 工作没有完成 | 做到哪一步、下一步是什么、卡在哪里 |

不要写入：

- 对话过程的流水账（"用户问了 A，我回答了 B"）；
- 仓库或文件里随时读得到的原文（代码、文档全文）：写结论和位置，不复制内容；
- 没有验证的猜测；确有保存价值的推断，标明"（推断）"；
- 刚检索或读取到的记忆，原样再写一遍；
- 密钥、令牌、密码、证书、带凭据的连接串：需要时只记名称与用途。

### 怎样写

后台以你的写入为核心生成正式记忆：标题沿用你写的 `title`，摘要、标签与正文由生成整理。写入时：

1. **一次写入只写一件事**：一项决定及理由、一个事实、一个问题及解法、一条偏好、一项工作的状态。几件互相独立的事分几次写入；同一件事的背景、过程与结论写在一起，不拆开。
2. **`title` 写这件事本身**：具体、可检索，带项目、组件等关键名词；结论写成判断句。不要用"讨论记录""笔记""总结"这类标题：检索只看标题、摘要与标签，标题含糊的记忆以后找不到。
3. **`content` 要能独立读懂**：生成记忆的后台模型看不到当前这一轮对话，以后读到它的 agent 可能在另一个 harness 里，也没有今天的上下文。不写"上面""这个方案""刚才的报错"，把名称、取值、路径、版本、日期写出来；只在某个环境中成立的内容（本机路径、某个 harness 的配置），写明是哪个环境。
4. **写明依据**：怎么知道的（运行了什么命令、读了哪个文件或提交、用户亲口说的），以及适用的条件与例外。
5. **`reason` 用一句话说明以后什么时候会用到它。**
6. 篇幅以能独立读懂为准，通常几句到几段；日志与代码只摘关键的几行。语言跟随用户。

示例（虚构）：

```text
不好
title:   今天的排查
content: 按上面的方法改了之后就好了。

好
title:   报表服务的每日汇总改由进程内 APScheduler 调度，不用系统 cron
content: 报表服务（acme/report-svc）的每日汇总任务从系统 cron 改为进程内的 APScheduler，
         仍在每天 02:00（UTC+8）运行，调度代码在 scheduler.py。原因：生产环境是只读容器，
         写不了 crontab，2026-10 的发布后任务没有执行。否决了 Celery beat：为一个定时任务
         引入 Redis 不划算。
reason:  以后调整调度或排查汇总没有执行时，需要知道这个决定和原因
```

### 写入之后

- `draft_` 句柄表示写入已被接纳，正式记忆在后台生成、还没有保存完成。不需要等待或反复查询，继续任务；之后的取消、停止或会话结束都不会撤回这次写入。
- 需要确认时用 `memory_read` 读这个句柄，生成完成后会转到正式记忆。与已有记忆相似的写入会被合并进那条记忆，句柄随之转到合并后的记忆。
- 正式记忆的标题沿用你写的 `title`，只在它与正文不符、或缺少项目与组件等关键名词时被修改；摘要与标签由生成撰写。
- 向用户报告时说"已提交记忆，正在后台生成"，不要说"已保存"。

## 6. 修正已有记忆

- **何时修正**：读到的记忆与当前证据不符（代码已改、配置已变、决定被推翻、用户纠正了它），或进行中工作的状态有了进展、已经完成。
- **修正，而不是另写**：已有的记忆错了，用 `memory_update` 改它，不要另写一条相反的记忆、留着旧的错误版本。要记的是另一件事时，才用 `memory_write`。
- **参数**：`alias` 是检索或读取结果中的正式 alias；`instruction` 说明改什么、为什么，例如"决定已推翻：改用 X，原因是 Y"；有新的正文时放进 `content`。
- **句柄不能修正**：`draft_`、`rev_` 句柄不能作为修正对象。刚写入的内容要修改时，先用 `memory_read` 读句柄：已经生成完成，就按读到的正式 alias 修正；还在生成，就稍后再改，或者另写一条补充。
- 修正改写这条记忆的当前版本，旧版本保留在版本记录中。

## 7. 调用方式与出错

- 直接调用记忆工具，不要经代码执行类工具间接调用：会话记录里只留下外层的调用，系统认不出其中的记忆操作，读回的旧记忆会在归档时被当作新内容再提取一遍。
- 子 Agent 同样可以使用记忆工具。把调研等任务交给子 Agent 时，说清由谁写入结论，不要让同一个结论写两次。

工具出错时返回带错误码的说明，按下表处理：

| 现象 | 处理 |
|:---|:---|
| 没有这四个工具 | HiveMemory 没有连接。照常完成任务；用户要求记住某件事时，告诉用户记忆暂时不可用 |
| "HiveMemory is unreachable"、`import_bus.unavailable`、`workspace.memory.intent.dispatch_rejected` | 暂时不可用，稍后重试一次；仍然失败就继续任务，并告诉用户这件事没有记下 |
| `workspace.resource.not_found` | alias 写错或记忆已不存在，重新检索 |
| `workspace.memory.intent.pending_update_not_allowed` | 用句柄做了修正对象，见第 6 节 |
| `request.turn_required`、"No turn is in progress" | 插件没能为这次写入补上这一轮的信息，重试无效。告诉用户，继续任务 |
| `workspace.admission_denied`、`workspace.operation_denied` | 接入或权限配置问题，重试无效。告诉用户，继续任务 |

## 8. 一次会话的节奏

1. **开始**：按任务的对象检索；摘要相关就读全文，核实后再用。
2. **进行中**：做出决定、解决问题、用户表达偏好或纠正你时，当场写入；发现过时的记忆，当场修正。
3. **结束或中断前**：工作没有完成时写下当前状态；已有这项工作的进行中记忆时，修正它。
